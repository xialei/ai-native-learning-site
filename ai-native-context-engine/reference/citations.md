## 1. 第 0 章 概述 / 全书主线 —— 论文论点 = 本书论点的学术背书

### 引用点 A：harness 不改模型也能大幅提升表现（最强动机证据）
- **论文出处**：§1 Introduction，页 4。
- **原文要点**：
  - Bölük (2026) 修改 edit-tool 格式与周边 tool harness，横跨 15 个模型，编码基准上获得显著增益，其中一个模型提升高达 **10×**。
  - Trivedy (2026) 在固定 GPT-5.2-Codex 上，仅靠"重构系统提示 + 中间件注入上下文 + 自验证钩子"，把 Terminal-Bench 2.0 从 **52.8% 提到 66.5%**。
  - Meta-Harness (Lee et al., 2026) 进一步证明 harness 的部分组件可以**自动优化**。
  - 论文同时诚实声明：最强受控证据目前来自编码 agent 基准，尚不能证明"在所有场景下 harness 都比模型更重要"，但足以说明 agent 性能"jointly 依赖模型与执行系统"。
- **建议引用方式**：放在第 0 章"瓶颈从模型转向 Context"的论证处，作为"这不是本书一家之言"的证据。措辞示例：
  > 近期综述（Li et al., 2026）援引受控实验指出，在模型权重不变的前提下，仅改造工具格式与上下文中间件，编码 agent 的 Terminal-Bench 2.0 通过率从 52.8% 提升到 66.5%；个别模型在编码基准上提升可达 10 倍。这说明 agent 的可靠性天花板，并不只由模型决定。
- **引用价值**：直接为本书核心命题提供同行评议级的量化证据，把"观点"变成"有出处的论断"。务必保留论文自己的限定（"最强证据来自编码场景"），避免夸大。

### 引用点 B：prompt → context → harness 三段演进
- **论文出处**：§2.2，页 6。
- **原文要点**：论文区分三圈递进——
  - **Prompt engineering**：塑造单次模型调用的输入（指令、示例、输出格式）。
  - **Context engineering**：管理模型在多步执行中每一步可见的完整信息状态，把上下文窗口当作"主动管理的资源"而非"被动对话记录"。
  - **Harness engineering**：把设计单元扩大到围绕模型调用的闭环系统，协调 prompt/context 与执行环境、工具接口、持久状态、生命周期、可观测、验证、治理。
  - 论文强调：harness engineering **不替代**前两者，而是把它们整合进一个更广的、保证执行"有界、可观测、可验证、可恢复"的运营过程。
- **建议引用方式**：作为全书主线的学术坐标。措辞示例：
  > 学术界已用三段式概括这条路径：prompt engineering → context engineering → harness engineering（Li et al., 2026）。本书的 Context Engine 正落在 context engineering 这一段，并向上触及 harness 的运行时与治理边界。
- **引用价值**：把本书自我定位的"Context Engine"放进公认的演进谱系里，读者一眼能看清本书位置。

## 3. 第 4 章 Hybrid Retrieval —— "信息放置与信息存在同样重要"

### 引用点 E：U 型注意力曲线（Lost in the Middle）
- **论文出处**：§5.1，页 19；引 Liu et al. (2024a)。
- **原文要点**：在 20 篇文档的多文档问答中，当相关文档位于上下文**中间**时，准确率比放在首尾下降超过 **30%**。该 U 型曲线跨模型、任务、上下文长度成立，即便专为长上下文训练的模型亦然。结论：**信息放置与信息存在同等重要**。
- **建议引用方式**：第 4 章论证"为什么 Hybrid Retrieval 之后还要 Ranking/重排"时引用——检索到≠放对位置。措辞示例：
  > 文献表明检索到正确内容还不够：当相关段落落在上下文中段时，准确率比置于首尾下降逾 30%（Liu et al., 2024a，转引自 Li et al., 2026）。这正是检索之后必须排序与压缩的原因。
- **引用价值**：为"检索→排序→优化"三段分工提供硬证据，而非仅靠工程直觉。

### 引用点 F：context rot（上下文腐烂，退化远早于窗口填满）
- **论文出处**：§5.1，页 19–20；引 Hong et al. (2025)。
- **原文要点**：Hong et al. 评测 18 个前沿模型（含 GPT-4.1、Claude Opus 4、Gemini 2.5、Qwen3），在隔离输入长度与任务难度的受控条件下，**每个模型都随输入增长而退化**；退化非均匀、与任务相关；语义模糊查询退化更陡；退化在窗口填满前很早就开始——"一个标称 200K 的模型可能在 50K 就出现明显性能下降"。论文称之为 context rot，并指出这是"任何累积工具结果、中间推理和文件内容的 agent 的正常工况"。
- **建议引用方式**：第 4/7 章论证"不能靠堆上下文解决问题"时引用。措辞示例：
  > 所谓 context rot（Hong et al., 2025）表明，模型退化远早于上下文窗口填满：标称 200K 的模型在 50K 即可出现显著下降。这意味着 Context Engine 的职责不是"把窗口塞满"，而是"给每一步刚好够用的高信号 token"。
- **引用价值**：量化反驳"窗口大就不需要管理"的常见误解。

## 4. 第 5 章 Graph Expansion —— "相关性在写入时未必可见"

### 引用点 G：A-MEM 与"写入时不可知的相关性"
- **论文出处**：§5.5.2，页 23。
- **原文要点**：A-MEM（Xu et al., 2026b）借鉴 Zettelkasten，为每条记忆生成带关键词、标签、描述和动态链接的结构化笔记；新记忆加入时，会**回溯更新**已有相关笔记的上下文与属性，让记忆图随知识积累而演化。论文点明这解决了一个检索系统的根本限制：**一条已存记忆的相关性，在写入时未必可见，往往要等到与后续信息对照后才能判定**。
- **建议引用方式**：第 5 章论证 Graph Expansion（尤其"多跳扩展/事后补边"）的必要性时引用。措辞示例：
  > 记忆系统研究（A-MEM, Xu et al., 2026b）指出一个根本限制：一条事实的相关性在写入时未必可见，只有在与后续信息对照后才显现。这正是 Graph Expansion 需要"动态补边、回溯连接"而非"一次性静态建图"的原因。
- **引用价值**：把本书"图扩展"设计的动机，锚定到学术界对记忆图演化的同类判断上。

### 引用点 H：observation–reflection–retrieval 三元组（扩展/反思的标准模板）
- **论文出处**：§5.5.1，页 22；引 Park et al. (2023) Generative Agents。
- **原文要点**：Memory Stream 存储带时间戳和重要性分数的观察；检索综合 recency、importance、relevance 三信号；reflection 周期性把观察合成更高层洞察。消融显示三者各自独立贡献行为质量，缺一即退化。论文称该三元组"仍是 agent 记忆设计的标准模板"。
- **建议引用方式**：第 5 章讲扩展策略（如"重要性打分""时效衰减""反思式合并"）时引用作设计依据。
- **引用价值**：为本书的 6 种扩展策略提供学术原型参照。

## 5. 第 6 章 Context Ranking —— "给最小的、高信号的 token 集"

### 引用点 I：context engineering 的核心原则
- **论文出处**：§5.2，页 20；引 Anthropic applied AI team 与 Karpathy (2025)。
- **原文要点**：Anthropic 把 context engineering 定义为"策划并维护推理时最优 token 集的策略集合"；由此原则是"**在每一步找到使期望结果概率最大化的、最小的高信号 token 集**"。该原则驱动本节所有技术：progressive disclosure（按需加载）、compaction（清理已用 token）、memory retrieval（只取最相关记录）。
- **建议引用方式**：第 6 章 Ranking 的目标函数处引用。措辞示例：
  > Ranking 的目标可以一句话概括：在每一步选出"使正确结果概率最大化、且最小的高信号 token 集"——这正是学术界对 context engineering 的核心定义（Li et al., 2026 引 Anthropic）。
- **引用价值**：把本书 Ranking 的"选什么"问题，挂到公认的工程原则下。

### 引用点 J：Set Cover 与"覆盖-成本"的学术同构
- **论文出处**：§5.3 token-efficient tool design + §7.3 cost tracking，页 20–21/30。
- **原文要点**：工具定义是上下文消耗大户，每个 schema/名称/描述/参数类型每次调用都注入；大批工具可在 agent 读到用户请求前就消耗数万 token。原则是"**少而精的工具优于大而全的菜单**"——若人类工程师都说不清某场景该用哪个工具，就别指望模型做得更好。
- **建议引用方式**：第 6 章讲"选择即质量"、Set Cover 式覆盖-成本权衡时，用"少而精优于多而全"作旁证。
- **引用价值**：为本书"选择阶段决定上下文质量"提供来自工具层的同构证据。

## 6. 第 7 章 Context Optimizer —— 压缩 / Token 经济 / 按需加载的直接学术对应

> 第 7 章是本书与论文 §5 重合度最高的章节，可引用点最密集。

### 引用点 K：三层记忆 = 操作系统内存层级
- **论文出处**：§5.2 末 + §5.3–5.5，页 20–23。
- **原文要点**：三层记忆架构（active context window / session-level state / cross-session storage）已成为主流组织框架，**直接映射到操作系统的经典内存层级**，既提供直觉，也提供"把对的技术匹配到对的时间尺度"的词汇表。
- **建议引用方式**：第 7 章开篇讲"为什么压缩/分页是必要的"时引用。措辞示例：
  > 学术界已把 agent 的上下文按时间尺度分为三层——活动窗口、会话状态、跨会话存储，并明确指出其与操作系统内存层级的同构（Li et al., 2026）。本书的 Optimizer 正是这层"内存管理器"。
- **引用价值**：为本书"Demand Paging / Progressive Context"的 OS 类比提供学术背书。

### 引用点 L：MemGPT —— 把上下文窗口当 RAM、外部存储当磁盘
- **论文出处**：§5.5.1，页 22；引 Packer et al. (2023) MemGPT。
- **原文要点**：MemGPT 把 LLM 上下文窗口当 RAM、外部存储当磁盘，给模型显式 page in/out 的函数调用；与 OS 虚拟内存的类比"精确"——正如 OS 通过透明分页给应用"更大内存的幻觉"，MemGPT 给 LLM"更长上下文的幻觉"。
- **建议引用方式**：第 7 章 Progressive Context / Demand Paging 小节引用作设计原型。
- **引用价值**：本书的按需分页在学术上有明确对应物，不是自造概念。

### 引用点 M：compaction 的调参纪律——先最大化召回，再优化精度
- **论文出处**：§5.6，页 24；引 Team (2025a)。
- **原文要点**：compaction（压缩）要保留架构决策、未解 bug、实现细节，丢弃冗余工具输出和已被后续步骤吸收的中间推理。推荐调参方向：**先最大化召回**（从轨迹里捕获一切可能相关的内容），**再迭代提升精度**（删除多余）——不能反着来，因为"过早删掉的东西，后面需要时不可恢复"。最轻的压缩形式是 tool result clearing（把完整工具输出替换为路径引用）。
- **建议引用方式**：第 7 章压缩策略小节，作为"压缩方向不可逆、必须先宽后严"的工程纪律引用。
- **引用价值**：把本书压缩策略的取舍原则，锚定到实践报告的经验教训上。

### 引用点 N：sub-agent 上下文隔离的 token 经济学
- **论文出处**：§5.6，页 24；引 Anthropic (2025f)。
- **原文要点**：把子任务交给独立上下文窗口的 sub-agent，只向 orchestrator 回传 **1,000–2,000 token** 的精炼摘要；详细探索上下文隔离在 sub-agent 内。简单子任务可不共享上下文；复杂子任务需共享状态时则把 orchestrator 全量上下文传入——但**共享上下文很贵**：产生更大 prefill、且消除跨不同系统提示的 KV-cache 复用。该权衡须按任务类型显式做出。
- **建议引用方式**：第 7 章（以及第 13 章 Multi-Agent）讲"共享上下文 vs 隔离上下文"的 token 成本曲线时引用。
- **引用价值**：为本书"共享 Context vs 消息传递"的取舍提供量化量级（1–2K 摘要阈值、prefill/cache 代价）。

### 引用点 O：KV-cache 是生产 agent 最重要的单一指标
- **论文出处**：§5.3，页 21；引 Manus team (Team, 2025b)。
- **原文要点**：Manus 团队经五轮生产架构迭代后认定 **KV-cache 命中率是"生产级 AI agent 最重要的单一指标"**；Claude Sonnet 上缓存 token $0.30/MTok，未缓存 $3.00/MTok（10× 差距）。由此三条设计规则：①保持提示前缀稳定（开头差一个 token 就使其后全部失效）；②把上下文当 append-only（改写历史动作/观察会破坏复用）；③用确定性序列化（JSON 键序不稳会静默击穿缓存）。
- **建议引用方式**：第 7 章（与第 9 章 Cache）讲 Token 经济与缓存友好的上下文结构时引用。措辞示例：
  > 生产实践（Manus, Team 2025b）把 KV-cache 命中率列为"生产 agent 最重要的单一指标"：缓存 token 与未缓存 token 价格相差约 10 倍。这要求上下文结构必须前缀稳定、append-only、确定性序列化——Optimizer 的输出格式不是任意的。
- **引用价值**：把"压缩"从"省 token"升级为"保缓存命中"，是本书第 7+9 章衔接处的关键论据，且有真实单价数字。

## 7. 第 8 章 Context Runtime —— 生命周期状态与"上下文即受治理状态"

### 引用点 P：lifecycle 状态 ≠ context 层 ≠ observability 层
- **论文出处**：§6.1，页 25–26。

## 13. 贯穿全书：三个系统级权衡（可直接用作各章导言的引用骨架）

论文 §11 的三个 cross-layer 效应，几乎可作为本书多个章节导言的统一引用源：

| 论文权衡 | 含义 | 本书对应处 |
|---|---|---|
| **Cost-Quality-Speed Trilemma**（§11.1） | 更强评测/治理/可观测/执行保真→增成本与延迟；三者不可同时最优化 | 第 9/10 章、第 0 章原则 6 |
