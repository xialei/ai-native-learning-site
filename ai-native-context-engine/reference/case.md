# 企业案例补充指南（Case Study Playbook）

> 目标：给《AI Native Context Engine》补上**有说服力的企业案例**。
> 本文不写案例本身，而是告诉你在**哪里补、补什么要点、怎么写才更有说服力**。
> 配套红线：不编造。真实数据你来提供；若无，则标注「示意性推演」。

---

## 一、现状诊断：为什么现在没说服力

全书 15 章只有**两个假设场景**贯穿，且都是教学性的 worked example，不是 case study：

| 场景 | 出现章节 | 角色 | 缺什么 |
|---|---|---|---|
| AI 研发（Experiment / Dataset / GPU / MLflow） | ch3/4/5/6/7/8/10/11 | 教学例子 | 无真实公司、无规模、无效果指标 |
| 新能源风电（风电场 / 风机 / ERA5 / 工单） | ch0/6/12/13 | 教学例子 | 无真实公司、无规模、无效果指标 |

**缺的四样东西**（真实案例的标志）：

1. **真实公司名**——读者要知道是谁在用。
2. **真实规模**——数据量、QPS、用户数、Agent 数，证明系统扛得住。
3. **效果指标**——延迟降了多少、Token 省了多少、准确率提了多少、人力省了多少。**必须量化。**
4. **部署叙事**——怎么迁移的、踩了什么坑、分几期上线。

结果是：书现在是「设计书」气质，不是「实践书」气质。读者懂「该怎么设计」，但判断不了「落地后到底有没有用」。

## 二、说服力强的案例长什么样（通用模板）

每个案例按这个结构写，说服力最强。**七个部分，缺一不可**：

### 1. 背景与规模
- 谁在用（公司 + 行业）。
- 规模数据：多少数据源、多少对象、多少 QPS、多少并发 Agent、多少用户。
- 一句话让读者知道「这不是玩具系统」。

### 2. 痛点（量化）
- 上线前具体卡在哪。**能量化就量化**：
  - 「故障定位平均 4 小时」比「故障定位慢」强 10 倍。
  - 「40% 的工单需要人工翻 5+ 个系统」比「工单处理麻烦」强 10 倍。
- 痛点要和这一章的设计目标对应——这一章解决的就是这个痛。

### 3. 旧方案为什么不行（对照）
- 传统 RAG / 人工 / 消息传递，**具体**卡在哪一步。
- 这是全书最该有的「对照实验」：旧方案 vs Context Engine。
- 写清楚「为什么加更多文档/更大模型没用」——堵住读者「是不是换个更强的模型就行」的念头。

### 4. Context Engine 怎么解（流水线全链路）
- 一个具体问题进来，**完整走一遍流水线**：
  - Intent 判了什么 → 哪几个 Retriever 命中 → Graph Expansion 扩出什么对象 → Ranking 保留谁砍谁 → Optimizer 压成多少 Token → Agent 怎么答的。
- 这是案例的核心价值——把散在 15 章的设计，在一个真实问题上串成一条线。
- **关键点**：标出「哪一步是胜负手」。不是所有步骤都同等重要，案例要说清楚是检索赢的、还是扩展赢的、还是压缩赢的。

### 5. 效果指标（必须量化）
- 延迟、Token 成本、准确率/召回率、人力节省、响应时间。
- **给前后对比**：「故障定位 4h → 20min」「Token 成本 ↓ 60%」「命中率 62% → 89%」。
- 没有数字的案例=没有说服力的案例。

### 6. 踩坑（增加可信度）
- 真实部署一定踩坑。写 1-2 个：
  - Graph Hop 调太大导致爆炸、Cache 没失效导致脏数据、Policy Filter 误删关键对象、Streaming 延迟抖动……
- **踩坑反而加分**——它证明案例是真的，不是 PPT。完美无瑕的案例最不可信。
- 每个坑配「怎么解的」，呼应书里的设计原则。

### 7. 一句话：证明哪条设计原则
- 这个案例验证了第 0 章的哪条原则（Context 是产品 / Policy 是硬约束 / 阶段可观测 / ……）。
- 让案例和全书主线挂钩，不是孤立的炫耀。

## 三、具体在哪里补、补什么要点

按「投入产出比」排序。**强烈建议优先补 ch0、ch5、ch7、ch11/ch12 这四处**——它们分别卡在全书最需要证据的位置。

### 🔴 优先级 1：ch0 概述 —— 开篇动机案例
- **位置**：「为什么写这本书」一节，在讲完 RAG 痛点之后插入。
- **要点**：一个真实公司，因为 Agent 看不到跨系统的关系，导致过一次具体的业务事故/低效。一句话点出「不是模型不够强，是上下文不够」。
- **说服力杠杆**：开篇案例定全书基调。读者在前 3 分钟就被说服，后面才读得下去。
- **写法**：背景 → 事故经过 → 事后复盘发现「信息其实都在，只是 Agent 看不到关系」→ 引出 Context Engine。

### 🔴 优先级 2：ch5 图扩展 —— 胜负手案例
- **位置**：「为什么需要扩展」一节。
- **要点**：一个真实问题，传统 RAG / 纯检索答错或答不出，Graph Expansion 补全关系后答对。**这是全书最能体现 Context Engine 价值的章节**，必须有案例证明「扩展」不是锦上添花，是必需。
- **说服力杠杆**：用 before/after 对比——同样的对象集，扩展前 LLM 答什么，扩展后答什么。读者一眼看到差异。
- **写法**：问题 → 纯检索能拿到的对象（不够）→ 扩展出哪些对象（补全了关键链路）→ LLM 据此给出的答案 → 答案为什么对。
- **量化**：扩展前召回率 vs 扩展后；或「扩展前 60% 问题答不准 → 扩展后 85%」。

### 🔴 优先级 3：ch7 优化器 —— Token 经济性案例
- **位置**：「优化目标」或「Token Allocation」一节。
- **要点**：真实场景下，候选 Context 有多少 Token，压缩后多少，省了多少钱/提升了多少并发。**Token 是这本书唯一容易量化的成本指标**，最有说服力。
- **说服力杠杆**：直接给钱——「每月 LLM 成本从 ¥X 降到 ¥Y」或「同样预算下并发 Agent 数 ×3」。
- **写法**：压缩前 Token 数 → 压缩策略（哪些对象被摘要、哪些被合并）→ 压缩后 Token 数 → 换算成成本/吞吐。
- **注意**：别只说「省了 Token」，要说清楚「省了 Token 但信息没丢」（信息增益公式），否则读者会怀疑压缩牺牲了质量。

### 🔴 优先级 4：ch11 / ch12 领域插件 —— 行业落地案例
- **位置**：每章的「完整示例」一节，把现在的假设示例升级成真实案例。
- **要点**：ch11 补一个真实 AI 研发团队（模型为什么效果下降），ch12 补一个真实能源/制造企业（发电量为什么下降）。这是全书最贴近「企业」的地方，必须有真实公司背书。
- **说服力杠杆**：领域插件是商业化的核心卖点（ch14 商业化路径）。真实行业案例 = 可复制的样板，读者能想象「我这个行业也能这么干」。
- **写法**：行业背景 → 数据源现状（散落几个系统）→ 装了哪个 Context Plugin → 自动构建出什么 Object Graph → Business Agent 解决了什么具体问题 → 效果。

### 🟡 优先级 5：ch4 检索 —— Hybrid 必要性案例
- **位置**：「六类 Retriever」之后。
- **要点**：一个真实问题，证明单一检索搞不定，必须 Hybrid。比如精确设备编号（要 Keyword）+ 语义问句（要 Vector）+ 实时状态（要 Streaming）组合的问题。
- **说服力杠杆**：展示六类 Retriever 各自命中什么，缺一类就答错。

### 🟡 优先级 6：ch6 排序 —— 选择即质量案例
- **位置**：「Context Diversity」或「Explain」一节。
- **要点**：真实场景下，Top-N 全选高相关 Document 导致答错，引入 Diversity / Set Cover 后答对。证明「选择」比「检索」更影响最终质量。
- **说服力杠杆**：Explain 的真实输出截图——「为什么 GPU 进来了、为什么 README 被踢了」，这是可观测性的活广告。

### 🟡 优先级 7：ch10 可观测性 —— 排障案例
- **位置**：「为什么需要 Debugger」一节。
- **要点**：一次真实的线上翻车（Agent 引用了错误文档/没看到最新日志），靠 Trace + Explain 定位到是哪一步出的错，多久定位完。
- **说服力杠杆**：「出问题后 2 小时定位根因，而不是猜 3 天」。可观测性的价值在生产事故时才显现，案例正好捕捉这个时刻。

### 🟡 优先级 8：ch13 多 Agent —— 协作案例
- **位置**：「多 Agent 示例」一节。
- **要点**：真实的多 Agent 协作场景，对比「消息传递」和「共享 Context」两种方式的 Token 成本和一致性。
- **说服力杠杆**：共享 Context vs 消息传递，Token 成本曲线对比——消息传递随 Agent 数指数增长，共享 Context 是平的。

### 🟢 优先级 9：ch14 演进路线 —— 分期落地案例
- **位置**：Phase 1-4 某个阶段。
- **要点**：一个真实公司按 Phase 1 → 2 → 3 分期上线，每期交付了什么、几个月、客户反馈。
- **说服力杠杆**：证明路线图可行，不是纸上谈兵。「6 个月跑通 MVP」要有真实时间线背书。

## 四、可信度红线（不编造怎么操作）

这是最重要的约束。三条规则：

### 规则 1：真实数据 vs 示意性推演，明确标注
- **真实部署数据**：你提供的真实公司、真实指标。直接写「某新能源企业（脱敏）」+ 真实数字。
- **示意性推演**：基于源稿已有场景，合理推演的端到端流程。**必须标注**「以下为示意性案例，对象与指标为推演值」。
- 两种都可以用，但**绝不能把推演当真实**。读者一旦发现一个假数字，全书可信度归零。

### 规则 2：数字要有量纲和来源
- ❌「效率大幅提升」
- ✅「故障定位时间从平均 4.2 小时降至 23 分钟（基于上线后 3 个月 47 次故障样本）」
- 没有量纲的数字 = 没有数字。

### 规则 3：案例数量宜精不宜多
- 2-3 个**写透的**真实案例，胜过 10 个一笔带过的。
- 优先把 ch0、ch5、ch7 三个位置的案例写实写透，其他章节引用同一个案例的不同侧面即可（一个案例可以串联多章）。
- **最高效的做法**：选 1 个真实企业，写一个贯穿全书的主案例，在 ch0/ch5/ch7/ch12 分别展示它的不同环节。这样既省事，又前后呼应。

## 五、推荐的主案例架构（如果只做一个）

选一个真实企业，写一条贯穿全书的主案例线。建议结构：

| 章节 | 展示主案例的哪个环节 | 证明什么 |
|---|---|---|
| ch0 | 事故背景 + 痛点 | Context 比 Model 更卡瓶颈 |
| ch4 | 一次请求走了哪几路检索 | Hybrid 必要性 |
| ch5 | 扩展出关键关系链 | 图扩展是胜负手 |
| ch6 | Ranking 保留/砍掉哪些对象 | 选择即质量 |
| ch7 | 压缩前后 Token 对比 | Token 经济性 |
| ch10 | 出问题后怎么靠 Trace 定位 | 可观测性价值 |
| ch12 | 这个企业的领域插件落地 | 商业化可复制 |

**一个案例，七个证据点。** 这比每章硬造一个不同案例省力得多，而且前后呼应、可信度累积。

---

## 六、给写作者的话

1. 先从你手上有的真实素材里，挑**一个最完整的企业**作为主案例。
2. 把它的痛点、规模、旧方案、流水线、效果、踩坑六要素填满。
3. 按上面的章节映射表，把这个案例的不同环节插进对应章节。
4. 每个插入点控制在 200-400 字，不要长篇——案例是论据，不是主角。
5. 全书所有「示意性」内容统一加标注，真实内容标注来源（脱敏公司名 + 时间 + 样本量）。

补完这步，书就从「设计书」变成「有证据的设计书」——说服力质的飞跃。
