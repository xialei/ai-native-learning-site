第 3 章 · Knowledge Builder

知识从哪里来

Context Engine 再聪明，也救不了垃圾进、垃圾出。在检索、扩展、排序任何一步之前，得先有人把企业数据变成结构化的对象。这件事由 Knowledge Builder 负责——它是整个系统的入口，也是知识质量的源头。没有高质量的 Ontology，就不存在高质量的 Context。

为什么需要 Knowledge Builder

Knowledge Builder 是 Context Engine 的入口，也是 AI Knowledge Runtime 里最重要的模块。它的职责是持续从企业各种数据源中自动构建 Ontology。

理清一条因果链：Context Engine 决定 Agent 的智能水平；Retrieval 决定上下文质量；而 Knowledge Builder 决定整个系统的知识质量。三者的关系是上游决定下游——源头的水不干净，下游再怎么过滤也有限。

Knowledge Builder 决定整个系统的知识质量。没有高质量 Ontology，就不存在高质量 Context。

设计目标

先纠正一个常见误解：Knowledge Builder 的目标不是建知识图谱。它要建的是一个"AI 可以理解、推理、执行的业务世界"。这两者的区别在于——知识图谱往往止步于"实体和关系"，而这里的 Ontology 还要包含可执行的 Action、实时的事件、可量化的 Metric。

它必须满足六点：自动构建、增量更新、实时同步、可解释、可版本管理、可扩展。这六点对应的五条设计原则：

  • AI First——用 LLM 做抽取的主力，而不是纯人工标注；
  • Incremental First——增量更新优先，不做每天全量重建；
  • Streaming First——数据变化走流式，实时同步进 Ontology；
  • Schema Evolution——结构能演化，历史可重放；
  • Human-in-the-loop——关键环节有人审，不盲目信任模型输出。

总体架构

Knowledge Builder 的架构是一条从数据源到 Ontology Store 的流水线。数据从上面进来，经过 Connector 和 Normalizer 统一格式，进入 Builder 的各个 Extractor，最后经过校验和版本化入库。

数据源设计

Knowledge Builder 必须支持插件化数据源。建议统一一套 Connector Interface，让 Builder 不关心数据源长什么样。数据源分五大类：

类别示例
StructuredMySQL、PostgreSQL、Oracle、Hive、Iceberg、Paimon
StreamingKafka、Fluss、Pulsar
DocumentPDF、Word、Excel、Markdown
DevelopmentGit、Notebook、MLflow、Jenkins
RuntimeKubernetes、Prometheus、日志

所有 Connector 输出统一 Object——这是第 2 章定义的契约。无论数据来自关系库还是 Kafka 流，Normalize 之后都是同一种结构。这就是为什么第 2 章要把它定成"宪法"：Connector 的实现者只需要遵守一份契约。

Entity Discovery

目标是发现业务对象。看一段日志，人能一眼看出里面有哪些实体，但机器需要方法。比如这段：

Training started.
Dataset weather_v2
GPU H20

应该自动抽取出三个 Entity：Experiment、Dataset、GPU。

建议的做法是 Rule + LLM 混合抽取。这两者分工明确：

  • 规则负责高精度——正则、字段映射这些确定性的东西交给规则，它们不会幻觉；
  • LLM 负责高召回——非结构化文本里的隐式实体，交给 LLM 去捞。

Relation Discovery

Relation 比 Entity 难抽。因为关系往往不在文本里明写，而是需要推理。比如：

Experiment uses Dataset
Experiment deployed_on GPU
Model generated_by Notebook

输出是标准的三元组：

source: experiment
relation: uses
target: dataset

建议用 Graph Pattern + LLM 共同完成。Graph Pattern 利用已有的 Ontology 结构去匹配可能的关系模板，LLM 处理那些模板覆盖不到的隐式关系。

Event Discovery

企业知识里最容易缺失的就是事件。TrainingStarted、TrainingFinished、AlarmRaised、RepairCompleted——这些状态变化如果不抽出来，Context 就只能反映静态快照。

所有 Event 必须带四个字段：Timestamp（什么时候）、Actor（谁干的）、Object（作用在谁身上）、Status（结果如何）。有了这四个字段，就能构建事件时间线，支撑"为什么训练失败"这类时序分析。

Metric 与 Action Discovery

Metric 自动发现可量化指标：Loss、Accuracy、Latency、Cost、Temperature、Power、Wind Speed。统一成 Metric Object，支持历史趋势。

Action 是 Knowledge Builder 最有想象力的一部分。它不只是理解信息，还要发现"可执行动作"。比如：

  • Git 里的 deploy.sh、rollback.sh；
  • Notebook 里的 submit_job()；
  • K8s 里的 kubectl rollout restart。

把这些统一抽成 Action 对象之后，Agent 才知道"我能执行什么"。这把 Ontology 从"知识库"扩展成了"能力库"。

Ontology Merge：解决同一对象

多个数据源可能产生同一个对象。MLflow、Git、Notebook 里都可能出现 Experiment-001。Builder 要自动 Merge，这叫 Object Identity Resolution。

判断"是不是同一个对象"靠四个信号共同决定：Name、Alias、UUID、Metadata。单靠任何一个都不够——名字可能撞，UUID 可能没填。多信号联合判断才能把误合并压到可接受的水平。

Validation：过门才能入库

Builder 输出的对象必须经过校验才能进 Ontology。校验维度：

  • Schema——字段是否符合第 2 章的契约；
  • Relation——关系是否合法（source/target 是否存在）；
  • Loop——是否引入了循环依赖；
  • Permission——权限是否合规；
  • Reference——引用是否完整；
  • Version——版本是否连续。

Validation Failure 的对象不能进 Ontology——宁可丢弃，也不要让脏数据污染知识库。这是质量底线。

前车之鉴：别照搬源系统的 schema

校验只能拦住"格式错"的对象，拦不住"方向错"的建模。自动抽取最容易踩的坑，是 LLM 把源系统里的表结构原样搬进 Ontology——字段照抄、命名照搬、一条源数据行里混杂多个实体也建成单一类型。这么建出来的 Ontology 看着满满当当，其实是源系统 schema 的拙劣副本，业务语义全丢了。

这不是假设。Palantir Foundry 的 Ontology 设计文档把这类问题总结成几条反模式，每一条都直指自动抽取的软肋：

  • Kitchen Sink——把源数据表 1:1 映射成对象属性，不做取舍；属性命名直接抄源系统的字段习惯（比如 dtLastInspMod），而不是用业务语言（lastInspectionDate）；一条源数据行里混了多个实体，却建成单个对象类型。
  • System Silos——因为数据来自不同源系统，就给同一个真实世界的实体建多个对象类型。这恰恰是 Knowledge Builder 多源抽取最容易产生的后果。
  • Department Silos——不同部门各自造一套同一对象类型，映射的是组织架构而不是业务现实。
  • 命名歧义——类型叫"Item"、属性叫"value"，没人知道它到底指产品、订单行，还是金额、数量。

Foundry 给出的应对清单也值得抄过来：对现实建模而非对系统建模、有意识地做取舍、跨团队协作避免重复建模、用接口做抽象而非硬造大而全的类型。这些原则翻译到本书，就是 Knowledge Builder 的 Rule + LLM 抽取必须配合质量纪律——LLM 输出不仅要过 Validation，还要过"是不是在照搬源 schema"这道关。否则建出来的 Ontology 越大，垃圾越多。来源：Foundry Ontology 文档，Ontology 设计最佳实践/反模式

Version Management

Ontology 必须版本化。一个 Experiment 从 v1 到 v2 到 v3，要支持 Snapshot、Diff、Rollback、Replay。

为什么 Replay 重要？因为 Agent 要能解释历史——"三个月前那次实验用的什么参数"。没有版本化，历史就丢了，Context 的可追溯性（第 0 章原则 5）就落不了地。

Streaming Update：不是全量重建

推荐用 Fluss 作为实时 Context Bus。所有新增、修改、删除都 Event 化，Builder 消费这些 Event 来更新 Ontology——而不是每天全量重建。

全量重建的问题在于延迟和成本：数据变了，要等到第二天重建才能反映进 Ontology。而 Event 驱动能做到秒级同步。对于实时性强的业务（比如风电场告警），这是刚需。

插件架构

Builder 不关心数据源，只认统一 Connector。接口很简单：

type Connector interface {
    Discover()
    Extract()
    Normalize()
    Sync()
}

新增一个数据源就是实现这四个方法。这让 Knowledge Builder 可以持续接入新系统，而不需要改核心代码。

Trace：每个对象都能解释

Builder 必须记录每个对象的来源信息：Entity 的来源、抽取规则、LLM Prompt、Confidence、更新时间。这些信息是 Explain 的基础——当有人问"这个对象从哪来、可信吗"，你能答上来。

一个硬约束：模型输出不能直接入库

LLM 抽取必须与规则校验、人工审核和来源证据结合，不能直接把模型输出写入生产 Ontology。

这是整个 Builder 最重要的工程纪律。LLM 会幻觉，会抽错关系，会编造不存在的实体。如果把它的输出直接写进生产 Ontology，脏数据会顺着检索、扩展一路污染到 Agent 的答案。正确的做法是：LLM 抽取 → 规则校验 → 人工审核（关键对象）→ 带来源证据 → 才入库。Human-in-the-loop 不是可选项。

怎么评估 Builder 好不好

建议用这些指标评估 Knowledge Builder 的质量：

  • 实体识别准确率——抽出来的实体对不对；
  • 关系准确率——抽出来的关系对不对；
  • 来源覆盖率——企业数据有多少被接进来了；
  • 增量延迟——数据变化多久反映到 Ontology；
  • 冲突率——多源合并时产生多少冲突；
  • 人工审核通过率——模型抽取的质量有多高；
  • 历史版本可重放率——能不能回放历史 Ontology。

这些指标里，"人工审核通过率"是最诚实的——它直接反映 LLM 抽取到底有多靠谱。如果通过率太低，说明你的 Rule 兜底不够，或者 Prompt 设计有问题。

MVP 与工程拆分

第一版别贪多。先支持 MySQL、Paimon、Git、MLflow、PDF 五个数据源，自动抽取 Entity、Relation、Document 即可。Event 放第二版，Action 放第三版。

工程上建议拆成独立模块，方便并行开发：

knowledge-builder/
  connector/
    mysql/  git/  mlflow/  pdf/
  extractor/
    entity/  relation/  event/  metric/  action/
  validator/
  version/
  trace/

本章小结

Knowledge Builder 的职责不是导入数据，而是持续构建企业知识。它最终输出的是统一 Ontology。后续所有模块——Retriever、Graph Expansion、Context Engine、Agent Runtime——都建立在 Builder 的输出之上。

Knowledge Builder 是企业知识进入 AI 世界的入口，也是 Context Engine 的知识生产流水线。

首个版本应优先完成 Connector SDK、Entity/Relation 抽取、增量同步、Schema 校验和发布回放。记住那条纪律：模型输出永远不能直接写进生产 Ontology。详细接口和 Schema 以第 2 章契约为准。
