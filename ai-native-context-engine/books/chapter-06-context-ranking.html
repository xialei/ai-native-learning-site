第 6 章 · Context Ranking

在有限 Token 里，选什么给模型看

如果说 Hybrid Retrieval 决定找到什么，Graph Expansion 决定补充什么，那么 Context Ranking 决定最终把什么交给 LLM。检索和扩展会带回几百个对象，但模型一次只能看那么多。选谁、不选谁，是这一章的全部问题。

模块定位

Context Ranking 位于 Graph Expansion 之后。它的职责是从大量 Context Candidate 中，筛选出当前任务最有价值的 Context。

它不是传统搜索里的排序器（Ranking），而是 Context Selection Engine（上下文选择引擎）。区别在于：搜索排序是"把最相关的排前面"，而 Context Selection 要考虑的不止相关性——还有时效、权限、Token 成本、业务优先级。它是一个多维决策，不是单一相似度。

为什么需要 Ranking

经过 Hybrid Retrieval 和 Graph Expansion 后，通常会得到这样一个规模的结果：

300~500 个 Object
1000+ Relation
100+ Event
几十篇 Document
几十个 Metric

但 LLM 一次只能接收有限 Token。因此必须选择，而不是全部发送。

这件事的难度在于"全发"和"全不发"之间，有一个巨大的灰色地带。发太多，Token 爆了，模型注意力被稀释；发太少，关键信息缺失，答非所问。Ranking 的价值就是在中间找到那个最优子集。

整体架构

输入与输出

统一输入是 Context Package，包含 Objects、Relations、Documents、Events、Metrics、Actions。每个对象带 ID、Type、Metadata、Source、Timestamp、Score。

输出是 Ranked Context Package，比输入多了四个字段：Rank、Priority、Final Score、Reason。比如：

Experiment
  Score: 97
  Reason: Current Experiment
          High Importance
          Recent
          Owner Match

注意那个 Reason——Ranking 必须支持 Explain。每个对象为什么进、为什么被踢，都要能解释。这是第 10 章 Observability 的基础。

Ranking Pipeline

七个排序因子

建议采用多维评分，而不是 Embedding Similarity。下面七个因子共同决定一个对象的最终分数。

1. Relevance（相关性）

来源是 Query、Intent、Ontology。比如 Loss 这个指标，和 Experiment 高度相关。相关性是基础分，但不是唯一分。

2. Freshness（时效性）

当前 GPU 状态、今天的告警、昨天的日志，优先级远高于三个月前的数据。实时业务场景里，时效性往往比相关性更重要——一个过时的"高相关"对象，价值不如一个新鲜的"中等相关"对象。

3. Importance（业务重要性）

来自 Ontology。Experiment 五星、GPU 四星、Owner 两星、Comment 一星。重要性是业务定义的，不是算出来的——它反映的是"这个对象对业务有多关键"。

4. Authority（可信度）

MLflow 五星、Notebook 四星、Wiki 三星、Slack 一星。来源影响最终排序——同样一个数据，来自 MLflow 比来自 Slack 可信得多。

5. Permission（权限）

用户没有权限的对象，直接过滤，而不是降分。这是硬约束，和第 0 章原则 4 一致。

权限过滤还要细到属性粒度，不只是"对象可见不可见"。Palantir Foundry 支持在 object type 上直接配 cell-level（单元格级）安全——对象实例级和属性值级两层，且独立于背后数据源权限。它比传统的 Restricted View 方案更轻：配置直接挂在类型上、策略变更近乎实时生效（旧方案改权限得重建整条管道）、还能给流式数据源加行列级权限（旧方案做不到）。本书这里的 Permission 因子可以照这个粒度深化：无权限的对象直接过滤，而对象内部无权限的属性也按 cell 级脱敏，而不是整个对象扔掉。来源：Foundry Ontology 文档，Object and property security policies

6. Distance（图距离）

Graph Distance。Experiment → Dataset 距离是 1，Experiment → Dataset → Statistics 距离是 2。距离越远，Score 越低。这控制了扩展的范围——太远的对象即使相关，也降权。

7. Token Cost（Token 成本）

不同对象占用 Token 不同：Document 1000 Token、Metric 20 Token、Event 15 Token。如果价值接近，优先选低 Token 的。这是为压缩阶段服务的——同样的信息量，用更少的 Token 表达。

Final Score

七个因子合成一个分数：

Final Score = Relevance + Freshness + Importance
            + Authority + Business Priority
            - Distance - Token Cost

两个负向因子值得注意：Distance 和 Token Cost。它们让排序不仅看"价值高不高"，还看"代价大不大"。一个距离远、Token 又大的对象，即便相关性高，也可能被踢出去。

"价值接近时优先低 Token"这条原则，在更上游还有一个工业对应物：按需索引。不是所有属性都值得进高成本的可搜索、可排序索引。Palantir Foundry 用 render hints 标记每个属性的用途——比如 Searchable 决定它能不能被过滤、排序、聚合；不需要被搜索的属性，取消这个提示就能显著减轻重建索引的负担、加快索引速度。这和 Token Cost 的精神是一致的：资源有限，只把"会被用到的"放进高成本通道。本书在排序层用 Token Cost 选对象，Foundry 在存储层用 render hints 选索引，本质都是按需加载。来源：Foundry Ontology 文档，Property metadata / Render hints

Explain：每个对象都能解释

Ranking 必须支持 Explain。例如：

Experiment
  Score: 95
  原因: Current Project
        Recent
        High Authority
        Token Low

Agent 可以据此 Debug。更重要的是，当业务人员问"为什么 Agent 没看到这个信息"，你能拿出具体原因——是 Token 太高被踢了，还是权限不够被过滤了。没有 Explain 的 Ranking，在生产环境里就是黑盒。

Context Diversity：不能全是同一类

一个常见错误：Top 10 全是 Document。但实际上 LLM 需要的是覆盖——Experiment、Dataset、Metric、GPU、Notebook、Commit 各要一点。Ranking 不是简单的 Top Score，而是要保证 Context 丰富。

这背后是一个经典的算法问题：Set Cover。目标不是"选分数最高的 N 个"，而是"用有限的 Token 覆盖最多的信息维度"。

"少而精优于多而全"是同构的另一面。生产实践反复印证：铺一个大而全的候选集，不如精选一组覆盖度高的对象——前者稀释注意力、增加 Token 成本、放大选择错误。这条经验来自工具层（工具菜单越大，选择错误和提示注入面越大），但同样适用于上下文选择：选什么、不选什么，本身就是质量的决定因素，而不只是检索之后的附庸。来源：Li et al., 2026, §4.2/§11.2

Conflict Resolution：冲突怎么办

多个 Source 可能冲突。比如 MLflow 说 Accuracy 92%，Notebook 说 91%。Ranking 优先 Authority 高的，保留 MLflow。冲突解决不能靠"取平均"——数据可信度不同，平均是在稀释真相。

Ranking API

type Ranker interface {
    Rank(ctx context.Context, pkg ContextPackage) (ContextPackage, error)
}

支持插件化——不同的业务可以有不同的排序策略。

Context Quality：不止输出分数

Ranking 不仅输出 Score，还输出 Quality 指标：Coverage（覆盖率）、Freshness（新鲜度）、Authority（权威度）、Completeness（完整度）。这些供 Prompt Builder 参考——它知道这份 Context 的质量水位，能据此决定是否需要再补检索。

关键提醒：生产实现应同时报告相关性、覆盖率、冲突率和 Token 效率，避免把单一分数误认为 Context 质量。一个高分数的 Context 可能覆盖率很低，单一分数会掩盖这个问题。

两个高级能力

Goal-aware Ranking（目标感知排序）

传统 Ranking 只看 Query。建议增加 Goal 维度——同样问"为什么训练慢"：

Research Agent 优先 GPU 和 Profile，Operator Agent 优先集群和调度器，Business Agent 优先成本。Goal 决定 Ranking——这让排序从"问题驱动"升级为"目标驱动"。

Context Coverage Optimization（上下文覆盖优化）

很多 RAG 的 Top 10 全是 Document，但实际上 LLM 需要 Experiment、Dataset、Metric、Action、History、Policy 的组合。因此 Ranking 不是 Top Score，而是最大 Coverage——类似 Set Cover。这是 Context Engine 的核心研究方向。

Learning Ranking：会学习的排序

未来支持 Feedback。如果用户经常点击 GPU 相关的对象，GPU 的 Importance 会自动提升。Ranking 不断学习，越来越贴合实际使用。这把排序从"静态规则"变成"自适应系统"。

MVP

分三个阶段：

  • 第一阶段：Relevance、Freshness、Importance、Permission、Token Cost、Explain；
  • 第二阶段：Learning Ranking、Diversity、Conflict Resolution；
  • 第三阶段：Reinforcement Ranking、Adaptive Ranking、User Preference。

本章小结

Context Ranking 不是搜索排序。而是在有限 Token 下，选择最值得让 LLM 看到的业务上下文。它决定了 Agent 是否真正拥有高质量 Context。
