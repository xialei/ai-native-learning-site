从一个模块到 AI 操作系统

最后一章，抬头看路。Context Engine 不会一夜之间长成，它得一个阶段一个阶段地演进。这一章给出四个阶段的路线图——从 Knowledge Engine 一路走到 Enterprise AI Operating System。每一阶段都是一个能交付的完整产品，而不是半成品。

产品愿景

AI Knowledge Runtime（AKR）的最终目标不是构建一个更好的 RAG，而是构建企业 AI 的统一 Context Runtime，让所有 Agent 基于统一上下文完成推理、协作和执行。

最终形态是这样一条链：

Context Engine 成为整个 AI 平台的核心。这条链从前十三章一直在讲，这里把它放到时间轴上看怎么一步步实现。

总体演进路线

建议采用四个阶段：

每一个阶段都是完整产品。这条原则很重要——不要发布"半成品阶段"。每个阶段结束都应该能交付一个客户能用的东西。

这条"阶段化演进、每段都是能独立运行的正确小系统"的纪律，开源社区有可对照的实现者视角。Pi Agent Harness 在其学习资料里给出一条自制 Runtime 的五阶段施工图：① 一个最小但完整的循环（从第一天就养成"错误当消息不抛出"的纪律）→ ② 持久化与恢复重建（读回历史、复用循环，但先忍住不做多会话分叉）→ ③ 上下文撞墙时学会自动压缩 → ④ 操作状态机 + 事件驱动 + 队列 + 钩子（从"库"升级成"运行时"）→ ⑤ 工具三阶段管线（prepare 校验/权限 → execute 可中止/流式 → finalize 可改写）与多供应商。它的核心纪律和本章一致——"下一阶段总在上一阶段的地基事件上长出，而非推翻重写"。本书的 Phase 1→4 是产品阶段划分（每个阶段交付一个完整产品），Pi 的五阶段是实现阶段划分（每个阶段交付一个能跑的系统）；两者一个对外、一个对内，但"不分阶段、不半成品"的原则互相印证。来源：Pi Agent Harness 学习站，learning-site/12-build-own-runtime.html

Phase 1：Knowledge Engine

目标：统一企业知识。

能力：Ontology、Knowledge Builder、Hybrid Retrieval、Context Package、Prompt Builder。

对应产品：企业知识助手。研发周期 3~4 个月。

这个阶段就是把第 2、3、4 章落地。它能交付一个比 RAG 强的"知识助手"——能检索对象而不只是文档。但它还没有图扩展、没有排序优化，Context 是初步的。

Phase 2：Context Engine

目标：统一企业上下文。

新增：Graph Expansion、Context Ranking、Context Optimizer、Context Runtime、Context Cache、Context Trace。形成真正的 Context Engine。

对应产品：Research Copilot、Business Copilot、Coding Copilot。研发周期 4~6 个月。

这个阶段把第 5 到第 10 章落地。到这里，系统才是名副其实的 Context Engine——有扩展、有选择、有压缩、有运行时、有缓存、有可观测。它能支撑起真正的 Copilot 产品。

Phase 3：Business Runtime

目标：Context 成为企业运行时。

新增：Business Context、Research Context、Realtime Context、Workflow、Context Event、Context Subscription、Multi-Agent Context。形成 Business Runtime。

对应产品：行业 Agent 平台。研发周期 6~9 个月。

这个阶段把第 11、12、13 章落地。Context 从"为单个 Agent 服务"升级为"为企业运行时服务"——多个 Agent 协作，实时事件驱动，领域插件化。

Phase 4：Enterprise AI Operating System

最终目标：Context 成为企业 AI 操作系统。

新增：Context Protocol、Context Scheduler、Context Marketplace、Domain Context Plugin、Multi-Agent Runtime、Autonomous Workflow。最终形成 Enterprise AI OS。

这是愿景的终点——Context 成为像操作系统内核一样的基础设施，所有 Agent 和应用都跑在它上面。

时间线：6 / 12 / 18 / 24 个月

技术路线

逐步演进，不跳跃。每一年的能力都建立在前一年之上——第一年建知识基础，第二年建运行时，第三年建操作系统。

沿着这条路走，有几个学术界已经标出来的硬骨头，Context Engine 绕不过去，得提前认领。

第一块是上下文漂移。前面讲的 context rot 是单步退化——输入越长越差。漂移是另一回事：agent 跑到 100 轮以上，即使每轮都做压缩，摘要里积累的微小误差会复合放大，最终行为偏离原始意图——重复已完成的工作、无意识地自相矛盾、丢失动机目标。现有技术能延缓，但无一能根治。这划出了本书能力的边界：长程可靠性不能只靠 context engineering，还要靠验证环、人机检查点和异常检测来补。来源：Li et al., 2026, §5.7

第二块是把上下文管理重述成状态估计问题。未来的方向不是塞更多 token，而是能量化"每次压缩、检索、遗忘丢了多少任务相关信息"，并用不确定性感知的摘要、事实溯源、矛盾处理和显式陈旧标记，让 agent 能从持久 artifact 重建缺失状态，而不是盲目信任自己的压缩历史。来源：Li et al., 2026, §12.2

第三块是能力与控制的同步演进。能力越强，权限越大，控制问题也越大——更大的工具菜单增加选择错误和注入面，持久记忆带来溯源和隐私风险。Context Engine 的演进不只是加能力，还要加对应的治理。好在有一件便宜的事可做：每个 harness 组件都编码了一条"模型自己做不了某事"的假设，模型变强后这些假设会过时——有团队在升级模型后移除了上下文重置等机制，成本从 $200 降到 $125 而质量不变。这意味着演进也包括简化：定期用评测发现哪些组件已经多余，而不是只会加不会减。来源：Li et al., 2026, §11.2/§7.4/§12.5 引 Anthropic

上面三块讲的都是"Context Engine 要解决的外部难题"。但还有一类问题不在外部，而在 Context Engine 自己身上——这套系统自身怎么迭代改进。前面十四章都在讲怎么给 Agent 造上下文，却没有回答：Context Engine 的 prompt、检索策略、压缩规则本身，由谁来改、怎么改、改坏了怎么防。这正是 harness 工程文献里被单列出来的一层——"自我改进的 harness"。它给本书路线图补上最后一块拼图。

Context Engine 自身如何迭代

一个朴素的直觉是：让模型自己改自己的配置。但文献给出的结论很审慎——递归结构本身不够，基座模型必须有足够能力才能改进机制本身。早期实验 STOP（Self-Taught Optimizer）让"改进者改进自己"，在强模型上能持续改进，但在弱模型上反而变差。也就是说，harness 改进放大的是模型能力的部署效果，而不能替代模型智能。来源：Lilian Weng, Harness Engineering for Self-Improvement, 2026, §4.3

还有一条对模型选型很实用的发现：能"写出有用的 harness 编辑"（harness-updating 能力），在不同规模模型间差异不大，小模型也能写出和大模型过程同构的 skill；但"用好更新后 harness"（harness-benefit 能力）是非单调的，中等档位模型受益最大——因为它需要足够的长程指令遵循和精准的工具调用时机才能把已有 harness 的价值发挥出来。这提醒本书的模型选型（第 9 章缓存、第 8 章运行时）不能只看"写配置"的能力，更要单独评估"长程指令遵循 + 工具调用时机"这一维度。来源：Lilian Weng, Harness Engineering for Self-Improvement, 2026, §4.3 引 Lin et al., 2026

真正工程化程度最高、最值得照搬的，是 Agentic Harness Engineering（AHE）提出的三大支柱。它在 Terminal-Bench-2 上优于人工设计的 harness，而且冻结后的同一个 harness 不再继续进化，也能直接迁移到 SWE-bench-verified 并保持优势——说明它学到的是可迁移的工程经验，而不是针对某个 benchmark 的过拟合技巧。三大支柱可以原样映射到本书：

AHE 支柱含义本书对应
组件可观测性harness 拆成可编辑组件清单（system prompt / tool description / tool implementation / middleware / skill / sub-agent config / long-term memory），每个失败模式强制映射到具体组件，编辑才能精准打击第 1 章核心模块 + 第 8 章运行时组件
经验可观测性每条轨迹存一个文件，生成单任务根因报告，再聚合成 benchmark 总览，原始轨迹按需访问——分层访问结构，token 效率更高第 10 章 RCA + Trace 分层
决策可观测性每次编辑配一条"下一轮要验证的预测"，编辑必须证据驱动（根因→预期修复→可能引入的回归风险）第 10 章证据日志 + 第 8 章 Version

三条支柱里最关键的不是"怎么改"，而是边界。AHE 划了一条硬约束：编辑只能作用于 harness workspace，runs 目录、tracer、verifier、LLM 配置全部只读。这直接堵死了一大类 reward hacking——比如让 agent 偷偷关掉 verifier、换个更弱的模型、或者偷偷加大推理预算，好让"进步"指标好看。每一份进步都必须能归因到 harness 编辑本身，而不是归因到"把裁判换走了"。这条原则在本书落地就是：把"可编辑区"（检索权重、压缩规则、ranking 阈值、prompt 模板）和"只读区"（trace 数据、评测器、模型网关配置、Policy Engine 的 ACL 规则）在架构层硬隔离，而不是靠约定——它应该和第 1 章的 Policy Engine 一起，作为不可被自动化改动的底盘。来源：Lilian Weng, Harness Engineering for Self-Improvement, 2026, §4.3

这套"组件化 + 可观测 + 证据驱动编辑 + 只读边界隔离"的范式，对应到本书路线图是一个新阶段——它不改变 Phase 1→4 的产品划分，但在每个 Phase 之上叠加一个"持续改进环"：

自我改进的风险与人的位置

把"自动改进"打开，就要同时把它管住。文献把这条路上会踩的坑列成了一份清单，逐条对照本书的场景：

  • 弱/模糊的评估器：只有指标可量化、客观的任务，自我改进循环才 work 得好。涉及语义理解质量的任务（如 Research Context 的"这个假设是否成立"），评估器设计是长期难点——本书第 10 章的 Quality Score 不能只靠单测通过率。
  • 负面结果：模型训练数据整体偏向成功案例，导致模型不擅长判断"该放弃这个假设了"。Harness 应该让失败尝试容易被保留下来——这直接呼应上面弱点挖掘的设计，也是缩小任务搜索空间最有效的方式之一。
  • 多样性坍塌：进化/RL 循环容易过度利用已知高回报模式，收敛到同质解。若未来让 skill/prompt 库自动进化，需要专门机制（如基于 embedding 相似度的新颖性拒绝采样、子代越多父代被选概率越低）防止同质化。
  • 长期健康度：短期任务完成度指标（如单测通过）无法捕捉可维护性、职责边界、迁移成本、向后兼容性这些长期成本——对企业级交付场景尤其重要，这也是 Phase 4 把 Context Federation 列为独立能力的原因。

最后一条关于人的位置，值得单独说。原则不是"把人移出循环"，而是"让人上移到更高的抽象层"——人应该设在"harness 编辑验证""证据链审计"这类关键决策点上，而不是陷入具体 prompt 调优。本书的演进应当遵循同样的原则：自动化的改进环处理可复现、可窄范围修改的问题；涉及职责边界、权限扩张、向后兼容的决策，保留人工介入点。来源：Lilian Weng, Harness Engineering for Self-Improvement, 2026, §5

回到路线图本身。文献给出的两阶段预测可以作为本书判断"为什么模型越来越强还要投资 Context Engine"的锚点：短期内，harness 工程会往"元方法论"演化——优化的不是答案本身，而是"获得更好答案的机制"；长期看，很多 harness 层的改进最终会被内化进模型本身的行为（类比 prompt engineering 的手工技巧被 instruction tuning 取代），但指定目标、约束、上下文和评估标准的需求不会消失——harness 层的接口价值是持久的，只是实现细节会被模型能力吸收。这意味着投资本书"指定目标/约束/评估"这一层的抽象和协议设计（Context Protocol、Policy、Trace schema），比投资具体的手工规则更有长期价值，因为前者不会被模型进步淘汰。来源：Lilian Weng, Harness Engineering for Self-Improvement, 2026, §3

与现有平台结合

产品矩阵

最终形成的产品矩阵：

AI Knowledge Runtime

├── Context Engine
├── Context Runtime
├── Research Context
├── Business Context
├── Context Cache

所有能力统一产品。这就是 AKR 的完整面貌——它不是一个组件，而是一套覆盖知识构建、上下文生成、运行时管理、领域插件、协议和 Agent 的完整产品线。

商业化路径

逐步扩大客户价值。从单点 Copilot 切入，到行业插件，再到企业级运行时，最后是 Context Marketplace——一个让第三方贡献领域 Context 的市场。

与 Palantir Foundry 的区别

常被拿来对比的是 Palantir Foundry。它们的链路对比：

PalantirAKR
Ontology → OAG → ApplicationKnowledge Builder → Context Engine → Context Runtime → Business Runtime → Agent Runtime → Application

AKR 更加关注：Context 的生命周期、Agent 协作、实时上下文、Context 可观测性、Context Protocol。Palantir 止步于 Ontology 到应用，AKR 多了运行时、多 Agent、协议这几层——这些是 AI 时代特有的需求。

不过有一处值得反过来向 Foundry 借鉴：模型和工具的接入应该标准化成契约。Foundry 的 Function Interface 描述"函数该长什么样"——输入、输出、错误类型的规范，它本身不是函数，而是让别的函数去实现的一份契约。最直接的案例是它的 chat completion 接口：用户注册的自建模型，本质上就是"实现了这个接口的函数"，几乎等同于"包一层 OpenAI 兼容适配器"的现成模板。本书主张"Agent 不直接访问数据源、统一从 Context Engine 获取上下文"，这层抽象同样可以走"接口契约 + 多实现"的路子——把检索、扩展、压缩各环节都定义成接口，具体模型、具体数据源作为可替换的实现插进来，平台演进时换底层不动契约。来源：Foundry Ontology 文档，Function interfaces

本章小结

AI Knowledge Runtime（AKR）的目标不是成为新的知识库，也不是新的 Agent 平台，而是构建企业 AI 的 Context Runtime，让企业所有 Agent 基于统一上下文理解业务、协同推理、执行任务，并持续演化。

构建企业 AI 的 Context Runtime，让企业所有 Agent 基于统一上下文理解业务、协同推理、执行任务，并持续演化。

Context 将成为企业 AI 时代最重要的基础设施。从 Knowledge 到 Context 到 Runtime 到 AI Operating System——四个阶段，每一步都交付完整产品，每一步都让 Context 离"企业 AI 的内核"更近一步。

这是全书的最后一章。回到第 0 章的那条主线——对象模型 → 知识构建 → 检索 → 图扩展 → 选择 → 压缩 → 运行时 → 观测 → 多 Agent 协作——你现在应该能看清每一环在整条链路上的位置，以及它们为什么必须是这个顺序。剩下的，就是动手了。
