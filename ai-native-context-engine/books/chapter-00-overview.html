把"上下文"当成产品来做

大模型已经够强了。真正卡住企业 AI 落地的，往往不是模型，而是模型看不到的东西——那些散落在十几个系统里、互相之间毫无关联的业务上下文。这本书讲的就是怎么把这件事系统性地解决掉。

为什么写这本书

过去两年我看过太多企业 AI 项目，它们的技术栈大同小异：一个问题进来，去向量库里捞几段文档，拼到 Prompt 里，丢给大模型，结束。这套流程有个名字，叫 RAG。

RAG 没错，但它解决的是一个很窄的问题——"让模型能看到文档"。而企业里真正麻烦的，从来不是模型看不到文档，而是模型看不到关系：

  • 这次实验用了哪个数据集？
  • 这台风机上个月为什么报过警？
  • 这个模型是谁训的、什么时候训的、用的什么代码版本？
  • 这条工单涉及的设备，当前用户有没有权限看？

这些问题，靠"捞文档"是答不出来的。它们需要的是结构化的、带关系的、带权限的、有时效的上下文。而生成这种上下文，恰恰是 RAG 从来没认真对待过的环节。

这不是一家之言。学术界已经把这件事说得很直白：agent 可靠性的天花板，不只由模型决定，还由模型周围的基础设施决定。一篇 2026 年的综述梳理了一批受控实验——在模型权重完全不变的前提下，仅改造工具格式和上下文中间件，某个编码 agent 在 Terminal-Bench 2.0 上的通过率就从 52.8% 拉到了 66.5%；个别模型在编码基准上的提升甚至达到 10 倍。来源：Li et al., Agent Harness Engineering: A Survey, 2026, §1

这些数字传递的信号很明确：当你抱怨"模型不够聪明"的时候，真正卡脖子的往往不是模型，而是模型看不到的上下文。这本书要解决的，正是这一层。

Context Engine 是 AI Agent 的上下文操作系统。它持续从企业数据中构建、组织、优化并安全地提供上下文，让 Agent 理解的是真实业务，而不仅仅是文档内容。

这本书面向平台工程师、AI 应用工程师和系统架构师。我们不讨论模型训练，不讨论怎么搭数据仓库，也不想再造一个 Agent 框架。Context Engine 的位置很明确——它夹在 Agent 和企业数据之间，专门负责生成经过治理的上下文。

问题与非目标

先把边界划清楚，免得这本书越写越大。

传统 RAG 的流水线是这样的：

它能表达文档相关性，但表达不了下面这些东西——而它们恰恰是企业场景的核心：

维度传统 RAGContext Engine
最小检索单元Document ChunkObject / Object Graph
检索方式向量为主Hybrid Retrieval
输出静态 Prompt动态 Context Package
相关性判据文档相似度业务语义、权限和证据

几个明确的非目标：

  • 不讨论模型训练与微调；
  • 不实现通用数据仓库；
  • 不替代 Agent Framework，Agent 怎么推理、怎么调工具是它自己的事。

Context Engine 只做一件事：把企业数据变成 Agent 能直接消费的、可信的上下文。其它事情，让别人去做。

一个核心抽象

如果整本书只能记住一句话，记住这条主线：

这里最关键的一步转变，是把文档降级、把对象扶正。

在 RAG 里，文档是主角。但在真实业务里，主角从来不是某份 SOP——而是那份 SOP 背后的设备、实验、工单和人。文档只是这些对象的证据载体。Context Engine 把对象变成"一等公民"，文档退居为对象的一个属性、一份证据。

这个视角一换，后面所有的设计都顺了：检索不再是搜文档，而是找对象；扩展不再是多捞几段，而是沿着关系图补全上下文；排序不再是算相似度，而是算"哪个对象最值得让模型看到"。

全书主线

这本书围绕一条流水线展开。每一章对应流水线上的一个环节，章节之间是契约关系而不是松散的话题——第 2 章定义唯一的对象模型，后面所有章节都只实现或消费这份契约，不重复定义。

第 1 章给出系统边界，第 2 章给出唯一数据契约。Research Context 和 Business Context 是领域插件实例，它们不重新定义平台基础能力，只是把通用模型套到具体行业里。

把这条主线放回更大的背景里看会更清楚。学术界把围绕大模型的工程实践分为三圈递进：prompt engineering（塑造单次模型调用的输入）→ context engineering（管理模型在多步执行中每一步可见的完整信息状态，把上下文窗口当作主动管理的资源）→ harness engineering（把 prompt 和 context 整合进一个保证执行"有界、可观测、可验证、可恢复"的闭环系统）。来源：Li et al., 2026, §2.2

本书的 Context Engine 正落在中间这一圈——它深耕 context engineering，把上下文当成产品来做；同时向上触及 harness 的运行时与治理边界（第 8 章运行时、第 9 章缓存、第 10 章可观测、第 0 章原则 4 的 Policy 硬约束）。后面每一章，都是在回答"context engineering 这一圈具体怎么落地"。

六条设计原则

这六条原则贯穿全书，后面每一章的设计决策都能追回到它们。我建议你在读任何一章之前先把它们记在心里。

1. Context 是产品，Ontology 是基础设施

用户（Agent）最终消费的是 Context，不是知识图谱。Ontology、向量库、图索引这些都是为了产出 Context 而存在的底座。别本末倒置——不要为了建一个漂亮的图谱而忘了它服务的终点。

这条原则不是闭门造车想出来的。工业界最成熟的 Ontology 平台 Palantir Foundry 早就把话说得很直白：Ontology 的价值不在于"数据"，而在于"决策"。传统数据架构只存数据，不捕捉决策背后的推理过程和随之而来的行动，所以学不到东西，也接不上 AI。Foundry 主张让新数据快速整合成高保真语义表示，再通过与运营系统的实时连接实现"动作集成"——这恰恰是本书把 Ontology 定位为"基础设施"、把 Context 定位为"交付给 Agent 的产品"的工业依据。来源：Foundry Ontology 文档，Why create an Ontology

2. Agent 只消费经过授权的 Context

Agent 永远不直接碰原始数据。所有数据都必须经过 Context Engine 的治理——授权、脱敏、审计——之后才能到达 Agent。这不是可选优化，是硬约束。

3. 检索、扩展、选择和压缩是不同阶段

很多人喜欢把这些步骤揉在一起，一个"智能检索"把活全干了。这会让系统变得无法调试。我们坚持把它们拆成独立阶段，每个阶段职责单一、边界清晰、可观测。出了问题你能定位到是哪一步出的。

4. Policy 是硬约束，默认开启

权限、脱敏这些 Policy 不是排序时可以权衡的"特征"，而是输出前必须重新校验的硬门。任何对象在进入最终 Context Package 之前，都必须过这一道。

5. Context 必须可追溯、可回放、可评测

每一份进入 Prompt 的上下文，都要能回答"它从哪来、为什么被选中、当时是什么状态"。做不到这一点，系统上不了生产。

6. 在线路径优先保证安全和稳定

延迟和成本当然重要，但顺序是：先安全、再稳定、最后才优化延迟和成本。在线路径上为了快而牺牲正确性，迟早会出事。

贯穿全书的约定：后续章节都以第 2 章的 Context Package 为共同契约。这意味着你读任何一章时，对象长什么样、Package 里有哪些字段，都去第 2 章查，不需要各章重复定义。

本章小结

Context Engine 不是"更好的 RAG"。它换了一个起点：把对象而不是文档当作最小单元，把上下文而不是 Prompt 当作最终产物，把治理而不是检索当作核心职责。

从第 1 章开始，我们会一层层拆开这套系统——从系统边界、对象模型，一直到运行时、观测和多 Agent 协作。每一章都建立在前一章的契约之上。
