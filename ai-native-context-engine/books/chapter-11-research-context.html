第 11 章 · Research Context

研发世界的统一上下文

从这一章开始，我们离开通用平台，进入领域插件。Research Context 是 Domain Context Plugin 的第一个实例——它把通用对象模型套到 AI 研发场景里。通用对象、生命周期和 Context Package 以第 2 章和第 8 章为准，本章只定义研发领域的对象映射、关系和使用方式。

模块定位

Research Context 是 Context Engine 在 AI 研发场景中的领域模型（Domain Context）。它的职责是统一描述 AI 研发全过程中的对象、关系、状态和行为，为 Research Agent 提供完整的研发上下文。

它不是 Notebook，也不是 MLflow，而是 AI 研发知识的统一运行时。这句话的含义是：Notebook 和 MLflow 只是数据来源，Research Context 把它们以及 Git、数据平台、GPU 集群、模型仓库、特征平台、文档系统的信息，统一成一个 Agent 能消费的上下文。

为什么需要 Research Context

目前 AI 研发的数据分散在多个系统：Git、Notebook、MLflow、数据平台、GPU 集群、模型仓库、特征平台、文档系统。

Agent 无法理解这些对象之间的关系。比如问"这个模型为什么效果下降"，实际上需要关联：数据集、特征、实验、Commit、GPU、参数、Evaluation。这些信息分散在七个系统里，靠 Agent 自己去连、去猜，几乎不可能。

Research Context 的目标，就是把这些研发对象组织成一个统一的 Context Graph。

Research Context 架构

所有研发对象统一纳入 Context。注意这里每个对象都对应第 2 章定义的通用 Object——Research Context 不重新发明对象模型，只是把研发领域的具体东西映射进去。

Context Plugin Marketplace

Research Context 只是第一个领域插件。Context Engine 的设计是插件化的：

如果你们在新能源行业，可以直接提供风电 Context、光伏 Context、电网 Context、储能 Context、气象 Context。每个插件都包含：Ontology Schema、Builder、Retriever、Expansion Rule、Ranking Rule、Prompt Template。装上即用。

"打包即用"在工业上已经被验证可行，但有几条工程约束必须先说清楚。Palantir Foundry 的 Marketplace 可以把 object type、action type、function、视图打包成产品分发到别的环境，但它踩出来的坑值得抄录：第一，权限规则不能绑死具体用户，必须改成引用群组——否则装到别的环境，那个用户不存在，权限规则直接失效；第二，对象实例本身不能被打包，只能打包类型定义和数据集，安装后由对方环境重新生成对象；第三，打包 action type 时最好把关联的 link type 一起带上，否则动作装过去会缺关系。本书的 Context Plugin Marketplace 要遵循同一条纪律：可分发的是定义，不是实例；权限要可移植，不能绑死具体身份。来源：Foundry Ontology 文档，Foundry DevOps / Marketplace

本章小结

Research Context 不是研发知识库，而是 AI 研发全过程的统一上下文模型（Research Context Graph），让 Agent 能够像研发工程师一样理解实验、数据、模型、代码和资源之间的关系。
