业务世界在 AI 运行时里的样子

上一章把通用模型套到了研发场景，这一章套到业务场景。Business Context 是 Domain Context Plugin 的业务实例——它统一描述企业业务对象、关系、事件和规则。通用对象模型、Policy、Runtime 和 Context Package 不在本章重复定义，我们只看业务世界怎么映射进来。

模块定位

Business Context 是 Context Engine 在企业业务场景中的领域模型（Domain Context）。它的职责是统一描述企业业务对象、业务关系、业务事件和业务规则，为 Business Agent 提供实时业务上下文。

Business Context 不是业务数据库，而是 企业业务世界在 AI Runtime 中的统一表达。数据库存的是记录，Business Context 存的是这些记录之间的业务含义和实时状态。

为什么需要 Business Context

企业业务数据通常分散在多个系统：ERP、CRM、MES、SCADA、IoT、OA、Workflow、数据仓库、数据湖、文档系统。

Agent 无法理解这些系统之间到底是什么关系。比如用户问"为什么今天风电场发电量下降"，实际上需要串联一长串对象：

风机 → 测风塔 → ERA5 → 功率预测模型 → 告警 → 工单 → 维修记录 → 天气变化 → 电网限电。这条链横跨 IoT、气象、模型、运维、电网五个领域。Business Context 就是把这些对象组织起来。

Business Context 架构

所有业务知识统一表达。你能看到这六个组成正好对应第 2 章的对象类型——Object、Relation、Event、Metric、Action、Policy（Rule）。Business Context 没有发明新类型，只是把通用类型填上业务语义。

Business Event

Business Context 统一管理业务事件：

风速突变 → 预测完成 → 设备离线
→ 功率下降 → 限电 → 人工确认 → 工单关闭

所有事件进入 Event Stream。这条事件链就是一次"发电量下降"的完整故事——从风速突变开始，到工单关闭结束。Agent 看到的是故事，不是孤立的告警。

Business Metric

业务指标统一抽象：实时功率、预测功率、风速、温度、辐照度、利用小时数、设备健康度、模型误差。Metric 是 Context 的组成部分——它让 Agent 不仅知道"有什么对象"，还知道"这些对象表现如何"。

Business Rule

业务规则统一建模：

风速 > 25m/s          → 停机
预测误差 > 20%        → 重新训练
设备离线 > 10min      → 创建告警

Rule 不仅用于推理，还参与 Context Expansion。这是 Business Context 区别于 Research Context 的地方——研发场景的规则少，业务场景的规则多且硬。规则触发时，相关的对象会被拉进 Context。

Business Action

Agent 最终执行 Action：创建预测、启动训练、生成报表、创建工单、发送通知、重新部署模型、更新参数。Action 统一注册，供 Agent 调用。这把 Business Context 从"理解业务"扩展到"执行业务"。

每个插件包含：Ontology Schema、Builder、Retrieval Rule、Expansion Rule、Ranking Rule、Prompt Template。统一接入 Context Engine。这意味着进入一个新行业，不是从零搭系统，而是装一个插件。

但插件之间的共性，应该用抽象来表达，而不是硬造一个属性稀疏的"大而全"类型。Palantir Foundry 的 Interface 机制就是这个思路：它定义一个对象类型的"形状"和"能力"，让多个不同类型一致地实现它。比如定义一个 Facility 接口（带 Facility Name、Location），Airport、Manufacturing Plant、Maintenance Hangar 各自实现它、再各带特有属性——关键好处是，将来新增一个实现该接口的类型，已有的工作流不用改就自动兼容。一个对象类型还能实现多个接口，接口之间也能继承。本书的行业插件可以照这个做：风电场、光伏电站、储能站都是"设施"，先抽 Facility 接口兜住共性，再让各自插件带特有对象。这样跨行业的通用工作流（比如"列出所有设施的健康度"）只认接口，不认具体类型，新行业接入时老逻辑自动复用。来源：Foundry Ontology 文档，Interfaces

"混合存储 + 抽取层"这个落地方向，业界已有生产级参照。当前部署最广的 agent 长期记忆层，就用向量库做语义相似、图库做关系、KV 做快速事实三后端混合，再加一层 LLM 抽取来识别事实和偏好、路由到合适的存储——在公开基准上比纯上下文方案少用约 90% 的 token，准确率还更高，已被云厂商选为其 Agent SDK 的独家记忆方案。本书把向量、图、对象存储分层（第 1 章第 5 层），和这条生产路径是同构的。来源：Li et al., 2026, §5.5.2 引 Mem0, Chhikara et al., 2025

Business Runtime

企业级 Runtime 还有一层常被低估的价值：集体记忆。当一个 agent 在某次任务上踩了坑、解决了，这段经验应该沉淀下来，让组织里其他 agent 实例不必重复踩同一个坑。业界已有开放标准把这件事结构化——三层共享（本地、组织、跨团队），并在 agent 遇到错误时自动查询集体知识库。本书第 10 章的 RCA 产出的根因和建议，正是这种集体记忆的原料；第 13 章的多 Agent 共享，是它的消费侧。来源：Li et al., 2026, §5.5.2 引 cq, Mozilla AI, 2025

本章小结

Business Context 不是业务数据库，也不是知识图谱，而是企业业务世界在 AI Runtime 中的统一上下文模型（Business Context），让 Agent 能够理解对象、关系、事件、指标、规则和动作，并完成业务推理与业务执行。

企业业务世界在 AI Runtime 中的统一上下文模型，让 Agent 能够理解对象、关系、事件、指标、规则和动作，并完成业务推理与业务执行。
