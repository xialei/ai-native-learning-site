第 4 章 · Context Retrieval Framework

检索的终点是上下文，不是文档

传统 RAG 的检索，目标是"找到相关文档"。Context Engine 的检索，目标是"构建业务上下文"。这一章定义从 Query Planning 到候选 Context 输出的完整检索流水线——它更像数据库的 Query Optimizer，而不只是向量搜索。

设计目标

Context Retrieval Framework（CRF）是 Context Engine 的检索入口，Hybrid Retrieval 是其中的执行能力。它的职责不是"搜索文档"，而是为 Agent 构建高质量、高可信、低 Token 成本的业务上下文。

返回结果已经不是 Document，而是 Context——这是本质区别。

为什么需要 Hybrid Retrieval

企业数据不是单一种类。一个稍微像样的企业，数据就散落在十几个系统里：文档（PDF、Word）、数据库、数据仓库、数据湖、Git、Notebook、MLflow、Kafka、Paimon、Fluss、Prometheus、Kubernetes、API、实时日志。

这些数据形态千差万别，无法依赖一种 Retrieval。向量搜索搞不定设备编号这种精确匹配，关键词搜索搞不定语义近似，SQL 搞不定非结构化文本。所以需要统一的 Hybrid Retrieval Framework，它要同时支持：结构化数据、非结构化数据、实时数据、对象关系、业务知识、Tool。

架构

CRF 的核心是一张扇出的图：一个 Query 进来，先 Rewrite，再由 Orchestrator 路由到多个 Retriever 并行执行，最后 Merge、Ranking、交给 Context Builder。

六类 Retriever

Hybrid Retrieval 统一管理六类 Retriever，每一类都有自己擅长的场景。

Keyword Retriever

适用于 SOP、Wiki、PDF、日志、设备编号、型号、ErrorCode。典型实现是 Elasticsearch 或 OpenSearch。它的优势是精确、可解释，在工业领域效果尤其好——设备编号、故障代码这些精确字符串，向量搜索反而不如关键词。

Vector Retriever

适用于语义检索。典型实现是 Milvus、Qdrant、PGVector、FAISS。负责 Document、Chunk、Embedding、Semantic Search。它是传统 RAG 的主力，但在 CRF 里只是六分之一。

向量检索的工业落地路径是固定的：文本先分块，再 embedding，存进向量属性，最后做 KNN 近邻查询。这四步一步都不能省。分块尤其关键——embedding 模型有输入长度上限，而且整篇长文档一起嵌入，语义会被"稀释"，切成更小片段区分度才高。Palantir Foundry 的语义搜索就是按这条链路走的：文本转向量，存进 Ontology 的 vector 类型属性，再由 KNN 查询消费；它的 vector 属性只接受 KNN 查询、不能用在 Action 里、最大维度 2048。本书的 Vector Retriever 应遵循同样的"分块-嵌入-近邻"范式，而不是图省事对整篇文档直接嵌入。来源：Foundry Ontology 文档，Ontology search

Graph Retriever

适用于 Ontology。比如 Experiment → Dataset → Feature → Checkpoint → Evaluation 这条链。它返回的是 Object、Relation、Event，而不是 Document。这是 CRF 和传统 RAG 分道扬镳的地方——Graph Retriever 让检索能顺着关系走。

SQL Retriever

适用于结构化数据。Hive、MySQL、Paimon、Iceberg、DuckDB。SQL Retriever 可以生成 SQL、执行、把结果自动转换成 Context。问"上个月所有实验的平均 Loss"，这种问题天然适合 SQL，向量搜索无能为力。

Streaming Retriever

支持实时 Context。Kafka、Fluss、MQ、CDC、IoT。它返回的是最新状态，而不是历史状态。风机当前转速、训练任务当前进度——这些实时数据，靠批处理是捞不到的。

Tool Retriever

Tool 也是一种 Knowledge。deploy()、rollback()、restart()、predict()、train()、Workflow、Notebook。Agent 不只是知道信息，还能知道"可以执行什么"。Tool Retriever 把能力也纳入检索范围。

Retriever擅长典型实现
Keyword精确匹配、设备编号Elasticsearch / OpenSearch
Vector语义检索Milvus / Qdrant / PGVector
Graph对象关系遍历Ontology Store
SQL结构化查询Hive / MySQL / Paimon / DuckDB
Streaming实时状态Kafka / Fluss / CDC / IoT
Tool可执行能力deploy / rollback / restart

Retrieval Orchestrator：系统的大脑

Orchestrator 是整个系统的大脑。它不关心具体 Retrieval，只负责决定什么时候调用、调用几个、调用顺序。它的职责清单：

  • Query Rewrite——改写查询提升召回；
  • Query Classification——判断这是什么类型的问题；
  • Retriever Routing——决定走哪几个 Retriever；
  • Parallel Retrieval——并行执行检索；
  • Merge——合并结果；
  • Ranking——排序；
  • Cache——命中缓存；
  • Trace——记录全过程。

这八件事里，Routing 是最体现智能的。问"为什么训练慢"和问"风机发电量"，需要的 Retriever 组合完全不同。Orchestrator 要根据问题类型动态选择——这是它被称为"Query Optimizer"的原因。

Query Rewrite

用户的问题往往太短，直接检索召回率很低。比如用户问：

为什么 Loss 上升？

Rewrite 会把它扩展成一组检索关键词：

Experiment
Training
Loss
Learning Rate
GPU
Commit
Evaluation

目的是提升召回率。Rewrite 可以结合三样东西共同完成：LLM（理解语义）、Ontology（知道哪些对象相关）、用户历史（知道用户关心什么）。单靠任何一样都不够。

Rewrite 不是可有可无的优化，而是检索质量的前提。Palantir Foundry 的语义搜索文档把这点说得很直白：直接把用户原始提问扔给关键词搜索，效果往往不好——它建议在用户查询和实际检索之间插入一个 LLM 预处理步骤，去掉"帮我找找看"这类无意义修饰语、补上同义词和相关词。本书把"为什么 Loss 上升"扩展成 Experiment、Training、Learning Rate 一组检索词，正是同一思路。区别在于本书的 Rewrite 还能结合 Ontology 知道哪些对象相关，比纯靠 LLM 更准。来源：Foundry Ontology 文档，Ontology augmented generation

顺带提一个反直觉的点：模型上下文窗口越来越大之后，语义检索未必总是必需的。Foundry 的文档也承认，如果完整上下文能塞进窗口（比如 128K 能装 300 多页文本），可以先不检索、直接全量注入 prompt，等真正需要时再引入检索。但这不等于"窗口大就不用管上下文"——窗口填满之前，模型的有效注意力早就开始衰减了（这见第 7 章的压缩设计）。所以策略是"能塞则塞、塞不下才检索"，而不是非此即彼。来源：Foundry Ontology 文档，Ontology augmented generation

Retrieval Merge

多个 Retriever 返回结果后，统一转换成 Retrieval Result——可能是 Object、Document、Event、Metric、Action。Merge 之后形成 Context Candidate，供后续排序。

这一步的关键是统一格式——不管来自哪个 Retriever，都映射成第 2 章的对象类型。这是让"六路检索"能被统一处理的前提。

Retrieval Ranking

Ranking 不再仅计算 Similarity，而采用多因子评分。检索阶段的粗排只用于多路结果合并后的去重排序，完整的多维评分公式与因子定义（Relevance、Freshness、Importance、Authority、Permission、Distance、Token Cost 等）以第 6 章 Context Ranking 为权威契约，本章不重复定义。

注意 Token Cost 是负向因子——价值接近时，优先选低 Token 的对象。这是为后面的压缩阶段服务的。Ranking 输出 Top-N Context。

为什么检索完了还要专门排一道序？因为"检索到"不等于"放对了位置"。一项多文档问答的实验发现：当相关文档被放在上下文的中间时，模型准确率比放在首尾下降超过 30%——这条 U 型曲线跨模型、跨任务成立，连专门为长上下文训练的模型也躲不开。来源：Liu et al., 2024a，转引自 Li et al., 2026, §5.1

这意味着 Retrieval 的产物不能一股脑塞进 Prompt，必须先排序：重要的对象往前放，冗余的往后挪甚至剔掉。这正是 CRF 这一层粗排、以及第 6 章最终精选要解决的问题——它们共同回答的不只是"找到了什么"，还包括"按什么顺序给模型看"。

需要说明：这里的 Ranking 是检索阶段的粗排，最终的候选选择属于第 6 章的 Context Ranking。两层的区别在于，CRF 的 Ranking 是多路结果合并后的去重排序，第 6 章是从候选里精选进 Prompt 的最终选择。

Context Builder

Hybrid Retrieval 不直接返回 Prompt，而返回 Context Object。比如一次检索可能返回：Experiment、Dataset、GPU、Feature、Notebook、Commit、Evaluation 这一组对象。

Context Builder 负责把它们组装成候选 Context——它做 Object Merge，形成完整的候选 Context。注意 Context Builder 只负责组装，不负责决定检索策略（那是 Orchestrator 的事），也不负责最终选择（那是第 6 章的事），更不负责压缩——Graph Expansion 是第 5 章的独立阶段，Compression 是第 7 章 Context Optimizer 的职责，都不由 Context Builder 承担。

API 设计

统一接口，所有 Retriever 都实现它：

type Retriever interface {
    Name() string
    Retrieve(ctx Context, query Query) ([]RetrievalResult, error)
}

支持动态注册——新增一个 Retriever 不需要重启系统。这让 CRF 可以持续扩展新的检索能力。

输出格式

统一输出 Context Package，这也是第 2 章的契约：

ContextPackage
├── Objects
├── Relations
├── Documents
├── Events
├── Metrics
├── Actions
├── Confidence
└── Trace

Context Engine 后续所有模块，都基于 ContextPackage 工作。这就是为什么第 2 章要把它定义成全书唯一的契约——CRF 的输出就是它的输入，格式必须对齐。

演进方向：从检索到 Query Optimizer

这个模块被命名为 Context Retrieval Framework，不是偶然。因为它负责 Query Planning → Routing → Retrieval → Merge → Candidate Context 的完整流水线，更接近数据库中的 Query Optimizer，而不只是向量搜索。

后续实现可继续补充 Query Planner、Retriever Router、Context Merger 和 Context Trace。但要记住职责边界：最终候选选择、压缩和运行时管理仍分别归属第 6、7、8 章。CRF 到 Candidate Context 为止，不越界。

MVP

分三个阶段：

  • 第一阶段：Keyword、Vector、SQL Retriever + Merge + Ranking + Context Builder；
  • 第二阶段：Graph、Streaming、Tool Retriever；
  • 第三阶段：Query Rewrite、Context Cache、Context Trace、Adaptive Routing。

本章小结

Hybrid Retrieval 的目标不是"检索文档"。而是从企业所有知识源中，统一检索对象、关系、事件、指标、动作，最终构建 Agent 可直接消费的 Context。

从企业所有知识源中，统一检索对象（Object）、关系（Relation）、事件（Event）、指标（Metric）、动作（Action），最终构建 Agent 可直接消费的 Context。
