第 13 章 · Multi-Agent Context

Context 才是共享资产

多 Agent 协作，最常见的做法是让 Agent 之间互相发消息。但消息越传越长，Token 越烧越多，信息还容易对不上。Context Engine 换了个思路：多个 Agent 基于统一的 Context Package 协同工作，而不是通过 Prompt 或 Message 传递信息。本章聚焦多 Agent 如何共享、引用和演化 Context。

模块定位

Multi-Agent Context 是 Context Engine 在多 Agent 协作场景下的上下文共享机制。它的职责是让多个 Agent 基于统一的 Context Package 协同工作，而不是通过 Prompt 或 Message 传递信息。

核心观念转换：Context 是共享资源，Agent 是 Context 的消费者（Consumer）和生产者（Producer）。Agent 不是自治的孤岛，而是围绕同一份 Context 协作的角色。

为什么需要 Multi-Agent Context

看传统 Multi-Agent 怎么工作：

问题一堆：Prompt 越来越长、信息不断重复、Token 成本持续增加、Context 不一致、无法追踪来源。每经过一个 Agent，消息就胖一圈，最后那个 Agent 收到的可能是一坨冗余信息。

Context Engine 的做法是共享：

所有 Agent 共享统一 Context。Agent 之间不直接通信，而是通过读写共享的 Context Package 协作。这把"消息传递"变成了"共享状态"——就像多个线程操作同一块内存，而不是互相发邮件。

但共享是有代价的，得讲清楚边界。把上下文在 agent 之间完整共享，会产生更大的 prefill，还会消除跨不同系统提示的 KV-cache 复用——这正是第 9 章把"缓存命中"看得那么重的原因。生产实践给出的折中是：简单子任务可以不共享上下文，让子 agent 用独立窗口只回传一个 1,000–2,000 token 的精炼摘要；只有真正需要共享状态的复杂子任务，才把完整上下文传过去。换句话说，"共享 Context"不是无脑全量共享，而是按任务类型在共享与隔离之间显式取舍。来源：Li et al., 2026, §5.6 引 Anthropic

Context Package

所有 Agent 统一输入：

ContextPackage
├── Objects
├── Relations
├── Events
├── Metrics
├── Actions
├── Memory
├── Metadata
└── Trace

Agent 不关心数据来源，只消费 Context。注意这里比第 2 章多了 Memory——多 Agent 场景需要共享记忆，这是协作的基础。

Agent 职责

每个 Agent 的职责统一抽象成五步：

读取 Context → 推理 → 执行 Tool → 更新 Context → 提交 Runtime。而不是直接调用其他 Agent。这个"提交 Runtime"很关键——Agent 不把结果发给另一个 Agent，而是写回共享 Context，由 Runtime 决定谁接下来读。

Agent Collaboration

一个典型的协作场景：Research Agent 训练模型，生成 Checkpoint 和 Evaluation。Business Agent 自动读取最新的 Checkpoint，无需重新 Retrieval。

这就是共享 Context 的威力——一个 Agent 的产出，自动成为其他 Agent 的输入，不需要任何显式的消息传递。

这套"共享而非传递"的思路，再往外推一步就是跨组织协作。Palantir Foundry 的 Shared Ontology 机制解决的就是这个场景：它让多个组织在同一套共享工作流下协作，本体放在专门的 shared space 里，自动继承组织标记（organization markings）和角色授权（role grants）——典型用途是和客户、合作方在同一套本体上联合建模、联合数据交换。本章的"Context 才是共享资产，Agent 只是执行者"和后续的 Context Federation，可以借鉴这种"独立共享空间 + 标记与授权继承"的模式：跨组织共享的不是某一方的私库，而是一块带好权限标记的共享领地，各方按既有授权读写。来源：Foundry Ontology 文档，Shared ontologies

把这种协作方式放回更大的图景里看。学术界把多 agent 编排归纳成五种模式：层级编排（上层控制器分发任务）、团队编排（一组带名字的专职 agent 协同）、工作流编排（按显式阶段组织）、扇出（并行探索多种方案）、图组合（用交互图表达多种协调模式）。本书的"共享 Context"属于团队编排这一类，并且天然支持 planner-generator-evaluator 这种把规划、执行、验证拆成独立角色的结构——因为角色之间靠读写同一份 Context 协作，比靠消息传递更容易做到职责分离又状态一致。来源：Li et al., 2026, §6.3

Sub-agent 生命周期：从共享到可调度

五种编排模式回答了"agent 之间怎么协作"，但还有一个更底层的问题没回答：主 agent 启动一个子 agent 之后，这个子 agent 的生命周期怎么管——怎么启动、怎么等它、怎么查它的进度、出了问题怎么取消、跑完怎么把结果收回来。harness 工程把这一层叫"子代理与后台任务"，并给出一组标准的生命周期原语：

原语语义
spawn启动一个子 agent 任务
resume从中断点恢复一个已暂停的子 agent
wait阻塞等待子 agent 完成
list列出当前所有子 agent 及其状态
close正常结束并回收一个子 agent
interrupt强制中止一个失控或超时的子 agent

这组原语补上了本书从"共享 Context"到"可调度执行"之间缺的一环：前面讲的 Ownership、Version、Lock 解决的是"多个 agent 读写同一份 Context 时不打架"，但这组原语解决的是"主 agent 怎么把活派出去、又怎么把结果收回来"。它和第 8 章的 Context Event（ContextCreated / ContextUpdated …）是配合关系——spawn/close 对应子 agent 生命周期事件，wait/list 让主 agent 能对自己的执行历史做推理，而不是 fire-and-forget 之后什么都看不见。来源：Lilian Weng, Harness Engineering for Self-Improvement, 2026, §1 Pattern 3

这里有一条容易踩漏的纪律：并行必须是显式且可检查的。如果子 agent 的输出只存在于临时的会话上下文里，它很快就会过时，而且一旦主 agent 中断就再也看不见——主 agent 无法对自己的执行历史做推理，也无法在中断后恢复。所以子 agent 的中间状态必须结构化落盘（日志、状态记录、产出物），而不是只活在 chat context 里。这和第 8 章"Context 状态落盘而非只存快照"、第 10 章"Trace 每条存一个文件"是同一条原则在不同层的体现：能落盘的不要留在内存里，能结构化的不要留在自由文本里。来源：Lilian Weng, Harness Engineering for Self-Improvement, 2026, §1 Pattern 3

Context Update：Delta 而非全量

Agent 完成任务后，提交 Context Delta：

新增: Checkpoint
新增: Evaluation
更新: Metric

Runtime 自动 Merge。Delta 是增量的——Agent 只提交自己改动的部分，而不是把整个 Context 重发一遍。这和第 8 章的 Incremental Update、第 7 章的 Progressive Context 一脉相承。

Ownership 与 Version

Context 不是 Agent 私有，而是 Runtime 的。所有修改统一提交。这意味着没有哪个 Agent "拥有"Context——它们都是租户，Runtime 才是房东。

每次 Context 变化生成 Version：

支持 Rollback、Replay。如果某个 Agent 改坏了，可以回滚到上一个版本。

Context Lock：并发安全

多个 Agent 同时修改同一对象时，Runtime 负责 Object Lock、Version Check、Merge Conflict，保证一致性。没有锁的并发修改会互相覆盖——这是共享状态系统必须解决的问题，和数据库的乐观锁/悲观锁是一回事。

Context Subscription

Agent 可以订阅 Context。Research Agent 订阅 Experiment，Business Agent 订阅 Forecast，Operation Agent 订阅 Alarm。对象变化自动通知。这让 Agent 不需要轮询——它关心的对象一变，就被推送到。

Context Event Bus

所有 Context 变化进入 Event Bus：

Create / Update / Delete / Merge / Snapshot

支持异步协作。Event Bus 是订阅机制的底层——变化先入 Bus，再分发给订阅者。

Context Permission：共享但权限不同

所有 Agent 共享 Context，但权限不同：

Agent权限
Research Agent可以访问 Checkpoint
Business Agent不能访问 Checkpoint
Operation Agent只能访问 Deployment

Runtime 统一 ACL。共享不等于无差别可见——每个 Agent 只能看到它有权看的部分。这是第 0 章原则 2（Agent 只消费经过授权的 Context）在多 Agent 场景的落实。

Context API

type ContextRuntime interface {
    // 基础生命周期，见第 8 章 §15
    Create()
    Load()
    Update()
    Merge()
    Snapshot()
    Archive()
    // 多 Agent 扩展
    Subscribe()   // 订阅 Context 变化
    Publish()     // 发布 Context 变化
}

所有 Agent 统一协议。基础生命周期接口以第 8 章 §15 为准（Create / Load / Update / Merge / Snapshot / Archive），多 Agent 场景在此之上扩展 Subscribe 和 Publish——这是多 Agent 协作需要的，让 Agent 能订阅彼此产生的 Context 变化。

多 Agent 示例

用户："为什么今天预测误差变大？"

Research Agent 负责模型、训练、Checkpoint；Business Agent 负责天气、风场、设备；Operation Agent 负责 GPU、Deployment、Runtime。三个 Agent 共享同一 Context，共同生成最终答案。每个 Agent 不需要知道另外两个在干什么——它们通过共享 Context 隐式协作。

Context Protocol：像 HTTP 一样的协议

更进一步，多 Agent 协作需要一套标准协议，就像：

  • HTTP——页面通信；
  • SQL——数据查询；
  • Kubernetes API——容器编排。

Context Protocol 的消息类型：

协议约束：协议消息必须携带 schema_version、context_id、tenant、provenance 和权限声明；发生版本冲突时优先返回可合并的 ContextDelta，而不是静默覆盖。

这条约束很重要——静默覆盖是多 Agent 系统最危险的故障模式。两个 Agent 同时改同一对象，如果一个静默覆盖另一个，数据就丢了。优先返回可合并的 Delta，让冲突显式化，才能保证一致性。

学术侧把这条思路推得更远：当 planner 把工作交给 executor、agent 调用工具、subagent 交还控制权、或系统升级到人时，这个交接不应该只传一段文本摘要，而应该一并携带意图、约束、权限、artifact、溯源、预算状态、风险等级、trace 历史和未决决策。本书的 Context Package 已经天然承载了其中大半——objects/relations/provenance/trace/policy 字段都在。缺口主要在预算状态和风险等级，可以作为后续协议版本的补充。来源：Li et al., 2026, §12.4

本章小结

Multi-Agent 的核心不是 Message Passing，而是多个 Agent 基于统一 Context Package 协同推理、协同执行、协同更新。Context 才是共享资产，Agent 只是不同角色的执行者。
