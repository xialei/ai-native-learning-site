AI Native Context Engine. 第 1 章 · 总体架构
第 1 章 · Overall Architecture

系统的边界在哪

在动手实现任何一个模块之前，得先把一件事说清楚：Context Engine 到底管什么、不管什么。边界划不清的系统，最后都会变成什么都要管的怪物。这一章只做一件事——把 Context Engine 放进整个 AI 平台里，告诉你它站在哪、对着谁、做什么。

设计目标

Context Engine 是 AI Platform 的智能中间层。它的位置很具体：夹在 AI Gateway 和企业数据之间。它干的活是把企业数据——那些躺在数据库、数据湖、Git、MLflow、Kafka 里的原始东西——转换成 Agent 能理解、能推理、能执行的 Context。

注意这里的措辞是"转换"，不是"搬运"。Context Engine 不是另一个数据管道，它产出的不是数据，而是上下文。这个区分贯穿全书。

它要达成四个目标：

  • 统一上下文构建能力——不管数据来自哪个系统，出来的 Context 都是同一份契约；
  • 支撑多种 Agent——Research Agent、Business Agent、Coding Agent、Ops Agent，共用一套上下文基础设施；
  • 屏蔽底层数据源差异——Agent 不需要知道 MLPipeline 长什么样、SCADA 协议是什么；
  • 提供权限、优化、可观测能力——这三件事不是可选增强，是上线的前提。

平台定位：它站在哪

这是全书最重要的一张图。如果只记一个东西，记这个垂直堆栈：

这个堆栈里每一层都有明确的职责，而 Context Engine 的职责是所有层里最难外包的：它要既懂业务语义，又懂权限治理，还要懂怎么把结果压缩进有限的 Token 窗口。Gateway 只管路由，数据平台只管存取，中间这一层才是"把数据变成 Agent 能用的东西"的地方。

一个判断标准：如果你的 Agent 需要自己去连数据库、自己判断权限、自己拼关系——那说明你缺的不是更好的 Agent，而是缺一个 Context Engine。

这个判断有学术界的共识撑腰。一篇 2026 年的综述把这件事概括成"约束瓶颈论点"：基础设施质量，而不只是模型能力，决定了真实世界 agent 可靠性的天花板。Context Engine 正是为这条瓶颈专门设的一层——它不是"锦上添花"，而是"没有它就过不了线"。来源：Li et al., 2026, §1/§13

六层架构

从上到下，整个平台分成六层。Context Engine 本身只是其中一层，但它是把上下游串起来的那一层。

这六层不是随手分的，每一层的边界对应一个清晰的职责切换：

  • Agent Layer负责推理和执行，它只消费 Context，不关心上下文怎么来的；
  • Context Runtime负责 Context 的生命周期——创建、更新、快照、恢复，让上下文在多轮推理里"活起来"；
  • Context Engine负责把数据加工成 Context 的核心流水线——检索、扩展、排序、压缩；
  • Knowledge Runtime是知识的统一抽象层——Entity、Relation、Event、Metric、Action、Policy；
  • Storage提供对象存储、图索引、向量、全文检索和缓存；
  • Infrastructure是 Kubernetes、Paimon、Fluss、Kafka 这些底层组件。

本书主要讲第 2、3、4 层。第 5、6 层会提到选型建议，但不深入——那是另一个领域的话题。

把这套架构放回学术坐标里，能看清楚 Context Engine 的定位。学术界有人把围绕 agent 的基础设施分成七层（ETCLOVG）：执行环境、工具接口、上下文、生命周期、可观测、验证、治理。本书深耕的正是其中的"上下文"层，并自然延伸到生命周期（第 8 章）、可观测与验证（第 10 章）、治理（第 0 章的 Policy 硬约束）——这和学术侧把可观测与治理"从生命周期钩子里提升为独立层"的判断是一致的。来源：Li et al., 2026, §2.3

换一个更直白的说法：Context Engine 就是一个 harness——包裹在基座模型外层、决定模型如何获取上下文、如何推理、如何调用工具、如何管理状态的那套运行时系统。harness 工程文献给出一条优化对象演进链：指令 prompt → 结构化上下文 → workflow → harness 代码 → optimizer 代码。模型越强，优化目标越该往右移——从手写规则走向可执行的搜索空间。这条链和本书的章节顺序几乎同构：第 3 章建结构化上下文（Knowledge Builder），第 4–6 章是 workflow（检索→扩展→排序），第 7 章是 optimizer（压缩与 Token 分配），第 8 章是 harness 运行时（Runtime）。把它记住，后面每一章都知道自己在整条链上的位置。来源：Lilian Weng, Harness Engineering for Self-Improvement, 2026, §4

核心模块与边界

这是全书后续章节的地图。Context Engine 内部拆成若干模块，每个模块边界必须划清楚——这是系统能不能调试的关键。

在拆之前，先借一个外部参照系对齐认知。Palantir Foundry 把 Ontology 拆成四大组成：对象与链接类型（把数据映射成对象）、动作类型与函数（让对象可被修改、可执行）、接口（多态建模）、应用层（视图、Workshop 等深度集成）。这四块和本书的分层是同构的——Foundry 的"对象与链接"对应第 4 层 Knowledge Runtime，"动作与函数"对应 Action 模型，"接口"对应第 11/12 章的领域插件。本书的差异在于：Foundry 止步于 Ontology 到应用，本书在它之上多了运行时、缓存、可观测和多 Agent 协作这几层 AI 时代特有的需求（第 14 章会专门对比）。来源：Foundry Ontology 文档，Ontology 概览

几个最容易混淆的边界，提前说清楚：

Context Builder vs Ranking vs Optimizer vs Prompt Builder

这几个名字听着像，干的活完全不同。Context Builder 负责组装——把各阶段结果拼成第 2 章定义的 Context Package，它不决定检索策略，也不决定留谁删谁，更不负责压缩。Context Ranking 负责选择——从候选里挑出最值得进 Prompt 的。Context Optimizer 负责压缩——去重、合并、摘要、Token 分配。Prompt Builder 负责装配——把 Optimizer 输出的 Context Package 组织成模型可消费的结构化 Prompt。

为什么非得拆开？因为如果让一个"智能检索"把组装、选择、压缩、装配全干了，出了问题你根本定位不到是哪一步出了错。分开之后，每一步都有明确的输入输出契约，每一步都能单独观测。

Intent Planner：意图驱动

还有一个容易漏的模块：Intent Planner。它负责解析用户意图，决定后续阶段的策略——Retriever 怎么路由、Graph Expansion 往哪个方向扩（第 5 章 §16.2）、Context Optimizer 压什么留什么（第 7 章）。没有它，扩展和压缩就是写死的 Hop 规则；有了它，同一个对象在不同问题下会扩出不同的上下文。Intent Planner 让整条流水线从"固定图遍历"升级为"上下文规划"。

Policy Engine 是硬约束

Policy Engine 管 ACL、脱敏、审计。它不是排序时可以权衡的"特征分"，而是一道硬门——任何对象进最终 Package 之前都必须过。这意味着哪怕某个对象相关性得分极高，只要权限不通过，它就进不来。这条原则在第 0 章讲过，这里落实成具体模块。

Knowledge Builder 是上游入口

Knowledge Builder 自动从数据里抽取 Entity、Relation、Event、Metric、Action。它是整个系统的入口，也是知识质量的源头。没有它产出高质量的 Ontology，后面所有模块都是无米之炊。这是第 3 章的主题。

读这张图有几个要点：

  • Graph Expansion 在 Retrieval 之后——先找到入口对象，再沿着关系补全上下文；
  • Policy Filter 在 Ranking 之前——权限是硬约束，先过滤再排序，而不是降分处理；
  • Context Optimizer 在最后——选完之后才压缩，压缩是为最终的 Token 窗口服务的。

Context Package

流水线的终点产物是一个 Context Package。它是第 2 章定义的唯一契约，这里先看一眼它的样子，建立直觉（字段以第 2 章 §8 为权威定义，本章不重复）：

context:
  objects: []
  relations: []
  events: []
  metrics: []
  actions: []
  documents: []
  provenance: []
  schema_version: "1.0"
  policy: {}
  trace: {}
  token_budget: 24000

Agent 只消费 Context Package，而不是直接消费 Prompt。这是一个根本性的转变：传统做法是系统产出一段 Prompt 文本，这里系统产出的是一个结构化对象，Prompt 只是它在最后一步的渲染结果。结构化意味着可追溯、可回放、可评测——这些是第 8 到第 10 章的基础。

API

Context Engine 对外暴露六个核心接口。它们的命名本身就是一份使用说明：

接口职责
BuildContext()构建一份新的 Context Package
ExpandContext()对已有 Context 做图扩展
OptimizeContext()压缩、分配 Token、组装 Prompt
MergeContext()合并多来源的 Context（工具结果、记忆、实时数据）
ExplainContext()解释某份 Context 为什么是这样组成的
SnapshotContext()对 Context 做快照，用于回放和审计

注意这套 API 不是 REST 风格的"资源增删改查"，而是一组面向上下文生命周期的动词。这反映了 Context Engine 的本质——它管理的是一个持续演化的对象，不是一堆静态记录。

MVP：先跑起来

不要一上来就建整个六层架构。第一阶段只需要这条最小回路：

  • Entity / Relation 抽取（Knowledge Builder 的核心）；
  • Hybrid Retrieval（至少 Keyword + Vector）；
  • 一跳 Graph Expansion（先别搞多跳）；
  • Context Builder（能产出 Context Package）；
  • Token Budget（能塞进模型窗口）；
  • Context Trace（能知道发生了什么）。

这套 MVP 足以支撑一个能用的 Research Copilot。后面章节会讲每一块的完整设计，但落地时请克制——MVP 先把这条回路跑通，比什么都有说服力。

本章小结

Context Engine 是 Agent 与企业数据之间的治理和推理中间层。它把离线的知识构建、在线的 Context 生成、运行时的生命周期管理三件事连接起来，同时保证权限、证据和可观测性贯穿全链路。

记住三件事：它的位置在 Gateway 和数据之间；它的产物是结构化的 Context Package 而非 Prompt 文本；它的内部模块职责必须分离到可调试的粒度。
