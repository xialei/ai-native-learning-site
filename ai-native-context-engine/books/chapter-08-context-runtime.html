AI Native Context Engine. 第 8 章 · Context Runtime
第 8 章 · Context Runtime

让上下文活起来

传统 RAG 里，Context 的生命只有一次：拼一次 Prompt，喂给模型，结束。但 Agent 不是这么工作的——它会调工具、看结果、再推理、再调工具。整个过程里 Context 一直在变。这一章讲怎么管理这个持续演化的运行时状态。本章聚焦单 Agent / Session；多 Agent 共享见第 13 章。

模块定位

Context Runtime 是整个 AI Knowledge Runtime 的运行时核心。它的职责是负责 Context 的创建、更新、演化、共享和生命周期管理。

核心转变：Context 不再只是 Prompt，而是 Agent Runtime 的状态。这一句话是本章的全部要旨。Prompt 是一次性的输入，状态是持续维护的对象——这两者的工程含义完全不同。

这里要把三种"状态"分清楚，否则很容易混。第一类是喂给模型推理的信息（检索结果、记忆、对话历史）——那是第 4–7 章的上下文。第二类是系统自己用来继续和协调执行的状态（待办子任务、检查点、重试、共享 artifact）——那是本章 Runtime 管的运营状态。第三类是观测记录（Trace、日志、监控）——那是第 10 章的事。学术界也特意把这三类分开，避免"状态"这个词被笼统使用而搅在一起。来源：Li et al., 2026, §6.1

Runtime 架构

Context Runtime 统一管理所有 Context。Agent 不直接碰存储，也不直接碰 Context Engine——它只和 Runtime 对话。Runtime 负责协调 Store、Engine、Tool、Memory、Realtime 这些数据来源。

这条抽象链路在真实运行时里长什么样？开源运行时 Pi 把 Expand→Optimize→Consume 实现成一个纯函数三段管线：先把会话分支上的全部条目（Entry）过一遍 transform——决定哪些留下、哪些被压缩替换（第 7 章的 Optimizer 在这步介入）；再对每个条目 project——投影成 0 到 N 条喂给模型的消息（一次压缩条目会展开成"摘要 + 被保留的近期消息"两条以上）；最后派生状态从原始分支只读地推出"当前用什么模型、开哪些工具"。三段职责分离，而且状态派生读的是压缩前的完整分支——也就是说，远期对话被压成摘要了，但"当前模型配置"仍能从历史里重放重建。这套管线在每次调用模型前重跑一次，所以 Context 不是被存下来的快照，而是会话树的派生视图，模型永远拿不到陈旧上下文。来源：Pi Agent Harness 源码，packages/agent/src/harness/session/context.ts

Session 把一次 Agent 任务的所有状态打包在一起：谁在用、目标是什么、当前 Context、历史、记忆、快照。这让一次 Agent 会话成为一个可管理、可恢复的单元。

快照还承担一个治理含义。安全研究正在形成一个新共识：上下文不该被当成"被动的提示素材"，而该被当成受治理的状态——和数据库里的记录一样，它要可审计、可校验、在输出前重新过权限。Snapshot 和 Version 就是把这条原则落地的基础设施：每一次状态变更都被记录、可回溯、可在事后校验是否越权。来源：Li et al., 2026, §9.6 引 Kim et al., 2026

Context Update：增量，不是重算

Tool 执行后，Context 更新。比如：

Deploy() → Deployment Status → Context Update

不是重新 Retrieval，而是 Incremental Update。这是 Runtime 存在的核心价值——如果每次工具调用都要重新检索一遍，Agent 就退化成了"每次都从零开始"的 RAG。增量更新只把新的 Observation 合并进现有 Context，快且省。

这背后是个经典的取舍：无状态重放（从交互历史重建执行，利于可复现、可审计，但轨迹变长后很贵）还是有状态执行（把状态持久化到文件、库、任务图，利于连续和恢复，但带来一致性难题）。业界主流做法是混合——既保留可回放的交互历史，又依赖持久 artifact。本章的 Snapshot + 增量 Update，正是这种混合模式的落地：快照保证可回放，增量更新保证连续性。来源：Li et al., 2026, §6.1–6.2

Context Merge

多个来源的更新要统一 Merge：

Tool 的结果、记忆、实时数据、检索结果，统一 Merge 形成最新 Context。Runtime 是这个 Merge 的协调者——它知道哪个来源优先级高、哪个该覆盖哪个。

"该覆盖哪个"这件事不能含糊，必须有显式的冲突解决策略。Palantir Foundry 的对象实例就是一个典型：它既能被输入数据源更新，也能被用户 Action 编辑更新，当同一个对象（同一主键）同时收到两边的数据时，平台需要一套冲突解决策略决定最终值以谁为准。本书的 Merge 也一样——Tool 结果、记忆、实时数据、检索结果可能指向同一个对象的不同值，Runtime 不能默认"后到的覆盖先到的"，而要按来源优先级和业务规则明确裁决，否则上下文会出现自相矛盾的字段。来源：Foundry Ontology 文档，Action types

Version 与 Diff

Context 支持 Version。v1 → v2 → v3，方便 Rollback、Audit、Replay。

更实用的是 Context Diff：两个 Context 比较。比如：

GPU
  90% → 95%

Diff 自动生成，Agent 无需全部重新读取。它只需要知道"什么变了"——这和第 7 章的 Progressive Context 理念一致，只传递增量。

Version 和 Snapshot 让上下文演化有了沙箱保护。这个思路工业上有成熟对应物。Palantir Foundry 的 Scenario 机制就是对 Ontology 的一次"分支"——所有假设分析的编辑都只存在于隔离沙箱，不影响主 Ontology；只有当结论被采纳时，"Apply scenario"才把所有暂存编辑作为单一事务原子提交回去。它一旦创建就不可变，要改得新建或复制一个；单个场景最多 30000 次编辑；合并还得在 Action 的安全策略里配足权限，因为合并相当于一次性批量改生产数据。本书第 8 章的 Snapshot（Tool 执行前后打点）和 Version（v1→v2→v3 支持 Rollback/Replay）可以借鉴这套"fork-验证-原子合并"模型——尤其是"采纳时才作为单次事务提交"这点，能避免半截更新污染主线。来源：Foundry Ontology 文档，Ontology scenarios

Share 与 Lock

Context Share：多个 Agent 共享同一 Context。Research Agent、Business Agent、Coding Agent 共享同一个 Experiment，无需重复 Retrieval。这避免了每个 Agent 各自检索一遍的浪费。多 Agent 的细节见第 13 章。

Context Lock：多个 Agent 同时修改同一 Object 时，Runtime 负责加锁，避免冲突。没有锁的并发修改会互相覆盖，导致数据丢失。

Context Event Bus

所有变化产生 Event：

ContextCreated
ContextExpanded
ContextUpdated
ContextMerged
ContextArchived

统一进 Event Bus。这让 Context 的变化可以被订阅——别的 Agent 或监控系统可以感知到"这个 Context 更新了"。这是异步协作的基础。

Event Bus 最小该怎么落地？参考实现里有一个干净的切法：把"内容流"和"操作账本"物理拆成两条。Pi 就这么做——会话树上只存 内容条目（消息、压缩检查点、分支摘要、模型/工具变更），另起一条操作记录（operation_started / operation_finished / step_attempt / tool_started / usage）专门记运行时元数据：谁启动了这次操作、哪一步在哪重试、这次调用花了多少 token、为什么触发压缩。内容条目是 Agent 看到的对话，操作记录是 Runtime 的账本，两者分开存储、独立查询。这么做还有一个意外收益：恢复时只查"未完成的 operation_started"——零条说明空闲、一条说明挂起需续跑、两条以上就是损坏要报错。本书的 Event Bus 可以借鉴这条"内容与账本分离"的纪律：ContextCreated 这类事件不该混进 Context Package 本身，而要落在一条可独立审计的侧带上。来源：Pi Agent Harness 源码，packages/agent/src/harness/session/types.ts

Context Store：分层存储

建议分层：

层级存储用途
Hot ContextRedis当前活跃会话，最快
Warm ContextPaimon近期会话，可恢复
Cold ContextObject Storage历史归档，长期保存

分层让存储成本和访问速度匹配——热数据放 Redis，冷数据放对象存储。这和第 9 章的 Cache 分层是配套的。
