KV cache 家族：槽位、双缓存与 context shift

上一章的 FAILED_PREPARE 几乎都发生在这里。llama.cpp 的 KV cache 是一个「格子本」：每格记 pos 和一个序列集合，找槽就是在格子里划出连续空位。

4.1unified 与分序列：两种 KV 布局

构造 KV cache 前先回答一个问题：所有序列共享一个大缓存，还是每序列一个独立缓存？kv_unified 参数决定：

src/llama-context.cpp:287-302 — n_ctx_seq 的划分（摘录，注释为译注）
c++cparams.kv_unified = params.kv_unified;

// ref: https://github.com/ggml-org/llama.cpp/pull/17046#discussion_r2503085732
cparams.n_ctx = GGML_PAD(cparams.n_ctx, 256);

if (cparams.kv_unified) {
    cparams.n_ctx_seq = cparams.n_ctx;      // 共享：每序列可用全部 context
} else {
    cparams.n_ctx_seq = cparams.n_ctx / cparams.n_seq_max;
    cparams.n_ctx_seq = GGML_PAD(cparams.n_ctx_seq, 256);
    if (cparams.n_ctx_seq == 0) {
        throw std::runtime_error("n_ctx_seq == 0");
    }
    // ...保证 n_ctx == n_ctx_seq * n_seq_max，余量不丢
}

这个选择一路传到 cache 构造函数，变成「流」的数量：

src/llama-kv-cache.cpp:84-88 — n_stream（摘录）
c++model(model), hparams(hparams), v_trans(v_trans),
    n_seq_max(n_seq_max), n_stream(unified ? 1 : n_seq_max), n_pad(n_pad), n_swa(n_swa), swa_type(swa_type),
读懂这段： unified 模式下 n_stream=1——所有序列写进同一片 cells，靠 find_slot 动态分槽，总容量就是 n_ctx；分序列模式下 n_stream=n_seq_max，每片 cells 独占 n_ctx_seq 个格子，互不侵占。前者吞吐高（并发请求共享空间）但互相干扰，后者隔离好但容量利用率低。llama-server 默认开 unified（slot 共享一个 context 的前提）。

4.2cells：格子本的数据结构

每片 cells 是一个 llama_kv_cells——只存元信息，不存 K/V 数据本身：

src/llama-kv-cells.h:34-50 — llama_kv_cells（摘录，注释为译注）
c++// meta information about KV cells that can be part of multiple
// sequences at the same time
class llama_kv_cells {
public:
    using seq_set_t = std::bitset<LLAMA_MAX_SEQ>;

    void reset() {
        for (uint32_t i = 0; i < pos.size(); ++i) {
            pos[i]   = -1;          // -1 = 空格子
            ext[i].reset();
            shift[i] =  0;
            seq[i].reset();          // 序列集合：bitset，一格可属多个序列
        }
        has_shift = false;
        ...
    }
读懂这段： 每个格子四件套：pos（该位置的 RoPE 位置，-1 空）、ext（多维位置：图像 token 的 x/y 坐标）、shift（待平移量，K-shift 用）、seq（bitset——一格可以同时属于多个序列，这是 prefix 复用的基础：两个请求共享的 prompt 片段只占一份格子）。「数据」（K/V 张量）与「记账」（cells）分离：cells 告诉你格子 i 存的是哪个序列的哪个 pos，K/V 只按 idx 寻址。

4.3find_slot：找槽算法

decode 里每次 init_batch 都会调 find_slot(ubatch, cont)。核心是一个 head 指针的环形扫描：

src/llama-kv-cache.cpp:1001-1018 — find_slot 回卷与连续槽（摘录，注释为译注）
c++uint32_t head_cur = v_heads[seq_to_stream[seq_id]];

// head 前面还有足够空格子 → 回到开头找，期望把缓存「填满」
// （head 只增不减的话，环形空间会从尾部开始浪费）
if (head_cur > cells.get_used() + 2*n_tokens) {
    head_cur = 0;
}

if (n_tokens > cells.size()) {
    LLAMA_LOG_ERROR("%s: n_tokens = %d > size = %u\n", __func__, n_tokens, cells.size());
    return { };
}

uint32_t n_tested = 0;

// 连续槽：一次测整个 ubatch 能否放下；非连续：逐个 token 测
const uint32_t n_test = cont ? n_tokens : 1;

格子可用性的判定（完整版，含 SWA 复用）：

src/llama-kv-cache.cpp:1039-1061 — can_use 判定（摘录，注释为译注）
c++// can we use this cell? either:
//  - the cell is empty
//  - the cell is occupied only by one sequence:
//    - mask SWA, using current max pos for that sequence in the cache
//                always insert in the cell with minimum pos
bool can_use = cells.is_empty(idx);

if (!can_use && cells.seq_count(idx) == 1) {
    const llama_pos pos_cell = cells.pos_get(idx);

    if (!can_use) {
        const llama_seq_id seq_id_cell = cells.seq_get(idx);

        // SWA mask：这个格子里的 pos 已经滑出滑动窗口 → 可覆盖
        if (llama_hparams::is_masked_swa(n_swa, swa_type, pos_cell,
                cells.seq_pos_max(seq_id_cell) + 1)) {
            can_use = true;
        }
    }
}
读懂这段： 三个要点。① head 回卷：`head > used + 2*n_tokens` 时从头找——head 附近的「已用」格子其实早已被 SWA 滑出窗口或被 seq_rm 释放，从头扫能减少碎片；② cont 参数：因果注意力希望 ubatch 的 KV 落在连续格子上（注意力 kernel 按连续段 mask），失败就 clear 重来；非连续模式一格一格凑。说明：这条连续槽路径在当前锚点的所有调用点都传 false（src/llama-kv-cache.cpp:769、:2419），实现仍在、自动调度已不启用它；③ SWA 覆盖：滑动窗口外的格子等价于死数据，find_slot 直接把它当空位用——SWA 模型的 KV cache 自带「原地 recycling」。

全扫完还不够就返回空 slot_info——上一章看到的 FAILED_PREPARE 就是由这里触发的。

4.4iswa：滑动窗口的双缓存

Gemma-2/3 这类模型有「全局注意力层 + 滑窗注意力层」混合。llama.cpp 为它们造了两种 cache：

src/llama-kv-cache-iswa.cpp:52-81 — 双缓存的尺寸计算（摘录，注释为译注）
c++// chain filters：按 is_swa(il) 把层分到两个 cache
const layer_filter_cb filter_base = [&](int32_t il) {
    if (filter && !filter(il)) { return false; }
    return !model.hparams.is_swa(il);        // 非滑窗层 → base cache
};

const layer_filter_cb filter_swa  = [&](int32_t il) {
    if (filter && !filter(il)) { return false; }
    return  model.hparams.is_swa(il);        // 滑窗层 → swa cache
};

const uint32_t size_base = kv_size;

// note: the SWA cache is always padded to 256 for performance
//       https://github.com/ggml-org/llama.cpp/issues/17037
uint32_t size_swa = GGML_PAD(std::min(size_base,
        hparams.n_swa*(unified ? n_seq_max : 1) + n_ubatch), 256);

// when using full-size SWA cache, we set the SWA cache size to be equal to the base cache size
if (swa_full) {
    size_swa = size_base;
}
读懂这段： size_swa 的公式值得琢磨：滑窗层只需要 `n_swa + n_ubatch` 个格子（窗口 + 当前批），乘上序列数——相比 base cache 是巨大的节省。`--swa-full` 可以退回全尺寸（精度参考配置）。双缓存通过 llama_memory_i 同一接口对外（class llama_kv_cache_iswa : public llama_memory_i），decode 无感知；内部把 seq_rm/seq_cp/seq_keep/seq_add/seq_div 这些访问原语成对转发给两个子 cache，而 prepare() 则把 ubatch 拆成 sinfos_base / sinfos_swa 两组分头处理——按层切分的实质在这里。这里值得记住的模式：接口不变，实现按层切分。

4.5context shift：无限生成的诀窍

长文本生成超过 n_ctx 时怎么办？llama-server 的答案：保住开头、丢掉中段，剩下的位置号整体前移。默认保留 n_keep 个开头 token（system prompt 等），从 n_keep 之后删掉约一半（n_discard，可由 n_discard 参数指定），再把后面的位置号整体减掉 n_discard。这是两步操作：

tools/server/server-context.cpp:2912-2956 — slot 的 context shift（摘录，注释为译注）
c++// 触发条件：prompt + 生成中，长度逼近 n_ctx
if (slot.state == SLOT_STATE_GENERATING &&
        slot.prompt.n_tokens() + 1 >= slot.n_ctx) {
    ...
    // n_keep：保住开头的 system prompt 不被丢弃
    int n_keep = slot.task->params.n_keep < 0 ? slot.task->n_tokens() : slot.task->params.n_keep;
    if (add_bos_token) { n_keep += 1; }
    n_keep = std::min(slot.n_ctx - 4, n_keep);

    const int n_left    = slot.prompt.n_tokens() - n_keep;
    int       n_discard = slot.task->params.n_discard ? slot.task->params.n_discard : (n_left / 2);

    // ref: https://github.com/ggml-org/llama.cpp/pull/24786
    n_discard = std::clamp(n_discard, 0, std::max(0, n_left - 1));

    SLT_WRN(slot, "slot context shift, n_keep = %d, n_left = %d, n_discard = %d\n", ...);

    // 第一步：删掉中段（keep 之后 discard 个 token）的 KV
    slot.mem.seq_rm (slot.id, n_keep,             n_keep + n_discard);
    // 第二步：其余部分位置号整体前移 -n_discard
    slot.mem.seq_add(slot.id, n_keep + n_discard, slot.prompt.tokens.pos_next(), -n_discard);
    ...
}

但位置号只是「记账」。K 向量里烘焙的 RoPE 相位是跟着旧 pos 走的——所以还需要一次K-shift：用计算图把所有 K 重新施加位置差：

src/llama-kv-cache.cpp:857-883 — update() 里的 K-shift（摘录，注释为译注）
c++if (do_shift) {
    if (!get_can_shift()) {
        GGML_ABORT("The current KV cache / model configuration does not support K-shift");
    }

    // apply K-shift if needed
    if (hparams.rope_type != LLAMA_ROPE_TYPE_NONE) {
        ggml_backend_sched_reset(sched);

        auto * res = lctx->get_gf_res_reserve();
        res->reset();

        auto * gf = build_graph_shift(res, lctx);   // 单独为「平移 K」建一张图
        if (!ggml_backend_sched_alloc_graph(sched, gf)) {
            LLAMA_LOG_ERROR("%s: failed to allocate compute graph for K-shift\n", __func__);
            return updated;
        }
        ...
    }
}
读懂这段： 「记 fibers」和「改数据」是两层：seq_rm/seq_add 改 cells 的 pos（O(n) 记账，瞬时）；build_graph_shift 建一张小图，把每个 K 向量按 shift[i] 重算 RoPE（一次前向计算的开销）。这也解释了 decode 状态机为什么敢「重试一次」——整理动作里 shift 是用算图的方式做的，不破坏 cache 的一致性。V 向量不需要 shift（V 不含位置信息）。旧版还有 defrag（碎片整理），现在已从代码里移除——defrag_thold 在 include/llama.h:384 已标 [DEPRECATED]，仅在 llama_context_default_params()（src/llama-context.cpp:3669）里保留一个 -1.0f 的默认值。
mmproj 不支持 shift server-context.cpp 里明确 GGML_ABORT("not supported by multimodal")——多模态 chunk 一个图像对应多个 token 位置，shift 会破坏图文对齐。加载了 mmproj 时 ctx_shift 被自动禁用。端侧多模态应用要么留足 context，要么自己管理丢弃。

4.6对照：FreeToken 的混合缓存

FreeToken 面对的模型（DeepSeek-V4 类 hybrid）KV 是「全注意力 + 线性状态（GDN）」混合，prefix 复用要多带一份线性状态快照：python/freetoken/kvcache/hybrid_radix_cache.py 的 docstring 开门见山：

python/freetoken/kvcache/hybrid_radix_cache.py — 模块 docstring（摘录，注释为译注）
python"""Hybrid (full-attn KV + GDN linear-state) radix cache.

A SEPARATE class from ``RadixPrefixCache`` (Option C) that REUSES the shared ``RadixTreeNode``
and walk/split logic, so the production KV radix is untouched (zero risk to non-hybrid models).
It adds a second "currency": an optional GDN state snapshot (``node.mamba_value`` = a
LinearStatePool slot id) attached at chunk/page-aligned boundary nodes, with its own LRU
eviction. Mirrors sglang ``MambaRadixCache`` (donate-not-copy, dual eviction, internal-node
tombstone, ``full_ref >= mamba_ref``) on FreeToken's tree.
"""

match_prefix 把可复用长度截断到「最近一个仍持有活快照的节点」——GDN 是循环状态，只能从存档点续跑：

对照读： llama.cpp 的复用单位是「KV 格子」（bitset 多序列共享），FreeToken 的复用单位是「radix 树节点 + 页对齐 KV 页 + GDN 快照槽」——三种资源各自记账。llama.cpp 的 context shift 丢中段保两端；FreeToken 的 hybrid 模型天然没有「无限生成长度」问题（线性状态恒定大小），但换来的约束是：prefix 复用必须在 CHUNK_SIZE 边界上——断言 `CHUNK_SIZE % page_size == 0` 就是为此写的。第 10 章展开。

4.7小结

  • unified（1 流，动态分槽）vs 分序列（n_seq_max 流，各占 n_ctx_seq）——服务吞吐与隔离的取舍。
  • cells 只存元信息：pos + seq bitset；一格多序列是 prefix 复用的基石。
  • find_slot：head 回卷 + 连续槽测试 + SWA 死区复用；失败即 FAILED_PREPARE。
  • iswa 双缓存按层切分：滑窗层 cache 只需 n_swa + n_ubatch 大小。
  • context shift = seq_rm/seq_add（记账）+ build_graph_shift（重算 K 的 RoPE）。
  • FreeToken 的混合模型多一份要管理的状态：GDN 快照，复用截断到快照边界。
