整体架构：on-device 推理到底难在哪

云端引擎（vLLM 那一类）的约束是「吞吐」；on-device 引擎的约束是「这台机器只有这么多显存、这么多带宽」。先把两个约束讲清楚，再看两个引擎各自怎么拆系统。

1.1问题定义：两堵墙

on-device 推理与数据中心推理面对的不是一个问题。数据中心里你可以堆 8 张 H100；而一台游戏本、一块 RTX 4070、甚至一部手机，资源上限是固定的。具体来说有两堵墙：

  • 容量墙：70B 模型即使 4-bit 量化也要 ~40GB，超过多数消费级 GPU 的 8~24GB 显存。放不下，就要决定「放多少层进显存、剩下留给谁」。
  • 带宽墙：decode 阶段每生成一个 token 都要把全部权重读一遍（memory-bound）。显存带宽 250~1000 GB/s，比 HBM3e 的 3~8 TB/s 低一个数量级。CPU 内存带宽（~50-100 GB/s）更低一个台阶。

两个引擎对这两堵墙的答案完全不同，这正是本书分两条线讲的原因：

  • llama.cpp：通用轻量级。核心思路是「压缩到放得下 + 按层切分到多设备 + CPU 兜底」。它不假设你有什么硬件——CUDA、Metal、Vulkan、SYCL、OpenCL、WebGPU，甚至纯 CPU 都能跑同一个 GGUF。
  • FreeToken：消费级 GPU 的 MoE 专用。MoE 模型（DeepSeek-V4、Qwen3.6、GLM-5.2 这类）总参数巨大但每个 token 只激活少数专家——于是它把全部专家权重放内存（pinned）、GPU 显存只留一个 LRU 槽池，缺谁补谁，再用 CPU 和 PCIe 带宽把补不上的缺口填掉。前提是你有一块像样的 NVIDIA 卡。
怎么读 第 1~9 章走 llama.cpp 线：加载、decode 循环、KV、图、多设备、采样、投机、server。第 10~12 章走 FreeToken 线：引擎分层、专家缓存、CPU/GPU 协同。第 13 章把两边放回一张对照表，并给出自研路线。两线之间不要求先后——但第 2 章的量化概念在 FreeToken 章节里会反复出现。

1.4一次请求在两个引擎里的形状

同样一句 prompt「写一个快排」，两台典型机器上的关键路径：

阶段llama.cpp（单卡 24GB + 64GB 内存）FreeToken（单卡 16GB + 64GB 内存）
加载GGUF mmap 直读，按 free memory 切 n_gpu_layers；放不下的层留在 CPUFTW 分片 O_DIRECT 读入 pinned host bank（专家）+ 显存（稠密权重）
prefill整段 prompt 一个 ubatch（受 n_ubatch 限制），一次前向chunked prefill，边算第 N 层边把第 N+1 层专家从内存流进显存（双缓冲）
decode每 token 一次 llama_decode → 图复用（can_reuse）→ sched 分发到设备每 token 一次 graph replay；路由命中的专家在槽池里，缺失的走 PCIe 或 CPU executor（q* 比例分流）
KVllama_kv_cells 槽位制，unified 或分序列，iswa 双缓存radix/SWA/GDN 混合前缀缓存，页大小 1~128 随后端
出口llama-server（多 slot 并发）或统一 llama 二进制 serveFastAPI :1919，OpenAI/Anthropic/Responses 三套路由 + ft shell

注意第二列的「图复用」和第三列的「graph replay」不是同一个东西：前者是跳过重建 C 计算图（CPU 侧开销），后者是重放预录制的 CUDA graph（消除 launch 开销）。名字都叫图，解决的问题不同。

1.5对「自研引擎」的第一个启示

要点 先回答「你的模型是什么形状」。稠密模型 + 想覆盖所有硬件 → 走 llama.cpp 路线（量化 + 分层 + 通用后端）；MoE + 只针对 NVIDIA 消费卡 → 走 FreeToken 路线（槽池 + 带宽协同）。两条路线没有优劣，只有目标硬件和模型形态的区别。 下一步进入 第 2 章：GGUF 与模型加载。
