decode 循环：一次 llama_decode 里发生了什么

批校验 → KV 分槽 → ubatch 拆分 → 建图执行 → logits 提取 → 输出重排。整条路径都在 llama_context::decode 这一个 C++ 函数里（约 400 行）。

3.1n_batch 与 n_ubatch：两个 batch 尺寸

include/llama.h:361-362 定义了两个容易混淆的参数：

include/llama.h — 上下文参数（摘录）
cuint32_t n_batch;    // 逻辑最大批：一次 llama_decode 能提交的 token 数
uint32_t n_ubatch;   // 物理最大批：一次真正前向计算的 token 数

两者的关系由 memory->init_batch(*balloc, cparams.n_ubatch, output_all) 驱动：llama_batch_allocr 把 n_tokens_all 的输入切成若干 ubatch，每个 ubatch 独立走一遍「KV 分槽 + 建图 + 前向」。为什么要切？KV cache 要为每个 ubatch 找槽位——一次找 2048 个连续位置比一次找 512 个难得多（第 4 章细讲）。decode 入口的断言点明了约束：

src/llama-context.cpp — decode 入口断言（摘录）
c++GGML_ASSERT(n_tokens_all <= cparams.n_batch);
GGML_ASSERT((cparams.causal_attn || cparams.n_ubatch >= n_tokens_all)
    && "non-causal attention requires n_ubatch >= n_tokens");
读懂这段： 因果注意力下可以切 ubatch（每段独立算注意力）；非因果（fill-in-middle、某些编码器）必须一个 ubatch 装下全部——它要看到整段上下文。

3.2decode 主流程

图 3.1：decode 主路径。FAILED_PREPARE 的「重试一次」是理解内存管理的关键：engine 把「腾地方」的职责交给 memory 模块，自己只负责再问一遍。

3.3源码：内存状态机

decode 的中段是一个循环，处理 KV cache「装不下」的情形。这是整个 llama.cpp 内存管理的枢纽：

src/llama-context.cpp:1749-1786 — init_batch 状态机（摘录，注释为译注）
c++llama_memory_context_ptr mctx;

while (true) {
    mctx = memory->init_batch(*balloc, cparams.n_ubatch, output_all);
    if (!mctx) { return -2; }

    switch (mctx->get_status()) {
        case LLAMA_MEMORY_STATUS_SUCCESS:
            break;                          // 槽位找到，继续
        case LLAMA_MEMORY_STATUS_FAILED_PREPARE:
            {
                if (!did_optimize) {
                    did_optimize = true;
                    // 只重试一次：先做 shift 等整理动作
                    if (memory_update(true)) {
                        LLAMA_LOG_DEBUG("%s: retrying batch size %d after cache optimization", ...);
                        continue;
                    }
                }
                LLAMA_LOG_WARN("%s: failed to find a memory slot for batch of size %d", ...);
                return 1;                  // 正数返回值：不是错误，是「这次没跑成」
            }
        case LLAMA_MEMORY_STATUS_FAILED_COMPUTE:
            return -2;
    }
    break;
}
读懂这段： ① memory 是 llama_memory_i 接口（src/llama-memory.h），统一三种实现：普通 KV、iswa 双缓存、循环状态（Mamba/GDN 类）。decode 只面对这个接口； ② FAILED_PREPARE 的处理是「整理一次 + 重试一次」——did_optimize 标志保证不会无限循环。整理动作包括 context shift（把 KV 窗口平移）等，见第 4 章； ③ 返回值约定容易记错：正数 = 业务性失败（没跑成但状态一致），负数 = 系统性错误。

3.4源码：ubatch 执行与 logits 提取

状态机退出后进入 do-while 循环，每个 ubatch 调用 process_ubatch（内部做建图 + 执行，第 5 章展开）。成功后把 logits/embd 异步搬回 host：

src/llama-context.cpp:1865-1885 — logits 提取（摘录，注释为译注）
c++auto * t_logits = res->get_logits();
...
// 从「logits 所在的设备」异步拷到 host 缓冲
if (logits.data && t_logits && n_outputs > 0 && needs_raw_logits(ubatch, sampling.samplers)) {
    ggml_backend_t backend_res = ggml_backend_sched_get_tensor_backend(sched.get(), t_logits);
    GGML_ASSERT(backend_res != nullptr);

    float * logits_out = logits.data + n_outputs_prev*n_vocab;
    if (n_outputs) {
        ggml_backend_tensor_get_async(backend_res, t_logits, logits_out, 0,
            n_outputs*n_vocab*sizeof(float));
    }
}
读懂这段： 两个细节值得记住。① sched_get_tensor_backend：logits 可能落在任何一块设备上（sched 切图后输出张量挂在哪块卡就拷哪块）；② n_outputs_prev：多 ubatch 时输出按「先来先填」追加进 host 缓冲，顺序与用户提交顺序不一定一致——这正是下面 output_swaps 存在的原因。

3.5源码：output_swaps 与选择排序

decode 的最后一段把输出顺序还原成「用户提交时的顺序」。llama.cpp 选择的算法值得一看：

src/llama-context.cpp:1990-2023 — 输出重排（摘录，注释为译注）
c++auto & out_ids = balloc->get_out_ids();
GGML_ASSERT(out_ids.size() == (size_t) n_outputs);

for (int64_t i = 0; i < n_outputs; ++i) {
    int64_t out_id = out_ids[i];
    output_ids[out_id] = i;
    if (out_id != i) { sorted_output = false; }
}

// 让输出恢复用户 batch 里的顺序（recurrent 模型尤其需要）
if (!sorted_output && n_outputs > 1) {
    // selection sort，最小化交换次数（wiki: selection sort）
    for (uint32_t i = 0; i < n_outputs - 1; ++i) {
        uint32_t j_min = i;
        for (uint32_t j = i + 1; j < n_outputs; ++j) {
            if (out_ids[j] < out_ids[j_min]) { j_min = j; }
        }
        if (j_min == i) { continue; }
        std::swap(out_ids[i], out_ids[j_min]);
        // 记下交换，等到读 logits/embd 时才应用
        output_swaps.push_back({ i, j_min });
    }
}
读懂这段： 两个反直觉的设计。① 用 O(n²) 的选择排序而不是 O(n log n)——注释写明目标是「最小化交换次数」，因为每次交换都要记录到 output_swaps，交换越少越好；② 交换是惰性应用的：decode 结束时不真的移动数据，而是在调用方 llama_get_logits_ith 读第 i 个输出时，按 swaps 链条找到它实际存放的位置。单 token decode（最常见情形）完全零开销。
为什么需要重排 recurrent（Mamba/GDN 类）模型按序列处理，ubatch 内的输出顺序由内部实现决定；KV unified 模式下多序列交错也同理。调用方（llama-server 的 slot）期望「我提交的第 k 个请求的输出在位置 k」——约定不能破，就在出口处还原。

3.6对照：FreeToken 的 decode

FreeToken 没有这样一个巨型函数，它的 decode 分散在三层。调度层（python/freetoken/scheduler/decode.py，全文 39 行）只有一件小事——把运行中的请求排成 batch：

python/freetoken/scheduler/decode.py:9-39 — DecodeManager（摘录，注释为译注）
python@dataclass
class DecodeManager:
    page_size: int
    running_reqs: Set[Req] = field(default_factory=set)

    @property
    def inflight_tokens(self) -> int:
        # 每个 decode 请求预留 1 页增长余量
        tokens_reserved = (self.page_size - 1) * len(self.running_reqs)
        return sum(req.remain_len for req in self.running_reqs) + tokens_reserved

    def schedule_next_batch(self) -> Batch | None:
        if not self.runnable: return None
        return Batch(reqs=sorted(self.running_reqs, key=lambda req: req.uid),
                     phase="decode")
对照读： llama.cpp 的 decode 是「引擎内一次调用的完整生命周期」；FreeToken 的 decode 是「调度器循环里的一个阶段」（scheduler.py:197 overlap_loop，第 10 章展开）。前者单请求深度优先，后者多请求时间片轮转——服务形态决定的：llama-server 的 slot 是「一个序列独占一个上下文」，FreeToken 是「4 个并发请求共享一个引擎」。

3.7小结

  • n_batch（逻辑批，≤2048）与 n_ubatch（物理批）分离；KV 找槽以 ubatch 为单位。
  • 内存状态机：FAILED_PREPARE → 整理一次 → 重试一次 → 放弃。返回值正数=业务失败、负数=错误。
  • logits 异步拷回，多 ubatch 追加填写；output_swaps + 选择排序在读取时还原顺序，零额外拷贝。
  • FreeToken 把同样的逻辑摊到 scheduler/engine/graph 三层，多请求共享而非 slot 独占。
