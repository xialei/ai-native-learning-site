FreeToken：为消费级 GPU 重写的引擎

llama.cpp 追求「什么硬件都能跑」；FreeToken 押注一个假设——消费级单卡 + CPU 内存大 + 模型是 MoE。三件事叠起来，才有了第 11/12 章的 offload 与协同设计。

10.1定位与约束

FreeToken 目标场景：DeepSeek-V4-Flash 级别的 MoE（256 专家、43 层、约 290B 参数，仓库 README 自称 "290B+ frontier"）在 8-24GB 消费卡上跑。它不做的事很说明问题：GGUF 支持极窄（只有一条 gemma4 → Gemma4GGUFForCausalLM 的注册路径，读原生 Q4_0/Q6_K；主流路径是自研 FTW + HF safetensors）、没有 CPU fallback 前向（除 routed experts 外全部算子要求 GPU）、没有通用模型架构支持（模型注册表按架构枚举）。换来的是：针对 MoE decode 的极致优化。引擎并发上限默认 4：

python/freetoken/engine/config.py:26 — 并发上限（摘录）
pythonclass EngineConfig:
    max_running_req: int = 4
max_running_req=4 不是偷懒，是与 CUDA Graph 档位（[1,2,4]+range(8,160,8)，第 5 章）对齐——batch ≤4 是端侧常态，4 之上走 padding。所有设计都围绕「小 batch、低延迟」。

10.2进程模型：ZMQ 多进程

第 9 章看过 api_server.py 的五组路由，这里补全进程拓扑。FreeToken 不是单进程：父进程跑 FastAPI/uvicorn 且不碰模型，请求经 ZMQ 队列转发给后端 worker。默认配置（num_tokenizer=0、TP=1）下后端恰好是 3 个进程——1 个 scheduler（内含 Engine 实例）、1 个 tokenizer、1 个 detokenizer（后两者共用同一进程）；--num-tokenizer N 或 TP>1 时按 world_size 线性增多：

    ...

supervisor.py 管启动握手：

python/freetoken/server/supervisor.py — 启动握手（摘录，注释为译注）
python"""Backend startup/liveness supervision, decoupled from run_api_server so it is unit

The scheduler/tokenizer worker processes are spawned by launch.start_subprocess, which

拆进程的动机就是 GIL。Python 里 HTTP 解析、JSON 序列化、流式 token 后处理都是 CPU 工作，与引擎主循环抢同一个 GIL；拆进程后 HTTP 进程的解析开销与引擎进程的调度开销并行，ZMQ 队列天然削峰。supervisor 的 drain_ready 等每个 worker ack（附带加载进度），顺带把「加载到 99% 卡住」的观感问题也解决了——专家库加载阶段单独上报（phase_slug 里 expert bars 优先于 weight 匹配，加载进度 UI 不再停在最后一格）。

10.3调度主循环：overlap_loop

FreeToken 调度的核心是双流重叠（python/freetoken/scheduler/scheduler.py:207-261）：

python/freetoken/scheduler/scheduler.py — overlap_loop（摘录，注释为译注）
pythondef overlap_loop(self, last_data):
    """The main loop of overlapping scheduling and execution.

    It will overlap the execution of current batch and processing of last batch's
    results, which can effectively hide CPU latency and improve GPU utilization."""
    # 把未处理的 batch 暴露给 abort 检查
    self._last_data = last_data
    blocking = not (last_data is not None  # 有 batch 待处理就不阻塞收消息
        or self.prefill_manager.runnable
        or self.decode_manager.runnable
        or self._pending_rebuild is not None)
    for msg in self.receive_msg(blocking=blocking):
        self._process_one_msg(msg)

    # 调度器完全空闲时才执行排队的 cache rebuild（安全点）
    if self._pending_rebuild is not None and last_data is None and not (...):
        self._execute_pending_rebuild()

    # 关键：本迭代的 H2D token 拷贝要排在上一批采样写入之后 ——
    # 否则复用刚释放的 table_idx 的新请求，其 prompt 会被上一任
    # 占用者的未决输出写覆盖（丢图像占位符等）
    self.stream.wait_stream(self.engine.stream)
    forward_input = self._schedule_next_batch()
    ongoing_data = None
    if forward_input is not None:
        with self.engine_stream_ctx:   # 批次跑在 engine 流上
            self.engine.stream.wait_stream(self.stream)
            # 前缀命中时在 engine 流上做 GDN 快照 COW 恢复
            self._restore_linear_states(forward_input.batch)
            ongoing_data = (forward_input, self._forward(forward_input))

    # drain：上一批的结果处理（页表重指向、哨兵 scatter）
    # 会写本批还在读的状态，必须显式排序
    self.stream.wait_stream(self.engine.stream)
    self._process_last_data(last_data)
    self._flush_abort_acks()
    return ongoing_data
每个迭代做三件事：收消息（新请求/abort，有 batch 在飞就不阻塞）、排下一批（H2D 拷贝、建 batch）、交引擎前向 + 处理上一批结果。真正值钱的是那三处 wait_stream：调度流与引擎流各自异步推进，在「读对方刚写的数据」处显式插栅栏——先是调度流等引擎流（本批 H2D 必须排在上一批采样写入之后），再是引擎流等调度流（前向必须等 batch 建好），最后调度流再等引擎流一次（drain 会写本批还在读的状态）。注释里那句「corrupting tokens (e.g. dropping an image placeholder)」是真实事故——table_idx 复用 + 流间无序 → 上一批的输出写覆盖新批的 prompt 拷贝。双流重叠的复杂度不在「并行」而在「排序」：谁等谁、等哪一段，每处都要写明白。

hybrid 模型的 KV 管理有三类资源：普通 KV 页、GDN 线性状态槽（1 live + 2 ping-pong）、SWA 窗口页。每种都有独立池、独立淘汰逻辑（radix 树各自记账），准入时都要单独检查。reserved_size = decode_manager.inflight_tokens——decode 中请求的增长余量（每请求预留 1 页，第 3 章见过）也被计入，防止「prefill 抢光、decode 涨不动」。
一段代码的进化痕迹 早期版本这里算的是 estimated_len = extend_len + output_len（裸 token 数）。但 CacheManager 给每个请求分配 KV 时是按整页来的——两个各占 0.6 页的短请求按 token 记账能挤进同一页的余量，真分配时却各自要一整页，准入就超卖了。后来补了 _kv_reservation_size：预留量改成「新增整页数 × page_size」，与分配口径对齐（#367）。准入按什么记账，分配就必须按什么记账——这个故事值得每个写调度器的人记住。

10.5toolcall anchor：调度层的状态检查点

FreeToken 有一个 llama.cpp 没有的机制：toolcall anchor。它默认关闭，需 --enable-special-token-ckpt 启用（且只在 hybrid / SWA 缓存下生效）。动机：agent 场景下模型输出 tool call，客户端执行后把结果 + 重写的 tool call 回传续跑。重写后的文本与原输出在 opener 之后必然分叉——若能记住「opener 出现时」的状态，续跑就能从那里恢复而不是全部重算。先看 anchor id 的确定（utils/hf.py:82-96）：

python/freetoken/utils/hf.py — anchor id 提取（摘录，注释为译注）

    None when there is no opener or the tokenizer spells it with more than one token:
    the scheduler's special-token checkpoint matches sampled ids one at a time, so only
    a one-token opener can anchor."""
    ...
    ids = tokenizer.encode(opener, add_special_tokens=False)
    return int(ids[0]) if len(ids) == 1 else None

检测到后，在合适时机把 GDN 状态冻结进 ping-pong 槽（scheduler/cache.py:148-173）：

python/freetoken/scheduler/cache.py — snapshot_toolcall_anchor（摘录，注释为译注）
pythondef snapshot_toolcall_anchor(self, reqs) -> None:
    """Freeze each decoding request's GDN state at its tool-call anchor, into the
    ping-pong slot that is idle during decode ... Must run on the engine stream
    before the current step's kernels: cached_len equals the anchor exactly when
    every enqueued step up to the anchor-consuming one has been issued ..."""
    if not self.is_hybrid:
        return
    for r in reqs:
        a = r.toolcall_anchor_len
        if (a is None
            or r.mamba_ping_pong is None
            or r.mamba_last_track_seqlen is not None
            or r.cached_len != a              # 恰好走到锚点
            or align_down(a, self.page_size) != a):  # 锚点必须页对齐
            continue
        dst = r.mamba_ping_pong[r.mamba_next_track_idx]
        pool.copy_from(r.linear_slot_idx, dst)   # 冻结 live 状态到空闲槽
        r.mamba_last_track_seqlen = a
        r.mamba_next_track_idx = 1 - r.mamba_next_track_idx  # ping-pong 翻转
这个机制能精确工作靠三个条件。单 token opener：检测是逐采样 id 匹配，opener 编码成多 token 就锚不上——这是 tokenize 时机决定的硬约束。流序精确性：「cached_len 恰好等于 anchor」意味着到锚点为止的所有 step 已发出、下一个还没发，快照拷贝正好落在两者之间的流序里。页对齐：快照要进 radix 树供后续复用，复用边界是页对齐的。SWA 模型还有配套的「锚点窗口保留」（maybe_free_swa_out_of_window 里 cap = anchor - window - gap，保证 [anchor-window, anchor) 可续跑）。

10.6对照：一个请求的完整生命周期

把各章零件串起来。两个引擎处理同一条请求的路径：

阶段llama.cpp / llama-serverFreeToken
HTTP 入口单进程 HTTP server + task 队列父进程 FastAPI → ZMQ → scheduler 子进程
prompt 处理slot 选择（LCP→LRU）→ 前缀复用radix 树匹配 → chunked prefill
decode 调度slot 独占 context，逐 slot 采样DecodeManager 按 uid 排序组批，共享引擎
状态检查点投机检查点（spec_ckpt）toolcall anchor 快照（GDN ping-pong）
输出流式 JSON，slot 逐 token 推送DetokenizeMsg → HTTP 进程流式回传
表里最大的结构性差异在第二行：llama.cpp 的复用单位是「slot 里现存的 KV」，FreeToken 是「radix 树里的页 + GDN 快照」。llama.cpp 靠 LCP 选槽命中 slot 内的前缀，slot 被抢走就失效——但第 9 章讲过它还有一层 RAM prompt cache 兜底，能把已不在任何 slot 的 prompt 恢复回来，所以并非只能会话内复用；FreeToken 的 radix 树则在引擎生命周期内共享，粒度更细（页级）、命中率更高。agent 场景多轮高频续跑时差距明显。

10.7小结

FreeToken 的关键词是「押注」：定位押在消费级单卡 + MoE + 4 并发上，放弃通用性，换来每处优化的自由度。结构上多进程 + ZMQ 绕开 GIL，supervisor 握手顺带解决了加载进度上报；调度上是 overlap_loop 双流重叠——调度流与引擎流各走各的，读对方数据处插 wait_stream（三处）；准入上是 chunked prefill 的三类资源检查（KV 页 / GDN 槽 / SWA 页）。最有意思的是 toolcall anchor（默认关闭，需 --enable-special-token-ckpt）：单 token opener + 流序精确快照 + 页对齐，agent 续跑免重算。
