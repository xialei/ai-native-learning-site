OffloadMoeCache：把 137 GiB 专家装进 12 GiB 显存

KV cache 管的是「每个 token 一格」；专家缓存管的是「每个 (层,专家) 一格」——而且格子里的内容比 KV 重几百倍，搬一次的代价要用 LRU 摊平。这一章拆 FreeToken 最核心的部件：槽池、双映射、bank 布局、LRU、prefill 双缓冲，以及让这一切能跑起来的磁盘格式与显存预算。

11.1先算账：专家到底有多大

拿 DeepSeek-V4 的配置（python/freetoken/models/deepseek_v4/args.py）算一遍：

python/freetoken/models/deepseek_v4/args.py — 关键维度（摘录）
pythondim: int = 4096          # H，hidden size
moe_inter_dim: int = 2048   # I，专家中间维
n_layers: int = 43
n_routed_experts: int = 256
n_activated_experts: int = 6   # top_k

每个专家是三个矩阵：gate_up（2I×H）、down（H×I），合计 3IH 个权重。乘上层数与专家数，就是 routed experts 的全部体积。OffloadMoeCache 把每专家字节数写成了公式表（moe/offload_cache.py:84-96）：

python/freetoken/moe/offload_cache.py:84-96 — 每专家字节公式（摘录，注释为译注）
python# keyed by the config-time format tag (expert_quant / moe_weight_format), not
# quant_format: "mxfp4" sizes the mxfp4_triton banks, "nvfp4" also covers its
# repacked variants
_BANK_BYTES_PER_EXPERT = {
    "bf16": lambda H, I: 3 * I * H * 2,
    "fp8_block": lambda H, I: 3 * I * H + (...scale...),
    "q4_0": lambda H, I: 2 * I * (H // 32) * 18 + H * (I // 32) * 18,
    "nvfp4": lambda H, I: 2 * I * (H//2 + H//16 + 2) + H * (I//2 + I//16 + 2),
    "mxfp4": lambda H, I: 2 * I * (H//2 + H//32 + 2) + H * (I//2 + I//32 + 2),
    "ds_fp4": lambda H, I: 2 * I * (H//2 + H//32) + H * (I//2 + I//32),
}
格式每专家（H=4096, I=2048）43 层 × 256 专家全部体积
bf163IH×2 = 48 MiB约 516 GiB
fp8_block3IH + 块 scale ≈ 24 MiB约 258 GiB
ds_fp4（DSV4 原生）≈ 12.75 MiB约 137 GiB

137 GiB（最低量化）对上 8-24 GB 显存，差距是一个数量级。但注意 top_k=6：每层每步只激活 6/256 ≈ 2.3% 的专家。稀疏性给了缓存机会——如果在 GPU 上留一个 L×E 总量中一小部分的「槽池」，把热专家放里面，冷专家按需从 CPU 内存经 PCIe 搬进来，就能用远小于全量的显存吃到大部分命中。这个槽池就是 OffloadMoeCache。

这里的账目与 KV cache 完全不同量级：一个 KV 格子是 head_dim 级的几个 KB，一个专家槽是 12-48 MiB。搬错一次的代价是搬 KV 的上千倍，所以替换策略（LRU）、搬运方式（合并拷贝）、甚至磁盘格式（对齐到 O_DIRECT）都要为「减少搬运」服务。llama.cpp 没有这个问题——它从不把专家当可换入换出的资源，见 11.7。

11.2flat id 与双映射：一个扁平槽池

OffloadMoeCache 的核心是三层结构：host 源（每层一份 [E, ...] 的 pinned 内存 bank）、GPU 槽池（每个 bank 一条 [cache_size, ...] 的显存）、以及两本映射账。注意 cache_size 是全部层的总槽位数，不是每层各留一份——热层多占、冷层少占，池子共享：

python/freetoken/moe/offload_cache.py:169-185 — 双映射（摘录，注释为译注）
pythonself.slot_for_id = torch.full(
    (self.num_layers, self.num_experts),   # 正表：[L, E] -1=不在池中
    -1, dtype=torch.int32, device=self.device,
)
# Reverse map, in the flat id space flashlib's slot_cache works in:
# id == layer_id * num_experts + expert, so one array replaces the (layer,
# expert) pair and evicting a slot needs no decode.
self.id_of_slot = torch.full(
    (self.cache_size,),                    # 反表：[cache_size] 槽→flat id
    -1, dtype=torch.int32, device=self.device,
)
self.usage = torch.zeros((self.cache_size,), dtype=torch.int64, device=self.device)
self.step = torch.zeros((), dtype=torch.int64, device=self.device)

LRU 的全部机制就是最后两个量：每次 decode 步 step += 1，命中/载入的槽把 usage[slot] = step 盖个时间戳；要驱逐时取 argmin(usage)。没有链表、没有堆——设备端一个规约就够，且形状固定，可以编进 CUDA Graph。逐专家的 LRU 变体（hybrid 后端用）另有 expert_recency [L, E]（:196-201），按「专家最近何时被路由」而非「槽何时被写」挑该抓哪些缺失。

图 11.1：一个扁平槽池服务所有层的所有 bank。双映射让「路由改写」查 slot_for_id、「驱逐」查 id_of_slot 各走各的；前 2E 槽平时也当普通缓存用，prefill overlap 时被临时征用为双缓冲（11.5）。

11.3bank schemas：八种量化格式一个缓存机制

「一个专家」不是一块连续内存，是若干个bank（权重 + scale 各自成列）。格式决定 bank 有几列、每列什么形状；而缓存机制对 bank 内部字节不感兴趣，只负责按行搬运。所有格式的 bank 名字集中在一张表里（offload_cache.py:32-78）：

python/freetoken/moe/offload_cache.py:32-78 — _BANK_SCHEMAS（节选，注释为译注）
python# quant_format -> bank names, in registration order: the single place a format's
# bank layout is declared. The cache machinery (copy_missing, the prefill double
# buffers, bank_views) iterates banks in this order ...
_BANK_SCHEMAS = {
    "bf16": ("gate_up", "down"),
    # DeepSeek-V3-style 128x128 block-fp8 ... gate_up [L*E, 2I, H] fp8 + gate_up_scale
    "fp8_block": ("gate_up", "gate_up_scale", "down", "down_scale"),
    "q4_0": ("gate_up", "down"),
    # native ModelOpt rows ...: packed e2m1 codes + fp8-e4m3 per-16 block scales
    # + per-output-row fp16 globals (w1/w3 carry distinct globals, ...)
    "nvfp4": ("gate_up_packed", "gate_up_scale", "gate_up_global",
              "down_packed", "down_scale", "down_global"),
    # pre-tiled layouts for the borrowed kernels; the globals are folded into the
    # block scales at repack time and collapse to [L*E] GPU-resident alpha vectors
    "nvfp4_marlin": ("gate_up_packed", "gate_up_scale", "down_packed", "down_scale"),
    "nvfp4_b12x": (...同上...),
    # gpt-oss mxfp4, transposed split-K layout ...: blocks_t / scales_t / bias
    "mxfp4_triton": ("gate_up_blocks", "gate_up_scales", "gate_up_bias",
                     "down_blocks", "down_scales", "down_bias"),
    # DeepSeek-V4 FP4: packed e2m1 codes + e8m0 per-32 block scales, no global scale
    "ds_fp4": ("gate_up_packed", "gate_up_scale", "down_packed", "down_scale"),
}

机制与格式解耦的代价集中在拷贝路径。每个 bank 的「每行字节数」必须能对齐到 16 字节，才能把所有 bank 的拷贝融合成一次 launch（_build_fused_copy_plan，:380-441；退化路径是每 bank 一次 launch）。另一个格式相关的巧合约束是 marlin 内核的槽位上限：

python/freetoken/moe/offload_cache.py:100-101 — marlin 槽位上限
python# vLLM's marlin grouped-GEMM hands the full [cache_size] slot cache as its expert
# dimension; moe_align_block_size requires round_up(experts, 32) < 1024, i.e. <= 992.
MARLIN_MAX_CACHE_SIZE = 992
992 这个数字的外来性值得停下来看：槽池明明是 FreeToken 自己的数据结构，上限却由「借用的 vLLM marlin 内核要求对齐后的 expert 维 < 1024」倒逼出来——moe_align_block_size 要求 round_up(experts, 32) < 1024，向上取整到 32 的倍数后仍小于 1024，上限就落在 992。nvfp4_marlin 格式下 cache_size 不得超过 992（validate_rebuild，:443-463 里强制），其他格式没有此限。复用别人的内核，就要接受别人的约束写进自己的配置——这是工程边界真实的样子。

11.4decode 路径：ensure_experts → copy_missing

decode 时每层 MoE 的前向分三步（layers/moe.py:285-296）：改写路由 id、搬缺失、算 GEMM：

python/freetoken/layers/moe.py — _decode_routed（摘录，注释为译注）
pythoncache.ensure_experts(self.layer_id, topk_ids)   # topk_ids 就地变槽 id
cache.copy_missing()                                # 缺失行经 PCIe 入槽
return self._expert_gemm(
    cache, hidden_states, topk_weights, topk_ids,
    views=cache.bank_views(),                       # 直接读整条 [cache_size] 槽池
    n=None, ...)

ensure_experts 的实现在 CUDA 内核里（moe/offload_kernels.py 的 ensure_experts），但它的两个关键行为在 Python 侧注释里写得很清楚。其一，改写是就地的——路由直方图统计必须赶在改写之前做（offload_cache.py:843-853）：

python/freetoken/moe/offload_cache.py:843-853 — ensure_experts（摘录）
pythondef ensure_experts(self, layer_id: int, expert_ids: torch.Tensor) -> None:
    if self.collect_decode_freq:
        # ``expert_ids`` still holds raw expert ids here (the kernel rewrites them to
        # slot ids in place), so snapshot the routing histogram before that happens.
        ids = expert_ids.reshape(-1).long()
        self.decode_freq[layer_id].scatter_add_(0, ids, torch.ones_like(ids))
    self._pending_src_layer = layer_id
    self._pending_whole_layer = False
    ensure_experts(self, layer_id, expert_ids)

其二，_pending_src_layer 是一层簿记：内核只负责选受害者（argmin usage）、写 evict_slots/src_indices/num_indices 三个设备端数组，真正的搬运留给随后的 copy_missing（:1011 起）。为什么不合并成一步？因为「选槽」在计算流上（要赶在 GEMM 前），而「搬运」可能要走 fused copy 内核或特殊的整层路径——分离后每一步都能被 CUDA Graph 捕获（copy_missing 见 :1011-1053）：

python/freetoken/moe/offload_cache.py:1011-1053 — copy_missing（摘录，注释为译注）
pythondef copy_missing(self) -> None:
    layer_id = self._pending_src_layer
    if layer_id in self._unpinned_layers:
        if not self._pending_whole_layer:
            raise RuntimeError(
                f"layer {layer_id} is unpinned: its only copy is the whole-layer "
                f"pageable materialize (position == expert id); ensure_experts's "
                f"LRU slot remap cannot be honored without a device alias"
            )
        # 非 pinned 层唯一的搬运方式：整层同步 pageable H2D，
        # 槽位 = 专家 id，永不被 CUDA Graph 捕获
        for per_layer, cache in self.banks:
            cache[: self.num_experts].copy_(per_layer[layer_id])
        return
    if self._copy_fused_ok:
        # 一次 launch 搬所有 bank 的缺失行；evict/src/num 三数组跨 bank 共享
        fast_index_copy_multi_jit(
            self._copy_dst_ptrs, self._copy_src_ptrs[layer_id],
            self._copy_feat_bytes, self.evict_slots,
            self.src_indices, self.num_indices,
        )
        return
    from freetoken.kernel import fast_index_copy_jit
    for per_layer, cache in self.banks:
        fast_index_copy_jit(cache, self.evict_slots, per_layer[layer_id],
                            self.src_indices, self.num_indices)
「CUDA-graph 安全」这个硬约束靠三个细节撑起来。所有簿记数组（evict_slots、src_indices、num_indices）形状固定、内容设备端产生，图重放时直接复用；fused copy 的指针描述符在 set_bank_sources 时固化成设备端 tensor（_copy_dst_ptrs 等），cache 生命周期内地址不变；非 pinned 层（LOCKED/PAGEABLE，见第 12 章）没有设备别名，无法表达「把行搬到任意槽」，所以直接抛错——把不可能表达的约束在运行时喊出来，好过静默出错。另外注意 ensure_experts 与 copy_missing 之间没有同步原语：同一流上先 launch 后 launch 天然有序。

11.5prefill 路径：整层流式与双缓冲

prefill 与 decode 的处境完全不同：一个 chunk 可达数千 token，几乎必然激活每层的全部 256 个专家（6/256 是每 token 的分布，乘上几千 token 后命中每一个专家的概率接近 1）。逐专家 LRU 毫无意义——干脆整层整层地搬。prefill 默认不走 LRU：槽位 = 专家 id，路由 id 原样通过（_prefill_routed，moe.py:353-356 的注释 "position == expert id, so the routing ids pass through unmapped"）。例外是 DeepSeek-V4：它 override 了 _prefill_routed，对小于整层的小 chunk 会退回 LRU 路径（models/deepseek_v4/moe.py:96-110），免得为几百 token 搬满整层。

整层搬运若串行，PCIe 时间会直接叠在 GEMM 时间上。prefill_overlap 的方案：把槽池最前面的 2×num_experts 个槽临时征用为双缓冲——层 L 用 L%2 号缓冲，层 L 的 GEMM 与层 L+1 的 H2D 并行：

python/freetoken/moe/offload_cache.py:611-616 — 双缓冲借用槽池（摘录，注释为译注）
python# The double buffers borrow the slot cache's first 2 * num_experts slots
# (one full expert layer per buffer), one view per registered bank.
self.prefill_bank_buffers = [
    cache[: 2 * self.num_experts].view(2, self.num_experts, *cache.shape[1:])
    for _, cache in self.banks
]
python/freetoken/layers/moe.py:386-396 — 每层的双缓冲交替（摘录）
pythondef _wait_prefill_overlap(self, cache) -> tuple:
    if self.layer_id == 0:
        cache.begin_prefill()
    cache.prefetch_prefill_layer(self.layer_id)      # 本层已 prefetch 则直接跳过
    cache.prefetch_prefill_layer(self.layer_id + 1)  # 排上下一层的 H2D
    return cache.wait_prefill_layer(self.layer_id)   # 等本层 ready event

双缓冲交替有三件易错事，代码里各有一处防护。第一，缓冲复用必须先释放：buffer 的 release event 在 GEMM 完成后记录，复用方 wait 它（offload_cache.py:832-841），否则层 L+2 的拷贝会覆盖层 L 还在算的字节——复用前的断言 _prefill_buffer_released（:679-681）兜底。第二，跨 prefill 的栅栏。overlap 调度下，新 prefill 的第一个 prefetch 可能排进流里时，上一个 decode 批次还在跑，而那次 decode 刚把专家载入被借走的槽——不设栅栏，prefetch 会踩掉运行中 GEMM 正在读的字节（begin_prefill，:645-658 的 fence 段为 :650-658）：

python/freetoken/moe/offload_cache.py:650-658 — begin_prefill 的 fence（摘录，注释为译注）
pythonif self.prefill_copy_stream is not None:
    # Fence this prefill's copy-stream work behind everything already enqueued
    # on the compute stream. The release/ready events only order against the
    # *previous prefill*; under overlap scheduling a new prefill can be enqueued
    # while the preceding decode batch is still running, and that decode may
    # have loaded experts into the slots the buffers borrow -- without this
    # fence the first prefetch would stomp bytes a running GEMM is reading.
    self.prefill_begin_event.record(torch.cuda.current_stream(self.device))
    self.prefill_copy_stream.wait_event(self.prefill_begin_event)

第三，借用槽的缓存账必须清掉：_invalidate_prefill_buffer（:635-643）把这两个缓冲里所有槽的 slot_for_id 置回 -1、usage 清零——usage=0 让它们成为下次 argmin 的首选受害者。借用是「白拿」，归还时要把账抹平。

在此之上还有一个可选优化 hit-D2D（moe_prefill_hit_d2d，需 CUDA ≥ 13.0 的 cudaMemcpyBatchAsync——绑定的 8 参数签名是 13.0 才有的，12.8/12.9 多一个 failIdx 参数，因此代码在 JIT 编译前就按 torch.version.cuda < (13, 0) 拦下）：chunk 开始时把 slot_for_id 快照到 pinned 主存（一次 host sync），之后每层把「已在槽池里的专家」用设备端 gather 直接 D2D 拼进缓冲，只让缺失行走 PCIe，且按连续 run 合并成一次 batch memcpy（_prefetch_split，:746-817）。小于 256KB 的 bank 不参与 gather——cudaMemcpyBatchAsync 混入小块会整体退化为同步拷贝（offload_cache.py:17-26 的注释实测 gpt-oss 2048tok 端到端 -22%）：

python/freetoken/moe/offload_cache.py:17-26 — 256KB 门槛的由来（摘录，注释为译注）
python# cudaMemcpyBatchAsync silently degrades to a SYNCHRONOUS copy when a batch mixes
# large entries with sub-~256KB entries on registered host memory (H100 + CUDA 13.0,
# empirically bisected: a single 5-22KB entry beside one large entry blocks the
# calling thread for the full transfer; >=253KB entries never do). ...
_SMALL_BANK_FEAT_BYTES = 256 * 1024
hit-D2D 的可用性判定（_hit_d2d_usable，:703-733，包含日志收尾到 :733）是一个可复用的模式：任何不可用条件（快照缓冲没建、fused copy 不可用、cache_size ≤ 2E、驱动缺 batch memcpy）都降级到整层拷贝路径，且在日志里喊一次（_hit_d2d_fallback_logged 防刷屏）。静默降级是性能调优最深的坑——用户以为开了优化，实际跑的是旧路径，数字对不上还查不出来。

11.6磁盘格式与显存预算：FTW 与 plan_cache_budget

缓存机制跑得快，前提是 host bank 装得快。FreeToken 为此定义了自己的权重格式 FTW（FreeToken Weight）。动机在文件头写得直白（checkpoint/ftw.py:1-31）：

python/freetoken/checkpoint/ftw.py — 模块 docstring（摘录，注释为译注）
python"""FreeToken Weight (FTW) checkpoint: one O_DIRECT-friendly on-disk format for a whole model.

... It exists because reading the original safetensors back fast is awkward:
tensors are packed with no alignment, so an individual tensor can't be O_DIRECT-read at an
arbitrary offset; ...

* **Aligned.** Every tensor starts at a 4096-aligned region offset and is padded to 4096;
  shards are cut at 4096-aligned boundaries. So any tensor ... is read with offset, length
  (rounded up to 4096), and destination all block-aligned -- exactly what O_DIRECT requires.
* **Unified.** It holds dense weights as kind="weight" ... and the offload expert state as
  kind="experts_bank" ...
"""
ALIGN = 4096                # O_DIRECT block alignment
DEFAULT_SHARD_LIMIT = 8 << 30   # 8 GiB per shard

读盘侧（FTWReader，:208-288）的选路有个不显眼的取舍：O_DIRECT 不可用时退到 mmap，而不是退到普通缓冲读——「整片 mmap + 内核预读」远快于「逐 chunk 走 page cache」。host bank 的分配也有讲究：先 mmap 出惰性匿名区、填满数据、再 cudaHostRegister（pin-after-fill，moe/host_banks.py:6-10）；顺序反过来（先注册后填）会先触发一轮全页 zero-fill，DSV4 的 137 GiB 会白白多花约 47 秒。

显存侧，专家槽池和 KV 页池是竞争者。谁让谁、让多少，集中在一段无副作用的小算术里（engine/cache_budget.py:48-95）：

python/freetoken/engine/cache_budget.py — plan_cache_budget（摘录，注释为译注）
pythonhi = min(total_experts, max_slots)
# Prefill overlap borrows two full expert-layer buffers, so it needs >= 2*num_experts
# slots; disable it (and lower the floor) if the cap cannot fit that.
overlap = prefill_overlap and hi >= 2 * num_experts
lo = 2 * num_experts if overlap else num_experts

kv_reserve_bytes = kv_reserve_pages * cache_per_page

moe_cache_size = max(lo, min(raw, hi))
...
# A tiny budget can floor num_pages at kv_reserve_pages even when ``remaining`` is
# below the reserve (or negative), yielding a plan that exceeds budget_bytes.
# Reject here so --moe-cache-auto fails in arithmetic instead of OOMing in a

assert total <= budget_bytes, (...)
策略是 MoE 优先的贪心：先给 KV 留底（kv_reserve_tokens 默认 8192，engine/config.py:43 注释明说 "small by design (MoE-priority)"），剩下的预算专家全拿，KV 吃残余。地步（lo）不是装饰：开了 prefill overlap 就至少要 2E 个槽（双缓冲借用），这个约束在这里与第 11.5 节的运行时断言首尾呼应。约束的两端都要写——规划端保证不产生非法几何，运行端断言兜底，两处注释互相引用。

预算不止启动时算一次。池子支持运行时重调（engine/engine.py:874 rebuild_runtime_cache：原地 resize 槽池/KV 页/GDN 槽，重捕获 CUDA Graph，不重载权重），暴露为 POST /v1/cache/rebuild 和 ft ctl cache --moe N --kv N（docs/cli.md:124）。重调的安全性靠两段式拒绝：先做纯几何校验（0a）与预算 fit-check（0b），校验不过就带着旧缓存原样拒绝，绝不先 free 再发现不够——「先拆后建失败」的服务器只能重启。

11.7对照：llama.cpp 的「专家放 CPU」是另一种解

llama.cpp 也面临「专家装不进显存」，它的答案是 buffer 类型覆盖——把 expert 张量静态地指到 CPU 内存（common/arg.cpp:2755-2770）：

common/arg.cpp — --cpu-moe / --n-cpu-moe（摘录，注释为译注）
c++{"-cmoe", "--cpu-moe"},
    "keep all Mixture of Experts (MoE) weights in the CPU",
    [](common_params & params, ...) {
        params.tensor_buft_overrides.push_back(llm_ffn_exps_cpu_override());
    }
...
{"-ncmoe", "--n-cpu-moe"}, "N",
    "keep the Mixture of Experts (MoE) weights of the first N layers in the CPU", ...

覆盖的正则与目标类型在 common/common.h:1131-1141：

common/common.h — 覆盖规则（摘录）
c++const char * const LLM_FFN_EXPS_REGEX = "\\.ffn_(up|down|gate|gate_up)_(ch|)exps";
...
inline llama_model_tensor_buft_override llm_ffn_exps_cpu_override() {
    return { LLM_FFN_EXPS_REGEX, ggml_backend_cpu_buffer_type() };
}

名字里带 ffn_*_exps 的张量落到 CPU buffer，于是调度器把这几层的 MoE 算子分派给 CPU 后端，每一步 decode 都在 CPU 上算 routed experts——张量不动，计算过去。

对照读： 两种解的差别是「张量不动计算动」vs「计算不动张量动」。llama.cpp 的粒度是静态配置：启动时定死哪几层的专家在 CPU，运行期零搬运、零缓存、零意外，代价是这几层每步都吃 CPU 内存带宽（第 12 章会看到 FreeToken 如何量化并利用这条带宽）。FreeToken 的粒度是动态缓存：全部层共享一个槽池，LRU 逐 token 决定谁在显存里。llama.cpp 的方案简单到不需要这一章的任何机制；FreeToken 的方案在 top_k/num_experts 小、路由偏斜、多请求共享热度时反超——两个设计各自押注了自己的典型负载。
维度llama.cpp（--cpu-moe）FreeToken（OffloadMoeCache）
放置粒度整层（正则匹配张量名）单个 (层, 专家) 槽位
替换策略无（静态，运行期不变）全局 LRU（usage/step）
decode 路径CPU 上算 GEMV，零搬运PCIe 拉缺失行 + GPU GEMM
prefill 路径同 decode（CPU 算或 mmap 读）整层流式 + 双缓冲 + hit-D2D
显存预算n_gpu_layers / buffer override 静态划分plan_cache_budget 贪心 + 运行时重调
额外约束无overlap 需 ≥2E 槽；marlin ≤992 槽

11.8小结

回到开头的账：137 GiB（ds_fp4）对 12 GiB 显存，靠 top_k=6 的稀疏性，一个小槽池就能吃到高命中。支撑这个槽池的是一套刻意保持简单的机制：扁平槽池 + slot_for_id/id_of_slot 双映射，LRU 只是 usage 时间戳加 argmin，没有链表没有堆，可以整段编进 CUDA Graph；8 种量化格式只在 _BANK_SCHEMAS 里声明 bank 布局，缓存机制对 bank 内部字节一概不感兴趣，只按行搬字节。decode 走三步：ensure_experts（选槽改写）→ copy_missing（fused copy）→ GEMM，簿记全在设备端；prefill 则整层流式，借槽池前 2E 槽当双缓冲，begin_prefill fence 防 decode 踩字节，hit-D2D 把命中行分流出去。磁盘侧 FTW 把全模型排成 4096 对齐的连续字节区供 O_DIRECT 直读，pin-after-fill 免掉一轮白搬；预算侧 MoE 优先贪心 + 两段式运行时重调，拒绝发生在算术层而不是 CUDA 分配上。llama.cpp 的对照是静态 buffer override——张量不动计算动，简单，且不共享热度。

槽池解决「谁在显存里」。下一步是「剩下的缺失怎么办」：PCIe 搬与 CPU 算这两条路怎么分、怎么并行。第 12 章：CPU/GPU 带宽协同。
