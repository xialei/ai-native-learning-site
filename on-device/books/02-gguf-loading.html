GGUF 与模型加载：权重从磁盘到显存

on-device 引擎的第一件事是「把模型装进这台机器」。GGUF 怎么编码元数据与张量、量化格式怎么选、mmap 为什么省内存、n_gpu_layers 怎么切——这一章把加载路径走完。

2.1GGUF 文件格式

GGUF（GPT-Generated Unified Format）是 llama.cpp 的单文件模型容器。一个文件里装三样东西：魔数与版本、键值元数据（架构名、上下文长度、tokenizer）、张量表（名字 + 类型 + 维度 + 偏移）。解析入口在 ggml/src/gguf.cpp：

ggml/src/gguf.cpp — gguf_init_from_reader 的头部校验（摘录，注释为译注；GGUF_MAGIC/VERSION 定义在 ggml/include/gguf.h:41-42）
c++// 文件魔数与版本（gguf.h）
#define GGUF_MAGIC   "GGUF"
#define GGUF_VERSION 3          // v1 已不支持，v3 为当前版本

// gguf.cpp:452 — 解析入口
static struct gguf_context * gguf_init_from_reader(...) {
    // 1) 读 4 字节魔数，逐字符比对
    for (uint32_t i = 0; i < magic.size(); i++) {
        if (magic[i] != GGUF_MAGIC[i]) {
            GGML_LOG_ERROR("%s: invalid magic characters...", __func__);
            gguf_free(ctx);
            return nullptr;
        }
    }
    // 2) 读版本号；高 16 位为 0 说明字节序与主机不符
    // 3) 读 n_tensors、n_kv，再逐个读键值对与张量信息
}
读懂这段： 版本检查里有一个容易忽略的细节——(ctx->version & 0x0000FFFF) == 0 用于探测大小端不匹配（大端机器读出的版本号会位移到高位）。GGUF 的设计目标是单文件、自描述、可 mmap：元数据都读进内存（很小），张量数据不拷贝，靠文件偏移直接映射。

关键元数据键（常量定义在 ggml/include/gguf.h）包括 general.alignment 等；模型架构名、quant version 等由 llama 层按字符串约定读取。张量信息表的每项记录了名字、维度、类型和对齐后的数据偏移——这就是 mmap 直读的索引。

2.2量化格式：从 Q4_0 到 NVFP4

llama_ftype 枚举（include/llama.h:116 起）给出了全部支持文件类型。挑几个里程碑（完整表见源码 :117-156）：

include/llama.h:116-158 — llama_ftype 节选（摘录，Q4_0=2 在 :119，Q1_0/Q2_0 在 :157-158）
cLLAMA_FTYPE_MOSTLY_Q4_0      = 2,   // 最基础的 4-bit 块量化
LLAMA_FTYPE_MOSTLY_Q4_K_M    = 15,  // K-quants：按重要性分块的 4-bit
LLAMA_FTYPE_MOSTLY_IQ2_XS    = 20,  // I-quants： importance 导向，2.x-bit
LLAMA_FTYPE_MOSTLY_TQ1_0     = 36,  // TQ：ternary，1-bit 级别
LLAMA_FTYPE_MOSTLY_MXFP4_MOE = 38,  // MoE 专家的 MXFP4（gpt-oss 系）
LLAMA_FTYPE_MOSTLY_NVFP4     = 39,  // NVFP4：4-bit + fp8 块 scale
怎么选： 数值上大致是「位宽每降 1-bit，困惑度代价递增，但显存占用减半」。日常推理 Q4_K_M 是质量/体积折中点；极限压缩（1~2-bit）用 IQ/TQ 系列；MoE 专家权重现在流行 MXFP4/NVFP4（第 10~11 章的 FreeToken 会原生读这些格式）。

每组量化的反量化数学都在 ggml/src/ggml-quants.c 与 ggml/src/ggml-cpu/quants.c 实现，各架构另有 ggml/src/ggml-cpu/arch/{x86,arm,powerpc,riscv,s390,wasm,loongarch}/quants.c 放 SIMD 特化；GPU 端在 CUDA 后端有配套的 dequant kernel 与 MMQ（matrix-mul-quantized）路径。

2.3mmap：不加载的加载

加载器 src/llama-model-loader.h 持有 use_mmap 标志。打开 mmap 后，权重数据不经历「读进 CPU 缓冲再拷进显存」两步，而是把文件页直接映射进进程地址空间：

  • CPU 层：张量指针就是映射地址本身（buffer_from_host_ptr），首次访问按页调入，物理内存里放不下的部分由 OS 回收（冷层自然被淘汰）。
  • GPU 层：CUDA 后端从映射地址发起 H2D 拷贝，避免多一次主机内存驻留。

load_mode 的选择逻辑在 src/llama-model.cpp 的 load_tensors()：

src/llama-model.cpp:1405-1438 — load_tensors 开头（摘录，注释为译注）
c++bool llama_model_base::load_tensors(llama_model_loader & ml) {
    const bool use_mlock = params.load_mode == LLAMA_LOAD_MODE_MLOCK
                        || params.load_mode == LLAMA_LOAD_MODE_MMAP_MLOCK;
    ...
    if (ml.use_mmap && params.load_mode == LLAMA_LOAD_MODE_AUTO) {
        for (const auto & dev : devices) {
            ggml_backend_dev_props props;
            ggml_backend_dev_get_props(dev.dev, &props);
            if (!props.caps.mmap_support) {
                ml.use_mmap = false;   // 某设备不支持 mmap → 全局退回
                break;
            }
        }
    }
    // resolve AUTO on systems without mmap support (e.g. iGPUs)
    if (ml.lazy.mode == LLAMA_LAZY_MODE_AUTO) { ... // 同样退回 OFF }
读懂这段： 两个 AUTO 都会「按能力降级」：设备不支持 mmap 就关 mmap，iGPU 这类设备直接把 lazy 模式关掉。这是 on-device 引擎的典型写法——默认值必须是「探测后的最优」而不是「理论最优」。

2.4n_gpu_layers：按 free memory 切层

「模型 40GB、显存 16GB」怎么办？llama.cpp 的答案是 --n-gpu-layers：把 transformer 的第 i_gpu_start 层之后搬进 GPU，其余留 CPU。而默认值会按每块设备的 free memory 比例自动分配多卡之间的层：

src/llama-model.cpp:1461-1519 — split 点计算与层分配（摘录，注释为译注）
c++// 默认 split：每块设备按 free memory 占比
if (all_zero) {
    for (size_t i = 0; i < n_devices(); ++i) {
        ggml_backend_dev_t dev = devices[i].dev;
        size_t total; size_t free;
        ggml_backend_dev_memory(dev, &free, &total);
        // 设备报 0 字节时退回 host 内存（issue #18577）
        if (free == 0 && total == 0) {
            ggml_backend_dev_memory(cpu_dev, &free, &total);
        }
        splits[i] = free;
    }
}
// 归一化成累计比例
...
const int i_gpu_start = std::max(n_layer_all + 1 - n_gpu_layers, 0);
const int act_gpu_layers = devices.empty() ? 0 : std::min(n_gpu_layers, n_layer_all + 1);
auto get_layer_buft_list = [&](int il) -> llama_model::impl::layer_dev {
    const bool is_swa = il < n_layer_all && hparams.is_swa(il);
    // 层号超出 GPU 覆盖范围 → CPU
    if (il < i_gpu_start || (il - i_gpu_start) >= act_gpu_layers) {
        return {cpu_dev, &pimpl->cpu_buft_list};
    }
    // 在 GPU 覆盖范围内 → 按 split 比例挑一块卡
    const int layer_gpu = std::upper_bound(
        splits.begin(), splits.begin() + n_devices(),
        float(il - i_gpu_start)/act_gpu_layers) - splits.begin();
    return {devices.at(layer_gpu).dev, ...};
};
// 输入层始终留 CPU：几乎没有收益
pimpl->dev_input = { cpu_dev, &pimpl->cpu_buft_list };
// 逐层分配 + 输出层
for (int il = 0; il < n_layer_all; ++il) {
    pimpl->dev_layer[il] = get_layer_buft_list(il);
}
pimpl->dev_output = get_layer_buft_list(n_layer_all);
读懂这段： ① n_gpu_layers() 返回「要放 GPU 的层数」（用户指定则用之，否则全部）；② i_gpu_start 是 GPU 起始层号——层数从后往前数，因为推理时层是串行走的，把尾部层放 GPU 同样生效；③ 多卡时按 free memory 加权切，不是平均切——24GB+8GB 的组合，24GB 卡分到 3/4 的层；④ 输入层（embedding）永远留 CPU，注释写明「offload 收益极小」。
坑 这套「按 free memory 比例切层」是静态的：加载时定死。推理过程中 KV cache 增长挤压显存时，它不会重新分配。这就是为什么后面章节（06）还要讲 fit-params——先在 CPU 上模拟整个内存规划，确认装得下再真的加载。

2.5FreeToken 侧：为什么它不用 GGUF（为主）

FreeToken 也支持 GGUF（python/freetoken/models/gguf/），但它的主路径是 FTW（FreeToken Weight）——一种为「把专家权重读进 host bank」优化过的自有格式（python/freetoken/checkpoint/ftw.py）。它的模块 docstring 说明了动机：

python/freetoken/checkpoint/ftw.py — FTW 格式 docstring（摘录，注释为译注）
python"""FreeToken Weight (FTW) checkpoint: one O_DIRECT-friendly on-disk format
for a whole model.

...safetensors 张量间无对齐，单个张量无法在任意偏移上 O_DIRECT 读；
每个 expert bank 一个文件的旧方案覆盖不了稠密权重，也把 norm/bias/router
这类小张量变成几百次小 IO。

FTW 修复两点：
* **Aligned** — 每个张量起始于 4096 对齐的区间偏移并 pad 到 4096；shard 在
  4096 对齐的边界切分。任何张量（或其 shard 内切片）都可以用对齐的
  offset/length/destination 一次读出——正是 O_DIRECT 要求的。
* **Unified** — kind="weight"（稠密权重）与 kind="experts_bank"（offload
  专家状态）放在同一个逻辑连续字节区里。

Layout on disk:
    <dir>/freetoken_weight.json        # 索引: tensors[] + shards[] + meta
    <dir>/freetoken-00000.ftw          # 字节区，按 ≤ 8 GiB 切 shard
"""
读懂这段： GGUF/safetensors 是「通用可交换」优先；FTW 是「磁盘→host bank 一次 DMA 到位」优先。所有张量 4096 对齐后，O_DIRECT 多线程 preadv 可以把 NVMe 顺序带宽打满，绕过 page cache。这条线在第 11 章展开（expert bank 装载流程）。

2.6小结

  • GGUF = 魔数/版本 + KV 元数据 + 对齐张量表；单文件、可 mmap、自描述。
  • 量化位宽谱系：Q4_0（2）→ Q4_K_M（15）→ IQ2_XS（20）→ TQ1_0（36）→ MXFP4_MOE（38）→ NVFP4（39）。
  • mmap 让「加载」变成「建立映射」；load_mode AUTO 按设备能力降级。
  • n_gpu_layers 按 free memory 比例静态切层，输入层恒留 CPU。
  • FreeToken 的 FTW 是同一个问题的另一种答案：放弃交换性，换取 O_DIRECT 直读。
