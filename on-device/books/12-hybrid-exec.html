hybrid：让 PCIe 与 CPU 内存带宽同时卖力

offload 把缺失专家全交给 PCIe 搬；hybrid 问了一个更准的问题：这一步的缺失里，多少该搬（GPU 吃 PCIe）、多少该就地算（CPU 吃内存带宽）？答案不是拍脑袋，是一台机器跑一次基准测出来的比例。

12.1两块带宽，一道分法

第 11 章的 offload 模式下，decode 每步每层的缺失专家都要过 PCIe（典型 16-32 GB/s）。而 CPU 这边——内存带宽 50-100 GB/s 的桌面机——整个 decode 期间基本闲着。hybrid 把两边同时用上：每步的缺失专家分成两份，一份经 PCIe 拉到 GPU 槽池由 GPU 算，剩下的直接在 CPU 上用 host bank 算 GEMV，两边的部分结果相加。

切分比例的推导写在 engine.py 的注释里（python/freetoken/engine/engine.py:714-718）：

python/freetoken/engine/engine.py — fetch fraction 推导（摘录，注释为译注）
python# _resolve_hybrid_fetch：--moe-hybrid-max-fetch -1 (auto) 的解析
# Perfect fetch/compute overlap wants fetched : cpu-computed misses = pcie_bw :
# (cpu_bw - pcie_bw), i.e. fetching a pcie_bw / cpu_bw fraction of each decode
# step's misses -- both sides then finish together instead of one idling.
读懂这段： 推导：设缺失量为 M，取 q 份走 PCIe、(1-q) 份走 CPU。PCIe 侧耗时 M·q/pcie_bw，CPU 侧耗时 M·(1-q)/cpu_bw。两边同时结束（重叠无等待）要求 M·q/pcie_bw = M·(1-q)/cpu_bw，解得 q = pcie_bw/cpu_bw。注意 CPU 侧公式里没有减 pcie_bw——减去的那部分出现在另一处（offload_cache.py:142 的 "fetched : cpu = pcie : cpu - pcie"），那是独立带宽下的近似；实测的重叠带宽（下一节）直接把争用效应测进去了，所以 engine 用的是简单的 pcie_bw/cpu_bw。同一策略两处推导、口径差一档——读代码时别把它们当成矛盾，它们对应「测什么」的两个版本。

这个 q 从哪来？不是默认值，是一台机器自己测自己：

python/freetoken/moe/bench_profile.py — 读取实测重叠带宽（摘录，注释为译注）
python# Preferred source is the *overlapped* pair (CPU MoE and PCIe gather measured
# while running concurrently -- the real contention regime): fetched/misses =
# pcie_ov / (pcie_ov + cpu_ov). Older profiles without it fall back to the
# standalone bandwidths ... which reduces to pcie/cpu.
for entry in entries:
    cpu_ov, pcie_ov = entry.get("cpu_moe_overlap_gbs"), entry.get("pcie_gather_overlap_gbs")
    if cpu_ov and pcie_ov:
        return min(1.0, pcie_ov / (pcie_ov + cpu_ov))
    cpu, pcie = entry.get("cpu_moe_gbs"), entry.get("pcie_gather_gbs")
    if cpu and pcie:
        return min(1.0, pcie / cpu)

12.2benchbw：给这台机器测一遍带宽

比例来自 ft bench bw（moe/benchbw.py），一台 GPU 跑一次，结果存 ~/.cache/freetoken/benchbw/<gpu-uuid>.json（docs/cli.md:198，按 UUID 键控——同型号卡插不同槽位带宽可能不同）。它测三组数：

测量方法用途
cpu_moe_gbsCPU MoE GEMV 实测（真实内核、真实 bank）hybrid/offload 判定（阈值默认 2×）
pcie_gather_gbscopy_missing 式 gather 实测同上，比值 = cpu/pcie
cpu_moe_overlap_gbs / pcie_gather_overlap_gbs两边同时满载跑 2 秒q* 分流比例（争用口径）

重叠测量的结构（benchbw.py:538-595）：双线程共享 barrier 起跑，CPU 侧线程循环跑 bs=1 的 CPU decode 步（run_task 释放 GIL），主线程循环 gather + synchronize 保证 DMA 真的在飞，各自报自己的 bytes/elapsed。为什么必须实测争用而不用独立带宽推导？docstring 给了反例：

python/freetoken/moe/benchbw.py:538-547 — measure_overlap_bw docstring（摘录，注释为译注）
python"""Concurrent achieved bandwidths (GB/s): the CPU MoE GEMV and the PCIe gather running
at the same time -- the contention regime hybrid decode's overlap actually lives in.

The standalone numbers cannot predict this split. Assuming full DRAM contention (CPU
keeps ``cpu_bw - pcie_bw`` under DMA) over-penalizes a CPU kernel that never saturated
DRAM to begin with -- the DMA then mostly rides the leftover bandwidth; assuming no
contention ignores it entirely. Measuring the contended pair directly gives the hybrid
backend its bandwidth-matched fetch split: fetched : cpu-computed = pcie_ov : cpu_ov.
"""

判定与分流用这套 profile 的决策链（docs/cli.md:82、engine/engine.py:1560-1628）：moe_strategy=auto 时默认 offload；若 profile 判定 hybrid（CPU 带宽 > 2× PCIe），再核对 CPU 执行器支持该激活函数、编译扩展没过期，都过了才升级 hybrid——每一步降级都有日志，绝不静默。分流比例 --moe-hybrid-max-fetch=-1（auto）读同一个 profile：没有 profile 就退回固定 cap=1（engine.py:728-733）。

读懂这段： 这个设计把「调参」变成了「测量」。q* 没有公式可推导——不同主板、内存条数、PCIe 通道数的组合，谁也推不准，测一次就一劳永逸（profile 按 format+GPU 键控，换格式或换卡才重测）。自适应的本质是承认自己算不准，把不确定的部分交给测量。
一段代码的进化痕迹 整条 hybrid 升级链有一个前提：host 和 GPU 之间存在一条 PCIe。统一内存 GPU（DGX Spark 的 GB10、Jetson）把这个前提抽掉了——没有 host/device 边界，offload 家族的一切搬运都是同一块 DRAM 的两个名字互倒，实测每个请求多出约 130 秒的停顿（#369）。#445 的修法不是给 hybrid 打补丁，而是在决策链最前面加一个分岔：探测到统一内存且模型装得下，auto 直接选 fused（常驻专家），跳过整个 benchbw hybrid 判定——「CPU 带宽升级」在共享内存的机器上没有意义。带宽策略要跟着内存拓扑走：PCIe 存在时才有「两边」可协同。

12.3hybrid decode：一份路由的两半

hybrid 的每步每层（layers/moe.py:298-345）是把第 11 章的 ensure_experts 换成带 cap 的变体，然后路由一分为二：

python/freetoken/layers/moe.py — _decode_hybrid（摘录，注释为译注）
pythonraw = topk_ids.clone()                            # 原始专家 id 留给 CPU 侧
cache.ensure_experts_hybrid(self.layer_id, topk_ids) # 原地改写：槽 id 或 -1（超 cap 的缺失）
...
on_gpu = topk_ids >= 0
cpu_ids = torch.where(on_gpu, raw.new_full((), -1), raw).contiguous()
pending = executor.decode_submit(self.layer_id, hidden_states, topk_weights, cpu_ids)
# ↑ CPU 池先开跑，再去做 GPU 的 PCIe fetch + GEMM —— 重叠点

cache.copy_missing()                              # GPU 只拉 cap 内的缺失（≤K 个）
gpu_slots = topk_ids.clamp_min(0)                 # -1 → 槽 0（权重置 0）
gpu_w = torch.where(on_gpu, topk_weights, topk_weights.new_zeros(())).contiguous()
gpu_routed = self._expert_gemm(cache, hidden_states, gpu_w, gpu_slots, ...)
cpu_routed = executor.decode_sync(pending)        # 等 CPU 部分算完
return gpu_routed + cpu_routed

「每条路由恰好算一次」靠的是双向置零：GPU 侧把 CPU 负责的路由权重置 0（id clamp 到槽 0，乘出来是 0）；CPU 侧把 GPU 负责的路由 id 置 -1（C++ 内核跳过 id<0）。两边都跑、各自只算自己那份、结果相加——没有 if 分支，全部是形状固定的张量操作，CUDA Graph 可捕获。

cap 的语义（offload_cache.py:855-874 ensure_experts_hybrid docstring）：每步每层最多把 hybrid_max_fetch 个（或 fetch_fraction×misses 个）缺失拉上 GPU，超出的记为 -1 交给 CPU；fetch 数量记进 num_indices 给 copy_missing，cap 前的总缺失数记进 num_missing_full 给统计。抓哪些缺失优先？看 expert_recency——最近活跃的专家优先上 PCIe（:196-201）。

读懂这段： 为什么「CPU 部分先提交、后等待」是安全的？decode_submit 只做三件事：D2H 拷激活与路由到 pinned IO、发 doorbell（12.4）、返回句柄——GPU 流上的后续节点（PCIe gather、GEMM）与 CPU 池的计算天然并行，汇合点在 decode_sync 的 WAIT 上。A/B 开关 FREETOKEN_HYBRID_OVERLAP=0 把 sync 提前到 gather 之前，串行跑两边——这个环境变量只用于测量重叠收益，不是功能开关（moe.py:325-326 注释明说 "Measurement knob"）。

12.4memop 握手：不用回调的 GPU-CPU 门铃

CPU 执行器（moe/cpu_executor.py）把「GPU 停下来等 CPU 算完」做成了一套门铃协议。第一版用 cudaLaunchHostFunc（回调派发），问题是延迟——文件头的账算得很清楚：

python/freetoken/moe/cpu_executor.py:32-43 — memop 方案的动机（摘录，注释为译注）
python# Flag-based GPU<->CPU handshake for hybrid/cpu decode. The default host-func path
# (cudaLaunchHostFunc submit+sync per layer) pays ~30-50us of callback dispatch latency
# per call with the GPU stream idle -- 2 calls per MoE layer per decode step (~6 ms/step
# on a 75-layer model). Instead the GPU raises a mapped-pinned "ready" flag at submit; a
# persistent CPU coordinator (in _cpu_moe) polls it, runs the layer, and sets a "done"
# flag the GPU waits on at sync -- no host-func round-trip. Both GPU-side operations are
# STREAM MEMORY OPERATIONS (cuStreamWriteValue64 / cuStreamWaitValue64, resolved from the
# driver at runtime): they execute on the GPU front end with no SM-resident kernel, so
# GPU utilization stays truthful during the CPU compute window. (The first cut used a
# spin-wait kernel; that pinned reported utilization at 99% and laptop CPU/GPU dynamic
# power schedulers responded by clamping the CPU frequency -- a net decode regression on
# power-coupled edge devices.) ...

C++ 侧的两次 write 与一次 wait（kernel/csrc/cpu_moe/cpu_moe_ext.cpp:646-664）：

python/freetoken/kernel/csrc/cpu_moe/cpu_moe_ext.cpp — memop submit/sync（摘录，注释为译注）
c++static void cumemop_submit(uintptr_t stream, uintptr_t done_addr,
                           uintptr_t ready_addr, int64_t slot) {
  // Order matters and is preserved by the front end: reset done BEFORE raising ready,
  // so the coordinator's completion write for THIS step can never be wiped.
  cumemop_check(g_cu_write64(s, done_addr + slot * 8, 0ULL, kCuWriteDefault),
                "cuStreamWriteValue64(done)");
  cumemop_check(g_cu_write64(s, ready_addr + slot * 8, 1ULL, kCuWriteDefault),
                "cuStreamWriteValue64(ready)");
}

static void cumemop_sync(uintptr_t stream, uintptr_t done_addr, int64_t slot) {
  cumemop_check(g_cu_wait64(s, done_addr + slot * 8, 1ULL, kCuWaitValueGeq),
                "cuStreamWaitValue64(done)");
}
图 12.1：门铃协议。三级退化路径：memop（默认）→ host-func（探测失败/超容量）→ watchdog 报错（卡死）。每级都是「功能正常但慢一档」，没有静默的错。
读懂这段： 三个历史教训都写在注释里，比机制本身更值钱：① 回调延迟——每层 2 次回调 × 30-50µs，层数一多每步白丢几毫秒（源码按 75 层模型算出 ~6ms/步），门铃把「每层两次往返」变成「每步一次轮询」；② 自旋内核骗了电源管理——GPU 利用率假 99%，笔记本的功耗调度看到「GPU 忙」就压 CPU 频率，解码反而更慢。memop 在 GPU 前端执行、不占 SM，利用率数字恢复诚实；③ watchdog 的三重确认（cpu_executor.py:607-617）——门铃 pending 跨 ≥10 秒、第一次见到时就 pending、期间 served 计数一动不动，三条同时成立才判死。两点采样会撞上正常的微秒级 pending 窗口，served 计数不变才是「协调者死了」的铁证。

12.5host bank：为带宽把每一步都做对

CPU 算 GEMV 的速度上限是内存带宽，host bank 的每个细节都在为这条带宽服务。物理核 pin（cpu_executor.py:92-116）：

python/freetoken/moe/cpu_executor.py:92-99 — 只用物理核（摘录，注释为译注）
pythondef physical_core_cpus() -> list[int]:
    """One logical CPU per physical core, restricted to this process's affinity.

    MoE decode is memory-bandwidth-bound, so SMT siblings only contend for the
    same core's load ports without adding bandwidth. Picking one logical CPU per
    physical core (and pinning to it) gives the best, most stable bandwidth.
    ..."""

协调者也要占核：auto 尺寸时从 worker 池里扣出最后一个物理核给协调者（:223-228），宁可少一个 worker 也不让 busy-poll 与 GEMV 抢核。pinned 内存的分配不走 torch 的 allocator——kernel/pinned.py 的理由是个具体的数字：

python/freetoken/kernel/pinned.py:1-6 — 精确尺寸 pinned（摘录）
python"""Exact-size pinned host tensors (e.g. offload expert banks).

The offload gather kernel (``fast_index_copy``) reads host memory zero-copy from the
GPU, so allocations must be pinned + device-mapped. We avoid
``torch.empty(pin_memory=True)`` because its caching allocator rounds sizes up to the
next power of two (a 70GB bank would reserve 128GB)."""

普通层用 mmap + 填满后注册（pin-after-fill，moe/host_banks.py:5-12——顺序反了会先付一轮全页 zero-fill，DSV4 的 137 GiB 约 47 秒白搬）。不 pin 的层（LOCKED：只有 OS 锁无设备地址；PAGEABLE：什么都不锁）没有 GPU 可见的别名，第 11 章见过它们在 copy_missing 里走整层同步路径——对应运行时字段 layer_residency 与 _unpinned_layers（offload_cache.py:212-216）。

ds_fp4 模型（DeepSeek-V4）还有一个「把标量循环挪出临界路径」的实例：W4A8 参考实现要求激活先过一遍 FP8 round-trip，C++ 侧的实现是单线程标量链（~0.3ms/层，H=4096），整条 decode 都在等它。有 GPU 时把这个数值上完全相同的 round-trip 挪到 GPU 上做（D2H 之前），CPU 侧跳过：

python/freetoken/moe/cpu_executor.py:303-310 — GPU prequant（摘录，注释为译注）
python# ds_fp4: the reference FP8 activation round-trip is a scalar per-element chain
# that the C++ side runs single-threaded on the CUDA host-callback thread --
# straight on the decode critical path (~0.3ms/layer at H=4096, every worker and
# the GPU waiting on it). When a GPU is present we run the numerically identical
# round-trip as a captured GPU kernel BEFORE the D2H ... Measured on
# DeepSeek-V4-Flash bs=1 decode: 12.85 -> 15.65 tok/s, output bit-identical

读懂这段： 15.65 对 12.85 是 22% 的提升，来源只是「别让每层的 decode 都在单线程标量循环上排队」（DSV4 有 43 层 MoE，每层省一次往返）。两个配套值得记：① 位等价测试（tests/moe/test_dsfp4_prequant.py）——GPU 侧用与 GPU W4A8 路径 bit-identical 的 kernel，测试跑两种 round-trip 各一遍逐位断言相等，「数值相同」不是声称而是被测过的性质；② 改动标在代码里而非只在 changelog（注释里的 tok/s 数字），下一个读代码的人能直接看到这个分支为什么存在。

12.6对照：llama.cpp 的 CPU 后端为什么不需要这一切

第 11 章说过，llama.cpp 的 --cpu-moe 是「张量不动、计算过去」：MoE 算子分派给 CPU 后端，每步都在 CPU 上算 routed experts。它没有 memop 握手、没有门铃、没有 worker 池 affinity——因为 ggml 的调度模型里 CPU 与 GPU 是两个后端在一张图里接力：sched 把图切开，CPU 段在 CPU 上跑、GPU 段在 GPU 上跑，同步点是图的两端，天然清晰。

对照读： FreeToken 不能这么做：它要的是同一条 CUDA 流上的重叠——CPU GEMV 与 PCIe fetch 并行，且整段要被 CUDA Graph 捕获。host node / memop 是 CUDA 流模型里「嵌一段 CPU 工作」的唯一正道，门铃与 watchdog 是把它做成生产可用的全部附加成本。llama.cpp 不捕获 CPU 工作（CPU 后端跑在图外），所以它不需要协议，只需要一个正确的切图。两个引擎在「GPU-CPU 协同」上的复杂度差，根源是要不要把 CPU 塞进 CUDA 流。
维度llama.cppFreeToken
协同模型sched 切图，CPU/GPU 各跑各段同一条 CUDA 流上 host node + memop 嵌入
同步方式图边界（sched 内部 barrier）门铃 ready/done + watchdog 兜底
CPU 线程ggml 线程池（n_threads）物理核 pin + 独立协调者核 + torch 线程让路
分支决策启动时静态（--cpu-moe / override）每步动态（recency 排序 + fetch fraction）
数值纪律各后端实现各自算子GPU/CPU 位等价测试钉住 round-trip

12.7小结

  • q* = pcie_bw/cpu_bw：两边同时收工的分流比例；来自实测争用带宽（benchbw 重叠测量），不是公式推导。
  • hybrid decode 双向置零：GPU 权重置 0、CPU id 置 -1，每条路由恰好算一次，全设备端形状固定。
  • memop 门铃：write done=0 → write ready=1 → … → wait done；前端执行不占 SM，利用率数字诚实。
  • 教训三连：回调 30-50µs×2/层太贵；自旋内核骗功耗调度反降频；watchdog 判死要三重确认。
  • host bank 的一切为带宽服务：物理核 pin、协调者独占核、精确尺寸 pinned、pin-after-fill。
  • GPU prequant 挪标量循环出临界路径：12.85 → 15.65 tok/s，位等价测试钉住正确性。
  • llama.cpp 的对照：切图接力不需要协议——复杂度差源于「CPU 是否要进 CUDA 流」。
