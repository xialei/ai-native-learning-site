计算图与调度：张量怎么落到正确的设备上

模型 forward 不是一段段手写的循环，而是一张 ggml 计算图。本章讲三件事：图怎么被复用、显存怎么被预留、节点怎么被分配到 CPU/GPU 并切图。

5.1图复用：为什么 decode 第二步起不用重建图

每个 ubatch 的图拓扑只由「形状参数」决定——token 数、序列数、输入种类。参数不变，图就不变，于是 llama.cpp 缓存上一张图，先问一句「还能用吗」：

src/llama-context.cpp:1341-1382 — process_ubatch 的图复用（摘录，注释为译注）
c++auto * res = gf_res_prev.get();
auto * gf  = res->get_gf();

const auto gparams = graph_params(res, ubatch, mctx, gtype);

if (!graph_reuse_disable && res->can_reuse(gparams)) {

    if (cparams.pipeline_parallel) {
        ggml_backend_sched_synchronize(sched.get());

} else {

内层逐个检查图的输入节点（embd、pos、out_ids、KV mask、recurrent state……每种输入类各自实现 can_reuse），例如 KV mask 比对的就是上一章那几个量（src/llama-graph.cpp:48-68）：

src/llama-graph.cpp — can_reuse_kq_mask（摘录，注释为译注）
c++static bool can_reuse_kq_mask(
        ggml_tensor * kq_mask,
        const llama_kv_cache_context * mctx,
        const llama_ubatch & ubatch,
        const llama_cparams & cparams) {
    const auto n_kv     = mctx->get_n_kv();
    const auto n_tokens = ubatch.n_tokens;
    const auto n_stream = cparams.kv_unified ? 1 : ubatch.n_seqs_unq;

    bool res = true;
    res &= (kq_mask->ne[0] == n_kv);            // KV 窗口长度变了 → 图要重建
    res &= (kq_mask->ne[1] == n_tokens/n_stream);
    res &= (kq_mask->ne[2] == 1);
    res &= (kq_mask->ne[3] == n_stream);
    return res;
}
读懂这段： 复用不是「跳过计算」，是「跳过 CPU 上的建图 + 分配」这两个 CPU 密集步骤，GPU 计算照跑。注意 decode 单 token 场景下形状几乎恒定（n_tokens=1、n_kv 渐增——n_kv 变了 mask 形状就变，所以窗口涨的时候还是要重建；这正是 KV padding 到 256 对齐的动机之一：让 n_kv 阶梯状跳变，多数步复用成立）。计数器 n_reused 会在 llama_perf 里报告为「graphs reused」。

5.2sched_reserve：三次 reserve 的启动仪式

启动时 llama.cpp 会用「最坏情况」图把计算缓冲一次性预留到位，推理期间 galloc 只在其中做原地分配。reserve 序列是 pp → tg → pp 三次：

src/llama-context.cpp:623-681 — 三次 reserve（摘录，注释为译注）

            LLAMA_LOG_WARN("%s: compute buffer allocation failed, retrying without pipeline parallelism\n", ...);
            cparams.pipeline_parallel = false;   // 退一步重试
            ...
        }
        ...
    }
    n_splits_pp = ggml_backend_sched_get_n_splits(sched.get());
    n_nodes_pp  = ggml_graph_n_nodes(gf);
}

// 再用 tg（token generation，bs=1）图 —— 只为拿到 splits/nodes 计数
{
    auto * gf = graph_reserve(n_seqs, n_seqs, n_seqs, mctx.get(), model.hparams.no_alloc);
    ...
    n_splits_tg = ggml_backend_sched_get_n_splits(sched.get());
    n_nodes_tg  = ggml_graph_n_nodes(gf);
}

// 最后再用 pp 图 reserve 一遍 —— 避免 ggml-alloc 在推理期间重新分配
{
    ggml_cgraph * gf = nullptr;
    switch (model.arch) {
        case LLM_ARCH_MINIMAX_01:
            // 特例：inp_diag_decay 随 n_seq_tokens^2 增长，n_seqs==1 反而更耗
            gf = graph_reserve(n_tokens, 1, n_outputs_pp, mctx.get(), ...);
            break;
        default:
            gf = graph_reserve(n_tokens, n_seqs, n_outputs_pp, mctx.get(), ...);
    };
    ...
}
读懂这段： 启动日志里的两行输出「compute buffer size = xxx MiB」「graph nodes = N (with bs=512), M (with bs=1)」就是这里打出来的。三次 reserve 的逻辑：① pp 图最大（要装下 n_ubatch 个 token 的激活），先按它分配；② 跑一遍 tg 图测出 decode 场景的 splits 数——这决定运行时切图次数，必须保证 decode 图也放得下；③ 再以 pp 收尾，确保最终驻留的缓冲是最大形状。MINIMAX_01 的 switch 提醒我们「最坏情况」不总是 bs 最大的那个——个别架构的中间激活随序列数平方增长。

5.3split_graph：把一张图切给多个后端

多设备（或 CPU+GPU 混跑）时，一张图的不同节点会落在不同后端上。ggml_backend_sched_split_graph（ggml/src/ggml-backend.cpp:1066）用五遍扫描完成分配（前三遍定后端归属，后两遍补剩余 src 与切图找拷贝点）：

5.4对照：FreeToken 的 CUDA Graph

llama.cpp 的图是「每次推理现建的张量 DAG」（哪怕复用也要填输入）；FreeToken 把 decode 前向整段录制成 CUDA Graph，运行时一次 replay 消掉上千次 kernel launch 的 CPU 开销。先看 batch 尺寸候选怎么定（python/freetoken/engine/graph.py:68-87，函数体到 :87）：

python/freetoken/engine/graph.py — bs 候选（摘录，注释为译注）
pythondef _determine_cuda_graph_bs(cuda_graph_bs, cuda_graph_max_bs, free_memory):
    if cuda_graph_bs is not None:
        return cuda_graph_bs

    free_memory_gb = free_memory / (1 << 30)
    if cuda_graph_max_bs is None:
        if free_memory_gb > 80:  # H200
            cuda_graph_max_bs = 256
        else:
            cuda_graph_max_bs = 160

    candidates = [1, 2, 4] + list(range(8, cuda_graph_max_bs + 1, 8))
    return [bs for bs in candidates if bs <= cuda_graph_max_bs]

捕捉阶段每个 bs 录一张图，共享同一个内存池：

python/freetoken/engine/graph.py:158-198 — capture 与 replay（摘录，注释为译注）
pythonfor bs in pbar:
    graph = torch.cuda.CUDAGraph()
    batch = Batch(reqs=[self.dummy_req] * bs, phase="decode")
    ...
    with get_global_ctx().forward_batch(batch):
        self.buffer.logits[:bs] = model.forward()
        # 先跑一遍「热身」再录：保证 offload cache 已热，
        # 否则录制下来的图会带着冷缓存的专家拷贝
        with torch.cuda.graph(graph, pool=pool, stream=self.stream):
            self.buffer.logits[:bs] = model.forward()
        self._reset_moe_offload_cache()
    if pool is None:
        pool = graph.pool()  # 复用同一块 graph 内存池，省显存
    self.graph_map[bs] = graph

def replay(self, batch: Batch) -> torch.Tensor:
    assert self.can_use_cuda_graph(batch)
    self.buffer.copy_from(batch)               # 输入写进固定的捕捉缓冲
    g = self.graph_map[batch.padded_size]
    self.attn_backend.prepare_for_replay(batch)
    g.replay()
    return self.buffer.logits[: batch.size]
对照读： 两种「图」解决的问题不同：llama.cpp 的 can_reuse 省的是建图 + 分配（CPU 上的张量拓扑搭建），CUDA Graph 省的是kernel launch（每秒上万次小提交的驱动开销）。FreeToken 能录整张图的前提是形状完全静态：bs 用 padded_size 补齐到候选档位、GDN 槽位经由 copy_from 写入、每档捕捉前先跑一遍热身 forward 把 offload cache 烘热——源码注释说得很直白：「Resetting here forces CUDA graph capture to replay cold-cache expert copies」，所以 reset 只能放在捕捉之后，为下一档复位。代价是一段可观捕捉时间和一块固定池显存——消费级卡上 max_bs=160 的候选要录 20+ 张。llama.cpp 走的是另一极：图每次可变、灵活但 CPU 开销大。第 13 章会把这个对照收进自研清单。

5.5小结

  • 图拓扑由 ubatch 形状参数唯一决定 → can_reuse 逐输入类校验，decode 常态复用。
  • sched_reserve 用 pp→tg→pp 三次 reserve 一次性预留计算缓冲；个别架构最坏情况不是 bs 最大时。
  • split_graph 五遍扫描：预分配锚定 → GPU 成片扩张（CPU 只兜底）→ 同缓冲类型升级 → 从 dst/view_src 补剩余 src → 切图找拷贝点。
  • FreeToken 用 CUDA Graph 换掉另一类开销（launch），前提是把一切形状焊死成候选档位。
