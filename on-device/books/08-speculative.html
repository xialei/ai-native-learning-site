投机解码：用小模型赌大模型的输出

decode 的本质瓶颈是内存带宽——每出一个 token 都要把全部权重过一遍。投机解码的答案：让便宜的东西一次猜一串，贵的东西一次验一串。llama.cpp 目前支持 11 种投机实现，FreeToken 一个都还没有。

8.1为什么端侧特别需要投机

服务端集群跑投机解码的收益有限——batch 大时 GPU 本来就饱和，多算几个 token 反而挤占吞吐。端侧正相反：batch=1、带宽受限、单请求延迟就是一切。批量出 4 个 token、接受率 60% 的话，等效速度 ×2.2（4×0.6=2.4 token/次前向 vs 1）。llama.cpp 的投机支持全在 common/speculative.cpp，注册表一眼可见：

common/speculative.cpp:30-45 — 投机类型注册表（摘录）
c++const std::map<std::string, common_speculative_type> common_speculative_type_from_name_map = {

注册表里的 11 种实现归成两大家族：draft 系列（需要一个小模型/额外权重）和 ngram 系列（纯 CPU 自投机，不需要任何额外模型）。接口倒是统一的，都是 common_speculative_impl 的虚函数：process（随 target 批量喂 draft）/ draft（生成草稿 token 序列）/ accept（校验后回收）。

8.2兼容性：词表必须对齐

draft 模型与 target 模型的词表必须一致——每个 draft token 最终都要映射回 target 词表。校验逻辑（common/speculative.cpp:67-130）：

common/speculative.cpp — 词表兼容检查（摘录，注释为译注）
c++// vocab 类型（BPE/SentencePiece）必须一致
if (vocab_type_tgt != vocab_type_dft) { ... return false; }

// bos/eos 的处理与 id 必须一致
if (llama_vocab_get_add_bos(vocab_tgt) != llama_vocab_get_add_bos(vocab_dft) || ...) {
    return false;
}

// 词表大小允许 ±128 的差异 —— 但逐 token 文本必须一致
if (vocab_diff > SPEC_VOCAB_MAX_SIZE_DIFFERENCE) {  // #define ... 128
    return false;
}
for (int i = SPEC_VOCAB_CHECK_START_TOKEN_ID; i < std::min(n_vocab_tgt, n_vocab_dft); ++i) {
    const char * token_text_tgt = llama_vocab_get_text(vocab_tgt, i);
    const char * token_text_dft = llama_vocab_get_text(vocab_dft, i);
    if (std::strcmp(token_text_tgt, token_text_dft) != 0) {
        return false;   // 同 id 不同文本 → 拒绝
    }
}
代码里两个 magic number 各有来历。SPEC_VOCAB_CHECK_START_TOKEN_ID = 5：前几个 id 是 special tokens，不同模型分词器对它们的取舍不同，所以从 id=5 才开始逐字比对。SPEC_VOCAB_MAX_SIZE_DIFFERENCE = 128：允许 target 比 draft 略大——典型情形是相同分词器、target 多了几个微调 token。这两个数字就是「双模型投机」的准入门槛。

8.3draft-simple：最小实现

最简单的 draft 实现只有 200 来行，把整个机制讲清楚了（common/speculative.cpp:179-424）：

common/speculative.cpp — draft 循环（摘录，注释为译注）
c++void draft(common_speculative_draft_params_vec & dparams) override {
    ...
    // 每个还在起草的序列：最后一个已确认 token 喂给 draft 模型
    for (llama_seq_id seq_id = 0; seq_id < (llama_seq_id) n_seq; ++seq_id) {
        auto & dp = dparams[seq_id];
        if (!dp.drafting) { continue; }
        n_drafting++;
        common_batch_add(batch, dp.id_last, dp.pos0, { seq_id }, true);
    }

    int ret = llama_decode(ctx_dft, batch);   // 起始 token 先算一步
    ...
    while (n_drafting > 0) {
        common_batch_clear(batch);
        for (每个 drafting 序列) {
            // 用 draft 自己的 sampler 从 draft logits 采样
            common_sampler_sample(smpl, ctx_dft, i_batch, true);
            const auto * cur_p = common_sampler_get_candidates(smpl, true);
            const llama_token id = cur_p->data[0].id;

            // 只收集高置信度的草稿：首候选概率低于 p_min 就停
            if (cur_p->data[0].p < params.p_min) {
                drafting[seq_id] = false;
                n_drafting--;
                continue;
            }
            result.push_back(id);
            // 达到 n_max 就停
            if (params.n_max <= (int) result.size() || ...) { ...; continue; }
            common_batch_add(batch, id, dp.pos0 + i + 1, { seq_id }, true);
        }
        if (batch.n_tokens == 0) { break; }
        llama_decode(ctx_dft, batch);       // draft 模型每步一 decode
        ++i;
    }

    // 草稿数不足 n_min → 全部作废（验证一次不值当）
    for (auto & dp : dparams) {
        if (dp.drafting && dp.result->size() < (size_t) params.n_min) {
            dp.result->clear();
        }
    }
}
draft 循环就靠三个旋钮控制：n_max 管最多猜几个；n_min 管少于这个数就整批作废——验证一次的开销大于收益时，白猜；p_min 管何时提前收手——draft 模型首候选概率低于它就停止继续猜，低置信度 token 大概率被拒，与其浪费验证算力不如提前收手。草稿生成时 draft 模型逐 token decode，target 模型随后一次 decode 验证整串（server 端组织，见 8.5）。
一段代码的进化痕迹 起始位置这个字段曾叫 n_past。名字埋着雷：n_past 在 llama.cpp 语境里到处是「token 数量」的意思，而这个字段要的是位置——server 端填 slot.prompt.n_tokens()（数量）在纯文本下恰好对得上，一旦 prompt 里插了图，图文 token 数与位置数就分道扬镳，从图之后投机全错位（#28715）。修复分两步：字段改名 pos0，server 端改传 slot.prompt.tokens.pos_next()（下一个真实位置）。类型不够用的地方，命名替你兜底；命名错了，类型系统也救不回来。

8.4EAGLE3 与变体家族

draft-simple 需要「一个完整的小语言模型」。EAGLE3 系不训练小模型，而是复用 target 的中间层特征：draft 解码器以 (token, 特征) 对为输入——注释写明输入约定（common/speculative.cpp:394-408）：

common/speculative.cpp — EAGLE3 输入约定（摘录，注释为译注）
c++// EAGLE3 speculative decoding state
//
// Input of draft decoder: (This is different compared to MTP)
//   At "pos P", the decoder takes input pair (t_{P+1}, g_P), with RoPE at P.
//   g_P = target 中间层特征（features_buf 拼接 target_layer_ids 指定的层）

draft 阶段把上一个 verify 周期存下的 target 特征拼进 batch.embd：

common/speculative.cpp — EAGLE3 延迟配对（摘录，注释为译注）
c++// Complete the deferred boundary pair (dp.id_last, pending_g_last) at memory
// pos pending_pos_last. dp.id_last is target's freshest sample (= corrected
// token after verify, or first generated token after prefill), matching the
// EAGLE3 input convention (token[P+1], g_embd[P]) at pos P.
llama_memory_seq_rm(llama_get_memory(ctx_dft), seq_id, pending_pos_last[seq_id], -1);
common_batch_add(batch, dp.id_last, pending_pos_last[seq_id], { seq_id }, true);
std::memcpy(batch.embd + (size_t)(batch.n_tokens - 1) * n_embd_dec,
            pending_g_last[seq_id].data(),
            row_bytes);
EAGLE3 的草稿输入不是纯 token，而是「token + target 中间层特征」拼对——特征来自 verify 阶段 target 前向时顺带提取的中间层输出（verify_g 缓存，下一个周期复用）。这让它比独立小模型更准：draft 解码器看得见 target 的「内心状态」，接受率显著更高。剩余变体一句话带过：draft-mtp 用模型自带的 multi-token prediction 头（无需第二个权重文件）——它一个驱动要覆盖三种模式：gemma4 共享 target KV、所有头跑一张图；step35 有 n_mtp_layers 个训练好的头，每个草稿步一个（chain_heads）；qwen35/qwen35moe 只有单个头（源码注释里点名的就是这三个家族）；draft-dflash/dspark 是另两种轻量 draft 结构；ngram 系列完全不用第二个模型——从最近输出里找 n-gram 匹配当作草稿，CPU 上零成本，适合结构化文本（代码、重复模式的 JSON）。

8.5验证与回滚：server 端的簿记

草稿串进入 target 模型一次 decode，逐位置与 target 采样对比：一致则接受，首个不一致处截断、回滚 KV。server 端的簿记逻辑（tools/server/server-context.cpp:3057-3068）：

tools/server/server-context.cpp — 投机检查点（摘录，注释为译注）
c++// TODO: avoid restoring the draft context and re-evaluating the drafted
// tokens when not needed [TAG_SPEC_AVOID_DRAFT_REEVAL]

if (ctx_dft) {

    }

    }
}

if (!draft.empty()) {

验证失败后的回滚就是第 4 章那对原语：seq_rm(seq, pos_max+1, -1) 把草稿区的 KV 记账删掉。recurrent 模型（rs 序列状态）不能随便删，所以才有 COMMON_CONTEXT_SEQ_RM_TYPE_RS 分支，草稿串超过 rs 容量时才做完整检查点快照（ckpt.update_tgt/dft）。投机解码的工程成本大半在这里：接受率提升是模型的事，回滚正确性是引擎的事。

8.6对照：FreeToken 的空白

FreeToken 目前没有任何投机解码实现。有一个耐人寻味的痕迹：DeepSeek-V4 的配置里有 n_mtp_layers: int = 1（python/freetoken/models/deepseek_v4/args.py:33），但全仓只有这一个定义、没有任何消费方；weight.py 加载专家库时明确跳过 MTP 层：

python/freetoken/models/deepseek_v4/weight.py:176-178 — MTP 被跳过（摘录，注释为译注）
pythondef iter_expert_pieces(model_path, config, kind, *, parallel=False, workers=8, chunk=8 << 20):
    """Routed experts, one piece per expert: ``{gate, up, down}`` e2m1 pairs and their e8m0
    ``_scale`` companions (``w1`` / ``w3`` / ``w2``). The MTP layer's experts are skipped."""
这个空缺不是疏忽而是排序：FreeToken 的 decode 路径被 CUDA Graph 焊死成固定形状（第 5 章），草稿串长度可变的投机验证会把形状打碎——要么每档草稿长度再录一批图（显存爆炸），要么放弃图。CUDA Graph 与投机解码在当前实现下互斥。反过来，llama.cpp 的动态图（第 5 章 can_reuse）恰好天然支持「草稿长度每次都变」——两种图策略的优势互换了一次。自研引擎若两条都要，得在 graph capture 时把草稿长度也做成档位（FreeToken 的 bs 档位思路可以平移过来）。

8.7小结

端侧是投机解码收益最大的地方——batch=1、带宽受限，一次前向出 2-4 个等效 token 就是实打实的加速。机制上 11 种实现共用一个接口：draft（猜）→ target 一次验证 → accept/回滚。draft 系的准入门槛是词表对齐（±128 容差 + 逐 token 文本一致），ngram 系连模型都不要。p_min/n_min/n_max 三个旋钮分别管「何时收手、何时白猜、最多猜多少」。真正费工的不是算法是簿记：验证失败的回滚就是 seq_rm 记账删除。FreeToken 一侧没有投机——MTP 字段有、实现无，根因是 CUDA Graph 静态形状与变长草稿互斥。
