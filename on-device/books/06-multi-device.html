多设备：一张卡装不下，然后呢

消费级场景的「多设备」包括 CPU+GPU 混跑和多卡。llama.cpp 的方案是「按层切 + sched 动态切」，FreeToken 的方案是「单卡装注意力 + CPU 扛专家」——两条路线都在回答同一道题：内存装不下时，什么留在慢介质上。

6.1后端注册表：动态加载的设备抽象

llama.cpp 支持十几种硬件，靠的不是 if-else 堆叠，而是一个运行时注册表。后端可以编译成独立动态库，启动时扫描目录加载（ggml/src/ggml-backend-reg.cpp:578-605）：

这套东西其实就是一个插件系统的最小实现：约定导出符号（注册表 + score），运行时扫描 libggml-*.so / .dll。好处很实际——硬件厂商可以不碰主仓发布自己的后端；用户可以只编译需要的后端；同一台机器上不同实现的库按 score 择优。静态编译时这些符号退化成内置注册。还有一点值得强调：llama 二进制是统一的——不存在「llama-cuda」「llama-metal」分身。

6.2按层切分：layer 模式的默认切法

多卡默认 split-mode=layer：每卡拿连续一段层。层怎么分到卡？第 2 章见过的 get_layer_buft_list，这里看完整上下文（src/llama-model.cpp:1488-1537）：

切分算法朴素到令人安心：free memory 比例 → 归一化前缀和 → upper_bound 定层所属卡。有个此前没展开的细节：embedding/input 层恒 CPU——注释原话是「there is very little benefit to offloading the input layer」。这段逻辑同时决定权重分布和 KV cache 归属（层在哪卡，那层的 KV 就在哪卡）。

6.3split-mode 三选一

CLI 上一个 flag，背后是三种执行方式（include/llama.h:198-203）：

include/llama.h — llama_split_mode（摘录）
cenum llama_split_mode {
    LLAMA_SPLIT_MODE_NONE   = 0, // single GPU
    LLAMA_SPLIT_MODE_LAYER  = 1, // split layers and KV across GPUs
    LLAMA_SPLIT_MODE_ROW    = 2, // 旧 row 切分，已被 tensor 取代（弃用）
    LLAMA_SPLIT_MODE_TENSOR = 3,
};

layer 与 tensor 的取舍，官方文档一句话讲透（docs/multi-gpu.md）：

layer vs tensor（docs/multi-gpu.md 原文大意） 流水线并行（layer）让不同层驻留不同卡、token 顺序流过——跨卡传输最少，但需要足够多的 token 才能摊平流水线气泡。张量并行（tensor）把每层切到多卡、每层做多次跨卡规约——对互联带宽极其敏感。layer 最大化 batch 吞吐，tensor 最小化延迟。消费级多卡通常没有 NVLink，PCIe 上 layer 几乎总是对的选择。

tensor 模式还有硬约束，源码里直接写死（src/llama-context.cpp:3762-3772）：

src/llama-context.cpp — TENSOR 模式约束（摘录，注释为译注）
c++if (model->split_mode() == LLAMA_SPLIT_MODE_TENSOR) {

        LLAMA_LOG_INFO("%s: enabling flash_attn since it is required for SPLIT_MODE_TENSOR\n", __func__);
        params.flash_attn_type = LLAMA_FLASH_ATTN_TYPE_ENABLED;   // 自动档 → 强制开 FA
    }
    if (params.flash_attn_type != LLAMA_FLASH_ATTN_TYPE_ENABLED) {
        LLAMA_LOG_ERROR("%s: SPLIT_MODE_TENSOR requires flash_attn to be enabled\n", __func__);
        return nullptr;      // 明确关 FA → 拒绝启动
    }
    if (model->get_split_state_ud.n_devices == 1) {
        LLAMA_LOG_WARN("%s: SPLIT_MODE_TENSOR being used for a single device is not recommended\n", __func__);
    }
}
为什么 tensor 模式非要 FA 不可？张量并行下注意力头被切到多卡，每卡只握有一部分 head 的 K/V，普通 eager attention 要拼完整 mask 矩阵，而 FA 按块算、不依赖完整形状。文档还明确：tensor 模式下自动 fit（--fit）不可用，得自己压 ctx-size / parallel / ngl。

6.4pipeline parallel：layer 模式的调度细节

layer 模式下多卡可以组成流水线，但流水线并行「会增加内存用量」，所以只在特定条件组合下启用（src/llama-context.cpp:427-434）：

src/llama-context.cpp — pipeline_parallel 条件（摘录，注释为译注）
c++// TODO: move these checks to ggml_backend_sched
// enabling pipeline parallelism in the scheduler increases memory usage,
// so it is only done when necessary
bool pipeline_parallel =
    model.n_devices() > 1 &&
    model.n_gpu_layers() > hparams.n_layer_all &&
    model.split_mode() == LLAMA_SPLIT_MODE_LAYER &&
    cparams.offload_kqv &&
    !model.has_tensor_overrides();

// pipeline parallelism requires support for async compute and events in all devices
// （逐设备检查 async compute + events，CPU 后端跳过）
条件里 n_gpu_layers() > n_layer_all 的意思是「全部层（含输出层）都在 GPU 上」——部分层在 CPU 时 CPU 本来就是瓶颈，流水线无益还费内存。内存代价来自每个 split 边界要缓冲一个 micro-batch 的中间结果。async compute + events 检查则防止不支持流间事件的老设备死锁。此外第 5 章见过：pp 预留失败时还会退掉 pipeline_parallel 重试一次。

6.5对照：FreeToken 不切层，切「搬运什么」

FreeToken 面对的是另一道题：消费级单卡（8-24GB）跑 DeepSeek-V4 级别的 MoE。单卡谈不上切层，它的多设备故事是注意力 + 共享专家 + KV 留在 GPU，routed experts 放 CPU 内存按需搬（第 11/12 章主角）。多卡时它做的是标准 TP，但多加了一步内存一致性检查（python/freetoken/engine/engine.py:811-830）：

python/freetoken/engine/engine.py:811-830 — _sync_get_memory 硬错（摘录，注释为译注）
python# TP 各 rank 上报 free memory，取 min 作为预算基准；
# 卡间不平衡超过 2GiB 直接拒绝启动——不平衡说明某张卡被
# 其他进程占用，按 min 算出的 offload 预算会在那张卡上 OOM
mems = self._sync_get_memory()
if max(mems) - min(mems) > 2 * (1 << 30):
    raise RuntimeError("TP rank free memory imbalance > 2GiB ...")
这两个引擎对「多设备」的理解根本不是一回事。llama.cpp 的多设备是「把一个稠密模型拆开」，优化目标是跨卡流量最小；FreeToken 是「把一个稀疏模型安放好」，优化目标是专家搬运带宽最大。切层 vs 放专家：前者的切分单位是层（一个大矩阵不拆），后者是专家（矩阵集合里按需搬运的子矩阵）。这个差别决定了第 11 章 OffloadMoeCache 的整个设计空间。

6.6小结

这一章的两条路线说到底都是在回答「装不下怎么办」。llama.cpp 的答案是把模型拆开运：后端注册表靠运行时扫描动态库 + score 择优，llama 二进制统一不分后端；layer 模式按 free-memory 比例切层、输入层恒留 CPU、sched 运行时再微调；tensor 模式是实验性的 TP，强制 FA、不支持 fit，row 已弃用；pipeline parallel 只在「全层上卡 + LAYER 模式 + 无 override」时才启用。FreeToken 的答案更釜底抽薪——单卡 + CPU 专家库，不切模型，切「搬运什么」。
