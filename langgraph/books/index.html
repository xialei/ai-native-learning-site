1.1LangGraph 是什么

LangGraph 是一个用于构建有状态、多角色 Agent 应用的低层编排框架。它的核心思想是把 Agent 的逻辑建模成一张图：

  • 节点（Node） = 计算单元：一个函数，接收当前状态、返回状态更新（可以调 LLM、调工具、做任何 Python 计算）。
  • 边（Edge） = 控制流：决定下一个执行哪个节点，可以是固定的，也可以是基于状态动态判断的（条件边）。
  • 状态（State） = 共享数据：在节点之间流转的结构化数据，由用户用 TypedDict / Pydantic 定义，由 reducer 决定如何合并。

这个抽象之所以重要，是因为真实的 Agent 不是「一次 LLM 调用」就能解决的——它需要在循环中调用工具、记录中间结果、在合适的时候停下来等人确认、出错后能从断点恢复。LangGraph 把这些工程需求统一成图的执行语义，让你既能用高层 API 快速起手，也能在需要时下钻到节点和边的层面精细控制。

提示 为什么选「图」作为抽象：市面上很多 Agent 框架把循环藏在黑盒里（一个 while + LLM 决策），简单场景很爽，但一旦要做「先做 A 再让人审核、审核不过回到 A、过了进入并行子任务」这类有结构的流程，黑盒就很难表达。图天然能描述分支、循环、并行与子图嵌套，而且每一步的状态都可观测、可持久化、可恢复——这正是把 Agent 从 Demo 推向生产所必需的可控性。

1.2核心价值

围绕「可控、可记、可协同」，LangGraph 提供了把 Agent 推向生产所需的六块能力：

能力一句话说明
可控性显式的状态与控制流，节点和边都可见可调，不再是黑盒循环。条件边让你精确决定每一步走向。
持久化Checkpointer 在每一步后自动保存状态快照，按 thread_id 隔离，支持回放、断点续跑与时间旅行调试。
人机协同interrupt() 在任意节点暂停执行、把控制权交回调用方；用 Command(resume=...) 带着人的输入继续，天然支持审核与确认。
流式输出stream() 支持 values / updates / messages / debug 多种模式，既能拿到每步状态增量，也能逐 token 流式 LLM 输出。
多智能体子图即节点，可把一组节点封装成可复用模块；通过 Supervisor / Swarm 等模式编排多个 Agent 协作分工。
生产就绪原生支持异步、并发节点、超时控制；可对接 Postgres/SQLite 检查点，并通过 LangGraph 部署为可水平扩展的服务。
六块能力是同一条主线：这六块不是彼此孤立的功能点，而是同一条主线的不同切面——「可控性」是图抽象带来的结构红利，「持久化」和「人机协同」是可控性的工程化延伸，「流式输出」让可控性可观测，「多智能体」让图可以嵌套组合。理解这条主线，就能明白为什么本站先讲图、再讲状态、再讲控制流，最后才落到选型。

1.3快速开始｜用 create_react_agent 三行起一个 Agent

最快体验 LangGraph 的方式是用 create_react_agent 起一个能调工具的 ReAct Agent。它本质上是预置好的「LLM 节点 ↔ 工具节点」循环图，三行就能跑起来：

最简 ReAct Agent —— 模型 + 工具即可得到一个 CompiledStateGraph
pythonfrom langchain_openai import ChatOpenAI
from langgraph.prebuilt import create_react_agent

# 1. 准备模型与工具
model = ChatOpenAI(model="gpt-4o-mini")

def get_weather(city: str) -> str:
    """查询某个城市的天气。"""
    return f"{city} 今天晴， 22°C"

# 2. 三行起手式： 模型 + 工具 → 一个可调用的 Agent
agent = create_react_agent(model, tools=[get_weather])

# 3. 调用： 框架自动在 "调模型" 与 "调工具" 间循环， 直到模型不再发起工具调用
result = agent.invoke({"messages": [{"role": "user", "content": "北京天气怎么样？"}]})
print(result["messages"][-1].content)  # 模型最终给出的自然语言回答
三行背后是一张图：create_react_agent(model, tools) 内部其实帮你建了一张 StateGraph——它有一个调用 LLM 的 agent 节点、一个执行工具的 tools 节点，以及一条「模型发起工具调用就进 tools，否则就结束」的条件边。你看到的 invoke 并不是一次性的 LLM 调用，而是框架在两个节点间循环多轮，直到模型判断不再需要工具。这正是后面第 02、05 章会带你手写一遍的图。
注意 关于 create_react_agent：它返回一个 CompiledStateGraph，但源码已正式将其标记为弃用（@deprecated(category=LangGraphDeprecatedSinceV10)），迁移目标是 langchain 包中带中间件系统的 create_agent（from langchain.agents import create_agent）。新项目建议直接用 create_agent。本站第 05 章会先用 create_react_agent 快速理解 ReAct 循环，再在第 10 章讨论何时该转向更底层的 StateGraph 自建。

1.5如何使用本站

本站内容按由浅入深的顺序组织，建议按编号顺序阅读。每一章都基于本代码库的真实 API，配可运行示例，并着重讲「为什么这样设计」——帮你既能自建 Agent，也能在选型时判断框架是否契合你的场景。

学习路径 推荐顺序：01 核心概念 → 02 第一个图 → 03 状态与 Reducer → 04 控制流 → 05 ReAct Agent → 06 人机协同 HITL → 09 持久化记忆 → 07 多智能体 → 08 经典模式 → 11 流式输出 → 12 实战案例 → 10 选型指南。

前三章建立「图—状态—节点」的心智模型；第 4、5 章把控制流和 Agent 循环接上；第 6、9 章补齐生产必需的暂停与记忆；第 7、8 章进入多智能体编排；第 12 章用一个把既有 AutoML 流水线重构为图的真实案例把前九章概念总装一遍；最后第 10 章用一张决策表帮你把所学映射到自建 vs 选型的实际抉择，末节再补一类生态新选项（System One 分类模型）。

章序是有讲究的：这个顺序刻意把「持久化（09）」放在「人机协同（06）」之后、「多智能体（07）」之前，是因为 HITL 的 interrupt() 依赖 Checkpointer 才能跨进程恢复——先理解暂停的语义，再理解它怎么被持久化落地，最后才能在多智能体里正确地编排可中断的子图。如果你已有基础，可以直接跳到 10 章看决策表，再回查需要的章节。

全书词表

各章反复出现的术语收拢在这里，按学习路径顺序排列。「详见」指向讲得最透的章节；读正文遇到陌生词，先回来查这一张表。

术语含义详见
StateGraph图的构建器（builder）：往里 add_node、add_edge 定义结构，本身不能跑，要 compile 之后才产出 CompiledStateGraph（实现了 Runnable 接口的可运行图）。01 §1.8
add_node向图注册一个计算节点：读当前状态、返回一份状态更新。02 §2.2
add_edge / 条件边（conditional edge）普通边（add_edge）连出固定顺序；条件边（add_conditional_edges）挂一个路由函数，看当前状态决定下一站。04 §4.3
START / END两个保留地址（实际值 __start__ / __end__），分别指代图的入口与出口，只能用在 add_edge 里。02 §2.3
State / Node / Edge图的三大件：State 是节点间流转的共享数据（通常用 TypedDict 定义）；Node 是「读状态、返回更新」的计算单元；Edge 是决定下一站的控制流。01 §1.2
reducer（归约器）挂在 State 字段上的合并规则，决定节点返回的更新怎么并进当前值——追加、覆盖还是归约；写法就是 Annotated[type, reducer]。03 §3.3
add_messages官方提供的消息归约器：按 ID 合并、追加而非覆盖，聊天历史必备。03 §3.4
Channel（通道）State 每个字段在编译后对应的「存储盒子」，reducer 真正落脚执行的载体；默认不写注解就是 LastValue。01 §1.7
LastValue / BinaryOperatorAggregate两种内置通道：前者只留最后一个值、并发写入直接报错；后者把多个写入逐个喂给 reducer 合并。03 §3.7
super-stepPregel 执行引擎的一轮：同一轮内调度的节点并行执行，一轮结束时统一合并写入、存一次 checkpoint。01 §1.7
invoke / stream()编译后图的两种调用方式：invoke 跑完整张图拿最终状态；stream 边跑边吐中间结果。11 §11.2
条件边（conditional edge）「看状态再决定」的边：路由函数根据当前状态返回下一站名字，是 ReAct 循环和多 agent 路由的核心。04 §4.3
Send向节点投递一份独立输入的消息原语：一处返回多个 Send 即 fan-out 并行，典型 map-reduce 场景。04 §4.5
Command节点返回的控制指令：goto=... 在节点内部改道，update=... 同时更新状态，resume=... 用于恢复执行。04 §4.6
interrupt()在节点内部暂停图、把控制权交还给人的 API；恢复后在同一位置再次执行，返回人的答案。近期源码新增可选 response_schema 参数，把恢复值的 JSON Schema 随暂停事件带给客户端。06 §6.3
HITL（人机协同）Human-in-the-Loop：在不可逆副作用发生前插入同步等待点，图暂停、人确认后用 Command(resume=...) 带着人的输入继续。06 §6.1
checkpoint / Checkpointer每个 super-step 后自动保存的完整状态快照，以及负责存它的组件；按 thread_id 分桶，是暂停恢复与回放的物理基础。09 §9.2
thread_id会话隔离的钥匙：同一个 thread 内状态接续（短期记忆），换一个就是全新会话；恢复执行也靠它定位快照。09 §9.6
Store跨会话的长期记忆：全局命名空间键值库，按 (namespace, key) 读写，任何 thread 都能访问同一份数据。09 §9.3
子图（subgraph）把一张编译好的图当作另一个图的节点——多智能体分层和工程模块化的同一块基石。07 §7.3
Supervisor / Swarm两种多智能体拓扑：前者中央调度、所有协调过一个点；后者 agent 之间直接交接控制权。07 §7.2
create_react_agent预置「LLM 节点 ↔ 工具节点」循环的 Agent 工厂；1.x 已标记弃用，迁移目标是 langchain 的 create_agent，但仍是理解 ReAct 的最佳入口。05 §5.2
ToolNode / tools_condition手写 ReAct 的一对搭档：前者接管全部工具执行，后者判断最后一条消息有没有 tool_calls 来决定去留。05 §5.6
System One 模型不生成文本、只对给定 state 返回带类型答案和概率的专用分类模型（代表：TypeSafe AI 的 Jev）。一次请求多问并行评估，适合接管 agent 循环里的快判断；开放推理和生成仍交给 LLM。10 §10.9
stream_modestream() 的切面选择器：values / updates / messages / custom / debug 等七种，分别对应状态快照、增量、逐 token、自定义推送等输出。11 §11.2
ReAct 循环「想一步、做一步」的 Agent 骨架：LLM 决定是否调工具，调完回 LLM 继续，直到不再需要工具。05 §5.1
