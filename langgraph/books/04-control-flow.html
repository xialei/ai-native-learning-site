控制流：边、条件路由、并行与跳转

流程写进函数体就「焊死」了——不可视化、不可持久化、不可重放。LangGraph 用「边」回答「下一步去哪」：普通边、条件边、Send fan-out、Command 跳转四种原语各管哪种动态，语义边界各在哪。

4.1为什么用「边」而不是用代码 if/else？

传统的 agent 写法是把流程写进一个函数：if 用户问 X 就调工具 A,else 就调工具 B。问题在于——流程被「焊死」在代码里，不可视化、不可持久化、不可重放。LangGraph 把「下一步去哪」从函数体内抽离出来，变成图上的边。这样有三个好处：

  • 可视化：边是显式的数据，能直接画出来，你能一眼看清 agent 的决策结构。
  • 可持久化：每一步的转移都被 checkpointer 记录，中断后能从任意节点恢复，而不需要把「当前执行到哪行代码」塞进状态。
  • 可组合：同一个节点可以被不同的图复用，因为它的「去向」由外层图决定，而不是写死在自己体内。

但「用边表达控制流」立刻引出一串新问题。最简单的顺序怎么连？多个起点同时指向一个节点时，框架在等什么（4.2）——然后是「看状态再决定去哪」怎么表达，判断函数返回的东西和图结构怎么对上（4.3–4.4）。想同时派发 N 个独立子任务，或者想在节点内部临时改道，这两种「动态」分别用哪个原语（4.5–4.7）；原语用错了会怎样，循环失控、路由出口悬空，框架怎么兜底（4.10）。

往下读时会反复碰到同一个追问：每个原语的语义边界在哪——哪些事它管，哪些事它不管。先看最普通的边。

4.2普通边 add_edge:确定的顺序，以及隐式的 join

最朴素的边。签名是 add_edge(start_key: str | list[str], end_key: str)。单起点时，起点跑完就跑终点；多起点（传 list）时，图会等待所有起点都完成再跑终点——这是隐式的 join 语义，常用于汇聚并行分支。

「等待」具体是怎么实现的？值得进源码看一眼。编译时，多起点边会被存进 waiting_edges（state.py:979），随后逐条交给编译产物 attach_edge（state.py:1395）。attach_edge 对多起点做了一件单起点不做的事：创建一个名为 join:a+b:c 的屏障通道（state.py:1551），起点 a、b 各自往屏障里写自己的名字，终点 c 订阅这个屏障。屏障的类型是 NamedBarrierValue（named_barrier_value.py:13），它的触发条件只有一条：见过的名字集合等于全部名字集合时才放行（named_barrier_value.py:74 的 is_available）。所以 join 不是「轮询查状态」，而是每个起点完成时往屏障里「签到」，全签到齐了，终点节点才被触发。

这条链路有一个容易忽视的推论：屏障默认不设超时、不设兜底。如果某个起点节点在你的图里根本不可能被触发（比如它只被一条条件边指向、而条件永远不成立），终点不会报错也不会永远卡住——执行会自然结束，只是终点被永远跳过。想让「终点必须等人齐」变成强约束，需要自己在结构上保证每个起点都可达。

图 4.1：多起点 join 的屏障语义。add_edge(["a","b"], "c") 编译成 join:a+b:c 屏障通道，a、b 完成时各签到一次，签到齐才触发 c。

注意两个硬约束：END 不能作起点（没有「从终点出发」），START 不能作终点（不能「回到入口」）。在非 StateGraph 的图里，一个节点只能有一条出边；StateGraph 配合 reducer 后可以有多条。

确定顺序的线性图
pythonfrom typing import Annotated
import operator
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    messages: Annotated[list[str], operator.add]

def greet(state: State):
    return {"messages": ["你好"]}

def ask(state: State):
    return {"messages": ["请问需要什么帮助？"]}

builder = StateGraph(State)
builder.add_node("greet", greet)
builder.add_node("ask", ask)
# 确定的顺序：START -> greet -> ask -> END
builder.add_edge(START, "greet")
builder.add_edge("greet", "ask")
builder.add_edge("ask", END)

graph = builder.compile()
print(graph.invoke({"messages": []}))
# {'messages': ['你好', '请问需要什么帮助？']}

4.3条件边 add_conditional_edges:看状态再决定

条件边是 agent 路由的核心。它的真实签名是：

langgraph/graph/state.py — add_conditional_edges 签名
pythondef add_conditional_edges(
    self,
    source: str,
    path: Callable[..., Hashable | Sequence[Hashable]] | Runnable,
    path_map: dict[Hashable, str] | list[str] | None = None,
) -> Self

source 是「从哪个节点出发时执行判断」；path 是一个函数，接收 state、返回「下一跳的标识」；path_map 是可选的映射表。这里有个关键设计：path 返回的不是节点名，而是一个「标识」，再由 path_map 把标识翻译成真正的节点名。分离这两层有两个好处：

  • 解耦决策与拓扑：path 函数只关心「用户意图是哪种」（返回 "search" / "chat"），不必知道图里对应的节点叫什么名字，方便重命名节点。
  • 可视化：path_map 明确列出了所有可能的目的地，LangGraph 能据此画出完整的分支图。源码里有一句警告——没有类型注解也没有 path_map 时，可视化会假设这条边可能去往图里任意节点，图就糊成一团了。

所以官方推荐二选一：要么给 path 函数加 -> Literal["node_a", "node_b", "__end__"] 类型注解，要么提供 path_map。两者本质都是告诉框架「这条边可能的出口有哪些」。

路由示例：根据 state["choice"] 分流
pythonfrom typing_extensions import TypedDict
from typing import Literal
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    choice: str        # 用户意图
    answer: str

def classify(state: State):
    # 这里通常是接 LLM 做意图识别
    return state["choice"]

def search_tool(state: State):
    return {"answer": f"已检索到关于 {state['choice']} 的资料"}

def chat(state: State):
    return {"answer": "我来和你聊聊这个问题"}

builder = StateGraph(State)
builder.add_node("search_tool", search_tool)
builder.add_node("chat", chat)

# 用 Literal 注解声明所有可能出口——框架据此画分支图
def route(state: State) -> Literal["search_tool", "chat", "__end__"]:
    if state["choice"] == "search":
        return "search_tool"
    elif state["choice"] == "end":
        return "__end__"
    return "chat"

builder.add_conditional_edges(START, route)
# 各分支最终汇到 END
builder.add_edge("search_tool", END)
builder.add_edge("chat", END)

graph = builder.compile()
print(graph.invoke({"choice": "search"}))
# {'choice': 'search', 'answer': '已检索到关于 search 的资料'}
关于 path_map 的等价写法： 上面用 Literal 注解让 path 直接返回节点名。如果你想用语义标识而非节点名，可以改成 path_map={"search": "search_tool", "talk": "chat", "done": END}，这时 path 返回 "search" 等标识。两种写法等价，选可读性更好的那种。
图 4.2：条件分支图。用 add_conditional_edges，适合意图识别后分流。

4.4循环：边可以指回之前的节点

边的 end_key 可以指向「已经执行过」的节点，这就构成了循环。这是 LangGraph 表达 ReAct（推理-行动）循环的基础——agent 节点调用 LLM 决定是否用工具，工具节点执行后再回到 agent，如此往复直到 LLM 不再请求工具。

循环不会无限跑下去：当 agent 节点判断「任务完成」时，通过条件边返回 "__end__" 跳出循环；也可以设置 recursion_limit 兜底防止失控。

图 4.3：ReAct 循环。agent ↔ tools 形成环，__end__ 跳出。
经典 ReAct 循环骨架
pythonfrom typing import Annotated, Literal
import operator
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[list, add_messages]

def agent(state: State):
    # 简化：假设 LLM 返回 tool_calls 时需要调工具，否则结束
    last = state["messages"][-1]
    return {"messages": [last]}  # 实际接 LLM

def tools(state: State):
    return {"messages": [{"role": "tool", "content": "工具结果"}]}

def should_continue(state: State) -> Literal["tools", "__end__"]:
    last = state["messages"][-1]
    # 若最后一条消息带 tool_calls，继续调工具；否则结束
    if getattr(last, "tool_calls", None):
        return "tools"
    return "__end__"

builder = StateGraph(State)
builder.add_node("agent", agent)
builder.add_node("tools", tools)
builder.add_edge(START, "agent")
# 经典 ReAct 循环：agent -> (条件) -> tools -> agent
builder.add_conditional_edges("agent", should_continue)
builder.add_edge("tools", "agent")  # 指回 agent，形成环

graph = builder.compile()
为什么循环要靠「条件边 + 回边」而不是 while 循环 把循环写成图上的环，循环的每一步都被 checkpointer 持久化。一旦 LLM 调用超时或需要人工介入，你能从任意一步恢复，而不是从头跑。这是「图即控制流」相对「函数即控制流」的根本优势。

4.5Send 并行 fan-out：map-reduce 式并行

条件边的 path 函数除了返回节点名，还可以返回 Send 对象的列表。Send 的语义是「向某个节点投递一份独立的输入」。当 path 返回多个 Send 且目标相同，这些任务会在同一个 super-step 里并行执行，再用 reducer 汇总结果。

这是实现 map-reduce 的标准姿势：map 阶段对每个元素发一个 Send，reducer（如 operator.add）把所有结果累加。

map-reduce:多文档并行摘要
pythonfrom typing import Annotated
import operator
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send

class State(TypedDict):
    docs: list[str]                          # 待处理文档
    summaries: Annotated[list[str], operator.add]  # 汇总槽，用 add 累加

def summarize_one(state):
    # 每次只处理一个文档——这里的 state 是 Send 投递的 arg，不是全局 State
    doc = state["doc"]
    return {"summaries": [f"摘要： {doc[:10]}..."]}

def fan_out(state: State) -> list[Send]:
    # 对每个文档发一个 Send，目标都是 summarize_one，它们会并行跑
    return [Send("summarize_one", {"doc": d}) for d in state["docs"]]

builder = StateGraph(State)
builder.add_node("summarize_one", summarize_one)
builder.add_conditional_edges(START, fan_out)   # fan-out
builder.add_edge("summarize_one", END)          # 汇聚到 END

graph = builder.compile()
result = graph.invoke({"docs": ["文档一内容...", "文档二内容...", "文档三内容..."]})
print(result["summaries"])
# ['摘要： 文档一内容......', '摘要： 文档二内容......', '摘要： 文档三内容......']
#  （文档名自带 "..."，截取后再拼一次，所以是 6 个点——输出以实际运行结果为准）
Send 灵活在哪： Send 定义在 types.py:732，签名是 Send(node, arg, *, timeout=None)——node 和 arg 是位置参数，timeout 是关键字参数。arg 是投递给目标节点的输入——它不必是全局 State 的形状，这是 Send 最灵活的地方：你可以给同一个节点喂完全不同的数据结构。返回 operator.add 的 reducer 会把每个 Send 产出的 {"summaries": [...]} 列表拼接起来。

动态演示——点 ▶ 或 ⏭ 步进，看 3 个 Send 如何在同一 super-step 并发、再由 reducer 归并（并行性是静态图的天敌，动画才看得清）：

并行边界 同一批 Send 在同一个 super-step 里并发调度，而不是跨 step。这意味着它们的写入会在该 step 结束时一起走 reducer 汇总，然后才进入下一 step。理解这一点对避免写冲突很重要。

4.6Command 跳转：在节点内部改道并更新状态

Command 是另一种控制流原语，但它的位置不同——它不是在「边」上声明，而是由节点 return 出来。一个节点返回 Command(goto="node", update={...}) 时，它同时做了两件事：把 update 写进状态，并指定下一跳节点。这适合「无显式边」的图——节点自己决定去哪。

节点 return Command 控制流程
pythonfrom typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command

class State(TypedDict):
    foo: str
    bar: str

def node_a(state: State):
    # 既更新状态(foo='bar')，又指定下一跳为 node_b
    return Command(goto="b", update={"foo": "bar"})

def node_b(state: State):
    # 跳到 END，同时写入 bar
    return Command(goto=END, update={"bar": "baz"})

builder = StateGraph(State)
builder.add_node("a", node_a)
builder.add_node("b", node_b)
builder.add_edge(START, "a")  # 只有入口边，节点间的转移全靠 Command
graph = builder.compile()

print(graph.invoke({"foo": ""}))
# {'foo': 'bar', 'bar': 'baz'}
Command 的能力不止 goto+update: Command 类定义在 types.py:827，goto 字段（types.py:852）的类型是 Send | Sequence[Send | N] | N——可以是单个节点名、节点名列表、一个 Send、或 Send 列表（即 Command 也能触发并行）；resume 字段配合 interrupt() 实现人机协同恢复（详见第 06 章）；graph=Command.PARENT 能从子图向父图发指令（详见第 07 章多智能体）。这些都建立在「节点 return Command」这个统一入口上。

4.7Send vs Command:到底用哪个？

这是初学者最容易混淆的点。两者都能「指定下一跳」，但语义模型完全不同：

本质区别

Send 是「向节点投递一份独立输入」——它是消息，强调并行 fan-out。你在一个地方返回多个 Send，它们各自带着自己的 arg 并行去往目标节点，典型的 map-reduce 场景。Send 通常在条件边的 path 函数里返回。

Command 是「从当前节点控制下一步去哪」——它是指令，强调就地改道。节点 return 一个 Command，既更新状态又指定去向，适合节点内部根据自身逻辑动态决定流程，而不必预先在图上画边。

概括：Send 是「我要派发 N 个并行子任务」，Command 是「我这条节点跑完，下一步去这儿，顺便把状态改成这样」。

图 4.4：Send 与 Command 对照。左边是「边上的动态」——条件边按状态派发多份消息；右边是「节点内的动态」——节点返回一条指令，改道与写状态同时完成。

4.8add_sequence:批量加顺序边

当一连串节点就是纯线性执行时，逐条 add_edge 有点啰嗦。add_sequence 接收一个节点列表，自动把它们依次连起来，等价于对相邻节点逐个 add_edge。节点可以是裸函数（名字从函数名推断），也可以是 (name, func) 元组显式命名。

批量顺序边
pythonfrom typing import Annotated
import operator
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START

class State(TypedDict):
    foo: Annotated[list[str], operator.add]
    bar: str

def step1(state: State):
    return {"foo": ["step1"], "bar": "baz"}

def step2(state: State):
    return {"foo": ["step2"]}

builder = StateGraph(State)
# 一次性加好 step1 -> step2 的顺序边
builder.add_sequence([step1, step2])
builder.add_edge(START, "step1")  # 仍需手动接 START

graph = builder.compile()
print(graph.invoke({"foo": []}))
# {'foo': ['step1', 'step2'], 'bar': 'baz'}
注意： add_sequence 只负责节点之间的串联，入口 START 仍需单独接。它还有两个校验：序列不能为空；节点名不能重复（否则报错，提示用元组显式命名）。

4.9选型小结：该用哪个？

需求原语关键特征
固定顺序，无分支add_edge / add_sequence编译期确定，最简单
按状态选下一节点add_conditional_edgespath 函数 + path_map/Literal，可可视化
循环（ReAct）条件边 + 回边边指回前序节点，__end__ 跳出
对 N 个输入并行处理Send返回 Send 列表，reducer 汇总
节点内动态改道 + 改状态Command节点 return,goto+update 合一

实际工程里这几者经常组合：一个 agent 图往往是「条件边做路由 + 回边做循环」，遇到批量任务时用 Send fan-out，遇到需要节点内部灵活跳转（比如多步规划）时用 Command。理解每种原语的语义边界，才能在自建 agent 时画出既清晰又够用的图。

4.10新手常犯的错误

控制流这一章最容易踩的两个坑，都和「路径没闭合」有关：一个是循环跑不出去，一个是条件边返回了一个没被声明的出口。

循环永远到不了 END，撞上 recursion_limit

4.4 讲过循环靠「条件边返回 __end__ 跳出」。但如果你的退出条件写错了（比如 LLM 一直返回 tool_calls、或判断逻辑恒真），循环就永远停不下来。LangGraph 不会任由它跑死：每个图都有一个 recursion_limit（源码默认值在 _internal/_config.py:32 的 DEFAULT_RECURSION_LIMIT = 10007，可用环境变量 LANGGRAPH_DEFAULT_RECURSION_LIMIT 覆盖），超了就抛 GraphRecursionError。这是循环的「保险丝」——默认值给得很宽裕，正常 Agent 不会撞到，但一旦写出真正的逻辑死循环，跑满 10007 个 super-step 后仍会撞限报错暴露问题。

最小复现：条件边永远返回 "loop"，撞 recursion_limit 报错
pythonfrom typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.errors import GraphRecursionError


class State(TypedDict):
    n: int


def loop(state: State) -> dict:
    return {"n": state["n"] + 1}


# 故意写错：永远回 "loop"，永远不返回 END → 死循环
def should_stop(state: State) -> str:
    return "loop"


builder = StateGraph(State)
builder.add_node("loop", loop)
builder.add_edge(START, "loop")
builder.add_conditional_edges("loop", should_stop)
builder.add_edge("loop", END)  # 这条边永远走不到
graph = builder.compile()

graph.invoke({"n": 0}, {"recursion_limit": 5})
# GraphRecursionError: Recursion limit of 5 reached ...
#                limit by setting the `recursion_limit` config key.
保险丝的用法： 这里把 recursion_limit 调到 5 方便复现，框架实际默认值是 10007（_internal/_config.py： DEFAULT_RECURSION_LIMIT = 10007）。报错信息直接告诉你解法：在 config 里设 {"recursion_limit": N}。注意 recursion_limit 是「每张图最多执行多少个 super-step」，默认值给得很宽裕，正常带工具循环的 Agent 远用不到——所以生产里更常见的做法是按需调小（{"recursion_limit": N}），给 Agent 套一道更紧的保险。但调参只是兜底——真正的修法是让退出条件确实能成立（比如 LLM 不再带 tool_calls 时返回 END）。

条件边返回了 Literal/path_map 里没有的出口

4.3 强调过：要么给 path 函数加 -> Literal[...] 注解，要么提供 path_map。但常见错误是：注解里漏写一个实际会返回的出口（比如忘了 "__end__"），或 path 返回的标识在 path_map 里查不到。这时框架在运行时把返回值当节点名去查映射表，查不到就抛一个裸的 KeyError（graph/_branch.py:203）——注意它不是 GraphRecursionError 之类的语义化异常，就是字典查询失败，第一次撞上很容易误以为是别处出了问题。且因为可视化依据的就是 Literal/path_map，你在结构图上根本看不出这条隐藏出口。

反面：Literal 漏写了 "__end__"，却可能返回它
python# ✗ 注解只声明了 "tools"，但函数可能返回 "__end__"
def should_continue(state) -> Literal["tools"]:
    if not getattr(state["messages"][-1], "tool_calls", None):
        return "__end__"   # 不在声明的 Literal 里 → 图结构对不上
    return "tools"

# ✓ 把所有可能出口都写进 Literal
def should_continue(state) -> Literal["tools", "__end__"]:
    if not getattr(state["messages"][-1], "tool_calls", None):
        return "__end__"
    return "tools"
声明与返回要对账： 把 "__end__" 补进 Literal 后，框架才能正确画出这条到 END 的边、并在运行时识别它。用 path_map 时同理——path 能返回的每个标识都必须在 map 里有对应节点。养成习惯：path 能返回几个值，Literal/path_map 就列几个，二者必须一一对应。
共同根源 这两个坑的共同根源都是路径没闭合：第一个是循环没有真正的出口（只有回边、没有跳出边），第二个是条件边声明了不全的出口集合。画图时问自己一句「从每个节点出发，所有可能的下一跳我都画出来了吗」，能挡掉绝大多数控制流 bug。

4.11读完本章，你应该能回答

先自己作答，再展开对照。

Q1 · add_edge(["a", "b"], "c") 的 join 靠屏障通道实现。如果 b 节点在你的图里根本没有被任何边触发过，invoke 会发生什么——报错、永远卡住，还是别的？这暴露了屏障语义的什么特性？
会安静地结束：a 跑完后往屏障 join:a+b:c 签到 "a"，但 b 永远不来签到，屏障不满足 seen == names（named_barrier_value.py:74），c 不被触发——而图里也没有别的可执行节点了，于是执行正常返回，结果里没有 c 的产出。不报错、不卡死、不提示，正是屏障「默认不设兜底」的体现：放行条件只有「签到齐」，没有「签到超时」，也没有「起点必须可达」的编译期检查。所以 join 的完整性要靠图结构保证，不能指望框架替你发现「有人的 c 永远等不到」。
Q2 · 一个 LastValue 字段（无 reducer），三个 Send 在同一个 super-step 里并行写它，会看到什么错误？把同一个实验换到条件边返回三个普通节点名（不是 Send），错误还会发生吗？为什么？
会抛 InvalidUpdateError: Can receive only one value per step——三个 Send 的目标节点在同一个 super-step 并行执行，三个写入在 step 结束时一起撞进 LastValue，违反「一步一值」。换成条件边返回三个普通节点名后错误不会发生，因为普通条件边的多个出口是或的关系：path 只决定下一批去哪些节点，返回值列表里每个节点都在下一个 super-step 执行，彼此的写入同样同 step 合并——但注意，若 path 真的返回了多个节点名，它们也是并行、也会撞 LastValue。「三个不冲突」的真正原因是多数条件边只返回一个出口；返回多个出口时，约束和 Send 场景完全一致：要么配 reducer，要么保证不写同一字段。Send 和普通路由在这个语义上没有区别。
Q3 · 一个「agent → tools → agent」的循环，从进 agent 到跑完，最多会消耗多少个 recursion_limit 配额？如果 config 里给了 20，agent 节点实际最多能执行几轮？
每轮 agent→tools 消耗 2 个 super-step：agent 一个、tools 一个，所以限额 20 最多支持 10 轮完整循环（最后一轮 agent 若决定结束，还需要它自己那 1 步，包含在内）。recursion_limit 数的是 super-step 而不是「agent 被调用的次数」——把带工具循环的 Agent 配额想成「循环次数」会差一倍。这也是为什么默认值 10007（_internal/_config.py:32）看起来夸张：它是按 super-step 计的，再宽裕也仍然是一道硬保险丝。
Q4 · Command 的 goto 能接受一个 Send 列表，Send 通常也从条件边返回——那 Command 是不是就能完全替代 Send + 条件边？说出一个条件边仍有独立价值的场景。
功能上确实高度重叠：goto 的类型签名（types.py:852）本身就允许 Sequence[Send]，节点内完全可以 return Command(goto=[Send(...), Send(...)])。但条件边有两个不可替代的价值：一是可视化——add_conditional_edges 在编译期就把「可能出口」登记进图结构，get_graph/draw_mermaid 画得出来，Command 的 goto 在节点函数体内，结构图上看不到；二是多节点复用——同一节点的路由逻辑写在边上是外层图的属性，节点本身保持纯计算，换一个图复用时不必连带搬走路由代码。Command 适合「路由逻辑属于这个节点自身」的场景，条件边适合「路由属于图的结构」的场景。
Q5 · 条件边 path 函数返回了一个 Literal 和 path_map 里都没声明的字符串，运行时报什么？为什么说这个错误的「凶手」和报错信息对不上号？
报一个裸的 KeyError，内容是那个未声明的字符串本身（graph/_branch.py:203）。对不上号的原因：框架把你的返回值直接当作 key 去查 ends 映射表，映射表里没有这个 key，抛出的是 Python 字典查询的原生异常——它不像 GraphRecursionError 那样告诉你是循环问题，也不指明「是条件边的出口没声明」。错误源头（声明不全的 Literal/path_map）和异常形态（KeyError）之间隔着两层：path 函数返回 → ends 查表失败。排查思路就是反着来：看到 KeyError 且值像一个节点名，先检查所有条件边的 Literal/path_map 是否覆盖了 path 的全部返回值。
