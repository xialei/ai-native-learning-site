ReAct Agent:让 LLM 学会「想一步、做一步」

ReAct = Reasoning + Acting。LLM 先思考要做什么，再调用工具，观察结果后继续思考——这个循环就是几乎所有现代 Agent 的骨架。本页基于 LangGraph 源码，带你用两种方式搭出同一个 ReAct Agent。

5.1ReAct 循环到底是什么

传统 LLM 调用是「一问一答」：用户输入 → LLM 输出文本 → 结束。问题在于，LLM 不能真正去查数据库、调 API、做计算，它只能「说」不能「做」。

ReAct 的核心思想很简单——给 LLM 一个「工具箱」，让它可以：

  • 思考（Reasoning）：读到用户问题和历史消息后，LLM 决定下一步该干什么。如果需要外部信息，它会在回复里带上 tool_calls——一个结构化的「我要调用某个工具，参数是这些」的指令。
  • 行动（Acting）：运行时（在我们的语境里就是 LangGraph 图）解析 tool_calls，真正去执行对应工具，把结果包装成 ToolMessage 放回消息列表。
  • 观察（Observation）：LLM 再次被调用，这次它能看到工具返回的结果。基于结果它要么继续调工具，要么给出最终答案。

这个「思考 → 行动 → 观察 → 再思考」的循环会一直转，直到 LLM 的回复里不再包含 tool_calls，说明它觉得信息够了，可以直接回答用户了——循环结束，返回最终状态。

图 5.1：ReAct 循环——用户输入进入 Agent 节点，LLM 思考后若带 tool_calls 则进 Tools 执行，结果回传后继续思考；直到不再调工具，返回最终回复
读懂这段：为什么要把循环做成「图」而不是一个简单的 while True？因为图天然支持：持久化（每个节点切换都是一次 checkpoint 时机）、人机协同（可以在工具执行前 interrupt）、并行（v2 版本每个 tool_call 用 Send 并行分发）、可观测（每个节点独立追踪）。这些是用裸 while 循环很难做好的事情。

5.2方式一：用 create_react_agent 快速起手

如果你只需要一个标准的「带工具的聊天 Agent」，create_react_agent 三行就能跑起来。它内部已经帮你搭好了 agent 节点、tools 节点、条件边，还处理了各种边界情况（工具不存在、参数校验失败、步数耗尽等）。

下面这个例子直接来自源码 docstring 里的示例——一个查询天气的 Agent:

最简 ReAct Agent —— create_react_agent 一行封装好 agent/tools 节点 + 条件边
pythonfrom langgraph.prebuilt import create_react_agent


def check_weather(location: str) -> str:
    """返回指定地点的天气预报。"""
    # 真实场景里这里会调天气 API
    return f"It's always sunny in {location}"


# 一行创建 ReAct Agent:
#   model  ： 用字符串语法 "provider:model" 初始化聊天模型
#   tools  ： 传一个函数列表，会自动转成 BaseTool
#   prompt ： 字符串会变成 SystemMessage 拼到消息最前面
graph = create_react_agent(
    "openai:gpt-4o",
    tools=[check_weather],
    prompt="You are a helpful assistant",
)

# stream 调用，stream_mode="updates" 每个节点完成时输出增量
inputs = {"messages": [{"role": "user", "content": "what is the weather in sf"}]}
for chunk in graph.stream(inputs, stream_mode="updates"):
    print(chunk)
读懂这段：model 用字符串 "openai:gpt-4o" 时，框架内部会调 init_chat_model 初始化；普通函数 check_weather 会被自动转成 BaseTool（靠 docstring 给 LLM 看工具说明）；prompt 字符串会被包装成 SystemMessage 拼到消息列表最前面。三行代码背后其实是一张完整的 StateGraph——下一节拆参数时会看清它的全貌。

运行后你会看到类似这样的输出——注意 agent 节点先产出带 tool_calls 的 AIMessage，然后 tools 节点执行后产出 ToolMessage，最后 agent 节点再产出最终回复：

stream 输出 —— 三个 chunk 分别对应 agent → tools → agent 三步
text{'agent': {'messages': [AIMessage(content='', tool_calls=[{'name': 'check_weather', 'args': {'location': 'sf'}, 'id': 'xxx'}])]}}
{'tools': {'messages': [ToolMessage(content="It's always sunny in sf", ...)]}}
{'agent': {'messages': [AIMessage(content='The weather in San Francisco is sunny!')]}}
读懂这段：三个 chunk 完美对应了图 5.1 的循环：第一个 agent chunk 是 LLM 决定调工具（产出的 AIMessage 带 tool_calls）；tools chunk 是 ToolNode 执行后回填的 ToolMessage；第二个 agent chunk 是 LLM 看到工具结果后，判断信息够了，不再调工具，直接给出自然语言回答——循环到此结束。

5.3create_react_agent 参数详解

源码里 create_react_agent 的完整签名参数很多，但每个都有明确用途。理解这些参数，你就能判断「我需要的能力它支不支持」，而不是一遇到新需求就想着手写。下面这张表对照源码 docstring 整理：

参数类型用途
modelstr | BaseChatModel | Callable静态模型可用字符串（如 "openai:gpt-4o"）或模型实例；也可传 (state, runtime) -> BaseChatModel 的可调用对象实现动态选模型（比如根据上下文切换 GPT-4 / GPT-3.5）。若已用 bind_tools 绑定工具，绑定的工具必须是 tools 参数的子集。
toolsSequence | ToolNode工具列表（普通函数会自动转 BaseTool），或直接传一个 ToolNode 实例。传空列表则 Agent 退化为纯 LLM 节点，不调工具。
promptstr | SystemMessage | Callable | Runnable系统提示。str 转 SystemMessage 拼到消息开头；传 Callable 则接收完整 state，可动态生成提示词（比如根据时间、用户身份）。
response_formatschema | (prompt, schema) | None结构化输出。传 Pydantic 模型 / TypedDict / JSON Schema,Agent 循环结束后会额外调一次 LLM（用 with_structured_output）生成符合 schema 的结果，放在 state["structured_response"]。需要模型支持 .with_structured_output。
pre_model_hookRunnableLike | None在 agent 节点（调 LLM）之前插入的节点。常用于裁剪/摘要长消息历史，避免上下文超长。必须返回 messages 或 llm_input_messages 之一。
post_model_hookRunnableLike | None在 agent 节点之后插入的节点。常用于护栏 / 输出校验 / 人机协同。仅在 version="v2" 下可用。它还能接管路由：决定去 tools、去结构化输出还是结束。
state_schematype | None自定义 state schema，必须含 messages 和 remaining_steps（若用 response_format 还要含 structured_response）。默认用内置 AgentState。
checkpointerCheckpointer | None检查点 saver，持久化单线程（单次对话）的状态，实现「聊天记忆」。跨步恢复也靠它。
storeBaseStore | None跨线程（多对话/多用户）的持久存储。配合 InjectedStore 注入到工具里。
interrupt_beforelist[str] | None在指定节点执行前暂停，可选 "agent" 或 "tools"。比如在 "tools" 前暂停，让人确认后再执行——这就是人机协同的基础。
version"v1" | "v2"默认 "v2"。v1:工具节点处理整条消息，所有 tool_call 在节点内并行；v2:每个 tool_call 用 Send 独立分发，天然支持并行且对人机协同更友好。
读懂这段：源码里有个细节值得注意：remaining_steps 这个隐藏 state 键。它大致等于 recursion_limit - total_steps_taken。当它小于 2 且 LLM 还想调工具时，Agent 不会抛 GraphRecursionError，而是返回一句 "Sorry, need more steps to process this request."——这是一种优雅的「兜底」，避免死循环把递归限制耗尽后直接报错。
迁移提示 本页所讲的 create_react_agent 在 LangGraph 1.x 中已被标记为 deprecated。源码中的原始文档字符串明确写道：它已迁移到 langchain.agents.create_agent，后者提供了等价的 Agent 工厂并带有更灵活的中间件（middleware）系统。但 create_react_agent 仍然是理解 ReAct 循环原理的最佳入口——它把 Agent 的内部结构完完整整地暴露给你看。本页先讲它，再带你从零手写同样的循环，这样无论将来 API 怎么迁移，你都能看懂、能改造。

5.4方式二：从零手写 ReAct（核心！）

create_react_agent 帮你封装了很多，但只有亲手搭一遍，你才真正理解 ReAct 的骨架。更重要的是，当你的需求超出标准模式——比如多步推理规划、自定义循环逻辑、工具间有依赖关系——你就得回到手写这条路上来。

手写版用到的全部是 LangGraph 最基础的积木：StateGraph、MessagesState、bind_tools、tools_condition、ToolNode。下面是完整可运行的代码：

手写 ReAct —— StateGraph + 两个节点 + 条件边 + 回边，与 create_react_agent 结构等价
pythonfrom langchain_core.tools import tool
from langchain.chat_models import init_chat_model
from langgraph.graph import StateGraph, MessagesState, END
from langgraph.prebuilt import ToolNode, tools_condition


# ---- 1. 定义工具：用 @tool 装饰器，docstring 会成为给 LLM 看的工具说明 ----
@tool
def search(query: str) -> str:
    """搜索网络并返回结果摘要。"""
    # 演示用，真实场景接搜索 API
    return f"关于「{query}」的搜索结果：LangGraph 是一个用于构建状态化多智能体应用的框架。"


@tool
def calculator(expression: str) -> str:
    """计算一个数学表达式的值。"""
    try:
        # 注意：生产环境不要用 eval，这里仅作演示
        return str(eval(expression))
    except Exception as e:
        return f"计算失败： {e}"


tools = [search, calculator]

# ---- 2. 初始化模型并绑定工具 ----
# bind_tools 会把工具的 schema 注入模型，让模型知道"可以调这些工具，参数长这样"
model = init_chat_model("openai:gpt-4o")
model_with_tools = model.bind_tools(tools)


# ---- 3. 定义 agent 节点：调用 LLM ----
def call_model(state: MessagesState):
    # 取出当前消息列表，调用绑定工具后的模型
    response = model_with_tools.invoke(state["messages"])
    # 返回会被 add_messages reducer 合并进 state["messages"]
    return {"messages": [response]}


# ---- 4. 构建 graph ----
workflow = StateGraph(MessagesState)

# 两个节点：agent(调 LLM) 和 tools(执行工具)
workflow.add_node("agent", call_model)
workflow.add_node("tools", ToolNode(tools))

# 入口 -> agent
workflow.set_entry_point("agent")

# 关键！条件边：agent 之后去哪？
#   tools_condition 检查最后一条消息(AIMessage)有没有 tool_calls
#   有 ->； 去 "tools"；没有 ->； 去 END
workflow.add_conditional_edges(
    "agent",
    tools_condition,  # 返回 "tools" 或 "__end__"
)

# tools 执行完，回到 agent 继续思考(这就构成了循环)
workflow.add_edge("tools", "agent")

# 编译
graph = workflow.compile()

# ---- 5. 运行 ----
for chunk in graph.stream(
    {"messages": [{"role": "user", "content": "LangGraph 是什么？它有多少个字母？"}]},
    stream_mode="updates",
):
    print(chunk)
读懂这段：这段代码和 create_react_agent 做的事在结构上是完全一样的：两个节点（agent、tools）+ 一条条件边 + 一条回边。区别只在于 create_react_agent 额外处理了 prompt、动态模型、结构化输出、hooks、步数兜底这些边角。手写版让你看清「骨架长什么样」，以后要加什么都是在这个骨架上改。注意 MessagesState 内置了 add_messages reducer，所以节点只需返回新消息列表，框架会自动把历史拼接好。
提示 手写时为什么推荐用 ToolNode 而不是自己写工具执行？ToolNode 不是简单的「调用函数」。源码显示它处理了：参数校验（ValidationError 转 ToolInvocationError 并过滤掉注入参数的错误）、状态注入（InjectedState）、存储注入（InjectedStore）、运行时注入（ToolRuntime）、错误处理策略、Command 返回值的归一化、并行执行等等。除非你的工具极简，否则用 ToolNode 几乎总是比手写更稳。

5.5tools_condition:条件路由的判断逻辑

手写版里那个 tools_condition 看起来像魔法，其实源码里它非常短——核心就几行：

tools_condition 源码核心 —— 兼容 list/dict/BaseModel 三种 state 形态，检查最后一条消息有无 tool_calls
pythondef tools_condition(state, messages_key="messages"):
    """标准 ReAct 条件路由：有 tool_calls 去 tools，否则结束。"""
    if isinstance(state, list):
        ai_message = state[-1]
    elif (isinstance(state, dict) and (messages := state.get(messages_key, []))) or (
        messages := getattr(state, messages_key, [])
    ):
        ai_message = messages[-1]
    else:
        raise ValueError(f"No messages found in input state to tool_edge: {state}")

    # 判断最后一条消息是不是带 tool_calls 的 AIMessage
    if hasattr(ai_message, "tool_calls") and len(ai_message.tool_calls) > 0:
        return "tools"
    return "__end__"
读懂这段：它做的事情就两步：① 找到最后一条消息（兼容 list、dict、BaseModel 三种 state 形态）；② 看这条消息有没有 tool_calls。有就去 "tools" 节点，没有就去 "__end__"。为什么单独抽出这么个函数？因为这个判断逻辑在每个 ReAct Agent 里都一样，反复手写既啰嗦又容易写错（比如忘了处理 state 是 list 的情况）。但它又足够简单，你完全可以替换成自己的版本——比如你想「只有第一个 tool_call 才去 tools，其余丢弃」，或者「根据工具名路由到不同的工具节点」，直接写个自定义函数传给 add_conditional_edges 即可。

5.6ToolNode 与 v2 并行分发

ToolNode 的输入是当前 state（它会从中取最后一条 AIMessage 的 tool_calls），输出是若干 ToolMessage——每个 tool_call 对应一个。源码里它的 _func 方法大致流程是：

  • _parse_input：从 dict/list/BaseModel 里解析出 tool_calls 列表，并记录输入类型。
  • 为每个 tool_call 构造 ToolRuntime（包含 state、config、store、context 等）。
  • 用线程池（v1）或 Send 并行分发（v2）执行每个工具，拿到 ToolMessage 或 Command。
  • _combine_tool_outputs：把所有输出合并成统一格式（dict 输入返回 {"messages": [...]}，list 输入返回 [...]）。

关于 v2 的并行分发：这是 version="v2" 的核心改进。源码里 should_continue 函数在 v2 模式下会这样返回：

v2 的 Send 并行分发 —— 每个 tool_call 独立投递，而非节点内线程池并行
python# v2 模式下，should_continue 返回的不是字符串 "tools",
# 而是一组 Send，每个 Send 对应一个 tool_call
return [
    Send("tools", ToolCallWithContext(
        __type="tool_call_with_context",
        tool_call=call,
        state=state,
    ))
    for call in last_message.tool_calls
]
读懂这段：也就是说，每个 tool_call 都会作为一次独立的 Send 触发 tools 节点的一个并行实例。这比 v1 在节点内部用线程池并行更优雅，因为：① 每个工具调用都是图里独立的一步，checkpoint、interrupt、追踪都能精细到单个 tool_call 粒度；② 人机协同时，可以只恢复某一个被 interrupt 的 tool_call，不影响其他已完成的；③ 和 LangGraph 的并行调度模型原生对齐，不再依赖节点内部的线程池。

5.7pre_model_hook:裁剪长上下文

最典型的用途是管理长对话历史。LLM 的上下文窗口有限，对话一长，token 成本飙升甚至超限。pre_model_hook 让你在每次调 LLM 前先把历史消息裁剪一下——但注意，它裁剪的是「喂给 LLM 的输入」，不一定要改 state 里的 messages（可以用 llm_input_messages 只改输入不改 state）。

源码 docstring 强调：如果要在 pre_model_hook 里改 messages，必须用 RemoveMessage(id=REMOVE_ALL_MESSAGES) 先清空再追加，否则会变成「追加」而不是「替换」。下面是个裁剪历史只保留最近 N 条的示例：

pre_model_hook 示例 —— 用 llm_input_messages 只改 LLM 输入，完整历史仍保留在 state 里
pythonfrom langchain_core.messages import RemoveMessage
from langgraph.graph.message import REMOVE_ALL_MESSAGES
from langgraph.prebuilt import create_react_agent


def trim_history(state):
    """pre_model_hook：只把最近 6 条消息喂给 LLM，避免上下文过长。

    返回 llm_input_messages 而不是 messages —— 这样 state["messages"]
    里的完整历史仍然保留(下次还能读到)，只是这次调 LLM 用的是裁剪版。
    """
    messages = state["messages"]
    # 保留最近 6 条作为 LLM 输入
    recent = messages[-6:]
    return {"llm_input_messages": recent}


graph = create_react_agent(
    "openai:gpt-4o",
    tools=[check_weather],  # 即 5.2 定义的那个查天气工具
    prompt="You are a helpful assistant",
    pre_model_hook=trim_history,
)
读懂这段：这里有个关键区分：messages 会更新 state 里的消息列表（配合 add_messages reducer），而 llm_input_messages 只是本次 LLM 调用的临时输入，不写进 state。上面的例子用后者，意味着完整历史始终保留在 state 里（持久化、后续可检索），只是喂给 LLM 的是裁剪版——这正是大多数场景想要的。如果你想彻底丢弃旧消息以省存储，才用前者配合 REMOVE_ALL_MESSAGES。

5.8post_model_hook:护栏与 HITL

post_model_hook 在 LLM 产出 AIMessage 之后、路由决策之前运行。源码显示它不仅能「看」LLM 输出，还能接管路由——post_model_hook_router 会判断有没有待执行的 tool_call，决定去 tools、去结构化输出还是结束。

典型用途：

  • 输出校验：检查 LLM 是否输出了不该输出的内容，不通过就强制重试或走人工。
  • 护栏（Guardrails）：用另一个小模型或规则检查回复是否安全/合规。
  • 人机协同：某些工具调用前需要人确认，可以在这里判断工具名，触发 interrupt。

源码 docstring 写得很清楚：post_model_hook 是个「接收当前 state、返回 state 更新」的可调用对象（和普通节点签名一样）。下面是个最简护栏示例——LLM 每次产出后，检查最后一条消息里有没有敏感词：

post_model_hook 示例 —— LLM 输出后做一道规则护栏，违规就改写回复
pythonfrom langgraph.prebuilt import create_react_agent


def safety_check(state):
    """post_model_hook:LLM 输出后做一道规则护栏。

    签名和普通节点一样：(state) ->； 部分更新。
    这里检测最后一条 AIMessage 是否含敏感词，违规就把它替换成提示。
    """
    last = state["messages"][-1]
    content = getattr(last, "content", "")
    if "机密" in str(content):
        # 改写这条消息：用同 ID 追加，add_messages 会原地替换
        from langchain_core.messages import AIMessage
        return {"messages": [AIMessage(content="(检测到敏感词，已拦截)", id=last.id)]}
    return {}  # 不违规就什么都不改


graph = create_react_agent(
    "openai:gpt-4o",
    tools=[check_weather],
    post_model_hook=safety_check,   # 仅 v2;LLM 每次输出后先过这道闸
)
读懂这段： 注意 post_model_hook 插在 agent 之后、should_continue 路由之前（见图 5.10）。它返回 {} 表示不改任何东西，放行到正常路由；返回 {"messages": [...]} 则改写消息。这里用同 id 追加，靠 add_messages 的「同 ID 替换」语义原地改掉违规内容——正是 3.4 讲的那个特性在护栏场景的应用。
注意 源码注释明确写着 post_model_hook "Only available with version='v2'"。因为 v2 的 Send 并行分发模型让「LLM 输出后、工具执行前」这个时机更清晰。如果你在 v1 模式下传 post_model_hook，行为会不符合预期。默认就是 v2，所以一般不用担心。

5.9response_format:让 Agent 吐结构化结果

有时候你不想让 Agent 自由发挥，而是要它按固定 schema 返回——比如一个「订单提取 Agent」必须返回 {订单号, 金额, 商品列表}。这就是 response_format 的用途。

response_format 示例 —— 传 Pydantic 模型，Agent 循环结束后额外调一次 LLM 生成结构化结果
pythonfrom pydantic import BaseModel, Field
from langgraph.prebuilt import create_react_agent


class WeatherReport(BaseModel):
    """结构化的天气报告。"""
    location: str = Field(description="地点")
    temperature: float = Field(description="温度(摄氏度)")
    summary: str = Field(description="一句话总结")


graph = create_react_agent(
    "openai:gpt-4o",
    tools=[check_weather],
    prompt="你是天气助手，用工具查完天气后给出结构化报告。",
    response_format=WeatherReport,  # 传 Pydantic 模型
)

result = graph.invoke(
    {"messages": [{"role": "user", "content": "sf 现在天气怎么样？"}]}
)

# 结构化结果在 state["structured_response"]，是一个 WeatherReport 实例
report = result["structured_response"]
print(report.location)      # "sf"
print(report.temperature)   # 比如 18.5
print(report.summary)       # "旧金山晴天，气温适宜。"
读懂这段：源码里 generate_structured_response 函数揭示了它的工作原理：Agent 循环（调工具）正常结束后，会额外调一次 LLM，这次用 model.with_structured_output(schema) 把整段对话历史喂进去，生成符合 schema 的对象，放进 structured_response。也可以传元组 (prompt, schema)，那个 prompt 会作为 system message 拼到结构化输出那次 LLM 调用前面，用来给「提取」行为下更精确的指令。注意：这要求模型支持 .with_structured_output——OpenAI、Anthropic 的主流模型都支持。

5.11何时用 create_react_agent vs 何时手写

用 create_react_agent（或迁移后的 create_agent）当
  • 需求标准：就是「LLM + 一组工具 + 循环到没 tool_calls」。
  • 想快速起跑，不想纠结图结构。
  • 需要 prompt、结构化输出、长上下文裁剪这些开箱即用的能力。
  • 团队协作，希望用社区维护的标准实现，减少自研负担。
手写 StateGraph + ToolNode 当
  • 需要定制控制流：比如工具之间有依赖（A 的结果喂给 B）、要多轮规划后再执行、要在循环里插入非 LLM 的决策节点。
  • 需要自定义循环逻辑：比如限制某个工具最多调 N 次、检测到死循环时换策略、根据工具结果决定回不回 agent。
  • 需要多步推理：标准的 ReAct 是「想一步做一步」，但你想先让 LLM 做个计划（Plan），再逐步执行（Execute），最后反思（Reflect）——这就是 ReWOO / Plan-and-Execute 等模式，得手写。
  • 要把 Agent 作为子图嵌进更大的多智能体系统，且需要精细控制输入输出 schema。
读懂这段：一个实用的判断标准：如果你发现自己在 create_react_agent 上堆了超过两三个 hook 和自定义 state 字段来「打补丁」，那基本说明该手写了——直接用 StateGraph 反而更清晰、更好维护。本站第 10 章会给出一张完整的选型决策表，帮你把这条经验规则细化到具体场景。

5.12本页要点回顾

  • ReAct = 思考→行动→观察的循环，LLM 通过 tool_calls 表达「要做什么」，运行时执行后用 ToolMessage 回传结果，直到 LLM 不再要求调工具。
  • create_react_agent 是快路径：一行封装好 agent/tools 节点 + 条件边 + prompt + 结构化输出 + hooks，适合标准需求。注意它已 deprecated，迁移到 langchain.agents.create_agent。
  • 手写是理解原理的必经之路：核心就是 StateGraph + 两个节点 + tools_condition 条件边 + tools→agent 回边。
  • tools_condition:检查最后一条 AIMessage 有无 tool_calls，有去 tools，无去 END。
  • ToolNode:自动执行 tool_calls 并返回 ToolMessage，处理了校验、注入、错误、并行。v2 用 Send 让每个 tool_call 独立并行。
  • pre_model_hook:调 LLM 前裁剪/摘要历史（用 llm_input_messages 只改输入不改 state）。post_model_hook:调 LLM 后做护栏/校验/HITL，仅 v2。
  • response_format:传 Pydantic 模型，Agent 循环结束后额外调一次 LLM 生成结构化结果，放在 state["structured_response"]。

5.13新手常犯的错误

ReAct Agent 这一块的两个高频坑，都和「工具」有关：一个是 LLM 根本不知道有工具可用，一个是工具报错把整张图带崩。

① 忘了 bind_tools,LLM 永远不会调工具

5.4 手写版里 model.bind_tools(tools) 是关键一步——它把工具的 schema 注入模型，模型才知道「可以调这些工具、参数长这样」。新手常直接拿裸 model 当 agent 节点，结果 LLM 的回复里永远不带 tool_calls，tools_condition 第一轮就返回 "__end__"——图「成功」跑完，却什么工具都没调。这种 bug 不会报错，只是静默地退化为纯聊天。

反面 vs 正面：工具必须 bind 进模型
pythonmodel = init_chat_model("openai:gpt-4o")

# ✗ 用裸 model,LLM 不知道有工具可用
def call_model(state):
    return {"messages": [model.invoke(state["messages"])]}
# → AIMessage 不带 tool_calls → tools_condition 直接返回 __end__
#   图跑完了，但工具一次没调

# ✓ 先 bind_tools 再用
model_with_tools = model.bind_tools(tools)
def call_model(state):
    return {"messages": [model_with_tools.invoke(state["messages"])]}
读懂这段： 用 create_react_agent 时不用担心这个——它内部会自动 bind_tools。但手写 StateGraph 时，这步必须自己做。排查信号：看 agent 节点产出的 AIMessage 有没有 tool_calls 字段，没有就是没 bind 上（或模型不支持工具调用）。

② 工具抛异常，默认会让整张图崩溃

5.4 的提示里提过 ToolNode 会处理错误，但没展开。源码显示：它的默认错误处理器 _default_handle_tool_errors 只把参数校验类错误（ToolInvocationError）转成 ToolMessage，其他异常（除零、API 超时、KeyError……）一律重新抛出——于是整个图直接崩，而不是把错误喂回 LLM 让它自纠。生产环境几乎一定要把这个默认行为改掉。

最小复现：工具抛 ValueError，默认配置下图崩溃
pythonfrom langchain_core.tools import tool
from langgraph.prebuilt import ToolNode


@tool
def divide(a: int, b: int) -> int:
    """整数除法。"""
    return a // b   # b=0 时抛 ZeroDivisionError


# ✗ 默认 handle_tool_errors 只兜参数校验，ZeroDivisionError 会直接抛出
tool_node = ToolNode([divide])
# 当 LLM 调 divide(a=1, b=0) 时，图抛 ZeroDivisionError 崩溃

# ✓ 传 handle_tool_errors=True，把所有异常转成 ToolMessage 喂回 LLM
tool_node = ToolNode([divide], handle_tool_errors=True)
# 现在 divide(a=1, b=0) 会产出一条内容为错误信息的 ToolMessage,
# LLM 看到后能自己纠正(比如改用非零除数重试)，而不是整张图崩掉
读懂这段： 源码里 ToolNode 的 handle_tool_errors 默认是 _default_handle_tool_errors（只接 ToolInvocationError）。传 True 会变成「捕获所有 Exception」，把异常信息包成 ToolMessage 回给 LLM——这正是 ReAct 循环想要的：工具失败也是一种「观察」，让 LLM 据此调整。也能传一个函数自定义错误文案，或传异常类型元组只捕获特定异常。
一句话总结 这两个坑的共同点是把「工具可用」和「工具可靠」当成默认成立了。第一个假设模型知道工具存在（忘了 bind），第二个假设工具不会失败（忘了配 handle_tool_errors）。生产级 ReAct Agent 的标配是：bind_tools 确保模型能调、handle_tool_errors=True 确保调崩了也能恢复。
