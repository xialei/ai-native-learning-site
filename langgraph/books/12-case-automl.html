12 · 实战案例 — 尝试用 LangGraph 重构一条 AutoML 流水线

前十一章讲「图怎么写」，本章讲「真实工程怎么用图」：把一条 26 节点 AutoML 流水线里手写的并发、审批、持久化、日志，逐一换成图原语——两层图、分区 State、Send、interrupt、双通道 stream，前九章的概念各就各位。

12.1案例背景：一条已用 LangGraph、却没用到点子上的流水线

案例是一条已存在的 AutoML 流水线：用户提交表格/时序预测任务，系统自动走完「理解问题 → 搜模型 → 建数据集 → 评估 → 调参迭代 → 注册交付」。它不是 demo——有软硬失败规则、人工审批点、一跑几小时到几天的长任务。

它已经用着 LangGraph，但只用了最浅的一层——好比买了智能手机只用来打电话：26 个节点平铺成一张大图，图覆盖不到的难点（并发、持久化、人机协同）全靠图外的手写机制在扛。用起来是什么体验？

  • 任务停在等人审批，页面却显示「运行中」——没人知道该自己出手，任务能卡一整天。
  • 想知道第 3 个候选训练到第几轮？界面上没有，只能翻日志。
  • 任务半夜挂了想重试——从哪个节点续跑记在手写 JSON 里，对不上就从头再来。

翻开代码，这些体验背后是五套手写机制：

  • 状态：178 个字段平铺一个 dict，谁读谁写全靠约定，节点返回的 patch 一不小心就覆盖别人的字段。
  • 并发：Top-K 候选在节点内用 ThreadPoolExecutor 手动开线程，外面还套 while True。
  • 审批：自定义 checkpoint_state.json + resume 函数，暂停是「节点内一个文件写入」，业务状态机不知道。
  • 可观测：有个 9 节点 trial 子图用 graph.invoke() 调用——内部事件被整个吞掉。
  • 日志：log_node_start/end 手写几十处，漏一处可观测就断一截。

每一套，前九章都有现成的图原语替换。本章做的就是这次替换——对照表既是问题清单，也是本章目录：

手写机制（重构前）图原语（重构后）对应章节
178 字段扁平 dict，整 patch 覆盖分区 State + 自定义 reducer03 状态·Reducer
26 节点平铺一张图 / mermaid 视觉分组两层结构：顶层只显示 4 个阶段子图07 多智能体（子图即节点）

范围声明 重构目标刻意定为机械等价：换机制不换行为——链路、软硬失败规则、审批点位全保留，不引入 LLM 推理闭环。真实业务的流水线要先「换引擎不换行为」，等价性才可验证；智能体化是第二步（见 12.9）。本章代码均为按重构方案蒸馏的教学示例，不逐字对应原仓库。
本章结构 12.2–12.7 是六个递进的决策——图怎么分层、状态怎么分区、并发怎么发、审批怎么停、断点怎么存、进度怎么看见；每个决策 = 一个手写机制 → 一个图原语。12.8 讲图之上的产品前端，12.9 收尾。若只关心某一环节，按 12.1 的对照表跳读即可。

12.2两层图结构：像浏览器书签栏一样组织节点

第一个决策：图怎么分层。最初的拆法把 26 个大节点拆成 38 个细粒度节点、全部平铺一张图——结果只是把「26 个节点太乱」变成「38 个节点更乱」。真正的解法类似浏览器书签：38 个节点按业务阶段收进 4 个文件夹（compiled 子图），书签栏（顶层）只显示文件夹。点开文件夹才是细节点——这就是「下钻」。

  • stage_a · 理解与发现（10 节点）：init → 校验 → 搜模型 → 血缘解析
  • stage_b · 数据与契约（3 节点）：特征元数据 → 物化数据集 → 问题契约
  • stage_c · 评估门禁（6 节点）：评估 → 领域评估 → 过拟合诊断 → 门禁路由
  • stage_d · 调优迭代（14 节点）：调优准备 → idea 库 → trial 循环 → 迭代编排 / Top-K 分支
  • 顶层尾（3 节点）：feature_analysis_post → cleanup → finalize

子图内合计 36 节点，加 trial 内嵌子图自己的 9 个，即「约 38」的口径。顶层只呈现约 10 个节点，一屏读完——复杂度没有被藏起来，而是按读者分层：这条只显示文件夹的顶层主干，下面叫它「主脊」。非工程角色只看主脊，工程师按需下钻到子图内部。

分层有一条硬约束：cleanup 必须留在顶层。原流水线里任何节点失败都要跳到统一的 cleanup 做清理，而子图是黑盒：只能从入口进，跳不进中间节点——cleanup 若埋进 stage_a，stage_c 失败时就够不着它。由此得出边界判据：

子图边界判据 需要被全图任意位置跳转/汇合的节点（cleanup、finalize）留在顶层；只被本阶段内读写的流程做成子图。先画跨子图的边，再给剩余节点分组——拓扑决定边界，而非业务名词。

另一个问题：子图内部的分叉，顶层怎么知道走了哪条。stage_c 的门禁有四向分流，但子图对外只有一个 END，顶层看不到内部走了哪条路。解法是出口信号字段：子图最末节点往状态写一个信号（如 signals.eval_exit_route = "tune_required"），顶层条件边读这个信号决定下一跳——子图内部怎么分叉是自己的事，结论用一个字段告诉顶层。重构前的 26 个内联路由闭包，就此收敛为「子图出口 + 顶层条件边」一个模式。

动态演示——步进看主脊推进、出口信号如何被顶层条件边消费、以及下钻子图内部与顶层尾的边界约束：

子图作为节点嵌入 + 出口信号 + 顶层条件边（蒸馏示例）
pythonfrom langgraph.graph import StateGraph, START, END

# ---- 阶段子图：内部路由全部收敛到 END，只留一个出口信号 ----
def build_stage_c():
    g = StateGraph(AutoMLState)
    g.add_node("run_evaluation", run_evaluation)
    g.add_node("overfitting_diagnosis", overfitting_diagnosis)
    g.add_node("gate_router", gate_router)      # 末节点：只写信号，不路由
    g.add_edge(START, "run_evaluation")
    g.add_edge("run_evaluation", "overfitting_diagnosis")
    g.add_edge("overfitting_diagnosis", "gate_router")
    g.add_edge("gate_router", END)               # 四向分流 → 收敛为一个信号字段
    return g.compile()

def gate_router(state: AutoMLState) -> dict:
    # 内部分流逻辑照旧，但结论只写进出口信号字段
    route = compute_gate_route(state)   # pass_or_eval_only / tune_required / ...
    return {"runtime": {"signals": {"eval_exit_route": route}}}

# ---- 顶层：子图当节点，条件边读信号决定下一跳 ----
top = StateGraph(AutoMLState)
top.add_node("stage_a", build_stage_a())
top.add_node("stage_c", build_stage_c())
top.add_node("stage_d", build_stage_d())
top.add_node("cleanup", cleanup)          # 失败短路汇合点：必须留顶层
top.add_edge(START, "stage_a")
top.add_edge("stage_a", "stage_c")
top.add_edge("stage_c", "stage_d")
top.add_edge("stage_d", "cleanup")
读懂这段：① build_stage_c() 返回 compiled graph 直接作为 add_node 参数——「子图即节点」（第 07 章同一机制，这里用于工程分层）；② gate_router 的返回值没有路由指令、只有信号——分流决策被数据化了；③ 顶层连边极简，四向语义藏在 eval_exit_route 取值里，条件边按信号跳转。

12.3分层 State：178 个扁平字段 → 7 个分区

第二个决策：状态怎么组织。178 个字段平铺一个 dict，问题在更新语义：节点返回 patch、reducer 负责合并，扁平结构下返回 {"tune": {...}} 就可能覆盖 tune 的其他字段——像多个人共编一张表格，每次都要小心别碰坏别人的格子。解法是按读写边界分区：把字段分进 7 个分区，每个分区一个 reducer，节点只动自己分区的键。

分区 State + 分区级合并 reducer（蒸馏示例）
pythonfrom typing import Annotated, TypedDict

def section_merge(name: str):
    """分区级合并：只更新 patch 里出现的键，不动分区内的其他键。"""
    def reducer(old: dict | None, new: dict | None) -> dict:
        merged = dict(old or {})
        merged.update(new or {})
        return merged
    return reducer

# 每个分区是一个嵌套 TypedDict；reducer 一律挂在顶层 schema 的分区键上
# （LangGraph 只读顶层 Annotated——分区「内部」的 Annotated 不生效，实测验证）
class TuneSection(TypedDict, total=False):
    idea_library: list
    best_trial: dict     # 多写者字段：靠节点内显式比较取优（见下）
    iteration_pass: int  # 防并发更新回退：同上，显式 reconcile

class SignalsSection(TypedDict, total=False):
    eval_exit_route: str          # stage_c 出口信号
    experiment_exit_route: str    # stage_d 出口信号

class AutoMLState(TypedDict, total=False):
    runtime: RuntimeSection                  # 含 signals 子键
    problem: Annotated[dict, section_merge("problem")]  # 契约级：目标列/任务类型/时序契约
    data:    Annotated[dict, section_merge("data")]
    model:   Annotated[dict, section_merge("model")]
    eval:    Annotated[dict, section_merge("eval")]
    tune:    Annotated[dict, section_merge("tune")]
读懂这段：分区靠读写证据划分：grep 每个字段被谁读谁写，高频共读共写的归一个分区。这会暴露反直觉的归属——target_column 名字像数据字段，但它建契约后定型、被下游只读传播，本质是契约，应上移到 problem。另注意一个实测验证的框架边界：reducer 只看顶层 schema 的 Annotated——写在分区 TypedDict 内部的 Annotated[dict, best_reducer] 不生效。

三个配套设计：

  • 出口信号单独一个 signals 分区：eval_exit_route 这类信号被顶层条件边读，不归属任何业务分区——单独放 runtime.signals（last-write-wins），不污染业务分区的 reducer 边界。
  • 多写者字段显式 reconcile：best_trial 被四个节点写，「后来者覆盖」会丢历史最优。解法是双保险：section_merge 兜住「不同键互不覆盖」，节点内（prepare_tuning/trial_loop/finalize）比较主指标、只留最优——第 03 章「为字段选对合并语义」在分区结构下的落地。iteration_pass 防回退同理，节点内 max() 后写。
  • 迁移期留兼容层：flatten_state(sectioned) -> legacy_flat 让新旧 state 并存，节点逐个迁移，迁完再删——第 09 章的灰度思路。
经验 分区边界最怕按业务名词直觉分。用读写证据说话：字段被谁写、被谁读、读写是否在同一阶段。证据会告诉你哪些字段「名字在这、家在别处」——那些正是扁平时代留下的隐式耦合，分区化是让它们显式化的机会。

12.4Send fan-out：替掉 ThreadPoolExecutor

第三个决策：并发怎么做。Top-K 调优是唯一的真并发场景——选 K 个候选模型，每个独立跑完整调优子流程，最后汇总选优。重构前塞在一个节点函数里，ThreadPoolExecutor 手动开 K 个线程、每线程串调 4 个节点函数；线程没有界面、没有断点、异常互相污染。重构后换成 Send：

Top-K 并发：Send fan-out + 子图（蒸馏示例）
pythonfrom typing import Annotated
import operator
from langgraph.types import Send, Command

# 汇聚槽挂在顶层 schema 上（operator.add 才会生效——见 12.3 的框架边界）
class AutoMLState(TypedDict, total=False):
    candidate_results: Annotated[list, operator.add]

# fan-out 有两种等价写法（均实测可跑）：

# 写法一：条件边的 path 函数返回 Send 列表（第 04 章的标准姿势）
def topk_fanout(state: AutoMLState) -> list[Send]:
    return [
        Send("tune_candidate_subgraph", {"candidate": c,
                                          "problem": state["problem"],
                                          "data": state["data"]})
        for c in state["model"]["topk_candidates"]
    ]
top.add_conditional_edges("search_bridge", topk_fanout)   # 从上游节点 fan-out

# 写法二：普通节点直接返回 Command(goto=[Send...])
def topk_fanout_node(state: AutoMLState) -> Command:
    return Command(goto=[Send("tune_candidate_subgraph", {...})
                         for c in state["model"]["topk_candidates"]])

top.add_edge("tune_candidate_subgraph", "topk_promote")   # 汇聚选优
读懂这段：对照第 04 章 map-reduce，结构一模一样——变的只是 map 目标从函数变成子图。每个候选得到独立状态投影（只读 problem/data，写 candidate_results），K 个子图实例同一 super-step 并发，结果经 operator.add 归并。易踩的坑：Send 只能从条件边 path 函数或 Command(goto=) 发出——普通节点直接 return [Send(...)] 会被当成 state patch，实测抛 InvalidUpdateError。

换掉线程换来三件事，都源于「并发单元从线程变成了图节点」：

  • 可观测：每个候选每步都是图节点，updates 天然可见——线程时代想知道 3 号候选跑到哪只能翻日志。
  • 可中断：任意候选内 interrupt()，整图挂起、checkpoint 落盘，恢复后从断点继续。
  • 失败可续跑：一个候选抛异常，整次 invoke 以异常结束（默认取消同批其他任务，见 _should_stop_others）——但已完成候选的写入已随 checkpoint 落盘，同 thread_id 重新 invoke，只补跑失败的那个。线程时代恢复位置全靠手写记录。
Send 的隔离契约要先定 「候选子图只读 problem/data/model、写独立 candidate_results」这个契约在状态分层落地时就定稿，而不是并发改造时才定——它决定子图接口形状，是后续拆分的前提。拖到最后才发现隔离方式不对，返工波及全部已完成的拆分。接口先行，实现后行。

12.5interrupt({type})：把 HITL 从文件约定变成类型契约

第四个决策：人机协同怎么做。流水线有三种人工审批点：调参 idea 审批、领域指标确认、test 集确认。重构前用自定义 JSON 文件 + resume 函数实现，缺陷前面已经见过：暂停等人时 status 仍标 "running"，没人知道该出手，任务能卡一整天。根因：暂停只是节点内一个文件写入，业务状态机根本不知道。

重构后三种审批点统一为原生 interrupt()，且每个 interrupt 的 value 都带 type 字段：

审批点interrupt type前端渲染resume 载荷
idea 审批idea_approvalidea 列表卡片（勾选批准）批准的 idea id 列表
领域指标确认domain_metric_confirm指标确认卡（建议指标 + 修改）确认的指标集
test 集确认test_confirm指标对比卡（valid vs test）yes/no
为什么 type 字段重要：interrupt 的 value 本来就是任意 JSON——结构化价值全在消费端。前端拿到 __interrupt__ 事件后按 value.type 选渲染组件。「一种 type 一种 UI 组件」的映射表就是图后端和前端的契约：新加审批点 = 图里一处 interrupt + 前端一个组件，两边各自声明、互不渗透。
idea 审批：interrupt 带类型化载荷（蒸馏示例）
pythonfrom langgraph.types import interrupt, Command

def generate_idea_library(state: AutoMLState) -> dict:
    ideas = build_idea_library(state)
    high_risk = [i for i in ideas if i.risk in ("MEDIUM", "HIGH")]
    if high_risk and not state["tune"].get("approved_idea_ids"):
        # 第一次执行：抛给前端；resume 后从这里拿到批准列表
        approved = interrupt({
            "type": "idea_approval",     # 前端据 type 选 UI 组件
            "ideas": high_risk,           # 结构化载荷
        })
        ideas = apply_approvals(ideas, approved)
    return {"tune": {"idea_library": ideas}}

# ---- 前端审批服务：按 type 分发，resume 回传 ----
def approve(thread_id: str, decision: dict):
    config = {"configurable": {"thread_id": thread_id}}
    graph.invoke(Command(resume=decision["approved_ids"]), config)
读懂这段：第 06 章的三条纪律全部生效：副作用在 interrupt 之后（apply_approvals 拿到批准列表后才改写 ideas）；节点会从头重跑（interrupt 前不能有不可重复副作用——build_idea_library 是纯计算，实测执行两次，可接受）；interrupt 数量与顺序两次执行间不能变（if 判断的「是否已有批准记录」在两次执行间不变，分支走向稳定，安全）。

status 语义怎么修：旧机制 status 留 "running" 的根因是暂停只是节点内一个文件写入，业务状态机不知道。换成 interrupt() 后暂停变成可从快照推导的一等状态：读 get_state(config)，snapshot.interrupts 非空 = 在等人。前端审批徽标有了可信数据源，不用每个审批点自己维护标志位。

12.6Checkpointer：一个任务一条 thread

第五个决策：断点存哪、怎么恢复。手写 checkpoint 时代，「存什么、存哪、怎么恢复」是自定义 JSON 的私有约定；换图后这些全交给 Checkpointer，自己只做一个决定——thread_id = task_id。重试 = 同一 thread_id 重新 invoke，图从最后一个 checkpoint 自动恢复。

SqliteSaver + thread_id=task_id（蒸馏示例）
pythonimport sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver  # pip install langgraph-checkpoint-sqlite

# 常驻服务用裸连接构造（from_conn_string 返回的是上下文管理器，适合脚本一次性跑）
conn = sqlite3.connect("automl_checkpoints.db", check_same_thread=False)
checkpointer = SqliteSaver(conn)
graph = top.compile(checkpointer=checkpointer)

# 提交任务：thread_id 用任务 ID——重试/恢复/审批共用这一个键
config = {"configurable": {"thread_id": task_id}}
graph.invoke(initial_state, config)

# 任务失败重试：同一个 thread_id 重新 invoke，从断点续跑
graph.invoke(None, config)          # None = 不带新输入，从 checkpoint 继续

# HITL 恢复：还是同一个键
graph.invoke(Command(resume=decision), config)
读懂这段：thread_id 是「状态隔离边界 + 恢复寻址依据」（第 09 章），这里把粒度定在「一个业务任务」——不是一次调用、不是一个会话。AutoML 任务跑几小时到几天，穿插部署、审批、重试，task_id 把这条任务的一切执行历史钉在一起。粒度选什么，取决于你的「可恢复执行单元」是什么。

两个落地细节：① SqliteSaver 来自独立的 langgraph-checkpoint-sqlite 包，引入要加依赖；② 手写的 save/load_workflow_checkpoint 不必立刻删——迁移期改造成 Checkpointer 薄封装，保留旧「从哪重试」解析给存量任务，迁完再删（与 12.3 同一个灰度思路）。

12.7可观测：双通道 stream 驱动进度 UI

第六个决策：进度怎么让人看见。12.1 的问题还记着：想知道第 3 个候选训练到第几轮，只能翻日志——两层结构下顶层 stage_d 是黑盒，用户恰恰最关心黑盒里的 trial 进度。图的答案是组合 stream_mode：

双通道 stream：updates 管全景，custom 管下钻（蒸馏示例）
pythonfrom langgraph.config import get_stream_writer

# 子图内部节点：每轮训练结束主动推一条 custom 事件
def train_one_trial(state):
    writer = get_stream_writer()            # 子图内取 writer
    for rnd in range(max_rounds):
        metric = train_and_eval(state, rnd)
        writer({"kind": "trial_progress",
                "trial": state["trial_id"], "round": rnd,
                "metric": metric})
    ...

# 服务端：一条 stream，双通道分发（subgraphs=True 是拿到子图事件的关键）
for ns, mode, payload in graph.stream(state, config,
                                      stream_mode=["updates", "custom"],
                                      subgraphs=True):
    if mode == "updates" and not ns:
        update_ridge_ui(payload)             # ns 为空 = 顶层主脊：✓ / ● / ○
    elif mode == "custom":
        append_trial_row(payload)            # 子图冒泡上来的 trial 进度
读懂这段：对照第 11 章：updates 是框架自动吐的节点级 patch，custom 是节点用 get_stream_writer() 主动推的数据。一条 stream 两个频道。两个实测验证的要点：① custom 默认不冒泡——不加 subgraphs=True，子图内推的事件一条都收不到；加上后事件带 ns 标明来自哪层。② 组合模式 + subgraphs=True 时输出是 (ns, mode, payload) 三元组，解包按这个形状来。不需要轮询接口，不需要自建事件总线。

为什么这套可观测是「送的」 手写时代可观测靠每个节点自觉打日志，漏写一处断一截。换图后节点边界即事件边界：updates 是执行模型的自然产物，零额外代码；custom 只在需要细粒度处补几行 writer 调用。可观测性从「约定」变成「结构性质」——本章所有重构里 ROI 最高的一项。

12.8给图做前端：中断语义如何变成产品交互

前六节讲「把流水线搬上图」。本节换视角：图确定之后，产品前端长什么样。案例项目的做法是先做纯前端交互原型（setInterval 模拟 stream、内存 store 模拟暂停/恢复），把「创建 → 推进 → 下钻 → 审批 → 恢复 → 交付」动线在浏览器里走通，产品、前后端三方对齐后再实现真图。原型沉淀出三张映射表：

映射一：interrupt type → 审批 UI

12.5 的三行表在这里变成前端注册表：每个 type 对应一个卡片组件 + 一个 resume 载荷结构。新审批点 = 图里一处 interrupt + 前端一个组件。

映射二：图结构 → 信息架构

图概念产品概念
顶层主干（主脊，~10 节点）实验详情页的「进度脊」——给管理者/非工程角色看全链路
阶段子图内部节点点任一主脊步骤后的「下钻面板」——给工程师看细节
trial 子图（两层嵌套）调优步骤内的 trial 追踪表——每轮训练一行实时刷新
interrupts 非空全局「待审批」徽标 + 卡片入口
thread_id实验 ID——审批深链、重试按钮的寻址键
读懂这张表：产品信息架构就是图结构的一次投影：两层图 → 两级视图，出口信号 → 步骤流转语义，interrupt → 审批工作流。反过来：如果产品需要一个「图结构表达不了」的视图（如跨实验对比），要么图粒度不对，要么它不该由单次执行提供——这种张力在评审期暴露，比实现期便宜十倍。

映射三：状态推导 → 状态语义

status 不由节点各自维护，统一从快照推导：snapshot.interrupts 非空 → interrupted；snapshot.next 非空且有事件在流 → running；stream 正常结束 → completed。修正了手写时代最大的状态 bug（暂停时标 running），每个状态徽标都有了单一真相来源。

方法论小结 图原语的 UI 形态（interrupt 卡片、子图下钻、暂停徽标）是设计决策，不是实现细节。用假 stream 在纯前端定稿，成本几天；在真图上边实现边改，成本几周。LangGraph 原语语义恰好给原型足够保真度——模拟器只需忠实翻译这些语义，不需理解业务。

12.9收尾：从等价重构到 Agentic 闭环

六个决策做完，对照 12.1 的三个用户体验问题逐条验收：

能力重构前重构后受益方
读图26 节点平铺，新同事读一天顶层 10 节点，一屏读完；细节按需下钻所有人
可观测手写日志，子图内部不可见updates 全景 + custom 下钻，双通道运维/前端
可中断自定义文件约定，status 语义错原生 interrupt + 推导式 status审批人
可恢复手写 save/load + 重试入口表Checkpointer + thread_id 自动续跑运维
可并发ThreadPoolExecutor 手写Send fan-out，候选状态投影隔离 + 失败可从 checkpoint 续跑用户（更快出结果）

回到开头三个体验问题：「等人却显示运行中」→ interrupt + 推导式 status；「候选训练进度看不到」→ custom 事件下钻；「重试不知道从哪续」→ thread_id 自动续跑。而图的真正回报在下一步：等价重构把每个环节变成了细粒度、带类型化接口的图节点——这正是智能体化的前提。Agentic 闭环（评估 → 诊断 → 假设 → 再评估）本质是在现有节点上叠一个「推理环」：overfitting_diagnosis 的输出喂给 LLM 节点生成假设，假设经审批变成新 idea，进入既有 trial 循环。环的每一站都是已存在的节点——软失败语义、出口信号契约、interrupt 点位全部直接复用。

呼应第 10 章 这个案例是第 10 章决策树的活体样本：不需要 create_react_agent（没有自由工具循环），不需要 Supervisor（没有角色分工对话）；需要的是 StateGraph 底层原语。判断依据从来不是「是不是 AI 应用」，而是任务有没有结构化流程、副作用和中断语义。判据普适：流程越重、越需要 HITL 与可恢复，越该下钻到图原语；纯对话助手从 prebuilt 起步即可。

如果只带走五条

  • 先等价、再进化：换引擎不换行为，等价性可验证之后，才谈叠加智能行为。
  • 边界由拓扑决定：子图边界看「跨组跳转的边」，不看业务名词；cleanup 这类全图汇合点必须留顶层。
  • 接口先行：Send 的隔离契约、interrupt 的 type 协议、stream 的事件 schema——这些跨边界的契约在动工前定稿，返工成本最低。
  • 状态语义从快照推导：interrupts/next/stream 事件是唯一真相来源，别让业务节点各自维护状态标志。
  • UI 是图结构的投影：先在纯前端原型上定稿「中断态长什么样」，再实现真图——设计决策不应该发生在实现期。
