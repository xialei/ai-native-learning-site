状态与 Reducer:谁来决定「旧值 + 新值」等于什么

第 1 章说节点返回「更新请求」、第 2 章看到更新被合并进 State——但「合并」这两个字一直被一笔带过。这一章把合并拆开：默认为什么是覆盖、覆盖在哪些场景会吃掉数据、怎么用一个注解换成你要的合并语义。读完你就有了回答「这个字段该不该配 reducer」的判断依据。

3.1开场：多轮对话第二轮就「失忆」

先看一个马上会撞上的场景。按第 2 章的三步法搭一个最简单的多轮 chatbot：user 节点写用户消息，bot 节点写回复，边把它们串起来。跑第一轮没问题；第二轮一进来，你发现模型把第一轮说过的话全忘了——检查状态，messages 里只剩最后一条。

代码没有任何「删除」操作，消息去哪了？这就是本章要解决的第一个问题：节点返回的更新，落到 State 上时到底发生了什么。答案由每个字段的合并规则（Reducer）决定——而默认规则恰好是「覆盖」。本章从 State 长什么样、节点之间怎么共享它讲起（3.1）；然后拆开默认合并规则，看它在什么场景会吃掉数据（3.2）；再讲怎么用 Annotated 把「覆盖」换成「追加」「累加」，包括内置和自定义 reducer（3.3–3.6）；最后把合并逻辑放回整个执行流程，落到设计 reducer 的两条铁律上（3.8–3.9）。

在 LangGraph 里，图不是「传参调用链」，而是「共享黑板」：所有节点都读取同一份 State，处理后返回一个 局部更新（Partial State），框架再把这个更新合并进总 State。这种设计让节点之间解耦——每个节点只关心自己要读什么、写什么，不需要知道上下游的返回结构。

State 通常用一个 TypedDict 定义，也可以用 Pydantic 的 BaseModel。下面是最基本的例子：

最基础的 State —— 节点只返回要更新的字段子集，框架负责合并
pythonfrom typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END


# 用 TypedDict 定义状态：每个字段就是一个 channel(通道)
class State(TypedDict):
    question: str   # 用户的问题
    answer: str     # 模型的回答


def ask_node(state: State) -> dict:
    # 节点只返回要更新的字段，不必返回整个 State
    return {"answer": f"关于「{state['question']}」的初步回答"}


builder = StateGraph(State)
builder.add_node("ask", ask_node)
builder.add_edge(START, "ask")
builder.add_edge("ask", END)

graph = builder.compile()
print(graph.invoke({"question": "什么是 LangGraph"}))
# {'question': '什么是 LangGraph', 'answer': '关于「什么是 LangGraph」的初步回答'}
部分更新的含义：ask_node 只返回 {"answer": ...}，并不返回 question。框架把这个返回值与当前 State 合并：没有 reducer 时默认「覆盖」，于是 answer 被写入、question 保持不变。这就是「节点返回部分更新」的含义——你不必每次都返回全量 State。

你也可以用 Pydantic，这样字段会有校验和默认值：

Pydantic State —— 带校验和默认值，适合需要强约束的场景
pythonfrom pydantic import BaseModel
from langgraph.graph import StateGraph, START, END


class State(BaseModel):
    question: str
    answer: str = ""  # 带默认值


def ask_node(state: State) -> dict:
    return {"answer": "来自 Pydantic State 的回答"}


builder = StateGraph(State)
builder.add_node("ask", ask_node)
builder.add_edge(START, "ask")
builder.add_edge("ask", END)
print(builder.compile().invoke({"question": "hi"}))
# {'question': 'hi', 'answer': '来自 Pydantic State 的回答'}
校验发生在入口：注意 invoke 返回的是普通 dict（即使 State 是 Pydantic 模型）。Pydantic 在这里的价值是入口校验：传入的字段类型不对会立刻报错，answer 带默认值 ""，调用方没传也不会报错。适合字段较多、需要类型校验或嵌套结构的场景；但多数 agent 用 TypedDict 就够了。
提示 为什么用 TypedDict？它是「带类型提示的字典」，运行时就是一个普通 dict，零开销，mypy/pyright 都认得，且能通过 Annotated 挂载 reducer。只有当你需要字段校验、默认值、嵌套模型时才上 Pydantic。

3.2默认合并 = 覆盖：一个会咬人的坑

关键问题来了：当一个 key 没有指定 reducer 时，新值如何与旧值合并？ 答案是——直接覆盖。框架在源码里为没有 reducer 的字段创建的是一个 LastValue 通道，它的 update 逻辑就是 self.value = values[-1]（摘录见第 1 章 1.7，last_value.py:56）：谁后写谁赢，旧值被丢弃。

图 3.2：LastValue 的覆盖时序。两次顺序写入各自触发一次 update，盒子每次整体替换为最新写入；配了 reducer 的盒子则把每次写入归约进历史。

这在写「普通字段」时很合理（比如 answer 本来就该被新回答覆盖），但在处理 消息列表（messages） 时就是灾难：

陷阱：messages 没有指定 reducer，默认「覆盖」导致历史丢失
pythonfrom typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END


# 陷阱：messages 没有指定 reducer，默认是"覆盖"
class BadState(TypedDict):
    messages: list


def user_node(state: BadState) -> dict:
    return {"messages": [{"role": "user", "content": "你好"}]}


def bot_node(state: BadState) -> dict:
    # 本意是"在历史后面追加一条 AI 回复"
    # 但默认 reducer 是覆盖，于是历史只剩这一条
    return {"messages": [{"role": "assistant", "content": "你好呀"}]}


builder = StateGraph(BadState)
builder.add_node("user", user_node)
builder.add_node("bot", bot_node)
builder.add_edge(START, "user")
builder.add_edge("user", "bot")
builder.add_edge("bot", END)

result = builder.compile().invoke({"messages": []})
print(result["messages"])
# [{'role': 'assistant', 'content': '你好呀'}]   ← 用户消息被覆盖丢了！
一条返回值顶掉全部历史：user_node 写入了一条用户消息，紧接着 bot_node 返回 {"messages": [AI回复]}。由于 messages 没有 reducer，新值直接顶掉旧值——用户消息被丢弃。任何需要「累积历史」的场景都必须给这个字段配 reducer。

不仅如此，LastValue 还有一个更严格的限制：它每一步只能接收一个写入。如果你有多个并行节点（fan-out）同时往同一个没有 reducer 的 key 写，框架会直接抛出 InvalidUpdateError。源码里的报错信息写得很清楚：

LastValue 通道在并发写入时报错 —— fan-out 必须配 reducer
textAt key 'messages': Can receive only one value per step.
Use an Annotated key to handle multiple values.
报错的弦外之音：这条报错点出了 reducer 的两大职责——一是决定单次写入如何累积（覆盖 vs 追加），二是让多个并发写入能被合并成一个确定结果。这就是为什么写 agent 几乎一定要给 messages 配 reducer。

3.3Annotated[type, reducer]：给字段挂上归约器

解决上面的坑，只需要在类型注解里用 Annotated 挂一个 reducer 函数。语法是：

Annotated 挂载 reducer 的固定签名
pythonfrom typing import Annotated
# Annotated[类型, reducer函数]
# reducer 的签名固定为：(旧值, 新值) -> 合并后的值
框架怎么认出 reducer：Annotated 是 Python 标准库的类型工具，它把「额外元信息」挂在类型上而不改变运行时类型。LangGraph 在编译时检查 Annotated 的最后一个 metadata（state.py:1904 的 _is_field_binop），若它是「接收两个位置参数的可调用对象」，就把该字段建成 BinaryOperatorAggregate 通道——每次更新时调用 reducer(旧值, 新值)。

给 messages 挂上合适的 reducer 后，上面的例子就能正常累积历史了。LangGraph 内置了一个专门处理消息的 reducer——add_messages，正是为这个场景而生。

3.4add_messages:按 ID 合并的消息归约器

add_messages 是 LangGraph 最核心的内置 reducer，位于 langgraph.graph（源码在 langgraph/graph/message.py）。它的行为是：

  • 同 ID 的消息 → 用新消息替换旧消息（适合流式更新、修正）
  • 新 ID 的消息 → 追加到列表末尾（保证 append-only 历史）
  • 没有 ID 的消息会自动分配一个 UUID
  • 还能识别 RemoveMessage 来按 ID 删除历史消息

我们直接看源码里的用法，再改写上面的陷阱：

用 Annotated[list, add_messages] 改写陷阱 —— 历史完整保留
pythonfrom typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END, add_messages
from langchain_core.messages import HumanMessage, AIMessage


# 关键：用 Annotated[list, add_messages] 指定 reducer
class GoodState(TypedDict):
    messages: Annotated[list, add_messages]


def user_node(state: GoodState) -> dict:
    # 返回的是"要追加的新消息",reducer 会自动合并进历史
    return {"messages": [HumanMessage(content="你好", id="1")]}


def bot_node(state: GoodState) -> dict:
    return {"messages": [AIMessage(content="你好呀，有什么可以帮你？", id="2")]}


builder = StateGraph(GoodState)
builder.add_node("user", user_node)
builder.add_node("bot", bot_node)
builder.add_edge(START, "user")
builder.add_edge("user", "bot")
builder.add_edge("bot", END)

result = builder.compile().invoke({"messages": []})
for m in result["messages"]:
    print(type(m).__name__, ":", m.content)
# HumanMessage ： 你好
# AIMessage ： 你好呀，有什么可以帮你？     ← 历史完整保留了！
一行注解，语义对调：与 3.2 的陷阱相比，唯一的改动是 messages: Annotated[list, add_messages]。现在 user_node 写入的 HumanMessage 会被追加进历史，而不是被 bot_node 的返回覆盖。一个注解，就把「覆盖语义」切换成了「追加语义」。

同 ID 替换的特性也很实用——比如流式输出时不断更新同一条 AI 消息：

同 ID 替换 —— 流式更新时同一条消息被原地刷新
pythonfrom langchain_core.messages import HumanMessage, AIMessage
from langgraph.graph import add_messages

# 第一轮：写入一条 id="2" 的 AI 消息
msgs1 = [HumanMessage(content="你好", id="1")]
msgs2 = [AIMessage(content="你好", id="2")]
print(add_messages(msgs1, msgs2))
# [HumanMessage(content='你好', id='1'), AIMessage(content='你好', id='2')]

# 第二轮：用相同 id="2" 写入更完整的内容 → 替换而非追加
msgs3 = [AIMessage(content="你好呀，很高兴认识你！", id="2")]
print(add_messages(msgs1 + msgs2, msgs3))
# [HumanMessage(content='你好', id='1'),
#  AIMessage(content='你好呀，很高兴认识你！', id='2')]   ← 第二条被原地更新
同 ID 就是「那条消息」：第二轮用 id="2" 再次写入，因为 ID 与历史中已有消息相同，add_messages 不会新增一条，而是把那条旧消息替换成新内容。这正是流式输出、工具调用修正、多步回溯等场景所需要的「原地更新」能力。
图 3.4：add_messages 按 ID 走两条合并路径——同 ID 原地替换（流式刷新、修正），新 ID 追加（append-only 历史）。一个机制同时服务两种场景。
设计 为什么按 ID 而不是简单 append？因为 agent 场景里消息不是「只增不改」的。流式生成要不断更新同一条 AI 消息的 content；工具调用出错可能要修正上一条；多步推理会回溯。按 ID 合并把「追加」和「更新」统一成同一个机制：ID 相同就更新，ID 不同就追加——比纯 list + list 灵活，又比全量覆盖安全。

add_messages 还支持用 format="langchain-openai" 参数把消息格式化成 OpenAI 兼容结构，用法是 Annotated[list, add_messages(format="langchain-openai")]（内部用了 functools.partial 柯里化）。

3.5MessagesState:省去手写 Annotated 的现成状态

因为 messages: Annotated[list, add_messages] 这个组合太常用，LangGraph 直接提供了一个现成的 TypedDict 叫 MessagesState。源码极其简单：

MessagesState 源码 —— 只是预先挂好 add_messages 的 TypedDict
python# 源码：langgraph/graph/message.py
class MessagesState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
没有任何魔法：MessagesState 没有任何特殊处理，就是把你每次都要写的那行 Annotated[list, add_messages] 封装好了。用它就不用自己写 Annotated 了，还能直接继承它来扩展更多字段：
直接用 / 继承 MessagesState —— 两种扩展方式
pythonfrom langgraph.graph import StateGraph, START, END, MessagesState
from langchain_core.messages import HumanMessage, AIMessage


# 方式一：直接用 MessagesState(只有 messages 一个字段)
builder = StateGraph(MessagesState)
builder.add_node("chat", lambda state: {"messages": [("assistant", "嗨")]})
builder.add_edge(START, "chat")
builder.add_edge("chat", END)
print(builder.compile().invoke({"messages": [HumanMessage(content="在吗", id="1")]}))
# {'messages': [HumanMessage(content='在吗', id='1'),
#               AIMessage(content='嗨', id=...)]}


# 方式二：继承 MessagesState，加上自己的字段
from typing import Annotated
import operator


class AgentState(MessagesState):
    # messages 字段从父类继承，已带 add_messages reducer
    tool_call_count: Annotated[int, operator.add]  # 自定义累加字段
最常见的自建状态结构：方式二继承 MessagesState，既保留了带 reducer 的 messages，又新增了一个用 operator.add 累加的 tool_call_count。这是自建 agent 时最常见的状态结构——消息历史 + 业务计数。
提示 本代码库里 create_react_agent 的内部状态 AgentState（位于 libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py）就是同样的写法：messages: Annotated[Sequence[BaseMessage], add_messages]。你自建 agent 时照搬这个结构即可。

3.6自定义 Reducer:operator.add 与手写函数

reducer 不止 add_messages 一种。只要满足 (旧值, 新值) -> 合并值 签名的二元函数，都能挂到 Annotated 上。框架在源码里（state.py 的 _is_field_binop）会检查 Annotated 的最后一个 metadata 是不是「接收两个位置参数的可调用对象」，是的话就建成一个 BinaryOperatorAggregate 通道。

最常见的是 operator.add——对 list 是拼接，对 int 是相加：

operator.add 累加器 —— 节点自循环三次，计数累加、步骤拼接
pythonimport operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END


class CounterState(TypedDict):
    # 用 operator.add 做累加：每次节点返回的数值会被加到旧值上
    count: Annotated[int, operator.add]
    # list 也能用 operator.add，效果是列表拼接
    steps: Annotated[list[str], operator.add]


def step_node(state: CounterState) -> dict:
    return {"count": 1, "steps": [f"step@count={state['count']}"]}


builder = StateGraph(CounterState)
builder.add_node("step", step_node)
builder.add_edge(START, "step")
# 让节点自循环三次：step -> step -> step -> END
# add_conditional_edges 在此用来"看 count 决定走哪"，下一章(04)详讲
builder.add_conditional_edges(
    "step",
    lambda s: "step" if s["count"] < 3 else END,
)
builder.add_edge("step", END)  # 兜底

result = builder.compile().invoke({"count": 0, "steps": []})
print(result)
# {'count': 3, 'steps': ['step@count=0', 'step@count=1', 'step@count=2']}
1 加三次等于 3，不是 1：每次 step_node 返回 {"count": 1}，但因为有 operator.add，这个 1 不是覆盖而是加到旧值上：0→1→2→3。同理 steps 每次返回单元素列表，被拼接成三元素列表。条件边根据 count < 3 决定继续循环还是结束。

你也可以完全手写一个 reducer，实现更复杂的合并逻辑：

手写 reducer —— 用 " -> " 连接路径节点名
pythonfrom typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END


# 手写 reducer：把新字符串拼到旧字符串后面，用 " -> " 连接
def concat(left: str, right: str) -> str:
    if not left:
        return right
    return f"{left} -> {right}"


class PathState(TypedDict):
    path: Annotated[str, concat]   # 挂上自定义 reducer


def visit_a(state: PathState) -> dict:
    return {"path": "A"}

def visit_b(state: PathState) -> dict:
    return {"path": "B"}

def visit_c(state: PathState) -> dict:
    return {"path": "C"}


builder = StateGraph(PathState)
builder.add_node("a", visit_a)
builder.add_node("b", visit_b)
builder.add_node("c", visit_c)
builder.add_edge(START, "a")
builder.add_edge("a", "b")
builder.add_edge("b", "c")
builder.add_edge("c", END)

print(builder.compile().invoke({"path": ""}))
# {'path': 'A -> B -> C'}
纯函数就能上岗：concat 是个普通二元函数，符合 (旧, 新) -> 合并 签名，所以能直接当 reducer 用。三个节点依次写入 "A"、"B"、"C"，reducer 把它们连成 "A -> B -> C"。任何纯函数合并逻辑都可以这样挂上去——去重、字典合并、最大值都行。

3.7三种 Reducer 行为对比

把默认覆盖、add_messages、operator.add 放在一起对比，差异最清晰。假设旧值（left）和新值（right）如下：

Reducerleft（旧值）right（新值）合并结果典型用途
默认（无 reducer）109999（覆盖）普通字段：answer、current_step
默认（无 reducer）[a, b][c][c]（覆盖）（messages 易踩坑）
默认并发写入1099 + 88（两个并行节点）InvalidUpdateError 报错fan-out 必须配 reducer
add_messages[msg(id=1)][msg(id=2)][msg(id=1), msg(id=2)]（追加）对话历史 append-only
add_messages[msg(id=1), msg(id=2)][msg(id=2, 新内容)][msg(id=1), msg(id=2,新)]（同ID替换）流式更新、修正消息
operator.add538（累加）计数器、累加分数
operator.add[a, b][c, d][a, b, c, d]（拼接）收集多节点产出
表格里真正要盯的一行：三行带「默认并发写入」的报错是这里的关键——任何 fan-out（并行节点）写同一个字段，都必须有 reducer。其余行展示了同一对输入在不同 reducer 下得到完全不同的结果：覆盖、追加、替换、累加、拼接。选 reducer 就是选合并语义。

3.9Reducer 设计铁律：确定性 + 可序列化

注意 reducer 必须确定且可序列化。reducer 的输出会被 checkpointer 持久化到磁盘/数据库（用于断点续跑、时间旅行、对话记忆）。这意味着两件事：

1. 必须是确定性的。 同样的 (left, right) 必须得到完全相同的结果。不要在 reducer 里用 random、不要依赖当前时间、不要读取外部可变状态。否则恢复 checkpoint 后重放会得到不一致的状态，破坏图的正确性。

2. 结果必须可序列化。 checkpointer 用 JSON/msgpack 把 State 落盘。不要在 reducer 里返回数据库连接、文件句柄、线程锁、lambda、自定义不可序列化对象。消息对象用 LangChain 的 BaseMessage 子类（已支持序列化），普通字段用 dict/list/str/int/float 这些原生类型。

一个反面教材：

反面教材 —— reducer 里依赖时间且返回不可序列化对象
pythonimport time
from typing import Annotated

# 反面教材：千万别这么写
def bad_reducer(left: list, right: list) -> list:
    # 错误1：依赖当前时间 → 不确定，重放结果会变
    timestamp = time.time()
    # 错误2：把不可序列化的对象塞进状态 → checkpointer 落盘会失败
    return left + right + [{"ts": timestamp, "conn": open("/dev/null")}]

# class BadState(TypedDict):
#     data: Annotated[list, bad_reducer]   # 不要用
两个雷，一条边界：bad_reducer 踩了两个雷——time.time() 让每次重放结果不同（破坏确定性），open("/dev/null") 返回文件句柄无法被 JSON 序列化（checkpointer 落盘直接失败）。正确做法是：reducer 只做纯数据变换，需要「副作用」（读数据库、调 API）的逻辑放到节点函数里，节点把可序列化的结果交给 reducer 合并。这条边界是 LangGraph 状态管理的核心设计哲学——reducer 管合并，节点管计算。

先自己作答，再展开对照。

Q1 · 3.2 的陷阱里，bot 节点返回 {"messages": [AI回复]} 后历史只剩一条。如果 bot 节点改成返回 {"messages": state["messages"] + [AI回复]}（读出来拼好再整份写回），不配 reducer 能解决问题吗？会引入什么新风险？
顺序执行时能跑：每步只有一个写入，LastValue 收一个值，内容也确实是「旧历史+新消息」。但它把合并责任从框架挪回了业务代码，并在并行时刻翻车：一旦两个节点并行写 messages，两个「整份历史」撞进 LastValue 直接抛 InvalidUpdateError；即便配了 operator.add，两条「整份历史」会拼接出重复消息。正确做法仍是配 add_messages——节点只交「增量」，合并语义归字段。这也是第 1 章 Q2「更新请求而非新状态」约定的具体代价。
Q2 · Annotated[list, add_messages] 和 Annotated[list, operator.add] 都能累积，区别在哪？如果你要实现「流式刷新同一条 AI 消息」，哪个能用，哪个会出什么乱子？
add_messages 按 ID 合并：同 ID 替换、新 ID 追加，还能 RemoveMessage 删除；operator.add 是盲拼接：int 相加、list 连接，不认识 ID。流式刷新必须用 add_messages——每一步产出同 ID 的「半成品」消息，历史里那条被原地替换，长度不涨；用 operator.add 的话，每个 chunk 都会被拼进列表，历史里堆满重复的中间态，长度随流式步骤线性膨胀。
Q3 · 为什么框架检查的是「Annotated 最后一个 metadata 是不是双位置参数的可调用对象」（_is_field_binop），而不是随便哪个参数位置？这排除了什么误挂？
约定取最后一个 metadata：这是「reducer 写在注解末位」的固定语法，检查两个位置参数是签名门槛——reducer 会在 update 循环里以 (旧值， 新值) 调用（binop.py:143），签名不符到运行时才炸，编译期先筛掉。它排除了两类误挂：把单参数函数（如 len）或带 keyword-only 参数的函数当 reducer——前者调用时参数个数对不上，后者不符合二元纯函数契约。EphemeralValue 这类 BaseChannel 实例走的是 _is_field_channel 分支（state.py:1850），不会进这条判定。
Q4 · Pydantic 版 State 在 invoke 返回的是普通 dict。为什么框架不返回模型实例？入口校验和「内部存储格式」是什么关系？
内部存储层是 channel 盒子，落盘走 checkpointer 的 JSON/msgpack 序列化——存的从来都是可序列化数据，不是对象引用。Pydantic 模型只在入口做一次校验/默认值填充，校验通过后拆成普通 dict 进通道；输出时同样组装回 dict。这样校验能力（入口严）和执行效率（内部无模型包装、可序列化、可恢复）互不妨碍。代价是节点内拿不到 Pydantic 的字段校验，那是入口的事。
Q5 · 3.9 说 reducer 必须「确定性 + 可序列化」。reducer 之外，节点函数呢——节点里能不能调数据库？结合「reducer 管合并，节点管计算」这条边界说说理由。
节点可以调数据库/API，那是「计算」，本来就该在节点里；但节点返回给 reducer 合并的值必须可序列化。reducer 不行：它会被 checkpointer 的重放机制反复调用（时间旅行、断点恢复都靠重放写入记录），调外部服务既不确定也无法在恢复时复现。所以边界画在「副作用与纯函数」之间：副作用进节点，合并进 reducer；节点产出纯数据，reducer 只做纯变换。破坏这条线，恢复重放就是第一受害者。
