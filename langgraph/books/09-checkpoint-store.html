持久化记忆:Checkpointer 与 Store

LangGraph 用两层记忆模型分别解决"单次对话"和"跨会话长期记忆"——Checkpointer 按 thread_id 存状态快照,Store 按 namespace + key 存共享数据,理解它们的边界是自建生产级 Agent 的关键一步。

9.1两层记忆:为什么不是一个笼统的"记忆"

一个 Agent 跑起来之后,最常被问到的两个工程问题是:"它能记住我上句话吗?"和"它能记住我是谁吗?"。听起来都像"记忆",但这两件事的作用域完全不同:前者属于一次会话内部的上下文累积,后者属于跨多次会话的用户档案。LangGraph 没有把它们塞进一个笼统的"记忆"概念里,而是拆成了两个正交的抽象——Checkpointer(短期 / 会话记忆)和 Store(长期 / 跨会话记忆)。这种分离本身就是一种设计取舍,我们在选型时也应该照着这个边界去划分自己的数据。

图 9.1:Checkpointer 按 thread_id 分桶,每个 thread 是一条独立状态链;Store 是全局命名空间键值库,任何 thread 都能按 (namespace, key) 读写同一份数据。

上图是核心区分:Checkpointer 按 thread_id 分桶,每个 thread 是一条独立的状态链,彼此完全隔离;而 Store 是一个全局的命名空间键值库,任何 thread、任何节点都能按 (namespace, key) 读写同一份数据。一个管"这次会话走到哪了",一个管"这个用户是谁、喜欢什么"。

9.2Checkpointer:短期 / 会话记忆

Checkpointer 的职责是:在图执行的每个 superstep 之后,把当前完整状态(channel 值、版本、pending writes)做一次快照,按 thread_id 存起来。它是在 compile(checkpointer=...) 时挂上去的,挂上之后你必须在 invoke 时传入 thread_id——否则它不知道把快照存到哪个桶里。

thread_id = 会话的身份证
pythonfrom typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver   # 仅用于测试/开发
from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[list, add_messages]   # add_messages: 追加而非覆盖

def chatbot(state: State) -> State:
    # 这里简化为回显;真实场景里会调 LLM
    last = state["messages"][-1].content
    return {"messages": [{"role": "assistant", "content": f"你说的是: {last}"}]}

builder = StateGraph(State)
builder.add_node("chatbot", chatbot)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)

# 启用 checkpointer: 之后每次 invoke 都要带 thread_id
graph = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "thread-1"}}

# 第一轮: 用户说话 -> 存入 thread-1 的状态链
graph.invoke({"messages": [{"role": "user", "content": "你好"}]}, config)

# 第二轮: 同一个 thread_id, 框架自动加载上一轮的状态(含历史消息)
graph.invoke({"messages": [{"role": "user", "content": "我刚才说了什么?"}]}, config)

# 换一个 thread_id = 全新会话, 看不到 thread-1 的历史
new_config = {"configurable": {"thread_id": "thread-2"}}
state2 = graph.get_state(new_config)
print(state2.values)   # -> {}  (空状态, 新会话从零开始)
读懂这段: thread_id 的本质就是"会话"的身份证。同一个 thread_id 多次 invoke,状态(这里是消息列表)会在 reducer(add_messages)作用下不断累积——这就是"多轮对话记忆"的全部秘密,没有魔法,就是"按 key 存取 + 每次加载"。换了 thread_id,就是开了一个全新会话,对之前的对话一无所知。

那么该选哪种 Checkpointer 实现?本代码库提供了三种,对应不同部署阶段:

  • InMemorySaver(langgraph.checkpoint.memory):数据存在进程内存,进程退出即丢。源码 docstring 写着"Only use for debugging or testing purposes"。仅用于测试/开发。
  • SqliteSaver(langgraph.checkpoint.sqlite,本仓库 libs/checkpoint-sqlite):落本地文件,单机、轻量,适合 Demo。注意它"does not scale to multiple threads",要并发请用 AsyncSqliteSaver 或上 Postgres。
  • PostgresSaver / AsyncPostgresSaver(langgraph.checkpoint.postgres,本仓库 libs/checkpoint-postgres):生产推荐,支持并发连接池与 pipeline。需要单独安装。
三种 Checkpointer 实现
python# SqliteSaver: 本地文件, 适合单机 Demo
import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver

# 方式一: 自己管理连接(check_same_thread=False 是必须的)
conn = sqlite3.connect("checkpoints.sqlite", check_same_thread=False)
checkpointer = SqliteSaver(conn)

# 方式二: 用上下文管理器, 自动开关连接
with SqliteSaver.from_conn_string("checkpoints.sqlite") as checkpointer:
    graph = builder.compile(checkpointer=checkpointer)
    # ... invoke ...

# PostgresSaver: 生产环境(需先 pip install langgraph-checkpoint-postgres)
from langgraph.checkpoint.postgres import PostgresSaver

DB_URI = "postgresql://postgres:postgres@localhost:5432/langgraph?sslmode=disable"
with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    checkpointer.setup()   # 首次使用必须调用: 建表 + 跑迁移
    graph = builder.compile(checkpointer=checkpointer)
    # ... invoke ...
PostgresSaver.setup() 不能忘 看源码,PostgresSaver.setup() 会创建 checkpoints、writes 等表并执行版本迁移,它的 docstring 明确写着"MUST be called directly by the user the first time checkpointer is used"。而 SqliteSaver.setup() 是在被调用时自动触发的——这是两个实现的一个细节差异,部署时容易踩坑。

9.3Store:长期 / 跨会话记忆

Checkpointer 的作用域是单个 thread——它天生看不到别的 thread。但很多场景需要跨 thread 共享数据:用户偏好、长期档案、知识库片段。这些数据不该塞进某个会话的状态里(否则换会话就丢了),于是有了 Store。Store 是一个全局命名空间键值库,在 compile(store=...) 时挂上,节点里通过注入的 store 参数按 (namespace_tuple, key) 存取。

关键在于 namespace 是一个元组,能天然表达层级,比如 ("user", user_id)。这样"记住用户偏好"就变成:在节点里 store.put(("user", user_id), "prefs", {...}),之后哪怕换了 thread_id,只要拿到同一个 user_id 就能 store.get(("user", user_id), "prefs") 取出来——真正实现了"跨会话记忆"。

Store 实现跨会话用户偏好
pythonfrom typing import Annotated
from typing_extensions import TypedDict
from langchain_core.runnables import RunnableConfig
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore
from langgraph.store.base import BaseStore
from langgraph.graph.message import add_messages

class State(TypedDict):
    user_id: str
    messages: Annotated[list, add_messages]
    response: str

def assistant(state: State, config: RunnableConfig, store: BaseStore) -> State:
    user_id = state["user_id"]
    # 1. 从 Store 读这个用户的长期偏好(跨会话!)
    item = store.get(("user", user_id), "prefs")
    prefs = item.value if item else {"lang": "zh"}

    # 2. 基于偏好生成回复(这里简化)
    last = state["messages"][-1]["content"]
    reply = f"[偏好 {prefs}] 收到: {last}"

    # 3. 把本次学到的偏好写回 Store —— 下次别的 thread 还能读到
    store.put(("user", user_id), "prefs", {"lang": "zh", "theme": "dark"})

    return {"response": reply}

builder = StateGraph(State)
builder.add_node("assistant", assistant)
builder.add_edge(START, "assistant")
builder.add_edge("assistant", END)

# 同时挂 checkpointer(短期) + store(长期): 两层记忆各司其职
graph = builder.compile(
    checkpointer=InMemorySaver(),
    store=InMemoryStore(),   # 生产可换 PostgresStore
)

# 会话 1: thread-1, 写入偏好
cfg1 = {"configurable": {"thread_id": "thread-1"}}
graph.invoke(
    {"user_id": "u-42", "messages": [{"role": "user", "content": "我喜欢深色主题"}]},
    cfg1,
)

# 会话 2: 换了 thread_id, 但同一个 user_id —— Store 里的偏好还在!
cfg2 = {"configurable": {"thread_id": "thread-2"}}
result = graph.invoke(
    {"user_id": "u-42", "messages": [{"role": "user", "content": "你好"}]},
    cfg2,
)
# result["response"] 里会带上刚才写入的 {lang: zh, theme: dark}
读懂这段: 节点签名 def assistant(state, config, store: BaseStore)——LangGraph 会按参数名注入已挂载的 store。这一点在本仓库的节点协议 langgraph/graph/_node.py 里有明确定义:store: BaseStore 是可注入的形参。除了 store,还可以注入 config、writer: StreamWriter,或通过 runtime: Runtime 拿到 runtime.store。
为什么 Store 用 namespace 元组 看 InMemoryStore 的实现,内部数据结构是 dict[tuple[str,...], dict[str, Item]]——按 namespace 分桶、桶内按 key 取值。元组天然是层级路径,既能做精确存取 ("user","42"),也能用 search(("user",)) 按前缀批量检索某用户下的所有条目。这比扁平的字符串 key 表达力强得多,也和 Postgres 的 JSONB 前缀匹配语义对齐,从内存实现平滑迁移到数据库几乎不用改业务代码。

Store 的语义检索:不止是键值,还能向量搜索

上面演示的 get/put 是精确存取,但 Store 还有一项更强的能力:语义搜索。源码里 BaseStore(在 libs/checkpoint/langgraph/store/base/__init__.py)的 search 方法支持 query 参数——传入一段自然语言,它会按向量相似度返回匹配的条目。这让 Store 能直接当"长期记忆库 / RAG 知识库"用,不用再外挂一个向量库。

要开启语义搜索,创建 Store 时传 index 配置(见 InMemoryStore 实现):

Store 语义搜索:把长期记忆变成可检索的知识库
pythonfrom langgraph.store.memory import InMemoryStore

store = InMemoryStore(
    index={
        "dims": 1536,                 # 向量维度,要对齐你用的 embedding 模型
        "embed": my_embed_fn,         # 把文本转向量的函数
        "fields": ["text"],           # 对 value 里的哪些字段建索引
    },
)

# 存入若干条记忆(每个 item 的 value 含被索引的 "text" 字段)
store.put(("memories", "u-42"), "m1", {"text": "用户在研究 LangGraph 的流式输出"})
store.put(("memories", "u-42"), "m2", {"text": "用户偏好简洁的代码示例"})

# 语义检索:用自然语言 query,按相似度返回
results = store.search(
    ("memories", "u-42"),
    query="这家伙最近在折腾什么",   # 自然语言,非精确 key
    limit=3,
)
# results 按相似度排序,最相关的在前;m1 会排前面
读懂这段: index 配置三要素:dims(向量维度)、embed(embedding 函数)、fields(对 value 的哪些字段建向量索引)。search 的 query 参数一旦传入,就走语义相似度排序;不传则退化为按 namespace 前缀的普通检索。这套机制让 Store 既能做精确 KV(get/put),又能做模糊语义检索(search(query=)),是 LangGraph 把"长期记忆"和"检索增强"合并到一处的关键设计。注意 Store 的实现都在 libs/checkpoint(和 checkpointer 同库),内存版用于开发,生产可换 Postgres 版。

Runtime:Store 与上下文的统一注入

前面节点都是靠形参 store: BaseStore 单独注入 Store。除了这种"逐个注入",LangGraph 还提供一个统一容器 Runtime(源码 langgraph/runtime.py:125):Runtime[ContextT] 同时持有 .store 和 .context。节点声明形参 runtime: Runtime 就能一次性拿到这两个对象。

Runtime:Store + 上下文一起注入
pythonfrom langgraph.runtime import Runtime

# 用 context_schema 声明图的上下文类型(替代已弃用的 config_schema)
class MyContext(TypedDict):
    user_id: str
    tenant: str

builder = StateGraph(State, context_schema=MyContext)

def node(state: State, runtime: Runtime[MyContext]):
    store = runtime.store          # 挂载的 Store
    ctx = runtime.context          # 上下文(user_id, tenant 等)
    item = store.get(("user", ctx["user_id"]), "prefs")
    ...
context_schema 与 config_schema 源码 langgraph/graph/state.py:212 里 StateGraph 支持 context_schema 参数,用于声明"运行时上下文"的类型。旧的 config_schema 已被弃用,新代码用 context_schema。区分: config(RunnableConfig)仍用于传可变调用参数(如 thread_id、模型温度);context 用于传相对稳定的运行时上下文(如当前用户、租户、权限)。两者都可通过 Runtime 拿到,而 store 也归 Runtime 管——这是 LangGraph 把"运行时依赖"收敛到单一入口的设计。

9.4Checkpointer vs Store:一张表说清边界

维度Checkpointer(短期记忆)Store(长期记忆)
作用域单个 thread_id 内跨所有 thread / 全局
主键thread_id(+ checkpoint_id)(namespace_tuple, key)
存的内容图的完整状态快照(channel 值 + 版本 + writes)任意 JSON 可序列化字典
写入时机框架自动:每个 superstep 后节点里显式 store.put(...)
读取方式按 thread_id 自动加载为初始状态节点里显式 store.get/search(...)
典型用途多轮对话历史、HITL 暂停/恢复、回放重试用户档案、长期偏好、知识库、共享数据
启用方式compile(checkpointer=...)compile(store=...)
生产实现PostgresSaver / SqliteSaverPostgresStore / InMemoryStore

一个常见的误区是"用 Store 来存对话历史"。这通常不是好主意:对话历史是带时序、与图执行强绑定的状态,Checkpointer 已经在每个 superstep 自动快照了它(配合 add_messages reducer),再用 Store 手动存一遍既重复又容易和图状态不一致。反过来,用户偏好这种与单次会话无关、需要跨会话共享的数据,也不该塞进某个 thread 的状态里——会话一换就丢了。按作用域选对抽象,是这章最该带走的一条判断准则。

9.5Checkpoint 的能力:不止于"记住"

Checkpointer 的价值远不止"让对话有记忆"。因为每一步都存了完整快照,它顺带解锁了三个生产级能力:

暂停 / 恢复(人机协同 HITL)

这是 Checkpointer 存在的首要理由之一。当节点调用 interrupt() 时,框架把当前状态存入 checkpoint 后暂停执行,把控制权交回调用方;等你拿到人的输入后,用 Command(resume=...) 再次 invoke,框架从 checkpoint 加载状态、注入 resume 值、继续往下走。没有 Checkpointer,interrupt 之后进程就没了,resume 根本无从谈起——这正是第 06 章讲 HITL 的前提。

时间旅行:从历史 checkpoint 重放

因为同一个 thread 下存的是一串带 checkpoint_id 的历史快照,你可以用 get_state_history(config) 拿到这条时间线,然后挑任意一个历史点作为起点重新跑——就像"存档读档"。

时间旅行:历史快照重放
pythonfrom langgraph.checkpoint.memory import InMemorySaver

graph = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "demo"}}

# 跑几步, 每步都会产生一个 checkpoint
graph.invoke({"messages": [{"role": "user", "content": "第一步"}]}, config)
graph.invoke({"messages": [{"role": "user", "content": "第二步"}]}, config)

# get_state_history: 拿到这条 thread 的历史快照列表(从新到旧)
history = list(graph.get_state_history(config))
print(f"共 {len(history)} 个快照")
for snap in history:
    # StateSnapshot: values / next / config / metadata / created_at / parent_config
    print(snap.config["configurable"]["checkpoint_id"], snap.metadata)

# 时间旅行: 选一个历史快照, 用它的 config 作为新起点重新 invoke
# 这会从那个 checkpoint "分叉"出一条新的状态线, 不影响主线
past_config = history[-1].config   # 比如选最早的那个
graph.invoke({"messages": [{"role": "user", "content": "从过去重新走"}]}, past_config)
读懂这段: StateSnapshot 是个 NamedTuple(见 langgraph/types.py),字段包括 values(当时的状态值)、next(下一步要执行的节点)、config(含 checkpoint_id)、parent_config(父快照,用于回溯整条链)等。配合 update_state(config, values) 还能在某个历史点上手动改状态再续跑,实现"假设分析"。

容错重试

当某个节点抛异常,因为前面的步骤都已经持久化,你可以从最近一个成功的 checkpoint 恢复,而不是从头重跑整个流程。对于长链路 Agent(跑了几十步、调了多个外部工具),这一点直接决定了可用性:外部 API 偶发失败不应该让用户重来。配合 interrupt 还能在失败处停下等人介入修正,再 resume。

9.6thread_id 设计实践

thread_id 看起来是个小细节,但它直接决定了记忆的边界,值得单独说清:

  • 一个用户 + 一个会话 = 一个 thread_id:同一用户连续对话用同一个 thread_id,状态累加,实现"多轮对话记忆"。
  • 换 thread_id = 开新会话:新 thread_id 从空状态开始,看不到旧 thread 的历史。这是"重开对话"的标准做法。
  • 单次独立任务用唯一 ID:如果每次执行都是独立的一次性工作流(比如批处理一个文档),用 uuid4 这种唯一 ID,避免互相污染。
  • 跨会话记忆不要靠 thread_id:用户在 thread-A 说"我喜欢深色",thread-B 不会因为换了 thread_id 就知道——这正是 Store 要解决的问题。thread_id 管会话内,Store 管跨会话。

典型组合是:thread_id 由你的会话管理逻辑生成(比如 f"{user_id}-{session_id}"),而 user_id 同时作为 Store 的 namespace 之一(("user", user_id))。这样既保证会话内记忆隔离,又让长期偏好可共享。

图 9.2:同一用户的多个会话各自 thread_id 互不可见,但都通过 Store 共享同一份偏好。
记忆策略速查 对话历史 / 当前任务状态 / 待恢复的中断 → 用 checkpointer(靠 thread_id 累积,框架自动存取)。用户档案 / 长期偏好 / 跨会话知识库 / 多 Agent 间共享数据 → 用 store(按 namespace + key,节点里显式存取)。判据只有一条:这份数据是否需要跨 thread_id 共享?是 → Store;否 → Checkpointer。

9.7Durability:检查点到底何时落盘

前面几节一直在说"checkpointer 会存状态",但有一个更细的问题没回答:一个 super-step 内如果有多个节点,检查点是每个节点都存、还是整个 step 存一次?节点执行到一半进程崩了怎么办?这就涉及 Durability——源码里它是 Literal(见 langgraph/types.py:89):

langgraph/types.py — Durability 定义
pythonDurability = Literal["sync", "async", "exit"]
# 默认值:"async"(在 invoke/stream 时传入,不是 compile)

三种模式控制的是检查点的写入时机与保证强度。这是性能与可靠性之间的旋钮——写得越频繁,崩溃后丢的越少,但开销越大:

模式写入时机崩溃后能恢复吗开销
sync每个节点完成后同步落盘能,粒度到单个节点最高(每节点一次写)
async每个super-step完成后落盘(默认)能,但可能丢失最后未完成的 step中等
exit仅在图执行结束/中断时落盘仅中断或正常结束点可恢复最低
设置 Durability(invoke / stream 时,不是 compile)
python# durability 是运行期参数,挂在 invoke/stream 上(见 pregel/main.py 的 stream 签名)。
# 注意:compile() 不接受 durability —— 写 compile(durability="sync") 会 TypeError。
config = {"configurable": {"thread_id": "t-1"}}

graph.invoke(
    inputs,
    config,
    durability="sync",   # 本次运行:每节点落盘,最安全但最慢
)

# 也可以不传,默认 "async";或写进 config 的 configurable 里复用:
# config["configurable"]["checkpoint_during"] 已弃用,改名 durability
读懂这段: durability 是运行期参数,传给 invoke/stream,而不是 compile——源码里 CompiledStateGraph.stream() 的签名有 durability: Durability | None = None(pregel/main.py),为 None 时回落到 "async"(main.py:2602 的 config.get(...).get(CONFIG_KEY_DURABILITY, "async"))。这意味着同一段图可以按调用不同粒度落盘:敏感步骤用 "sync",日常用默认 "async"。默认 "async" 是个经过权衡的选择:它保证"已完成的 super-step 不丢",对绝大多数 Agent 场景够用——Agent 的一个 step 通常就是一个完整的推理+工具调用轮次,丢失未完成的那一步重新跑即可,代价可接受。只有当单步内有不可重做的副作用(比如 step 内调了外部付款 API)时,才需要上 "sync" 确保每节点落盘。
怎么选 默认 async 适合 95% 的场景。sync 留给"单步内有不可重做副作用"的场景。exit 适合一次性短任务、对崩溃恢复要求低(崩了重跑整个图也无所谓)。注意:要享受任何 Durability 保证,前提是配了真正的持久化 checkpointer(SQLite/Postgres)——InMemorySaver 进程一退就全没了,谈不上"耐久"。

9.8DeltaChannel:增量通道(Beta)

这是持久化体系里较新的一块。DeltaChannel 是一种特殊的 channel 类型(源码 langgraph/channels/delta.py:25),和普通 channel 不同:普通 channel 存"当前值",DeltaChannel 存增量——它内部保存一个 sentinel(哨兵)并重放(replay)写入记录,而不是直接存最终值。

它解决的问题是:流式增量语义。普通 channel 每次 update 会覆盖旧值;但有些状态字段天生是"累加"的(比如逐 token 的 LLM 输出、事件流),你希望下游拿到的是"这一步新增了什么",而不是"当前全部是什么"。DeltaChannel 让这种增量语义在 channel 层就成立。

langgraph/channels/delta.py — DeltaChannel 要点
python# 类定义(源码 delta.py:25),标注为 Beta:
class DeltaChannel(Generic[Value], BaseChannel[Any, Any, Any]):
    # 只在 checkpoint blob 里存 sentinel
    # 重建状态靠"重放祖先 writes 经过 reducer"
    # 快照节奏由两个计数器控制: per-channel 更新数 + 总 supersteps
    ...
Beta,勿用于生产 源码里 DeltaChannel 明确标注为 Beta——它的快照节奏由两个内部计数器控制,API 和行为可能变化。除非你在做底层实验或紧跟框架演进,否则暂不要在生产 StateGraph 里直接使用。理解它的存在价值在于:它解释了"为什么有些字段你看到的是增量而非全量"——这是框架为高效流式做的底层设计。

对应用层开发者,记住一句话就够:DeltaChannel 是框架内部用来支持增量流式的底层通道,Beta 阶段你不需要手动碰它。你用到的是它"上层"的能力——即第 11 章讲的 stream_mode="updates" / "messages",那些是 DeltaChannel 思想在用户侧的体现。

9.9安装与本仓库对照

Checkpointer 的不同实现是各自独立发布的包。核心抽象 BaseCheckpointSaver 在 langgraph-checkpoint(本仓库 libs/checkpoint),InMemorySaver 就在这里;SQLite 和 Postgres 实现是单独的库:

  • SQLite:随 langgraph-checkpoint-sqlite 提供,源码在 libs/checkpoint-sqlite。开箱即用,无需额外依赖。
  • Postgres:需要单独安装,源码在 libs/checkpoint-postgres。
生产实现替换
python# Postgres checkpointer 需要单独安装(psycopg 3 + 连接池)
#   pip install langgraph-checkpoint-postgres
# 该包的 pyproject.toml 声明了: psycopg>=3.2.0, psycopg-pool>=3.2.0
from langgraph.checkpoint.postgres import PostgresSaver      # 同步
from langgraph.checkpoint.postgres import AsyncPostgresSaver # 异步

# 安装后即可与 InMemorySaver 平替替换:
with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    checkpointer.setup()                 # 首次建表 + 迁移(必调)
    graph = builder.compile(checkpointer=checkpointer)

# Store 同理: InMemoryStore 用于开发, 生产换 PostgresStore
from langgraph.store.memory import InMemoryStore            # 开发/测试
# from langgraph.store.postgres import PostgresStore        # 生产(需安装)
从测试到生产:平滑替换 因为 InMemorySaver、SqliteSaver、PostgresSaver 都实现同一个 BaseCheckpointSaver 抽象(get_tuple / put / put_writes / list / delete_thread),compile(checkpointer=...) 接口完全一致——开发时用内存、联调用 SQLite、生产上 Postgres,业务代码一行都不用改。Store 这边的 InMemoryStore 和 PostgresStore 同样遵循 BaseStore 的 get/put/search/delete 契约。这种"抽象先行、实现可换"的设计,是你在自建 Agent 时也应该模仿的:把记忆后端做成可替换的依赖,而不是写死在节点里。

9.10新手常犯的错误

持久化这一章的坑几乎都集中在"我以为它存了,其实没存"和"我以为它会自动配,其实要手动调"上。下面四个都是对照本仓库源码验证过的真实报错,踩过一遍就记住了。

① 挂了 checkpointer 却忘记传 thread_id → KeyError
pythonfrom typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

class State(TypedDict):
    x: int

def add(state: State) -> State:
    return {"x": state["x"] + 1}

g = StateGraph(State).add_node("add", add).add_edge(START, "add").add_edge("add", END).compile(checkpointer=InMemorySaver())

# ✗ 挂了 checkpointer, 却没带 thread_id —— 框架不知道往哪个桶存
g.invoke({"x": 1})
# KeyError: 'thread_id'
# 追踪: _loop.py 的 __enter__ 调 checkpointer.get_tuple(config),
# InMemorySaver.get_tuple 里直接 config["configurable"]["thread_id"] 取值,缺键即 KeyError。
#
# ✓ 挂了 checkpointer 就一定要带 thread_id:
cfg = {"configurable": {"thread_id": "t-1"}}
g.invoke({"x": 1}, cfg)   # 正常
踩坑点: 没有 checkpointer 时 invoke 不需要 thread_id;一旦 compile(checkpointer=...),每次调用都必须带。报错是一个裸的 KeyError,不是友好提示,新人容易误以为是别的 bug。
② PostgresSaver 忘记调 setup() → 表不存在
pythonfrom langgraph.checkpoint.postgres import PostgresSaver

# ✗ 直接拿来 compile, 没调 setup()
with PostgresSaver.from_conn_string(DB_URI) as ckpt:
    g = builder.compile(checkpointer=ckpt)
    g.invoke(inputs, {"configurable": {"thread_id": "t-1"}})
    # psycopg.errors.UndefinedTable: relation "checkpoints" does not exist
    # 因为 put() 会跑 UPSERT_CHECKPOINTS_SQL, 而建表的 setup() 没执行过。
    #
    # ✓ 首次必须显式调 setup()(docstring: "MUST be called directly by the user"):
    with PostgresSaver.from_conn_string(DB_URI) as ckpt:
        ckpt.setup()          # 建 checkpoints/writes/blobs 表 + 跑迁移
        g = builder.compile(checkpointer=ckpt)
踩坑点: SqliteSaver.setup() 是被调用时自动触发的(docstring 明说"called automatically when needed"),所以 SQLite 从不报这个错;但 PostgresSaver.setup() 必须用户手动调。两套实现的细节差异,是部署从 SQLite 切到 Postgres 时最常踩的坑。
③ 拿 InMemorySaver / InMemoryStore 上生产 → 重启即清零
python# ✗ 生产环境用内存版, 进程一重启, 所有 checkpoint / 长期记忆全没
graph = builder.compile(checkpointer=InMemorySaver(), store=InMemoryStore())
# InMemorySaver docstring: "Only use for debugging or testing purposes."
# InMemoryStore docstring: "Data is lost when the process exits."
#
# ✓ 生产换持久化实现(接口一致, 业务代码不改):
graph = builder.compile(
    checkpointer=PostgresSaver.from_conn_string(DB_URI),  # 或 SqliteSaver(单机)
    store=InMemoryStore(),   # 长期记忆: 生产换 PostgresStore
)
踩坑点: 内存版在开发联调时一切正常(速度快、零配置),容易直接带进生产。判断准则:这份数据进程重启后还要不要?要,就必须用 SqliteSaver/PostgresSaver 等落盘实现。两者实现同一个 BaseCheckpointSaver 接口,替换只改 compile(checkpointer=...) 这一行。
④ Store 的 namespace 不能带点号、也不能为空
pythonstore.put(("user.42",), "prefs", {"theme": "dark"})   # ✗ label 里有 '.'
# InvalidNamespaceError: Invalid namespace label 'user.42' ... cannot contain periods ('.').

store.put((), "prefs", {"theme": "dark"})          # ✗ 空 namespace
# InvalidNamespaceError: Namespace cannot be empty.
#
# ✓ 用元组分层, 每段都是纯字符串、无点号:
store.put(("user", "42"), "prefs", {"theme": "dark"})
踩坑点: 点号被保留给 Postgres 实现里的路径/前缀匹配语义,所以 label 内禁用;空 namespace 也不行。这条校验在 store/base/__init__.py 的 _validate_namespace 里,所有 Store 实现共享。想用 user.id 这种复合 key,拆成元组 ("user", "42") 才是正确姿势。
