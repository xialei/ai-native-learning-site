多智能体：Supervisor、层级与 Swarm

当单个 agent 装不下你的任务时，把它拆成多个分工的子 agent。本章拆解 LangGraph 编排多智能体的三种主流架构，以及它们共同的技术基础——「子图即节点」。

7.1何时需要多智能体

大多数任务用一个 agent + 几个好工具就能解决。不要为了「多」而多。引入多智能体通常是因为出现了下面三种信号之一：

  • 工具太多导致 prompt 膨胀：一个 agent 绑了 30 个工具，LLM 在工具选择上频繁出错、context 也被工具描述塞满。把工具按职责分组，每个子 agent 只看到自己那 5~8 个工具，准确率反而上升。
  • 需要不同角色或不同模型：一个 agent 既要做检索又要写代码，而检索用便宜模型、写代码用强模型。把不同职责拆给不同 agent，各自挂最合适的模型，prompt 也更聚焦。
  • 需要并行：一份文档要让「摘要 agent」「翻译 agent」「抽词 agent」同时处理，或者要同时调研 N 个子问题再汇总。并行天然要求多个独立执行单元。

注意这三条都是「职责/工具确实需要分离」的硬信号。如果只是「想让系统看起来更高级」而拆分，反而会引入额外的协调开销和状态传递复杂度。

不要过早引入多智能体 先问自己：单 agent + 好工具能否解决？把工具描述写精、prompt 调好，往往比拆成多 agent 更简单也更可控。只有当工具/职责确实需要分离、或确实需要并行时，再上多 agent。而一旦决定上，Supervisor 是最稳妥的起点——它可控性最高，后续也最容易演进成层级或 Swarm。

7.2三种主流架构模式

多智能体的拓扑千变万化，但归结下来就三种基本范式：Supervisor（主管）、Hierarchical（层级）、Swarm（群集/接力）。它们的区别本质上是「控制权在哪里」。

1. Supervisor 主管模式：中央调度

一个 supervisor 节点充当「调度员」：它看着当前状态，决定下一步调用哪个 worker agent;worker 执行完回到 supervisor，由它再决定继续派活还是结束。这是最常用、最可控的形态——所有跨 agent 的协调都经过一个点，便于观测和加审核。

图 7.1：Supervisor 中央调度——所有 worker 执行完都回到 supervisor 再决策，控制权始终在一个点上。

在 LangGraph 里，最直接的实现方式是：每个 worker 用 create_react_agent 包成一个独立子图（它本身是一个 CompiledStateGraph），再把这些子图作为节点 add_node 进外层图；supervisor 节点是一个调 LLM 的函数，返回 Command(goto=..., update=...) 同时指定下一跳并写入状态。

Supervisor 模式：子图即节点 + Command 路由
pythonfrom typing import Annotated, Literal
from typing_extensions import TypedDict
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import create_react_agent
from langgraph.types import Command

# --- 共享状态：所有 agent 通过它通信 ---
class State(TypedDict):
    messages: Annotated[list, add_messages]
    next: str   # supervisor 决定的下一跳

model = ChatOpenAI(model="gpt-4o-mini")

def search_tool(city: str) -> str:
    """查询城市天气。"""
    return f"{city} 今天晴， 22°C"

def python_repl(code: str) -> str:
    """执行一段 Python 代码并返回结果。"""
    return f"执行结果： {eval(code)}"

# 检索 agent 只看到检索类工具；编码 agent 只看到编码工具
researcher = create_react_agent(model, tools=[search_tool], name="researcher")
coder = create_react_agent(model, tools=[python_repl], name="coder")

# --- Supervisor：用 LLM 在 worker 间路由 ---
def supervisor(state: State) -> Command[Literal["researcher", "coder", "__end__"]]:
    decision = model.invoke([
        {"role": "system", "content": "你是调度员。根据用户需求决定下一步：'researcher'(查资料)、'coder'(写代码)或 'FINISH'(完成)。只回这个词。"},
        *state["messages"],
    ])
    choice = decision.content.strip()
    goto = "FINISH" if choice == "FINISH" else choice
    return Command(goto=goto, update={"next": goto})

# --- 组装外层图 ---
builder = StateGraph(State)
builder.add_node("supervisor", supervisor)
builder.add_node("researcher", researcher)   # 子图即节点
builder.add_node("coder", coder)
builder.add_edge(START, "supervisor")
builder.add_edge("researcher", "supervisor")  # 跑完回 supervisor
builder.add_edge("coder", "supervisor")

graph = builder.compile()
result = graph.invoke({"messages": [{"role": "user", "content": "北京天气怎么样？"}]})
print(result["messages"][-1].content)
读懂这段： supervisor 返回的 Command(goto=..., update=...) 把「决策」和「写状态」合在一步——这是 Command 的核心价值，无需为 supervisor 单独画条件边。goto 的类型注解 Literal["researcher", "coder", "__end__"] 既给编辑器看，也让 LangGraph 据此渲染出完整的分支拓扑。

2. Hierarchical 层级模式：树状分解

当任务复杂到一层 supervisor 管不过来——比如「做一份市场调研报告」要拆成「数据收集」「分析」「写作」三大块，而每块内部又有多个子 agent——就给 supervisor 之上再叠 supervisor，形成树。每一层 supervisor 只管理自己那一组子 agent，把子任务的结果汇报给上一层。

图 7.2：层级模式——「supervisor + 子 agent」这一组本身就是一个子图，把它作为节点放进更外层的图，递归下去就是任意深度。

层级模式的技术实现和 Supervisor 完全一样——「supervisor + 子 agent」这一组本身就是一个子图，把这个子图作为节点放进更外层的图，就形成了第二层。递归下去就是任意深度。下面是把一组「调研 supervisor」整体打包成节点的示意：

层级模式：把内层子图当节点塞进外层
pythonfrom typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command

class TeamState(TypedDict):
    task: str
    results: list[str]

# --- 内层：调研组(supervisor + 两个 worker)，整体编译成一个子图 ---
inner = StateGraph(TeamState)
# ... 省略 inner 的 supervisor 与 worker 定义，结构同上一节 ...
inner_graph = inner.compile()

# --- 外层：顶层 supervisor 把"调研""写作"两组当作节点 ---
class RootState(TypedDict):
    task: str
    research: list[str]
    draft: list[str]

def root_supervisor(state: RootState) -> Command:
    if not state.get("research"):
        return Command(goto="research_team", update={"task": state["task"]})
    if not state.get("draft"):
        return Command(goto="writing_team", update={"task": state["task"]})
    return Command(goto=END)

root = StateGraph(RootState)
root.add_node("root_supervisor", root_supervisor)
root.add_node("research_team", inner_graph)   # 内层编译好的图当节点
root.add_node("writing_team", inner_graph)      # 实际中写作组是另一个 inner_graph
root.add_edge(START, "root_supervisor")
root.add_edge("research_team", "root_supervisor")
root.add_edge("writing_team", "root_supervisor")
top_graph = root.compile()

层级的代价是调试复杂度随深度上升：一次顶层调用可能触发多层嵌套的子图执行，流式输出和 checkpoint 的层级关系会变深。实践上两到三层通常是上限，再深就该考虑是否任务本身可以重新切分。

3. Swarm 群集/接力模式：直接交接

Swarm 没有「中央调度员」。每个 agent 自己判断「这件事我还能不能继续做，不能就交给谁」，通过共享 state 直接把控制权 handoff 给下一个 agent。这适合线性流水线（A 做完交给 B,B 做完交给 C）或动态切换（根据当前状态决定下一步该谁接手，但没有一个独立的调度节点）。

图 7.3：Swarm 接力——每个 agent 结束前返回 Command(goto="下一个 agent")，无中央调度节点。

在 LangGraph 里，Swarm 的实现方式是让每个 agent 节点在结束前返回 Command(goto="下一个 agent", update={...})。交接的「信号」通常是一条带特殊标记的 message，下一个 agent 从共享的 messages 里读到上下文继续。下面是一个最小接力示例：

Swarm:用 Command 在 agent 间接力
pythonfrom typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.types import Command

class State(TypedDict):
    messages: Annotated[list, add_messages]
    query: str

def researcher(state: State) -> Command:
    finding = f"关于 '{state['query']}' 的检索结果： ..."
    return Command(
        goto="coder",
        update={"messages": [{"role": "user", "content": f"基于以下资料写代码： {finding}"}]},
    )

def coder(state: State) -> Command:
    return Command(
        goto=END,
        update={"messages": [{"role": "assistant", "content": "代码已写好： ..."}]},
    )

builder = StateGraph(State)
builder.add_node("researcher", researcher)
builder.add_node("coder", coder)
builder.add_edge(START, "researcher")  # 之后全靠 Command 接力
graph = builder.compile()

Swarm 的优点是没有单点调度开销，每个 agent 只关心「我之后交给谁」，很适合职责清晰、流向确定的流水线。代价是全局可控性下降——没有一处能看到全貌，要追踪流程得顺着每个 agent 的 handoff 逻辑一路读下去。当交接规则变复杂（比如 A 可能给 B 也可能给 C）时，Swarm 会迅速退化成「隐式的 supervisor」，这时不如显式用 Supervisor 模式。

7.3子图即节点：多智能体的技术基础

上面三种模式能成立，都依赖 LangGraph 的一个核心设计：任何 CompiledStateGraph 都可以作为另一个图的节点。create_react_agent 返回的是 CompiledStateGraph，手写的 builder.compile() 也是，所以它们都能直接 add_node 进外层图。

这里有一个必须理解的关键点：state schema 的兼容。子图可以有自己的 schema，不必和父图完全一致——父图调用子图时，会按字段名做输入/输出映射，同名字段自动传递，子图里没有的字段被忽略。这就允许每个 agent 拥有自己专属的状态字段，同时通过共享字段（通常是 messages）与外层通信。

schema 映射：同名字段自动传递
pythonfrom typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

# 父图状态：只关心 messages
class ParentState(TypedDict):
    messages: Annotated[list, add_messages]

# 子图状态：有专属字段 notes，但也有 messages 用来与父图对接
class ChildState(TypedDict):
    messages: Annotated[list, add_messages]
    notes: list[str]   # 子图专用，父图看不到

def child_node(state: ChildState):
    return {"messages": [{"role": "assistant", "content": "子图处理完毕"}]}

child_builder = StateGraph(ChildState)
child_builder.add_node("child_node", child_node)
child_builder.add_edge(START, "child_node")
child_builder.add_edge("child_node", END)
child_graph = child_builder.compile()

# 父图：把子图当作一个普通节点
parent = StateGraph(ParentState)
parent.add_node("child", child_graph)   # 子图即节点
parent.add_edge(START, "child")
parent.add_edge("child", END)
parent_graph = parent.compile()

result = parent_graph.invoke({"messages": [{"role": "user", "content": "hi"}]})
print(result["messages"][-1]["content"])  # 子图处理完毕

这种「子图即节点 + schema 映射」的设计是多智能体可组合性的根基。它意味着你可以先把每个 agent 当独立图开发、测试，再像搭积木一样拼进更大的编排图，而不必为「agent 之间怎么嵌套」写特殊胶水代码。

7.4通信机制

多智能体之间怎么传信息？LangGraph 提供三条路径，按「作用域」从近到远排列：

  • 共享 state:最基本的方式。所有 agent 读写同一个 state（通常是 messages 列表），一个 agent 写入后，下一个 agent 自然读到。字段合并由 reducer 决定——add_messages 是追加，operator.add 是列表拼接。
  • Command(goto=, update=):在指定下一跳的同时写入状态。这是 Supervisor / Swarm 模式里 supervisor 和 worker 之间的标准通信方式——「去 researcher 那儿，顺便把这条指令带上」。
  • Command(graph=Command.PARENT, goto=...):从子图向父图发指令。子图内部的节点可以「越级」告诉父图下一步去哪，而不是只回到自己的直接调用者。这是层级模式下实现「跨层跳转」的关键。
Command.PARENT:子图向父图发跳转指令
pythonfrom typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command

class ParentState(TypedDict):
    done: bool

class ChildState(TypedDict):
    jump: bool

def child_node(state: ChildState):
    if state["jump"]:
        # graph=Command.PARENT： 这条 goto 是给父图的，不是给当前子图的
        # 源码 state.py:1761 见到 PARENT 会 raise ParentCommand， 由父图执行栈捕获并改道
        return Command(graph=Command.PARENT, goto="parent_final")
    return {}

child = StateGraph(ChildState)
child.add_node("child_node", child_node)
child.add_edge(START, "child_node")
child_graph = child.compile()

def parent_final(state: ParentState):
    return {"done": True}

# 关键： 子图必须作为节点 add_node 进父图(而不是在某个节点里手动 .invoke()),
# 这样父图的执行栈才会捕获子图抛上来的 ParentCommand 并改道。
parent = StateGraph(ParentState)
parent.add_node("child", child_graph)        # 子图即节点(正确姿势)
parent.add_node("parent_final", parent_final)
parent.add_edge(START, "child")
parent.add_edge("parent_final", END)
parent_graph = parent.compile()

parent_graph.invoke({"done": True})  # child 收到 jump=True， 向父图发 PARENT goto=parent_final

Command.PARENT 让子图拥有「向上反馈」的能力，而不必把决策全堆在父图里。但要用得克制——跨层跳转多了，控制流会变得难以追踪。原则上，层内的协调用普通 Command(goto=...)，只有「子任务提前完成、需要父图改道」这类确有必要的情况才用 Command.PARENT。

Command.PARENT 只在「子图作为节点」时生效 上面子图是通过 parent.add_node("child", child_graph) 挂进父图的——这是 Command.PARENT 能工作的前提。源码 _retry.py 里，只有当子图作为父图的一个节点执行时，父图执行栈才会 except ParentCommand 捕获子图抛上来的跳转指令并改道。如果你换成在某个节点里手动 child_graph.invoke(...) 调子图，那 ParentCommand 没有外层栈去接，会直接冒泡成异常（_io.py 的 map_command 在无父图时 raise InvalidUpdateError("There is no parent graph")）——达不到改道效果。结论：Command.PARENT 走的是图执行栈，不是普通函数调用。

7.5三种模式对比

维度Supervisor 主管Hierarchical 层级Swarm 群集/接力
控制方式中央 supervisor 统一调度多层 supervisor 树状分解agent 间直接 handoff，无中央
可控性高（单点观测、易加审核）中（需逐层追踪）低（全局流程隐藏在各 agent 内）
扩展性worker 多了 supervisor 成瓶颈可承载复杂任务，但深度有限线性扩展好，分支多了难管理
通信开销每次都要过 supervisor跨层通信成本高点对点，开销最小
适用场景职责可清晰分组、需要可控调度任务可树状分解、多阶段多角色线性流水线、动态切换主导 agent
演进建议最稳妥起点Supervisor 不够用时再叠层流向确定且无需中央审核时

实际工程里这三种并非互斥，常常混用：用 Supervisor 做顶层调度，某个 worker 内部本身又是 Swarm 流水线；或用层级分解，叶子节点用 create_react_agent 直接当 worker。关键是先想清楚「控制权该集中还是分散」，再选对应拓扑。

7.6落地清单

  • 先确认单 agent 真的装不下——工具数 > 15、或需要不同模型、或需要并行，才是多 agent 的硬信号。
  • 从 Supervisor 起步：worker 用 create_react_agent，supervisor 用 Command(goto=...) 路由。这是可控性最高、也最容易后续演进的结构。
  • 定义清晰的共享 state（通常以 messages 为枢纽），让 agent 间的信息流转有明确的载体，而不是靠隐式约定。
  • 子图即节点：把每个 agent 当独立图开发测试，再 add_node 拼装；注意 schema 同名字段自动映射，专属字段不会泄漏到父图。
  • 只在确有必要时用 Command(graph=Command.PARENT, goto=...) 做跨层跳转，避免控制流失控。

7.7新手常犯的错误

多智能体的坑大多不在「图跑不起来」，而在「图跑起来了但 agent 之间没接上」。下面三个都是对照本仓库源码验证过的，属于「能编译、能跑、但结果不对」的静默错误或半静默错误。

① 自定义 worker 的 state_schema 漏掉 messages → ValueError
pythonfrom typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph.message import add_messages
from langgraph.prebuilt import create_react_agent

# ✗ 想给 worker 加专属字段， 但忘了 messages / remaining_steps
class MyWorkerState(TypedDict):
    notes: Annotated[list[str], add_messages]   # 只有 notes， 没 messages

agent = create_react_agent(model, tools=[...], state_schema=MyWorkerState)
# ValueError: Missing required key(s) {'messages', 'remaining_steps'} in state_schema
# 源码 chat_agent_executor.py:545 校验： 自定义 schema 必须含 messages + remaining_steps
#
# ✓ 自定义 schema 必须继承或显式带上这两个键：
class MyWorkerState(TypedDict):
    messages: Annotated[list, add_messages]
    remaining_steps: int
    notes: Annotated[list[str], add_messages]   # 专属字段
踩坑点： create_react_agent 默认用内置 AgentState（含 messages），一旦传 state_schema 覆盖，框架就不再自动补 messages，你得自己保证 schema 里有 messages 和 remaining_steps。漏了会直接报错（还算友好）；更隐蔽的是字段名拼错——父图的 messages 和子图的 msgs 不同名，schema 映射时不会自动传，worker 收不到历史消息却不会报错，表现为「agent 像失忆了」。
② Command（goto=...） 的目标没写进 Literal → 边缺失、可静态分析性丢失
pythonfrom typing import Literal
from langgraph.types import Command

# ✗ supervisor 可能 goto "reviewer"， 但 Literal 里没列它
def supervisor(state) -> Command[Literal["researcher", "coder", "__end__"]]:
    return Command(goto="reviewer", update={...})   # reviewer 不在 Literal 里！
# 源码 state.py:850-856： 分支边(ends)从返回类型 Literal 反推注册。
# Literal 里没有 "reviewer" → 图拓扑里没有 coder→reviewer 这条边。
# 但注意：运行时仍会路由成功！goto 在 _io.py:69 变成对 branch:to:reviewer
# 通道的写，目标节点是已注册节点时照常执行（实测验证）。
# 代价在别处： mermaid 拓扑图少边、checkpointer 断点续跑受影响、
# 以及如果 goto 了一个完全没注册的节点名（如拼错），
# 只会在运行时看到一条 warning：
#   "Task coder ... wrote to unknown channel branch:to:ghost, ignoring it."
#   （_algo.py:312）——节点被静默跳过， 图提前结束。
#
# ✓ goto 的所有可能目标都要进 Literal 注解：

踩坑点： 先说实测结论（很多教程把这条坑讲反了）：Command(goto="X") 的 X 不在 Literal 里也能路由成功——前提是 X 是一个已注册节点。机制是：goto 在运行时被 map_command 转成对 branch:to:X 通道的写入，进而调度 X 节点；这条路不查 Literal。那 Literal 到底管什么？它决定图拓扑——Literal 的值被设为 ends，静态注册 coder→X 的条件边：漏写后 get_graph()/mermaid 里少这条边，可视化、静态校验都会失真。而真正的静默炸弹是goto 一个没注册的节点名（拼错、删了节点忘改）：不会抛 InvalidUpdateError，只会打一条 warning 然后跳过——图「无声地」提前结束。所以纪律是两条：Literal 要列全（为了拓扑完整性）；上线前跑一遍冒烟测试（防止 goto 目标拼错时只有 warning 没有异常）。锚点：map_command 在 _io.py:69、ends 注册在 state.py:850-856、warning 在 _algo.py:312。
