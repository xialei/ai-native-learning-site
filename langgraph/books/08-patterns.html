经典模式:在 ReAct 骨架上加反思、规划与纠错

Reflection、Reflexion、Plan-and-Execute、四种 RAG 变体——这些被反复引用的 Agent 模式,本质上都是在基础 ReAct 循环(第 05 章)的基础上,再插入几个"反思 / 规划 / 纠错"节点和回边。本章基于本代码库 examples 目录的 notebook 模式,逐个拆开讲清"为什么这样设计",帮你在自建与选型时知道该套哪一套。

8.1一个心智锚点:这些都是 ReAct 的变体

关于 examples 目录 本代码库 examples/reflection、examples/reflexion、examples/plan-and-execute、examples/rag/ 下的 notebook 现在是归档占位文件(指向已合并到 LangChain 文档的教程),但它们记录的图结构、state schema、节点职责划分是真实且稳定的。本章把这些模式用 LangGraph 1.x 的 StateGraph / Command / Send 重新写成可运行骨架,直接对应当前 API。

阅读前请先记住一个心智锚点:第 05 章的 ReAct 是"agent 节点 ↔ tools 节点"的二人转。本章所有模式做的事,都可以概括成一句话——在这二人转里再加一个或几个节点,并在节点之间加条件边和回边,把单向循环变成带反馈的多循环。掌握了第 04 章的控制流原语,组合这些模式是自然的。

8.2Reflection(反思):生成 → 评估 → 再生成

Reflection 解决的问题是:LLM 第一遍写出来的东西往往不够好。与其让人来挑刺,不如再请一个"评估者"节点专门挑刺,把批评意见喂回去让生成者改,循环几轮直到评估者说"可以了"。

为什么不让同一个 LLM 调用"又写又评"?因为生成和评估是两种相反的认知方向:生成要发散,评估要收敛。把它们拆成两个节点(甚至两个不同的 prompt / 模型),各自专注一件事,效果比一个节点包揽要好——这是"分工"在图层面的体现。两个节点之间用条件边控制循环次数,这是 ReAct 之外最简单的一种"反馈循环"。

图 8.1:Reflection——generator 与 reflector 两节点循环,评估不过就回到 generator 再生成,直到达标或撞循环上限。
Reflection:生成器 ↔ 评估器循环
pythonfrom typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain.chat_models import init_chat_model

# 生成器与评估者用两个不同 prompt 的模型实例
generator_llm = init_chat_model("openai:gpt-4o").with_structured_output(
    {"type": "object", "properties": {"draft": {"type": "string"}}}
)
reflector_llm = init_chat_model("openai:gpt-4o").with_structured_output(
    {"type": "object",
     "properties": {"critique": {"type": "string"},
                    "satisfactory": {"type": "boolean"}}}
)

class ReflectionState(TypedDict):
    messages: Annotated[list, add_messages]   # 原始问题 + 各轮草稿/批评
    iterations: int                            # 循环计数,用来兜底防死循环

MAX_ITER = 3  # 兜底:无论评估者怎么说,最多改 3 轮

def generator(state: ReflectionState):
    resp = generator_llm.invoke(state["messages"])
    return {"messages": [("assistant", resp["draft"])], "iterations": state["iterations"] + 1}

def reflector(state: ReflectionState):
    resp = reflector_llm.invoke(state["messages"])
    return {"messages": [("user", f"改进建议: {resp['critique']}")]}

def should_continue(state: ReflectionState):
    if state["iterations"] >= MAX_ITER:
        return END
    return "generator"   # 实际可从 messages 末尾解析 satisfactory 字段

workflow = StateGraph(ReflectionState)
workflow.add_node("generator", generator)
workflow.add_node("reflector", reflector)
workflow.add_edge(START, "generator")
workflow.add_edge("generator", "reflector")
workflow.add_conditional_edges("reflector", should_continue, {"generator": "generator", END: END})
graph = workflow.compile()
适用场景: 写作(文章 / 邮件 / 营销文案)、代码生成、翻译这类"有明确质量标准、且改一改能明显变好"的任务。注意 Reflection 的成本是每轮多一次 LLM 调用,若任务本身一次就能做好(比如简单事实问答),加反思纯属浪费——它只对"草稿质量离上限有距离"的任务划算。

8.3Reflexion:把反思沉淀成 episodic memory

Reflection 的问题在于:每一轮的批评用完就丢,下次遇到同类问题还会犯同样的错。Reflexion 的改进点是——把反思结论存进一个长期累积的 reflections 列表(state 的一部分,语义上相当于"情节记忆"),生成者每次动笔前先读这个列表,把历史教训纳入考虑。

这个设计的关键在于 reflections 用 operator.add 作为 reducer(第 03 章):每次反思节点返回一条新教训,它会被追加到列表而不是覆盖。于是状态里就形成了一条不断增长的"经验流",生成者读它时看到的是全部历史教训。这正是"记忆"在图里的实现方式——一个带累加 reducer 的 state 字段。

图 8.2:Reflexion——reflector 把教训写进 reflections(累加 reducer),generator 下次读全部历史教训再生成。
Reflexion:reflections 用 operator.add 累加
pythonimport operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain.chat_models import init_chat_model

model = init_chat_model("openai:gpt-4o")

class ReflexionState(TypedDict):
    messages: Annotated[list, add_messages]
    # 关键:reflections 用 operator.add 累加,语义上是"情节记忆"
    # 每轮 reflector 产出的教训会 append 进来,生成器下次能看到全部历史
    reflections: Annotated[list[str], operator.add]
    attempt: int

MAX_ATTEMPTS = 3

def generator(state: ReflexionState):
    lessons = "\n".join(f"- {r}" for r in state.get("reflections", []))
    sys = f"你是一个解题 agent。过往反思教训:\n{lessons}\n请避免重复同样的错误。"
    resp = model.invoke([("system", sys), *state["messages"]])
    return {"messages": [resp]}

def evaluate(state: ReflexionState):
    # 实际场景:执行代码 / 跑测试 / 用另一个 LLM 评分
    last = state["messages"][-1].content
    passed = "def " in last and "return" in last
    return {"_pass": passed}  # 临时键,实际应放进 state schema

def reflector(state: ReflexionState):
    resp = model.invoke([
        ("system", "总结这次失败的根本原因,用一句话给出可复用的教训。"),
        ("user", state["messages"][-1].content),
    ])
    return {"reflections": [resp.content], "attempt": state["attempt"] + 1}

def should_continue(state: ReflexionState):
    if state["attempt"] >= MAX_ATTEMPTS:
        return END
    return "generator"

workflow = StateGraph(ReflexionState)
workflow.add_node("generator", generator)
workflow.add_node("reflector", reflector)
workflow.add_edge(START, "generator")
workflow.add_edge("generator", "reflector")
workflow.add_conditional_edges("reflector", should_continue, {"generator": "generator", END: END})
graph = workflow.compile()
适用场景: 代码竞赛(USACO)、多步推理、智能体导航这类"会反复失败、且失败原因可复用"的任务。Reflexion 相比 Reflection 多出的价值,完全取决于"教训是否真的可复用"——如果每次失败的原因都和具体上下文强绑定、无法泛化,那 reflections 列表只会越长越干扰。所以它更适合同一会话内多次尝试同类问题的场景;跨会话的记忆要配合第 09 章的 Store 持久化。

8.4Plan-and-Execute:先规划全局,再逐步执行

ReAct 是"想一步做一步",每一步只看眼前。问题是:没有全局视野,容易在长任务里走偏、重复劳动、或漏掉关键步骤。Plan-and-Execute 把流程拆成两段——先让 planner 节点一次性生成完整的步骤列表,再让 executor 逐条执行,执行完由 re-planner 评估要不要根据新信息调整计划。

为什么 planner 用 with_structured_output 返回一个 Plan(steps: list[str])?因为计划是结构化数据(一组步骤),不是自然语言文本。用结构化输出让 LLM 直接吐 Pydantic 对象,比让它写自由文本再去正则解析稳得多。计划存在 state 的 plan 字段里,executor 每次取第一条执行,执行完把它移到 past_steps(用 operator.add 累加),re-planner 看到"已完成哪些 + 还剩哪些 + 最新观察"后决定是否重排。

图 8.3:Plan-and-Execute——planner 一次性出全局计划,executor 逐条执行,re-planner 据新信息调整剩余计划。
Plan-and-Execute:结构化计划 + 逐条执行 + 重排
pythonimport operator
from typing import Annotated
from pydantic import BaseModel, Field
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langchain.chat_models import init_chat_model

model = init_chat_model("openai:gpt-4o")

# 用结构化输出让 planner 直接吐结构化计划,而不是自由文本
class Plan(BaseModel):
    """一组可执行步骤。"""
    steps: list[str] = Field(description="按顺序执行的步骤列表")

class PlanExecuteState(TypedDict):
    input: str
    plan: list[str]                            # 当前待执行步骤
    past_steps: Annotated[list[tuple], operator.add]  # 已完成累加
    response: str                              # 最终答案

def planner(state: PlanExecuteState):
    planner_llm = model.with_structured_output(Plan)
    plan = planner_llm.invoke([
        ("system", "为用户目标制定一份分步执行计划,步骤要具体可执行。"),
        ("user", state["input"]),
    ])
    return {"plan": plan.steps}

def executor(state: PlanExecuteState):
    current_step = state["plan"][0]
    result = model.invoke([
        ("system", "执行下面这一步,给出结果。"),
        ("user", current_step),
    ]).content
    remaining = state["plan"][1:]
    return {"past_steps": [(current_step, result)], "plan": remaining}

def replanner(state: PlanExecuteState):
    replanner_llm = model.with_structured_output(Plan)
    new_plan = replanner_llm.invoke([
        ("system",
         "你是 re-planner。根据已完成的步骤和结果,判断剩余计划是否需要调整。"
         "若已能回答原始目标,返回空步骤列表;否则返回调整后的剩余步骤。"),
        ("user",
         f"目标: {state['input']}\n已完成: {state['past_steps']}\n剩余: {state['plan']}"),
    ])
    return {"plan": new_plan.steps}

def should_end(state: PlanExecuteState):
    if not state["plan"]:
        return END
    return "executor"

workflow = StateGraph(PlanExecuteState)
workflow.add_node("planner", planner)
workflow.add_node("executor", executor)
workflow.add_node("replanner", replanner)
workflow.add_edge(START, "planner")
workflow.add_edge("planner", "executor")
workflow.add_edge("executor", "replanner")
workflow.add_conditional_edges("replanner", should_end, {"executor": "executor", END: END})
graph = workflow.compile()
适用场景: 长任务(多步研究、复杂报告、多文件重构)、需要全局规划的场景、以及"前期信息不全、执行中会暴露新情况"的任务(re-planner 的价值就在这)。代价是:planner 一次生成的计划可能不准,若任务本身只需两三步,Plan-and-Execute 的开销大于 ReAct。它和 ReAct 的取舍本质是规划深度 vs 执行延迟:任务越长、步骤间耦合越紧,越值得先规划。

8.5RAG 变体:让检索更聪明、更会纠错

朴素 RAG 是"用户问 → 检索 → 拼进 prompt → 生成"的单向流水线。问题是:不是每个问题都需要检索、检索回来的文档未必相关、生成的答案未必被文档支持。下面四个变体分别从"是否检索 / 检索什么 / 如何纠错"三个维度给朴素 RAG 加反馈回路。它们的共同点:都还是 StateGraph,只是多了几个判断节点和回边。

4.1 Agentic RAG:agent 自己决定检索与否

把 retriever 封装成一个工具,交给 ReAct agent。agent 读到问题后自己判断:需不需要检索?检索什么词?检索一次不够要不要再检索?这比朴素 RAG 的"无脑检索一次"灵活得多——简单问题直接答,复杂问题多轮检索。

为什么用工具封装而不是单独写个 retrieve 节点?因为"要不要检索、检索几次"本质是 LLM 的推理决策,用 tool_calls 表达最自然——这正是第 05 章 ReAct 循环擅长的事。所以 Agentic RAG 在结构上几乎就是一个标准的 ReAct agent,只是工具列表里多了一个 retrieve。

图 8.4:Agentic RAG——结构≈标准 ReAct,只是工具列表里多了一个 retrieve。

4.2 Adaptive RAG:先路由,再选路径

Agentic RAG 把"是否检索"交给 LLM 临场决定,但有些场景你希望一开始就根据问题类型分流。Adaptive RAG 在入口放一个 router 节点,判断问题难度:简单的直接答、需要知识的走本地 RAG、需要时效性的走 web search。三条路径互不干扰,各自走到终点。

这个模式的核心是 add_conditional_edges(START, route)——在图的入口就做条件路由。为什么用结构化输出做路由?因为"简单 / RAG / web"是离散分类,让 LLM 直接输出类别比让它写自由文本再解析稳。router 本身不产生答案,只做分流,所以它是纯粹的"控制流节点"。

图 8.5:Adaptive RAG——入口 add_conditional_edges(START, route) 一分多路,各路径互不干扰。
Adaptive RAG:入口条件路由一分三路
pythonfrom typing import Annotated, Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain.chat_models import init_chat_model
import operator

model = init_chat_model("openai:gpt-4o")

class AdaptiveState(TypedDict):
    messages: Annotated[list, add_messages]
    documents: Annotated[list, operator.add]   # 检索/web 结果累加

def route_question(state: AdaptiveState) -> Literal["llm", "rag", "web"]:
    router_llm = model.with_structured_output(
        {"type": "object",
         "properties": {"datasource": {"type": "string", "enum": ["llm", "rag", "web"]}}}
    )
    resp = router_llm.invoke([
        ("system",
         "把问题路由到: llm(常识/无需检索)、rag(需知识库)、web(需实时网络信息)。"),
        ("user", state["messages"][-1].content),
    ])
    return resp["datasource"]

def direct_llm(state: AdaptiveState):
    resp = model.invoke(state["messages"])
    return {"messages": [resp]}

def rag_path(state: AdaptiveState):
    docs = ["(知识库文档片段)"]  # = retriever.invoke(query)
    resp = model.invoke([*state["messages"], *docs])
    return {"messages": [resp], "documents": docs}

def web_path(state: AdaptiveState):
    docs = ["(web search 结果)"]  # = search_api.run(query)
    resp = model.invoke([*state["messages"], *docs])
    return {"messages": [resp], "documents": docs}

workflow = StateGraph(AdaptiveState)
workflow.add_node("llm", direct_llm)
workflow.add_node("rag", rag_path)
workflow.add_node("web", web_path)
workflow.add_conditional_edges(
    START,
    route_question,
    {"llm": "llm", "rag": "rag", "web": "web"},
)
workflow.add_edge("llm", END)
workflow.add_edge("rag", END)
workflow.add_edge("web", END)
graph = workflow.compile()
适用场景: 问题类型分布明确、且不同类型适合不同检索源的客服 / 知识问答系统。价值在于"早分流省成本"——简单问题不浪费检索,复杂问题不走错路径。代价是 router 自身可能误判,所以分类边界要设计得清晰。

4.3 Corrective RAG (CRAG):检索后自我修正

Adaptive RAG 是"检索前分流",CRAG 则是"检索后纠错"。它假设检索结果质量参差,所以在检索后加一个 grading 节点评估每篇文档与问题的相关性:相关的留下生成,不相关的丢弃并转去 web search 补救。这是一条"检索 → 评估 → 必要时换源重试"的反馈回路。

为什么要在生成前 grading?因为把不相关文档塞进 prompt 会误导 LLM(它倾向于"信任"给定的上下文)。CRAG 的设计哲学是:与其让 LLM 在一堆噪声里挣扎,不如先用一个轻量判断把噪声过滤掉,过滤不掉就换更可靠的信息源。grading 节点通常用一个便宜的小模型做二元判断,成本远低于让大模型在噪声上下文里胡编。

图 8.6:CRAG——检索后 grading 过滤噪声,都不相关就转 web search 换源,一条"检索→评估→换源"纠错回边。
CRAG:grading 过滤 + 换源纠错
pythonimport operator
from typing import Annotated, Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain.chat_models import init_chat_model

model = init_chat_model("openai:gpt-4o")

class CragState(TypedDict):
    messages: Annotated[list, add_messages]
    documents: Annotated[list, operator.add]   # 过滤后的相关文档
    web_results: Annotated[list, operator.add]

def retrieve(state: CragState):
    docs = [f"(候选文档 {i})" for i in range(3)]  # = retriever.invoke(...)
    return {"documents": docs}

def grade_documents(state: CragState):
    grader_llm = model.with_structured_output(
        {"type": "object", "properties": {"relevant": {"type": "boolean"}}}
    )
    question = state["messages"][0].content
    filtered = []
    for doc in state["documents"]:
        resp = grader_llm.invoke([
            ("system", "判断文档是否与问题相关,只回 relevant 布尔值。"),
            ("user", f"问题: {question}\n文档: {doc}"),
        ])
        if resp["relevant"]:
            filtered.append(doc)
    return {"documents": filtered}

def decide_to_generate(state: CragState) -> Literal["generate", "web_search"]:
    if not state["documents"]:
        return "web_search"
    return "generate"

def web_search(state: CragState):
    results = ["(web search 补救结果)"]
    return {"web_results": results, "documents": results}

def generate(state: CragState):
    context = "\n\n".join(state["documents"] + state.get("web_results", []))
    resp = model.invoke([
        ("system", "仅基于以下文档回答,不要编造。\n\n文档:\n" + context),
        *state["messages"],
    ])
    return {"messages": [resp]}

workflow = StateGraph(CragState)
workflow.add_node("retrieve", retrieve)
workflow.add_node("grade", grade_documents)
workflow.add_node("web_search", web_search)
workflow.add_node("generate", generate)
workflow.add_edge(START, "retrieve")
workflow.add_edge("retrieve", "grade")
workflow.add_conditional_edges("grade", decide_to_generate, {"generate": "generate", "web_search": "web_search"})
workflow.add_edge("web_search", "generate")
workflow.add_edge("generate", END)
graph = workflow.compile()
适用场景: 知识库质量参差、检索召回不稳定、且对答案准确性要求高的场景(医疗、法律、企业内部文档问答)。CRAG 的核心收益是"用纠错换可信度",代价是 grading 多一轮 LLM 调用;若你的检索器本身召回率很高,CRAG 的纠错分支几乎不会触发,就是纯开销。

4.4 Self-RAG:全流程自我反思

Self-RAG 把"自我评估"推到极致:不仅检索后评估文档相关性,生成后还自评"回答是否被文档支持"。它内嵌了多个反思点——是否需要检索、检索结果是否相关、回答是否有据——形成多轮自我反思的闭环。

和 CRAG 的区别:CRAG 只在检索后纠错一次,Self-RAG 在多个环节都插了评估节点,且生成后还会回头检查"幻觉没有"。代价是图更复杂、LLM 调用更多;收益是幻觉率最低。它适合对事实准确性要求最高的场景。

图 8.7:Self-RAG——多环节反思(是否检索 / 文档相关 / 答案被支持),多条回边,幻觉率最低但成本最高。
Self-RAG:多环节自我反思闭环
pythonimport operator
from typing import Annotated, Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain.chat_models import init_chat_model

model = init_chat_model("openai:gpt-4o")

class SelfRagState(TypedDict):
    messages: Annotated[list, add_messages]
    documents: Annotated[list, operator.add]

def need_retrieve(state: SelfRagState) -> Literal["retrieve", "generate"]:
    llm = model.with_structured_output(
        {"type": "object", "properties": {"need": {"type": "boolean"}}}
    )
    resp = llm.invoke([
        ("system", "判断回答这个问题是否需要检索外部知识。"),
        ("user", state["messages"][-1].content),
    ])
    return "retrieve" if resp["need"] else "generate"

def retrieve(state: SelfRagState):
    docs = [f"(检索文档 {i})" for i in range(2)]
    return {"documents": docs}

def grade_relevance(state: SelfRagState) -> Literal["generate", "retrieve"]:
    if not state["documents"]:
        return "retrieve"
    return "generate"

def generate(state: SelfRagState):
    context = "\n\n".join(state["documents"]) or "(无检索文档,用模型自身知识)"
    resp = model.invoke([
        ("system", "基于以下文档回答,文档为空时谨慎使用自身知识。\n\n" + context),
        *state["messages"],
    ])
    return {"messages": [resp]}

def hallucination_check(state: SelfRagState) -> Literal["__end__", "retrieve"]:
    llm = model.with_structured_output(
        {"type": "object", "properties": {"grounded": {"type": "boolean"}}}
    )
    answer = state["messages"][-1].content
    docs = "\n\n".join(state["documents"])
    resp = llm.invoke([
        ("system", "判断回答是否完全被以下文档支持。只回 grounded 布尔值。"),
        ("user", f"文档:\n{docs}\n\n回答:\n{answer}"),
    ])
    return END if resp["grounded"] else "retrieve"

workflow = StateGraph(SelfRagState)
workflow.add_node("retrieve", retrieve)
workflow.add_node("generate", generate)
workflow.add_conditional_edges(START, need_retrieve, {"retrieve": "retrieve", "generate": "generate"})
workflow.add_conditional_edges("retrieve", grade_relevance, {"generate": "generate", "retrieve": "retrieve"})
workflow.add_conditional_edges("generate", hallucination_check, {END: END, "retrieve": "retrieve"})
graph = workflow.compile()
适用场景: 对事实准确性 / 可溯源要求极高的场景(医疗、法律、合规)。Self-RAG 的多个反思节点能显著压低幻觉,但每个节点都是一次 LLM 调用,延迟和成本是朴素 RAG 的数倍——它用"慢和贵"换"准和可信"。如果你的业务对延迟敏感,Self-RAG 通常不是首选。

8.6RAG 变体对比:何时检索 / 检索什么 / 如何纠错

四个变体的差异,本质上是对"检索决策"放在流程的哪个位置、以及纠错回路有几条。下面这张总表把它们沿着三个维度摆开,方便你在选型时横向对照:

模式何时检索检索什么如何纠错图复杂度
Agentic RAGLLM 临场决定(工具调用)LLM 自己构造查询,可多轮无显式纠错,靠 agent 多轮调用自然收敛低(≈ 标准 ReAct)
Adaptive RAG入口 router 预先分流按分流选源(本地 / web / 不检索)无纠错回路,路径在入口就定死中(一分多路)
Corrective RAG总是先检索一次固定查询一次检索后 grading,不相关转 web search 换源中(一条纠错回边)
Self-RAG自评是否需要检索按需检索,可重试多环节反思:文档相关性 + 答案是否被支持,多回路高(多条反思回边)

选型直觉:需求越偏"灵活",选 Agentic;越偏"分流",选 Adaptive;越偏"可信",选 CRAG 或 Self-RAG。CRAG 和 Self-RAG 的区别是"纠错几次"——CRAG 只在检索后纠一次,Self-RAG 在检索和生成后都纠。准确性要求每上一个台阶,成本大约翻一倍,这不是免费的。

8.7共同骨架:没有新原语

这些模式的共同骨架 回头看这七个模式(Reflection、Reflexion、Plan-and-Execute、四种 RAG 变体),它们本质上都是"给基础 ReAct 加上额外的反思 / 规划 / 纠错节点和循环"。具体地说:
  • 新增节点都是普通函数节点:reflector、planner、re-planner、grader、router……每个承担一个明确的"评估 / 决策"职责。
  • 新增循环都是条件边 + 回边:评估不过就回到生成 / 检索节点,这是第 04 章 add_conditional_edges 的标准用法。
  • 新增记忆都是带 reducer 的 state 字段:reflections 用 operator.add 累加教训,past_steps 累加完成项,documents 累加检索结果。
换句话说,本章没有引入任何新原语——全部是 StateGraph + 节点 + 条件边 + 回边 + reducer 的组合。掌握第 03、04、05 章后,组合这些模式是自然的:你需要哪种反馈回路,就加哪个节点和哪条回边。这也是 LangGraph 把控制流做成显式图的好处——模式不是框架预设的"开关",而是你可以像搭积木一样拼出来的结构。

8.8组合与取舍:模式不是单选题

实际工程里,这些模式常常组合使用。Plan-and-Execute 的 executor 内部可以是一个 Agentic RAG;Reflexion 的评估节点可以用 CRAG 的 grading 思路;Adaptive RAG 的 rag 路径可以再嵌一个 Self-RAG 子图。组合的边界只在于:每多一个反思节点,就多一次 LLM 调用、多一段延迟、多一份成本。

一个实用的取舍原则:从最简的模式起步,只在确实解决不了的失败模式上加节点。先跑朴素 RAG,发现"简单问题也检索"就上 Agentic;发现"检索回来一堆噪声"就加 CRAG 的 grading;发现"答案有幻觉"再加 Self-RAG 的生成后检查。不要一上来就堆 Self-RAG + Reflexion + Plan-and-Execute——那样调试困难、成本爆炸,且大多数反思节点在多数情况下不会触发,纯属浪费。

这也呼应了第 05 章末尾的判断标准:如果你发现自己在某个模式上堆了太多补丁,往往说明该把它拆成更清晰的子图,或者退一步用更简单的模式。模式的目的是解决问题,不是炫技。

8.9本页要点回顾

  • Reflection:generator → reflector 循环,评估者批评、生成者改进,适合写作 / 代码生成。关键是把"生成"和"评估"拆成两个专注的节点。
  • Reflexion:在 Reflection 基础上,把反思教训存进 reflections: Annotated[list[str], operator.add] 累加的"情节记忆",生成器读历史教训避免重蹈覆辙。适合会反复失败、教训可复用的任务。
  • Plan-and-Execute:planner 用 with_structured_output(Plan) 一次生成全局步骤列表,executor 逐条执行,re-planner 据新信息调整。适合长任务、需全局规划的场景。
  • Agentic RAG:retriever 封装成工具,交给 ReAct agent 自行决定是否 / 何时 / 检索几次。最轻量的 RAG 增强,结构≈标准 ReAct。
  • Adaptive RAG:入口 router 节点用结构化输出分流(直接答 / 本地 RAG / web search),add_conditional_edges(START, route) 实现一分多路。
  • Corrective RAG:检索后 grading 节点评估文档相关性,差的转 web search 换源。一条"检索 → 评估 → 换源"纠错回边。
  • Self-RAG:多环节自我反思(是否检索 / 文档相关 / 答案被支持),多条反思回边,幻觉率最低但成本最高。
  • 共同骨架:这些模式全部是 StateGraph + 节点 + 条件边 + 回边 + reducer 的组合,没有新原语。掌握控制流后,组合模式是自然的;从最简模式起步,按需加节点。

8.10新手常犯的错误

本章的图都能编译通过、也能跑前几步,坑集中在"循环跑飞"和"reducer 语义和直觉相反"上。下面三个都对照本仓库源码验证过。

① 反馈循环忘了加循环上限 → GraphRecursionError
python# ✗ reflector 永远说"不够好", should_continue 永远回 "generator", 死循环
def should_continue(state):
    return "generator"   # 没有 iterations 上限, 也没有解析 satisfactory

graph.invoke(initial_state)
# GraphRecursionError: Recursion limit of 10007 reached without hitting a stop condition.
# 默认上限 LANGGRAPH_DEFAULT_RECURSION_LIMIT=10007 (_internal/_config.py:32), 撞到才停。
#
# ✓ 任何回边都要配一个"硬上限"兜底(本章所有示例都这么做的):
MAX_ITER = 3
def should_continue(state):
    if state["iterations"] >= MAX_ITER:   # 硬上限
        return END
    return "generator"   # 再叠一个业务判断(解析 satisfactory)更稳
踩坑点: Reflection / Reflexion / Self-RAG / CRAG 都有回边,只要评估节点一直说"再来一轮",就是死循环。LangGraph 不会自动检测"你在原地打转",只靠 recursion_limit 兜底(默认 10007,源码 _internal/_config.py:32 的 DEFAULT_RECURSION_LIMIT,撞限抛 GraphRecursionError,消息见 main.py:3003)。10007 步的 LLM 调用代价惊人,所以每条回边都要配一个计数器上限,别指望业务判断永远收敛。
② 给"过滤/替换"语义的字段用了 operator.add → 越过滤越长
pythonimport operator
from typing import Annotated
from typing_extensions import TypedDict

class CragState(TypedDict):
    # ✗ 想用 documents 做"过滤后的相关文档", 却配了 operator.add
    documents: Annotated[list, operator.add]   # reducer 是 list + list = 拼接

def retrieve(state):  return {"documents": ["doc1", "doc2", "doc3"]}   # state.documents = 3 篇

def grade(state):
    filtered = ["doc1"]   # 只剩 1 篇相关
    return {"documents": filtered}
# 期望: documents 变成 ["doc1"](只剩相关的)
# 实际: documents = ["doc1","doc2","doc3"] + ["doc1"] = 4 篇! 过滤根本没生效
#
# ✓ 要"替换"语义, 就别配 reducer(默认 LastValue = 最后一次写入覆盖):
class CragState(TypedDict):
    documents: list   # 无 Annotated reducer → LastValue, 覆盖而非累加
踩坑点: 这是本章最容易踩的语义陷阱。operator.add 是追加(list 拼接),适合"只增不减"的记忆字段(reflections、past_steps);但"过滤"是要替换掉旧值,这时不该配 reducer——源码 state.py:1871 里,没有 reducer 注解的字段会回落到 LastValue(最后一次写入覆盖),这才是过滤该用的语义。判断准则:这字段是累加历史(用 reducer)还是反映当前最新值(不配 reducer)?CRAG 的 documents 是后者。
③ 路由 LLM 吐了 Literal 之外的值 → KeyError
pythonfrom typing import Literal

# Adaptive RAG 的 router, 期望返回 "llm" / "rag" / "web"
def route_question(state) -> Literal["llm", "rag", "web"]:
    resp = router_llm.invoke(...)   # LLM 偶尔会回 "LLM" / " rag " / "search"
    return resp["datasource"]
# 假设 LLM 回了 "search"(不在 Literal / path_map 里):
# KeyError: 'search'   (_branch.py:203 的 self.ends[r] 字典查找)
# 若返回 None / START: ValueError: Branch did not return a valid destination
#
# ✓ 路由函数里做归一化 + 兜底, 别把 LLM 原始输出直接当路由键:
def route_question(state) -> Literal["llm", "rag", "web"]:
    raw = router_llm.invoke(...)["datasource"].strip().lower()
    return raw if raw in ("llm", "rag", "web") else "llm"   # 未知→走最稳的兜底路
踩坑点: 源码 _branch.py:201-208 里,带 path_map / Literal 的条件边会把返回值当字典 key 查 self.ends[r],查不到就 KeyError。LLM 输出天然不稳定(大小写、空格、同义词),所以路由节点不能把 LLM 原始输出直接当路由键——要先归一化(strip/lower)再做白名单校验,未命中走一条兜底路径。这是 Adaptive RAG / Self-RAG 这类"LLM 当路由器"模式的通病。
