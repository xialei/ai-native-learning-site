第一个图：从 add_node 到 invoke

用三步法搭出一张可运行的 StateGraph——注册节点、连边、编译——看清状态如何在节点之间流转。整张图只有两个节点、三条边，却浓缩了 LangGraph 建图的核心套路。

2.1三步法总览

无论图多复杂，用 StateGraph 建图永远遵循同一个节奏：

  1. add_node（注册节点）：把一个个 Python 函数登记到图里，给它们起个名字。节点函数的职责是「读当前状态、返回状态更新」。
  2. add_edge（连接边）：用 START、节点名、END 这些「地址」连出有向边，告诉框架执行完谁该轮到谁。
  3. compile（编译）：把 builder 转成一个实现了 Runnable 接口、可以 invoke / stream 的可运行图。

为什么是这三步、而不是一个声明式的大配置？因为 LangGraph 刻意把「定义结构」和「执行结构」分开：StateGraph 只是个建造者（builder），本身不能跑；只有 compile() 之后才生成可执行的 CompiledStateGraph。这样分开有两个好处：一是编译时能做一次完整的图校验（有没有入口、有没有悬空节点），二是同一个 builder 可以用不同 checkpointer / store 编译出多个运行实例，复用结构、隔离运行。

图 2.1：本章要搭的图。输入 {"x": 1}，经 +1 再 *2，最终 {"x": 4}。

2.2第一步：add_node 注册节点

add_node 把一个函数登记成图里的节点。它的真实签名（摘自源码 langgraph/graph/state.py）是：

langgraph/graph/state.py — add_node 签名（节选）
pythondef add_node(
    self,
    node: str | StateNode,            # 节点名，或直接传函数(用函数名当节点名)
    action: StateNode | None = None,  # 当 node 是字符串时，这里放实际函数
    *,
    defer: bool = False,
    metadata: dict[str, Any] | None = None,
    input_schema: type | None = None, # 不传则用图的状态 schema
    retry_policy: RetryPolicy | None = None,
    cache_policy: CachePolicy | None = None,
    error_handler: StateNode | None = None,
    destinations: dict[str, str] | tuple[str, ...] | None = None,
    timeout: float | timedelta | TimeoutPolicy | None = None,
    trace_policy: TracePolicy | None = None,
) -> Self:  # 返回 self，支持链式调用
读懂这段： 日常用得最多的就是前两个参数。两种写法等价：要么直接传函数（框架取它的 __name__ 当节点名），要么显式给个名字字符串再加函数。源码 docstring 里的真实示例就是前一种——直接 add_node(my_node)。
源码 add_node docstring 的真实示例
pythonfrom typing_extensions import TypedDict
from langgraph.graph import START, StateGraph

class State(TypedDict):
    x: int

def my_node(state: State) -> State:
    return {"x": state["x"] + 1}

builder = StateGraph(State)
builder.add_node(my_node)  # 节点名自动取函数名 "my_node"

如果想自定义节点名（比如同一个函数要在图里出现两次，或想要更可读的标签），就用第二种写法 add_node("step1", step1)——名字在前、函数在后。本章示例就用这种显式命名，便于和边的连接对应起来。

护栏 源码里有一道护栏：add_node 会拒绝把节点命名为 START 或 END（报 Node `...` is reserved），也不允许名字里含保留分隔符。这两个名字是图的「虚拟地址」，只能用在 add_edge 里指代入口和出口，不能当成普通节点。

2.3第二步：add_edge 连接边，START 与 END

节点注册好之后，它们之间还互不相干。add_edge 负责连出有向边，决定执行顺序。签名很简洁：

langgraph/graph/state.py — add_edge 签名
pythondef add_edge(self, start_key: str | list[str], end_key: str) -> Self:
    ...

start_key 传一个节点名（或一组节点名，表示「等这组全都完成再继续」），end_key 传一个目标。这里有两个特殊「地址」贯穿始终：

langgraph/constants.py — START / END 常量
pythonfrom langgraph.graph import START, END
# 源码 constants.py 里：START = "__start__", END = "__end__"
  • START 是虚拟入口：它不是一个真正的节点，而是「图的起点」这个概念。add_edge(START, "step1") 等价于说「图启动后第一个执行 step1」。源码里它还有个便利别名 set_entry_point("step1")，内部就是调 add_edge(START, ...)。
  • END 是终止：一旦某条边把控制权交给 END，图就停止执行。add_edge("step2", END) 表示「step2 跑完就结束」。同样有别名 set_finish_point("step2")。
方向约束 源码对这两个常量有明确约束：END 不能作为边的起点（END cannot be a start node），START 不能作为边的终点（START cannot be an end node）——方向是单向的，入口只能出、终点只能进。编译时还会校验「图必须至少有一条从 START 出发的边」，否则报 Graph must have an entrypoint。
最小复现：忘了从 START 接出边，compile 时就报错
python# 只注册了节点、连了 step1 -> step2，却没接 START
builder.add_node("step1", step1)
builder.add_node("step2", step2)
builder.add_edge("step1", "step2")

builder.compile()
# ValueError: Graph must have an entrypoint:
#             add at least one edge from START to another node
读懂这段： 这条校验在 compile() 时触发，不是 add_edge 时——所以你会等到编译才看到报错。解法就是补一条 add_edge(START, "step1")。新手常以为「注册了节点图就能跑」，但 START 是唯一的入口，没有从它出发的边，框架不知道第一个该执行谁。
三条边串成一条线
python# 三条边串成一条线：入口 → step1 → step2 → 终止
builder.add_edge(START, "step1")
builder.add_edge("step1", "step2")
builder.add_edge("step2", END)

2.4第三步：compile 编译为可运行图

StateGraph 只是建造者，不能直接跑。调 compile() 才会做图校验、把节点和边装配成一个 CompiledStateGraph——它实现了 Runnable 接口，因而有 invoke / stream / ainvoke / astream / batch 等方法。签名（同样摘自源码）：

langgraph/graph/state.py — compile 签名（节选）
pythondef compile(
    self,
    checkpointer: Checkpointer = None,  # 传 InMemorySaver 等可启用持久化
    *,
    store: BaseStore | None = None,     # 跨会话长期记忆
    interrupt_before: list[str] | None = None,  # 在指定节点前暂停(HITL)
    interrupt_after: list[str] | None = None,
    debug: bool = False,
    name: str | None = None,
) -> CompiledStateGraph:
读懂这段： 本章先把可选项全空着，得到一张最朴素的图。checkpointer / store / interrupt 这些参数会在第 06、09 章用到——它们正是把图从「一次性计算」升级成「可暂停、可记忆、可恢复」的关键，而你现在看到的 compile 就是它们统一的挂载点。

2.5完整可运行示例

把三步合起来，就是一张能跑的图。这个例子扩展自源码 add_node docstring 里的真实示例——原来只有一个节点（x + 1），这里加到两个节点，串成一条流水线：

第一个完整图 — 三步法 + invoke
pythonfrom typing_extensions import TypedDict
from langgraph.graph import START, END, StateGraph

# 1. 定义状态：一个只持有 x 的容器
class State(TypedDict):
    x: int

# 2. 定义节点：签名是 (state) -> 部分更新
#    返回的 dict 会与当前状态合并(默认覆盖同名键)
def step1(state: State) -> dict:
    return {"x": state["x"] + 1}   # 加 1

def step2(state: State) -> dict:
    return {"x": state["x"] * 2}   # 乘 2

# 3. 三步法建图
builder = StateGraph(State)
builder.add_node("step1", step1)   # 注册节点(显式命名)
builder.add_node("step2", step2)
builder.add_edge(START, "step1")   # 入口 → step1
builder.add_edge("step1", "step2") # step1 → step2
builder.add_edge("step2", END)     # step2 → 终止

# 4. 编译为可运行图
graph = builder.compile()

# 5. 执行：1 → (+1) = 2 → (*2) = 4
print(graph.invoke({"x": 1}))
# {'x': 4}
执行过程： 你给 invoke 的 {"x": 1} 作为初始状态从 START 进入；框架把它喂给 step1，step1 返回 {"x": 2}，与状态合并后 x 变成 2；接着按边走到 step2，它读到 x=2、返回 {"x": 4}，合并后 x 变成 4；再到 END，图停止，最终状态 {"x": 4} 作为结果返回。
图 2.2：执行时的状态流转。每个节点读全量状态、返回部分更新，框架负责合并。
契约 每个节点的签名是 def node(state: State) -> dict——读全量状态、返回部分更新。返回的 dict 不必包含所有键，框架只会拿你返回的那些键去更新状态。默认行为是「覆盖」（源码里对应 LastValue 通道）：新值直接顶掉旧值。但「覆盖」不是唯一的合并策略——你可以用 Annotated[list, add_messages] 给某个键指定 reducer，让该键做「追加」而非「覆盖」。这正是聊天历史能越积越长的原理，第 03 章专门展开。

2.6方法链：三步可以串成一句

留意源码签名末尾的 -> Self：add_node 和 add_edge 都返回 builder 自身，因此可以链式调用。整张图可以用一个表达式写完：

链式调用建图
pythongraph = (
    StateGraph(State)
    .add_node("step1", step1)
    .add_node("step2", step2)
    .add_edge(START, "step1")
    .add_edge("step1", "step2")
    .add_edge("step2", END)
    .compile()   # compile 是链的终点，返回 CompiledStateGraph
)
print(graph.invoke({"x": 1}))   # {'x': 4}
读懂这段： 链的最后一个环节是 compile()——它返回的不再是 builder（Self），而是 CompiledStateGraph。所以 compile 是建图链的终点：编译产物上根本没有 add_node（调了直接 AttributeError）；而如果你拿着 builder 的引用在 compile 之后又调 builder.add_node(...)，源码只会打一条警告（"Adding a node to a graph that has already been compiled…"）——改动静默不生效，已编译的图不变。两种情形都指向同一件事：「建造」与「执行」分离，链式调用把结构搭完，compile 封口并产出可运行对象。

2.7查看图结构：get_graph 与 draw_mermaid

编译后的图自带一个「自省」方法 get_graph()，它返回一个可绘制的 Graph 对象（来自 langchain_core）。这个对象能直接导出 mermaid 文本，也能遍历节点——对调试和文档化很有用：

图自省
python# 导出 mermaid 文本(可直接粘进任意 mermaid 渲染器)
print(graph.get_graph().draw_mermaid())

# 遍历图里的节点(.nodes 是 dict，键就是节点名)
for name in graph.get_graph().nodes:
    print(name)
# 输出大致是：
# __start__
# step1
# step2
# __end__
实用价值： get_graph() 还接受一个 xray 参数：传 True 会把子图节点展开显示内部结构，在调试多智能体（每个 Agent 其实是个子图）时特别好用。当你的图长到十几个节点、带条件分支和子图时，一张能看的结构图往往是排查「为什么走到了这里」的最快路径。
为什么先从静态边开始 这张图的边是写死的：step1 永远接 step2。真实 Agent 的控制流当然不会这么僵硬——它需要「根据状态决定下一步走哪」。LangGraph 用条件边和 Command(goto=...) 来表达这种动态路由，而它们都建立在同样的 add_edge / compile 地基上。先把这张静态图跑通、确认状态流转符合预期，再去把某条边换成条件边，出问题时你心里才有「它本来应该怎么走」的基准线。

2.8新手常犯的错误

这一章只有三步，但三步里最容易绊倒新手的恰恰是「忘了第三步」和「重名」。下面两个坑都源自本仓库源码，踩过一次就再也不会犯。

① 对着 builder 直接 invoke，忘了 compile()

2.1 反复强调 StateGraph 只是建造者、本身不能跑，但新手写顺手了很容易拿着 builder 就 invoke。源码里 invoke / stream 这些方法只挂在编译后的 CompiledStateGraph 上，builder 上根本没有——于是你拿到的不是图的结果，而是一个 AttributeError。

反面 vs 正面：builder 不能 invoke，编译后才能
pythonbuilder = StateGraph(State)
builder.add_node("step1", step1)
builder.add_edge(START, "step1")
builder.add_edge("step1", END)

# ✗ 忘了 compile，直接拿 builder invoke
builder.invoke({"x": 1})
# AttributeError: 'StateGraph' object has no attribute 'invoke'

# ✓ 先 compile 再 invoke
graph = builder.compile()
print(graph.invoke({"x": 1}))   # {'x': 2}
读懂这段： 报错信息本身就是一条线索——它说 StateGraph 「没有 invoke 属性」，而不是「参数错误」。这提醒你：执行能力是 compile() 赋予的。compile 返回的 CompiledStateGraph 才实现了 Runnable 接口。

② 两次 add_node 用了同一个名字

另一个高频坑：复制粘贴节点时没改名字，或者用 add_node(my_node) 这种「函数名即节点名」的写法时，两个不同函数恰好 __name__ 相同。源码在 add_node 里会先查重，撞名就直接报错，不会悄悄覆盖。

最小复现：同名节点报 ValueError
pythonbuilder.add_node("step1", step1)
builder.add_node("step1", step2)   # 名字撞了
# ValueError: Node `step1` already present.
读懂这段： 这条护栏是好事——LangGraph 不允许同名节点，避免了「后注册的悄悄顶掉先注册的」这种难查的 bug。遇到这个报错，要么改名字，要么确认你是不是真的想注册两次（若是，给它们不同的名字）。
共同点 这两个坑的共同点是把「建造」和「执行」混在了一起。第一个是拿建造者当执行物用，第二个是以为建造阶段会「覆盖」而非「拒重名」。记住 2.1 的那条主线——StateGraph 搭结构、compile() 封口并产出可运行对象——这两个坑就都不会踩。
