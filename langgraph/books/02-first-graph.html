第一个图：从 add_node 到 invoke

第 1 章给出了六个概念，但没回答「一动手到底先干什么」。这一章用一张 x+1 再 ×2 的小图把「builder → compile → invoke」管线走通，顺路回答三个问题：为什么要分三步、一个节点执行时状态怎么流、编译前后各能做什么。整张图只有两个节点、三条边，却浓缩了建图的全部套路。

2.1开场：三个 API 就够了吗？为什么要分三步

第 1 章结束时你已经知道建图要用 add_node、add_edge、compile。但动手前值得先问一句：为什么是三步？为什么不能一个函数把图配完？

把三个症状反过来推就明白了。假设 LangGraph 真提供 run_my_graph(nodes=[...], edges=[...]) 一把梭：

  • 参数列表里怎么表达「图必须从哪开始」？入口信息得混进 edges 参数。
  • 节点多了以后，出错时怎么知道是「结构写错了」还是「节点跑挂了」？没有一道把结构整体校验一遍的关卡。
  • 同一套结构想配两套运行配置（比如测试用内存快照、生产用 SQLite 快照），只能整个函数调两遍。

LangGraph 的三步法正是对着这三件事设计的：add_node/add_edge 只管「搭结构」——它是个建造者（builder），本身不能跑；compile() 一道关做整体校验（有没有入口、边指向的节点存不存在），校验过了才生成可执行的 CompiledStateGraph；invoke 是执行，只存在于编译产物上。同一个 builder 用不同 checkpointer 编译两次、得到两个共享结构但运行配置独立的实例——第 1 章 Q4 留的那道题，这里动手验证。

图 2.1：三个阶段各管一件事。结构与执行分离——builder 校验前只是数据，compile 一道关做完校验和装配，invoke 只属于编译产物。

无论图多复杂，节奏永远不变：add_node 注册节点 → add_edge 连边 → compile 封口。本章就按这条时间线走，每一步都对照源码看它到底做了什么。

2.2第一步：add_node 注册节点

建图的第一问：我的每个步骤怎么登记进图？add_node 把一个函数登记成节点。它的真实签名（摘自源码 langgraph/graph/state.py）是：

langgraph/graph/state.py — add_node 签名（节选）
pythondef add_node(
    self,
    node: str | StateNode,            # 节点名，或直接传函数(用函数名当节点名)
    action: StateNode | None = None,  # 当 node 是字符串时，这里放实际函数
    *,
    defer: bool = False,
    metadata: dict[str, Any] | None = None,
    input_schema: type | None = None, # 不传则用图的状态 schema
    retry_policy: RetryPolicy | None = None,
    cache_policy: CachePolicy | None = None,
    error_handler: StateNode | None = None,
    destinations: dict[str, str] | tuple[str, ...] | None = None,
    timeout: float | timedelta | TimeoutPolicy | None = None,
    trace_policy: TracePolicy | None = None,
) -> Self:  # 返回 self，支持链式调用
常用的只有前两个： 日常用得最多的就是前两个参数。两种写法等价：要么直接传函数（框架取它的 __name__ 当节点名），要么显式给个名字字符串再加函数。源码 docstring 里的真实示例就是前一种——直接 add_node(my_node)。其余参数（retry_policy、timeout、cache_policy……）先全部无视，它们是后面章节的伏笔：重试和超时在第 5 章的 agent 里露面，缓存策略要等图跑慢了才用得上。
源码 add_node docstring 的真实示例
pythonfrom typing_extensions import TypedDict
from langgraph.graph import START, StateGraph

class State(TypedDict):
    x: int

def my_node(state: State) -> State:
    return {"x": state["x"] + 1}

builder = StateGraph(State)
builder.add_node(my_node)  # 节点名自动取函数名 "my_node"

如果想自定义节点名（比如同一个函数要在图里出现两次，或想要更可读的标签），就用第二种写法 add_node("step1", step1)——名字在前、函数在后。本章示例就用这种显式命名，便于和边的连接对应起来。

护栏 源码里有一道护栏：add_node 会拒绝把节点命名为 START 或 END（报 Node `...` is reserved，state.py:805），也不允许名字里含保留分隔符。这两个名字是图的「虚拟地址」，只能用在 add_edge 里指代入口和出口，不能当成普通节点。

2.3第二步：add_edge 连边——图从哪开始、到哪结束

节点登记完还是一座座孤岛：谁先跑、跑完轮到谁？add_edge 用有向边回答。签名很简洁：

langgraph/graph/state.py — add_edge 签名
pythondef add_edge(self, start_key: str | list[str], end_key: str) -> Self:
    ...

start_key 传一个节点名（或一组节点名，表示「等这组全都完成再继续」，第 4 章 4.2 的 join 语义），end_key 传一个目标。这里有两个特殊「地址」贯穿始终：

langgraph/constants.py — START / END 常量
pythonfrom langgraph.graph import START, END
# 源码 constants.py 里：START = "__start__", END = "__end__"
  • START 是虚拟入口：它不是一个真正的节点，而是「图的起点」这个概念。add_edge(START, "step1") 等价于说「图启动后第一个执行 step1」。源码里它还有个便利别名 set_entry_point("step1")（state.py:1079，内部就是 return self.add_edge(START, key)）。
  • END 是终止：一旦某条边把控制权交给 END，图就停止执行。add_edge("step2", END) 表示「step2 跑完就结束」。同样有别名 set_finish_point("step2")（state.py:1116）。
方向约束 源码对这两个常量有明确约束：END 不能作为边的起点（END cannot be a start node，state.py:953），START 不能作为边的终点（START cannot be an end node，state.py:955）——方向是单向的，入口只能出、终点只能进。编译时还会校验「图必须至少有一条从 START 出发的边」，否则报 Graph must have an entrypoint（state.py:1144）。
最小复现：忘了从 START 接出边，compile 时就报错
python# 只注册了节点、连了 step1 -> step2，却没接 START
builder.add_node("step1", step1)
builder.add_node("step2", step2)
builder.add_edge("step1", "step2")

builder.compile()
# ValueError: Graph must have an entrypoint:
#             add at least one edge from START to another node
报错为什么来得这么晚： 这条校验在 compile() 里触发（compile 内部调 state.py:1129 的 validate()），不是 add_edge 时——所以你会等到编译才看到报错。解法就是补一条 add_edge(START, "step1")。新手常以为「注册了节点图就能跑」，但 START 是唯一的入口，没有从它出发的边，框架不知道第一个该执行谁。
三条边串成一条线
python# 三条边串成一条线：入口 → step1 → step2 → 终止
builder.add_edge(START, "step1")
builder.add_edge("step1", "step2")
builder.add_edge("step2", END)

2.4第三步：compile——从结构到可运行对象

结构搭完了，为什么不能直接跑？compile() 到底做了什么？第 1 章图 1.8 画过三步（校验、字段转 Channel、装配 Pregel 计划），这一节落到 API 层面。签名（同样摘自源码）：

langgraph/graph/state.py — compile 签名（节选）
pythondef compile(
    self,
    checkpointer: Checkpointer = None,  # 传 InMemorySaver 等可启用持久化
    *,
    store: BaseStore | None = None,     # 跨会话长期记忆
    interrupt_before: list[str] | None = None,  # 在指定节点前暂停(HITL)
    interrupt_after: list[str] | None = None,
    debug: bool = False,
    name: str | None = None,
) -> CompiledStateGraph:
本章全部用默认值： 先把可选项全空着，得到一张最朴素的图。checkpointer / store / interrupt 这些参数会在第 06、09 章用到——它们正是把图从「一次性计算」升级成「可暂停、可记忆、可恢复」的关键，而你现在看到的 compile 就是它们统一的挂载点。

2.5invoke 时状态怎么流：一张图看懂 super-step

三步齐了，把整张图跑起来。这个例子扩展自源码 add_node docstring 里的真实示例——原来只有一个节点（x + 1），这里加到两个节点，串成一条流水线：

第一个完整图 — 三步法 + invoke
pythonfrom typing_extensions import TypedDict
from langgraph.graph import START, END, StateGraph

# 1. 定义状态：一个只持有 x 的容器
class State(TypedDict):
    x: int

# 2. 定义节点：签名是 (state) -> 部分更新
#    返回的 dict 会与当前状态合并(默认覆盖同名键)
def step1(state: State) -> dict:
    return {"x": state["x"] + 1}   # 加 1

def step2(state: State) -> dict:
    return {"x": state["x"] * 2}   # 乘 2

# 3. 三步法建图
builder = StateGraph(State)
builder.add_node("step1", step1)   # 注册节点(显式命名)
builder.add_node("step2", step2)
builder.add_edge(START, "step1")   # 入口 → step1
builder.add_edge("step1", "step2") # step1 → step2
builder.add_edge("step2", END)     # step2 → 终止

# 4. 编译为可运行图
graph = builder.compile()

# 5. 执行：1 → (+1) = 2 → (*2) = 4
print(graph.invoke({"x": 1}))
# {'x': 4}
图 2.2：super-step 视角的状态流转。一次 invoke 不是「逐函数调用」，而是若干 super-step：每步先执行当步的所有节点（本例每步一个），步末把写入统一合并进通道（触发点 pregel/_algo.py:319），再由更新后的通道触发下一步的节点。
契约 每个节点的签名是 def node(state: State) -> dict——读全量状态、返回部分更新。返回的 dict 不必包含所有键，框架只会拿你返回的那些键去更新状态。默认行为是「覆盖」（源码里对应 LastValue 通道）：新值直接顶掉旧值。但「覆盖」不是唯一的合并策略——你可以用 Annotated[list, add_messages] 给某个键指定 reducer，让该键做「追加」而非「覆盖」。这正是聊天历史能越积越长的原理，第 03 章专门展开。

2.6方法链：三步可以串成一句

留意源码签名末尾的 -> Self：add_node 和 add_edge 都返回 builder 自身，因此可以链式调用。整张图可以用一个表达式写完：

链式调用建图
pythongraph = (
    StateGraph(State)
    .add_node("step1", step1)
    .add_node("step2", step2)
    .add_edge(START, "step1")
    .add_edge("step1", "step2")
    .add_edge("step2", END)
    .compile()   # compile 是链的终点，返回 CompiledStateGraph
)
print(graph.invoke({"x": 1}))   # {'x': 4}
链的终点是 compile： 最后一个环节 compile()——它返回的不再是 builder（Self），而是 CompiledStateGraph。所以 compile 是建图链的终点：编译产物上根本没有 add_node（调了直接 AttributeError）；而如果你拿着 builder 的引用在 compile 之后又调 builder.add_node(...)，源码只会打一条警告（"Adding a node to a graph that has already been compiled…"，state.py:790）——改动静默不生效，已编译的图不变。两种情形都指向同一件事：「建造」与「执行」分离，链式调用把结构搭完，compile 封口并产出可运行对象。

2.7查看图结构：get_graph 与 draw_mermaid

编译后的图自带一个「自省」方法 get_graph()，它返回一个可绘制的 Graph 对象（来自 langchain_core）。这个对象能直接导出 mermaid 文本，也能遍历节点——对调试和文档化很有用：

图自省
python# 导出 mermaid 文本(可直接粘进任意 mermaid 渲染器)
print(graph.get_graph().draw_mermaid())

# 遍历图里的节点(.nodes 是 dict，键就是节点名)
for name in graph.get_graph().nodes:
    print(name)
# 输出大致是：
# __start__
# step1
# step2
# __end__
实用价值： get_graph() 还接受一个 xray 参数：传 True 会把子图节点展开显示内部结构，在调试多智能体（每个 Agent 其实是个子图）时特别好用。当你的图长到十几个节点、带条件分支和子图时，一张能看的结构图往往是排查「为什么走到了这里」的最快路径。
为什么先从静态边开始 这张图的边是写死的：step1 永远接 step2。真实 Agent 的控制流当然不会这么僵硬——它需要「根据状态决定下一步走哪」。LangGraph 用条件边和 Command(goto=...) 来表达这种动态路由，而它们都建立在同样的 add_edge / compile 地基上。先把这张静态图跑通、确认状态流转符合预期，再去把某条边换成条件边，出问题时你心里才有「它本来应该怎么走」的基准线。

2.8新手常犯的错误

这一章只有三步，但三步里最容易绊倒新手的恰恰是「忘了第三步」和「重名」。下面两个坑都源自本仓库源码，踩过一次就再也不会犯。

对着 builder 直接 invoke，忘了 compile()

2.1 反复强调 StateGraph 只是建造者、本身不能跑，但新手写顺手了很容易拿着 builder 就 invoke。源码里 invoke / stream 这些方法只挂在编译后的 CompiledStateGraph 上，builder 上根本没有——于是你拿到的不是图的结果，而是一个 AttributeError。

反面 vs 正面：builder 不能 invoke，编译后才能
pythonbuilder = StateGraph(State)
builder.add_node("step1", step1)
builder.add_edge(START, "step1")
builder.add_edge("step1", END)

# ✗ 忘了 compile，直接拿 builder invoke
builder.invoke({"x": 1})
# AttributeError: 'StateGraph' object has no attribute 'invoke'

# ✓ 先 compile 再 invoke
graph = builder.compile()
print(graph.invoke({"x": 1}))   # {'x': 2}
读报错： 报错信息本身就是一条线索——它说 StateGraph 「没有 invoke 属性」，而不是「参数错误」。这提醒你：执行能力是 compile() 赋予的。compile 返回的 CompiledStateGraph 才实现了 Runnable 接口。

两次 add_node 用了同一个名字

另一个高频坑：复制粘贴节点时没改名字，或者用 add_node(my_node) 这种「函数名即节点名」的写法时，两个不同函数恰好 __name__ 相同。源码在 add_node 里会先查重（state.py:803），撞名就直接报错，不会悄悄覆盖。

最小复现：同名节点报 ValueError
pythonbuilder.add_node("step1", step1)
builder.add_node("step1", step2)   # 名字撞了
# ValueError: Node `step1` already present.
这条护栏是好事： LangGraph 不允许同名节点，避免了「后注册的悄悄顶掉先注册的」这种难查的 bug。遇到这个报错，要么改名字，要么确认你是不是真的想注册两次（若是，给它们不同的名字）。
共同点 这两个坑的共同点是把「建造」和「执行」混在了一起。第一个是拿建造者当执行物用，第二个是以为建造阶段会「覆盖」而非「拒重名」。记住 2.1 的那条主线——StateGraph 搭结构、compile() 封口并产出可运行对象——这两个坑就都不会踩。

2.9读完本章，你应该能回答

先自己作答，再展开对照。

Q1 · 三步法里，哪一步做了「有没有入口」的校验？为什么这个检查放在那一步，而不是在 add_edge 时就做？
在 compile() 里（内部调 state.py:1129 的 validate()）。放在编译时有两个理由：入口合法性取决于「全部边拼完之后」的整体——你在 add_edge 阶段随时可能补上 START 边，逐边报错会误伤中间状态；同理悬空节点、未知目标这类「结构级」错误都只在结构封口时才能定论。代价是报错时机后移：编译前一切静默，所以写完图要立刻 compile 一次当作「类型检查」。
Q2 · graph.invoke({"x": 1}) 的返回值 {'x': 4} 是哪一层的数据？如果 step1、step2 都返回 {"x": ...}，它们的返回值是直接拼成结果，还是经过别的路径？
返回值是各通道（channel）的最终值组成的 dict，不是把节点返回值直接拼接。每个节点的返回只是「写入请求」：step1 写 x=2 进 x 通道，step2 读到 2、写回 4，END 前最后读取通道现值得到 4。合并动作发生在每个 super-step 末尾（pregel/_algo.py:319 的 update）。这就是为什么返回值永远完整、而节点永远只返回部分更新——中间的翻译层是通道 + reducer。
Q3 · 同一个 builder，第一次 compile(checkpointer=A)，第二次 compile(checkpointer=B)。第二次编译后，第一次编译出的图还能正常 invoke 吗？builder 上之后再 add_node 会怎样？
还能。compile 是读取 builder 的结构生成新实例，不消耗它，两个产物互相独立（各自的 checkpointer、各自的通道实例）。之后再 add_node：源码只发警告"Adding a node to a graph that has already been compiled"（state.py:790），改动不生效于任何已编译产物——既不进第一个也不进第二个，除非再 compile 一次。警惕点：这是警告不是异常，漏看的话「明明加了节点怎么不跑」。
Q4 · 为什么 add_node("START", ...) 会报错？「START 不是节点」和「START 不能当边终点」这两条约束分别在拦什么？
state.py:805 的保留名护栏拒绝注册 START/END。两条约束各管一头：START 不是节点（它是编译时补造的 EphemeralValue 入口通道 + 触发器的虚拟源，state.py:1354），把它当普通节点注册会跟入口机制撞车；「START 不能当边终点」拦的是「别的节点执行完回到起点」——入口在图语义里只出不进，写 add_edge("a", START) 会得到 ValueError。END 同理只能进不能出。
Q5 · 图 2.2 里，一次 invoke 被切成了三个 super-step。如果 step1 和 step2 没有边相连、而是都被 START 直接触发（add_edge(START, "step1"); add_edge(START, "step2")），执行会变成什么样？
step1 和 step2 会落进同一个 super-step 并行执行：它们同时读到 x=1，各自返回写入。x 是无 reducer 字段，两个写入撞进 LastValue 通道就抛 InvalidUpdateError（第 1 章 1.6 的最小复现）。这个例子说明 super-step 的边界由「通道更新触发哪些节点」决定：同批触发的节点并行、共享同一次合并窗口——想顺序执行就把它们用边串起来，想并行就共享触发源，并给被写的字段配 reducer。
