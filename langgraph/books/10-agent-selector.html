10 · Agent 选型指南

本页是整站的收口，回答两件事：我的任务到底需不需要 Agent，该自建还是用 create_react_agent？如果自建，该套哪种架构模式？用两棵决策树、一张对照表和一份生产清单把答案钉死；末节另补一类生态新选项——把循环里的快判断从 LLM 调用换成专用分类模型。

10.1为什么这个问题值得单开一页

学完前面的章节，你已经看过 StateGraph、Reducer、控制流、ReAct、HITL、checkpointer、多智能体和经典模式。但「知道有哪些零件」和「知道该选哪个零件」是两件事。最常见的两种踩坑是：任务明明只是单轮问答，却套了个多智能体 Supervisor，白白增加调试面；或者明明需要规划-反思和人机审批，却硬用 create_react_agent 凑，最后在 prebuilt 的缝里塞满 hack。这一页的目的，就是让你在动手写第一行代码之前，先花十分钟把架构定对。

核心判断原则只有一句：架构服务于任务，别为复杂而复杂。能用 prebuilt 跑通就别自建；必须自建时，再按任务特征选最小的那个模式。

提示 选型的本质是「按需升级」：先用最轻的方案验证需求能不能跑通，跑不通再加节点、加循环、加子图。每一次升级都必须由明确的任务特征驱动，而不是「听起来更高级」。这套思路贯穿下面两棵决策树。

10.2决策树一｜自建 vs prebuilt

第一棵树回答「用多重的框架」。判断顺序是从轻到重——先排除最简单的情况，再逐级升级。每一步升级都意味着你接受更多的代码量和调试成本，所以务必在低层级确认「真的不够用」之后再上移。

图 10.2：决策树一——从轻到重逐级判断，左侧四个落点对应四种方案；A2→A3→A4 是单向升级，Q4 的「否」回退到 A2。

四个落点的取舍逻辑：

  • A1 直接调用 LLM：如果你只是做翻译、摘要、改写、单轮问答，就别上 Agent。Agent 的全部价值在于「循环 + 工具 + 状态」，没有这些需求时框架只会拖慢你。一个 model.invoke(messages) 比任何 prebuilt 都快、都好调试。
  • A2 create_react_agent：标准的「模型决定调工具→执行工具→把结果喂回模型→模型决定继续或结束」循环，prebuilt 已经帮你接好了。本代码库里 create_react_agent 返回一个 CompiledStateGraph，意味着它本身就是一张图，只是控制流被锁死成 ReAct 循环。你的工具列表、system prompt、结构化输出都能通过参数传进去，绝大多数「带工具的助手」到这里就够了。
  • A3 StateGraph 自建：当你需要在循环里插入 ReAct 之外的东西——先规划再执行、执行后反思重试、关键动作前暂停等人审批、根据中间结果动态路由到不同子流程——prebuilt 的单一循环就装不下了。这时用 StateGraph 自己拼节点和条件边，每个控制流分支都由你掌控。
  • A4 多智能体：当任务天然是「多个角色各管一摊」（研究员+写手+审稿），或需要把一个大任务拆成可并行的子任务，单图循环已经不够。从 Supervisor 模式起步：一个调度节点决定下一步派给哪个子 agent，子 agent 完成后回交调度。能用单图自建解决就别上多智能体——多智能体的状态边界和调试成本是单图的数倍。
升级路径 从 A2 升到 A3 时，你在 A2 里写的工具函数、state schema、prompt 都能直接搬过来。create_react_agent 用的就是 ToolNode 和 MessagesState，和自建图共享同一套原语。所以「先用 prebuilt 验证需求，再按需拆成自建图」是低风险路径——不是推倒重来，而是把现成循环拆开加节点。

10.3决策树二｜架构模式选择

如果你落到了 A3（自建）或 A4（多智能体），第二棵树回答「套哪种模式」。这些模式在前面的章节都讲过，这里把它们按任务特征重新组织成一张选型图。

图 10.3：决策树二——按任务特征逐级筛选模式；任一步命中「是」即落到对应模式，全部为「否」则回退到纯 ReAct。

几点关键说明：

  • 模式可组合。一棵树画成顺序判断只是为了好读，真实项目里往往是「Plan-Execute + 每步执行带 Reflection + 关键步前 HITL」。组合方式就是把对应节点和条件边一起塞进同一张 StateGraph。
  • 没落到任何模式就回 ReAct。如果你的自建需求只是「比 prebuilt 多一两个条件分支」，别硬套模式，直接在 ReAct 循环上加节点即可。模式是用来解决问题的，不是用来凑数的。
  • RAG 不是独立架构而是插件。检索节点几乎可以插进任何模式——ReAct 里加个 retrieve 工具、Plan-Execute 里每步执行前先检索、Reflection 评审时检索标准答案。所以「需要检索」通常不单独决定架构，而是给已选架构加一个节点。

10.4速查表｜场景 → 推荐方案

把两棵决策树的结论压缩成一张速查表。复杂度栏的「低/中/高」是相对值，衡量的是「从零搭到生产可用」的工程量。

典型场景推荐方案复杂度关键 API

10.5自建 Agent 八项清单

如果你决定自建（落到了 A3 或 A4），下面这八项是任何生产级 agent 都绕不开的清单。每一项对应前面某一章的深入讲解，这里只点出「为什么必须有」和「落地时选哪个 API」。

① 状态设计：reducer 选对

状态是图的唯一事实来源，reducer 决定多节点更新如何合并。消息列表用 Annotated[list, add_messages] 保证幂等覆盖；累加型字段用 operator.add；覆盖型字段用默认。reducer 写错=状态静默丢失，是最难查的坑。

② 控制流：条件边/循环/终止

用 add_conditional_edges 做路由，用条件边回环实现迭代。每个循环必须有明确终止条件：要么模型不再调工具，要么显式判断输出达标。没有终止条件的循环会撞 recursion_limit。

③ 工具设计：粒度与错误处理

工具粒度要平衡：太细模型要调十次，太粗模型控不住。ToolNode 的 handle_tool_errors 必须配，把工具异常转成 ToolMessage 喂回模型让它自纠，而不是整个图崩掉。

④ 记忆：短期 thread_id + 长期 store

会话内记忆靠 compile(checkpointer=InMemorySaver()) + thread_id；跨会话长期记忆靠 compile(store=InMemoryStore())。checkpointer 没启用，HITL 直接不工作。

⑤ 人机协同：关键动作 interrupt

发邮件、删数据这类不可逆动作前，用 interrupt(value) 暂停，把「我打算做什么」抛给客户端，人确认后用 Command(resume=...) 恢复。interrupt 必须放在副作用之前，因为恢复时节点会重跑。

⑥ 容错：retry / 防死循环

节点级重试用 RetryPolicy(max_attempts=, retry_on=) 挂在 add_node 上；图级防死循环靠 recursion_limit 兜底，抛 GraphRecursionError。两者都要配，前者挡偶发失败，后者挡逻辑死循环。

⑦ 流式：stream_mode 选择

前端要 token 逐字出用 stream_mode="messages"；要节点级增量用 "updates"；要完整状态快照用 "values"；节点内自定义事件用 "custom" + StreamWriter。可同时传多个 mode。

⑧ 可观测：tracing

生产 agent 必须能回放每一次节点执行、每一次工具调用、每一次 LLM 调用。LangGraph 内建 tracing，配合 LangSmith 等平台即可看到完整调用链。没有 tracing 的 agent 在线上出问题时只能盲猜。

出厂检验 把这八项当成生产 agent 的出厂检验单。缺任何一项，要么是功能不全（HITL/记忆缺失），要么是线上必炸（无终止条件/无错误处理）。下面用一个最小自建示例把前几项串起来，对照看更清楚。

10.6用代码看｜生产可用最小自建 Agent

这段代码把清单里的 ①②③④⑤⑥⑦ 都落到了具体 API 上：状态用 add_messages + operator.add 双 reducer；控制流用条件边回环形成 ReAct；工具用 ToolNode 接管执行；记忆用 InMemorySaver + thread_id;HITL 用 interrupt() 拦在工具前；容错用 RetryPolicy + recursion_limit；流式用 stream_mode="updates"。⑧ tracing 默认开启，跑起来就能在追踪平台看到完整链路。

代码来源说明 — 一个带 HITL 审批 + retry + 记忆的最小自建 ReAct Agent。
pythonimport operator
from typing import Annotated, Optional
from typing_extensions import TypedDict

from langchain_core.messages import BaseMessage
from langchain_openai import ChatOpenAI
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode
from langgraph.types import interrupt, Command, RetryPolicy


# ① 状态设计：messages 用 add_messages 保证幂等，notes 用累加 reducer
class AgentState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]
    notes: Annotated[list[str], operator.add]   # 多节点追加，不会互相覆盖
    pending_action: Optional[str]


# 工具：发邮件——③ 粒度适中，返回可序列化的字符串
def send_email(to: str, subject: str, body: str) -> str:
    """发送一封邮件。"""
    # 真实实现接 SMTP，这里返回确认
    return f"已发送至 {to}: {subject}"


tools = [send_email]
tool_node = ToolNode(tools)  # ③ 默认 handle_tool_errors 会把异常转成 ToolMessage

model = ChatOpenAI(model="gpt-4o").bind_tools(tools)


# ② 控制流：模型节点，决定继续调工具还是结束
def call_model(state: AgentState):
    response = model.invoke(state["messages"])
    return {"messages": [response]}


# ⑤ HITL：发邮件前暂停问人。批准放行给 tools，拒绝则回一条占位 ToolMessage 并折回 agent
def review_action(state: AgentState):
    last_msg = state["messages"][-1]
    if last_msg.tool_calls:  # 模型想调工具，先让人确认
        tc = last_msg.tool_calls[0]
        question = f"即将执行： {tc['name']}({tc['args']})。批准吗？(yes/no)"
        answer = interrupt(question)  # 第一次抛，恢复时返回人的输入
        if str(answer).strip().lower() != "yes":
            # 拒绝：回一条 ToolMessage 占位(回应这个 tool_call，避免悬空)，并折回 agent
            return {"messages": [{"role": "tool", "content": "用户拒绝执行",
                                   "tool_call_id": tc["id"]}],
                    "pending_action": "rejected"}
    # 批准则放行，交给 tool_node
    return {"pending_action": "approved"}


# ② 路由一：agent 有工具调用 → review；无 → 结束
def should_continue(state: AgentState):
    last_msg = state["messages"][-1]
    if last_msg.tool_calls:
        return "review"
    return END


# ② 路由二：review 后按审批结果分流——批准 → tools；拒绝 → 回 agent(跳过执行)
def after_review(state: AgentState):
    if state.get("pending_action") == "approved":
        return "tools"
    return "agent"   # 拒绝：带着占位 ToolMessage 回模型，让它改主意


builder = StateGraph(AgentState)
# ⑥ retry：模型节点偶发超时自动重试(参数名是 retry_policy=，旧的 retry= 已废弃)
builder.add_node("agent", call_model, retry_policy=RetryPolicy(max_attempts=3))
builder.add_node("review", review_action)
builder.add_node("tools", tool_node)

builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", should_continue, {"review": "review", END: END})
# 关键：review 之后用条件边分流，而不是无条件 review → tools——否则拒绝时 tools 照样会执行
builder.add_conditional_edges("review", after_review, {"tools": "tools", "agent": "agent"})
builder.add_edge("tools", "agent")  # 工具结果回模型，形成 ReAct 循环

# ④ 记忆：启用 checkpointer,HITL 才能跨进程恢复
checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)

# ⑦ 流式 + ④ thread_id 隔离会话
config = {"configurable": {"thread_id": "session-1"}, "recursion_limit": 25}
for chunk in graph.stream({"messages": [("user", "给 alice@example.com 发封会议通知")]},
                          config, stream_mode="updates"):
    print(chunk)
# 运行到 review 节点会暂停，抛出 interrupt；客户端用 Command(resume="yes") 恢复
整张图值得盯的一处： 整张图的控制流是 START → agent → should_continue 分流：模型不调工具就 END，要调工具就先进 review。review_action 里的 interrupt() 拦在工具执行之前——这是铁律，因为恢复时 review 节点会从头重跑，interrupt() 之前若已有副作用就会重复执行。审批结果由 after_review 分流：人回 "yes" 放行到 tools 节点（ToolNode 自动执行 send_email 并把结果转成 ToolMessage），工具结果再回 agent 形成回边；回 "no" 则带着一条占位 ToolMessage 折回 agent，根本不经过 tools——这点必须用条件边保证，因为 ToolNode 取的是「最近一条 AI 消息」的 tool_calls（tool_node.py: tool_calls = list(latest_ai_message.tool_calls)），若拒绝时仍无条件走 review → tools，那封邮件照样会被发出去。retry_policy=RetryPolicy(max_attempts=3)（注意参数名是 retry_policy，旧的 retry= 已废弃）只挂在 agent 节点上挡 LLM 偶发超时，recursion_limit=25 则是图级兜底防逻辑死循环。这就是一张「生产可用最小自建 agent」的样子——比 create_react_agent 多出的恰恰是 prebuilt 装不下的那一段：审批节点。

10.7自建 Agent 四大杀手

这四个坑踩中任何一个，轻则状态错乱，重则线上死循环。逐条对照排查：

  • 循环无终止条件 → GraphRecursionError。条件边回环必须有出口：模型不再产出 tool_calls、或显式判断结果达标、或人拒绝后改走 END（或像 §10.6 那样折回 agent 让模型改主意，但这也得有最终收敛的出口）。光靠 recursion_limit 兜底是「撞墙才停」，不是正常结束。排查时看 should_continue / after_review 的每个分支是否都能在有限步内通向 END。框架默认 recursion_limit 为 10007（源码 _internal/_config.py:32 DEFAULT_RECURSION_LIMIT = 10007，可用环境变量 LANGGRAPH_DEFAULT_RECURSION_LIMIT 覆盖），撞到时会抛 GraphRecursionError: Recursion limit of {N} reached without hitting a stop condition.。所以「没终止条件」的循环不是不报错，只是默认值给得很宽裕，要跑满一万多步才撞墙——死循环会暴露，但可能跑很久。生产里绝不靠撞限兜底，更常见的做法是按需把 recursion_limit 调小（{"recursion_limit": N}）套一道更紧的保险。上面 §10.6 的示例显式设了 recursion_limit: 25：这不是「与默认值对齐」，而是主动收紧——提醒你显式关注这个上限；复杂图需要更多步时按需调大，但前提是退出条件确实能成立。
  • reducer 写错 → 状态静默丢失。最隐蔽的坑。如果 messages 字段没标 Annotated[list, add_messages]，多个节点同时往里写消息时后写会覆盖先写，对话历史凭空少一半。累加型字段（如 notes）没标 operator.add 也是同样问题。症状是「agent 好像失忆了」，但代码里明明 return 了——检查 reducer。
  • checkpointer 没启用 → HITL 无法恢复。interrupt() 本身能抛出 GraphInterrupt 让图暂停（这步不报错），但暂停状态要靠 checkpointer 持久化才能被 Command(resume=...) 恢复——源码 types.py:908 明确： "To use an interrupt, you must enable a checkpointer, as the feature relies on persisting the graph state."。没配 checkpointer 时，Command(resume=...) 会撞到 ValueError("No checkpointer set")（main.py 多处守卫），暂停的图彻底恢复不了。同理 thread_id 没传也会导致每次 invoke 都是新会话，记忆和暂停都找不到。规则：只要用了 interrupt 或要多轮记忆，就必须 compile(checkpointer=...) 且每次 invoke 带 thread_id。
  • 工具返回不可序列化对象 → checkpoint 写入失败。checkpointer 要把整个 state 序列化存盘，工具直接 return 一个数据库连接对象、文件句柄、自定义类的非可序列化实例，会在写 checkpoint 时炸掉。工具的返回值必须是可 JSON/msgpack 序列化的纯数据（str/dict/list/数字等）。需要持有资源时，把资源放进程级单例，工具只返回数据。
注意 这四条里最危险的是「reducer 写错」和「不可序列化返回值」——它们都不在跑通时报错，而是在特定路径下静默出错，往往要等到线上才暴露。开发期就养成两个习惯：state 里凡是会被多节点写的字段，一律显式标 reducer；工具返回值只返回纯数据，资源放外部。能避免 90% 的线上事故。

10.8本代码库导航

选定方案后，你会需要深入源码。本仓库是 monorepo，每个库一个子目录，职责清晰。下面按「从核心到外围」列一遍，帮你按需翻源码而不是从头读。

checkpoint-postgresPostgres checkpointer 与 store。生产持久化的首选。上线多副本、要跨进程恢复状态时用。
checkpoint-sqliteSQLite checkpointer 与 store。单机持久化的轻量选择。单进程服务、本地工具、CI 测试里用。
cliLangGraph 命令行，本地起开发服务器、部署。本地调试 graph、或打包部署到 LangGraph 平台时用。
sdk-pyPython 客户端 SDK，调 LangGraph Server 的 REST API。把 agent 部署到服务端后，前端/后端用这个 SDK 调用。
sdk-jsJS/TS 客户端 SDK，同上但给前端用。浏览器或 Node 端调 LangGraph Server 时用。

依赖关系也值得记一下，方便判断改动影响面：checkpoint 是最底层，被 checkpoint-postgres/checkpoint-sqlite/prebuilt/langgraph 依赖；prebuilt 只被 langgraph 依赖；sdk-py 不依赖 langgraph 核心，只依赖 httpx/orjson 等基础库（方向反过来：cli 依赖 sdk-py）。所以改 checkpoint 的接口会波及最广，改 prebuilt 影响次之，改 sdk-py/sdk-js 基本独立。选型时如果只是用，从 langgraph+prebuilt 入手就够；要部署才需要 cli 和 sdk-*。

10.9生态动态｜System One 模型：把循环里的快判断换成专用分类模型

第 10 章作为收口章，前面的两棵决策树回答「选哪种架构」，这一节补上下一层问题：选定之后，循环里每一步该调什么。要介绍的 System One 模型和前面章节有三处直接接口：

  • 改的是决策树的成本项，不是判据。本章两棵树都按「任务特征」逐级升级——A2→A3→A4 的每一步由「任务需不需要」驱动。Jev 改变的是另一层的核算：以前「要不要再插一个判断节点」要掂量一次 LLM 调用的延迟和开销，这正是大家习惯把多个判断塞进一个 prompt 的原因；一个判断接近零成本之后，「每个判断一个节点、代码里组合」反而成为顺手的默认。
  • 落点就是第 05 章的 ReAct 循环。博客开篇给 agent 的定义——LLM 决定、工具执行、模型评估结果、继续循环——就是第 05 章手写的那张「agent 节点 ↔ tools 节点」条件边回环。循环里「模型决定是否调工具」「评估工具结果」这类步骤，本质是快判断而非开放推理，正是 System One 模型声称擅长的部分。
  • 置信度门控与第 06 章 HITL 是同一模式的两种实现。文档的语音银行示例（0.6 地板挡住没把握的请求；「批准转账」要 0.85 以上否则先向用户确认）结构上就是「置信度不够 → 落回人工」，和 interrupt() + Command(resume=...) 做的事同构——差别只在触发条件从「每次都问」变成「低置信才问」。AutoModeMiddleware 在工具执行前拦截风险调用，对应的是 harness 圈的 PreToolUse 检查点（claude、codex、cursor 内置同类机制但闭源）。

TypeSafe AI 发布的模型 Jev（当前版本 jev-1.13.0）不是生成式 LLM，而是官方所称的 System One 模型——名字取自卡尼曼《思考，快与慢》对两种思维模式的区分：System 1 快而直觉，System 2 慢而深思。Jev 只做前者：给定材料，做出快而聚焦的判断。它不写回复、不产代码、不解释推理；训练目标是校准（官方称用强化学习做校准决策训练，RLCD）——让概率对齐真实结果的不确定性。注意校准是跨预测组的统计性质，不保证单次回答正确。官方口径：分类任务上推理至多比同类 LLM 快 200 倍、成本低 400 倍。

这一节把官方文档（docs.typesafe.ai）里对工程决策有影响的内容收拢在一起：调用形态、问题类型、多问组合原则、置信度用法、官方模式与 cookbook 实测、失败模式清单、模型规格与接入方式，末尾回到本页的两棵决策树。

调用形态：state + questions

请求（POST /v1/systemone）只有两个核心字段。state 是要评估的内容：字符串、JSON 对象或数组皆可——官方比喻成「拿给一排专家做判断前呈现的材料」，建议优先用对象，每个字段有名字、关系清晰，只有单段文本的简单场景才用字符串（一个退化工单的 state 可以同时装对话记录、订单数据、退款政策）。questions 是一组问题：所有问题看同一个 state、各自独立评估，返回带类型的答案和概率。问题里可以用点路径引用 state 的具体字段（如 ticket.messages[0].text、refund_policy），指明判断哪一部分。

两条硬约束现在就要记住：只收文本，图片、音频、视频要预先转成文字或结构化字段；主训语言是英语，包括中文（CJK）在内的其他语言能跑但精度更低——用在中文语料上先自测。

三种问题类型与选择标准

类型回答什么返回映射到代码
Choice从固定选项里选一个（选项间无序：路由到哪个部门、文档是什么类型）choice + 每个选项的概率 + confidence分支
Score沿有序等级打分（每档含义由你定义，分数可落在两档之间）score + 等级对照 + 分布 + confidence阈值
Noul是非题（概率本身就是有用信号）noul（0~1，命题为真的概率）if

每个问题有四要素：ID（只给你的代码用，不发给模型——完整问题要写在 instructions 里，别指望 ID 自解释）、type、instructions（评估逻辑全在这）、criteria（Choice 的选项 / Score 的等级 / Noul 的可选说明）。criteria 要和 instructions 说的是同一件事，一个问 A、另一个描述 B 会让精度变差。

类型怎么选？两个易混点文档讲得很直白：想测程度用 Score，别用 Noul——Noul 的 0.5 表示模型给「是」「否」等概率（不确定），不是「中等水平」；问「这个候选人 Python 强吗」这种程度问题，该用带定义档位的 Score。其次是代码能直接执行哪个答案就用哪个：Choice 对应分支、Score 对应阈值、Noul 对应 if，列表可能不全时给 Choice 加一个 other 选项兜底。

返回的答案有两个可组合性质：被约束在你给的选项里——模型只会返回选项或等级上的概率分布，代码不用从生成的散文里捞值；彼此独立——一个答案不是另一个问题的隐藏上下文，增删问题不影响其他问题的结果。

多问组合：拆小判断，代码里加权

一次请求内所有问题并行评估：多加问题几乎不增加延迟，只多付问题本身的 token，文档原话是「问一个可能不需要的问题接近免费」。由此有三条组合原则：

  • 每个问题只问「懂行的人看一眼材料就能答」的判断。「这消息急吗」是好问题；「分析这条消息并给出最佳行动」不是——那是慢推理，应该拆成小问题、代码里组合。
  • 复合判断拆成单因素问题加权重（官方称 Composite scoring 模式）。比如工单优先级 = 严重度 + 挫败度 + 可复现信息量三个 Score，权重由你的代码定；结果和团队判断不符时改权重重跑，不用改 prompt。
  • 投机式提问（Speculative fan-out 模式）：把可能用不到的问题也一并发出，代码事后挑着用——不是 bug 报告就忽略 severity 答案，换来的省掉一整轮往返。
二次请求是例外 同一请求内的问题互相独立：一个答案不会变成另一个问题的上下文。真正需要第二次请求只有一种情况——没有第一个答案就构造不出第二个请求：要按答案取数据、定 state 的构成、或定下一题的选项。官方给的正面例子是选 skill：先对 182 个候选全量排序并问「这轮要不要 skill」，再把 top-3 的全文取回来精读——第二次请求用了第一次拿不到的证据。反过来，如果第二个请求的问题本可以直接塞进第一次，就该塞进去。
代码来源说明 — TypeSafe 官方 quickstart 的支持工单示例（摘录，注释为本书说明）
pythonfrom typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()  # 从环境变量读 TYPESAFE_API_KEY，默认模型 jev-latest

response = client.system_one(
    state="Hi, I've been trying to connect my Stripe account for 3 days "
          "and it keeps failing. I'm losing sales. Please help ASAP.",
    questions={
        "department": Choice(
            instructions="Which team should handle this",
            criteria={
                "billing": "Payment or subscription issues",
                "technical": "Bugs or integration problems",
                "sales": "Pricing or account questions",
            },
        ),
        "frustration": Score(
            instructions="How frustrated the customer appears",
            criteria=["Calm, just stating facts",
                      "Frustrated but civil",
                      "Very angry, strong language"],
        ),
        "is_urgent": Noul(
            instructions="The message conveys urgency or time-sensitivity",
        ),
    },
)

print(response.answers["department"].choice)   # "billing"，另带各选项概率与 confidence
print(response.answers["frustration"].score)   # 1.035，可落在两档之间
print(response.answers["is_urgent"].noul)      # 0.999

置信度：把「要不要行动」也变成数据

Choice 和 Score 的答案自带 confidence，它是从概率分布的形状算出的统计量：分布尖（集中在某一档）说明有把握，平（各档接近）说明没把握。Noul 没有这个字段——它的概率本身就是信号。官方给的是默认算法但不锁死：完整的 probabilities 就在响应里，你可以按自己的场景另算。文档里有一句值得记住的话：一个不能表达诚实不确定性的系统不可信。

用法是三档分流：高置信自动执行；中置信谨慎处理（要用户确认、标记复审、或先补信息）；低置信不行动，转人工或回退。关键在阈值随风险伸缩，不是一刀切——文档的语音银行示例：0.6 作为置信度下限，挡住模型真正没把握的请求；「查余额」0.6 就够（最坏情况是读错余额，可恢复）；「批准转账」要 0.85 以上，否则先向用户口头确认。你的代码编码你的风险偏好，阈值要从保守值起步、用自己的数据调。

官方归纳的四个模式与 cookbook 实测

文档把用法归纳成四个架构模式，都是「Jev 判断、代码决策」的分工：

模式一句话要点
Speculative fan-out一次调用发出所有可能用到的问题（含推测性的），代码按结果挑着用多加问题接近免费，省往返

模型规格与适配边界

定价按输入 token 计：$0.042/百万（$42/十亿），输出 token 免费。限流 25 万 token/秒、1200 请求/分钟，官方注明随容量动态调整。上下文：单请求 64k token（state + 全部问题合计），且 state + 最长单个问题不超过 32k。

版本与别名：别名 jev-latest / jev-preview 当前都指向 1.13.0，但别名背后的模型会随发布漂移——如果你的置信度阈值是针对某个版本调的，直接 pin 版本号（jev-1.13.0），响应的 model 字段会回报实际作答的版本 ID，方便留痕。

适配方式是这套产品里比较特别的一点：不做客户数据微调、不做 LoRA，所有账户共享同一份权重，领域适配全走请求侧——专有内容放 state、领域规则和边界情况写进 instructions/criteria、大判断拆成原子问题在代码里组合。不拿客户请求/响应训练，企业客户可签零数据留存（ZDR）。

接入：SDK、agent skill 与 LangChain 中间件

Python SDK（typesafe-sdk，要求 ≥3.10）提供同步/异步 client 和类型化的 Choice/Score/Noul 问答对象，RetryPolicy 默认指数退避并尊重 retry-after；JavaScript SDK（@typesafe-ai/sdk）同构。官方还给 coding agent 发了一个 skill（Claude Code 里 claude plugin marketplace add typesafe-ai/skills 后 claude plugin install typesafe@typesafe-ai），它的核心指令之一是纠正 agent「一问一调」的习惯——把多个问题塞进一次调用，包括只对部分输入有意义的问题。

LangChain 侧的入口是 langchain-typesafe 包的 TypeSafeClassifier：.invoke() 传 state + questions，拿回分类结果而不是聊天回复；state 可以直接传 LangChain messages，从节点或 middleware 里用 agent 现成的上下文调它。博客演示了两个 create_agent 中间件。ModelRouterMiddleware 用 Jev 评估用户消息的难度并按 criteria 选模型——便宜模型接「直接查询、抽取、局部修改」，强模型接「架构与高风险决策」，指令是「选能完成任务的最低成本模型」；路由结果整个 run 内生效，概率与置信度随 agent state 流转。AutoModeMiddleware 则在工具执行前用 Jev 检查风险并拦截：

代码来源说明 — LangChain 博客的 Auto Mode 示例（摘录，注释为本书说明）
pythonfrom langchain.agents import create_agent
from langchain_typesafe.experimental.middleware import AutoModeMiddleware

guardrail = AutoModeMiddleware(tools=["bash"])  # 这些工具执行前先过一遍 Jev 风险检查
agent = create_agent("openai:gpt-5.6-luna", middleware=[guardrail])

Auto Mode 这段博客点了一个 harness 圈内部皆知的事实：claude、codex、cursor 内置的「执行前分类危险操作」机制一直锁在闭源部分；现在有了便宜够快的分类器，普通 agent 也能套用同一模式。对照第 06 章：这相当于给 HITL 加了一个自动档——高置信低风险的工具调用直接放行，可疑的才落到 interrupt() 等人。博客还列了几个已上线的用法：Browserbase 用它跑低成本浏览器操作 agent、实时交易 agent、大规模邮件分诊。

回到本页的两棵决策树：Jev 不改判树本身，改判据的成本项。具体到前面章节：第 05 章 ReAct 循环里的「是否调工具」「结果评得对不对」，第 08 章 Reflection 的评审节点、第 07 章多智能体的路由边，这些点位上的判断现在多了一个「不调 LLM、改调分类模型」的选项；第 06 章的 interrupt() 前面可以垫一道置信度粗筛，只把低置信的落到人。判据和本章一贯的原则相同：架构服务于任务——先分清循环里的哪一步是开放推理、哪一步只是快判断，再决定每一步该调什么。它替代的是「LLM 当分类器」的用法，替代不了推理和生成。

10.10选型原则

选型 先 prebuilt 验证，再按需自建；架构服务于任务，别为复杂而复杂。能用 model.invoke() 就别上 Agent；能用 create_react_agent 就别拼 StateGraph；能用单图自建就别上多智能体。每一次升级都必须有明确的任务特征驱动，而不是「听起来更高级」。生产化的重心永远在状态设计、终止条件、错误处理、HITL 和可观测这五件事上——它们决定了 agent 是能上线还是只能演示。

Q1 · 需求：「客服 bot，多轮对话要记住上下文，工具只有查订单一个。」决策树一落在哪？如果下周需求变成「查不到订单时要先问用户再重查」，架构要动哪一处？
第一问落在 A2：create_react_agent + checkpointer——单一工具、无规划、无审批，prebuilt 循环完全够用，加 checkpointer（compile 时挂）和 thread_id 就有了多轮记忆。第二问的「问用户再重查」是典型 HITL：interrupt() 暂停要人输入。此时仍不必拆成自建图——create_react_agent 本身支持 interrupt（interrupt_before/interrupt_after 参数），工具查不到时让模型发起提问即可。真正逼你升 A3 的特征是「查不到时要按规则走固定分支（重查次数上限、转人工）」这类 ReAct 循环装不下的控制流。升级路径是 10.2 说的低风险路径：工具、state schema、prompt 原样搬，把循环拆开加节点。
Q2 · 图 10.2 里 A2→A3→A4 是单向升级，Q4 的「否」回退到 A2。为什么回退箭头只画在 A4→A2 而不是 A4→A3？说出这个设计想传达的工程判断。
因为「拆成多智能体」是最难回头的一步：状态被切成多个子图 schema、协调逻辑分散到多个 supervisor/handoff 节点，一旦拆开，合并回单图的成本远高于在单图里继续加节点。而 A3 自建图收缩回 A2（把自建循环重新收敛成 prebuilt 的标准循环）通常只是「把自定义节点删掉、换回 create_react_agent」，工具和 schema 都通用。所以回退箭头想传达的是：多智能体是「确认单图装不下之后」才该做的决定，而且拆之前先想好「如果拆错了，把子图重新 add_node 回主图的路径」——子图即节点（07 章）保证了这条退路存在，但 schema 对接要提前设计。Q4 的「否」正是这个检查点：拆出来的角色真的各自独立吗？不是，就回 A2。
Q3 · 10.5 清单第②项说「每个循环必须有明确终止条件」。有同学说：「不用管，撞 recursion_limit 会抛 GraphRecursionError，天然安全。」这个说法错在哪？两个兜底（recursion_limit 与业务计数器）分别挡什么？
错在把「最后会报错」当成「安全」。recursion_limit 是最外层的保险丝：默认 10007（_internal/_config.py:32），按 super-step 计数。一个「agent→tools」轮次就是 2 个 super-step，逻辑死循环的图会真的转几千圈——几千次 LLM 调用、几千次工具执行的账单和延迟先到，GraphRecursionError 最后才到，而且它抛在用户请求路径上，体验是硬崩。recursion_limit 挡的是「框架层的失控」（比如遗漏的终止分支），它不知道你的业务上「反思 3 轮就该收敛」；业务计数器（iterations >= MAX_ITER 就 return END）挡的是「业务层的过度迭代」，两者计数的东西不同——前者数 super-step，后者数业务轮次——所以互相替代不了。此外把 recursion_limit 调小（如 25）能让失控更早暴露，但它仍不是终止条件本身。
Q4 · 速查表里「发邮件/删数据」推荐 ReAct + HITL。如果直接去掉 interrupt、让 agent 自动执行，再配上 RetryPolicy(max_attempts=3)，线上会出什么问题？这说明 HITL 和 Retry 各自管什么？
RetryPolicy 管的是「失败后原样重试」——节点抛异常时按策略重新执行，默认参数不变。对发邮件这种不可逆副作用，第一次可能已经发出去了，异常发生在「发送后的确认步骤」上，重试就是再发一封；幂等的工具（查询）重试无害，非幂等的动作（发邮件、删数据、付款）重试是放大事故。这正是 HITL 存在的原因：interrupt 在副作用发生前把「我打算做什么」亮给人审批，人确认后才执行——它管的是「该不该做」，Retry 管「失败了再来一次」。两者管的对象不同，互相不可替代：不可逆动作前的审批不能靠重试补，偶发的网络抖动也不该每件事都问人。生产配置通常是：非幂等动作 interrupt + 人确认；幂等动作 RetryPolicy 自动兜。
Q5 · 10.9 说 System One 的判据是「循环里的哪一步是开放推理、哪一步只是快判断」。用这个判据检查 08 章的三个模式：Reflection 的评审、CRAG 的 grading、Plan-and-Execute 的 planning，哪个最适合换小模型，哪个最不适合？为什么？
最适合的是 CRAG 的 grading：输入是「文档 × 问题」，输出是「相关/不相关」的三分类，判断空间封闭、标准相对客观，正是「快判断」——换小模型或专用分类器收益最直接（每个检索结果都要评，调用量大）。次适合的是 Reflection 的评审：输出是「达标/不达标 + 批评意见」，判断部分封闭，但「批评意见」是开放生成，换小模型会损失批评质量，可以只把「达标判定」换成小模型、批评仍用大模型。最不适合的是 Plan-and-Execute 的 planning：拆解任务需要理解全局、权衡步骤依赖，是典型开放推理，判错会传导到后面所有执行步骤——这一步省的钱会被 re-planner 的额外轮次加倍还回来。判据落点：输出空间封闭、错误局部、调用频次高的点位适合小模型；输出空间开放、错误会级联的点位留给强模型。
