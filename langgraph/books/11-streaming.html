流式输出:让用户实时看到 Agent 在做什么

Agent 跑起来往往要几秒到几十秒,如果用户只能干等一个最终结果,体验会很差。LangGraph 的 stream() 提供七种 stream_mode,既能拿到每步状态增量,也能逐 token 流式 LLM 输出,还能让节点主动推送自定义数据。本章基于本代码库 langgraph/types.py 与 pregel/main.py 的真实 API 讲透。

11.1为什么 streaming 是"一等公民"

一个 ReAct Agent 从用户提问到给出答案,中间要经历"LLM 思考 → 决定调工具 → 工具执行 → LLM 再思考 → …"。如果整个过程是黑盒,用户只能盯着 loading 转圈——这在生产里几乎不可接受。LangGraph 把流式做成了框架的一等能力:执行图的每一步、LLM 的每一个 token,都可以实时吐给前端。

关键在于:streaming 在 LangGraph 里不是"额外加的补丁",而是和图执行同源的——图本身就是一个 super-step 一个 super-step 地推进,每个 super-step 自然就是一个流式事件点。所以你不需要为了流式去改图结构,只需要在 stream() 调用时告诉它"你想看哪些切面"。

11.2七种 stream_mode:选你要的切面

这是本章的核心。源码里 StreamMode 是一个 Literal(见 langgraph/types.py:122),明确定义了七种值:

langgraph/types.py — StreamMode 定义
pythonStreamMode = Literal[
    "values", "updates", "checkpoints", "tasks", "debug", "messages", "custom"
]
读懂这段: 这七种不是任意拼凑的,各有明确职责。下面表格把每种模式"吐什么、什么时候吐、要不要 checkpointer"讲清——这三个维度是选 stream_mode 时的全部判断依据。
Mode吐什么触发时机需 checkpointer
values每步之后的完整 state每个 super-step 后(含 interrupt)否
updates每步变化的字段(按节点名分组)每个节点完成后否
messagesLLM 逐 token 输出 (chunk, metadata)节点内任何 LLM 调用产 token 时否
custom节点内用 StreamWriter 主动推的任意数据节点内调用 writer(...) 时否
checkpoints检查点事件(格式同 get_state())每次创建 checkpoint 时是
tasks任务开始/结束事件(含结果与报错)每个 task 开始与结束时否
debugcheckpoints + tasks 的合集 + 额外元数据上述两者触发时部分(仅 checkpoints 部分需)

注意三个细节:第一,messages 是逐 token 的——这是官方"first-class streaming"卖点对应的能力,能让你前端像 ChatGPT 那样一个字一个字蹦出来。第二,只有 checkpoints 模式必须配 checkpointer:它的 emit 被 if self._checkpointer_put_after_previous is not None 守卫,无 checkpointer 时静默跳过;而 tasks 的 emit 无此守卫,有没有 checkpointer 都正常吐。第三,debug 本质是 checkpoints + tasks 的合集(源码 docstring 原文: Emit `"checkpoints"` and `"tasks"` events for debugging purposes),不是独立信息源——所以无 checkpointer 时 debug 仍会吐 task 事件,只是少了 checkpoint 事件。

最常用的两种 生产里 90% 的场景只需要 updates 和 messages:updates 用来在 UI 上展示"Agent 正在做什么"(哪个节点跑完了、改了哪些字段),messages 用来把 LLM 的回答逐 token 推给前端。其余几种偏向调试和可观测。

11.3updates / values:拿每步状态

updates 和 values 是最基础的两个模式,区别只在"吐完整 state 还是只吐变化部分"。values 每个 super-step 吐一份完整 state(适合前端整体刷新),updates 只吐当步变化的字段、按节点名分组(适合增量更新、日志展示)。

updates 模式:看每个节点的增量
python# stream 签名(见 pregel/main.py:2655):
#   stream(input, config=None, *, stream_mode=None, version="v1", subgraphs=False, ...)
for chunk in graph.stream(
    {"messages": [("user", "讲个笑话")]},
    config,
    stream_mode="updates",   # 每个节点完成时输出增量
):
    # v1 默认下,chunk 是 {节点名: 该节点返回的更新}
    for node_name, state_update in chunk.items():
        print(f"节点 `{node_name}` 更新: {state_update}")
# 输出示意:
# 节点 `agent` 更新: {messages: [AIMessage(tool_calls=[...])]}
# 节点 `tools` 更新: {messages: [ToolMessage(...)]}
# 节点 `agent` 更新: {messages: [AIMessage(content="...笑话...")]}
读懂这段: 注意默认 version="v1" 时,chunk 是裸 dict,没有 type/ns 等元信息。同一 step 里若有多个节点并行,它们的 updates 会分开吐(源码 docstring: those updates are emitted separately),而不是合并——这是并行场景下需要留意的。

11.4messages:逐 token 流式 LLM 输出

这是体验上最重要的一种。messages 模式会捕获节点内任何 LLM 调用产生的 token,以 (message_chunk, metadata) 二元组的形式逐个吐出。源码里 MessagesStreamPart 的定义(见 types.py:288)明确: data 是 tuple[AnyMessage, dict],metadata 含 langgraph_step、langgraph_node、langgraph_triggers 等键。

messages 模式:逐 token 输出
pythonfor chunk in graph.stream(
    {"messages": [("user", "讲个笑话")]},
    config,
    stream_mode="messages",
    version="v2",   # 用 v2 拿统一结构,见 11.6
):
    if chunk["type"] == "messages":
        message_chunk, metadata = chunk["data"]
        if message_chunk.content:
            print(message_chunk.content, end="", flush=True)
        # metadata["langgraph_node"] 告诉你 token 来自哪个节点
        # 可用它过滤,比如只展示 agent 节点的回答
读懂这段: message_chunk 通常是 AIMessageChunk——它和完整 AIMessage 同构,只是 content 是增量片段。把所有 chunk 的 content 拼起来就是完整回答。metadata 里的 langgraph_node 很有用:多 agent 图里,你能据此区分"这段话是检索 agent 说的还是写作 agent 说的"。
子图里的 token 默认拿不到 默认 subgraphs=False 时,子图内部的 LLM token 不会被 emit——嵌了 create_react_agent(本质是子图)时,不开 subgraphs=True 就拿不到它内部的逐 token 输出。具体机制与诊断见 §11.7,常见错误形态见 §11.10③。

11.5custom:节点主动推送任意数据

前三种模式都是"框架自动吐",custom 不同——它让你在节点内部主动往流里推任意数据。这靠 get_stream_writer()(在 langgraph.config)实现,它返回一个 StreamWriter(类型定义在 types.py:138: StreamWriter = Callable[[Any], None])。

典型用途:进度条、中间产物、或者接入非 LangChain 原生模型的流式输出(比如直接调 OpenAI SDK 的流式接口,在每个 chunk 上 writer(chunk),外部用 custom 接收)。

custom 模式:节点内主动推送
pythonfrom langgraph.config import get_stream_writer

def my_node(state: State):
    writer = get_stream_writer()          # 节点内获取 writer
    writer({"progress": "开始处理..."})   # 主动推送自定义数据
    # ... 做一些事 ...
    writer({"progress": "处理完成", "intermediate": result})
    return {"answer": final}

# 接收端:用 stream_mode="custom" 拿到 writer 推的数据
for chunk in graph.stream(inputs, stream_mode="custom", version="v2"):
    if chunk["type"] == "custom":
        print(chunk["data"])   # {"progress": "开始处理..."}
读懂这段: StreamWriter 源码注释明确:"Always injected into nodes if requested as a keyword argument, but it's a no-op when not using stream_mode='custom'"。也就是说,除了 get_stream_writer(),你也可以直接在节点签名里声明形参 writer: StreamWriter 让框架注入(见 graph/_node.py 的节点 Protocol)。但注意:没开 custom 模式时,writer 是空操作,推了也收不到。
Python < 3.11 的异步坑 get_stream_writer() 源码 docstring 有明确警告:它依赖 contextvar 传播,如果你用 Python < 3.11 且异步运行 LangGraph,它不工作(3.11 起 asyncio.create_task 才正确传播 contextvar)。同步运行不受影响。生产环境建议直接用 Python ≥ 3.11。

11.6version="v2":统一的 StreamPart 结构

这是容易忽略但很重要的一点。stream() 的 version 参数(见 pregel/main.py:2670)默认是 "v1",此时不同 stream_mode 返回的 chunk 形状不一——裸 dict、二元组混着来,你得按模式分别解析。version="v2" 之后,所有 chunk 统一成 StreamPart 结构:{"type": ..., "ns": ..., "data": ...},不再需要分情况处理。

图 11.1:v1 各模式返回形状不一(裸 dict / 二元组 / 任意),v2 统一成 {type, ns, data}。生产代码建议直接用 v2。
v2:组合多种 mode,统一解析
python# 传 list 一次组合多种 mode;v2 下每个 part 都有 type 字段
for part in graph.stream(
    inputs, config,
    stream_mode=["values", "updates", "messages", "custom"],
    version="v2",
):
    if part["type"] == "updates":
        # part["data"] 是 {节点名: 更新}
        ...
    elif part["type"] == "messages":
        msg, metadata = part["data"]
        ...
    elif part["type"] == "custom":
        # part["data"] 是节点 writer 推的任意数据
        ...
读懂这段: 组合多种 mode 时,传一个 list 给 stream_mode。源码 docstring 说明:组合模式下,v1 会输出 (mode, data) 元组,v2 则每个 part 自带 type 字段——这就是 v2 的价值:你用一个 if part["type"] == ... 分发就能处理所有模式,代码更干净。ns 是命名空间元组,标明事件来自哪个(子)图,配合 subgraphs=True 用于区分多层图的事件来源。

11.7subgraphs:要不要看子图内部

前面提到 subgraphs 参数(默认 False)。它的作用是:是否把子图内部的事件也吐出来。源码 docstring(main.py:2713)明确: subgraphs=True 时,事件会带 namespace 标明来源路径,形如 ("parent_node:<task_id>", "child_node:<task_id>")。

subgraphs=True:拿子图(如 create_react_agent)内部的 token
python# 假设外层图里有个节点是 create_react_agent 构建的子图
for part in graph.stream(
    inputs, config,
    stream_mode="messages",
    subgraphs=True,        # 关键:否则拿不到子图内部 token
    version="v2",
):
    if part["type"] == "messages":
        msg, metadata = part["data"]
        # part["ns"] 标明这段 token 来自哪一层子图
        # 例如 () 表示外层图, ("worker:abc",) 表示 worker 子图内
        print(part["ns"], msg.content, end="")
读懂这段: create_react_agent 返回的是一个 CompiledStateGraph,作为节点嵌进外层图时它就是个子图。不开 subgraphs=True,messages 流会在子图边界"断掉"——你能看到子图节点的 updates,但看不到它内部 LLM 的逐 token 输出。多 agent 场景下这是个必踩的坑。

11.8tags 与 nostream:精细控制哪些 LLM 调用入流

有时你不希望某次 LLM 调用出现在 messages 流里——比如内部的结构化输出、路由判断,这些中间步骤不需要暴露给前端。LangGraph 用一个特殊 tag 解决:给模型加 tags=["nostream"],该次调用会照常执行,但不产生 messages 流事件。

tags=["nostream"]:让某次 LLM 调用不出现在流里
python# 路由用的 LLM 调用,不需要让用户看到它的 token
router_llm = model.bind(tags=["nostream"])
decision = router_llm.invoke([...])   # 照常执行,但 messages 流里看不到它

# 源码依据:constants.py:24  TAG_NOSTREAM = sys.intern("nostream")
# pregel/_tools.py:111  if tags and TAG_NOSTREAM in tags: return None  (不 emit)
读懂这段: 源码里 TAG_NOSTREAM(在 constants.py)就是字符串 "nostream"。pregel/_tools.py 的处理逻辑明确:如果某次调用的 tags 里含 nostream,它返回 None(即不 emit 到 messages 流)——注释原文是 "caller explicitly opted out"。这是精细控制流式可见性的标准手段。

11.9stream_events(v3):事件驱动的统一入口

除了 stream(),LangGraph 还提供 stream_events()(见 pregel/main.py:3638),它支持 version: Literal["v1","v2","v3"]。其中 v1/v2 兼容 LangChain 的 Runnable.stream_events(吐 StreamEvent dict);v3 是较新的实验性 API,返回一个 GraphRunStream 对象,调用方通过迭代它的 typed projection 驱动——不开后台线程。

stream_events(version="v3"):可拿 output/interrupted/interrupts
python# v3 是事件驱动的统一入口,尤其适合配合 interrupt 用
run = graph.stream_events(inputs, config=config, version="v3")

# 无论注册了哪些 transformer,这几个属性都能用:
final = run.output          # 最终输出
if run.interrupted:
    print(run.interrupts)   # [Interrupt(value='...'), ...]  (list)
    # 配合 Command(resume=...) 恢复,见第 06 章

# 迭代拿流式事件
for part in run:
    ...   # 按 part 的类型处理
v3 是实验性的 源码 docstring 明确标注: version="v3" 的 API is experimental and may change。如果你要长期稳定的生产代码,目前更稳妥的是 stream(..., version="v2")。stream_events(v3) 的优势在于和 interrupt 配合时能直接拿到 run.interrupts——这是第 06 章人机协同里恢复流程的入口。

11.10新手常犯的错误

① checkpoints 模式静默不吐——因为没配 checkpointer
python# 没给图 compile checkpointer,却想用 checkpoints 模式看检查点事件
graph = StateGraph(State).add_node(...).add_edge(START, ...).compile()   # 没有 checkpointer=

for part in graph.stream(inputs, stream_mode="checkpoints", version="v2"):
    print(part)   # 什么都不输出!for 循环一次都不进,也不报错

# 原因:checkpoints 事件的 emit 被 `if self._checkpointer_put_after_previous is not None` 守卫
# (见 _loop.py:632)。无 checkpointer 时该字段为 None,emit 被短路 → 静默产出 0 个事件。
# 注意:tasks 模式不受此影响(emit 在 _loop.py:674 无守卫),没有 checkpointer 也照常吐;
# debug 模式 = checkpoints + tasks,无 checkpointer 时仍会吐 task 事件,只是少了 checkpoint 事件。
# 修复:想看 checkpoint 事件就 compile 时传入 checkpointer;只想看任务流用 tasks 即可,不必配 checkpointer。
graph = StateGraph(State).add_node(...).add_edge(START, ...).compile(checkpointer=InMemorySaver())
读懂这段: 这是 streaming 最隐蔽的坑——不报错、不输出。"需 checkpointer"的只有 checkpoints 模式:无 checkpointer 时它静默产出 0 个事件,而不是抛异常。源码依据是 _loop.py:632 的 if self._checkpointer_put_after_previous is not None 守卫——无 checkpointer 时该字段为 None,emit 被短路。但别误伤 tasks:它的 emit(_loop.py:674)没有这道守卫,有没有 checkpointer 都正常工作。排查时一旦发现 checkpoints 流"空跑",先查图有没有 checkpointer,再看 stream_mode。
② custom 模式收不到数据——writer 在异步 + Python < 3.11 下拿不到 runtime
python# Python 3.10 + 异步运行,节点里调 get_stream_writer()
async def my_node(state: State):
    writer = get_stream_writer()          # 触发 RuntimeError
    ...

# 报错(见 config.py:29):
#   RuntimeError: Called get_config outside of a runnable context

# 原因:get_stream_writer() -> get_config() -> 从 contextvar 取 runtime。
# Python < 3.11 的 asyncio 不传播 contextvar(get_stream_writer docstring 明确警告),
# 于是取不到 runnable config。同步运行不受影响。
# 修复:升级到 Python ≥ 3.11(见 §11.5 callout),或在同步上下文里运行。
读懂这段: §11.5 的 callout 已点出 Python < 3.11 的异步坑,这里补上具体症状:不是静默 no-op,而是 get_stream_writer() 内部调用 get_config() 时,因 contextvar 没传播而取不到 runnable config,抛 RuntimeError: Called get_config outside of a runnable context(config.py:29)。同步运行 + 任意 Python 版本都正常——这进一步说明生产环境锁定 Python ≥ 3.11 的必要性。
③ 子图内部的 LLM token 拿不到——忘了 subgraphs=True
python# 外层图里嵌了 create_react_agent 作为子图节点
for part in graph.stream(
    inputs, config,
    stream_mode="messages", version="v2",   # 漏了 subgraphs=True
):
    ...   # 只看到外层图的 updates,子图内 LLM 的逐 token 全部缺失——但不报错

# 原因:messages 的事件源是 _tools.py 的处理器,它在 `subgraphs=False` 时
# 对子图内的调用直接 `return None`(_tools.py:117: if not self.subgraphs and len(ns) > 0 ...)。
# 修复:显式传 subgraphs=True,并用 part["ns"] 区分事件来自哪一层子图(见 §11.7)。
for part in graph.stream(inputs, config, stream_mode="messages", subgraphs=True, version="v2"):
    ...
读懂这段: 这是 §11.4 / §11.7 都强调过的高频坑,这里收口为一条可对照的诊断步骤:messages 流"断"在子图边界、且无任何报错时,检查是否漏传 subgraphs=True。源码依据是 _tools.py:117——当 subgraphs=False 且事件来自非父级子图(len(ns) > 0 and ns != self.parent_ns)时,处理器返回 None,token 不 emit。三个坑的共同特征是"静默失败":没有异常、没有日志,只是流里缺东西——这是 streaming 调试时最该建立的肌肉记忆。

11.11选型小结:该用哪种?

需求推荐
前端逐字显示 LLM 回答stream_mode="messages" + version="v2";嵌套子图加 subgraphs=True
展示"Agent 正在做什么"的进度stream_mode="updates",按节点名展示
自定义进度条 / 中间产物stream_mode="custom" + 节点内 get_stream_writer()
同时要状态增量 + token + 自定义stream_mode=["updates","messages","custom"] + version="v2"
调试图执行 / 排查问题stream_mode="debug"(= checkpoints + tasks)
配合 interrupt 做人机协同stream_events(version="v3") 拿 run.interrupts
隐藏内部 LLM 调用给该模型 bind(tags=["nostream"])

一句话:生产用 stream(version="v2") 拿统一结构,messages 显示给用户、updates 显示给日志、custom 做自定义进度。子图场景别忘了 subgraphs=True,Python 环境 ≥ 3.11。这是把 Agent 从"黑盒等待"变成"透明实时"的关键一层。
