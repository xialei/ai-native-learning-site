06 · 人机协同 — 让 Agent 学会「停一停，问问人」

当 Agent 准备执行发邮件、删数据、付款这类不可逆动作时，先暂停、把决策权交还给人——这就是 Human-in-the-Loop。LangGraph 用 interrupt（）、Command（resume=） 和 interrupt_before= 三件套把这件事做到了图的原生层。

6.1为什么 HITL 不是「可选项」

纯自动 Agent 最大的风险在于：它在一个不可逆的副作用上跑得太快。LLM 把收件人邮箱拼错一个字符、把「测试库」理解成「生产库」、把金额单位从元当成万元——任何一次都可能酿成事故。HITL 的本质是在副作用发生前插入一个同步等待点：图暂停、状态落盘、把「我打算做什么」亮给操作者看，等人按下确认或补充输入后才继续。

为什么要把这件事做进框架，而不是在业务代码里随便 input()？

  • 状态一致性：暂停时整张图的状态必须完整持久化，恢复时从同一处继续，中间不能丢消息、不能重复执行副作用。
  • 跨进程恢复：生产里发起暂停的进程和执行恢复的进程通常不是同一个（前端审批、后端 worker），需要靠 thread_id 在 checkpointer 里重新定位状态。
  • 可审计：每一次暂停、每一次人的输入都对应一个 checkpoint，事后能完整回放。

LangGraph 把这三点压缩成了两个 API:interrupt() 在节点内部抛暂停，interrupt_before= 在节点边界抛暂停。两者都依赖 checkpointer，这是 HITL 能成立的物理基础。

提示 HITL 不是让 Agent 变慢，而是让它在「花钱/删数据/发消息」这种不可逆动作前有一个可审计的停顿点。可逆的探索（查天气、读文件）大可放手让它自动跑；不可逆的副作用才值得一次人工确认。区分这两类动作，是设计 Agent 时首先要做的取舍。

6.2两种暂停方式｜节点内 vs 节点边界

LangGraph 提供两套 HITL 机制，它们在「谁发起暂停」这一点上根本不同。下面这张图对比了两者的触发位置：

图 6.2：两种暂停方式对比——interrupt（） 在节点内部任意位置精确提问；interrupt_before= 在节点边界统一拦截
读懂这段：方式一的暂停点可以在节点代码的任意位置，因此你能在暂停时把「我要做什么、参数是什么」打包成一个 value 抛给客户端，表达力强；方式二不改节点代码，只在 compile（） 时声明「在这些节点前停」，适合对一整套现成图统一加确认点。新代码推荐方式一，存量图改造用方式二。

6.3用代码看｜interrupt() + Command（resume=）（推荐）

这是官方文档主推的方式（interrupt() 于 0.2.47、2024 年 11 月引入，定义在 langgraph/types.py:851，在节点内部直接调用）。先记住这条：同一个 interrupt() 会被执行两次——第一次抛异常让图暂停，图恢复后在同一个位置再被调到时，返回人的答案。带着这条看最小的可运行例子（可直接粘贴运行，注释里是实跑输出）：

interrupt() + Command（resume=） 最小闭环 —— 两轮 stream 完成提问与回答
pythonimport uuid
from typing import Optional
from typing_extensions import TypedDict

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.constants import START
from langgraph.graph import StateGraph
from langgraph.types import interrupt, Command


class State(TypedDict):
    """图状态。"""

    foo: str
    human_value: Optional[str]
    """human_value 将通过 interrupt 由人填写。"""


def node(state: State):
    # 第一次执行： interrupt() 抛 GraphInterrupt， 把问题送给客户端
    # 第二次执行(被 Command resume 恢复)： 直接返回 resume 值 "30"
    answer = interrupt("what is your age?")
    print(f">； 收到人通过 interrupt 给的输入： {answer}")
    return {"human_value": answer}


builder = StateGraph(State)
builder.add_node("node", node)
builder.add_edge(START, "node")

# 必须启用 checkpointer, 否则恢复时 Command(resume=...) 会报错！
checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)

# thread_id 是 checkpointer 存取状态的钥匙
config = {"configurable": {"thread_id": uuid.uuid4()}}

# 第一轮： 触发暂停
for chunk in graph.stream({"foo": "abc"}, config):
    print(chunk)
# > {'__interrupt__': (Interrupt(value='what is your age?', id='45fda8478b2ef754419799e10992af06'),)}

# 第二轮： 人回答 "30"， 用 Command(resume=...) 恢复
for chunk in graph.stream(Command(resume="30"), config):
    print(chunk)
# >； 收到人通过 interrupt 给的输入： 30
# > {'node': {'human_value': '30'}}
读懂这段：两次 stream 用的是同一个 config（同一个 thread_id）——恢复时框架靠它从 checkpointer 找回状态。第一轮输入是正常的状态 dict；第二轮输入不是 dict 而是 Command(resume="30")，框架识别出这是恢复指令，取出该 thread 的 checkpoint 继续。两次 print 之间隔了一整个人工应答——这个人可能是几秒后点击的前端用户，也可能是几小时后审批的后台服务。

整个流程里，node 函数被完整执行了两遍，而你自己一行「恢复分支」的代码都没写。把它拆成时间线看，同一个函数在两轮里的行为完全不同：

第一轮 stream({"foo": "abc"})第二轮 stream(Command(resume="30"))
node 从哪开始函数开头也是函数开头（从头重跑）
interrupt("what is your age?")抛出 GraphInterrupt，本行之后代码不执行不抛异常，直接返回 "30"
函数的返回值没有（执行到一半被掐断）{"human_value": "30"}
客户端看到什么__interrupt__ 事件，value = 问题{'node': {'human_value': '30'}}
读懂这段：这就是 interrupt() 的核心设计：同一份节点代码，两次执行跑出「提问」和「拿答案」两个语义。你不需要在节点里写「如果是恢复就……」的 if-else 状态机——「第几次执行」这个信息由框架在内部维护，对节点代码完全透明。

为什么恢复必须「从头重跑」

一个自然的疑问：图都已经精确知道 node 是在 interrupt() 这一行停的，为什么不从这一行「续跑」，而要把整个函数重新执行一遍？

因为停住的不是「第 3 行代码」，而是「第 3 行代码所在的那个函数调用栈」。第一次执行到 interrupt() 时图暂停，此时 Python 进程里的局部变量、函数栈帧都随异常一起丢弃了；图真正拥有的只有 checkpoint 里的图状态（各 channel 的值）。局部变量不在图状态里，框架无法替你恢复它们。想从「中间某行」续跑，就得把所有局部变量也持久化下来——进程甚至可能已经换了一个，这做不到。所以唯一可靠的恢复点，是「用图状态作为输入、重新执行一遍函数」：函数开头总是能从图状态重建出一切。

「框架怎么知道这次 interrupt() 该返回答案而不是再抛异常」也不是什么特殊机制——答案就记录在恢复数据里。同一个 interrupt() 第二次被调到时，框架从恢复数据里找到对应值，直接返回。两次执行在同一个位置分岔，靠的不是代码里埋的标记，而是恢复数据里「有没有待送达的答案」。

把这套机制拆开：interrupt() 源码逐行读

上面这个「第一次抛、第二次返回」的行为，全部由 langgraph/types.py:851 的实现驱动。函数体核心逻辑只有四步，逐行看（源码里与主流程无关的子图透传和断言略去）：

interrupt（） 源码核心逻辑（langgraph/types.py:851，注释为讲解）
pythondef interrupt(value: Any) -> Any:
    conf = get_config()["configurable"]
    scratchpad = conf[CONFIG_KEY_SCRATCHPAD]
    # ① 本次是节点内第几次调 interrupt()： 0、1、2...
    #    （LazyAtomicCounter，每次调用 +1，同一节点内递增）
    idx = scratchpad.interrupt_counter()

    # ② 已收集的恢复值列表： 多个 interrupt 恢复时按位置对号
    if scratchpad.resume:
        if idx < len(scratchpad.resume):
            return scratchpad.resume[idx]    # 本次的恢复值已就位 → 直接返回

    # ③ 本轮刚送达的恢复值： 裸值 Command(resume="30") 走的就是这条
    v = scratchpad.get_null_resume(True)
    if v is not None:
        scratchpad.resume.append(v)          # 记入列表， 供同节点后续 interrupt() 对号
        return v

    # ④ 没有恢复值（人还没回答）→ 抛 GraphInterrupt：
    #    异常一路冒泡出节点， 被图的主循环（pregel/_loop.py）捕获——
    #    当前图状态 + 这个 interrupt 一起落盘， 执行干净地停止
    raise GraphInterrupt(
        (Interrupt.from_ns(value=value, ns=conf[CONFIG_KEY_CHECKPOINT_NS]),)
    )
读懂这段：拆完就清楚了：判断「第几次」靠一个随调用递增的计数器（①）；拿「答案」有两条相邻的路径——②是已收集的恢复值列表（多个 interrupt 恢复时按位置对号），③是本轮刚送达的恢复值（最简单的裸值 Command(resume="30") 走的就是这条）；④「暂停」则是抛异常后由框架主循环接住并持久化。②③执行的是同一条规则：第 idx 次 interrupt() 对应第 idx 个恢复值——源码 docstring（types.py:866）原话是 "matches resume values to interrupts based on their order in the node"。两次执行之间不能改变 interrupt() 的数量或顺序（比如把它挪进条件分支），否则恢复值会喂错对象。

上面④号机制还解释了一个高频坑：别用裸 except Exception 包住 interrupt()。GraphInterrupt 继承自 Exception（langgraph/errors.py:102，继承链 GraphInterrupt → GraphBubbleUp → Exception），宽口径的 except 会把它吞在节点里——异常到不了框架主循环，图既不暂停也不落盘，HITL 静默失效。要么不包，要么捕获后先对 GraphInterrupt 放行（raise）再处理其他异常。

从「从头重跑」推出的两条纪律

纪律一：interrupt() 之前不能有不可重复的副作用。既然恢复时节点要完整重跑，interrupt() 之前的每一行都会执行两次（第一次抛异常前、第二次恢复后）。下面这个顺序是错的，实跑验证 send_email 确实发了两遍：

反面示例 —— 副作用放在 interrupt() 之前，恢复重跑时重复执行
pythondef node(state):
    send_email(...)          # ❌ 恢复重跑时会再发一遍！
    answer = interrupt("确认发送吗？")
    ...

正确顺序是反过来：interrupt() 拿到答案（= 确认）之后，再执行副作用。这正是 6.8 节审批流 plan → approve → execute 三段结构的设计根源。

纪律二：同一节点多次 interrupt() 时，恢复值按调用顺序对号入座。原因就是上面源码②③共同的规则。配合两个实践推论：① 恢复时若图里有多个同时待处理的 interrupt（典型场景：两个并行节点各自 interrupt），必须用 Command(resume={interrupt_id: 值}) 按 id 定向恢复，只传裸值会被框架直接拒绝（实跑验证：RuntimeError: When there are multiple pending interrupts, you must specify the interrupt id when resuming）——而同一节点内先后调用的多个 interrupt 不算「同时待处理」，裸值会按序逐个消费，同样安全；② 验证循环（反复问人直到答案合法）不要写成节点内 while True——循环次数不定会改变两次执行间 interrupt() 的调用序，恢复匹配就乱了，正确做法见 6.10 节铁律三。

注意 checkpointer 与 interrupt() 的准确关系：不配 checkpointer，第一轮 invoke 不会报错——图照样执行到 interrupt() 照样停（实跑验证：返回值里带 __interrupt__）。但状态没有落盘，恢复时会直接抛 RuntimeError: Cannot use Command(resume=...) without checkpointer（pregel/_loop.py:907）。也就是说，checkpointer 不是「暂停」的前提，而是「暂停之后还能恢复」的前提。另外 InMemorySaver 只存内存，进程退出即丢，生产审批流请用 AsyncPostgresSaver 等持久化实现——checkpointer 在，暂停几小时甚至几天后换个进程也能凭同一个 thread_id 恢复（见 6.5 节）。

6.4interrupt_before / interrupt_after（老 API，节点级）

这种方式不修改节点代码，而是在 compile() 时声明「在哪些节点之前/之后暂停」。源码里 StateGraph.compile 的签名是这样的：

compile（） 的 interrupt_before / interrupt_after 参数 —— 编译期声明暂停点
pythondef compile(
    self,
    *,
    checkpointer=None,
    store=None,
    interrupt_before: All | list[str] | None = None,
    interrupt_after: All | list[str] | None = None,
    ...
):
    """
    interrupt_before： 在这些节点执行"之前"暂停。
    interrupt_after：  在这些节点执行"之后"暂停。
    """
读懂这段：interrupt_before 接收一个节点名列表，表示「执行到这些节点时先停下」。它和 interrupt() 的根本区别是：这里是编译期静态声明——你不改任何节点代码，只改 compile 的参数，就能让整张图在指定节点前统一暂停。这对存量图非常友好：一个已经在跑的 ReAct Agent，只要重新 compile 时加上 interrupt_before=["tools"]，立刻就在每次工具执行前停下来。

它的典型场景是 ReAct Agent 在工具执行前统一拦截。create_react_agent 内部就是把这个参数透传给 compile，源码注释明确写了：

create_react_agent 透传 interrupt_before —— 来自 libs/prebuilt/.../chat_agent_executor.py
python# 来自 libs/prebuilt/.../chat_agent_executor.py
interrupt_before: list[str] | None = None,
#   可选， 要拦截的节点名。取值通常是 "agent" 或 "tools"。
#   用于在执行动作前插入人工确认。
读懂这段：create_react_agent 内部的图只有两个节点：agent（调 LLM）和 tools（执行工具）。把 "tools" 放进 interrupt_before，等于说「LLM 决定要调工具后，先别执行，停下来给人看一眼」。这是对存量 Agent 加 HITL 成本最低的方式——零代码改动。

用法很直白：

用 interrupt_before=["tools"] 让 ReAct Agent 在工具执行前暂停
pythonfrom langgraph.checkpoint.memory import InMemorySaver
from langgraph.prebuilt import create_react_agent

# 一个会发邮件的 Agent
def send_email(to: str, subject: str, body: str) -> str:
    """发送邮件(真实场景里这里对接邮件服务)。"""
    return f"已发送邮件给 {to}: {subject}"

checkpointer = InMemorySaver()

# 关键： 在 "tools" 节点之前暂停
agent = create_react_agent(
    "openai:gpt-4o-mini",
    tools=[send_email],
    checkpointer=checkpointer,
    interrupt_before=["tools"],   # 工具执行前停下来
)

config = {"configurable": {"thread_id": "thread-1"}}

# 第一轮： LLM 决定调用 send_email， 但 tools 还没执行就暂停了
for chunk in agent.stream(
    {"messages": [{"role": "user", "content": "给 boss@x.com 发封请假邮件"}]},
    config,
    stream_mode="updates",
):
    print(chunk)
# agent 节点产出了带 tool_calls 的 AIMessage， 随后图在 tools 前暂停
读懂这段：第一轮 stream 结束后，图并没有真正结束——它停在 tools 节点前等待。此时状态里已经有一条带 tool_calls 的 AIMessage（LLM 说「我要调 send_email，参数是...」），但 send_email 还没被执行。这正是你想要的人工确认时机：LLM 的意图已经明确，副作用还没发生。

暂停后，图并没有结束——它停在 tools 节点前等待。这时你要做的不是 Command(resume=)，而是查看状态、确认无误后，用 None 继续：

查看暂停状态并继续 —— 用 stream（None, config） 放行
python# 查看当前状态： LLM 打算调什么工具、传什么参数
state = agent.get_state(config)
print(state.values["messages"][-1].tool_calls)
# [{'name': 'send_email', 'args': {'to': 'boss@x.com', 'subject': '请假', 'body': '...'}}]

# 人工确认： 没问题， 继续执行 tools 节点
for chunk in agent.stream(None, config, stream_mode="updates"):
    print(chunk)
# tools 节点执行 send_email， 产出 ToolMessage， 回到 agent， 最终返回
读懂这段：stream(None, config) 里的 None 表示「不带新输入，从上次暂停处继续」。这和方式一的 Command(resume=) 形成对照：interrupt_before 不需要传答案，因为它没有「提问」，只是个节点级停顿——人确认后直接放行即可。如果人发现参数不对，可以用 update_state 改掉再继续（见 6.6 节）。

interrupt_before 和 interrupt() 的本质区别在于「谁发起暂停」：前者是编译期静态声明的统一拦截，后者是节点运行时按需发起的精确提问。前者不用改节点代码、对现成 Agent 友好；后者能在节点内部任意位置暂停并把任意问题抛出去，表达力更强。新代码做「工具前确认」也可以用 interrupt() 在工具节点开头写，但 interrupt_before=["tools"] 对存量图零侵入，各有所长。

6.5thread_id｜暂停-恢复的物理基础

无论是哪种方式，暂停和恢复都绕不开一个东西：thread_id。

config 里的 thread_id —— checkpointer 存取状态的钥匙
pythonconfig = {"configurable": {"thread_id": "order-abc-123"}}
graph.invoke(inputs, config)
读懂这段：checkpointer 按 thread_id 存取状态。同一个 thread 跨多次 invoke 共享同一份状态——这就是 HITL 能「暂停一次、过几小时甚至几天再恢复」的根因。换个 thread_id 就等于开了一段全新的对话，根本找不到之前暂停的状态。

源码 StateGraph.compile 的 docstring 说得很清楚：

thread_id 的工程含义 —— 来自 libs/langgraph/.../graph/state.py
python# 来自 libs/langgraph/.../graph/state.py
# thread_id 是存取 checkpoint 的钥匙。
# 用唯一 ID 表示独立运行； 复用同一 ID 可跨多次 invoke 累积状态(如对话记忆)。
config = {"configurable": {"thread_id": "my-thread"}}
graph.invoke(inputs, config)
读懂这段：把这段和上面的 HITL 流程对照看：thread_id 把「一次业务流程」和「一段图状态」绑死。做审批流时，一个待审批工单 = 一个 thread_id；做多轮对话时，一个用户会话 = 一个 thread_id。它既是状态隔离边界，也是恢复时的寻址依据。跨 thread 不共享记忆，要跨 thread 共享得用 store（见第 09 页）。

实际运作机制是这样的：

  1. 第一次 invoke(inputs, config)：checkpointer 在 thread-1 下写一个 checkpoint，图跑到暂停点，再写一个带「待恢复」标记的 checkpoint。
  2. 暂停期间：状态静静躺在 checkpointer 里（Postgres 一行记录、SQLite 一行记录），谁都不动它。
  3. 恢复 invoke(Command(resume=...), config) 或 invoke(None, config)：LangGraph 用同一个 thread_id 取出最新 checkpoint，从暂停点之后继续。

所以恢复时必须用同一个 thread_id。这也是为什么前端审批系统要把 thread_id 当成任务 ID 传过来传过去。

6.6获取与更新状态｜get_state / update_state

暂停之后，人不能瞎确认——得先看看图当前在哪儿、下一步要干什么、状态里有什么。LangGraph 提供了 get_state 和 update_state 两个方法，源码在 langgraph/pregel/main.py：

get_state / update_state 签名 —— 源自 langgraph/pregel/main.py

get_state 返回一个 StateSnapshot，它的字段是理解整个 HITL 调试的关键（来自 langgraph/types.py）：

StateSnapshot 的字段 —— 某一步开始时的状态快照
pythonclass StateSnapshot(NamedTuple):

实战中你最常用的是 .values（看状态）、.next（看下一步）、.interrupts（看暂停时抛了什么问题）：

update_state 则允许人在恢复前直接改状态——比如审核发现 LLM 把收件人写错了，人直接把 messages 里的 tool_calls 参数改对，再继续：

    print(chunk)
读懂这段：update_state 的 as_node 参数告诉框架「把这些值当成是某个节点产出的」——这样状态合并会走那个节点对应的 reducer（比如 messages 走 add_messages）。它不重跑节点，只写值并推进 checkpoint 指针。这种「人工修正再放行」的用法非常适合审核纠错：LLM 的决定大体对、只是参数有瑕疵时，不用整轮重来，改一下就行。

把所有概念揉到一个真实场景里：一个会执行删除操作的 Agent，在真正调用删除工具前，用 interrupt() 让人确认。我们用最贴近源码 docstring 范式的方式写。

审批流完整图 —— plan 决定做什么， approve 暂停问人， execute 按审批结果执行
pythonimport uuid
from typing import Annotated, Optional
from typing_extensions import TypedDict
from langchain_core.messages import HumanMessage

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.types import interrupt, Command


# ---------- 状态 ----------
class State(TypedDict):
    messages: Annotated[list, add_messages]
    pending_tool: Optional[str]    # 待执行的工具名
    approved: Optional[bool]       # 人工审批结果


# ---------- 模拟一个危险的删除工具 ----------
def delete_records(table: str, condition: str) -> str:
    """删除数据库记录(危险动作， 执行前必须人工确认)。"""
    # 真实场景这里对接数据库； 演示直接返回
    return f"已从 {table} 删除满足 {condition} 的记录"


# ---------- 规划节点： 决定要删什么 ----------
def plan_node(state: State):
    # 实际项目里这里调 LLM 决定参数； 演示硬编码
    return {"pending_tool": "delete_records",
            "messages": [HumanMessage(
                content=f"计划执行： delete_records(table=users, condition=age<18)"
            )]}


# ---------- 审批节点： 停下来问人 ----------
def approve_node(state: State):
    # 第一次执行： interrupt 抛出， 把待执行动作描述送给客户端
    # 第二次执行(被 resume 恢复)： 直接拿到人的 yes/no
    decision = interrupt({
        "question": "确认执行以下删除操作吗？",
        "tool": state["pending_tool"],
        "args": {"table": "users", "condition": "age < 18"},
    })
    # decision 是客户端用 Command(resume=...) 传回来的
    approved = str(decision).strip().lower() in ("yes", "y", "true", "1")
    return {"approved": approved}


# ---------- 执行节点： 根据审批结果决定是否真的删 ----------
def execute_node(state: State):
    if not state.get("approved"):
        return {"messages": [HumanMessage(content="已取消， 未执行删除。")]}
    result = delete_records(table="users", condition="age < 18")
    return {"messages": [HumanMessage(content=result)]}


# ---------- 组装图 ----------
builder = StateGraph(State)
builder.add_node("plan", plan_node)
builder.add_node("approve", approve_node)
builder.add_node("execute", execute_node)
builder.add_edge(START, "plan")
builder.add_edge("plan", "approve")
builder.add_edge("approve", "execute")
builder.add_edge("execute", END)

# 必须 checkpointer
checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)

# ---------- 跑一遍 ----------
config = {"configurable": {"thread_id": "delete-task-001"}}

# 第 1 轮： 跑到 approve 节点， interrupt 抛出问题
for chunk in graph.stream({"messages": []}, config, stream_mode="updates"):
    print(chunk)
# {'plan': {...}}
# {'__interrupt__': (Interrupt(value={'question': '确认执行以下删除操作吗？', ...}, id='...'),)}

# 查看暂停时抛了什么
snap = graph.get_state(config)
print("待确认：", snap.interrupts[0].value)
# 待确认： {'question': '确认执行以下删除操作吗？', 'tool': 'delete_records', ...}
print("下一步：", snap.next)
# 下一步： ('approve',)

# 第 2 轮： 人审批通过， 用 Command(resume=...) 恢复
for chunk in graph.stream(Command(resume="yes"), config, stream_mode="updates"):
    print(chunk)
# {'approve': {'approved': True}}
# {'execute': {'messages': [HumanMessage(content='已从 users 删除满足 age < 18 的记录')]}}
读懂这段：这个例子展示了 HITL 的完整闭环：plan 决定要做什么副作用但不执行；approve 用 interrupt() 把「要做什么」亮给人看、停下来等回答；人通过 Command(resume="yes") 给出决策，图恢复后 approve 节点重跑拿到答案；execute 只有在 approved=True 时才真正调用 delete_records。关键设计：delete_records 这种不可逆动作被严格隔离在 execute_node 里，且只受 approved 控制；而 interrupt() 放在 approve_node 里、副作用之前，即使节点被恢复重跑也不会误触发删除。

对应到图结构上，这个审批流长这样：

图 6.8：审批流图结构——plan → approve（interrupt 暂停）→ execute；只有 approved=True 时 execute 才调用 delete_records
注意 这是 HITL 在生产环境最关键的性质。interrupt() 抛出 GraphInterrupt 时，LangGraph 已经把当前状态（含「停在哪个节点的哪个 interrupt」）写进 checkpointer。只要 checkpointer 是持久化的（Postgres、SQLite），即使 worker 进程崩溃、被重启，暂停几小时甚至几天后才有人来审批，恢复请求打到一个完全不同的进程——只要带上同一个 thread_id + Command(resume=...)，图就能从暂停点精确恢复。InMemorySaver 进程退出即丢，只用于演示；生产审批流务必用持久化 checkpointer。

6.9两种方式怎么选

把两种 HITL 机制放在一张表里对照，选型时一目了然：

维度interrupt() + Command(resume=)interrupt_before / interrupt_after
暂停发起方节点运行时按需发起编译期静态声明
能否带问题给客户端能，interrupt(value) 抛任意值不能，只是节点级停顿
恢复方式Command(resume=答案)invoke(None, config) 或改状态后继续
节点是否重跑是，从头重跑（interrupt 第二次返回值）否，从暂停的节点边界继续
对存量图侵入需改节点代码零侵入，只改 compile 参数
典型场景审批提问、补充输入、多轮澄清工具执行前统一拦截、调试断点
是否需 checkpointer必须必须
读懂这段：经验法则：需要把「问题」抛给客户端、需要精确控制暂停点，用 interrupt()；只想对现成 Agent 在某个节点统一加个确认点、不想改节点代码，用 interrupt_before。两者可以混用——同一个图里某些节点用 interrupt() 精确提问，另一些用 interrupt_before 做兜底拦截。

6.10自建/选型提示

如果你在自建 agent 框架，HITL 这一层最容易看出实现是「能跑的 demo」还是「能上线的系统」。要点：

  • 暂停必须和状态持久化同源——不能状态存 A 处、暂停标记存 B 处，否则一致性会崩。LangGraph 的做法是 interrupt() 抛的 GraphInterrupt 直接被 checkpointer 捕获并和状态一起落盘，两者天然同源。
  • 恢复要支持跨进程，靠的是稳定的寻址键（LangGraph 用 thread_id），不要依赖内存里的回调。生产里发起暂停的 worker 和执行恢复的审批服务通常是两个进程，只有靠持久化 + 稳定 ID 才能找回状态。
  • 副作用必须放在暂停点之后——这是 interrupt() 设计成「节点重跑」的根本原因，它逼你把副作用和决策分离（机制推导见 6.3 纪律一）。
选型 选 Agent 框架时，可以直接问它三个问题：① 暂停时状态是否自动持久化？② 恢复能否跨进程（带个 ID 就能找回）？③ 暂停点之前能否保证不执行副作用？如果有一个答「不能」，那它 HITL 的生产可用性就要打问号。LangGraph 在这三点上都是「能」——这正是它把 HITL 做进图框架而非交给业务代码的回报。

这就是「为什么 HITL 要做进图框架」的答案——状态流转、暂停恢复、副作用隔离，三者绑在一起才安全。下一章（09 持久化记忆）会展开 checkpointer 和 store 的细节，把 HITL 赖以成立的物理基础讲透。

interrupt（） 的三条铁律（源码级）

6.3 节已经从源码推出了前两条铁律的机制（为什么如此，见「把这套机制拆开」一节），这里聚焦各自的高频踩坑场景与应对：

铁律一：别用裸 except Exception 包住 interrupt()

机制回顾（详见 6.3）：GraphInterrupt 继承自 Exception（langgraph/errors.py:102，继承链 GraphInterrupt → GraphBubbleUp → Exception），靠冒泡到框架主循环才能暂停落盘。宽口径 except 把它吞在节点里，图既不暂停也不落盘——HITL 静默失效：

反面示例 —— 裸 except Exception 会吞掉 GraphInterrupt
pythondef node(state):
    try:
        ans = interrupt("确认？")
        return do_work(ans)
    except Exception:          # ❌ 会吞掉 GraphInterrupt！
        return {"err": "failed"}

正确做法是别包，或者捕获后先对 GraphInterrupt 放行再处理其他异常：

正面示例 —— 捕获后先放行 GraphInterrupt 再处理其他异常
pythonfrom langgraph.errors import GraphInterrupt
except Exception as e:
    if isinstance(e, GraphInterrupt):   # 让它继续往上冒泡
        raise
    return {"err": "failed"}

这个坑最常出现在「给节点统一包一层重试/监控装饰器」时——装饰器里的 try/except 同样会拦下暂停信号。

铁律二：恢复时不要改变 interrupt() 的调用顺序

机制回顾（详见 6.3 源码②③）：恢复值按 interrupt() 的调用顺序对号入座，不按内容。所以一旦你的图在两次调用之间改了 interrupt() 的数量或顺序（比如代码更新、或某个 interrupt() 被包进条件分支而条件变了），恢复匹配就会错位——本该喂给 A 的答案喂给了 B，或直接报错。

这里真正的风险在生产部署：一旦有暂停中的工单（旧代码产生的 checkpoint），部署带 interrupt 顺序变更的新代码要格外谨慎——旧 thread 的恢复可能对不上新代码的调用序。稳妥做法是让旧工单按旧版本代码恢复完毕后再上线，或恢复时用 interrupt id 定向匹配（Command(resume={interrupt_id: 值})，见 6.3 纪律二）。

铁律三：验证循环别用节点内 while True，用条件边循环

一个常见误区：想在节点里写 while True 循环反复问用户直到输入合法。这会和铁律二打架——循环次数不定意味着 interrupt() 的调用序在两次执行间可能不同，恢复时匹配会乱。

正确做法是把循环交给图的边，而不是节点内的 while：节点执行一次（调一次 interrupt() 拿答案）→ 退出 → 用一条条件边判断「答案合法吗？」，合法走下一步，不合法回到本节点再跑一遍。这样每次执行节点里 interrupt() 恒定调用一次，顺序永远对得上，框架的状态机和暂停恢复才协调。这是 LangGraph「图即状态机」哲学的直接体现：控制流该交给图，而不是 Python 循环。
