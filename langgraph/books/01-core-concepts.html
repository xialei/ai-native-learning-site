核心概念

LangGraph 把 agent 当作"状态机 + 图"来编程——掌握 State、Node、Edge、Reducer、Channel、Compile 这六块,你就掌握了它的全部心智模型。

1.1为什么是图,而不是链

如果你用过 LangChain 的链(LCEL),你会发现链是"一条线"——数据从前往后流,中间拼接若干步。而真实的 agent 往往需要循环(思考-行动-观察)、分支(根据结果决定下一步)、记忆(跨多轮保留上下文)。LangGraph 的设计起点就是:与其把 agent 写成一条越来越长的 prompt 链,不如把它显式建模成一张有状态的有向图。

这一页先把六个核心概念过一遍,每个都配一句话定义、一段可运行代码、以及它"在图里扮演什么角色"。理解了这六块,后面所有章节都是在它们之上做组合。

提示 LangGraph 的本质是"把 agent 当作状态机/图来编程"。链是线性的、无状态的、一次性把 prompt 拼死;而图是结构化的、有共享状态的、可以在节点之间循环和分支的。状态(State)是图的"内存",节点(Node)是"计算单元",边(Edge)是"控制流",Reducer 决定"状态怎么合并"。一旦你用这四个词去描述一个 agent,它就不再是一团模糊的 prompt,而是一个可以被画出、被调试、被复用的程序。

1.2总览:四大件如何协作

在看每个概念的细节前,先用一张图理解 State / Node / Edge / Reducer 的关系。节点从状态里读数据,做完计算后返回一个状态更新(partial state);这个更新不是直接覆盖,而是交给对应字段的 Reducer 去合并;合并完的新状态再由 Edge 决定流向下一个节点。

图 1.2:State 在中央,节点读写都经过它;更新经 Reducer 合并后写回,边负责把控制流从 A 传到 B。

关键点:节点之间不直接传数据,而是都通过 State 中转。这就是为什么 LangGraph 能支持循环、并行、断点恢复——因为状态是显式的、可持久化的,而不是藏在某个函数调用栈里的局部变量。

1.3State(状态):图的共享数据结构

一句话定义:State 是图的共享数据结构,通常用 TypedDict 定义,所有节点都读写它。

State 是 LangGraph 的"主内存"。每个节点拿到的输入就是当前 State 的一个快照,节点做完事后返回的更新会被合并回 State。用 TypedDict 是因为它既能给编辑器/类型检查器提示字段类型,又能在运行时像普通 dict 一样使用——不需要写 dataclass 或 pydantic 模型(当然你也可以用它们,LangGraph 都支持)。

代码来源说明 — State 的两种典型字段:带 reducer 的 messages、普通字段 count。
pythonfrom typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import add_messages


class State(TypedDict):
    # messages 用 add_messages 归约器:追加而非覆盖
    messages: Annotated[list, add_messages]
    # count 是普通字段,默认行为是"最后写入者胜"(LastValue)
    count: int
读懂这段: 这里有两个字段,展示了 State 的两种典型用法。messages 加了 Annotated[list, add_messages],意味着每次节点返回新消息时,它们会被追加到列表里(而不是替换整个列表);count 没有任何注解,所以用默认的 LastValue 通道——后写覆盖先写。这是"状态合并语义"在最常见场景里的体现:聊天历史要累积、计数器要覆盖。

在图中的角色:State 是数据的"单一事实来源(single source of truth)"。节点之间不直接传参,而是都通过 State 中转。这让图的执行可以被暂停、持久化、恢复——因为状态是显式可序列化的。

1.4Node(节点):执行计算单元

一句话定义:Node 是一个普通函数 def node(state) -> partial_state,接收当前状态,返回状态更新(不是全量状态)。

这是新手最容易踩的坑:节点返回的不是完整的新 State,而是只想修改的那几个字段的更新。比如 State 有 messages 和 count 两个字段,但你的节点只想追加一条消息,那就只返回 {"messages": [...]},不用管 count。LangGraph 会把你的更新和现有 State 合并(怎么合并由 Reducer 决定)。

代码来源说明 — 一个最小的 chatbot 节点:读最后一条消息、返回一条 AIMessage。
pythonfrom langchain_core.messages import AIMessage


def chatbot(state: State) -> dict:
    # 节点读 state:拿到当前所有消息
    last_user_msg = state["messages"][-1]
    # 做计算:这里用固定回复示意,真实场景会调 LLM
    reply = f"你说了:{last_user_msg.content},我收到了。"
    # 返回更新:只写想改的字段,不必返回全量 state
    # add_messages 会把这条 AIMessage 追加到 messages 列表
    return {"messages": [AIMessage(content=reply)]}
读懂这段: 节点签名是 State -> Partial[State]。返回值可以是 dict、也可以是 Command 对象(后者还能顺便控制跳转,后面控制流章节会讲)。节点还可以接收第二个参数 config: RunnableConfig,用来拿 thread_id、回调等运行时信息。注意这里只返回 messages——只改你关心的一两个字段,是 LangGraph 的核心约定。

在图中的角色:Node 是"动词",负责所有的计算——调 LLM、查数据库、执行工具、做判断。一个图里可以有任意多个节点,每个节点是一个独立的、可测试的、可重试的单元。

1.5Edge(边):定义控制流

一句话定义:Edge 定义节点之间的控制流,分普通边(add_edge)和条件边(add_conditional_edges)。

普通边是"固定的下一步":A 跑完一定去 B。条件边是"看情况":A 跑完后,调用一个路由函数,根据当前 State 决定去哪个节点(或去 END 结束)。条件边是构建 ReAct 循环、多 agent 路由的核心——没有它,图就只能是一条直线。

代码来源说明 — ReAct 骨架:普通边进 chatbot,条件边决定去 tools 还是 END,tools 回 chatbot 形成循环。
pythonfrom langgraph.graph import StateGraph, START, END


def should_continue(state: State) -> str:
    # 条件路由函数:根据 state 决定下一个节点
    # 返回值是"目标节点名"或 END
    last_msg = state["messages"][-1]
    if last_msg.tool_calls:
        # AI 想调工具,就去 tools 节点
        return "tools"
    # 没有工具调用,直接结束
    return END


builder = StateGraph(State)
builder.add_node("chatbot", chatbot)
# some_tool_node 是个会执行 tool_calls、回填 ToolMessage 的节点。
# 本页聚焦控制流,先把它的实现当成"黑盒"——见第 5 章(5.6)的 ToolNode
builder.add_node("tools", some_tool_node)

# 普通边:入口固定进 chatbot
builder.add_edge(START, "chatbot")
# 条件边:chatbot 跑完后,由 should_continue 决定去哪
builder.add_conditional_edges("chatbot", should_continue)
# 普通边:tools 跑完回 chatbot(形成循环)
builder.add_edge("tools", "chatbot")
读懂这段: 这段代码就是 ReAct agent 的骨架:chatbot 决定要不要调工具,要调就去 tools 节点,调完回 chatbot 继续推理,循环到不需要调工具为止。START 和 END 是 LangGraph 的两个保留字(实际值是 "__start__" 和 "__end__"),分别代表图的入口和出口。条件边返回的字符串就是"下一站的名字",这是 agent 能"自主决策"的关键。

在图中的角色:Edge 是"连线",决定数据/控制流往哪走。普通边让图变成"流水线",条件边让图变成"状态机"——能根据运行时状态动态选择路径,这是 agent 能"自主决策"的基础。

1.6Reducer(归约器):状态合并方式

一句话定义:Reducer 用 Annotated[type, reducer] 指定某个字段的状态如何合并,签名是 (old_value, new_value) -> merged_value。

这是 LangGraph 区别于普通函数调用的关键设计。考虑一个场景:两个节点并行执行,都往 messages 里写了新消息。如果没有 Reducer,后写的会覆盖先写的;有了 Reducer,框架知道该把它们合并起来。最常用的 Reducer 是 add_messages——它把新消息追加到旧列表里(而不是替换),并且如果新消息和某条旧消息 ID 相同,就替换那条(支持"编辑历史消息")。

代码来源说明 — add_messages 的合并行为:追加、同 ID 替换、支持 RemoveMessage 删除。
pythonfrom typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import add_messages


class State(TypedDict):
    # add_messages: 追加新消息;同 ID 则替换;支持 RemoveMessage 删除
    messages: Annotated[list, add_messages]
    # 自定义 reducer:用 operator.add 把列表拼起来
    # steps: Annotated[list, operator.add]
    # 没有注解的字段 -> LastValue(后写覆盖)


# 看 add_messages 的合并行为:
# old = [HumanMessage("你好", id="1")]
# new = [AIMessage("你好啊", id="2")]
# 合并后 = [HumanMessage("你好", id="1"), AIMessage("你好啊", id="2")]
# 如果 new 里有 id="1" 的消息,它会替换 old 里那条,而不是追加
读懂这段: Reducer 的存在让"并行节点写同一字段"变得安全。默认的 LastValue 通道每一步只能接收一个值,如果同一 step 有两个节点同时写一个非 Reducer 字段,会直接报错(InvalidUpdateError);而带 Reducer 的字段会把多个更新归约成一个。这也是为什么聊天历史必须用 add_messages——否则多轮对话的每条消息都会被下一条覆盖掉。
最小复现:两个并行节点写同一字段,触发 InvalidUpdateError
pythonfrom typing_extensions import TypedDict
from langgraph.graph import StateGraph
from langgraph.errors import InvalidUpdateError


class State(TypedDict):
    # hello 没有 reducer -> 默认 LastValue,每步只能收一个值
    hello: str


def node_b(state: State) -> dict:
    return {"hello": "world"}  # 两个节点都写 hello


builder = StateGraph(State)
builder.add_node("a", node_b)
builder.add_node("b", node_b)
builder.add_node("c", node_b)
builder.set_entry_point("a")
builder.add_edge("a", "b")  # a 跑完,同时 fan-out 到 b 和 c
builder.add_edge("a", "c")
graph = builder.compile()

graph.invoke({"hello": "there"})
# InvalidUpdateError: At key 'hello': Can receive only one value per step.
#                Use an Annotated key to handle multiple values.
读懂这段: a 跑完后同时把控制流交给 b 和 c(fan-out),它们在同一 step 都写了 hello。因为 hello 没挂 reducer,背后是 LastValue 通道,它每步只认一个值——两个写入撞在一起就报错。解法是给字段配 reducer(比如 Annotated[str, lambda o, n: n],或干脆用一个能归约的类型)。这个"为什么需要 reducer"的故事,在 1.7 讲 Reducer 与 Channel 的关系时会再落到底层通道上。

在图中的角色:Reducer 是"合并规则",定义在 State 的类型注解上。它让状态更新变成可组合、可并行的操作,而不是粗暴的覆盖。理解 Reducer 是理解 LangGraph 并行执行和消息累积的前提。至于 reducer 函数最终是被谁调用、存在哪一层抽象里,留给下一节的 Channel。

1.7Channel(通道):底层状态存储抽象

一句话定义:Channel 是 State 每个字段在编译后对应的"存储盒子"——它规定了这个字段"怎么存、怎么更新、怎么持久化"。

你在 State 里写的 messages、count 这些字段,在编译时不会变成普通的 Python 变量,而是各自被包进一个 Channel 对象。前面 1.6 你写的 Annotated[list, add_messages] 注解,编译时就变成了一个 "带 reducer 的盒子";没有注解的字段则变成 "只认最后一个值的盒子"。Channel 就是 Reducer 真正落脚的那一层——reducer 函数不是凭空被调用的,而是被盒子的 update() 方法调用的。

图 1.7:State 字段 → Channel 盒子。带 reducer 的注解变成能合并的盒子,普通字段变成只存最后一个值的盒子。推断逻辑在 state.py:1850 的 _get_channel,无注解字段走 state.py:1871 的 LastValue fallback。

盒子的种类由有没有 reducer 注解决定,框架在编译时自动推断,你不用手写:

字段写法编译后的 Channel盒子的"更新规则"
messages: Annotated[list, add_messages]BinaryOperatorAggregate(add_messages)把所有写入用 reducer 逐个合并(追加 / 同 ID 替换)
count: int(无注解)LastValue(int)只保留最后一个值;同一 step 收到 2 个值就报错
x: Annotated[int, EphemeralValue(int)]EphemeralValue只存活到下一步,不写入 checkpoint(临时值)

每个 Channel 都实现三个核心方法:get()(读当前值)、update(values)(收一批写入、合并进盒子)、checkpoint()(把值序列化存盘)。Pregel 引擎在每个 super-step 结束时,统一调所有盒子的 update(),这就是 Reducer 真正被调用的时刻。

代码来源说明 — LastValue.update 的"每步只收一个"逻辑(last_value.py:56,错误信息见 last_value.py:61)。
pythonclass LastValue(BaseChannel):
    # 源码 last_value.py:56 —— 这就是 1.6 那个 InvalidUpdateError 的发源地
    def update(self, values: Sequence[Value]) -> bool:
        if len(values) == 0:
            return False
        if len(values) != 1:                      # 同一步收了多个值
            raise InvalidUpdateError(            # ← 1.6 报的就是这个错
                f"At key '{self.key}': Can receive only one value per step."
            )
        self.value = values[-1]              # 只留最后一个,这就是"后写覆盖"
        return True

# 对比 BinaryOperatorAggregate.update(binop.py:123)——
# 它不报错,而是把多个值逐个喂给 operator(self.value, value):
#   for value in values:
#       self.value = self.operator(self.value, value)   # operator 就是你的 reducer (binop.py:143)
# 所以 add_messages 能"追加",而不是被覆盖——区别全在这个盒子里。
读懂这段: 1.6 节那个 InvalidUpdateError 的根,就在 LastValue.update 这 4 行里:b、c 两个并行节点都写了 hello,Pregel 把 ["world", "world"] 两个值塞进 hello 的 LastValue 盒子,len(values) != 1 直接抛错。而 BinaryOperatorAggregate 走的是 for 循环逐个合并,所以它天生能吃多个并行写入。一句话:reducer 注解不是装饰,它决定了你字段的盒子是"会报错"还是"会合并"。这是 Channel 抽象最值得你记住的一行代码。
要不要手写 Channel 99% 的场景不用。你只要会写 Annotated[type, reducer],框架就自动给你装上 BinaryOperatorAggregate;不写就默认 LastValue(源码 state.py:1871 的 fallback 分支)。只有当你需要一种内置盒子没有的状态语义(只读、自动过期、跨线程共享、增量流式),才去继承 BaseChannel 自己实现 get/update/checkpoint 三个方法——第 9 章的 DeltaChannel(增量流式)就是这种"自定义盒子"的例子。

在图中的角色:Channel 是"存储引擎",藏在 State 背后。它是 Reducer 的载体——你在 State 注解里写的每一条合并规则,最终都落到某个 Channel 盒子的 update() 里执行。日常把它当作"实现细节"忽略完全没问题,但当你看到 InvalidUpdateError 或想理解"为什么流式能拿到增量"时,记住:答案在盒子这一层。

1.8Compile(编译):StateGraph → Runnable

一句话定义:compile() 把 StateGraph(构建器)变成 CompiledStateGraph(一个 Runnable),之后可以 invoke / stream / batch。

StateGraph 是一个构建器(builder)——你往里 add_node、add_edge,它只是把结构存起来,不能直接运行。调用 compile() 后,它会校验图(有没有入口、有没有孤立节点)、把每个 State 字段转成 Channel、把节点和边转成执行计划,最终产出一个 CompiledStateGraph。这个编译后的对象实现了 LangChain 的 Runnable 接口,所以它和 LCEL 链一样可以 invoke、stream、batch、ainvoke。

代码来源说明 — 编译带 checkpointer 的图,invoke / stream / batch 用法与 LCEL 一致。
pythonfrom langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

builder = StateGraph(State)
builder.add_node("chatbot", chatbot)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)

# 编译:加 checkpointer 让图支持"短期记忆"和断点恢复
# 不加 checkpointer 也能跑,但无法跨 invoke 保留状态
graph = builder.compile(checkpointer=InMemorySaver())

# 编译后就是个 Runnable,用法和 LCEL 链一样
config = {"configurable": {"thread_id": "thread-1"}}
result = graph.invoke(
    {"messages": [("user", "你好")]},
    config,
)
# result["messages"] = [HumanMessage("你好"), AIMessage("你说了:你好,我收到了。")]

# 同一个 thread_id 再 invoke,会接续上一轮的 messages(短期记忆)
result2 = graph.invoke(
    {"messages": [("user", "我刚才说了什么?")]},
    config,
)

# 也支持流式输出、批量
for chunk in graph.stream({"messages": [("user", "嗨")]}, config):
    print(chunk)
for r in graph.batch(
    [{"messages": [("user", "A")]}, {"messages": [("user", "B")]}],
    [{"configurable": {"thread_id": "t1"}}, {"configurable": {"thread_id": "t2"}}],
):
    pass
读懂这段: compile() 还能接收 interrupt_before / interrupt_after(在指定节点前后暂停,用于人机协同)、store(长期记忆)、debug 等参数。这里只要记住:构建和执行是分离的——你先构建图结构,编译后得到一个可复用的、可持久化的执行单元。同一个 thread_id 多次 invoke 会接续状态,这是 checkpointer 带来的"短期记忆"。

在图中的角色:Compile 是"从设计图到可运行程序"的那一步。它做了三件事:校验图结构、把声明式的节点/边/状态编译成命令式的执行计划(Pregel 引擎)、把结果包装成标准 Runnable。这一步让 LangGraph 既能保持声明式的简洁,又能拥有运行时的性能和可控性。

1.9六概念速查表

概念是什么怎么用类比
State共享数据结构TypedDict 定义字段程序的"内存"
Node计算单元def node(state) -> dict函数/步骤
Edge控制流add_edge / add_conditional_edgesif-else / goto
Reducer状态合并规则Annotated[type, reducer]= vs +=
Channel底层存储抽象自动推断(高级可自定义)数据库引擎
Compile构建器 → Runnablebuilder.compile()编译/打包
为什么是这六个 这六个概念覆盖了"定义数据 → 定义计算 → 定义流转 → 定义合并 → 底层存储 → 产出可执行物"的完整闭环。前四个(State/Node/Edge/Reducer)是你每天都在用的;Channel 是偶尔需要的底层;Compile 是每次都要调但通常只用默认参数的。掌握它们之后,后面所有的章节(多 agent、人机协同、持久化)都只是在这六块上做加法。

1.10新手常犯的错误

正确用法讲了这么多,但真正让人记住一个概念的,往往是踩过的坑。下面三个是这一章的六个概念里最高频的误区,每条都对应一个已经讲过的机制——复习时对照着看,比只背"正确写法"更牢。

① 节点返回全量 state,而不是 partial state

1.4 强调节点返回的是只想修改的那几个字段的更新,不是完整的新 State。新手常把整个 state 拷出来改完再 return state——多数时候能跑,但它埋了两个雷:一是和 reducer 语义打架(add_messages 想追加,你却把完整列表当"更新"传回去,行为变得不可预期);二是抹掉了"只关心一两个字段"这个让节点可复用、可测试的核心约定。

反面 vs 正面:节点该返回什么
python# ✗ 反面:拷出全量 state 再返回
def chatbot(state: State) -> dict:
    state["messages"].append(AIMessage(content="hi"))
    return state  # 把整个 dict 回传,和 reducer 约定冲突

# ✓ 正面:只返回想改的字段
def chatbot(state: State) -> dict:
    return {"messages": [AIMessage(content="hi")]}
读懂这段:第二版只返回 {"messages": [...]},把"怎么合并"交给 1.6 的 reducer。add_messages 会把它追加进历史,而不是被当成一份完整的新列表。记住签名是 State -> Partial[State],不是 State -> State。

② 忘了给 messages 加 add_messages,历史被覆盖

这是 1.6 反复出现的主题:messages 不挂 reducer 就走默认 LastValue,后写覆盖先写,多轮对话里每条消息都被下一条顶掉。因为这条坑足够典型,第 3 章(3.2)专门用了一段可运行代码展示"历史丢失"的全过程和修法——这里不重复,只记住一句话:凡是要累积历史的字段,必须配 reducer。

③ fan-out 写同一字段,撞出 InvalidUpdateError

1.6 的最小复现已经看过:LastValue 通道每步只认一个值,两个并行节点写同一个无 reducer 的字段就报 InvalidUpdateError。这其实和 ② 是同一枚硬币的两面——reducer 的两大职责:决定单次写入怎么累积(覆盖 vs 追加),以及让多个并发写入能归约成一个确定结果。遇到这个报错,别去"减少并行",而是给字段配 reducer。

一句话总结 这三条的共同根源都是把"状态更新"当成了"状态覆盖"。LangGraph 的心智模型里,节点返回的是更新请求,怎么落地由 reducer 决定——一旦你开始问"这个字段该用哪种合并语义",你就从"写普通函数"切换到了"设计状态机"。
