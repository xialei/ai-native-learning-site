核心概念

先看一个用「链」写到第三轮就散架的 agent 场景，把它的三个症状拆成四个工程问题，再看 LangGraph 用哪六个概念逐一回答——每个概念都配可运行代码和源码出处。

1.1开场：一条链写到第三轮，散架了

你要做一个客服助手。第一版需求很简单：用户发来问题 → 查订单（调一次订单接口）→ 把查询结果拼进 prompt → 输出回复。用 LangChain 的链（LCEL）写，半小时就上线了——链就是「一条线」：数据从前往后流，每一步的输出接下一步的输入。

然后需求开始加码，三个症状接连出现：

  • 循环：模型看完订单数据，经常说「我还得再查一次物流」。要查几轮，事先没人知道——而链的步骤数是拼的时候就写死的。你只能在某个环节里塞一个 while 循环，于是「流程长什么样」从链的结构里掉进了某个函数体内，再也画不出来。
  • 并行：产品说订单查询和物流查询没有依赖，可以同时发。链的第 N 步只有一个上游、一个下游，汇合点在哪、等谁做完，框架不管——你只能自己开 ThreadPoolExecutor，把并发管理手写在业务代码里。
  • 停顿：查完订单，想先暂停下来问用户「要不要继续查物流？」，等人确认再继续。进程一停，函数栈里的局部变量全没了；服务重启后，该从哪一行接着跑？
根源 三个症状指向同一个缺口：链这个抽象里，没有一个地方放着「目前查到了什么」（状态），没有一种写法能说「下一步去哪由数据决定」（控制流），没有一种机制能把执行进度存下来、换个进程再捡起来（可恢复）。循环、并行、停顿不是三个需求，是同一个缺口的三个切面。

LangGraph 的全部 API，就是在回答一个问题：如果把 agent 写成一张有状态的图——节点是步骤，边是走向，每个节点读写同一份状态——上面三件事是不是就有着落了？这一章先建立回答这个问题需要的心智模型，后面所有章节都是在这套模型上做加法。

图 1.1：同一类任务，两种抽象。左：链的步骤拼完就固定，循环和分支没有落脚点；右：图把「要不要再来一轮」表达成一条条件边，循环本身就是图结构。

1.2把困境拆开：四个问题，六个概念

1.1 的三个症状，翻译成工程问题是这样四个。注意它们的排列顺序——不是 API 文档的目录顺序，而是你动手时会依次撞上的顺序：

#问题LangGraph 的部件本节
①「目前查到了什么」放在哪，节点之间怎么共享？State：一份所有节点都能读写的结构化数据1.3
②每一步的计算怎么写？和共享状态是什么关系？Node：一个读状态、返回「更新」的普通函数1.4
③下一步去哪？怎么表达循环和分支？Edge：固定走向（普通边）+ 看状态决定（条件边）1.5
④几个节点同时写一个字段，谁赢？还是该合并？Reducer：写在字段注解上的合并规则1.6

Reducer 那一问的答案，最终要落到一层底层抽象上：Channel（1.7）——State 的每个字段在运行时其实是一个「盒子」，reducer 就是盒子的更新规则。最后，声明完的图怎么变成能跑的程序，由 Compile（1.8）回答。最后，声明完的图怎么变成能跑的程序，由 Compile（1.8）回答。

图 1.2：四个部件怎么咬合。节点之间不直接传数据，都经过 State 中转；更新由 Reducer 合并后写回；Edge 决定控制流往哪走。

读这张图先记住一条：节点之间不直接传数据。A 的结果不是作为函数参数传给 B 的，而是先落进 State，B 再从 State 里读。为什么非要绕这一道？因为只有状态是「图以外、函数以外」的显式数据，循环才能在任意一步停下来、停下来的状态才能存盘、存了盘才能换个进程接着跑——这些正是 1.1 三个症状的解药。状态藏在函数调用栈里的话，以上全部免谈。

1.3State：数据放哪，节点怎么共享

一份所有节点共享的结构化数据。LangGraph 里你用一个 TypedDict 声明它（也可以用 Pydantic，第 3 章对比两者取舍）：每个字段就是一项「目前已知的信息」。执行时，每个节点拿到的输入是当前 State 的完整快照；节点做完事返回的更新，由框架合并回 State（怎么合并是 1.6 的事，这里先按下）。

代码来源说明 — 最朴素的 State：两个普通字段，先不带任何注解。
pythonfrom typing_extensions import TypedDict


class State(TypedDict):
    # 对话历史：每一轮都要接着上一轮长，而不是被新消息顶掉
    messages: list
    # 普通计数字段：每步直接给最新值
    count: int
为什么用 TypedDict： 它运行时就是一个普通 dict——零开销、编辑器和 mypy 都认识，后面还能通过 Annotated 在字段上挂合并规则（1.6）。注意这份定义此刻什么注解都没挂，这是故意的：messages 写成这样，第一轮对话之后历史就会丢——这颗雷 1.6 会当场引爆，现在先记住「字段 = 一份共享数据」就够了。

在整张图里，State 扮演的是唯一事实来源（single source of truth）。节点不互相传参（见 1.2 的图），一切以 State 为准。这带来的直接回报：状态是显式的、可序列化的——所以图可以暂停后恢复、恢复时可以用存盘的状态。第 6 章（人机协同）和第 9 章（持久化）都站在这个设计上。

1.4Node：每一步怎么写

答案朴素得可疑：一个普通 Python 函数。签名固定为「接收 State，返回一个 dict」。调 LLM、查数据库、执行工具，都在这个函数里做。

但有一个新手最容易踩的约定藏在返回值里：节点返回的不是完整的新 State，而是只想修改的那几个字段的更新。State 有 messages 和 count 两个字段，你的节点只想追加一条消息，就只返回 {"messages": [...]}，别管 count。

代码来源说明 — 一个最小的 chatbot 节点：读最后一条消息、返回一条 AIMessage。
pythonfrom langchain_core.messages import AIMessage


def chatbot(state: State) -> dict:
    # 节点读 state：拿到当前所有消息
    last_user_msg = state["messages"][-1]
    # 做计算：这里用固定回复示意，真实场景会调 LLM
    reply = f"你说了：{last_user_msg.content}，我收到了。"
    # 返回更新：只写想改的字段，不必返回全量 state
    return {"messages": [AIMessage(content=reply)]}
签名的准确读法： State -> Partial[State]——返回值是「更新请求」，不是新状态。框架拿到这个 dict 后，交给每个字段的合并规则去落地（1.6）。返回值也可以是 Command 对象（顺便控制下一跳，第 4 章会讲）。节点还能接收第二个参数 config: RunnableConfig，用来取 thread_id、回调等运行时信息。「只返回要改的字段」这个约定是节点可复用、可单测的前提：一个只依赖输入、只声明自己输出的函数，才好放进不同的图里跑。

节点是图里的「动词」：调 LLM、查数据库、执行工具、做判断，全在节点里。一个节点就是一个可独立测试、可重试的单元——这个性质后面会被反复兑现（重试策略、超时控制、断点恢复都挂在节点这一层）。

1.5Edge：流程怎么走，循环怎么转

下一步去哪？LangGraph 的答案是「边」，分两种：

  • 普通边（add_edge）：A 跑完一定去 B，写死的顺序。
  • 条件边（add_conditional_edges）：A 跑完后，调一个路由函数看当前 State，决定去哪个节点（或去 END 收工）。

没有条件边，图就只能是一条直线——1.1 的三个症状一个都治不了。条件边是 agent「看起来在自主决策」的全部秘密：所谓决策，就是路由函数读了 State 之后返回一个「下一站的名字」。

代码来源说明 — ReAct 骨架：普通边进 chatbot，条件边决定去 tools 还是 END，tools 回 chatbot 形成循环。
pythonfrom langgraph.graph import StateGraph, START, END


def should_continue(state: State) -> str:
    # 条件路由函数：根据 state 决定下一个节点
    # 返回值是"目标节点名"或 END
    last_msg = state["messages"][-1]
    if last_msg.tool_calls:
        # AI 想调工具，就去 tools 节点
        return "tools"
    # 没有工具调用，直接结束
    return END


builder = StateGraph(State)
builder.add_node("chatbot", chatbot)
# some_tool_node 是个会执行 tool_calls、回填 ToolMessage 的节点。
# 本页聚焦控制流，先把它的实现当成"黑盒"——见第 5 章的 ToolNode
builder.add_node("tools", some_tool_node)

# 普通边：入口固定进 chatbot
builder.add_edge(START, "chatbot")
# 条件边：chatbot 跑完后，由 should_continue 决定去哪
builder.add_conditional_edges("chatbot", should_continue)
# 普通边：tools 跑完回 chatbot(形成循环)
builder.add_edge("tools", "chatbot")
十几行，就是完整骨架： 这就是 ReAct agent（第 5 章会从零搭一遍）：chatbot 决定要不要调工具，要调就去 tools，调完回 chatbot 继续推理，循环到不需要为止。START 和 END 是两个保留字（实际值是 "__start__" 和 "__end__"，源码 constants.py:30/28 里用 sys.intern 定义的），代表图的入口和出口。条件边返回的字符串就是「下一站节点名」——1.1 那个「查几轮不知道」的需求，到这里变成了一个返回字符串的普通函数。

再对照图 1.1 右半看一遍：那两条一正一反的箭头不是装饰，就是这段代码里的 add_conditional_edges 和 add_edge。循环不是控制流补丁，是图的一部分——这正是它能被持久化、被暂停的原因（每一步转移都是图结构上显式的一笔）。

1.6Reducer：两个节点同时写一个字段，怎么办

这也是最容易被低估的一问。1.4 说节点返回「更新」，那更新怎么落到 State 上？这个问题在两种场景下会爆：

场景一：单节点顺序写。user 节点往 messages 写一条用户消息，bot 节点接着写一条回复。如果合并规则是「新值覆盖旧值」，第一轮的用户消息就被第二轮的回复顶掉了——多轮对话等于每轮失忆。场景需要一个能「追加」的字段。

场景二：并行写入。两个节点在同一步被并行执行，都往 hello 写值。没有合并规则的话，框架直接拒绝执行——下面这段代码可以原样跑一遍，亲手撞一次这个错：

最小复现：两个并行节点写同一字段，触发 InvalidUpdateError
pythonfrom typing_extensions import TypedDict
from langgraph.graph import StateGraph
from langgraph.errors import InvalidUpdateError


class State(TypedDict):
    # hello 没有 reducer -> 默认 LastValue，每步只收一个值
    hello: str


def node_b(state: State) -> dict:
    return {"hello": "world"}  # 两个节点都写 hello


builder = StateGraph(State)
builder.add_node("a", node_b)
builder.add_node("b", node_b)
builder.add_node("c", node_b)
builder.set_entry_point("a")
builder.add_edge("a", "b")  # a 跑完，同时 fan-out 到 b 和 c
builder.add_edge("a", "c")
graph = builder.compile()

graph.invoke({"hello": "there"})
# InvalidUpdateError: At key 'hello': Can receive only one value per step.
#                Use an Annotated key to handle multiple values.
图 1.6：同一份 State，两种下场。上：无 reducer 的字段被两个并行写入撞上，LastValue 盒子直接抛错；下：配了 reducer 的字段把两个写入逐个归约成一个结果。细节见 1.7 的源码。

统一解法：给字段挂一个 Reducer——一个签名固定为 (旧值, 新值) -> 合并结果 的函数，写在字段的 Annotated 注解上。它同时解决上面两个场景：单节点反复写时怎么累积（覆盖还是追加），以及多个并行写入怎么归约成一个确定结果。

代码来源说明 — add_messages 的合并行为：追加、同 ID 替换、支持 RemoveMessage 删除。
pythonfrom typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import add_messages


class State(TypedDict):
    # add_messages： 追加新消息；同 ID 则替换；支持 RemoveMessage 删除
    messages: Annotated[list, add_messages]
    # 自定义 reducer：用 operator.add 把列表拼起来
    # steps: Annotated[list, operator.add]
    # 没有注解的字段 -> LastValue(后写覆盖)


# 看 add_messages 的合并行为：
# old = [HumanMessage("你好", id="1")]
# new = [AIMessage("你好啊", id="2")]
# 合并后 = [HumanMessage("你好", id="1"), AIMessage("你好啊", id="2")]
# 如果 new 里有 id="1" 的消息，它会替换 old 里那条，而不是追加
1.3 埋的雷，在这里拆： messages: list 改成 Annotated[list, add_messages]，一个注解，把「覆盖语义」换成了「追加语义」。这就是 Reducer 的全部形式：不是什么新 API，是字段注解上的一个二元函数。凡是要累积历史的字段，必须配 reducer；凡是「最新值即真相」的字段（计数器、当前路由），不配反而是对的。选择权在你，判断依据是字段的业务语义。
建议实跑一次 上面那个最小复现值得认真跑一遍：InvalidUpdateError: Can receive only one value per step 是 LangGraph 新手报错率第一名。它的根源、以及 reducer 函数到底被谁调用，下一节的 Channel 会落到底。

1.7Channel：合并逻辑落在哪一层

1.6 说 reducer 决定合并——那 reducer 是被谁、在什么时刻调用的？答案藏在 State 每个字段背后的运行时结构里。你写的 messages、count，在编译时不会变成普通的 Python 变量，而是各自被包进一个 Channel（通道）对象——可以理解成「每个字段一个盒子」，盒子规定了这个字段怎么存、怎么收更新、怎么存盘。

对应关系是机械的：1.6 里你写的 Annotated[list, add_messages]，编译时变成一个「拿 reducer 合并多个写入」的盒子；没写注解的字段，变成一个「只认最后一个写入」的盒子。reducer 函数不是被框架凭空调用的——它是盒子 update() 方法里的一行代码。

图 1.7：State 字段 → Channel 盒子。带 reducer 注解的字段变成能合并的盒子，普通字段变成只存最后一个值的盒子。推断逻辑在 state.py:1850 的 _get_channel，无注解字段走 state.py:1871 的 LastValue 兜底。

盒子的种类由有没有 reducer 注解决定，框架在编译时自动推断，你不用手写：

字段写法编译后的 Channel盒子的「更新规则」
messages: Annotated[list, add_messages]BinaryOperatorAggregate(add_messages)把所有写入用 reducer 逐个归并（追加 / 同 ID 替换）
count: int（无注解）LastValue(int)只保留最后一个值；同一 step 收到 2 个值就报错
x: Annotated[int, EphemeralValue(int)]EphemeralValue临时值：写入后只对紧接着的下一个 super-step 可读，随后自动清空（图入口的 START 通道就是它，state.py:1354）

每个 Channel 对外暴露三个核心方法：get()（读当前值）、update(values)（收一批写入、合并进盒子）、checkpoint()（把当前值序列化存盘）。自己写自定义 Channel 时，抽象基类 BaseChannel 强制实现 get()/update()/from_checkpoint() 三者（checkpoint() 有默认实现）。Pregel 引擎在每个 super-step 结束时，统一调所有盒子的 update()——这就是 reducer 真正被执行的时刻。

代码来源说明 — LastValue.update 的「每步只收一个」逻辑（last_value.py:56 起摘录，报错文案在 last_value.py:64）。
python# langgraph/channels/last_value.py:56 —— 1.6 那个 InvalidUpdateError 的发源地
def update(self, values: Sequence[Value]) -> bool:
    if len(values) == 0:
        return False
    if len(values) != 1:                    # 同一个 super-step 收到多个写入
        msg = create_error_message(
            message=f"At key '{self.key}': Can receive only one value per step. Use an Annotated key to handle multiple values.",
            error_code=ErrorCode.INVALID_CONCURRENT_GRAPH_UPDATE,
        )
        raise InvalidUpdateError(msg)       # ← 1.6 报的就是这个错

    self.value = values[-1]                # 只留最后一个，这就是「后写覆盖」
    return True
对比 — BinaryOperatorAggregate.update 的归约循环（binop.py:123 起摘录，reducer 调用在 binop.py:143）。
python# langgraph/channels/binop.py:123 —— 它不报错，把多个写入逐个归约：
def update(self, values: Sequence[Value]) -> bool:
    if not values:
        return False
    if self.value is MISSING:
        self.value = values[0]              # 第一个写入直接播种
        values = values[1:]
    for value in values:                    # 剩下的逐个喂给合并函数
        self.value = self.operator(self.value, value)  # (binop.py:143)
    return True
报错的根： 1.6 那个 InvalidUpdateError，根就在 LastValue.update 的 len(values) != 1 分支里：b、c 两个并行节点都写了 hello，Pregel 在每个 super-step 结束时把 ["world", "world"] 两个值送进 hello 的 LastValue 盒子（触发点在 pregel/_algo.py:319 的 channels[chan].update(vals)），直接抛错。而 BinaryOperatorAggregate 先用第一个写入播种，再把剩下的逐个喂给 operator——也就是你的 reducer——天生能吃多个并行写入。结论：reducer 注解不是类型装饰，它决定你字段的盒子是「遇到并行写入就报错」还是「把并行写入合并起来」。
要不要手写 Channel 99% 的场景不用。会写 Annotated[type, reducer]，框架就自动配 BinaryOperatorAggregate；不写就默认 LastValue（state.py:1871 的 fallback 分支）。只有当内置盒子给不了你要的状态语义（只读、自动过期、跨线程共享、增量流式），才去继承 BaseChannel 实现 get/update/checkpoint——第 9 章的 DeltaChannel（增量流式）就是这种自定义盒子的实例。

日常开发可以完全忽略这一层，把它当实现细节；但有两类时刻它必须被想起来：遇到 InvalidUpdateError 想知道为什么，以及想知道流式输出为什么能拿到增量——两个答案都在盒子里。

1.8Compile：从声明到能跑的程序

最后一个问题：节点、边、字段都声明完了，什么时候真正跑起来？为什么 builder 不能直接 invoke？因为 StateGraph 只是一个构建器（builder）——add_node、add_edge 只是把结构存进内存，此时连图的合法性都没检查过。调用 compile() 后它才变成可执行的 CompiledStateGraph。

图 1.8：compile() 的三步。构建和执行分离——同一个 builder 可以用不同 checkpointer 编译出多个运行实例。
代码来源说明 — 编译带 checkpointer 的图，invoke / stream / batch 用法与 LCEL 一致。
pythonfrom langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

builder = StateGraph(State)
builder.add_node("chatbot", chatbot)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)

# 编译：加 checkpointer 让图支持"短期记忆"和断点恢复
# 不加 checkpointer 也能跑，但无法跨 invoke 保留状态
graph = builder.compile(checkpointer=InMemorySaver())

# 编译后就是个 Runnable，用法和 LCEL 链一样
config = {"configurable": {"thread_id": "thread-1"}}
result = graph.invoke(
    {"messages": [("user", "你好")]},
    config,
)
# result["messages"] = [HumanMessage("你好"), AIMessage("你说了：你好，我收到了。")]

# 同一个 thread_id 再 invoke，会接续上一轮的 messages(短期记忆)
result2 = graph.invoke(
    {"messages": [("user", "我刚才说了什么？")]},
    config,
)

# 也支持流式输出、批量
for chunk in graph.stream({"messages": [("user", "嗨")]}, config):
    print(chunk)
for r in graph.batch(
    [{"messages": [("user", "A")]}, {"messages": [("user", "B")]}],
    [{"configurable": {"thread_id": "t1"}}, {"configurable": {"thread_id": "t2"}}],
):
    pass
compile() 还能接什么： interrupt_before / interrupt_after（在指定节点前后暂停，人机协同用）、store（长期记忆）、debug 等参数。这里记住主线就够：构建和执行是分开的——先声明图结构，编译后得到可复用、可持久化的执行单元；同一个 thread_id 多次 invoke 会接续状态，那是 checkpointer 的功劳，第 9 章展开。

1.10新手常犯的错误

正确用法讲了这么多，但真正让人记住一个概念的，往往是踩过的坑。下面三个是这一章的六个概念里最高频的误区，每条都对应一个已经讲过的机制——复习时对照着看，比只背「正确写法」记得牢。

节点返回全量 state，而不是 partial state

1.4 强调节点返回的是只想修改的那几个字段的更新，不是完整的新 State。新手常把整个 state 拷出来改完再 return state——多数时候能跑，但它埋了两个雷：一是和 reducer 语义打架（add_messages 想追加，你却把完整列表当「更新」传回去，行为变得不可预期）；二是抹掉了「只关心一两个字段」这个让节点可复用、可测试的核心约定。

反面 vs 正面：节点该返回什么
python# ✗ 反面：拷出全量 state 再返回
def chatbot(state: State) -> dict:
    state["messages"].append(AIMessage(content="hi"))
    return state  # 把整个 dict 回传，和 reducer 约定冲突

# ✓ 正面：只返回想改的字段
def chatbot(state: State) -> dict:
    return {"messages": [AIMessage(content="hi")]}
正面写法对在哪：它只返回 {"messages": [...]}，把「怎么合并」交给 1.6 的 reducer。add_messages 会把它追加进历史，而不是当成一份完整的新列表。记住签名是 State -> Partial[State]，不是 State -> State。

忘了给 messages 配 add_messages，历史被覆盖

这是 1.6 反复出现的主题：messages 不挂 reducer 就走默认 LastValue，后写覆盖先写，多轮对话里每条消息都被下一条顶掉。因为这条坑足够典型，第 3 章（3.2）专门用了一段可运行代码展示「历史丢失」的全过程和修法——这里不重复，只记一条：凡是要累积历史的字段，必须配 reducer。

fan-out 写同一字段，撞出 InvalidUpdateError

1.6 的最小复现已经看过：LastValue 通道每步只认一个值，两个并行节点写同一个无 reducer 的字段就报错。它和上一条其实是同一枚硬币的两面——reducer 的两大职责：决定单次写入怎么累积（覆盖 vs 追加），以及让多个并发写入能归约成一个确定结果。遇到这个报错，别去「减少并行」，给字段配 reducer。

根源 这三条的共同根源是把「状态更新」当成了「状态覆盖」。LangGraph 的心智模型里，节点返回的是更新请求，怎么落地由 reducer 决定——一旦你开始问「这个字段该用哪种合并语义」，你就从「写普通函数」切换到了「设计状态机」。

1.11读完本章，你应该能回答

先自己作答，再展开对照。这些题检验的是因果和取舍，不是术语复述。

Q1 · 两个并行节点分别返回 {"count": 1} 和 {"count": 2}，State 里 count: int 没有任何注解。运行会发生什么？要让它不报错，有哪两类改法，语义差别是什么？
抛 InvalidUpdateError: At key 'count': Can receive only one value per step——LastValue 盒子每个 super-step 只收一个写入。改法一：挂归并型 reducer，如 Annotated[int, operator.add]，两个写入被加成 3，语义是「都算数」；改法二：挂挑选型 reducer，如取 max，语义是「只要赢家」。选择依据是业务含义：计数累积用前者，状态竞争（谁最新用谁）用后者。报错的根源不是「并行」，是无 reducer 的字段遇到了多个写入。
Q2 · 节点里写 state["messages"].append(reply) 然后 return state，多数时候能跑。说出它坏在哪，以及正确写法。
两个问题：一是全量 state 被当作「更新」重新提交，messages 挂了 add_messages 时，完整历史被当成新一轮写入去归并——行为取决于 reducer 实现，通常造成消息重复或顺序错乱；二是抹掉了 partial-update 约定，节点被迫了解全图字段，不可复用。正确写法：只返回 {"messages": [reply]}，原地 append 也别做（那是把可变共享当更新机制）。本质：节点返回的是「更新请求」，不是「新状态」。
Q3 · 图恢复执行时，为什么框架选择「从头重跑节点」，而不是「从暂停的那一行继续」？这个设计逼着你在写节点时遵守什么纪律？
暂停时函数栈帧和局部变量已经随进程消失，框架拥有的只有 checkpoint 里的图状态（各 channel 的值）；「从第 N 行继续」需要持久化全部局部变量，跨进程做不到。唯一可靠的恢复点是「以图状态为输入重跑一遍函数」——函数开头总能从图状态重建一切。纪律：interrupt 之前不能放不可重复的副作用（发邮件、扣款要放在恢复拿到答案之后）。第 6 章会把恢复重跑的代价展开成几条明确的纪律。
Q4 · StateGraph 和 CompiledStateGraph 的分工是什么？同一个 builder 编译两次（配不同的 checkpointer），得到的是什么关系？
前者是构建器：只存结构（节点、边、状态 schema），不能跑；compile() 时校验图（入口、悬空节点）、把字段转成 channel、生成 Pregel 执行计划，产出实现 Runnable 接口的可执行图。编译两次得到两个共享同一份结构、运行配置互相独立的实例——比如一个带 InMemorySaver 用于测试、一个带 SqliteSaver 用于生产，结构不用重写。这就是「构建/执行分离」买到的复用。
Q5 · 判断题：State 里 current_route: str 记录「本步决定走哪条分支」，只有一个节点会写它。该字段需不需要 reducer？retrieved_docs: list 呢？
current_route 不需要——它是「最新值即正确值」的单写者字段，默认 LastValue（后写覆盖）恰好正确；随手挂个 operator.add 反而会越加越长。retrieved_docs 需要看写入模式：单节点逐步追加，不配也能工作（每步一个写入、覆盖为「新列表」），但配 operator.add 语义更准（多次写入累积）；若有两个节点并行检索再汇总，则必须配，否则直接撞 InvalidUpdateError。判断标准只有一条：字段的业务语义要求「覆盖」还是「累积」。
