整体架构：Codex 这台「Agent 机器」由哪些部件组成

Codex 是一个 137 个 crate 的 Rust 工作区，但真正理解它的 Agent 运行时，只需抓住三层：协议层（类型）、内核层（运行时引擎）、前端层（外壳）。下面把整台机器拆开，看清每个 crate 各管什么。

1.1一分钟版本

一个编码 Agent 运行时，本质上是在回答三个问题：① 模型这一轮该看到什么（Context）？② 这一轮要做什么（调用 LLM / 执行工具）？③ 这一切如何被记住、并能在崩溃后重建（Session/Rollout）？ Codex 把这三个问题的答案落在 codex-rs 工作区的一组 crate 里：

  • codex-protocol — 类型契约：ResponseItem、Op、EventMsg、SandboxPolicy…… 所有跨层共享的数据类型独立成一个 crate。
  • codex-core — Agent 内核：CodexThread / Session / run_turn 循环、上下文构建、压缩、工具调度、配置。
  • codex-tui / codex-cli / codex-app-server — 前端外壳：终端 UI、命令行、程序化 RPC，三者共享内核与协议。

关键洞察：内核不直接调 LLM API、不渲染终端、不持有 UI 状态——它只通过 protocol 定义的 Op/Event 与外界通信。 想自己做 Agent Runtime，你真正要消化的是 core 与 protocol 两个 crate。

1.3协议先行：为什么类型要独立成 crate

可能让你意外的是：codex-protocol 这个 crate 几乎不含业务逻辑，它只定义类型。但它是整个架构的地基。来看 lib.rs 导出了什么：

codex-rs/protocol/src/lib.rs — 协议层导出的模块
rustpub mod approvals;
pub mod config_types;
pub mod items;          // TurnItem、ContextCompactionItem 等
pub mod models;         // ResponseItem —— 会话条目的核心枚举
pub mod protocol;       // Op、EventMsg、SandboxPolicy、Event
pub mod turn_input;     // TurnInput / TurnInputRequest / SteerSubmission
pub mod permissions;
pub mod openai_models;  // ReasoningEffort、ToolMode 等
// ... 还有 mcp / network_policy / realtime / 等等
pub use thread_id::{RolloutId, ThreadId};
pub use tool_name::{ToolName, DEFAULT_FUNCTION_NAMESPACE};
读懂这段： 把所有「跨层共享的数据形状」抽出来，意味着 内核发出的 Event 和前端收到的 Event 是同一个 Rust 类型——编译期保证两端对齐，没有手写 JSON schema 漂移的问题。这是 Codex 架构的第一个关键决策：协议即类型。第 2 章会彻底拆开 Op/Event/ResponseItem。

1.4内核的入口：CodexThread

L1 的核心是 CodexThread——它是「一个会话线程」的拥有者，对内驱动 Session，对外暴露 Op 通道。来看它的导出与字段：

codex-rs/core/src/lib.rs — 内核导出 CodexThread
rustmod codex_thread;
// ...
pub use codex_thread::{BackgroundTerminalInfo, CodexThread};
pub use codex_thread::{CodexThreadSettingsOverrides, GuardianRootMessage};
pub use codex_thread::{GuardianRootSnapshot, ThreadConfigSnapshot};
pub use session::turn_context::TurnContext;
codex-rs/core/src/codex_thread.rs — CodexThread 持有的东西（节选）
rustuse codex_protocol::protocol::{Event, Op, Submission, ...};
use codex_rollout::state_db::StateDbHandle;
use tokio::sync::{Mutex, oneshot, watch};
use tokio_util::sync::CancellationToken;

static LIVE_THREADS: Gauge = Gauge::new("core.threads.live");

#[derive(Clone, Debug)]
pub struct ThreadConfigSnapshot {
    pub model: String,
    // ... 模型、审批、沙箱等当前线程配置
}
为什么这么设计： CodexThread 把「一个会话的所有运行时状态」打包成一个可克隆的句柄——它内部用 tokio 的异步通道（oneshot 做请求-响应、watch 做状态广播、CancellationToken 做取消）。前端拿到 CodexThread 后，只需往里发 Op、从 Event 流里读结果。内核与前端之间唯一的耦合就是 Op/Event 通道。 第 3 章会展开它如何驱动 turn。

1.6对自研与使用的第一个启示

要点 别一上来就做 TUI 和一堆工具。自研 Runtime 的 MVP 只需三件事串起来：① 一套协议类型（你的 Op/Event/Message）；② 一个「采样 → 工具 → 再采样」的循环；③ 一个能持久化与回放的会话模型。 这三件事恰好对应本章的 protocol + codex_thread/turn + rollout，后续章节逐一拆开。
捷径 想快速跑起来：cd codex-rs && cargo run --bin codex -- "explain this codebase to me"。源码入口在 cli/src/main.rs（命令分发）与 tui/src/main.rs（终端启动）。
