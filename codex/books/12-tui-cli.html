12 · TUI 与 CLI：前端的多种姿态

第 2 章我们说 Codex 是「协议优先」——内核与前端解耦。这一章看前端如何消费那个协议。 Codex 不止是「终端里的聊天框」，它是一组前端：交互式 TUI、非交互 exec、app-server 守护进程、MCP server 模式。 它们共享同一套 Op/Event 协议，却服务于截然不同的使用场景——从人机结对编程到 CI 无人值守。

12.1前端的四种姿态

Codex 的二进制 codex 是一个多子命令的 CLI。不传子命令时进入交互式 TUI；传子命令则进入不同模式：

codex-rs/cli/src/main.rs:104

12.2TUI：基于 ratatui 的终端界面

交互式 TUI 用 ratatui + crossterm 渲染。它的核心不是一个简单的 println 循环，而是一个事件驱动的状态机——三类事件汇入一个 AppEvent 通道：用户键鼠事件、内核 Event、定时器。

codex-rs/tui/src/custom_terminal.rs
use crossterm::cursor::{MoveTo, SetCursorStyle};
use crossterm::style::{Print, SetColors, SetBackgroundColor, ..};
use crossterm::terminal::Clear;

/// 设置一帧渲染后光标应处的位置（由 ratatui 在 flush 时落到终端）。
pub fn set_cursor_position<P: Into<Position>>(&mut self, position: P) {
    self.cursor_position = Some(position.into());
}

/// 渲染一帧：把 Widget 画到 buffer，再 flush 到终端。
pub fn render_widget_ref<W: WidgetRef>(&mut self, widget: W, area: Rect) {
    widget.render_ref(area, self.buffer);
}
codex-rs/tui/src/app.rs
pub(crate) struct App {
    // 统一的事件出口：用户输入 / 内核事件 / 定时器都走这里
    pub(crate) app_event_tx: AppEventSender,
    // 每个子 Agent 线程一个独立的事件通道
    thread_event_channels: HashMap<ThreadId, ThreadEventChannel>,
    thread_event_listener_tasks: HashMap<ThreadId, JoinHandle<()>>,

    pub(crate) async fn handle_tui_event(..) { .. }  // 处理一帧事件
}

注意 thread_event_channels：TUI 不只展示一个 Agent 的输出，它为每个子 Agent 线程维护独立通道（呼应第 11 章多 Agent）。这让你能在 TUI 里同时看到主 Agent 和它派生的 explorer/worker 的活动。

12.3TUI 与内核的桥梁：app-server 协议

关键点：TUI 不直接持有 CodexThread。它通过 app-server-protocol 的 JSON-RPC 风格协议与内核通信——发 ClientRequest，收事件。

codex-rs/tui/src/app_server_session.rs
// TUI 启动一个会话：发 ThreadStart 请求
pub(crate) async fn request_thread_start_with_history_fallback(..) {
    match request_handle.request_typed(ClientRequest::ThreadStart {
        request_id,
        ..                          // 初始历史、配置、instructions
    }).await { .. }
}

// 列模型、拉 requirements 等也是 typed request
request_handle.request_typed::<ModelListResponse>(ClientRequest::ModelList {
    request_id: model_request_id, ..
})
图 12.1：TUI 不直接持有内核，而是通过 app-server 协议发请求、收事件。同一协议也供桌面 app / 远程客户端复用。
为何不直接持有 把 TUI 与内核用协议隔开，换来的是前后端可独立部署：内核可以跑成守护进程（app-server），TUI 只是众多客户端之一。桌面 app、Web 客户端、远程控制都能复用同一协议。这就是第 2 章「协议优先」在前端层的兑现。

12.4exec：非交互执行

codex exec 面向脚本与 CI——给一个 prompt，跑完输出结果，不进交互循环。它支持 --json 输出结构化事件流，便于程序解析。

codex-rs/exec/src/cli.rs
// cli/src/main.rs 里 `use codex_exec::Cli as ExecCli`，故 Subcommand::Exec(ExecCli) 引用的就是它。
pub struct Cli {
    pub shared: ExecSharedCliOptions,
    /// 输出 JSON 事件流（别名 experimental-json）
    #[arg(long = "json", alias = "experimental-json")]
    pub json: bool,
}

pub enum Command {
    /// 按 id 恢复之前的会话，或 --last 取最近。
    Resume(ResumeArgs),
    /// Fork 一个之前的会话到新会话。
    Fork(ForkArgs),
    /// 对当前仓库跑代码评审。
    Review(ReviewArgs),
}

exec 模式复用第 4 章的 rollout 能力——Resume 和 Fork 直接操作历史会话。它的输出是一组结构化 item 事件：

codex-rs/exec/src/exec_events.rs
// 生命周期事件：一个 item 的开始 / 更新 / 完成
pub enum ThreadEvent {
    ItemStarted(ItemStartedEvent),
    ItemUpdated(ItemUpdatedEvent),
    ItemCompleted(ItemCompletedEvent),
    Error(ThreadErrorEvent),
}

// 一个 item 的具体内容（嵌在上述事件里）
pub enum ThreadItemDetails {
    AgentMessage(AgentMessageItem),        // Agent 的一条消息
    CommandExecution(CommandExecutionItem), // 一次命令执行
    FileChange(FileChangeItem),           // 文件变更
    McpToolCall(McpToolCallItem),          // MCP 工具调用
    Error(ErrorItem),                    // 错误
}

pub struct CollabAgentState { .. }   // 协作子 Agent 状态

这套 item 事件模型把内核的原始 Event 投影成面向消费者的结构——CI 系统关心的是「哪条命令跑了、改了哪些文件、Agent 说了什么」，而非内核的 Op/Event 细节。ItemStarted/Updated/Completed 三态让下游能实时跟踪进度。

12.5app-server：守护进程与多会话

codex app-server 把内核跑成一个长驻守护进程，支持多传输（stdio / WebSocket / Unix socket）、多会话、远程控制。这是 Codex 走向「桌面 app + 云端」的基石。

codex-rs/app-server/src/lib.rs
use crate::transport::{
    ConnectionOrigin, ConnectionState,
    OutboundConnectionState,
    RemoteControlPolicy, RemoteControlStartConfig,
    TransportEvent,
    acquire_app_server_startup_lock,      // 单实例锁
    start_control_socket_acceptor,        // 控制 socket
    start_remote_control,                 // 远程控制
    start_stdio_connection,               // stdio 传输
    start_websocket_acceptor,             // WebSocket 传输
    route_outgoing_envelope,              // 出站信封路由
};

transport 层抽象了多种连接方式，让同一个 app-server 既能被本地 TUI 经 stdio 调用，也能被桌面 app 经 WebSocket 调用，还能接受远程控制（带 RemoteControlPolicy 鉴权）。acquire_app_server_startup_lock 保证一台机器上只有一个守护实例，多个前端连到同一个共享 app-server——这就是 codex agents 子命令能「浏览所有本地会话」的原理。

12.6MCP server 模式：角色反转

codex mcp-server 让 Codex 自己作为 MCP 服务器暴露——第 10 章里 Codex 是 MCP 客户端，这里它反过来成为服务器，供其它 Agent 客户端调用。这构成一个有趣的对称：Codex 既能消费 MCP 工具，也能被消费为 MCP 工具。

这意味着你可以把 Codex 作为一个「编码能力」挂到任何支持 MCP 的客户端下——比如另一个 Agent 框架需要写代码时，不必自己实现工具，直接 spawn 一个 Codex MCP server。这是 Agent 生态互操作的关键。

12.7会话管理：resume / fork / queue / archive

CLI 提供一组会话管理命令，全部建立在第 4 章 rollout 持久化之上：

命令作用对应 InitialHistory
codex resume恢复会话继续Resumed
codex fork从某点分叉新会话Forked
codex queue给已有会话排队消息Resumed (+ steer)
codex archive归档会话—
codex delete永久删除会话—

这些命令把 rollout 的「事件源」能力直接暴露给用户——会话不是一次性的，而是可恢复、可分叉、可归档的持久资产。这是 Codex 区别于「阅后即焚」式 Agent 的核心特征。

12.8小结与对自研的启示

自研 checklist 前端多样性是 Agent 落地的关键——同一内核要服务不同场景。① 协议优先——内核与前端用协议隔开，别让 TUI 直接持有内核对象，否则加新前端要重写。② 一份内核多种前端——交互式 / 非交互 / 守护进程 / 作为工具被调用，覆盖人机与机机两类消费者。③ 非交互模式要有结构化输出——CI 需要可解析的事件流（JSON item），不是给人看的 ANSI 文本。④ 多传输守护进程——app-server 支持 stdio/WebSocket/socket，才能服务桌面和远程。⑤ 会话是一等公民——resume/fork/queue/archive 让会话可持久管理，而非阅后即焚。⑥ 角色可反转——既能消费 MCP 也能作为 MCP 被消费，融入更大生态。
一句话 Codex 的前端哲学：「协议隔离内核，一份内核多种姿态」。TUI/exec/app-server/mcp-server 四种前端共享同一套 Op/Event 协议，从结对编程到 CI 无人值守到生态互操作，全由同一个内核支撑。
