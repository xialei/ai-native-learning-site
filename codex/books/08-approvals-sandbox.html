08 · 审批与沙箱：让 Agent 安全地动手

一个能读写文件、执行 shell 的 Agent，每一步都可能出错。Codex 用两层防线约束它： 沙箱（Sandbox）从 OS 层限制能碰什么；审批（Approval）决定哪些动作要停下来问人。 本章拆解这两个系统的协作，以及它们如何被同一个 execpolicy 引擎统一裁决。

8.1两条防线，一次裁决

很多 Agent 框架把「能不能执行」拆成一堆零散的 if-else。Codex 的设计更收敛：它把权限判定（这条命令允许吗？）与沙箱构造（用什么沙箱跑它？）合并成一个 ExecApprovalRequirement 决策结果，由工具编排器（tool orchestrator）统一消费。

图 8.1：一条命令的完整裁决路径。execpolicy 给出 Decision（语义判定），审批策略 AskForApproval 再决定要不要把判定结果上报给人。两者合并成 ExecApprovalRequirement。
设计要点 注意裁决是静态发生的——在进程真正 spawn 之前。Codex 不依赖「先跑了再说，出问题再回滚」。它先问 execpolicy「这条命令属于哪类」，再据此构造沙箱或拦下。这让安全策略可审计、可版本化（写成 TOML 规则文件）。

8.2沙箱策略：SandboxPolicy

SandboxPolicy 是对「进程能访问哪些资源」的抽象描述——它不绑定具体平台，而是一个声明式的意图。平台后端（macOS seatbelt / Linux bubblewrap+seccomp / Windows restricted token）负责把这个意图落地成真实的内核限制。

codex-rs/protocol/src/protocol.rs:1078
/// Determines execution restrictions for model shell commands.
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize, Display, JsonSchema, TS)]
pub enum SandboxPolicy {
    /// No restrictions whatsoever. Use with caution.
    DangerFullAccess,

    /// Read-only access configuration.
    ReadOnly {
        /// true 时允许出站网络；默认 false。
        network_access: bool,
    },

    /// 进程已处在外部沙箱中。允许全盘访问，但遵守 network 设置。
    ExternalSandbox {
        network_access: NetworkAccess,
    },

    /// 同 ReadOnly，但额外允许写入工作目录 (workspace)。
    WorkspaceWrite {
        /// 额外可写目录（除 cwd 和可能的 TMPDIR 之外）。
        writable_roots: Vec<AbsolutePathBuf>,
        network_access: bool,
        /// true 时不在默认可写根中加入 per-user TMPDIR。
        exclude_tmpdir_env_var: bool,
        /// true 时不在默认可写根中加入 /tmp (UNIX)。
        exclude_slash_tmp: bool,
    },
}

四个变体构成一个从松到紧的阶梯。注意 WorkspaceWrite 才是 Agent 正常工作时的默认档——它允许写当前项目，但依然挡住对系统其它位置的写入。

反直觉点 ReadOnly 和 WorkspaceWrite 都默认禁网（network_access: false）。也就是说，Agent 默认不能联网发请求。需要网络（如 npm install）时，要么显式放开，要么命中一条 execpolicy allow 规则。这是「最小权限」原则的直接体现。

8.3审批策略：AskForApproval

如果说 SandboxPolicy 回答「能不能在技术上做」，那么 AskForApproval 回答「要不要停下来问问人」。二者正交：你可以沙箱很紧但从不问人（全自动），也可以沙箱很松但每步都问（人盯模式）。

codex-rs/protocol/src/protocol.rs:992
pub enum AskForApproval {
    /// 用于 untrusted 项目。除非 execpolicy 显式放行，否则每条命令都要审批。
    UnlessTrusted,

    /// 模型决定何时请人审批（默认值）。
    OnRequest,

    /// 细粒度控制：某类为 true 则放行，为 false 则自动拒绝而非询问。
    Granular(GranularApprovalConfig),

    /// 从不请人审批。失败直接返回给模型，绝不升级给人。
    Never,
}
codex-rs/protocol/src/protocol.rs:1018
pub struct GranularApprovalConfig {
    /// 是否允许 shell 命令审批请求（含提权请求）。
    pub sandbox_approval: bool,
    /// 是否允许 execpolicy 的 prompt 规则触发的询问。
    pub rules: bool,
    /// 是否允许 skill 脚本执行的审批提示。
    /// （历史字段：skill 已改走普通 turn 沙箱/审批，此开关现仅影响提示词）
    pub skill_approval: bool,
    /// 是否允许 request_permissions 工具触发的提示。
    pub request_permissions: bool,
    /// 是否允许 MCP elicitation 提示。
    pub mcp_elicitations: bool,
}

Granular 是面向「自动化部署」场景的关键设计。当评审者是一个自动审核 Agent（而非真人）时，你不希望它被某些类别的弹窗卡住，而是直接拒绝。例如：允许 sandbox_approval（让自动审核批准沙箱提权），但关掉 mcp_elicitations（不让外部 MCP 把流程挂起等待人工输入）。

策略何时问人典型场景
UnlessTrusted几乎总是问克隆下来的陌生项目（Untrusted）
OnRequest模型判断需要时日常交互开发（默认）
Granular(..)按类别开关自动审核 / CI 无人值守
Never从不完全信任的沙箱环境

8.4信任等级与审批者

两个辅助枚举把策略和「这个项目可信吗」「谁来回答审批」串起来。

codex-rs/protocol/src/config_types.rs:641
/// 项目目录的信任等级，决定审批策略与沙箱模式。
pub enum TrustLevel {
    Trusted,
    Untrusted,
}

codex-rs/protocol/src/config_types.rs:183
pub enum ApprovalsReviewer {
    /// 默认：由终端前的真人回答审批。
    User,
    /// 由一个自动审核子 Agent 回答（无人值守）。
    AutoReview,
}

当一个项目被标记为 Untrusted，Codex 会强制套用 AskForApproval::UnlessTrusted——即「宁可烦人，不可越权」。而 ApprovalsReviewer::AutoReview 则把审批弹窗导向一个专门的审核 Agent，使整个审批流程可以在 CI 里无人跑通。这两个枚举共同定义了 Codex 的自主程度：从全人盯到全自动。

8.5execpolicy：规则引擎与 Decision

审批策略是粗粒度的开关，但 Agent 执行的命令千差万别——ls 该问人吗？rm -rf / 呢？git push 呢？这些判断不能写死在代码里。Codex 用一个独立的 execpolicy crate 提供可配置的规则引擎，规则写在 *.rules 规则文件里（位于各配置层的 rules/ 目录，默认 codex_home/rules/default.rules）。

每条命令解析后，引擎给出一个三值判定：

codex-rs/execpolicy/src/decision.rs
pub enum Decision {
    Allow,      // 放行（可能附带 bypass_sandbox）
    Prompt,     // 需要审批
    Forbidden,  // 拒绝
}

这个 Decision 进入 create_exec_approval_requirement_for_parsed_commands，与审批策略合并，产出最终的 ExecApprovalRequirement：

codex-rs/core/src/exec_policy.rs:394
match evaluation.decision {
    Decision::Forbidden => ExecApprovalRequirement::Forbidden { reason, .. },
    Decision::Prompt => {
        let prompt_is_rule = evaluation.matched_rules.iter().any(|rm| {
            is_policy_match(rm) && rm.decision() == Decision::Prompt
        });
        match prompt_is_rejected_by_policy(approval_policy, prompt_is_rule) {
            // 审批策略拒绝展示此 prompt → 直接 Forbidden
            Some(reason) if prompt_is_rule => ExecApprovalRequirement::Forbidden { reason, .. },
            Some(reason)                  => ExecApprovalRequirement::Forbidden { reason, .. },
            // 策略允许 → 需要审批
            None => ExecApprovalRequirement::NeedsApproval { reason, .. },
        }
    }
    Decision::Allow => ExecApprovalRequirement::Skip {
        bypass_sandbox: /* 每个命令段都被显式 allow 规则放行时为 true */
        ..
    },
}
关键细节 prompt_is_rejected_by_policy 是 Granular 模式的核心：当某类审批被配置成 false，一个本该 Prompt 的命令不会去打扰人，而是直接被 Forbidden 返回给模型。这让「自动审核」不会卡在等待输入上——它收到的是一个明确的「拒绝」，从而可以调整策略重试。

更有意思的是 proposed_execpolicy_amendment：当一条命令被审批（或被放行）后，引擎会提议一条新规则，让下次同类命令免审批。这是 Codex 的「学习」机制——用户批一次 npm test，之后 npm test 就自动放行，规则被追加进 default.rules 文件。

8.6ExecApprovalRequirement：统一决策结果

三股输入（execpolicy Decision + AskForApproval + 文件系统沙箱状态）最终汇总成一个枚举，供工具编排器消费：

codex-rs/core/src/tools/sandboxing.rs:152
/// Specifies what tool orchestrator should do with a given tool call.
pub(crate) enum ExecApprovalRequirement {
    /// 无需审批。
    Skip {
        bypass_sandbox: bool,  // 首次尝试是否绕过沙箱（如被显式放行）
        proposed_execpolicy_amendment: Option<ExecPolicyAmendment>,
    },
    /// 需要审批。
    NeedsApproval {
        reason: Option<String>,
        proposed_execpolicy_amendment: Option<ExecPolicyAmendment>,
    },
    /// 禁止执行。
    Forbidden { reason: String },
}

这个枚举是「审批」与「沙箱」两大系统的事实接口。拿到 Skip 就直接构造沙箱跑；拿到 NeedsApproval 就发 EventMsg 询问；拿到 Forbidden 就把拒绝原因作为工具输出回灌给模型。模型于是知道「这条命令不被允许」，可以选择别的路径——这正是 Agent 在约束下自主规划的体现。

8.7平台沙箱后端

SandboxPolicy 是意图，落地靠 sandboxing crate 的 SandboxManager。它按平台选择后端，把意图翻译成具体的进程启动参数。

codex-rs/sandboxing/src/manager.rs
pub enum SandboxType {
    None,
    MacosSeatbelt,         // macOS: sandbox-exec (seatbelt)
    LinuxSeccomp,          // Linux: bubblewrap + seccomp（landlock 为 legacy 选项）
    WindowsRestrictedToken,// Windows: 受限令牌
}

pub fn get_platform_sandbox(windows_sandbox_enabled: bool) -> Option<SandboxType> {
    if cfg!(target_os = "macos") {
        Some(SandboxType::MacosSeatbelt)
    } else if cfg!(target_os = "linux") {
        Some(SandboxType::LinuxSeccomp)
    } else if cfg!(target_os = "windows") {
        if windows_sandbox_enabled { Some(SandboxType::WindowsRestrictedToken) }
        else { None }
    } else { None }
}

关键方法是 SandboxManager::transform——它接收一个 SandboxTransformRequest（内含原始命令 SandboxCommand + 权限配置 + 沙箱类型），输出一个 SandboxExecRequest（带沙箱启动参数、可直接执行的 host-native 请求）。这是「意图 → 可执行进程」的转换边界。

平台后端机制
macOSseatbeltsandbox-exec，profile 限定文件/网络
Linuxbubblewrap + seccompbwrap 建容器化命名空间限文件，seccomp 限系统调用；landlock 为可选 legacy（--use-legacy-landlock）
Windows受限令牌降权进程令牌 + ACL

沙箱的可写根概念值得展开。即使 WorkspaceWrite 允许写工作目录，Codex 仍会保护目录内的敏感子路径——例如 .git/hooks。因为 Agent 一旦能写 git hook，就能在下次 commit 时插入恶意脚本，构成提权。于是有 WritableRoot 的「可写根内只读子路径」设计：

codex-rs/protocol/src/protocol.rs:1134
pub struct WritableRoot {
    pub root: AbsolutePathBuf,
    /// 这些子路径即便在可写根下也保持只读（防 .git/hooks 等提权点）。
    pub read_only_subpaths: Vec<AbsolutePathBuf>,
    /// 受保护的元数据路径名（不得被创建/替换）。
    pub protected_metadata_names: Vec<String>,
}
安全纵深 这是纵深防御（defense in depth）的典型例子：不只「能写工作目录」，还要「工作目录里的危险点仍不可写」。沙箱不是一道墙，而是一张带漏洞例外的网。自研 Agent 时极易忽略这类二级提权路径。

8.8权限配置：PermissionProfile

在 SandboxPolicy 之上，Codex 还有一层 PermissionProfile，它决定「谁来构建沙箱」以及网络策略。这层主要服务于多前端场景（app-server / exec-server 可能自带外部沙箱）。

codex-rs/protocol/src/models.rs:420
pub enum PermissionProfile {
    /// Codex 自己负责构造沙箱。
    Managed {
        file_system: ManagedFileSystemPermissions,
        network: NetworkSandboxPolicy,
    },
    /// 不施加外层沙箱。
    Disabled,
    /// 文件隔离由外部调用方强制执行。
    External { network: NetworkSandboxPolicy },
}

三个变体对应三种部署形态：Managed 是本地 CLI/TUI 的常态（Codex 自管沙箱）；External 用于进程已被外部沙箱包裹的场景（如容器内）；Disabled 则是显式放弃隔离。sandboxing crate 的 compatibility_sandbox_policy_for_permission_profile 负责把 profile 与 SandboxPolicy 协调成一致。

8.9小结与对自研的启示

自研 checklist 最小安全闭环，按优先级：① 先有沙箱再谈自主——哪怕第一版只是「只允许写工作目录」的简单包装，也比裸跑强。用平台原生机制（macOS seatbelt / Linux bubblewrap），别自己造。② 决策前置——在 spawn 前就用一个枚举（Allow/Prompt/Forbidden）裁决，别等出错再回滚。③ 规则可配置——把「哪些命令免审批」写成数据文件（TOML/JSON），而非硬编码，并支持「批一次就学会」的规则追加。④ 警惕二级提权——可写区内的 .git/hooks、.ssh 等必须额外只读。⑤ 预留自动审核位——审批回答者要可替换（人 / 子 Agent），为无人值守 CI 留口子。
整体视角 Codex 的安全设计是「意图声明 + 平台落地 + 规则可学」：用 SandboxPolicy/AskForApproval 声明意图，用平台后端落地，用 execpolicy 规则让策略随使用自我进化。三层叠加，才让一个能跑 shell 的 Agent 既能干活又不出格。
