10 · MCP 与扩展：让 Agent 的能力可插拔

内置工具（shell、apply_patch）只是底线。Codex 真正的扩展性来自三条线：MCP（Model Context Protocol）接外部工具服务器， Connectors / Plugins封装「应用」为 Agent 可调用的能力，Skills提供可审批的脚本化工作流。 它们共享同一套 ToolSpec 暴露机制——对模型而言，内置工具和扩展工具没有分别。

10.1统一的工具暴露面：ToolSpec

第 7 章我们见过 ToolSpec。这里重新审视它的五个变体，因为扩展系统正是通过这几个口子接入的：

codex-rs/tools/src/tool_spec.rs:24
/// 序列化为 JSON 时，产出合法的 OpenAI Responses API "Tool"。
#[derive(Debug, Clone, Serialize, PartialEq)]
#[serde(tag = "type")]
pub enum ToolSpec {
    /// 标准 function 工具（内置与 MCP 工具都走这个）。
    Function(ResponsesApiTool),
    /// 命名空间工具（把一组工具归到一个 namespace 下）。
    Namespace(ResponsesApiNamespace),
    /// 动态工具发现：模型先搜，再决定调哪个。
    ToolSearch {
        execution: String,
        description: String,
        parameters: JsonSchema,
    },
    /// 内置网页搜索（OpenAI 服务端工具）。
    WebSearch { external_web_access: Option<bool>, .. },
    /// 自由格式工具（如 apply_patch，非 JSON 参数）。
    Freeform(FreeformTool),
}
设计要点 所有扩展能力最终都坍缩成 Function（或 Namespace）变体塞进工具列表。模型看到的就是一个统一的 function 列表，不知道某个工具是内置 shell 还是远程 MCP 服务器提供的。这种「接入面统一、后端多样」的设计，让 Codex 的工具生态可以无限扩展而不污染核心。

10.2MCP：外部工具服务器协议

MCP 是 Anthropic 牵头的开放协议，定义了「LLM 客户端如何从外部服务器发现并调用工具/资源」。Codex 作为 MCP 客户端，可以挂载任意 MCP 服务器——本地 stdio 进程或远程 HTTP 服务。

codex-rs/config/src/mcp_types.rs:514
pub enum McpServerTransportConfig {
    /// stdio 传输：Codex spawn 一个本地子进程，通过 stdin/stdout 通信。
    Stdio {
        command: String,
        args: Vec<String>,
        env: Option<HashMap<String, String>>,
        env_vars: Vec<McpServerEnvVar>,
        cwd: Option<LegacyAppPathString>,
    },
    /// streamable-http 传输：连远程 HTTP 服务器。
    StreamableHttp {
        url: String,
        /// 读哪个环境变量拿 bearer token（密钥不写进配置）。
        bearer_token_env_var: Option<String>,
        http_headers: Option<HashMap<String, String>>,
        /// 值来自环境变量的 header（避免明文密钥）。
        env_http_headers: Option<HashMap<String, String>>,
        /// 本地命令，输出动态 header 的 JSON（如临时 token）。
        http_headers_helper: Option<String>,
    },
}

两种传输对应两种部署：stdio 用于本地工具（如一个查日历的脚本），HTTP 用于 SaaS 集成（如连企业内部 API）。注意安全细节——bearer_token_env_var 和 env_http_headers 把密钥隔离在环境变量里，配置文件只存「变量名」而非值，这是防泄密的标配。

图 10.1：MCP 服务器与内置工具走同一条 ToolRouter 路径。对模型而言，jira_create_issue 和 shell 没有分别。

10.3McpServerConfig：挂载点的全部控制

一个 MCP 服务器不只是「连上去」，还有大量治理开关——这是 Codex 把扩展能力做成「企业可用」的关键。

codex-rs/config/src/mcp_types.rs:181
pub struct McpServerConfig {
    pub transport: McpServerTransportConfig,
    pub auth: McpAuth,                          // 认证流程
    pub environment_id: String,               // 在哪个执行环境起
    pub enabled: bool,                          // 是否初始化
    pub required: bool,                         // codex exec 时失败是否报错退出
    pub supports_parallel_tool_calls: bool,   // 工具能否并行调用
    pub omit_tools_from: Option<Vec<ToolExposureSurface>>, // 从哪些模型面隐藏
    pub startup_timeout_sec: Option<Duration>,
    pub tool_timeout_sec: Option<Duration>,     // 工具调用超时
    pub default_tools_approval_mode: Option<AppToolApproval>,
    pub enabled_tools: Option<Vec<String>>,     // 工具白名单
    pub disabled_tools: Option<Vec<String>>,    // 工具黑名单
    pub scopes: Option<Vec<String>>,             // OAuth scopes
    pub oauth: Option<McpServerOAuthConfig>,
    pub tools: HashMap<String, McpServerToolConfig>, // 逐工具审批设置
}

这套字段体现了「细粒度治理」：enabled_tools/disabled_tools 让你只暴露一个 MCP 服务器里需要的几个工具；default_tools_approval_mode 与逐工具的 tools 覆盖，让审批策略可以精确到单个工具；omit_tools_from 能把某些工具从特定模型面（如某个子 Agent）隐藏。第 8 章的 GranularApprovalConfig.mcp_elicitations 也在此处生效——MCP 服务器的 elicitation 请求可以被整体关掉。

10.4Connectors：应用即工具

Connectors（connectors crate）是 MCP 之上的更高层抽象：它把一个「应用」（如 GitHub、Slack）封装成有元数据、有缓存、有运行时上下文的可调用单元。ConnectorRuntimeManager 负责它们的生命周期与目录缓存。

codex-rs/connectors/src/lib.rs
pub struct ConnectorRuntimeManager { .. }

pub struct DirectoryListResponse {
    apps: Vec<DirectoryApp>,
    next_token: Option<String>,   // 分页游标
}

pub struct DirectoryApp { .. }   // 目录里的一个应用
pub struct AppInfo { .. }        // 启用后解析出的应用信息

// 带缓存的目录查询，避免每次都去远端拉
pub fn cached_directory_connectors(cache_context) -> Option<Vec<AppInfo>>

Connectors 解决的是「应用生态」问题：一个企业可能有几十个内部系统，逐个写 MCP 服务器太重。Connector 框架提供统一的发现、缓存、路由机制——你可以把一组应用装进一个 marketplace，按需启用。这与第 11 章的多 Agent 协作紧密相关：某些 connector 本身就是「应用 Agent」。

10.5Plugins：可编程的扩展钩子

Plugin（plugin + core-plugins crate）比 Connector 更底层，它提供钩子（hooks）——在 Agent 运行的特定时机插入自定义逻辑。一个 plugin 可以声明自己提供哪些能力。

codex-rs/plugin/src/lib.rs
pub struct PluginCapabilitySummary { .. }   // 插件能力摘要

pub struct PluginHookSource { .. }        // 钩子来源
pub struct ExecutorPluginHookSource { .. } // 执行器侧钩子

codex-rs/core-plugins/src/lib.rs
pub type LoadedPlugin = codex_plugin::LoadedPlugin<codex_config::McpServerConfig>;
// 一个 plugin 可以自带 MCP 服务器配置（overlay）

关键设计在最后一行：一个 LoadedPlugin 参数化在 McpServerConfig 上，意味着插件可以携带 MCP 服务器配置作为 overlay。装一个 plugin，等于同时注入了它的钩子逻辑和它依赖的 MCP 工具服务器。这让插件成为一个自洽的能力包——这是 Codex 走向「应用市场」式分发的基石（core-plugins 里有 manager 模块管 ConfiguredMarketplacePlugin）。

10.6Skills：可审批的脚本化工作流

Skill 是面向「重复性操作」的扩展：把一套多步操作封装成脚本，模型按需调用。与普通工具不同，Skill 执行走独立的审批通道——这正是第 8 章 GranularApprovalConfig.skill_approval 的由来。

codex-rs/skills/src/lib.rs
// 系统级 skill 安装到 codex_home 下的缓存目录
pub fn system_cache_root_dir(codex_home) -> AbsolutePathBuf;
pub fn install_system_skills(codex_home) -> Result<(), SystemSkillsError>;

pub enum SystemSkillsError { .. }

Skill 的特殊性在于它执行的是脚本（可能是 shell、python），而脚本天然比单条命令更难静态审计。所以 Codex 给它单独的审批开关：skill_approval: false 时，skill 脚本的执行请求会被直接 Forbidden（而非弹窗），让自动审核场景不被挂起。这是「能力越强、管控越细」原则的体现。

10.7ToolSearch：动态工具发现

当挂载的工具太多（几十个 MCP 服务器，上百个工具），把它们全塞进系统提示会爆上下文。ToolSearch 变体解决这个问题：模型不直接看到所有工具，而是先调用 tool_search 按需检索，再调用检索到的具体工具。

codex-rs/tools/src/tool_spec.rs:27
ToolSearch {
    execution: String,      // 检索执行方式
    description: String,    // 给模型看的说明
    parameters: JsonSchema, // 检索参数 schema
}
为什么这很重要 ToolSearch 是 Agent 处理「工具爆炸」的标准解法。想象一个接了 50 个企业系统的 Codex——不可能把 50 套工具的 schema 都塞进上下文。用 ToolSearch，模型只在需要 Jira 时搜出 jira_* 工具，用完即弃。这与第 5 章的上下文工程、第 6 章的压缩是一脉相承的「按需加载」哲学。

10.8三层扩展的关系

层粒度典型形态审批通道
MCP Server单工具服务器stdio/HTTP 进程per-tool / default_tools_approval_mode
Connector应用带目录缓存的应用包AppToolApproval
Plugin能力包（hooks + MCP overlay）marketplace 分发requirements 约束
Skill脚本工作流多步脚本skill_approval 独立开关

四者并非互斥，而是组合：一个 plugin 可以带 MCP overlay，一个 connector 可以暴露多个 MCP 工具，一个 skill 可以调用任意工具。它们共同构成 Codex 的「能力长尾」——核心保持精简，长尾靠扩展。

10.9小结与对自研的启示

自研 checklist 扩展性要早设计、晚实现——先把接入面定下来。① 统一 ToolSpec——无论内置还是扩展，对外都是同一种 function 描述，模型不需要区分来源。② 传输分层——本地用 stdio，远程用 HTTP，密钥走环境变量不落配置。③ 细粒度治理——每个扩展点都要有白/黑名单、超时、审批模式、可见性控制，否则企业不敢用。④ 动态发现——工具多了就要 ToolSearch，别硬塞上下文。⑤ 能力打包——plugin 把「逻辑 + 依赖的 MCP 配置」打成一体，是分发能力的正确粒度。
一句话 Codex 的扩展哲学：「统一接入面 + 分层治理 + 按需发现」。MCP/Connector/Plugin/Skill 四条线，最终都坍缩进同一个 ToolSpec，让 Agent 的能力可以无限生长，而核心循环一行不改。
