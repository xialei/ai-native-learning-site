09 · 配置系统：分层、合并与约束

Codex 既要满足单个开发者在笔记本上的轻量配置，又要支撑企业 MDM 托管、项目级策略、CI 无人值守等截然不同的场景。 它的解法不是「一个大 config 文件」，而是一套分层合并（layered merge）体系： 多个来源各贡献一层 TOML，按优先级叠加成「生效配置」；再用一套约束（requirements）机制保证托管层能锁死安全边界。

9.1配置层栈：ConfigLayerSource

每一份配置都带「出处」。ConfigLayerSource 枚举穷举了所有可能的来源，并给每个来源一个优先级数值——数值大的覆盖数值小的。

codex-rs/config/src/config_layer_source.rs:6
pub enum ConfigLayerSource {
    /// 随安装包自带的默认配置。
    PackagedDefaults { file: AbsolutePathBuf },
    /// MDM（移动设备管理）下发的托管偏好。
    Mdm { domain: String, key: String },
    /// 主机级配置文件。
    System { file: AbsolutePathBuf },
    /// 企业云 bundle 下发的配置。
    EnterpriseManaged { id: String, name: String },
    /// 用户配置，可选叠加一个 profile。
    User { file: AbsolutePathBuf, profile: Option<String> },
    /// 项目 .codex 目录里的配置。
    Project { dot_codex_folder: AbsolutePathBuf },
    /// 本次会话的命令行 flag 覆盖。
    SessionFlags,
    /// 旧式托管配置（文件 / MDM）。
    LegacyManagedConfigTomlFromFile { file: AbsolutePathBuf },
    LegacyManagedConfigTomlFromMdm,
}

pub fn precedence(&self) -> i16 {
    match self {
        PackagedDefaults { .. } => -10,
        Mdm { .. } => 0,
        System { .. } => 10,
        EnterpriseManaged { .. } => 15,
        User { profile, .. } => if profile.is_some() { 21 } else { 20 },
        Project { .. } => 25,
        SessionFlags => 30,
        LegacyManagedConfigTomlFromFile { .. } => 40,
        LegacyManagedConfigTomlFromMdm => 50,
    }
}
图 9.1：配置层栈。底层是打包默认值，顶层是托管配置。每一层只覆盖同名字段，未覆盖的从下层继承。
关键洞察 项目配置（Project, 25）优先级高于用户配置（User, 20）。这意味着你 clone 一个仓库后，它的 .codex/config.toml 能覆盖你的全局设置——这正是「Untrusted 项目」机制存在的理由：陌生项目可能把 sandbox_mode 设成 danger-full-access，所以 Codex 默认对未声明信任的项目套紧策略。

9.2合并机制：overlay 叠加

层与层之间不是「整体替换」，而是字段级合并。merge_toml_values 把 overlay（高优先级层）叠进 base（低优先级层）：表（table）递归合并，标量直接覆盖。

codex-rs/config/src/merge.rs:57
/// Merge config `overlay` into `base`, giving `overlay` precedence.
pub fn merge_toml_values(base: &mut TomlValue, overlay: &TomlValue) {
    merge_toml_values_at_path(base, overlay, &mut Vec::new());
}

所以你在全局 config.toml 里设了 model = "gpt-5"，而项目配置只写了 sandbox_mode = "workspace-write"，合并结果是两者都生效——项目层没有提到的字段从用户层继承。这避免了「要么全配要么不配」的痛苦。

合并也不会掩盖拼写错误。加载完成后，Codex 会对合并后的生效配置以及各 requirements 层再做一次「被忽略字段」检查（基于 serde 的 ignored-field 追踪，见 strict_config.rs）：发现未识别的键，就在启动时给出警告——Codex is ignoring N unrecognized configuration setting(s). Check for typos or deprecated settings. 警告只列出来源和字段名（不回显配置值），最多展示三条，并对几个已迁移的旧键（network_proxy、allowed_permissions、include_view_image_tool）附上迁移提示。

9.3ConfigToml：用户配置的结构

ConfigToml 是 ~/.codex/config.toml 的反序列化目标。它几乎全用 Option——因为每个字段都可能「未设置」，从而让下层值透传上来。

codex-rs/config/src/config_toml.rs:155
pub struct ConfigToml {
    /// 模型选择覆盖。
    pub model: Option<String>,
    /// /review 功能用的评审模型。
    pub review_model: Option<String>,
    /// 从 model_providers map 里选用哪个 provider。
    pub model_provider: Option<String>,
    /// 上下文窗口大小（token 数）。
    pub model_context_window: Option<i64>,
    /// 自动压缩的 token 触发阈值。
    pub model_auto_compact_token_limit: Option<i64>,
    /// 审批策略。
    pub approval_policy: Option<AskForApproval>,
    /// 沙箱模式。
    pub sandbox_mode: Option<SandboxMode>,
    /// sandbox=workspace-write 时的可写根等细节。
    pub sandbox_workspace_write: Option<SandboxWorkspaceWrite>,
    /// 默认权限 profile 名（: 开头是内置）。
    pub default_permissions: Option<String>,
    /// 命名权限 profile。
    pub permissions: Option<PermissionsToml>,
    /// 系统指令。
    pub instructions: Option<String>,
    /// 用文件覆盖模型指令（官方强烈不建议，见下方警告）。
    pub model_instructions_file: Option<AbsolutePathBuf>,
    /// 作为 developer 角色插入的开发者指令。
    pub developer_instructions: Option<String>,
    // ... 还有 profile、mcp_servers、tools、hooks 等
}
官方警告 model_instructions_file 字段（用一个文件覆盖模型指令）上方写着：「用户被强烈建议不要使用此字段，偏离 Codex 认可的指令会降低模型表现。」（而普通的 instructions 字段只带一句 System instructions.。）这说明系统提示词是经过大量调优的——自研 Agent 时也应克制随意改写系统提示，而优先用 developer_instructions（developer 角色）这类受控注入点。

9.4SandboxMode 与 profile

配置层暴露给用户的沙箱概念是 SandboxMode，比第 8 章的 SandboxPolicy 更简化——它面向配置文件，不带可写根细节。

codex-rs/protocol/src/config_types.rs:104
pub enum SandboxMode {
    /// 默认：只读。
    ReadOnly,
    /// 可写工作目录。
    WorkspaceWrite,
    /// 无限制（危险）。
    DangerFullAccess,
}

而 default_permissions 指向一个权限 profile。名字以 : 开头的是内置 profile（:read-only / :workspace / :danger-full-access），否则从 [permissions] 表里按名解析。这与第 8 章的 PermissionProfile（Managed/External/Disabled）对接，把「配置里的名字」翻译成「运行时的权限结构」。

9.5约束系统：requirements.toml

分层合并有个天然问题：如果企业想强制某个安全策略（比如「绝不允许 danger-full-access」），光靠覆盖是不够的——用户或项目层仍可能写回来。Codex 用一套独立的 requirements 机制解决：托管层不提供「配置值」，而是提供「约束」，约束会校验合并后的生效配置是否越界。

codex-rs/config/src/config_requirements.rs:44
pub enum RequirementSource {
    SystemRequirementsToml { file: AbsolutePathBuf },
    // ... 其它托管来源（MDM、EnterpriseManaged、Composite 等）
}

/// 合并归一化后的 requirements。
pub struct ConfigRequirements {
    pub model_provider: Option<Sourced<String>>,
    pub model_providers: Option<Sourced<HashMap<String, ModelProviderInfo>>>,
    pub computer_use: Option<Sourced<ComputerUseRequirementsToml>>,
    pub feature_requirements: Option<Sourced<FeatureRequirementsToml>>,
    pub managed_hooks: Option<ConstrainedWithSource<ManagedHooksRequirementsToml>>,
    pub plugins: Option<Sourced<BTreeMap<String, PluginRequirementsToml>>>,
    pub marketplaces: Option<Sourced<MarketplaceRequirementsToml>>,
    pub exec_policy: Option<Sourced<RequirementsExecPolicy>>,
}

requirements 不只画安全红线。例如 model_provider/model_providers 出现在 requirements 里时，托管方可以锁定模型 provider 的选择并下发完整的 provider 定义（含认证与 headers）——必选 provider 直接覆盖本地与会话配置，每个必选定义替换同名的本地条目。也就是说，同一个文件既能「禁止某些值」（约束），也能「强推某些值」（必选定义）。

注意 ConstrainedWithSource 这个类型名——它表示「带来源的约束」。约束的语义是「能否设置」而非「设成什么」。例如 approvals_reviewer 的约束可以是「只允许 user」，这样无论用户层怎么配，配置加载时校验不通过都会回落到约束允许的值并给出启动警告，自动审核开不了。这是企业安全治理的基石。

配置 vs 约束 配置（config）回答「值是什么」，可被高优先级层覆盖；约束（requirements）回答「值允许是什么」，不可被覆盖，只能校验。这套分离让 Codex 既能给用户自由，又能让管理员画红线。自研企业级 Agent 时，这是必学模式——否则你的「安全默认」会被用户 config 一行覆盖掉。

9.6Profile：命名的配置预设

当一个人在多个场景用 Codex（工作 / 个人 / 演示），反复改 config 很烦。--profile 机制允许命名预设：$CODEX_HOME/<name>.config.toml。选中某个 profile 时，User 层的优先级从 20 升到 21（见 9.1），相当于在用户基础配置之上再叠一层。

codex-rs/protocol/src/config_types.rs:118

pub struct ProfileV2Name(String);

// 解析失败的提示：
"invalid --profile value `{}`; pass a plain name such as `work`"

profile 是纯加法：它只在你已有的用户配置之上叠加，不替换。这让「切换工作场景」变成一条 flag，而非重写整个配置文件。但叠加不等于「处处生效」：显式选中的 profile 设置（model、reasoning effort 等启动选择）会压过托管系统给新会话下发的默认值——托管默认只填补 profile 没有表态的字段，且被项目配置盖住的 profile 设置不算「表态」。

9.8小结与对自研的启示

自研 checklist 配置系统别等做大了再补。① 一开始就分层——默认值 / 用户 / 项目 / 会话 flag，每层带优先级。② 字段级合并而非整文件替换，用 Option 表示「未设置」。③ 配置与约束分离——企业场景必须有「不可被覆盖的红线」，否则安全默认形同虚设。④ 项目配置优先级高于用户配置是合理的（仓库自带策略），但必须配套「未信任项目默认收紧」机制。⑤ 提供 profile 预设——不同场景一键切换。
设计取舍 Codex 的配置设计：「自由叠加 + 不可逾越的约束」。配置层让每个角色（开发者/项目/企业）都能表达偏好，约束层保证安全边界不被覆盖。二者合一，才让同一套二进制能在个人笔记本和企业集群里都安全运行。
