上下文压缩 Compaction：历史太长怎么办

一个长会话很快就会超出模型的上下文窗口。Codex 的解法是 compaction（压缩）：在采样前检测 token 预算，超限时把旧历史摘要成一条 compaction summary，腾出空间继续。本章拆开触发条件、本地 vs 远程压缩、token 预算模式三条路径。

6.1何时触发：采样前检查

第 3 章的 run_turn 第一步就是 run_pre_sampling_compact——在构建 prompt 之前先检查是否该压缩：

codex-rs/core/src/session/turn.rs:1013 — 采样前压缩检查
rustasync fn run_pre_sampling_compact(
    sess: &Arc<Session>,
    turn_context: &Arc<TurnContext>,
    client_session: &mut ModelClientSession,
    cancellation_token: &CancellationToken,
) -> CodexResult<()> {
    maybe_run_previous_model_inline_compact(...).await?;

    // 检查 token 状态
    let token_status = context_window::context_window_token_status(sess, turn_context).await;

    // 配置的自动压缩预算或可用上下文窗口耗尽时压缩
    if token_status.token_limit_reached {
        let step_context = sess.capture_step_context(...).await?;
        run_auto_compact(
            sess, step_context, /*fallback*/ None, client_session,
            InitialContextInjection::DoNotInject,
            CompactionReason::ContextLimit,
            CompactionPhase::PreTurn,
        ).await?;
    }
    Ok(())
}
读懂这段： 触发条件是 token_status.token_limit_reached——由 context_window_token_status 计算得出，它综合了「配置的自动压缩预算」和「可用上下文窗口」两个阈值。注意 CompactionReason::ContextLimit 和 CompactionPhase::PreTurn——压缩有原因和阶段标签，方便遥测与策略分支。压缩发生在采样之前，确保发给模型的 prompt 不会超窗。

6.2三条压缩路径

压缩不止一种实现。run_auto_compact 根据功能开关和 provider 能力，分派到三条路径：

codex-rs/core/src/session/turn.rs:1179 — run_auto_compact 分派
rustasync fn run_auto_compact(sess, step_context, fallback, client_session, injection, reason, phase) {
    if turn_context.config.features.enabled(Feature::TokenBudget) {
        // 路径 A：token 预算压缩
        // 压缩就是重置请求，强制开新 context window
        crate::compact_token_budget::run_inline_auto_compact_task(...).await?;
        return Ok(());
    }

    match turn_context.provider.capabilities().remote_compaction {
        RemoteCompactionSupport::V2 if features.enabled(Feature::RemoteCompactionV2) => {
            // 路径 B：远程压缩 v2（服务端做摘要）
            run_inline_remote_auto_compact_task_v2(...).await?;
        }
        // 路径 C：本地压缩 / 旧远程压缩 ...
    }
}
读懂这段： 三条路径按优先级：① TokenBudget（本地，开新窗口）——不调用模型做摘要，直接重置 context window，最快最省；② 远程压缩 V2——provider 服务端帮你做摘要（OpenAI 后端能力）；③ 本地压缩——本地调模型生成摘要。选哪条取决于功能开关 + provider 能力。RemoteCompactionSupport 是 provider 能力枚举。
图 6.2：压缩按功能开关 + provider 能力分派到三条路径。

6.3TokenBudget 压缩：开新窗口

最优雅的路径是 TokenBudget 压缩——它不调用模型生成摘要，而是直接装一个全新的 context window：

codex-rs/core/src/compact_token_budget.rs:18 — token 预算压缩
rust/// 运行 token 预算手动压缩，走正常压缩生命周期。
/// ///
/// token 预算压缩跳过模型/服务端摘要，改为安装一个全新的 context window。
/// 它仍被建模为压缩，这样 compact hooks 和 ContextCompaction turn item
/// 能观察到与本地或远程压缩相同的生命周期。
pub(crate) async fn run_manual_compact_task(sess, turn_context) -> CodexResult<()> {
    // 仍发 TurnStarted 事件，保持生命周期一致
    sess.send_event(&turn_context, EventMsg::TurnStarted(...)).await;
    let step_context = sess.capture_step_context(...).await?;
    let world_state = sess.build_world_state_for_step(&step_context).await?;
    run_compact_task_inner(&sess, &step_context, world_state, CompactionTrigger::Manual).await
}

// 自动触发版本（同样的内核，trigger = Auto）
pub(crate) async fn run_inline_auto_compact_task(sess, step_context, injection) -> CodexResult<()>;
读懂这段： 精妙之处在于统一生命周期：即便 TokenBudget 压缩不做摘要，它仍发 TurnStarted、仍走 run_compact_task_inner、仍产生 ContextCompaction turn item、仍触发 compact hooks。这样无论走哪条路径，下游（遥测、hook、事件流）看到的压缩事件是一致的。CompactionTrigger::Manual / Auto 区分手动触发（用户调 /compact）和自动触发（预算耗尽）。

6.4压缩后的历史长什么样

压缩发生后，旧历史被一条 compaction summary 替代。它作为一个特殊的 ResponseItem 注入，类型是 ContextCompacted（见第 4 章 rollout）。对应的 context fragment 是 CompactionSummary：

codex-rs/core/src/context/compaction_summary.rs — 压缩摘要 fragment
rust// 压缩后，旧的历史被一条摘要替代，作为 context fragment 注入。
pub(crate) use compaction_summary::CompactionSummary;
图 6.4：压缩把旧历史折叠成一条摘要，尾部保留以维持近期上下文。

压缩后 ContextManager 的 history_version 递增（见第 5 章），reference_context_item 重置——下一轮做全量上下文重注入。事件 EventMsg::ContextCompacted 通知前端。

6.5采样中超窗：ContextWindowExceeded 恢复

采样前检查不能保证万无一失——模型可能在采样中途产出超长内容导致超窗。第 3 章看到 run_sampling_request 的 loop 里专门处理这个：

codex-rs/core/src/session/turn.rs:1406 — 采样中超窗的处理
rustmatch try_run_sampling_request(...).await {
    Ok(output) => return Ok((output, ...)),
    Err(err) => match err.details() {
        CodexErrorDetails::ContextWindowExceeded => {
            sess.set_total_tokens_full(&turn_context).await;  // 标记满
            return Err(err);   // 上抛，触发压缩后重试
        }
        CodexErrorDetails::UsageLimitReached(e) => { ... return Err(err); }
        _ => err,
    },
}
读懂这段： ContextWindowExceeded 不在 loop 里重试，而是上抛给上层。但上抛后并非「压缩完重新进入采样」——它走通用错误分支，发出 turn 错误事件并 break 结束当前 turn（让用户继续）。压缩的真正防线在采样之前（run_pre_sampling_compact，见 6.1）与采样成功之后（若 token 触顶 should_roll_over，在 mid-turn 跑 run_auto_compact）。也就是说，压缩主要跑在成功路径上预防超窗，而非作为超窗错误的兜底重试。set_total_tokens_full 标记窗口已满，让下一轮 pre-sampling 检查能据此触发压缩。

6.6压缩的状态机与触发器

触发器 (CompactionTrigger)含义来源
Manual用户手动触发（如 /compact）run_manual_compact_task
Auto预算耗尽自动触发run_inline_auto_compact_task
原因 (CompactionReason)阶段 (CompactionPhase)说明

6.7小结与对自研的启示

要点 Codex 的压缩有三个值得抄的设计：① 采样前预检 + 采样中兜底，双保险防超窗；② 多路径统一生命周期——无论本地摘要、远程摘要还是直接开新窗口，下游看到的事件/hook 一致；③ 压缩即重置 reference——压缩后下一轮全量重注入上下文，保证一致性。
自研 checklist 最小压缩：当 token 数超过阈值（如窗口的 80%），取旧历史的最近 N 轮之外的部分，调一次模型生成「之前发生了什么」的摘要，替换掉旧部分，保留尾部 N 轮。先做本地摘要这一条路径，跑通后再加「直接开新窗口」的快路径。别忘了递增一个 history_version，让消费者知道历史变了。
