★ 上下文构建：模型每一轮到底看到什么

Codex 不是简单地把会话历史拼成字符串发给模型——它把上下文拆成可组合的「片段（Fragment）」，按角色（developer/user/system）和时机注入，并在每轮 turn 重新组装。本章拆开 Fragment 体系、AGENTS.md 注入、ContextManager 与 build_prompt 的完整流水线。
核心洞见 上下文不是历史，而是「历史 + 注入指令 + 工具结果 + 状态」的函数 → 每轮采样前，Codex 用 build_prompt 把会话历史、base instructions、工具规格、输出 schema 组装成一个 Prompt，喂给模型。注入的指令来自一组可组合的 Fragment。

5.1一个 Prompt 由什么组成

第 3 章看到 run_sampling_request 每轮调用 build_prompt。来看看它到底装了什么：

codex-rs/core/src/session/turn.rs:1509 — build_prompt
rustpub(crate) fn build_prompt(
    input: Vec<ResponseItem>,              // 会话历史（消息/工具调用/结果）
    step_context: &StepContext,
    base_instructions: BaseInstructions,     // 基础系统指令
) -> Prompt {
    let turn_context = &step_context.turn;
    Prompt {
        input,                                        // ① 会话历史
        tools: step_context.tool_router.model_visible_specs(), // ② 工具规格
        parallel_tool_calls: true,                    // ③ 允许并行工具
        base_instructions,                            // ④ 基础指令
        output_schema: turn_context.final_output_json_schema.clone(), // ⑤ 输出 schema
        output_schema_strict: !is_basic_session_source(...),
        cyber_access_program: turn_context.cyber_access_program, // ⑥ cyber 访问程序（ChatGPT 认证）
    }
}
读懂这段： 一个 Prompt 有六部分：① 会话历史 input（ResponseItem 列表，含已注入的 fragment）；② 工具规格（告诉模型有哪些工具可用）；③ 并行工具开关（Codex 默认允许模型一次请求多个工具）；④ base_instructions（系统级指令）；⑤ 输出 schema（结构化输出约束）；⑥ cyber_access_program（ChatGPT 认证下的 cyber 治理选项）。注意 input 不只是用户消息——它已经包含了被注入的 developer/user fragment（见 5.3）。

5.2Fragment：可组合的上下文单元

Codex 把要注入的上下文抽象成 ContextualUserFragment——一个 trait，每种指令/提醒都是一个实现。来看 context/mod.rs 里的 fragment 清单：

codex-rs/core/src/context/mod.rs — Fragment 模块清单（节选）
rustmod base_instructions;            // 基础指令（核心系统提示）
mod developer_instructions;        // developer 角色指令
mod user_instructions;             // user 角色指令
mod apps_instructions;             // 已启用 app 的指令
mod permissions_instructions;      // 权限/审批规则说明
mod current_time_reminder;         // 当前时间提醒
mod compaction_summary;            // 压缩摘要（替代旧历史）
mod model_switch_instructions;     // 模型切换说明
mod environment_context;           // 环境信息
mod hook_additional_context;       // hook 注入的额外上下文
mod token_budget_context;          // token 预算提醒
mod user_shell_command;            // 用户 shell 信息
mod multi_agent_role_instructions; // 多 Agent 角色指令
mod guardian_policy;               // 守护策略
// ... 还有 37 个其他 fragment（mod 声明共 51 个）
读懂这段： 每一种「要告诉模型的东西」都是一个独立 fragment 模块。这种拆分让上下文可组合、可按需启用——例如多 Agent 模式才注入 multi_agent_role_instructions，压缩后才注入 compaction_summary。这是 Codex 上下文工程的核心设计：不是一整块写死的 system prompt，而是可独立启用的片段。

5.3Fragment 的契约：ContextualUserFragment trait

每个 fragment 实现同一个 trait，决定它以什么角色、什么内容注入：

codex-rs/context-fragments/src/fragment.rs:64 — Fragment trait（节选）
rust/// 作为消息片段注入的上下文载荷。
/// /// 实现者拥有 response role，并提供确切的片段正文。
pub trait ContextualUserFragment {
    fn content_kind(&self) -> ContentItemKind;   // 分类标识
    fn role(&self) -> &'static str;            // "developer" | "user" | "system"
    fn body(&self) -> String;                   // 正文
    fn markers(&self) -> (&'static str, &'static str); // 起止标记（识别已注入片段）
    fn requires_separate_message(&self) -> bool { false }
}
codex-rs/core/src/context/developer_instructions.rs:5 — 一个具体 fragment
rustpub(crate) struct DeveloperInstructions { instructions: String }

impl ContextualUserFragment for DeveloperInstructions {
    fn content_kind(&self) -> ContentItemKind {
        ContentItemKind("generic.developer_instructions".to_string())
    }
    fn role(&self) -> &'static str { "developer" }   // ← 以 developer 角色注入
    fn body(&self) -> String { self.instructions.clone() }
    fn markers(&self) -> (&'static str, &'static str) { ("", "") }
}
读懂这段： role() 决定片段以什么身份出现——DeveloperInstructions 用 "developer"，UserInstructions 用 "user"。markers 是巧思：注入的片段带起止标记，之后可以识别并 diff——这支撑了「只在变化时重新注入」的增量机制（见 5.5）。content_kind 给片段分类，方便统计与过滤。
角色 OpenAI Responses API 区分 system / developer / user 三种角色。Codex 把不可协商的规则放 developer，把项目/用户指令也倾向 developer 或 user。base_instructions 是最高优先级的系统指令。

5.4AGENTS.md：项目级指令注入

Codex 的「项目指令」机制是 AGENTS.md——放在项目根目录（或子目录）的 Markdown 文件，告诉 Agent 这个项目该怎么干活。它由 AgentsMdManager 发现并加载：

codex-rs/core/src/agents_md_manager.rs:22 — AgentsMdManager
rust/// 拥有指令来源、刷新串行化与已应用的快照。
/// 刷新互相串行；调用 provider 时不持有状态锁。
pub(crate) struct AgentsMdManager {
    refresh_lock: Semaphore,                       // 刷新串行化，避免并发读盘
    state: Mutex<AgentsMdState>,
}

/// 根会话保留 provider；子 Agent 只继承已应用的快照。
pub(crate) struct SessionInstructions {
    user: Option<Instructions>,                    // 全局/用户指令（可由 provider 在请求边界刷新）
    thread: Option<Instructions>,                  // 线程级指令（ThreadInstructionsProvider 提供）
    user_provider: Option<Arc<dyn UserInstructionsProvider>>,
    thread_provider: Option<Arc<dyn ThreadInstructionsProvider>>,
}

struct AgentsMdCache {
    selections: Option<Vec<TurnEnvironmentSelection>>,
    active_project_trust_level: Option<TrustLevel>,  // 信任级别影响审批
    loaded: Option<Arc<LoadedAgentsMd>>,             // 加载到的 AGENTS.md 内容
}

// 每个 turn（模型请求边界）刷新：provider 重读指令，必要时重新发现仓库 AGENTS.md
pub(crate) async fn refresh(&self, config, environments)
    -> (CodexResult<Option<Arc<LoadedAgentsMd>>>, Vec<String>);
读懂这段： AgentsMdManager 在每个 turn 前 refresh——全局/线程指令通过 provider 在请求边界重读（改了全局 AGENTS.md 不用重启会话），环境或信任级别变了才重新扫描仓库目录。刷新用 Semaphore 串行化，读结果时不持锁。关键：它还解析 TrustLevel（Trusted / Untrusted）。这直接影响安全：untrusted 项目的命令默认要审批（见第 8 章）。AGENTS.md 不只是指令，还是信任边界——上下文加载和安全策略在这里交汇。另外线程级指令超过 1 万 estimated token 会被整条拒绝（不截断）。
实践 在项目根放一个 AGENTS.md，写上构建命令、代码规范、禁忌操作。Codex 每个 turn 都会读到它。仓库自己的 AGENTS.md 就是个范例——它告诉 Codex 该用 just 跑测试、crate 名带 codex- 前缀等。

5.5ContextManager：历史的管家与增量注入

ContextManager 是会话历史的管家——它不只存历史，还负责「该注入什么、哪些变了」的增量计算：

codex-rs/core/src/context_manager/history.rs — ContextManager 字段（节选）
rust/// 会话历史的转录
pub(crate) struct ContextManager {
    // 最老的 item 在前面。快照共享 vector 直到需要修改，避免深拷贝。
    items: Arc<Vec<ResponseItemEnvelope>>,
    // 历史被重写（压缩或回滚）时递增。
    history_version: u64,
    token_info: Option<TokenUsageInfo>,
    /// 用于 diffing 和生成模型可见设置更新 item 的参考上下文快照。
    /// 这是下一个常规模型 turn 的基线。
    reference_context_item: Option<TurnContextItem>,
    /// 最近追加到模型可见历史的世界状态。
    world_state_baseline: Option<WorldStateSnapshot>,
}
读懂这段： 三个关键字段揭示设计：① items: Arc<Vec> 用 Arc 共享——只读消费者（如克隆历史构建 prompt）零拷贝，只有修改时才复制（COW）。② history_version 是版本号，压缩/回滚时递增，让消费者能检测历史是否变了。③ reference_context_item 是增量注入的核心：它记录「上一次注入给模型的上下文状态」，下一轮 diff 之——只在变化时才重新注入完整上下文，没变就跳过，省 token、保 prompt cache。
关键 reference_context_item 为 None 时，下一轮会做全量重注入（没有基线可 diff）。回滚可能清空它——这正是「回滚后第一个 turn 上下文会重建」的原因。这种增量 diff 机制让 Codex 的上下文既完整又不浪费。

5.6工具结果截断与图像处理

上下文里最占 token 的是工具输出（尤其 shell 命令的长输出）和图像。ContextManager 也管这些的截断：

codex-rs/core/src/context_manager/mod.rs — 截断与估算工具
rustpub(crate) use history::estimate_image_bytes;          // 估算图像字节
pub(crate) use history::estimate_item_token_count;     // 估算 item 的 token 数
// 截断实现在 codex_utils_output_truncation crate：
//   truncate_function_output_payload / truncate_text / TruncationPolicy
// context_manager/history.rs 在记录工具结果时内联调用截断：
//   预算优先用 metadata.history_truncation_token_limit（逐工具上限），
//   否则回退到 序列化预算 + 序列化余量（with_serialization_allowance）
读懂这段： 工具输出不会无脑全塞进 prompt——记录历史时就地按策略截断（保留头尾、中间省略），避免一个 ls -R 就把上下文撑爆。截断预算支持逐工具覆盖：MCP 服务器可在配置里给单个工具设 output_token_limit，随 CodexHarnessMetadata.history_truncation_token_limit（serde 名 fallback_token_limit_override）一路带进历史，并且跨 resume/fork 保留。图像也估算 token 占用。这些都是「上下文预算管理」的一部分，与第 6 章的压缩配合。

5.7小结：上下文工程的要点

一张图记牢 每 turn 开始：① AgentsMdManager::refresh 刷新指令快照（环境/信任级别变了才重新发现项目指令）；② capture_step_context 快照模型可见状态；③ 按 diff 决定注入哪些 Fragment（developer/user 角色）；④ Fragment 与历史合并进 input；⑤ build_prompt 装上 tools / base_instructions / output_schema；⑥ 喂给 LLM。
对自研的启示 别把 system prompt 写成一大段。把指令拆成可独立启用的片段（项目指令、工具规则、时间提醒、状态摘要），每轮按需组装。实现一个 reference 基线做增量 diff——没变的指令不重复注入，这是省 token 和保 prompt cache 的关键。最小 MVP：一个 system 消息 + 会话历史，先跑通，再逐步拆 fragment。
