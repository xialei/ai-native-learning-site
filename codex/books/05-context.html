上下文构建：模型每一轮到底看到什么

每一轮都要把会话历史重新喂给模型——那模型每轮看到的，就是一条不增不减的历史吗？AGENTS.md 里的项目指令是什么时候被塞进去的，塞在历史的哪个位置？工具输出动辄几万 token，全量进历史很快就把窗口撑爆，Codex 怎么处理？这些拼装动作每轮重复做，由谁负责、在哪段代码里？

Codex 的答案是把上下文拆成可组合的「片段（Fragment）」，按角色（developer/user/system）和时机注入，每轮 turn 重新组装。本章拆开 Fragment 体系、AGENTS.md 注入、ContextManager 与 build_prompt 的完整流水线。

答案地图 先交代四问各自的答案:：① 不是——模型每轮看到的是历史加上按需注入的指令片段，上下文是「历史 + 注入」的函数（5.1 / 5.2）；② AGENTS.md 在每个 turn 开始时刷新快照、按需作为 Fragment 注入，与项目/用户指令一样走 developer/user 角色（5.4 / 5.3）；③ 工具输出走截断、图像走降级压缩，各有一条处理路径（5.6）；④ 拼装由 build_prompt 每轮执行，历史本身由 ContextManager 增量维护（5.5 / 5.1）。
核心洞见 上下文不是历史，而是「历史 + 注入指令 + 工具结果 + 状态」的函数 → 每轮采样前，Codex 用 build_prompt 把会话历史、base instructions、工具规格、输出 schema 组装成一个 Prompt，喂给模型。注入的指令来自一组可组合的 Fragment。

5.1一个 Prompt 由什么组成

第 3 章看到 run_sampling_request 每轮调用 build_prompt。来看看它到底装了什么：

codex-rs/core/src/session/turn.rs:1666 — build_prompt
rustpub(crate) fn build_prompt(
    input: Vec<ResponseItem>,              // 会话历史（消息/工具调用/结果）
    step_context: &StepContext,
    base_instructions: BaseInstructions,     // 基础系统指令
    incremental_tools: bool,                 // 增量工具模式（world state 决定）
) -> Prompt {
    let turn_context = &step_context.turn;
    Prompt {
        input,                                        // ① 会话历史
        tools: if incremental_tools { Arc::default() } else { step_context.tool_router.model_visible_specs() }, // ② 工具规格（增量工具模式下给默认空集）
        parallel_tool_calls: true,                    // ③ 允许并行工具
        base_instructions: if incremental_tools { BaseInstructions::default() } else { base_instructions }, // ④ 基础指令（增量工具模式下置空）
        output_schema: turn_context.final_output_json_schema.clone(), // ⑤ 输出 schema
        output_schema_strict: !is_basic_session_source(...), // ⑥ 严格 schema 校验开关
        cyber_access_program: turn_context.cyber_access_program, // ⑦ cyber 访问程序（ChatGPT 认证）
    }
}
一个 Prompt 七块料： 一个 Prompt 有七部分：① 会话历史 input（ResponseItem 列表，含已注入的 fragment）；② 工具规格（告诉模型有哪些工具可用）；③ 并行工具开关（Codex 默认允许模型一次请求多个工具）；④ base_instructions（系统级指令）；⑤ 输出 schema（结构化输出约束）；⑥ output_schema_strict（Responses API 是否严格校验 output_schema——普通会话开启，guardian/basic 会话关闭）；⑦ cyber_access_program（ChatGPT 认证下的 cyber 治理选项）。②④ 两块都吃 incremental_tools 开关（由 world state 决定，见第 4 章）——增量模式下工具与基础指令都置空，靠 world state 快照另行投递。注意 input 不只是用户消息——它已经包含了被注入的 developer/user fragment（见 5.3）。

这七块料里 base_instructions 的投递方式值得单独说一句：#51156 之后，base instructions 不再走 ResponsesApiRequest.instructions 顶层字段（该字段已从 wire 上移除），而是在发送前把指令文本包装成一条 developer 角色的 message，用 Uuid::new_v5 从指令文本本身算出一个稳定 id，splice(0..0, prefix) 插到 input 最前面（client.rs:996-1005）。稳定 id 的好处是缓存友好——同样的指令每次算出同样的 id，prompt 前缀不变。

5.2Fragment：可组合的上下文单元

Codex 把要注入的上下文抽象成 ContextualUserFragment——一个 trait，每种指令/提醒都是一个实现。来看 context/mod.rs 里的 fragment 清单：

codex-rs/core/src/context/mod.rs — Fragment 模块清单（节选）
rustmod base_instructions;            // 基础指令（核心系统提示）
mod developer_instructions;        // developer 角色指令
mod user_instructions;             // user 角色指令
mod apps_instructions;             // 已启用 app 的指令
mod current_time_reminder;         // 当前时间提醒
mod compaction_summary;            // 压缩摘要（替代旧历史）
mod model_switch_instructions;     // 模型切换说明
mod environment_context;           // 环境信息
mod hook_additional_context;       // hook 注入的额外上下文
mod token_budget_context;          // token 预算提醒
mod user_shell_command;            // 用户 shell 信息
mod guardian_policy;               // 守护策略
// permissions_instructions / multi_agent_role_instructions 已上移 codex-prompts crate（经 re-export 提供）
// ... 还有 42 个其他 fragment（mod 声明共 54 个）
每块料独立插拔： 每一种「要告诉模型的东西」都是一个独立 fragment 模块。这种拆分让上下文可组合、可按需启用——例如多 Agent 模式才注入 MultiAgentRoleInstructions（现由 codex-prompts crate 统一提供），压缩后才注入 compaction_summary。这是 Codex 上下文工程的核心设计：不是一整块写死的 system prompt，而是可独立启用的片段。

5.3Fragment 的契约：ContextualUserFragment trait

每个 fragment 实现同一个 trait，决定它以什么角色、什么内容注入：

codex-rs/context-fragments/src/fragment.rs:56 — Fragment trait（节选）
rust/// 作为消息片段注入的上下文载荷。
/// /// 实现者拥有 response role，并提供确切的片段正文。
pub trait ContextualUserFragment {
    fn content_metadata(&self) -> ContentItemMetadata; // 出处元数据，默认 harness()
    fn content_kind(&self) -> ContentItemKind;   // 分类标识
    fn role(&self) -> &'static str;            // "developer" | "user" | "system"
    fn body(&self) -> ContentItem;              // 正文（不限于纯文本）
    fn markers(&self) -> (&'static str, &'static str); // 起止标记（识别已注入片段）
    fn type_markers() -> (&'static str, &'static str); // 按类型打的标记
    fn matches_text(text: &str) -> bool;  // 判断正文是否含某文本
}
codex-rs/core/src/context/developer_instructions.rs:20 — 一个具体 fragment
rustpub(crate) struct DeveloperInstructions { instructions: String }

impl ContextualUserFragment for DeveloperInstructions {
    fn content_metadata(&self) -> ContentItemMetadata {
        ContentItemMetadata::developer_instructions(/*from_additional_requirements*/ false)
    }
    fn content_kind(&self) -> ContentItemKind {
        ContentItemKind("generic.developer_instructions".to_string())
    }
    fn role(&self) -> &'static str { "developer" }   // ← 以 developer 角色注入
    fn markers(&self) -> (&'static str, &'static str) { Self::type_markers() }
    fn type_markers() -> (&'static str, &'static str) { ("", "") }
    fn body(&self) -> ContentItem { input_text(self.instructions.clone()) }
}
身份由 role() 定： role() 决定片段以什么身份出现——DeveloperInstructions 用 "developer"，UserInstructions 用 "user"。markers 是巧思：注入的片段带起止标记，之后可以识别并 diff——这支撑了「只在变化时重新注入」的增量机制（见 5.5）。content_kind 给片段分类，方便统计与过滤。#53831 之后每个 fragment 还自带 content_metadata()——声明这段内容是谁产的（ContentItemProvenance：harness、developer instructions、skills、hooks、工具……），出处由生产方在注入时给定而非事后从渲染文本反推，正文也从裸 String 升级成 ContentItem（多数片段仍是 input_text，但已能承载非文本内容）。
角色 OpenAI Responses API 区分 system / developer / user 三种角色。Codex 把不可协商的规则放 developer，把项目/用户指令也倾向 developer 或 user。base_instructions 是最高优先级的系统指令。

5.4AGENTS.md：项目级指令注入

Codex 的「项目指令」机制是 AGENTS.md——放在项目根目录（或子目录）的 Markdown 文件，告诉 Agent 这个项目该怎么干活。它由 AgentsMdManager 发现并加载：

codex-rs/core/src/agents_md_manager.rs:22 — AgentsMdManager
rust/// 拥有指令来源、刷新串行化与已应用的快照。
/// 刷新互相串行；调用 provider 时不持有状态锁。
pub(crate) struct AgentsMdManager {
    refresh_lock: Semaphore,                       // 刷新串行化，避免并发读盘
    state: Mutex<AgentsMdState>,
}

/// 子代理继承已应用快照；声明共享的 thread provider 也会一并继承。
pub(crate) struct SessionInstructions {
    user: Option<Instructions>,                    // 全局/用户指令（可由 provider 在请求边界刷新）
    thread: Option<Instructions>,                  // 线程级指令（ThreadInstructionsProvider 提供）
    user_provider: Option<Arc<dyn UserInstructionsProvider>>,
    thread_provider: Option<Arc<dyn ThreadInstructionsProvider>>,
}

struct AgentsMdCache {
    selections: Option<Vec<TurnEnvironmentSelection>>,
    active_project_trust_level: Option<TrustLevel>,  // 信任级别影响审批
    loaded: Option<Arc<LoadedAgentsMd>>,             // 加载到的 AGENTS.md 内容
}

// 每个 turn（模型请求边界）刷新：provider 重读指令，必要时重新发现仓库 AGENTS.md
pub(crate) async fn refresh(&self, config, environments)
    -> (CodexResult<Option<Arc<LoadedAgentsMd>>>, Vec<String>);
改 AGENTS.md 不用重启： AgentsMdManager 在每个 turn 前 refresh——全局/线程指令通过 provider 在请求边界重读（改了全局 AGENTS.md 不用重启会话），环境或信任级别变了才重新扫描仓库目录。刷新用 Semaphore 串行化，读结果时不持锁。关键：它还解析 TrustLevel（Trusted / Untrusted）。这直接影响安全：untrusted 项目的命令默认要审批（见第 8 章）。AGENTS.md 不只是指令，还是信任边界——上下文加载和安全策略在这里交汇。另外线程级指令超过 1 万 estimated token 会被整条拒绝（不截断）。
实践 在项目根放一个 AGENTS.md，写上构建命令、代码规范、禁忌操作。Codex 每个 turn 都会读到它。（这个仓库曾经也有自己的 AGENTS.md——告诉 Codex 该用 just 跑测试、crate 名带 codex- 前缀——后来 #49713 把它和仓库本地的 Codex 配置一起删了；机制还在，范例没了。）

5.5ContextManager：历史的管家与增量注入

ContextManager 是会话历史的管家——它不只存历史，还负责「该注入什么、哪些变了」的增量计算：

codex-rs/core/src/context_manager/history.rs:93 — ContextManager 字段（节选）
rust/// 会话历史的转录
pub(crate) struct ContextManager {
    // 最老的 item 在前面。快照共享 vector 直到需要修改，避免深拷贝。
    items: Arc<Vec<ResponseItemEnvelope>>,
    // 历史被重写（压缩或回滚）时递增。
    history_version: u64,
    // 节选：中间还有 review_history / retained_context / reset_version 等字段
    token_info: Option<TokenUsageInfo>,
    /// 用于 diffing 和生成模型可见设置更新 item 的参考上下文快照。
    /// 这是下一个常规模型 turn 的基线。
    reference_context_item: Option<TurnContextItem>,
    /// 最近追加到模型可见历史的世界状态。
    world_state_baseline: Option<WorldStateSnapshot>,
}
三个字段各有算计： 三个关键字段揭示设计：① items: Arc<Vec> 用 Arc 共享——只读消费者（如克隆历史构建 prompt）零拷贝，只有修改时才复制（COW）。② history_version 是版本号，压缩/回滚时递增，让消费者能检测历史是否变了。③ reference_context_item 是增量注入的核心：它记录「上一次注入给模型的上下文状态」，下一轮 diff 之——只在变化时才重新注入完整上下文，没变就跳过，省 token、保 prompt cache。
关键 reference_context_item 为 None 时，下一轮会做全量重注入（没有基线可 diff）。回滚可能清空它——这正是「回滚后第一个 turn 上下文会重建」的原因。这种增量 diff 机制让 Codex 的上下文既完整又不浪费。

5.6工具结果截断与图像处理

上下文里最占 token 的是工具输出（尤其 shell 命令的长输出）和图像。ContextManager 也管这些的截断：

codex-rs/core/src/context_manager/mod.rs — 截断与估算工具
rustpub(crate) use history::estimate_image_reference_bytes; // 估算图像字节（内联 + 文件 ID 引用）
pub(crate) use history::estimate_item_token_count;     // 估算 item 的 token 数
// 截断实现在 codex_utils_output_truncation crate：
//   truncate_function_output_payload / truncate_text / TruncationPolicy
// context_manager/history.rs 在记录工具结果时内联调用截断：
//   预算优先用 metadata.history_truncation_token_limit（逐工具上限），
//   否则回退到 序列化预算 + 序列化余量（with_serialization_allowance）
先截断再进历史： 工具输出不会无脑全塞进 prompt——记录历史时就地按策略截断（保留头尾、中间省略），避免一个 ls -R 就把上下文撑爆。截断预算支持逐工具覆盖：MCP 服务器可在配置里给单个工具设 output_token_limit，随 CodexHarnessMetadata.history_truncation_token_limit（serde 名 fallback_token_limit_override）一路带进历史，并且跨 resume/fork 保留。图像在进历史前由 image_preparation.rs 统一准备：估算 token 占用，超限或处理失败的不硬塞——以占位文本替代（如「image content omitted because it exceeded the supported size limit」）。这些是「上下文预算管理」的一部分，与第 6 章的压缩配合。此外还有一组反方向的开销：Codex 把近期执行过的工具调用以压缩元数据的形式重新附着进每次采样请求（executed_tool_calls.attach_to_prompt，最多挂 256 条待定调用、直接元数据留 1MB——早期版本的 8KB/32KB 单参数与总量预算已删除）——模型无需靠复述历史就能「记得」刚做过什么；整条消息还有一道 15MB 的软预算（bound_executed_tool_calls_for_message，超了就按「先削结果元数据、再削来源与参数」的顺序 sheds），压缩提示词则只附加 Code Mode 的调用。

5.7小结：上下文工程的要点

一张图记牢 每 turn 开始：① AgentsMdManager::refresh 刷新指令快照（环境/信任级别变了才重新发现项目指令）；② capture_step_context 快照模型可见状态；③ 按 diff 决定注入哪些 Fragment（developer/user 角色）；④ Fragment 与历史合并进 input；⑤ build_prompt 装上 tools / base_instructions / output_schema；⑥ 喂给 LLM。
对自研的启示 别把 system prompt 写成一大段。把指令拆成可独立启用的片段（项目指令、工具规则、时间提醒、状态摘要），每轮按需组装。实现一个 reference 基线做增量 diff——没变的指令不重复注入，这是省 token 和保 prompt cache 的关键。最小 MVP：一个 system 消息 + 会话历史，先跑通，再逐步拆 fragment。

本章小结

上下文这一章的主张可以用一句话说：模型看到的输入是现场组装出来的，不是历史的原样回放——每 turn 按 diff 决定注入什么，这是第 4 章「日志即事实」之后的另一半：日志是全集，上下文是每轮从全集里选出的视图。六步流水线与 fragment 拆分的原则收拢在 5.7 的两个 callout。
