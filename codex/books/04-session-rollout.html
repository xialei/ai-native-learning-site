会话与 Rollout：Codex 怎么记住、怎么重生

一个 Agent 跑了几十轮，中途崩溃了——重开后怎么接着干？答案在两个 crate 里：core/src/session/ 维护内存中的会话状态，rollout + history 把会话以 JSONL 追加式持久化、并能回放重建。本章拆开这套「会话即日志」的设计。

4.1会话在内存里长什么样：Session

Session 是一个会话线程在内存中的拥有者。它持有会话历史（一串 ResponseItem）、世界状态（world state）、以及各种服务句柄。第 3 章的 run_turn 就是它的方法驱动的。

codex-rs/core/src/session/session.rs — Session 的角色（关键方法节选）
rust// Session 持有会话的全部运行时状态，对内被 run_turn 驱动，对外通过 Event 通信。
// 关键能力（方法名示意）：
sess.clone_history().await            // 克隆当前会话历史 → 用于构建 prompt
sess.send_event(&turn_context, msg)   // 发出一个 EventMsg 给前端
sess.capture_step_context(...)        // 快照模型可见状态（step context）
sess.record_context_updates(...)      // 记录上下文更新并设参考 item
sess.build_world_state_for_step(...)  // 为当前 step 构建 world state
sess.get_base_instructions().await    // 取基础指令
读懂这段： Session 不直接持久化——它只管「这一轮内存里会话长什么样」。持久化交给 RolloutRecorder（见 4.3）。这种分离让内存模型与磁盘格式解耦：你可以换持久化后端而不动内核逻辑。注意 clone_history——每次采样前克隆历史，保证流式产出期间历史的一致性。

4.2会话条目的信封：ResponseItemEnvelope

持久化时，每个 ResponseItem 被包进一个「信封」，附带 harness 自己的元数据：

codex-rs/history/src/lib.rs:39 — ResponseItemEnvelope
rust/// 带 history-only 元数据的模型历史条目。
span/// 持久化保持 response item 完整，元数据单独存储。
#[derive(Debug, Clone, PartialEq)]
pub struct ResponseItemEnvelope {
    pub item: ResponseItem,
    pub metadata: Option<CodexHarnessMetadata>,
}

/// harness 拥有、随 response item 一起持久化的元数据
pub struct CodexHarnessMetadata {
    pub client_authored: bool,   // 是否由 app-server 客户端提供的 developer 消息
}
读懂这段： Envelope 模式（信封）是持久化的常见手法：保持原始 ResponseItem 不被污染，把 harness 私有的元数据挂在旁边。这样回放时既能拿到纯净的会话内容，又能读到附带的上下文。注意它实现了 Deref<Target=ResponseItem>——大多数地方可以当 ResponseItem 直接用。

4.3Rollout：追加式 JSONL 日志

「rollout」是 Codex 对会话持久化文件的称呼。它的格式是 JSONL（每行一个 JSON），追加写入——每发生一件值得记录的事，就 append 一行。这等价于一个事件溯源日志（event sourcing）。

codex-rs/history/src/lib.rs:206 — 一行 rollout 的结构
rust#[derive(Serialize, Deserialize, Clone, JsonSchema)]
pub struct RolloutLine {
    pub timestamp: String,
    pub ordinal: Option<u64>,     // 序号，用于排序/定位
    #[serde(flatten)]
    pub item: RolloutItem,        // 真正的内容（展开进同一层 JSON）
}
codex-rs/history/src/rollout_payload.rs:23 — RolloutItem 能记什么
rust#[serde(tag = "type", rename_all = "snake_case")]
enum RolloutItemWire<'a> {
    SessionMeta { payload },                 // 会话元信息（id、cwd、forked_from...）
    ResponseItem { payload, metadata },      // 一条会话条目（消息/工具调用/结果）
    InterAgentCommunication { payload },     // 多 Agent 间通信
    Compacted { payload },                   // 压缩事件（旧的被摘要替代）
    TurnContext { payload },                 // turn 上下文快照
    WorldState { payload },                  // 世界状态变更
    SecurityRiskScore { payload },           // 安全风险评分
    EventMsg { payload },                    // 原始事件（用于完整回放）
    RealtimeItem { payload },                // 实时对话条目
}
读懂这段： rollout 不只记 ResponseItem，还记 SessionMeta（会话 id、工作目录、从谁 fork 的）、WorldState（世界状态变更）、Compacted（压缩发生）、甚至原始 EventMsg。这使得 rollout 既是会话历史，也是完整的运行轨迹——回放时能重建到任意时刻的完整状态。#[serde(flatten)] 让 item 展开进 RolloutLine 同一层，配合 tag = "type" 每行自描述。
工具 注释里写了：Rollouts are recorded as JSONL and can be inspected with tools such as...——你可以直接 cat 或 jq 看 rollout 文件，每行就是一个事件。文件存在 ~/.codex/sessions/ 下。

4.4记录器与状态库

实际写入磁盘的是 RolloutRecorder，而会话索引/元数据存在一个 SQLite 状态库里：

pub struct RolloutRecorder { ... }

// 关键 API：
RolloutRecorderParams::new(...)                 // 新建会话参数

RolloutRecorderParams::resume(path: PathBuf)    // ★ 恢复已有 rollout（构造 Resume 参数）
RolloutRecorder::new(config, params)            // 用参数构造 recorder
recorder.list_threads(...)                      // 列出所有会话
codex-rs/rollout/src/state_db.rs — SQLite 状态库（函数节选）
rustpub async fn init(config) -> Option<StateDbHandle>           // 初始化状态库
pub async fn list_thread_ids_db(...) -> ...                   // 列出会话 id
pub async fn list_threads_db(...) -> ...                      // 列出会话（带元数据）
pub async fn find_rollout_path_by_id(...)                     // 按 id 找 rollout 文件路径
pub async fn apply_rollout_items(...)                        // 把 rollout 条目写进索引

读懂这段： 双层存储——JSONL 文件是事实来源（append-only，不可变），SQLite 是索引/缓存（快速列出会话、按 id 查路径）。reconcile_rollout 和 read_repair_rollout_path 负责「对账」：当索引与 JSONL 不一致时，以 JSONL 为准修复索引。这是事件溯源 + 物化视图的经典组合。

4.5回放与重建：InitialHistory

重启后恢复会话，就是把 rollout 文件回放成内存历史。这由 InitialHistory 表达：

codex-rs/history/src/lib.rs:222 — 会话的初始历史来源
rustpub enum InitialHistory {
    New,                              // 全新会话
    Cleared,                          // 已清空
    Resumed(ResumedHistory),          // ★ 从 rollout 恢复
    Forked(Vec<RolloutItem>),         // 从某点 fork 出新分支
}

pub struct ResumedHistory {
    pub conversation_id: ThreadId,
    pub history: Arc<Vec<RolloutItem>>,   // 回放出的历史条目
    pub rollout_path: Option<PathBuf>,     // rollout 文件路径（继续追加）
}
读懂这段： 恢复会话就是 RolloutRecorderParams::resume(path) 构造参数 → RolloutRecorder::new(config, params) → RolloutRecorder::get_rollout_history(path) 把 JSONL 逐行反序列化成 Vec<RolloutItem> → 包成 ResumedHistory → 喂给 Session。关键在于：恢复后 rollout 文件继续追加（rollout_path 还在），所以恢复的会话和原会话是同一个文件。Forked 变体支持「从某历史点分叉」——类似 git 的分支，forked_from_id 记录了来源。

4.6World State：会话追踪的真实世界

除了消息历史，Session 还追踪一个 world state（世界状态）——模型在当前会话里「造成的外部影响」的快照。它由 context/world_state/ 模块构建，每轮 turn 开始时刷新：

图 4.6：世界状态从历史派生，每轮注入 prompt，让模型有「记忆」。

world state 让模型不只看到对话文本，还能知道「当前的指令、权限、可用工具、环境等运行时状态」——这对编码 Agent 至关重要，保持状态一致。它由若干 WorldStateSection（ModelInstructionsState、PermissionsState、ToolsState、EnvironmentsState 等）拼成，每个 section 独立 diff，只在变化时更新。它也被持久化进 rollout（WorldState 变体）。

4.7回滚：扔掉最近几轮

会话支持回滚——扔掉最近 N 个用户 turn，回到之前的状态。这通过 Op::ThreadRollback 触发，对应事件 EventMsg::ThreadRolledBack。因为 rollout 是 append-only，回滚不是删除文件内容，而是记录一个回滚点、重建历史时截断到该点（或 fork 出新分支）。

设计 append-only + fork 的设计借鉴了 git：历史不可变，新进展是新行，想「回到过去」就从过去某点 fork。这让会话天然支持分支探索，且崩溃恢复时不会因部分写入损坏（最多丢最后半行）。

4.8小结与对自研的启示

要点 Codex 的会话持久化有三个关键决策：① 会话即日志（append-only JSONL，每行一个带 type 标签的事件）；② 事实来源 + 索引分离（JSONL 是真相，SQLite 是加速索引，带对账修复）；③ 恢复即回放（重启时把日志重放成内存历史，继续追加）。
自研 checklist 最小持久化：每产生一个消息/工具调用/结果，就 println! 一行 JSON 到 session.jsonl。重启时逐行读回成消息列表。先别管 SQLite 索引和 fork——等会话多了再加。崩溃恢复天然就有了：最后一行可能残缺，跳过即可。
