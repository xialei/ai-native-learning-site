★ Turn 循环：一个 prompt 在 Codex 里到底怎么跑

这是整个代码库最核心的执行路径。一个 turn 不是一次 LLM 调用，而是一个「采样 → 解析工具 → 执行工具 → 把结果塞回历史 → 再采样」的循环，直到模型不再请求工具为止。本章从 CodexThread 一路追到 run_turn 的 loop {}，看清流式、重试、中断、steering 分别发生在哪个环节。
核心洞见 「Agent 循环」的本质，是一个带状态的 while 循环 → 每轮把会话历史 + 上下文喂给 LLM，拿回文本或工具调用；若是工具调用，执行后把结果追加进历史，再进下一轮。Codex 把这个「工具 → 再采样」循环实现在 run_turn 的 loop {} 里（run_sampling_request 内部还有一个只管流式重试的 loop {}，二者分工不同）。

3.2run_turn：turn 的前置准备

run_turn 是 turn 的入口，它负责「采样前」的所有准备：前置压缩、捕获 step context、记录用户输入、构建技能/插件注入。真正采样在它调用的 run_sampling_request 里。

codex-rs/core/src/session/turn.rs:163 — run_turn 签名与前置压缩（节选）

    mut input: Vec<TurnInput>,

    prewarmed_client_session: Option<ModelClientSession>,

    let first_step_context = sess.capture_step_context_with_required_mcp_servers(...).await?;

    // 5. 最终进入采样循环 run_sampling_request

读懂这段： 注意三个细节。① 前置压缩（pre-sampling compact）：在构建 prompt 之前就检查 token 预算，避免还没发请求就超窗。② step context 快照：capture_step_context 把「模型这一轮该看到的状态」冻结下来，保证一个 turn 内的多次采样看到一致的世界。③ prewarmed_client_session：client session 可被预热复用，省去每轮重建连接的开销。

3.3两个 loop：run_turn 的「再采样」与 run_sampling_request 的「重试」

要厘清「Agent 循环」，必须区分两个 loop {}：run_turn 的 loop 驱动「工具 → 再采样」——每完成一轮采样，若模型请求了工具（needs_follow_up），执行完工具、把结果回填历史后再进下一轮采样；而 run_sampling_request 内部的 loop 只负责流式重试——它遇到可重试的流式错误才继续，一旦采样成功就立即返回。run_turn 的循环才是通常所说的「Agent 循环」：

codex-rs/core/src/session/turn.rs:423 — run_turn 的采样循环（节选）
rustloop {                                            // ★ Agent 循环：工具 → 再采样
    // 1. 取走队列里 pending 的 steering 输入（首轮通常为空）
    let pending_input = if can_drain_pending_input {
        sess.input_queue.get_pending_input(&sess.active_turn).await.0
    } else {
        Vec::new()
    };

    // 2. 每个 step 捕获一次 step context（首轮复用 run_turn 前面捕获的那份）
    let step_context = match next_step_context.take() { ... };

    // 3. 克隆会话历史，交给 run_sampling_request（内部构建 prompt、调 LLM、执行工具）
    let sampling_request_input = sess.clone_history().await
        .for_prompt(&step_context.settings.model_info.input_modalities);
    let sampling_request_result = run_sampling_request(
        ..., sampling_request_input, cancellation_token.child_token(),
    ).await;

    match sampling_request_result {
        Ok((output, sampling_request_input)) => {   // 第二项是本次实际送入的 history，后供 after-agent hook 使用
            let SamplingRequestResult { needs_follow_up: model_needs_follow_up, .. } = output;
            let needs_follow_up = model_needs_follow_up || has_pending_input;
            // needs_follow_up：模型本轮是否请求了工具（工具已在 run_sampling_request 内执行完）

            if !needs_follow_up {
                // 模型给出了不含工具调用的最终回答 → 结束 turn
                break;
            }
            // 采样成功后若 token 触顶，先 mid-turn 压缩再继续；
            // 有工具调用 / 待处理输入：结果已回填历史，回到 loop 顶部再采样一轮
            continue;
        }
        Err(err) => { ... // TurnAborted / 超窗 / 通用错误分支 }
    }
}
读懂这段： 每轮 loop 重新克隆历史——工具执行结果已经被追加进 session 历史，下一轮采样自然能看到（构建 prompt 发生在 run_sampling_request 内部，不是这里）。循环退出条件是 !needs_follow_up，其中 needs_follow_up = model_needs_follow_up || has_pending_input——除工具调用外，队列里还有待处理输入也会驱动循环继续。工具执行发生在 run_sampling_request 内部（它调 try_run_sampling_request，在那里流式产出 ResponseItem、执行工具、累加 needs_follow_up），所以一轮 run_turn loop = 一次「采样 + 工具执行」，工具结果回填后回到 loop 顶部再采样。

那 run_sampling_request 自己的 loop {} 干什么？它只做流式重试：

codex-rs/core/src/session/turn.rs:1566 — run_sampling_request 的重试循环（节选）
rustloop {                                            // 仅流式重试，非工具→再采样
    // 取历史（首轮用传入的 input，之后从 session 克隆）并构建 prompt
    let prompt_input = if let Some(input) = initial_input.take() {
        input
    } else {
        sess.clone_history().await
            .for_prompt(&step_context.settings.model_info.input_modalities)
    };
    let prompt = build_prompt(prompt_input, step_context.as_ref(), base_instructions.clone());

    match try_run_sampling_request(..., &prompt, ...).await {
        Ok(output) => return Ok((output, ...)),   // 采样成功 → 立即返回（工具也在这内部执行完）
        Err(err) => match err.details() {
            CodexErrorDetails::ContextWindowExceeded => { ... return Err(err); }
            CodexErrorDetails::UsageLimitReached(e) => { ... return Err(err); }
            _ => err,                                 // 其他错误，下面判断重试
        },
    };

    if !err.is_retryable() { return Err(err); }
    // 可重试错误：更新重试状态，回到 loop 顶部再来一次（同一轮采样重试，非新一轮工具循环）
    handle_retryable_response_stream_error(&mut retry_state, ...).await?;
}
读懂这段： run_sampling_request 的 loop 只在可重试的流式错误时继续——采样一成功就 return Ok，把控制权交回 run_turn。重试逻辑内建在这个循环里：流式出错时，按 is_retryable() 决定是重试（继续 loop）还是上报（返回 Err）。别把它和 run_turn 的「工具→再采样」循环搞混。
关键 注意 ContextWindowExceeded 会直接返回错误而非重试——它先 set_total_tokens_full 标记窗口已满，再上抛。上抛后该 turn 走通用错误分支：发出 turn 错误事件并 break 结束当前 turn（让用户继续），并不在同一个 turn 内自动压缩重试。真正的压缩防线上移到了采样之前——run_pre_sampling_compact（见第 6 章）在构建 prompt 前就检查预算；而采样成功后若 token 仍触顶（should_roll_over），会在 mid-turn 触发一次 run_auto_compact 为下一轮腾空间。即「压缩」主要跑在成功路径上，而非作为超窗错误的兜底重试。（例外：Guardian 审查预算耗尽后触发的超窗，会先压缩一次再继续采样。）

3.4流式：LLM 回答怎么边产边发

try_run_sampling_request 内部调用 client.rs 的流式接口。LLM 的回答不是一次性返回，而是逐个产出 ResponseItem，每产出一个就发对应的 EventMsg：

图 3.4：流式产出。每个 ResponseItem 边产边发 Event，工具结果回填后触发下一轮。

codex-api（codex-api/src/sse/responses.rs）把 provider 的 SSE 流解析成 ResponseEvent 流，client.rs 消费并转发它，try_run_sampling_request 消费它并通过 sess.send_event 实时广播。TUI 收到 AgentMessageContentDelta 的增量 delta 就立刻渲染——这就是你看到 Codex「逐字打字」的原因。

3.5Steering：Agent 跑着时怎么插话

Codex 允许在 turn 运行时插入新输入，这叫 steering（转向）。它由 TurnInputMode 控制：

codex-rs/protocol/src/turn_input.rs:133 — TurnInputMode

pub enum TurnInputMode {
    /// 空闲时启动新 turn；否则转向当前活动 turn。
    StartOrSteer,
    /// 仅当线程空闲时才启动。
    StartIfIdle,
    /// 仅当指定的 turn 仍活动时才转向。
    Steer { expected_turn_id: String },
}
codex-rs/protocol/src/turn_input.rs:184 — 提交结果（节选，start_or_steer 路径）
rustpub enum TurnInputSubmission {
    /// Core 启动了一个 turn
    Started { turn_id: String },
    /// Core 转向了活动中的 turn（不创建新 turn）
    Steered { turn_id: String },
    /// Core 拒绝了输入
    NotSubmitted { reason: NotSubmittedReason },
}
读懂这段： 当你在一个跑着的 turn 里再发一条消息，Codex 不是开新 turn，而是 steer 当前 turn——新输入被塞进 input_queue，在当前工具执行完后的合适时机送达模型。NotSubmittedReason 列出了拒绝原因（NoActiveTurn、ExpectedTurnMismatch、ActiveTurnNotSteerable、ServerDraining、PendingTriggerTurn 等），让前端能精确反馈。注意 并非所有 turn 都可 steer——某些 turn kind（NonSteerableTurnKind，如 Review、Compact）拒绝转向。

steering 输入排在 input_queue.rs 的 TurnInputQueue（内部是 Vec<TurnInput>；同文件的 VecDeque 存的是 Agent 间通信邮件，不是 steering），由 MailboxDeliveryPhase（core/src/state/turn.rs）控制送达时机（通常在当前工具完成后、下一次采样前）：

3.6中断与恢复

用户可以发 Op::Interrupt 中断当前 turn。中断不是杀死进程，而是触发 CancellationToken，让循环在合适的安全点退出：

codex-rs/protocol/src/protocol.rs:1828 — AgentStatus 状态
rustpub enum AgentStatus {
    PendingInit,                 // 等待初始化
    Running,                     // 正在跑
    Interrupted,                 // turn 被中断，可接收更多输入
    Completed(Option<String>),   // 完成，含最终消息
    Errored(String),             // 出错
    Shutdown,                    // 已关闭
    NotFound,
}
codex-rs/core/src/agent/status.rs:6 — 从事件推导状态
rustfn agent_status_from_event(msg: &EventMsg) -> Option<AgentStatus> {
    match msg {
        EventMsg::TurnStarted(_) => Some(AgentStatus::Running),
        EventMsg::TurnComplete(ev) => Some(match &ev.error {
            Some(error) => AgentStatus::Errored(error.message.clone()),
            None => AgentStatus::Completed(ev.last_agent_message.clone()),
        }),
        EventMsg::TurnAborted(ev) => match ev.reason {
            TurnAbortReason::Interrupted | TurnAbortReason::BudgetLimited => {
                Some(AgentStatus::Interrupted)
            }
            _ => Some(AgentStatus::Errored(format!("{:?}", ev.reason))),
        },
        EventMsg::Error(ev) => Some(AgentStatus::Errored(ev.message.clone())),
        EventMsg::ShutdownComplete => Some(AgentStatus::Shutdown),
        _ => None,
    }
}
读懂这段： 状态完全由事件驱动推导——TurnStarted → Running，TurnComplete → Completed（无错误时）/ Errored（携带终端错误时，ev.error），TurnAborted 按原因分到 Interrupted 或 Errored。中断后的 turn 是可恢复的：线程空闲时前端可发 Op::RecoverTurn（走 recover_turn_if_idle），复用已记录的 turn_id 重新采样，不产生新的用户输入。这是「崩溃可恢复」的基础（配合第 4 章的 rollout 持久化）。

3.7小结：turn 循环的完整心智模型

一张图记牢 run_turn（准备：压缩 / step context / 记录输入）→ run_turn 的 loop {}（取 pending 输入 → 捕获 step context → 克隆历史 → 调 run_sampling_request：在其重试循环里 build_prompt → 流式调 LLM → 产 ResponseItem → 发 Event → 若有 FunctionCall 则执行工具、结果回填历史 → 返回 needs_follow_up）→ 有工具调用或有待处理输入则回到 loop 顶部再采样，否则 TurnComplete。
对自研的启示 你的 Agent 循环最小实现就是一个 while not done：每轮把消息列表发给模型，解析返回——若有 tool_calls，执行后把结果 append 进消息列表，继续循环；否则结束。把「重试」「中断」「steering」做成循环里的分支条件，而非独立系统，这是 Codex 给的范本。
