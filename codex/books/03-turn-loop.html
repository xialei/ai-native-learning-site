★ Turn 循环：一个 prompt 在 Codex 里到底怎么跑

这是整个代码库的心脏。一个 turn 不是一次 LLM 调用，而是一个「采样 → 解析工具 → 执行工具 → 把结果塞回历史 → 再采样」的循环，直到模型不再请求工具为止。本章从 CodexThread 一路追到 run_sampling_request 的 loop {}，看清流式、重试、中断、steering 全怎么咬合。
核心洞见 「Agent 循环」的本质，是一个带状态的 while 循环 → 每轮把会话历史 + 上下文喂给 LLM，拿回文本或工具调用；若是工具调用，执行后把结果追加进历史，再进下一轮。Codex 把这个循环实现在 run_sampling_request 的 loop {} 里。

3.2run_turn：turn 的前置准备

run_turn 是 turn 的入口，它负责「采样前」的所有准备：前置压缩、捕获 step context、记录用户输入、构建技能/插件注入。真正采样在它调用的 run_sampling_request 里。

codex-rs/core/src/session/turn.rs:153 — run_turn 签名与前置压缩

    // 5. 最终进入采样循环 run_sampling_request
}
读懂这段： 注意三个细节。① 前置压缩（pre-sampling compact）：在构建 prompt 之前就检查 token 预算，避免还没发请求就超窗。② step context 快照：capture_step_context 把「模型这一轮该看到的状态」冻结下来，保证一个 turn 内的多次采样看到一致的世界。③ prewarmed_client_session：client session 可被预热复用，省去每轮重建连接的开销。

3.3run_sampling_request：那个 loop {}

这是 Agent 的心脏。一个 loop {}，每轮：取历史 → 构建 prompt → 调 LLM → 处理结果。来看真实代码（精简后）：

codex-rs/core/src/session/turn.rs:1341 — 采样循环（节选）
rustasync fn run_sampling_request(
    sess: Arc<Session>,
    step_context: Arc<StepContext>,
    client_session: &mut ModelClientSession,
    input: Vec<ResponseItem>,
    cancellation_token: CancellationToken,
) -> CodexResult<(SamplingRequestResult, Vec<ResponseItem>)> {
    let base_instructions = sess.get_base_instructions().await;
    let tool_runtime = ToolCallRuntime::new(...);     // 工具运行时
    let max_retries = turn_context.provider.info().stream_max_retries();
    let mut retry_state = ResponsesStreamRetryState::default();
    let mut initial_input = Some(input);

    loop {                                            // ★ Agent 心脏
        // 1. 取会话历史（首次用传入的 input，之后从 session 克隆）
        let prompt_input = if let Some(input) = initial_input.take() {
            input
        } else {
            sess.clone_history().await.for_prompt(&modalities)
        };

        // 2. 构建 prompt（历史 + base instructions + 上下文片段）
        let prompt = build_prompt(prompt_input, step_context.as_ref(), base_instructions.clone());

        // 3. 调用 LLM（流式），出错则按可重试性决定重试或返回
        match try_run_sampling_request(..., &prompt, ...).await {
            Ok(output) => return Ok((output, ...)),   // 模型不再要工具 → 结束
            Err(err) => match err.details() {
                CodexErrorDetails::ContextWindowExceeded => { ... return Err(err); }
                CodexErrorDetails::UsageLimitReached(e) => { ... return Err(err); }
                _ => err,                                 // 其他错误，下面判断重试
            },
        };

        if !err.is_retryable() { return Err(err); }
        // 4. 可重试错误：更新重试状态，回到 loop 顶部再来一次
        handle_retryable_response_stream_error(&mut retry_state, ...).await?;
    }
}
读懂这段： 这就是「Agent 循环」的全部秘密。每轮 loop 重新克隆历史并构建 prompt——这意味着工具执行结果已经被追加进 session 历史，下一轮采样自然能看到。循环退出条件是 try_run_sampling_request 返回 Ok（模型给出了不含工具调用的最终回答）。重试逻辑内建在循环里：流式出错时，按 is_retryable() 决定是重试（继续 loop）还是上报（返回 Err）。
关键 注意 ContextWindowExceeded 会直接返回错误而非重试——它先 set_total_tokens_full 标记窗口已满，再上抛。上抛后该 turn 走通用错误分支：发出 turn 错误事件并 break 结束当前 turn（让用户继续），并不在同一个 turn 内自动压缩重试。真正的压缩防线上移到了采样之前——run_pre_sampling_compact（见第 6 章）在构建 prompt 前就检查预算；而采样成功后若 token 仍触顶（should_roll_over），会在 mid-turn 触发一次 run_auto_compact 为下一轮腾空间。即「压缩」主要跑在成功路径上，而非作为超窗错误的兜底重试。

3.4流式：LLM 回答怎么边产边发

try_run_sampling_request 内部调用 client.rs 的流式接口。LLM 的回答不是一次性返回，而是逐个产出 ResponseItem，每产出一个就发对应的 EventMsg：

图 3.4：流式产出。每个 ResponseItem 边产边发 Event，工具结果回填后触发下一轮。

client.rs 把 provider 的 SSE 流解析成 ResponseItem 流，并通过 sess.send_event 实时广播。TUI 收到 AgentMessage 的增量 delta 就立刻渲染——这就是你看到 Codex「逐字打字」的原因。

3.5Steering：Agent 跑着时怎么插话

Codex 允许在 turn 运行时插入新输入，这叫 steering（转向）。它由 TurnInputMode 控制：

codex-rs/protocol/src/turn_input.rs:129 — TurnInputMode

pub enum TurnInputMode {
    /// 空闲时启动新 turn；否则转向当前活动 turn。
    StartOrSteer,
    /// 仅当线程空闲时才启动。
    StartIfIdle,
    /// 仅当指定的 turn 仍活动时才转向。
    Steer { expected_turn_id: String },
}
codex-rs/protocol/src/turn_input.rs:161 — 提交结果
rustpub enum TurnInputSubmission {
    /// Core 启动了一个 turn
    Started { turn_id: String },
    /// Core 转向了活动中的 turn（不创建新 turn）
    Steered { turn_id: String },
    /// Core 拒绝了输入
    NotSubmitted { reason: NotSubmittedReason },
}
读懂这段： 当你在一个跑着的 turn 里再发一条消息，Codex 不是开新 turn，而是 steer 当前 turn——新输入被塞进 input_queue，在当前工具执行完后的合适时机送达模型。NotSubmittedReason 列出了拒绝原因（NoActiveTurn、ExpectedTurnMismatch、ActiveTurnNotSteerable 等），让前端能精确反馈。注意 并非所有 turn 都可 steer——某些 turn kind（NonSteerableTurnKind）拒绝转向。

steering 输入通过 input_queue.rs 的 VecDeque 排队，由 MailboxDeliveryPhase 控制送达时机（通常在当前工具完成后、下一次采样前）：

3.6中断与恢复

用户可以发 Op::Interrupt 中断当前 turn。中断不是杀死进程，而是触发 CancellationToken，让循环在合适点优雅退出：

codex-rs/protocol/src/protocol.rs:1749 — AgentStatus 状态
rustpub enum AgentStatus {
    PendingInit,                 // 等待初始化
    Running,                     // 正在跑
    Interrupted,                 // turn 被中断，可接收更多输入
    Completed(Option<String>),   // 完成，含最终消息
    Errored(String),             // 出错
    Shutdown,                    // 已关闭
    NotFound,
}
codex-rs/core/src/agent/status.rs:6 — 从事件推导状态
rustfn agent_status_from_event(msg: &EventMsg) -> Option<AgentStatus> {
    match msg {
        EventMsg::TurnStarted(_) => Some(AgentStatus::Running),
        EventMsg::TurnComplete(ev) => Some(AgentStatus::Completed(ev.last_agent_message.clone())),
        EventMsg::TurnAborted(ev) => match ev.reason {
            TurnAbortReason::Interrupted | TurnAbortReason::BudgetLimited => {
                Some(AgentStatus::Interrupted)
            }
            _ => Some(AgentStatus::Errored(format!("{:?}", ev.reason))),
        },
        EventMsg::Error(ev) => Some(AgentStatus::Errored(ev.message.clone())),
        EventMsg::ShutdownComplete => Some(AgentStatus::Shutdown),
        _ => None,
    }
}
读懂这段： 状态完全由事件驱动推导——TurnStarted → Running，TurnComplete → Completed，TurnAborted 按原因分到 Interrupted 或 Errored。中断后的 turn 是可恢复的：前端可发 Op::RecoverTurn 让采样在原 turn_id 下继续。这是「崩溃可恢复」的基础（配合第 4 章的 rollout 持久化）。

3.7小结：turn 循环的完整心智模型

一张图记牢 run_turn（准备：压缩 / step context / 记录输入）→ run_sampling_request 的 loop {}（取历史 → build_prompt → 流式调 LLM → 产 ResponseItem → 发 Event → 若有 FunctionCall 则执行工具、结果回填历史 → 回到 loop）→ 模型不再要工具时 TurnComplete。
对自研的启示 你的 Agent 循环最小实现就是一个 while not done：每轮把消息列表发给模型，解析返回——若有 tool_calls，执行后把结果 append 进消息列表，继续循环；否则结束。把「重试」「中断」「steering」做成循环里的分支条件，而非独立系统，这是 Codex 给的范本。
