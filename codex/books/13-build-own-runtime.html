13 · 自制 Agent Runtime：从读到造的路线图

读 Codex 源码的最终目的，是造出你自己的 Agent Runtime。这一章把前 12 章拆解的机制浓缩成一条可执行的构建路线—— 从最小可跑的循环开始，按里程碑逐步叠加能力，最终逼近一个生产级编码 Agent。每个里程碑都标明对应章节，让你能随时回查实现细节。

13.1核心理念：先跑通，再补全

很多人想造 Agent，一上来就设计协议、做沙箱、搞多 Agent——结果几个月跑不出一个能用的循环。Codex 自己的演进顺序恰恰相反：先有一个能「收 prompt → 调模型 → 执行工具 → 再调模型」的闭环，再逐步加上下文管理、压缩、安全、扩展、协作。这条路线也应是你的路线。

图 13.1：六个里程碑。颜色由深到浅表示「必需度递减、可延后」——M0/M1 是底线，M5 是进阶。

13.2M0：最小循环（第 2、3 章）

目标：一个能在终端里「问一句、答一句、必要时调一次工具」的程序。不要超过 300 行。

// 伪代码：最小 Agent 循环
async fn run_turn(messages: &mut Vec<Message>, user_input: String) {
    messages.push(Message::user(user_input));

    loop {
        // 1. 采样：把整个 messages 发给模型，附上工具 schema
        let response = model.sample(messages, &tool_schemas).await;

        // 2. 解析：模型回了消息还是工具调用？
        match parse(response) {
            AgentMessage(text) => {
                print(text);
                break;            // 没有工具调用 → 本轮结束
            }
            ToolCall(name, args) => {
                // 3. 执行工具
                let output = registry.execute(name, args).await;
                // 4. 回灌结果，继续循环
                messages.push(Message::tool_result(output));
            }
        }
    }
}
这一步只做三件事 ① 一个 Message 列表代表会话；② 一个 sample() 调用 LLM；③ 一个 loop 在「有工具调用」时继续、「纯消息」时退出。别在这步做流式、压缩、沙箱——那些是后面的里程碑。先把闭环跑通，能用 echo 当工具验证循环正确。

13.3M1：工具系统（第 7 章）

把 M0 里硬编码的工具，抽象成一个可扩展的系统。核心是一个 trait 和一个注册表：

// 仿 Codex 的 ToolExecutor，但极简版
#[async_trait]
trait Tool {
    fn name(&self) -> &str;
    fn schema(&self) -> JsonSchema;          // 给模型看的参数描述
    async fn run(&self, args: Value) -> Result<String>;
}

struct ToolRegistry { tools: HashMap<String, Box<dyn Tool>> }

// 先实现两个工具
impl Tool for RunCommand { .. }   // 执行 shell
impl Tool for EditFile { .. }     // 读写改文件

关键点：① schema 用 JSON Schema，直接喂给模型的 function calling；② 工具输出必须可截断（一个 cat 大文件就会炸上下文）；③ 先别管并行和 Freeform——等基础稳定。Codex 的 apply_patch 用 Freeform（lark 语法）是因为 patch 参数用 JSON 描述太易错，但你 M1 阶段用普通 function 工具改文件就够了。

13.4M2：持久化与恢复（第 4 章）

让会话不只是内存里的 Vec<Message>，而是可恢复的持久资产。最简实现：每条消息追加写一行 JSONL。

// 仿 Codex 的 RolloutLine，但极简
struct RolloutLine {
    timestamp: String,
    ordinal: u64,        // 单调递增序号
    item: Item,          // Message / ToolCall / ToolResult
}

// 每个 turn 结束追加；启动时读回重建 messages
fn append(session_id, line) { writeln!(file, "{}", json(line))?; }
fn resume(session_id) -> Vec<Message> { read_jsonl(session_id).map(parse) }

事件源（event sourcing）的好处在这里兑现：会话是一份只追加日志，resume 就是 replay，fork 就是从某点复制日志再继续。先别上 SQLite 索引——纯 JSONL 够你用很久，等会话多到扫描慢了再加索引（Codex 的 state_db 就是为此而生）。

13.5M3：上下文工程（第 5 章）

到这步你的 Agent 已经能干活，但系统提示是写死的。M3 让上下文可组装——把不同来源的指令拼成发给模型的 prompt。

// 仿 Codex 的 ContextualUserFragment，但极简
trait Fragment {
    fn role(&self) -> Role;        // system / developer / user
    fn body(&self) -> String;
}

fn build_prompt(fragments: &[dyn Fragment], history: &[Message]) -> Vec<Message> {
    // 基础指令 + 项目 AGENTS.md + 环境信息 + 历史
    let mut msgs = fragments.iter().map(|f| Message::new(f.role(), f.body())).collect();
    msgs.extend(history);
    msgs
}

核心思想：上下文不是一个大字符串，而是有序的 Fragment 列表。每个 Fragment 知道自己的角色和内容。这样你能动态插入项目级 AGENTS.md（让 Agent 了解项目约定）、环境信息（OS、git 状态）、开发者指令——而不必改代码。Codex 的 ContextManager 还做了「增量 diff」（只发变化部分），但 M3 阶段全量重发即可。

13.6M4：压缩与安全（第 6、8 章）

这是从「玩具」到「能用」的临界点。两个能力必须补：

压缩——上下文会涨，涨过模型窗口就崩。最简实现：采样前检查 token 数，超阈值就把最早的历史消息摘要成一段。

async fn maybe_compact(messages: &mut Vec<Message>) {
    if count_tokens(messages) > LIMIT {
        let summary = model.summarize(&messages[..half]).await;
        *messages = [Message::system(summary), messages[half..].to_vec()].concat();
    }
}

安全——能跑 shell 的 Agent 必须有沙箱。M4 最小实现：用平台原生机制（macOS seatbelt / Linux bubblewrap）限制只写工作目录，在 spawn 前用一个 Allow/Prompt/Forbidden 枚举裁决。

安全不是可选 M4 之前你的 Agent 跑在裸环境里，一个 rm -rf 就能毁掉一切。哪怕第一版沙箱只是「只允许写 cwd」的简单包装，也必须在让 Agent 跑真实任务前加上。Codex 的 WritableRoot 还保护 .git/hooks 这类二级提权点——你至少要想清楚「可写区里还有什么不能写」。

13.7M5：扩展、协作、多前端（第 10、11、12 章）

前五个里程碑做完，你已有了一个能干活的、安全的、可恢复的 Agent。M5 是进阶——按需选取：

能力何时做对应 Codex 机制
MCP 工具接入需要挂外部工具时统一 ToolSpec + stdio/HTTP 传输（第 10 章）
多 Agent 派生单 Agent 上下文不够 / 需并行spawn_agent + 角色预设 + 深度护栏（第 11 章）
非交互 / 守护进程要进 CI 或做服务app-server 协议 + 多传输（第 12 章）
动态工具发现工具数量爆炸时ToolSearch 按需检索（第 10 章）
自动审核要无人值守时ApprovalsReviewer::AutoReview + Granular（第 8 章）
M5 的取舍 这些能力每个都显著增加复杂度。多 Agent 尤其要慎重——它是放大器，既放大能力也放大 token 成本和调试难度。Codex 用派生深度 + 并发上限双重护栏兜底，但你自己实现时，建议先确认单 Agent 已经非常稳定，再引入派生。大多数场景下，一个上下文管理良好的单 Agent 比一群失控的子 Agent 更有效。

13.8贯穿始终的设计原则

从 Codex 源码里提炼出的六条原则，适用于你的每个里程碑：

要做的

  • 协议优先：内核与前端用协议隔开，加新前端不重写内核（第 2、12 章）。
  • 意图声明，平台落地：SandboxPolicy 声明意图，平台后端落地，别自己造沙箱内核（第 8 章）。
  • 决策前置：在执行前裁决 Allow/Prompt/Forbidden，而非出错后回滚（第 8 章）。
  • 事件源持久化：会话是只追加日志，resume/fork 天然支持（第 4 章）。
  • 按需加载：上下文只装当前需要的，工具靠 ToolSearch 动态发现（第 5、10 章）。
  • 配置与约束分离：偏好可覆盖，安全红线不可覆盖（第 9 章）。

别做的

  • 别一上来全做：先跑通最小循环，沙箱/压缩/多 Agent 都是后面的事。
  • 别让工具输出不截断：一个大文件输出就炸上下文。
  • 别随意改系统提示：系统提示经过调优，优先用 developer 角色注入（第 5 章）。
  • 别让子 Agent 提权：派生的 Agent 权限只能降不能升（第 11 章）。
  • 别忽略二级提权：可写区里的 .git/hooks、.ssh 必须额外只读（第 8 章）。
  • 别无护栏递归：多 Agent 必须有深度 + 并发双重上限（第 11 章）。

13.10结语：Codex 教会我们的事

读完这 13 章，你应该看到一个生产级编码 Agent 的全貌。它不是魔法，而是一组可拆解、可仿造的工程机制：一个 turn 循环驱动一切，工具系统提供手脚，上下文工程管理记忆，压缩对抗遗忘，沙箱与审批守住边界，rollout 让会话不朽，多 Agent 把能力正交扩展。

Codex 最值得学的，不是某个精巧的技巧，而是它的分层克制：每一层只管一件事，层与层用协议/枚举/trait 解耦。这种克制让它能在个人笔记本和企业集群里同样运行，能从「问一句答一句」长到「派生团队并行编码」。当你造自己的 Runtime 时，记住这份克制——先跑通闭环，再补全能力，永远让安全先于自主。

下一步 合上这份教程，打开你的编辑器，从 M0 开始。用 300 行写出第一个能调工具的循环——那一刻，你就从「读 Agent」变成了「造 Agent」。Codex 的源码永远在这里作参考：每个机制都有对应的章节和文件路径，随时可回查。祝你造得顺利。

「读源码是为了不再迷信源码。当你理解了一个系统为何如此设计，你就有能力设计一个更好的。」
