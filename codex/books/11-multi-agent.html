11 · 多 Agent 与协作：分而治之的运行时

单个 Agent 受限于一个上下文窗口、一条注意力线。Codex 的多 Agent 系统让一个「主 Agent」能派生（spawn）子 Agent， 把独立子任务并行分派出去，再汇总结果。这不是简单的函数调用——每个子 Agent 是一个完整的 CodexThread， 有自己的会话、配置、上下文，只是继承了父 Agent 的权限与角色约束。本章拆解这套协作机制。

11.1六个协作工具：spawn / send_input / wait_agent / close_agent / list_agents / resume_agent

多 Agent 能力对模型暴露为一组工具。主 Agent 通过调用它们来管理子 Agent 的生命周期：

codex-rs/core/src/tools/handlers/multi_agents_spec.rs
// v1: 用 Namespace 暴露；v2: 用 Function。两者等价。
pub fn create_spawn_agent_tool_v1(options) -> ToolSpec {
    ToolSpec::Namespace(ResponsesApiNamespace {
        name: MULTI_AGENT_V1_NAMESPACE.to_string(),
        tools: [
            // spawn_agent: 派生一个新子 Agent，分派任务
            { name: "spawn_agent", description: "...", .. },
            // send_input: 向已有 Agent 发消息（interrupt=true 可打断重定向）
            { name: "send_input", description: "Send a message to an existing agent. Use interrupt=true to redirect work immediately. You should reuse the agent by send_input if you believe your assigned task is highly dependent on the context of a previous task.", .. },
        ],
    })
}

六个动作构成完整生命周期：

工具作用文件
spawn_agent派生子 Agent，分派任务multi_agents/spawn.rs
send_input向已有子 Agent 追加输入 / 打断重定向multi_agents/send_input.rs
wait_agent等待子 Agent 完成（带超时）multi_agents/wait.rs
list_agents列举当前派生的子 Agent 及状态multi_agents_spec.rs
close_agent关闭子 Agentmulti_agents/close_agent.rs
resume_agent恢复一个被关闭/中断的子 Agentmulti_agents/resume_agent.rs
复用 vs 新建 send_input 的描述强调：当新任务「高度依赖前一个任务的上下文」时，应复用已有 Agent 而非新 spawn。这是上下文经济的体现——一个已经探索过某模块的 Agent，其上下文里已有相关知识，复用比从头 spawn 另一个更省 token、更快。模型被明确教导这个权衡。

11.2Agent 角色：内置 default / explorer / worker

派生子 Agent 时可指定 agent_type（角色）。角色不是空泛的标签，而是带配置覆盖的预设——它能在子 Agent 继承的父配置之上叠加限制（如换模型、调低推理强度、关闭某些 feature）。

codex-rs/core/src/agent/role.rs:351 (built_in 模块)
pub(super) fn configs() -> &'static BTreeMap<String, AgentRoleConfig> {
    BTreeMap::from([

        ("explorer", AgentRoleConfig {
            description: r#"Use `explorer` for specific codebase questions.
Explorers are fast and authoritative.
They must be used to ask specific, well-scoped questions on the codebase.
Rules:
- ...trust the explorer results without additional verification...
- You are encouraged to spawn up multiple explorers in parallel when you have
  multiple distinct questions... This parallelism is a key advantage of delegation...
- Reuse existing explorers for related questions."#,
            config_file: "explorer.toml",  // 内嵌的配置覆盖
        }),

        ("worker", AgentRoleConfig {
            description: r#"Use for execution and production work.
Typical tasks: implement part of a feature / fix tests / split large refactors.
Rules:
- Explicitly assign **ownership** of the task (files / responsibility)...
- Always tell workers they are **not alone in the codebase**, and they should
  not revert the edits made by others..."#,
        }),
    ])
}

三个内置角色各有定位：explorer 是只读侦察兵（快、权威、可并行）；worker 是执行者（写代码、改文件，强调所有权与不互相覆盖）；default 是通用型。角色描述本身就是系统提示的一部分——它直接告诉主 Agent「何时该用哪种角色」「怎么分配工作」。

权限不可提升 注释写明：「角色可定制或削减子 Agent 能力，但绝不替换父会话的权限」。子 Agent 的沙箱、审批策略从父继承，角色只能收紧不能放宽。这是安全的关键不变量——否则一个 explorer 角色就能把自己升级成 danger-full-access，权限模型就崩了。

11.3派生流程：从工具调用到子线程

handle_spawn_agent 是核心。它把一次工具调用翻译成 AgentControl::spawn_agent_with_metadata，真正起一个子 CodexThread。

codex-rs/core/src/tools/handlers/multi_agents/spawn.rs:44
async fn handle_spawn_agent(invocation) -> Result<..> {
    let role_name = args.agent_type.as_deref().filter(|r| !r.is_empty());

    // 1. 计算子线程的派生深度，检查是否超限
    let child_depth = next_thread_spawn_depth(&session_source);
    let max_depth = turn.config.agent_max_depth;
    if exceeds_thread_spawn_depth_limit(child_depth, max_depth) {
        return "Agent depth limit reached. Solve the task yourself.";  // 拒绝派生
    }

    // 2. 构建派生配置（继承父配置）
    build_agent_spawn_config(&session.get_base_instructions().await, turn.as_ref())?;
    reject_full_fork_agent_type_override(role_name)?;          // 禁止角色全量覆盖
    apply_requested_spawn_agent_model_overrides(..);            // 应用模型覆盖
    apply_spawn_agent_role(&session, &mut config, role_name).await?;  // 应用角色
    apply_spawn_agent_runtime_overrides(&mut config, turn.as_ref())?;

    // 3. 真正派生：AgentControl 起子线程
    let result = session.services.agent_control
        .spawn_agent_with_metadata(.., child_depth, role_name, fork_parent_spawn_call_id)?;
}

三步逻辑清晰：先查深度限额，再组装配置（继承 + 角色覆盖），最后交给 AgentControl 起线程。失败会返回可读的错误给模型，让模型自行决定换策略。

11.4派生深度与递归护栏

子 Agent 也是 Agent，也能再派生孙子 Agent。若无限制，会出现无限递归的 Agent 树，耗尽资源。Codex 用派生深度（spawn depth）护栏：

codex-rs/core/src/agent/registry.rs:87
pub(crate) fn next_thread_spawn_depth(session_source) -> i32 {
    session_depth(session_source).saturating_add(1)   // 父深度 + 1
}

pub(crate) fn exceeds_thread_spawn_depth_limit(depth: i32, max_depth: i32) -> bool {
    depth > max_depth   // 超过配置的 agent_max_depth 就拒绝
}

主 Agent 深度为 0，它派生的子 Agent 深度为 1，孙 Agent 为 2……当深度超过 agent_max_depth，spawn_agent 被拒绝，模型收到「Agent depth limit reached. Solve the task yourself.」——强制它自己解决而非继续分派。这是递归系统必备的底线机制。

图 11.1：Agent 派生树。同层可并行派生多个（explorer 并行侦察），但深度受 agent_max_depth 限制，超出即拒绝。

11.5AgentControl：子 Agent 的控制面

AgentControl 是管理所有子线程的中心对象，提供完整的控制 API：

codex-rs/core/src/agent/control.rs:114
pub(crate) struct AgentControl { .. }

impl AgentControl {
    pub(crate) async fn send_input(..)              // 向子 Agent 投递输入
    pub(crate) async fn send_inter_agent_communication(..) // Agent 间通信
    pub(crate) async fn emit_sub_agent_activity(..)  // 上报子 Agent 活动
    pub(crate) async fn interrupt_agent(agent_id)   // 打断某子 Agent
    pub(crate) async fn get_status(agent_id) -> AgentStatus
    pub(crate) async fn list_live_agent_subtree_thread_ids(..)
    pub(crate) async fn list_agents(..)
    pub(crate) async fn subscribe_status(..)        // 订阅状态变化
    pub(crate) async fn spawn_agent_with_metadata(..) // 派生
}

注意 send_inter_agent_communication——子 Agent 之间可以通信，不只限于「父→子」。这让协作模式更丰富：一个 worker 完成自己的部分后，可以把结果直接发给另一个 worker，而不必回父 Agent 中转。配合 subscribe_status，父 Agent 能异步感知所有子 Agent 的进度。

同时 AgentRegistry::reserve_spawn_slot 用 max_threads 做并发上限——不只是深度受限，同时存活的子 Agent 总数也受限。双重护栏防止 Agent 失控繁殖。

11.6fork 与上下文继承

spawn.rs 里有个 fork_parent_spawn_call_id 字段——它支持一种特殊派生：fork。普通 spawn 给子 Agent 一个全新空会话；fork 则让子 Agent 继承父 Agent 当前的上下文快照，相当于「在父的当前状态上分支」。

codex-rs/core/src/tools/handlers/multi_agents/spawn.rs
fork_parent_spawn_call_id: args.fork_context.then(|| call_id.clone()),

fork 适用于「我想在当前理解的基础上，并行探索多个方向」的场景。它复用了第 4 章 rollout 的快照能力——fork 本质是创建一个共享父历史的子会话。配合 reject_full_fork_agent_type_override（禁止 fork 时全量覆盖角色），保证 fork 出的子 Agent 仍在受控范围内。

11.8小结与对自研的启示

自研 checklist 多 Agent 是「放大器」——既放大能力也放大成本和复杂度，别过早引入。① 先单 Agent 跑通，确认一个 Agent 的 turn 循环、工具、上下文都稳定，再谈派生。② 子 Agent 是完整线程而非函数——它有自己的会话和上下文，继承父权限，这比「调一个子函数」重得多，要权衡 token 成本。③ 必须有递归护栏——派生深度 + 并发上限双重限制，否则一个失控的 Agent 就能繁殖到耗尽资源。④ 角色即配置覆盖——用角色预设（explorer/worker）约束子 Agent 的能力和行为，而非让它和父一样全能。⑤ 教模型何时分派——把协作策略写进角色描述（并行、复用、所有权），模型不会自己学会高效分派。⑥ 权限只降不升——子 Agent 绝不能突破父的权限边界，这是安全红线。
一句话 Codex 的多 Agent 哲学：「完整子线程 + 角色约束 + 递归护栏」。每个子 Agent 是一个继承父权限的独立 CodexThread，靠 spawn 深度与并发上限兜底，靠角色预设让分派有章法。这是把单 Agent 能力正交扩展为团队协作的标准范式。
