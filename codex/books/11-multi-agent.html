11 · 多 Agent 与协作：分而治之的运行时

单个 Agent 受限于一个上下文窗口、一条注意力线。Codex 的多 Agent 系统让一个「主 Agent」能派生（spawn）子 Agent， 把独立子任务并行分派出去，再汇总结果。这不是简单的函数调用——每个子 Agent 是一个完整的 CodexThread， 有自己的会话、配置、上下文，只是继承了父 Agent 的权限与角色约束。本章拆解这套协作机制。

11.1协作工具：V1 / V2 两套工具面

快照实现 本节的工具名、feature flag 与注册路径都是锚点提交的实验线实现，主干仍在演进——学机制，别背清单。

用户可见的一面：多 Agent 能力对模型暴露为一组工具，主 Agent 通过调用它们管理子 Agent 的生命周期。V1 与 V2 是两套互斥的暴露方案，由 multi_agent_v2_enabled 开关二选一：

派生子 Agent 时可指定 agent_type（角色）。角色不是空泛的标签，而是带配置覆盖的预设——它能在子 Agent 继承的父配置之上叠加限制（如换模型、调低推理强度、关闭某些 feature）。

11.3派生流程：从工具调用到子线程

handle_spawn_agent 是核心。它把一次工具调用翻译成一个 SpawnRequest，交给 AgentControl::spawn，真正起一个子 CodexThread。构建子配置的那一坨「继承父配置 + 角色覆盖」逻辑已被收拢到独立模块 agent/child_config.rs 的 prepare_agent_spawn_config——V1/V2 两个 handler 共用这一个入口。

codex-rs/core/src/tools/handlers/multi_agents/spawn.rs:53
async fn handle_spawn_agent(invocation) -> Result<..> {
    let role_name = args.agent_type.as_deref().map(str::trim).filter(|r| !r.is_empty());

    // 1. 计算子线程的派生深度，检查是否超限
    let child_depth = next_thread_spawn_depth(&session_source);
    let max_depth = turn.config.agent_max_depth;
    if exceeds_thread_spawn_depth_limit(child_depth, max_depth) {
        return Err(RespondToModel("Agent depth limit reached. Solve the task yourself."));
    }

    // 2. 构建派生配置：统一收拢在 agent/child_config.rs（继承 + 角色 + fork 约束）
    let prepared = prepare_agent_spawn_config(
        &session, step_context.as_ref(),
        SpawnConfigOptions {
            version: SpawnConfigVersion::V1,
            full_history_fork: args.fork_context,   // fork 时角色让位（child_config.rs 内部处理）
            role_name,
            model: args.model.as_deref(),
            reasoning_effort: args.reasoning_effort.clone(),
        },
    ).await?;

    // 3. 真正派生：组装 SpawnRequest，交给 AgentControl 起子线程
    let result = session.services.agent_control
        .spawn(SpawnRequest {
            caller: session.thread_id,
            config: prepared.config,
            input: AgentInput::UserInput(input_items),
            source: thread_spawn_source(.., child_depth, prepared.role_name.as_deref(), ..)?,
            options: SpawnAgentOptions {
                fork_parent_spawn_call_id: args.fork_context.then(|| call_id.clone()),
                fork_mode: args.fork_context.then_some(SpawnAgentForkMode::FullHistory),
                parent_thread_id: Some(session.thread_id),
                parent_turn_id: Some(turn.sub_id.clone()),
                root_turn_id: turn.turn_metadata_state.root_turn_id(),
                turn_trigger: turn.turn_metadata_state.current_turn_trigger(),
                environments: Some(step_context.environments.clone()),
                multi_agent_v2_usage_hints: None,
                cyber_access_program: turn.cyber_access_program,
            },
        })
        .await?;   // 返回 (LiveAgent, ThreadConfigSnapshot)
}

三步逻辑清晰：先查深度限额，再把配置组装整个交给 prepare_agent_spawn_config（agent/child_config.rs:51）——fork 约束（reject_full_fork_agent_type_override）、模型覆盖、角色应用（apply_spawn_agent_role）都在里面按序执行——最后组装一个 SpawnRequest（agent/api.rs:195：caller + config + input + source + options）交给 AgentControl::spawn。早期版本这里直接调用 spawn_agent_with_metadata/spawn_agent_with_communication 两个 facade（#47235，2026-09-22 起统一收拢为 SpawnRequest 请求对象），V1 与 V2 的派生路径由此归一——差别只在 input 是用户输入还是 Agent 消息、以及 options 里多不多 usage hints。失败会返回可读的错误给模型，让模型自行决定换策略。

11.4派生深度与递归护栏

子 Agent 也是 Agent，也能再派生孙子 Agent。若无限制，会出现无限递归的 Agent 树，耗尽资源。Codex 用派生深度（spawn depth）护栏：

codex-rs/core/src/agent/registry.rs:80
pub(crate) fn next_thread_spawn_depth(session_source) -> i32 {
    session_depth(session_source).saturating_add(1)   // 父深度 + 1
}

pub(crate) fn exceeds_thread_spawn_depth_limit(depth: i32, max_depth: i32) -> bool {
    depth > max_depth   // 超过配置的 agent_max_depth 就拒绝
}

主 Agent 深度为 0，它派生的子 Agent 深度为 1，孙 Agent 为 2……当深度超过 agent_max_depth，spawn_agent 被拒绝，模型收到「Agent depth limit reached. Solve the task yourself.」——强制它自己解决而非继续分派。这是递归系统必备的底线机制。

图 11.1：Agent 派生树。同层可并行派生多个（explorer 并行侦察），但深度受 agent_max_depth 限制，超出即拒绝。

11.5AgentControl：子 Agent 的控制面

控制面拆成了契约与实现两层：AgentControl 是一个 trait（agent/api.rs:40），定义 spawn / send / interrupt / resolve / inspect / list / watch / admit_turn / record_usage 等控制契约，注释明确写着「boxed Send futures allow callers to use Arc<dyn AgentControl>」——为将来替换本地实现留了口子。当前唯一实现是 LocalAgentControl（agent/control.rs:106），由每个根会话持有（SessionServices.agent_control），整个派生树共享同一实例，让 registry 限定在根线程范围内。实现体按职责拆进 agent/control/ 子模块（spawn / delivery / interrupt / budget / completion / residency / watch 等）。

那个「为将来替换本地实现留的口子」在本锚点已经打开了：ThreadManager::with_agent_control_factory（thread_manager.rs:620）允许宿主进程注入自己的控制器工厂——工厂收到线程 ID，返回一个 Arc<dyn AgentControl>。doc 注释把边界划得很清楚：「New roots use their thread ID as the controller identity; resumed threads must match their persisted session identity. Factory errors fail startup. Internal sessions inherit their parent's controller, and warm resume retains the live controller without calling the factory.」以及一句关键限制——「Host backends support MultiAgentV2; V1 requires local control」：宿主后端只支持 V2，V1 仍要求本地控制。不装工厂就走默认的本地后端，行为与从前一致。

控制面还有了两类观测。其一，spawn 延迟打点：agent/control/spawn_telemetry.rs:12 的 SpawnMeasurements 把一次成功派生拆成 residency_reservation（预留驻留名额）/ fork_context（fork 快照）/ child_create（建子线程）/ durability_wait（等持久化）/ input_admission（准入首个输入）五段时长加总时长，按 fork 模式（none/all/last_n）、历史模式（legacy/paginated）、V1/V2 归并成有界标签再上报（codex-otel），失败的派生不发部分耗时——避免用半截数据污染指标。失败本身也有对应打点：record_collab_spawn_failure（handlers/multi_agents_common.rs:78）按错误类别（limit_reached / invalid_request / thread_not_found / unsupported_operation / internal）记录 spawn 失败原因，V1/V2 两个 spawn handler 都会调用。其二，Guardian 给 V2 worker 供证据时有界收敛：MAX_ROOT_MESSAGES = 16（agent/control/user_authorization.rs:43）——root_user_authorization 返回给子 Agent 的根会话消息最多 16 条，旧 rollout 里更多的历史按兼容容量补足。

16 这个界还牵出一个开关：guardian_root_handoff_context（features/src/lib.rs:1665-1671，UnderDevelopment、默认关，#49057）。开了它，V2 worker 向根线程要证据时（root_user_authorization，agent/control/user_authorization.rs:47）多走一步「根 handoff 上下文」：按 worker 的 agent path 调 selected_message_indices（agent/control/root_handoff.rs:16）从根历史里挑出真正与这个 worker 相关的少量消息（handoff 调用、发往它的消息），选出的消息集会参与 review_context_revision 哈希——上下文变了，Guardian 侧的修订号跟着变，缓存失效。没开开关时 worker_path 为空，退回固定窗口行为。把「给 worker 看什么」从数量界（16 条）演进到「按需挑选」，是证据供给从粗到细的下一步。

注意 send_inter_agent_communication——子 Agent 之间可以通信，不只限于「父→子」。这让协作模式更丰富：一个 worker 完成自己的部分后，可以把结果直接发给另一个 worker，而不必回父 Agent 中转。配合 subscribe_status，父 Agent 能异步感知所有子 Agent 的进度。

11.6fork 与上下文继承

spawn.rs 里有个 fork_parent_spawn_call_id 字段——它支持一种特殊派生：fork。普通 spawn 给子 Agent 一个全新空会话；fork 则让子 Agent 继承父 Agent 当前的上下文快照，相当于「在父的当前状态上分支」。

codex-rs/core/src/tools/handlers/multi_agents/spawn.rs
fork_parent_spawn_call_id: args.fork_context.then(|| call_id.clone()),

fork 适用于「我想在当前理解的基础上，并行探索多个方向」的场景。它复用了第 4 章 rollout 的快照能力——fork 本质是创建一个共享父历史的子会话。配合 reject_full_fork_agent_type_override（禁止 fork 时全量覆盖角色），保证 fork 出的子 Agent 仍在受控范围内。

V1 与 V2 的 fork 参数不同：V1 是布尔 fork_context（全量继承），V2 换成 fork_turns 字符串参数，支持 none（不继承）、all（等价 FullHistory）、正整数 N（只带最近 N 轮，SpawnAgentForkMode::LastNTurns，agent/types.rs:22-24），解析在 multi_agents_v2/spawn.rs:274-307（fork_mode）。V2 里再传旧的 fork_context 会被明确拒绝——「fork_context is not supported in MultiAgentV2; use fork_turns instead」。fork 粒度从开关变成了可调的窗口，主 Agent 可以按任务需要只带「最近几轮」上下文，而不是整个历史。

11.7Agent 消息板：点对点之外的第三条通路

前面两节的消息通路都是「定向」的：send_message 发给某个 Agent，send_inter_agent_communication 走控制面通道。2026-09 起，V2 多了一个共享空间选项——Agent 消息板（ext/agent-message-board crate，Feature::AgentMessageBoard，默认关闭）。它是一个频道制的讨论板：Agent 往 channel 里 post，其他 Agent 订阅后能收到新帖通知——从「你告诉我」变成「我贴出来，谁需要谁来看」。

codex-rs/ext/agent-message-board/src/tools/spec.rs:10

九个工具覆盖了「建频道 → 发帖 → 读帖 → 搜索 → 订阅」的完整闭环，全部挂在 V2 的工具命名空间下（与 send_message 同一个 namespace）。存储是本机 SQLite（agent_message_board_1.sqlite），架构上是可替换后端的：AgentMessageBoard trait 定义契约，LocalAgentMessageBoard 是本地实现，host（MessageBoardHost）负责提供身份与存储位置——「实现拥有存储和通知分发，工具与 feature 注册分开」是 crate 文档原话。

它和 disable_direct_message 开关是配套的：11.1 的源码注记提到，开启 multi_agent_v2.disable_direct_message 后 V2 名单缩成 interrupt_agent + list_agents——直接消息工具全部退场，Agent 间通信只能走消息板，并且路由装配时会校验消息板工具确实可用（spec_plan.rs:502-513，报错「disable_direct_message requires an available agent message board in this session」）。为什么要有这种模式？定向消息是「推」——发件人决定谁看到；消息板是「留痕的广播」——所有协作过程沉淀成可搜索的记录，人可以随时翻看 Agent 们讨论了什么，也天然规避了消息风暴（N 个 Agent 两两互发是 N² 条，贴板上是 N 条）。

源码注记： 核心桥接在 core/src/agent_message_board.rs——把扩展的存储通知与内核的「active-turn」服务接起来：通知只投递给正在跑 turn 的 Agent（空闲 Agent 不唤醒、不排队），新帖以 AgentMessageBoardNotification fragment 注入上下文（见第 5 章的 fragment 清单思路）。注册入口 install_agent_message_board 要求同时开启 AgentMessageBoard 与 MultiAgentV2 两个 feature、且非常态（ephemeral）会话。

「本地 SQLite 是唯一后端」这个说法本锚点已不准确，要改成「两种后端按配置二选一」。装配入口 install_agent_message_board（core/src/agent_message_board.rs:33）现在读 multi_agent_v2.message_board_in_memory 开关（core/src/config/mod.rs:1346，默认 false）：false 走原来的 LocalAgentMessageBoard::open(&sqlite, tree, host)，true 走进程内的 InMemoryMessageBoards（ext/agent-message-board-extension crate，同一棵派生树共享一块内存板）。选择是逐次会话决定的，且有一条硬约束：常态（ephemeral）会话只有在开了 in-memory 时才许用消息板——否则 Ok(None) 直接不装。这和「训练环境共享一块内存板、包括临时会话」的注释是同一个动机：不让临时会话在磁盘上留痕。

后端抽象还长出了第三条腿——远程消息板。新 crate agent-message-board-client 的 RemoteAgentMessageBoard（client.rs:56）用 HTTP + SSE 实现同一个 AgentMessageBoard 契约：构造时给 HttpClient、板子 URL、会话 ID 与访问令牌，读写的 HTTP 策略完全由调用方注入——crate 文档开宗明义「reads and writes never fall back to a private local board」（永不静默降级到本地板）。这意味着多进程部署（比如多个 codex 实例协作、或宿主进程代管消息板）时，Agent 树可以指向一块共享的远程板，而内核侧的工具面与语义完全不变。

11.8协作模式总结

模式做法适用场景
并行侦察同时 spawn 多个 explorer多个独立的代码库问题
分块执行spawn 多个 worker，各管一块文件大重构拆分
复用上下文send_input 给已有 Agent（V1；V2 对应 send_message）依赖前序上下文的后续任务
fork 探索fork 出继承父状态的子 Agent（V1 fork_context；V2 fork_turns 可选 none / all / 最近 N 轮）在当前理解上多向探索
Agent 间通信send_inter_agent_communication（AgentControl 内部通道）；或消息板 post（11.7，默认关闭）worker 间直接交接结果
打断重定向send_input(interrupt=true)（V1；V2 对应 interrupt_agent）子 Agent 走偏时纠偏

11.9小结与对自研的启示

自研 checklist 多 Agent 同时放大能力和成本、复杂度，别过早引入。① 先单 Agent 跑通，确认一个 Agent 的 turn 循环、工具、上下文都稳定，再谈派生。② 子 Agent 是完整线程而非函数——它有自己的会话和上下文，继承父权限，这比「调一个子函数」重得多，要权衡 token 成本。③ 必须有递归护栏——派生深度 + 并发上限双重限制，否则一个失控的 Agent 就能层层派生、耗尽资源。④ 角色即配置覆盖——用角色预设（explorer/worker）约束子 Agent 的能力和行为，而非让它和父一样全能。⑤ 要求模型按策略分派——把协作策略写进角色描述（并行、复用、所有权），模型不会自己学会高效分派。⑥ 权限只降不升——子 Agent 绝不能突破父的权限边界，这是安全红线。
要点 Codex 的多 Agent 设计：「完整子线程 + 角色约束 + 递归护栏」。每个子 Agent 是一个继承父权限的独立 CodexThread，靠 spawn 深度与并发上限兜底，靠角色预设让分派有章法。它把单 Agent 的能力扩展为团队协作。
