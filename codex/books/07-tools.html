★ 工具系统：模型能做什么，怎么做

工具是 Agent 的手。Codex 用 ToolExecutor trait 定义工具的运行时契约，用 ToolSpec 描述给模型的 JSON schema，用注册表统一调度内置工具与 MCP 工具。本章拆开工具抽象、内置工具清单、从分发到执行的全生命周期，以及 apply_patch 的自由格式语法。
核心洞见 工具 = 给模型的规格 + 给内核的执行器 → 一个工具有两面：spec() 告诉模型「我叫什么、参数是什么」（JSON schema），handle() 告诉内核「收到调用后怎么执行」。两面由 ToolExecutor trait 绑在一起。

7.1ToolExecutor：工具的运行时契约

工具抽象住在独立的 codex-tools crate（不依赖 core），这样它可以被多处复用。核心是 ToolExecutor trait：

codex-rs/tools/src/tool_executor.rs:106 — ToolExecutor trait
rust/// 模型可见工具的共享运行时契约。
/// ///
/// 实现者把模型可见的 spec 与可执行运行时绑定在一起。
/// 宿主 crate 可在之上叠加路由、hook、遥测等编排，而无需重开 spec/runtime 拆分。
pub trait ToolExecutor<Invocation>: Send + Sync {
    /// 此运行时实例处理的具体工具名。
    fn tool_name(&self) -> ToolName;

    /// 给模型的规格（JSON schema）
    fn spec(&self) -> ToolSpec;

    /// 宿主应用 step 级策略前的首选暴露方式。
    fn exposure(&self) -> ToolExposure { ToolExposure::Direct }

    fn search_info(&self) -> Option<ToolSearchInfo> { ... }

    /// 是否支持并行工具调用
    fn supports_parallel_tool_calls(&self) -> bool { false }

    /// ★ 收到调用后怎么执行
    fn handle(&self, invocation: Invocation) -> ToolExecutorFuture<'_>;
}
读懂这段： ToolExecutor 是泛型 <Invocation>——不同工具的调用参数类型可以不同（内置工具用一种、扩展工具用 ExtensionToolCall）。三个关键方法：tool_name() 报名号、spec() 给模型看规格、handle() 执行。exposure() 决定工具是「直接可见」还是「需搜索发现」（配合 tool_search，见第 10 章）。supports_parallel_tool_calls 默认 false——shell 这类有副作用的工具不并行。

7.2ToolSpec：给模型看的规格

ToolSpec 是工具的「对外简历」，序列化后就是 OpenAI Responses API 的 Tool JSON：

codex-rs/tools/src/tool_spec.rs — ToolSpec 枚举
rust/// 序列化为 JSON 时，产生一个合法的 OpenAI Responses API "Tool"。
#[derive(Debug, Clone, Serialize, PartialEq)]
#[serde(tag = "type")]
pub enum ToolSpec {
    Function(ResponsesApiTool),         // 普通函数工具（JSON 参数）
    Namespace(ResponsesApiNamespace),   // 命名空间工具（一组工具）
    ToolSearch { execution, description, parameters }, // 工具搜索
    WebSearch { ... },                  // 内置网页搜索
    Freeform(FreeformTool),             // ★ 自由格式工具（非 JSON）
}
读懂这段： 大多数工具是 Function（参数是 JSON）。但 apply_patch 用 Freeform——参数不是 JSON 而是一段自定义语法的文本（见 7.5）。Namespace 把一组相关工具打包成一个命名空间。WebSearch 是 OpenAI 内置的网页搜索能力。这套枚举覆盖了 Responses API 支持的所有工具形态。

读懂这张表： 注意工具名以源码 TOOL_NAME 常量为准，而非文件名——current_time.rs 内部的 TOOL_NAME = "curr_time"，plan.rs 的工具名是 update_plan。唯一的 shell 执行工具是 exec_command：它的 spec 定义在 shell_spec.rs（create_exec_command_tool_with_environment_id），handler 在 unified_exec/exec_command.rs，参数结构 ExecCommandArgs 见 7.8（注意 spec 文件名 shell_spec.rs 容易误导，但它定义的工具名就是 exec_command）。MCP 工具并非固定名 mcp，而是按 mcp__<server>__<tool> 动态生成的命名空间工具（7.10 详述）。多 Agent 也不再是单一 multi_agents 工具，而是一个命名空间下的 spawn_agent/send_input/wait_agent/list_agents/close_agent。

7.4exec_command 工具：参数与控制

exec_command 是最高频的工具（唯一的 shell 执行工具）。它的参数 schema 揭示了 Codex 对命令执行的精细控制：

codex-rs/core/src/tools/handlers/shell_spec.rs — exec_command 工具参数
rustlet mut properties = BTreeMap::from([
    ("cmd", JsonSchema::string(Some("Shell command to execute.".into()))),
    ("workdir", JsonSchema::string(Some(
        "Working directory for the command. Defaults to the turn cwd.".into()))),
    ("tty", JsonSchema::boolean(Some(
        "True allocates a PTY; false or omitted uses plain pipes.".into()))),
    ("yield_time_ms", JsonSchema::number(Some(
        "Wait before yielding output. Defaults to 10000 ms.".into()))),
    ("max_output_tokens", JsonSchema::number(Some(
        "Output token budget. Defaults to 10000 tokens.".into()))),
    // ... 可能还有 environment_id 等
]);
读懂这段： 四个控制点：① workdir 控制工作目录（默认 turn cwd）；② tty 决定是否分配伪终端（交互式命令需要）；③ yield_time_ms 是「长命令」的关键——命令跑超过这个时间不阻塞，先返回一个 session id 让模型继续，输出后续可拉取；④ max_output_tokens 限制输出 token，配合第 5 章的截断。这些参数让 exec_command 既能跑短命令，也能管理长进程。

7.5apply_patch：自由格式的文件编辑

apply_patch 是 Codex 编辑文件的核心工具。它不是普通 JSON 函数工具，而是 Freeform 自由格式工具——参数是一段基于 lark 语法定义的 patch 文本：

codex-rs/core/src/tools/handlers/apply_patch_spec.rs — apply_patch 工具定义
rust/// 返回一个可用于编辑文件的工具。适合 GPT-5 模型。
pub fn create_apply_patch_freeform_tool(...) -> ToolSpec {
    ToolSpec::Freeform(FreeformTool {
        name: "apply_patch".to_string(),
        description: "The `apply_patch` tool can be used to edit files. 
            This is a FREEFORM tool, so do not wrap the patch in JSON.".to_string(),
        format: FreeformToolFormat {
            r#type: "grammar".to_string(),
            syntax: "lark".to_string(),
            definition,   // APPLY_PATCH_LARK_GRAMMAR（include_str! 读入）
        },
    })
}
codex-rs/core/src/tools/handlers/apply_patch.lark — patch 语法
larkstart: begin_patch hunk+ end_patch
begin_patch: "*** Begin Patch" LF
end_patch:   "*** End Patch" LF?

hunk: add_hunk | delete_hunk | update_hunk
add_hunk:    "*** Add File: " filename LF add_line+
delete_hunk: "*** Delete File: " filename LF
update_hunk: "*** Update File: " filename LF change_move? change?

change: (change_context | change_line)+ eof_line?
change_context: ("@@" | "@@ " /(.+)/) LF
change_line: ("+" | "-" | " ") /(.*)/ LF
eof_line: "*** End of File" LF
读懂这段： apply_patch 用一种类似 unified diff 但更简洁的格式：每个 patch 以 *** Begin Patch 开头、*** End Patch 结尾，内含若干 hunk。hunk 有三种：Add File（新增）、Delete File（删除）、Update File（修改）。Update 用 @@ 标上下文锚点，+/-/ （空格）表示增/删/保留行。选 Freeform 而非 JSON，是因为 patch 文本里的换行/特殊字符在 JSON 里要转义，徒增模型出错率——直接用语法格式更可靠。
设计 include_str!("apply_patch.lark") 把语法文件在编译期嵌入二进制——无需运行时读盘。这种「工具的参数语法本身也是数据」的设计，让模型生成的 patch 可被 lark 解析器严格校验。

7.7并行工具调用

第 5 章看到 build_prompt 设了 parallel_tool_calls: true——Codex 允许模型一次请求多个工具。这些工具的并行执行由 tools/parallel.rs 和 orchestrator 协调：

  • 模型在一个回包里发出多个 FunctionCall。
  • orchestrator 检查每个工具的 supports_parallel_tool_calls()——只对支持并行的工具并行执行。
  • 有副作用或状态依赖的工具默认不并行，串行执行避免竞态。
  • 每个工具独立产出 FunctionCallOutput，全部完成后一起回填历史。
codex-rs/core/src/tools/parallel.rs:113 — 并行执行门
rustlet supports_parallel = router.tool_supports_parallel(&call);
// ...
let _guard = if supports_parallel {
    Either::Left(lock.read().await)    // 支持并行 → 读锁（多个可同时持有）
} else {
    Either::Right(lock.write().await)  // 不支持并行 → 写锁（独占）
};
注意 并行的边界是每个工具自己的 supports_parallel_tool_calls() 实现，而非运行时去检测「两个工具是否改同一文件」。机制很简洁：一个 tokio::sync::RwLock<()> 充当执行门——声明支持并行的工具拿读锁（多个可同时持有，真正并发），不支持的拿写锁（独占串行）。supports_parallel_tool_calls() 默认返回 false；exec_command、view_image、tool_search 等覆盖为 true。换句话说，是否并行由工具实现者静态声明，不靠运行时冲突检测。

7.8unified_exec 模块：shell 与文件操作的融合

unified_exec 是一个模块（handlers/unified_exec/），它把 shell 执行与文件操作统一到一个入口。注意：模块名是 unified_exec，但对模型暴露的工具名是 exec_command（ToolName::plain("exec_command")）。它的参数结构 ExecCommandArgs 定义在 handlers/unified_exec.rs：

codex-rs/core/src/tools/handlers/unified_exec.rs — ExecCommandArgs
rust#[derive(Debug, Deserialize)]
pub(crate) struct ExecCommandArgs {
    pub(crate) cmd: String,
    shell: Option<String>,        // 指定 shell
    login: Option<bool>,          // 登录 shell
    tty: bool,                     // PTY
    yield_time_ms: u64,            // 长命令让出
    max_output_tokens: Option<usize>,
    // ...
}

exec_command 与 code-mode（code-mode crate）配合，提供一个更结构化的执行环境——模型可以在一个持久 shell 会话里连续操作，而非每次都起新进程。它由 code_mode_runtime 支撑，是 Codex 向「长时编码会话」演进的方向。注意 §7.7 提到 exec_command 覆盖了 supports_parallel_tool_calls() 为 true——它拿读锁、可并行执行；而 supports_parallel_tool_calls() 默认返回 false（写锁、串行），大多数工具都走默认，这正是 exec_command 的特别之处。

7.9小结与对自研的启示

要点 Codex 工具系统的三个关键设计：① spec/runtime 双面体（ToolSpec 给模型看，ToolExecutor 给内核跑，一个 trait 绑定）；② 注册表 + 路由（ToolRegistry 注册，ToolRouter 按名路由，内置与 MCP 工具走同一套）；③ Freeform 工具（对 patch 这类非 JSON 友好的参数，用语法格式而非 JSON，降低模型出错率）。
自研 checklist 最小工具系统：定义一个 Tool trait（name() / schema() / run(args)），注册到 HashMap。先做两个工具：run_command（执行 shell）和 edit_file（改文件）。schema 用 JSON Schema 描述参数。先别管并行和 Freeform——等基础跑通再加。务必让工具的输出可截断，否则一个 cat 大文件就炸上下文。
