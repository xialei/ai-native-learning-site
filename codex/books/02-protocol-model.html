消息与协议模型：会话长什么样，内核与前端怎么对话

Codex 用三套类型把「会话」和「通信」讲清楚：ResponseItem 是会话里的每一条记录，Op 是前端发给内核的指令，EventMsg 是内核回给前端的事件。理解这三者，就拿到了读懂整个代码库的钥匙。

2.1三套类型，一张图看清

图 2.1：前端与内核通过 Op/Event 双向通信；会话本身是一串 ResponseItem。

一句话总结：Op 是「请做这件事」，Event 是「发生了这件事」，ResponseItem 是「会话里记下了这件事」。 三者共同构成了 Codex 的全部通信语义。

2.2ResponseItem：会话的最小单位

会话在 Codex 里不是一个字符串，而是一个 ResponseItem 列表。每个变体代表会话里的一种「记录」。这是整个协议里最重要的类型：

codex-rs/protocol/src/models.rs:950 — ResponseItem 枚举（节选）
rust#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, JsonSchema, TS)]
#[serde(tag = "type", rename_all = "snake_case")]
pub enum ResponseItem {
    Message {                         // 一条普通消息（user/assistant/...）
        id: Option<ResponseItemId>,
        role: String,                 // "user" | "assistant" | "developer" | "system"
        content: Vec<ContentItem>,
        phase: Option<MessagePhase>,  // "commentary" | "final_answer"
    },
    Reasoning {                       // 模型的推理过程（chain-of-thought）
        id: Option<ResponseItemId>,
        summary: Vec<ReasoningItemReasoningSummary>,
        content: Option<Vec<ReasoningItemContent>>,
        encrypted_content: Option<String>,
    },
    FunctionCall {                    // 模型请求调用一个工具
        id: Option<ResponseItemId>,
        name: String,                 // 工具名，如 "shell"
        namespace: Option<String>,
        arguments: String,            // JSON 字符串（注意：是字符串，不是对象）
        call_id: String,
    },
    FunctionCallOutput {              // 工具执行结果，回填给模型
        id: Option<ResponseItemId>,
        call_id: Option<String>,     // 对应上面的 FunctionCall
        name: Option<String>,
        output: FunctionCallOutputPayload,
    },
    LocalShellCall { ... },           // 旧版 shell 调用（带 action/status）
    CustomToolCall { ... },           // 自由格式工具调用
    AgentMessage { ... },             // 多 Agent 间消息
    ToolSearchOutput { ... },         // tool_search 的结果
    // ... 还有 AdditionalTools / CustomToolCallOutput 等
}
读懂这段： 三个最核心的变体是 Message（谁说了什么）、FunctionCall（模型要调工具）和 FunctionCallOutput（工具结果回填）。一个 turn 的典型会话片段就是：Message(user) → Reasoning → FunctionCall → FunctionCallOutput → Message(assistant)。注意 arguments 是 字符串而非已解析的 JSON——这是为了对齐 OpenAI Responses API 的线格式，由 Session::handle_function_call 在执行前才解析。
设计要点 ResponseItem 用 #[serde(tag = "type")] 做内部标签枚举——序列化时每个 item 自带 "type": "message" / "function_call" 等字段。这让 rollout 文件（JSONL）每行自描述，回放时无需上下文即可判别类型。

2.3Op：前端发给内核的指令

Op 是前端向内核发出的请求。它是一个 #[non_exhaustive] 枚举，意味着可以持续扩展而不破坏下游。核心变体：

codex-rs/protocol/src/protocol.rs:545 — Op 枚举（节选）
rust#[derive(Debug)]
#[non_exhaustive]
pub enum Op {
    /// 中断当前任务（不杀后台终端进程）
    Interrupt,

    /// 提交一轮 turn 输入（核心入口）
    TurnInput {
        request: Box<TurnInputRequest>,
        mode: TurnInputMode,                       // StartOrSteer / StartIfIdle / Steer
        reply: oneshot::Sender<CodexResult<TurnInputSubmission>>,
    },

    /// 恢复一个被中断的 turn
    RecoverTurn { thread_settings: ThreadSettingsOverrides, reply: ... },

    /// 审批一个命令执行
    ExecApproval { id: String, turn_id: Option<String>, decision: ReviewDecision },

    /// 审批一个代码补丁
    PatchApproval { id: String, decision: ReviewDecision },

    /// 应用线程设置覆盖（不启动 turn）
    ThreadSettings { thread_settings: ThreadSettingsOverrides },

    /// 多 Agent 间通信
    InterAgentCommunication { communication: InterAgentCommunication },

    /// 重载用户配置（不重启线程）
    ReloadUserConfig,

    // ... 还有 RealtimeConversation* / ResolveElicitation / RefreshMcpServers 等
}
读懂这段： 注意 TurnInput 变体里带了一个 reply: oneshot::Sender——这是 请求-响应模式：前端提交 turn 时拿到一个 oneshot 通道，内核处理完（或出错）后通过它回送结果。而 Interrupt 这种没有 reply，是纯信号。mode: TurnInputMode 区分了三种提交方式：StartOrSteer（空闲则开新 turn，否则插话当前 turn）、StartIfIdle（仅空闲时开新 turn）、Steer { expected_turn_id }（仅当指定 turn 活跃时插话），第 3 章会展开。

2.4Event / EventMsg：内核回给前端的事件

内核的回应包在 Event 里，它关联了 submission id，方便前端把事件与请求对应：

codex-rs/protocol/src/protocol.rs:1278 — Event 结构
rustpub struct Event {
    /// 这个事件关联的 submission id
    pub id: String,
    /// 载荷
    pub msg: EventMsg,
}

真正的内容在 EventMsg 枚举里。它有几十个变体，覆盖了 turn 生命周期的每个阶段：

codex-rs/protocol/src/protocol.rs:1296 — EventMsg 枚举（节选）
rust#[serde(tag = "type", rename_all = "snake_case")]
pub enum EventMsg {
    Error(ErrorEvent),                         // 执行 submission 时出错
    Warning(WarningEvent),                     // 警告（turn 继续，但要通知用户）

    /// Agent 开始一个 turn（v1 线格式叫 task_started）
    #[serde(rename = "task_started", alias = "turn_started")]
    TurnStarted(TurnStartedEvent),

    /// Agent 完成所有动作（v1 叫 task_complete）
    #[serde(rename = "task_complete", alias = "turn_complete")]
    TurnComplete(TurnCompleteEvent),

    AgentMessage(AgentMessageEvent),           // Agent 的文本输出
    UserMessage(UserMessageEvent),             // 发给模型的消息
    AgentReasoning(AgentReasoningEvent),       // 推理事件
    AgentReasoningRawContent(...),             // 原始 chain-of-thought

    TokenCount(TokenCountEvent),               // token 用量更新
    ContextCompacted(ContextCompactedEvent),   // 会话被压缩
    ThreadRolledBack(ThreadRolledBackEvent),   // 会话回滚
    SessionConfigured(SessionConfiguredEvent), // 配置已应用
    // ... 还有 EnvironmentConnected / RealtimeConversation* / 等
}
读懂这段： 一个 turn 的典型事件序列是：TurnStarted → (AgentReasoning... → AgentMessage... → 工具事件...) → TurnComplete。所有事件都关联 id（submission id），前端可以安全地并发处理多个 turn 的事件而不串台。注意 #[serde(rename = "task_started", alias = "turn_started")]——这是为了同时兼容 v1/v2 线格式。
流式 AgentMessage / AgentReasoning 在流式输出时会多次发射（增量 delta），不是一次性给完整文本。TUI 收到后做增量渲染。这奠定了第 3 章「流式采样」的事件基础。

2.6小结与对自研的启示

要点 Codex 的协议设计有三个值得抄的点：① 把会话建模成结构化 item 列表，而非裸字符串（每个 item 自带 type 标签，可序列化、可回放）；② 请求-响应用 oneshot 通道关联（Op 带 reply，Event 带 id），并发安全；③ 类型独立成 crate，内核与前端编译期对齐，杜绝手写 schema 漂移。
自研 checklist 最小协议只需定义：一个 Message item、一个 ToolCall item、一个 ToolResult item；一个 Submit Op；TurnStarted / TokenDelta / TurnComplete 三个 Event。这够跑起一个 MVP。
