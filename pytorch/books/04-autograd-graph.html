autograd 计算图：反向代码是什么时候写的

PyTorch 没有单独的「建模阶段」——前向跑的时候，反向的执行计划就同步记好了。这章看这个记录过程的三个部件：节点（Node）、边（Edge）、终止符（AccumulateGrad），以及那份 696 条规则的反向公式表 derivatives.yaml。

4.1反向代码的来源：derivatives.yaml

先回答最根本的问题：x + y 的梯度公式是谁写的？答案不是 C++ 代码，而是一份声明式文件。翻开 tools/autograd/derivatives.yaml，加法的规则长这样：

tools/autograd/derivatives.yaml — add 的反向规则（原文摘录）
yaml- name: add.Tensor(Tensor self, Tensor other, *, Scalar alpha=1) -> Tensor
  self: handle_r_to_c(self.scalar_type(), grad)
  other: handle_r_to_c(other.scalar_type(), maybe_multiply(grad, alpha.conj()))
  result: self_t + maybe_multiply(other_t, alpha)

格式直白：算子签名做键，每个输入一条反向表达式。self 的梯度就是 grad 原样传回，other 的梯度乘上 alpha。构建时（tools/autograd/gen_autograd.py 读这份文件），代码生成器把这 696 条规则展开成 696 组 C++ 反向函数，再由第 3 章的机制注册到 Autograd key 的格子里。你调用 loss.backward() 时跑的「反向代码」，源头是这份 YAML，不是任何人手写的函数。

为什么值得强调「生成」二字：读源码时搜 class AddBackward 是搜不到的——它叫 AddBackward0，住在 build 目录里，构建后才有。想知道某个算子反向长什么样，正确动作是查 derivatives.yaml 而不是猜源码文件。附带的收获是反向规则可以直接当文档读：比如 addmm 的三条梯度公式（self / mat1 / mat2 各一条，derivatives.yaml）就摊在那里，比任何教材都准确。

也有些算子的反向规则栏是空的——那不是遗漏，是声明「此 op 不可微」或「梯度就是 grad 本身不需要额外逻辑」。696 这个数字相对于 2590 个算子的差额，一部分就在这里。

4.2Node 与 Edge：图的最小单元

前向每执行一个可导算子，autograd kernel（第 3 章那格）就做三件事：保存输入的引用、根据 derivatives.yaml 的规则确定反向函数、把一个 Node 对象连进图。Node 是所有反向函数的基类：

torch/csrc/autograd/node.h — Node 构造（摘录，注释为译注）
cppstruct TORCH_API Node : c10::intrusive_ptr_target {
 public:
  /// Construct a new `Node` with the given `next_edges`
  explicit Node(uint64_t sequence_nr, edge_list&& next_edges = edge_list())
      : sequence_nr_(sequence_nr), next_edges_(std::move(next_edges)) {
    for (const Edge& edge : next_edges_) {
      update_topological_nr(edge);
    }

    if (AnomalyMode::is_enabled()) {
      metadata()->store_stack();

      // If anomaly mode is enabled and graph is constructed, then assign the
      // currently evaluating node as the parent of this node.
      // A parent is a Node where this Node is created.
      // We are tracking the parents to track multiple backward operations.
      assign_parent();
    }

三个成员撑起整个图结构：next_edges_（指向下游节点的边列表）、input_metadata_（各输入的形状/dtype，反向时要用）、sequence_nr_（全局递增序号，标记节点创建顺序，异常检测时用来判断「图是不是被 backward 多次」）。每个具体算子的反向——AddBackward0、MulBackward0、MmBackward0——都是 Node 的子类，各自的 apply 里是生成的梯度公式。

Edge 更简单，简单到值得把整个定义看完：

torch/csrc/autograd/edge.h — Edge 定义核心（摘录，注释为译注）
cppstruct Edge {
  Edge() noexcept : function(nullptr), input_nr(0) {}

  Edge(c10::intrusive_ptr<Node> function_, uint32_t input_nr_) noexcept
      : function(std::move(function_)), input_nr(input_nr_) {}

  // （相等比较、is_valid 等辅助方法省略）

  /// The function this `Edge` points to.
  c10::intrusive_ptr<Node> function;

  /// The identifier of a particular input to the function.
  uint32_t input_nr;
};

两个成员：下游节点是谁（function）、梯度该塞进它的第几个输入（input_nr）。第二个字段平时被忽略，但它解决的问题很实际——反向函数的多个输入（比如矩阵乘的 mat1、mat2）要各自收到正确的梯度，没有 input_nr 就得靠顺序猜。整张 autograd 图，物理形态就是 Node 持有一组 Edge，没有更多结构。

4.3grad_fn 与 AutogradMeta：tensor 怎么记住图

tensor 需要一个字段指向「生成我的那个 Node」——这就是 x.grad_fn。它住在 AutogradMeta 里，第 2 章没展开的那块：

torch/csrc/autograd/variable.h — AutogradMeta 字段（摘录，注释为译注）
cppstruct TORCH_API AutogradMeta : public c10::AutogradMetaInterface {
  std::string name_;

  Variable grad_;
  c10::intrusive_ptr<Node> grad_fn_;
  c10::weak_intrusive_ptr<Node> grad_accumulator_;

四个字段，两个指针类型值得盯住。grad_fn_ 是 intrusive_ptr（强引用）：只要中间结果活着，生成它的 Node 就活着。grad_accumulator_ 却是 weak_intrusive_ptr（弱引用）——它指向叶子参数的 AccumulateGrad。方向不对称的原因到第 5 章讲引擎时才完全展开，这里先给一句：参数的生命周期由用户代码管理（它要活过整个训练），图节点不该反过来攥着参数不放；而中间结果的生命周期就该由图接管，backward 完一起释放。

AutogradMeta 是懒分配的：不需要梯度的 tensor（绝大多数推理张量、常量、输入数据）身上这块内存压根不存在。头文件注释原话：「a Variable may store a nullptr, in lieu of a default constructed AutogradMeta」。这也解释了为什么 requires_grad 检查便宜到可以作为热路径分支。

4.4AccumulateGrad：叶子节点与 .grad 的写入点

图走到叶子（也就是参数）时需要终点。参数没有下游可传，它的「下游」就是 param.grad 这个字段本身。承担这个角色的是 AccumulateGrad：

torch/csrc/autograd/functions/accumulate_grad.h — AccumulateGrad（摘录，注释为译注）
cppstruct TORCH_API AccumulateGrad : public Node {
  explicit AccumulateGrad(Variable variable_);

  variable_list apply(variable_list&& grads) override;

  void release_resources() override {
    variable.reset();
    Node::release_resources();
  }

它的 apply 只干一件事：把收到的梯度累进 variable.grad_（累，是因为一个参数可能被多条路径使用，梯度要按路径求和——这才是 accumulate 这个名字的完整含义）。累加时还有一份 Gradient Layout Contract：尽量让 .grad 的内存布局（strides）与参数本身一致，优化器 kernel 和分布式梯度规约才能按最预期的路径走。平时感知不到它，一旦和某些自定义算子的输出布局对不上，最先出问题的就是这一层。

关联 第 6 章 optimizer.zero_grad() 清的正是这里写进去的 .grad。为什么默认要手动清零而不是每步自动覆盖：梯度累积（gradient accumulation）——显存放不下大 batch 时，把几个小 batch 的梯度攒起来再更新——依赖「不清零就继续加」的语义。AccumulateGrad 的「累」字，一半是设计，一半是给这个用法留的。

4.5图长什么样：一次真实前向的记录

把上面三个部件拼起来，跑一个最小前向，看图的实际形状：

中间算子的反向节点 叶子参数的终点节点
图 4.2：y = (x @ w + b).relu() 记下的图。前向是自左向右求值，图里箭头自右向左——backward 的执行顺序。y 的 grad_fn 指向 ReluBackward0，每个中间节点再通过 next_edges 指向更早的节点；三个参数各自的 AccumulateGrad 是终点。真实模型无非是这张小图的几十层重复。

两个常见的困惑在这张图上各有一句话的解释。其一，「为什么 loss 是标量也能 backward」：引擎从 y 的 grad_fn 出发沿边倒推，每个节点只关心「下游给我的梯度」和「我该给上游什么」，标量输出只是让整张图恰好只有一个起点。其二，「detach 后为什么还能继续前向但不回传」：detach 生成了没有 grad_fn 的新 TensorImpl（第 2 章那张表），对引擎来说它就是又一片叶子——叶子不需要反向函数，也就没有边指回来。

4.6三个控图开关的成本账

requires_grad、no_grad、detach 都动图，但动的位置不同，成本结构也不同。训练代码的显存问题大半出在这三者的搭配上：

开关动作省了什么代价
requires_grad=Falsetensor 出生就不带 AutogradMeta记图开销 + 保存中间结果这块输入永远不回传梯度
no_grad()GradMode 关闭，autograd key 直接放行同上，但对一段代码批量生效区域内算的任何东西都不能 backward
detach()浅拷贝，切断历史下游不再持有上游的引用链数据仍共享（第 2 章），原地改有风险

值得专门说的是 no_grad 的真实成本结构。它不是「让计算变慢一点的小税」，而是省去了保存中间结果的大头——推理时显存占用骤降，主要就是不再为反向存 activation。反过来，训练循环里手滑把前向包进 no_grad，症状不是报错，而是 backward() 时一句 "element 0 of tensors does not require grad and does not have a grad_fn"——图根本没记。调试这类问题时先查这个。

要点 前向记图的全部产出是：每个中间 tensor 一个 grad_fn 指针 + 每个节点一组 next_edges。反向所需的「程序」在图里，「数据」（保存的输入输出）也在图里。下一章的引擎拿到的就是这份完整材料，它的任务是调度——让这几百个 Node 在多线程下按依赖关系正确执行。
