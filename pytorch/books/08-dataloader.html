DataLoader：GPU 等数据的账，多进程怎么还

训练慢的常见原因排第一的是数据供给。DataLoader 的多进程机制不复杂——worker 进程、几条队列、一个 pin 内存线程——但「为什么乱序不会发生」「为什么 num_workers 设错反而更慢」「shutdown 为什么慢」这三个问题的答案都在源码里。

8.1一笔账：不预取时 GPU 在干什么

设一个 batch 的 GPU 计算是 100ms，数据准备（读图、解码、增广、拼接）也是 100ms。单进程同步加载的循环是：CPU 备数据 100ms → GPU 算 100ms → CPU 备下一份……GPU 一半时间在空转。DataLoader 的多进程 + 预取把这两段流水化：worker 进程提前备好若干 batch，主进程取的时候数据是现成的，理想情况 GPU 利用率翻倍。预取量就是 prefetch_factor × num_workers 个 batch（默认 factor=2）。

这个账同时给出了 num_workers 的调法：它决定的是「并行备数据的深度」，不是「数据准备的总速度」。数据准备本身是 CPU 密集的，worker 太多在 CPU 核数少的机器上互相争抢，反而拉长每个 batch 的就绪时间——「设错反而慢」的机制原因。

8.3乱序怎么办：主进程怎么保证顺序

worker 各自独立干活，谁先完成看运气，但训练必须按原 dataset 顺序消费（shuffle 的随机性在「发索引前」已经定了，worker 不能再改顺序）。解决方式是把「乱序生产」和「有序消费」拆开：派发的每个任务自带一个递增序号（_send_idx），worker 结果连同序号一起回来；主进程的 _next_data（dataloader.py）维护两个指针——_send_idx（下一个要派发的序号）和 _rcvd_idx（下一个要交付的序号）。先到的结果若序号不等于 _rcvd_idx，就暂存在 _task_info 字典里（源码注释原话「store out-of-order samples」，dataloader.py）；等于时才真正交给训练循环。所以即使 worker 1 比 worker 0 先完成，训练循环拿到的「第 k 个 batch」确实就是第 k 个。（构造参数里还有个 in_order=False会把这套等待关掉，换吞吐、牺牲顺序，docstring 明说可能影响可复现性。）

这条机制直接解释了一个高频问题：多 worker 时如何保证随机种子一致。worker 进程是 fork/spawn 出来的，随机状态若不处理，每个 worker 的增广序列会相同或错乱。DataLoader 的做法：迭代器启动时从 loader 的 generator 抽一个 base_seed，连同 worker_id 传进 _worker_loop；worker 侧（_utils/worker.py）执行 seed = base_seed + worker_id，给 random、torch、numpy 各设一份独立种子。「每个 epoch 换一次种子」靠的是每次新建迭代器时 base_seed 重新随机。用户侧的怪现象——「num_workers>0 时增广结果和单进程不一样」——九成是自己的 dataset 在 __getitem__ 里用了全局随机源而不是 per-worker 生成器。

为什么会乱序在先：预取意味着「还没被消费的 batch 已在半路」。迭代器按 prefetch_factor × num_workers 控制在途任务量上限（_try_put_index，dataloader.py），完成顺序天然不确定。乱序不是缺陷而是并行的必然结果，消费端的「按序号暂存重排」才是设计。理解这一点后，「DataLoader 输出顺序错乱」类 bug 的排查方向就清楚了：先看是不是自定义 sampler 或 collate 打破了序号契约。

8.4关停为什么慢：shutdown 的设计

训练结束或中断时，DataLoader 的收尾常被抱怨「卡几秒」。这不是意外，是刻意设计——dataloader.py 里有一大段 NOTE [ Data Loader Multiprocessing Shutdown Logic ]专门讲进程关停的取舍，核心约束抄一句：

torch/utils/data/dataloader.py — shutdown 的首要目标（原文摘录）
python#   1. The iterator gracefully exits the workers when its last reference is
#      gone or it is depleted.
#
#      In this case, the workers should be gracefully exited because the
#      main process may still need to continue to run, and we want cleaning
#      up code in the workers to be executed (e.g., releasing GPU memory).
#      Naturally, we implement the shutdown logic in `__del__` of
#      DataLoaderIterator.

「优雅退出」意味着 worker 里的清理代码（释放 CUDA 上下文、关文件句柄）必须跑完；实现放在迭代器的 __del__ 里，靠引用计数触发。三个后果：训练循环里 epoch 之间不重建迭代器能省下这收尾（值得做）；强制 kill 会有僵尸 worker 风险（队列里的半成品）；调试时卡在收尾，先看是不是某个 worker 卡在 I/O 上等主进程收尸。

要点 DataLoader 一章的三个落点：多进程买的是「数据准备与 GPU 计算重叠」，num_workers 是预取深度不是吞吐；乱序靠序号契约在消费端重排，随机行为要靠 per-worker 种子治理；shutdown 的慢是「优雅退出」的代价，epoch 间复用迭代器可以绕开。
