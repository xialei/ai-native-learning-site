整体架构：import torch 之后，你拿到的是什么

每天敲 import torch，几秒后拿到一个会算梯度、能上 GPU 的库。这章拆开这几秒：Python 层加载了什么、真正的本体住在哪、torch / ATen / c10 三个目录怎么分工，以及为什么一个库要养出 1500 万行 C++。

1.1先说结论：Python 只是前厅

torch/__init__.py 有 3588 行，但它不是 PyTorch 的本体。本体是编译产物 torch._C——一个几十 MB 的 C++ 扩展模块，里面装着 tensor、算子、自动求导引擎的全部实现。__init__.py 干的核心事情只有一件：把这个扩展整个导进来，再往上面包一层 Python 皮。

torch/__init__.py — import 时的加载路径（摘录，注释为译注）
python    old_flags = sys.getdlopenflags()
    sys.setdlopenflags(os.RTLD_GLOBAL | os.RTLD_LAZY)

    from torch._C import *  # noqa: F403

    sys.setdlopenflags(old_flags)
    del old_flags

else:
    # Easy way.  You want this most of the time, because it will prevent
    # C++ symbols from libtorch clobbering C++ symbols from other

from torch._C import * 之后，你的 Python 进程里多出了几千个 C 函数和 C++ 类的绑定。torch.add、torch.Tensor、torch.nn.functional.linear 之下的实现，全在这个命名空间里。Python 文件后来做的都是包装：torch/nn/ 在 Module 上加注册树和 hook，torch/optim/ 在 C++ 更新算子外加参数分组，torch/autograd/ 给 backward() 递参数。层数不深，但每层都有存在理由，后面各章挨个进。

为什么加载要动 dlopen flags：torch 的 C++ 扩展依赖一堆第三方库（MKL、libstdc++……）。RTLD_GLOBAL 分支把这些符号提前以全局可见的方式装好，否则某些环境下 MKL 链接不上或出现重复加载。注释里两次提到 mysterious segfaults——这是加载顺序问题的典型症状，官方把两种模式都留着，默认走安全的那条。

1.2加载失败的报错，暴露了目录结构

如果扩展没编好，import torch 会先试着导入一个哨兵符号，失败后给出一段很具体的报错。这段报错值得整段抄下来，因为它顺手指出了 PyTorch 仓库的一个坑：

torch/__init__.py — 加载失败的引导（摘录）
python# Check to see if we can load C extensions, and if not provide some guidance
# on what the problem might be.
try:
    # _initExtension is chosen (arbitrarily) as a sentinel.
    from torch._C import _initExtension
except ImportError:
    import torch._C as _C_for_compiled_check

    if _C_for_compiled_check.__file__ is None:
        raise ImportError(
            textwrap.dedent(
                """
                Failed to load PyTorch C extensions:
                    It appears that PyTorch has loaded the `torch/_C` folder
                    of the PyTorch repository rather than the C extensions which
                    are expected in the `torch._C` namespace. ...
                """
            ).strip()
        ) from None
报错在防什么：torch 的源码目录里真有个 torch/_C/ 文件夹（存 C++ 辅助源码和声明）。如果你在仓库根目录下直接 import torch，Python 会把那个文件夹当成 torch._C 模块——一个没有 __file__ 的命名空间包，随后所有功能全部失灵。于是 __init__.py 特意检查 __file__ is None 来识别这种情形。读源码的第一课：别站在仓库根目录跑 Python。

1.3三层目录：c10、ATen、torch

进到 C++ 侧，仓库顶层两个目录撑起了全部核心代码，第三个 torch/csrc/ 是 Python 绑定层。它们是三层，不是三份平行代码——下层不知道上层存在，上层依赖下层。

核心机制（书的前五章） Python 可见面 支撑组件
图 1.3：三层 C++ 结构。c10 = core tensor library 的缩写，最底下、最薄、被所有人依赖；ATen = "A Tensor library"，算子全在这；torch/csrc 做的事只有一件——把 C++ 对象包成 Python 能摸的东西。依赖方向单一向上，所以读源码可以从 c10 开始一路向上，不会被反向依赖打断。

三层里最出人意料的是最底下那层有多小。c10 全目录不过几万行 C++，装的都是「tensor 是什么」这类定义；ATen 占大头，算子实现和调度机制全在这；torch/csrc 是粘合层，Python 看到的每一个类都是从这里 PyTypeObject 出来的。也就是说，整个 PyTorch 的「难」，集中在 ATen 这一层——而它恰恰是 Python 用户完全看不见的那层。

1.41500 万行代码，从哪读起

pytorch/pytorch 仓库现在约 1500 万行代码（含第三方与生成文件），核心目录大致 600 万行。听起来没法下手的体量，但有三个事实会大幅缩小实际需要读的范围。

第二，Python 层只有薄薄一层。所有 .py 加起来不到 C++ 的零头，而且大多是包装：真正的数学没有一个字节在 Python 里发生。

第三，目录就是依赖图。第 1.3 节那张图反过来就是阅读顺序——c10 的 tensor 定义（第 2 章）→ ATen 的 dispatch（第 3 章）→ torch/csrc 的绑定 → Python 侧的 nn/optim（第 6、7 章）。顺着依赖方向走，每一步都有前面打好的底。

1.5张量、算子、图：三个词的定义先立住

后面所有章节都建立在这三个概念上，先把它们用一句话立住，细节留到各章。

概念一句话定义细节在哪
Tensor（张量）一个多维数组，拆成三块存：元信息（TensorImpl）、数据（StorageImpl）、版本号（VariableVersion）第 2 章
op（算子）一个可调用的数学操作，声明在 native_functions.yaml，按 tensor 的能力标签分发到具体实现第 3 章
graph（计算图）前向执行时自动记录的「反向执行计划」，每个算子贡献一个节点第 4 章

有一个顺序值得强调：PyTorch 是「动态图」框架，这句话在源码里对应一个非常具体的动作——图不是先定义后执行，而是在算子执行的那一瞬间，由 dispatcher 顺手记录的。理解了这一点，「eager 模式」「define-by-run」这些词就都有了着落：第 3 章看 dispatch 怎么顺手挂上记录，第 4 章看记录下来的是什么，第 5 章看记录的东西怎么被多线程执行。

要点 import 只是把 C++ 扩展抬进 Python；之后你敲的每行张量代码都走同一条路——Python 绑定 → dispatcher → ATen kernel。第 2 章从这条路的尽头开始：tensor 本身长什么样。
