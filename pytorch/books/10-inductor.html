Inductor：图怎么变成 Triton kernel

Dynamo 交出前向图之后，编译管线还剩三站：AOTAutograd 把图拆成前向+反向（顺带决定哪些中间值留着、哪些重算），Inductor 的 Scheduler 把算子融合成大 kernel，最后生成 Triton 代码并 autotune。这章按执行顺序走一遍，重点讲两个决定性能的机制：min-cut 分区和算子融合。

10.1管线总览：compile_fx 的自述

整个管线的入口是 compile_fx（torch/_inductor/compile_fx.py），主函数 _compile_fx_main 的 docstring 就是最好的目录导览，原文照抄：

torch/_inductor/compile_fx.py — 管线步骤自述（原文摘录）
python    """
    Main part of compile_fx, called after wrapping is done.

    Roughly speaking, here the steps will be:
    (1) apply pre-grad passes
    (2) create `fw_compiler` and `bw_compiler` functions out of `inner_compile`
    (3) call aot_autograd, which:
    - (3a) creates a joint graph with `decompositions`,
    - (3b) partitions it with `partition_fn` into fw and bw graphs (applying joint-graph passes),
    - (3c) calls `fw_compiler` and `bw_compiler` on those graphs (applying post-grad passes)
    - (3d) finally, assembles the fw and bw compiled functions back together and returns.
    """

读法：先把前向图做一遍预处理（归并冗余、规范化），然后构造「前向编译器」和「反向编译器」两个回调，最后交给 AOTAutograd 去拆图——拆出来的两张图分别交给那两个回调（也就是 Inductor）编译，编完再拼回一个可调用的整体。docstring 里的 (3a)–(3d) 就是 AOTAutograd 内部的四步，10.2 讲其中的分区分步。下面的图把整条线画出来：

10.2min-cut 分区：保存还是重算

训练编译要回答一个 eager 模式不存在的问题：反向需要前向的中间值（比如 relu 的输出），编译后的前向是把它们全存下来（占显存），还是反向时重算（占算力）？答案因值而异，而「哪些存哪些算」的最优解是一个图论问题——在联合图上找最小割：

torch/_functorch/partitioners.py — min_cut_rematerialization_partition 签名与 docstring（摘录，省略号与注释为译注）
pythondef min_cut_rematerialization_partition(
    joint_module: fx.GraphModule,
    _joint_inputs: Any,
    compiler: str = "inductor",
    *,
    num_fwd_outputs: int,
    ...):
    """
    Partitions the joint graph such that the backward recomputes the forward.
    Recomputing helps in trading off memory bandwidth with computation.
    """

机制直说：把「前向计算代价」「显存保存代价」「重算代价」建模成图的边权，跑最小割算法，割线把节点分成「必须保存」和「反向重算」两堆。大矩阵乘这类重算代价高的留保存，逐元素小算子（relu、norm 的中间态）重算便宜就砍掉。docstring 里 "trading off memory bandwidth with computation" 说的就是这笔交换。eager 模式做不到这个粒度——它只有「全存」这一个选项（激活检查点 activation checkpointing 是手工版的粗粒度重算，第 13 章对照）。

一处演进痕迹：联合图的「反向公式」不是现成的反向图，而是把 04 章那套 derivatives.yaml 生成的规则应用到图上得到的大图——先合再拆，才有全局最优。「先联合后切分」是 AOTAutograd 区别于「前向反向分别编译」的关键一步。

10.3Scheduler：融合怎么发生

拿到前向（或反向）图后，Inductor 的第一件大事是排程。Scheduler（torch/_inductor/scheduler.py）把每个算子变成调度节点（SchedulerNode），分析它们对内存的读写依赖，把「读同一块缓冲、逐元素操作」的相邻节点合并成一个 FusedSchedulerNode——这就是融合。融合的收益链是：一次 kernel launch 替代多次（省启动开销），中间结果留在寄存器/共享内存不落显存（省带宽）。

融合的边界也由依赖决定：两个算子若一个要读另一个的「全部历史」（比如 reduction 求和后再归一化），硬融合会破坏并行性，Scheduler 会拆开。最终排出的「组」就是 Triton kernel 的边界——图里一个 op 不对应一个 kernel，一组 op 对应一个 kernel，这是编译路径和 eager 路径在微观结构上的本质区别。

关联 矩阵乘这类大算子不参与逐元素融合，但有自己的选型层：tuned_mm（kernel/mm.py，lowering for autotuning aten.mm）会在 Aten、Triton、CUTLASS 等实现间做自动选择。看到的 profile 里 "triton_mm" 还是 "cutlass" 就由这一层决定。

10.4autotune 与编译缓存

Triton 代码生成后还有一个「选参数」步骤：block 大小、循环展开数等配置影响性能且无解析最优解。CachingAutotuner（runtime/triton_heuristics.py）的做法是穷举候选配置真实跑一遍（benchmark_all_configs，:1821）取最快——这就是第一次运行 compile 慢的主要原因之一，也是 benchmark 模式下必须 warmup 的原因。

编译产物的两级缓存把这笔一次性的贵费用摊平：FxGraphCache（codecache.py）缓存「整张图的编译结果」，key 是图内容 + 相关配置的哈希——同一个模型第二次启动、或多个 rank 编同一张图，直接命中；Triton kernel 级缓存再往下管一层。缓存的 guard 语义与 09 章一致：环境变了（驱动、架构、配置）缓存失效重编。

分布式训练里的一个实用细节：多卡启动时所有 rank 会各自编一遍同样的图。FxGraphCache 是文件级缓存，理论上有进程间共享的可能，但实际多机各存各的——因此「编译时间」在大规模启动里是全体 rank 同时付出的。torch.compile 的 warmup 优化（异步编译、编译调度）就是冲着这段墙钟时间去的，async_compile（torch/_inductor/async_compile.py）把编译任务丢进子进程并行做。

10.5把账算完：编译收益从哪来

把 09、10 两章合起来算一次账。torch.compile 相对 eager 的收益，来自四个互相独立的来源，profile 里都能各自验证：

来源机制典型占比
kernel 融合Scheduler 合并逐元素算子，省启动 + 省中间落盘小算子多的模型最大头
重算换显存min-cut 分区砍掉保存，减少带宽压力显存吃紧时显著
去掉 Python 开销整段图一次执行，无逐 op 的解释器/dispatch 开销小 batch、小模型时最大头
autotune每个 kernel 现场选配置计算密集算子上的稳定小赚

四个来源互相独立意味着：收益不是均匀的。大模型大 batch 训练时第 3 行几乎为零（本来就是 GPU 密集），主要赚第 1、2 行；小模型推理时第 3 行是全部。理解这点，再看「compile 到底快多少」的各种实测数字就不会困惑——它们测的是不同来源的组合。

要点 Inductor 一章的两根支柱：min-cut 分区决定「存还是算」（显存侧），Scheduler 融合决定「几个算子一个 kernel」（带宽侧）。加上 Dynamo 的缓存语义（09 章），torch.compile 的全部机制就这三大块。
