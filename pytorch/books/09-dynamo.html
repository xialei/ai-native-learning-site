Dynamo：把 Python 函数变成图，且不出错

torch.compile 的第一站是 Dynamo：截住 Python 字节码、转成 FX 图。难点从来不是「能不能转」，而是「转不动时怎么办」——Python 太动态，图必然有覆盖不了的地方。Dynamo 的答案是一套 guard + 回退机制：保证任何情况下要么产出正确编译结果、要么退回 eager。这章沿一次编译走完全程。

9.1入口：C 层的帧监控

torch.compile(model) 不改模型代码，也不解析源码字符串。它安装了一个 eval frame 回调——CPython 每次要执行一个 Python 帧时先问一句「这个帧要不要被 Dynamo 处理」。这个钩子在 C 层（torch._C._dynamo.eval_frame），Python 侧的 set_eval_frame 只是入口包装：

torch/_dynamo/eval_frame.py — C 钩子的导入（摘录）
pythonfrom torch._C._dynamo.eval_frame import (
    ...
    set_eval_frame,
    ...
)

被标记处理的帧，其字节码交给 Dynamo 的 convert_frame 分析：模拟执行字节码、把张量操作记进 FX 图、把非张量逻辑（分支条件、循环边界）固化成 guard 条件。两个包装类各有分工——OptimizeContext 开启捕获，DisableContext 把一块代码明确排除在编译外（torch.compiler.disable 的落点）。

为什么选字节码而不是 AST：AST 只知道「代码写了什么」，不知道「这次跑的是哪条路径、什么形状」。字节码帧带着真实的运行时状态：参数的实际值、tensor 的实际 shape。Dynamo 在字节码层面做的是「符号化重放」——控制流按本次执行路径固化，张量操作进图。这决定了它的天然边界（后面讲）：没跑过的分支没进图。

9.2guards：编译结果的生效条件

Dynamo 编译出的不是「这个函数的机器码」，而是「这次执行路径的机器码 + 一组成立条件」。条件（guard）覆盖：参数的 shape/dtype/stride、Python 值（比如 batch size、flag）、全局状态。下次调用先查 guard：

  • 全过 → 直接执行已编译产物，零分析成本。
  • 有挂 → 重新分析字节码，为「新路径」再编译一份。

所以动态 shape 的默认行为是「每换一个 shape 编译一份」，而不是「编译一份通用的」。要通用就得开 dynamic=True：形状变成符号（比如 s0、s1），guard 从「shape == 128」变成「shape 是符号、满足某约束」。

符号从哪来：FakeTensorMode（torch/_subclasses/fake_tensor.py）给每个 tensor 一个「影子」——只有形状元信息、没有数据（第 10 章的 min-cut 分区也靠它）。符号形状的推导与约束收集在 ShapeEnv（torch/fx/experimental/symbolic_shapes.py）里做。这两个类是 Dynamo 与 Inductor 的共享地基：前者提供「不真算也能跑图」的能力，后者保证符号形状自洽。

9.38 次之后：重编译上限的取舍

「每条新路径编译一次」策略在病态场景会失控：训练循环里若有个值总在变（比如动态 batch 的尾批），每次变化触发重编译，编译又慢（秒级），训练就卡死在编译上。Dynamo 的限流在 config 里：

torch/_dynamo/config.py — 重编译上限（原文摘录）
python# controls the maximum number of cache entries with a guard on same ID_MATCH'd
# object. It also controls the maximum size of cache entries if they don't have
# any ID_MATCH'd guards.
# [@compile_ignored: runtime_behaviour]
recompile_limit = 8

# [@compile_ignored: runtime_behaviour] safeguarding to prevent horrible recomps
accumulated_recompile_limit = 256

同一个代码对象 8 次重编译后放弃（后续调用静默回 eager），累计 256 次是全进程的保险丝。这两个数字解释了大量「为什么我的模型 compile 了但不快」：图根本没编几份，热路径仍走 eager。诊断入口是 torch._dynamo.utils.counters（或 TORCH_LOGS=recompiles）——先看重编译原因，再决定是开 dynamic 还是改代码。

与重编译上限配套的是回退面。Dynamo 里有一张跳过原因表（convert_frame.py 的 CatchErrorsWrapper，:2589）：非 Python 函数、已处于 dispatch 模式、特定字节的生成器……遇上了直接放弃编译。这套「宁可回退、不可出错」的边界和第 3 章 dispatcher 的设计同构：先保证正确，再谈加速。

演进痕迹 训练场景里优化器默认不进图（第 7 章那行 _disable_dynamo_if_unsupported）不是能力不足，是收益判断：优化器的 foreach/fused 路径已是高度调优的 C++/CUDA，图编译能再加的不多，而 guard 维护成本真实存在。「什么值得进图」是 torch.compile 的核心产品决策，散落在各处的 disable 标记就是这份决策的记录。

9.4从 Dynamo 到 AOTAutograd：一次 compile 的接力

torch.compile(backend="inductor") 的完整管线在第 10 章展开，这里先立好交接面：Dynamo 产出 FX 图（前向），AOTAutograd 接手拆成前向图 + 反向图（用的还是第 4 章那套 min-cut 思想），再分别交给 Inductor 编译。三段的分工记成三行：Dynamo 管「Python 语义 → 图」，AOTAutograd 管「图 → 前向+反向两张图」，Inductor 管「图 → kernel」。

这个接力的用户可感知面是「编译错误发生在哪一段」。报错里出现 Dynamo 字样，多半是字节码分析不支持某写法（回退或报错）；出现 AOTAutograd / partition，是联合图切分出了问题（常与 inplace/view 有关）；出现 Inductor / Triton，是 kernel 生成或 autotune 的问题。三段各自的诊断工具不同（counters、min-cut 可视化、TORCH_LOGS=graph_breaks），按报错关键词选工具能省大量时间。

要点 Dynamo 的本质是一套「带生效条件的缓存」：字节码 → 图 + guards，guard 全过走缓存，否则为新路径再编一份。8 次上限、回退面、dynamic 开关都是围绕这个缓存的策略参数。下一章进编译管线的下游：图怎么变成 Triton kernel。
