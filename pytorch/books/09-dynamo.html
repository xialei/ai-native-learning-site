Dynamo：把 Python 函数变成图，且不出错

torch.compile 的第一站是 Dynamo：截住 Python 字节码、转成 FX 图。难点从来不是「能不能转」，而是「转不动时怎么办」——Python 太动态，图必然有覆盖不了的地方。Dynamo 的答案是一套 guard + 回退机制：保证任何情况下要么产出正确编译结果、要么退回 eager。这章沿一次编译走完全程。

9.1入口：C 层的帧监控

torch.compile(model) 不改模型代码，也不解析源码字符串。它安装了一个 eval frame 回调——CPython 每次要执行一个 Python 帧时先问一句「这个帧要不要被 Dynamo 处理」。这个钩子在 C 层（torch._C._dynamo.eval_frame），Python 侧的 set_eval_frame 只是入口包装：

torch/_dynamo/eval_frame.py — C 钩子的导入（摘录）
pythonfrom torch._C._dynamo.eval_frame import (
    ...
    set_eval_frame,
    ...
)

被标记处理的帧，其字节码交给 Dynamo 的 convert_frame 分析：模拟执行字节码、把张量操作记进 FX 图、把非张量逻辑（分支条件、循环边界）固化成 guard 条件。两个包装类各有分工——OptimizeContext 开启捕获，DisableContext 把一块代码明确排除在编译外（torch.compiler.disable 的落点）。

为什么选字节码而不是 AST：AST 只知道「代码写了什么」，不知道「这次跑的是哪条路径、什么形状」。字节码帧带着真实的运行时状态：参数的实际值、tensor 的实际 shape。Dynamo 在字节码层面做的是「符号化重放」——控制流按本次执行路径固化，张量操作进图。这决定了它的天然边界（后面讲）：没跑过的分支没进图。

9.2guards：编译结果的生效条件

Dynamo 编译出的不是「这个函数的机器码」，而是「这次执行路径的机器码 + 一组成立条件」。条件（guard）覆盖：参数的 shape/dtype/stride、Python 值（比如 batch size、flag）、全局状态。下次调用先查 guard：

  • 全过 → 直接执行已编译产物，零分析成本。
  • 有挂 → 重新分析字节码，为「新路径」再编译一份。

所以动态 shape 的默认行为是「每换一个 shape 编译一份」，而不是「编译一份通用的」。要通用就得开 dynamic=True：形状变成符号（比如 s0、s1），guard 从「shape == 128」变成「shape 是符号、满足某约束」。

符号从哪来：FakeTensorMode（torch/_subclasses/fake_tensor.py）给每个 tensor 一个「影子」——只有形状元信息、没有数据（第 10 章的 min-cut 分区也靠它）。符号形状的推导与约束收集在 ShapeEnv（torch/fx/experimental/symbolic_shapes.py）里做。这两个类是 Dynamo 与 Inductor 的共享地基：前者提供「不真算也能跑图」的能力，后者保证符号形状自洽。

9.38 次之后：重编译上限的取舍

「每条新路径编译一次」策略在病态场景会失控：训练循环里若有个值总在变（比如动态 batch 的尾批），每次变化触发重编译，编译又慢（秒级），训练就卡死在编译上。Dynamo 的限流在 config 里：

torch/_dynamo/config.py — 重编译上限（原文摘录）
python# controls the maximum number of cache entries with a guard on same ID_MATCH'd
# object. It also controls the maximum size of cache entries if they don't have
# any ID_MATCH'd guards.
# [@compile_ignored: runtime_behaviour]
recompile_limit = 8

# [@compile_ignored: runtime_behaviour] safeguarding to prevent horrible recomps
accumulated_recompile_limit = 256

同一个代码对象 8 次重编译后放弃（后续调用静默回 eager），累计 256 次是全进程的保险丝。这两个数字解释了大量「为什么我的模型 compile 了但不快」：图根本没编几份，热路径仍走 eager。诊断入口是 torch._dynamo.utils.counters（或 TORCH_LOGS=recompiles）——先看重编译原因，再决定是开 dynamic 还是改代码。

与重编译上限配套的是回退面。Dynamo 里有一张跳过原因表（convert_frame.py 的 CatchErrorsWrapper，:2589）：非 Python 函数、已处于 dispatch 模式、特定字节的生成器……遇上了直接放弃编译。这套「宁可回退、不可出错」的边界和第 3 章 dispatcher 的设计同构：先保证正确，再谈加速。

演进痕迹 训练场景里优化器默认不进图（第 7 章那行 _disable_dynamo_if_unsupported）不是能力不足，是收益判断：优化器的 foreach/fused 路径已是高度调优的 C++/CUDA，图编译能再加的不多，而 guard 维护成本真实存在。「什么值得进图」是 torch.compile 的核心产品决策，散落在各处的 disable 标记就是这份决策的记录。

9.4graph break：一张图从哪里断开、怎么接上

9.3 讲的是整段放弃：某个代码对象压根不编。但更常见的现象是「编是编了，trace 中途断一下」——这就是 graph break。它和整段回退的差别在于：断裂点之前的算子已经进图，Dynamo 把这半截先编译掉，再从断裂点之后继续接着 trace，一个函数最终产出多段图。9.1 的注记留了个尾巴——「没跑过的分支没进图」——分支条件是张量时怎么办？断开、把条件求值留在 eager、前后各接一段图，这正是本节要展开的机制。

哪些写法会触发断裂？Dynamo 维护了一份注册表（torch/_dynamo/graph_break_registry.json，600 项左右，每项一个编号、一段解释、几条修改建议）。高频触发写法就这几类：

  • 张量当分支条件：if loss.sum() > 0:。图里没有 loss 的值，跳转方向定不下来。这是最高频的一类，注册表编号 GB0170，报错名 Data-dependent branching，建议里给了替代写法：能写成 shape guard 的改用普通 Python int，动态分支用 torch.cond，纯条件取值用 torch.where。
  • 取值出图：loss.item()、Tensor.numpy()、print(tensor)。数据从张量世界回到 Python 世界，trace 断（GB0124：config.capture_scalar_outputs 默认关着，想捕获得设环境变量 TORCHDYNAMO_CAPTURE_SCALAR_OUTPUTS=1）。
  • 改图输入的元数据：x.transpose_(1, 2)、requires_grad_()。输入 tensor 的 shape/标志是 guard 的一部分，原地改等于让 guard 失效（GB0125 报 requires_grad_；inplace view 的建议是换成 x = x.transpose(1, 2) 这种非原地写法）。
  • 别的语言/别的表示：Tensor.numpy()（trace_numpy 默认关，GB0105）、sparse tensor。
  • 默认断裂的 print()：print 是个普通内置调用，trace 不动它就断。想不断，用 torch._higher_order_ops.print（以 HOP 形式进图），或把自定义日志函数加进 config.reorderable_logging_functions 让 Dynamo 挪到编译区末尾重放。

断开之后怎么接上？Dynamo 生成一组续跑函数。看数据依赖分支的处理（symbolic_convert.py 的 generic_jump，一条 if 断裂后产出两个续跑点）：

torch/_dynamo/symbolic_convert.py — generic_jump 里生成两个续跑点（摘录）
pythonif_next = self.create_call_resume_at(
    self.next_instruction,
    all_stack_locals_metadata,
)
...
if_jump = self.create_call_resume_at(
    inst.target,
    all_stack_locals_metadata,
)

jump_inst = create_instruction(inst.opname, target=if_jump[0])
...
self.output.add_output_instructions([jump_inst] + if_next + if_jump)

编译产物里出现两个 __resume_at_<字节码偏移> 函数（名字就带断点位置，trace 里能看到），中间由一条真实的 Python 条件跳转指令连接——条件成立走 if_next 指向的继续点，不成立走 if_jump 指向的。也就是说断裂不是「断」，是 Python 函数之间的正常调用：前半段图跑完，条件在 eager 里求值，然后调进对应的 resume 函数继续跑后半段图。不涉及跳转的断裂（比如一个不支持的 CALL）同样收尾，只是只生成一个续跑点，那条不支持的字节码本身原样执行（eager），再从下一条接着编译。

断裂的判定先于断裂：Dynamo 不是等撞上不支持的写法才停。trace 过程中维护一份推测记录（speculation log），第一次编译把「可以从哪里恢复」的候选点都记下来；真正断的时候重放这份记录，在第一个失效点停下、就地切图。所以断裂位置看起来在「行 N」，实际编译可能早就在为「行 N 之后的某处」做准备了。断裂也可以被禁掉：fullgraph=True（或 error_on_graph_break=True）把断裂从「容忍」改成「报错」——torch.export 就工作在这个模式下，导出要求整段一张图，dynamic 写法必须先处理干净。

诊断从两个入口进。第一个是 TORCH_LOGS=graph_breaks，实际输出长这样（以 loss.item() 为例）：

TORCH_LOGS=graph_breaks 的输出结构（格式按源码，内容有删节）
textGraph break in user code at model.py:57
Graph Break Reason: Unsupported Tensor.item() call with capture_scalar_outputs=False
  Explanation: Dynamo does not support tracing `Tensor.item()` with config.capture_scalar_outputs=False.
  Hint: Set `torch._dynamo.config.capture_scalar_outputs = True` or `export TORCHDYNAMO_CAPTURE_SCALAR_OUTPUTS=1` ...

User code traceback: (略)

读法：第一行定位到你的源码行；Reason 段的几行是模板化的——报错名（拿这个名字去注册表里能对上编号）、Explanation 说 Dynamo 拒绝的理由、Hint 给替代写法或开关，末尾还有一段 Developer debug context 和文档链接。多数 graph break 靠 Hint 就能解。

第二个入口是 torch._dynamo.explain(fn)(*args)：不装 Inductor，只让 Dynamo 跑一遍分析，返回一份 ExplainOutput——编出了几段图、每段有哪些算子、guard 是什么、断裂原因列表。快速回答「我这段代码到底编成了几块」用这个最省事。

要点 graph break 不是 bug，是「Python 太动态」这个前提下的正常分工：图编得动的进图，编不动的留在 eager，用续跑函数把两段缝起来。性能问题的信号是断裂次数和位置——torch._dynamo.explain 一看便知；两条经验是热路径尽量别断（一次断裂引入一次 eager 往返），修法优先选 Hint 里的改写而不是关断裂（error_on_graph_break=True 让断裂直接报错，逼你把动态写法处理干净）。

9.5从 Dynamo 到 AOTAutograd：一次 compile 的接力

torch.compile(backend="inductor") 的完整管线在第 10 章展开，这里先立好交接面：Dynamo 产出 FX 图（前向），AOTAutograd 接手拆成前向图 + 反向图（用的还是第 4 章那套 min-cut 思想），再分别交给 Inductor 编译。三段的分工记成三行：Dynamo 管「Python 语义 → 图」，AOTAutograd 管「图 → 前向+反向两张图」，Inductor 管「图 → kernel」。

这个接力的用户可感知面是「编译错误发生在哪一段」。报错里出现 Dynamo 字样，多半是字节码分析不支持某写法（回退或报错）；出现 AOTAutograd / partition，是联合图切分出了问题（常与 inplace/view 有关）；出现 Inductor / Triton，是 kernel 生成或 autotune 的问题。三段各自的诊断工具不同：Dynamo 用 counters 与 TORCH_LOGS=graph_breaks（9.4），AOTAutograd 用 min-cut 可视化，Inductor 用 TORCH_COMPILE_DEBUG 导出的编译产物目录，按报错关键词选工具能省大量时间。

要点 Dynamo 的本质是一套「带生效条件的缓存」：字节码 → 图 + guards，guard 全过走缓存，否则为新路径再编一份。8 次上限、回退面、graph break 的接缝、dynamic 开关都是围绕这个缓存的策略参数。下一章进编译管线的下游：图怎么变成 Triton kernel。
