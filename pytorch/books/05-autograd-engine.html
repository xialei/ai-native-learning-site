autograd 引擎：backward 的多线程执行器

上一章说清楚图是什么，这章看图怎么被执行。引擎在 torch/csrc/autograd/engine.cpp，一个文件三千多行，核心结构其实只有三样：GraphTask（一次 backward 的账本）、每设备一条工作线程加一条就绪队列、每个节点一个依赖计数。retain_graph、梯度 hook、CUDA 流同步全都挂在这三样上。

5.1入口：一次 backward 调用的路径

从 Python 侧到 C++ 引擎，中间没有多少站。loss.backward() 先到 torch/autograd/__init__.py 的 backward，整理参数后调用 _engine_run_backward，再到 torch/autograd/graph.py 的同名包装，最后一步交给 Variable._execution_engine.run_backward——这一行就是 Python 和 C++ 引擎的分界线。graph.py 里的包装函数做的是线程本地状态（TLS）的存取，源码里那段注释值得看：TLS 上下文如果不在调用前后正确清理，会在下一次 backward 时死锁，这是真实修过的 bug。

进到 C++ 侧，一切从 Engine::execute 开始：

torch/csrc/autograd/engine.cpp — execute 开头（摘录，注释为译注）
cppauto Engine::execute(
    const edge_list& root_edges,
    const variable_list& inputs,
    bool keep_graph,
    bool create_graph,
    bool accumulate_grad,
    const edge_list& outputs) -> variable_list {
  // （开头的参数校验与 create_graph 警告省略）
  auto compiled_autograd = the_compiled_autograd.load();

  // accumulate_grad is true if and only if the frontend call was to
  // backward(), not grad(). grad() returns the sum of the gradients
  // w.r.t. the inputs and thus needs the inputs to be present.

  // A fresh first time Engine::execute call should start on the CPU device,
  // initialize a new thread local ready queue on CPU or reuse the existing one
  // (if there is one allocated already, i.e. consecutive backward calls,
  // re-entrant backward calls), then memoize the local_ready_queue in GraphTask
  init_local_ready_queue();
  bool not_reentrant_backward_call = worker_device == NO_DEVICE;

  // Store root nodes so we can traverse through the graph later
  c10::SmallVector<Node*, 4> temp_roots{root_edges.size()};
  for (const auto i : c10::irange(root_edges.size())) {
    temp_roots[i] = root_edges[i].function.get();
  }

  auto graph_task = std::make_shared<GraphTask>(
      /* keep_graph */ keep_graph,
      /* grad_mode */ create_graph,
      /* reentrant_depth */ not_reentrant_backward_call ? 0 : total_depth + 1,
      /* cpu_ready_queue */ local_ready_queue,
      /* graph_roots */ std::move(temp_roots));

参数里的 keep_graph 就是 Python 侧的 retain_graph，create_graph 是高阶梯度开关。函数开头初始化本线程的就绪队列，然后造出 GraphTask——注意它是 shared_ptr，后面所有工作线程都攥着它，谁也不提前释放。这个函数后半段构造 GraphRoot、算依赖，最后把第一个任务塞进队列并进入等待循环（调用方线程在 backward 期间是阻塞的）。

5.2GraphTask：一次 backward 的账本

GraphTask 是这次 backward 的全部共享状态。它的关键字段不多，每个都对应一类用户可感知的行为：

字段含义对应的用户可见行为
dependencies_每个节点还差几路输入才可执行执行顺序正确性的保证（5.4）
not_ready_已到但没凑齐的梯度暂存区菱形结构（多路径汇聚）不丢梯度
exec_info_ / needed_本次需要执行哪些节点指定 inputs 的 grad()；hook 过滤
captured_vars_要返回给调用方的梯度autograd.grad() 的返回值
keep_graph_是否保留图retain_graph 参数
outstanding_tasks_还没执行完的任务数backward 何时返回

开始执行前的准备工作有两步，都在 execute 里。第一步 compute_dependencies：从根出发遍历全图，数清每个节点被几条边指着——这个数就是它必须等齐的输入份数。第二步 init_to_execute：如果用户调的是 grad(loss, inputs) 而不是 backward(loss)，把「与 inputs 无关的子树」标记为不需要执行。两步都做在同一个 GraphTask 上，之后的执行就只查账本、不再碰图。

为什么先算依赖再执行：图是动态长出来的，节点间没有任何拓扑序字段（sequence_nr 只用于异常诊断）。与其执行时反复判断「我该不该等」，不如开工前一次性把每个节点的依赖数算好、执行时只做减法。这是空间换顺序：一次 O(V+E) 遍历，换每个节点 O(1) 的就绪判断。第 12 章的 FSDP2 也会在反向里插自己的 all-gather，靠的正是这套通用的依赖机制而不是改引擎。

5.3工作线程与就绪队列

引擎的线程模型是理解 backward 性能的钥匙，规则只有一条：每个设备一条工作线程，每条线程一条自己的就绪队列。首次 backward 的用户线程扮演 CPU 工作线程；CUDA tensor 的节点会触发为该 GPU 创建专属线程（每个设备进程内只建一次，长期复用）。

torch/csrc/autograd/engine.cpp — thread_main（摘录，注释为译注）
cppauto Engine::thread_main(const std::shared_ptr<GraphTask>& graph_task) -> void {
  // When graph_task is nullptr, this is a long running thread that processes
  // tasks (ex: device threads). When graph_task is non-null (ex: reentrant
  // backwards, user thread), this function is expected to exit once that
  // graph_task complete.

  // local_ready_queue should already been initialized when we get into
  // thread_main
  TORCH_INTERNAL_ASSERT(local_ready_queue != nullptr);
  while (graph_task == nullptr || !graph_task->future_result_->completed()) {
    // （local_graph_task：本次从队列取出的任务所属的 GraphTask）
    NodeTask task = local_ready_queue->pop();
    if (task.isShutdownTask_) {
      C10_LOG_API_USAGE_ONCE("torch.autograd.thread_shutdown");
      break;
    }

    local_graph_task = task.base_.lock();
    if (!local_graph_task) {
      // GraphTask for function is no longer valid, skipping further execution.
      continue;
    }

    set_device(worker_device);

    if (task.fn_ && !local_graph_task->has_error_.load()) {
      // Set the ThreadLocalState before calling the function.
      at::ThreadLocalStateGuard tls_guard(local_graph_task->thread_locals_);
      c10::WarningUtils::WarningHandlerGuard warnings_guard(
          &local_graph_task->warning_handler_);

      try {
        GraphTaskGuard guard(local_graph_task);
        NodeGuard ndguard(task.fn_);
        {
          RECORD_FUNCTION(
              c10::str(
                  "autograd::engine::evaluate_function: ",
                  task.fn_.get()->name()),
              c10::ArrayRef<const c10::IValue>());
          evaluate_function(
              local_graph_task,
              task.fn_.get(),
              task.inputs_,
              local_graph_task->cpu_ready_queue_);
        }
      } catch (std::exception& e) {
        // See Note [ Persisting PyErr state across autograd engine threads ]
        thread_on_exception(local_graph_task, task.fn_, e);
      }

循环体结构简单：从队列取任务、检查这次 backward 是否已被异常终止、恢复线程本地状态、执行、异常则记录到 GraphTask。两个细节值得停留。

其一，队列为空时线程 pop 阻塞，不做忙等。GPU 工作线程平时全在睡觉，backward 一来才醒——所以 idle 的 PyTorch 进程 CPU 占用为零，是设计使然而非巧合。

其二，device 线程是常驻的（graph_task == nullptr 的分支），跨多次 backward 复用。首次调用会支付线程创建成本，此后每次 backward 只是唤醒。这就是为什么第一个 step 的 backward 明显比后续慢。

其三，执行中出错的传播方式不是跨线程抛异常，而是记到 GraphTask 上（thread_on_exception 内部调 set_exception，在 GraphTask 上留下 has_error_ 标志并把异常存进 future_result_）。has_error_ 一旦置位，主循环里 task.fn_ && !has_error_.load() 的条件不再满足，其余任务跳过执行但仍走计数递减；而 future_result_ 一旦完成，while 循环条件 !graph_task->future_result_->completed() 不再成立，各线程依次退出。错误处理同样搭在这套计数与队列机制上。

5.4执行与计数：evaluate_function

每个入队的任务就是「某节点依赖已凑齐，可以执行了」。执行函数 evaluate_function承担三件事：调 Node 的 apply 拿到梯度输出、按 next_edges 把梯度分发给下游、递减下游依赖计数，减到零就入队。分发与计数的核心片段（engine.cpp 起，收在 else 分支进入前）：

torch/csrc/autograd/engine.cpp — 依赖递减与入队（摘录，注释为译注）
cpp  // Lock mutex for the accesses to GraphTask dependencies_, not_ready_ and
  // cpu_ready_queue_ below
  std::lock_guard<std::mutex> lock(graph_task->mutex_);
  for (const auto i : c10::irange(num_outputs)) {
    auto& output = outputs[i];
    const auto& next = fn.next_edge(i);

    if (!next.is_valid())
      continue;

    // Check if the next function is ready to be computed
    bool is_ready = false;
    auto& dependencies = graph_task->dependencies_;
    auto it = dependencies.find(next.function.get());

    if (it == dependencies.end()) {
      auto name = next.function->name();
      TORCH_CHECK(false, "dependency not found for ", name);
    } else if (--it->second == 0) {
      dependencies.erase(it);
      is_ready = true;
    }

    auto& not_ready = graph_task->not_ready_;
    auto not_ready_it = not_ready.find(next.function.get());
    if (not_ready_it == not_ready.end()) {
      // （exec_info_ 过滤：本次不执行的节点直接跳过）
      // No buffers have been allocated for the function
      InputBuffer input_buffer(next.function->num_inputs());

      input_buffer.add(
          next.input_nr,
          std::move(output),
          opt_parent_stream,
          next.function->stream(),
          next.function.get());

      if (is_ready) {
        auto queue = ready_queue(cpu_ready_queue, next.function->device());
        queue->push(
            NodeTask(graph_task, next.function, std::move(input_buffer)));
      } else {
        not_ready.emplace(next.function.get(), std::move(input_buffer));
      }
    }
InputBuffer 与 CUDA 流同步：evaluate_function 开头有一段「等上游事件」的逻辑（opt_parent_stream / opt_ready_event）：上游梯度在别的流上算完时，这里插入 stream wait 保证消费不早于生产。单卡代码永远感知不到它；多流训练（比如用多个 stream 并行几层）时的「偶发 NaN」，值得先怀疑这里的同步是否被自定义 hook 打乱。

5.5执行顺序：广度优先的实际效果

很多人以为 backward 是「深度优先」：从 loss 一路推到最底层再回头。实际不是。依赖计数机制天然产生的是一种自适应的并行推进：所有依赖已清零的节点同时可执行、各设备各取各的。用一个两层 MLP 的图看实际顺序：

图 5.1：backward 不是树遍历，是依赖驱动的推进。引擎从不知道「第几层」，只认计数。这个设计换来一个重要性质：图中任何节点的执行不需要等全图遍历到某个固定位置——只要它的输入齐了，随时开始。

这个性质直接解释了两个日常现象。一是 retain_graph 为什么会拖慢第二次 backward：图不释放、节点引用都在，第二次执行没法复用第一次的任何中间缓存，该算的全部重算。二是 hook 的执行时机——tensor 的 post-accumulate hook 挂在 AccumulateGrad 上，所以它跑在「该参数梯度刚写完」的时刻，而不是 backward 结束的统一时刻。

5.6回顾：把图和引擎接起来

两章合起来，backward 的完整故事是：前向时 dispatcher 的 autograd key 把 696 条 YAML 规则实例化成 Node/Edge 图（04 章）；backward 时引擎为这次调用造 GraphTask、数依赖、多设备线程按计数推进、梯度最终经 AccumulateGrad 写进 .grad（本章）。全部过程里，用户代码只出现两次——发起前向，和调用 backward。

有一个把两章连起来的对照值得放进脑内：前向的「顺序」来自 Python 语句的先后，后向的「顺序」来自依赖计数。前者是书写顺序，后者是数据流顺序。动态图框架的全部自由与全部开销，都藏在这句话里——自由是因为图随代码走，昂贵是因为每步都在解释执行。第 9 章的 Dynamo 就要从这里下手：把「解释执行」变成「编译执行」，同时尽量不破坏这套语义。

要点 引擎三件套：GraphTask（账本）、每设备线程 + 就绪队列（并行单元）、依赖计数（顺序保证）。理解了这三样，retain_graph、hook 时机、多卡并行、首次 backward 变慢，全部有了出处。
