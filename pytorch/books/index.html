目标读者：天天在用 PyTorch，想弄清 loss.backward() 和 optimizer.step() 背后到底发生了什么的工程师。

为什么值得读 PyTorch 的源码

一个反常的现象：PyTorch 是几乎所有大模型训练的底座——开源训练框架、各家公司的内部训练平台，最底下那一层都是它——但认真读过它源码的工程师，比例远低于读 vLLM 或推理引擎的人。原因大概有两条。一是「会调 API 就能干活」，梯度出了问题查一下 requires_grad 也就过去了；二是它把真正的复杂度藏在了 C++ 里：你在 Python 里敲 x + y，穿过 torch._C、Dispatcher、ATen kernel 才落到内存上，这条路径在 Python 层完全看不见。

这本书就想把这条看不见的路径摊开。另一个时机上的原因：训练框架的能力正在往 PyTorch 本体里沉。ZeRO 式的参数分片变成了原生的 FSDP2，Megatron 式的流水线调度进了 torch.distributed.pipelining，手写收集通信换成了 DTensor 的自动分片传播，checkpoint 换成了 DCP。以前要在 DeepSpeed、Megatron 里读到的机制，现在很多就是 torch/ 目录下的几行 Python。读 PyTorch 内部，等于一次看清这条下沉的线；书里讲到这些位置时，也会顺手和 DeepSpeed/Megatron 的对应实现做个对照。

怎么读 前八章是一条主线：一次训练 step 从数据进来，到参数更新出去，每一步对应哪个目录、哪段 C++。第九到十一章是加速线（09/10 编译、11 显存与 CUDA）。第十二、十三章是放大规模时躲不开的两块（分布式、工程化）。最后一章把前面的东西拼成一张自研清单。

PyTorch 怎么把训练变快

一次训练 step 本身只有四步：取数据、前向、反向、更新参数。PyTorch 的所有优化都挂在这四步上。每一步慢在哪里、PyTorch 拿什么去治，先列一张表：

优化手段解决什么问题章节
自动求导 autograd手写反向不可维护——前向一变，反向就得跟着改04 / 05
Dispatcher 统一分发CPU/GPU/自动求导几十种组合，算子不用每个都手写一遍03
hook 与注册机制不改模型代码就能插入日志、调试、量化逻辑06
fused / foreach 优化器一亿参数逐个更新，优化器自己成了瓶颈07
混合精度 AMPfp32 权重的显存与带宽07
多进程 DataLoaderGPU 等数据，算力空转08
torch.compile（Dynamo + Inductor）Python 解释器开销、小算子碎片09 / 10
CUDA Graphs每步几万次 kernel 启动的 CPU 开销11
CachingAllocator / expandable segments显存碎片与莫名其妙的 OOM11
FSDP2 / DTensor单卡装不下模型或激活12
流水线并行层多卡多，张量并行通信太密12 / 13
DCP 异步 checkpoint存档时训练停摆13
profiler / Kineto不知道时间花在了哪13

图 0b：loss.backward() 一次调用流过引擎的全过程。两个值得先记住的点：反向的「代码」早在前向就写好了（每个算子自带反向函数），backward 只是调度它们按依赖倒序执行；执行是多线程的，每个设备一条工作线程、各有一条就绪队列，大图才能跑满多卡。

学习路径

STEP 1

整体架构

import torch 之后发生了什么：torch._C 扩展、c10/ATen/torch 三层目录的分工，Python API 和 C++ 核心怎么接线。
STEP 2

Tensor 内部

TensorImpl / StorageImpl / VariableVersion：一个 tensor 拆成三块，view 和 detach 靠什么实现，为什么属性访问这么快。
STEP 3

Dispatcher

DispatchKey 与 kernel 表：一次 add() 怎么选中 CPU/CUDA/autograd 的实现，自定义后端和 __torch_dispatch__ 插在哪。
STEP 3

autograd 计算图

前向怎么顺手记图：Node / Edge / AccumulateGrad，derivatives.yaml 里 696 条反向规则，no_grad 的真实代价。
STEP 5

autograd 引擎

GraphTask、每设备线程与就绪队列、依赖计数：backward 怎么多线程跑起来，retain_graph、hooks、异常都在哪一层。
STEP 6

nn.Module

__setattr__ 里的注册树，_call_impl 的 hook 快慢路径，state_dict 怎么长出来，torch.compile 悄悄改了哪。
STEP 7

优化器与 AMP

Optimizer 基类、AdamW 的三条实现路径（单张量 / foreach / fused），LRScheduler、GradScaler 与 loss scale。
STEP 8

DataLoader

多进程喂数据：worker 进程、每 worker 一条 index_queue、共享结果队列、pin_memory 线程，主进程怎么保证不乱序，常见坑的源码位置。
STEP 9

Dynamo

帧监控把 Python 函数变图：eval frame、guards、动态 shape、为什么 8 次之后就放弃重编译。
STEP 10

Inductor 与 AOTAutograd

图 → Triton kernel：min-cut 分区决定重算什么，Scheduler 怎么融合算子，FxGraphCache 和 autotune 省下的时间。
STEP 11

显存与 CUDA

显存分配器（块池、max_split_size、expandable segments）、CUDA Graphs 捕获回放、SDPA 后端选择与 sdpa_kernel 限定。
STEP 12

分布式

DeviceMesh 排设备拓扑、DTensor 的自动分片传播，FSDP2 在前向/反向里插了什么、NCCL 与 SymmMem 通信路径，与 ZeRO 的对照。
STEP 13

训练工程

DCP 的 planner 协议与异步存档、流水线调度（GPipe/1F1B/零泡）、torchrun 弹性拉起、profiler 怎么读。
ROADMAP

自研路线

PyTorch 留给用户的扩展点：自定义算子（torch.library）、Python dispatch 挂钩、torch.export 与 AOTInductor，以及写一个自己的「迷你 torch」的里程碑。

全书词表

各章反复出现的术语收拢在这里，按学习路径顺序排列。「详见」指向讲得最透的章节；读正文遇到陌生词，先回来查这一张表。

术语含义详见
torch._C编译出来的 C++ 扩展模块，PyTorch 真正的本体；import torch 时被整包导进 Python 命名空间01
c10 / ATen两层 C++ 核心库：c10 是与后端无关的基础（tensor 元信息、DispatchKey），ATen 是算子库（aten/src/ATen）01
TensorImpl / StorageImpltensor 的两块内部结构：TensorImpl 存形状、步长、类型等元信息；StorageImpl 存实际数据指针，可被多个 tensor 共享02
VariableVersion（version counter）每个 tensor 身上的版本计数器，原地修改会加一；autograd 靠它发现「保存下来的值被偷偷改了」02
view（视图）与原 tensor 共享同一块 Storage、只换形状或偏移的 tensor；reshape 可能拷贝，view 一定不拷贝02
DispatchKey / DispatchKeySettensor 身上的「能力标签」集合：CPU、CUDA、Autograd、Functionalize……dispatcher 按它选实现03
Dispatcher（算子分发器）C++ 全局单例：维护每个算子一张按 key 索引的 kernel 表，调用时查表选中一个实现03
op / native_functions.yamlPyTorch 里一个可调用的算子。约 2590 个 op 声明在 native_functions.yaml，由代码生成器长出绑定与分发代码03
kernel一个算子在某个 key 下的具体实现函数；「注册 kernel」= 往表里某个格子填函数03
autograd / 计算图自动求导机制。前向执行时每个算子把「怎么算自己的梯度」记成一个 Node，节点间用 Edge 连成图；backward 沿图反向执行04
Node / Edge / grad_fn图的节点是一个反向函数（Node），边指向「梯度要流去哪个下游节点的第几个输入」。tensor.grad_fn 指向生成它的那个 Node04
AccumulateGrad叶子参数专属的终止节点：梯度流到它就累进 param.grad，不再往下传04
requires_grad / detach / no_grad三个控图开关：参数带 requires_grad=True 才入图；detach 切断与历史的关系；no_grad 里的前向整段不记图04
derivatives.yaml696 条「前向算子 → 反向表达式」的规则表，autograd 的反向代码由它生成04
GraphTask / 就绪队列引擎一次 backward 的执行单元：统一数好每个节点的依赖，按设备拆成多个就绪队列，每条设备线程消化自己的队列05
retain_graphbackward 默认跑完就释放图；要对着同一批中间结果再 backward 一次就得保留05
hook（钩子）用户在固定位置注册的回调：module 有 forward/backward hook，tensor 梯度有 post-accumulate hook，优化器步骤也有06
state_dict「参数名 → 张量」的字典：module 层级拼前缀生成，是 checkpoint 的通用格式06
param group / foreach / fused优化器把参数分成组、每组一套超参；foreach 把整组参数拼成一次多张量算子，fused 再进一步并成一个 CUDA kernel07
AMP / GradScaler自动混合精度：前向用 fp16/bf16 省显存带宽；fp16 下梯度可能下溢，GradScaler 先放大 loss、更新前再缩回来07
collate / pin_memoryDataLoader 把一批样本拼成一个 batch 的动作叫 collate；pin_memory 把数据拷进锁页内存，加快进 GPU 的异步传输08
Dynamo / guardtorch.compile 的前端：截住 Python 字节码、编译成图；guard 是编译结果的生效条件，条件不满足就重新编译09
FakeTensor / ShapeEnv不占显存的「影子 tensor」，只有形状没有数据；动态 shape 下形状是符号表达式，ShapeEnv 负责推这些符号09
AOTAutograd / min-cut 分区把前向和反向提前编译的机制：在联合图上跑最小割算法，决定哪些中间结果留着、哪些反向时重算10
Inductor / Scheduler / autotunetorch.compile 的后端：Scheduler 把算子图重排融合成大 kernel，编译成 Triton/C++；autotune 对同一算子试多组配置选最快的10
FxGraphCache编译结果缓存：同一张图第二次出现就直接取，省掉编译时间10
CachingAllocatorCUDA 显存分配器：向驱动整块要内存、切成块复用，PyTorch 进程「释放」的显存其实还在它手里11
expandable segments分配器的可选模式：用虚拟内存映射代替整块预留，长而不一的显存请求不再互相卡11
CUDA Graph（捕获/回放）把一串 GPU 操作录成图、之后整图提交回放，消掉每步几万次 kernel 启动的 CPU 开销11
SDPAscaled_dot_product_attention：一个 API 背后五个后端自动挑快的，sdpa_kernel 上下文管理器可手动限定11
c10d / ProcessGroup分布式通信层：init_process_group 建组，all_reduce / all_gather / reduce_scatter 等集合通信原语，NCCL 是 GPU 后端12
DeviceMesh / DTensorDeviceMesh 把全局卡排成逻辑网格；DTensor 是「带分片信息的 tensor」，算子在它身上跑时自动做分片传播与通信12
FSDP2 / fully_shard全分片数据并行的新实现：参数、梯度、优化器状态都按 mesh 分片，前向时临时 all-gather、用完立刻释放；对应 ZeRO-3 的思路12
microbatch / 1F1B流水线并行的执行单位与调度：把 batch 切成 microbatch，一个设备「做一次前向、做一次反向」交替推进，压住气泡13
DCP / planner分布式 checkpoint：每个 rank 只存自己那份分片；planner 协议决定谁存什么、怎么合并13
torchrun / elastic分布式启动器：拉起 N 个进程、建好通信组，进程挂了能按配置弹性重启13
profiler / Kineto性能分析器：记录 kernel、通信、显存事件成 Chrome trace，训练慢的时候用它找答案13
torch.export / 自定义算子把模型导出成可独立部署的图格式；torch.library 注册自定义算子，让新 kernel 也享受分发、编译与导出14
