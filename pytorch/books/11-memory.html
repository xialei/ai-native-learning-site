显存：块池、碎片，以及 CUDA Graph 为什么要求静态

训练时的显存几乎全部由 PyTorch 自己的缓存分配器管理——cudaMalloc 只在池子不够时才被调用。这章先讲分配器怎么用「块 + 池」把 free/delete 变成账面操作，再看三个调参选项分别对应哪种碎片；后半章讲 CUDA Graphs：为什么回放要求形状和地址都不变，以及 PyTorch 侧为此做的两件配合工作。

11.1为什么需要缓存分配器

裸用 cudaMalloc/cudaFree 有两个问题：调用本身慢（毫秒级，且可能隐式同步），反复申请释放同一批大小的缓冲会把显存切得七零八落。PyTorch 的做法是进程启动后自己管一块「批发来的」显存：cudaMalloc 拿到的大块记在池子里，上层 Tensor 的分配/释放只发生在池内——free 一个 Tensor 并不真的还给驱动，只是把块标记为可用，下一个同尺寸请求直接复用。

所以 nvidia-smi 看到的显存占用和 torch.cuda.memory_allocated 报的「真实使用」是两回事：前者是池子大小（reserved），后者是池内已分出的（allocated）。训练稳定后 reserved 常年远大于 allocated，这不是泄漏，是分配器在留着复用。

c10/cuda/CUDACachingAllocator.cpp — 分配器行为自述（原文摘录）
cpp//
// Yet another caching allocator for CUDA device allocations.
//
// - Allocations are associated with a stream. Once freed, blocks can be
//   re-allocated on the same stream, but not on any other stream.
// - The allocator attempts to find the smallest cached block that will fit the
//   requested size. If the block is larger than the requested size, it may be
//   split. If no block is found, the allocator will delegate to cudaMalloc.
// - If the cudaMalloc fails, the allocator will attempt to free one cached
//   block of sufficient size that is not split and retry the allocation.
//   If this also fails, the allocator will attempt to free all cached blocks
//   that are not split and retry the allocation.
// - Large (>1MB) and small allocations are stored in separate pools.
//   Small requests are packed into 2MB buffers. Large requests will use the
//   smallest available free block or allocate a new block using cudaMalloc.
// - To reduce fragmentation, requests between 1MB and 10MB will allocate and
//   split a 20MB block, if no free block of sufficient size is available.
// - To further reduce fragmentation, blocks >= max_split_size are not allowed
//   to be split.

这段注释是分配器的说明书，四个动作各对应一层机制：按 stream 归属块（跨 stream 复用必须先 recordStream 做同步，否则出现「别的 stream 还没算完，块就被复用了」的竞态）；best-fit 找块；放不下先试着释放再重试；大小区分池。下面这张图把一次请求的路径画出来：

11.2两个调参选项分别治什么病

PYTORCH_CUDA_ALLOC_CONF 的两个常用选项，各自对应一种碎片来源：

选项治什么代价
max_split_size_mb块切太碎：大块被切成小块后，再来一个大请求放不下。≥ 该值的块禁止切分，保住大块完整性大块宁可闲置也不拆，利用率略降
expandable_segments:True段预留过多：每个段按需增长（2MiB 粒度物理页映射），不用的页可还给驱动，OOM 时回收「空物理页」依赖 cuMemMap 系 API；CUDA Graph 捕获期有交互限制

expandable_segments 的思路在源码注释里写得很清楚：地址空间和物理内存分离——先预留几乎整卡显存的虚拟地址（256TiB 地址空间随便用），实际按需映射物理页。变长序列长度训练（每个 step 序列长度不同、分配模式抖动）是最受益的场景。

困惑点 OOM 报错里 「Reserved but unallocated」很大，说明池子里有大量空闲碎片，为什么还要 OOM？因为空闲块是按 stream 和大小隔离的，可能没有一块连续空间能满足当前请求。此时开 expandable_segments 比手动 empty_cache 更对症——后者的代价是全部缓存清零、下个 step 重新 cudaMalloc。

11.3CUDA Graphs：捕获一次，回放千百次

每个 kernel launch 都有固定开销，而训练循环里「这组 kernel 序列」每个 step 都一样。CUDA Graphs 把一整个 step 的 kernel 序列录制下来，之后一次 CPU 调用回放整个序列——launch 开销从「每 kernel 一次」变成「每 step 一次」，小 batch 推理和短 kernel 密集的场景收益最大。

torch/cuda/graphs.py — torch.cuda.graph 上下文管理器（摘录，注释为译注）
pythonclass graph:
    r"""Context-manager that captures CUDA work into a
    :class:`torch.cuda.CUDAGraph` object for later replay.

    Arguments:
        cuda_graph (torch.cuda.CUDAGraph): Graph object used for capture.
        pool (optional): Opaque token ... hinting this graph's capture
            may share memory from the specified pool.
        stream (torch.cuda.Stream, optional): If supplied, will be set as
            the current stream in the context.
        capture_error_mode (str, optional): specifies the
            cudaStreamCaptureMode for the graph capture stream.
            Can be "global", "thread_local" or "relaxed".
    """

捕获不是「把 CUDA 调用记录成日志」这么轻巧——捕获期间 CUDA 驱动处于特殊状态：不允许 cudaMalloc 等不安全调用（所以 capture_error_mode 默认 global，其他线程也不许乱动）。PyTorch 侧为此专门做了配合：捕获期间分配器的分配行为被改道到一个私有内存池（上面 graphs.py 里的 pool 参数），图内所有张量的地址在捕获时就定死了。

为什么回放要求静态：回放时驱动按录制好的地址直接执行，输入数据必须写进「同一块地址」再回放，形状变化则意味着 kernel 序列变化，整张图作废。这就是 graphs.py docstring 花大量篇幅讲 static input 的原因——不是 PyTorch 限制多，是 CUDA 捕获机制本身如此。

11.4谁在用：SDPA 的后端选择

显存一章如果不讲一个具体用户，就容易停在分配器数字上。拿 scaled_dot_product_attention（缩写 SDPA）当例子：同一个 sdpa 入口背后有五个实现，Dispatcher（03 章）在这里又一次充当了路由器——只不过这次选哪个 kernel 不看 dispatch key，看运行时的启发式与用户开关：

后端数值表示适用场景
math0万能回退：纯算术组合，无显存优化
flash_attention1主流选择，平铺 tiling 省显存
efficient_attention2memory-efficient 实现（xformers 谱系）
cudnn_attention3新硬件上 cuDNN 实现常更快
overrideable4用户自定义后端的挂钩

枚举本身极简（aten/src/ATen/SDPBackend.h，num_sdp_backends = 5），真正的决策在 sdp_utils.cpp 的 priority_order：

aten/src/ATen/native/transformers/cuda/sdp_utils.cpp — 后端优先级（原文摘录）
cpp// flash_attention V2 is universally faster than efficient_attention and Math
std::array<SDPBackend, num_backends> priority_order(sdp_params const& params) {
  if (!priority_order_init_) {
    priority_order_init_ = true;
    if (check_prefer_cudnn_attention()) {
        const std::vector<int64_t> cudnn_order = {static_cast<int64_t>(at::SDPBackend::cudnn_attention),
                                                  static_cast<int64_t>(at::SDPBackend::flash_attention),
                                                  static_cast<int64_t>(at::SDPBackend::efficient_attention),
                                                  static_cast<int64_t>(at::SDPBackend::math)};
        at::globalContext().setSDPPriorityOrder(cudnn_order);
    }
  }
  return at::globalContext().sDPPriorityOrder();
}

读法：默认优先级 flash > efficient > math，满足条件的设备把 cudnn 提到最前。实际执行哪个，还能被 torch.nn.attention.sdpa_kernel 上下文管理器强行限定——排查性能问题时，先确认「跑的到底是哪个后端」比调参数更有用。

演进痕迹 这个「一个入口五个后端」的 API 形态本身值得记一笔：早期版本 attention 是 flash_sdp / mem_efficient_sdp 等分散入口，后来才收敛成 scaled_dot_product_attention 单入口加内部路由。API 收敛、实现分散，是 PyTorch 这类框架的常见演化方向——10 章 torch.compile 的「一入口多编译后端」也是同一模式。

11.5要点

显存一章的三件事：分配器把 free 变成账面操作（所以显存曲线不跌）；碎片有两个治理选项，对症才有效；CUDA Graphs 用「录制-回放」换 launch 开销，代价是要求形状与地址静态。三件事背后是同一个事实——PyTorch 在 Python 层之下，对 GPU 内存和 kernel 执行各管了一层自己的机制。

要点 单机显存管好后，下一道坎是几台机器怎么像一个机器那样训练：梯度在设备间怎么传、参数怎么切。第 12 章从 c10d 通信层讲到 FSDP2。
