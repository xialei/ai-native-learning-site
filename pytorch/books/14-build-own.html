自研路线：读完之后，把每一层变成里程碑

前十三章按依赖顺序拆了 PyTorch 的每一层。这一章换个方向：如果你要自己造一个「迷你 PyTorch」——为自己的加速器、自己的训练平台——各层该按什么顺序做、每层最小做到什么程度算完成。同时给出 PyTorch 官方预留的扩展点：很多「自研」其实只需要注册，不需要重写。

14.1先分清：注册就能做，还是必须重写

PyTorch 的扩展点从轻到重排成一个序列，多数需求落在前三档，不必动源码：

扩展档位API能做什么对应章节
注册新算子torch.library.define / impl（library.py/:776）自定义算子挂进 dispatcher，与内置算子同权03
注册 fake/求导规则torch.library.register_fake（library.py）让新算子过 Dynamo/compile、自动求导03/04
Python dispatch 挂钩__torch_dispatch__ / __torch_function__拦截所有算子：DTensor、稀疏、量化都走这里03/12
替换编译后端torch.compile(backend=...)换掉 Inductor，自定义图到代码的编译09/10
新后端接入PrivateUse1 dispatch key + 注册器让 PyTorch 跑在新硬件上03

第三方的「PyTorch 生态」基本都是这些档位上的实现：替换后端的例子是各种推理编译器，新后端接入的例子是各家 AI 芯片的插件，Python 挂钩的例子是 12 章 DTensor 本尊。动手之前先在这张表里找到自己的位置，能省掉大量重复工作。

torch/library.py — 自定义算子的入口（原文摘录）
pythondef define(qualname, schema, *, lib=None, tags=()):
    r"""Defines a new operator.

    In PyTorch, defining an op (short for "operator") is a two step-process:
    - we need to define the op (by providing an operator name and schema)
    - we need to implement behavior for how the operator interacts with
    various PyTorch subsystems, like CPU/CUDA Tensors, Autograd, etc.

    This entrypoint defines the custom operator (the first step)
    you must then perform the second step by calling various
    ``impl_*`` APIs, like :func:`torch.library.impl` or
    :func:`torch.library.register_fake`.
    """

docstring 里那句「两步走」就是 03 章 dispatcher 的注册模型：define 只往 OperatorEntry 登记名字和 schema，impl 往具体的 dispatch key（CUDA、Meta、PrivateUse1……）挂 kernel。一个算子可以有一个 CUDA kernel 加一个 fake kernel，两者由 dispatcher 自动路由。

14.2自研「迷你 torch」的里程碑

如果目标不是扩展而是自研（比如为新加速器建整条栈），前十三章的每一层就是一张里程碑清单。顺序按依赖排，每一档都有「最小正确」标准：

里程碑最小正确标准参考源码
张量与存储分离多 tensor 共享一份 storage；view 不拷贝数据02 章 TensorImpl/StorageImpl
dispatch 表同一 op 按设备/dtype 路由到不同 kernel；有可插拔位03 章 OperatorEntry
自动求导前向记录 Node/Edge；反向按依赖计数执行（不是栈遍历）04/05 章 Node、Engine
Module 与优化器参数注册走统一入口；optimizer 持参数引用而非拷贝06/07 章
数据管道worker 预取；关停不挂死08 章 DataLoader
编译/融合（可选）先做算子级融合；缓存编译产物10 章 Scheduler
显存池（可选）释放变账面操作；OOM 降级路径11 章 CachingAllocator
分布式（可选）布局声明与通信分离；all-gather 批处理12 章 DTensor/FSDP2

两个排序原则值得展开。第一，「反向引擎按依赖计数」出现在第 3 里程碑而不是更低——05 章讲过 GraphTask 的 dependencies_ 计数是多分支图的唯一正确执行序，先写成递归栈遍历的框架，在遇到分支合并时会整体返工。第二，编译和显存池标为可选，因为它们的门槛在调参和测试基建，而不在核心算法：没有 profiling 基建（13 章）之前做 autotune，是蒙着眼调。

困惑点 自研框架最常见的失败顺序是反着来：先写分布式，再补自动求导。结果是每一层都建立在「假设下层可换」的接口上，最后发现 04 章的 AutogradMeta 和 12 章的 Placement 需要共享同一份元数据，接口合不拢。PyTorch 自己的演化史（autograd 元数据长在 TensorImpl 上、DTensor 长在 dispatch 上）说的就是这件事：层的边界先于层的实现。

14.3离线部署：export 与 AOTInductor

训练框架的最后一公里是导出：把 Python 里的动态图变成可以在无 Python 环境部署的产物。PyTorch 的答案分两步：

第一步 torch.export（torch/export/__init__.py）：跑一遍模型，产出 ExportedProgram——一张规范化为 functional ATen 算子的图，Python 控制流已被消除，形状假设作为约束记录在案（docstring 的 Soundness Guarantee 一节原话：ExportedProgram 被视为有效，当且仅当这些假设成立；假设验不过直接 fatal error）。这是 09 章 Dynamo 的延伸：同一个追踪引擎，产出从「可回退的编译缓存」变成「不可回退的部署产物」。

第二步 AOTInductor（torch/_inductor/__init__.py 的 aoti_compile_and_package）：把 ExportedProgram 直接编成 C 代码/CUDA 代码，打进 .pt2 包，加载方（aoti_load_package，:257）不依赖 Python。10 章讲过 Inductor 管线的三站，AOTInductor 就是把这条管线的产品从「Python 侧的编译函数」改成「提前编译的原生产物」——省掉的正是部署机上没有的那份编译开销和 Python 本身。

为什么 export 要单独一个 API 而不直接用 torch.compile：两者的容错语义相反。compile 编不动时回退 eager，保证「能跑」；export 遇到图化不了的结构直接报错，保证「产物完整」。一个面向训练时的性能，一个面向部署时的确定性——同一条追踪管线，两种失败策略。看懂这个分工，就明白为什么两个 API 长期共存。

14.4全书回顾

十四章的路线合起来看是一条因果链：因为 Tensor 与存储分离（02），dispatch 才有单点可插拔（03）；因为 dispatch 单点，autograd 才能挂在其中一条 key 链上（04）；因为图记录完整，反向引擎才能按依赖并行（05）；Module、优化器、数据加载（06-08）是纯应用层，随时可换；Dynamo 和 Inductor（09-10）站在 dispatch 和字节码两个边界上做编译；显存与 CUDA（11）和分布式（12）放大规模；工程四件套（13）保证跑得久；最后所有层都能从 14.1 的表里找到扩展位。

读源码的意义在最后收口：PyTorch 1500 万行代码里，多数是算子实现和测试，核心机制——上面这条因果链——不过十来个文件。知道哪十来个，读「大仓库」和读「小项目」就没有区别。

要点 全书的十来个核心文件：torch/__init__.py（导入）、c10/core/TensorImpl.h（张量）、c10/core/DispatchKey.h 与 Dispatcher.h（路由）、torch/csrc/autograd/node.h 与 engine.cpp（反向）、torch/nn/modules/module.py（模块）、torch/optim/adam.py（优化器）、torch/utils/data/dataloader.py（数据）、torch/_dynamo/eval_frame.py 与 torch/_inductor/compile_fx.py（编译）、c10/cuda/CUDACachingAllocator.cpp（显存）、torch/distributed/tensor/_api.py（分布式）。每章的第一个摘录几乎都出自这里。
