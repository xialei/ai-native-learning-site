Tensor 内部：一个张量被拆成了三块

Python 里的 torch.Tensor 看起来是一个对象，C++ 里其实是三块：元信息一块、数据一块、版本号一块。这个拆分解释了 view 为什么近乎免费、detach 为什么不碰数据、原地修改为什么能被 autograd 察觉。这章把三块拆开讲。

2.1为什么不是一个对象

如果让你设计 Tensor，最自然的写法是一个类：形状、数据指针、步长都放里面。PyTorch 早期（TH 那一代）确实接近这个形态，但按这个形态演进会接连撞上三堵墙：

  • 数据想共享。x.view(-1)、x[0:5]、x.t() 都不该拷贝数据——所以「数据」必须是一个能被多个 tensor 同时指着的东西。
  • 元信息想独立变化。两个 tensor 可以共享同一块数据却有不同形状（view）、不同偏移（切片）。形状/步长/偏移的生命周期和数据的生命周期不同步。
  • 版本计数想跨 tensor 共享。autograd 要发现「我保存的中间结果被原地改了」，可 view 和原 tensor 共享数据，改谁都算改同一个——版本号也得跟着数据走，而不是跟着单个 tensor 走。

三堵墙推出同一个结论：拆。PyTorch 的拆法是三块，全在 c10/core 下：

TensorImpl：元信息 + 两个指针 StorageImpl：真正放数据 Python 可见包装
图 2.1：一个 tensor 的三块结构。要点是中间那个 TensorImpl 身上同时攥着两条指针：往右指向数据（StorageImpl），往下指向版本计数器（VariableVersion）。view/切片产生的新 TensorImpl 换掉元信息、共用数据和版本号——这就是「拆开」的全部动机。

2.2TensorImpl：元信息那一块

TensorImpl 是 PyTorch 里被摸得最多的 C++ 类——每一次算子调用都要读它的形状、dtype 和 key_set。类声明很长（实现文件三千多行），但字段可以归成四组：

c10/core/TensorImpl.h — 类声明开头（摘录，注释为译注）
cppstruct C10_API TensorImpl : public c10::intrusive_ptr_target {
  TensorImpl() = delete;
  ~TensorImpl() override;

  // Note [Enum ImplType]
  // This enum is temporary. In the followup refactor we should
  // think about how to specialize TensorImpl creation for view
  // tensors. Currently we only special case its key_set_ but
  // there's also potential to share version_counter_ directly
  // without creating first and then override in as_view.
  enum ImplType { VIEW };

四组字段，按「算子调用时被谁读」排：

字段组内容谁在用
形状信息sizes_、strides_、storage_offset_、numel_、is_contiguous_ 等缓存位每个算子；切片/reshape 只改这组，不动数据
类型与设备data_type_（TypeMeta，即 dtype）、device_opt_dispatcher 选 kernel、分配内存
分发标签key_set_（DispatchKeySet）dispatcher——第 3 章的主角
引用storage（指向 StorageImpl）、version_counter（指向 VariableVersion）数据读写与原地修改检测
一个值得停下来看的细节：构造函数被显式 = delete 了——不留一个「空 tensor」的默认态。源码里紧挨着有一句注释：打算消灭所有「未初始化状态」，让每个 tensor 一出生字段就是全的。一个被删掉的默认构造函数，是整个类的设计态度。

再往下是 storage_offset，切片功能的承重墙：

c10/core/TensorImpl.h — storage_offset（摘录，注释为译注）
cpp  /**
   * Return the offset in number of elements into the storage that this
   * tensor points to.  Most tensors have storage_offset() == 0, but,
   * for example, an index into a tensor will have a non-zero storage_offset().
   *
   * WARNING: This is NOT computed in bytes.
   */
  int64_t storage_offset() const {
    // TODO: maybe this should be toggled by strides
    if (C10_UNLIKELY(matches_policy(SizesStridesPolicy::CustomSizes))) {
      return storage_offset_custom();
    }
    return storage_offset_;
  }

x[3:5] 之所以不拷贝：新 TensorImpl 的 storage_offset_ 是 3、形状是 (2,)，数据还是原来那块。单位是元素个数不是字节，注释特意用 WARNING 标出——这是写自定义算子时的常见错误来源。

2.3StorageImpl：数据那一块

StorageImpl 短得多。它只回答三个问题：数据在哪（DataPtr）、多长（size_bytes）、怎么释放（Allocator）。

c10/core/StorageImpl.h — 类声明（摘录，注释为译注）
cppstruct C10_API StorageImpl : public c10::intrusive_ptr_target {
 public:
  struct use_byte_size_t {};

  StorageImpl(
      use_byte_size_t /*use_byte_size*/,
      SymInt size_bytes,
      at::DataPtr data_ptr,
      at::Allocator* allocator,
      bool resizable)
      : data_ptr_(std::move(data_ptr)),
        size_bytes_(std::move(size_bytes)),
        size_bytes_is_heap_allocated_(size_bytes_.is_heap_allocated()),
        resizable_(resizable),
        received_cuda_(false),
        allocator_(allocator) {
类声明前残留着一段注释：讲 view 之后 resize 会让数据指针重复、版本计数只按 storage 粒度追踪等坑——都是这个拆分方案的已知代价，被写下来提醒后来的维护者。DataPtr 是个值得记住的类型：它不光是 void*，还带着一个删除器（deleter），「怎么释放这块内存」是跟着数据走的，而不是写死在某处。CPU 上删除器走 free，CUDA 上走 CachingAllocator（第 11 章的主角）。

还有一个命名疑惑值得提前拆掉：C++ 里同时存在 Tensor 和 TensorImpl，训练代码里还见过 Variable。关系是——Tensor 是持有 intrusive_ptr<TensorImpl> 的外壳；Variable 曾是独立类型，2018 年前后和 Tensor 合并，现在的 variable.h 里只剩一行别名：

torch/csrc/autograd/variable.h — Variable 的下落（摘录）
cppusing Variable = at::Tensor;

autograd 代码里满眼的 variable_list，读作 std::vector<Tensor> 即可。历史名字留在签名里，是这一代代码库的常态。

2.4VariableVersion：版本号那一块

第三块最小，也最容易被忽略，直到哪天你被 one of the variables needed for gradient computation has been modified by an inplace operation 报错砸中。那句话的判断依据就在这：

c10/core/TensorImpl.h — VariableVersion（摘录，注释为译注）
cppstruct C10_API VariableVersion {
 private:
  struct VersionCounter : intrusive_ptr_target {
    VersionCounter(uint32_t version) : version_(version) {}
    std::atomic<uint32_t> version_;
  };
  c10::intrusive_ptr<VersionCounter> version_counter_;

 public:
  // Note [Disabled VariableVersion]
  // VariableVersion struct has an intrusive_ptr pointing VersionCounter struct
  // with an atomic variable. Thus `VariableVersion(/*version=*/0)` is not as
  // cheap as we expected. ...
  // Example use cases are:
  //  - Inference tensors don't track version counter, so they'll just always
  //    have disabled VariableVersion.
  //  - In SavedVariable class we override version_counter_ inside its
  //  constructor
  //    so that we can use the cheap constructor there.
  enum Disabled { DISABLED };

机制三句话：每个 tensor 带一个原子计数器；原地修改（add_、relu_……）会把它加一；反向执行时，autograd 对「保存下来的中间结果」核对版本号，对不上就报上面那个错。报错的本质是：反向需要的值，已经和你前向时算的那个不是同一份了。

这个设计里有两个用心的地方。一是 std::atomic：源码上方有一段注释解释为什么必须原子——多线程前向时若无保护，版本计数会引入竞争，反而破坏线程安全。二是 DISABLED 构造：计数器分配堆内存不便宜，而推理场景根本不做原地检测，于是给了条不分配的通路。inference tensor（torch.inference_mode() 的产物）身上就是这条 DISABLED 计数器——它不是「版本号为 0」，是「根本没有计数器」。

困惑点 为什么 view 和原 tensor 会「共享」版本号？因为版本计数器的粒度是 storage（见 2.3 前那段残留注释）：同一块数据上的任何改动都该被看见，无论从哪个 tensor 视角发起。detach 出来的 tensor 同理共享——这就是「detach 后原地改会污染原图」的根源。

2.5view、detach、inference_mode：三块结构的行为对照

三块结构立起来之后，用户侧那些「行为各异」的操作，其实是同几个动作的不同组合。逐个对：

操作TensorImplStorageImplVariableVersionautograd 元信息
x.view(...) / 切片新建（形状/偏移不同）共享共享新 grad_fn，is_view_ = true
x.detach()新建（元信息照抄）共享共享无（切断历史）
x.clone()新建新建新建新 grad_fn（clone 的反向）
torch.inference_mode() 内创建新建新建DISABLED无

两张表的规律一致：除了 clone 这类显式复制，所有便宜操作都只动 TensorImpl。所谓「view 是零拷贝的」，精确含义就是：只分配了一个新的元信息结构，数据和版本号都是指针共享。反过来，TensorImpl 的浅拷贝语义也就有了明确定义——源码里用一整段 NOTE 讲清楚：

c10/core/TensorImpl.h — NOTE [ TensorImpl Shallow-Copying ]（摘录，注释为译注）
cpp  // TensorImpl shallow-copying is used when we want to have two Variables share
  // the same tensor metadata (e.g. sizes / strides / storage pointer /
  // storage_offset), but each with a different autograd history. Example call
  // sites:
  //
  // 1. `var_detached = var.detach()` uses `shallow_copy_and_detach()` to create
  // `var_detached` that shares the same tensor metadata with `var`, but with a
  // completely new autograd history.
  // 2. `var.set_data(tensor)` uses `shallow_copy_from()` to copy tensor
  // metadata from `tensor` into `var`, while keeping `var`'s original
  // AutogradMeta.

这段 NOTE 把 detach 讲到了底：detach = 浅拷贝元信息 + 换掉 autograd 历史，数据与版本号原样共享。所以「detach 出来的张量改了会影响原张量」不是副作用，是定义使然。而 set_data 是另一个方向——保持 autograd 元信息、整体换掉数据本体，优化器里更新参数用的就是它。

回看 2.1 的三堵墙：数据共享（view 不拷贝）、元信息独立（切片改偏移）、版本共享（原地检测跨 tensor）——三堵墙各自对应三块里的一块。当初那个「不就是一个类吗」的问题，到这里可以反过来问了：不分块，这三件事哪一个能便宜地做成？

2.6性能含义：为什么这些设计值得记

最后一节把设计换成数字。日常训练里最常见三类操作的内部成本：

  • view / reshape / 切片：一次 TensorImpl 分配（几十字节级别）+ 一次引用计数加一。与数据大小无关。这就是「reshape 不该出现在性能焦虑里」的依据——慢的是 reshape 后引起的布局变化让后续 kernel 变慢，不是 reshape 本身。
  • .to(device) / .cpu()：跨设备必然拷贝数据，这层省不掉。但注意目标侧的分配走的是 CachingAllocator（第 11 章）——同一尺寸反复传输时，分配成本接近于零，剩下的就是 PCIe/NVLink 带宽本身。
  • inference_mode 的提速：除了免掉反向记录，还免掉了版本计数器的堆分配与原子递增。张量小、算子碎的推理负载里，这笔账能省出可观的 CPU 时间。

还有一条写给要读后续章节的人：第 3 章会讲到 dispatcher 拿 key_set_ 选实现——现在只需要知道，TensorImpl 身上那个 DispatchKeySet 字段，是整个算子分发体系的钥匙。第 4 章的 AutogradMeta 也直接挂在 TensorImpl 上（成员 autograd_meta_，是个可空指针——不需要求导的 tensor 连这块元数据都不分配，算一种零成本优化），这三章正好构成一条完整的链：tensor 是什么 → 算子怎么找到它该跑的代码 → 代码执行时怎么顺手记下反向。

要点 记三块各自的名字和职责就够：TensorImpl 管形状与身份，StorageImpl 管数据，VariableVersion 管改动痕迹。所有「零拷贝」操作都只在第一块上做文章；所有「疑似灵异」的共享副作用，都发生在后两块的指针上。
