Dispatcher：一次 x + y，代码怎么选中 CPU kernel

你在 Python 写 x + y，同一行代码在 CPU tensor、CUDA tensor、no_grad 区、torch.compile 里走的是完全不同的实现。决定「这次调用落进哪个实现」的机制就是 dispatcher。这章从一次调用走完全程，把 DispatchKey、kernel 表、autograd 的挂载点一次讲清。

3.1同一个 add，有几种写法

先列一遍事实。x + y 这一个调用，在不同上下文里需要不同行为：

  • CPU tensor：普通 C++ 循环。
  • CUDA tensor：一次 kernel launch。
  • requires_grad 的 tensor：先记进计算图（第 4 章），再调上面某个实现。
  • no_grad 区：跳过记录，直接算。
  • torch.compile 里：根本不真算，转成图交给编译器。
  • Meta tensor（只有形状没有数据）：不碰数据，只推出输出形状。

六个行为，一套 API。如果靠 if-else 在每个算子里罗列条件，2590 个算子（native_functions.yaml 顶层的 func 数，另有 7 条注释掉的条目）每个都要写一遍、每加一种上下文全部重写。dispatcher 的思路是把「上下文」从算子里抽出来：每个 tensor 自带一组标签（DispatchKeySet），调用时按标签查表。算子作者只注册「我这 Context 下的实现」，不知道也不关心别的 Context 存在。

一段解释设计的话：c10/core/DispatchKey.h 里 BackendComponent 枚举上方的注释值得整段读——它说「backend 这个词通常指真正实现数值计算的那些 handler」，并且强调一个细节：大部分 backend 的枚举顺序没有语义，唯一有意义的场景是多 backend 同时参与 dispatch（比如 CPU 和 CUDA 同时在场时，CUDA 优先级必须更高）。一张表按优先级查行，顺序就是语义——这是后面所有机制的地基。

3.2DispatchKey：tensor 身上的标签

DispatchKey 是一个枚举，但结构上有两截：BackendComponent（CPU、CUDA、Meta……「数字在哪里算」）和叠在它上面的 functionality（Autograd、Functionalize……「算之前/之后要不要做额外的事」）。两者做笛卡尔积，拼出完整的 key 空间：

c10/core/DispatchKey.h — BackendComponent 注释（摘录，注释为译注）
cpp  // These keys don't correspond to individual kernels.
  // Instead, they represent the backends that are allowed to override specific
  // pieces of functionality:
  // - dense kernels (e.g. DispatchKey::CPU)
  // - sparse kernels (e.g. DispatchKey::SparseCPU)
  // - quantized kernels (e.g. DispatchKey::QuantizedCPU)
  // - autograd kernels (e.g. DispatchKey::AutogradCPU)
  // We reserve space in the runtime operator table for this full cross product
  // of
  // [backends in this enum] x [keys below that are explicitly marked as having
  // per-backend functionality]
Dense：真正算数 autograd 系：记录与簿记 其余格位：按需注册
图 3.2：key 空间是 backend × functionality 的网格。一次调用不是「选一个 key」，而是 tensor 的 DispatchKeySet 在网格里点亮若干格，dispatcher 按优先级逐格询问「这格有 kernel 吗」，第一个有 kernel 的格先执行；它干完自己的事（比如记图）后用 redispatch 把调用传给下一格。第 4 章讲的「autograd 记图」就发生在这一格。

ADInplaceOrView原地操作与视图 op 的簿记：bump 版本号、view 的 as_view 登记第 2 章版本计数在这里被加

3.3查表：Dispatcher::call 与 OperatorEntry

机制本体是两个类。Dispatcher 是全局单例，管所有算子；每个算子在它那里有一个 OperatorEntry，其中核心是一张 dispatchTable_——按下标索引的 kernel 数组，下标由 DispatchKeySet 算出。先看热路径，这是全 PyTorch 被执行次数最多的几行代码：

aten/src/ATen/core/dispatch/Dispatcher.h — call 的快路径（摘录，注释为译注）
cpptemplate <class Return, class... Args>
C10_ALWAYS_INLINE_UNLESS_MOBILE Return Dispatcher::call(
    const TypedOperatorHandle<Return(Args...)>& op,
    Args... args) const {
  auto dispatchKeySet =
      op.operatorDef_->op.dispatchKeyExtractor()
          .template getDispatchKeySetUnboxed<Args...>(args...);
  // （调试分支省略：show_dispatch_trace 时打印调用轨迹）
  const KernelFunction& kernel = op.operatorDef_->op.lookup(dispatchKeySet);
#ifndef PYTORCH_DISABLE_PER_OP_PROFILING
  auto step_callbacks =
      at::getStepCallbacksUnlessEmpty(at::RecordScope::FUNCTION);
  if (C10_UNLIKELY(
          step_callbacks.has_value() && op.operatorDef_->op.isObserved())) {
    return callWithDispatchKeySlowPath<Return, Args...>(
        op, *step_callbacks, dispatchKeySet, kernel, std::forward<Args>(args)...);
  }
#endif

四步，每步都有名字：收集——从参数里的 tensor 抽出 DispatchKeySet（tensor 自带，第 2 章那个 key_set_ 字段）；查表——lookup 按这组 key 算下标；观测——profiler 开着才走慢路径（C10_UNLIKELY，正常时一个分支预测就跳过）；调用——执行选中的 kernel。日常调用走的就是这四步，没有比这更多的了。

查表那一半在 OperatorEntry 里：

aten/src/ATen/core/dispatch/OperatorEntry.h — lookup（摘录，注释为译注）
cpp  const KernelFunction& lookup(DispatchKeySet ks) const {
    const auto idx = ks.getDispatchTableIndexForDispatchKeySet();
    if (C10_UNLIKELY(idx == -1)) {
      reportError(ks.highestPriorityTypeId());
    }
    const auto& kernel = dispatchTable_[idx];
    // A valid kernel *always* has a boxed kernel and *may* have an
    // unboxed kernel. However, we typically do unboxed calls in at::
    // APIs, where the kernel 1) will very likely be valid and 2)
    // should have an unboxed kernel. Checking the unboxed kernel
    // first will allow us to avoid touching the boxed kernel at all
    // in the common case.
    if (C10_UNLIKELY(!kernel.isValidUnboxed())) {
      if (!kernel.isValid()) {
        reportError(ks.highestPriorityTypeId());
      }
    }
    return kernel;
  }
两个补充点：其一，idx == -1 的含义是「这组 key 没法映射到单一表格下标」（比如 key set 里混入了不该出现的 alias key），此时报错信息用的是最高优先级的 key——这就是日常见到的 "not implemented for" 报错的真实出处。其二，注释里 boxed/unboxed 的区别：boxed 调用把参数装进通用容器（IValue 列表），任何签名的 kernel 都能接；unboxed 是直连 C++ 签名的快路径。表里常驻 boxed，unboxed 有就先走——这是同一张表上的两级缓存。

3.4一个 key 拦截之后：redispatch 链

图 3.2 里「记图后 redispatch」那一步是理解整个体系的关键。Autograd key 的 kernel 干完记录工作后，调用并没有结束——它带着同一组参数继续问下一优先级的 key。这个动作叫 redispatch：

aten/src/ATen/core/dispatch/Dispatcher.h — redispatch 声明（摘录）
cpp  template <class Return, class... Args>
  Return redispatch(
      const TypedOperatorHandle<Return(Args...)>& op,
      DispatchKeySet currentDispatchKeySet,
      Args... args) const;

redispatch 与 call 的差别在 key set 从哪来：call 每次从参数重新收集；redispatch 收到的是调用方算好的集合——autograd kernel 调它之前，已经把自己那一位掐掉，查表自然落到下一格。这个「key set 随调用下传、每层掐掉自己那一位」的约定在源码里有个专门的注释（Note [Plumbing Keys Through The Dispatcher]，boxing/BoxedKernel.h，起因是省掉每次 redispatch 都重读线程局部变量的开销）。一条调用链就这样串起来：Functionalize（如注册）→ Autograd（记图）→ ADInplaceOrView（版本号/视图簿记）→ Backend（真算）。每一层只做自己的事，做完交棒。

困惑点 为什么 autograd 不是「在算子完成后由引擎回调」，而要占一个 dispatch key？答案在性能与组合性：记图必须发生在真正计算之前（要保存输入、构造 Node），而且必须对 2590 个算子统一生效。放一个 key 在链路最高优先级段，恰好同时满足这两条——每个算子的 autograd kernel 由 derivatives.yaml 生成（第 4 章），数学实现则完全不感知 autograd 的存在。分层注册 + 顺序拦截，比在每个 kernel 里写「如果 requires_grad 就……」便宜得多。

no_grad 的实现现在也一眼可见了：torch.no_grad() 只是把 GradMode 置关（一个 thread-local 布尔，c10/core/GradMode.h 全文不到百行）。Autograd key 的 kernel 进来先问一句 GradMode——关着就不记图，直接 redispatch 到 backend。一层薄开关控制一层行为，层与层之间零耦合。

3.5用户可插的两层：torch.library 与 __torch_dispatch__

dispatcher 不只是内部机制，它就是 PyTorch 的插件系统。给用户留了两个层级的入口，位置不同、用途不同。

算子级：注册一个新 op 的 kernel。这是写自定义 CUDA 算子、接 NCCL 之外通信原语的标准做法，第 14 章展开用法；这里只看它落在机制的哪个位置：

torch/library.py — register_fake（摘录）
pythondef register_fake(
    op: _op_identifier,
    func: Callable | None = None,
    /,
    *,
    lib: Library | None = None,
    _stacklevel: int = 1,
    allow_override: bool = True,
):
    r"""Register a FakeTensor implementation ("fake impl") for this operator.

    Also sometimes known as a "meta kernel", "abstract impl".
    ...
    """

所谓 fake impl，就是往 Meta backend 的格子里填函数——「只推形状不真算」因此成为一种注册行为。第 10 章 Inductor 里那些「影子执行」全都踩在这格上。

tensor 级：子类化拦截一切调用。Python key 让整个 tensor 子类（如第 12 章的 DTensor）接管 dispatcher：

torch/overrides.py — __torch_function__ 的位置（文件头注释，摘录）
python"""
Python implementation of ``__torch_function__``

While most of the torch API and handling for ``__torch_function__`` happens
at the C++ level, some of the torch API is written in Python so we need
python-level handling for ``__torch_function__`` overrides as well.
...（后文指向 functional.py 与 test_overrides.py 的指引及 NumPy 渊源说明，略）
"""
两个入口怎么选：想把「某一种数学」接到新硬件上——注册 op（算子级，C++ 层，快）；想把「一类 tensor 的所有行为」都改掉——子类化（tensor 级，Python 层，灵活但每次调用多一层）。DTensor 选的是后者，因为它要拦的不是某个算子而是「分片状态下所有算子的语义」（第 12 章细讲）。

3.6回顾与下一章的接口

把这章的机制压回三句话：tensor 带着 DispatchKeySet；dispatcher 按优先级查表选中 kernel；kernel 干完自己的事可以 redispatch 给下一层。autograd、 Functionalize、DTensor、自定义 op，全部是往这张表的不同格子里填东西—— PyTorch 的「可扩展」说的就是这张表的可扩展。

下一章进表里最核心的那个格子：Autograd key 的 kernel。它由 696 条 YAML 规则生成，工作只有一个——前向执行的瞬间，把「反向该怎么算」写进一张图。

要点 一次 x + y 的完整链路：Python 绑定（torch._C）→ Dispatcher::call 抽 DispatchKeySet → OperatorEntry::lookup 查表 → 逐优先级执行（autograd 记图 → inplace 簿记 → CUDA kernel）。谜底没有超出一行摘要的范围：一张二维表和几行 inline 代码。
