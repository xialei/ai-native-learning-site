整体架构：没有「内核」的 Agent 运行时

dsh 最反直觉的一点是它没有特权核心——LLM 适配器、会话存储、工具、甚至 Agent 循环本身，都是挂在同一个插件容器上的插件。这一章我们把整台机器拆开：先看插件框架 Cordis，再看一个进程如何被装配出来。

1.1一分钟版本

  • dsh = Cordis 插件框架 + 一组插件 + 一个装配器（profiles/bundles）。
  • Cordis 只提供三件事：服务仓库（ctx.<key>）、类型化事件总线、可逆副作用（ctx.effect()）。
  • 每个产品能力都是一个插件，通过声明 inject 依赖别的服务、通过事件与别人通信，卸载时副作用自动回卷。
  • 启动 = 按层叠加配置行：bundle（按序）→ profile patch → home patch → --patch，同 id 后写者整行替换。
  • 想让 dsh 长出新能力？不是 fork 内核，而是「在别人旁边再挂一个插件」。
为什么这样设计：Agent 运行时的需求变化极快（新工具、新模型、新沙箱、新 UI），fork 内核的扩展方式会让每次升级都变成合并冲突。把「机制」全部下沉到插件框架，「策略」全部放到插件里，升级就变成重新装配。

1.2Cordis：五个核心想法

Cordis 是 vendor 进仓库的插件框架（docs/cordis-primer.md），它把插件系统压缩成五个想法：

想法含义dsh 里的例子
插件即服务插件是带 inject/apply(ctx) 的对象，向上下文贡献能力dsh-llm、dsh-tool-fs、dsh-compaction-basic
上下文即仓库服务认领稳定的 ctx.<key>，消费者按 key 找服务而不是 import 具体实现ctx.tools、ctx.llm、ctx.sessions
声明式依赖inject: ['tools'] 等到服务存在才激活，代替手工启动顺序工具插件等待 tools 注册表
类型化事件通过 TS declaration merging 声明事件名，5 种派发模式agent/pre-step（waterfall）、session/event（emit）
可逆副作用Prompt 段、工具 schema、适配器、监听器都经 ctx.effect()/ctx.on() 安装，卸载即回卷热重载插件时提示词与工具目录同步消失

五种事件派发模式

派发模式是事件公共契约的一部分（源码用 @mode 标签标注，生成目录会校验声明与派发点一致）：

模式是否等待顺序返回值dsh 中的用途
emit否按注册顺序观察无session/event 广播、tool/result
waterfall否（顺序）按注册顺序有agent/pre-step、agent/request、tools/pre-execute
parallel是（并发）并行无遥测、副作用广播
serial是（顺序）按注册顺序有agent/turn-stopping
bail否按注册顺序，直到有人 bail有短路型策略判断
关键 waterfall 是环绕中间件：监听器拿到 (...args, next)，调用 next() 把（可包装的）结果委托给下一个服务，不调用直接返回即短路。对「单一决策」类事件，短路就是设计意图——策略监听器可以独占决策，只观察的监听器必须委托。prepend: true 只在必须先于普通注册执行时使用。

1.3用代码看：一个插件长什么样

插件可以是「带可选字段的函数」，也可以是 Service 子类。下面是 dsh-base 装配里典型的行（packages/bundle/base/cordis.patch.yml）——注意 !!js 表达式：config 在插件上下文中求值，disabled 在每次挂载决策时对 loader 上下文求值：

packages/bundle/base/cordis.patch.yml
yaml- insert:
    # 沙箱模式默认由环境变量决定，回退 workspace-write
    - id: sandbox-policy
      name: '@deepseek-ai/dsh-sandbox-policy'
      config:
        mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
        workspaceRoot: !!js process.cwd()

    # 平台差异用 disabled 表达：同一行代码，Windows 上换 pwsh
    - id: bash-sandbox
      name: '@deepseek-ai/dsh-bash-sandbox'
      disabled: !!js process.platform === 'win32'
      config:
        timeoutMs: 60000

    - id: pwsh-sandbox
      name: '@deepseek-ai/dsh-pwsh-sandbox'
      disabled: !!js process.platform !== 'win32'

    # 审批策略与沙箱模式联动：全放开时不再询问
    - id: approval
      name: '@deepseek-ai/dsh-user-approval'
      config:
        policy: !!js "(process.env.DSH_PERMISSION_MODE ?? 'workspace-write') === 'danger-full-access' ? 'never' : 'ask'"
读法：每一行 {id, name, config} 就是一次插件挂载。patch 按 id 定位并整行替换 config（不合并）——所以「按模式取值不同」的行不属于共享 base，而属于各自的 mode bundle。这就是后面 profiles 一节「层与层只谈 id」的物理基础。

插件本体则藏在 name 指向的 npm 包里。下面是权限预设插件注册的三档预设，同一个文件再往下几十行（packages/bundle/base/cordis.patch.yml）：

packages/bundle/base/cordis.patch.yml — permission presets
yaml    - id: permission
      name: '@deepseek-ai/dsh-permission-presets'
      config:
        presets:
          read-only:
            sandbox: read-only
            approval: ask
          workspace-write:
            sandbox: workspace-write
            approval: ask
          danger-full-access:
            sandbox: danger-full-access
            approval: never
注意：沙箱模式（文件影响范围）与审批策略（问不问人）是两个正交维度，预设把它们打包成一条配置。第 9 章安全篇会展开这两个维度各自的机制。

1.4Profiles 与 bundles：一个进程的装配过程

dsh 所有形态都从同一个 CLI 启动（apps/cli/package.json 中 "bin": {"dsh": "lib/bin.js"}），差别只在 --profile：

命令用途在 dsh-base 之上追加
dsh web本地 Web UI（--profile web 的别名）dsh-web-app：浏览器应用 + HTTP 服务
dsh --profile headless "任务"一次性运行器，无服务器dsh-headless
dsh --profile sdkSDK JSON-RPC 服务器（TS/Python SDK 连这里）dsh-sdk-app
dsh --profile sdk-minimal独立精简 SDK 树（唯一不用 dsh-base 的形态）dsh-sdk-minimal（自带完整树）
dsh --profile acp仅自动化场景的 ACP 服务器dsh-acp-app

装配顺序固定为（docs/architecture.md）：

  1. profile 的 package.json 里 dsh.profile.bundles 列出的每个 bundle，按声明顺序；
  2. profile 自己的 cordis.patch.yml；
  3. home 级 cordis.patch.yml；
  4. 命令行 --patch 覆盖层。
哪些层 live 热重载：自定义 profile 默认 live 热重载；web 也是 live。而 headless/sdk/sdk-minimal/acp 只在启动时应用所有层——一次性或 stdio 应用在接活之后再换依赖，生命周期就作废了。这个行为在 v0.1.6 里换了一个拥有者：早期版本由 ProfileTemplate 上的 patchReload 字段按 profile 声明，现在该字段已删除，重载生命周期整体归 packages/boot/hmr（dsh-hmr）管——它在 base bundle 里注册（disabled: !!js "!ctx.get('profileContext')"），profile 在场才启用；监听 profile 的 manifest 与两个 patch 文件（profile 自己的 + home 级），变更后经 reconcileProfilePatches（hmr/src/index.ts:230）重新应用 patch 层；headless/sdk/acp 的 bundle 显式加一行 hmr / disabled: true 关掉它。语义没变，「声明在哪个 YAML 行」变了。

v0.1.6 还给 base 带来了两个新的管理面行（在 base patch 的 insert 列表最前面）：

packages/bundle/base/cordis.patch.yml:16 — 插件管理与热重载行（节选）
yaml    - id: tool-plugin-manager
      name: '@deepseek-ai/dsh-plugin-manager/tools'
      disabled: true                     # 模型侧工具，出厂关闭，预设行可开

    - id: plugin-manager
      name: '@deepseek-ai/dsh-plugin-manager'
      disabled: !!js "!ctx.get('profileContext')"   # 有 profile 才启用

    # Profile configuration reloads by default; module roots are opt-in.
    - id: hmr
      name: '@deepseek-ai/dsh-hmr'
      disabled: !!js "!ctx.get('profileContext')"
      config:
        root: []                        # 默认只监听配置，不监听模块源码
三行三种开关姿势：tool 行用静态 disabled: true（工具默认不出场，cordis 预设或用户 patch 打开）；service 行用 !!js 表达式按运行时事实（profileContext 在不在）决定；hmr 行再叠一层 config——root: [] 表示 profile 配置重载是默认行为，模块源码热替换是可选项（要在 profile patch 里写 root: ["."]）。同一个 YAML 文件里三种声明粒度，值得对照着读。

dsh-base 是 web/headless/sdk/acp 共享的第一层。它的 patch 文件头注释把这一层的自我定位讲得很清楚（packages/bundle/base/cordis.patch.yml 开头）：

packages/bundle/base/cordis.patch.yml（文件头注释）
yaml# The dsh-base bundle patch: the shared core of each base-backed profile, applied as
# ONE insert over the empty profile root. Later bundle patches and the user's
# profile cordis.patch.yml address these rows by id, with the last write
# winning per row.
#
# A patch replaces the targeted row's whole `config` rather than merging into
# it, so a row whose value differs by mode does NOT live here: it belongs to
# each mode bundle, keeping any single row down to one bundle layer plus the
# user's. Mode-specific rows appear below only with shared plugin identity and
# neutral defaults; each mode bundle restates its complete configuration.
#
# Row order carries no load semantics (activation is service-availability
# driven); the grouping is for readers.
三件事：① 整个 base 是一次 insert；② 后续层按 id 寻址、同 id 整行替换（last write wins per row）；③ 行顺序不承载加载语义——激活由服务可用性驱动，分组只是给读者看的。

装配完成后，可以用一条命令看到自己机器上真实的插件树：

shell
dsh --profile web --dump-config
审计入口：打印出的任何一行都可以被你自己的 patch 替换。排查「我的配置为什么没生效」时，第一件事就是 dump-config 看该行的最终 config 是谁写的。

v0.1.6 补上了装配面的最后一块拼图：插件不用手编 YAML 也能管。packages/boot/plugin-manager 提供 plugin_manager 工具（六个 action：list_plugins / list_bundles / set_plugin / set_bundle / install_bundle / remove_bundle）与 Web 侧栏的 Plugins 页；dsh <name> 命令行简写也落在同一条命令族里——CLI 把首个非选项、且不等于 plugin 的位置参数展开成 --profile <name>（apps/cli/src/args.ts:186-189），所以 dsh myprofile 等价于 dsh --profile myprofile，而 dsh plugin … 保留给插件管理子命令。工具侧每一步都要求 danger-full-access 或本次调用的审批（理由串自带 Profile changes persist across sessions; installed Host code runs outside the workspace sandbox）——安装的 Host 代码在进程内、工作区沙箱之外运行，这是它必须过审批的原因。变更写入 profile 自己的 cordis.patch.yml（行级 disabled 覆盖）与 package.json 的 dsh.profile.bundles 列表；一次只允许一个变更（profile 写锁串行化），失败或取消的安装会把 package.json 与 pnpm-lock.yaml 快照回滚（index.ts:57 的 RESTORED_FILES），一批 protected modules（plugin-manager 自己、loader、include、webserver、hmr 等 16 个模块，index.ts:44）禁止被停用——管理面不能拔掉自己的电源。

1.6三种事件域：扩展点坐标系

改任何东西之前，先决定事件落在哪个域（docs/architecture.md）：

域特征何时用例子
会话事件持久事实，追加进日志，经 session/event 广播事实必须在重载后依然成立turn/start、tool/result、todo/write
Agent 事件携带 live Agent（inbox、step、status、request）观察或拦截进行中的工作agent/pre-step、agent/request-error
能力事件把策略/适配器接到缝上，不 import 循环给某条能力缝加策略fs/*、tools/*、telemetry/*
判别法：需要重启后还在 → 会话事件；需要拿到 Agent 对象本身 → Agent 事件；只是把实现接到某个接口上 → 能力事件（往往连监听器都不用写，注册服务即可）。

1.7能力缝：三角色模型

缝（seam）是带三个角色的可替换能力（docs/architecture.md）：

  • Service Definition：声明接口（类型与事件）；
  • Service Provider：实现它；
  • Consumer：使用它——通常是模型可见的工具。

一个包可以兼任多个角色，但单个角色不构成缝；新增一个能力意味着把三个角色都设计出来。规范示例是 shell 执行：

图 1-1 — 能力缝三角色：定义声明接口，提供者实现，消费者（通常是工具）使用。产品级替换发生在中列。
Service Definition（契约）Service Provider（实现，可替换）Consumer（模型侧工具）
要点 「新行为去哪」在 dsh 里有对照表（docs/architecture.md 的 Where new behavior goes 表）：加模型提供者 → 在 ctx.llm 注册适配器；加模型可见能力 → 在 ctx.tools 注册工具；拦截请求/工具/回合 → 用对应 agent/* 或 tools/* 事件；加持久会话状态 → 扩展 SessionEventMap 并从日志渲染。这些入口全部不需要动循环代码。

1.8对「自研 Harness」的第一个启示

要点 自研 Harness 的 MVP 只需要两块：① 一个能从「模型回复 → 工具调用 → 结果回填」走通的循环；② 一个 append-only 的事件日志作为唯一事实源。 Cordis 的服务仓库、事件域、能力缝是 dsh 为「可扩展性」付出的复杂度——先把最小可用的一版跑通，再决定要不要这么切。下一步进入 第 2 章：会话日志。
