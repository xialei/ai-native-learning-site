沙箱与审批：fail-closed 的两种形态

dsh 的安全模型由两条正交的轴组成：文件沙箱（进程能写哪里）与审批（人是否点头）。两条轴各自 fail-closed，还共享同一套升级编排。这一章看政策解析、后端选择、审批审计对，以及把三者缝起来的 escalation 协议。

9.1一分钟版本

  • 沙箱：ctx.sandboxPolicy 是唯一政策之家（默认 read-only），ctx.sandbox 是执行缝（confine(argv, policy) 返回包过的 argv 或 fail-closed 抛错）。政策与执行分家——一个解析事实，一个做本地进程限制。
  • 三种模式 read-only / workspace-write / danger-full-access 只管文件效果；网络与进程可见性明确排除在词汇表外。
  • 审批：ctx.approval，政策 ask/never；结果封闭联合 allowed-once / rejected / cancelled / unavailable——唯一授权是 allowed-once，且只授权本次调用。
  • 每次 ask 在日志里留下 approval/asked + approval/decided 审计对；必须在 open turn 内（turn 是日志的重放边界）。
  • 模型否认不了沙箱：拒绝统一为 [sandbox: file access denied under …] 标记 + 同轮升级提示，模型可以带着 sandbox_permissions + justification 原样重试一次，由 approveEscalation 严格加宽并先过审批。

9.2政策之家：resolve() 的三层优先级

packages/sandbox/sandbox-policy/src/index.ts:163 — SandboxPolicyService.resolve()
typescriptresolve(request: SandboxPolicyRequest = {}): SandboxExecutionPolicy {
  const { session } = request
  return {
    // 已批准的显式模式 > 会话日志里最后一次 sandbox/mode 事件 > 部署默认
    mode: request.mode
      ?? (session === undefined ? undefined : this.overrideOf(session))
      ?? this.defaultMode,
    // 会话 cwd 是其 workspace-write 边界；配置根仅是 agentless 调用的后备

    ...session === undefined ? {} : { sessionId: session.id },
  }
}
读法：mode: 'read-only' 是配置默认（注释：「fail-safe default; a deployment that wants a workspace-writable agent opts in explicitly」——想要可写必须显式选入）。会话覆盖以 sandbox/mode 事件形式追加进日志，由 sandboxMode 投影折叠（stateVersion 1）。每次执行边界（工具执行前）重新 resolve 一次——executors 和 providers 保持 session-free，事实读取集中在政策之家。

9.3执行缝：confine() 返回 argv，不许静默放行

   * Wrap `argv` so it executes confined under `policy` on this host; the

   */

}

ConfinedArgv 不只返回 argv，还返回三条自描述事实：

packages/sandbox/sandbox/src/index.ts:95 — ConfinedArgv（节选）
typescriptexport interface ConfinedArgv {
  argv: string[]                            // runner, profile, 分隔符, 原始 argv
  /** full | partial —— partial 不得当作 full 用 */
  enforcement: SandboxEnforcement
  /** 本后端的拒绝方言：EROFS(bwrap)/EACCES(Landlock)/EPERM(Seatbelt) */
  denialSignatures: readonly string[]
  /** runner 自身失败的证据规则（区分「没跑成」与「被沙箱挡下」） */
  runnerFailureRules: readonly RunnerFailureRule[]
}
为什么返回方言：消费者的失败分类分两步——先排除 informationalLines、核对 allowedExitCodes 识别 runner 自身失败（命令根本没跑），再匹配 denialSignatures 识别沙箱拒绝（confinement 生效且挡下了它）。「Exit status alone never proves runner failure」。每个后端报告自己的方言，而不是让消费者匹配跨后端联合——「the union claims denials a given backend never produces」。

9.4后端链：探针仲裁，fail-closed 兜底

dsh-sandbox-local 按平台选择 runner 链（packages/sandbox/sandbox-local/src/index.ts 模块注释）：Linux 先 bwrap 后 Landlock；macOS 用 Seatbelt（sandbox-exec）；Windows 用 ACL restricted-token runner。两个关键行为：

  • 功能探针：候选后端先跑一次真实探针（如 bwrap 用 read-only profile 跑 true；Seatbelt 通过 sandbox-exec -p 应用真实 profile），结果有界缓存——「Functional probes arbitrate multi-runner chains and may be skipped for a sole candidate, whose own refusal remains the fail-closed end」。
  • fail-closed：「Missing or unusable confinement fails closed rather than returning the original argv」——confine 不出 enforcing argv 就抛 SandboxUnavailableError（码 SANDBOX_UNAVAILABLE），错误文本直接给出各平台修法建议（装 bubblewrap / Landlock 内核 / sandbox-exec / ACL runner）。

Windows 后端还有一套精密的 SID 设计：写权限 SID 是按 workspace 路径派生的 per-workspace 身份（workspaceWriteSid），其 ACE 每 workspace 一次物化并长存（跨会话复用缓存）；而每个活跃会话有随机私有临时目录 + 自己的 SID（tempWriteSid），dispose 时撤销。该 rung 主动上报 partial enforcement——「WRITE_RESTRICTED must retain Everyone in its restricting list and NTFS hard links alias one file object across paths」。

9.5审批：政策 → answerer 瀑布 → 审计对

packages/interaction/user-approval/src/index.ts:208 — ApprovalService.request()
typescriptasync request(req: ApprovalRequest): Promise<ApprovalOutcome> {
  const session = req.agent.session
  if (!hasOpenTurn(session)) {
    throw new Error(
      'approval.request() outside an open turn: the approval/asked + approval/decided audit pair '
      + 'must be turn-enclosed (a bare event between turns is crash-tail garbage on reload). '
      + 'Ask from inside the turn that needs the decision.',
    )
  }
  const id = ApprovalRequestId(randomUUID())
  session.append('approval/asked', { id, toolName, ...callId, ...reason })
  const outcome = await this.decide(req, session)
  session.append('approval/decided', { id, outcome })
  return outcome
}

四个 fail-closed 细节：① 'never' 政策在派发前短路——注释点明这是为了防 prepend 监听器抢跑，把「never 必然拒绝」的承诺保留在服务自己的路径上；② 无 answerer 时 waterfall 默认值就是 unavailable；③ answerer 返回词汇表之外的野值归一化为 unavailable；④ answerer 抛错同样归 unavailable（「A throwing answerer must fail the QUESTION closed, not the caller's tool call open — the seam contains its callbacks」）。另外两个实现细节值得学：审计对必须在 open turn 内（否则重载时被当成 crash-tail 丢弃）；先进入 Promise 链再派发，同步抛错的监听器也落进同一收容路径。

  // ① 严格加宽是 EXECUTION 检查——schema enum 只是封闭目标词汇表，
  //    生效模式是每次调用的真相
  if (!(WIDER_MODES[effectiveMode] ?? []).includes(mode as SandboxMode)) {
    throw new Error(`sandbox escalation to "${mode}" is not strictly wider than this call's current "${effectiveMode}" mode`)
  }
  if (approval.approver === undefined) throw …  // ② 无审批服务 → 抛错
  if (approval.agent === undefined) throw …    // ③ agentless → 抛错
  const outcome = await approval.approver.request({
    …,
    reason: `escalate sandbox to ${mode}: ${justification}`,
  })
  switch (outcome) {
    case 'allowed-once': return mode as SandboxMode
    // rejected / cancelled / unavailable 各有逐字错误文本，什么都没执行
  }
}
结构学但不依赖：EscalationApprover 是最小结构形状（只有 request 方法），不是 ApprovalService 类型——「the tool layer … closes over ctx.approval.request(...) and hands the closure down, so this package never depends on the approval or agent packages」。WIDER_MODES 阶梯是 read-only→{workspace-write, danger-full-access}、workspace-write→{danger-full-access}；schema enum 固定为完整 ESCALATION_TARGETS 而非按默认模式裁剪——否则一个 danger-full-access 默认部署会让窄模式会话失去升级杠杆。

9.7权限预设：两个旋钮一个选择器

dsh-permission-presets（packages/interaction/permission-presets）把两个独立旋钮打包成命名预设：

预设sandbox 模式approval 政策
workspace-writeworkspace-writeask
danger-full-accessdanger-full-accessnever
custom不匹配任何预设的组合只读回为派生状态 custom——README 现在的说法是「clients show the derived custom state, but users cannot select or persist it」：它只在当前命中时出现在选项列表里，可以切走，不能选中，也不能被命名成表项
bundler 不是 owner：README 明说「It bundles the knobs; execution and approval keep their own values, so removing the package later leaves the last selection in effect」——预设包只是把两件事写进各自的事件，它不拥有任何执行语义；卸掉它，最后的模式与政策原样生效。它就是第 1 章判别法的应用：打包面（UI 概念）与能力面（enforcement）分开。

9.8要点

要点 ① 政策与执行分家：resolve() 三层优先级（显式批准 > 会话事件 > 部署默认），confine() 只认完全指定的政策；② 词汇表刻意小：沙箱只管文件效果，网络/进程可见性排除在外；③ 审批唯一授权是 allowed-once，且 always 一次调用；'never' 在派发前短路；④ 审计对必须 turn-enclosed；⑤ 升级是共享编排：严格加宽 + 结构化审批接口 + 逐字错误文本，两个执行家族（bash/fs）共用同一套。下一步看其他能力缝的实例：第 10 章：能力缝实战。
