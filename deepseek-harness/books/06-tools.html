工具系统与并行调度：一次调用的完整管线

问题：模型说「调用 read(file.txt)」之后发生了什么？这条链要回答四个问题——管线有几段、策略挂在哪（①）？多个工具调用怎么并行才安全，结果会不会乱序（②）？用户中止时，跑了一半的调用怎么收场（③）？模型想批量操作文件时，能不能不靠 N 次往返（④）？6.1 把问题摆出来，6.2–6.3 作答①，6.4–6.5 作答②③，6.6 作答④，6.7 收尾回收。

6.1问题：一次调用的完整链路

工具系统的一切都为了回答：怎么让「模型发号施令」这件事既自由又受控。四个具体问题：

  • ① 一次调用走几段、策略挂在哪——审批、超时、沙箱决策，是写在工具体里还是外置？
  • ② 并行怎么才安全——N 个调用同时跑，日志里结果顺序跟谁走？
  • ③ 中止/失败怎么收场——已派发的、未派发的各归哪里？
  • ④ 批量操作要不要 N 次模型往返——有没有一次往返完成整段程序的办法？

速览答案：① 五段管线（pre-execute → 守卫 → execute → 工具体 → post-execute → finalize），策略全部外置为监听器/注册项，工具体零策略（6.2–6.3）；② parallel-safe 进滚动窗口池、exclusive 成栅栏、结算永远按模型顺序（6.4）；③ 已开始的排空提交、未开始的补合成错误结果，全部落日志（6.5）；④ PTC：一个 run_code 程序在代码里编排所有工具调用，子调用走完整管线（6.6）。

ToolDefinition 的可选成员（packages/core/tools/src/index.ts）：① finalizeContent(exec, result)（:258）——模型可见内容的同步末段变换，注册表在执行开始时快照回调，即使管线失败路径也恰被调用一次；② projectContent(exec, result)（:246）——新于 finalize 的一级：在进入 post-execute 之前跑（finalizeContent 在其后、恰在无损物化前），管线失败绕过 post-execute 时 projection 被跳过而 finalize 仍被调用；③ timeoutMs ——协作超时预算，由独立的 tool-call-timeout-policy 插件经 tools/execute around 包装强制，永不发给模型（schemas() 白名单只有 name/description/parameters）；④ isConcurrencySafe(args) ——只有返回 true 才加入并行组，省略/异常/非 true 一律独占；⑤ presentCall/presentResult ——UI 卡片渲染，纯函数、可在流式与重放两处调用。

6.3① 五段管线

图 6-1 — 工具调用管线。pre-execute 与 post-execute 是 waterfall，execute 是 around 中间件；失败与拒绝都终到同一种持久事实：tool/result。
输入 / 工具体管线阶段（单调守卫是同步注册项，其余为事件缝）持久化终点异常路径（虚线）
PreToolDecision：pre-execute 的监听器（审批 UI、沙箱策略）返回决策；拒绝发生在这一段。决策是封闭四元联合（packages/core/tools/src/index.ts:606）：allow / deny{reason, info?} / cancel / ask——cancel 与 deny 不同：它不携带拒绝理由，落成规范的中止结果 toolAbortedBeforeDispatchResult()（工具体从未派发，但没有 policy-denial 的呈现语义——取消不是拒绝）。通过后由单调守卫（monotonic guards，packages/core/tools/src/index.ts:730）做注册层拒绝——守卫是 scope 层上的同步注册项（ToolGuard，不是事件），在扩展性 policy 全部跑完之后、工具体之前评估；它只能返回拒绝理由或 undefined，没有「允许」这个返回值，所以监听器顺序无法把拒绝翻回放行，第一个拒绝生效且不可被后续注册复活。tools/execute 是 around：next() 返回下一段结果，监听器可替换信号（超时策略就是这样融合 abort 的）。

6.4② 调度器：并行组与独占栅栏

核心在 packages/core/agent-loop/src/tool-calls.ts 的 executeToolCalls。分组规则只有三行：

packages/core/agent-loop/src/tool-calls.ts — 分组
typescript  let next = 0
  let concluded = false
  while (next < planned.length) {
    // 先提交再重新分类，让注册表变更影响尚未开始的调用。
    const first = planned[next]!
    const mode = ctx.tools.executionMode(first.exec).kind
    const group = mode === 'parallel' ? planned.slice(next) : [first]   // ← 独占调用自成一组（栅栏）
    const outcome = await runGroup(ctx, turn, step, group, mode, signal, acceptContext)
    next += outcome.consumed
    concluded ||= outcome.concluded
    if (outcome.aborted) {
      for (const call of planned.slice(next)) appendSkippedToolCall(session, turn, step, call.block)
      return { concluded }
    }
  }

组内是一个滚动窗口池：fillPool 把 in-flight 数量顶到上限，Promise.race 逐个收割，每次收割后尝试按序提交：

packages/core/agent-loop/src/tool-calls.ts — runGroup 核心（节选）
typescript  const { maxParallelToolCalls } = ctx.agentLoop.config   // 默认 10（constants.ts）
  const slots: (Slot | undefined)[] = group.map(() => undefined)
  const callSeqs: Array<SessionSeq | undefined> = group.map(() => undefined)
  let nextToStart = 0, committed = 0, started = 0
  let aborted = signal.aborted

  // committed 只沿「连续的模型顺序」推进。
  const commitReady = async (): Promise<void> => {
    while (committed < group.length) {
      const slot = slots[committed]
      if (slot === undefined) break        // 前面的还没完成 → 停在此处等待
      const call = group[committed]
      const result = slot.needsPost
        ? await ctx.tools[TOOL_RUNTIME_SCHEDULER].finalize(slot.exec, slot.result)
        : ctx.tools[TOOL_RUNTIME_SCHEDULER].finish(slot.exec, slot.result)
      appendToolResult(session, turn, step, call!.block, result, callSeqs[committed]!)
      for (const context of result.additionalContexts ?? []) acceptContext(context)
      concluded ||= result.concludesTurn === true
      committed++
    }
  }

  const fillPool = async (): Promise<void> => {
    while (!aborted && nextToStart < group.length && inFlight.size < maxParallelToolCalls) {
      // 有序提交后重读后续模式：注册表变更可以制造栅栏。
      const nextCall = group[nextToStart]!
      if (nextToStart > 0 && mode === 'parallel'
        && ctx.tools.executionMode(nextCall.exec).kind !== 'parallel') break
      await startCall(nextToStart)
      nextToStart++
      await commitReady()
      if (signal.aborted) aborted = true
    }
  }

  try {
    await fillPool()
    while (inFlight.size > 0) {
      const settledIndex = await Promise.race(inFlight.values())
      inFlight.delete(settledIndex)
      await commitReady()
      if (signal.aborted) aborted = true
      await fillPool()
    }
  } catch (error) {
    schedulerFailure ??= { error }
    await Promise.allSettled(inFlight.values())   // 内部失败：排空已派发，不伪造结果，向上抛
    throw schedulerFailure.error
  }
三个值得注意的细节：① 提交先于分类——「重新分类前先提交」保证注册表变更（scope 收紧、插件卸载）能影响未开始的调用；② 模型序结算——commitReady 只推进连续槽位，慢的调用挡住后面所有的结算，但绝不乱序；③ 失败策略二分——内部调度器失败：排空已派发、不伪造结果、向上抛；用户中止：排空已开始 + 给未开始的补合成结果（如下）。

为什么连「没执行」也要落日志：第 2 章的 Model-visible means logged——模型请求了这些调用，历史里必须出现它们的结局（否则供应商 API 在下一轮会拒绝悬挂的 tool_call）。与第 5 章崩溃恢复的合成结果一样，这些文本本身就是写给模型看的操作指引。

6.6④ PTC：程序化工具调用

dsh 最有特色的模式之一：mode: 'native' | 'ptc' | 'both'（packages/core/tools/src/index.ts:670）。PTC 模式下模型不再直接调用工具，而是调用唯一的 run_code，在代码里编排所有工具：

packages/core/tools/src/index.ts — PTC 约束
typescriptconst PTC_ONLY_INSTRUCTION = `\`${RUN_CODE_NAME}\` is the only tool you can call directly
— a tool call naming any other tool fails. Reach every tool the SDK declares
below from inside the program.`
要素事实
保留传输run_code（RUN_CODE_NAME）是保留名，参数 {code, description}；不受任何可过滤层（scope/restrict）影响
逐程序控制每次 run_code 可带三个可选控制参数（ptc.ts:108 RUN_CODE_CONTROLS）：timeoutMs（整个程序的耗时预算，覆盖 runtime.timeout 默认/上限才暴露）、sandbox_permissions + justification（本程序一次性更宽的沙箱模式，走 approveEscalation 审批，subject 是 'program'——与 bash 的 'command'、fs 的 'operation' 并列）。输出 schema 带 sandbox{mode, denied, enforcement:'full'|'partial'}，denied 时附加升级提示文本（「approves this complete program for one execution only… Programs are never replayed automatically」）
子调用全管线run_code 里的每次工具调用都走完整五段管线（含审批），携带 parent 令牌标记为子派发
持久事件tool/ptc-dispatch-start 与 tool/ptc-dispatch（两者是独立事件，由 subCallId 配对）；子调用 id 形如 <parent>:ptc:<n>
并发上限maxParallelSubCalls（默认 10），代码里的并行派发进有界队列
执行后端ptc-runtime 缝（ctx.ptcRuntime），生产后端为 fresh Node 进程（dsh-ptc-runtime-node，受会话沙箱策略约束）；信任姿态与 bash 等价
为什么 PTC 把「N 次模型往返」压缩成「1 次往返 + 1 段程序」：模型写一段脚本同时 read 5 个文件再 grep，延迟与 token 都显著下降，而权限模型不变——因为子调用 traverse 同一条审批管线。代价是信任边界与 run_code 代码执行环境等同 bash（第 9 章回到这一点）。

6.7收尾：四个问题的答案

答案回收 ① 五段管线：pre-execute（waterfall，PreToolDecision 四元决策）→ 单调守卫（同步注册项，只能拒绝）→ execute（around，超时融合）→ 工具体 → post-execute → finalizeContent → 冻结 tool/result；策略全部外置，工具体零策略；projectContent（post-execute 前）与 finalizeContent（物化前）两级内容变换分工明确（6.2–6.3）。② 并行：parallel-safe 进滚动窗口池（默认 10）、exclusive 成栅栏、结算只沿连续模型序推进——慢调用挡结算但不乱序（6.4）。③ 中止/失败：已开始的排空提交，未开始的补 TOOL_ABORTED_BEFORE_DISPATCH 合成结果，全部持久化（6.5）。④ PTC：一个 run_code 程序一次往返完成整段程序，子调用走完整管线，权限模型不变（6.6）。下一步进入 第 7 章：LLM 适配层与流式。
