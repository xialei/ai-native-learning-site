Agent 循环实现：ReactLoopAgent 的并发模型

并发场景下的循环怎么保证语义明确？followup/steer/inject/cancel 是同一原语的坐标组合；唤醒靠闩锁不丢；失败靠三层收容不炸驱动器——0.2.0 又补上了第四层：失败的 step 留下的未决工具调用，会先补上保守的错误结果再失败。本章沿这四条线走，最后给出全部事件派发点的总表。

4.1并发下的循环，语义怎么才能推理得动

第 3 章沿时间轴走了一遍 turn/step；这一章换个视角，看循环的「操作系统层」。把任意时刻打向循环的操作列出来——followup、steer、inject、cancel、wake、失败、注册——它们能被推理的前提是：每一条在 idle/running/maintenance 任何组合下都有确定语义。

四个答案先给轮廓，各节展开。注入与取消的语义来自 Phase 三态和「三注入 API 是同一 send 原语的坐标组合」（4.2–4.3）；唤醒不丢，靠的是 wakeRequested 闩锁——maintenance 期间与已中止活动上的唤醒先寄存、收敛点重放（4.4）；失败有四层收容：live 广播 → 持久 turn/end → 未决工具调用的保守结果补录 → 驱动器边界吞掉（4.5，最后这层是 0.2.0 新加的）；注册边界是每个 Agent 一个 Scope，回卷由生命周期所有者负责（4.6）。

idlerunningmaintenance（独占维护）
关键不变量：驱动器（kick）在进入前拥有 running phase、退出后才交还 idle；status getter 把 maintenance 也归为对外可见的 'idle'——维护中不接活，但也不算「在跑 turn」。取消（cancel）通过 AbortController 传递 cause，AbortController 由每次唤醒新建，因此取消天然限定在当前活动内。

4.3用代码看：send() 与三种注入

三个公开 API 都是同一个 send 原语的便捷形式。注意 wakingAfterAbort 的捕获点——在 splice 之前，这样 splice 观察者里的重入 cancel 无法改写分类（packages/core/agent-loop/src/agent.ts 的 send 捕获点）：

packages/core/agent-loop/src/agent.ts
typescript  send(message: UserMessage, target: InboxTarget, wakeup: boolean): void {
    // 唤醒型输入不能加入已被中止的活动，所以改投下一回合。
    // 在插入前捕获，避免 splice 观察者里的重入 cancel 重新分类。
    const wakingAfterAbort = wakeup && this.phase.kind !== 'idle' && this.phase.abort.signal.aborted
    const resolvedTarget = wakingAfterAbort ? 'next-turn' : target
    this.inbox.splice(resolvedTarget, Infinity, 0, [message])
    if (wakeup) this.wakeDriver(wakingAfterAbort)
  }

  followup(input: UserMessage): void {
    this.send(input, 'next-turn', true)
  }

  steer(input: UserMessage): void {
    this.send(input, 'next-step', true)
  }

  inject(input: UserMessage): void {
    this.send(input, 'next-step', false)
  }

  cancel(cause: AgentCancelCause, options: CancelOptions = {}): void {
    if (!options.keepInbox) {
      this.inbox.clear()
      if (this.phase.kind !== 'idle') this.phase.wakeRequested = false
    }
    if (this.phase.kind !== 'idle') this.phase.abort.abort(cause)
  }
APItarget唤醒？语义
followupnext-turn是本回合结束后开启新回合（对话的下一句）
steernext-step是下一步立刻看到（用户打断纠正方向）
injectnext-step否安静排队，等别的消息来唤醒（文件变更通知、skill 内容等）
为什么 abort 后要重分类：唤醒型消息若落在一个已中止的 running 活动里，它不会被消费——放到 next-turn 保证它在下一个回合边界出现，而不是消失在旧活动的收尾里。而 cancel({keepInbox: true}) 保留队列只中止活动，也就是「打断当前动作、保留排队输入」。

4.4用代码看：wakeDriver() 的闩锁

唤醒在「没人在听」时会丢吗？不会——被闩住等重放（packages/core/agent-loop/src/agent.ts 的 wakeDriver 闩锁）：

packages/core/agent-loop/src/agent.ts — wakeDriver()
typescript  /**
   * Start one driver, or latch its wake behind maintenance or an aborted
   * activity. A wake sent while idle always opens its turn boundary, even
   * when its message was cleared; only a latched replay is suppressed when
   * the queue no longer holds the wake.
   * @param wakeAfterAbort - the {@link send} classification, captured before
   *   the inbox insertion so a reentrant cancel cannot reclassify it.
   */
  private wakeDriver(wakeAfterAbort = false): void {
    if (this.phase.kind !== 'idle') {
      // Maintenance 和 aborted 驱动器无法送达唤醒：闩起来在收敛点重放。
      // 存活中的驱动器自己认领排队工作；disposal 永不闩锁，
      // 因此 teardown 不必等待任何模型回合。
      const reason = abortedCancelCause(this.phase.abort.signal)
      if (reason?.kind !== 'disposed' && (this.phase.kind === 'maintenance' || wakeAfterAbort)) {
        this.phase.wakeRequested = true
      }
      return
    }
    const driver = Promise.withResolvers<void>()
    this.activityDone = driver.promise
    this.setPhase({
      kind: 'running',
      abort: new AbortController(),
      turn: this.phase.lastTurn,
      step: 0,
      wakeRequested: false,
    })
    this.loopCtx.agents.withInitiator(this, () => this.kick()).then(driver.resolve, driver.reject)
  }

  async whenIdle(): Promise<void> {
    let activity: Promise<void>
    do {
      await (activity = this.activityDone)
    } while (activity !== this.activityDone)   // 等待期间又有新活动？继续等
  }
三个细节：闩锁只在 maintenance 或「唤醒落在已中止活动」时设置，且 disposed 原因永不闩锁——卸载不等模型回合；判定用 abortedCancelCause()（packages/core/agent-loop/src/agent.ts，第 3 章见过）而不是裸读 signal.reason——原因同样要做形状清洗，避免 Node fetch 自造的带栈 reason 被误当结构化 cause。whenIdle() 的 do-while 是防竞态写法：等待期间 activityDone 被换成新活动的 Promise，就继续等新的那个。每次唤醒都新建 AbortController + 新 running phase，phase.turn 从 lastTurn 续起。

4.5用代码看：kick() 与失败的收容

packages/core/agent-loop/src/agent.ts
typescript  private async kick(): Promise<void> {
    try {
      while (await this.turn()) {}      // turn() 返回 true = 还有排队输入，继续
    } catch (_error) {
      // 已报告的失败与取消在驱动器边界被收纳。
    } finally {
      if (this.phase.kind === 'running') {
        const { turn, wakeRequested } = this.phase
        this.setPhase({ kind: 'idle', lastTurn: turn })
        if (wakeRequested && this.inbox.hasPending) this.wakeDriver()  // 闩锁重放
      }
    }
  }

失败如何「在活体边界被报告」？throwError 先以 agent/error（emit，不等待）发布，再重新抛出交给 kick 的 catch：

packages/core/agent-loop/src/agent.ts — throwError()
typescript  private throwError(error: unknown): never {
    const turn = this.phase.kind === 'running' ? this.phase.turn : this.phase.lastTurn
    const step = this.phase.kind === 'running' ? this.phase.step : 0
    this.dispatch.emit('agent/error', { turn, step, error })
    throw error
  }
containment 三层：错误先经 throwError()（packages/core/agent-loop/src/agent.ts）变成 agent/error 的 live 广播，再抛出、由 turn() 的 catch 折叠成 turn/end {reason: error} 写进会话（finally 里 append），最后在 kick 边界被吞掉（不再向上炸栈）——驱动器永不因为一次失败而死亡，whenIdle() 的等待者也总能等到收敛。注意 live 广播先于持久事实：监听 agent/error 的插件不能在回调里假设 turn/end 已经落盘。

0.2.0 的第四层：未决工具调用的保守补录

四层中的第三层是 0.2.0 新加的。考虑这个序列：assistant 消息带两个 tool-call，第一个工具跑完、结果已落盘，第二个执行到一半时模型流本身失败（或插件抛错）。此时日志里躺着一条没有结果的 tool-call——旧版直接失败，重启后的崩溃恢复会把这回合记为 interrupted 并生成合成的收尾事件；但本进程内的下一步重试看到的会话，是「有一个工具调用永远悬着」。

0.2.0 在 step 的 try 块入口挂了一个 ToolCallRecovery 观察者（packages/core/agent-loop/src/agent.ts），监听本会话的事件流。step 失败时，catch 先把这些未决调用补成保守的错误结果再重新抛出（packages/core/agent-loop/src/agent.ts 的 catch/finally）：

packages/core/agent-loop/src/agent.ts — step 失败时的工具结果补录（节选）
typescript} catch (error: unknown) {
  try {
    for (const event of toolRecovery.results()) {
      this.session.append('tool/result', event.data, {
        surfaceOp: 'append',
        ...event.sourceEventSeqs === undefined ? {} : { sourceEventSeqs: event.sourceEventSeqs },
      })
    }
  } catch (recoveryError: unknown) {
    throw new AggregateError(
      [error, recoveryError],
      'Step failed and its pending tool results could not be recorded',
      { cause: error },
    )
  }
  throw error
} finally {
  stopRecovery()
  this.session.append('step/end', { turn, step })
}
ToolCallRecovery 本体在 packages/core/session/src/repair.ts 的 ToolCallRecovery——同一个小类服务三处：失败的 live step（此处）、中断日志的关闭事件合成（第 5 章）、fork 的种子构建。它只追踪「未决身份」，不保留事件历史：observe() 扫 assistant/message 里的 tool-call 块、tool/call、tool/result 三类事件，turn/step 边界清空登记；results() 按观测到的最新事件续编 seq、复用其时间戳，为每个未决调用生成一条 cause 为 interrupted 的错误 tool/result。生成失败不静默——AggregateError 把原始失败与恢复失败捆在一起抛出，两条事实都不丢。
为什么说「保守」：补录的结果不试图描述真实失败原因（那是 step 失败本身的事，走 4.5 开头那三层），只保证「每个 assistant 发出的 tool-call 都有配对的 result」。会话日志因此始终满足 serialize 阶段的完整性检查（DeepSeek 适配器拒绝「历史以未决工具结尾」的请求，第 7 章 serialize.ts 的 INVALID_REQUEST），失败后的下一个请求不会带着悬空调用去撞供应商的校验。恢复语义（interrupted cause）与崩溃恢复的合成事件完全一致——进程内失败与进程外崩溃在日志形态上不再有区别。

4.6Agent 级 Scope：每个循环实例自己的注册边界

构造函数里两行决定了「每个 Agent 是一个隔离的注册世界」（packages/core/agent-loop/src/agent.ts 的构造函数）：

packages/core/agent-loop/src/agent.ts — 构造函数（节选）
typescript    this.dispatch = agentEvents(loopCtx, this)
    this.scope = createScope(loopCtx, this)
    this.ctx = this.scope.ctx
    this.inbox = new ReactLoopInbox(this.ctx.sessionProjections, session, this.dispatch)
    /* v8 ignore next -- the loop registers its own turnBoundary unit, so the key is always present */
    const lastTurn = this.loopCtx.sessionProjections.stateOf(session, 'turnBoundary')?.lastTurn ?? 0
    this.phase = { kind: 'idle', lastTurn }
    this.runtimeContext = new RuntimeContextProjection(this.ctx, session)
（节选，行内注释为原文注释）三个事实：热路径派发器 agentEvents(loopCtx, this) 构造一次、复用终生，它的文档注释写着它把 agent 主体和 scope carrier 绑在一起，让 scope key 和 payload 里的 agent 不可能分叉；回合计数 lastTurn 不是内存猜的，而是从 turnBoundary 持久投影单元读的——重启后回合号继续递增；派发顺序是「先建 scope 再建 ctx」：this.ctx 就是 this.scope.ctx 本身，没有额外 extend——agent 这个字段由融合派发器在每次派发时注入 payload 与 thisArg，工具侧拿到的 exec.agent 则来自 ctx.agents.requireInitiator()。scope 的注册（第 8 章详述）在驱动器退出后被生命周期所有者回卷。
v0.1.6 的注册位置变化：标准 Inbox 投影（inboxProjectionDefinition）不再由 ReactLoopInbox 构造函数自己注册——构造函数现在是空体，JSDoc 明确要求「registry with the standard Inbox projection registered by AgentLoop」。注册挪到了 AgentLoop 的配置校验末尾（packages/core/agent-loop/src/index.ts，紧跟 turnBoundary 注册），注释原话：「Register only after every config validation above has passed, so a rejected constructor leaves no projection unit behind」——被拒绝的 AgentLoop 构造不在注册表里留下投影单元。这是把「谁注册」从「谁使用」手里拿走：Inbox 只消费投影，AgentLoop 拥有注册时机。读旧代码或旧书时注意这条搬移。

4.8小结

这一章的四个答案可以合成一句话：循环把每种并况都化归到「Phase 三态 + 活动私有 AbortController + 事件日志」这三个结构上。注入与取消是 send 原语在（target × wakeup）坐标上的取值，cancel 的作用域天然等于一个 AbortController 的生命周期（4.2–4.3）；唤醒不丢，是因为「暂时无法兑现」被记成 phase 上的一个布尔，收敛点统一重放，唯 disposal 例外——卸载不等模型回合（4.4）；失败按层次收敛：throwError 的 live 广播 → turn()/finally 的持久 turn/end → 0.2.0 新增的未决工具调用补录（ToolCallRecovery，让进程内失败在日志形态上与崩溃恢复一致）→ kick 边界吞掉，驱动器不死亡（4.5）；注册边界是每个 Agent 一个 createScope(loopCtx, this)，Inbox 投影的注册时机由 AgentLoop 统一拥有（4.6）。下一步进入 第 5 章：持久化与崩溃恢复。
