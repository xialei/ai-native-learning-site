LLM 适配层与流式：封闭词汇表与一条 Messages 直连

问题：模型在进程外、循环在进程内，中间这条 HTTP 流怎么管？具体拆成四个——适配器的公共词汇表怎么定（①）？失败怎么分类才能被机器路由（②）？重试为什么拆成策略与执行两半（③）？DeepSeek 官方适配器怎么把一个请求发出去、收回来（④）？7.1 把问题摆出来，7.2–7.6 逐个作答，7.7 收尾回收。

7.1问题：进程内循环与进程外模型之间，这条流怎么管

前几章的循环一遇到 step() 就要出进程调模型（第 3 章）；dsh 不 import 任何模型 SDK，而是自己定义词汇表、让供应商适配器来翻译。四个具体问题：

  • ① 公共词汇表怎么定——请求侧传什么、流上收什么，循环与适配器的接口切在哪，才让供应商差异进不来？
  • ② 失败怎么分类——网络断了、配额没了、上下文超了，怎么归成稳定码让重试与 compaction 各取所需，而不是解析错误文本？
  • ③ 重试为什么拆成两半——「哪些错可重试、退避多久」与「等着、记账、再发一次」为什么分属供应商与插件？
  • ④ DeepSeek 官方适配器怎么发一个请求——消息怎么序列化、HTTP 错误怎么归类、图像走 Files 还是内联？

速览答案：① 请求侧是 GenerateOptions（消息类型为 RequestMessage[]），流侧是 7 种 StreamChunk 的封闭联合，词汇表两头的更新都有结构依据（7.2）；② 失败统一为 LlmFailure，稳定机器路由码 + 供应商无关的特征识别函数，永不解析 message 文本（7.3）；③ 策略归供应商路由（retry-policy.ts）、执行归 dsh-llm-retry 插件（agent/request-error 上的恢复缝），循环只认 {kind:'retry'}（7.4）；④ 官方适配器 v0.1.7 起是单协议 Messages 直连：serialize 组装线上体、fetch 拿 SSE、translate 翻译成 StreamChunk、providerError 归一化错误（7.5）。7.6 看适配器上的插件扩展缝 dsh_session_log。

7.2① StreamChunk：流的封闭词汇表

packages/llm/llm/src/types.ts:440
typescriptexport type StreamChunk =
  | { type: 'block-start'; index: number; blockType: ContentBlockType }
  | { type: 'text-delta'; index: number; text: string }
  | { type: 'reasoning-delta'; index: number; text: string }
  | { type: 'tool-call-delta'; index: number; id: ToolCallId; name?: string; argumentsDelta: string }
  | { type: 'block-end'; index: number; block: ContentBlock }
  | { type: 'usage'; usage: TokenUsage }
  | {
    type: 'finish'
    reason: FinishReason       // stop | tool-calls | max-tokens | aborted | error
    /** Replay metadata for a successful response; see ReplayEnvelope. */
    replayState?: ReplayEnvelope
  }
读法：块以 index 分组——block-start 开、若干 delta、block-end 收口并携带完整块。reasoning（思考）与 text 是不同块类型，因此「思考不进模型历史、但可上 UI」这类策略有结构依据。finish 的 reason 直接驱动循环的 step 结局（第 3 章）。usage 的缓存读写 token 计数是分离字段，不是互斥联合。

messages 的类型签名在讲故事：循环构建的请求传的是派生历史（dsh-agent-loop，第 2 章），首条系统消息带着 system prompt——所以 system 字段文档明确写着「one-shot 调用者专用；循环构建的请求不设它」。一次性调用者（会话标题、compaction）没有日志身份可引用，于是有了 RequestUserInput（types.ts:475）——id?: never; source?: never 用类型系统声明「这个 user 输入没有持久会话身份，别给它编 id」。工具定义侧还有一个 deferLoading?: true（ToolSchema，types.ts:467）：请求把工具定义延后装载进模型上下文，用 Anthropic 的 defer_loading 术语——工具清单变长时，不常用的定义不必占每次请求的前缀。
还没定案的事：哪些字段算 epoch 级：循环构建请求时用的 config 是 LlmCallConfig（call-config.ts:23）——provider/model/reasoningEffort/temperature/maxTokens/stop 六个字段，每个请求从日志 header 重建而非逐调用传入。哪些字段该进这个集合，作者自己留了 TODO(call-config-shape)（call-config.ts:15）：「Revisit which fields are epoch-level for cache reuse and where provider-specific request options belong」。为什么这个问题不好答：字段越多，header 变化越频繁（第 3 章 reason 'change' 的触发条件），每次变化都可能打断 KV 缓存前缀；字段越少，供应商特有的采样选项又没有安放位置。目前的分界线是「影响缓存复用的请求头状态」——temperature 和 maxTokens 都在集合里，所以改采样参数会记一条 request/header change，这是有意为之的可见性而非遗漏。

typescript/** Classify a provider error without trusting arbitrary response fields. */
export function providerError(raw: unknown, status: number | undefined, headers?: Headers): LlmError {
  const error = …
  const detail = `${type} ${typeof error.code === 'string' ? error.code : ''} ${message}`
  let code: string
  if (status === 401 || status === 403 || ['authentication_error', 'permission_error'].includes(type)) code = 'AUTH'
  else if (isQuotaExceededError(detail) || status === 402) code = 'QUOTA'
  else if (status === 429 || type === 'rate_limit_error') code = 'RATE_LIMIT'
  else if (isContextWindowExceededError(detail)) code = 'CONTEXT_WINDOW_EXCEEDED'
  else if (status === 400 || status === 413 || type === 'invalid_request_error') code = 'INVALID_REQUEST'
  else if ((status !== undefined && status >= 500) || ['api_error', 'overloaded_error'].includes(type)) code = 'SERVER'
  else code = status === undefined ? 'SERVER' : `HTTP_${status}`
  // retry-after → providerRetryAfterMs；request-id / x-request-id → requestId
  return new LlmError(message, code, { …status, requestId, providerRetryAfterMs })
}
设计价值：分类靠「HTTP 状态 + 特征识别函数 + 结构化 type 字段」三路证据，唯独不靠调用方解析 message。特征函数（error.ts:80/:94）识别的是措辞模式——上下文超限的五种正则、配额的六种说法——把「供应商换了措辞」的爆炸半径压在适配器内。消费者只有三种：llm-retry 看 code 决定重不重试（7.4），compaction 看 CONTEXT_WINDOW_EXCEEDED/IMAGE_OFFLOAD_REQUIRED 决定压不压（第 11 章），UI 看其余码决定怎么提示。流内错误（SSE error 事件）走同一个 providerError——status 传 undefined，兜底成 SERVER。

执行者是独立插件 dsh-llm-retry（packages/llm/llm-retry/src/index.ts），它挂在循环的恢复扩展点上：

async function recover(
  { agent, turn, step, provider, failure, retryPolicy: policy, signal }:
    Parameters<Events['agent/request-error']>[0],
  next: () => Promise<RequestErrorAction>,
): Promise<RequestErrorAction> {
  if (policy === undefined) return next()
  // …normal 模式：code ∈ retryableCodes 且未超 maxRetries 时安排退避重试；
  //   always 模式：融合 signal 与插件 lifetime，每次失败都重试…
  agent.session.append('llm/retry', eventData)          // ← 先记账：失败的完整事实
  if (!await cancellableDelay(delayMs, fusedSignal)) return

关注点分离：循环只定义「失败后问监听器怎么办」这个钩子（agent/request-error waterfall，第 4 章表格）；策略（哪些码可重试、退避曲线）由供应商适配器解析并提供；执行（等待、记账、决定 retry）由这个插件完成。持久化分两步：决定重试时立刻写一条 llm/retry，把失败码、退避时长、策略键、第几次重试这些事实先落盘——「cancellable wait 之前先记账」；退避等待成功走完、确实要发下一次请求时，才写 llm/retry-started。所以若进程在退避期间被杀，日志里留下的是「打算重试但没开始」，而不是「重试已开始」。想换重试实现（比如接进自己的熔断器），换监听器即可，循环与适配器都不动。

7.5④ DeepSeek 官方适配器：Messages 直连

packages/llm/llm-deepseek 注册唯一的 provider 路由 deepseek-official（index.ts:57）。适配器在 v0.1.7 收拢成单协议 Messages 直连：v0.1.6 时代的协议选择器（protocol 配置项 + protocols/、common/ 两个目录）被整体删除——适配器文件头自述「Direct Messages transport with one cancellable lifecycle per model request.」（commit 99e22ebbeb）。配置里再写 protocol 会直接报错：

这不是删掉了一个选择，而是把选择点外移：连哪家 API 由 baseURL 决定。公共 API 默认 'https://api.deepseek.com/anthropic'（PUBLIC_BASE_URL，config.ts:115）；内部部署走 $DEEPSEEK_BASE_URL 环境层（BASE_URL_ENV，config.ts:118，注释原话：honored only from trusted layers——产品信任自己启动于其中的检出，所以检出可以让自己的 agent 指向该检出要用的网关）。写一个 Messages 兼容的 baseURL，就得到一个 Messages 兼容的供应商，不需要 dsh 里存在第二个协议实现。

适配器本体（src/adapter.ts，144 行）是 LlmAdapter 的直接子类，请求生成器分三层。先看完整流水线：

packages/llm/llm-deepseek/src/adapter.ts — generate() 与 request()（节选，:52/:76）
typescriptprivate async * generate(options, connection): AsyncGenerator<StreamChunk> {
  const signal = options.signal === undefined ? consumer.signal : AbortSignal.any([consumer.signal, options.signal])
  using watchdog = idleWatchdog(signal, connection.streamIdleTimeoutMs, 'MESSAGES_IDLE')
  const iterator = this.request(options, connection, watchdog.signal, () => { watchdog.pulse() })
  try {
    while (true) {
      const next = await watchdog.next(iterator)
      if (next.done) return
      yield next.value
    }
  } catch (error) {
    if (超时) throw new LlmError(…, 'TIMEOUT')       // 流空闲超时 → 可重试
    if (options.signal?.aborted) throw new LlmError(…, 'ABORTED')
    if (error instanceof LlmError) throw error
    throw new LlmError(…, 'TRANSPORT')               // 连接层故障 → 可重试
  } finally {
    consumer.abort()
    try { await iterator.return(undefined) } catch (_abortedRequestCleanup) {
      // The request already settled; aborting its reader cannot replace that outcome.
    }
  }
}

    yield* translate(parseSse(response.body, activity), options.model)

读这个结构：三层各管一件事。generate()（:52）管生命周期——idle watchdog（@deepseek-ai/dsh-timeout）用 using 守护，任何一次流读超过 streamIdleTimeoutMs（默认 300_000）就放弃读并把错误归为 TIMEOUT（可重试）；消费方取消归 ABORTED，其余归 TRANSPORT；finally 里 iterator.return() 保证取消时底层 fetch reader 被关闭，但注释明确写着 aborting its reader cannot replace that outcome——已结算的请求不许被清理动作改写结局。request()（:76）管内容——图像先试 Files 引用；解析失败且仅当失败类型是 FileResolutionFailure 时整体退回 base64 内联，从 beginAttempt 重走；serialize() 组装线上体；插件扩展字段在 fetch 前注入、2xx 后 accept()。translate()（translate.ts:104）管翻译——把供应商 SSE 事件翻成 7 种 StreamChunk，thinking 块原生重放（回放降级时回调 onReplayDegrade 上报，不暴露内容）。三层共享同一个 activity() 回调喂 watchdog 呼吸——连 Files API 等待期间也在续命，超时计的只是「无任何进展」的时间。

凭据与端点绑定成对（types.ts:54）：配置只带凭据引用名（环境变量名），逐请求解析；类型注释原话「a request can never pair one generation's URL with another generation's secret」——凭据引用跟着同一次解析出的连接快照走，配置热更新换的是整个快照而不是单个字段。另外两处端点细节收拢在 messages-api.ts（messages 与 Files API 共用）：messagesApiRoot 只在基址路径不以 /v1 结尾时补挂 /v1（:11）；带文件引用的请求才附加 anthropic-beta 头（MESSAGES_FILES_BETA）。

7.6扩展缝（接④）：dsh_session_log 请求字段

适配器暴露 ctx.deepseekLlmApiExtensions 注册表：插件可以往 DeepSeek 请求里注入自定义字段。内置的例子是会话日志上传（packages/session/session-log-deepseek/README.md）：

packages/session/session-log-deepseek — README 摘要
text为官方 DeepSeek LLM API 请求做增量式 canonical 会话日志上传。
该插件注入 ctx.sessions 与 ctx.deepseekLlmApiExtensions，拥有
dsh_session_log 请求字段与持久事件 session-log-deepseek/delivery-accepted
（接受水位线从它派生）。

· 默认 enabled: true —— 部署进程注册请求字段；overlay 可用
  enabled: false 选择退出。录制 lane（$VITEST/$DSH_SNAPSHOT）例外：
  录制的 fixture 既是回放输入又是期望输出，保持默认关闭。
· v1 字段内容：sessionFormatVersion、原始 header、数值 afterSeq/throughSeq、
  水位线之后的全部完整 canonical 事件。
· 适配器在 HTTP 2xx 后、消费 SSE 体前调用 accept()；接受即追加
  delivery-accepted {throughSeq}。传输/非 2xx 失败不追加，
  之后请求重发不确定区间。
· 故障方向是 at-least-once：不确定性造成重复，永不跳序。
  并发接受可乱序；折叠最大匹配 throughSeq 防止游标回退。
看懂这个设计 这条扩展缝就是第 1 章能力缝三角色模型的又一次落地：适配器不写死任何请求字段语义，而是开放一个带 accept 回调的注册缝。服务端因此能拿到完整的 canonical 会话日志后缀（服务端可做更好的缓存/回放），而客户端用持久水位线事件保证至少一次投递且不回退。另一个注册在缝上的字段是 dsh_plugin_packages（插件清单上报，由 plugin-package-inventory 提供）。

7.7收尾：四个问题的答案

答案回收 ① 词汇表：请求侧 GenerateOptions 用 RequestMessage[] 把「持久历史」与「无身份的一次性输入」分型（RequestUserInput 的 id?: never），流侧 7 种 StreamChunk 封闭联合——供应商差异全部被适配器吸收在边界上（7.2）。② 错误分类：LlmFailure 的稳定 code 驱动三类消费者——重试、compaction、UI；分类靠 HTTP 状态 + 特征函数 + 结构化 type，唯独不解析 message 文本（7.3）。③ 重试：策略（哪些码可重试、退避曲线）长在供应商路由上，执行（等待、记账、再发）长在 dsh-llm-retry 插件里；持久化分两步——决定重试先写 llm/retry，等待走完才写 llm/retry-started（7.4）。④ 官方适配器：单协议 Messages 直连，generate/request/translate 三层分工——生命周期（idle watchdog、取消融合）、内容（Files→内联退化、serialize）、翻译（SSE→StreamChunk）；凭据与端点绑定同一快照（7.5）。扩展缝（7.6）则展示了适配器边界对外开放的那一面：请求字段也能插件化。下一步进入 第 8 章：System Prompt 组装与 Scope。
