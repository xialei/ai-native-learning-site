LLM 适配层与流式：一种协议，多种供应商

dsh 不 import 任何 SDK 调用模型——它定义了一个词汇表（消息、块、流分片、错误码），任何供应商适配器都翻译成这个词汇表。这一章看协议本体、稳定的错误分类、重试插件，以及 DeepSeek 官方适配器的细节。

7.1一分钟版本

  • 适配器注册在 ctx.llm（packages/llm/llm），按 provider 字符串路由；没有注册的 provider 在派发时报 NO_ADAPTER。
  • 流式协议是 7 种 StreamChunk 的封闭联合——适配器把 SSE 翻译成它们；循环把 chunk 流聚合成块、工具调用与 usage。
  • 失败统一为 LlmFailure：稳定机器路由码（AUTH/RATE_LIMIT/SERVER/…），永不靠解析 message 文本路由。
  • 重试策略由供应商声明（retry-policy.ts），由独立插件 dsh-llm-retry 在 agent/request-error 上执行；循环只认 {kind:'retry'}。
  • DeepSeek 适配器自带 1M 上下文、256K 输出、5 分钟流空闲超时，以及 reasoning effort → thinking/reasoning_effort 的映射。

7.2StreamChunk：流的封闭词汇表

packages/llm/llm/src/types.ts:378
typescriptexport type StreamChunk =
  | { type: 'block-start'; index: number; blockType: ContentBlockType }
  | { type: 'text-delta'; index: number; text: string }
  | { type: 'reasoning-delta'; index: number; text: string }
  | { type: 'tool-call-delta'; index: number; id: ToolCallId; name?: string; argumentsDelta: string }
  | { type: 'block-end'; index: number; block: ContentBlock }
  | { type: 'usage'; usage: TokenUsage }
  | {
    type: 'finish'
    reason: FinishReason       // stop | tool-calls | max-tokens | aborted | error
    /** 成功响应的重放元数据（ReplayEnvelope）。 */
    replayState?: ReplayEnvelope
  }
读法：块以 index 分组——block-start 开、若干 delta、block-end 收口并携带完整块。reasoning（思考）与 text 是不同块类型，因此「思考不进模型历史、但可上 UI」这类策略有结构依据。finish 的 reason 直接驱动循环的 step 结局（第 3 章）。usage 的缓存读写 token 计数是分离字段，不是互斥联合。

packages/llm/llm-deepseek/src/adapter.ts:329 — httpErrorCode()
typescriptexport function httpErrorCode(status: number, error?: WireError['error']): string {
  if (status === 401 || status === 403) return 'AUTH'
  if (status === 413) return 'INVALID_REQUEST'
  const detail = [error?.code, error?.type, error?.message].filter(Boolean).join(' ')
  if (isQuotaExceededError(detail)) return QUOTA_EXCEEDED_CODE
  if (status === 429) return 'RATE_LIMIT'
  if (status === 400) {
    if (isContextWindowExceededError(detail)) return CONTEXT_WINDOW_EXCEEDED_CODE
    return 'INVALID_REQUEST'
  }
  if (status >= 500) return 'SERVER'
  return `HTTP_${status}`
}
设计价值：错误注释明确写着「按 code 路由，绝不解析 message」——HTTP 状态、配额特征、上下文超限特征在适配器内归一化，重试/compaction/用户提示三类消费者就能跨供应商共享逻辑。适配器自己的错误仅用 HTTP_<status> 兜底码表示。

7.4重试：策略归供应商，执行归插件

重试配置长在供应商路由上（packages/llm/llm/src/retry-policy.ts），两种模式：

packages/llm/llm/src/retry-policy.ts
typescriptconst DEFAULT_MAX_RETRIES = 5
const DEFAULT_INITIAL_DELAY_MS = 500
const DEFAULT_MAX_DELAY_MS = 10_000
const DEFAULT_JITTER_RATIO = 0.1
const DEFAULT_RETRYABLE_CODES = Object.freeze([
  EMPTY_RESPONSE_CODE,   // EMPTY_RESPONSE
  'RATE_LIMIT',
  'SERVER',
  'TIMEOUT',
  'TRANSPORT',
])

export interface NormalRetryPolicyConfig {
  mode: 'normal'
  /** 首次请求之后最多重试次数（默认 5）。 */
  maxRetries?: number
  /** 本策略允许的稳定失败码。 */
  retryableCodes?: string[]
  backoff?: BackoffConfig
}

export interface AlwaysRetryPolicyConfig {
  /** 重试每次模型请求失败，直到成功、取消或销毁。 */
  mode: 'always'
  backoff?: BackoffConfig
}

执行者是独立插件 dsh-llm-retry（packages/llm/llm-retry/src/index.ts），它挂在循环的恢复扩展点上：

packages/llm/llm-retry/src/index.ts
typescriptexport const name = 'llm-retry'
export const inject = ['agents', 'sessionProjections']
/** 本执行器无配置；retryPolicy 归供应商。 */
export type Config = Readonly<Record<string, never>>

async function recover(
  { agent, turn, step, provider, failure, retryPolicy: policy, signal }:
    Parameters<Events['agent/request-error']>[0],
  next: () => Promise<RequestErrorAction>,
): Promise<RequestErrorAction> {
  if (policy === undefined) return next()
  // …normal 模式：code ∈ retryableCodes 且未超 maxRetries 时安排退避重试；
  //   always 模式：融合 signal 与插件 lifetime，每次失败都重试…
  agent.session.append('llm/retry-started', { retryId, turn, step, retry })
  return { kind: 'retry' }
}
关注点分离：循环只定义「失败后问监听器怎么办」这个钩子（agent/request-error waterfall，第 4 章表格）；策略（哪些码可重试、退避曲线）由供应商适配器解析并提供；执行（等待、记账、决定 retry）由这个插件完成，且每次调度重试前先持久化 llm/retry-started 事件——「cancellable wait 之前先持久」，崩溃后重试历史可审计。想换重试实现（比如接进自己的熔断器），换监听器即可，循环与适配器都不动。

线上请求的组装（packages/llm/llm-deepseek/src/serialize.ts）：

packages/llm/llm-deepseek/src/serialize.ts — 线上请求（节选）
typescript  const resolvedThinking = resolveThinking(options, defaults)
  return {
    model: options.model,
    messages,
    stream: true,                              // 永远流式，usage 上报开启
    stream_options: { include_usage: true },

effort 映射：配置的 'off'|'low'|'high'|'max' 解析为 thinking enabled + reasoning_effort；off 不作为线上 effort 暴露（resolveThinking 注释：不把 off 暴露为 wire effort——thinking 被部署禁用时所有请求强制 off，wire 上表现为 thinking disabled）。省略 effort 时解析为 high（Config 注释）。可选字段一律省略而非发 null，让供应商默认值生效。

7.6扩展缝：dsh_session_log 请求字段

适配器暴露 ctx.deepseekLlmApiExtensions 注册表：插件可以往 DeepSeek 请求里注入自定义字段。内置的例子是会话日志上传（packages/session/session-log-deepseek/README.md）：

packages/session/session-log-deepseek — README 摘要
text为官方 DeepSeek LLM API 请求做增量式 canonical 会话日志上传。
该插件注入 ctx.sessions 与 ctx.deepseekLlmApiExtensions，拥有
dsh_session_log 请求字段与持久事件 session-log-deepseek/delivery-accepted
（接受水位线从它派生）。

· 默认 enabled: false —— 不注册任何请求字段。
· v1 字段内容：sessionFormatVersion、原始 header、数值 afterSeq/throughSeq、
  水位线之后的全部完整 canonical 事件。
· 适配器在 HTTP 2xx 后、消费 SSE 体前调用 accept()；接受即追加
  delivery-accepted {throughSeq}。传输/非 2xx 失败不追加，
  之后请求重发不确定区间。
· 故障方向是 at-least-once：不确定性造成重复，永不跳序。
  并发接受可乱序；折叠最大匹配 throughSeq 防止游标回退。
看懂这个设计 这是「能力缝」思想在 LLM 协议层的体现：适配器不写死任何请求字段语义，而是开放一个带 accept 回调的注册缝。服务端因此能拿到完整的 canonical 会话日志后缀（服务端可做更好的缓存/回放），而客户端用持久水位线事件保证至少一次投递且不回退。另一个注册在缝上的字段是 dsh_plugin_packages（插件清单上报，由 plugin-package-inventory 提供）。

7.7要点

要点 ① dsh 与模型的所有交互都穿过一个自有的封闭词汇表（StreamChunk/ContentBlock/FinishReason），供应商差异被适配器吸收在边界上；② 错误是分类学不是字符串——稳定 code 驱动重试、compaction、用户提示三种消费；③ 重试的策略与执行分离，且每次重试先持久化再等待；④ 适配器暴露扩展缝，让请求字段也能插件化。下一步进入 第 8 章：System Prompt 组装与 Scope。
