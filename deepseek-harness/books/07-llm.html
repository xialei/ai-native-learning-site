LLM 适配层与流式：封闭词汇表、两条认证路由、一条 Messages 直连

模型在进程外、循环在进程内，中间这条 HTTP 流怎么管？dsh 不 import 任何模型 SDK，而是自己定义词汇表、让供应商适配器来翻译。本章沿请求的一生走：词汇表两头怎么定，失败怎么归成稳定码，重试为什么拆成策略与执行两半，官方适配器怎么发请求、收流——以及 0.2.0 把「官方适配器」一拆为二之后，传输与认证的边界划在哪。

7.1同一份传输代码，为什么要服务两种登录方式

先看这章新增的主线。v0.1.7 时代 packages/llm/llm-deepseek 一个包干完所有事：注册 provider 路由、解析凭据、发请求。0.2.0 把它拆开了——传输归传输，认证归认证：

  • llm-deepseek：纯传输库。DeepSeekAdapter、serialize、SSE 解析、Files API、错误分类都在这，但它不再注册任何 provider 路由，index.ts 里只剩 re-export。
  • llm-deepseek-api-key：注册 deepseek-official 路由。凭据是 API key（credentials 服务或环境变量 DEEPSEEK_API_KEY），请求头 x-api-key。
  • llm-deepseek-account：注册 deepseek-account 路由。凭据是登录账号的 token，请求头 x-dsh-auth-token，配额错误和 401 有专门的重映射。

两个认证插件的差异全部收进一个函数签名：resolveAuth(connection) 返回 { headers, onRequestError? }（DeepSeekRequestAuth，types.ts:85）。适配器只管「把 headers 原样发出去、出错时把 error 交给 onRequestError 映射」（adapter.ts:82），不再关心你用的是 key 还是账号。这一节读完你会明白：为什么拆分后新加一种登录方式不用动传输层，以及「模型请求因凭据失败」的语义怎么从传输错误里分离出来。其余各节沿请求的一生走——词汇表（7.2）、错误码（7.3）、重试（7.4）、一次请求的完整流水线（7.5）、会话日志扩展缝（7.6）。

边界声明：harness 关心模型的哪些特性。dsh 全仓库搜不到 MLA、MoE、FP8、MTP 这些词——这不是遗漏而是分界：模型怎么算（多头注意力的显存账、专家并行的通信、量化内核）是推理引擎的事，本站《深入浅出vLLM》《深入浅出SGLang》讲的就是那一层。harness 与模型的全部接触面收在适配器边界内，只关心三件事：思考模式（reasoning 块进不进历史、effort 怎么映射，7.5）、缓存前缀（哪些请求头变化会打断 KV 复用，7.2 的 LlmCallConfig 取舍）、文件输入（Files 引用与内联退化，7.5）。模型能力升级只要不破这三件事，harness 一行不改。

读法：块以 index 分组——block-start 开、若干 delta、block-end 收口并携带完整块。reasoning（思考）与 text 是不同块类型，因此「思考不进模型历史、但可上 UI」这类策略有结构依据。finish 的 reason 直接驱动循环的 step 结局（第 3 章）。usage 的缓存读写 token 计数是分离字段，不是互斥联合。

messages 的类型签名在讲故事：循环构建的请求传的是派生历史（dsh-agent-loop，第 2 章），首条系统消息带着 system prompt——所以 system 字段文档明确写着「one-shot 调用者专用；循环构建的请求不设它」。一次性调用者（会话标题、compaction）没有日志身份可引用，于是有了 RequestUserInput（types.ts:487）——id?: never; source?: never 用类型系统声明「这个 user 输入没有持久会话身份，别给它编 id」。工具定义侧还有一个 deferLoading?: true（ToolSchema，types.ts:479）：请求把工具定义延后装载进模型上下文，用 Anthropic 的 defer_loading 术语——工具清单变长时，不常用的定义不必占每次请求的前缀。deferLoading 与 0.2.0 的 toolUpdate 是一对：ToolUpdate = 'in-history' | 'addition-only'（types.ts:407）描述模型路由怎么消费后续的声明变化，deferLoading 描述单个工具要不要立刻进上下文；前者靠后者的配合才能把「先声明、后激活」落成线上协议。
还没定案的事：哪些字段算 epoch 级：循环构建请求时用的 config 是 LlmCallConfig（call-config.ts:23）——provider/model/reasoningEffort/temperature/maxTokens/stop 六个字段，每个请求从日志 header 重建而非逐调用传入。哪些字段该进这个集合，作者自己留了 TODO(call-config-shape)（call-config.ts:15）：「Revisit which fields are epoch-level for cache reuse and where provider-specific request options belong」。为什么这个问题不好答：字段越多，header 变化越频繁（第 3 章 reason 'change' 的触发条件），每次变化都可能打断 KV 缓存前缀；字段越少，供应商特有的采样选项又没有安放位置。目前的分界线是「影响缓存复用的请求头状态」——temperature 和 maxTokens 都在集合里，所以改采样参数会记一条 request/header change，这是有意为之的可见性而非遗漏。

关注点分离：循环只定义「失败后问监听器怎么办」这个钩子（agent/request-error waterfall，第 4 章表格）；策略（哪些码可重试、退避曲线）由供应商适配器解析并提供；执行（等待、记账、决定 retry）由这个插件完成。持久化分两步：决定重试时立刻写一条 llm/retry，把失败码、退避时长、策略键、第几次重试这些事实先落盘——「cancellable wait 之前先记账」；退避等待成功走完、确实要发下一次请求时，才写 llm/retry-started。所以若进程在退避期间被杀，日志里留下的是「打算重试但没开始」，而不是「重试已开始」。想换重试实现（比如接进自己的熔断器），换监听器即可，循环与适配器都不动。

onRequestError 是这次拆分里最值得看的设计。传输层在 request 的 catch 里调用它，把错误映射权交还给凭据的持有者：通用配额码 QUOTA 在账号路由上没有意义（那是账户余额问题），重映射成 ACCOUNT_QUOTA；401 说明 token 失效，映射成 ACCOUNT_TOKEN_INVALID 并顺手 rejectToken 把坏 token 从凭据存储里移除。注意 catch 的写法——rejectToken 本身失败（存储层故障）被显式吞掉，注释原话是「存储失败不能顶替推理失败」：用户看到的必须是请求的真实失败，而不是清理动作的失败。适配器侧则完全不知道这些细节，它只看到「headers」和「一个错误映射回调」。类型上这也可见：DeepSeekAdapter 变成了 <C extends Connection> 的泛型（adapter.ts:20），两个插件各自用自己的连接类型实例化它。

      method: 'POST', signal, body: extensions.payload, redirect: 'error',
      headers: {
        …attributionHeaders(),
        'content-type': 'application/json', 'accept': 'text/event-stream',
        …auth.headers,                                       // 认证头由 resolveAuth 提供
        'anthropic-version': '2023-06-01',
        …betas.length === 0 ? {} : { 'anthropic-beta': betas.join(',') },
        'x-deepseek-harness-user-id': …,
        …options.sessionId === undefined ? {} : { 'x-deepseek-harness-session-id': String(options.sessionId) },
        …options.purpose === 'compaction' ? { 'x-deepseek-harness-compact': '1' } : {},
      },
    })
    if (!response.ok) {
      if (await files.retry(detail)) continue          // 仅文件配额类错误可重试
      const failure = providerError(raw, response.status, response.headers)   // transport.ts:22，7.3 节
      throw new LlmError(message, failure.code, { …failure.failure, cause: new Error(text) })
    }
    await extensions.accept()                          // 2xx 后、消费 SSE 前——7.6 节的投递接受
    if (response.body === null) throw new LlmError(…, 'EMPTY_RESPONSE')
    yield* translate(parseSse(response.body, activity), options.model)
    return
  }
} // 整个 request 体包在 try/catch 里，catch 调 auth.onRequestError 映射错误（见上）
读这个结构：三层各管一件事。generate()（:51）管生命周期——idle watchdog（@deepseek-ai/dsh-timeout）用 using 守护，任何一次流读超过 streamIdleTimeoutMs（默认 300_000）就放弃读并把错误归为 TIMEOUT（可重试）；消费方取消归 ABORTED，其余归 TRANSPORT；finally 里 iterator.return() 保证取消时底层 fetch reader 被关闭，但注释明确写着 aborting its reader cannot replace that outcome——已结算的请求不许被清理动作改写结局。request()（:75）管内容——图像先试 Files 引用；解析失败且仅当失败类型是 FileResolutionFailure 时整体退回 base64 内联，从 beginAttempt 重走；serialize() 组装线上体；beta 头现在按需拼两种（Files、工具变更），一个都没有时不发 anthropic-beta；插件扩展字段在 fetch 前注入、2xx 后 accept()。translate()（translate.ts:104）管翻译——把供应商 SSE 事件翻成 7 种 StreamChunk，thinking 块原生重放（回放降级时回调 onReplayDegrade 上报，不暴露内容）。三层共享同一个 activity() 回调喂 watchdog 呼吸——连 Files API 等待期间也在续命，超时计的只是「无任何进展」的时间。

动态工具更新：一条声明史怎么走到线上

0.2.0 之前，工具清单变了就意味着下一请求整体换掉 tools 数组——对 KV 缓存是一次前缀重写。0.2.0 给了另一条路：声明留在历史里，变化以消息形式追加。整条链路分四段：

第一段，模型侧声明能力。目录里 deepseek-flash 声明 toolUpdate: 'addition-only'——这条路由能把 developer 消息里的 tool-addition 块读作「激活某个 deferLoading 声明的工具」，但不支持删除语义；'in-history' 则连 tool-removal 也走历史（types.ts:401 的文档）。两个都没声明的路由维持旧行为：每次请求发完整清单。

第二段，循环侧记账。循环在 buildRequest 里把新旧 header 的工具名单做差集（agent.ts:640-646），差异写成一条 developer/message 事件，content 是 tool-addition/tool-removal 块，addition 部分携带 headerSeq 指回定义所在的 request/header 事件。这个事件本身进了会话日志，所以重启后可重放。

第三段，会话侧折叠。新文件 packages/core/session/src/tool-history.ts 的 ToolHistoryProjection 把 request/header 与 developer/message 两类事件折成不可变的 ToolHistory（tools + updates）：当前声明系列从哪个 header 开始、每条 update 激活了哪些定义，都从 headerSeq 反查出来。折叠与模型能力无关——日志里怎么记，这里就怎么折。Session.toolHistory()（session/src/index.ts:825）按增量消费事件返回快照。

第四段，发送侧投影。循环把 toolHistory 放进 GenerateOptions；llm 层在真正派发给适配器前调用 projectToolUpdates（content.ts:424，派发点在 llm/src/index.ts:1069），按路由的 toolUpdate 模式决定发什么：

7.6扩展缝：dsh_session_log 请求字段

适配器暴露 ctx.deepseekLlmApiExtensions 注册表：插件可以往 DeepSeek 请求里注入自定义字段。内置的例子是会话日志上传（packages/session/session-log-deepseek）。0.2.0 给它加了一个上界：

packages/session/session-log-deepseek — README 摘要（0.2.0）
text· 默认 enabled: true。0.2.0 起 enabled 是 Volatile 布林：改配置对下一个请求
  生效，不用重启；Web Settings → General 的上传开关就是写这个字段。
  关闭期间录制的事件不丢——重新开启后未接受的后缀（含关闭期事件）恢复上传。
· maxBytes（默认 8 MiB）：单个请求携带的 dsh_session_log 字段按 UTF-8 字节
  计的上界。发送「水位线之后的最长连续前缀」：一条完整事件如果超限，
  上传停在上一个事件，等后续事件把它推出 maxBytes 再一起走。
· 适配器在 HTTP 2xx 后、消费 SSE 体前调用 accept()；接受即追加
  delivery-accepted {throughSeq}。传输/非 2xx 失败不追加，
  之后请求重发不确定区间。
· 故障方向是 at-least-once：不确定性造成重复，永不跳序。
  并发接受可乱序；折叠最大匹配 throughSeq 防止游标回退。
maxBytes 的语义是「整块字段」而不是「每个事件」：jsonBytes()（index.ts:125）按 UTF-8 字节数计整条 wire 事件，组装循环逐事件累加（index.ts:203-211），第一个放不下的完整事件让本轮上传停在上一个边界——事件不拆包，宁可等待。README 对副作用的描述很直白：单个事件超过 maxBytes 时上传会停住，直到该事件被后续行为推出上界（这条上界是防一个巨型 diff 或一次超长工具输出把请求体撑爆；被它卡住的会话在日志里会收到一条说明）。这是把「不能发的」变成「暂时少发的」——与全书水位线推进的哲学一致：游标永不回退，但前进的速度可以按预算调节。
这条缝的两面 适配器不写死任何请求字段语义，而是开放一个带 accept 回调的注册缝（7.5 request() 里的 prepareExtensions/accept）。服务端因此能拿到完整的 canonical 会话日志后缀，客户端用持久水位线事件保证至少一次投递且不回退。注册在缝上的另一个字段是 dsh_plugin_packages（插件清单上报）。0.2.0 的新消费者是遥测：OpenTelemetry 的会话日志通道是独立配置，README 特别注明它与本插件的 enabled 开关互不牵连。

7.7回到开头的拆分

现在可以回答 7.1 的问题了：为什么拆。答案藏在 7.5 的两段代码对比里——api-key 路由的 resolveAuth 是一行 headers 赋值，account 路由的 resolveAuth 带着配额重映射、401 检测、token 回收三层逻辑。这两种复杂度没有任何交集，却共享全部传输行为：watchdog、Files 退化、beta 头、SSE 翻译、错误分类。v0.1.7 把它们缝在一个包里时，每次给账号路由加逻辑都要碰传输文件，反之亦然；拆开后，传输包甚至不知道有几种登录方式存在——host.ts 的四个钩子就是它对认证的全部了解。

本章其余部分各归其位：词汇表两头（GenerateOptions/StreamChunk）让供应商差异被吸收在适配器边界（7.2）；LlmFailure 稳定码驱动重试、compaction、UI 三类消费者（7.3）；重试策略归供应商、执行归插件，持久化先记账后开始（7.4）；一次请求走 generate→request→translate 三层（7.5），工具变更以历史消息的形式进请求（7.5 末尾）；适配器边界对外还有一条 dsh_session_log 扩展缝，现在带着 8 MiB 的字节预算（7.6）。下一步进入 第 8 章：System Prompt 组装与 Scope。
