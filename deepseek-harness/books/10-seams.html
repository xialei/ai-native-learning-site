能力缝实战：shell / fs / web / skill / jobs

第 1 章给了「能力缝」的定义，这一章把它放进五个领域实地巡检：shell 的执行器互斥、fs 的三世界与版本守卫、web 的选择器报错、skill 的注册表合并、jobs 的所有权围栏——同一条缝，五个领域各自长出不同的规矩；随后看 ssh 家族怎样把旧契约接上新实现，mcp 与 browser/computer-use 怎样沿用旧规矩长出新缝。

10.1同一条缝，五个领域，形状为什么不一样

第 1 章定义了「能力缝 = Service Definition + Provider + Consumer」。但定义只是骨架——真正决定一个缝好不好用、错不错报的，是它在自己领域里长出来的约束。判别法只有一条：看能力语义。执行类能力（shell）天然互斥——两个执行器抢同一条 ctx.shell 会让模型无法预期行为，所以挂两个就 fail loud，兜底是 Cordis 的重复注册冲突报错；目录类能力（skill / mcp-resources）天然可叠加——多一个来源只是目录多几行，但「来源不同、模型所见相同」要求把渲染收拢进一个 consumer，provider 类型对模型透明；选择类介于中间（web 每操作选一个，零个或多个可用都报错且语义不同）。这条判别法还解释了锚点之后长出来的新家族：ssh 看着像新缝，其实是 fs / subprocess / sandbox 三个旧契约的新实现——消费者一行不改就拿到远端能力，实测「契约远小于实现面」；mcp 与 browser-use / computer-use 才是新缝，注册语义严格复用判别法，没有发明新东西。下面逐个领域巡检：

  • shell：执行器契约 ctx.shell，每组合恰好挂一个实现（bash-local / bash-sandbox / pwsh-local / pwsh-sandbox）；挂两个 fail loud。
  • fs：契约 ctx.fs，后端谱系 fs-local / fs-sandbox（fence）/ fs-observation-policy；突变带版本守卫，错误码稳定（FS_STALE_VERSION…）。
  • web：ctx.web 单服务管 search+fetch，每操作选一个可用 provider；零或多个可用都是错误，语义各不同。
  • skill：ctx.skills 注册表合并任意 provider 的目录；provider 类型不影响模型所见——渲染全在一个 consumer 包。
  • jobs：契约 ctx.jobs（后台作业注册表），作业归属启动它的会话，完成以会话内通知送达而非轮询。

10.3fs 家族：一个契约，三个世界

packages/fs/fs/src/index.ts:50 — fs/* 事件词汇表
typescriptinterface Events {
  /**
   * Single-slot decision for the next FileSystem.writeText. Calling next()
   * yields the bare provider's unconditional write; the first listener that
   * returns an intent owns the decision rather than composing with peers.
   */
  'fs/write-intent'(target: FsTarget, actor, next): Promise<FsWriteIntent | undefined>
  /** editText 的单槽决策，同样 first-intent-wins */
  'fs/edit-intent'(target: FsTarget, actor, next): Promise<{ version: FsVersion } | undefined>
  /**
   * Record an authoritative positive or negative observation. Listeners must
   * be synchronous recorders: throws fail the tool call and returned promises
   * are not awaited.
   */
  'fs/observed'(target: FsTarget, observation: FsObservation, actor): void
}
两种派发模式的分工：意图事件是 waterfall，但语义是「单槽决策」——第一个返回 intent 的监听器独占决定权，不与同伴组合（区别于第 1 章的环绕语义：这里 next() 只是「放弃决策权」）；观察事件是 emit，监听器必须同步（抛错直接打炸工具调用）。fs-sandbox 后端的 fence 不走事件——它挂在继承的方法上：覆写 writeText() / editText() 这两个突变入口，先跑私有的 checkedTarget()（fs-sandbox/src/index.ts:122），再把检查通过的那个新 target 交给父类实现，避免「这里查、那边写」的 TOCTOU。拒绝时抛 FS_SANDBOX_DENIED，由工具渲染成第 9 章那个 [sandbox: file access denied under <mode> mode] 标记。注释写得很克制：这是「受信代码对模型可控路径的策略检查，不是内核边界」，内核级隔离仍然是 ctx.shell（bash-sandbox）的职责。
packages/fs/fs/README.md — 契约承诺（摘要）
text把任意路径解析为稳定目标身份（跨别名保持 identity）；
在边界内读整份文本或分块流式读、读原始字节；
列目录（稳定、不含内容）；
原子地 create-or-replace 写、原子地字面编辑。
两种突变都接受可选版本守卫：省略=无条件写；
提供=自上次观察后文件已变则报 FS_STALE_VERSION。
所有错误是带稳定码的 FsError（FS_NOT_FOUND / FS_STALE_VERSION /
FS_AMBIGUOUS_EDIT / FS_SANDBOX_DENIED…）——按码分支，永不按文本。
看懂这个设计 fs 的关键取舍：挂 fs-sandbox 而非 fs-local，就是启用限制的全部改动——模型工具、政策插件、schema 一概不动（fs/fs/README.md:32「swapping backends changes nothing for the policy plugin, the tools, or the tool schemas」）。实现上 fs-sandbox 直接继承 LocalFileSystem（fs-sandbox/src/index.ts 模块注释：「It extends LocalFileSystem so all text-storage mechanics … are the local implementation's, verbatim; this package adds only the per-call POLICY fence on the two mutations. Reads pass through untouched」）——读永远不设防，突变才 fenced，且 fence 与 bash 收到的是同一个 resolve() 政策（第 9 章），两个家族永不框到不同的根。

10.4web 家族：选择器与两个「没配好」错误

packages/web/web/src/index.ts:172 — resolveProvider()
typescriptfunction resolveProvider<P extends ResolvableProvider>(selection: Selection<P>): P {
  const { configuredId, providers } = selection
  if (configuredId !== undefined) {
    const provider = providers.get(configuredId)
    if (!provider) throw new WebError(…, 'WEB_PROVIDER_CONFIGURED_MISSING')
    if (!provider.available()) throw new WebError(…, 'WEB_PROVIDER_CONFIGURED_UNAVAILABLE')
    return provider
  }
  const usable = [...providers.values()].filter(provider => provider.available())
  if (usable.length === 0) throw new WebError('no usable web provider is registered', 'WEB_PROVIDER_UNAVAILABLE')
  if (usable.length > 1) throw new WebError(`multiple usable web providers are registered (${ids}); configure one explicitly`, 'WEB_PROVIDER_AMBIGUOUS')
  return usable[0]
}
配置即承诺：配了名就得能用（MISSING 与 UNAVAILABLE 分开报）；没配名时「一个可用」才自动选择，「多个可用」是错误不是随机挑一个——WebError 词汇表把「怎么连上网」收进单一 owner。另一个细节：fetch 的注释「A non-2xx response is a result, not a throw」——HTTP 404 是正常结果，只有能力本身跑不起来才抛错。这与第 7 章 LlmFailure 的分类学同源：错误码表达「哪类事实」，不混入业务结果。
一个补上了的洞：web-search-deepseek 把 apiKey: z.string().role('secret') 注册进 settings 命名空间，网页端读取时靠 redactSecrets 把 secret 字段从返回值里剥掉（api/settings-controller 的每次 remote read 都强制 redactSecrets: true）。初版剥除遍历器只走 object/dict/array 三种容器——藏在 union、intersection 或 transform 里的 secret 会原样放行，作者在 redact.ts 里留了 TODO(settings-wire-redaction)，并配了一条注册约定：机密无法经由被遍历容器抵达的 schema，绝不可注册到暴露于协议的 namespace 上，fail-closed 的 describeForWire() 是暂缓的答案。#4587（2026-09-21）把这条路走完了：walk 现在显式处理 union / intersect / transform 分支（redact.ts:87），注释从「must not be modeled that way」改成「visits every union branch, conservatively removing any field declared secret by a branch」，describeForWire() 随整个 settings 包重写一起退场。一个演化痕迹：防线从「约定」升级成了「机制」。

看懂这个设计 「Different sources produce the same model-visible format.」——本地目录技能与远程服务技能在模型眼里长得一模一样（排序后的名字+描述列表，按需加载全文）。如果每个 provider 自己渲染目录，加一个来源就多一种模型体验；把渲染收拢到一个 consumer，provider 来源再多，模型看到的目录形式也只有一个。（这句话 2026-09-08 的文档收敛提交 f1c1ff5a08 换掉了原文「Provider type does not change what the model sees, because all model-facing rendering lives in one consumer package.」——意思没变，措辞从「为什么」改成了「结果是什么」。）

10.6jobs 家族：所有权围栏与会话内通知

packages/jobs/jobs/src/types.ts — JobStatus / JobOutcome / JobSpec（节选）
typescript// 客户端安全的投影词汇表在 view.ts（types.ts:13 转发）——状态类型是叶子
export type JobStatus = 'running' | 'stopping' | 'completed' | 'killed' | 'failed'   // view.ts:19

export interface JobOutcome {                       // types.ts:16
  /** finished (completed) / cancelled (killed) / broke (failed) */
  status: 'completed' | 'killed' | 'failed'
  /** 渲染进状态行的 kind 专属细节（'exit code: 3'、'max-tokens'） */
  detail?: string
  /** 结果是值而非流的作业在这里一次性交出（subagent 报告等） */
  result?: string
}

export interface JobSpec {                          // types.ts:126，交给 JobRegistry.start
  kind: JobKind              // 也是 id 前缀：bash-N、subagent-N…
  label: string              // 模型可读的一行标签
  /**
   * Owning session. Access is fenced by it, and the owner's live Agent must be
   * the one currently registered under that id: its disposal cancels and
   * awaits the job. Omitting the owner creates an unowned job, open to any
   * caller until service disposal.
   */
  owner?: SessionId
  outputLimitBytes?: number
  output?: readonly JobOutputSource[]    // 拉源由注册表按自己的节奏泵入输出环
  /** preflight 之后启动工作，同步返回 hooks；抛错则什么都没注册 */
  run(job: JobHandle): JobHooks
}
packages/jobs/jobs/src/types.ts:105 — JobHooks（节选）
typescriptexport interface JobHooks {
  /** 同步、幂等；reason 原样转发 */
  cancel(reason?: string): void
  /** 在 producer 释放资源之后才 resolve；不得 reject（rejection 会被转为 failed） */
  done: Promise<JobOutcome>
}
三个契约决定三个行为：owner 是 SessionId 且按启动会话围栏访问（「one agent never sees another's work」——围栏要求 owner 名下的 live Agent 必须是当前注册的那个 id；省略 owner 造的是无主作业，对任何调用者开放直到服务销毁）；agent 销毁时取消并等待作业——不留孤儿。done resolve 于「producer 释放资源之后」而非工作完成时——运行时把 rejection 转为 failed 但「without claiming that the work stopped」，诚实报告。完成通知作为会话内 notice 送达 owner agent（tool-jobs 派发），模型下一轮自然看到，不用主动轮询；空闲 owner 的送达策略默认 wakeup（开一个 turn），可配 quiet 或 maxConsecutiveWakes 封顶自激励链。id 是 <kind>-N 递增——可读、可排序、可引用。

10.6b旧契约接新实现：ssh 家族，外加两条新缝的对照

五条缝讲完「缝的形状」，本节先看锚点（dsh-v0.1.5-rc.2）之后长出来的 ssh 家族：它根本不是新缝，而是 fs / subprocess / sandbox 三个旧契约的新实现。同锚点之后长出的另外两条缝（mcp、browser/computer-use）是「新缝」，放进同表对照，下一节展开：

家族包缝语义
ssh/（POSIX 远程执行）ssh + fs-ssh + subprocess-ssh + sandbox-ssh一个部署持有的 OpenSSH alias 连到远端 helper，四包分别坐进 ctx.ssh / ctx.fs / ctx.subprocess / ctx.sandbox 四把现有的椅子——fs 三世界、sandbox 文件效果围栏的契约原样延伸到远端。安全模型是堆叠的：每条流保留一个 256 位 TLS PSK（只走管理 RPC，永不进流前缀），helper 启动前校验安装物 digest，helper 以 --disable-sigusr1 启动封掉同用户信号的调试入口。断连语义诚实：「A disconnected client cannot confirm the remote outcome; operations are never reconnected or replayed automatically」——不做重连重放
「旧契约接新实现」的答案落在 ssh 家族：fs/subprocess/sandbox 的消费者一行不改就拿到远端能力，这正是「契约远小于实现面」的实测。mcp 与 browser/computer-use 作为对照放进了同表：它们才是新缝，判别法怎么跑见下一节。

10.6c新缝沿用旧规矩：MCP 与 browser/computer-use

mcp 与 browser-use / computer-use 是真正的「新缝」，但注册语义没有发明新东西——判别法对它们原样跑通：

mcp-resources：每条配置一个 MCP server 连接，任意多 provider 合并（skills 型）；首个 provider 注册三个共享工具 list_mcp_resources / list_mcp_resource_templates / read_mcp_resource（显式 server 名，scope 里没配服务器的调用者完全看不到这些工具与提示文本）。资源操作的效果归 resource service 所有——provider 只供给操作。服务器 instructions 渲染成字面 prompt 段（MCP_SERVERS，order 3100，第 8 章），instruction 上限 maxInstructionBytes 默认 32768。SDK 侧锁定 2026-07-28 协议（versionNegotiation mode "auto"），stdio 探测进程的环境是擦洗过的（第 9 章的信任边界延伸到子进程 env）。
browser-use / computer-use：两个新缝结构完全一致——一包共享注册服务（ctx.browserUse / ctx.computerUse）+ 独占 named provider 注册（shell 型），同一时刻只挂一个浏览器后端（Playwright MCP / Chrome DevTools MCP / Stagehand）或一个桌面 provider；具体实现在 experimental 组里保持实验标记。配套地，e2b provider 已移除、code-runtime 更名 ptc-runtime（第 6 章表里的名字已是新名）。

10.8收尾

五个领域巡检完，判别法的价值也显出来了：缝的形状不由框架强加，而由能力语义决定——执行类互斥（shell 挂两个 fail loud）、目录类可叠加（skill / mcp-resources 合并）、选择类介于中间（web 每操作选一，0 或 ≥2 都报错且语义不同）。注册语义跟着形状走：独占型靠重复注册冲突报错兜底；合并型把渲染收拢进 consumer，错误码即契约（FS_*、WEB_PROVIDER_*）让调用者按码分支。ssh 家族证明了这套契约的含金量：fs/subprocess/sandbox 的接口在远端原样复刻，消费者一行不改；fs/write-intent 这类事件也是缝的一部分——单槽决策，不是环绕中间件。新缝（mcp 合并 + 首注册者带共享工具、browser/computer-use 独占单选）判别法原样跑通，没有发明新规矩。下一步看 compaction——最依赖会话日志不变量的子系统：第 11 章：Compaction。
