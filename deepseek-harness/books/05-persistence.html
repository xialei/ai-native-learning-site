持久化与崩溃恢复：把日志安全地放到磁盘上

问题：第 2 章说会话日志是唯一事实——那这条日志怎么可靠地落到磁盘（①）？进程在任意一行代码处被 kill，重启怎么把「撕裂的尾巴」缝合成供应商可接受的历史（②）？格式版本怎么演进，旧日志还能不能读（③）？5.1 把问题摆出来，5.2–5.4 作答①，5.5 作答③，5.6 作答②，5.7 收尾回收。

5.1问题：可靠落盘、撕裂尾巴、格式演进

三个工程问题，一个比一个靠后：

  • ① 日志怎么可靠地落盘——谁拥有写？append 和持久是一回事吗？进程死了日志会不会半行？
  • ② 崩溃之后怎么恢复——开口的 turn、未结算的 tool/call，怎么缝成供应商接受、模型可决策的历史？
  • ③ 格式怎么演进——V4 改了事件词汇表（第 2 章），昨天存在磁盘上的 v3 日志今天还读得回来吗？

速览答案：① 存储是缝（SessionPersistence 接口 + JSONL 后端），写所有权由内核仲裁，append 尽力而为、flush 才是持久性屏障，flush 点由独立的检查点策略插件挂载（5.2–5.4）；② 缝合 = interruptedTurnClosers()，确定性合成闭包（5.6）；③ 不可变代际文件 + 静态迁移链，v3→v4 的迁移包是最新样本（5.5）。

5.2① SessionHandle 契约

所有后端共用的句柄接口（packages/session/session-persistence/src/handle.ts）。注释把每条契约写得极精确：

packages/session/session-persistence/src/handle.ts（节选，注释为译注除末段外）
typescript/**
 * Log access granted by an open. `write` is read-write: the session's single
 * mutator, which also reads its own log. `read` only observes — it never
 * takes ownership and works while another handle or process holds `write`.
 */
export type SessionAccess = 'read' | 'write'

export interface SessionHandle extends AsyncDisposable {
  readonly id: SessionId
  /** The immutable stored header, fixed at create/open. */
  readonly header: SessionHeader
  /** Fork 继承前缀的精确事件数；非 seeded 为 0。存储元数据，不进可重放日志。 */
  readonly inheritedEventCount: SessionLogOffset
  readonly access: SessionAccess

  /**
   * Read a slice of the valid contiguous logical log. The slice is a legal
   * log prefix segment: a torn physical tail is never returned, and repeated
   * reads on this handle never observe an older state than a prior read.
   * @returns the caller-owned outer slice plus the ownership state of its
   *   event values.
   */
  read(offset?: number, length?: number, options?): Promise<SessionHandleReadResult>

  /**
   * Append a contiguous batch continuing the current logical end. The first
   * event's seq MUST equal the stored next-seq; committed events are never
   * rewritten. Persistence is best-effort: on resolution the batch is
   * accepted, ordered, and visible to reads on this backend instance, but
   * only a resolved flush promises it survives a crash.
   */
  append(events: readonly SessionEvent[], options?): Promise<void>

  /**
   * The durability barrier — the one operation that promises storage: on
   * resolution every acknowledged append is durable and the session is
   * materialized for other processes.
   */
  flush(options?): Promise<void>

  /**
   * Release the handle. Idempotent, asynchronous, deliberately not cancellable.
   */
  close(): Promise<void>
}
新鲜度契约：一旦 write 句柄上的 append/flush 兑现，之后在同一后端实例上开始的任何读（任何句柄、或经 stat/list）至少能看到该前缀；与写并发的读只保证「合法连续前缀」。read 永不回退、永不返回撕裂的物理尾巴。

5.3① 单写者：内核仲裁的写锁

「同一会话只能有一个写者」不是靠应用层约定，而是靠操作系统（packages/session/session-persistence-jsonl/src/lease.ts 文档注释）：

packages/session/session-persistence-jsonl/src/lease.ts — SessionWriteLease（文档注释）
text/**
 * Cross-process write-ownership lock for one session's artifact directory,
 * held for the whole life of a write handle. The arbiter is the kernel:
 * POSIX takes a non-blocking flock(2) on `session.lock` beside the log, and
 * Windows holds a named kernel semaphore derived from that path — never a
 * file lock or handle, so readers, searches, and directory removal proceed
 * freely while the lock is held. Contention maps to SessionAlreadyOwnedError;
 * the kernel releases the lock when the holder's descriptor or last object
 * handle closes, including on any process death, so a crashed holder never
 * blocks a successor. A live but wedged holder keeps the lock until its
 * process exits: there is deliberately no expiry that could expropriate a
 * stalled writer whose resumed appends would tear the log.
 *
 * A POSIX lock names an inode, not a path, so after locking the holder
 * verifies the locked inode is still the file at the lock path and retries
 * otherwise: an unlinked-and-recreated lock file carries a fresh inode, and
 * a lock on the orphaned one proves nothing.
 */
设计取舍 故意没有锁过期：一个卡死的持有者会把锁保留到进程退出——因为收回锁可能让「唤醒后继续追加」的旧写者撕碎日志。崩溃进程的锁由内核自动释放（描述符关闭），所以“崩溃的持有者永不阻塞后来者”与“活着的卡死持有者保留锁”同时成立。POSIX 侧锁的是 inode 而非路径，持锁后还要验证 inode 未被换掉。

5.4① 检查点策略：flush 的语义边界

检查点不是循环的职责，而是一个独立插件（packages/session/session-checkpoint-policy/src/index.ts）。整个插件只有三个监听器，全部实现为「先 flush，再放行下游」：

packages/session/session-checkpoint-policy/src/index.ts
typescriptexport const name = 'session-checkpoint-policy'
export const inject = ['llm', 'sessionPersistence', 'sessions', 'tools']

/** 延迟构造下游模型流，直到完整已记录的请求前缀持久化。检查点失败则阻止适配器派发。 */
function afterCheckpoint(ctx: Context, session: Session, next: () => AsyncIterable<StreamChunk>): AsyncIterable<StreamChunk> {
  return (async function* (): AsyncIterable<StreamChunk> {
    await ctx.sessions.flush(session)
    yield* next()
  })()
}

export function apply(ctx: Context): void {
  // ① llm/stream：模型请求派发前，持久化完整请求前缀
  ctx.on('llm/stream', (options, next) => {
    if (options.sessionId === undefined) return next()
    const session = ctx.sessions.get(options.sessionId)
    return session === undefined ? next() : afterCheckpoint(ctx, session, next)
  })

  // ② tools/execute：仅顶层调用（exec.agent 存在且无 parent）持久化 tool/call
  //    嵌套派发复用外层的持久化；中止则返回合成结果而非执行。
  ctx.on('tools/execute', async (exec, next) => {
    if (exec.agent === undefined || exec.parent !== undefined) return next()
    await ctx.sessions.flush(exec.agent.session)
    if (exec.signal.aborted) return abortedBeforeDispatchResult()
    return next()
  })

  // ③ agent/pre-step：每个请求边界前，持久化前一步提交的全部内容。
  ctx.on('agent/pre-step', async ({ agent }, next) => {
    await ctx.sessions.flush(agent.session)
    return next()
  })
}
语义：三个 flush 点分别保证「派发给模型前，请求已持久」「工具副作用开始前，tool/call 已持久」「下一个请求前，上一步的一切已持久」。全部 fail-closed——检查点失败时下游适配器/工具体不会被调用。被中止的顶层调用返回合成错误结果（code TOOL_ABORTED_BEFORE_DISPATCH，文本 "Error: tool call aborted before dispatch"）。注意回合边界（turn/end）不 flush——读存储的消费者在 whenIdle() 后自行 flush（第 2 章 turn/end 事件的注释）。

规则回顾（docs/architecture.md + SESSION_FORMAT_VERSION 注释）：header-only 的 stat/list 只扫目录、选最高代际、翻译历史头，不读事件体也不发布后继；body 读（requireStoredLog()）才在内存中组合迁移链、校验最终结果，把它 memoize 成 status:'prepared'——但这时还没有写任何文件。publishStoredMigration() 只在 write 打开（index.ts:387）被调用，「独占发布」的独占指的是写所有权，不是读路径的动作；只读打开拿到的就是一个 prepared 结论，文件保持原样。已提交的代际路径永不重命名、替换或删除。v2→v3 步骤把系统提示词提升为 system/message 表面事件、重映射本地事件引用、翻译 PTC/preset 名称、并把信封规范化（surfaceOp.start/end → startSeq/endSeq）——插入 system 事件会改变事件数与紧邻 seq，这正是 v2→v3 必须 bump 的原因。
V3→V4 的迁移为什么「只有头」：V4 引入了「父/子目录代际」——子 agent 会话自己成了持久代际文件，迁移一个父会话的历史时，体转换必须知道它当时有哪些子会话（tool-result 语义依赖子会话事实）。所以 sessionFormatV3ToV4 的 createStage() 直接抛 SessionFormatUnsupportedMigrationError（migration.ts:14 注释原话 "Header-only migration declaration; body restoration requires explicit child evidence"），真正的体迁移由调用方带 createSessionFormatV3ToV4(children) 显式驱动——JSONL 后端在 prepareStoredMigration 里干这件事：children() 过滤 origin='subagent' 且 parentSession 指向本会话的目录产物，prepareCatalogFacts() 把子代际快照成目录事实，validateRelatedSources() 在发布前重扫目录（清单变了就作废整个 prepared 结论），最后 createSessionFormatCatalogWithChildren(related.facts).createRestore(header, { recovery: 'recoverable', validation: 'transformed' }) 用「带子证据的目录」替换静态目录。没有子会话的父会话要传空数组——错误信息原话：「V3 catalog migration requires explicit historical child facts, including an empty array for a parent without children」。这是 V4 带来的结构性变化：格式迁移不再只是「转换器写对了就行」，还要证明「转换时看到的世界是完整的」。
这个迁移包自己也是迭代的产物：初版 v2-to-v3（提交 f7a6221158，"add identity V2-to-V3 migration and writer skeleton"）只做恒等转换；随后几轮提交逐步加入系统提示词提升（e04cfc4c87）、旧 preset 引用到 PTC 的迁移（ff33f79eb1）、信封规范化（657e68186a）。发布前的最后一轮修复（5212603a4b，"audit every historical content carrier before V3 migration"）补的是初版缺失的内容准入审计：日志里藏着 message 内容的位置远不止五种 Message 事件——压缩摘要（compaction/summary.data.summary）、PTC 前身输出（tool/code-dispatch.data.content）、嵌套在 assistant/message.data.stream[] 里的原始 chunk 块，都是内容载体。为什么必须逐一审计：迁移承诺「保留历史请求含义」，而一个没被理解过的未知 block 类型，无法证明迁移保留了它的含义——所以未知种类直接拒绝整个迁移（SessionFormatUnsupportedMigrationError，诊断带源事件类型、seq 和完整索引路径），而不是「保留字节、假装安全」。审计只检查不重写：tool arguments 和 replayState 保持不透明。写迁移代码时「枚举所有藏数据的位置」这一步没有捷径，唯一的办法是把事件清单过一遍——这个教训对所有要写 format migration 的人适用。

5.6② 崩溃恢复：openTurnClosers() 的确定性缝合

进程在任何时刻死掉，日志都会留下「开口的 turn、开口的 step、未结算的 tool/call」。恢复代码扫描整条日志、合成确定性闭包（packages/core/session/src/repair.ts）。V4 里这个函数泛化成了两用途——崩溃恢复用 interrupted 原因，fork 种子（切割点落在源会话开口回合内）用 forked 原因，共享同一条缝合路径（OpenTurnCloseCause，repair.ts:32）：

packages/core/session/src/repair.ts — openTurnClosers()（节选）
typescriptexport type OpenTurnCloseCause = { readonly kind: 'interrupted' } | { readonly kind: 'forked' }

export function openTurnClosers(events: readonly SessionEvent[], cause: OpenTurnCloseCause): SessionEvent[] {
  let openTurn: number | null = null
  let openStep: number | null = null
  // 每个回合边界重置；assistant 块登记调用，tool/call 事件补充 seq。
  const pendingCalls = new Map<ToolCallId, { step: number; callSeq?: SessionSeqType }>()
  for (const event of events) {
    switch (event.type) {
      case 'turn/start': openTurn = event.data.turn; openStep = null; pendingCalls.clear(); break
      case 'turn/end':   openTurn = null; openStep = null; pendingCalls.clear(); break
      case 'step/start': openStep = event.data.step; break
      case 'step/end':   pendingCalls.clear(); openStep = null; break
      case 'assistant/message':
        // assistant 消息携带 tool-call 块；在出现同 callId 的 tool/result 前都是 pending
        for (const block of event.data.message.content) {
          if (block.type === 'tool-call') pendingCalls.set(block.id, { step: event.data.step })
        }
        break
      case 'tool/call':  /* 记录 callSeq 供合成结果引用 */ break
      case 'tool/result': pendingCalls.delete(event.data.message.source.callId); break
    }
  }
  // 平衡的日志：无需缝合。开口的 turn ⇒ events 非空 ⇒ last 存在。
  const last = events.at(-1)
  if (openTurn === null || last === undefined) return []

  // 合成事件沿用最后真实事件的 seq 基点与时间戳（确定性、不发明未来时间）。
  let seq = last.seq + 1
  const time = last.time
  const closers: SessionEvent[] = []
  // ① 先给未决调用补结果（供应商拒绝悬挂的 assistant 调用）。
  //    正文文案按 cause.kind 取 CLOSER_TEXT：interrupted 与 forked 措辞不同。
  const text = CLOSER_TEXT[cause.kind]
  for (const [callId, { step, callSeq }] of pendingCalls) {
    const started = callSeq !== undefined
    /* …合成 ToolResultMessage：isError: true，
           id 前缀 `${cause.kind}-tool-result-${callId}-${seq}` 确定性… */
    closers.push({
      type: 'tool/result', seq: SessionSeq(seq++), time,
      data: { turn: openTurn, step, message, error: started
        ? { name: 'ToolOutcomeUnknownError', code: TOOL_OUTCOME_UNKNOWN }
        : { name: 'ToolNotStartedError', code: TOOL_NOT_STARTED } },
      surfaceOp: 'append',
      ...started ? { sourceEventSeqs: [callSeq] } : {},
    })
  }
  // ② 再补 step/end —— 开着 step 写 turn/end 是不变量违例
  if (openStep !== null) {
    closers.push({ type: 'step/end', seq: SessionSeq(seq++), time, data: { turn: openTurn, step: openStep } })
  }
  // ③ 最后以 cause 对应的 reason 结束回合（interrupted 或 forked）
  closers.push({ type: 'turn/end', seq: SessionSeq(seq++), time, data: { turn: openTurn, reason: { kind: cause.kind } } })
  return closers
}

// 崩溃恢复入口：interruptedTurnClosers(events) = openTurnClosers(events, {kind:'interrupted'})
两种错误码的语义差（合成结果正文明确写给模型看）：已开始但结果未知（TOOL_OUTCOME_UNKNOWN）→ 模型被告知「仅当只读或幂等才重试；可能有副作用时先核实外部状态或询问用户，不要盲目重试」；未记录为已开始（TOOL_NOT_STARTED）→「若仍需要就重试」。V4 的 forked cause 让同一套机制多了一个消费者：fork 种子在源会话开口回合内切割时，同样的缝合逻辑给出 forked 版措辞——「本分支继承的历史记录了这次调用开始，但不含结果；父会话可能在 fork 点之后已完成它」——模型据此自己决定重试策略，错误码两种 cause 共享（事实相同：调用的记录生命周期不完整）。缝合顺序固定为：先结果、再 step/end、最后 turn/end——因为供应商 API 拒绝悬挂的调用，且 turn/end 出现在开口 step 上是重建不变量违例。

5.7收尾：三个问题的答案

答案回收 ① 可靠落盘 → 三道机制叠出来：存储是缝（SessionPersistence 五方法接口 + JSONL 后端，换后端不动核心），写所有权由内核仲裁（flock/命名信号量，故意无过期），append 可见、flush 耐崩溃，检查点策略插件把 flush 挂在 llm/stream、tools/execute、agent/pre-step 三个语义边界且全部 fail-closed（5.2–5.4）。② 撕裂尾巴 → openTurnClosers() 确定性缝合：未决调用按「已开始/未开始」给两种错误码与写给模型看的正文，顺序固定结果→step/end→turn/end；同一条路径现在也服务 fork 种子（5.6）。③ 格式演进 → 不可变代际 + 静态迁移链，后继文件只在 write 打开时发布；V3→V4 迁移把「显式子会话证据」变成硬要求——体转换必须证明自己看到的世界是完整的（5.5）。下一步进入 第 6 章：工具系统与并行调度。
