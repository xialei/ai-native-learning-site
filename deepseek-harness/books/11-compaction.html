Compaction：在 append-only 日志上「改历史」

日志不可变，但上下文必须能缩。dsh 的答案不是删除，而是遮蔽：选一段表面范围，用一条摘要节点替换它的表面位置，原始事件原封不动地留在日志里。这一章看缝（CompactionEngine）、触发（pressure / context-overflow）、影子定价协议，以及缓存友好的摘要调用。

11.1一分钟版本

  • ctx.compaction 是抽象缝（CompactionEngine），三个方法对应三种入口：compactIfNeeded（自动）、compactNow（手动、idle）、compactRegion（强制区域）。
  • 内置后端 compaction-basic：thresholdRatio 0.8（请求压力阈值）、retainRatio 0.16（逐字尾部保留）、maxTokens 8192（摘要生成上限）。
  • 两个自动触发点：agent/pre-step 上按 pressure 检查；agent/request-error 上按 CONTEXT_WINDOW_EXCEEDED 做 overflow 恢复。
  • 事务由持久事件串成：compaction/start（锁）→ compaction/summary（定价）→ 紧跟的 user/message（真正做表面替换）→ compaction/end（放锁）。
  • 摘要调用是「重放对话 + 最后一条指令」——system/tools/消息前缀逐字复用，让辅助调用命中供应商的 warm prefix 缓存；标记 purpose: 'compaction'。

11.2缝：三个方法三种入口

packages/compaction/compaction/src/index.ts:96 — CompactionEngine
typescriptexport abstract class CompactionEngine extends Service {
  /** 自动：pressure 用最近路由请求计量；context-overflow 可在阈值下强制有效缩减 */
  abstract compactIfNeeded(
    agent: CompactionAgentContext, trigger: CompactionTrigger, signal: AbortSignal,
  ): Promise<CompactionResult | null>

  /**
   * 手动：仅 idle 时经 runMaintenance 执行；先同步启动 idle 任务，
   * 选好范围后先落一条独立 compaction/start——该持久标记就是锁。
   */
  abstract compactNow(
    agent: ManualCompactAgentContext, signal: AbortSignal, sourceCommandId?: CommandId,
  ): Promise<CompactionResult | null>

  /**
   * 强制：把 [start, end] 的表面节点换成一个摘要节点。start/end 是
   * 表面位置（surface position）不是数值区间——之前的替换可能让
   * visible seq 非单调，start 可以大于 end。两边必须 tool-pairing
   * balanced：assistant 工具调用必须与其结果保持配对。
   */
  abstract compactRegion(
    start: SessionSeq, end: SessionSeq, agent: CompactionAgentContext, signal?: AbortSignal,
  ): Promise<CompactionResult>
}
两个类型纪律：① trigger 是封闭联合 'pressure' | 'context-overflow'——失败类也有封闭分类（ManualCompactionError code：busy/cancelled/changed/summary/commit/persistence）；② 「tool-pairing balanced」边界由共享谓词 toolPairingBalancedBefore/After 检查——为什么？deriveMessages（第 2 章）重建的消息序列里，一个 assistant 的 tool_calls 若失去对应 tool result，下一次请求就是 invalid。压缩永远不许打断调用/结果配对。

11.3事件编舞：锁、定价、替换、放锁

影子定价协议：compaction/prune 事件的注释是——「a surface replace event is priced by the metering event immediately before it … which states the heuristic token price of the exact replaced range so a pure consumer can subtract it without retaining per-node prices. The replacement MUST be appended synchronously right after this event.」计量服务用路由定价，而替换节点的投影折叠用固定启发式定价（shadowedTokenCount）——region.ts:375 的注释解释：「prices replacements with the fixed heuristic so the O(1) projection fold stays in agreement with its own appends; retention, range selection, and the shrink comparison read the route-priced tokens instead」。别被「路由定价」这个名字骗了：它不是真实 tokenizer。token-meter 的定价建立在两个源上——固定密度启发式（estimate.ts，CHARS_PER_TOKEN = 4，注释自陈「Fixed text-density estimate used until exact tokenization is needed」），以及路由模型声明的图像/文件请求表示（route-pricing.ts，只在适配器声明了图像计价时覆盖这几类块）。所以「route-priced」的含义是「按本路由的请求投影计价」，比启发式准，但不是分词器。两种定价各司其职：折叠一致性要确定性（同样的内容永远算同样的数），选择决策要尽量贴近本路由的真实开销。

11.4触发：pressure 与 overflow 恢复

先把两个触发点放进一个具体场景：一个深度会话逼近 20 万 token 的上下文窗口。假设当前路由请求计到 18 万 token（阈值 = 20 万 × 0.8 = 16 万，18 万已越过），此刻模型刚返回一轮 tool calls——下一个 step 开始前，挂在 agent/pre-step 上的压力监听器醒来，调 compactIfNeeded(agent, 'pressure', signal)。接下来发生的事（packages/compaction/compaction-basic/src/index.ts 的 compactIfNeeded）：

  • 计量：ctx.tokenMeter.measure(session) 按最近一次路由请求的信封计 token（不是估算整段日志——只有模型真正看到的表面才算数）。
  • 查容量：ctx.llm.resolveModelInfo(provider, model) 拿到该模型的 contextWindow，乘 thresholdRatio 0.8 得出阈值 token 数。适配器没声明容量会直接抛 TargetPressureConfigError——压不压缩取决于一个配置事实，不能悄悄跳过。
  • 先摘低垂果实：达标后先跑 model-free 的 tool-result 修剪（如果挂了 pruner），重新计量；很多会话修剪完就低于阈值了，一次模型调用都不用花。
  • 选范围：selectCompactableRange(session, measurement, retainTokens)（region.ts:117）从尾部向前累计节点 token，直到攒够 retainRatio 的逐字保留区（默认 16%——最近的对话原样留下，模型才不失去当前工作的细节），再从保留区边界向左回退，直到 toolPairingBalancedBefore 确认边界不劈开任何 assistant tool-call/result 对。
  • 压缩并复检：对选出的 [start, end] 跑 11.3 节的事务；成功后重新计量，仍超标就再来一轮（上限 compactionRetries），全打完还超标才抛错。

第二个入口在 agent/request-error 上，对应另一种场景：会话没到 80% 阈值，但请求里有大量 tool-result 大块，供应商直接回了 400 上下文超限。两个监听器的关键差异都写在返回值语义里：

packages/compaction/compaction-basic/src/index.ts — 两个触发点（节选）
typescript// ① 步间压力检查：在 agent/pre-step 上，失败只告警不阻断回合
ctx.on('agent/pre-step', async ({ agent, signal }, next) => {
  if (!signal.aborted) {
    try {
      const result = await this.compactIfNeeded(agent, 'pressure', signal)
      if (result !== null) logResult(result, 'step pressure')
    } catch (error) {
      ctx.logger.warn(`step compaction failed: ${message}; continuing the turn`)
    }
  }
  return next()
})

// ② overflow 恢复：在 agent/request-error 上，只认 CONTEXT_WINDOW_EXCEEDED
ctx.on('agent/request-error', async ({ agent, failure, signal }, next) => {
  if (failure.code !== CONTEXT_WINDOW_EXCEEDED_CODE || signal.aborted) return next()
  // 超过 maxOverflowRetries 就放弃；成功的 assistant/message 重置计数
  const generation = agent.session.surface.replaceGeneration
  const result = await this.compactIfNeeded(agent, 'context-overflow', signal)
  // 表面 generation 没变 = 什么都没替换 → 保留原始错误；
  // 变了 → { kind: 'retry' } 用新表面重发原请求
  if (agent.session.surface.replaceGeneration <= generation) return next()
  return { kind: 'retry' }
})
初读最容易误判的一点：pressure 失败只 warn、overflow 失败却把错误原样放行——差别不在代码风格，在谁还活着。pressure 检查发生在 step 之间，模型请求还没发，压缩失败只是「本步多花点 token」，回合继续是对的；overflow 发生在模型已经拒绝之后，压缩若什么都不做，放回 next() 就等于把同一个必死的请求交回默认错误处理。另注意 overflow 路径的 compactIfNeeded 走的是「绕过阈值」分支（index.ts 注释：「overflow bypasses the normal threshold and retained-tail policy so it can force one useful balanced reduction」——provider 已经确认超限，0 阈值全量选择，只受 tool-pairing 约束）。replaceGeneration（第 2 章）在这里当「表面是否真的变了」的守卫：压缩失败但 prune 已经落地时，注释说「That durable reduction is sufficient retry proof; do not discard it just because the optional second phase threw」——部分成果也算进展，重试从替换后的表面继续。

手动入口落在哪：/compact 命令（dsh-command-compact，bundle/base/cordis.patch.yml:323）走第三个方法 compactNow——它只在 idle 时经 runMaintenance 执行，而且目标与自动触发不同：「one useful reduction below the automatic threshold」——用户主动要压缩时，会话可能还没到 0.8 阈值，所以 compactNow 用 0 阈值语义强制做一次有效缩减（ManualCompactionError 的 busy 码就是 11.3 那把事件锁在说话）。

11.5摘要调用：重放对话，命中 warm prefix

packages/compaction/compaction-basic/src/summarizer.ts — 设计注释与指令（节选）
typescript/**
 * The summarization directive, delivered as the FINAL user message after the
 * replayed conversation rather than as a distinct summarizer system prompt.
 * Keeping the conversation's own system prompt, tools, and message prefix in
 * front of it makes the auxiliary call a genuine prefix of the last routed
 * request, so the provider's KV cache is reused instead of invalidated.
 */
const COMPACTION_INSTRUCTION = [
  'You are now acting as a compaction engine for this AI coding assistant. '
  + 'Condense the conversation ABOVE into a structured checkpoint…',
  '',
  '## Primary Request and Intent',
  "- [the user's original and evolving goals; quote verbatim where the exact wording matters]",
  '## Key Technical Concepts', '## Files and Code', '## Errors and Fixes',
  '## Pending Jobs', '## Current Work', '## Next Step', '## Critical Context',
  '',
  'Rules:',
  '- Preserve exact file paths, commands, error strings, identifiers, numeric values…',
  '- Capture user feedback and explicit instructions faithfully, especially corrections.',
  '- Do NOT mention this summarization request or that the context was compacted.',
  '- Output only the checkpoint text: do not call any tool…',
  `- If the conversation already contains a <compacted-summary> block, it is a PRIOR checkpoint. 
    Do not copy it forward verbatim: preserve still-true facts, drop stale ones, merge…`,
]

/** Framing that makes the replacement user message established context. */
const CHECKPOINT_PREAMBLE =
  'This is an automatically generated checkpoint condensing an earlier span of the '
  + 'conversation to free up context. Treat the captured context as established background…'

export interface SummarizationInput {
  /** 会话的工具 schema——为前缀缓存对齐而复用 */
  readonly tools?: readonly ToolSchema[]
  /** 派生出的 system 头（若有）在前，其后是被遮蔽区域，表面顺序 */
  readonly messages: readonly Message[]
}
三处缓存敏感设计：① 指令是最后一条 user 消息而不是独立 system prompt——前缀 = 会话自己的 system + tools + 消息开头，与最近一次路由请求逐字相同，KV 缓存直接复用，唯一的新 token 是尾部指令。注意 system 头现在已经不走单独的 system 字段了：提交 8bde913784（"replay the derived system head as a message"）把它并进 messages 的队首——既然会话本来就把它派生为一个 Message、两个适配器也都接受前导 system 历史，再传一条字符串只是让适配器把它重新拼回同样的线上消息；② 摘要调用带 purpose: 'compaction'（第 7 章 GenerateOptions 的辅助调用分类，适配器可把它映射为模型不可见的传输元数据或专用生成策略；真正用于分离重放游标的是并行的 sessionId——types.ts:449 注释：「Session identity stamped by the loop for request routing. Replay uses it to separate cursors」）；③ 落地的 checkpoint 消息由 CHECKPOINT_PREAMBLE 框定 + <compacted-summary> 标签包裹结构化内容，且指令要求模型「遇到旧 checkpoint 就合并而非照抄」——连续多轮压缩不会堆叠陈旧摘要。第 8 章的 runtime-context 快照协议正是这一切的先决条件：动态上下文不进 system prompt，所以重放前缀才可能与路由请求对齐。

11.6检查点来源：后端无关的识别标记

packages/compaction/compaction/src/checkpoint.ts:19 — COMPACT_CHECKPOINT_MARKER
typescriptconst COMPACT_CHECKPOINT_MARKER = Object.freeze({ kind: 'plugin', plugin: 'compact' } as const)

/** Message provenance carried by a concrete compaction checkpoint. */
export type CompactionCheckpointSource = typeof COMPACT_CHECKPOINT_MARKER & {
  readonly compactionId: CompactionId
  readonly sourceCommandId?: CommandId
}

export function isCompactCheckpointSource(source: MessageSource): boolean {
  return source.kind === 'plugin' && source.plugin === COMPACT_CHECKPOINT_MARKER.plugin
}
为什么单拎一个文件：注释说这个模块是「a pure type/value/predicate outlet (no cordis imports, no module augmentation) so client and wire programs can name the checkpoint source without loading the host plugin's Context merges」。识别一个消息是不是 compaction 检查点，不该强迫消费者加载整个宿主插件——第 8 章 RuntimeContextProjection 用 source.plugin 恢复快照归属是同一招：消息来源是持久、可折叠、后端无关的事实通道。

11.7要点

要点 ① 压缩 = 遮蔽不是删除：日志只增，表面用 replace 换成摘要节点；② 事务即事件编舞：start 持锁 → summary 定价 → 相邻 user/message 替换 → end 放锁，失败尝试也留在日志；③ 影子定价协议让纯消费者 O(1) 对账，启发式与路由定价各管折叠与决策；④ 摘要调用重放会话前缀命中 KV 缓存，purpose 隔离游标；⑤ 边界必须 tool-pairing balanced，永远不打断调用/结果配对。下一步看多 agent 编排：第 12 章：编排与多 Agent。
