AI 层：摸到模型的统一手掌

pi-ai 凭什么让上层循环「换 Provider 成本近乎为零」——哪些东西被统一了，错误怎么处理？一个 Model 值对象要画像到什么程度，上层策略才能只读事实、不猜行为？「系统提示 + 工具声明」后来为什么搬进了消息流？厂商之间那些「同义不同形」的参数（工具选择、思考预算、strict 模式），抽象层又怎么收编？本章沿这些问题看 pi-ai 怎么把数十家 Provider 装进一套契约。
产品视角 「15+ Provider，数百个模型。」 Anthropic、OpenAI、Google、Azure、Bedrock、Mistral、Groq、Cerebras、xAI、Hugging Face、Kimi、MiniMax、NVIDIA、OpenRouter、Ollama、Meta（Muse 订阅，OAuth 自动刷新）……API key 或 OAuth 鉴权；用 /model 或 Ctrl+L 会话中途切模型，Ctrl+P 循环收藏夹；还能经 models.json 或扩展加自定义 Provider 与模型。→ 本章看这套「换 Provider 成本近乎为零」的抽象在源码里怎么落地。

10.1pi-ai 的定位：把「模型」从「循环」里拆出来

回想架构分层：pi-agent-core 只管消息与循环，它不直接调任何厂商 API。真正跟 Anthropic / Google / OpenAI 对话的是 pi-ai。它的职责可以概括为：把「换 Provider」的成本压到近乎为零，同时对上层暴露一个极其稳定的接口。

这套设计的三个不变量，几乎决定了整个上层怎么写：

  • 模型是值对象，不是连接：Model 只是「描述一个可调用模型」的纯数据（名字、baseUrl、窗口大小、能力）。连接、鉴权、网络都在别处处理。它能在会话、压缩、UI 之间到处传，而不用带着一个 live socket。
  • 流式返回事件，不返回最终串：stream() 返回 AssistantMessageEventStream——一个逐事件推送的协议（消息开始/更新/结束）。这直接喂给第 3 章的 streamAssistantResponse，让「打字机效果」和「响应用户打断」成为天然能力。
  • 错误不会抛出，而是编码在流里：契约明确「request/model/runtime 失败应编码进流，而不是 throw」。这是为了恢复——上层能在流结束处读到 stopReason: "error" + errorMessage，进而判断该压缩还是该重试（第 8 章）。
为什么「错误编码在流里」如此重要？若失败以 throw 形式逃逸，上层循环要写一堆 try/catch 去猜「这次是不是该重试、该压缩」。而 Pi 的统一约定是：任何失败都变成一条带 stopReason:"error" 的 assistant 消息。于是第 8 章的 _checkCompaction / _isRetryableError 只需读消息字段，逻辑异常干净。这值得你写 Runtime 时抄。

10.3.1 错误的二次分类：溢出识别与可重试判定

「错误编码在流里」只是半件事——错误消息到手后，怎么知道这次该压缩还是该重试？两类判断都收在 pi-ai 的 utils 里，靠的不是玄学，而是从各家错误文本里逐条收编的正则模式。

溢出识别（isContextOverflow）是两者里最费劲的。理想的溢出错误长得像 Anthropic 的「prompt is too long」，但现实是每个 provider 的失败方式都不一样：OpenAI 说「exceeds the context window」，Bedrock 说「input is too long for requested model」，LiteLLM 代理有自己的一套话术；Cerebras 更绝——超限时直接返回没有响应体的 400/413，只能靠「provider 是 Cerebras + 状态码」这个组合判断；z.ai 有时根本不报错，静默收下超限请求，只能事后用 usage.input > contextWindow 兜底检测；小米 MiMo 会把输入截断到恰好填满窗口再返回 finish_reason: "length"、输出 0 token——「没有输出 + 输入贴着窗口」就是它的溢出面相。于是这个函数是三段式：错误消息先过「已知非溢出模式」（限流类先排除，防止误判），再匹配溢出正则；无错误但成功时检查 usage 是否贴穿窗口；length 结束且零输出时再查一次窗口占用。值得咀嚼的是这份注释里的维护姿态——源码把每家的原始错误文本样例逐条列在函数头注释里，新的网关话术出现时就照着补一条。你自研时遇到「模型报错但不知道能不能救」，这份数据模型（错误文本 → 归类 → 对应自救动作）比任何通用启发式都可靠。

可重试判定（isRetryableAssistantError）则是两张表：RETRYABLE_PROVIDER_ERROR_PATTERN（overloaded / rate limit / 429 / 5xx 全家 / 520、524 这些 Cloudflare 特有码 / Azure 的峰值容量话术）与 NON_RETRYABLE_PROVIDER_LIMIT_ERROR_PATTERN（quota、billing、insufficient credits——钱的问题不重试，重试也不会好）。同样是「错误编码在流里」的红利：这个判定只需要读 errorMessage 字符串，于是在 pi-ai 的 retryAssistantCall（供压缩摘要等轻量调用用）和第 8 章生产层的自动重试之间共享同一份分类——「什么算暂时性错误」全站只有一张答案。而 _isRetryableError 的实际实现只有三行，顺序有讲究：先排除溢出，再问可重试——溢出由压缩管道负责，重试管道不越界。

10.2Model 值对象：一个「模型」的完整画像

Model 在 packages/ai/src/types.ts，约 30 个字段。逐个看那些上层真正依赖的：

packages/ai/src/types.ts · Model 接口
export interface Model<TApi extends Api> {
  id: string;                 // 唯一标识（如 "claude-opus-5"）
  name: string;               // 人类可读名
  api: TApi;                   // 协议族：anthropic-messages | openai-responses | google …
  provider: ProviderId;        // Provider：anthropic / google / openai …
  baseUrl: string;            // 指向哪（可换端点/网关）
  reasoning: boolean;        // 是否支持思考
  thinkingLevelMap?: ThinkingLevelMap;  // 把 pi 的思考档位映射到各厂商的值
  input: ("text" | "image")[];    // 能吃什么输入
  inputLimits?: ModelInputLimits;  // 输入上限 + 进历史前的图片预处理画像
  cost: ModelCost;            // 计价（用于精确 token 与成本估算）
  promptCache?: ModelPromptCache;  // 各缓存档位的存活秒数（缺档位 = 不明，不保温）
  contextWindow: number;     // 上下文窗口 —— 压缩与溢出判断的锚点
  maxTokens: number;        // 最大输出 —— 长度恢复判断的锚点
  samplingParams?: ...;       // 默认采样参数（temperature 等）
  headers?: ...;              // 附加请求头
  compat?:
    TApi extends "openai-completions" ? OpenAICompletionsCompat   // 按协议族的
    : TApi extends "openai-responses" ? OpenAIResponsesCompat      // 兼容行为覆写
    : TApi extends "anthropic-messages" ? AnthropicMessagesCompat
    : TApi extends "bedrock-converse-stream" ? BedrockCompat
    : TApi extends "mistral-conversations" ? MistralConversationsCompat : never;
}

几个值得展开的字段：

  • api vs provider:两者不是一回事。api 是协议族（该怎么对话，走 anthropic 还是 openai-responses 语法），provider 是Provider（向谁付费、谁鉴权）。一个 Provider 可以同时实现多种 api 兼容。
  • contextWindow / maxTokens：这是「能力画像」里最要命的两条。第 6 章压缩用 contextWindow判断是否溢出，第 8 章的溢出恢复用 maxTokens 判断「输出是否提前被掐断」。
  • thinkingLevelMap：pi 定义了自己的一套「思考级别」档位（第 4 章见过 ThinkingLevelEntry），但各家厂商叫法不同（有的叫 effort，有的叫 thinking budget）。这里的映射把 pi 的抽象语言翻译成各厂商的具体参数，未映射则用默认。
  • promptCache：prompt cache 条目在各保留档位（short/long）下预计存活多少秒。请求侧则用 SimpleStreamOptions.cacheRetention 声明「这次想用哪个档位」（默认 short，env PI_CACHE_RETENTION=long 可整体切到 long）。别看它只是几个数字——它是生产层「缓存保温」策略的输入：模型画像里没有某档位的存活时长，意味着「这家 provider 的缓存行为还没被验证过」，pi 就绝不替它做保温（内置目录里目前只有直连 Anthropic 填了 5 分钟/1 小时；自定义模型可以在 models.json 里用 promptCache 声明后加入）。这是画像方法论的又一例：「能不能做某策略」先变成画像上的一条事实，再让策略去读它。
  • inputLimits：输入侧的另一份画像，分两截。maxRequestBytes 与 images.maxPerMessage/maxPerRequest 是描述性的硬上限（目录生成时从各家文档收编进来：Anthropic 单请求 32MB、单请求最多 100/600 张图，OpenAI 512MB/1500 张，Bedrock 每消息 20 张……）；images.resize 则是可执行的预处理画像——新图片进会话历史之前就按它编码（maxWidth/maxHeight/maxBytes/jpegQuality，默认 2000×2000、4.5MiB、JPEG 质量 80），附件、read 工具、工具返回的图片三处共用同一份。注意这里的取舍：图片只编码一次，中途换模型不重写历史里的旧图——否则缓存前缀全废。这是「先对齐再进历史」的策略：与其让请求在 API 上炸掉，不如在画像里声明「我家吃多大的图」。models.json 的 modelOverrides[...].inputLimits 按 images.resize 字段深合并，你可以给经网关的模型收紧阈值。
  • compat（条件类型）:同协议的不同实现常有细微差别（比如 OpenAI Responses 的老版 compat 开关）。它按 api 收紧类型，保证「只有该协议族才可能有对应 compat」。
一个模型 = 一份「画像」，这很重要：正因为 Model 是纯数据，你可以在 run 前、压缩前、UI 里分别读取它的窗口与能力，而无需真正建连。这是「把策略（要不要压缩）和事实（窗口多大）分离」的典范。

10.3Provider 契约：stream 才是宇宙的中心

每个提供商模块（src/providers/anthropic.ts、google.ts 等）都实现同一套 ProviderStreams 契约。最核心的是 stream：

packages/ai/src/types.ts · ProviderStreams 契约
export interface ProviderStreams {
  // 主入口：把「模型 + 上下文」流式地吐成 assistant 消息事件
  stream(model: Model<Api>, context: TranscriptContext, options?): AssistantMessageEventStream;
  // 简化版：只给一条 user 消息，无工具（用于压缩摘要等轻量调用）
  streamSimple(model: Model<Api>, context: TranscriptContext, options?): AssistantMessageEventStream;
  // 可选：异步续跑（deferred），拿回一个 durable handle
  fetchDeferred?(model, handle, options?): AssistantMessageEventStream;
  cancelDeferred?(model, handle, options?): Promise<void>;
}

注意参数类型是 TranscriptContext 而不是 Context——这是一对刻意区分的类型：

packages/ai/src/types.ts · Context 与 TranscriptContext（原文注释为译注）
// 调用方拿到的请求输入：systemPrompt/tools 只是「头部 system 消息」的简写
export interface Context {
  systemPrompt?: string;
  messages: Message[];
  tools?: Tool[];
}

// provider 实际收到的：prompt 与工具声明全部由消息流里的 system 消息承载。
// 只有 normalizeContext() 能造出这个类型——裸 Context 到不了 provider 手里
export type TranscriptContext = {
  messages: Message[];
  readonly [transcriptContextBrand]: true;
};

Context 仍允许你用「系统提示 + 消息 + 工具」三件套表达一次请求——这正是第 5 章 buildSessionContext 产出的形状。但进 provider 前必须过 normalizeContext()：它把 systemPrompt/tools 简写折叠成一条头部 system 消息，返回带品牌标记的 TranscriptContext。brand 是 TypeScript 的惯用手法——一个不存在的 phantom 字段让两个结构相同的类型互不兼容，编译器替你把关「没归一化的请求进不了 provider」。所以上层的数据流是：

数据流串联
// agent-core 里其实只有这一句真正打到模型：
const llmContext = normalizeContext({ messages: llmMessages });
const stream = model.stream(model.model, llmContext, options);
// 上层再从 stream 里收 AssistantMessageEvent（msg_start / msg_update / msg_end）

带 deferred 能力的 Provider，还能「异步续跑」：请求返回一个 handle，真正的结果后台继续生成，稍后 fetchDeferred(handle) 拿回。这服务于超长推理场景，避免长时间占着连接。

设计考量：streamSimple 的存在提醒我们——抽象层不该只提供一个「万能笨重接口」，而应为不同调用场景提供不同「带宽」。压缩这种内部辅助调用不该背负完整 Agent 请求的复杂度。

10.3b流式事件协议：内容与载体分离

流的产出不是一段最终文本，而是一串 AssistantMessageEvent。内容被细分为几种「分块」，这是第 2 章「消息类型学」的延续：

packages/ai/src/types.ts · 内容分块类型
export interface TextContent {
  type: "text";
  text: string;
  textSignature?: string;   // 端侧 token（如 OpenAI 的 msg id / 签名）
}
export interface ThinkingContent {
  type: "thinking";
  thinking: string;
  thinkingSignature?: string; // 思考的端侧 id，续轮时回传以保持连续性
  redacted?: boolean;          // 被安全过滤遮蔽（内容不可读，仅留签名）
}
export interface ToolCall {
  type: "toolCall";
  id: string; name: string; arguments: Record<string, any>;
  thoughtSignature?: string;  // Google 特有：复用思考上下文的密钥
  namespace?: string;         // OpenAI Responses 动态/命名空间工具
}

这些「分块类型」与第 2 章的 AgentMessage.content 是同一套词汇——AI 层的流事件最终被 agent-core 转成 AssistantMessage 的 content 数组。注意「签名」字段体系：textSignature、thinkingSignature、thoughtSignature 本质都是「把端侧不透明 token 原样回传」以维持多轮连续性（尤其思考被遮蔽时，内容是空的，但签名还在，续轮还能续得上）。

被遮蔽的思考仍可持续：redacted: true 表示这轮思考被安全过滤器遮蔽，你读不到内容。但 thinkingSignature 保留了加密后的不透明载体，原样回传给 API 即可保持思维连续性。这是「模型侧保护隐私、应用侧保功能」的精细平衡。

10.3c流式代理：带宽减半的 SSE 重建

10.1–10.4 讲了 stream() 契约与流事件类型，但没讲 packages/agent/src/proxy.ts——一个把 LLM 调用路由到「只管代理」的服务端的流式客户端。它最妙的优化是服务器在增量事件里不重复携带整条消息，客户端自己逐块重建：

proxy.ts · 增量文本事件（服务器只发 delta）
// 服务器发送的瘦事件：只有「哪一块 + 增量」（节选）
export type ProxyAssistantMessageEvent =
  | { type: "start" }
  | { type: "text_start"; contentIndex: number }
  | { type: "text_delta"; contentIndex: number; delta: string }
  | { type: "text_end"; contentIndex: number; contentSignature?: string }
  | { type: "thinking_start"; contentIndex: number }
  | { type: "thinking_delta"; contentIndex: number; delta: string }
  | { type: "thinking_end"; contentIndex: number; contentSignature?: string }
  | { type: "toolcall_start"; contentIndex: number; id: string; toolName: string }
  | { type: "toolcall_delta"; contentIndex: number; delta: string }
  | { type: "toolcall_end"; contentIndex: number; toolCall: ToolCall }
  | { type: "done"; reason: ...; usage: ... }
  | { type: "error"; reason: ...; errorMessage?: string; usage: ... }

客户端维护一个 partial 消息对象，把增量拼进去，并对外重新产出标准事件。最精妙的是工具调用参数的增量 JSON 解析：

proxy.ts · 流式工具调用参数重建
case "toolcall_start":
  partial.content[proxyEvent.contentIndex] = {
    type: "toolCall", id: proxyEvent.id, name: proxyEvent.toolName,
    arguments: {}, partialJson: "",
  } satisfies ToolCall & { partialJson: string } as ToolCall;
  return { type: "toolcall_start", contentIndex, partial };

case "toolcall_delta": {
  const content = partial.content[proxyEvent.contentIndex];
  if (content?.type === "toolCall") {
    content.partialJson += proxyEvent.delta;                    // 累积残缺 JSON
    content.arguments = parseStreamingJson(content.partialJson) || {}; // 边到边解析
    return { type: "toolcall_delta", contentIndex, delta: proxyEvent.delta, partial };
  }
  throw new Error("Received toolcall_delta for non-toolCall content");
}

parseStreamingJson 是 pi-ai 提供的「接受残缺 JSON、尽量解析」的解析器——工具参数通常还是一个不完整的对象时，就能解析出已能确定的字段，让 UI 能提前渲染「即将调用的工具」。一旦 toolcall_end 到达，用完整对象覆盖并清掉 partialJson。

三个细节一次给到：
  • 带宽优化——delta 里不重复带整条消息，长对话能省大量字节；
  • 可恢复性——parseStreamingJson 让「调工具意图」能提前浮现，而非等整个 JSON 到齐；
  • 契约一致——客户端重建后仍按标准 AssistantMessageEvent 输出，上层完全无感知。
这与本章前面学到的「错误进流/流协议」是同一条纪律。

10.4模型目录与生产侧封装

模型清单集中在生成文件（models.generated.ts / model-catalog.ts），把「某 Provider 某型号具备什么能力」集中描述——这通常由脚本从厂商文档生成，保持最新且不手抄。生产 harness 在 model-runtime.ts / model-registry.ts 之上再加一层运行态封装：

生产侧真正跑请求前的还有鉴权检查——第 8 章我们在 prompt() 里见过：

agent-session.ts · 跑前鉴权校验（节选，第 8 章见过）
if (!this.model) throw new Error(formatNoModelSelectedMessage());
const hasConfiguredAuth =
  this._modelRuntime.hasConfiguredAuth(this.model.provider) ||
  (await this._modelRuntime.checkAuth(this.model.provider)) !== undefined;
if (!hasConfiguredAuth) {
  // 若走 OAuth 就给更贴切的提示，否则提示 /login<provider>
  if (this._modelRuntime.isUsingOAuth(this.model.provider)) { ... }
  throw new Error(formatNoApiKeyFoundMessage(this.model.provider));
}

压缩路径用的摘要请求也走 ModelRuntime 的鉴权封装（_getSummarizationRequestAuth），确保「压缩用的模型」同样合法可用——这不是顺手为之，而是避免「主模型有 key、摘要模型的 key 没配」导致的诡异压缩失败。

分层链路收口：生成目录（静态画像）→ Registry（检索货架）→ Runtime（运行态鉴权/建连）→ AgentSession（喂循环）。四层各司其职，让「换模型」这件事在任一层次都不需要改协议。这正是把「稳定的抽象」与「易变的 Provider」隔开的完整实践。

10.6.1 四个值得记住的 Provider 兼容细节

抽象层的好处是「一套契约打天下」，但代价是要把厂商之间的差异收编进数据模型。pi-ai 里有四处收编很典型，值得自研时借鉴：

  • 工具选择（ToolChoice）：pi 定义了 provider 中立的 type ToolChoice = "auto" | "none"，挂在 SimpleStreamOptions.toolChoice 上。摘要这类「不该调工具」的请求就显式传 "none"（见第 6 章）。各 provider 再翻译成自家术语——Anthropic 转成 { type: "none" }、Google 走 functionCallingMode、OpenAI/Responses 透传 tool_choice。差异藏在适配器里，上层只说一个意图。
  • 思考预算字段（thinkingTokenBudgetField）：vLLM/Qwen/llama.cpp 这类 OpenAI 兼容端点上，「推理」与「答案」共享 max_tokens——不设预算，一轮重度推理可能吃光整个响应、一个字答案都不吐。pi 把「用哪个字段封顶」也做成可配：ThinkingTokenBudgetField = "thinking_token_budget" | "thinking_budget" | "thinking_budget_tokens"（分别是 vLLM / Qwen·DashScope·SGLang / llama.cpp 的字段名）。旧的布尔 supportsThinkingTokenBudget 保留为 thinking_token_budget 的别名。配合 { "$var": "thinking.budget" } 这个 chat-template 变量，思考级别就能跨端点统一调控。
  • Anthropic 拒答兜底（allowedFallbackModels）：Anthropic 支持服务端拒答 fallback——主模型拒答时由服务端自动切到备选模型。但不是所有模型都能写进 fallbacks，写错了 API 会拒。于是 AnthropicMessagesCompat.allowedFallbackModels 显式列出「被允许的兜底模型 + 本地定价元数据」，适配器只在列表非空时才发 fallbacks，并在返回里用本地价格给兜底响应算成本。把「能不能兜底」也当成模型画像的一部分，而不是运行时瞎试。这份元数据还能被用户改：models.json 的 modelOverrides["<model-id>"].compat.allowedFallbackModels 直接替换内置列表（不是合并；给个空数组就整体关掉兜底），最多 3 条且每条必须带完整 cost——因为兜底响应要按本地价格计费，缺价格就算不出成本。
  • strict 工具开关的默认值翻转（supportsStrictMode）：这条有个值得记住的演化痕迹。早期 OpenAI Completions 适配器的逻辑是「OpenAI 兼容 ⇒ 默认支持 strict 工具字段，再逐家排除不支持的（Moonshot、Together、NVIDIA、Cerebras……）」——黑名单思维。实际运转让它撑不住了：扩展可以同时注册 strict 和非 strict 工具，某家端点混用两者直接报 400；而且「兼容」的端点千千万，黑名单永远追不完。于是默认值翻转为 false，只有生成目录里验证过的模型显式开启——从「证明你有问题才关」变成「证明你没问题才开」。工具 schema 的 strict 字段也只在 supportsStrictMode !== false 时才附上（有的端点连多余字段都拒收）。相邻的一个小例子：多模态 user 消息进 OpenAI Completions 时，空文本块会被直接滤掉（commit 1b6ddca87）——有的端点连「text: ""」都不肯收，与其在画像里加开关，不如直接在适配器里归一。
自研启示：抽象层的真正工作量不在「定义接口」，而在把这些「同义但不同形」的厂商参数——工具选择、思考预算、兜底策略、schema 严格度——逐个翻译成统一意图、再把意图落回各家术语。ToolChoice（一个枚举）与 thinkingTokenBudgetField（一个字段名枚举）是两种典型收编：前者把差异吸收进抽象、后者把差异枚举成配置。而 supportsStrictMode 的默认值翻转展示了第三种：能力声明宁可保守，让「被验证过」成为唯一的开启路径。

10.6.2 系统提示走进消息流：SystemMessage 与它的重放规则

10.3 留了一个问题的下半截：TranscriptContext 里只剩 messages，那系统提示和工具声明放在哪？答案是也放在消息流里，以一条条 SystemMessage 的形式。这是 pi-ai 类型体系里变化最大的一处：

packages/ai/src/types.ts · SystemMessage（节选，注释为译注）
export interface SystemMessage {
  role: "system";
  // 头条消息里是基础 prompt；后续消息里是追加的指令
  content: string | TextContent[];
  // 命名小节：头条声明，后续按名字替换，null 删除该节
  sections?: Record<string, string | null>;
  // 从这里开始可用的完整工具定义 / 从这里停用的工具
  toolsAdded?: Tool[];
  toolsRemoved?: ToolReference[];
  timestamp: number;
}

第一条 system 消息（normalizeContext 折叠出来的那条，或会话开头的 baseline）声明完整的 prompt 与工具；之后每条只带增量——追加一段 content、替换某个命名 section、增删几个工具。重放规则收在一个函数里：

packages/ai/src/utils/transcript.ts · 重放（节选，注释为译注）
// 从任意消息列表重放出「此刻真正生效的」一条 system 消息
export function getCurrentSystemMessage(messages: TranscriptMessages): SystemMessage | undefined {
  const content: string[] = [];
  const sections = new Map<string, string>();
  let timestamp: number | undefined;
  for (const message of messages) {
    if (!isSystemMessage(message)) continue;
    timestamp ??= message.timestamp;                                   // 时间戳取头条那条的
    const text = contentText(message.content);
    if (text.length > 0) content.push(text);                      // content 是追加
    for (const [name, value] of Object.entries(message.sections ?? {})) {
      if (value === null) sections.delete(name);
      else sections.set(name, value);                             // sections 按名替换
    }
  }
  const tools = getCurrentTools(messages);   // 工具同理：toolsRemoved 删、toolsAdded 增
  // 既没有任何 system 消息、也没有工具声明 → 返回 undefined
  if (timestamp === undefined && tools.length === 0) return undefined;
  return { role: "system", content: content.join("\n\n"), ..., timestamp: timestamp ?? 0 };
}

为什么要把 prompt 塞进消息流？因为它让 prompt 获得普通消息的一切待遇：能序列化、能重放、能被压缩条目存档（第 6 章）、能随会话树分叉。以前 systemPrompt 是 AgentState 上的一个独立字段，压缩、分叉、扩展改 prompt 都要各自维护「字段现在的值是什么」；现在它就是 transcript 的前缀，重放一遍自然得出。

但 provider 各家接受度不同，于是有一道收口：

packages/ai/src/utils/transcript.ts · 能力协商（注释为译注）
// 能中途收 system 消息的 provider（如 Anthropic）按原样保留；
// 不能的（如 OpenAI 系）把重放结果收敛成一条头部消息，后面的全丢
export function resolveTranscript(context, supportsMidConvoSystemMessages) {
  return supportsMidConvoSystemMessages ? context : collapseSystemMessages(context);
}

// collapseSystemMessages：把重放结果放在头部，其余 system 消息全部滤掉
export function collapseSystemMessages(context) {
  const head = getCurrentSystemMessage(context.messages);
  const messages = context.messages.filter((m) => m.role !== "system");
  return { messages: head ? [head, ...messages] : messages };
}

是否支持由模型画像上的 compat 标志声明（supportsMidConvoSystemMessages、Anthropic 另有 supportsMidConvoToolChanges）。这个函数体本身只有一行三元，但值得咀嚼的是它的签名——「中途 system 消息」只有能不能发、没有撤回一说：中途改 prompt 意味着前面几轮对话是在旧 prompt 下进行的，这件事无法对已发生的轮次生效，所以不存在「让新 prompt 作用于历史」的语义，能力协商也就不需要更细的档位。这是一个「能发给 API 的」与「模型真实经历的」之间的诚实折中。

演化痕迹：曾经存在过一个 replace 字段。SystemMessage 曾有 replace?: boolean——「应用本条之前，先丢弃之前所有 system 状态」，且一旦 transcript 里出现「迟到的 replace」，无论 provider 能力如何都整体收敛成头部消息。这个字段后来被整体删除（commit 16292398a）：生产层发现，把扩展强制注入的 prompt 持久化成一条 replace 消息，会在每次变更时把完整 prompt 与工具清单写一遍 transcript、丢失结构化 sections，还让本会话之后的中途 system 消息全部失效。根本原因是概念错位——「本次请求临时用的 prompt」不是对话状态，不该进 transcript。如今这类强制 prompt 在 coding-agent 层被投影处理：请求时通过 transformContext 把 system 消息收拢成一条持有强制文本的头部消息，transcript 里始终只存结构化 sections（见第 8 章）。重放规则因此变得纯粹：对 system 消息只做追加、按名替换、增删工具，没有例外分支。
Anthropic 的原生工具变更与缓存占位：两个 compat 标志都开时，Anthropic 走 beta 特性 mid-conversation-tool-changes-2026-07-01 的原生工具增删：初始工具保持激活并作为缓存锚点，之后声明的工具全部 defer_loading: true，由消息流里的 tool_addition 块按需激活、tool_removal 撤回——请求级工具列表只增不减，缓存前缀不因工具变更而失效。还有个反直觉的防御：Anthropic 只要有任何工具带 defer_loading 就会注入隐藏的 prompt 脚手架，pi 于是在第一次请求就声明一个永不激活的占位工具 __pi_deferred_placeholder__，把这段脚手架提前钉进缓存前缀——没有它，第一个真正的迟到工具会打穿整个缓存（源码注释注明「实测：没有它是全量 miss」）。

10.5收尾：一张心智模型与四个答案

收尾——四个问题的答案：统一的是「值对象 + 流契约」：Model 是纯数据画像，stream() 只发事件、错误编码在流里（stopReason:"error"），上层压缩/重试只读消息字段。画像画到「策略只读事实」的程度：contextWindow/maxTokens 喂压缩与恢复，promptCache/inputLimits/compat 标志决定「能不能做某策略」——事实进画像、策略只读表。系统提示进消息流，是因为它让 prompt 获得普通消息的一切待遇（序列化、重放、随分叉）；replay 规则只有追加/按名替换/增删工具三种，临时强制 prompt 不进 transcript。收编靠两种手法：把差异吸收进抽象（ToolChoice 一个枚举）或枚举成配置（thinkingTokenBudgetField）；能力开关宁可保守——supportsStrictMode 默认翻转成 false，让「被验证过」成为唯一开启路径。
