AI 层：摸到模型的统一手掌

前几章都在「消息/循环/会话」这一侧打转。这一页把镜头转向 @earendil-works/pi-ai——Pi 怎么用一个 Model 值对象和一套 stream() 契约，把 Anthropic、Google、OpenAI、Groq、DeepSeek、GitHub Copilot 等数十个供应商统一成同一个手掌，让上层 Agent 循环只认一种流协议。
产品视角 「15+ 供应商，数百个模型。」 Anthropic、OpenAI、Google、Azure、Bedrock、Mistral、Groq、Cerebras、xAI、Hugging Face、Kimi、MiniMax、NVIDIA、OpenRouter、Ollama……API key 或 OAuth 鉴权；用 /model 或 Ctrl+L 会话中途切模型，Ctrl+P 循环收藏夹；还能经 models.json 或扩展加自定义供应商与模型。→ 本章看这套「换供应商成本近乎为零」的抽象在源码里怎么落地。

10.1pi-ai 的定位：把「模型」从「循环」里拆出来

回想架构分层：pi-agent-core 只管消息与循环，它不直接调任何厂商 API。真正跟 Anthropic / Google / OpenAI 对话的是 pi-ai。它的职责一句话概括：把「换供应商」的成本压到近乎为零，同时对上层暴露一个极其稳定的接口。

这套设计的三个不变量，几乎决定了整个上层怎么写：

  • 模型是值对象，不是连接：Model 只是「描述一个可调用模型」的纯数据（名字、baseUrl、窗口大小、能力）。连接、鉴权、网络都在别处处理。它能在会话、压缩、UI 之间到处传，而不用带着一个 live socket。
  • 流式返回事件，不返回最终串：stream() 返回 AssistantMessageEventStream——一个逐事件推送的协议（消息开始/更新/结束）。这直接喂给第 3 章的 streamAssistantResponse，让「打字机效果」和「响应用户打断」成为天然能力。
  • 错误不会抛出，而是编码在流里：契约明确「request/model/runtime 失败应编码进流，而不是 throw」。这是为了恢复——上层能在流结束处读到 stopReason: "error" + errorMessage，进而判断该压缩还是该重试（第 8 章）。
为什么「错误编码在流里」如此重要？若失败以 throw 形式逃逸，上层循环要写一堆 try/catch 去猜「这次是不是该重试、该压缩」。而 Pi 的统一约定是：任何失败都变成一条带 stopReason:"error" 的 assistant 消息。于是第 8 章的 _checkCompaction / _isRetryableError 只需读消息字段，逻辑异常干净。这值得你写 Runtime 时抄。

10.2Model 值对象：一个「模型」的完整画像

Model 在 packages/ai/src/types.ts，约 30 个字段。逐个看那些上层真正依赖的：

packages/ai/src/types.ts · Model 接口
export interface Model<TApi extends Api> {
  id: string;                 // 唯一标识（如 "claude-opus-5"）
  name: string;               // 人类可读名
  api: TApi;                   // 协议族：anthropic-messages | openai-responses | google …
  provider: ProviderId;        // 供应商：anthropic / google / openai …
  baseUrl: string;            // 指向哪（可换端点/网关）
  reasoning: boolean;        // 是否支持思考
  thinkingLevelMap?: ThinkingLevelMap;  // 把 pi 的思考档位映射到各厂商的值
  input: ("text" | "image")[];    // 能吃什么输入
  cost: ModelCost;            // 计价（用于精确 token 与成本估算）
  contextWindow: number;     // 上下文窗口 —— 压缩与溢出判断的锚点
  maxTokens: number;        // 最大输出 —— 长度恢复判断的锚点
  samplingParams?: ...;       // 默认采样参数（temperature 等）
  headers?: ...;              // 附加请求头
  compat?:
    TApi extends "openai-responses" ? OpenAIResponsesCompat      // 按协议族的
    : TApi extends "anthropic-messages" ? AnthropicMessagesCompat // 兼容行为覆写
    : TApi extends "bedrock-converse-stream" ? BedrockCompat : never;
}

几个值得展开的字段：

  • api vs provider:两者不是一回事。api 是协议族（该怎么对话，走 anthropic 还是 openai-responses 语法），provider 是供应商（向谁付费、谁鉴权）。一个供应商可以同时实现多种 api 兼容。
  • contextWindow / maxTokens：这是「能力画像」里最要命的两条。第 6 章压缩用 contextWindow判断是否溢出，第 8 章的溢出恢复用 maxTokens 判断「输出是否提前被掐断」。
  • thinkingLevelMap：pi 定义了自己的一套「思考级别」档位（第 4 章见过 ThinkingLevelEntry），但各家厂商叫法不同（有的叫 effort，有的叫 thinking budget）。这里的映射把 pi 的抽象语言翻译成各厂商的具体参数，未映射则用默认。
  • compat（条件类型）:同协议的不同实现常有细微差别（比如 OpenAI Responses 的老版 compat 开关）。它按 api 收紧类型，保证「只有该协议族才可能有对应 compat」。
一个模型 = 一份「画像」，这很重要：正因为 Model 是纯数据，你可以在 run 前、压缩前、UI 里分别读取它的窗口与能力，而无需真正建连。这是「把策略（要不要压缩）和事实（窗口多大）分离」的典范。

10.3Provider 契约：stream 才是宇宙的中心

每个提供商模块（src/providers/anthropic.ts、google.ts 等）都实现同一套 ProviderStreams 契约。最核心的是 stream：

packages/ai/src/types.ts · ProviderStreams 契约
export interface ProviderStreams {
  // 主入口：把「模型 + 上下文」流式地吐成 assistant 消息事件
  stream(model: Model<Api>, context: Context, options?): AssistantMessageEventStream;
  // 简化版：只给一条 user 消息，无工具（用于压缩摘要等轻量调用）
  streamSimple(model: Model<Api>, context: Context, options?): AssistantMessageEventStream;
  // 可选：异步续跑（deferred），拿回一个 durable handle
  fetchDeferred?(model, handle, options?): AssistantMessageEventStream;
  cancelDeferred?(model, handle, options?): Promise<void>;
}

这里的关键是 `Context` 与流的定义。`Context`（来自 pi-ai）就是「系统提示 + 历史消息 + 工具定义」打包体——正是第 5 章 buildSessionContext 产出的那一坨。所以上层的数据流是：

数据流串联
// agent-core 里其实只有这一句真正打到模型：
const stream = ctx.model.stream(ctx.model.model, context, options);
// 上层再从 stream 里收 AssistantMessageEvent（msg_start / msg_update / msg_end）

为什么「简化版 streamSimple」要单独存在？因为它服务一个特殊场景：压缩摘要（第 6 章）。压缩时你不需要工具、不需要历史里漂亮的结构，只要「给它一堆旧消息，讨一句总结」——于是用一条轻量路径，省掉工具定义与约束参数，既更快也更不容易被工具网络干扰。

带 deferred 能力的供应商，还能「异步续跑」：请求返回一个 handle，真正的结果后台继续生成，稍后 fetchDeferred(handle) 拿回。这服务于超长推理场景，避免长时间占着连接。

设计品味：streamSimple 的存在提醒我们——抽象层不该只提供一个「万能笨重接口」，而应为不同调用场景提供不同「带宽」。压缩这种内部辅助调用不该背负完整 Agent 请求的复杂度。

10.4流式事件协议：内容与载体分离

流的产出不是一段最终文本，而是一串 AssistantMessageEvent。内容被细分为几种「分块」，这是第 2 章「消息类型学」的延续：

packages/ai/src/types.ts · 内容分块类型
export interface TextContent {
  type: "text";
  text: string;
  textSignature?: string;   // 端侧 token（如 OpenAI 的 msg id / 签名）
}
export interface ThinkingContent {
  type: "thinking";
  thinking: string;
  thinkingSignature?: string; // 思考的端侧 id，续轮时回传以保持连续性
  redacted?: boolean;          // 被安全过滤遮蔽（内容不可读，仅留签名）
}
export interface ToolCall {
  type: "toolCall";
  id: string; name: string; arguments: Record<string, any>;
  thoughtSignature?: string;  // Google 特有：复用思考上下文的密钥
  namespace?: string;         // OpenAI Responses 动态/命名空间工具
}

这些「分块类型」与第 2 章的 AgentMessage.content 一脉相承——AI 层的流事件最终被 agent-core 转成 AssistantMessage 的 content 数组。注意「签名」字段体系：textSignature、thinkingSignature、thoughtSignature 本质都是「把端侧不透明 token 原样回传」以维持多轮连续性（尤其思考被遮蔽时，内容是空的，但签名还在，续轮还能续得上）。

被遮蔽的思考仍可持续：redacted: true 表示这轮思考被安全过滤器遮蔽，你读不到内容。但 thinkingSignature 保留了加密后的不透明载体，原样回传给 API 即可保持思维连续性。这是「模型侧保护隐私、应用侧保功能」的精细平衡。

10.5流式代理：带宽减半的 SSE 重建

10.1–10.4 讲了 stream() 契约与流事件类型，但没讲 packages/agent/src/proxy.ts——一个把 LLM 调用路由到「只管代理」的服务端的流式客户端。它最妙的优化是服务器在增量事件里不重复携带整条消息，客户端自己逐块重建：

proxy.ts · 增量文本事件（服务器只发 delta）
// 服务器发送的瘦事件：只有「哪一块 + 增量」（节选）
export type ProxyAssistantMessageEvent =
  | { type: "start" }
  | { type: "text_start"; contentIndex: number }
  | { type: "text_delta"; contentIndex: number; delta: string }
  | { type: "text_end"; contentIndex: number; contentSignature?: string }
  | { type: "thinking_start"; contentIndex: number }
  | { type: "thinking_delta"; contentIndex: number; delta: string }
  | { type: "thinking_end"; contentIndex: number; contentSignature?: string }
  | { type: "toolcall_start"; contentIndex: number; id: string; toolName: string }
  | { type: "toolcall_delta"; contentIndex: number; delta: string }
  | { type: "toolcall_end"; contentIndex: number; toolCall: ToolCall }
  | { type: "done"; reason: ...; usage: ... }
  | { type: "error"; reason: ...; errorMessage?: string; usage: ... }

客户端维护一个 partial 消息对象，把增量拼进去，并对外重新产出标准事件。最精妙的是工具调用参数的增量 JSON 解析：

proxy.ts · 流式工具调用参数重建
case "toolcall_start":
  partial.content[proxyEvent.contentIndex] = {
    type: "toolCall", id: proxyEvent.id, name: proxyEvent.toolName,
    arguments: {}, partialJson: "",
  } satisfies ToolCall & { partialJson: string } as ToolCall;
  return { type: "toolcall_start", contentIndex, partial };

case "toolcall_delta": {
  const content = partial.content[proxyEvent.contentIndex];
  if (content?.type === "toolCall") {
    content.partialJson += proxyEvent.delta;                    // 累积残缺 JSON
    content.arguments = parseStreamingJson(content.partialJson) || {}; // 边到边解析
    return { type: "toolcall_delta", contentIndex, delta: proxyEvent.delta, partial };
  }
  throw new Error("Received toolcall_delta for non-toolCall content");
}

parseStreamingJson 是 pi-ai 提供的「接受残缺 JSON、尽量解析」的解析器——工具参数通常还是一个不完整的对象时，就能解析出已能确定的字段，让 UI 能提前渲染「即将调用的工具」。一旦 toolcall_end 到达，用完整对象覆盖并清掉 partialJson。

三个细节一次给到：
  • 带宽优化——delta 里不重复带整条消息，长对话能省大量字节；
  • 可恢复性——parseStreamingJson 让「调工具意图」能提前浮现，而非等整个 JSON 到齐；
  • 契约一致——客户端重建后仍按标准 AssistantMessageEvent 输出，上层完全无感知。
这跟本章前面学到的「错误进流/流协议」一脉相承。

10.6模型目录与生产侧封装

模型清单集中在生成文件（models.generated.ts / model-catalog.ts），把「某供应商某型号具备什么能力」集中描述——这通常由脚本从厂商文档生成，保持最新且不手抄。生产 harness 在 model-runtime.ts / model-registry.ts 之上再加一层运行态封装：

生产侧真正跑请求前的还有鉴权闸门——第 8 章我们在 prompt() 里见过：

agent-session.ts · 跑前鉴权校验（节选，第 8 章见过）
if (!this.model) throw new Error(formatNoModelSelectedMessage());
const hasConfiguredAuth =
  this._modelRuntime.hasConfiguredAuth(this.model.provider) ||
  (await this._modelRuntime.checkAuth(this.model.provider)) !== undefined;
if (!hasConfiguredAuth) {
  // 若走 OAuth 就给更贴切的提示，否则提示 /login<provider>
  if (this._modelRuntime.isUsingOAuth(this.model.provider)) { ... }
  throw new Error(formatNoApiKeyFoundMessage(this.model.provider));
}

压缩路径用的摘要请求也走 ModelRuntime 的鉴权封装（_getSummarizationRequestAuth），确保「压缩用的模型」同样合法可用——这不是顺手为之，而是避免「主模型有 key、摘要模型的 key 没配」导致的诡异压缩失败。

分层链路收口：生成目录（静态画像）→ Registry（检索货架）→ Runtime（运行态鉴权/建连）→ AgentSession（喂循环）。四层各司其职，让「换模型」这件事在任一层次都不需要改协议。这正是把「稳定的抽象」与「易变的供应商」隔开的完整实践。

10.6.1 三个值得记住的供应商兼容细节

抽象层的好处是「一套契约打天下」，但代价是要把厂商之间的差异收编进数据模型。pi-ai 里有三处收编很典型，值得自研时借鉴：

  • 工具选择（ToolChoice）：pi 定义了 provider 中立的 type ToolChoice = "auto" | "none"，挂在 SimpleStreamOptions.toolChoice 上。摘要这类「不该调工具」的请求就显式传 "none"（见第 6 章）。各 provider 再翻译成自家术语——Anthropic 转成 { type: "none" }、Google 走 functionCallingMode、OpenAI/Responses 透传 tool_choice。差异藏在适配器里，上层只说一个意图。
  • 思考预算字段（thinkingTokenBudgetField）：vLLM/Qwen/llama.cpp 这类 OpenAI 兼容端点上，「推理」与「答案」共享 max_tokens——不设预算，一轮重度推理可能吃光整个响应、一个字答案都不吐。pi 把「用哪个字段封顶」也做成可配：ThinkingTokenBudgetField = "thinking_token_budget" | "thinking_budget" | "thinking_budget_tokens"（分别是 vLLM / Qwen·DashScope·SGLang / llama.cpp 的字段名）。旧的布尔 supportsThinkingTokenBudget 保留为 thinking_token_budget 的别名。配合 { "$var": "thinking.budget" } 这个 chat-template 变量，思考级别就能跨端点统一调控。
  • Anthropic 拒答兜底（allowedFallbackModels）：Anthropic 支持服务端拒答 fallback——主模型拒答时由服务端自动切到备选模型。但不是所有模型都能写进 fallbacks，写错了 API 会拒。于是 AnthropicMessagesCompat.allowedFallbackModels 显式列出「被允许的兜底模型 + 本地定价元数据」，适配器只在列表非空时才发 fallbacks，并在返回里用本地价格给兜底响应算成本。把「能不能兜底」也当成模型画像的一部分，而不是运行时瞎试。
自研启示：抽象层的真正工作量不在「定义接口」，而在把这些「同义但不同形」的厂商参数——工具选择、思考预算、兜底策略——逐个翻译成统一意图、再把意图落回各家术语。ToolChoice（一个枚举）与 thinkingTokenBudgetField（一个字段名枚举）是两种典型收编：前者把差异吸收进抽象、后者把差异枚举成配置。
