编码 Agent：把前面所有碎片拼成一个「能跑的产品」

十章攒下的碎片——循环、会话、上下文、压缩、harness、工具、AI 层——靠哪条装配线拼成可运行的产品？模型怎么选、key 怎么验？目录里那些「从不抵达 provider 的虚拟模型」又是怎么接进这条线的？工具集在装配时怎么定？同一个内核怎么服务 TUI、脚本、RPC 三种外壳？外壳又怎么在不碰内核的前提下长出新能力？
产品视角 「改 harness，不改你的工作流。Pi 不是封箱产品。」 要一条命令、一个工具、一个 Provider、一个工作流或 UI 微调？直接让 Pi 自己造——它会即时改写自己，/reload 后继续。Pi 自带强力默认却跳过子 Agent、计划模式这类「功能」，转而把它们拆成原语：扩展（拿工具/命令/快捷键/事件/TUI）、技能（按需载入）、提示模板、主题，→ 还能打包成 Pi 包经 npm 或 git 分享。本章看这层「可改的外壳」在源码里怎么被装配出来。

11.1装配线：createAgentSession 与模型的三级回退

生产侧的入口是 packages/coding-agent/src/core/sdk.ts 的 createAgentSession()。它把所有碎片装配到一起，短短几十行里完成了：模型运行时初始化 → 会话发现 → 模型恢复 → 载体选择 → 工具装配。先看它的文档签名：

sdk.ts · CreateAgentSessionOptions（节选）
export interface CreateAgentSessionOptions {
  cwd?: string;        // 工作目录（项目级发现的基准）
  agentDir?: string;    // 全局配置目录，默认 ~/.pi/agent
  modelRuntime?: ModelRuntime; // 模型/鉴权运行时（可注入）
  model?: Model<any>;       // 显式指定模型
  thinkingLevel?: ThinkingLevel; // 思考级别，按模型能力钳制
  scopedModels?: ...;          // Ctrl+P 可循环的模型列表
}

模型是「显式给，还是自动找」？Pi 做了一套清晰的三级回退。看真实的装配逻辑：

sdk.ts · 模型的三级回退
// 1. 调用者显式给了 → 就用它
let model = options.model;

// 2. 有既有会话数据 → 从会话分支上恢复上次用的模型。
// Assistant 消息只报「答话的物理模型」，所以虚拟选择只存在 model_change 条目里
const sessionModel = getBranchSelection(
  sessionManager.getBranch(),
  (provider, modelId) => modelRuntime.getModel(provider, modelId),
);
if (!model && hasExistingSession && sessionModel) {
  const restoredModel = modelRuntime.getModel(sessionModel.provider, sessionModel.modelId);
  if (restoredModel && modelRuntime.hasConfiguredAuth(restoredModel.provider)) {
    model = restoredModel;
  }
  if (!model) {
    modelFallbackMessage = `Could not restore model ${sessionModel.provider}/${sessionModel.modelId}`;
  }
}

// 3. 都没有 → 用 findInitialModel（settings 默认值 → Provider 默认）
if (!model) {
  const result = await findInitialModel(...);
  model = result.model;
  if (!model) modelFallbackMessage = formatNoModelsAvailableMessage();
}

// 4. 思考级别按模型能力钳制（别让不支持的模型背不动）
thinkingLevel = clampThinkingLevel(model, thinkingLevel) as ThinkingLevel;
「会话即状态」的再一次体现：模型选择不是每次从零猜，而是优先记住上次用的。恢复失败（比如换了 Provider、key 没了）则给出 modelFallbackMessage 提示，再优雅降级到默认。这把「连续性」和「可诊断性」同时给了用户——你不会不明不白地换个模型，也不会被卡死。恢复读的是分支上的选择条目而不是「最后一条 model_change」：树导航可能把最新的 model_change 留在另一条分支上；而虚拟模型的选择永不写进 assistant 消息（消息只报物理模型），所以虚拟选择要靠 model_change 条目才恢复得出来——细节见下面 11.1c。

11.1b模型运行时：鉴权与服务注入

装配线下一个关键件是 ModelRuntime。它持有一份「配置目录位置的鉴权存储」（auth.json）和模型目录（models.json）：

sdk.ts · ModelRuntime 初始化
const modelsPath = options.agentDir ? join(agentDir, "models.json") : undefined;
const modelRuntime = options.modelRuntime ?? await ModelRuntime.create({
  authPath,        // ~/.pi/agent/auth.json —— 各家 key / token
  modelsPath,      // ~/.pi/agent/models.json —— 可用模型清单
});

ModelRuntime 回答三个运行态问题：

  • 这个 Provider 配过 key 吗：hasConfiguredAuth(provider)——第 8、10 章里 prompt() 跑前都靠它拦一次。
  • 这个 key 还有效吗：checkAuth(provider) 去验证，OAuth 与普通 key 走不同分支。
  • 这个模型的协议/鉴权怎么搭：把认证信息装进每次请求的 headers。它封装了「怎么安全地带着你的凭据去和厂商说话」。

注意注入式设计——调用方可传自定义 modelRuntime，默认是 ModelRuntime.create。这让测试与自定义厂商集成可以不碰主装配线。

可注入 = 可测、可换：医疗诊断的模型、私有部署的网关、临时 mock——都能通过传入自己的 ModelRuntime 接入，而 createAgentSession 一行不改。这是「依赖注入」在组装层的直接收益。

扩展也有一条接入模型的路径，且粒度到「单个请求」：pi.registerProvider(name, config) 注册一个自定义 Provider——给 baseUrl/apiKey/models 就是标准厂商；给一个 streamSimple(model, context, options) 回调则是自定义协议：pi 把归一化后的 TranscriptContext 交给你（prompt 和工具声明要从 system 消息里读：getCurrentSystemPrompt(context.messages)、getCurrentTools(context.messages)），你返回标准的 AssistantMessageEventStream，此后这个 provider 的请求全部走你的代码。注册在扩展初始加载时排队、之后立即生效，命令处理器里调用也无需 /reload。这是第 10 章「Provider 契约」的扩展侧出口：契约定义在 pi-ai，而实现者不限于内置的几十家。模型清单也跟上了第 10 章的三分型：条目按 type 判别（缺省 "chat"），图片/分类模型各自声明 api 并在 images/classifiers 字段挂上对应实现；省略 models 则内置目录的所有能力原样保留。一个细节：streamSimple 的文档要求自定义协议实现手动转发 options.onProviderStreamEvent——内置 provider 会发归一化前的原始流事件，你的自定义协议不发的话，下面 11.4 的事件在这家 provider 上就是哑的。

11.1c虚拟模型：选择与分发的分离

模型体系最新的演化是 packages/coding-agent/src/core/virtual-models.ts（约 230 行，配套 docs/virtual-models.md）：目录里可以出现一类从不抵达 provider 的条目——api === "pi-virtual" 的「虚拟模型」。用户选中它之后，每个请求先经一个路由函数映射到某个物理模型，再真正发出去。「用户选了谁」与「这次实际问谁」就此拆成两对概念——前者是选择（selection），后者是分发（dispatch）。

core/virtual-models.ts · 路由请求与路由结论（节选，注释为译注）
export interface ModelRouteRequest {
  model: Model;                  // 被选中的虚拟模型
  thinkingLevel: ModelThinkingLevel;  // 其含义由路由器自行解释
  reason: ModelRouteReason;   // 这次请求为什么发生（见下表）
  previous?: { model; thinkingLevel? };  // messages 里最近一条成功响应的物理模型
  failed?: { model; thinkingLevel?; message: AssistantMessage };  // retry 时的失败请求，messages 已不含它
  state?: TState;                // 本分支上一次路由返回的状态；direct 请求没有
  messages: readonly Message[];   // 本次请求的完整对话，含 system 消息
  signal?: AbortSignal;
}
export interface ModelRoute {
  model: Model;                  // 必须是有凭据的物理模型，否则请求以错误收场
  thinkingLevel: ModelThinkingLevel;
  state?: TState;                // 新路由状态，存到会话分支；返回 request.state 或 undefined 即不变
}

reason 是契约里最见功力的部分——它告诉路由器「这次请求处在对话的什么位置」，路由器据此决定「要不要换档」：

reason何时发生路由器该做什么
"user"用户亲写的消息开启的请求（steering / follow-up 也算）可以重新评估、换物理模型
"continuation"循环内的其余请求（工具轮次、续跑）沿用上轮路由——中途换模型会打断思维连续性
"retry"自动重试（含溢出压缩后的重试），携带 failed可对失败作出反应，比如换一家重发
"direct"循环外的直接调用（压缩摘要、扩展 streamSimple）无路由状态、不写状态条目

三个注册与执行口子把这套机制接进已有的层：(a) ModelRuntime.registerVirtualModel(def) 把定义挂上目录（与物理模型 id 冲突会直接抛错），扩展侧对应 pi.registerVirtualModel()，其 route(request, ctx) 就是一个异步函数；(b) 第 8 章 8.2b 看过 prepareRequest 投影里的路由块——每次请求前发现选中的是虚拟模型，就探测 userTurn、读状态、按 reason 调 resolveModel，把返回的物理模型换进本次请求；(c) withVirtualModels() 给目录加载收尾：注册过的虚拟模型合并进模型列表，且若某虚拟模型与物理 chat 模型同 id，物理的会被隐藏——同名时用户面对的是唯一入口。路由器的状态不进内存：它作为 pi.virtual-model-state 自定义条目追加到当前分支，跟随会话树分叉、在压缩中存活；每次路由结论变了就写一条新条目（第 5 章「状态即条目」的又一次应用）。路由器拿到的 ctx.modelRegistry 能反查其他模型并调用分类器——官方示例 examples/extensions/jev-router.ts 就是用一个分类器模型给「这个请求有多复杂」打分，复杂过阈值路由到大模型、首次编辑/写文件之后路由到快模型，把「阶段」本身作为路由状态。

为什么物理模型不写回 model_change？恢复会话时（11.1 的 getBranchSelection），assistant 消息只报「答话的物理模型」——若把分发结果当成选择写回去，一次路由就会被永久固化成用户的选择，下次会话不再路由。所以：物理响应不覆盖分支上的虚拟选择，分支上没写过虚拟选择时物理选择照常记录，未注册的虚拟模型回退到最后一个物理模型。routedModel（8.2b）与 TUI 底栏的 auto • high → gpt-5.6-luna • medium 两段式显示，都是这个「选择不变、分发在流」的投影态。

11.2工具装配：按运行形态差异化

工具不是全都一股脑塞给 Agent。前面第 9 章的分类法在这里落地——装配时决定「这次会话能动手到什么程度」。sdk 构造 AgentSession 时传入工具集：

tools/index.ts · 三套工具集
// 只读形态（如预览/审查）：read · grep · find · ls
createReadOnlyTools(cwd, options)
// 编码形态（默认）：read · bash · edit · write
createCodingTools(cwd, options)
// 全量：八件全给（含 Windows 下的 powershell）
createAllToolDefinitions(cwd, options)

还有更细的工具「开关」：noTools（默认抑制模式）——可选「"all"：一开始完全不给工具」或「"builtin"：禁用内置只读/编码工具但保留扩展工具」。这把「工作区安全」从全局配置下放到了会话级策略。

工具还经过了 withFileMutationQueue 这类包装——把对文件的写操作（edit/write）排进一个跨工具队列，避免并发写冲突（第 9 章提过的文件变更队列）。这属于「工具层的协作约束」：多个工具共享同一份工作区时，写操作必须串行化。

工具是「能力边界」，不是「功能清单」：Pi 把「给哪些工具、抑制哪些工具」当作会话装配时的一次性决策，而不是运行中到处临时开关。这让权限边界在启动时即确定，行为更可预测，也更安全。

11.3运行形态：同一个核心，三种外壳

装配好的 AgentSession（含 SessionManager、工具、模型）是「无头」的——它不发声音、不画界面。真正呈现给用户的是几种「外壳」，都在 packages/coding-agent/src/modes/（另有实验性的 experimental/server.ts）：

</dev/null 脚本 rpc / json-event / server 给外部工具/客户端接入

三种外壳都只订阅 AgentSession 抛出的事件流，并调用它的方法（prompt / steer / followUp / fork / abort）：

  • interactive（TUI）：最丰富的形态。渲染思考/工具/消息流，支持 Ctrl+P 循环模型、Esc 打断（steer）、分叉（fork）。它把第 8 章的队列、第 9 章的流式更新事件全部变成可见交互。
  • print-mode：无交互，流式把输出打到 stdout。echo prompt | pi --print 这类脚本化用法，或在 CI 里跑 Agent。
  • rpc / json-event / server：把 Agent 暴露成可编程接口（结构化事件协议），外部工具/编辑器/客户端通过它接入——这是「Agent 即服务」的形态。
架构红利：因为核心是「无头 + 事件总线 + 方法」，外壳可以随便换而核心一行不改。这就是分层带来的最终回报——第 3 章的循环、第 5 章的上下文、第 8 章的生产 harness，被 createAgentSession 拼成可复用的内核，再被三种外壳包装成三种产品。你的 Runtime 若也这样切「内核/外壳」，就能同时服务 CLI、服务端、IDE 插件。

11.3bTUI 外壳内部：一个独立的终端 UI 库

上面说外壳「订阅事件、画界面」，但「画」这件事本身值得单独拆开——interactive 外壳底下是一个独立仓库包 @earendil-works/pi-tui（packages/tui），自述只有一句：「Minimal TUI implementation with differential rendering」。它与 coding-agent 之间是干净的包边界：tui 不认识 agent，coding-agent 只消费 Component 与 TUI 两个接口。自己写 agent 外壳时，这条「核心不渲染、渲染库不认识核心」的分界线可以直接照抄。

第一块积木：组件 = 「给定宽度，吐出若干行」。整个库的能力从两个接口长出来。Component 的全部渲染契约是一个纯函数式的方法：

packages/tui/src/tui.ts · Component 接口（摘录）
export interface Component {
  /** Render the component to lines for the given viewport width */
  render(width: number): string[];
  /** Optional handler for keyboard input when component has focus. */
  handleInput?(data: string): void;
  /**
   * Invalidate any cached rendering state.
   * Called when theme changes or when component needs to re-render from scratch.
   */
  invalidate(): void;
}

render(width) 返回一个字符串数组——每个元素是终端里的一行。没有虚拟 DOM、没有响应式系统，「界面」就是「这次宽度下所有行的文本」。容器组件（VStack、Container）只是把子组件的行数组拼接起来；组件自己负责缓存：渲染结果与 invalidate() 何时清缓存都是组件的私事。典型的缓存实现如 Markdown 组件——命中条件是「文本没变、宽度没变」，而解析出的 token 树用 WeakRef 弱引用持有（token 树约为源文十倍大，长会话里每条消息都有一个 Markdown 组件，弱引用让主题预览这类突发重渲染之后内存能被回收）。

第二块积木：渲染请求的合并与节流。事件驱动的界面最怕「每个小改动都立刻重画」。pi-tui 的答案是把「请求重画」与「真的重画」拆开：

packages/tui/src/tui.ts · requestRender 与节流调度（摘录）
private renderRequested = false;
private static readonly MIN_RENDER_INTERVAL_MS = 16;   // 约一帧 60fps

requestRender(force = false): void {
  if (force) { this.resetRenderState(); this.requestImmediateRender(); return; }
  if (this.renderRequested) return;          // 已经排了队 → 本次请求合并掉（译注）
  this.renderRequested = true;
  process.nextTick(() => this.scheduleRender());
}

private scheduleRender(): void {
  if (this.stopped || this.renderTimer || !this.renderRequested) return;
  const elapsed = performance.now() - this.lastRenderAt;
  const delay = Math.max(0, TuiBase.MIN_RENDER_INTERVAL_MS - elapsed);  // 距上次渲染不足 16ms 就推迟
  this.renderTimer = setTimeout(() => { ... this.doRender(); ... }, delay);
}

一帧之内来十个事件也只有一次真实渲染。两个例外都走 requestImmediateRender 的单独通道：显式 force（同时清掉全部组件缓存），以及用户输入——注释写明「User input must preempt that throttled frame」，节流可以推迟模型输出的绘制，但不能让敲键的回显等超过一帧。

第三块积木：行级差分。每次 doRender() 把整棵组件树渲染成新的行数组，与上一帧的行数组逐行比较：

packages/tui/src/tui-main-screen.ts · 差分循环与全量重画触发（摘录，编号为注）
// ① 全量重画的触发条件（依次检查，命中即整屏重画）
if (this.previousLines.length === 0 ...)        // 首帧
if (widthChanged)                                 // 宽度变了——换行整体作废
if (heightChanged && !isTermuxSession())          // 高度变了（Termux 软键盘除外）
if (clearOnShrink && newLines.length < maxLinesRendered ...)  // 内容变短，残留行要清
if (firstChanged < prevViewportTop)               // 变化在视口上方，差分够不着
// Differential rendering can only touch what was actually visible.

// ② 行差分：找首尾两个变化的行号
let firstChanged = -1, lastChanged = -1;
const maxLines = Math.max(newLines.length, this.previousLines.length);
for (let i = 0; i < maxLines; i++) {
  const oldLine = i < this.previousLines.length ? this.previousLines[i] : "";
  const newLine = i < newLines.length ? newLines[i] : "";
  if (oldLine !== newLine) { if (firstChanged === -1) firstChanged = i; lastChanged = i; }
}

// ③ 部分更新：只写 [firstChanged, lastChanged] 这一段
// Only render changed lines (firstChanged to lastChanged), not all lines to end
// This reduces flicker when only a single line changes (e.g., spinner animation)
const renderEnd = Math.min(lastChanged, newLines.length - 1);
for (let i = firstChanged; i <= renderEnd; i++) { ... output.append(line) ... }

注释「This reduces flicker when only a single line changes (e.g., spinner animation)」点出了动机：spinner 每几十毫秒变一格，如果每次都往终端整屏重写，画面会闪；只重写变化的那几行，肉眼就只看到那一格在动。另外两个工程细节：全量重画和部分更新都包在 \x1b[?2026h / \x1b[?2026l（synchronized output）里，让终端把这一帧当原子操作显示，避免用户看见「画了一半」的中间态；还有一道自检——任何一行超过终端宽度（应测量可见宽度而非字符数）就写崩溃日志 pi-tui-crash.log 并提示「Use visibleWidth() to measure and truncateToWidth() to truncate lines」，宽字符算一列还是两列出错时 fail-fast 而不是静默错位。

组装：滚动区 + 固定停靠栏。interactive 外壳的布局只有两层：

packages/coding-agent/src/modes/interactive/chat-viewport.ts（摘录）
const transcript = new ScrollView(options.document, {
  follow: "end",        // 默认跟着最新输出走
  primary: true,        // 接收滚轮/翻页
  overscroll: "chain",
  scrollbar: "auto",
});
const dock = new VStack([
  { component: options.pendingMessages, shrink: 1, minSize: 0 },
  { component: options.status,          shrink: 1, minSize: 0 },
  { component: options.editor,          shrink: 1, minSize: 3 },
  { component: options.footer,          shrink: 1, minSize: 0 },
]);

整个界面 = 一个占满剩余空间的 ScrollView（transcript，basis:0, grow:1 吃掉所有富余高度）+ 底部一条可压缩的 VStack（待发消息 / 状态 / 输入框 / footer）。流式输出推进时，只有 transcript 的尾部在动；VStack 用 shrink/minSize 表达「优先压缩谁、压到几行为止」——比如输入框 shrink:1, minSize:3：可以压，但不能低于三行。

事件怎么变成画面：事件处理函数只做三件事——改组件状态、invalidate()、requestRender()。handleEvent 的开头固定是一句 this.footer.invalidate()（任何事件都可能改变 footer 内容）；message_start 收到 assistant 消息就 new 一个 AssistantMessageComponent 挂进 chatContainer 并 updateContent(msg, true)；message_update 流式期间反复调 updateContent(msg, true)——这个方法把容器里的子组件清掉重建，所以流式期间每个 token 到达都是「重建这一个组件的子树」，而其他几百个组件的缓存原封不动；queue_update 刷新待发消息栏后 requestRender()。渲染频率与事件频率解耦：事件可以一秒来几百次，绘制最多每 16ms 一次。

你自己写外壳时的最小方案：pi-tui 的三个积木——「render(width) → string[] 的纯函数组件 + invalidate 缓存失效」「requestRender 合并 + 16ms 节流」「新旧行数组逐行 diff、只写变化段」——机制都不复杂，却覆盖了一个流式 agent 界面的全部骨架。甚至有一个更便宜的起点：如果你的界面只是「追加日志」，跳过差分，只做「事件 → 组件树渲染成行 → 每帧重画一次」就能跑；等 spinner 闪烁、滚动条抖动这些症状出现时，再补 invalidate 和行 diff。

11.4产品外壳的演进：外壳如何不碰内核长能力

三种外壳里，interactive（TUI）迭代最快，因为它离用户最近。这里挑几个最近加入的特性——它们都不改内核契约，而是在 AgentSession 的事件流上做更聪明的呈现与会话级策略，正好说明「外壳如何在不碰内核的前提下长能力」。

  • /thinking 命令：slash 命令表里新增 { name: "thinking", argumentHint: "<level>" }，让用户直接切思考级别（档位 off/minimal/low/medium/high/xhigh/max，即 THINKING_LEVEL_OPTIONS）。它最终调用第 8 章的 setThinkingLevel()。
  • 模型 / 思考级别改默认「会话级」：切模型或调思考级别时，setModel / setThinkingLevel 现在带一个 { persist?: boolean } 选项。默认 只写进当前会话的 transcript、不动全局默认；只有显式持久化（如 Ctrl+S）才写回 settings。这把「我这次想用别的模型」与「以后都用这个模型」分开了——临时实验不再污染全局配置。
  • 压缩用量提示（compaction cost）：压缩和分支摘要会消耗 token，TUI 现在把这条用量从 transcript 里抽出来，渲染成 compaction_cost 提示行，让用户看见「这次压缩花了多少」。这是第 6 章那条「压缩有 usage」在交互层上的可见化。
  • prompt cache 保温（cache warming）：provider 的 prompt cache 条目闲置一段时间就过期，暂停后再发请求要重付全价输入。生产层为此装了一个 CacheWarmer（core/cache-warmer.ts）：真实请求发出后，在缓存条目到期前（取该模型 promptCache 画像上对应档位的存活时长，90% 处刷新并留 10 秒余量）把同一个请求重发一遍，但 maxTokens: 1——上下文原样进来，只吐一个 token，钱花在缓存读上，条目就续上了。发不发由一笔账决定：continuationProbability × missCost − warmCost ≥ $0.05 才值得保温（运行中概率算 1，空闲时用实测常数 0.15）。模式三档 off/streaming/idle，默认 streaming（agent 运行期间保温、结算即停；idle 连空闲时也续，30 分钟封顶）。每次成功刷新落成一条 { type: "usage", kind: "cache_warm" } 会话条目——计入 token 与费用总额，但不进模型上下文。扩展可在 cache_warming_decision 事件上改判（最后说话的算数），/session 能看到下一次决策与账目。第 10 章的 Model.promptCache 画像（10.2 节）就是这条策略的前提：没填存活时长的模型一律不保温。还有个容易漏的反直觉细节：定时器可能因系统休眠或事件循环阻塞而晚点——条目可能已经过期了。此时刷新不再是「保温」而是全价的缓存写，比不刷还亏。所以每次刷新前查一道 refreshDeadlineAt（计划时刻 + 剩余 TTL 的一半）：迟到过头就干脆停掉，别花冤枉钱。另一个后到的门卫管「这份请求还作不作数」：保温的不是请求本身，而是它写下的缓存条目，若下一次请求不会重复这份上下文（虚拟选择路由去了别的模型、或扩展在 context 事件里重写了消息），重发就是白花钱。于是每次启动保温时闭包捕获「当时的选中模型 + 消息列表」，到期要刷时先验一道 isCurrent()——模型变了或消息列表被改写，保温静默作废。
  • 会话共享改走 Radius：/share 不再只靠 gist，而是优先通过 Radius provider 上传成 artifact、拿回 canonical_url。未登录 Radius 时退回 gist。共享链路与鉴权也收敛进 AI 层的 provider 体系，而不是另起一套。共享内容也不再只是消息流水：导出时会追加一条 pi.share 自定义条目，把当时的 systemPrompt 与工具清单（名称/描述/参数）一并带上，让接收方看到 Agent 运行时的完整上下文。
  • 原始流事件开放给扩展（provider_stream_event）：provider 返回的每条 SSE 事件在归一化之前就以扩展事件的形式透传——provider_stream_event 带 provider/api/model 和原始事件负载（data），文档点明这是 pi 能拿到的最早结构化值，不是原始 HTTP 字节，且只读（改了会影响归一化）。三个纪律值得记：通知性质、不落盘；处理器按流的顺序 await——写慢了会拖慢整个流消费；处理器抛错只上报、不影响 provider 响应（但内置适配器会把它从「传输层失败」里摘出来，不让一次回调手滑触发 SSE 回退重连）。官方示例 debug-provider.ts 用它做了个 /debug-provider 查看器：按 assistant 消息分组展示原始事件，排查「provider 到底吐了什么」时不用再抓包。内核侧则是 pi-ai 的 StreamOptions.onProviderStreamEvent 一路传到 Agent——链路上任何一层都能旁观原始事件，而不必等归一化抹平之后。
  • 扩展打包的依赖纪律（防双运行时）：宿主提供的包（@earendil-works/pi-ai、pi-coding-agent、pi-tui、typebox……）必须声明在 peerDependencies 且范围 "*"，不能写进 dependencies——扩展若自带一份物理拷贝，编译后的 ESM 会绕过宿主的模块映射，产生两套类、两个注册表、两份初始化。ResourceLoader 现在会扫描包清单检测这种配置并发出警告（与错误并列出现在 TUI 诊断里）。这其实是 Node 生态「peer dependencies 用来共享单例」的老规矩在扩展体系里的落点：宿主注入的模块，宿主负责给，扩展只声明兼容范围。
  • 能力外置成内置扩展：codemode 与 MCP：v0.99.0 起仓库多了两个独立包——pi-codemode（QuickJS wasm 沙箱，模型写一段脚本去调工具，脚本自己控制循环与分支，不用每个动作都走一轮模型）与 pi-mcp（独立的 MCP 客户端）。两者都以「内置扩展」的身份接进产品：注册表（src/extensions/index.ts）里有四个，llama.cpp / codemode / tool-search / mcp，资源路径是 builtin:<name>，像文件资源一样默认加载、能被 pi config 列出与关闭。这一步值得注意的不仅是新功能，而是新能力的接入方式变了：不再往内核加代码路径，而是注册一个可被第三方替换（replaceable: true——任何注册了同名工具或命令的第三方扩展直接顶掉内置版）的扩展。内核保持「只管循环、会话、工具面」，语言沙箱和外部工具协议都是外壳上的可拔插件。第 9 章 9.5b 的暴露五值正是为这一步准备的词汇：MCP 工具按服务器的 exposure 配置映射到 direct/codemode/deferred 等取值，codemode 工具再在加载时用 prepareLoadout 把可代调的工具列进自己的描述——两个包协作的接缝全部落在暴露面上，内核零改动。
共同模式：这几项都遵循「内核不动，外壳做策略」——/thinking 只是 setThinkingLevel 的入口；会话级持久化靠 persist 选项分流；压缩提示复用 transcript 里已有的 usage；共享复用 Radius provider；缓存保温和原始流事件则都是「内核放出一个只读/可改判的口子，外壳决定怎么用」；codemode 与 MCP 更进一步——连「新能力」本身也做成可替换的外壳扩展（builtin:<name>），内核只出工具暴露面这层协议。这正是分层架构的红利：产品迭代可以很快，因为不必每次都下沉到内核。
扩展 API 顺带补两个后来长出来的点：pi.on() 现在返回退订函数——事件处理器可以随用随拆，与 unregisterProvider 之类的注销 API 一起补全扩展的生命周期；另外，在事件分发过程中增删处理器是安全的（分发前拍快照，变更只影响下一次分发），不会碰到「边遍历边改」的经典坑。
