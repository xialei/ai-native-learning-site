编码 Agent：把前面所有碎片拼成一个「能跑的产品」

前面十章分别讲了循环、会话、上下文、压缩、harness、工具、AI 层。这一页回答最后一个组装问题：所有这些碎片是怎么被 @earendil-works/pi-coding-agent 拼成一个真正可运行、可交互、可持续的 Agent 产品的——从 createAgentSession 这条「一调就成」的工厂，到 TUI / 打印 / RPC 三种运行形态。
产品视角 「改 harness，不改你的工作流。Pi 不是封箱产品。」 要一条命令、一个工具、一个 Provider、一个工作流或 UI 微调？直接让 Pi 自己造——它会即时改写自己，/reload 后继续。Pi 自带强力默认却跳过子 Agent、计划模式这类「功能」，转而把它们拆成原语：扩展（拿工具/命令/快捷键/事件/TUI）、技能（按需载入）、提示模板、主题，→ 还能打包成 Pi 包经 npm 或 git 分享。本章看这层「可改的外壳」在源码里怎么被装配出来。

11.1一调就成的工厂：createAgentSession

生产侧的入口是 packages/coding-agent/src/core/sdk.ts 的 createAgentSession()。它把所有碎片装配到一起，短短几十行里完成了：模型运行时初始化 → 会话发现 → 模型恢复 → 载体选择 → 工具装配。先看它的文档签名：

sdk.ts · CreateAgentSessionOptions（节选）
export interface CreateAgentSessionOptions {
  cwd?: string;        // 工作目录（项目级发现的基准）
  agentDir?: string;    // 全局配置目录，默认 ~/.pi/agent
  modelRuntime?: ModelRuntime; // 模型/鉴权运行时（可注入）
  model?: Model<any>;       // 显式指定模型
  thinkingLevel?: ThinkingLevel; // 思考级别，按模型能力钳制
  scopedModels?: ...;          // Ctrl+P 可循环的模型列表
}

模型是「显式给，还是自动找」？Pi 做了一套清晰的三级回退。看真实的装配逻辑：

sdk.ts · 模型的三级回退
// 1. 调用者显式给了 → 就用它
let model = options.model;

// 2. 有既有会话数据 → 尝试从会话里恢复上次用的模型
if (!model && hasExistingSession && existingSession.model) {
  const restoredModel = modelRuntime.getModel(existingSession.model.provider, existingSession.model.modelId);
  if (restoredModel && modelRuntime.hasConfiguredAuth(restoredModel.provider)) {
    model = restoredModel;
  }
  if (!model) {
    modelFallbackMessage = `Could not restore model ${provider}/${modelId}`;
  }
}

// 3. 都没有 → 用 findInitialModel（settings 默认值 → Provider 默认）
if (!model) {
  const result = findInitialModel(...);
  model = result.model;
  if (!model) modelFallbackMessage = formatNoModelsAvailableMessage();
}

// 4. 思考级别按模型能力钳制（别让不支持的模型背不动）
thinkingLevel = clampThinkingLevel(model, thinkingLevel) as ThinkingLevel;
「会话即状态」的再一次体现：模型选择不是每次从零猜，而是优先记住上次用的。恢复失败（比如换了 Provider、key 没了）则给出 modelFallbackMessage 提示，再优雅降级到默认。这把「连续性」和「可诊断性」同时给了用户——你不会不明不白地换个模型，也不会被卡死。

11.2模型运行时：鉴权与服务注入

装配线下一个关键件是 ModelRuntime。它持有一份「配置目录位置的鉴权存储」（auth.json）和模型目录（models.json）：

sdk.ts · ModelRuntime 初始化
const modelsPath = options.agentDir ? join(agentDir, "models.json") : undefined;
const modelRuntime = options.modelRuntime ?? await ModelRuntime.create({
  authPath,        // ~/.pi/agent/auth.json —— 各家 key / token
  modelsPath,      // ~/.pi/agent/models.json —— 可用模型清单
});

ModelRuntime 回答三个运行态问题：

  • 这个 Provider 配过 key 吗：hasConfiguredAuth(provider)——第 8、10 章里 prompt() 跑前都靠它拦一次。
  • 这个 key 还有效吗：checkAuth(provider) 去验证，OAuth 与普通 key 走不同分支。
  • 这个模型的协议/鉴权怎么搭：把认证信息装进每次请求的 headers。它封装了「怎么安全地带着你的凭据去和厂商说话」。

注意注入式设计——调用方可传自定义 modelRuntime，默认是 ModelRuntime.create。这让测试与自定义厂商集成可以不碰主装配线。

可注入 = 可测、可换：医疗诊断的模型、私有部署的网关、临时 mock——都能通过传入自己的 ModelRuntime 接入，而 createAgentSession 一行不改。这是「依赖注入」在组装层的直接收益。

11.3工具装配：按运行形态差异化

工具不是全都一股脑塞给 Agent。前面第 9 章的分类法在这里落地——装配时决定「这次会话能动手到什么程度」。sdk 构造 AgentSession 时传入工具集：

tools/index.ts · 三套工具集
// 只读形态（如预览/审查）：read · grep · find · ls
createReadOnlyTools(cwd, options)
// 编码形态（默认）：read · bash · edit · write
createCodingTools(cwd, options)
// 全量：八件全给（含 Windows 下的 powershell）
createAllToolDefinitions(cwd, options)

还有更细的工具「开关」：noTools（默认抑制模式）——可选「"all"：一开始完全不给工具」或「"builtin"：禁用内置只读/编码工具但保留扩展工具」。这把「工作区安全」从全局配置下放到了会话级策略。

工具还经过了 withFileMutationQueue 这类包装——把对文件的写操作（edit/write）排进一个跨工具队列，避免并发写冲突（第 9 章提过的文件变更队列）。这属于「工具层的协作约束」：多个工具共享同一份工作区时，写操作必须串行化。

工具是「能力边界」，不是「功能清单」：Pi 把「给哪些工具、抑制哪些工具」当作会话装配时的一次性决策，而不是运行中到处临时开关。这让权限边界在启动时即确定，行为更可预测，也更安全。

11.4运行形态：同一个核心，三种外壳

装配好的 AgentSession（含 SessionManager、工具、模型）是「无头」的——它不发声音、不画界面。真正呈现给用户的是几种「外壳」，都在 packages/coding-agent/src/modes/ 与 client|server 里：

</dev/null 脚本 rpc / json-event / server 给外部工具/客户端接入

三种外壳都只订阅 AgentSession 抛出的事件流，并调用它的方法（prompt / steer / followUp / fork / abort）：

  • interactive（TUI）：最丰富的形态。渲染思考/工具/消息流，支持 Ctrl+P 循环模型、Esc 打断（steer）、分叉（fork）。它把第 8 章的队列、第 9 章的流式更新事件全部变成可见交互。
  • print-mode：无交互，流式把输出打到 stdout。echo prompt | pi --print 这类脚本化用法，或在 CI 里跑 Agent。
  • rpc / json-event / server：把 Agent 暴露成可编程接口（结构化事件协议），外部工具/编辑器/客户端通过它接入——这是「Agent 即服务」的形态。
架构红利：因为核心是「无头 + 事件总线 + 方法」，外壳可以随便换而核心一行不改。这就是分层带来的最终回报——第 3 章的循环、第 5 章的上下文、第 8 章的生产 harness，被 createAgentSession 拼成可复用的内核，再被三种外壳包装成三种产品。你的 Runtime 若也这样切「内核/外壳」，就能同时服务 CLI、服务端、IDE 插件。

11.5产品外壳的演进：几个值得注意的交互特性

三种外壳里，interactive（TUI）迭代最快，因为它离用户最近。这里挑几个最近加入的特性——它们都不改内核契约，而是在 AgentSession 的事件流上做更聪明的呈现与会话级策略，正好说明「外壳如何在不碰内核的前提下长能力」。

  • /thinking 命令：slash 命令表里新增 { name: "thinking", argumentHint: "<level>" }，让用户直接切思考级别（档位 off/minimal/low/medium/high/xhigh/max，即 THINKING_LEVEL_OPTIONS）。它最终调用第 8 章的 setThinkingLevel()。
  • 模型 / 思考级别改默认「会话级」：切模型或调思考级别时，setModel / setThinkingLevel 现在带一个 { persist?: boolean } 选项。默认 只写进当前会话的 transcript、不动全局默认；只有显式持久化（如 Ctrl+S）才写回 settings。这把「我这次想用别的模型」与「以后都用这个模型」分开了——临时实验不再污染全局配置。
  • 压缩用量提示（compaction cost）：压缩和分支摘要会消耗 token，TUI 现在把这条用量从 transcript 里抽出来，渲染成 compaction_cost 提示行，让用户看见「这次压缩花了多少」。这是第 6 章那条「压缩有 usage」在交互层上的可见化。
  • 会话共享改走 Radius：/share 不再只靠 gist，而是优先通过 Radius provider 上传成 artifact、拿回 canonical_url。未登录 Radius 时退回 gist。共享链路与鉴权也收敛进 AI 层的 provider 体系，而不是另起一套。共享内容也不再只是消息流水：导出时会追加一条 pi.share 自定义条目，把当时的 systemPrompt 与工具清单（名称/描述/参数）一并带上，让接收方看到 Agent 运行时的完整上下文。
共同模式：这几项都遵循「内核不动，外壳做策略」——/thinking 只是 setThinkingLevel 的入口；会话级持久化靠 persist 选项分流；压缩提示复用 transcript 里已有的 usage；共享复用 Radius provider。这正是分层架构的红利：产品迭代可以很快，因为不必每次都下沉到内核。
