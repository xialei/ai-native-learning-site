基础 Agent 循环：一台吞吐消息的机器

第 3 章拆开 packages/agent 的 agent-loop.ts 与 agent.ts——这是整个 Pi 的「心脏」。它不处理会话持久化，只管一件事：把消息一次次喂给 LLM，执行工具，并对外发事件。

3.1两个入口：新开 vs 继续

循环有两个入口。agentLoop 带着一条新提示开始；agentLoopContinue 从当前上下文继续跑（用于重试）。

packages/agent/src/agent-loop.ts — 两个入口 & 各自的校验
typescriptexport function agentLoop(prompts, context, config, signal, streamFn) {
  // 把 prompt 追加进上下文，发 message_start/message_end，然后进主循环
  const stream = createAgentStream();
  void runAgentLoop(prompts, context, config, e => stream.push(e), signal, streamFn)
    .then(messages => stream.end(messages));
  return stream;   // 立即返回一个 EventStream，事件异步到达
}

export function agentLoopContinue(context, config, signal, streamFn) {
  // 不能从空的、或以 assistant 结尾的上下文"继续"
  if (context.messages.length === 0)
    throw new Error("Cannot continue: no messages in context");
  if (context.messages[context.messages.length - 1].role === "assistant")
    throw new Error("Cannot continue from message role: assistant");
  // 最后一条必须是 user 或 toolResult，否则 provider 会拒绝请求
  ...
}
读懂这段： 「继续」的前置条件非常严格——最后一条消息绝不能是 assistant。因为 LLM 不能「自己接自己」，必须由 user 消息或工具结果来驱动下一轮。这个约束在你的自研 Runtime 里也成立。

3.2主循环：内层 turn，外层 follow-up

runLoop 是一个双层 while：内层把「当前的 turn」跑到底（含工具循环）；外层在有 follow-up 消息时再开新 turn。

图 3.2：内层处理「一个 turn + 它的工具」，外层处理「steering/follow-up 消息」。
packages/agent/src/agent-loop.ts — 内层循环骨架（手写要点提炼）
typescriptwhile (true) {                       // 外层
  let hasMoreToolCalls = true;
  while (hasMoreToolCalls || pendingMessages.length > 0) {  // 内层
    // 1) 若上一 turn 已完成：prepareNextTurn(lastCompletedTurn) 可换 model/context
    //    （准备可能耗时，比如做压缩——之后若 backlog 为空就再拉一次 steering）
    // 2) turn_start；注入 pendingMessages（steering 或 follow-up 的 backlog）
    // 3) 流式拿一个 assistant 回复： message = streamAssistantResponse(...)
    // 4) 若 stopReason 是 error/aborted → turn_end + agent_end，退出
    // 5) 若含 toolCall：stopReason==="length" 则全部判失败；否则 executeToolCalls
    // 6) 把 toolResult 消息推回 currentContext.messages 与 newMessages
    // 7) turn_end；shouldStopAfterTurn? 退出
    // 8) pendingMessages = getSteeringMessages()  ← 是否有新的 steering
  }
  // 内层退出：没有工具也没有 steering。检查 follow-up
  const followUp = await config.getFollowUpMessages?.();
  if (followUp?.length) { pendingMessages = followUp; continue; }  // 交给内层
  break;   // 真的停了
}
读懂这段（自研者必看）： 注意 newMessages 与 currentContext.messages 的分野——currentContext 是整个历史（可能含预存在的上下文），newMessages 只统计本次循环新增的。循环结束时返回的是 newMessages，调用方（如 Agent）再把它并入自己的状态。

3.3流式回复与事件

streamAssistantResponse 是转化的关键点：先 transformContext、再 convertToLlm、调 streamFn，然后把「流式事件」翻译成 AgentEvent：

packages/agent/src/agent-loop.ts — 流式处理（节选）
typescriptfor await (event of response) {
  switch (event.type) {
    case "start":
      partialMessage = event.partial;
      context.messages.push(partialMessage);      // 先把半成品塞进上下文
      await emit({ type: "message_start", message: { ...partialMessage } });
      break;
    case "text_delta":  // 以及 thinking_*/toolcall_* 等增量事件
      partialMessage = event.partial;
      context.messages[context.messages.length - 1] = partialMessage; // 覆盖半成品
      await emit({ type: "message_update", assistantMessageEvent: event, message: { ...partialMessage } });
      break;
    case "done": case "error": {
      const finalMessage = await response.result();
      // 用最终消息替换挂在末尾的半成品
      context.messages[context.messages.length - 1] = finalMessage;
      await emit({ type: "message_end", message: finalMessage });
      return finalMessage;
    }
  }
}
读懂这段： 一个很优雅的细节——先把「半成品」放进 messages，每次增量用新对象原位覆盖最后一项，最后用 final 替换。这样任何时刻上下文里都只有「当前位置」的正确消息，无需在结束时额外拼接。

3.4事件时序一图流

图 3.4：带工具调用的一次 prompt 的典型事件序列。完整的精确序列见官方 README 与第 1 章引用的文档。
事件含义
agent_start / agent_end整次运行开始/结束；agent_end 携带全部 newMessages
turn_start / turn_end一个「turn」= 一次 assistant 回复 + 它的工具/结果

3.5Agent 类：有状态的封装 + 三个队列

Agent 把 runAgentLoop 包成一个有状态对象，并引入两个队列实现「并发下往运行中的 agent 塞消息」：

packages/agent/src/agent.ts — 属性与队列（要点）
typescriptexport class Agent {
  private steeringQueue: PendingMessageQueue;  // run 中途注入
  private followUpQueue: PendingMessageQueue;  // 运行将停时才注入

  async prompt(input): Promise<void> {
    if (this.activeRun) throw new Error("already processing...");
    const msgs = this.normalizePromptInput(input);
    await this.runPromptMessages(msgs);
  }
  steer(message): void { this.steeringQueue.enqueue(message); }  // 非阻塞
  followUp(message): void { this.followUpQueue.enqueue(message); }
  abort(): void { this.activeRun?.abortController.abort(); }
}

// 队列的 drain 语义受 QueueMode 控制：
//   "all"          → 一次全部放出（drain 全部）
//   "one-at-a-time" → 每次只放最旧的一条（默认）
读懂这段： PendingMessageQueue.drain() 在 QueueMode === "one-at-a-time"（默认）时只放出最旧的一条，"all" 才一次全部放出。这避免了「乘胜追击」——每次只多塞一条，让 agent 消化完再决定。这些队列在 getSteeringMessages/getFollowUpMessages 里被 loop 拉取——即拉模型（pull），不是模型主动注入。循环开头会先拉一次（用户可能在等待时已经打字），prepareNextTurn 准备（可能长跑，比如压缩）之后若 backlog 为空还会再补拉一次——否则 one-at-a-time 模式可能在一个 turn 里送出两条。

3.6对自研与使用的启示

要点 ① 双层循环（turn / follow-up）是为「中途介入」服务的——steering 在 turn 内插入，follow-up 等到将停时插入。② 事件流是 UI 的生命线，把「运行时决策」与「UI 呈现」解耦（事件订阅）。③ 转换点（transformContext → convertToLlm）是上下文管理的天然挂载点。 这三条几乎能原样移植进你自己的 Runtime。
