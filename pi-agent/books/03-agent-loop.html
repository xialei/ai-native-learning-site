基础 Agent 循环：一次 turn 之后，凭什么继续

循环什么时候停、什么时候继续，由谁说了算？每次调模型前还有哪几道准备工序？流式回复是逐 token 到的，上下文怎么保证任何时刻都是合法序列？用户中途插话从哪进来？这几个问题都指向同一处源码——agent-loop.ts，本章就把它拆开。

3.1循环的边界由谁决定

packages/agent 的 agent-loop.ts 与 agent.ts 是整个 Pi 的核心。它不碰会话持久化，只管一件事：把消息一次次喂给 LLM、执行工具、对外发事件。而「什么时候停下」是这个核心最难定的边界——停早了扩展没机会说话，停晚了多烧请求。具体拆开，有四个问题要回答：

  • 一个 turn 跑完后，循环凭什么继续？旧的写法是让回调返回布尔值「该停吗」；可工具结果本身就能续命（模型看到 toolResult 自然会接），怎么把这两件事统一？
  • 每次 provider 请求前还有哪些固定工序？压缩、注入 steering、换模型……这些「请求前准备」挂在哪个点才不会漏掉第一次请求？
  • 流式回复怎么进上下文？回复是逐 token 到的，上下文里任何时刻都得是合法消息序列，半成品怎么放？
  • 用户中途说的话从哪进来？steering 打断当前节奏、follow-up 等跑完再说——两条队列怎么被循环拉取？
答案地图 四问的答案依次是：finishTurn 钩子 + explicitContinuation 续命标记（3.2/3.3）；请求前的三道工序（3.3）；「半成品先入列、增量原位覆盖」（3.4）；Agent 类里的两个队列（3.5）。先剧透一句：循环把「要不要继续」的裁决权从过程式的 if 判断改写成一个返回 continue/end 的回调——裁决发生在 turn_end 之前，但执行被推迟到所有队列清空之后。这个设计贯穿全章。

3.2主循环骨架：内层 turn，外层续命

runLoop 是一个双层 while：内层把「当前的 turn」跑到底（含工具循环）；外层在有跟问消息或 continue 承诺时再开新 turn。

图 3.2：内层处理「一个 turn + 它的工具」，外层处理「steering/follow-up 消息 + continue 承诺」。
packages/agent/src/agent-loop.ts — runLoop 主循环骨架（手写要点提炼，对照源码 165–320 行）
typescriptlet pendingMessages = (await config.getSteeringMessages?.()) || [];  // 开局先拉一次
let explicitContinuation = false;     // finishTurn 的 continue 承诺是否还欠着

while (true) {                        // 外层
  let hasMoreToolCalls = true;
  while (hasMoreToolCalls || pendingMessages.length > 0) {  // 内层
    // 1) 若上一 turn 已完成：prepareNextTurn 可换 model/context/messages
    //    （准备可能长跑，比如做压缩——之后若 backlog 为空就再补拉一次 steering）
    // 2) declareToolChanges：把「能执行的工具 vs 消息里声明的工具」差集
    //    合并成一条 system 消息，先于本次请求写入消息流
    // 3) 把 prepared + pending 消息发 message_start/end 并写入上下文
    // 4) prepareRequest({context, model, thinkingLevel}) ← 每次请求前，含第一次；
    //    返回值可整体替换本轮的 context / model / thinkingLevel
    // 5) 流式拿一个 assistant 回复：message = streamAssistantResponse(...)
    // 6) stopReason 是 error/aborted → finishTurn + turn_end + agent_end，硬退出
    // 7) 有 toolCall：stopReason==="length" 则整批判失败（参数可能被截断）；
    //    否则 executeToolCalls（sequential 或 parallel 由 executionMode 决定）
    // 8) decision = finishTurn(lastCompletedTurn)；发 turn_end
    //    end → agent_end 退出；continue → 记下续命承诺 explicitContinuation
    //    若已有工具调用或新 steering 在手，承诺已被满足，标记清零
    // 9) pendingMessages = getSteeringMessages()  ← 是否有新的 steering
  }
  // 内层将停：先看 follow-up
  const followUp = await config.getFollowUpMessages?.();
  if (followUp?.length) { pendingMessages = followUp; explicitContinuation = false; continue; }
  // 再兑现 continue 承诺：没有自然请求时，补一个只带上下文的空 turn
  if (explicitContinuation) { explicitContinuation = false; continue; }
  break;   // 真的停了
}
自研者必看： 注意 newMessages 与 currentContext.messages 的分野——currentContext 是整个历史（可能含预存在的上下文），newMessages 只统计本次循环新增的。循环结束时返回的是 newMessages，调用方（如 Agent）再把它并入自己的状态。

3.3finishTurn / prepareRequest：两个可编程边界

第 1 步「什么时候继续」由 finishTurn 裁决，第 4 步「这次请求带什么」由 prepareRequest 决定。两者共同替代了旧版单一的 shouldStopAfterTurn——旧回调只能回答「停不停」，回答不了「这次请求换成什么上下文」。

packages/agent/src/types.ts — 两个钩子的契约
typescript// turn 结束时的裁决：在 turn_end 之前调用；undefined = 维持原调度
export type AgentTurnDecision = { action: "continue" } | { action: "end" };

export type FinishTurn = (
  turn: AgentTurnContext,      // message / toolResults / context / newMessages 都在这
  signal?: AbortSignal,
) => AgentTurnDecision | void | Promise<AgentTurnDecision | undefined> | Promise<void>;
// 文档要点：{action:"continue"} 保证「还有下一次 provider 请求」。
// 若 toolResult/steering/follow-up 调度本来就会发请求，就不再多发；
// error 和 aborted 依然是硬退出，continue 救不回来。

export type PrepareRequest = (
  request: { context: AgentContext; model: Model; thinkingLevel: ThinkingLevel },
  signal?: AbortSignal,
) => AgentRequestUpdate | void | Promise<AgentRequestUpdate | undefined>;
// 文档要点：每次会话请求前都调用，包括第一次；此时 pending 消息已写入。
packages/agent/src/agent-loop.ts — runLoop 里的两处调用点（对照上面骨架的第 4、8 步）
typescript// 第 4 步：请求前替换运行时状态（pending 消息已全部入列）
const requestUpdate = await config.prepareRequest?.(
  { context: currentContext, model: config.model, thinkingLevel: config.reasoning ?? "off" },
  signal,
);
if (requestUpdate) {
  currentContext = requestUpdate.context ?? currentContext;
  config = { ...config, model: requestUpdate.model ?? config.model, ... };
}

// 第 8 步：工具结果落定之后、turn_end 之前
lastCompletedTurn = { message, toolResults, context: currentContext, newMessages };
const decision = await config.finishTurn?.(lastCompletedTurn, signal);
await emit({ type: "turn_end", message, toolResults });

if (decision?.action === "end") {
  await emit({ type: "agent_end", messages: newMessages });
  return;                          // end：裁决在 turn_end 之后立即生效
}
explicitContinuation = decision?.action === "continue";
pendingMessages = (await config.getSteeringMessages?.()) || [];
if (hasMoreToolCalls || pendingMessages.length > 0) {
  explicitContinuation = false;    // 已有自然请求，续命承诺视为满足
}
图 3.3：continue 是「保证还有下一次请求」，不是「立刻多跑一轮」——能被现有调度满足就不再加请求。
为什么拆成两个钩子 finishTurn 拿到的是已经落盘的完整 turn（assistant + 全部 toolResult），适合做「要不要继续」的裁决——错误与中止也走它，但只是被通知，不是被授权续命。prepareRequest 拿到的是即将发出去的那份上下文，适合做「这次请求换什么」的替换——它连第一次请求都覆盖，所以能统一「每轮前的上下文改写」，第 8 章的 AgentSession 就靠它把 SessionManager 的投影装进每次请求。

3.4流式回复与事件

streamAssistantResponse 是转化的关键点：先 transformContext、再 convertToLlm、调 streamFn，然后把「流式事件」翻译成 AgentEvent：

packages/agent/src/agent-loop.ts — 流式处理（节选）
typescriptlet messages = context.messages;
if (config.transformContext) {          // AgentMessage[] → AgentMessage[]
  messages = await config.transformContext(messages, signal);
}
const llmMessages = await config.convertToLlm(messages);   // 窄化成 Message[]
const response = await streamFunction(config.model, ...);

let partialMessage: AssistantMessage | null = null;
for await (event of response) {
  switch (event.type) {
    case "start":
      partialMessage = event.partial;
      context.messages.push(partialMessage);      // 先把半成品塞进上下文
      await emit({ type: "message_start", message: { ...partialMessage } });
      break;
    case "text_delta":  // 以及 thinking_*/toolcall_* 等增量事件
      partialMessage = event.partial;
      context.messages[context.messages.length - 1] = partialMessage; // 原位覆盖半成品
      await emit({ type: "message_update", assistantMessageEvent: event, message: { ...partialMessage } });
      break;
    case "done": case "error": {
      const finalMessage = await response.result();
      // 用最终消息替换挂在末尾的半成品
      context.messages[context.messages.length - 1] = finalMessage;
      await emit({ type: "message_end", message: finalMessage });
      return finalMessage;
    }
  }
}
一个很讲究的细节——先把「半成品」放进 messages，每次增量用新对象原位覆盖最后一项，最后用 final 替换。这样任何时刻上下文里都只有「当前位置」的正确消息，无需在结束时额外拼接。另一个容易漏看的防线：回复带着 toolCall 却 stopReason === "length"（输出被 token 上限截断）时，整批工具调用一律判失败——流式参数会经过一个尽力修复的 JSON 解析器，截断的参数可能校验通过但内容残缺，执行它等于埋雷，所以全部报错让模型重发。
图 3.4：带工具调用的一次 prompt 的典型事件序列。完整的精确序列见官方 README 与第 1 章引用的文档。
事件含义
agent_start / agent_end整次运行开始/结束；agent_end 携带全部 newMessages
turn_start / turn_end一个「turn」= 一次 assistant 回复 + 它的工具/结果；turn_end 先于 finishTurn 决策的执行
message_start / message_update / message_end单条消息三种状态；update 专用于流式
tool_execution_start / update / end单个工具的声明与完成（含流式 partial）

3.5Agent 类：有状态的封装 + 两个队列

裸的循环函数没有状态。Pi 用 Agent 类把它包起来，顺带持有 steeringQueue/followUpQueue 两个队列，并把上面两个钩子作为公开属性转发给 loop 配置。

工具变更也要「发消息」：内层循环在注入 steering 消息之前还有一步 declareToolChanges——context.tools 是运行时能执行的工具，而消息流里的 system 消息声明的是模型可以调用的工具，两者一旦不一致（比如压缩后换了工具集、扩展改了 loadout），差集就变成一条带 toolsAdded/toolsRemoved 字段的 system 消息插进消息流。模型由此得知「从现在起能用什么、不能用什么」，而且这条声明会随会话持久化——重放历史时无需额外状态就能恢复出当时的工具集。为什么选「往消息流里写」而不是「每次请求附带一个参数」？因为消息流能被序列化、能被重放，参数不能。
packages/agent/src/agent.ts — 属性、钩子与队列（要点）
typescriptexport class Agent {
  private steeringQueue: PendingMessageQueue;  // run 中途注入
  private followUpQueue: PendingMessageQueue;  // 运行将停时才注入
  public finishTurn?: FinishTurn;              // 每个完整 turn 后的裁决点
  public prepareRequest?: PrepareRequest;      // 每次请求前的上下文替换点

  async prompt(input): Promise<void> {
    if (this.activeRun) throw new Error("already processing...");
    const msgs = this.normalizePromptInput(input);
    await this.runPromptMessages(msgs);
  }
  steer(message): void { this.steeringQueue.enqueue(message); }  // 非阻塞
  followUp(message): void { this.followUpQueue.enqueue(message); }

  // 不消费地看一眼：下一个 turn 将送出哪条排队消息
  peekQueuedMessages(): AgentMessage[] {
    const steering = this.steeringQueue.peek();
    return steering.length > 0 ? steering : this.followUpQueue.peek();
  }
  abort(): void { this.activeRun?.abortController.abort(); }
}

// 队列的 drain 语义受 QueueMode 控制：
//   "all"          → 一次全部放出（drain 全部）
//   "one-at-a-time" → 每次只放最旧的一条（默认）
PendingMessageQueue.drain() 在 QueueMode === "one-at-a-time"（默认）时只放出最旧的一条，"all" 才一次全部放出。这避免了「乘胜追击」——每次只多塞一条，让 agent 消化完再决定。这些队列在 getSteeringMessages/getFollowUpMessages 里被 loop 拉取——即拉模型（pull），不是模型主动注入。循环开头会先拉一次（用户可能在等待时已经打字），prepareNextTurn 准备（可能长跑，比如压缩）之后若 backlog 为空还会再补拉一次——否则 one-at-a-time 模式可能在一个 turn 里送出两条。新增的 peekQueuedMessages() 供 UI 预览「下一条要送的是什么」而不消费它。

3.6收尾：四个答案

回到开头的四个问题。

  • 循环的边界由谁决定？finishTurn 在 turn_end 之前给出 continue/end 裁决；continue 只承诺「还有下一次请求」，能被工具结果、steering、follow-up 的正常调度满足，否则循环在退出前补一个只读上下文的空 turn。error/aborted 是硬退出，续命无效。
  • 请求前有几道工序？三道，顺序固定：prepareNextTurn（可长跑的准备，如压缩）→ declareToolChanges（工具差集写成 system 消息）→ prepareRequest（最后一刻替换 context/model/thinkingLevel）。
  • 流式半成品怎么处理？先入列、增量原位覆盖、final 替换——上下文任何时刻都是合法序列；带工具调用的 length 截断整批判失败。
  • 中途插话从哪进来？Agent 的 steering/follow-up 两条队列，循环以拉模型取用；one-at-a-time 是默认节奏，peekQueuedMessages 支持预览不消费。
移植提示 「finishTurn 在 turn_end 前裁决、决策在 turn_end 后执行」「prepareRequest 覆盖包括第一次在内的每次请求」这两条把「循环控制」与「循环本体」分开了——你自研 Runtime 时可以原样搬走；第 8 章会看到生产层怎么用这两个钩子接管上下文。
