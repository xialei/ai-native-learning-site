消息与类型体系：AgentMessage 与 Message 的「翻译」

整个 Pi 都围绕一个核心抽象运转：AgentMessage。它比 LLM 认识的 Message 更宽、更可扩展。本章讲清这两套类型为什么必须分开住、自定义消息怎么塞进来还保持类型安全，以及发请求前的几步转换里，哪一步绝不允许崩。

2.1核心矛盾：一个灵活的运行时，一个固执的 LLM

先看矛盾在哪。Pi 归一化后的 Message 类型只认四种角色：system、user、assistant、toolResult——这是 LLM 的一亩三分地，多一点都不收。但一个真正的 Agent 运行时还想表达很多「非 LLM 消息」：给 UI 的通知、自定义的应用消息、压缩的记账条目。两边谁也不迁就谁，所以 Pi 干脆用两套类型：

图 2.1：AgentMessage 是「宽」的运行时类型，Message 是「窄」的 LLM 类型，convertToLlm 是唯一的窄化出口。

2.2AgentMessage：怎么做到可扩展

看 packages/agent/src/types.ts 里 AgentMessage 的定义：

packages/agent/src/types.ts — AgentMessage 与声明合并
typescript// 基础消息：直接复用 pi-ai 的 Message（user/assistant/toolResult）
import type { Message } from "@earendil-works/pi-ai";

// 空的"扩展点"接口 —— 应用通过 declaration merging 塞自定义消息类型
export interface CustomAgentMessages {
  // Empty by default - apps extend via declaration merging
}

// Message 联合上应用自定义的消息，构成"宽"的运行时消息
export type AgentMessage =
  | Message
  | CustomAgentMessages[keyof CustomAgentMessages];
CustomAgentMessages 初始为空，应用用 TypeScript 的声明合并往里加键，例如 declare module "..." { interface CustomAgentMessages { notification: NotificationMessage } }，AgentMessage 就自动包含了你的类型。别小看这个空接口——Pi 的会话、UI、harness 全靠它才能往会话里塞「不是 LLM 消息」的东西而保持类型安全。这是整本书反复出现的一个设计决定：运行时的类型宽，发给模型的类型窄。

2.3convertToLlm：唯一的出口，且不能崩

每次调 LLM 前，循环要把所有 AgentMessage 变成 LLM 懂的 Message。这活由一个函数承担，而它的契约里写着一条容易忽略的要求：绝不能抛异常。

packages/agent/src/types.ts — convertToLlm 的契约（文档注释 + 默认实现）
typescript// 每次 LLM 调用前，把 AgentMessage[] 转为 Message[]
convertToLlm: (messages: AgentMessage[]) => Message[] | Promise<Message[]>;

// agent.ts 里的默认实现：只放行 LLM 认识的四种角色，其余一律过滤
function defaultConvertToLlm(messages: AgentMessage[]): Message[] {
  return messages.filter(
    (message) =>
      message.role === "system" ||
      message.role === "user" ||
      message.role === "assistant" ||
      message.role === "toolResult",
  );
}
默认实现就是个过滤器——自定义消息（如 notification）直接被丢弃，不进 LLM。注意 system 也在放行之列：系统提示现在以 SystemMessage 的形式躺在消息列表里（它的演化故事在第 10 章），它是要发给模型的，不能滤。默认实现可以覆盖：把自定义消息转换成 user 消息，或做更细的字段归一化，随你。唯一不能破的规矩是「绝不 throw」——失败就返回安全回退值。转换器一崩，整个事件流就乱了，这是自研时最容易踩的坑。

2.4transformContext：窄化之前的可选项

在 convertToLlm 之前，还有一个可选的 transformContext，它工作在 AgentMessage 层面——做「上下文管理」「注入外部上下文」这类需要完整消息类型的操作：

packages/agent/src/agent-loop.ts — streamAssistantResponse 里的两步转换
typescript// 第一步：AgentMessage[] → AgentMessage[]（可选清洗/裁剪/注入）
let messages = context.messages;
if (config.transformContext) {
  messages = await config.transformContext(messages, signal);
}

// 第二步：AgentMessage[] → Message[]（窄化到 LLM 认识的格式）
const llmMessages = await config.convertToLlm(messages);
// 第三步：Context{systemPrompt, messages, tools} 折叠成 TranscriptContext（见第 10 章）
const llmContext = normalizeContext({ messages: llmMessages });
官方文档给的动机是「transformContext：剪掉旧消息、注入外部上下文」。而生产 harness 正是在这个位置接入会话树的上下文构建——它会从会话里挑出该发给模型的消息（见 第 5 章）。第三步是 provider 层收尾：normalizeContext 把散落的 systemPrompt 折叠进消息列表，之后 provider 看到的统一是 TranscriptContext（详见 第 10 章）。

2.5把前面串起来：一条消息的一生

消息流转总括
text用户输入 ──> AgentMessage(user) ──> [会话/上下文] ──> transformContext
                                              （可裁剪/注入）
                                                     │
                                                     └──> convertToLlm ──> Message[] ──> LLM
                                                                                        │
                                                       回填: LLM 输出 ──> AssistantMessage
                                                                        │ 带 toolCall
                                                                        └──> 工具执行 ──> ToolResultMessage
关键点： 助理回复（AssistantMessage）与工具结果（ToolResultMessage）也都是 AgentMessage 的一员。于是整条会话历史就是一串 AgentMessage——这让我们能在第 4 章的「会话树」里，把它作为一等公民存储和检索。

2.6速查：Pi 的核心类型

类型角色用于
MessageLLM 真懂provider 调用边界
AgentMessage运行时统一会话、上下文、循环全程
AgentTool工具定义schema + execute + 钩子
AgentEventUI 事件agent_start … agent_end
AgentToolResult工具返回回填给 LLM 的内容 + 元数据

2.7收尾：宽窄两个类型，一个出口

要点 你也应该维护「宽的运行时消息」和「窄的 LLM 消息」两个类型，并只在一个明确的出口做转换。这样自定义消息（进度、UI、工具副作用）可以自由进出会话，而 LLM 始终只看到干净的历史。很多 Agent 框架的混乱，源头就是把两套类型揉在了一起。
