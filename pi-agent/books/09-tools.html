工具层：Agent 如何「动手」

一个工具要定义哪些东西？模型给的参数不可靠时在哪修？从「模型说要调工具」到「结果回到模型手里」中间经过哪些阶段？一条消息带多个工具调用时，顺序跑还是并行跑、谁来定？还有那个绕不开的问题：谁有权拦下一个工具调用——工具自己、循环、还是外挂的扩展？本章把工具层从契约到管线到生产工具箱逐层拆开。

9.1工具层的四个疑问

第 3 章里，工具只是循环里的一个环节。真要自己实现一遍，问题立刻具体起来。先是契约——一个工具最少要定义哪些字段？模型给的参数常有瑕疵（相对路径、JSON 字符串包数组），在哪一层修？接着是管线——一次工具调用从 assistant 消息到 toolResult 消息，中间要经过校验、权限、执行、后处理，这些步骤如何组织，出错时走哪条路？然后是并发——模型经常一次要调多个工具，读写文件可以并行，但两个都写同一个文件就不行，串行还是并行由谁决定？最后是权限——危险命令谁来拦？拦的逻辑放在工具里、循环里、还是外面？

答案地图：契约看 AgentTool + prepareArguments 容错（9.2）；管线是 prepare → execute → finalize 三阶段（9.3）；并发靠全局配置 + 工具自声明 executionMode（9.4）；权限则是个反直觉的答案——工具层不设权限，全部交给 beforeToolCall 钩子，生产上由扩展接管（9.5）。
图 9.1　工具层的三层结构：契约、管线、生产工具。权限不在这三层里——它挂在 9.5 的钩子上

9.2工具长什么样：AgentTool 契约与参数容错

顶层工具接口在 packages/agent/src/types.ts。它继承 pi-ai 的 Tool（name/description/parameters），核心要求三样东西——label（给 UI 看的名字）、parameters schema（给模型看的说明书）和 execute（真正动手）：

packages/agent/src/types.ts · AgentTool 接口（要点）
export interface AgentTool<TParameters extends TSchema = TSchema, TDetails = any>
  extends Tool<TParameters> {              // 基座：name + description + parameters(TSchema)
  // 1. 元数据：给 UI 显示的人类可读标签
  label: string;

  // 2. 执行入口：id + 参数 + 中止信号 + 流式更新回调（抛错=失败，不往 content 里塞错误）
  execute(toolCallId: string, params: Static<TParameters>, signal?: AbortSignal,
          onUpdate?: AgentToolUpdateCallback<TDetails>): Promise<AgentToolResult<TDetails>>;

  // 3. 可选增强
  prepareArguments?: (args: unknown) => Static<TParameters>; // schema 校验前改写原始参数
  replay?: "never" | "safe";                     // 崩溃恢复时该副作用能否安全重放
  executionMode?: "sequential" | "parallel";  // 本工具是否强制串行
}

几个被低估的设计点，逐句拆：

  • signal（AbortSignal）：每个工具 execute 都收到中止信号。这打破了「工具一旦跑起来就不能停」的僵局——用户可以 steer 打断一个正在执行的 Bash。这是让中断语义（第 8 章）能落到工具层的关键。
  • onUpdate 流式回调：长任务（如 Bash 持续输出）可以边跑边发 partialResult，对应 Agent 事件 tool_execution_update。回调只在 execute 存续期内有效，工具落定后的调用会被忽略。
  • executionMode 混搭：全局可设 toolExecution，但单个工具可以自我声明「我必须串行」——比如「编辑文件」在你预期上有依赖时。（见 9.4）
  • prepareArguments：模型给的参数常是相对路径、带省略号；在 schema 校验前改写原始参数（补全 cwd、展开 ~），让模型侧更轻、执行侧更正确。
  • replay 恢复语义：durable 意图已落盘但结果未知时（崩溃恢复），该副作用能不能安全重放——"never" 不重放、"safe" 可重放。这是把「幂等性」提升为工具契约的一部分。
概括：工具的 execute 签名其实是一个「可中止、可流式、可枚举」的 IO。你在自制 Runtime 里定义工具时，这几样（signal / onUpdate / 参数校验）几乎是开箱就得有的最低配置。注意放行检查不在工具身上——beforeToolCall 是 AgentLoopConfig 上的全局钩子（第 3 章），工具自身只声明 label、replay、executionMode 这些「自我描述」。

9.2.1 模型不守契约时：prepareArguments 的容错分支

edit 工具的契约是「一组 { oldText, newText } 编辑」，但真实模型并不总按契约来。生产版的 prepareEditArguments 做了三道容错，本质上是「宁可猜对也别让一次合法编辑失败」：

core/tools/edit.ts · prepareEditArguments 容错分支
// 1) 有些模型（Opus 4.6、GLM-5.1）把 edits 当 JSON 字符串发，而非数组
if (typeof args.edits === "string") {
  const parsed = JSON.parse(args.edits);
  if (Array.isArray(parsed))       args.edits = parsed;       // 数组：直接用
  else if (isSingleEditInput(parsed)) args.edits = [parsed];     // 单对象：包成数组
else if (isSingleEditInput(args.edits)) args.edits = [args.edits]; // 对象（非字符串）：同样包成数组
}

注意第三条——有的模型直接发一个 { oldText, newText } 对象（不是数组、也不是字符串）。isSingleEditInput 会把它识别出来并包成单元素数组。三道分支合起来覆盖了「数组 / JSON 字符串里是数组 / JSON 字符串里是对象 / 直接对象」四种乱法。基础层 agent/src/harness/tools/edit.ts 同步了同样的逻辑——契约层与生产层保持一致。

另一个细节是 BOM（字节顺序标记）。带 UTF-8 BOM 的文件，匹配前要先剥离 BOM（模型不会在 oldText 里写那个不可见字符）。Pi 把这个能力从 edit-diff.ts 里原先的 stripBom 抽到 utils/text.ts，重命名为 splitBom——返回 { bom, text }，写回时再把 BOM 拼回去，避免剥离 BOM 后悄悄改了文件编码。

容错的边界：这些容错只动「输入形状的归一」，不替模型判断语义（不猜它想改哪行、不放松唯一性校验）。把「模型不守契约」当成常态来设计工具入口，是让 Agent 在真实模型下少崩的关键工程习惯。

9.3从 toolCall 到 toolResult：prepare → execute → finalize

生产代码把「跑一个工具」拆成三个阶段，跑在 packages/agent/src/agent-loop.ts 的 executeToolCalls 里。看管线全景：

图 9.2　工具调用三阶段管线：出错的路径不抛异常，而是变成一条错误结果走完全程

看 prepareToolCall 里「出错了也不抛出，而是立刻返回错误结果」的哲学——错误被当作一条普通的结果走完管线，让模型自己读：

agent-loop.ts · prepareToolCall（节选）
async function prepareToolCall(currentContext, assistantMessage, toolCall, config, signal) {
  const tool = currentContext.tools?.find((t) => t.name === toolCall.name);
  if (!tool) return {
    kind: "immediate",
    result: createErrorToolResult(`Tool ${toolCall.name} not found`),
    isError: true,
  };

  try {
    const preparedToolCall = prepareToolCallArguments(tool, toolCall);
    const validatedArgs = validateToolArguments(tool, preparedToolCall);
    if (config.beforeToolCall) {
      const beforeResult = await config.beforeToolCall(
        { assistantMessage, toolCall, args: validatedArgs, context: currentContext }, signal);
      if (signal?.aborted) return {   // 中止优先于钩子结果：等来的放行也不算数
        kind: "immediate", result: createErrorToolResult("Operation aborted"), isError: true };
      // beforeToolCall 钩子可以 block！（这是权限/审校的挂点）
      if (beforeResult?.block) {
        const result = createErrorToolResult(beforeResult.reason || "Tool execution was blocked");
        if (beforeResult.terminate === true) result.terminate = true;
        return { kind: "immediate", result, isError: true };
      }
    }
    return { kind: "prepared", toolCall, tool, args: validatedArgs };
  } catch (error) {
    return { kind: "immediate", result: createErrorToolResult(String(error)), isError: true };
  }
}
两种提前返回值得注意：kind: "immediate" 表示「根本没真正执行」——工具未找到、参数校验失败、被 hooks block、被中止，全部归为 immediate。而归为 kind: "prepared" 的才真正走 execute。这两种结果都统一转成错误消息喂回给模型，模型从错误里学会不犯第二次。这是「让 LLM 自己纠错」的机制化表达。另一个细节：abort 检查放在钩子返回之后——钩子慢吞吞审完才放行，但中止信号一到，放行结果立即作废。

9.4顺序还是并行：执行模式与整批终止

一个 assistant 消息里可以带多个 toolCall。怎么跑？executeToolCalls 的决策规则是——默认看全局配置，但任何单个工具都能「强制串行」：

agent-loop.ts · executeToolCalls 决策
async function executeToolCalls(currentContext, assistantMessage, config, signal, emit) {
  const toolCalls = assistantMessage.content.filter((c) => c.type === "toolCall");
  // 只要这批里有一个工具自称必须串行，整批就走串行
  const hasSequentialToolCall = toolCalls.some(
    (tc) => currentContext.tools?.find((t) => t.name === tc.name)?.executionMode === "sequential",
  );
  if (config.toolExecution === "sequential" || hasSequentialToolCall) {
    return executeToolCallsSequential(...);
  }
  return executeToolCallsParallel(...);
}

两种模式的差别，精确定义为三件事：

维度顺序执行并行执行
工具是否同时跑逐个 await，一个完成才跑下一个所有非 immediate 的工具 Promise.all 并发
中途中止每个工具后检查 signal.aborted，中止就 break中止就停止继续收集，已提交的用 Promise.all 等完
结果顺序天然按 call 顺序Promise.all 仍按原数组顺序归位（不会乱序）

并行版本把「要真正执行的部分」收集成函数数组，最后统一 Promise.all：

agent-loop.ts · executeToolCallsParallel（节选）
// immediate 的（已直接出结果）直接归位；剩下的包成 async 函数
finalizedCalls.push(async () => {
  const executed = await executePreparedToolCall(preparation, signal, emit);
  const finalized = await finalizeExecutedToolCall(currentContext, assistantMessage, preparation, executed, config, signal);
  await emitToolExecutionEnd(finalized, emit);
  return finalized;
});
// …最后：
const orderedFinalizedCalls = await Promise.all(finalizedCalls);

还有一层批次级的终止语义 shouldTerminateToolBatch：

agent-loop.ts · 整批终止
function shouldTerminateToolBatch(finalizedCalls): boolean {
  // 批次的「全部工具都要求 terminate」才提前结束本轮 turn
  return finalizedCalls.length > 0 &&
    finalizedCalls.every((f) => f.result.terminate === true);
}
设计取舍：必须「全部都 terminate」才结束 turn，而不是「有任何一个」。因为工具结果里带 terminate 通常是「这轮已经完成任务」，但如果同一批里还有个只读查询，仍应让模型读到它的结果再决定。安全与灵活在这里做了妥协——极端保守（全 terminate 才收手）。

9.5谁来放行一个工具：钩子链与 user_bash

权限问题的答案分两半：模型发起的工具调用走 beforeToolCall 钩子链；用户亲手敲的命令走 user_bash 事件。先看前者——注意一个关键事实：pi 内核里没有内置权限确认。agent-loop 只留了钩子挂点，具体放不放行由生产层决定。生产 agent-session 把扩展的 tool_call 事件接到这个挂点上：

agent-session.ts · 安装工具钩子（_installAgentToolHooks，节选）
// 安装一次工具钩子，复用给每个 Agent run（避免重复安装）
this.agent.beforeToolCall = async ({ toolCall, args }) => {
  // 没有扩展监听 tool_call 时直接放行（返回 undefined = 不干预）
  if (!runner.hasHandlers("tool_call")) return undefined;
  try {
    return await runner.emitToolCall({
      type: "tool_call", toolName: toolCall.name, toolCallId: toolCall.id, input: args });
  } catch (err) {
    // 扩展抛错 → 原样抛给 agent-loop → 工具被 block（fail-closed）
    if (err instanceof Error) throw err;
    throw new Error(`Extension failed, blocking execution: ${String(err)}`);
  }
};

「谁有权放行一个工具」在这里收敛成一条链：扩展（可 block）→ 真正 execute。没有扩展监听时全部放行；扩展想拦，就在 tool_call 事件里返回 { block: true, reason }（官方示例 examples/extensions/protected-paths.ts 就是这样实现路径保护的）。扩展抛错也按 block 处理——官方文档原话：扩展文档「A tool_call handler failure blocks the tool as a fail-safe」。

9.5.1 user_bash：用户亲手执行的命令也过钩子

上面的拦截链针对的是「模型发起的工具调用」。但还有一个权限盲区：用户在 TUI 里用 !（或 !!）前缀亲手敲的命令——它不经过任何工具，直接在终端里跑。这条路径同样给扩展留了钩子（user_bash 事件），而且处理方式很有讲究：

extensions/types.ts · user_bash 的返回类型（判别联合）
// 返回 undefined → 照常本地执行；返回时必须二选一：
export type UserBashEventResult =
  | { operations: BashOperations; result?: never }   // 换掉执行器（如远程 shell），仍由 pi 跑
  | { operations?: never; result: BashResult };       // 扩展自己跑完了，交回完整结果
agent-session.ts / interactive-mode.ts · 两个方向的配合（节选）
// session 侧：executeBash 接受 operations 参数——执行器可被替换
await executeBashWithOperations(resolvedCommand, cwd,
  options?.operations ?? createLocalBashOperations({ shellPath }), ...);

// 交互层：扩展出错时，绝不回退到本地执行
try {
  eventResult = await extensionRunner.emitUserBash({ type: "user_bash", command, ... });
} catch {
  // The extension runner already reported the error. Do not fall back to local execution.
  return;
}

三点值得记。一、判别联合表达「异或」：operations（我只换执行环境）与 result（我跑完了，直接用我的结果）不能同时给，TypeScript 用 result?: never 把这个约束写进类型；运行时还有一道 isUserBashEventResult 校验，不符合直接抛错。因为对 bash 来说，「扩展想拦但返回了残缺对象」绝不能被解释成「那就本地跑吧」——! 敲进来的命令是要真改系统的，语义含糊时唯一安全的动作是不执行。这就是 fail-closed：把「失败怎么办」的默认值设为「不做」，而不是「退回原路」。

二、执行器是抽象的：executeBashWithOperations 把「跑命令」抽象成可替换的 BashOperations（本地 shell 只是默认实现），扩展可以换成远程执行、容器执行。而 recordBashResult 落盘的是一条 bashExecution 角色的消息（带 command/output/exitCode/cancelled/truncated/excludeFromContext），进 LLM 上下文时由 bashExecutionToText 渲染成 Ran \`command\` 开头的 user 消息——!! 前缀（excludeFromContext: true）的输出不进上下文。

架构洞察：工具本身不该关心权限与审校——那是 harness 的职责。工具只做「被允许做的 IO」。分层之后，你能在不动任何工具源码的情况下，给所有工具统一加日志、限流、审校、权限。pi 把这个思路推到极致：内核连内置确认都没有，权限策略 100% 由扩展在 tool_call 事件里表达。这也是你第 12 章值得借鉴的。而 user_bash 补上了另一半：用户的直接操作也要过同一套权限哲学，并且失败时的方向是「拒绝执行」而非「换个方式执行」。

9.5b生产工具箱：七个默认核心工具

生产 harness 的工具在 packages/coding-agent/src/core/tools/。它们不是散装函数，而是统一通过 createToolDefinition / createTool 工厂，按需开关（读只读/编码/全部三套）：

tools/index.ts · 工具清单与分类
export type ToolName = "read" | "bash" | "powershell" | "edit" | "write" | "grep" | "find" | "ls";
export const allToolNames: Set<ToolName> = new Set([...]);

// 只读三件套（read / grep / find / ls）—— 安全无副作用
export function createReadOnlyToolDefinitions(cwd, options) {
  return [createReadToolDefinition(cwd, options?.read),
           createGrepToolDefinition(cwd, options?.grep),
           createFindToolDefinition(cwd, options?.find),
           createLsToolDefinition(cwd, options?.ls)];
}
// 编码四件套（+ bash / edit / write / read）—— 会改动工作区
export function createCodingToolDefinitions(cwd, options) {
  return [createReadToolDefinition(...), createBashToolDefinition(...),
           createEditToolDefinition(...), createWriteToolDefinition(...)];
}
工具动作典型返回特性
read读文件（多文件可合并请求）内容 + 行号，超长截断路径白名单校验、大文件截断
bash执行 shell 命令stdout/stderr + 退出码副作用最强，权限策略全靠 tool_call 扩展，输出累积/截断
edit精确替换文件片段成功/失败 + 该行上下文片段唯一性校验、写前 diff、文件变更队列
write整文件写入写入确认配合 edit 的队列
grep正则搜索匹配行 + 文件名忽略二进制、限定扩展名
find按名/模式找文件路径列表结果截断
ls列目录条目 + 类型/大小辅助定位

重点看 bash——它的 execute 签名里接了 signal，让「用户 Esc 打断一个跑飞了的命令」在工具层可中止；同时它是默认工具集里最能改变系统状态的工具。生产 harness 把所有核心工具都挂到 ToolExecutionMode 与全局 beforeToolCall/afterToolCall 钩子上（见 9.5），扩展可以给任意工具加权限门。

平台差异：Windows 上还有一个可选的 powershell 工具——它与 bash 共用同一套 createShellToolDefinition 骨架，契约、权限模型完全一致，只是换成 PowerShell 语法。它不进默认工具集（默认仍是 read/bash/edit/write），需显式 tools:["powershell"] 或走 createAllTools 全量开启，且仅在 Windows 可用。
安全模型概括：Pi 的工具分「只读（read/grep/find/ls）」与「会改动系统（bash/edit/write）」。内核对两者都无条件放行——真正的门禁装在 tool_call 扩展事件 上，由用户装哪个扩展决定（路径保护、远程审批……）。你自己做 Runtime 时，把副作用强度作为工具分类的第一维，能让权限系统简单一半。

还有一个藏在 Tool 接口里的字段值得知道：constrainedSampling。内置的 read/bash/edit/write 都带 { type: "json_schema", strict: "prefer" }——意思是「模型倾向用 JSON Schema 严格模式来填参数」。strict 是个光谱：prefer 表示 provider 支持就收紧、不支持就静默退回普通 schema（把模型从不支持 strict 的供应商迁到 pi-ai 上，参数照填）；require 则相反——provider 不支持就直接报错，绝不悄悄降级。哪些 JSON Schema 关键字（$ref、allOf 等）会被 strict 模式拒收，在 pi-ai 的 constrained-sampling.ts 里白名单管理。给工具定参数 schema 时知道这件事有实际意义：schema 越保守，strict 模式下的参数质量越高。

演化痕迹：strict 的「降级」对象也变过。工具侧的 prefer 只是光谱的一半；另一半在 provider 侧——supportsStrictMode 决定要不要把 strict 字段发出去。这条开关的默认值经历了一次翻转：早年是「OpenAI 兼容端点默认发 strict，再黑名单排除已知不支持的（Cerebras、Moonshot……）」，结果是混用 strict/非 strict 工具的端点直接报 400、且黑名单永远追不完新网关。后来默认值翻转为 false——只有目录里验证过的模型显式开启（第 10 章 10.6.1 详过这个案例）。给你的启示：prefer 的「静默降级」之所以能成立，前提是下游开关的默认值足够保守——能力协商的两层（工具的 prefer/require + provider 的 supports 开关）必须同向保守，光谱设计才不会漏。

9.6终端的秩序：stdout 接管与文件写串行化

9.1–9.5 讲的是「工具怎么定义、怎么被管线驱动」，但有两处工程细节藏在「多个组件抢同一资源」时起作用——一个是抢终端输出，一个是抢同一个文件。它们决定了工具在并发与 TUI 共存时是否还能保持秩序。

9.6.1 安全接管 stdout/stderr

TUI 要渲染界面，而 bash 工具会往 stdout 写——两者直接打架会让屏幕花掉。coding-agent/src/core/output-guard.ts 通过「暂时接管 process.stdout.write」再"还给"原实现，并维护一条串行化的 raw 写入链（rawStdoutWriteTail），加 10ms 重试防背压：

output-guard.ts · 接管 stdout
let rawStdoutWriteTail: Promise<void> = Promise.resolve();
async function writeRawStdoutChunk(text: string): Promise<void> {
  while (true) {
    try {
      await new Promise<void>((resolve, reject) => {
        getRawStdoutWrite()(text, (error) => error ? reject(error) : resolve());
      });
      return;                  // 成功即返回
    } catch {
      await sleep(RAW_STDOUT_RETRY_DELAY_MS); // 10ms 后重试（应对背压）
    }
  }
}

它的价值不在「抢」，而在有序——所有写终端的内容都汇入同一条串行管道，谁也别想在别人的字符中间插队，从而避免花屏与字符撕裂。

9.6.2 按"真实文件"串行化写入

9.5b 的工具表里 edit/write 那行写着「文件变更队列」，但没展开它最实在的一点：队列键取自 realpath，而不是传入的路径字符串。

tools/file-mutation-queue.ts · realpath 键 + Promise 链队列
async function getMutationQueueKey(filePath: string): Promise<string> {
  const resolvedPath = resolve(filePath);
  try { return await realpath(resolvedPath); }   // 同一个真实文件→同一个键
  catch (error) {
    if (isMissingPathError(error)) return resolvedPath; // 文件尚不存在，退回绝对路径
    throw error;
  }
}

// 维护每文件一条 Promise 链：前一个写完，才轮到自己
const currentQueue = fileMutationQueues.get(key) ?? Promise.resolve();
let releaseNext!: () => void;
const nextQueue = new Promise<void>((r) => { releaseNext = r; });
const chainedQueue = currentQueue.then(() => nextQueue);
fileMutationQueues.set(key, chainedQueue);
await currentQueue;   // 等前面的写完成
try { return await fn(); } finally { releaseNext(); ... }

用 realpath 的好处：对「同一个物理文件」的并发编辑——哪怕一个用 ./src/a.ts、一个用 /abs/src/a.ts、一个经过符号链接——都会被归到同一把「锁」串行执行；而不同文件仍并发，不拖慢整体。Promise 链 + releaseNext 是一个极简、无外部依赖的「异步互斥锁」。

共通教训：两处都是「并发下的秩序治理」。shared 资源的竞争（终端、文件）若放任不管，系统偶尔就出“灵异”bug。Pi 的做法可移植性极强——realpath 归并 + Promise 链互斥，是你在自制 Runtime 里给任何外部状态（文件、日志、UI）加串行化时可直接复用的模板。

9.7收尾：四个问题的答案

回到开头的四个问题：

  • 契约——AgentTool 五要素：label、parameters、execute(signal/onUpdate)，加可选的 prepareArguments / replay / executionMode。模型参数不可靠 → prepareArguments 归一输入形状（edit 的四路容错），不猜语义。
  • 管线——prepare（校验+钩子）→ execute（可中止可流式）→ finalize（afterToolCall 改写）。错误不抛异常，变成一条错误结果喂回模型，让模型自己纠错；abort 优先于钩子放行。
  • 并发——全局 toolExecution 配置为默认，单个工具声明 executionMode:"sequential" 即可把整批拉回串行；并行用 Promise.all 保证结果顺序；terminate 必须「全批一致」才提前收 turn。
  • 权限——内核只留 beforeToolCall 挂点，无内置确认；生产上由扩展在 tool_call 事件里放行或 block，扩展抛错也按 block（fail-closed）。用户手敲的 ! 命令走 user_bash 事件，同样 fail-closed。
