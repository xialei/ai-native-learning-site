会话与存储模型：一颗 append-only 的会话树

Pi 的 Session 不是简单的「消息数组」，而是一片 append-only 的 Entry 树，外加一组带类型地址的簿记值（branch tip、lane 配置/状态、操作元数据、usage 行）。下面展开这套模型与事务追加的纪律，是第 5～7 章的基石。
产品视角 「树形结构、可分享的会话历史。」 会话被存成树而非线性数组：用 /tree 跳回任意历史节点继续，所有分支住在同一个文件里；按消息类型过滤、给条目打书签；→ /export 导出 HTML，/share 上传 GitHub gist 拿可渲染的分享链接。本章就是这套「树」在源码里的实现。

4.1为什么不是「一个数组」

普通 Agent 用一个 AgentMessage[] 当历史。Pi 把它升级成一片追加式（append-only）有向树，原因是它要满足三个硬需求：

  • 分叉（fork）与多分支：一次「转向」（navigation）可能开出新分支，旧分支仍完整保留。
  • 崩溃恢复：每一步都落盘，进程死了能从最后一条 op.state 精确恢复。
  • 元数据与消息解耦：模型换了、思考级别改了、操作开始了——这些不是「消息」，但要可查询、可审计。

所以它把「会话里发生的一切」分成两个名字空间：Entry 树（可进 LLM 的内容，四个 type）与带类型地址的簿记值（不进 LLM：branch tip、lane 配置/状态、op.meta/op.state、usage 行、pending 产物）。所有写入都在一个事务里按 seq 严格递增提交。

4.1b交互沙盘：让会话树长起来

下面是一颗真实的最小 Session（复刻了 commit.ts + in-memory-storage-state.ts 的 seq / branch tip / parentId 语义，以及 fork.ts 的 fork 语义）。按钮触发的每一步都是真实的写入——追加消息让节点挂在 main 分支的叶子上、追加 usage只进簿记轨道不进树、回溯把 tip 指针拨回历史节点（再追加即长出新分支）、fork复制一条路径长出第二棵树、继承源 seq。右侧账本是 entry / usage / value / lane 四种写入混排的同一本账。

    4.2一棵 Entry 树 + 一组簿记值 + 一条纪律

    图 4.2：Session 的两类状态 + 两种附属写入。核心纪律——所有写入（entry/usage/value/list）在同一个事务里提交，靠 seq 严格递增保证顺序与可恢复性。
    packages/agent/src/harness/session/types.ts — Entry 的基类与种类
    typescriptexport type EntryType = "message" | "compaction" | "branch_summary" | "custom";

export interface EntryBase {
  id: string;
  parentId: string | null; // 追加时的分支叶子 id（由事务写入方给出）
  seq: number;        // 共享单调递增序号（由存储分配）
  timestamp: number;  // Unix 毫秒（由存储分配）
  type: EntryType;
  customType?: string;
}
export type Entry =
  | MessageEntry        // type: "message"        —— 真正的对话消息
  | CompactionEntry    // type: "compaction"     —— summary + retainedTail
  | BranchSummaryEntry // type: "branch_summary" —— 分支导航摘要
  | CustomEntry;        // type: "custom" + customType + data
    读懂这段： seq 是全局共享的（不是 per-type），由存储在事务里分配，保证「事件的先后」唯一可判定。parentId 指向「追加时那个分支的叶子」，从而把一个个 entry 串成树的分支。旧版的 model_change / thinking_level_change / active_tools_change 已不再是 Entry：模型、思考级别、激活工具现在住在 pi.lane.config/{lane} 这个簿记值里（见 4.3），第 5 章的上下文构建直接读它拿到「当前模型/思考级别」。

    4.3Branch：命名分支 + 叶子指针（就是 lane）

    Lane 是一个「分支怎么长」的指针，存储层叫 Branch，运行层叫 AgentLane。每个 lane 的叶子存在簿记值 pi.branch.tip/{lane} 里；追加新 entry 时，parentId 取该 lane 的当前 tip，并在同一个事务里推进 tip。

    packages/agent/src/harness/session/session.ts — 追加 = 插入 entry + 推进 tip（一个事务）
    typescriptasync appendToBranch(name, entry, context): Promise<string> {
  const id = this.idGenerator.next();
  await this.mutate(async (mutator) => {
    const tip = await mutator.getValue(branchTip(name), context);
    if (tip === undefined) throw new SessionInvariantError(`Unknown branch: ${name}`);
    await mutator.commit(
      [
        insertEntry({ id, parentId: tip.value, type: "message", message: entry.message }),
        setValueWrite(branchTip(name), id),      // 推进叶子指针
      ],
      context,
    );
  }, context);
  return id;
}
    读懂这段： 「追加 = 更新分支 tip」在同一个事务里完成，不存在「插了 entry 但 tip 没动」的中间态。把一个 lane 的 tip 移到已有 entry（等价于把「指针」拨回历史某点）就是实现「回溯/分叉」的原语——历史数据一条不删，第 7 章的 navigation 就靠它。lane 首次创建时（runtime/harness.ts），runtime 会用三个 value 写把 lane 落盘：pi.branch.tip/{lane} + pi.lane.config/{lane}（模型/思考级/激活工具种子）+ pi.lane.state/{lane}（空闲 lane 状态）。

    4.4事务提交的纪律：单调 seq、唯一 id、父必须存在

    每个事务里的写入按顺序分配 seq（从存储的 nextSeq 起），提交前统一校验：seq 严格单调、entry/usage id 全局唯一（含同事务内）、entry 的父必须已存在（含同事务内先写入的）。这是恢复时「我到底写到哪了」的唯一依据。

    packages/agent/src/harness/session/commit.ts — validateCommittedWrites（节选）
    typescriptexport function validateCommittedWrites(writes, firstSeq, state): void {
  let previousSeq = firstSeq - 1;
  const transactionIds = new Set<string>();
  const transactionEntryIds = new Set<string>();
  for (const write of writes) {
    if (write.seq <= previousSeq)
      throw new Error(`Non-monotonic storage sequence: ${write.seq}`);  // 必须严格递增
    previousSeq = write.seq;
    if (write.kind !== "entry" && write.kind !== "usage") continue;
    if (state.hasEntryOrUsageId(write.id) || transactionIds.has(write.id))
      throw new Error(`Duplicate entry or usage id: ${write.id}`);       // id 全局唯一
    if (write.kind === "entry" && write.parentId !== null &&
        !state.hasEntryId(write.parentId) && !transactionEntryIds.has(write.parentId))
      throw new Error(`Missing parent entry: ${write.parentId}`);        // 父必须存在
    transactionIds.add(write.id);
    if (write.kind === "entry") transactionEntryIds.add(write.id);
  }
}
    读懂这段： 写入只有四种 kind：entry（树节点）、usage（token 统计行）、value（set/delete 一个带类型地址的簿记值）、list（append/delete 一个列表值）。一个事务 = 一批写入共享连续 seq、一起成功一起失败。这套「单调 seq + 提交前校验」把 Session 变成了一本只增不改的账本：崩溃后从 JSONL 逐行重放事务即可重建任意时刻的状态，也能算出每个操作的 usage（SessionStats）。你自研时若需要「可恢复、可审计」，这套基调值得直接照抄。

    4.5Fork：从一棵树长出另一棵

    fork 有两种 scope：tree（整树克隆，适合「保存副本」）与 branch（只复制到某个 entry 为止的路径，开一条新主线）。它不再「产出 mutation 序列再重放」，而是先捕获一个源快照（全部 entries + 全部簿记值），再纯函数地算出目标快照，最后把目标快照一次性写成新存储。

    packages/agent/src/harness/session/fork.ts — createForkSnapshot（节选）
    typescriptexport function createForkSnapshot(source: ForkSourceSnapshot, options: ForkOptions): ForkDestinationSnapshot {
  const sourceTips = storedValuesInNamespace(source.scalarValues, branchTip(""));  // 所有分支 tip
  const { entryIds, destinationTips } = selectForkContents(sourceEntries, sourceTips, options);
  // branch scope：从 tip 沿 parentId 走到 entryId（position "before" 则停在它的父）
  for (const [branch, tipId] of destinationTips) {
    const configuration = findStoredValue(source.scalarValues, laneConfig(branch));
    store(branchTip(branch), tipId);                     // 复制分支 tip
    if (configuration !== undefined) {
      store(laneConfig(branch), configuration.value);    // 复制 lane 配置
      store(laneState(branch), { currentOperationId: null, lastOperationId: null, inbox: [] });
    }                                                    // lane 状态一律重置为空闲
  }
  for (const stored of source.scalarValues) {
    switch (classifyForkAddress(stored.address, options.scope, (entryId) => entryIds.has(entryId))) {
      case "copy": store(stored.address, stored.value); break;
      case "exclude":  case "reconstruct": break;   // op/pending/result 状态不带过去
    }
  }
  return { entries, scalarValues, nextSeq };
}
    读懂这段： fork 的关键分界是 classifyForkAddress 的三分类：copy（数据类值：session name、entry label 跟过去）、exclude（操作现场：pi.op.*、pi.pending.*、pi.result.* 不带——新会话必须从「空闲」开始）、reconstruct（lane 状态：上面已用「空闲初始值」重建）。配置（pi.lane.config）跟着 lane 走，所以 fork 出的会话保留你的模型选择。会话从父会话继承 parentSessionId，形成家谱。seq 不重排——副本从源树继承 seq，nextSeq 取自最大值 +1。

    4.6存储后端：内存 / JSONL / SQLite，共用一个 Storage 接口

    StorageBackedSession 是门面，真正读写靠 Storage 接口（commit/getEntries/getValue/scanBranch/scanEntries/scanUsage/...）。核心包自带两个实现：MemoryStorage（测试/示范用）与 JsonlStorage（生产默认）；SQLite 是独立包 @earendil-works/pi-session-backend-sqlite-node（packages/session-backends/sqlite-node），避免核心包硬依赖 node:sqlite。

    packages/agent/src/harness/session/in-memory-storage-state.ts — applyValidated（节选）
    typescript/**
 * Complete materialized session state for MemoryStorage and JsonlStorage.
 * This is intentionally unsuitable for database backends and long-running sessions
 * that may not fit in memory. Those backends should query indexed durable state
 * and update durable aggregates within each commit transaction.
 */
export class InMemoryStorageState {
  applyValidated(writes: readonly CommittedWrite[]): SessionStats {
    for (const write of writes) {
      switch (write.kind) {
        case "entry":
          this.entries.set(entry.id, entry);
          this.entriesBySeq.push(entry);            // seq 有序数组，供 scanEntries
          if (entry.type === "message") this.stats.messageCount++;
          break;
        case "value": {
          const key = physicalKey(write.namespace, write.key);  // namespace +  + key
          if (write.op === "delete") this.scalarValues.delete(key);
          else this.scalarValues.set(key, { address, value: write.value, seq: write.seq });
          break;
        }
        // usage / list 同理……
      }
      this.nextSeq = write.seq + 1;               // 高水位推进
    }
    return this.stats;
  }
}
    读懂这段： 注意注释里的自我定位：InMemoryStorageState 故意不适合数据库后端——真数据库应该「查索引 + 在事务里更新聚合」，而不是把整棵树 materialize 进内存。JSONL 后端（jsonl/storage.ts）复用同一个 InMemoryStorageState，但把每个事务序列化成一行 JSON 追加到文件（原子写：先写 .tmp 再 rename），启动时逐行重放恢复。SQLite 后端实现同一个 Storage 接口，核心逻辑与后端解耦。

    4.7查询：分支视角 vs 全局视角

    Session 提供两类查询：全局 findEntries（整片树，按 seq）与分支 branch(name).findEntries（从某个叶子沿 parentId 一路走到根）。分支行走落在存储的 scanBranch 里：

    packages/agent/src/harness/session/in-memory-storage-state.ts — scanBranch（节选）
    typescriptscanBranch(query: StorageBranchScan): Entry[] {
  const path: Entry[] = [];
  let entry = this.entries.get(query.start);
  if (entry === undefined) throw new Error(`Unknown branch start: ${query.start}`);
  while (entry !== undefined) {                // 叶子 → 根
    path.push(entry);
    if (entry.parentId === null) break;
    entry = this.entries.get(entry.parentId);
    if (entry === undefined) throw new Error("Corrupt branch: missing parent");
  }
  if (query.order === "oldestFirst") path.reverse();
  const stopped = [];
  for (const candidate of path) {
    stopped.push(candidate);
    if (candidate.id === query.stopAtId || candidate.type === query.stopAtType) break;
  }
  return stopped
    .filter((c) => query.type === undefined || c.type === query.type)
    .filter((c) => query.customType === undefined || c.customType === query.customType)
    .filter((c) => query.cursor === undefined || c.seq > query.cursor.seq)
    .slice(0, query.limit);   // （示意：limit/顺序分支略）
}
    读懂这段： 可停在指定 stopAtId 或 stopAtType（inclusive：命中节点本身也返回，例如「停在最近的 compaction」），再按 type/customType/cursor/limit 过滤。这个「分支行走」正是 第 5 章上下文构建的输入——它先拿到当前分支的全部 entries，再转换成发往 LLM 的消息。
    起点=叶子 e07，沿 parentId 上溯到根；遇到 compaction 即 stopAtType 停下（inclusive）
    yield 顺序（叶子→根）
    绿高亮=已 yield 的节点；橙框=stopAtType:"compaction" 命中后停下（inclusive：命中节点本身也被 yield）。这是第 5 章构建上下文时真正读到的分支子集。

    4.8为耐久而设的事务串行化与原子落盘

    4.4 讲了「追加式会话」保证数据一致，但没讲「并发写入谁来排队、进程死在半路怎么办」。两道防线都在 session 层：先是一个排他互斥线保证同一时刻只有一个读改写作业在飞：

    packages/agent/src/harness/session/mutation-line.ts — 完整源码
    typescript/** Serializes complete read-modify-write jobs for one Session. */
export class MutationLine {
  private tail: Promise<void> = Promise.resolve();
  private sealedError: Error | undefined;

  run<T>(operation: () => T | Promise<T>): Promise<T> {
    if (this.sealedError !== undefined) return Promise.reject(this.sealedError);
    const result = this.tail.then(() => operation());
    this.tail = result.then(() => undefined, () => undefined);
    return result;
  }

  seal(error: Error): Promise<void> {   // 关闭后拒绝一切新作业
    this.sealedError ??= error;
    return this.tail;
  }
}

    SessionMutation 的语义由此而来：beginMutation() 在 MutationLine 上排队拿到一个独占能力，它只允许一次 commit（第二次直接拒绝），end() 等待提交落地并释放互斥线。JSONL 后端再加最后一道防线——每个事务原子发布：先写 {path}.tmp，再 rename 覆盖正式文件；启动时逐行重放，不完整的最后一行（撕裂写）直接截断丢弃——半条事务永远不会被算数：

    packages/agent/src/harness/session/jsonl/storage.ts — open() 里的撕裂处理（节选）
    typescriptconst { lines, torn } = splitCompleteLines(content);
// ……校验 header（format 4：v/kind/id/storageVersion/createdAt/cwd）、逐行重放事务
if (torn) await publishFileAtomically(options.fileSystem, options.path, `${lines.join("\n")}\n`, context);
    为什么这值得抄？你的 Runtime 一旦要持久化到磁盘，「单一互斥线 + 单次 commit + 原子写 + 撕裂截断」这四件套就是崩溃一致性的全部基础。别指望 JSON.stringify 兜底——undefined 会被静默丢弃、NaN 会变 null、BigInt 直接抛错，每种都在无声地制造 bug。追加一行 + 启动重放的账本模型，让「恢复」退化成「再读一遍文件」。
    harness/session/session.ts · assertJsonSerializable（节选）
    export function assertJsonSerializable(value: unknown): void {
  const active = new WeakSet<object>();          // 记已访问，用于环检测
  const stack: JsonValidationFrame[] = [{ value }];
  while (stack.length > 0) {
    const frame = stack.pop()!;
    if ("exit" in frame) { active.delete(frame.exit); continue; }
    const candidate = frame.value;
    if (candidate === null || typeof candidate === "string" || typeof candidate === "boolean") continue;
    if (typeof candidate === "number") {
      if (!Number.isFinite(candidate)) invalidPayload("contains a non-finite number");
      continue;
    }
    if (active.has(candidate)) invalidPayload("contains a cycle");  // 环检测
    active.add(candidate);
    stack.push({ exit: candidate });
    // 对数组：拒绝稀疏数组、访问器、额外属性、符号键
    // 对对象：拒绝非平面对象、symbol 键、非可枚举/访问器属性、非有限数
  }
}

    它防的坑都很「阴」——只靠 JSON.stringify 是无法发现的：稀疏数组、访问器（getter）、携带符号键或额外属性的数组、非平面原型对象、NaN/Infinity、循环引用。这些一旦混进 JSONL，轻则污染读出结果，重则让整个会话文件读不回来。它用的是显式栈而非递归——深对象不会爆栈。

    为什么这值得抄？你的 Runtime 一旦要持久化到磁盘（本章 JSONL），「写前校验」就是第一道防线。别指望 JSON.stringify 兜底——undefined 会被静默丢弃、NaN 会变 null、BigInt 直接抛错，每种都在无声地制造 bug。一道显式校验器 + 引入即失败，成本极低、收益极高。

    4.9对自研与使用的启示

    要点 ① 别把历史当数组，把它当一棵可分叉树——代价是多一点抽象，收益是「回溯」「分支」「恢复」全部免费。② 内容（Entry 树）与簿记（类型地址值）分离，让你的「模型记录」不被运行噪音污染。③ 所有写入走同一套事务（entry/usage/value/list），存储分配 seq，保证单一事实来源。④ 后端走统一 Storage 接口，内存/JSONL/SQLite 随便换。⑤ 操作现场（op.meta/op.state/pending）与数据分开存——fork 时直接丢弃，崩溃时用它精确恢复。
