会话与存储模型：一颗 append-only 的会话树

Pi 的 Session 不是简单的「消息数组」，而是一片由 Lane / Entry / Record / Fact 构成的、可分叉、可恢复的树。下面展开这套模型的词汇表与不可变追加的纪律，是第 5～7 章的基石。
产品视角 「树形结构、可分享的会话历史。」 会话被存成树而非线性数组：用 /tree 跳回任意历史节点继续，所有分支住在同一个文件里；按消息类型过滤、给条目打书签；→ /export 导出 HTML，/share 上传 GitHub gist 拿可渲染的分享链接。本章就是这套「树」在源码里的实现。

4.1为什么不是「一个数组」

普通 Agent 用一个 AgentMessage[] 当历史。Pi 把它升级成一片追加式（append-only）有向树，原因是它要满足三个硬需求：

  • 分叉（fork）与多分支：一次「转向」（navigation）可能开出新分支，旧分支仍完整保留。
  • 崩溃恢复：每一步都落盘，进程死了能从最后一条 Record 精确恢复。
  • 元数据与消息解耦：模型换了、思考级别改了、操作开始了——这些不是「消息」，但要可查询、可审计。

所以它把「会话里发生的一切」分成两个名字空间：Entries（可进 LLM 的内容）与 Records（不可进 LLM 的运行簿记），外加Lanes（车道指针）与Facts（全局事实）。

4.1b交互沙盘：让会话树长起来

下面是一颗真实的最小 Session（复刻了 state.ts 的 seq / lane / parentId / log / walkToRoot / fork 语义）。按钮触发的每一步都是真实的 mutation——追加消息让节点挂在 main 车道的叶子上、追加 record只进簿记轨道不进树、回溯把叶子指针拨回历史节点（再追加即长出新分支）、fork复制一条路径长出第二棵树且 seq 从 1 重排。右侧 LogItem[] 是四种 kind 混排的同一本账本。

this.log · LogItem[] （seq↑）

    4.2四个词汇 + 一条纪律

    图 4.2：Session 的四类对象。核心纪律——一切都是追加写入，靠 seq 严格递增保证顺序与可恢复性。
    packages/agent/src/harness/session/types.ts — Entry 的基类与种类
    typescriptexport interface EntryBase {
  type: string;
  id: string;
  seq: number;        // 共享单调递增序号（由存储分配）
  parentId: string | null; // 追加那条 lane 的叶子 id（存储分配）
  timestamp: number;  // Unix 毫秒（存储分配）
}
export type Entry =
  | MessageEntry        // type: "message"   —— 真正的对话消息
  | ModelChangeEntry   // type: "model_change"
  | ThinkingLevelEntry // type: "thinking_level_change"
  | ActiveToolsEntry   // type: "active_tools_change"
  | CompactionEntry    // type: "compaction"
  | BranchSummaryEntry // type: "branch_summary"
  | CustomEntry;        // type: "custom" + customType
    读懂这段： seq 是全局共享的（不是 per-type），由存储分配，保证「事件的先后」唯一可判定。parentId 指向「追加那条 lane 当时的叶子」，从而把一个个 entry 串成树的分支。模型切换、思考级别切换都被记成 Entry——这样第 5 章的上下文构建才能「读到当前模型/思考级别」。

    4.3Lane：命名分支 + 叶子指针

    Lane 是一个「分支怎么长」的指针。默认只有 main。每个 lane 指向当前叶子 leafId；追加新 entry 时，parentId 自动取该 lane 的叶子。

    packages/agent/src/harness/session/state.ts — lane 的初始化与追加校验
    typescriptprivate readonly lanes = new Map<string, string | null>([["main", null]]);

// applyMutation 对 "entry" 的校验：必须链到 lane 的叶子
case "entry": {
  if (mutation.lane !== undefined) {
    const leafId = this.lanes.get(mutation.lane);
    if (mutation.entry.parentId !== leafId)
      invalid("does not chain to the lane leaf");   // 必须接到叶子
  }
  // 通过后：推进 lane 叶子 + 写入全局 log
  if (mutation.lane !== undefined) this.lanes.set(mutation.lane, mutation.entry.id);
  this.log.push({ kind: "entry", seq, entry: mutation.entry });
  break;
}
    读懂这段： 「追加 = 更新 lane 叶子」是一体的。moveLane(lane, to) 可以把一个 lane 的叶子移到已有 entry（等价于把「指针」拨回历史某点）——这是实现「回溯/分叉」的原语，而不是把历史删掉。第 7 章的 navigation 就靠它。

    4.4不可变追加的纪律与日志

    所有写入都必须满足 seq === sequence + 1（严格连续），这是恢复时「我到底写到哪了」的唯一依据。同时每个 mutation 都会 log.push(...)，形成一条可审计的 LogItem[]。

    packages/agent/src/harness/session/state.ts — 追加纪律 + log
    typescriptapplyMutation(mutation: SessionMutation): void {
  const seq = /* 从 mutation 里取 seq */;
  if (seq !== this.sequence + 1)
    invalid(`has non-consecutive seq ${seq}`);   // 必须严格 +1
  // ...按 kind 应用，并 this.log.push(...)
}
// log 的条目种类：entry / record / lane / fact（名册），全部有序
    读懂这段： 这套「严格递增 seq + 全量 log」把 Session 变成了一本只增不改的账本。崩溃后重放 log 就能重建任意时刻的状态，也能算出每个操作的 usage 与 token 统计（SessionStats）。你自研时若需要「可恢复、可审计」，这套基调值得直接照抄。

    4.5Fork：从一棵树长出另一棵

    fork 有两种 scope：tree（整树克隆，适合「保存副本」）与 branch（只复制到某个 entry 为止的路径，开一条新主线）。它通过「产出该状态的全部 mutation 序列」再在副本里重放来实现。

    packages/agent/src/harness/session/state.ts — fork 时产出 mutations
    typescriptcreateForkMutations(options: ForkOptions): SessionMutation[] {
  let copiedEntries, forkLanes;
  if (options.scope === "tree") {
    copiedEntries = this.findEntries({ order: "oldestFirst" });  // 全树
  } else {
    // branch：找到起点 entry，沿 parentId 一路往上收集路径
    copiedEntries = this.findEntriesOnBranch({ start: targetId, order: "oldestFirst" });
  }
  // 依次产出：entry mutations（重排 seq）→ lane mutations → name → labels
  return mutations;   // 新存储用同样的 applyMutation 重放，得到一棵独立树
}
    读懂这段： fork 的关键技巧是「把状态编码成 mutation 序列」，而不是复制内部字段——这保证了「任何存储后端都能用同一套 mutation 语义来 fork」。新副本的 seq 从 1 重新排，parentId 重新连锁。会话从父会话继承 parentSessionId，形成家谱。

    4.6存储后端：内存 vs SQLite

    Session 只是一个门面，真正读写靠 SessionStorage。核心包自带 InMemorySessionStorage（测试/示范用）；生产用 SQLite 后端（独立包 @earendil-works/pi-session-backend-sqlite-node，避免核心包硬依赖 node:sqlite）。

    packages/agent/src/harness/session/memory.ts — in-memory 追加
    typescriptasync appendEntry(newEntry: ProvisionedEntry, lane: string): Promise<TEntry> {
  const parentId = this.state.requireLane(lane);   // 取 lane 叶子当父
  const entry = {
    ...structuredClone(newEntry),
    parentId,
    seq: this.state.nextSequence,
    timestamp: Date.now(),
  };
  this.state.applyMutation({ kind: "entry", lane, entry });
  return structuredClone(entry);
}
    读懂这段： 注意「ProvisionedEntry」——调用方只提供「内容」（type/id/内容字段），而 seq/parentId/timestamp 这三个关键字段一律由存储分配，杜绝了「谁改了 seq」的作弊可能。SQLite 后端实现同一个 SessionStorage 接口，于是核心逻辑与后端解耦。

    4.7查询：分支视角 vs 全局视角

    Session 提供两类查询：全局 findEntries（整片树，按 seq）与分支 findEntriesOnBranch（从某个叶子沿 parentId 一路走到根）。

    packages/agent/src/harness/session/state.ts — 分支行走
    typescriptprivate *walkToRoot(start, bounds) {   // 生成器：叶子 → 根
  const visited = new Set<string>();
  let current = this.entriesById.get(start);
  while (current) {
    if (visited.has(current.id)) throw new SessionError("...", "Session branch contains a cycle");
    visited.add(current.id);
    yield current;
    if (current.id === bounds?.stopAtId || current.type === bounds?.stopAtType) break;
    current = this.entriesById.get(current.parentId);  // 沿 parent 上溯
  }
}
    读懂这段： 有环检测、可停在指定 id 或 type（例如「停在最近的 compaction」）。这个「分支行走」正是 第 5 章上下文构建的输入——它先拿到当前分支的全部 entries，再转换成发往 LLM 的消息。
    起点=叶子 e07，沿 parentId 上溯到根；遇到 compaction 即 stopAtType 停下
    yield 顺序（叶子→根）
    绿高亮=已 yield 的节点；橙框=stopAtType:"compaction" 命中后停下（inclusive：命中节点本身也被 yield）。这是第 5 章构建上下文时真正读到的分支子集。

    4.8为耐久而设的深度 JSON 校验

    4.4 讲了「追加式会话」保证数据一致，但没讲「写入前它凭什么敢保证你写的东西将来一定读得回来」。答案是 session.ts 里的 assertJsonSerializable——每次 commit 一个 entry/record 前，一个显式栈式遍历器会逐节点严查 JSON 可持久性：

    harness/session/session.ts · assertJsonSerializable（节选）
    export function assertJsonSerializable(value: unknown): void {
  const active = new WeakSet<object>();          // 记已访问，用于环检测
  const stack: JsonValidationFrame[] = [{ value }];
  while (stack.length > 0) {
    const frame = stack.pop()!;
    if ("exit" in frame) { active.delete(frame.exit); continue; }
    const candidate = frame.value;
    if (candidate === null || typeof candidate === "string" || typeof candidate === "boolean") continue;
    if (typeof candidate === "number") {
      if (!Number.isFinite(candidate)) invalidPayload("contains a non-finite number");
      continue;
    }
    if (active.has(candidate)) invalidPayload("contains a cycle");  // 环检测
    active.add(candidate);
    stack.push({ exit: candidate });
    // 对数组：拒绝稀疏数组、访问器、额外属性、符号键
    // 对对象：拒绝非平面对象、symbol 键、非可枚举/访问器属性、非有限数
  }
}

    它防的坑都很「阴」——只靠 JSON.stringify 是无法发现的：稀疏数组、访问器（getter）、携带符号键或额外属性的数组、非平面原型对象、NaN/Infinity、循环引用。这些一旦混进 JSONL，轻则污染读出结果，重则让整个会话文件读不回来。它用的是显式栈而非递归——深对象不会爆栈。

    为什么这值得抄？你的 Runtime 一旦要持久化到磁盘（本章 JSONL），「写前校验」就是第一道防线。别指望 JSON.stringify 兜底——undefined 会被静默丢弃、NaN 会变 null、BigInt 直接抛错，每种都在无声地制造 bug。一道显式校验器 + 引入即失败，成本极低、收益极高。

    4.9对自研与使用的启示

    要点 ① 别把历史当数组，把它当一棵可分叉树——代价是多一点抽象，收益是「回溯」「分支」「恢复」全部免费。② 内容（Entry）与簿记（Record）分离，让你的「模型记录」不被运行噪音污染。③ 存储分配 seq/parentId/timestamp，保证单一事实来源。④ 后端走统一接口，内存/SQLite 随便换。
