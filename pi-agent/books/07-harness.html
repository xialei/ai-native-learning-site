Harness 运行时骨架：谁在驱动这一切

★ 本站在意的另一半。第 3 章的循环只是一台「跑完就丢」的吞吐机；AgentHarness 是把它装进「可恢复、可分叉、可观察」的运行时。这一页看清 Pi 的契约 + 它的官方运行时实现——两者如今同住一个包。

7.1定位：Harness 在哪一层

先把 Harness 摆回整张图里。Pi 是三层包：

图 7.1：第 3 章的 agentLoop 与 Agent 类在 L1；agent-harness.ts 定义运行时契约（虚线框），runtime/ 目录给出官方实现（实心框，本章）；L2 的 AgentSession 是另一条自主实现线（第 8 章），不是 Harness 的实现者。

所以「Harness（马具）」在 Pi 里指的是：把 LLM 循环、会话存储、上下文、压缩、工具、持久化、恢复这一整套，收口成一个对象的那一层。它回答三个问题：

  • 操作：这次运行是要「run（回答）」、还是要「compaction（压缩）」、还是「navigation（导航/转向）」？
  • 驱动：谁推着操作往前走？——accept() 准入一个操作、drive() 沿着 13 个持久化状态叶子推到结算，任何一步的现场都写在存储里。
  • 韧性：过程崩溃了怎么恢复？中途被要求挂起（deferred）怎么续跑？
定位：packages/agent/src/harness/agent-harness.ts（622 行）是纯类型契约——Result 类型、事件载荷、钩子签名、AgentLane/AgentHarness 接口，一行实现代码都没有。实现是同包 runtime/harness.ts 里的 Harness 类（经 AgentHarness.create 导出），配 runtime/lane.ts 的 Lane 与 runtime/drive/ 的状态机。L2 的 AgentSession（第 8 章）是另一条自主实现线，不复用这套运行时。先记住这条，下面所有内容都是「契约长什么样 + 官方运行时怎么兑现」。

7.2操作状态机：三种操作

Harness 把「你想对这条会话做什么」抽象成三种操作。它们不是随便分的——恰好对应会话树的三种动作：

  • run = 在当前叶子往后长对话（prompt / skill / template 都是 run 的入口）
  • compaction = 把一段历史折叠成一个摘要节点（第 6 章）
  • navigation = 把车道指针挪到树上的另一个叶子（转向 / 分叉）
图 7.2：任一时刻一条 lane 至多有一个 operation；完成后回到 idle。三种操作共用同一套「准入 + 驱动 + 持久化」机制。

每种操作结束时都返回一张 Result，把"跑成什么样了"说清楚——注意这里没有异常：成功失败都是返回值：

packages/agent/src/harness/agent-harness.ts — 三种操作的 Result（78-103 行）
typescript// Result 本体（result.ts）：错误是值，不是 throw
export type Result<TValue, TError> =
  | { ok: true;  value: TValue }
  | { ok: false; error: TError };

export type RunResult = Result<
  OperationResultRecord | SuspendedRun,
  LaneBusy | InvalidMessage | UnknownSkill | UnknownTemplate | Closed>;
export type CompactionResult = Result<
  { compaction: OperationResultRecord; run?: OperationResultRecord | SuspendedRun },
  LaneBusy | NothingToCompact | Closed>;
export type NavigationResult = Result<
  { navigation: OperationResultRecord; run?: OperationResultRecord | SuspendedRun },
  LaneBusy | InvalidNavigation | UnknownTarget | Closed>;
export type ResumeResult = Result<OperationResultRecord | SuspendedRun, NothingToResume | Closed>;

// 成功侧的两种形状：
export interface OperationResultRecord {   // 结算记录（先落盘，再作为返回值）
  operationId: string;
  kind: "run" | "compaction" | "navigation";
  status: "completed" | "declined" | "aborted" | "failed";
  error?: OperationError;
  fromTipId: string | null;  tipId: string | null;
  startedAt: number;  endedAt: number;
}
export interface SuspendedRun {            // 挂起观察（可 resume）
  operationId: string;
  status: "suspended";
  deferred: DeferredHandle;
}
Result 侧形状含义
ok → OperationResultRecordstatus: completed / declined / aborted / failed一次已落盘的结算记录；declined = 无需做（如压缩时上下文已很短），failed 携带 OperationError
ok → SuspendedRun{ status: "suspended", deferred }主动挂起，等外部输入后再 resume()，携带 DeferredHandle（仅 run 会挂起）
errLaneBusy / NothingToCompact / NothingToResume / InvalidMessage / UnknownSkill / UnknownTemplate / InvalidNavigation / UnknownTarget / Closed带 _tag 的类型化错误（可 matchError 分发），不抛异常
读懂这段： 两个设计点。其一，「suspended」不在结算记录里——挂起时操作还没有 terminal status，返回的是独立的 SuspendedRun 观察（status: "suspended" + DeferredHandle），之后 resume() 接着跑；结算记录只在真正终态（completed/declined/aborted/failed）时产生。其二，compaction/navigation 的成功值还带一个 run?——结构性操作完成后可以顺带续跑一轮 run（runtime 的 continueAfterStructural），所以一次 compact() 可能同时结算出压缩记录和一轮 run 记录。这些 Result 类型描述的是"结果"；"为什么崩溃了也能拿到结果"，靠的是 7.4 的持久化状态。

7.3驱动模型：accept 准入 + drive 推进

一个 operation（比如一次 run）启动后，谁来推着它往前走？Harness 的答案是把这件事拆成两个独立的 lane 方法——先准入、再推进，中间任何时刻进程崩了都能从磁盘续上：

  • accept()：准入——校验请求（消息合法？skill 存在？lane 空闲？），把操作的意向（OperationMeta）和初始状态（pi.op.state = "starting"）写成持久化值，返回一个 OperationAdmission（operationId + kind + startedAt）。到这一步为止，一行 LLM 代码都没跑，但"我要做这件事"已经在盘上了。
  • drive()：推进——从磁盘读回当前状态叶子，执行对应的阶段逻辑，每个阶段结束都把下一个状态叶子落盘，循环直到操作结算。返回 DriveOutcome：要么 settled（拿到结算记录），要么 waiting（等重试间隔或等 deferred 轮询）。
图 7.3：prompt() 不是原子操作，而是「accept 准入 → drive 推进」的组合糖。accept 只写盘不动手；drive 沿着持久化状态叶子一步步推。两阶段之间、drive 循环的每一步之间，进程都可以死，恢复时从盘上最后一个状态叶子继续（见 7.4）。
packages/agent/src/harness/agent-harness.ts — accept / drive / DriveOutcome
typescript// 阶段一：准入。校验 + 写盘，返回 admission，不跑任何模型代码
accept(request: OperationRequest, context): Promise<OperationAdmissionResult>;
// OperationRequest = {kind:"prompt", prompt: string|AgentMessage|AgentMessage[]}
//   | {kind:"skill", name, additionalInstructions?}
//   | {kind:"prompt_template", name, args?}
//   | {kind:"compaction", customInstructions?}
//   | {kind:"navigation", targetId: string|null, options?}

// 阶段二：推进。按盘上的状态叶子逐步执行，直到结算或需要等待
drive(options: DriveOptions, context): Promise<DriveResult>;
// DriveOptions = {operationId, waitForRetry?: boolean, pollDeferred?: boolean}

export type DriveOutcome =
  | { kind: "settled"; outcome: OperationResultRecord }
  | { kind: "waiting"; operationId: string; reason: "retry"; notBefore: number }
  | { kind: "waiting"; operationId: string; reason: "deferred"; deferred: DeferredHandle };
读懂这段： 把「申请」和「施工」拆成两个方法，换来的是任意一点都能安全停下来：accept 之后进程死了，恢复时看到 pi.op.state = "starting"，照常从这续跑（甚至可以在创建 harness 时把所有未结算的 open 操作列出来，由外部决定谁续跑）；drive 每完成一个阶段就把下一个状态叶子写盘，所以重试等待、deferred 挂起都不需要内存里的任何东西活着。prompt()/skill()/compact()/navigateTree() 只是帮 accept+drive 拼好参数的糖（run 走 waitForRetry: true，resume 走 pollDeferred: true）。对自研者：这是比"手动步进"更实用的韧性模型——状态存盘 + 幂等推进，而不是暴露每一步的控制权。

7.4持久化的真正根基：13 个持久化状态叶子

上一节说 drive「每个阶段结束都把下一个状态落盘」——那到底落盘成什么？这才是 harness「可恢复」的命门，不是散落的标志位，而是一个带类型的状态值。Pi 把一次操作编排到任意时刻的现场，归纳成恰好 13 个状态叶子（源码注释原话："exactly 13 family-neutral dispatcher leaves"），整只存成一个持久化值 pi.op.state，旁边配一个描述操作意向的 pi.op.meta：

7.5AgentLane：一条"会话车道"的能力清单

上面三节的能力——操作、驱动、韧性——在代码里被收口成一个对象接口 AgentLane。每个 lane 是会话树上的一条独立"车道"（各有一个 tip 指针），"main" 是默认车道；它的方法就是「这条对话对象能请你做的一切」：

读懂这段： 这是「一个对象一把抓」的实用主义接口，30 余个成员。对自研者而言，不必拘泥每条，但要抓住主干：两段式操作（accept/drive）+ 高阶糖（prompt/compact/navigate）+ 队列类（steer/followUp/nextRun）+ 配置类（model/thinking/tools）+ 韧性类（resume/abort）+ 观察类（watch）。和常见 OO 设计不同的是它没有 session 暴露、没有手动步进——lane 只给你盘上事实的读取口和操作入口，不给内存对象的直通引用；这正是状态全部持久化之后的自然结果。这些方法全部由同包 runtime/lane.ts 的 Lane 类实现。

7.6钩子（Hooks）与事件（Events）

Harness 暴露两个订阅网：hooks（干预运行，如改上下文、拦截工具）与 events（观察运行）。两者都用「返回退订函数」的 API。实现侧（runtime/harness.ts）两者都是真注册表；钩子处理器抛错不会炸主流程——被捕获后以 handler_error 事件广播，运行继续。

packages/agent/src/harness/agent-harness.ts — HookMap（11 个钩子）与 Hooks/Events
typescriptexport interface HookMap {
  before_run:       { event: { prompt, resources };            result: { messages? } | undefined };
  before_drive:     { event: { operation: "run" | "compaction" | "navigation" };
                    result: void };                        // ★ drive 循环点火前（新钩子）
  before_run_end:   { event: { runId, messages };              result: { followUp? } | undefined };
  transform_context:{ event: { messages, systemPrompt };       result: { messages?, systemPrompt? } };
  before_request:   { event: { model, step, attempt, streamOptions };
                    result: { streamOptions? } | undefined }; // 每次 LLM 请求前
  before_payload:   { event: { model, payload };               result: { payload? } | undefined };
  after_response:   { event: { status?, headers?, message };   result: { message? } | undefined };
  before_tool:      { event: { toolCallId, toolName, args };
                    result: { args?, block?: {reason, terminate?} } | undefined };  // 可拦截工具
  after_tool:       { event: { toolCallId, toolName, args, content, isError, ... };
                    result: { content?, isError?, usage?, terminate? } | undefined };
  before_compaction:{ event: { reason, preparation, customInstructions? };
                    result: { decline?, compaction? } | undefined };
  before_navigation:{ event: { targetId, preparation, customInstructions? };
                    result: { decline?, summary? } | undefined };
}
export type HookName = keyof HookMap;

export interface Hooks {
  on<TName extends HookName>(name, handler, options?: { id?: string }): () => void;
}
export interface Events {
  on<TType extends HarnessEventType>(type, listener): () => void;
}
读懂这段： 对自研者：钩子是"策略注入点"，把可变策略（上下文改写、工具拦截、压缩触发）从主循环里抽出来。两个实现细节值得照着做：其一，钩子的 event/result 都是带类型的映射表（HookMap），Hooks.on 按名字自动推导 handler 签名——比 (payload: any) 强得多；其二，before_drive 挂在 drive 循环的第一步（7.3），是「操作就要开始推了」的统一哨口。events 则是被动观察（run_start / tool_end / compaction_end…），不干预、只广播；订阅回调收到的每个事件都带 lane 与可选 recovery 标记（recovery = 恢复路径重发的历史事件）。第 5 章见过的 transform_context 就接在 buildSessionContext 产出之后、发给模型之前。

7.7契约 vs 运行时：一个包里的两层

把 7.1 那条结论展开成清单。agent-harness.ts（622 行）是纯契约模块：Result 类型、事件载荷联合、HookMap、AgentLane/AgentHarness 接口，一行实现代码都没有。实现全在旁边的 runtime/ 目录，两者通过一个导出点对接：

packages/agent/src/harness/agent-harness.ts — 契约的唯一实现导出点（614-622 行）
typescriptexport interface AgentHarnessConstructor {
  create<TContext>(options: AgentHarnessOptions<TContext>, context: Context)
    : Promise<{ harness: AgentHarness<TContext>; open: OpenOperation[] }>;
}
// Runtime constructor for attaching the durable harness to one open session.
export const AgentHarness = { create: createAgentHarness } satisfies AgentHarnessConstructor;

createAgentHarness（runtime/harness.ts）做四件事：校验 tools/retry/compaction 配置 → 构造种子 lane 配置（model + thinkingLevel + activeToolNames）→ restoreSession 从盘上重建各 lane 状态 → 把恢复时发现的所有未结算操作作为 open: OpenOperation[] 一并返回。实现里的默认值长这样：

retryPolicy ?? { enabled: true, maxRetries: 3, baseDelayMs: 1_000, maxAgentDelayMs: 60_000 }

读懂这段： 「契约与实现同包」是个值得注意的仓库演化信号：agent-harness.ts 曾经只有类型（连 create 都是抛 SliceNotImplemented 的占位），如今 runtime/ 目录把接口逐条兑现——唯一的残留是 watchSession，它仍抛 SliceNotImplemented（session 级快照流尚未切开，lane 级的 watch() 已可用）。注意实现侧默认值和第 6 章之前讲的旧默认不同：重试默认开启（enabled: true, maxRetries: 3），且每轮退避延迟有 maxAgentDelayMs（默认 60 秒）封顶——没有这个上限，baseDelayMs * 2^(attempt-1) 在长时间故障里会指数膨胀到分钟级、小时级的等待。steering/followUp 默认 "all"（全部插队）而不是 "one-at-a-time"。另一个容易忽视的返回值是 open——创建 harness 时盘上若有上辈子没跑完的操作，会以 OpenOperation[] 形式交给你决定续跑与否（配合 7.3 的 accept/drive 模型）。L2 的 AgentSession（第 8 章）不在这条线上：它直接组合 Agent 类 + SessionManager，是并行于 runtime/ 的另一条实现，experimental 里只有两个客户端走 AgentHarness.create——session-worker（coding-agent 的服务化外壳）和 mini 的 worker（单进程精简 Agent 的后台）。

7.8对自研与使用的启示

要点 ① 定义显式的操作状态机（run/compaction/navigation 三种操作 + TerminalStatus 四种结算），胜过模糊的"处理请求"。② 错误是返回值，不是异常——Result<T, E> + 带 _tag 的类型化错误，让"lane 忙/没东西可压缩/目标不存在"都成为调用方要显式处理的值。③ 编排现场持久化为带类型的单值状态（13 个 pi.op.state 叶子 + effect_pending 核账家族），崩溃恢复 = 读回单值 + 一致性校验，不需要日志重放。④ accept 与 drive 分离——意向先落盘、施工按状态推进，任意点可死可续。⑤ 用钩子做策略注入（HookMap 带类型的 event/result），把可变逻辑移出主循环；钩子抛错降级为 handler_error 事件而非炸主流程。⑥ 快照走事件归约（reduceLaneSnapshot），观察者与执行者共享同一套事实。下一步看第 8 章——Pi 的生产 Agent 怎么在 Harness 之外直接组合 Agent + SessionManager 跑起来。
