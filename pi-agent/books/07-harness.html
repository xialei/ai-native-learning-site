Harness 运行时骨架：谁在驱动这一切

★ 本站在意的另一半。第 3 章的循环只是一台「跑完就丢」的吞吐机；AgentHarness 是把它装进「可恢复、可分叉、可观察」的运行时。这一页先看清 Pi 定义的接口契约——真实实现留到第 8 章。

7.1定位：Harness 在哪一层

先把 Harness 摆回整张图里。Pi 是三层包：

图 7.1：第 3 章的 agentLoop 在 L1；Harness 把它和会话/上下文/压缩一起收口成「运行时契约」（虚线框，本章）；L2 的 AgentSession 才是能顶着崩溃跑起来的实心实现（第 8 章）。

所以「Harness（马具）」在 Pi 里指的是：把 LLM 循环、会话存储、上下文、压缩、工具、持久化、恢复这一整套，收口成一个对象的那一层。它回答三个问题：

  • 操作：这次运行是要「run（回答）」、还是要「compact（压缩）」、还是「navigate（导航/转向）」？
  • 驱动：是 harness 自动一路跑到完（automatic），还是按「动作步进」一步步执行、每一步可被外部检查（manual）？
  • 韧性：过程崩溃了怎么恢复？中途被要求挂起（deferred）怎么续跑？
一句话定位：本章读的 packages/agent/src/harness/agent-harness.ts 是虚线框——它定义「运行时该长什么样」（类型、状态机、错误语义、默认值），绝大多数方法是占位 stub，直接抛 HarnessNotImplemented。真实能跑的实现是第 8 章的 AgentSession，它不继承 AgentHarness，而是按同一套 AgentLane 契约重新实现。先记住这条，下面所有内容都是「契约长什么样」。

7.2操作状态机：三种操作

Harness 把「你想对这条会话做什么」抽象成三种操作。它们不是随便分的——恰好对应会话树的三种动作：

  • run = 在当前叶子往后长对话（prompt / skill / template 都是 run 的入口）
  • compaction = 把一段历史折叠成一个摘要节点（第 6 章）
  • navigation = 把车道指针挪到树上的另一个叶子（转向 / 分叉）
图 7.2：任一时刻一条 lane 至多有一个 operation；完成后回到 idle。三种操作共用同一套「步骤执行 + 持久化」机制。

每种操作结束时都返回一个 Outcome，把"跑成什么样了"说清楚：

packages/agent/src/harness/agent-harness.ts — 三种操作的 Outcome
typescriptexport type RunOutcome =
  | { kind: "completed"; leafId; finalEntryId; finalMessage: AssistantMessage }
  | { kind: "aborted";  ... }
  | { kind: "failed";   ... error: OperationError; finalMessage? }
  | { kind: "suspended"; ... deferred: DeferredHandle };  // 被挂起，可 resume

export type CompactionOutcome =
  | { kind: "completed"; leafId; entry: CompactionEntry }
  | { kind: "declined" | "aborted"; leafId }
  | { kind: "failed"; leafId; error };

export type NavigationOutcome =
  | { kind: "completed"; newLeafId; summaryEntry? }   // 转向到哪个叶子
  | { kind: "declined" | "aborted"; leafId }
  | { kind: "failed"; leafId; error };
Outcome含义谁会产生
completed正常跑完，结果已落盘三种操作
aborted被外部 abort() 中止三种操作
failed出错终止，携带 OperationError三种操作
suspended主动挂起，等外部输入后再 resume()，携带 DeferredHandlerun（关键）
declined无需做（如压缩时上下文已很短）compaction / navigation
读懂这段： 「suspended」是一个重要拐点——run 不一定要一次跑完，它可以在「需要等待外部输入」（deferred）时暂停，把现场信息（DeferredHandle）存下来，之后 resume() 接着跑。注意：Outcome 描述的是"结果"，而"为什么能 resume"靠的是下一节讲的 record 日志——光有 Outcome 还不够，真正的现场是日志重放出来的。

7.3驱动模式：automatic vs manual，以及"两套接口怎么连"

一个 operation（比如一次 run）启动后，谁来推着它往前走？Harness 定义两种驱动：

  • automatic：调了 prompt() 后，harness 自己一路推到 outcome 返回。
  • manual：外部用 peekAction() 看下一步是什么、用 executeAction() 执行一步，每步之间可以检查快照、改参数、甚至中止。

这是最容易绕晕的地方，所以一次讲透。prompt() 和 peekAction()/executeAction() 在契约里是并列的两条 lane 方法——它们不是替代关系，而是同一件事的两个分辨率：

图 7.3：prompt() 是高阶入口，内部被拆成一串原子 ActionInfo。automatic 把这串动作自动跑完；manual 让外部在动作之间介入。在契约层这两套是并列抽象——Pi 实现层（第 8 章）用的是更底层的 record 日志来达成等价的"先持久化再执行"。
packages/agent/src/harness/agent-harness.ts — Action 步进接口
typescript// manual 驱动：先看下一步是什么，再执行它
peekAction(): Promise<ActionInfo | undefined>;       // 只"看"不执行
executeAction(): Promise<ActionInfo | undefined>;   // 执行一步
runToCompletion(): Promise<void>;                 // 自动模式：peek→execute 循环到 done

// ActionInfo 的种类（一次"原子"步骤）：
export type ActionInfo =
  | { kind: "append_entry"; ... }        // 追加一条信息
  | { kind: "append_record"; ... }       // 追加一条簿记
  | { kind: "move_lane"; ... }           // 移动 lane 指针（分叉）
  | { kind: "try_finish_run"; ... }      // 尝试结束 run
  | { kind: "execute_tool"; ... }       // 执行一个工具
  | { kind: "stream_assistant"; ... }   // 调 LLM 生成一轮
  | { kind: "fetch_deferred" | "cancel_deferred"; ... }
  | { kind: "hook"; name };              // 跑一个钩子
  | { kind: "sleep"; delayMs };          // 等待重试间隔
  | ...
读懂这段： 把「一次 turn」拆成无数个「可观察、可暂停的原子动作」，是 manual 模式的精髓——它让"持久化"与"执行"解耦：每个动作都先持久化再执行；若是 manual，外部可在动作间检查快照、甚至中止。automatic 只是「不断地 peek→execute」直到 done 的糖。注意：这套步进接口在契约里定义了，但生产 AgentSession（第 8 章）目前走 automatic 路径，用的是更底层的 record 日志（见 7.4）来表达同等的"先落盘再动手"。你自研时选哪套都行，关键是让每一步都可被持久化与重放。

7.4持久化的真正根基：Record 日志

上一节说"每个动作都先持久化再执行"——那到底持久化成什么？这才是 harness「可恢复」的命门，不是 Outcome，而是 append-only 的 record 日志。Pi 把一次操作里的每个关键动作，都写成一条不可变记录追加到会话里：

packages/agent/src/harness/session/types.ts — LaneRecord 的种类
typescriptexport interface OperationStartedRecord extends RecordBase {
  type: "operation_started";            // 操作开始：intent 是 run/compaction/navigation
  intent: { kind: "run" | "compaction" | "navigation"; ... };
}
export interface StepAttemptRecord extends RecordBase {
  type: "step_attempt";                 // 一次 LLM 调用尝试（assistant/compaction/branch_summary）
  step: "assistant" | "compaction" | "branch_summary"; attempt: number;
}
export interface ToolStartedRecord  { type: "tool_started";     ... }   // 工具开始（带 effectiveArgs、resultEntryId）
export interface QueueEnqueuedRecord{ type: "queue_enqueued";  ... }   // steer/followUp/nextRun 入队
export interface QueueCancelledRecord{ type: "queue_cancelled"; ... }   // 撤销一条排队消息
export interface WriteDeferredRecord{ type: "write_deferred"; ... }   // 挂起时把待写内容存下
export interface AbortRequestedRecord{ type: "abort_requested";... }   // 请求中止
export interface OperationFinishedRecord {
  type: "operation_finished"; outcome: "completed" | "aborted" | "failed" | "declined";
}
图 7.4：恢复 = 把 record 日志按 seq 重放，用纯函数 reduceLaneState() 算出当前该停在哪个动作。所以"现场"从不在内存里凭空维护，而是可从日志重算。
读懂这段： 这才是 suspended → resume() 能成立的真正原因——挂起时，已完成的每一步都已在日志里；恢复时重放日志，reduceLaneState()（reducer.ts，纯函数、不碰 IO）告诉你"上次停在 step_attempt 之后、工具还没开始"，于是从这里接着跑。先写日志再动手 = 崩了也不丢现场。对自研者：这是整个 harness 最值得抄的一条——用 append-only 日志 + 纯函数重放做状态机，远比在内存里维护易失状态可靠。第 8 章会看到 AgentSession 怎么把它接上真实的 LLM 调用与工具执行。

7.5AgentLane：一条"会话车道"的能力清单

上面三节的能力——操作、驱动、韧性——在代码里被收口成一个对象接口 AgentLane。Main lane 是默认车道；它的方法就是「这条对话对象能请你做的一切」：

packages/agent/src/harness/agent-harness.ts — AgentLane 方法一览
typescriptexport interface AgentLane {
  name: string;                       // "main"
  prompt(...): Promise<RunResult>;        // 发起一轮 run
  skill(name, extra): Promise<RunResult>;  // 用技能发起 run
  promptFromTemplate(name, args): Promise<RunResult>;
  compact(...): Promise<CompactionResult>;  // 触发压缩
  navigateTree(targetId, opts): Promise<NavigationResult>; // 转向/分叉
  resume(): Promise<ResumeResult>;        // 续跑挂起的操作
  abort(): Promise<AbortResult>;          // 中止当前操作
  steer / followUp / nextRun(msg): Promise<QueueResult>;  // 三队列
  cancelQueued(entryId): ...;
  recordUsage(usage, opts): ...;         // 把 LLM 用量记进会话
  waitForIdle / runWhenIdle(cb): ...;
  peekAction / executeAction / runToCompletion(): ...;  // 驱动
  getModel / setModel / getThinkingLevel / setThinkingLevel / ...;
  getActiveTools / setActiveTools(...): ...;
  readonly session: SessionTree;    // 对本 lane 的会话视图
  watch(): Promise<WatchHandle<LaneSnapshot>>;  // 订阅快照
}
// 注意：hooks / events / getTools / setTools 不在 AgentLane 接口里，
// 它们是 AgentHarness 类自己的成员（见 7.7）。
读懂这段： 这是「一个对象一把抓」的实用主义接口——prompt 走 run、压缩、转向、队列、恢复、驱动、状态读写、订阅都在一条消息里。对自研者而言，不必拘泥每条，但要抓住主干：操作类（run/compact/navigate）+ 队列类（steer/followUp/nextRun）+ 状态类（model/thinking/tools）+ 韧性类（resume/abort）+ 观察类（watch）。注意这些方法在基类里全是 stub（抛 HarnessNotImplemented），真正实现它们的只有第 8 章的 AgentSession。

7.6钩子（Hooks）与事件（Events）

Harness 暴露两个订阅网：hooks（干预运行，如改上下文、拦截工具）与 events（观察运行）。两者都用「返回退订函数」的 API。一个设计细节值得点破：基类用 UnavailableRegistry 兜底，让 hooks.on 永远不会"静默失效"——在实现就绪前注册钩子会立刻抛 HarnessNotImplemented，harness 关闭后改抛 HarnessClosed。

packages/agent/src/harness/agent-harness.ts — HookName 与 Hooks/Events
typescriptexport type HookName =
  | "before_run"       // run 开始前（可拦截/补消息）
  | "before_resume"    // resume 前（补缺失的工具/模型）
  | "before_run_end"   // run 结束前
  | "transform_context" // 改上下文（接 buildSessionContext）
  | "before_request"   // 每次 LLM 请求前
  | "before_payload" / "after_response" // payload 前后
  | "before_tool" / "after_tool" // 工具前后
  | "before_compaction" / "before_navigation";

export interface Hooks {
  on(name: HookName, handler, opts?): () => void;  // 返回退订函数
}
export interface Events { on(type, listener): () => void; }
读懂这段： 对自研者：钩子是"策略注入点"，把可变策略（上下文改写、工具拦截、压缩触发）从主循环里抽出来。UnavailableRegistry 的好处是「契约先行」时不必伪造一个空的钩子实现——注册即报错，逼着真正实现（第 8 章）把它串进每次运行。events 则是被动观察（run_start / run_end），不干预、只广播。

7.7基类 vs 实现：职责划分小结

把 7.1 那条结论展开成清单。基类 AgentHarness（implements AgentLane）的职责是契约 + 默认值 + 错误语义，它把方法分成三类：

  • 纯 stub（抛 HarnessNotImplemented，关闭后抛 HarnessClosed）：prompt / skill / compact / navigateTree / resume / abort / steer / followUp / nextRun / peekAction / executeAction / runToCompletion / watch……——这些是 7.2~7.5 讲的"运行时行为"，留给第 8 章实现。
  • 真实现的 getter/setter：getModel/setModel、getActiveTools/setTools、getRetryPolicy、getCompactionSettings、getStreamOptions 等——纯字段读写，不涉及运行时编排，基类就顺手做了。
  • 默认配置：构造时给诚实又合理的默认值，让"接口先立住"。
packages/agent/src/harness/agent-harness.ts — 基类的默认配置
typescript// 基类构造时给了诚实又合理的默认值：
this.retryPolicy = options.retry ?? { enabled: false, maxRetries: 0, baseDelayMs: 1000 };
this.compactionSettings = options.compaction ?? {
  enabled: true, reserveTokens: 16384, keepRecentTokens: 20000 };  // 同第 6 章
this.steeringMode = options.steeringMode ?? "one-at-a-time";
this.followUpMode = options.followUpMode ?? "one-at-a-time";
读懂这段： 真实 AgentSession（第 8 章）按 AgentLane 契约独立实现那些 stub 方法，把 transform_context 钩子接到 buildSessionContext、把 run 接到 7.4 的 record 日志状态机。这也呼应了第 1 章：先契约后实现——基类即使不实现也能立住接口，并给出一份能直接复用的默认配置。

7.8对自研与使用的启示

要点 ① 定义显式的操作状态机（run/compact/navigate + outcome），胜过模糊的"处理请求"。② 把运行拆成可持久化的原子动作，支撑手动驱动与崩溃恢复。③ 用 append-only record 日志 + 纯函数重放（reduceLaneState）做状态机——现场可从日志重算，而不是在内存里维护易失状态。④ 用钩子做策略注入，把可变逻辑移出主循环；用 UnavailableRegistry 让未实现的钩子"注册即报错"而非静默失效。⑤ 默认值先行——基类即使不实现也能立住接口。下一步看第 8 章，Pi 如何把这些变成真能顶着崩溃跑起来的生产 harness。
