Pi vs LangGraph：两个 Agent 运行时的逐项对比

两条路线的根分歧是什么——「Pi 这么做」等于「只能这么做」吗？六个维度（哲学/能力/场景/体验/灵活性/生产）上，各自把复杂度放在哪里、牺牲了什么？我的场景该选哪条？本章不评高下，把两者并排放——理解了取舍，你自研时才选得对。
定位 「LangGraph 给你一张可拼的图；Pi 给你一条可改的流水线。」 LangGraph 把控制流外化成声明式的节点与边，状态是图里流转的字典；Pi 把控制流内化成一段写死的顺序流程，状态是 append-only 的会话树。前者赢在「可拼可组合」，后者赢在「可读可改、崩溃即重生」。→ 下面六个维度逐一拆开看。

15.1设计哲学与核心抽象

两者的根分歧在这里：Agent 的「逻辑」到底该用什么形状表达。

LangGraph：图是第一公民声明式图

LangGraph 的核心抽象是 StateGraph——你用 add_node 注册计算单元（一个函数：读状态、返回状态更新），用 add_edge / add_conditional_edges 连控制流，最后 compile() 出一个 CompiledStateGraph。状态（State）是节点间流转的结构化字典，合并语义由 reducer 决定（如 Annotated[list, add_messages] 幂等追加、operator.add 累加、默认 last-write-wins）。

它刻意把循环「打开」给你看：ReAct 的「调模型↔调工具」不是黑盒 while，而是两个节点 + 一条条件边。理由很朴素——黑盒循环在「先做 A、人审核不过回 A、过了进并行子任务」这类有结构流程里很难表达，而图天然描述分支/循环/并行/子图嵌套。

Pi：流程是第一公民固化流程

Pi 的核心抽象是 Harness——把 LLM 循环、会话存储、上下文、压缩、工具、持久化、恢复收口成一个对象。但这个对象怎么跑？第 8 章看过：AgentSession.prompt() 就是一条写死的顺序方法体（命令解析 → 钩子 → 展开 → 校验 → 压缩预检 → before_agent_start → _runAgentPrompt），韧性（重试/压缩/续跑）硬编码在 _handlePostAgentRun 的 while 里。系统提示词只决定「模型怎么想」，这段流程才决定「运行时怎么跑」。

状态不是字典，而是一棵 append-only 会话树（Entry 树 + lane 簿记值）。控制流不靠你拼边，而靠 harness 提供的三种操作：run（往后长对话）/ compaction（折叠历史）/ navigation（挪指针到别的叶子）。契约层（AgentHarness）是一个 interface + { create: createAgentHarness } 工厂，实现在同包的 runtime/harness.ts；生产层的 AgentSession 则不实现这套接口，而是直接组合 Agent 类 + SessionManager 另起一条实现线。

根分歧：LangGraph 让你「声明结构，框架负责跑」；Pi 让你「读一段流程，它就那么跑、你按需改」。前者把复杂度交给图的拓扑设计，后者把复杂度交给流程的编排代码。哪条更顺手，取决于你要的 Agent 是「很多条分叉的流程」还是「一条主干 + 大量扩展点」。

15.2核心能力与生态

抽象不同，长出来的能力树也不同。下面把两边「开箱能干什么」对齐看。

能力PiLangGraph
控制流表达 固化流程 + 三操作状态机（run/compact/navigate）+ outcome（completed/aborted/failed/suspended/declined）。想加分支？改 prompt() 方法体或挂钩子。 节点 + 边 / 条件边 + Command(goto=) 路由 + Send 扇出做 map-reduce 并行。recursion_limit 兜底防死循环。
状态模型 append-only 会话树：Entry（内容）+ Record（簿记），seq/parentId/timestamp。分支是树形结构的一等公民（/tree、/fork）。 结构化字典（TypedDict/Pydantic）+ reducer 合并。分支靠 thread + 时间旅行分叉，不是原生树。
多智能体 故意不内置——「No 子 Agent」。经 tmux 拉起 Pi 实例，或写扩展自建。把可观测性留给操作系统。 一等公民——子图即节点，Supervisor / Hierarchical / Swarm 三范式，Command(goto=) 在子 agent 间接力。
持久化 append-only Entry 树 + lane 簿记值（tip/config/state/op.meta/op.state 逐次落盘），崩溃后从存储恢复（restoreSession → restoreLaneState 校验 meta/state 一致性）（第 7 章 §7.4）。运行中快照另有 reduceLaneSnapshot 纯函数增量维护（事件→快照），非全量存档。 Checkpointer 每 superstep 存完整状态快照，按 thread_id 分桶。InMemory/Sqlite/Postgres 后端。
人机协同 HITL suspended outcome + DeferredHandle + resume()；运行中 steer/followUp 队列插话。无内置「权限弹窗」。 interrupt()（首次抛异常、恢复时返回 resume 值、节点重跑）+ interrupt_before= + Command(resume=)。依赖 checkpointer。
上下文管理 第 5/6 章的主题：buildSessionContext 把 entries 投影成 messages、自动压缩、分支摘要、AGENTS.md/SYSTEM.md 注入、Skills 按需载入。 状态里的 messages 由 add_messages 累积；窗口管理靠自建节点裁剪或 prebuilt 的 trim。Store 做跨会话长期记忆。
Provider/模型 pi-ai 抽象层：15+ Provider、数百模型，/model 会话中途切，流式代理 + prompt caching + usage 累积（第 10 章）。 模型由 langchain 的 BaseChatModel 抽象，bind_tools 接工具；create_agent（原 create_react_agent，已迁往 langchain.agents）支持传 (state, runtime) -> BaseChatModel 做基于状态的动态选模型，但没有「会话中途用斜杠命令热切 + 缓存策略」这种产品级体验。
读懂这张表： 能力上两者「该有的都有」，但长法不同。LangGraph 的多智能体、并行扇出、子图嵌套是框架原生——你拼图就行；Pi 这些要么「故意不做」（子 Agent），要么靠「会话树的天然分叉」（navigation）或扩展。反过来，Pi 的上下文工程（压缩/分支摘要/指令注入）和会话中途热切模型是产品级深度，LangGraph 需要你自己补节点。生态差异由此而来：LangGraph 长在「编排范式」丰富，Pi 长在「单 Agent 跑得久、跑得稳」。

15.3适用场景与复杂度

抽象差异直接决定「什么样的任务在哪边更顺手」。LangGraph 的选型思路可以概括成一棵从轻到重升级的决策树：单轮问答→直接调 LLM；带工具助手→LangChain 的 create_agent 预置 Agent；需要定制控制流→StateGraph 自建；多角色协作→多智能体。Pi 没有这棵树，因为它不替你决定工作流——它给你一条主干流水线 + 扩展点，你按需改。

图 15.3：复杂度生长方向不同。LangGraph 纵向升级——任务越复杂，图的节点/边/子图越多；Pi 横向扩展——主干流程不变，复杂度塞进 Extensions / Skills / 钩子。
怎么选
  • 选 LangGraph：任务天然是「多角色分工」「并行扇出」「先规划再分步执行」「带审核回环」这类有结构的复杂流程——图能干净地表达拓扑，且每个分支可观测、可中断、可恢复。
  • 选 Pi：任务核心是「一个 Agent 长时间跑、跑得稳、能崩溃重生、上下文要精细控制」——你要的是一条被工程验证过的主干，外加按需扩展，而不是自己拼一张大图。编码 Agent、CLI 助手、可嵌入的运行时内核是它的甜区。

15.4开发体验与学习曲线

「能跑起来」和「跑得舒服」是两回事。两者的上手路径差别很大。

LangGraph：三行起手，按需下钻平缓升级

最爽的入口是 create_agent(model, tools)（from langchain.agents import create_agent，即原 LangGraph 的 create_react_agent——该名字已标记 deprecated，官方文档现把 LangGraph 定位为 low-level 编排运行时，并把初学者引到 LangChain 的高层 agents）——三行起一个能调工具的 Agent，返回一个 CompiledStateGraph。它本质是预置好的「LLM 节点↔工具节点」循环图。当你需要更多控制，下钻到 StateGraph 手拼节点和边——关键的是，prebuilt 和自建共享同一套原语（ToolNode、MessagesState、add_messages），所以从 A2 升到 A3 不是推倒重来，而是「把现成循环拆开加节点」。这条平缓升级路径是 LangGraph 学习曲线最大的优势。

但要付的税是心智模型多：State/Reducer/Channel/Conditional Edge/Command/Send/interrupt/checkpointer/store——每个都是独立概念，reducer 写错还会「状态静默丢失」（最隐蔽的坑），社区甚至把「自建 Agent 四大杀手」单列出来警示。

Pi：读一段流程，改一个点流程可读

Pi 的上手不是「拼图」而是「读流程」。你打开 agent-session.ts，prompt() 是一条从上到下的方法体——没有图的拓扑要脑补，控制流就是你读到的顺序。想加行为？挂钩子（beforeToolCall/afterToolCall/before_agent_start…）或写扩展，不动主干。

契约/实现分层也利于学习：第 7 章的 AgentHarness 是接口契约的虚线框（interface + 工厂，告诉你「运行时该长什么样」），同包 runtime/ 里就有实心实现，第 8 章的 AgentSession 是生产层的另一条实心实现线（不走 runtime/）。读虚线框建立心智模型，读实心框看落地，路径清晰。代价是：想改主干流程本身（比如插入一个全新的操作类型）要动 prompt() 的硬编码，比加一个 LangGraph 节点重。

维度PiLangGraph
第一个能跑的 Agent装好即用（TUI 开箱），但要理解 harness 分层LangChain create_agent 三行
从简单到复杂的路径挂扩展点（横向），主干不变prebuilt→StateGraph→多智能体（纵向），原语共享
核心心智模型一条流程 + 三操作 + 会话树 + durable 操作状态图 + 状态/reducer + 边/条件边 + checkpoint

15.5灵活性与控制力

「灵活」是个含混的词——得拆成「能组合的灵活」和「能直改的控制」两种，两边各自赢一面。

LangGraph：组合的灵活拓扑自由

图抽象的赢面在组合：任意节点 + 任意边 + 条件边回环 + 子图嵌套 + Send 并行，你能拼出 Reflection、Plan-Execute、RAG、HITL、多智能体任意组合——这些模式可自由组合，把对应节点和条件边一起塞进同一张 StateGraph 即可。控制流的形状完全由你定义，框架只负责按拓扑执行 + 每步存快照。这是「声明式」的红利：你描述「要什么结构」，不用描述「怎么一步步跑」。

但代价是对单步的精细控制较弱：你想在「模型返回后、工具执行前」插一段自定义逻辑，得专门加一个节点 + 改边；流程细节被分散到图的拓扑里，而不是集中在一处可读的方法体。

Pi：直改的控制流程可改

Pi 的赢面在直改：因为流程是写死的方法体，你能在任意两步之间插入逻辑——它就在 prompt() 那行代码的位置，看得见、改得动。钩子系统（HookMap 全量类型化映射，未注册的事件名在编译期就过不了类型检查；handler 出错转成 handler_error 事件而非静默失效）把可变策略移出主干，但主干本身对你是完全可读可改的源码。Pi 狂热追求可扩展，是为了「不必替你规定工作流」：别的工具烤进内核的（子 Agent、计划模式、权限弹窗、MCP），你都能自己搭或装包。

代价是组合的灵活度低：没有原生的多智能体拓扑、没有 Send 式并行扇出、子图嵌套要靠 tmux 或扩展自己组织。要拼一张「研究员→写手→审稿」的多角色图，Pi 不如 LangGraph 顺手——它更擅长「一个 Agent 把一件事跑深」。

概括：LangGraph 给你「积木式框架」——组合自由、拓扑可拼，但单点控制要绕到节点层面；Pi 给你「一台可改的机器」——单点控制直接改源码，但拼大型拓扑不是它的强项。前者是「框架替你跑结构」，后者是「你直接改流程」。

15.6生产就绪性

「能上线」是真金白银的考验。这里聚焦三件最硬的：崩溃恢复、持久化、可观测。

生产维度PiLangGraph
崩溃恢复机制 append-only 会话树 + durable 操作状态。每个动作先以事务写入 JSONL（entries + lane 簿记 + op.meta/op.state）再动手；崩溃后 restoreSession 读回各 lane 的 tip/config/state，校验 op.meta 意图与 op.state 相位一致后，从「上次停在哪个 boundary」接着跑（drive 的 checkpoint/resume 状态机）。「先写日志再动手 = 崩了也不丢现场」（第 7 章 §7.4）。 每步完整状态快照。Checkpointer 在每个 superstep 后存整个 state（channel 值 + 版本 + pending writes），按 thread_id 分桶。崩溃后从最近 checkpoint 恢复。HITL 的 interrupt() 也依赖它跨进程续跑。
持久化形态 会话存成树形 JSONL（Entry + Record），单文件含全部分支；写侧只管追加，完整性校验放在读取侧——启动重放时逐行验序、类型、safe integer，脏数据当场拒载而不是带病上线（第 4 章 §4.8）。内存 / SQLite 后端。 InMemorySaver（仅测试）/ SqliteSaver（单机）/ PostgresSaver（生产、并发连接池）。Store 做跨会话长期记忆（namespace+key）。get_state_history 时间旅行、可从历史 checkpoint 分叉新线。
恢复粒度 动作级——13 个持久化操作状态叶子精确记录「停在哪一步」（如 tools、deferred.suspended），drive 状态机按相位续跑。SuspendedRun + DeferredHandle 支持主动挂起后 resume()。 节点级——从某 superstep 的完整快照恢复，interrupt() 恢复时节点会从头重跑（故铁律：interrupt 必须在副作用之前）。
韧性编排 运行后收敛三段式（第 8 章 §8.5）：重试优先于压缩、压缩优先于兜底续跑，硬编码在 _handlePostAgentRun。_willRetryAfterAgentEnd 回扫最后一条 assistant 判可重试错误。 节点级 RetryPolicy(max_attempts=, retry_on=) 挂 add_node；图级 recursion_limit 兜底抛 GraphRecursionError。两者都要配。
可观测 JSON event stream / RPC 模式把内部事件（agent_start/turn_start/message_update…）结构化外发；同内核四种形态（交互/print/RPC/SDK）都可观测可直连（第 14 章）。 内建 tracing + LangSmith 平台看完整调用链；stream() 多模式（values/updates/messages/debug/custom）既拿状态增量也逐 token 流式。
并发秩序 stdout 接管串行化（防 TUI 花屏）+ realpath 归并的文件写互斥锁（同文件串行、异文件并行）（第 9 章 §9.6）。工程细节就地解决并发抢资源。 原生 async + 并发节点 + 超时控制；并行靠 Send 扇出 + reducer 聚合，框架在 superstep 边界同步。
两种「稳」的哲学 Pi 的稳靠「先写日志再动手」——每个动作先以事务写入 append-only 的 JSONL（entry + op.meta/op.state），崩溃后从存储恢复到「上次停在哪」的 boundary 精确接回，现场不在内存里凭空维护。LangGraph 的稳靠「快照存档」——每步存完整状态，恢复即读档，时间旅行还能回到任意历史点分叉。两者都做到了生产级崩溃恢复，但路径相反：Pi 逐事务写日志（轻量、boundary 级精确），LangGraph 存档（重量、节点级完整）。选哪个，看你更信任「日志确定性」还是「快照完备性」。

15.7收尾：六维总览与选型决策

把六个维度压成一张速查表。每格只放最直接的对照，方便你快速定位「我的场景更偏哪边」。

维度PiLangGraph
设计哲学固化流程 + 会话树；流程是第一公民声明式图 + 状态字典；图是第一公民
核心能力上下文工程深、模型热切、崩溃重生强；多智能体故意不做多智能体/并行/子图原生；上下文管理要自补节点
适用场景单 Agent 长跑稳跑、CLI/可嵌入内核、编码助手多角色分工、并行扇出、有结构的复杂流程

选型心法 别问「哪个更好」，问「我的复杂度长在哪」。如果你的复杂度是「流程拓扑复杂、多角色多分支」——选 LangGraph，图能干净表达，且每步可观测可恢复。如果你的复杂度是「单 Agent 要跑得久、上下文要精细、崩溃要能接回、还要能嵌入我的产品」——选 Pi，它把这条主干工程化到了极致，外加扩展点留给你。两者不是替代关系，而是两条路线：LangGraph 是「编排框架」，Pi 是「运行时内核」。理解了这层，你自研时才不会把「该拼图的需求」硬塞进「该改流程的内核」，反之亦然。
收束： 本站通篇在教你「Pi 这么做」，这一章把它和「另一种做法」并排，不是为了分高下，而是为了让你看清设计取舍。能看清取舍的人，自研 Runtime 时才敢做选择——而不是把别家的烤进内核、又抄不透其理由。Pi 那句口号「There are many agent harnesses, but this one is yours」的真意，正在于此。
