上下文压缩：摘要、切割点，与一次压缩如何接替上一次

何时触发？token 用量怎么估——provider 报过的 usage 在历史被改写之后还算数吗？切割点怎么选才不把对话拦腰截断？摘要怎么生成、失败怎么恢复？这四问串起本章。

6.1历史太长，丢什么、留什么

Compaction 的定义一句话：当上下文快满时，把「较早的历史」交给 LLM 生成一份结构化摘要，用一个 compaction 条目替换它们，同时保留最近一小段「尾巴」。压缩成功后的后续请求里，模型通常只看到「摘要 + 最近细节」，而不是无限增长的完整转写——但压缩关闭、未触发或失败时，请求仍带完整历史。要把这件事做对，得回答四个问题：

  • 何时触发？token 数怎么数？provider 报过的 usage 在上下文被改写之后还算数吗？
  • 切割点怎么选？压掉多少历史、留多少尾巴，切在哪才不把一条对话从中间截断？
  • 摘要怎么生成？全量重写还是增量合并？压缩失败的恢复流程（溢出重试）又怎么和压缩配合？
  • 压缩产物怎么回到上下文？摘要条目、系统提示存档、文件清单——各自怎么投影回 LLM 面前的消息？
答案地图 触发在 6.2（shouldCompact 的两笔预算）与 6.4（usage 优先 + 投影估算）；切点在 6.3（findProjectedCutPoint）；摘要与恢复在 6.5/6.5b；产物回上下文在 6.6–6.8。先把结论放在前面：压缩不是「删历史」，而是在 append-only 会话树上追加一条 compaction 条目——原始历史仍在盘上，模型面前只剩「摘要 + 尾巴」，而切割点选在投影（而不是原始转写）上，才能把 context_edit 改动过的上下文算对。

6.2何时触发：阈值与两笔预算

是否压缩取决于「当前上下文 token 数」是否超过「模型窗口 - 预留」。有两个配置项：

packages/agent/src/harness/compaction/compaction.ts — 设置与触发
typescriptexport interface CompactionSettings {
  enabled: boolean;      // 是否自动压缩
  reserveTokens: number;   // 给摘要 prompt 与输出预留多少 token
  keepRecentTokens: number; // 压缩后想保留「最近」多少 token
}
export const DEFAULT_COMPACTION_SETTINGS: CompactionSettings = {
  enabled: true,
  reserveTokens: 16384,   // 预留 ~16K
  keepRecentTokens: 20000, // 保留最近 ~20K
};

// 触发条件：现状 token > (窗口 - 预留)
export function shouldCompact(contextTokens, contextWindow, settings): boolean {
  if (!settings.enabled) return false;
  return contextTokens > contextWindow - settings.reserveTokens;
}
思路是「别等到窗口满才动，留出 reserveTokens 给这次摘要本身」。keepRecentTokens 决定压缩后模型还能看到多少「新鲜细节」。这两个数是压缩体验的关键旋钮——太小会损失细节，太大压缩不彻底。reserveTokens 还影响摘要输出上限（按模型最大输出 token 封顶），不只是触发线。

生产侧（coding-agent 的 settings-manager.ts）在这两个旋钮之上又加了一层解析：compaction.modelOverrides 允许按 "provider/modelId" 精确覆盖 reserveTokens/keepRecentTokens。动机很实际——一个 1M 窗口的模型与一个 32K 窗口的模型，合身的预留预算差了一个量级，全局一份默认值必然顾此失彼。解析顺序是模型覆盖 → 普通设置 → 内置默认，两个字段各自独立回退；AgentSession 在每次触发检查、手动 /compact、溢出恢复时都按当前模型调 getCompactionSettings(model) 拿生效值，换模型后下次检查就用新预算（进行中的那次压缩仍用开工时捕获的设置）。

6.3切割点：在投影上选，不在原始转写上选

第 5 章讲过：发给模型的历史不是原始转写，而是经过 context_edit 与 compaction 投影后的消息序列。切割点自然也要选在投影上——coding-agent 的实现已经从旧的 findCutPoint(entries) 换成 findProjectedCutPoint(entries: ProjectedSessionEntry[])，选点规则与旧版一致（合法切点 = user/assistant/bashExecution/custom 消息 + 独立 branch_summary 条目，toolResult 不行），但多了一条针对「恢复省略」的后缀规则：

packages/coding-agent/src/core/compaction/compaction.ts — findProjectedCutPoint（摘录，行号 824 起；注释为译注）
typescriptexport function findProjectedCutPoint(
  entries: ProjectedSessionEntry[], startIndex, endIndex, keepRecentTokens,
): CutPointResult {
  const cutPoints: number[] = [];
  for (let i = startIndex; i < endIndex; i++) {
    const entry = entries[i];
    // 合法切点：message 的若干角色（user/assistant/bashExecution/custom/…）+
    // 独立的 branch_summary 条目；toolResult 不行，compaction 条目本身也不是
    if (entry.sourceEntry.type !== "compaction" && entry.messages.some(isCutPointMessage))
      cutPoints.push(i);
  }

  let accumulatedTokens = 0, exceededBudget = false;
  let cutIndex = cutPoints[0];
  for (let i = endIndex - 1; i >= startIndex; i--) {   // 从新到旧累加
    const messageTokens = entries[i].messages.reduce((sum, m) => sum + estimateTokens(m), 0);
    if (messageTokens === 0) continue;
    accumulatedTokens += messageTokens;
    if (accumulatedTokens >= keepRecentTokens) {
      exceededBudget = true;
      // 凑满预算的位置往回找最近合法切点；找不到就回退到最后一个（commit 8bdcd4498 的旧语义）
      cutIndex = cutPoints.find((c) => c >= i) ?? cutPoints[cutPoints.length - 1];
      break;
    }
  }

  // 恢复省略的后缀规则：切割点之后若恰好是一段「上下文里看不见的后缀」——
  // 溢出恢复写下的省略 context_edit 把那次失败的 assistant 尝试整段藏掉了——
  // 切点就再往前进一格。任意元数据（如纯记账条目）不得移动切点，
  // 外部替换型编辑也会挡住推进（被省略的 assistant 回答的是改前输入，压进摘要会失配）
  const suffix = entries.slice(cutIndex + 1, endIndex);
  const isIntrinsicallyVisible = (e) =>
    e.sourceEntry.type !== "context_edit" && sessionEntryToContextMessages(e.sourceEntry).length > 0;
  const isOmitted = (e) => isIntrinsicallyVisible(e) && e.messages.length === 0;
  // 本可进上下文，却被省略编辑藏空
  const isRecoveryOmissionSuffix =
    exceededBudget && !hasExternalReplacement &&
    suffix.some((e) => e.sourceEntry.type === "message" && e.sourceEntry.message.role === "assistant" && isOmitted(e)) &&
    suffix.every((e) => e.sourceEntry.type !== "compaction" && (!isIntrinsicallyVisible(e) || isOmitted(e)));
  if (isRecoveryOmissionSuffix) cutIndex++;

  return { firstKeptEntryIndex: cutIndex, turnStartIndex, isSplitTurn };
}
三个精细的细节。其一，切割点若落在「正在进行的 turn 中间」会标记 isSplitTurn——此时 Pi 会把该 turn 的前缀单独再摘要一次（generateTurnPrefixSummary），保证被切开的 turn 也有上下文；?? cutPoints[cutPoints.length - 1] 的回退语义（结尾一堆工具结果自己超预算时退到最后一个安全切点，别让压缩空转）沿袭自旧实现。其二，messages 为 0 ≠ 天然不可见：compaction 条目在 index > 0 时投影为空（5.4 的规则），但那不算「省略后缀」；只有「本可进上下文、却被 context_edit 藏空」的条目才计入。其三，外部替换型编辑会挡住推进——被省略的 assistant 尝试回答的是改前的输入，若把它连同输入一起压进摘要，摘要与后续请求就对不上了。

6.4token 估算：先靠 provider usage，失效后靠投影重算

估算「现在用了多少 token」是触发与切点的前提。基础规则：优先用最近一次 assistant 消息里 provider 报告的 usage（精确），只对它之后的尾巴用字符启发式估算：

packages/agent/src/harness/compaction/compaction.ts — 估算与启发式
typescriptexport function estimateContextTokens(messages): ContextUsageEstimate {
  const usageInfo = getLastAssistantUsageInfo(messages);  // 最近一次有 usage 的 assistant
  if (!usageInfo) {
    // 没有任何 usage → 全部用字符启发式估算
  }
  const usageTokens = calculateContextTokens(usageInfo.usage);   // 精确：provider 报的
  // 之后每一条消息用 estimateTokens（约 4 字符 ≈ 1 token，图片算 ~4800 字符）
  return { tokens: usageTokens + trailingTokens, usageTokens, trailingTokens, ... };
}
// 触发判定的 contextTokens 就来自这里
用 provider 的真实 usage 而不是整段重算，省时又准（provider 会报告 prompt/eval 的精确 token，含 cache）。只有「usage 之后新增的部分」才走 chars/4 的启发式。

但 usage 有一个盲区：它报告的是那次请求时的上下文。如果那之后有人写入了 context_edit（省略或替换历史）或新的 compaction，旧 usage 对应的内容已经被改写，数字就过期了。coding-agent 为此在投影层加了一道失效判定：

packages/coding-agent/src/core/compaction/compaction.ts — estimateProjectedContextTokens（行号 249 起，要点）
typescriptexport function estimateProjectedContextTokens(
  projection: SessionProjection, branchEntries: SessionEntry[],
): ContextUsageEstimate {
  const estimate = estimateContextTokens(projection.messages);
  if (estimate.lastUsageIndex !== null) {
    // 找到 usage 落在哪个投影条目上，再看该条目之后
    // 是否还有 context_edit / compaction 写入
    if (usageEntryIndex > latestInvalidatingEntryIndex) return estimate;  // usage 仍有效
  }
  // usage 已失效（或有 usage 但有改写）：放弃 usage，对整条投影逐条重估
  let tokens = currentSystem ? estimateTokens(currentSystem) : 0;
  for (const message of projection.messages) {
    if (message.role !== "system") tokens += estimateTokens(message);
  }
  return { tokens, usageTokens: 0, trailingTokens: tokens, lastUsageIndex: null };
}
谁在用它 prepareCompaction 用它重算 tokensBefore（写进新 CompactionEntry 的数字必须反映「实际被替换的上下文」，包括被改写过的部分）；AgentSession._checkCompaction 在会话里存在 context_edit 时用它替代直接读 usage；每轮间隙的 shouldCompact 预检也走它。一句话：凡是有「改写历史」动作的会话，token 账本都以投影为准。

6.5让模型生成「结构化摘要」

摘要不是自由文本，而是用小号 prompt 让模型按固定格式输出。关键：若已有前一次摘要，则用「增量更新」prompt，把新消息并入旧摘要——避免每次全量重写。

packages/agent/src/harness/compaction/compaction.ts — 摘要 prompt 选择 + 调用
typescript// 首次压缩：完整格式；已有摘要：UPDATE_ 增量合并
let basePrompt = previousSummary ? UPDATE_SUMMARIZATION_PROMPT : SUMMARIZATION_PROMPT;
if (customInstructions) basePrompt = `${basePrompt}\n\nAdditional focus: ${customInstructions}`;

// 拼出"对话 + 旧摘要"放进 user 消息，经 request 边界 + retry 调用
const response = await request(
  { systemPrompt: SUMMARIZATION_SYSTEM_PROMPT, messages: summarizationMessages },
  createSummaryRequestOptions(completionOptions, context),
  context);
摘要 prompt 的格式（SUMMARIZATION_PROMPT）很讲究：## Goal / ## Constraints & Preferences / ## Progress(Done/In Progress/Blocked) / ## Key Decisions / ## Next Steps / ## Critical Context——这几乎就是「让我能无缝接手」的充分信息集。它把「压缩」变成了「结构化交接班」。摘要走的是独立请求：默认的 request 边界是 completeSimpleWithRetries(models, model, aiContext, options, retry, callbacks, context)（7 参），它内部用 createSummaryRequestOptions 强制 { ...options, signal, telemetryContext, cacheRetention: "none", sessionId: options.sessionId ?? uuidv7() }——sessionId 若调用方未传才生成新 uuidv7()，cacheRetention 恒为 "none" 不写缓存，让摘要彻底脱离主对话的缓存；摘要请求不传 toolChoice，completionOptions 只含 { maxTokens[, reasoning] }。增量合并的底稿在切分 turn 时取 previousSummary ?? "No prior history."——旧摘要直接作为下一轮的底稿，压缩因此是递归的：新摘要 = 旧摘要 + 新增消息的合并。

retain-none 压缩是 v0.87 里新出现的一档：appendCompaction 的 firstKeptEntryId 参数从必填的 string 放宽为 string | null。传 null 时，条目把自己的 ID 记成保留边界——压缩后模型面前的历史只剩摘要，尾巴为零：

coding-agent/src/core/session-manager.ts — appendCompaction（节选，行号约 1258；注释为译注）
typescriptexport appendCompaction<T = unknown>(
  summary: string,
  firstKeptEntryId: string | null,    // ← v0.87 起允许 null
  tokensBefore: number, details?, fromHook?, usage?,
): string {
  const systemMessage = getCurrentSystemMessage(this.buildSessionProjection().messages);
  const id = generateId(this.byId);
  const entry: CompactionEntry<T> = {
    type: "compaction", id, parentId: this.leafId, timestamp, summary,
    firstKeptEntryId: firstKeptEntryId ?? id,   // null → 保留边界记自己：什么都不留
    tokensBefore, details, usage, fromHook,
    ...(systemMessage ? { systemMessage: { ...systemMessage, timestamp: ... } } : {}),
  };
  this._appendEntry(entry);
  return entry.id;
}
retain-none 的用途在重复压缩：下一次压缩的摘要范围从上一条 compaction 的 firstKeptEntryId 起算，若上一条什么都不留（边界 = 它自己），那么上一轮侥幸留下的消息也会被并进这次摘要，而不是被静默跳过。同时 tokensBefore 在写入前会按「重建后的、改写过的投影」重新计算——数字反映的是真正被替换的上下文。被省略的原始条目仍留在盘上，但不再影响切点选择、摘要、检查点与 token 估算。

6.5b溢出恢复：先省略失败尝试，再压缩重试

上下文压满通常不是发生在「写文档写到一半」，而是 provider 直接报 context-overflow 错误，或 stopReason: "length" 提前截断。pi 允许这两种情况挑起一次「压缩 + 重试」的恢复。恢复的关键改动：失败的那次 assistant 尝试不再只是从内存里剥掉，而是持久化地省略——为它写下 replacement: null 的 context_edit：

coding-agent/src/core/agent-session.ts — _omitRecoveryAttempt（行号 1015 起；注释为译注）
typescriptprivate _omitRecoveryAttempt(message: AssistantMessage, toolResults: AgentMessage[] = []): void {
  const targets = [message, ...toolResults];
  const targetIds = targets.map((t) => this._findPersistedMessageEntryId(t));
  // 找不到对应条目且消息还在 agent state 里 → 投影消息没有源条目，直接报错
  if (unresolvedProjectedTarget) {
    throw new Error("Cannot persist recovery omission because a projected message has no source entry");
  }
  for (const targetId of targetIds) {
    if (!targetId) continue;
    const editId = this.sessionManager.appendContextEdit(targetId, null);  // null = 从模型上下文省略
    this._emit({ type: "entry_appended", entry });
  }
  this._refreshFinalizedContext();   // 用新投影刷新 agent.state.messages 与条目索引
}
恢复的完整时序（docs/compaction.md 原文复述）
textpersist final assistant response   ① 失败尝试先照常落盘
→ extension/public turn_end        ② 生命周期事件一个不少
→ extension/public agent_end
→ append context_edit omissions    ③ 再为失败尝试写省略编辑
→ session_before_compact → append compaction   ④ 然后才压缩
→ start the retry as a fresh run   ⑤ 重试作为全新 run 启动
为什么先落盘再省略 顺序反过来行不行？不行。若先省略再发事件，扩展和 UI 看到的是「这次回复从未存在」；而 raw 转写、导出、计费统计、历史搜索都还能翻到被省略的尝试——省略只改模型上下文，不改历史。若恢复压缩失败或被取消，省略编辑保留、不追加压缩、不排内部重试；排队中的 steering/follow-up 照常走原有规则，agent_before_settle 看到的是修复后的投影。这也解释了 6.3 的后缀规则：切点后那段「上下文不可见的省略后缀」必须一起进摘要，否则恢复后模型面前的历史会凭空少一块。

6.6写入 compaction 条目：顺手存档系统提示

摘要生成后，连同保留的尾巴与「文件操作」细节一起，作为一条 compaction 条目追加进会话。产物本身（CompactResult：summary / tokensBefore / usage / retainedTail / details）与第 5 章讲的展开方式（[摘要假消息, ...retainedTail]）不变；coding-agent 侧多存的一样东西——压缩那一刻的完整系统提示——现在从投影里取：

coding-agent/src/core/session-manager.ts — 压缩检查点（节选，注释为译注）
typescript// CompactionEntry 上的字段：边界处的完整 prompt 与工具声明状态

const entry: CompactionEntry<T> = {

系统提示不再是「永远在头顶的一条固定消息」，而是随对话演化、可被中途替换的状态（第 10 章）。这带来一个压缩特有的问题：压缩会把旧消息丢掉，如果那条记录「系统提示是什么」的 system 消息恰好落在被丢掉的部分，压缩后模型就失去了 prompt。所以压缩条目把边界处的 system 消息整体存档，重放时展开成「[系统消息, 摘要消息]」两条：

           content: [{ type: "text", text: COMPACTION_SUMMARY_PREFIX + m.summary + COMPACTION_SUMMARY_SUFFIX }],
           timestamp: m.timestamp };
摘要对模型来说是「一个来自系统的大量历史说明」，塞进显式的 <summary> 标签，让模型明确区分「这是历史压缩」与「这是本轮对话」。branchSummary（第 7 章 navigation）用同样的手法。

6.8分支摘要：navigation 时给被离开的分支留张便条

6.1–6.7 讲的是「上下文压缩」——同一条主线上的历史被压成摘要。但还有另一种摘要：当你 navigate 切到另一条分支（第 7 章 navigation）时，那条被离开的旧分支不该凭空消失，而会被压成一条 branch_summary 条目留作路标。这件事由 branch-summarization.ts 负责，分三步：

关键是 BRANCH_SUMMARY_PROMPT 的格式与 compaction 摘要同构——都是结构化「交接班」：## Goal / ## Constraints & Preferences / ## Progress(Done/In Progress/Blocked) / ## Key Decisions / ## Next Steps（比 compaction 少一节 ## Critical Context）。所以分支摘要不是「自由文本」，而是一份让模型回到这条分支时能无缝接手的清单。它生成的摘要前面会加一段 BRANCH_SUMMARY_PREAMBLE（说明「用户刚才探索了另一条分支」），末尾再用 formatFileOperations 追加「读过/改过哪些文件」的清单——这部分与 §6.6 的 compaction 摘要复用同一套 computeFileLists / formatFileOperations 工具。

别把分支摘要和上下文压缩混为一谈——compaction 是「主线太长压一压」，branch summary 是「离开分支前留张便条」。两者共用同款结构化 prompt、同一套文件清单工具、同一个请求边界 completeSimpleWithRetries + createSummaryRequestOptions（同样 cacheRetention:"none" + sessionId: options.sessionId ?? uuidv7()），只是触发时机与产物条目类型（compaction vs branch_summary）不同。6.7 的「摘要假消息」对二者一视同仁，都包成 <summary> 塞进上下文。
设计取舍： 不保留文件内容、只留清单，是 token 预算的精算——内容大概率会在后续 turn 被重新读，而「动过哪些文件」这种元信息一旦丢失就要重头猜。压缩的本质不是「少说话」，而是「留下以后还能用的索引」。

6.9收尾：四个答案

  • 何时触发？token 涨过「窗口 − 预留」即触发；预算可按模型覆盖。usage 是主账本，但 context_edit/compaction 写在它之后时数字作废，改由 estimateProjectedContextTokens 按投影重算。
  • 切割点怎么选？findProjectedCutPoint 从新到旧累加到 keepRecentTokens，回退到安全切点（不切工具结果、不切 compaction 条目）；「恢复省略」形成的上下文不可见后缀会连带推进切点，外部替换编辑则挡住推进。
  • 摘要怎么生成、失败怎么恢复？结构化交接班 prompt + 旧摘要作底稿的增量合并；retain-none 压缩（firstKeptEntryId: null）让重复压缩把上轮尾巴也并进来。溢出恢复按时序「先落盘 → 再省略 → 再压缩 → 全新 run 重试」，只给一次机会。
  • 产物怎么回上下文？compaction 条目存档系统提示、展开成「prompt + 摘要」两条；摘要包 <summary> 标签；文件清单作为元上下文写进摘要正文。
要点 token 预算是两笔账：reserveTokens（给这次摘要留空间）+ keepRecentTokens（保留多少细节）。切割要尊重对话边界，别从工具结果中间切。增量更新旧摘要，别每次全量重写（省 token 且更连贯）。摘要里带上文件清单等"元上下文"，比纯文本可控得多。
