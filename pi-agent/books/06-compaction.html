上下文压缩 Compaction：把历史「压成摘要」

第 5 章我们看到「最近一次 compaction 会被调到最前」。本章展开压缩的全过程：何时触发、如何选切割点、如何让模型生成结构化摘要、以及上一个 compaction 条目如何被新摘要增量更新。

6.1先用一段话讲清楚

Compaction = 当上下文快满时，把「较早的历史」交给 LLM 生成一份结构化摘要，用一个 compaction 条目替换它们，同时保留最近一小段「尾巴」。这样模型永远只看到「摘要 + 最近细节」，而不是无限增长的完整转写。

6.2何时触发：阈值与两笔预算

是否压缩取决于「当前上下文 token 数」是否超过「模型窗口 - 预留」。有两个配置项：

packages/agent/src/harness/compaction/compaction.ts — 设置与触发
typescriptexport interface CompactionSettings {
  enabled: boolean;      // 是否自动压缩
  reserveTokens: number;   // 给摘要 prompt 与输出预留多少 token
  keepRecentTokens: number; // 压缩后想保留「最近」多少 token
}
export const DEFAULT_COMPACTION_SETTINGS: CompactionSettings = {
  enabled: true,
  reserveTokens: 16384,   // 预留 ~16K
  keepRecentTokens: 20000, // 保留最近 ~20K
};

// 触发条件：现状 token > (窗口 - 预留)
export function shouldCompact(contextTokens, contextWindow, settings): boolean {
  if (!settings.enabled) return false;
  return contextTokens > contextWindow - settings.reserveTokens;
}
读懂这段： 思路是「别等到窗口满才动，留出 reserveTokens 给这次摘要本身」。keepRecentTokens 决定压缩后模型还能看到多少「新鲜细节」。这两个数是压缩体验的关键旋钮——太小会损失细节，太大压缩不彻底。

生产侧（coding-agent 的 settings-manager.ts）在这两个旋钮之上又加了一层解析：compaction.modelOverrides 允许按 "provider/modelId" 精确覆盖 reserveTokens/keepRecentTokens。动机很实际——一个 1M 窗口的模型与一个 32K 窗口的模型，合身的预留预算差了一个量级，全局一份默认值必然顾此失彼。解析顺序是模型覆盖 → 普通设置 → 内置默认，两个字段各自独立回退；AgentSession 在每次触发检查、手动 /compact、溢出恢复时都按当前模型调 getCompactionSettings(model) 拿生效值，换模型后下次检查就用新预算（进行中的那次压缩仍用开工时捕获的设置）。

6.3切割点：该压掉多少

findCutPoint 从新到旧累加每条消息的估计 token，直到凑足 keepRecentTokens，再回退到一个「安全切点」（合法切点包括 user/assistant/bashExecution/custom 消息、branchSummary/compactionSummary 消息，以及独立的 branch_summary 条目），避免从一条工具结果（toolResult）中间切开。

  for (let i = endIndex - 1; i >= startIndex; i--) {   // 从新到旧累加

读懂这段： 一个精细的细节——切割点若落在「正在进行的 turn 中间」会标记 isSplitTurn。此时 Pi 会把该 turn 的前缀单独再摘要一次（generateTurnPrefixSummary），保证被切开的turn也有上下文。这是「压掉一半对话」时仍不丢语义的关键。

6.4token 估算：先靠 provider usage，后靠字符启发

估算「现在用了多少 token」是触发与切点的前提。Pi 的聪明之处：优先用最近一次 assistant 消息里 provider 报告的 usage（精确），只对它之后的尾巴用字符启发式估算：

packages/agent/src/harness/compaction/compaction.ts — 估算与启发式
typescriptexport function estimateContextTokens(messages): ContextUsageEstimate {
  const usageInfo = getLastAssistantUsageInfo(messages);  // 最近一次有 usage 的 assistant
  if (!usageInfo) {
    // 没有任何 usage → 全部用字符启发式估算
  }
  const usageTokens = calculateContextTokens(usageInfo.usage);   // 精确：provider 报的
  // 之后每一条消息用 estimateTokens（约 4 字符 ≈ 1 token，图片算 ~4800 字符）
  return { tokens: usageTokens + trailingTokens, usageTokens, trailingTokens, ... };
}
// 触发判定的 contextTokens 就来自这里
读懂这段： 用 provider 的真实 usage 而不是整段重算，省时又准（provider 会报告 prompt/eval 的精确 token，含 cache）。只有「usage 之后新增的部分」才走 chars/4 的启发式。这是工程上的务实取舍。

6.5让模型生成「结构化摘要」

摘要不是自由文本，而是用小号 prompt 让模型按固定格式输出。关键：若已有前一次摘要，则用「增量更新」prompt，把新消息并入旧摘要——避免每次全量重写。

packages/agent/src/harness/compaction/compaction.ts — 摘要 prompt 选择 + 调用
typescript// 首次压缩：完整格式；已有摘要：UPDATE_ 增量合并
let basePrompt = previousSummary ? UPDATE_SUMMARIZATION_PROMPT : SUMMARIZATION_PROMPT;
if (customInstructions) basePrompt = `${basePrompt}\n\nAdditional focus: ${customInstructions}`;

// 拼出"对话 + 旧摘要"放进 user 消息，经 request 边界 + retry 调用
const response = await request(
  { systemPrompt: SUMMARIZATION_SYSTEM_PROMPT, messages: summarizationMessages },
  createSummaryRequestOptions(completionOptions, context),
  context);
读懂这段： 摘要 prompt 的格式（SUMMARIZATION_PROMPT）很讲究：## Goal / ## Constraints & Preferences / ## Progress(Done/In Progress/Blocked) / ## Key Decisions / ## Next Steps / ## Critical Context——这几乎就是「让我能无缝接手」的充分信息集。它把「压缩」变成了「结构化交接班」。摘要走的是独立请求：默认的 request 边界是 completeSimpleWithRetries(models, model, aiContext, options, retry, callbacks, context)（7 参），它内部用 createSummaryRequestOptions 强制 { ...options, signal, telemetryContext, cacheRetention: "none", sessionId: options.sessionId ?? uuidv7() }——sessionId 若调用方未传才生成新 uuidv7()，cacheRetention 恒为 "none" 不写缓存，让摘要彻底脱离主对话的缓存；摘要请求不传 toolChoice，completionOptions 只含 { maxTokens[, reasoning] }。

6.6写入 compaction 条目

摘要生成后，连同保留的尾巴与「文件操作」细节一起，作为一条 compaction 条目追加进会话：

packages/agent/src/harness/compaction/compaction.ts — compact 的产出
typescriptexport interface CompactResult {
  summary: string;            // 摘要文本（含文件操作清单）
  tokensBefore: number;        // 压缩前估计 token（记档用）
  usage?: Usage;               // 生成摘要的 LLM 用量
  retainedTail: AgentMessage[]; // 保留的最近消息
  details?: T;                 // 例如 readFiles / modifiedFiles
}
// compact() 最后：
const { readFiles, modifiedFiles } = computeFileLists(fileOps);
summary += formatFileOperations(readFiles, modifiedFiles);  // 把碰过哪些文件写进摘要
return ok({ summary, tokensBefore, usage: summaryUsage, retainedTail,
             details: { readFiles, modifiedFiles } });
读懂这段： retainedTail 直接存在 compaction 条目上——所以第 5 章的 sessionEntryToContextMessages 能「[摘要假消息, ...retainedTail]」地展开它。而 details 记录了「这段历史读过/改过哪些文件」，让后续上下文（或你自研时）能推断文件依赖而无需重扫。

coding-agent 的 appendCompaction 还往 compaction 条目上多存了一样东西——压缩那一刻的完整系统提示：

coding-agent/src/core/session-manager.ts — 压缩检查点（节选，注释为译注）
typescript// CompactionEntry 上新增的字段：边界处的完整 prompt 与工具声明状态
/** Complete prompt and tool state at this compaction boundary. */
systemMessage?: SystemMessage;

// appendCompaction 写入时快照当前生效的系统消息
const systemMessage = getCurrentSystemMessage(this.buildSessionContext().messages);
const entry: CompactionEntry<T> = {
  type: "compaction", summary, firstKeptEntryId, tokensBefore, details, usage, fromHook,
  ...(systemMessage ? { systemMessage: { ...systemMessage } } : {}),
};
读懂这段： 系统提示不再是「永远在头顶的一条固定消息」，而是随对话演化、可被中途替换的状态（第 10 章）。这带来一个压缩特有的问题：压缩会把旧消息丢掉，如果那条记录「系统提示是什么」的 system 消息恰好落在被丢掉的部分，压缩后模型就失去了 prompt。所以压缩条目把边界处的 system 消息整体存档，重放时展开成「[系统消息, 摘要消息]」两条：
typescript// sessionEntryToContextMessages 的 compaction 分支
if (entry.type === "compaction") {
  const summary = createCompactionSummaryMessage(entry.summary, entry.tokensBefore, entry.timestamp);
  return entry.systemMessage ? [entry.systemMessage, summary] : [summary];
}
// buildContextEntries 反向处理：保留段里的 system 消息一律剔除，
// 否则同一条 prompt 会出现两次（存档里一份、保留段里一份）
if (foundFirstKept && !(entry.type === "message" && entry.message.role === "system")) {
  contextEntries.push(entry);
}
配套的取舍：压缩收集待摘要消息时也跳过 system 角色（getMessageFromEntryForCompaction 里有一句注释「System messages are prompt state, not conversation」）——系统提示不参与摘要。另外切分 turn 时，拆成「历史摘要 + turn 前缀摘要」两段再合并，历史那段的种子文本现在取 previousSummary ?? "No prior history."——即上一轮的旧摘要直接作为增量更新的底稿，而不是每次都从「无历史」开始。压缩在 coding-agent 里因此是递归的：新摘要 = 旧摘要 + 新增消息的合并。

6.7在上下文里呈现：摘要假消息

落到 LLM 面前，摘要被包成一段 user 消息（来自 messages.ts）：

packages/agent/src/harness/messages.ts — 摘要消息的包装
typescriptexport const COMPACTION_SUMMARY_PREFIX =
  `The conversation history before this point was compacted into the following summary:` +
  `\n\n<summary>\n`;
export const COMPACTION_SUMMARY_SUFFIX = `\n</summary>`;

// convertToLlm 里，compactionSummary 角色 → user 消息，包上 <summary> 标签
case "compactionSummary":
  return { role: "user",
           content: [{ type: "text", text: COMPACTION_SUMMARY_PREFIX + m.summary + COMPACTION_SUMMARY_SUFFIX }],
           timestamp: m.timestamp };
读懂这段： 摘要对模型来说是「一个来自系统的大量历史说明」，塞进显式的 <summary> 标签，让模型明确区分「这是历史压缩」与「这是本轮对话」。branchSummary（第 7 章 navigation）用同样的手法。

6.8分支摘要：navigation 时把「被离开的分支」压成一条

6.1–6.7 讲的是「上下文压缩」——同一条主线上的历史被压成摘要。但还有另一种摘要：当你 navigate 切到另一条分支（第 7 章 navigation）时，那条被离开的旧分支不该凭空消失，而会被压成一条 branch_summary 条目留作路标。这件事由 branch-summarization.ts 负责，分三步：

关键是 BRANCH_SUMMARY_PROMPT 的格式与 compaction 摘要同构——都是结构化「交接班」：## Goal / ## Constraints & Preferences / ## Progress(Done/In Progress/Blocked) / ## Key Decisions / ## Next Steps（比 compaction 少一节 ## Critical Context）。所以分支摘要不是「自由文本」，而是一份让模型回到这条分支时能无缝接手的清单。它生成的摘要前面会加一段 BRANCH_SUMMARY_PREAMBLE（说明「用户刚才探索了另一条分支」），末尾再用 formatFileOperations 追加「读过/改过哪些文件」的清单——这部分与 §6.6 的 compaction 摘要复用同一套 computeFileLists / formatFileOperations 工具。

读懂这段： 别把分支摘要和上下文压缩混为一谈——compaction 是「主线太长压一压」，branch summary 是「离开分支前留张便条」。两者共用同款结构化 prompt、同一套文件清单工具、同一个请求边界 completeSimpleWithRetries + createSummaryRequestOptions（同样 cacheRetention:"none" + sessionId: options.sessionId ?? uuidv7()），只是触发时机与产物条目类型（compaction vs branch_summary）不同。6.7 的「摘要假消息」对二者一视同仁，都包成 <summary> 塞进上下文。
设计取舍： 不保留文件内容、只留清单，是 token 预算的精算——内容大概率会在后续 turn 被重新读，而「动过哪些文件」这种元信息一旦丢失就要重头猜。压缩的本质不是「少说话」，而是「留下以后还能用的索引」。

6.9对自研与使用的启示

要点 ① token 预算两笔账：reserveTokens（给这次摘要留空间）+ keepRecentTokens（保留多少细节）。② 切割要尊重对话边界：别从工具结果中间切。③ 增量更新旧摘要，别每次全量重写（省 token 且更连贯）。④ 摘要里带上文件清单等"元上下文"，比纯文本可控得多。
