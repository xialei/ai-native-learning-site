上下文构建 Context：决定「模型这一轮看到什么」

★ 本站在意的最核心一章。上一章我们把会话存成了「树的条目」；这一章讲清这些条目如何被挑选、重排、投影成一串能发给 LLM 的消息——这才是 Agent 的「记忆」真正呈现在模型面前的地方。
产品视角 「真正的上下文工程。」 Pi 的极简系统提示加上可扩展性，让你能真正掌控上下文窗口装什么、怎么管：AGENTS.md 在启动时从 ~/.pi/agent/、父目录、当前目录加载项目指令；SYSTEM.md 按项目覆盖或追加默认提示；Compaction 在逼近上下文上限时自动摘要旧消息，且可由扩展改写（话题级压缩、代码感知摘要、换摘要模型）；→ Skills 按需载入、提示模板 /name 展开、扩展还能在每轮前注入消息 / 过滤历史 / 做 RAG。本章看其中最核心的「投影」是怎么发生的。

5.1一句话版本

Context 构建是一条三级流水线，输入是「当前分支的全部 Entry」，输出是「发给模型的消息 + 当前运行状态」：

图 5.1：Context 构建三级管线。pathEntries → contextEntries → messages 是主轴；state 从原始 pathEntries 分叉派生，不经 ① 裁剪。输出的 messages 再经第 3 章 convertToLlm 发往 LLM。
为什么要分三级，而不是一步到位？ 因为这三步解决的是三个不同的问题，混在一起就没法独立替换：① 转换管「留哪些 entry」（token 控制，第 6 章压缩在这介入）；② 投影管「一条 entry 变成几条消息」（compaction 会展开成「摘要+尾巴」多条，见 5.3）；状态派生管「现在该用什么模型/思考级别」（只读不改，见 5.4）。把它们拆成纯函数，才能让「换压缩策略」「换投影方式」「重算运行状态」各自演进。

5.2三件套：谁干啥，数据怎么流

buildSessionContext 是总装函数，内部调三个纯函数，对应 5.1 图里的三级。注意三件事的输入各不相同——这是理解整章的钥匙：

packages/agent/src/harness/session/context.ts — 总装 + 状态派生
typescriptexport function buildSessionContext(pathEntries, options): SessionContext {
  const state = deriveSessionContextState(pathEntries);          // 状态：读【原始】pathEntries
  const contextEntries = buildContextEntries(pathEntries, options); // ① 转换：Entry[] → Entry[]
  const messages = contextEntries.flatMap((entry, index) =>
    sessionEntryToContextMessages(entry, index, contextEntries, options) // ② 投影：Entry → AgentMessage[]
  );
  return { ...state, messages };
}
关键看输入： deriveSessionContextState 和 buildContextEntries 都吃 pathEntries，但状态派生用原始分支、转换用转换后的——两条独立支线并行，互不影响。这意味着：哪怕 ① 把 90% 的历史压成摘要，state.model 仍能从被压掉的那些 model_change 里读出「当前模型」。消息会被压缩，运行状态不会丢。

① 转换：buildContextEntries —— 留哪些 entry

packages/agent/src/harness/session/context.ts — 默认转换 + 用户转换
typescriptexport function buildContextEntries(pathEntries, options): Entry[] {
  let entries = defaultContextEntryTransform(pathEntries);   // 先跑默认：compaction 裁剪
  for (const transform of options.entryTransforms ?? [])    // 再串用户挂的
    entries = [...transform(entries)];
  return entries;
}

// 默认转换：找到【最近一次】compaction，把它拎到最前，丢掉它之前的原始条目
export function defaultContextEntryTransform(pathEntries): Entry[] {
  let compaction, compactionIndex = -1;
  for (let i = pathEntries.length - 1; i >= 0; i--) {   // 从后往前找最近的一个
    if (pathEntries[i].type === "compaction") { compaction = pathEntries[i]; compactionIndex = i; break; }
  }
  return compaction === undefined
    ? [...pathEntries]                                  // 没压缩过：全量保留
    : [compaction, ...pathEntries.slice(compactionIndex + 1)]; // 有：摘要前置 + 尾巴
}
别误读「丢掉之前」： 丢的是压缩点之前的原始消息（它们已被摘要吸收），但 compaction 条目本身被拎到最前并保留——[compaction, ...之后的尾巴]。所以模型看到的是「摘要 + 最近细节」，而非「啥也没了」。defaultContextEntryTransform 是无条件先跑的，entryTransforms 是用户在它之后串的自定义转换（5.5 讲），两者是「默认 + 可选」而非并列。

一个具体例子：压缩前后的上下文

假设当前分支从旧到新是 8 条 entry（M=message、C=compaction、m=model_change），下面是它走完整条管线的样子：

图 5.2：一个实例。8 条 entry → ① 转换丢掉 C6 之前的 5 条（已被摘要吸收）、C6 前置，得 3 条 → ② 投影把 C6 展开成「摘要+尾巴」共 5 条消息。state 从原始分支的 m2 读出「当前用 opus」——它不在转换后的列表里，但状态支线读的是转换前数据，所以不丢。
一句话记住： ① 转换决定「留哪些 entry」（8→3），② 投影决定「一条变几条消息」（3→5，compaction 会展开），状态从原始分支独立读出——消息可压缩，运行状态不可丢。

5.3投影规则：每个 Entry → 几条 LLM 消息

packages/agent/src/harness/session/context.ts — sessionEntryToContextMessages
typescriptexport function sessionEntryToContextMessages(entry, index, entries, options): AgentMessage[] {
  if (entry.type === "message") {
    // 关键细节点：stopReason === "deferred" 的 assistant 消息不进上下文
    if (entry.message.role === "assistant" && entry.message.stopReason === "deferred") return [];
    return [entry.message];                             // 普通消息：直接投影
  }
  if (entry.type === "compaction") {
    return [
      createCompactionSummaryMessage(entry.summary, entry.tokensBefore, entry.timestamp),
      ...entry.retainedTail,                              // 压缩点保留的尾巴
    ];
  }
  if (entry.type === "branch_summary" && entry.summary) {
    return [createBranchSummaryMessage(entry.summary, entry.fromId, entry.timestamp)];
  }
  if (entry.type === "custom") {
    return [...(options.entryProjectors?.[entry.customType]?.(entry, index, entries) ?? [])];
  }
  return [];   // model_change / thinking_level_change / active_tools_change → 不投影成消息
}
读懂这段（极其重要）：
  • message → 直接投影；但 stopReason === "deferred" 的 assistant 消息会被丢弃——deferred 表示「这轮先不产出可进上下文的助手回复」，得等后续工具/续跑，避免把半截话塞给模型。
  • compaction → 展开为「1 条摘要假消息 + 保留尾巴（若干条）」，一个压缩点能投影出多条。
  • branch_summary → 1 条分支摘要假消息。
  • custom → 通过 entryProjectors[customType] 投影（可返回 0~N 条）；没配 projector 就返回空。
  • model_change / thinking_level_change / active_tools_change → 返回 []！它们不是「给模型的对话内容」，而是状态元数据（见 5.4）。

5.4状态派生：扫一遍就知「现在用什么模型」

上下文构建还顺带回答了运行时的「当前状态」：沿着分支扫一遍，遇到 model_change 就更新模型、遇到 thinking/active_tools 也更新，最后最新一次赋值生效。

packages/agent/src/harness/session/context.ts — deriveSessionContextState
typescriptfunction deriveSessionContextState(pathEntries): Omit<SessionContext, "messages"> {
  let thinkingLevel = "off";
  let model = null, activeToolNames = null;
  for (const entry of pathEntries) {
    if (entry.type === "thinking_level_change") thinkingLevel = entry.thinkingLevel;
    else if (entry.type === "model_change") model = { provider, modelId };
    else if (entry.type === "message" && entry.message.role === "assistant")
      model = { provider: entry.message.provider, modelId: entry.message.model }; // 也看助手消息
    else if (entry.type === "active_tools_change") activeToolNames = [...entry.activeToolNames];
  }
  return { thinkingLevel, model, activeToolNames };
}
读懂这段： 因为「切换模型/思考级别」被记成了 Entry，所以只要读一遍分支就能重算出「当前应该用哪个模型、哪个思考级别、哪些工具」。这让「运行时配置」与「会话历史」同步、可恢复——重启后重放分支即得当前配置。这是把状态建模成数据的高明之处。
光标从旧到新扫过每个 entry，遇到 model/thinking/tools 就更新右侧「当前状态」，最新一次赋值生效
扫完即得「重启后重放分支就能恢复的当前配置」——模型/思考级别/工具都不是单独存的，全在历史里。

5.5两个扩展点：entryTransforms 与 entryProjectors

packages/agent/src/harness/session/context.ts — 扩展点签名
typescript// 变换：作用于"条目数组"，可重排/删除/插入（在默认 compaction 变换之后）
export type ContextEntryTransform =
  (entries: readonly Entry[]) => readonly Entry[];

// 投影：把某个 custom 条目变成 LLM 消息（找不到就返回 undefined → 空）
export type CustomEntryContextMessageProjector = (
  entry: CustomEntry, index: number, entries: readonly Entry[],
) => readonly AgentMessage[] | undefined;

// buildContextEntries 里顺序应用所有 transform
export function buildContextEntries(pathEntries, options): Entry[] {
  let entries = defaultContextEntryTransform(pathEntries);
  for (const t of options.entryTransforms ?? []) entries = [...t(entries)];
  return entries;
}
读懂这段： 两个扩展点分工明确——entryTransforms 改「结构」（比如你的应用想额外隐藏某些 custom 条目），entryProjectors 改「呈现」（把某个 custom 条目变成模型该看的话）。生产 harness 用 `custom` 条目承载「工具产物摘要 / 分支导航」等信息，再配 projector 决定它们如何出现在上下文里。

5.6从 Context 到 LLM：两条路

buildSessionContext 产出的是 AgentMessage[]。之后走第 3 章说过的两步转换，最终到 Message[] 发往 LLM。这条「会话树 → 上下文 → LLM」的链路就是一次 run 中每一轮模型调用前的必经之路。

链路总括
textsession(当前分支) ──walkToRoot──> Entry[]
    └─ buildSessionContext
         ├─ deriveSessionContextState ──> model / thinking / activeTools
         └─ buildContextEntries (transform) → sessionEntryToContextMessages (project)
              └─> AgentMessage[]
                   └─ transformContext (可选) → convertToLlm ──> Message[] ──> LLM
关键点： 注意「会话树构建的上下文」替代了第 3 章里那个朴素 context.messages——生产 harness 会在 transform_context 钩子里调用 buildSessionContext，从而让「模型看到什么」完全由会话树驱动。

5.7一个「思考粒度」示例

假设分支里有这些条目（从新到旧示意）：

Entry投影出什么（进上下文）
message · assistant (stopReason=deferred)（无——被丢弃）
message · toolResult1 条 toolResult 消息
message · assistant1 条 assistant 消息
message · user1 条 user 消息
compaction1 条摘要 + retainedTail 若干条
(messaging 更早的…)（被 defaultContextEntryTransform 丢掉）
model_change状态：当前模型 = 该 provider/modelId

最终发给 LLM 的是：压缩摘要 + 尾巴 + 最近的 user/assistant/toolResult，而「当前用什么模型」作为运行状态单独传给循环。

5.8对自研与使用的启示

要点 ① 把「上下文管理」做成独立的纯函数（输入条目 → 输出消息），不要散落在循环里。② 用「条目 → 投影」而非「直接存消息」，才能支持压缩摘要、分支摘要、自定义投影。③ 状态（模型/思考/工具）也建模成条目，随历史可回放。④ 留两个扩展点：改结构的 transform、改呈现的 projector。
