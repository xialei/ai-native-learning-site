上下文构建 Context：决定「模型这一轮看到什么」

★ 本站在意的最核心一章。上一章把会话存成了「树的条目」；这一章讲清这些条目如何被挑选、重排、投影成一串能发给 LLM 的消息——这才是 Agent 的「记忆」真正呈现在模型面前的地方。条目怎么变成消息？留哪些丢哪些？运行状态藏在哪？已经写进历史的消息还能改吗？
产品视角 「真正的上下文工程。」 Pi 的极简系统提示加上可扩展性，让你能真正掌控上下文窗口装什么、怎么管：AGENTS.md 在启动时从 ~/.pi/agent/、父目录、当前目录加载项目指令；SYSTEM.md 按项目覆盖或追加默认提示；Compaction 在逼近上下文上限时自动摘要旧消息，且可由扩展改写（话题级压缩、代码感知摘要、换摘要模型）；→ Skills 按需载入、提示模板 /name 展开、扩展还能在每轮前注入消息 / 过滤历史 / 做 RAG。本章看其中最核心的「投影」是怎么发生的。

5.1树上怎么长出模型眼前的消息

第 4 章结束时，会话是一片 append-only 的 Entry 树。但模型不吃「树」，它吃一维的 AgentMessage[]。从树到消息，路上要过四道坎：

  • 条目怎么变成消息？一条 message 条目出一条消息，那 compaction、branch_summary、custom 呢？
  • 留哪些、丢哪些？压缩过的旧消息为什么不删条目、却也不再出现在上下文里？
  • 运行状态（模型/思考级别）从哪来？它在不在「消息」里？
  • 已经写进历史的消息还能改吗？消息流 append-only，可「上一轮模型看错了工具结果」这种修正从哪进来？
答案地图 前两问在 5.2–5.3（两级流水线：裁剪 + 投影），第三问在 5.4（两层各有答案：lane 值 vs 沿路径扫条目），第四问在 5.5（context_edit 追加式编辑 + buildSessionProjection）。5.6 汇总两条真实调用链，5.7 给一张投影速查表。先把结论摆在这里：上下文构建 = 「从树挑一条路径」→「裁剪到最近压缩点」→「逐条投影成消息」→「套用追加式编辑」，每一步都是可独立替换的纯函数。

5.2两级流水线：先裁剪，再投影

Context 构建是一条两级流水线，输入是「当前分支的全部 Entry」，输出是「发给模型的消息」。先提醒一处容易混淆的地方：本章有两个同名的 buildSessionContext——核心 harness 线的（packages/agent/src/harness/session/context.ts，本节）与生产 canonical 线的（packages/coding-agent/src/core/session-manager.ts，5.5）——前者服务 runtime/Lane 实现，后者服务第 8 章的 AgentSession。

图 5.1：Context 构建两级管线。pathEntries → contextEntries → messages 是主轴；核心线的运行状态（模型/思考级/工具）独立存放在 pi.lane.config/{lane} 簿记值里。输出的 messages 再经第 3 章 convertToLlm 发往 LLM。
packages/agent/src/harness/session/context.ts — 总装（async，只出消息）
typescriptexport async function buildSessionContext(
  pathEntries: readonly Entry[],
  options: SessionContextBuildOptions | undefined,
  context: Context,
): Promise<AgentMessage[]> {
  options ??= {};
  const entries = buildContextEntries(pathEntries);      // ① 裁剪：Entry[] → Entry[]
  const messages: AgentMessage[] = [];
  for (const entry of entries) {
    if (entry.type !== "custom") {
      messages.push(...sessionEntryToContextMessages(entry));  // ② 投影：同步那三种
      continue;
    }
    // custom → 查 projector（可能 async），没配就跳过
    const projector = options.entryProjectors?.[entry.customType];
    if (projector !== undefined) messages.push(...((await projector(entry, context)) ?? []));
  }
  return messages;
}
关键看三处： 只返回 messages——老版本会「顺带」派生模型/思考/工具状态，现在那件事完全归 lane 配置值管（5.4），投影管线变纯粹了。投影是逐条 await 的 for...of 而非 flatMap，因为 projector 可以是异步的。custom 条目在总装里分发：sessionEntryToContextMessages 对 custom 一律返回 []，真正的投影由 entryProjectors[customType] 在总装处做——没配 projector 的 custom 条目静默消失，不会报错。另外第三参 context 原样透传给 projector，扩展可以从中拿运行时信息。

裁剪：buildContextEntries 决定留哪些 entry

packages/agent/src/harness/session/context.ts — 找最近一次 compaction，前置
typescriptexport function buildContextEntries(pathEntries: readonly Entry[]): Entry[] {
  let compaction: CompactionEntry | undefined;
  let compactionIndex = -1;
  for (let index = pathEntries.length - 1; index >= 0; index--) {  // 从新到旧找
    const entry = pathEntries[index];
    if (entry?.type === "compaction") { compaction = entry; compactionIndex = index; break; }
  }
  return compaction === undefined
    ? [...pathEntries]                                        // 没压缩过：全量保留
    : [compaction, ...pathEntries.slice(compactionIndex + 1)]; // 有：摘要前置 + 尾巴
}
别误读「丢掉之前」： 丢的是压缩点之前的原始消息（它们已被摘要吸收），但 compaction 条目本身被拎到最前并保留——[compaction, ...之后的尾巴]。所以模型看到的是「摘要 + 最近细节」，而非「啥也没了」。这个函数没有任何 options 参数——扩展点只剩投影一侧（5.2 末的 projector），结构裁剪是写死的默认策略。生产 canonical 线的同名函数（5.5）更精细：按 firstKeptEntryId 保留压缩点之前的保留区。

图 5.2：一个实例。6 条 entry → ① 裁剪丢掉 C4 之前的 2 条（已被摘要吸收）、C4 前置，得 4 条 → ② 投影把 C4 展开成「摘要+尾巴」、X5 交给 async projector，共 6 条消息。custom 条目若没配 projector，会在这里静默消失。
概括： 裁剪决定「留哪些 entry」（6→4），投影决定「一条变几条消息」（4→6，compaction 展开、custom 异步投影）——两步各自是纯函数，才能独立替换。

5.3投影规则：每个 Entry → 几条 LLM 消息

packages/agent/src/harness/session/context.ts — isContextMessage + sessionEntryToContextMessages
typescriptfunction isContextMessage(message: AgentMessage): boolean {
  return (
    message.role !== "assistant" ||
    (message.stopReason !== "error" && message.stopReason !== "aborted" && message.stopReason !== "deferred")
  );
}

export function sessionEntryToContextMessages(entry: Entry): AgentMessage[] {
  switch (entry.type) {
    case "message":
      return isContextMessage(entry.message) ? [entry.message] : [];
    case "compaction":
      return [
        createCompactionSummaryMessage(entry.summary, entry.tokensBefore, entry.timestamp),
        ...entry.retainedTail.filter(isContextMessage),   // 压缩点保留的尾巴，同样要过闸
      ];
    case "branch_summary":
      return entry.summary ? [createBranchSummaryMessage(entry.summary, entry.fromId, entry.timestamp)] : [];
    case "custom":
      return [];          // 不在这投：buildSessionContext 把 custom 分发给 entryProjectors
  }
}
  • message → 先过 isContextMessage 过滤：stopReason 为 error / aborted / deferred 的 assistant 消息被丢弃——出错的、被中断的、挂起待续的半截回复不进上下文，避免污染下一轮对话。
  • compaction → 展开为「1 条摘要假消息 + 保留尾巴」，且尾巴同样过闸（retainedTail.filter(isContextMessage)）——半截回复哪怕被压缩保留下来，也不该再喂给模型。
  • branch_summary → 有 summary 才投影出 1 条分支摘要假消息；entry.summary 为空则 []。
  • custom → 这里固定返回 []！投影不在本函数做——buildSessionContext 会查 entryProjectors[customType]（可能 async）并分发。没配 projector 的 custom 条目静默消失。

生产 canonical 线的投影函数更多三件活：custom_message 条目（有 display 字段，直接投影成 custom 消息进上下文）、compaction 附带的 systemMessage（压缩边界完整 prompt 快照，第 6 章）、以及 5.5 的 context_edit 套用。骨架一致：一条 entry → 0~N 条消息。

5.4运行状态：两层两种答案

「现在用什么模型、哪个思考级别、哪些工具激活」从哪来？两条实现线给出了两种答案，各自的约束不同：

  • 核心 harness 线（Lane/Lane）：状态是 pi.lane.config/{lane} 簿记值（第 4 章 4.3）——lane 启动时读一次，写入即生效。多个 lane 并存时各读各的值，读是 O(1)。
  • 生产 canonical 线（SessionManager）：状态是普通条目（thinking_level_change / model_change entry），投影函数沿当前路径扫到「最后一条」作为现值；buildSessionProjection 返回的 SessionProjection 就带着 {thinkingLevel, model} 两个字段。单文件 JSONL 自描述——重放即恢复，无需独立的值轨道。
session-manager.ts · getSessionContextSettings（canonical 线：沿路径扫状态条目）
typescriptfunction getSessionContextSettings(path: SessionEntry[]): Pick<SessionContext, "thinkingLevel" | "model"> {
  let thinkingLevel = "off";
  let model: { provider: string; modelId: string } | null = null;
  for (const entry of path) {
    if (entry.type === "thinking_level_change") thinkingLevel = entry.thinkingLevel;
    else if (entry.type === "model_change") model = { provider: entry.provider, modelId: entry.modelId };
    else if (entry.type === "message" && entry.message.role === "assistant")
      model = { provider: entry.message.provider, modelId: entry.message.model };   // 兜底：最后一条回复的模型
  }
  return { thinkingLevel, model };
}
两种答案怎么选： 关键差异是「分支语义」。Lane 线天生多分支（每 lane 一棵子树 + 自己的 config），值必须带地址隔离；canonical 线是单主会话（分叉即造新文件），沿路径扫条目既拿到现值、又免费拿到「切换历史」（哪一轮换的模型，UI 回放时可见）。共同点更重要：状态都不混进「投影出的消息内容」——压缩/裁剪动得了消息，动不了「现在该用什么模型」。核心线先看 lane 写入（演示），再看两线对比。
packages/agent/src/harness/runtime/lane.ts — 配置就是一次 value 写入（核心线）
typescriptprivate async setConfiguration(
  update: (configuration: LaneState["configuration"]) => LaneState["configuration"],
  event: (previous, value) => LaneConfigEventPayload,
  context: Context,
): Promise<void> {
  await this.command((state) => {
    const configuration = update(state.configuration);
    return {
      kind: "commit",
      // 就这一个 value 写：模型/思考级/激活工具打包成一个配置对象
      writes: [setValue(laneConfig(this.name), configuration)],
      next: { ...state, configuration },   // 内存里立即生效
      materialize: () => undefined,
      events: () => [{ ...event(state.configuration, configuration), lane: this.name }],
    };
  }, context);
}
左侧是三个命令（切模型 / 调思考级 / 换工具），每执行一个就提交一次 value 写，右侧 pi.lane.config/main 立即更新；重启后 restoreSession 扫这个值即可恢复
配置不是「从历史里推出来的」，而是「谁最后写谁生效」的一个值——恢复时读值即可，无需重放任何条目。canonical 线的「扫条目」版本语义相同，只是「值」换成了「最后一条状态条目」。

5.5追加式上下文编辑：context_edit 与规范投影

最后一个问题最难：消息流 append-only，「改历史」从哪进来？生产 canonical 线的答案是加一种条目：context_edit——它不改目标条目，而是追加一条「编辑指令」，指明「哪个条目（targetId）在模型上下文里该呈现成什么」：

session-manager.ts · ContextEditEntry（注释为译注）
typescript/** Content that an append-only context edit may replace without changing message metadata. */
export type ContextEditableContent =
  | UserMessage["content"]
  | AssistantMessage["content"]
  | ToolResultMessage["content"]
  | CustomMessage["content"];

/** Append-only change to one earlier entry's contribution to model context. */
export interface ContextEditEntry extends SessionEntryBase {
  type: "context_edit";
  targetId: string;                          // 指向更早的 message / custom_message 等条目
  /** Null omits the target from model context. A value replaces only its content. */
  replacement: { content: ContextEditableContent } | null;   // null = 从模型上下文里隐去
}
读懂这个类型： 三个设计决定值得留意。其一，replacement 是「内容替换」而非「整条替换」——消息的 id、role、timestamp 等元数据原样保留，只换 content；其二，null 有专门语义「从模型上下文省略」——这正是第 6 章溢出恢复用来「隐去失败尝试」的手段（appendContextEdit(targetId, null)）；其三，可编辑范围用类型收窄到四种角色（user/assistant/toolResult/custom）——system 消息不在其列，prompt 状态不受追加式编辑影响。API 侧是 SessionManager.appendContextEdit(targetId, replacement)：只追加、不回改，同一 targetId 可以被编辑多次——同分支上最后一条生效。

这些编辑在哪一步生效？在 buildSessionProjection——v0.87 把它立为 canonical 线的唯一投影入口，返回值从裸消息数组升级成带来源的结构：

session-manager.ts · buildSessionProjection（行号 543 起；节选，注释为译注）
typescriptexport function buildSessionProjection(
  entries: SessionEntry[], leafId?: string | null, byId?: Map<string, SessionEntry>,
): SessionProjection {
  const path = buildSessionPath(entries, leafId, byId);          // 树 → 当前路径
  const { thinkingLevel, model } = getSessionContextSettings(path);   // ③ 沿路径扫状态
  const contextEntries = buildContextEntries(entries, leafId, byId);  // ② 裁剪（firstKeptEntryId 语义）
  // 收集编辑指令：同 targetId 后写覆盖先写（同分支最后一条生效）
  const edits = new Map<string, ContextEditEntry>();
  for (const entry of contextEntries) {
    if (entry.type === "context_edit") edits.set(entry.targetId, entry);
  }
  const projectedEntries = contextEntries.map(
    (sourceEntry, index): ProjectedSessionEntry => ({
      sourceEntry,
      // 老压缩条目若被保留在保留区里（其裸 id 在最新保留范围内），只有
      // index 0 的最新 compaction 贡献 checkpoint 与摘要，其余投影为空
      messages: sourceEntry.type === "compaction" && index > 0
        ? []
        : projectContextEntry(sourceEntry, edits.get(sourceEntry.id)),
    }),
  );
  return {
    entries: projectedEntries,                          // 带来源：sourceEntry → messages
    messages: projectedEntries.flatMap((entry) => entry.messages),
    thinkingLevel, model,
  };
}
与核心线相比多了四件活。一是带来源：每条投影消息都能溯源到 sourceEntry——第 6 章的切割点算法、压缩的「保留区」都要靠它把「消息」映射回「条目」；二是 firstKeptEntryId 裁剪：canonical 线的 compaction 条目带 firstKeptEntryId，裁剪保留「压缩点之前从它开始的保留区」，比核心线「一刀切」更省（保留区里 5.4 的状态条目也因此能被扫到）；三是状态随投影返回：thinkingLevel/model 一次算出，调用方不必再扫；四是编辑套用：projectContextEntry 在普通投影之后查 edits.get(sourceEntry.id)——有编辑就替换 content，replacement === null 整条隐去，assistant/toolResult 的字符串替换归一化成单个 text block（provider 那侧只认 content block）。
图 5.3：追加式编辑。edit#1、edit#2 都指向 M3，投影时 Map 收敛后 edit#2 生效——M3 从模型上下文隐去，而 transcript 里的三条原始条目一条未动。「改历史」被搬到了投影层。
为什么这么设计 「改历史」有两条路：回改原条目（破坏 append-only，崩溃恢复与审计全毁），或追加编辑指令、投影时套用（历史不可变，修正可追溯、可撤销——删掉编辑条目即还原）。Pi 选后者，而且把「谁在投影里生效」收敛成一条规则：同分支最后一条编辑赢。第 6 章的溢出恢复（隐去失败尝试）、压缩的 retain-none 语义，都建立在这层之上。

5.6两条真实调用链

两条线各有自己的取数入口，「会话树 → 上下文 → LLM」是每一轮模型调用前的必经之路：

链路总括（核心线：runtime/transcript.ts + drive/generation.ts；生产线：agent-session.ts）
text核心线（runtime/Lane，每轮生成前主动取）：
lane 状态.tipId ──scanBranch({stopAtType:"compaction", order:"newestFirst"})──> 原始 Entry[]
      └─ .reverse() ──> 旧→新的 pathEntries
            └─ buildSessionContext(entries, {entryProjectors}, context)   ← transcript.ts:69 readBoundedContext
                 ├─ buildContextEntries（① 裁剪：最近 compaction 前置）
                 └─ sessionEntryToContextMessages / entryProjectors（② 投影）
                      └─> AgentMessage[] ──transform_context 钩子──> LLM

生产 canonical 线（AgentSession，prepareRequest 被动接管）：
每次 provider 请求前（含第一次，第 8 章 8.2b）
      └─ this.sessionManager.buildSessionProjection()    ← session-manager.ts:543
           ├─ buildSessionPath → 裁剪 → 收集 context_edit → projectContextEntry
           └─> { entries, messages, thinkingLevel, model }
      └─ 用投影的 messages 整体替换请求 context；model/thinkingLevel 同步刷新
两条线的分工： 核心线是「生成入口主动调投影」（readBoundedContext，generation.ts:101），扩展点在 entryProjectors（异步 custom 投影）；生产线是「钩子被动接管请求」——prepareRequest 每次请求前用 buildSessionProjection().messages 整体替换上下文，让 SessionManager 成为唯一事实来源。共同的后半程也一样：AgentMessage[] → convertToLlm → provider Message[]（第 3 章），再由 pi-ai 的 normalizeContext 折叠（第 10 章）。

5.7投影速查表

两条线合并成一张表——「什么条目，投影出什么」：

条目投影出什么（进上下文）在哪条线
message · assistant (stopReason=error/aborted/deferred)（无——isContextMessage 丢弃）两线同
message · user / assistant / toolResult / system1 条消息（元数据原样）两线同
compaction1 条摘要（+canonical 线附带 systemMessage 快照）+ 保留尾巴（过闸）两线同，细节不同
branch_summary（有 summary）1 条分支摘要假消息两线同
custom（核心线，无 projector / 有 projector）（无） / 0~N 条，await projector(entry, context)核心线
custom（canonical 线，display/state 条目）（无——纯状态条目，重放恢复扩展内部状态用）canonical 线
custom_message1 条 custom 消息（display 控制 TUI 渲染，不影响上下文）canonical 线
context_edit → targetId套用到目标条目的投影：换 content，或 null 整条隐去canonical 线
thinking_level_change / model_change（不投影成消息；被 ③ 扫成现值）canonical 线

最终发给 LLM 的是：压缩摘要 + 过滤后的尾巴 + 最近的消息 + custom 投影 + 套用编辑后的修正。而「当前用什么模型」不在消息里——核心线读 lane 值，canonical 线由投影随行返回。

5.8收尾：四个答案

  • 条目怎么变消息？逐条投影：message 出 1 条（半截回复过闸丢弃）、compaction 展开成摘要+尾巴、branch_summary 出 1 条摘要、custom 走 projector（核心线）或 custom_message 直投影（canonical 线）。
  • 留哪些丢哪些？裁剪到最近压缩点：核心线「摘要前置 + 之后全留」；canonical 线按 firstKeptEntryId 连保留区一起留。原始条目永远不删——丢的只是「投影」。
  • 运行状态从哪来？不混进消息：核心线是 pi.lane.config 值（O(1) 读写），canonical 线沿路径扫状态条目、由投影随行返回。压缩/裁剪动不了它。
  • 历史还能改吗？context_edit 追加式编辑：投影时按 targetId 套用，最后一条生效；replacement: null 整条隐去。transcript 永不回改，修正全在投影层。
要点 给自研者四条：把「上下文管理」做成独立的纯函数（输入条目 → 输出消息），不要散落在循环里；用「条目 → 投影」而非「直接存消息」，才能支持压缩摘要、分支摘要、自定义投影、追加式编辑——Pi 能加 context_edit 这种新机制而不用改存储格式，正是因为消息从来不是存储的一等公民，投影才是；运行状态别混进上下文，它是独立的值或独立的状态条目，读写便宜、恢复即得；扩展点宁少而稳——一个 async projector（核心线）就够覆盖「注入/隐藏/改写」，给用户改「结构」的自由，往往意味着压缩策略失效。
