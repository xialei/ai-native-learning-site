上下文构建 Context：决定「模型这一轮看到什么」

★ 本站在意的最核心一章。上一章我们把会话存成了「树的条目」；这一章讲清这些条目如何被挑选、重排、投影成一串能发给 LLM 的消息——这才是 Agent 的「记忆」真正呈现在模型面前的地方。
产品视角 「真正的上下文工程。」 Pi 的极简系统提示加上可扩展性，让你能真正掌控上下文窗口装什么、怎么管：AGENTS.md 在启动时从 ~/.pi/agent/、父目录、当前目录加载项目指令；SYSTEM.md 按项目覆盖或追加默认提示；Compaction 在逼近上下文上限时自动摘要旧消息，且可由扩展改写（话题级压缩、代码感知摘要、换摘要模型）；→ Skills 按需载入、提示模板 /name 展开、扩展还能在每轮前注入消息 / 过滤历史 / 做 RAG。本章看其中最核心的「投影」是怎么发生的。

5.1一句话版本

Context 构建是一条两级流水线，输入是「当前分支的全部 Entry」，输出是「发给模型的消息」。运行状态（模型/思考级别/激活工具）不在这条管线里——它们是 pi.lane.config/{lane} 簿记值，由 lane 直接读（见 5.4）：

图 5.1：Context 构建两级管线。pathEntries → contextEntries → messages 是主轴；运行状态（模型/思考级/工具）独立存放在 pi.lane.config/{lane} 簿记值里。输出的 messages 再经第 3 章 convertToLlm 发往 LLM。
为什么要分两级，而不是一步到位？ 因为这两步解决的是两个不同的问题，混在一起就没法独立替换：① 裁剪管「留哪些 entry」（token 控制，第 6 章压缩在这介入）；② 投影管「一条 entry 变成几条消息」（compaction 会展开成「摘要+尾巴」多条，custom 交给 projector，见 5.3）。把它们拆成纯函数，才能让「换压缩策略」「换投影方式」各自演进。而「现在该用什么模型/思考级别」根本不是从历史推出来的——它是 lane 配置值，见 5.4。

5.2两步：谁干啥，数据怎么流

buildSessionContext 是总装函数，内部两步——先裁剪、再投影。注意它是 async 的：custom 条目的 projector 可能要查库/查文件，所以整个函数返回 Promise<AgentMessage[]>，只产出消息，不管状态：

packages/agent/src/harness/session/context.ts — 总装（async，只出消息）
typescriptexport async function buildSessionContext(
  pathEntries: readonly Entry[],
  options: SessionContextBuildOptions | undefined,
  context: Context,
): Promise<AgentMessage[]> {
  options ??= {};
  const entries = buildContextEntries(pathEntries);      // ① 裁剪：Entry[] → Entry[]
  const messages: AgentMessage[] = [];
  for (const entry of entries) {
    if (entry.type !== "custom") {
      messages.push(...sessionEntryToContextMessages(entry));  // ② 投影：同步那三种
      continue;
    }
    // custom → 查 projector（可能 async），没配就跳过
    const projector = options.entryProjectors?.[entry.customType];
    if (projector !== undefined) messages.push(...((await projector(entry, context)) ?? []));
  }
  return messages;
}
关键看三处： ① 只返回 messages——老版本会「顺带」派生模型/思考/工具状态，现在那件事完全归 lane 配置值管（5.4），投影管线变纯粹了。② 投影是逐条 await 的 for...of 而非 flatMap，因为 projector 可以是异步的。③ custom 条目在总装里分发：sessionEntryToContextMessages 对 custom 一律返回 []，真正的投影由 entryProjectors[customType] 在总装处做——没配 projector 的 custom 条目静默消失，不会报错。另外第三参 context 原样透传给 projector，扩展可以从中拿运行时信息。

① 裁剪：buildContextEntries —— 留哪些 entry

packages/agent/src/harness/session/context.ts — 找最近一次 compaction，前置
typescriptexport function buildContextEntries(pathEntries: readonly Entry[]): Entry[] {
  let compaction: CompactionEntry | undefined;
  let compactionIndex = -1;
  for (let index = pathEntries.length - 1; index >= 0; index--) {  // 从新到旧找
    const entry = pathEntries[index];
    if (entry?.type === "compaction") { compaction = entry; compactionIndex = index; break; }
  }
  return compaction === undefined
    ? [...pathEntries]                                        // 没压缩过：全量保留
    : [compaction, ...pathEntries.slice(compactionIndex + 1)]; // 有：摘要前置 + 尾巴
}
别误读「丢掉之前」： 丢的是压缩点之前的原始消息（它们已被摘要吸收），但 compaction 条目本身被拎到最前并保留——[compaction, ...之后的尾巴]。所以模型看到的是「摘要 + 最近细节」，而非「啥也没了」。这个函数没有任何 options 参数——扩展点只剩投影一侧（5.5），结构裁剪是写死的默认策略。

一个具体例子：压缩前后的上下文

假设当前分支从旧到新是 6 条 entry（M=message、C=compaction、X=custom），下面是它走完整条管线的样子：

图 5.2：一个实例。6 条 entry → ① 裁剪丢掉 C4 之前的 2 条（已被摘要吸收）、C4 前置，得 4 条 → ② 投影把 C4 展开成「摘要+尾巴」、X5 交给 async projector，共 6 条消息。custom 条目若没配 projector，会在这里静默消失。
一句话记住： ① 裁剪决定「留哪些 entry」（6→4），② 投影决定「一条变几条消息」（4→6，compaction 展开、custom 异步投影）——消息可压缩，但「当前模型/工具」根本不在消息里，它是 lane 配置值。

5.3投影规则：每个 Entry → 几条 LLM 消息

packages/agent/src/harness/session/context.ts — isContextMessage + sessionEntryToContextMessages
typescriptfunction isContextMessage(message: AgentMessage): boolean {
  return (
    message.role !== "assistant" ||
    (message.stopReason !== "error" && message.stopReason !== "aborted" && message.stopReason !== "deferred")
  );
}

export function sessionEntryToContextMessages(entry: Entry): AgentMessage[] {
  switch (entry.type) {
    case "message":
      return isContextMessage(entry.message) ? [entry.message] : [];
    case "compaction":
      return [
        createCompactionSummaryMessage(entry.summary, entry.tokensBefore, entry.timestamp),
        ...entry.retainedTail.filter(isContextMessage),   // 压缩点保留的尾巴，同样要过闸
      ];
    case "branch_summary":
      return entry.summary ? [createBranchSummaryMessage(entry.summary, entry.fromId, entry.timestamp)] : [];
    case "custom":
      return [];          // 不在这投：buildSessionContext 把 custom 分发给 entryProjectors
  }
}
读懂这段（极其重要）：
  • message → 先过 isContextMessage 闸门：stopReason 为 error / aborted / deferred 的 assistant 消息被丢弃——出错的、被中断的、挂起待续的半截回复不进上下文，避免污染下一轮对话。
  • compaction → 展开为「1 条摘要假消息 + 保留尾巴」，且尾巴同样过闸（retainedTail.filter(isContextMessage)）——半截回复哪怕被压缩保留下来，也不该再喂给模型。
  • branch_summary → 有 summary 才投影出 1 条分支摘要假消息；entry.summary 为空则 []。
  • custom → 这里固定返回 []！投影不在本函数做——buildSessionContext 会查 entryProjectors[customType]（可能 async）并分发。没配 projector 的 custom 条目静默消失。

5.4运行状态：不在投影管线里，在 lane 配置值里

「现在用什么模型、哪个思考级别、哪些工具激活」不再从历史条目里扫出来——它们是 pi.lane.config/{lane} 簿记值（第 4 章），lane 启动时读一次，之后写入即生效：

packages/agent/src/harness/runtime/lane.ts — 配置就是一次 value 写入
typescriptprivate async setConfiguration(
  update: (configuration: LaneState["configuration"]) => LaneState["configuration"],
  event: (previous, value) => LaneConfigEventPayload,
  context: Context,
): Promise<void> {
  await this.command((state) => {
    const configuration = update(state.configuration);
    return {
      kind: "commit",
      // 就这一个 value 写：模型/思考级/激活工具打包成一个配置对象
      writes: [setValue(laneConfig(this.name), configuration)],
      next: { ...state, configuration },   // 内存里立即生效
      materialize: () => undefined,
      events: () => [{ ...event(state.configuration, configuration), lane: this.name }],
    };
  }, context);
}
读懂这段 + 三条读写路径： 配置是一个 JSON 值（LaneConfiguration = {model, thinkingLevel, activeToolNames}，session/types.ts:69），不是条目。读：getModel/getThinkingLevel/getActiveTools 直接读内存里的 this.state.configuration；写：setModel/setThinkingLevel/setActiveTools 走 setConfiguration 提交 value 写（如上）；恢复：重启时 restoreSession 用 scanValues(laneConfig("")) 一次性扫出所有 lane 的配置（runtime/restore.ts），与 branch tip、lane state 一起重建运行时。对比老设计（把切换记成 model_change 等 Entry 再扫历史）：值读取是 O(1)，不用扫全分支；且压缩/裁剪永远动不了它——这正是第 4 章「Entry 树与簿记值分离」的直接受益者。
左侧是三个命令（切模型 / 调思考级 / 换工具），每执行一个就提交一次 value 写，右侧 pi.lane.config/main 立即更新；重启后 restoreSession 扫这个值即可恢复
配置不是「从历史里推出来的」，而是「谁最后写谁生效」的一个值——恢复时读值即可，无需重放任何条目。

5.5唯一的扩展点：entryProjectors

packages/agent/src/harness/session/context.ts — options + projector 签名
typescript// 构建选项里只有一个扩展点：custom 条目投影器
export interface SessionContextBuildOptions {
  entryProjectors?: Readonly<Record<string, EntryProjector>>;
}

// projector：把一个 custom 条目变成 LLM 消息（异步、两参、可返回 undefined）
export type EntryProjector = (
  entry: CustomEntry,
  context: Context,            // 透传运行时上下文（buildSessionContext 的第三参）
) => AgentMessage[] | undefined | Promise<AgentMessage[] | undefined>;
读懂这段： 扩展点收敛成了一个——老的 entryTransforms（改条目数组结构的 transform 链）已从源码里移除，结构裁剪收敛为写死的 compaction 策略；想要「隐藏/改写条目结构」，现在只能在投影层做减法：projector 返回 [] 或 undefined 即可把某个 custom 条目从上下文里隐掉。第二个参数 context 让 projector 能拿到运行时信息，异步返回意味着 projector 可以查库、查文件后再决定给模型看什么。生产 harness 用 custom 条目承载「工具产物摘要 / 分支导航」等信息，再配 projector 决定它们如何出现在上下文里。

5.6从会话树到 LLM：真实调用链

buildSessionContext 产出的是 AgentMessage[]。之后走第 3 章说过的转换，最终到 Message[] 发往 LLM。这条「会话树 → 上下文 → LLM」的链路就是一次 run 中每一轮模型调用前的必经之路。生产 harness 的入口在 runtime/drive/generation.ts：

链路总括（runtime/transcript.ts + runtime/drive/generation.ts）
text每次生成前的取数（runtime/transcript.ts）：
lane 状态.tipId ──scanBranch({stopAtType:"compaction", order:"newestFirst"})──> 原始 Entry[]
      └─ .reverse() ──> 旧→新的 pathEntries
            └─ buildSessionContext(entries, {entryProjectors}, context)
                 ├─ buildContextEntries（① 裁剪：最近 compaction 前置）
                 └─ sessionEntryToContextMessages / entryProjectors（② 投影）
                      └─> AgentMessage[]

发往 LLM 前的最后一跳（generation.ts 的 streamHarnessAssistant 调用）：
AgentMessage[] ──transformContext（transform_context 钩子链，可改 messages/systemPrompt）
      ──> toProviderMessages ──> Message[] ──> LLM
关键点： 「会话树构建的上下文」替代了第 3 章里那个朴素 context.messages——生成入口 readBoundedContext 每轮直接调 buildSessionContext（transcript.ts:69），让「模型看到什么」完全由会话树驱动；而 transform_context 钩子是树上构建完成之后的最后一道可编程关（可改消息、也可改系统提示），由 lane.hooks.runWithGate("transform_context", ...) 触发。

5.7一个「思考粒度」示例

假设分支里有这些条目（从新到旧示意）：

Entry投影出什么（进上下文）
message · assistant (stopReason=deferred)（无——isContextMessage 丢弃）
message · assistant (stopReason=error/aborted)（无——isContextMessage 丢弃）
message · toolResult1 条 toolResult 消息
message · assistant1 条 assistant 消息
message · user1 条 user 消息
compaction1 条摘要 + retainedTail（过滤后）若干条
custom（无 projector）（无——静默消失）
custom（配了 projector）0~N 条，await projector(entry, context)
（compaction 更早的…）（被 buildContextEntries 丢掉）

最终发给 LLM 的是：压缩摘要 + 过滤后的尾巴 + 最近的 user/assistant/toolResult + custom 投影。而「当前用什么模型」不在消息里——它是 pi.lane.config/{lane} 值，生成准备阶段读出后传给循环。

5.8对自研与使用的启示

要点 ① 把「上下文管理」做成独立的纯函数（输入条目 → 输出消息），不要散落在循环里。② 用「条目 → 投影」而非「直接存消息」，才能支持压缩摘要、分支摘要、自定义投影。③ 运行状态别混进上下文：模型/思考/工具是带地址的配置值，读写 O(1)、恢复即读，别学老设计扫历史重推。④ 扩展点宁少而稳：一个 async projector（条目 → 消息）就够覆盖「注入/隐藏/改写」三类需求；给用户改「结构」的自由，往往意味着压缩策略失效。
