生产 Harness：裸循环到稳定会话之间缺什么

★ 本站在意的另一半，落地版。第 7 章是 AgentHarness 契约；这一页走进 packages/coding-agent/src/core/agent-session.ts（约 4000 行）——把第 3 章的基础循环变成「可排队、可恢复、可分叉、可持久化」的完整 Agent 会话。用户的输入走一条固定流水线进来，模型每次看到的上下文由 SessionManager 投影接管，扩展在 turn_end / agent_before_settle 这些边界上能真正改写会话，跑完一轮后还有一套重试→压缩→续跑的自动驾驶。这些逐一拆开看。

8.1从契约到实现，中间隔着什么

第 7 章看过 packages/agent/src/harness/agent-harness.ts 里的 AgentHarness 契约——注意那是同包 runtime/ 里 Harness/Lane 的一条实现线，而这一页的 AgentSession 是另一条自主实现线（直接组合 Agent 类 + SessionManager，不实现 AgentLane）。从「能跑的循环」到「跑得稳的生产会话」，中间隔着四件事：用户的一句话怎么进运行时（拦截、改写、展开、入队，先后顺序由什么决定）？模型每次看到的上下文从哪来（第 5 章的投影逻辑，谁负责装进每次 provider 请求）？扩展在哪能真正改写会话（「通知」和「可操作」的事件边界差在哪，凭什么保证扩展写不坏上下文）？一轮跑完之后谁说了算（重试、压缩、续跑、结算的顺序怎么排）？

答案地图 输入流水线在 8.2，上下文接管在 8.2b（prepareRequest 接管 + prepareNextTurn 刷新），扩展边界在 8.4（事件桥、context 拆分、可操作边界），收敛在 8.5（收敛三段式 + agent_settled）；8.3 双队列、8.6 会话替换作为支撑件穿插。先把结论放在前面：AgentSession 不是另一个循环，而是循环外面的一层壳——它用四根接管钩子（prepareRequest / prepareNextTurnWithContext / finishTurn / transformContext）把裸循环的每个开放边界都换成自己的实现。
要点：两层的分界是「可测试的纯核心 vs 带副作用的壳」。基础层不碰 IO，canonical 层才能被单测反复打。你自己做 Agent Runtime 时也值得这样切——核心循环越纯，越好验证。

这一章后面会散落很多机制点（流水线、队列、事件桥、收敛、换会话），先在这里把它们钉在一个心智模型上，免得读着读着丢了主线。

问题答案
它是什么 生产 harness = AgentSession 这个类，把裸的 agentLoop 包成一个"有记忆、能恢复、可排队、可扩展"的会话对象。它不是另一个循环，而是循环外面的一层壳。
靠什么实现 靠一段写死的顺序流程，不是声明式配置、也不是 prompt。整个 prompt() 就是一条按固定步骤走的方法体（命令 → 钩子 → 展开 → 校验 → 压缩预检 → before_agent_start → _runAgentPrompt），每一步硬编码在前一步之后。韧性（重试 / 压缩 / 续跑）同样硬编码在 _handlePostAgentRun 的 while 循环里。系统提示词只决定"模型怎么想"，这段流程才决定"运行时怎么跑"。
没有它会怎样 退回第 3 章的 agentLoop：能跑一轮，但——不落盘（进程一退会话全没）、流式中无法安全追加/打断用户输入（没有 steer/followUp）、遇到错误或超长不会自救（没有重试/溢出压缩）、扩展挂不进去（没有 before_agent_start / input 等钩子）、运行中无法换会话（没有 teardown/apply 协议）。用户感知到的"Agent 越跑越稳、从不崩、能续上"，几乎全部来自这层壳，而不是 LLM 本身。
概括： harness 用固化流程把"会跑的循环"变成"跑得稳、跑得久、跑得能被观测和介入"的运行时。下面逐段拆这条流程；8.7 再把它收成一张清单。

8.2一次 prompt 的完整旅程

入口是 AgentSession.prompt(text, options)。别看这一条方法，它就是上面说的那段写死的顺序流程——把「用户敲的一句话」变成「LLM 循环上的一次运行」，中间要过十几个环节。全程时序如下：

图 8.2：prompt() 是一条固定顺序的流水线（命令 → 钩子 → 展开 → 流式则入队，否则 flush/校验/压缩预检 → before_agent_start → _runAgentPrompt）。三处可短路返回：扩展命令 handled、input 钩子 handled、流式入队。

看真实代码。第 1 步扩展命令是最快的短路——以 / 开头的指令若命中注册命令，直接执行并返回，根本不进 LLM：

agent-session.ts · prompt() 前半段（扩展命令 + input 钩子 + 技能展开）
// 1. 优先执行扩展命令（流式中也立即执行，命令自管 LLM 交互）
if (expandPromptTemplates && text.startsWith("/")) {
  const handled = await this._tryExecuteExtensionCommand(text);
  if (handled) { preflightResult?.(true); return; }
}

let currentText = text;
let currentImages = options?.images;
// 2. input 事件：扩展可完全接管（handled）或改写（transform）
if (this._extensionRunner.hasHandlers("input")) {
  const inputResult = await this._extensionRunner.emitInput(
    currentText, currentImages, options?.source ?? "interactive",
    this.isStreaming ? options?.streamingBehavior : undefined,
  );
  if (inputResult.action === "handled") { preflightResult?.(true); return; }
  if (inputResult.action === "transform") {
    currentText = inputResult.text;
    currentImages = inputResult.images ?? currentImages;
  }
}

// 3. 技能 /skill:name 与 prompt 模板展开为完整文本
this._expandSkillCommand(expandedText);
expandedText = expandPromptTemplate(expandedText, [...this.promptTemplates]);
读懂三个「短路」：扩展命令（1）、input 钩子（2）都能完全吞掉这一次输入（handled），不让它进 LLM；技能/模板（3）则把一句话展开成一大段塞进上下文。三者顺序固定——先给最高优先级、最便宜的拦截机会。

流水线的后半段（before_agent_start 事件之后）有个容易误读的顺序决定——消息数组的构建被刻意推迟到钩子跑完之后：

agent-session.ts · prompt() 中段：钩子之后才归一化图片、才 build messages（节选，注释为译注）
// 6. before_agent_start 先行 —— 此时 selectedTools 已定，模型也可能被扩展换掉
const result = await this._extensionRunner.emitBeforeAgentStart(expandedText, currentImages, ...);
// 扩展显式改了 selectedTools 就尊重它，没改则以运行时真实 loadout 为准
if (!handlerEditedTools) result.systemPromptOptions.selectedTools = this.getActiveToolNames();

// 7. 这之后才做图片归一化 —— 用的正是 before_agent_start 里选定的模型的画像
const normalized = await this._normalizePromptImages(currentImages);
const userText = normalized.hints.length > 0 ? `${expandedText}\n\n${normalized.hints.join("\n")}` : expandedText;

// 8. Build messages only after hooks and image normalization have completed.
messages = [];
const userContent = [{ type: "text", text: userText }, ...normalized.images];
messages.push({ role: "user", content: userContent, timestamp: Date.now() });
// nextTurn 结转消息、before_agent_start 返回的 custom 消息随后依次入列
为什么图片归一化非得等钩子跑完？缩放档案（maxWidth/maxBytes 等）来自当前模型的画像（第 10 章的 inputLimits.images.resize）。而 before_agent_start 里扩展可以切模型——若先缩放后切模型，图片就按旧模型的档案编码了。处理顺序的依据是「这条数据会被谁消费」：图片要跟着模型走，用户文本则不需要。顺带一提，处理失败的图片不会静默丢弃——失败原因作为 hint 文本追加在用户消息后面，让模型知道「你少看到一张图、为什么」。同一条归一化也盖住工具返回的图片（normalizeToolResultImages，在扩展钩子之后跑，扩展注入的图同样被处理），以及 read 工具读到的图片文件——三处共用模型档案，保证「进历史之前先对齐」。

8.2b模型面前的上下文：四根接管钩子

裸 Agent 循环把四个边界留成了公开钩子（第 3 章）；生产 harness 在构造函数里把四根全部接管（_installAgentNextTurnRefresh / _installAgentRequestProjection / _installAgentBoundaryHooks，再加 8.5 提到的 _installAgentForcedPromptProjection 包 transformContext）。其中最根本的一根是 v0.87 新装的 prepareRequest 投影——它让 SessionManager 的投影成为模型上下文的唯一来源：

agent-session.ts · _installAgentRequestProjection（行号 608 起；注释为译注）
private _installAgentRequestProjection(): void {
  const previousPrepareRequest = this.agent.prepareRequest;
  this.agent.prepareRequest = async (request, signal) => {
    // 每次会话请求（含第一次）前，用 SessionManager 的投影替换 agent 手里的消息
    const canonicalContext = {
      ...request.context,
      messages: this.sessionManager.buildSessionProjection().messages,
      // 消息声明 provider 看得见的 loadout；context.tools 保留可执行的实现
      tools: this.agent.state.tools.slice(),
    };
    // 再链上既有的 prepareRequest（比如强制 prompt 投影），以它返回值为准
    const previous = await previousPrepareRequest?.({ ...request, context: canonicalContext, ... }, signal);
    return {
      ...previous,
      context: previous?.context ?? canonicalContext,
      model: previous?.model ?? this.agent.state.model,
      thinkingLevel: previous?.thinkingLevel ?? this.agent.state.thinkingLevel,
    };
  };
}
这根钩子回答了 8.1 的第二个问题。它的位置选得很准：prepareRequest 在每次 provider 请求前触发、且此时 pending 消息（steering/follow-up）已经写入 agent 状态——所以投影永远包含最新内容；它能整体替换 context/model/thinkingLevel，所以换模型、改 thinking 都不需要循环知情。另一根 prepareNextTurnWithContext 接管则负责「turn 之间的重活」：先 _compactBeforeNextAssistantResponse（token 过阈值就先压缩），再重算系统提示 + 工具 loadout（_preparePromptAndToolLoadout），有变化就产出一条 patch system 消息随下轮注入。两根钩子各管一头——投影管「每次请求发什么」，prepareNextTurn 管「turn 之间要不要先动手术」。

8.3流式时的双消息队列：steer vs followUp

最难的地方：Agent 正在跑（流式），用户又发了一条消息，怎么办？Pi 用「双队列」解决，打破了你朴素的一声一答模型。先看关键判断——prompt() 检测到流式中时，强制你要么 steer 要么 followUp：

agent-session.ts · 流式时入队（注释为译注）
// 正在流式：必须显式声明是打断还是等待
if (this.isStreaming) {
  if (!options?.streamingBehavior) {
    throw new Error("Agent is already processing. Specify streamingBehavior ('steer' or 'followUp') to queue the message.");
  }
  if (options.streamingBehavior === "followUp") {
    await this._queueFollowUp(expandedText, currentImages);
  } else {
    await this._queueSteer(expandedText, currentImages);
  }
  preflightResult?.(true);
  return;
}

两种入队的差别，看底层实现（AgentSession 维护两条数组，再转发给基础包的 Agent）：

agent-session.ts · _queueSteer / _queueFollowUp（注释为译注）
private async _queueSteer(text: string, images?: ImageContent[]): Promise<void> {
  this._steeringMessages.push(text);      // 记录待投递（用于 UI 展示）
  this._emitQueueUpdate();
  const content: (TextContent | ImageContent)[] = [{ type: "text", text }];
  if (images) content.push(...images);
  this.agent.steer({ role: "user", content, timestamp: Date.now() });  // 只入队，不 await
}
private async _queueFollowUp(text: string, images?: ImageContent[]): Promise<void> {
  this._followUpMessages.push(text);
  this._emitQueueUpdate();
  const content: (TextContent | ImageContent)[] = [{ type: "text", text }];
  if (images) content.push(...images);
  this.agent.followUp({ role: "user", content, timestamp: Date.now() });  // 等当前动作做完再投
}

区分与投递时机：

队列语义何时投给 LLM
steer（打断）「别干这个了，先听我的」在 Tool 动作边界截断当前行动，立即注入下一条 user 消息
followUp（跟随）「把这个记下来，做完手上的再说」在 Agent 没有更多 Tool 调用或无 steer 等待时才交付
nextTurn（结转）「这一轮末尾追加的上下文」随下一条 user 消息一起作上下文注入（见 prompt 里 _pendingNextTurnMessages）

基础包的 Agent 类实际维护着这些队列，并提供两种投递模式；v0.87 还补了一个不消费的预览口：

packages/agent/src/agent.ts · peekQueuedMessages（行号 327 起）
// 队列模式 QueueMode: "all" 或 "one-at-a-time"（默认每次只投最旧一条）
// 预览：下一个 turn 将送出哪条排队消息，但不消费它（UI 展示用）
peekQueuedMessages(): AgentMessage[] {
  const steering = this.steeringQueue.peek();
  return steering.length > 0 ? steering : this.followUpQueue.peek();
}
为什么需要双队列？打断语义天然比「排队等」急迫。你在终端里按 Esc 想叫停 Agent 去读另一个文件，这是 steer；你顺手补一句「对了记得用 Vite」是 followUp。UI（TUI）正是靠 queue_update 事件把两侧队列实时画出来。你的 Runtime 若支持中断/追加，照抄这对队列即可。

8.4事件桥：Agent 事件 → 扩展 → 监听器 → 会话落盘

基础包的 Agent 只发 AgentEvent。生产层要做的两件事：(a) 把它转成扩展事件喂给 ExtensionRunner；(b) 把 message_end 落盘到 SessionManager。这就是 _handleAgentEvent，一块事件枢纽：

看真实的落盘分流（这是持久化的核心，读 _handleAgentEvent）：

agent-session.ts · message_end 时按类型落盘
if (event.type === "message_end") {
  // 自定义消息 → CustomMessageEntry（保留 customType / display / details）
  if (event.message.role === "custom") {
    this.sessionManager.appendCustomMessageEntry(
      event.message.customType, event.message.content,
      event.message.display, event.message.details,
    );
  }
  // 常规 LLM 消息（含 system）→ SessionMessageEntry（第 4 章讲过）
  else if (
    event.message.role === "system" ||
    event.message.role === "user" ||
    event.message.role === "assistant" ||
    event.message.role === "toolResult"
  ) {
    this.sessionManager.appendMessage(event.message);
  }
  // bashExecution / compactionSummary / branchSummary 在别处单独落盘
}

注意 system 消息也在落盘之列——系统提示如今是消息流里的一条条 SystemMessage，跟着普通消息一起持久化（它怎么来的，见 8.5 的三个写入时机）。注意事件在扩展层可以改写和拦截。工具调用先过 emitToolCall——扩展可以 block 它；助手消息结束过 emitMessageEnd——扩展可返回替换消息（这正是一致性/审校型扩展的挂点）。

顺序很重要：先是 _emitExtensionEvent(event)（给扩展，允许改写），再 _emit(...)（给 UI 监听器，只读展示），最后 appendMessage（落盘）。改写在先、展示在中、存盘在后——三层各吃一份，互不阻塞。

上下文转换事件的拆分：context 与 context_with_system

扩展挂进请求前的最后一道转换 context，v0.87 把它的可见范围收紧了：handler 只看得到对话消息，看不到 system（prompt + 工具声明）。pi 在每个 handler 跑完后把 prompt 状态恢复回去；只有需要完整转写的场景才走另一扇门 context_with_system：

extensions/runner.ts · emitContext 两段派发（行号约 1192；摘录，注释为译注）
// 第一段：context handler 只看对话
const visibleMessages = currentMessages.filter((m) => m.role !== "system");
const returned = await handler({ type: "context", messages: visibleMessages }, ctx);
// handler 完毕后恢复 prompt 状态：若返回的消息列表没变，转写原样保留（缓存前缀不破）；
// 变了则把当前 system 头部接回去，作为唯一的前置 system 消息
currentMessages = restoreSystemMessages(currentMessages, visibleSnapshot, returned);

// 第二段：context_with_system handler 拥有完整转写，输出原样采用
const hadLeadingSystemMessage = currentMessages[0]?.role === "system";
currentMessages = handlerResult?.messages ?? currentMessages;
// provider 从头部 system 消息读 prompt 与初始工具——丢了它请求就没有 prompt，
// 所以检查并报错（但尊重 handler 的输出）
if (hadLeadingSystemMessage && currentMessages[0]?.role !== "system") {
  // "Handler removed the leading system message; … Keep it at index 0 …"
}
两扇门怎么选 绝大多数动态上下文（RAG、注入记忆、过滤历史）只关心对话，走 context——pi 替你把 prompt 状态保护起来，返回未改动时还能保住缓存前缀。只有「请求级、必须拿到完整转写」的转换（如导出审计、转写级重排）才走 context_with_system，且结果原样采用，你得自己保证 index 0 是 system 消息。

除了这种「转换流」事件，扩展还有两个可操作边界：turn_end 与 agent_before_settle。它们能链式提出要写入会话的条目（custom / custom_message / context_edit / compaction 四种草稿）并请求一次续跑。写入安全由 emitBoundary 保证：

extensions/runner.ts · emitBoundary（行号 928 起；摘录，注释为译注）
async emitBoundary(baseEvent, buildContext): Promise<BoundaryDispatchResult> {
  let entries = [], shouldContinue = false, valid = true;
  let context = await buildContext(entries);     // 用「当前草稿集」预览上下文
  for (const { ext, handlers } of snapshotEventHandlers(this.extensions, baseEvent.type)) {
    for (const handler of handlers) {
      const event = { ...baseEvent, entries, continue: shouldContinue, context };
      const handlerResult = await handler(event, ctx);
      if (handlerResult?.entries !== undefined) entries = handlerResult.entries;   // 链式累积
      if (handlerResult?.continue !== undefined) shouldContinue = handlerResult.continue;
      context = await buildContext(entries);    // 每轮重算预览：新草稿必须能投影出合法上下文
      valid = true;                             // 投影失败 → valid = false，全部草稿作废
    }
  }
  return valid ? { entries, continue: shouldContinue, ... } : { entries: [], continue: false, ... };
}
边界为什么这么设计 每个草稿都即时重算预览，等于「先在沙盘上推演，推演失败就整体撤销」——扩展永远不能把「模型面前的上下文」写坏，最多是自己的提案被丢弃。continue: true 的语义与第 3 章 finishTurn 相同：保证一次下一请求，且 AgentSession 会校验「当前上下文确实跑得动一次请求」（canContinue 检查，见 _buildBoundaryContext）——凭空 continue 而上下文以 assistant 结尾、也没有排队消息，会被拒绝并报错。

8.5运行后收敛：重试 → 压缩 → 续跑 → 结算

一次 agent.prompt 结束（发出 agent_end）不等于整件事结束。生产模型在这一帧做「自动驾驶」：要不要重试？要不要压缩？队列里还有消息吗？能结算了吗？看 _runAgentPrompt 的主循环：

agent-session.ts · _runAgentPrompt 主循环（行号约 1470；注释为译注）
await this.agent.prompt(messages);
while (!this._agentRunAbortRequested) {
  if (await this._handlePostAgentRun()) {          // 重试/压缩/队列有活 → 续跑
    if (this._agentRunAbortRequested) break;
    await this.agent.continue();
    continue;
  }
  // 收敛到头：过最后一道可操作边界 agent_before_settle
  // （扩展仍可追加条目、请求一次续跑；返回 false 才结算）
  if (this._agentRunAbortRequested || !(await this._runBeforeSettleBoundary())) break;
  await this.agent.continue();
}
finally { // 结算是通知，不是决策：清临时 prompt、冲刷排队消息、发 agent_settled
  this._runSystemPromptOptions = undefined;
  this._flushPendingBashMessages();
  this._flushPendingCustomMessages();
  await this._emitAgentSettled();
}

收敛顺序的表达力：重试优先于压缩，压缩优先于兜底续跑，续跑之后才允许结算。判断「要不要」的逻辑堆积在三个函数里，生产版比基础 harness 契约多了「自动重试」这一维。重试的关键判断是 _willRetryAfterAgentEnd（回扫最后一条 assistant，看是否可重试错误且未超 maxRetries）：

agent-session.ts · 是否要在 agent_end 后自动重试
private _willRetryAfterAgentEnd(event): boolean {
  const settings = this.settingsManager.getRetrySettings();
  if (!settings.enabled || this._retryAttempt >= settings.maxRetries) return false;
  for (let i = event.messages.length - 1; i >= 0; i--) {
    if (event.messages[i].role === "assistant")
      return this._isRetryableError(event.messages[i]);
  }
  return false;
}

压缩分支是第 6 章的接驳处。_checkCompaction 处理三类自动触发并带一堆「防误触发」守卫（三类都汇入同一个 _runAutoCompaction()）：

  • 溢出 + 重试（overflow with retry）：assistant 因上下文溢出而错误或可恢复截断。此时先用 context_edit 把失败尝试持久化省略（_omitRecoveryAttempt，第 6 章 6.5b 详过），压缩后作为全新 run 重试；_overflowRecoveryAttempted 保证只试一次，避免死循环。
  • 溢出但不重试（overflow without retry）：一次成功的响应仍超出了上下文窗口。此时压缩，但保留这条已完成的响应、不重试——溢出不是错误，所以不丢工作成果。
  • 阈值（threshold without retry）：上下文用量（实际或估计）越过阈值，静默压缩，同样不重试。会话里有 context_edit 时用量改由 estimateProjectedContextTokens 按投影计算。
  • 守卫：换模型后跳过旧模型的溢出判断；「消息比最近一次压缩还旧」就不再次触发（避免刚压完又被旧 usage 拉回）；aborted 消息默认跳过；若 assistant 之后的省略编辑已把它的回复清空（latestAssistantEdit?.replacement === null），溢出判断也不再触发——那次尝试已经从模型上下文里隐去了。

注意「怎么知道溢出了」这个判断本身的分工：识别逻辑（错误文本正则 + usage 兜底 + 零输出贴窗检测）收在 pi-ai 的 isContextOverflow（第 10 章 10.3.1 详过），生产层只负责消费它。_isRetryableError 的实现因此只有三行，且顺序是设计：先排除溢出，再问可重试——溢出由压缩管道负责，重试管道不越界。重试与压缩不是竞争关系，而是按错误类型分流的两条管道。

这是「自适应收敛」的精髓：基础 harness 契约只定义了「有 compaction 操作」；生产层负责自己判断何时触发、何时不触发。除了「跑完后」的收敛线，还有两根「开跑前」的线：8.2b 的 prepareNextTurnWithContext 接管（每 turn 前按估算压缩 + 重算 loadout），以及压缩前给扩展的 session_before_compact 钩子——扩展可以拿到准备对象并 cancel 掉压缩。所有这些「自动驾驶」叠加起来，就是用户感知里「Agent 自己越跑越聪明、尽量不因上下文超限而中断」的来源。

结算的最后两站：agent_before_settle 与 agent_settled

_handlePostAgentRun 全部说「不用续」之后，循环不立即退出——先过 _runBeforeSettleBoundary：

agent-session.ts · _runBeforeSettleBoundary（行号 1531 起；摘录，注释为译注）
private async _runBeforeSettleBoundary(): Promise<boolean> {
  if (!this._extensionRunner.hasHandlers("agent_before_settle")) return this.agent.hasQueuedMessages();
  const result = await this._extensionRunner.emitBoundary(
    { type: "agent_before_settle", outcome: this._lastActivityOutcome },
    (entries) => this._buildBoundaryContext(entries, "agent_before_settle"),
  );
  this._commitBoundaryDrafts(result.entries);   // 草稿此刻才真正写入会话
  this._flushPendingCustomMessages();
  // continue 有效的前提：修复后的投影能跑一次请求（canContinue 校验）
  const shouldContinue = result.continue || this.agent.hasQueuedMessages();
  if (shouldContinue && !finalContext.canContinue) { …报错…; return false; }
  return shouldContinue;
}

它俩的分工写在扩展文档里：agent_before_settle 是最后一个可操作边界——能追加条目、请求一次续跑（重试/恢复/压缩/排队消息带来的续跑都在它之前完成）；agent_settled 则纯通知——发给「需要知道 Pi 不会再自动继续」的集成方，它返回什么都不会改变调度，其中的延迟动作也不可重入（_isEmittingAgentSettled 守卫着不重入）。_emitAgentSettled 还会顺带唤醒空闲等待（_resolveIdleWaitIfIdle）与触发缓存预热回调（cacheWarmer.onAgentSettled）。

系统提示的三个写入时机

8.4 里那句「system 消息也在落盘之列」值得展开。系统提示是消息流里的状态，而生产 harness 在三个时机写它：

  • 会话启动：_baseSystemPromptOptions 经 _preparePromptAndToolLoadout() 生成第一条 system 消息，随 agent_start 进入消息流。
  • 每次 before_agent_start：扩展可以在 event.systemPromptOptions 上改 selectedTools 等字段（或干脆用 forceSystemPrompt 塞一段完全自定义的 prompt——这段文本不进 transcript，发请求时由 transformContext 投影成头部 system 消息，见下面的小节）。生产层把改完的选项交给 _preparePromptAndToolLoadout()，它对比「消息流里当前生效的 sections」和「现在该有的」，有差异就产出一条新的 system 消息 unshift 进本次输入。注意那个 handlerEditedTools 判断：扩展显式改了 selectedTools 就尊重它，没改则以运行时真实 loadout 为准——避免「扩展没动、但 loadout 已经被 setActiveTools() 改过」的情况被旧值覆盖。
  • finally 收尾：_runSystemPromptOptions = undefined——本次运行挂的临时 prompt 设置（_runSystemPromptOptions 优先于 _baseSystemPromptOptions）只活一次运行，跑完即清。
agent-session.ts · _preparePromptAndToolLoadout（节选，注释为译注）
private _preparePromptAndToolLoadout(options, messages = this.agent.state.messages) {
  options.selectedTools = [...new Set(options.selectedTools)].filter((name) => this._toolRegistry.has(name));
  this.agent.state.tools = ...;                     // 让 agent 能执行的工具对齐
  // 只对 prompt 的 section 做差量：拿「消息流里当前生效的 sections」和「现在该有的」比
  const sections = diffSystemPromptSections(
    getCurrentSystemMessage(messages)?.sections ?? {},   // 重放出来的当前状态
    buildSystemPromptSections(options),                  // 现在该有的结构化 sections
  );
  // 有变化 → 产出一条只带 sections 补丁的 system 消息；没变化 → undefined（不发）
  return sections ? { role: "system", content: "", sections, timestamp: Date.now() } : undefined;
}
这段函数经历过一次值得记住的简化：早先它有两条产出路径——sections 差量补丁，或整段 content + replace: true 的替换消息（处理「扩展用 forceSystemPrompt 塞进来一整段不透明 prompt」的情况）。后来 replace 字段被整体删除：扩展强制注入的 prompt 是「本次请求临时渲染出来的文本」，不是对话状态——把它持久化进 transcript，会每次变更都重写一遍完整 prompt、丢掉结构化 sections，还让之后的中途 system 消息全部失效。如今的分工是：transcript 里只存结构化 sections（所以这里永远只做差量）；强制文本在发请求时才投影——_installAgentForcedPromptProjection() 在 agent.transformContext 外再包一层，若本次运行设了 forceSystemPrompt，就把 system 消息收拢成一条持有强制文本的头部消息，加上当前工具声明。transcript 与请求从「同一条消息流」解耦成「状态层 + 请求层」（重放规则见 第 10 章）。

8.6会话替换：换会话、新建、分叉与优雅收尾

生产 Agent 还能在运行中间换会话、分叉、导入 JSONL——对应到用户侧的斜杠命令是 /resume（恢复别的会话）、/new（开新会话）、/fork（从某条消息分叉）、/import（导入 JSONL）。它们背后都由 AgentSessionRuntime 统一管理，关键是任何替换都先完整地拆掉旧运行时。看替换公共流程（以 switchSession 为例，即 /resume 走的路径）：

agent-session-runtime.ts · switchSession
async switchSession(sessionPath, options?) {
  // 1. 先问扩展：允许切吗？（session_before_switch 可取消）
  const beforeResult = await this.emitBeforeSwitch("resume", sessionPath);
  if (beforeResult.cancelled) return beforeResult;

  const previousSessionFile = this.session.sessionFile;
  // 2. 打开目标会话，校验其 cwd 存在
  const sessionManager = SessionManager.open(sessionPath, undefined, options?.cwdOverride);
  assertSessionCwdExists(sessionManager, this.cwd);

  // 3. 拆旧：abort → session_shutdown 事件 → UI 摘除 → dispose
  await this.teardownCurrent("resume", sessionManager.getSessionFile());

  // 4. 建新运行时并套用
  this.apply(await this.createRuntime({ cwd, agentDir, sessionManager,
    sessionStartEvent: { type: "session_start", reason: "resume", previousSessionFile } }));

  // 5. 重绑会话引用，跑 withSession 回调
  await this.finishSessionReplacement(options?.withSession);
  return { cancelled: false };
}

拆旧顺序是整页最应当照着做的一段：

agent-session-runtime.ts · teardownCurrent —— 优雅收尾
private async teardownCurrent(reason, targetSessionFile?) {
  // 1. 先把当前响应的工具结果等落盘（abort 会妥善收尾）
  await this.session.abort();
  // 2. 发 session_shutdown 事件，给扩展一个钩子
  await emitSessionShutdownEvent(this.session.extensionRunner,
    { type: "session_shutdown", reason, targetSessionFile });
  // 3. 同步回调：主机 UI 在旧扩展上下文变 stale 前摘除组件
  this.beforeSessionInvalidate?.();
  // 4. dispose 释放资源
  this.session.dispose();
}

顺序的讲究：abort → shutdown 事件 → UI 摘除 → dispose。abort 保证「切换到新会面前，旧会话的当前 turn（含工具结果）已持久化」；shutdown 事件给扩展留清理钩子；beforeSessionInvalidate 特意做成同步回调（注释写明「不能把控制权交还事件循环」），因为要在旧的扩展上下文失效前摘掉扩展提供的 TUI 组件。分叉（fork）则复用同一套拆装，只是目标会话要先用 createBranchedSession(targetLeafId) 造一个分支 JSONL。

给你做 Runtime 的启示：「替换运行时」不是简单地session = newSession()。它需要一份严格的拆装协议——先持久化未决状态、再广播退场、再置换、再广播入场。顺序错了，轻则丢数据，重则扩展到旧会话的悬垂引用。Pi 在 agent-session-runtime.ts 里把这份协议收得很干净。

8.7收尾：四问的答案

  • 输入怎么进？prompt() 一条固定流水线：扩展命令 → input 钩子 → 技能/模板展开 → 流式则强制入 steer/followUp 队列 → flush bash → 模型/鉴权校验 → 压缩预检 → before_agent_start → _runAgentPrompt。三个可短路点（命令、钩子、入队），一个「钩子之后才归一化」的顺序决定。
  • 上下文从哪来？四根接管钩子把裸循环的开放边界全部换掉：prepareRequest 装投影（SessionManager 是唯一上下文来源）、prepareNextTurnWithContext 做 turn 间手术、finishTurn 桥接扩展边界、transformContext 投影强制 prompt。
  • 扩展在哪能改写会话？转换流两扇门（context 只看对话 / context_with_system 拥有完整转写）；可操作边界（turn_end / agent_before_settle）四种草稿链式累积、沙盘预演、失败整体作废，continue 需过 canContinue 校验。
  • 跑完谁收敛？重试→压缩→续跑的 while 循环，配三类压缩守卫与一次性的溢出恢复；收敛到头后 agent_before_settle 仍可追加条目续跑一次，最终 agent_settled 纯通知——集成方由此知道 Pi 不会再动。
