生产 Harness：agent-session 里的真实运行时

★ 本站在意的另一半，落地版。第 7 章看到的是AgentHarness接口契约；这一页走进 packages/coding-agent/src/core/agent-session.ts（约 3300 行）——把第 3 章的基础循环变成「可排队、可恢复、可分叉、可持久化」的完整 Agent 会话。它是你未来做 Agent Runtime 时最该抄的样板。

8.1从契约到实现：为什么有「两个 harness」

第 7 章看过 packages/agent/src/harness/agent-harness.ts 里的 AgentHarness 契约——注意那是同包 runtime/ 里 Harness/Lane 的一条实现线，而这一页的 AgentSession 是另一条自主实现线（直接组合 Agent 类 + SessionManager，不实现 AgentLane）。真正干活的主体在 coding-agent 包里：

分工很明确：

  • 基础包（右侧列之外）：纯「消息吞吐机」。它不知道消息要落盘、不知道 API key，也不知道 Bash 工具。只保证「给一串消息，正确地跑出一个 Loop」。
  • 生产 harness（右侧列）：把基础包装在壳里。它负责持久化（agent 事件 → SessionManager.appendMessage）、鉴权（模型/API key 校验）、恢复（压缩、重试、溢出恢复）、排队（steer/followUp）、以及扩展事件（ExtensionRunner 让第三方能挂进生命周期）。
要点：两层的分界是「可测试的纯核心 vs 带副作用的壳」。基础层不碰 IO，canonical 层才能被单测反复打。你自己做 Agent Runtime 时也值得这样切——核心循环越纯，越好验证。

那 Harness 到底"是"什么？怎么实现的？没有它会怎样？

这一章后面会散落很多机制点（队列、事件桥、持久化、收敛、换会话），先在这里把它们钉在一个心智模型上，免得读着读着丢了主线。

问题答案
它是什么 生产 harness = AgentSession 这个类，把裸的 agentLoop 包成一个"有记忆、能恢复、可排队、可扩展"的会话对象。它不是另一个循环，而是循环外面的一层壳。
靠什么实现 靠一段写死的顺序流程，不是声明式配置、也不是 prompt。整个 prompt() 就是一条按固定步骤走的方法体（命令 → 钩子 → 展开 → 校验 → 压缩预检 → before_agent_start → _runAgentPrompt），每一步硬编码在前一步之后。韧性（重试 / 压缩 / 续跑）同样硬编码在 _handlePostAgentRun 的 while 循环里。系统提示词只决定"模型怎么想"，这段流程才决定"运行时怎么跑"。
没有它会怎样 退回第 3 章的 agentLoop：能跑一轮，但——不落盘（进程一退会话全没）、流式中无法安全追加/打断用户输入（没有 steer/followUp）、遇到错误或超长不会自救（没有重试/溢出压缩）、扩展挂不进去（没有 before_agent_start / input 等钩子）、运行中无法换会话（没有 teardown/apply 协议）。用户感知到的"Agent 越跑越稳、从不崩、能续上"，几乎全部来自这层壳，而不是 LLM 本身。
一句话记住： harness 用固化流程把"会跑的循环"变成"跑得稳、跑得久、跑得能被观测和介入"的运行时。下面 8.2~8.6 逐段拆这条流程的每个闸门；8.7 再把它收成一张清单。

8.2一次 prompt 的完整旅程

入口是 AgentSession.prompt(text, options)。别看这一条方法，它就是上面说的那段写死的顺序流程——把「用户敲的一句话」变成「LLM 循环上的一次运行」，中间过了十几个闸门。全程时序如下：

图 8.2：prompt() 是一条固定顺序的流水线（命令 → 钩子 → 展开 → 流式则入队，否则 flush/校验/压缩预检 → before_agent_start → _runAgentPrompt）。三处可短路返回：扩展命令 handled、input 钩子 handled、流式入队。

看真实代码。第 1 步扩展命令是最快的短路——以 / 开头的指令若命中注册命令，直接执行并返回，根本不进 LLM：

agent-session.ts · prompt() 前半段（扩展命令 + input 钩子 + 技能展开）
// 1. 优先执行扩展命令（流式中也立即执行，命令自管 LLM 交互）
if (expandPromptTemplates && text.startsWith("/")) {
  const handled = await this._tryExecuteExtensionCommand(text);
  if (handled) { preflightResult?.(true); return; }
}

let currentText = text;
let currentImages = options?.images;
// 2. input 事件：扩展可完全接管（handled）或改写（transform）
if (this._extensionRunner.hasHandlers("input")) {
  const inputResult = await this._extensionRunner.emitInput(
    currentText, currentImages, options?.source ?? "interactive",
    this.isStreaming ? options?.streamingBehavior : undefined,
  );
  if (inputResult.action === "handled") { preflightResult?.(true); return; }
  if (inputResult.action === "transform") {
    currentText = inputResult.text;
    currentImages = inputResult.images ?? currentImages;
  }
}

// 3. 技能 /skill:name 与 prompt 模板展开为完整文本
this._expandSkillCommand(expandedText);
expandedText = expandPromptTemplate(expandedText, [...this.promptTemplates]);
读懂三个「短路」：扩展命令（1）、input 钩子（2）都能完全吞掉这一次输入（handled），不让它进 LLM；技能/模板（3）则把一句话展开成一大段塞进上下文。三者顺序固定——先给最高优先级、最便宜的拦截机会。

8.3流式时的双消息队列：steer vs followUp

最难的地方：Agent 正在跑（流式），用户又发了一条消息，怎么办？Pi 用「双队列」解决，打破了你朴素的一声一答模型。先看关键判断——prompt() 检测到流式中时，强制你要么 steer 要么 followUp：

agent-session.ts · 流式时入队
// 正在流式：必须显式声明是打断还是等待
if (this.isStreaming) {
  if (!options?.streamingBehavior) {
    throw new Error("Agent is already processing. Specify streamingBehavior ('steer' or 'followUp').");
  }
  if (options.streamingBehavior === "followUp") {
    await this._queueFollowUp(expandedText, currentImages);
  } else {
    await this._queueSteer(expandedText, currentImages);
  }
  preflightResult?.(true);
  return;
}

两种入队的差别，看底层实现（AgentSession 维护两条数组，再转发给基础包的 Agent）：

agent-session.ts · _queueSteer / _queueFollowUp
private async _queueSteer(text: string, images?: ImageContent[]): Promise<void> {
  this._steeringMessages.push(text);      // 记录待投递（用于 UI 展示）
  this._emitQueueUpdate();
  await this.agent.steer({ text, images }); // 打断正在进行的动作
}
private async _queueFollowUp(text: string, images?: ImageContent[]): Promise<void> {
  this._followUpMessages.push(text);
  this._emitQueueUpdate();
  await this.agent.followUp({ text, images }); // 等当前动作做完再投
}

区分与投递时机：

队列语义何时投给 LLM
steer（打断）「别干这个了，先听我的」在 Tool 动作边界截断当前行动，立即注入下一条 user 消息
followUp（跟随）「把这个记下来，做完手上的再说」在 Agent 没有更多 Tool 调用或无 steer 等待时才交付
nextTurn（结转）「这一轮末尾追加的上下文」随下一条 user 消息一起作上下文注入（见 prompt 里 _pendingNextTurnMessages）

基础包的 Agent 类实际维护着这些队列，并提供两种投递模式：

packages/agent/src/agent.ts · 队列模式
// QueueMode: "all" 或 "one-at-a-time"
// agent-loop 在每个边界（tool call / 一轮结束）检查队列：
//   one-at-a-time：每次只投最新一条 steer + 最新一条 followUp
//   all：同一批次全部投给 LLM
为什么需要双队列？打断语义天然比「排队等」急迫。你在终端里按 Esc 想叫停 Agent 去读另一个文件，这是 steer；你顺手补一句「对了记得用 Vite」是 followUp。UI（TUI）正是靠 queue_update 事件把两侧队列实时画出来。你的 Runtime 若支持中断/追加，照抄这对队列即可。

8.4事件桥与持久化：Agent 事件 → 会话落盘

基础包的 Agent 只发 AgentEvent。生产层要做的两件事：(a) 把它转成扩展事件喂给 ExtensionRunner；(b) 把 message_end 落盘到 SessionManager。这就是 _handleAgentEvent，一块事件枢纽：

看真实的落盘分流（这是持久化的核心，读 _handleAgentEvent）：

agent-session.ts · message_end 时按类型落盘
if (event.type === "message_end") {
  // 自定义消息 → CustomMessageEntry（保留 customType / display / details）
  if (event.message.role === "custom") {
    this.sessionManager.appendCustomMessageEntry(
      event.message.customType, event.message.content,
      event.message.display, event.message.details,
    );
  }
  // 常规 LLM 消息 → SessionMessageEntry（第 4 章讲过）
  else if (
    event.message.role === "user" ||
    event.message.role === "assistant" ||
    event.message.role === "toolResult"
  ) {
    this.sessionManager.appendMessage(event.message);
  }
  // bashExecution / compactionSummary / branchSummary 在别处单独落盘
}

注意事件在扩展层可以改写和拦截。工具调用先过 emitToolCall——扩展可以 block 它；助手消息结束过 emitMessageEnd——扩展可返回替换消息（这正是一致性/审校型扩展的挂点）。

顺序很重要：先是 _emitExtensionEvent(event)（给扩展，允许改写），再 _emit(...)（给 UI 监听器，只读展示），最后 appendMessage（落盘）。改写在先、展示在中、存盘在后——三层各吃一份，互不阻塞。

8.5运行后收敛：重试 → 压缩 → 续跑的三段式

一次 agent.prompt 结束（发出 agent_end）不等于整件事结束。生产模型在这一帧做「自动驾驶」：要不要重试？要不要压缩？队列里还有没有消息？看 _runAgentPrompt 和它的收敛函数：

agent-session.ts · prompt 后收敛循环
private async _runAgentPrompt(messages: AgentMessage | AgentMessage[]): Promise<void> {
  this._isAgentRunActive = true;
  try {
    await this.agent.prompt(messages);
    // 收敛：每次 continue 后再判断还要不要继续
    while (await this._handlePostAgentRun()) {
      await this.agent.continue();
    }
  } finally {
    this._systemPromptOverride = undefined;
    this._flushPendingBashMessages();
    this._flushPendingCustomMessages();   // 流式期间排队的 custom 消息，此刻落盘
    await this._emitAgentSettled();
  }
}

private async _handlePostAgentRun(): Promise<boolean> {
  const msg = this._lastAssistantMessage;
  this._lastAssistantMessage = undefined;
  if (!msg) return false;

  // 1. 可重试错误? → 准备重试并续跑
  if (this._isRetryableError(msg) && (await this._prepareRetry(msg))) return true;

  if (msg.stopReason === "error" && this._retryAttempt > 0) { /* 收尾 auto_retry_end 事件 */ }

  // 2. 需要压缩? → 压缩后继续
  if (await this._checkCompaction(msg)) return true;

  // 3. 队列还有消息（agent_end 扩展又追加了）? → 继续
  return this.agent.hasQueuedMessages();
}

收敛顺序的表达力：重试优先于压缩，压缩优先于兜底续跑。判断「要不要」的逻辑堆积在三个函数里，生产版比基础 harness 契约多了「自动重试」这一维。重试的关键判断是 _willRetryAfterAgentEnd（回扫最后一条 assistant，看是否可重试错误且未超 maxRetries）：

agent-session.ts · 是否要在 agent_end 后自动重试
private _willRetryAfterAgentEnd(event): boolean {
  const settings = this.settingsManager.getRetrySettings();
  if (!settings.enabled || this._retryAttempt >= settings.maxRetries) return false;
  for (let i = event.messages.length - 1; i >= 0; i--) {
    if (event.messages[i].role === "assistant")
      return this._isRetryableError(event.messages[i]);
  }
  return false;
}

压缩分支是第 6 章的接驳处。_checkCompaction 是生产 harness 里最精巧的函数之一，它处理三类自动触发并带一堆「防误触发」守卫（三类都汇入同一个 _runAutoCompaction()）：

  • 溢出 + 重试（overflow with retry）：assistant 因上下文溢出而错误或可恢复截断。此时先把被截断的 assistant 从 agent state 里剥掉（messages.slice(0, -1)），压缩后重试一轮；_overflowRecoveryAttempted 保证只试一次，避免死循环。
  • 溢出但不重试（overflow without retry）：一次成功的响应仍超出了上下文窗口。此时压缩，但保留这条已完成的响应、不重试——溢出不是错误，所以不丢工作成果。
  • 阈值（threshold without retry）：上下文用量（实际或估计）越过阈值，静默压缩，同样不重试。
  • 守卫：换模型后跳过旧模型的溢出判断；「消息比最近一次压缩还旧」就不再次触发（避免刚压完又被旧 usage 拉回）；aborted 消息默认跳过。
这是「自适应收敛」的精髓：基础 harness 契约只定义了「有 compaction 操作」；生产层负责自己判断何时触发、何时不触发。除了这条「跑完后」的收敛线，生产层还装了一条「开跑前」的线：_installAgentNextTurnRefresh 把 agent.prepareNextTurnWithContext 接管过来，每个 turn 开始前调 _compactBeforeNextAssistantResponse——若按估算 token 已过阈值，就先 _runAutoCompaction("threshold", false) 压一轮再让模型看到上下文。注意压缩前还会给扩展一个 session_before_compact 钩子——扩展可以拿到准备对象并 cancel 掉压缩。所有这些「自动驾驶」叠加起来，就是用户感知里「Agent 自己越跑越聪明、从不崩」的来源。

8.6会话替换：换会话、新建、分叉与优雅收尾

生产 Agent 还能在运行中间换会话、分叉、导入 JSONL——对应到用户侧的斜杠命令是 /resume（恢复别的会话）、/new（开新会话）、/fork（从某条消息分叉）、/import（导入 JSONL）。它们背后都由 AgentSessionRuntime 统一管理，关键是任何替换都先完整地拆掉旧运行时。看替换公共流程（以 switchSession 为例，即 /resume 走的路径）：

agent-session-runtime.ts · switchSession
async switchSession(sessionPath, options?) {
  // 1. 先问扩展：允许切吗？（session_before_switch 可取消）
  const beforeResult = await this.emitBeforeSwitch("resume", sessionPath);
  if (beforeResult.cancelled) return beforeResult;

  const previousSessionFile = this.session.sessionFile;
  // 2. 打开目标会话，校验其 cwd 存在
  const sessionManager = SessionManager.open(sessionPath, undefined, options?.cwdOverride);
  assertSessionCwdExists(sessionManager, this.cwd);

  // 3. 拆旧：abort → session_shutdown 事件 → UI 摘除 → dispose
  await this.teardownCurrent("resume", sessionManager.getSessionFile());

  // 4. 建新运行时并套用
  this.apply(await this.createRuntime({ cwd, agentDir, sessionManager,
    sessionStartEvent: { type: "session_start", reason: "resume", previousSessionFile } }));

  // 5. 重绑会话引用，跑 withSession 回调
  await this.finishSessionReplacement(options?.withSession);
  return { cancelled: false };
}

拆旧顺序是整页最值得抄的一段：

agent-session-runtime.ts · teardownCurrent —— 优雅收尾
private async teardownCurrent(reason, targetSessionFile?) {
  // 1. 先把当前响应的工具结果等落盘（abort 会妥善收尾）
  await this.session.abort();
  // 2. 发 session_shutdown 事件，给扩展一个钩子
  await emitSessionShutdownEvent(this.session.extensionRunner,
    { type: "session_shutdown", reason, targetSessionFile });
  // 3. 同步回调：主机 UI 在旧扩展上下文变 stale 前摘除组件
  this.beforeSessionInvalidate?.();
  // 4. dispose 释放资源
  this.session.dispose();
}

顺序的讲究：abort → shutdown 事件 → UI 摘除 → dispose。abort 保证「切换到新会面前，旧会话的当前 turn（含工具结果）已持久化」；shutdown 事件给扩展留清理钩子；beforeSessionInvalidate 特意做成同步回调（注释写明「不能把控制权交还事件循环」），因为要在旧的扩展上下文失效前摘掉扩展提供的 TUI 组件。分叉（fork）则复用同一套拆装，只是目标会话要先用 createBranchedSession(targetLeafId) 造一个分支 JSONL。

给你做 Runtime 的启示：「替换运行时」不是简单地session = newSession()。它需要一份严格的拆装协议——先持久化未决状态、再广播退场、再置换、再广播入场。顺序错了，轻则丢数据，重则扩展到旧会话的悬垂引用。Pi 在 agent-session-runtime.ts 里把这份协议收得很干净。

8.7把这一章装进你的 Runtime 清单

这一章的信息密度很高。把它压缩成一张「生产 harness 必备件」清单，也是你第 12 章自制 Runtime 的骨架：

能力Pi 的做法（文件）为什么缺它不行
输入管道prompt()：命令→钩子→展开→队列/校验没有统一入口，拦截/改写在别处无从挂
双队列steer / followUp / nextTurn流式中无法安全追加/打断用户输入
