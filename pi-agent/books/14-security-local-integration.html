安全边界、本地模型与程序化集成

这台「运行时」不光要跑得稳，还要敢在你不信任的地方跑、能在你没有网络时跑、能被你的代码当库调用。本章收拢三个「边界」话题：信任与沙箱（安全）、llama.cpp 本地模型接入（离线）、以及 SDK / RPC 的程序化嵌入（可编程）。它们共同回答了「一个能用的 Agent Runtime」的最后三个问题。
产品视角 「同一内核，四种形态；离线也能跑、被你的代码当库调。」 Pi 不只有交互式 TUI：pi -p 走 print/JSON 给脚本与 CI，stdin/stdout 传 JSONL 的 RPC 给非 Node 集成，SDK 把 Pi 当库嵌进你的应用（见 OpenClaw 这种真实落地）。想离线 / 重隐私？把 llama.cpp 本地服务器「伪装」成一个 Provider 就接上了。→ 本章看信任沙箱、本地模型适配、程序化嵌入这三条边界在源码里怎么收口。

14.1项目信任：一套可持久化、可继承的决策

Agent 会在你的工作目录里跑 Bash——它怎么知道「这个目录可以信任」?答案是 packages/coding-agent/src/core/trust-manager.ts，一套小而精的信任决策系统。核心是 TrustFile：路径 → 决策的一张表，决策只有三态 true / false / null。

trust-manager.ts · 信任表与「就近祖先」查询
type TrustFile = Record<string, boolean | null | undefined>;  // path → 是否可信

// 查一个 cwd 是否可信：从它自己开始，一路向父目录找最近的一个显式决策
function findNearestTrustEntry(data: TrustFile, cwd: string): ProjectTrustStoreEntry | null {
  let currentDir = normalizeCwd(cwd);
  while (true) {
    const value = data[currentDir];
    if (value === true || value === false) {
      return { path: currentDir, decision: value };   // 命中显式决策
    }
    const parentDir = dirname(currentDir);
    if (parentDir === currentDir) return null;        // 到根都没有 → 未决
    currentDir = parentDir;
  }
}

「就近祖先」是关键语义：你在 ~/work 下信任了 ~/work，那么 ~/work/repo-a、~/work/repo-b 都会被继承为可信，而无需逐目录确认。若某子目录被显式设为 false，又会盖过祖先的信任。这是一棵向上求最近决策的「决策继承树」。

落盘时还有三个讲究——排序、锁定、严格校验：

trust-manager.ts · 锁定 + 稳定写
function acquireTrustLockSync(path: string): () => void {
  // 用 proper-lockfile 在同一目录放 .lock，串行化并发写
  //   （多个 pi 进程同时信任/取消信任同一目录时不打架）
  return lockfile.lockSync(trustDir, { realpath: false, lockfilePath: `${path}.lock` });
}

function writeTrustFile(path: string, data: TrustFile): void {
  const sorted: TrustFile = {};
  for (const key of Object.keys(data).sort()) {        // 按键排序
    ...                                              // 稳定输出，便于 diff 与版本管理
  }
  mkdirSync(dirname(path), { recursive: true });
  writeFileSync(path, `${JSON.stringify(sorted, null, 2)}\n`, "utf-8");
}

配信任时的「选项推导」也很有品味——不是简单二选一，而是给你「信任 / 信任整个父目录 / 仅本次会话信任 / 不信任 / 仅本次会话不信任」等富选项。其中「信任父目录」会同时写父目录为 true、当前目录为 null（null 表示「跟随父目录」），让决策既持久又不过度扩散。

为什么这值得抄？信任系统的难点不在「信任」本身，而在「决策如何继承、如何持久化、如何并发安全」。Pi 用就近祖先 + 三态值 + proper-lockfile 把这三件事都收拾干净了。你做 Runtime 时，任何「跨进程、跨会话、要落盘的安全判断」都可以套这个模板：三态值、向上继承、加锁写、排序输出。

14.2沙箱边界：Bash 这道闸门

信任是「要不要问」；真正的隔离发生在 Bash 工具这条沙箱边界上。回顾第 9 章我们已经建立的图景：权限确认挂在 beforeToolCall 钩子上（第 8 章），stdout 由 output-guard 串行接管（第 9 章 §9.6）。这里补上 bash 自身的执行边界——它接住 AbortSignal 并杀掉整个进程树。

tools/bash.ts · 中止即杀全树
exec: async (command, cwd, { onData, signal, ... }) => {
  const child = spawn(..., { ... });
  // 记下子进程；外部 abort 时，不只是 kill 一个 pid，而是整棵进程树
  function onAbort() { killProcessTree(child); }   // 防止孤儿进程继续跑
  if (signal?.aborted) onAbort();
  else signal?.addEventListener("abort", onAbort, { once: true });
  // 输出经 onData 流式回传 → 上层 tool_execution_update
}

这里「杀整棵进程树」不是细节，而是安全与资源的基本盘：一条 sleep 100000 或一个 npm install，若只杀父进程，它的子进程会变成孤儿继续占机器、甚至继续写文件。Pi 用 exec 封装把进程树治理收拢成一处，配合第 9 章的 signal 参数，让「用户打断」真正落到 OS 层面。

再往外一层才是「把整个 pi 隔离起来」——那是容器化的范畴：用 Docker、Gondolin 或 OpenShell 把 pi 装进沙箱跑。此时「Agent 能碰到的」从「当前目录」缩小到「容器的文件系统」，Bash 执行的就不是宿主机命令而是容器内命令（bash-executor.ts 也支持 SSH/远端容器的远程执行）。这是信任模型之外真正的强隔离——信任是「软边界」（决定放行与否），容器是「硬边界」（决定能力范围）。

一句话区分：信任系统决定「要不要问」，beforeToolCall 钩子决定「放不放行」，AbortSignal→杀进程树决定「能不能停」，容器/Gondolin 决定「能碰到什么」。四层叠加才是完整的安全纵深。你自己做 Runtime 时，至少要把前两层（信任 + 放行）和「可中止」做扎实，容器化可以后补。

14.3本地模型：把 llama.cpp 变成一个 Provider

没有网络、在意隐私时，你想在本地跑模型。Pi 用第 10 章那套「多 Provider 抽象」顺手就接上了 llama.cpp——它根本不需要为本地模型造新机制，只需要一个「把本地 llama 服务器翻译成 Model/Provider」的适配器。

看两个关键翻译。一是 toPiModel——把 llama 服务器的模型信息映射成 Pi 的 Model 值对象（上下文窗口从 n_ctx 取，取不到回退 128000）：

extensions/llama/provider.ts · toPiModel
function toPiModel(model: LlamaModelInfo, serverUrl: string): Model<"openai-completions"> {
  const reportedContextWindow = model.meta?.n_ctx ?? model.meta?.n_ctx_train;
  const contextWindow =
    reportedContextWindow && reportedContextWindow > 0 ? reportedContextWindow : 128000;
  return {
    id: model.id, name: model.id,
    api: "openai-completions",      // 就借通用协议族
    provider: LLAMA_PROVIDER_ID,       // "llama.cpp"
    contextWindow, ...
  };
}

二是 Provider 的 stream/streamSimple 直接复用 pi-ai 的 OpenAI 兼容流，refreshModels 里还会先恢复「上次持久化的模型清单」，并从 catalog 里筛出可选模型作为活跃目录——判定由 modelIsSelectable 收口：

extensions/llama/provider.ts · 模型可选性判定
function modelIsSelectable(model: LlamaModelInfo, routerAutoload: boolean): boolean {
  if (model.status.value === "loaded")   return true;   // 已加载到内存，直接可路由
  // llama.cpp 把空闲休眠的模型报成 "sleeping"；发请求时会自动唤醒它
  if (model.status.value === "sleeping") return true;
  // 未加载的 preset 模型：只有 llama.cpp router 开了 autoload（首次用时自动加载）才可选
  return routerAutoload && model.status.value === "unloaded"
    && !model.status.failed && model.source === "preset";
}

// router 是否开了 autoload？先看 catalog 里有没有未加载的 preset，再问 server 的 /props
async function routerAutoloadEnabled(client, catalog, signal): Promise<boolean> {
  if (!catalog.some(m => m.status.value === "unloaded" && m.source === "preset")) return false;
  return (await client.props({ signal })).models_autoload === true;
}

models = catalog
  .filter((model) => modelIsSelectable(model, routerAutoload))   // loaded / sleeping /（autoload 时）未加载 preset
  .map((model) => toPiModel(model, serverUrl));
读懂这段：「可选」分三档——loaded（已驻留内存）、sleeping（休眠、发请求时唤醒）、unloaded preset（连内存都没进，但若 llama.cpp router 开了 models_autoload，首次请求会自动加载它）。前两档无条件可选，第三档要 routerAutoload 为真——而这个标志是 refreshModels 时调 LlamaClient.props() 问 server 的 /props 接口拿来的。注意 routerAutoloadEnabled 会先看 catalog 里有没有未加载 preset，没有就直接短路返回 false，避免无谓的 /props 往返。
最大的启示：接入本地模型没有造任何新机制——只是把一个本地服务器“伪装”成既有的 OpenAI 兼容 Provider。这正是第 10 章「统一协议抽象」的全部回报：一个新 Provider 的成本被压到「写一个适配器」。而 LlamaClient 负责的 list/load/unload/download/props/SSE watch，才是本地场景特有的「模型管理」逻辑（内存里该驻留哪几个模型、要不要先下载、router 能不能按需 autoload）。你把 /llama 这套「本地路由 + 按需加载」的思想用到自己 Runtime 的本地模型支持上，能省不少弯路。

14.4程序化集成：SDK、RPC 与 JSON 事件流

前面几章讲的是「人跟 Agent 交互」，这一节讲「你的程序跟 Agent 交互」——三种由浅入深的嵌入方式。

14.4.1 当库用：SDK

第 11 章已见 createAgentSession——它同时也是程序化嵌入的总入口。你把 pi 当模块 import 进自己的 Node 应用，一次调用拿到一个可 prompt/steer/abort 的 AgentSession。这正是学 Runtime 的你应该密切关注的那一条「公开 API 面」。

sdk.ts · 公开导出面
export async function createAgentSession(options): Promise<CreateAgentSessionResult>;
// 连带导出设计要用的类型：模型、工具、模板、技能…
export type { PromptTemplate } from "./prompt-templates.ts";
export type { Skill } from "./skills.ts";
export type { Tool } from "./tools/index.ts";

值得注意它把 PromptTemplate、Skill、Tool 这些「可注入素材」的类型也一并导出——嵌入方不仅能拿一个 session，还能复用 pi 的模板/技能/工具体系。这是「SDK 该导什么」的好示范：不只给运行时，还给素材与约定。

14.4.2 当服务用：RPC over stdin/stdout JSONL

想让外部进程驱动 pi（比如编辑器、CI、你自己的工具），最稳的通道是 RPC mode——通过 stdin/stdout 传 JSONL，每一行一个带 id 的请求或响应。看协议的命令集合：

modes/rpc/rpc-types.ts · RpcCommand
export type RpcCommand =
  | { id?: string; type: "prompt"; message: string; streamingBehavior?: "steer" | "followUp" }
  | { id?: string; type: "steer"; message: string }
  | { id?: string; type: "follow_up"; message: string }
  | { id?: string; type: "abort" }
  | { id?: string; type: "new_session"; parentSession?: string }
  | { id?: string; type: "set_model"; provider: string; modelId: string }
  | { id?: string; type: "compact"; customInstructions?: string }
  | { id?: string; type: "set_auto_compaction"; enabled: boolean } ...

这个命令集合几乎是「把第 8 章 AgentSession 的公开方法正面暴露了一遍」——prompt/steer/follow_up/abort 对应输入管道与队列，new_session/compact/set_model 对应会话与模型管理。它不是把内部对象丢给外部，而是精心收敛出一个“可行、可中断、可管理”的最小面。

RPC 的传输还匿名复用了第 9 章 §9.6 的 output-guard——响应要走 stdout，但 stdout 可能正被不知不觉地改动，于是 RPC 模式先 takeOverStdout 再 writeRawStdout，保证「协议行」干净、不被 UI 污染。这是把上一章那个「终端秩序」设计，直接复用到协议层的好例子。

14.4.3 结构化事件：JSON event stream

介于 print 与 RPC 之间还有 JSON event stream 模式——把原本打给人看的文本，换成结构化的 JSON 事件。它复用第 8 章那套事件语言（agent_start / turn_start / message_update…），让下游程序能按事件流式消费 Agent 的每一步进展，而不必自己去解析人类文本。

三者的取舍：SDK 最「深」但要把 pi 嵌进你的进程；RPC 最「稳、通用」，任何会跑子进程的语言都能驱动；JSON event stream 介于两者，偏「观察」。它们共享同一内核（第 8 章 AgentSession），只是外壳不同——这正是第 11 章「同一核心、多种外壳」的再一次印证。
