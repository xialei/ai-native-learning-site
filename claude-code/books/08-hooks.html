Hooks 生命周期：把你的逻辑焊进循环

★ 重点。循环的每个关节——工具调用前后、会话起止——都能挂你自己的脚本。这一章拆开 Hooks 的事件类型、stdin/stdout JSON 协议、退出码语义，并用仓库里真实的 Bash 命令校验器做范本。
定位 权限决定工具能不能跑，Hooks 决定跑前后插什么逻辑——拦危险、自动格式化、注入规范。 → 它是循环的「焊点」。

8.1一分钟版本

Hooks 让你在 agentic 循环的生命周期点上运行任意脚本。脚本的通信契约很简单：从 stdin 收一段 JSON，用 stdout / 退出码回话。最强大的是 PreToolUse——它能在工具执行前拦截，甚至阻止调用并把原因告诉模型，让模型换路。

本仓库里有大量真实用法：plugins/security-guidance 用 PostToolUse（编辑文件后审查；带 if 条件的 PostToolUse 在 git commit/git push 时触发深度复查）+ Stop（回合结束时把 diff 发给 LLM 复查）监测 25 类静态模式、Stop 时再交 LLM 做 45 类深度复查；plugins/explanatory-output-style 与 learning-output-style 用 SessionStart 注入教学上下文；plugins/ralph-wiggum 用 Stop 拦截退出、让循环继续。

8.3stdin/stdout JSON 协议

Hook 是一个被 Claude Code 拉起的进程。它从 stdin 读一段 JSON，包含会话与工具的上下文：

概念示例：PreToolUse 收到的 stdin JSON
json{
  "session_id": "abc123...",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",            // 要调的工具
  "tool_input": {
    "command": "grep -r foo src/"   // 工具的参数
  },
  "cwd": "/home/me/project"
}
读懂这段： Hook 拿到的是结构化的工具调用意图——工具名、参数、当前目录、会话 id。所以它能做精细判断：比如看到 tool_name=="Bash" 且 command 以 grep 开头，就建议改用 rg（这正是仓库范例做的事，见 §8.5）。

8.4退出码语义：控制的核心

Hook 怎么「回话」？靠退出码。这套语义是 Hooks 控制循环的核心：

退出码含义stdout/stderr 去向
0成功放行，继续执行工具stdout 给用户看（不给模型）
2阻止工具调用stderr 给模型看（模型会据此调整）
其他非零Hook 自身出错给用户看，不阻止执行
最关键的一招：退出码 2 退出码 2 不是简单拒绝，而是「教模型」——stderr 的内容会进入模型上下文，模型看到「为什么被拦」后会换策略。比如拦下 rm -rf 并写「禁止递归删除，请改用 git clean」，模型下一轮就真的会换。这让 Hook 成了可教学的护栏，而非死板的墙。

8.5真实范例：Bash 命令校验器

本仓库 examples/hooks/bash_command_validator_example.py 是一个完整的 PreToolUse Hook，它把 grep 改写成 rg、把 find -name 改写成 rg --files。先看它怎么在配置里挂上去：

settings.json — 挂载 PreToolUse Hook（来自范例文件头注释）
json{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",                 // 只匹配 Bash 工具
        "hooks": [
          {
            "type": "command",
            "command": "python3 /path/to/bash_command_validator_example.py"
          }
        ]
      }
    ]
  }
}

再看脚本本身的核心逻辑：

examples/hooks/bash_command_validator_example.py（真实仓库内容，节选）
pythonimport json, re, sys

# 校验规则：(正则, 提示) —— 命中就建议改用更优命令
_VALIDATION_RULES = [
    (r"^grep\b(?!.*\|)",
     "Use 'rg' (ripgrep) instead of 'grep' ..."),
    (r"^find\s+\S+\s+-name\b",
     "Use 'rg --files | rg pattern' instead of 'find -name' ..."),
]

def main():
    input_data = json.load(sys.stdin)            # 读 stdin JSON
    if input_data.get("tool_name") != "Bash":
        sys.exit(0)                              # 非 Bash，放行
    command = input_data.get("tool_input", {}).get("command", "")
    issues = [msg for pat, msg in _VALIDATION_RULES if re.search(pat, command)]
    if issues:
        for m in issues: print(f"• {m}", file=sys.stderr)
        sys.exit(2)                              # 退出码 2：阻止 + 告知模型原因
逐行读懂这段： ① 配置里 matcher:"Bash"——只对 Bash 工具触发，别的工具不惊动。② json.load(sys.stdin)——读入 §8.3 那段 JSON。③ 先判 tool_name——双保险，非 Bash 直接 exit 0 放行。④ 正则匹配命令——命中 grep/find -name 就收集提示。⑤ sys.exit(2)——阻止这次 Bash 调用，并把「该用 rg」写进 stderr 给模型。下一轮模型就会改用 rg。一个几十行的脚本，就在循环里焊进了一条「自动纠偏」规则。

8.6matcher 与作用域

Hooks 用 matcher 按工具名匹配（如 "Bash"、"Write"，或多个）。更复杂的护栏可以监测命令内容——plugins/security-guidance 用 PostToolUse（matcher Edit|Write|MultiEdit|NotebookEdit）在文件写入后监测 25 类安全模式：

  • GitHub Actions 注入、eval、dangerouslySetInnerHTML、pickle 反序列化、os.system、subprocess shell=True、不安全 yaml.load、TLS 校验关闭、torch.load……

它在编辑文件后做内容级提醒，并在 git commit/git push 与会话 Stop 时跑 diff 审查——说明 Hook 不只能拦 Bash，也能在文件写入后、提交时、退出前做内容级检查。再看它挂 git commit 复查的配置，这里出现了两个新键：

plugins/security-guidance/hooks/hooks.json（节选）
json{
  "type": "command",
  "command": "bash .../sg-python.sh .../security_reminder_hook.py",
  "if": "Bash(git commit:*)",        // 只在命令是 git commit 时才执行
  "asyncRewake": true,               // 后台跑，结果回灌唤醒主代理
  "rewakeMessage": "Background security review of commit — ..."
}
读懂这段： ① if 条件——matcher 之外的第二层过滤，用权限规则同款的 Bash(git commit:*) 语法判断命令内容，命中才真正拉起进程（否则 Bash 的每次调用都会白跑一个 Python）。② asyncRewake——让 hook 后台异步执行，不阻塞工具返回；等它跑完，用 rewakeMessage 把审查结论回灌进对话、唤醒主代理继续处理（摘要 rewakeSummary 显示在通知里）。这解决了「深度审查要跑 LLM，不能让用户干等」的矛盾：关键路径立即放行，审查结论稍后插话。异步 hook + 唤醒消息，是 Hook 从「同步守门」进化到「异步参谋」的关键一步。

8.8企业可锁定 Hooks

和权限一样，Hooks 也能被企业收口。examples/settings/settings-strict.json 里有 allowManagedHooksOnly: true——开了之后，用户和项目自己定义的 Hooks 全部失效，只认企业下发的。

为什么 Hook 能拦工具、能注入上下文，能力很大——也可能被滥用（比如恶意 Hook 偷数据）。所以受监管环境会要求「只允许 IT 审过的 Hooks」。allowManagedHooksOnly 就是这道闸，和 allowManagedPermissionRulesOnly 配对，把扩展层的自由度也锁进企业策略。

8.9hooks 模块：函数式的新写法（mods/）

2026 年 9 月起，仓库新增了 mods/ 目录——四个随 CLI 内置的插件源码（sec-default、diff、telemetry、agents-md）。它们代表了 Hooks 的第二种形态：hooks 模块。不再是一个被拉起的子进程脚本，而是一个 TypeScript 函数 register(on: On)，直接把处理函数挂到引擎事件上：

mods/sec-default/hooks/register.ts（真实仓库内容，节选）
typescriptimport type { On } from 'claude-code'

export function register(on: On) {
  // 每个事件挂一个 ($, e, next) 函数，而不是 shell 命令
  on('settings.read', ($, e, next) => next.to(e, 'append'))
  on('tool.register', async ($, e, next) => {
    // 能直接读调用方所在的层级，按策略决定放行或拒绝
    if (next.origin.tier === 'prepend' || next.origin.tier === 'append') {
      return next.to(e, 'append')
    }
    // …用户层注册则拒绝（fail closed）
    return isRefused ? { deny: REFUSAL } : next(e)
  })
}
读懂这段： 三点变化值得注意。① 通信契约变了——从「stdin JSON + 退出码」变成函数签名 ($, e, next)：事件对象 e 直接携带类型化数据，next 控制链式放行（还能知道调用来源的层级 origin.tier）。② 事件粒度更细——出现了 settings.read、tool.register、prompt.section 这类引擎内部事件，不再是只有 Pre/PostToolUse 级别。③ 仍是插件——每个 mod 就是一个带 hooks/hooks.json 的标准插件目录，只是 hooks.json 指向一个模块而非 shell 命令。这套 API 标注为早期访问、可能随版本变动；四个 mod 里 diff（/diff 面板）与 telemetry（$.telemetry 分析事件，只服务内置插件、拒绝用户安装的插件——正是靠 origin.tier 判别调用方）直接内置在 CLI 里，agents-md 负责把 AGENTS.md 接入为项目指令（见第 4 章 §4.3），sec-default 则在企业托管环境下最外层落座，把企业的 hooks、设置与工具策略挡在用户插件够不到的地方。
两种形态怎么选 脚本 Hook（stdin/exit code）——语言无关、可维护边界清晰，适合绝大多数护栏与注入场景，仍是默认写法。hooks 模块——强类型、能拿到引擎内部事件与链式上下文，适合深度定制（如本仓库 mods 的面板与安全策略）。目前函数 hooks 需要显式启用，且 API 未承诺稳定——生产配置仍以脚本 Hook 为准。

mods 还配上了完整的开发工具链，让「写一个 hooks 模块」从手工调试变成正规工程：

工具做什么
/plugin-types生成 mods/types/claude-code.d.ts——引擎全量事件与 $ 名词的类型声明，写模块时的依据（第 8 章两处事件清单都出自它）

8.10对使用的启示

要点 ① Hooks 是循环的焊点——不碰内核就能重塑行为。② 退出码 2 是可教学的护栏——拦下并告诉模型原因，它会换路，比硬拒绝聪明。③ PreToolUse 做护栏、PostToolUse 做校验、SessionStart 做注入——按事件性质选。④ 企业用 allowManagedHooksOnly 锁定——能力越大，越要受控。
