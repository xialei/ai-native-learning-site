上下文构建：模型每一轮到底看到什么

★ 重点。循环决定「怎么干」，上下文决定「看到什么」。这一章拆开每次调用模型前，那段被组装出来的消息列表：系统提示、CLAUDE.md 记忆、对话历史、工具结果、以及超长时的压缩。
核心问题 模型不能直接「看见」你的仓库，它只能看见发给它的那段文本。上下文工程就是决定这段文本装什么。 → 控制好上下文 = 控制好模型的注意力。

4.1一分钟版本

每次循环要调模型前，系统会组装一段消息列表发出去。这段列表大致由四部分拼成：

  • 系统提示（system prompt）：固定指令——你是谁、怎么用工具、守什么规矩。
  • 项目记忆（CLAUDE.md）：随仓库走的「备忘录」，告诉模型这个项目的约定、命令、结构。
  • 对话历史：之前每一轮的 user / assistant / tool_result。
  • 环境注入：当前目录、git 状态、时间等动态信息。

当历史太长快超窗口时，压缩（compaction）会把旧消息摘要化，腾出空间继续。子代理（第 7 章）则用独立窗口避免污染主上下文。

4.3CLAUDE.md：随仓库走的记忆

CLAUDE.md 是 Claude Code 最重要的上下文机制之一。它是一份 Markdown，告诉模型「在这个项目里该怎么干活」，并且随仓库提交，团队共享。

典型 CLAUDE.md 内容（概念示例）
markdown# 项目：my-service

## 构建与测试
- 跑测试：pnpm test（单测）/ pnpm test:e2e（端到端，需 docker）
- 类型检查：pnpm tsc --noEmit

## 代码约定
- 用函数式风格，少用 class
- 错误用 Result 类型，不要 throw 控制流
- 新增 API 必须在 openapi.yaml 同步登记

## 结构
- src/domain/ 业务逻辑（核心，先看这里）
- src/adapters/ 外部依赖适配
读懂这段： CLAUDE.md 不是文档给人看，是指令给模型看。写它的诀窍是写「模型猜不到、容易做错的」：构建命令、隐式约定、目录意图。模型能从代码读出来的（比如用了什么框架）少写；模型猜不到的（比如「这个目录是核心」）多写。
多层叠加 CLAUDE.md 会按目录层级叠加：全局 ~/.claude/CLAUDE.md（个人偏好）+ 仓库根（团队共享）+ 当前工作子目录（局部约定）。越靠近工作目录的越具体，模型会都看到。所以你可以在子目录放一个只管该模块的 CLAUDE.md。

4.4压缩：当历史超过窗口

循环跑久了，对话历史 + 工具结果会越来越长，逼近模型的上下文窗口上限。这时压缩（compaction / auto-compact）介入：

图 4.2：压缩把旧的、低信息密度的消息摘要化，保留近期原样。
代价 压缩是有损的：摘要可能丢掉某些细节（比如某次工具的具体输出）。所以重要信息（如关键决定、文件结构）最好落到 CLAUDE.md 或文件里，而不是指望它留在对话历史里被压缩保留。这也解释了为什么「把进度写进 todo 文件」是个好习惯——它不依赖上下文窗口。

4.5工具结果裁剪：另一个吃窗口的大户

对话历史里最占地方的往往不是文字，而是工具结果——读了个大文件、命令输出几千行。上下文构建会对此做裁剪：

  • 截断：超长输出只保留头尾，中间省略并标注。
  • 结构化：把原始输出整理成模型好读的格式（如表格、键值）。
  • 按需重读：旧的工具结果可能被压缩掉，需要时模型再用工具重新拉。
实践启示： 别让模型一次读整个大文件再反复带在历史里。更好的做法是让模型用工具精准读它需要的那部分（指定行号、grep 关键字），既省窗口又准。这是「agentic 读代码」比「把仓库塞进提示」高明的地方。

4.6子代理：用独立窗口隔离上下文

当主代理需要做一件信息量大、可能污染主线的事（比如全仓库搜索、读一堆文件做调研），与其把这些全堆进主上下文，不如派一个子代理：它有自己的上下文窗口，干完只把结论回传给主代理。

图 4.3：子代理用独立窗口隔离噪声，主上下文只保留结论。

这同时解决了两个问题：上下文污染与上下文窗口不够。详见第 7 章。

4.7对使用的启示：写好上下文比写好提示更重要

要点 ① CLAUDE.md 是最高杠杆的投资——一份好的项目记忆能让每次会话都省掉大量重复解释。② 别把仓库塞进提示——让模型用工具按需读，精准且省窗口。③ 重要信息落文件——别依赖对话历史，压缩会丢。④ 脏活累活派给子代理——保护主线上下文的信噪比。上下文工程的本质是注意力管理。
