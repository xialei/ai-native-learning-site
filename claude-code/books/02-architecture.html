整体架构：一个内核，多种外壳

Claude Code 不是单一程序，而是一组形态：终端 CLI/TUI、IDE 扩展、Web、SDK、GitHub 集成。它们共享同一个 agentic 内核，区别只在「谁在驱动、结果给谁看」。本章画出这张分层地图。

2.1一分钟版本

把 Claude Code 想成一个三明治：

  • 内核层：agentic 循环 + 上下文构建 + 工具执行 + 权限/Hooks 调度。这是真正的「引擎」，与界面无关。
  • 接入层：把内核包成不同外壳——交互式 TUI、headless 的 SDK、IDE 扩展、GitHub App。同一引擎，不同驱动方式。
  • 扩展层：插件、Skills、MCP 服务器、自定义命令与 Hooks——给内核加工具与行为，可跨项目复用。

关键洞察：内核与外壳解耦。你在终端里和 Claude Code 聊天、在 SDK 里跑一个无人值守任务、在 GitHub 上 @claude 改 PR——背后是同一个循环在转，只是「谁来发起、要不要人确认、结果输出到哪」不同。

2.2分层依赖图

图 2.1：三层架构。内核是引擎，接入层是外壳，扩展层是可插拔的能力。
这张图的用法： 遇到任何 Claude Code 行为，先问它落在哪层。「它为什么这么答」多半在 L0（上下文/循环）；「它为什么这么确认」在 L0 权限；「它为什么有这个命令」在 L2（插件/命令）；「我在 CI 里怎么跑它」在 L1（SDK）。分层定位能省掉大量迷茫。

2.3接入层逐个看：同一引擎，不同驱动

形态谁驱动是否要人确认结果给谁典型场景
CLI / TUI人，交互式是（默认 ask）终端日常编码、探索
SDK代码，无人值守可配置 / 通常跳过程序（流式事件）CI、脚本、批处理
IDE 扩展人，在编辑器内是编辑器面板边写边问、就地改
GitHub / Web事件触发（@claude）按仓库配置PR / issue 评论审 PR、处理 issue

注意第四列「结果给谁」——SDK 不把答案打印到终端，而是发成结构化事件流（文本增量、工具调用、工具结果）。这是它和 TUI 的关键差别，也是第 11 章的主题。

2.4扩展层：仓库里的真实范本

本仓库 plugins/ 目录就是扩展层的活教材。每个插件是一个标准目录：

plugins/README.md — 标准插件结构
textplugin-name/
├── .claude-plugin/
│   └── plugin.json          # 插件元数据（名称、版本、作者）
├── commands/                # slash 命令（可选）
├── agents/                  # 专职子代理（可选）
├── skills/                  # 技能（可选）
├── hooks/                   # 事件钩子（可选）
├── .mcp.json                # 外接 MCP 工具（可选）
└── README.md
读懂这段： 插件把命令、子代理、技能、Hooks、MCP 五种扩展原语打包成一个可分发单元。这意味着扩展层不是「写个脚本」那么简单，而是一套可组合、可分享、可版本化的能力封装——第 10 章会逐个拆开本仓库的官方插件。

2.5配置贯穿三层

配置（settings）是横切三层的粘合剂。同一套设置键，按层级叠加生效，下表自上而下为优先级从高到低（高优先级覆盖低优先级）：

层级文件谁定典型用途
企业managed-settings.jsonIT / 安全团队（MDM 下发）强制禁用某工具、锁定市场
本地项目.claude/settings.local.json个人（不提交）本地覆盖、实验
项目.claude/settings.json团队（随仓库走）项目权限规则、共享命令
用户~/.claude/settings.json个人开发者个人偏好、全局命令
优先级 企业策略具有最高优先级且不可被下级覆盖——这是「默认安全」的根基：即便用户想放开，IT 下发的 managed-settings 也能拦住。其余三层的覆盖顺序是本地 > 项目 > 用户（用户层优先级最低），命令行参数则介于企业与本地之间。详见第 6、9 章。

2.6对使用的第一个启示

要点 理解 Claude Code 的捷径是分层归因：行为怪 → 先定位是内核（循环/上下文）、接入（哪个外壳）、还是扩展（哪个插件/Hook）。绝大多数「它为什么不按我想的来」都能在这三层里找到答案。后续章节就是沿这三层往下钻。
