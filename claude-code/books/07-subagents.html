子代理与并行：用独立窗口隔离与加速

主代理一条道走到黑，上下文会越来越脏、越来越满。子代理（subagent）是解药：它有自己的上下文窗口，干完只把结论回传。这一章拆开派遣/回传契约、专职代理的定义，以及并行编排。
核心机制 派一个子代理去做脏活累活，它读完一堆文件，只回传一段结论——主线上下文不被污染。 → 既是上下文工程，也是并发工程。

7.1一分钟版本

子代理是一个拥有独立上下文窗口的 agent，由主代理按需派遣去完成一个范围明确的小任务，完成后只把结论（最终文本）回传给主代理。它同时解决两个问题：

  • 上下文污染：子代理内部读的一堆文件、产生的大量 tool_result 都不进主上下文，主线保持高信噪比。
  • 窗口上限：脏活在子代理的窗口里消化，不挤占主代理的预算。

更进一步的收益是并行：多个子代理可同时跑，各自独立窗口、独立循环。

7.3派遣与回传契约

从主代理的视角，派遣子代理就是发出一次 Task 工具调用——描述目标、指定用哪个代理类型，子代理跑完自己的循环，把最终文本作为 tool_result 回灌：

概念示例：主代理发出 Task 工具调用
json{
  "type": "tool_use",
  "name": "Task",
  "input": {
    "description": "调研 src/auth 目录的鉴权流程",
    "subagent_type": "code-explorer",     // 专职代理类型
    "prompt": "找出登录鉴权的完整调用链，列出关键文件与函数"
  }
}
// 子代理在自己的窗口里读文件、grep、跑循环，最终产出一段文本
// → 作为 tool_result 回灌给主代理：调用链摘要 + 关键文件清单
读懂这段（关键契约）： 子代理内部干了什么——读了哪些文件、产生了多少 tool_result、来回多少轮——统统不回传，主代理拿到的只有 tool_result 里那段最终文本。这就是上下文隔离契约：噪声留在子窗口，结论进入主窗口。主代理据此决定下一步（比如亲自去改那些关键文件）。

7.4专职子代理：可定义的专家

子代理不一定是「通用助手」，可以定义成专职角色：一份 Markdown 文件，带 frontmatter 声明名字、描述、可用工具、模型，正文是它的系统提示。本仓库 plugins/ 里就有大量真实范例：

插件专职子代理职责
feature-devcode-explorer / code-architect / code-reviewer代码探查 / 架构设计 / 质量审查
pr-review-toolkitcomment-analyzer / pr-test-analyzer / silent-failure-hunter / type-design-analyzer / code-reviewer / code-simplifier评论 / 测试 / 静默失败 / 类型设计 / 代码质量 / 简化
agent-sdk-devagent-sdk-verifier-py / agent-sdk-verifier-ts校验 SDK 应用最佳实践
plugin-devagent-creator / plugin-validator / skill-reviewer创建 / 校验 / 审查
概念示例：一个专职代理的定义文件（结构参考 plugins/feature-dev/agents/code-reviewer.md，已简化）
markdown---
name: code-reviewer
description: 审查代码变更，专注 bug、类型设计、可简化点
tools: Read, Grep, Glob            # 只给需要的工具，最小权限
model: sonnet                      # 可指定模型档位
---

你是资深代码审查者。收到一组变更后：
1. 先用 Read/Grep 理解上下文，不要只看 diff。
2. 按严重度排序给出问题，每条附文件:行号与具体建议。
3. 区分「必须改」与「可选」，不纠结风格小事。
只回传审查结论，不要试图自己改代码。
读懂这段： 三个设计要点。① tools 收窄——审查者只需要读和搜，不给写/执行，天然安全（呼应第 6 章最小权限）。真实仓库里的 code-reviewer.md 工具集更宽（含 WebFetch/WebSearch 等），这里为说明「最小权限」做了简化。② model 可降档——专职任务未必需要最强模型，省成本。③ 系统提示聚焦——专职代理的 persona 越明确，产出越稳。这就是把「角色」固化成可复用资产。

7.5并行编排：fan-out / fan-in

多个子代理可并发执行。最典型的真实范例是 plugins/code-review——它在审查阶段并行跑4 个代理（2 个 Sonnet 审 CLAUDE.md 合规 + 2 个 Opus 审 bug），各盯一个维度：

图 7.2：code-review 插件的并行审查——4 个代理同时跑，结论汇总。维度为真实插件配置。
为什么并行： 两个收益。① 速度——4 个维度同时跑，墙钟时间约等于最慢的那个，而非四者之和。② 独立视角——每个子代理只盯一个维度、互不干扰，比一个代理「同时审四件事」更专注、更少遗漏。这种 fan-out/fan-in 是用子代理做复杂审查的标准招式。

7.6何时用子代理

场景用子代理？理由
大范围探查（全仓库搜索、读一堆文件做调研）✅噪声大，隔离掉保护主线
可并行的独立维度（多角度审查）✅并行加速 + 独立视角
需要专家 persona（审查者、架构师）✅固化角色，产出更稳
会撑爆主窗口的脏活✅独立窗口消化
简单的顺序小改（改一处文案）❌派遣开销大于收益
需要完整可观测的逐步过程❌子代理内部过程被封装，不透明

7.7对使用的启示

要点 ① 脏活累活派给子代理——保护主线上下文信噪比，这是最常用收益。② 并行独立维度——审查、调研类任务用 fan-out/fan-in 又快又全。③ 把可复用的角色固化成专职代理——配最小工具集、合适模型档位，既安全又省钱。④ 代价是不透明——子代理内部过程被封装，调试时记得让它把结论写详细些。
