插件与 Skills：可分享的能力包

命令、子代理、技能、Hooks、MCP——这五种扩展原语能打包成一个插件，跨项目跨团队复用。本仓库自带十几个官方插件，就是最好的活教材。这一章拆结构、讲市场、做巡礼。
定位 插件是扩展层的标准分发单元——不碰内核，只往工具集与行为里加东西。 → 对应第 2 章架构图的 L2。

10.1一分钟版本

插件（plugin）是一个标准目录，把命令 / 子代理 / 技能 / Hooks / MCP 五种原语打包在一起，带一份 plugin.json 元数据。它可以发布到市场，别人一行命令装上就用。本仓库 plugins/ 目录就是官方范本——每个都对应一类真实工程场景。

10.2标准目录结构

plugins/README.md — 标准插件结构（真实仓库内容）
textplugin-name/
├── .claude-plugin/
│   └── plugin.json          # 插件元数据（名称、版本、作者）
├── commands/                # slash 命令（可选）
├── agents/                  # 专职子代理（可选）
├── skills/                  # 技能（可选）
├── hooks/                   # 事件钩子（可选）
├── .mcp.json                # 外接 MCP 工具（可选）
└── README.md
真实范例：plugins/claude-opus-4-5-migration/.claude-plugin/plugin.json
json{
  "name": "claude-opus-4-5-migration",
  "version": "1.0.0",
  "description": "Migrate your code and prompts from Sonnet 4.x and Opus 4.1 to Opus 4.5.",
  "author": { "name": "William Hu", "email": "whu@anthropic.com" }
}
读懂这段： 插件是组合体而非单一物。一个插件可以只含一条命令，也可以同时带命令+代理+技能+Hooks。目录结构本身就是契约——.claude-plugin/plugin.json 声明身份，其余子目录按需放原语。这种「五原语 + 元数据」的封装让能力可版本化、可分发、可审计。

10.3五种原语回顾

原语是什么章节
命令 commandsslash 命令，/name 触发的提示模板或流程本章 / 14

10.4Skills：渐进式披露

技能（Skill）是个特别的设计：它平时不进上下文，只在模型判断需要时按需载入。这避免了「为了一个偶尔用的能力，常驻占着窗口」的浪费。

  • 一份 skill 带一段指令（怎么用）和若干资源（参考文件、脚本）。
  • 模型看到 skill 的描述，在相关任务时主动展开它的指令。
  • 所以 skill 是「渐进式披露」——先给目录，要用再翻详情，不破坏提示缓存。

真实范例：plugins/frontend-design 的 frontend-design 技能会在做前端工作时自动介入，给排版/动效/视觉细节的指导；plugins/plugin-dev 带 7 个专家技能用于开发插件本身。

10.5本仓库官方插件巡礼

这十几个插件覆盖了真实工程里最高频的场景，是扩展层的最佳教材：

插件场景包含的原语
code-review自动 PR 审查命令 + 4 个并行子代理（2 Sonnet 审 CLAUDE.md 合规、2 Opus 审 bug）

怎么读这些插件： 别只看名字，打开目录看它用了哪种原语、怎么组合。比如 security-guidance 用 PostToolUse + Stop 监测约 25 类安全问题——说明 Hook 是最小成本的护栏；code-review 用 4 个并行代理（Sonnet + Opus 混合）——说明复杂审查的范式是 fan-out。每个插件都是一个可拆解的设计模式样本。

10.6市场与安装

插件通过市场（marketplace）分发。安装方式：

  • 交互式：/plugin 命令从市场安装。
  • 声明式：在 .claude/settings.json 的 enabledPlugins 里配置。
企业可控 市场不是想装就装：strictKnownMarketplaces（设为空数组即封禁未知市场）可限制只允许受信市场。本仓库 examples/settings/settings-lax.json 与 settings-strict.json 都启用了它——插件虽好，来源必须可控。

10.7对使用与扩展的启示

要点 ① 先找现成插件——你的需求（审查、提交、安全）多半已有官方范本，抄再改。② 选对原语——护栏用 Hook、专家角色用代理、偶尔用的能力用 Skill、流程用命令。③ 插件即团队资产——把团队约定打包成插件随仓库走，比写进文档更可执行。④ 来源可控——企业用 strictKnownMarketplaces 锁定受信市场。
