内置工具：模型动手的双手

循环让模型能多步推进，而工具让它真的「动得了手」。这一章拆开 Claude Code 内置的工具集——Bash、文件读写编辑、网络搜索抓取——看清每一次 tool_use 如何落地成一次真实动作，又如何把结果变成模型可读的 tool_result。
核心关系 模型只产出 tool_use 意图，真正动手的是 harness；动作的结果再被格式化回灌。 → 工具，就是模型伸向真实世界的那双手。

5.1一分钟版本

模型自己不会跑命令、不会读写磁盘——它只能声明意图：「我要调 Bash，参数是 …」。Claude Code 的 harness 接管这个声明，真正执行，再把结果喂回去。这套内置工具就是模型的「双手」：

  • Bash：跑 shell 命令，stdout/stderr/退出码成为结果。
  • Read：读文件（含图片、PDF、Jupyter notebook，可指定行范围）。
  • Write：创建或整体覆盖文件。
  • Edit：精确字符串替换（old → new，需唯一匹配）。
  • WebSearch / WebFetch：搜索与抓取网页。
  • Task / TaskOutput：派遣子代理与读取其输出（见第 7 章）。
心智锚点 工具不是「功能」，而是模型与世界的接口。每加一个工具，模型能触达的世界就大一圈；每关一个工具（权限 deny），它就少一条路。MCP（第 12 章）的存在，正是为了让你能无限往这个工具集里加东西。

5.2工具调用全流程：一次 tool_use 的旅程

第 3 章把循环画成「模型 ⇄ 工具」，这里把「工具」这个节点放大。一次 tool_use 从声明到结果回灌，要穿过权限与 Hooks 两道关卡：

图 5.1：tool_use 经 PreToolUse → 权限评估 → 执行 → PostToolUse，结果回灌。任一关卡可拦截。
读懂这张图： 工具调用不是「模型说要就跑」，而是穿过一条流水线：PreToolUse Hook 先跑（不管这个调用要不要权限），它能改写输入或直接放行/拦截；随后权限规则做最终裁定——allow 只是「跳过提示」，deny/ask 规则无论 Hook 返回什么都会照常生效。执行后才轮到 PostToolUse 收尾。这条流水线把第 3 章的循环、第 6 章的权限、第 8 章的 Hooks 串成一条线——每个工具调用都是一个可拦截、可审计的决策点。

5.3Bash 工具：把终端交给模型

Bash 是最强也最危险的工具：模型能跑任意 shell 命令。它的结果由 stdout / stderr / 退出码 三件套组成，非零退出码会被标成 is_error。

概念示例：Bash 的 tool_use（Anthropic 消息格式）
json{
  "type": "tool_use",
  "id": "toolu_01ABC...",
  "name": "Bash",
  "input": {
    "command": "pnpm test --filter auth",   // 要执行的命令
    "description": "跑 auth 模块测试"         // 模型对命令的说明
  }
}
读懂这段： ① 退出码即语义——命令以非零退出，tool_result.is_error=true，模型在下一轮会看到报错并据此调整（这正是「看报错再改」的来源）。② 工作目录持久——多次 Bash 调用共享工作目录与部分环境，cd 的效果会延续，但 shell 函数/变量不一定跨调用保留。③ 可上沙箱——配置里可让 Bash 在沙箱里跑，限制网络与文件写，本仓库 examples/settings/settings-bash-sandbox.json 就是一例。
安全提示 Bash 能跑任意命令 = 能 rm、能联网、能读密钥。所以它默认需要确认，且常被 PreToolUse Hook 审查（见 5.7 的真实范例）。生产环境务必搭配权限规则与沙箱，别裸跑。

5.4文件工具：Read / Write / Edit

这三个工具让模型能读写你的代码。理解它们的差别，就理解了 Claude Code 改代码的纪律：

  • Read：读文件。可指定 offset/limit 只读一段；能读图片、PDF、Jupyter notebook（按页或按 cell）。大文件不必全读。
  • Write：创建或整体覆盖文件。慎用——它会冲掉原内容。
  • Edit：精确字符串替换：old_string → new_string，且 old_string 在文件里必须唯一。
概念示例：Edit 的 tool_use
json{
  "type": "tool_use",
  "name": "Edit",
  "input": {
    "file_path": "src/auth/login.ts",
    "old_string": "const user = await db.find(email);",
    "new_string": "const user = await db.findByEmail(email);"
  }
}
读懂这段： ① 唯一性是硬约束——old_string 必须在文件里唯一匹配，否则 Edit 报错不改。这逼着模型定位到足够具体的上下文，避免改错地方。② 偏向 Edit 而非 Write——改现有文件优先用 Edit（小而准），Write 留给新建文件或整体重写，这是文件变更的纪律。③ 改前先读——模型通常先 Read 看准上下文再 Edit，盲改会被唯一性约束挡住。

5.5网络工具：WebSearch / WebFetch

模型的知识有截止日期，且不知道你内部的文档站点。网络工具补这块：

  • WebSearch：搜索网页，返回标题与 URL 列表（仅美国地区可用）。
  • WebFetch：抓取一个 URL，转成 Markdown，再用一个小模型针对该内容回答你给的 prompt。
可被权限关闭 网络工具不是非要开。本仓库 examples/settings/settings-strict.json 就禁用了 WebFetch 与 WebSearch——在对网络泄露敏感的环境里，这是一道常见闸门。这再次说明：工具是可选的，权限决定哪些手可用。

5.6工具结果的结构化：原始输出如何变模型可读

第 3 章 §3.3 讲过 tool_result 的结构，这里按工具看它们各自回什么。原始输出会被整理、必要时截断，再配上 tool_use_id 与 is_error：

工具原始产出回灌给模型的 tool_result
Bashstdout / stderr / 退出码输出文本；非零退出 → is_error=true
Read文件内容带行号文本；超长截断；图片/PDF 转可读表示
Edit替换是否成功成功提示 / 失败原因（如不唯一）
Write写入结果成功提示
WebSearch搜索结果标题 + URL 列表
WebFetch网页内容 + 小模型回答针对 prompt 的答案
关键点： 所有工具的输出最终都归约成同一种结构喂回模型——文本 + 错误标志 + id 配对。这种统一让循环不用关心「这是文件还是命令」，只消消费 tool_result。截断尤其重要：一个 cat 出几万行的文件，会被裁成头尾带省略号，避免撑爆上下文窗口（见第 4 章压缩与裁剪）。

5.7一个真实范例：拦截 Bash 把 grep 改成 rg

本仓库 examples/hooks/bash_command_validator_example.py 是一个真实的 PreToolUse Hook，专门盯 Bash 工具——它把 grep 改劝成 rg、把 find -name 改劝成 rg --files。这是「工具拦截」最直白的活样本：

examples/hooks/bash_command_validator_example.py — 校验规则（节选）
python# 定义校验规则：(正则模式, 提示信息)

    ),

读懂这段： 这就是图 5.1 里「PreToolUse Hook」的真实样子。退出码即协议——0 放行、2 阻断并把 stderr 喂给模型、1 出错但不阻断。模型收到「请用 rg 而非 grep」后会换命令重试。一个几行脚本，就把团队规范焊进了循环——这正是 Hooks 的威力，第 8 章会完整拆开这套 stdin/stdout JSON 协议。

5.8对使用的启示

要点 ① 工具是接口不是功能——决定模型能触达的世界，按需开/关。② 每次调用都过流水线——PreToolUse → 权限评估 → 执行 → PostToolUse，任一节可拦。③ 改文件守纪律——先 Read 后 Edit，old_string 要唯一，慎用 Write 覆盖。④ Bash 最强也最险——默认确认 + Hook 审查 + 沙箱三件套别省。⑤ 想加工具就上 MCP（第 12 章），工具集是开放的。
