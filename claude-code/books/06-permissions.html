权限模型：把「能动手」框在边界里

循环让模型能动手，权限让它别闯祸。这一章拆开每个工具调用前的那个决策点：allow / ask / deny 三态、按工具与路径的规则匹配、沙箱 Bash，以及企业如何用托管策略收口。
设计原则 默认安全（secure by default）——写文件、跑命令先问你；能放开，也能锁死。 → 权限是内建在循环里的一道闸，而非事后补救。

6.1一分钟版本

第 3 章那张循环图里，「执行工具」这个节点并非想跑就跑。每一次工具调用都是一个决策点：PreToolUse Hook 先跑（见第 8 章），随后权限规则做最终裁定，结果落在三态之一：

  • allow：直接执行，不打扰你。
  • ask：暂停，弹给你确认（交互模式下）。
  • deny：直接拒绝，模型会收到「被拒」的结果并据此调整。

规则可以按工具名 + 参数模式粒度配置：允许读文件、命令要先确认、rm -rf 一律拒绝。也能按团队、按企业策略统一收口。这就是 Claude Code「agentic 但不失控」的根基。

6.2三态模型与规则匹配

图 6.1：每个工具调用的权限评估，输出 allow/ask/deny。PreToolUse Hook 在其之前运行（见第 8 章）。
匹配逻辑： 规则按「工具 + 参数模式」匹配——比如 Bash 工具可按命令前缀匹配（git * 放行、rm -rf * 拒绝），Read/Write 可按文件路径 glob 匹配。通常 deny 优先级最高，先于 ask 与 allow 判定，确保危险操作无论如何都被拦。与 Hook 的先后：PreToolUse 先于权限规则运行（哪怕这个调用本不需要权限），Hook 的 allow 只是跳过提示，deny/ask 规则无论 Hook 返回什么都会照常评估。

6.3规则配置

权限规则写在 settings 的 permissions 块里，分 allow / ask / deny 三组：

概念示例：.claude/settings.json 权限规则
json{
  "permissions": {
    "allow": [
      "Read",                       // 读文件一律放行
      "Bash(git status)",           // 只放行 git status 这一条
      "Bash(pnpm test*)"            // 放行测试命令
    ],
    "ask": [
      "Bash",                       // 其余 Bash 命令都要确认
      "Write"                       // 写文件要确认
    ],
    "deny": [
      "Bash(rm -rf*)",             // 危险命令一律拒绝
      "WebFetch",                   // 禁止网络抓取
      "Read(./.env*)"              // 保护密钥文件
    ]
  }
}
读懂这段： 三组规则覆盖了从「全放行」到「精准拒绝」的光谱。注意 Bash(git status) 这种带参数模式的写法——它不是放行所有 Bash，只放行匹配 git status 的。本仓库 examples/settings/ 下的三套范例（lax / strict / bash-sandbox）就是这种配置的成熟范本，详见 §6.7。

6.4沙箱 Bash

对 Bash 工具，除了 allow/ask/deny，还有一道更强的约束：沙箱（sandbox）。沙箱把命令关进受限环境，限制网络访问与文件写入：

普通 Bash沙箱 Bash
网络访问允许受限/禁止
文件写入允许（受权限规则）受限/禁止
适用日常不信任命令、CI 自动化
重要边界（来自仓库 README） sandbox 属性只对 Bash 工具生效——它不适用于 Read、Write、WebSearch、WebFetch、MCP 工具、Hooks 或内部命令。所以要拦网络，光开沙箱不够，还得用 deny WebFetch / WebSearch（见 examples/settings/settings-strict.json）。

6.5--dangerously-skip-permissions

有一个开关能跳过所有确认：--dangerously-skip-permissions。它让每个工具调用直接 allow，不再 ask。典型用途是 CI / SDK 无人值守自动化——没有人坐在终端前点确认。

危险 名字里带 dangerously 不是吓唬人：它意味着模型可以不经确认地写文件、跑任意命令。只应在可信且隔离的环境里用（一次性容器、受限 VM、无敏感凭据的临时目录）。本仓库 examples/settings/settings-strict.json 与 settings-lax.json 都禁用了这个开关——可见官方态度：宁可不方便，不可不安全。

6.6企业托管策略与 MDM

在组织里，安全不能依赖个人自觉。Claude Code 提供托管策略（managed settings）：由 IT/安全团队下发，优先级最高，下级无法覆盖。

图 6.2：配置按层级叠加，企业策略在最上层且不可被下级推翻。

本仓库 examples/mdm/ 提供了真实部署模板：macOS 用 com.anthropic.claudecode.plist / .mobileconfig，Windows 用 ClaudeCode.admx / .adml 配 Set-ClaudeCodePolicy.ps1。可通过 Jamf、Kandji、Intune、组策略下发。某些键如 strictKnownMarketplaces、allowManagedHooksOnly、allowManagedPermissionRulesOnly 只在企业设置里才生效。

6.7三套范例对照（来自仓库 examples/settings/README.md）

本仓库自带三套成熟配置，覆盖从宽松到严格的光谱：

设置项settings-laxsettings-strictsettings-bash-sandbox
禁用 --dangerously-skip-permissions✅✅
封禁插件市场✅✅
封禁用户/项目自定义 allow/ask/deny✅✅
封禁用户/项目自定义 Hooks✅
拒绝 WebFetch / WebSearch 工具✅
Bash 工具需要审批✅
Bash 工具必须在沙箱内运行✅
怎么选： lax 适合个人开发、信任仓库；strict 适合团队/受监管环境，把能收的口都收了；bash-sandbox 专门针对「命令不可信」场景。三者可按需合并片段，不必整体照搬。

6.8对使用的启示

要点 ① 权限是循环里的闸，不是事后审计——每个工具调用都过一次。② deny 不是终点而是反馈——模型会收到拒绝原因并换路，所以精细的 deny 规则等于在「教」模型边界。③ 沙箱只管 Bash——拦网络要靠 deny WebFetch/WebSearch。④ 企业策略不可绕过——这是默认安全的最后一道墙。
