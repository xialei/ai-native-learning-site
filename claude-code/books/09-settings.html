配置体系：横切三层的粘合剂

权限、Hooks、模型、插件——都靠一套 JSON 配置串起来。这一章拆开 settings 的四层层级与优先级、常用键，以及本仓库自带的三套成熟范例与 MDM 部署模板。
定位 配置不是「可选调味」，而是把内核、接入、扩展三层粘在一起的横切机制。 → 第 2 章的三层架构里，settings 贯穿全部三层。

9.1一分钟版本

配置是若干 JSON 文件，按层级叠加合并，高优先级覆盖低优先级（企业策略除外——它不可被覆盖）。它管的事横跨三层：

  • 内核：权限规则（allow/ask/deny）、Hooks 定义。
  • 接入：默认模型、环境变量、--dangerously-skip-permissions 开关。
  • 扩展：启用哪些插件、哪些 MCP 服务器。

9.2四层层级与优先级

图 9.1：自下而上叠加，自上而下优先。企业策略在最顶且不可推翻。
关键认知： 这四层不是「四选一」，而是叠加合并——同一家里的不同键都会生效，相同键按优先级取上层。唯一特殊的是企业策略：它不是「覆盖」，而是「锁定」——它设的某些限制下级改不动。这是默认安全的根基（见 §9.6）。

9.3真实范例：严格配置

本仓库 examples/settings/settings-strict.json 是一套「能收的口都收了」的范例：

examples/settings/settings-strict.json（真实仓库内容，节选——省略了 excludedCommands / allowUnixSockets / httpProxyPort / socksProxyPort / enableWeakerNestedSandbox 等键）
json{
  "permissions": {
    "disableBypassPermissionsMode": "disable",   // 禁用 --dangerously-skip-permissions
    "ask": ["Bash"],                          // 所有 Bash 命令都要确认
    "deny": ["WebSearch", "WebFetch"]         // 拒绝网络搜索与抓取
  },
  "allowManagedPermissionRulesOnly": true,      // 只认企业规则，禁用户/项目自定义权限
  "allowManagedHooksOnly": true,                // 只认企业 Hooks，禁用户/项目自定义 Hooks
  "strictKnownMarketplaces": [],                     // 封禁未知插件市场
  "sandbox": {                                       // Bash 沙箱细则
    "autoAllowBashIfSandboxed": false,
    "network": {
      "allowAllUnixSockets": false, "allowLocalBinding": false,
      "allowedDomains": []
    }
  }
}
读懂这段（逐键）： ① disableBypassPermissionsMode:"disable"——堵死跳过权限的快捷方式。② ask:["Bash"] + deny 网络——命令必确认、网络全断。③ allowManagedPermissionRulesOnly / allowManagedHooksOnly——这两个是「锁定键」：开了之后，用户和项目自己写的权限规则与 Hooks 全部失效，只认企业下发的。④ sandbox——即便用沙箱也不自动放行 Bash，网络白名单为空。一句话：严格到连用户想放松都放松不了。

9.4宽松 vs 严格 vs 沙箱 对照

本仓库 examples/settings/README.md 给了一张对照表，原样 reproduce：

设置项settings-laxsettings-strictsettings-bash-sandbox
禁用 --dangerously-skip-permissions✅✅
封禁插件市场✅✅
封禁用户/项目自定义 allow/ask/deny✅✅
封禁用户/项目自定义 Hooks✅
拒绝 WebFetch / WebSearch 工具✅
Bash 工具需要审批✅
Bash 工具必须在沙箱内运行✅

对照 settings-lax.json 的真实内容——它极简，只两件事：

examples/settings/settings-lax.json（真实仓库内容）
json{
  "permissions": {
    "disableBypassPermissionsMode": "disable"   // 仅禁用跳过权限开关
  },
  "strictKnownMarketplaces": []                    // 封禁未知市场
}
对比启示： lax 只堵两个最危险的口（跳过权限、未知市场），其余放手——信任个人自觉。strict 把规则、Hooks、网络、沙箱全锁死。bash-sandbox 专注「命令不可信」场景。可见同一套配置键，组合方式决定了从「宽松信任」到「严格锁定」的光谱。

9.5常用配置键

键作用层
permissions权限规则 allow/ask/deny + 沙箱 + 跳过开关内核
hooks各事件钩子定义（见第 8 章）内核
model默认模型档位接入
env注入环境变量接入
enabledPlugins启用的插件扩展
enableAllProjectMcpServers项目 MCP 服务器开关扩展
includeCoAuthoredBy提交信息是否带 co-author接入
allowManaged*Only / strictKnownMarketplaces企业锁定键（仅企业设置生效）内核

9.6企业 MDM 部署

企业策略要能「锁死」，前提是它由 IT 通过 MDM 下发，用户改不到。本仓库 examples/mdm/ 提供了真实模板：

平台文件下发方式
macOScom.anthropic.claudecode.plist / .mobileconfigJamf / Kandji / Intune
WindowsClaudeCode.admx / .adml + Set-ClaudeCodePolicy.ps1组策略 / Intune
仅企业生效的键 strictKnownMarketplaces、allowManagedHooksOnly、allowManagedPermissionRulesOnly 这几个锁定键只在企业设置里才生效（来自 examples/settings/README.md）——放在用户/项目级是无效的。这正是「默认安全」的制度保障：关键锁定只能由 IT 下发，个人无法自行放开。

部署前，README 建议先在本地把配置应用到 managed-settings.json / settings.json / settings.local.json 测试通过，再推给组织。

9.7配置与三层架构的关系

回到第 2 章的分层图，settings 横切三层：它给内核设权限与 Hooks、给接入层设模型与 env、给扩展层设启用的插件与 MCP。所以改一处配置可能同时影响多个层——这也是为什么配置问题排查要从层级和键两维定位。

要点 ① 项目配置随仓库提交（团队共享），本地覆盖放 settings.local.json 且要 gitignore。② 测试再部署——MDM 推给全组织前先本地验。③ 按需合并片段——lax/strict/sandbox 不必整体照搬，取需要的键拼装。④ 锁定键只在企业级生效——想真正锁死，得走 MDM。
