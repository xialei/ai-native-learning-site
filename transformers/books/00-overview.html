Chapter 00 · Overview

三个问题:模型怎么记住互联网,怎么接上工具,解决问题的能力从哪来

大多数人用 Transformers 的方式是三行代码:加载模型、喂进文本、拿回输出。这个抽象太成功了,成功到人们开始对它产生两种相反的误解——一种觉得「模型什么都懂」,另一种觉得「模型就是个接缝预测器,什么都不真懂」。两种说法都把一件事糊在黑盒里:几百 GB 的权重文件,是怎么和「记住互联网」「调用工具」「解决问题」这三件具体的事对上号的。

这本书把黑盒打开。全书锚定 huggingface/transformers 仓库主干(v5 时代,版本 5.21.0.dev0 快照),每一章讲清一段真实源码。本章不进任何代码,只把三个问题摆正,并且诚实标注每个问题的答案有几分在库内、有几分在库外。

0.1为什么值得读这个库的源码

先说一个不太对称的现象。推理引擎(vLLM、SGLang)和 Agent 运行时(pi、Codex)的源码,工程师是愿意精读的,本站其他几本书讲的都是它们。但 Transformers 这个几乎所有大模型应用的第一行 import,多数人对它的了解停在「会调 API」。原因大概有两条。一是它太顺手,出了问题绕一下总能过去;二是它的体量吓人——仓库里 531 个模型架构、54.5 万多行建模代码,谁都不知道从哪下手。

但这个体量有很强的欺骗性。531 个架构里,真正独立的设计不到二十个,其余的全是从互相衍生的代码生成的(第 1 章讲这套生成机制)。而所有模型共同依赖的核心设施,集中在 src/transformers/ 顶层的十几个文件里:modeling_utils.py 5182 行、trainer.py 4726 行、generation/utils.py 4437 行、tokenization_utils_base.py 3782 行、cache_utils.py 2166 行。把这十几个文件读懂,531 个模型在你眼里就收敛成了一张图纸的 531 次参数化。

还有一层时机上的原因。2025 年底到 2026 年,这个库完成了 v4 → v5 的断代迁移:TensorFlow 和 Jax 整体移除、权重加载推倒重做、分词器后端化重构、注意力实现后端化、对话模板成为工具调用的正式入口。读 v4 时代的旧文章,很多细节已经对不上;读 v5 的源码,看到的是一条收敛后的主线。断代迁移本身也是内容——为什么一个库要花一年时间做减法,第 1 章和第 12 章都会回到这个问题。

0.2三个问题,各自拆到什么粒度

全书围绕三个问题展开。这三个问题不是并列的:第一个问「模型怎么知道的」,第二个问「模型怎么表达的」,第三个问「能力本身从哪来」。先把每个问题拆到源码能回答的粒度,再标清边界。

问题一:模型怎么「记住」整个互联网的

这个问题能拆成四段,每段都有实码作答。互联网的文本先经过分词器(tokenization_utils_base.py)变成 token 序列——这是进入模型的唯一入口,第 2 章讲。token 序列在训练时被压进权重:注意力层(Geva et al. 2021 给出的解释)按内容做检索,前馈层是一张巨大的键值记忆表——「记忆」的物理形态就是这两层里的矩阵数值,第 3 章讲压进去的机制和为什么是「有损的」。推理时,当前对话的记忆由 KV Cache 承担(cache_utils.py 整个类家族):本次会话记得住、进程结束就忘,它和权重记忆的分工是第 4 章的主题。窗口长度怎么撑到百万 token,RoPE 缩放(yarn、longrope)也在第 4 章。

边界要诚实:「记住了什么」存在权重文件的数值里,那是某次预训练 run 的产物,不在 GitHub 仓库里。书里能讲清的是记的机制——为什么几百 GB 权重装得下互联网的统计结构,以及为什么「模型知道某个具体事实」这个说法要打个引号。它不是数据库,没有「某条知识存在第几层」这种账可查——可解释性研究(Mechanistic Interpretability)还在追赶这件事。

问题二:模型怎么支持 Agent 调用工具的

这个问题在库里有一段非常具体的代码链。工具的定义(JSON Schema)经 apply_chat_template(tools=...) 被织进提示词(tokenization_utils_base.py:3021 起);对话被渲染成模型专属的控制符格式(chat template,第 8 章);模型生成时,停止条件盯着工具调用的结束标记(generation/utils.py);生成完成后,文本按 schema 被解析回结构化的函数调用(第 9 章)。这条链的每一环都在本仓库里,证据链完整。

边界同样要诚实:「循环」不在库里。执行工具、把结果回填、再调模型、判断何时停——这是 Agent Runtime 的活。本站已有四本书(pi、Codex、Claude Code、DeepSeek Harness)讲循环这一侧;这本书讲的是循环的另一半——「模型输出一个 tool call」这个动作,在模型侧是怎么实现的。两半拼起来,才是「Agent 调用工具」的完整答案。第 9 章会把这条分界线画在代码上。

问题三:「一套解决问题的办法」从哪来

先承认:解题能力是训练灌进权重的,主要靠后训练阶段的强化学习——那个过程发生在 TRL 等训练框架里,不在这个仓库。库内能看到的是能力的表达机制:同一次前向,怎么把概率分布变成不同的行为。贪心解码产出稳定答案,采样带温度产出多样性,beam search 拿质量换算力,投机解码拿小模型赌大模型(generation/candidate_generator.py);logits 加工(generation/logits_process.py 3252 行)负责重复惩罚、禁止词、格式约束;服务端场景下,continuous_batching 子系统让成百个并发对话共享一次调度(第 7 章)。

第 5、6、7 章讲这条生成主线,第 11 章讲权重怎么被训练改写——那是能力来源在库内的最近一段。第 13 章收口:把「模型侧」和「Agent 侧」的分工画成一张清单,想自己拼一套系统的人按图取件。

0.3库内与库外的边界

把三个问题的答案按「证据在哪」摆成一张表,这张表就是全书的边界声明:

问题库内可讲(本书范围)库外,本书只指路
怎么记住互联网分词入口、注意力检索 + FFN 键值记忆的机制、KV Cache 短期记忆、RoPE 长窗口、预训练目标(Trainer)具体知识的存在形态(权重文件本身);Mechanistic Interpretability 的进展
怎么调用工具chat template 织入 tools schema、控制符对话格式、生成停止条件、结构化输出解析Agent 循环(执行/回填/再调用)——本站 pi、Codex、Claude Code、DeepSeek Harness 四本书
解决问题的能力解码策略与 logits 加工(能力的表达)、训练循环(能力的写入)、量化与加载(权重的变换)RL 后训练的具体过程——TRL 库;奖励模型设计——独立研究方向

这张表还有一个用途:帮你把「模型不行」和「模型外面那层不行」分开。工具调用失败,可能坏在模型没生成对格式(库内,第 9 章),也可能坏在 Runtime 没把上一轮结果回填对(库外)——两边看的代码不同,修法也不同。

本章小结

三个问题的答案有几分在库内、几分在库外,这是全书先立好的边界:「记住互联网」的机制(分词、注意力检索、FFN 键值记忆、KV Cache)全在库内,但「记住了什么」在权重文件里;「调用工具」的模型侧(schema 织入、控制符渲染、停止条件、解析)全在库内,但 Agent 循环在库外;「解题能力」是训练写进权重的,库内能讲清它的表达机制(解码策略、logits 加工)和写入路径(Trainer)。
