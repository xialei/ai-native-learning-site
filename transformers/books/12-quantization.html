Chapter 12 · Quantization & Loading

量化与装载:权重的变换

前 11 章讲的是「模型已经就位之后」的事——注意力怎么算、token 怎么出、工具怎么调。这一章讲「就位之前」:一份 15 GB 的 bf16 权重怎么变成 4 GB 出头跑进你的显卡;一份 llama.cpp 的 GGUF 文件怎么进 transformers;一个第三方命名五花八门的 checkpoint 怎么被改写成本库的键名。第 1 章埋的三个钩子——26 个 quantizer 后端、from_pretrained 总入口、并行计划怎么进装载——在这里一起收口。

这一章先拆 26 个后端共用的一套协议(HfQuantizer 的钩子族),再走一遍 from_pretrained 从 config 到可用模型的装配线,然后是 bitsandbytes 4-bit 的一次完整量化、装载器本体的「键改名 + 张量变换」两段式,最后是 GGUF 这条最特别的路径——权重以压缩块形态常住内存,前向时才解开。

答案地图 四个问题的答案串起来是::① 「量化」不是模型能力,是权重的变换:26 个后端各一个 quantizer 文件,实现同一组 HfQuantizer 钩子(validate_environment / update_device_map / preprocess_model / postprocess_model),from_pretrained 在固定点位调用它们(12.1);② from_pretrained 是一条装配线:meta 设备建空壳 → 量化器/精度计划/设备映射完成协商 → 权重以「最终形态」流入(12.2);③ 4-bit 走「换层 + 在线量化」(12.3),GGUF 走「保块 + 前向按批大小选 GEMV 或分块解压」(12.4)——两种账法,显存充裕与紧张的机器各有胜场;④ 键名对不上的 checkpoint 靠 741 条改名 + 72 条张量变换的声明式映射表,每个算子带逆操作,保存时倒放回原格式;词表对不上不自动重塑,靠 LOAD REPORT 报错(12.3b、12.5、12.6)。

12.126 个后端,一套钩子协议

第 1 章盘点过 quantizers/ 目录:26 个 quantizer 文件加一个 base.py 和一个 auto.py。每个文件对应一种量化方案——bitsandbytes 4/8-bit、GPTQ、AWQ、HQQ、torchao、GGUF、mxfp4、nvfp4……名字不同,结构完全一致:实现 HfQuantizer(quantizers/base.py:74)声明的一组钩子。基类长这样:

quantizers/base.py:74 — HfQuantizer 钩子族(骨架,注释为译注)
pythonclass HfQuantizer(ABC):
    requires_calibration: bool   # 该方法要不要校准数据(AWQ/Quark 要,bnb 不要)

    def param_element_size(self, model, param_name, param): ...  # 量化后每元素几字节,喂给设备映射(:129)

钩子之间是「声明 + 协商」,不是硬编码流程。派发在 get_hf_quantizer(quantizers/auto.py:338):读 config 里有没有 quantization_config(有的话说明 checkpoint 本身是预量化的),和用户传参合并,经 AutoHfQuantizer.from_config(auto.py:202)按 quant_method 字符串查 AUTO_QUANTIZER_MAPPING(:77)实例化,再当场跑 validate_environment——bnb 没装、GPU 不在,从这一步就报错,而不是加载到一半。之后 from_pretrained 在固定点位调用:model 构造后 hf_quantizer.preprocess_model(modeling_utils.py:4304),权重加载完 hf_quantizer.postprocess_model(:4379),中途的 device_map 协商和 dtype 决定分别走 update_device_map 与 update_dtype(12.2 的装配线上标了位置)。

「哪个模块不量化」是各钩子交接最多的信息:get_keys_to_not_convert(base.py:39)自动挑出三类必须保持原精度的模块——权重绑定的(tied weights)、模型最后一个模块、输出嵌入(lm_head)——理由写在 docstring 里:「keep the lm_head in full precision for numerical stability reasons」(:41)。模型还能用 _keep_in_fp32_modules 类属性追加清单(见 12.3b)。这段逻辑是量化的第一个坑位指南:量化完模型输出乱码,八成是 lm_head 被一起压了。
钩子时机bnb-4bit 做什么GGUF 做什么

读这张表的正确姿势:左边一列是协议,右边两列是同一协议下的两种实现哲学。bnb 是「换层」哲学——Linear 换成 Linear4bit,权重进层时被压成 4-bit 参数;GGUF 是「保块」哲学——权重从头到尾是文件里的压缩块,模块换成了懂块的 GgufLinear。26 个后端全部落在这两极之间,协议不变。另外注意 requires_calibration 的分野:全库只有 9 个 quantizer 文件声明 True(aqlm、auto-round、awq、bitnet、compressed-tensors、gemma、quark、spqr、vptq)——这类「算出来」的量化要校准数据(量化前跑一批样本统计激活分布);bnb、GPTQ(quantizer_gptq.py:46 显式声明 False)这类「换表示」的不用。一个布尔值,两种量化范式的分界线。

12.2加载主线:from_pretrained 的装配线

第 1 章留了两句话:「from_pretrained 是权重装载的总入口,第 12 章拆」和「AutoModel 怎么找到类,12.2 节会回到这里」。现在兑现。先说分发:你写 AutoModelForCausalLM.from_pretrained(...),工厂(auto_factory.py:266)先读 config——本地有对应实现时经 _get_model_class(:182)从映射表拿到类,拿不到就按 config.architectures 字段猜;多模态套娃配置还会做一层继承:父 config 带 quantization_config 时,把它拷给 text_config(:250-252),否则量化配置在子模型上会丢。所有「Auto 前缀」类共用 _LazyAutoMapping 这张懒表——类只有被查到才 import,这正是第 1 章说的 _LazyModule import 秒开的另一半。

12.3b精度计划:keep_in_fp32 与量化例外

量化的反面是「哪些地方不许降精度」。v5 把这件事做成了 dtype_plan(modeling_utils.py:3764):两个类属性各管一种场景——

modeling_utils.py:3764 — _get_dtype_plan(摘录,注释为译注)
pythondef _get_dtype_plan(self, dtype: torch.dtype) -> dict:
    dtype_plan = {}
    # _keep_in_fp32_modules:只在「bf16 模型被强行用 fp16 加载」时兜底,
    # 把指定模块留在 fp32,防止 bf16→fp16 的精度损耗(#20287,:3768 注释)
    if self._keep_in_fp32_modules is not None and dtype == torch.float16:
        dtype_plan.update(dict.fromkeys(self._keep_in_fp32_modules, torch.float32))
    # _keep_in_fp32_modules_strict:fp16/bf16 都强制升 fp32
    if self._keep_in_fp32_modules_strict is not None and dtype in (torch.float16, torch.bfloat16):
        dtype_plan.update(dict.fromkeys(self._keep_in_fp32_modules_strict, torch.float32))
    return dtype_plan

两个属性的区别是「条件豁免」和「绝对豁免」。前者是历史行为的显式化:bf16 权重配 fp16 计算是出了名的坑,各模型在类属性上声明豁免名单;后者更进一步,fp16/bf16 一律升 fp32——MoE 的路由打分是重灾区,dots1 把 e_score_correction_bias 列进 strict 名单(dots1 :441),ernie4_5_vl_moe 把 gate.weight 和 moe_statics 列进去(:687):路由差一位,token 就走错专家,精度误差在这里被放大成行为差异。另一个用途见 11.3 节的 afmoe:它把 7 个 layernorm 变体和 expert_bias 列进非 strict 清单(:469)——归一化层的方差统计对精度敏感,是量化时最常被豁免的模块类型。全库 33 个模型用 strict 清单,12 个只用非 strict。

dtype_plan 如何进装载:from_pretrained 在权重到达前算出 plan(:4317),按「模块名 glob → 目标 dtype」的映射传给装载器(core_model_loading.py:1644);装载循环里每个张量名先过一遍 glob 匹配(:1677 建索引,:1717 匹配),命中则按 plan 的精度落盘,未命中才用全局 dtype。它的表亲是 quantizer 的 param_element_size(base.py:129):设备映射推断要预估每个模块占多少字节,量化器在这里回答「我的权重每元素几字节」(bnb 4-bit 是 0.5,quantizer_bnb_4bit.py:53)——「多大的模型装得进哪张卡」这道预算题,就是拿这个数算的。精度计划和显存预算是同一套模块尺寸账本的两个读法。

12.4GGUF:权重不解压,前向才算

前三节的所有路径,权重到达模型时都已经是普通张量。GGUF 路线反其道而行:llama.cpp 的量化文件,权重在模型里也保持压缩块形态。这条路径是「量化不是加载时的一次性变换,而是运行时的一种存在方式」的极端版本,v5 对它的重做幅度也最大。

旧实现(modeling_gguf_pytorch_utils.py 的 legacy 路径)把整个文件解压成浮点模型再加载;新实现(GgufHfQuantizer,quantizer_gguf.py:39,配 integrations/gguf/ 子包)把「能不解压的都别解压」做成一次规划:get_gguf_plan(integrations/gguf/utils.py:44)逐张量检查「从文件键到模型键的沿途变换是否全部 supports_packed」——块不跨行,行向操作(Unsqueeze :284、PermuteRows :306、行向拼接 ConcatenateRows :426)不碰字节,声明 supports_packed=True;列向重排 PermuteInputFeatures(:333)会切开块,它参与打包的方式是把置换取逆存成 input_permutation(:338),让 GgufLinear 前向时对激活做重排,权重保持原样——docstring 写得很直白(:327):「Columns cross blocks, so a packed tensor is left as stored and GgufLinear permutes its input instead」。

规划完成,替换开始:packable 的模块换成 GgufLinear(utils.py:126)——一个 weight 参数是 uint8 块的 nn.Linear。它的前向(:144)是这条路线的纲领:

integrations/gguf/utils.py:144 — GgufLinear.forward(骨架,注释为译注)
pythondef forward(self, x):
    flat = x.reshape(-1, self.in_features)
    if self.input_permutation is not None:     # 列置换转为对激活的重排
        flat = flat.index_select(1, self.input_permutation)
    if flat.shape[0] <= MAX_GEMV_ROWS:      # ≤8 行:走专门的多向量-矩阵 kernel
        out = mul_mat_vec(self.weight, flat, self.ggml_type, self.out_features)
    else:
        out = self._unpack_matmul(flat)      # 大批:分块解压 × 矩阵乘,永不整体解压
    ...
两条前向路径的分工:解码阶段一次只有一个新 token(行数 ≤8,MAX_GEMV_ROWS=8,kernels.py:26),走 mul_mat_vec——hub 上的 ggml-org/ggml-quantization kernel(kernels.py:97)直接在 uint8 块上算 GEMV,权重全程不解压;prefill 或批量场景行数超限,退到 _unpack_matmul:按 64M 元素一块地解压、乘完就扔(:160 docstring 原话「never fully materialized」)。MoE 专家同理打包成 GgufExperts(utils.py:177),top-k 的 token 用 mul_mat_id 一次算完(:200)。这正好是第 7 章「双路径」的量化版:decode 走窄 kernel,prefill 走宽路径。「解压与否」不是开关,是按批大小的连续谱。

这条路线还顺带演示了量化与 kernel 生态(12.6)的合流:能不能走打包路径,先看 validate_environment 里 get_gguf_kernel() 有没有当前机器的预编译 kernel(:69)——没有就连 kernel 都不装,整个模型转 dequantize 模式(:71,警告写明「It will need several times the memory the file does」);有,则 kernelize_ggml_layers(kernels.py:143)把 ggml 的 fused 层 kernel 挂到模型上,挂不上就回退到模型自己的层(:158 的日志:「no ggml kernel for ...; it keeps the model's own layer」)。注意力还有一个可选的 ggml-org/ggml-attn kernel(quantizer_gguf.py:166)。目前打包级支持(不解压)的架构有 qwen35、qwen35moe、lfm2 三个(GGUF_ARCHS,gguf_conversion_mapping.py:237),其余走 legacy 解压路径——架构覆盖面还在扩张中,读代码时以 GGUF_ARCHS 为准。

为什么 GGUF 值得单独一节:它是「权重文件格式、内存布局、计算 kernel」三层被当成一个整体设计的实例。bnb 4-bit 的世界观是「加载时压好,运行时就是普通层」;GGUF 的世界观是「压缩块就是运行时形态,解压才是异常路径」。前者的解压成本在加载时一次性付掉,后者的解压成本按需摊进每次前向——两种账法在显存充裕与紧张的机器上各有胜场,没有哪个全面胜出。服务引擎(vLLM/SGLang)同样要对量化格式做「解压或不解压」的决策,这里的规划逻辑(get_gguf_plan 的「沿途变换是否碰字节」)是理解那个更大世界的最小样本。

12.5装载器本体:WeightRenaming 与 WeightConverter

12.2 装配线的第⑧站背后,是 v5 全新写的装载器。MIGRATION_GUIDE_V5.md:32 宣布了这次重做:「This weight loading API is designed to apply operations to the checkpoints loaded by transformers」——设计目标是「对 checkpoint 施加操作」,而不是按序列化原样加载。设计的核心是两类变换:

core_model_loading.py — 两大类与配套算子(结构摘录)
pythonclass WeightTransform:                    # :798 基类,__slots__ 限死可挂的属性(:800)
    source_patterns / target_patterns      # 键的来源与去向
    distributed_operation / quantization_operation   # 挂载点:TP 切分(:804)、量化(:805)
    collected_tensors: dict[str, list[Future]]       # 异步收集池(:825)

class WeightRenaming(WeightTransform):     # :1027 只改键名,不动张量
class WeightConverter(WeightTransform):    # :1187 改键名 + 张量操作链
    operations: list[ConversionOps]        # Chunk/Split/Concatenate/Interleave/Transpose/...
    # 每个算子都带 reverse_op(:97),保存时原路倒放

映射表按 model_type 组织在 conversion_mapping.py(2320 行)里,_build_checkpoint_conversion_mapping(:150)登记了 741 条 WeightRenaming 和 72 条 WeightConverter。看两个真实条目,操作链的「味道」就出来了:

conversion_mapping.py:1131 — mixtral 的专家权重合并(摘录,注释为译注)
python"mixtral": [
    WeightRenaming(".block_sparse_moe.", ".mlp."),
    WeightConverter(
        source_patterns=[".experts.*.w1.weight", ".experts.*.w3.weight"],
        target_patterns=".experts.gate_up_proj",
        operations=[
            MergeModulelist(dim=0),   # 8 个专家各一列 w1/w3 → 各聚成 1 份(:1140)
            Concatenate(dim=1),        # gate 与 up 拼成 gate_up(:1143)
        ],
    ), ...]

另一条是 kimi_k25 视觉塔的 qkv 拆分(:535,该条目从 :496 起),方向相反:checkpoint 里存的是一个融合的 wqkv,本库要三个独立矩阵,还要顺手做 RoPE 的维度重排——

conversion_mapping.py:535 — qkv 拆分 + rope 重排(摘录,注释为译注)
python# Unfuse qkv and apply rope permutation
WeightConverter(
    source_patterns=[r"wqkv"],
    target_patterns=[r"attn.q_proj", r"attn.k_proj", r"attn.v_proj"],
    operations=[
        Chunk(dim=0),                 # 一份 wqkv 切三份
        PermuteForRope(subconfig_key="vision_config", permute_layer_names=["q_proj", "k_proj"]),
    ], ...)
PermuteForRope 是「键名转换」和「数值语义」纠缠的最好例子(core_model_loading.py:461):这个视觉塔的 checkpoint 来自另一个训练框架,它的 q/k 排布与本库 RoPE 实现的约定差一个置换。权重数值没错,只是「谁的约定」的问题——装载器把它转成本库约定。换句话说,conversion_mapping 处理的不只是「键名对不上」,还有「同一数学对象的不同内存排布」。qwen2_moe 的 gate/up 融合、各家族 MoE 的 w13→gate_up、跨家族的 embed_tokens 改名(:172),都是这张表上的条目。72 条 WeightConverter 还各带一个 distributed_operation 槽位(:804)——TP 切分不是装载后的后处理,是同一张表里的另一种变换,第 1 章的并行计划在这里落地。

装载循环(convert_and_load_state_dict_in_model,core_model_loading.py:1546)把这张表跑成流水线:checkpoint 的每个张量先按改名规则改键名(:1685),命中哪个 converter 就把自己挂到那个 converter 的收集池(collected_tensors,元素是 Future——异步加载);全部挂完,逐 converter 执行 convert:先把 Future 收割成真张量,再跑操作链,最后 set_param_for_module(:1378)把结果写进模型参数并盖上 _is_hf_initialized 章(:1417)——旁边的注释写「super important otherwise _init_weight will re-init the param」(:1416),盖了章的参数在「缺键补初始化」时会被跳过(modeling_utils.py:2364)。

异步加载是这张流水线的第二引擎:spawn_materialize(:1279)在线程池上提交张量搬运,GLOBAL_WORKERS = min(4, CPU 核数)(:1268),主线不等拷贝完成就处理下一个键——读 checkpoint 的 I/O 与换算的 CPU 时间重叠起来。三处例外强制同步(:1659-1669):磁盘卸载(内存受限)、在线量化(:1663,注释写明防止工作线程把全精度张量灌满 GPU 造成显存尖峰)、环境变量 HF_DEACTIVATE_ASYNC_LOAD(:1665)。迁移指南把异步搬运列为重做收益之一(「Faster model loading thanks to scheduling of tensor materialization」,MIGRATION_GUIDE_V5.md:70)。加载完的错误报告也是结构化的:LoadStateDictInfo(utils/loading_report.py:156)收齐 missing/unexpected/mismatched/conversion_errors 四类,log_state_dict_report(:273)打成终端宽度的 LOAD REPORT 表;conversion_errors 直接抛错(:310),形状不符且没开 ignore_mismatched_sizes 也抛(:315)——「加载一个键名对不上的老 checkpoint」从「读不懂的 traceback」变成了「一张带修复建议的账单」。
词表对不上怎么办:老实报错,不自动重塑。第 2 章埋过一个问题:换分词器意味着 embedding 行数对不上。v5 的答案是:shape 不符的键进 mismatched_keys,LOAD REPORT 列出来,默认抛 RuntimeError——库不做静默重塑,因为「新词表的行用什么初始化」是训练决策,不是装载决策。真要换词表,走显式 API resize_token_embeddings:新增行用旧嵌入的均值初始化(modeling_utils.py:3020),同样盖 _is_hf_initialized 章防止被补初始化覆盖(:3017)。装载器只管「照章办事」,改动语义的事留给明确的调用。

12.6kernel 化、保存侧与断代收口

量化管「权重怎么存」,kernel 管「计算怎么算」——v5 把后者也接进了同一套声明式体系。每个模型的建模文件里散布着装饰器:

models/llama/modeling_llama.py:51 — 两类装饰器(摘录,注释为译注)
python@use_kernel_forward_from_hub("RMSNorm")      # :51 整层替换:RMSNorm 换成 hub kernel
class LlamaRMSNorm(nn.Module): ...

@use_kernelized_func(apply_rotary_pos_emb)          # :205 函数替换:rotary 计算换实现
class LlamaAttention(nn.Module): ...

装饰器只是「贴标签」:kernels 库没装时它们原样返回类(hub_kernels.py:749 的 stub),模型照常工作。真正生效在装配线第⑨站——set_use_kernels(modeling_utils.py:3780)调用 kernelize(hub_kernels.py:953):按一张映射表(_KERNEL_MAPPING,:146,28 个条目:RMSNorm、rotary_pos_emb、SwiGLUMLP、激活函数家族、mamba 全家、MegaBlocksMoeMLP 等)把贴了标签的层换成 hub 上的预编译 kernel。映射表里连设备能力都写了条件——Qwen3.5 的 GatedDeltaNet 只在 SM121(GB10)与 ROCm gfx1151(Strix Halo)两个特定芯片上启用对应仓库的 kernel(:163,:162 的注释解释了原因:那两块卡上没有 fla/causal_conv1d 的常规编译),通用 CUDA 机器保持 PyTorch 原实现。290 处装饰器散布在 185 个模型文件里(llama 的 RMSNorm :51、qwen3 同款 :48),写新模型时,凡是映射表里有的层,都该挂上装饰器「等着被 kernelize」。

为什么这件事出现在「量化」一章:kernel 化与量化是同一个问题的两面——「默认实现慢,换一个更快的」。量化把「存 16 位」变成「存 4 位」,kernel 化把「PyTorch 组合算子」变成「一个 fused kernel」;两者都在装载期声明、按环境协商、失败优雅回退。运行期想关也关不掉:use_kernels 的 setter 明说「Disabling kernels at runtime is a no-op as there is no 'unkernelize' routine」(modeling_utils.py:4711)——kernel 化发生在装载期,是结构的一部分,不是运行开关。

最后是保存侧。12.5 说过每个算子带 reverse_op(:97);save_pretrained 带 save_original_format=True 时,装载被整个倒放:revert_weight_conversion(core_model_loading.py:1824)按相反顺序套逆操作,把本库的键名和张量排布还原成 checkpoint 原来的样子(modeling_utils.py:3461)。装载是可逆的——「进来是什么格式,出去还是什么格式」,第三方 checkpoint 不被本库「劫持」。

回到第 0 章的问题:为什么一个库要花一年时间做减法。这一章给的全是「减」的证据:TensorFlow 和 Jax 整体移除;裸的 load_in_4bit/load_in_8bit 参数删掉,只剩 quantization_config 一条路;v4 时代「先装好再改」的装载,换成「先改好再装」的一条装配线;所有键名变换、张量重排、TP 切分、量化操作,收进同一张声明式映射表——741 条改名、72 条变换、20 余种算子,每个带逆操作。减掉的是「同一件事的第五种做法」,留下的是「一件事只有一种声明方式」。声明式的好处在这一章处处可见:GGUF 的打包规划是在这张表上「决定,不是猜测」(get_gguf_plan 的 docstring:「this is decided, not guessed」,utils.py:50);TP 切分与量化共用一个挂载点;保存的逆变换是同一张表的倒放。读完 v5 的装载系统再回头看第 1 章的 import 表和第 5 章的生成循环:这个库最重的资产不是哪一段算法,而是「所有变化都过同一张声明表」的纪律。
图 12.1:量化与装载在 from_pretrained 里的位置。所有路径共享「meta 建壳 → 结构改造 → 权重流入」的三段式;bnb 与 GGUF 的差别只在④的权重形态。

本章小结

「量化与装载」是同一个系统的两个名字:v5 把 from_pretrained 重写成一条装配线——meta 设备建空壳,量化器/精度计划/设备映射/kernel 替换完成协商与结构改造,权重以「最终形态」流入。26 个量化后端实现同一组 HfQuantizer 钩子(validate/update/preprocess/postprocess);bnb 4-bit 走的是「换层 + 在线量化」,GGUF 走的是「保块 + 前向按批大小选 GEMV 或分块解压」,打包与否由「沿途变换是否碰字节」决定,不猜。装载器本体是 741 条改名 + 72 条张量变换的声明式映射表,每个算子带逆操作,保存时倒放回 checkpoint 原格式;缺键、形状不符、转换失败统一进 LOAD REPORT,词表重塑不自动做、留给 resize_token_embeddings。精度计划(_keep_in_fp32_modules 两级)与设备映射预算(param_element_size)是同一本模块尺寸账的两个读法。kernel 化(290 处装饰器、28 条映射)把「换更快的计算」接进同一套「声明→协商→回退」协议,且装上就卸不下——它是结构,不是开关。下一章收口:把全书拆过的部件拼成一张「自研路线图」。
