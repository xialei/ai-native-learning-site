生成循环：一次 generate 从头走到尾

第 3 章的前向输出 logit 向量，第 4 章的缓存让增量解码成为可能。但「一个 token 一个 token 循环生成、条件满足才停」这件事本身，是谁在驱动？答案是一个你可能天天在调、但很少打开的函数：generation/utils.py 的 generate()——4437 行文件里最长的入口方法，从校验参数到分发解码策略，串起整库推理侧的所有子系统。

这一章拆它的九步流程（:2569 起），再看唯一留在库内的解码主循环 _sample(:3104)——其余解码策略或被并入、或已移出库外改为按需从 Hub 拉取——最后看两个特殊机制：chunked prefill 与 MPS 设备上的「晚一步停」。

答案地图 四个问题的答案，一条条对上：① 生成循环是「前向 + 取 logit + 选词 + 追加判停」的重复，缓存让它每步只前向一个新位置(5.1/5.2)；② 对话回合之间的粘合是 kwargs 演进(_update_model_kwargs_for_generation)与缓存续写——上一步的输出就是下一步的输入(5.2/5.6)；③ 策略入口收敛成 GenerationMode 枚举 + 一张映射表，greedy 并入 sample，四种长尾策略改为 Hub 插件按需拉取(5.3)；④ 判停本身有同步代价，MPS 设备用「晚一步停 + 回滚」把每步的设备同步挤掉(5.5)。

5.1入口：九步准备，一次分发

generate() 的文档字符串有 93 行，但骨架是源码注释里编好号的九步。压到最干：

generation/utils.py:2569 — generate() 骨架（注释为译注）

两个值得停一停的入口分流：

custom_generate——把解码策略当插件：传一个 Hub 仓库名，generate 会拉取该仓库 custom_generate/generate.py 里的函数替换默认逻辑，签名不变、返回类型可以不同；传本地路径也行（需 trust_remote_code）。四个老策略(contrastive/dola/group-beam/constrained-beam)就是这么「降级」成 Hub 插件的：库内删代码，不再维护四条并行的 while 循环，需要的人按需拉取。另一个方向是传 Callable——库内走完九步准备，循环体换成你的函数：参数校验/缓存/处理器链这些公共设施照用，策略本身自便。
paged 触发的自动分流：generate 检测到 cache_implementation=="paged" 会打警告并把输入转发给 generate_batch——连续批处理在 v5 里已是一等公民，只是入口兼容旧写法（「你该直接用 generate_batch」的提示与自动转发并存，第 7 章展开）。

5.2主循环：六拍循环与 kwargs 演进

分发下去的策略方法里，最核心的是 _sample——v5 里 greedy 与 multinomial sampling 合并成一个方法（do_sample 开关决定选词方式），它是生成主循环的基准实现：

generation/utils.py:3104 — _sample 主循环（骨架，注释为译注）
pythondef _sample(self, input_ids, logits_processor, stopping_criteria, generation_config, ...):
    # 预填充:整个 prompt 一次前向,建立缓存
    outputs = self._prefill(input_ids, generation_config, model_kwargs, ...)

    while self._has_unfinished_sequences(this_peer_finished, synced_gpus, device=...):
        if prefill_consumed:
            model_inputs = self.prepare_inputs_for_generation(
                input_ids, next_sequence_length=1 if use_cache else None, **model_kwargs)
            outputs = model_forward(**model_inputs, return_dict=True)   # ① 前向一步

        model_kwargs = self._update_model_kwargs_for_generation(outputs, model_kwargs, ...)
        # ② 取最后一位 logit(fp32 拷贝,避免引用大张量)
        next_token_logits = outputs.logits[:, -1].to(copy=True, dtype=torch.float32, ...)

        # ③ 处理器链(第 6 章)→ ④ 选词
        next_token_scores = logits_processor(input_ids, next_token_logits)
        if do_sample:
            probs = nn.functional.softmax(next_token_scores, dim=-1)
            next_tokens = torch.multinomial(probs, num_samples=1).squeeze(1)
        else:
            next_tokens = torch.argmax(next_token_scores, dim=-1)

        # ⑤ 追加 + ⑥ 判停
        next_tokens = next_tokens * unfinished_sequences + pad_token_id * (1 - unfinished_sequences)
        input_ids = torch.cat([input_ids, next_tokens[:, None]], dim=-1)
        unfinished_sequences = unfinished_sequences & ~stopping_criteria(input_ids, scores)
        this_peer_finished = stop_check(unfinished_sequences, next_tokens, input_ids.shape[1])
        del outputs

逐拍看：

① prepare_inputs_for_generation。缓存就位后每步只需喂新 token——next_sequence_length=1 让模型侧裁到「缓存长度之后的那一位」。第一个循环轮跳过前向，因为 prefill 已替它做完（prefill_consumed 开关），直接从判停接续。

② logits[：， -1].to（copy=True， dtype=torch.float32）。一行三件事：拷贝、升 fp32（采样数值稳定性）、放回 input_ids 所在设备。注释解释为什么要 copy——不留 copy，outputs.logits 这个大张量会活到下一轮；首步 logits 可能有 [batch， 全序列长， 词表] 那么大。

⑤ 已结束的序列继续喂 pad。batch 里某条序列碰到 EOS 后 unfinished_sequences 置 0，后续每步它的「下一个 token」被那行乘加盖成 pad_token_id——继续占位、不再影响其他序列，batch 对齐的惯用法。

del outputs 那行注释值得读：「This is needed to properly delete outputs.logits ... Otherwise a reference to outputs is kept which keeps the logits alive in the next iteration」——循环体不留 outputs 引用，显存才能在长生成里保持平稳。大模型工程里的显存 bug 往往不是「没释放」，而是「有个变量悄悄引用着」。这 20 行是全库性能最敏感的代码，每一步都在跟张量生命周期搏斗。

kwargs 演进：上一步的输出如何变成下一步的输入

循环里最不起眼但最要紧的是 _update_model_kwargs_for_generation(:1231)：attention_mask 追加一列 1、token_type_ids 复制末列、position_ids 取「上位置值 + num_new_tokens」接续（按缓存长度折算位置是模型 forward 里的事）——上一步的全部痕迹经它滚进下一步。decoder 模型的 decoder_input_ids 不经它：新 token 由循环体里一行 torch.cat 追加。第 3 章 3.1 节骨架 ③ 的 past_seen_tokens 则在模型 forward 里从缓存账本读出(modeling_llama.py:376)。对话「记得之前说过什么」的工程事实，一半在缓存，一半在这行 kwargs 演进。

为什么砍掉四个策略？每条策略都是一条独立的 while 循环，彼此共享的只有「前向 + 处理器链」骨架；每修一个 bug、每加一种缓存类型都要乘四。库内保住三条主路径(sample/beam/assisted)，长尾转 Hub 插件——与 2.4 节分词后端收敛到 Rust 是同一个趋势：库的边界画在「高频使用的核心」处。generate 里还有一段 _get_deprecated_gen_repo 专门为老写法生成兼容跳转，注释标注 v4.62 移除——过渡期的礼貌。

5.4prefill 与 chunked prefill

生成第一步是 prefill：整个 prompt 一次前向，建立缓存。_prefill(:4251)有两个分支，分界线是 generation_config.prefill_chunk_size：

generation/utils.py:4251 — _prefill 两个分支（骨架，注释为译注）
pythondef _prefill(self, input_ids, generation_config, model_kwargs, is_first_iteration=True):
    # 分支一:一次前向,适合短/中 prompt
    if generation_config.prefill_chunk_size is None:
        model_inputs = self.prepare_inputs_for_generation(input_ids, ...)
        return self(**model_inputs, return_dict=True)

    # 分支二:prompt 切块逐块喂,缓存逐块长(超长 prompt / 显存吃紧)
    else:
        if cache is None:
            raise ValueError("Cannot use prefill chunking without a cache")
        getattr(torch, "_dynamo").config.cache_size_limit = 64  # flex 编译图会变多,提前放宽上限
        # 接着已有缓存续写时,input_ids 可能含旧 token,只切出新的那段
        input_chunks = torch.split(input_ids[:, -next_sequence_length:], chunk_size, dim=-1)
        attention_mask = model_kwargs.pop("attention_mask", None)
        past_length = cache.get_seq_length()   # 不再固定从 0 起算
        for input_chunk in input_chunks:
            current_length = past_length + input_chunk.shape[-1]
            model_kwargs["attention_mask"] = attention_mask[:, :current_length]
            ...  # 前向一块,缓存追加一块
为什么需要 chunked prefill：100 万 token 的 prompt，一次前向意味着一个 [1， 1000000， hidden] 的激活张量直接打爆显存。切块后峰值显存 = 单块激活 + 缓存，代价是 flex_attention 的编译图数量翻倍——所以循环前先把 dynamo 缓存上限从默认 8 提到 64，注释里说免得撞上「非常难读懂的报错」。服务端引擎(vLLM/SGLang)把「prefill 与 decode 分时复用」做成了独立的调度问题，Transformers 这里的 chunked prefill 是单机版的前置形态，第 7 章会再遇到这个术语。

另一个细节在 _prefill 开头：从已有缓存续写（接着上次对话）时，输入可能是「完整序列」或「只有新 token」两种，分支依据是 attention_mask 长度与 input_ids 长度的比较——续写不是重算，而是切片后只前向新的一段。这件事在一次修复(#49662)里才在分块路径上补齐：此前分支二固定 past_length = 0 且按整段 input_ids 切块，续写时分块 prefill 会与已有缓存错位；现在两条分支共用同一个 next_sequence_length，分块路径也从 cache.get_seq_length() 起算，并明确要求传进来的必须是一个缓存对象。

5.5判停：停止条件、streamer 与「晚一步停」

循环怎么停？generate 第 8 步装配的停止条件链是第一道，StopCheck 是循环里的实际判停点，它同时是流式输出的出口：

generation/utils.py:385 — StopCheck（注释为译注）
pythonclass StopCheck:
    """Decides when the decoding loop should stop, and hands each new token to a streamer."""

    def __call__(self, unfinished_sequences, tokens, length) -> bool:
        if self.streamer is not None:
            self.streamer.put(tokens.cpu())          # 流式输出与判停共用同一处钩子
        return bool(unfinished_sequences.max() == 0)

内置停止条件(stopping_criteria.py)有四类：MaxLengthCriteria（:62，按总长）、MaxTimeCriteria（:93，按墙钟时间）、EosTokenCriteria（:543，按 EOS）、StopStringCriteria(按字符串，如 stop_strings=["</answer>"])。用户自定义条件继承 StoppingCriteria(:48)塞进列表即可——判停是开放扩展点。

「晚一步停」（DeferredStopCheck， :403） 是全文件最讲究的优化：判停要读 unfinished_sequences.max() == 0——这是一次设备→主机同步，每步卡住主机等设备追上。v5 的解法：异步拷贝 stop 标志到 pinned 内存，下一轮才读上一轮的结果，主机永远比设备快一步；多用一次前向，finish() 返回要回滚的步数，循环外把多算的步数撤掉。目前只在 MPS 设备启用（is_supported 里 device.type ！= "mps" → False），注释写明「cuda 上若实测有收益再开」。流式 token 同样要同步，所以也晚一步——「多余的那个 token 永远不会流出：循环断掉时它还在飞，finish 时丢弃」。用一次冗余前向换掉每步一次的同步，这笔账在低算力设备上划算。

StopStringCriteria 是内置条件里最复杂的一个：停止串可能跨 token 边界，token 与停止串还可能部分重叠。它把「token → 停止串位置」的映射在开始前预计算成 embedding 向量，运行时一次查表 + 张量比较完成匹配——把 Python 逐串循环换成纯张量操作。第 9 章工具调用的「检测 JSON 收尾」场景会回到这里。

5.6输出与续写：缓存拿在手里接着聊

generate 默认只返回张量；return_dict_in_generate=True 时返回 GenerateDecoderOnlyOutput(:184)，把 sequences/scores/logits/attentions/hidden_states/past_key_values 打包。其中 past_key_values 字段最实用：一个回合结束后把缓存拿出来，下一回合把新 prompt 追加进去传入，就能「接着聊」而不重算历史——第 4 章 4.4 节「默认缓存类由模型决定」的机制在这里接上了：模型侧用 config.layer_types 选缓存类，用户侧 return_dict_in_generate 拿到缓存，下一回合原样传回。

图 5.1：generate 的两段结构。准备阶段把一切装配好，循环里只剩六拍；「判停」一路通向流式出口，一路通向返回。

本章小结

generate 是九步流水线：custom_generate/paged 分流 → GenerationConfig 校验 → 模式判定（GenerationMode 枚举 + GENERATION_MODES_MAPPING）→ 输入准备 → 长度折算 → 备缓存 → 装配两条链 → 分发。核心循环 _sample 是六拍：前向、取末位 logit（fp32 拷贝）、处理器链、选词、追加、判停；greedy 并入 sample（只差选词方式），contrastive/dola/group-beam/constrained-beam 四策略转 Hub 插件。prefill 一次前向建立缓存，prefill_chunk_size 切块摊薄长 prompt 峰值显存。判停双链：StoppingCriteriaList（长度/时间/EOS/字符串四类内置，开放扩展）+ StopCheck（兼流式出口）；StopStringCriteria 预计算 embedding 向量做跨 token 匹配；MPS 设备的 DeferredStopCheck 用「晚一步停 + 回滚」消掉每步设备同步。return_dict_in_generate 返回的缓存可直接续写对话。

循环里「选词」一拍被压成一行——背后是整条 logits 处理器链和采样参数体系。第 6 章：选词。
