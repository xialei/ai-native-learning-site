整体架构:531 个模型,一张图纸

打开 transformers 仓库,扑面而来的是 531 个模型目录、五万多行一个的 modeling 文件堆、54.5 万多行建模代码——从哪下手?都说「所有模型共用一套基类」,那套基类在哪个文件、管到哪一步为止?改一个模型的行为,为什么 HuggingFace 官方让你改另一个文件?读完源码想自己接一个新模型,又该抄哪一份?

这一章不进任何算法,只画地图。核心结论先给:531 个模型目录里,独立的设计不到二十个,其余由代码生成器从一份份「源模型定义」派生;所有模型共同依赖的设施,集中在 src/transformers/ 顶层的十几个文件里。这一章认目录、认继承链、认生成机制——后面每一章拆的,都是这张图纸上的某一块。

答案地图 四个问题,答案按节序给全::① 要读的是顶层十几个核心文件 + 一个模型作解剖样本,531 个目录不必逐个看(1.2 / 1.3);② 共用基类是 PreTrainedModel,在 modeling_utils.py,管加载/保存/设备/注意力路由,不管具体算什么(1.4);③ 改模型要改 modular_*.py——它才是源文件,modeling_*.py 是生成产物(1.5);④ 接新模型抄 modeling_llama.py + 一份 modular 源,走四步(1.6)。

1.1一分钟版本

Transformers 本质上在回答一个问题:「把『一个 Transformer 架构』从论文变成能加载、能微调、能生成、能上传下载的工程实体,哪些部分每个模型都要重做一遍,哪些做一次就够?」 它的答案是把后者的部分全部沉到基类和公共层:

  • PreTrainedModel(modeling_utils.py,5182 行) — 所有模型的基类:权重下载与加载、保存、设备放置、量化挂钩、注意力后端路由、梯度检查点。
  • GenerationMixin(generation/utils.py,4437 行) — 生成循环:greedy/beam/采样/投机解码,任何类混入它即可获得 .generate()(第 5 章)。
  • 每个模型目录 — 只写「这个架构特有」的部分:注意力变体、位置编码、层间连接,加一份 configuration。llama 目录总共 1389 行,其中 modeling_llama.py 只有 501 行。

关键观察:一个「7B 大模型」的完整实现,在库里只有 500 行左右。难的不是建模代码,是那 500 行下面垫着的 6.8 万行公共设施(1.2 节实测)。读这本书的姿势因此也定了——读一份最简模型(第 1.3 节选 llama),然后顺着它 import 的每个模块往下钻。

1.2体量怎么收敛:531 个目录,不到二十个设计

仓库 2026-10-20 主干快照的实测数字:models/ 目录下 531 个模型,516 份 modeling_*.py,合计约 54.5 万行 Python。表面上这是一座无法读完的迷宫,实际收敛方式有两条,先看第一条——文件是生成的。

实测(2026-10-20,823a6ea6d8)数字说明
models/ 子目录531每个架构一个目录(另有 1 份 __init__.py)
modeling_*.py516运行时实际 import 的实现
modular_*.py310人写的源文件,生成 modeling(1.5 节)
modular 源码合计188,517 行经转换器展开成 54.5 万行 modeling 代码
quantizer 后端26量化方案各一个文件(第 12 章)
src/transformers/*.py 顶层合计68,048 行所有模型共享的设施

第二条收敛是设计本身在收敛。Llama 系架构 2023 年发布后,业界新模型几乎全是它的变体:换位置编码方案、换注意力变体(GQA、滑动窗口、线性注意力)、换 FFN(MoE、门控),骨架不动。库里的反映是:qwen3_next 的 modular 源文件开头 import 的,就是 llama、mixtral、qwen2_moe、qwen3_moe 的现成类,加上少量新写的层。真正独立的设计——BERT 这类 encoder、T5 这类 encoder-decoder、CLIP 这类双塔、Whisper 这类语音——两只手数得过来。

生成物怎么读:打开多数 modeling_*.py(516 份里约 300 份),文件头都有一段红色警告:此文件由 modular_*.py 自动生成,手改会被覆盖;llama 这类没有 modular 源文件的例外,文件头只有 Apache 许可证。要理解某个模型,先找它旁边(或它继承链上游)的 modular 源文件;要找某个算子的真实出处,顺着 import 找上游模型。这两个动作能避免在生成代码里迷路。

1.3解剖样本:一个模型目录里有什么

选 llama 目录作样本——它是最小的新式架构之一,目录里四个文件:

文件行数内容
configuration_llama.py103LlamaConfig:超参数容器与默认值
modeling_llama.py501实现(生成产物)
tokenization_llama.py149分词器后端适配(第 2 章)
convert_llama_weights_to_hf.py602原始 meta 权重 → HF 格式转换脚本

modeling_llama.py 里的类,正好是一座 Transformer 自底向上的每一层:

src/transformers/models/llama/modeling_llama.py — 类清单(行号 pin:823a6ea6d8)
pythonclass LlamaRMSNorm(nn.Module):              # 52 行  归一化层
class LlamaRotaryEmbedding(nn.Module):        # 72 行  旋转位置编码
class LlamaMLP(nn.Module):                    # 152 行 前馈层(门控)
class LlamaAttention(nn.Module):              # 206 行 注意力(路由到后端)
class LlamaDecoderLayer(GradientCheckpointingLayer):  # 273 行 一层 = attn + mlp
class LlamaPreTrainedModel(PreTrainedModel):  # 317 行 声明能力契约
class LlamaModel(LlamaPreTrainedModel):       # 336 行 主体:embed + N 层 + norm
class LlamaForCausalLM(LlamaPreTrainedModel, GenerationMixin):  # 410 行 + lm_head + 损失
class LlamaForSequenceClassification(...):    # 484 行 任务头系列

这份清单值得记,因为 531 个模型里有三百多个都是同一份清单改几个类名。每个类的职责在后面对应的章节展开:Attention 在第 3 章,MLP 与「键值记忆」在 3.4 节,DecoderLayer 与梯度检查点在 11 章,ForCausalLM 的 forward 与 logits 在第 5 章。这里先看两个「清单之外的类」——它们是理解全库的钥匙。

钥匙一:LlamaPreTrainedModel,五份声明就是全部

modeling_llama.py:317 — 能力契约(全文摘录)
pythonclass LlamaPreTrainedModel(PreTrainedModel):
    config: LlamaConfig
    base_model_prefix = "model"
    supports_gradient_checkpointing = True
    _no_split_modules = ["LlamaDecoderLayer"]
    _skip_keys_device_placement = ["past_key_values"]
    _supports_flash_attn = True
    _supports_sdpa = True
    _supports_flex_attn = True
    _can_compile_fullgraph = True
    _supports_attention_backend = True
    _can_record_outputs = {
        "hidden_states": LlamaDecoderLayer,
        "attentions": LlamaAttention,
    }
为什么是「声明」而不是「实现」:基类 PreTrainedModel 的代码会读这些类属性来决定行为——加载时按 _no_split_modules 切设备,生成时按 _supports_* 选注意力后端,输出时按 _can_record_outputs 决定要不要回收中间态。模型作者的工作因此缩到「如实声明我能干什么」。这个模式贯穿全库:能力用声明表达,机制在基类统一实现。

钥匙二:LlamaForCausalLM,主体与任务头的分界

modeling_llama.py:410 — forward 核心路径(摘录,注释为译注)
pythonclass LlamaForCausalLM(LlamaPreTrainedModel, GenerationMixin):
    # 权重绑定:lm_head 与词嵌入共享同一份矩阵(省一份 vocab×hidden)
    _tied_weights_keys = {"lm_head.weight": "model.embed_tokens.weight"}
    # 并行切分计划(第 12 章):TP 按列切、PP 作为最后一段、FSDP 保持整份
    # 输入嵌入不写在这里:init_parallel_plans 给有 embed_tokens 的模型统一补 embedding_rowwise
    _tp_plan = {"lm_head": "colwise_gather_output"}
    _pp_plan = {"lm_head": (["hidden_states"], ["logits"])}
    _fsdp_plan = {"lm_head": "keep_full_weight"}

    def forward(self, input_ids=None, attention_mask=None, position_ids=None,
                 past_key_values=None, inputs_embeds=None, labels=None,
                 use_cache=None, logits_to_keep=0, **kwargs):
        outputs = self.model(...)          # 主体:embed → N×DecoderLayer → norm
        hidden_states = outputs.last_hidden_state
        # 只对最后几个位置算 logits——生成时每个新 token 只需要最后一个位置
        slice_indices = slice(-logits_to_keep, None) if isinstance(logits_to_keep, int) else logits_to_keep
        logits = self.lm_head(hidden_states[:, slice_indices, :])

        loss = None
        if labels is not None:          # 训练路径:labels 进来就算损失
            loss = self.loss_function(logits=logits, labels=labels, vocab_size=self.config.vocab_size, **kwargs)

        return CausalLMOutputWithPast(loss=loss, logits=logits,
            past_key_values=outputs.past_key_values, ...)
三个值得停下的细节:① 一份 forward 同时服务训练与生成——labels 给是训练,不给是推理,分支只有三行;② logits_to_keep 是生成性能的关键旋钮:32k 上下文生成一个 token,如果对全部位置算 logits,那是一次 vocab_size×32k 的大矩阵乘,而真正需要的只有最后一行;③ 并行计划(_tp_plan/_pp_plan/_fsdp_plan)直接写在类属性上——分布式不再是训练器外挂的适配,而是模型自己声明切法(第 12 章展开)。这张表只写「例外」:输入嵌入由 DistributedMixin.init_parallel_plans 统一补 embedding_rowwise,只要模型自己有一个叫 embed_tokens 的 nn.Embedding——tie 过的 lm_head 按词表切、嵌入却每卡复制整份 vocab×hidden,是此前最浪费的一处不对称。

1.4基类管什么:PreTrainedModel 与 from_pretrained

所有模型继承链的顶端是这个签名:

src/transformers/modeling_utils.py:1068 — 基类声明(摘录)
pythonclass PreTrainedModel(
    nn.Module, EmbeddingAccessMixin, ModuleUtilsMixin,
    PushToHubMixin, PeftAdapterMixin, DistributedMixin
):

六个父类各管一摊:nn.Module 是 PyTorch 本体;EmbeddingAccessMixin 统一暴露输入/输出嵌入的读写;ModuleUtilsMixin 提供参数量统计、梯度检查点开关这类小工具;PushToHubMixin 管模型上传下载;PeftAdapterMixin 管 LoRA 等适配器挂载;DistributedMixin 管设备映射与并行计划。基类本体最大的两件事是 from_pretrained(modeling_utils.py:3823 起,权重装载的总入口,第 12 章拆)和注意力后端路由(同文件 5121 行的 AttentionInterface,第 3 章 3.6 节拆)。

公共设施(本书前 9 章) 用户可见面 每模型私有
图 1.1:四层结构。L2 的 54.5 万行里,大部分是同一份图纸的变体;真正需要逐行读的是 L3 的 6.8 万行。依赖方向单一向上,读源码从 L4 向上走即可。

还要交代 import 的一条内幕。顶层 __init__.py 并不真的加载 531 个模型——它把 sys.modules 替换成一个 _LazyModule,你写 from transformers import LlamaForCausalLM 时才按需加载对应模块。这是 import 秒开、显存不炸的关键,也是「AutoModel 怎么找到类」这套自动机制(auto_modeling)的地基,第 12 章 12.2 节会回到这里。

1.5modular 机制:改模型为什么改另一个文件

2023 年之前,往库里加一个新模型意味着复制几千行近似的代码——531 个目录的重复就是这么来的。2024 年起库引入 modular transformers:每个新模型只写一份 modular_*.py,声明它继承谁、改了什么,其余交给转换器(utils/modular_model_converter.py,2212 行,基于 libcst 做 Python 语法树变换)展开成完整实现。

看一个真实样本的开头就明白了:

src/transformers/models/qwen3_next/modular_qwen3_next.py — 开头 import(摘录)
python# Qwen3-Next:线性注意力 + 门控 DeltaNet + MoE 的混合架构
from ..gemma2.modeling_gemma2 import Gemma2RotaryEmbedding      # 位置编码借 gemma2
from ..gemma3.modeling_gemma3 import Gemma3RMSNorm              # 归一化借 gemma3
from ..llama.modeling_llama import (
    LlamaForQuestionAnswering, LlamaForSequenceClassification, ...) # 任务头直接复用
from ..mixtral.modeling_mixtral import MixtralForCausalLM        # CausalLM 骨架借 mixtral
from ..qwen2_moe.modeling_qwen2_moe import (
    Qwen2MoeExperts, Qwen2MoeSparseMoeBlock, Qwen2MoeTopKRouter)  # MoE 部件借 qwen2_moe
from ..qwen3_moe.modeling_qwen3_moe import (
    Qwen3MoeAttention, Qwen3MoeDecoderLayer, Qwen3MoeMLP, ...)    # 注意力/层借 qwen3_moe

# ↓ 之后才是 Qwen3Next 自己写的部分:线性注意力门控、DeltaNet 规则等差异件
这张 import 表就是一张「家谱」:Qwen3-Next 的每个部件都有出处——框架层借 mixtral,注意力借 qwen3_moe,MoE 借 qwen2_moe,位置编码借 gemma2,归一化借 gemma3,任务头借 llama。它自己写的只有差异件。这也解释了 1.2 节的收敛数字:310 份 modular 源(18.8 万行)展开成 516 份实现(54.5 万行)。设计一个新模型在这个库里的含义,接近「写一份差异清单」。
工程后果 运行时改模型行为,不要手改 modeling_*.py——下一次代码生成会把改动冲掉。官方约定的改法是改 modular_*.py 再重新生成(CI 强制校验两边一致)。读源码时同理:modeling 文件是「编译产物」,modular 源文件才表达作者意图。

1.6自研起点:接一个新模型的四步

假设你要接入一个刚发布、库里还没有的开源模型。按现在库的工程约定,路径是四步:

  • 第一步,选骨架。确认它最接近哪个现有架构(十有八九是 Llama 系),找到那个模型的 modular 源文件作为起点;
  • 第二步,写差异。新建 modular_<model>.py,import 骨架模型的类,只覆写差异件——位置编码方案、注意力变体、FFN 结构、归一化;
  • 第三步,写配置与转换。configuration_<model>.py 声明超参数与默认值;如果原始权重是别的格式,再写一份 convert 脚本(602 行的 llama 转换脚本可作为模板);
  • 第四步,生成与注册。运行转换器得到 modeling_<model>.py,在 auto 映射表(models/auto/auto_mappings.py)登记架构名,从此 AutoModel 家族认识它。

四步里真正需要动脑的是第二步:判断「这个新架构相对已知骨架,差异到底在哪」。这个判断力恰好来自对公共层的理解——注意力后端怎么路由(3.6)、Cache 怎么换代(04)、RoPE 有哪些缩放参数(4.5)。这也是本章作为「地图」存在的理由:后面十二章讲的每个机制,都是接新模型时可能要触碰的旋钮。

要点 Transformers 的复杂度分布和直觉相反:模型层(54.5 万行)几乎不用逐行读,公共设施层(6.8 万行)才是主体。531 个模型是「一张图纸的 531 次参数化」,图纸上的每一件——注意力路由、KV Cache、生成循环、权重装载——后面各章挨个拆。

本章小结

这一章立起的地图:531 个模型目录收敛为「不到二十个独立设计 + 代码生成」;每个模型目录四类文件,其中 modeling_*.py 是 modular_*.py 经语法树转换生成的产物,改模型改 modular 源;所有模型继承 PreTrainedModel,基类用类属性声明能力、用统一代码实现机制;一份新模型的接入路径是「选骨架、写差异、写配置、生成注册」四步。
