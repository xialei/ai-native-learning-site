工具调用:模型侧的完整链条,以及库外的一切

这一章正面回答第 0 章的问题二:transformer 怎么支持 agent 调用各种工具?先给结论——模型侧的全部职责是「说对话」:把工具说明书织进 prompt(schema 渲染)、决定什么时候调用(模型能力,在权重里)、按约定格式产出调用(生成)、被停止条件截住(推理循环)、把文本解析回参数(response parsing)。执行工具、把结果喂回去、决定下一步——那是 Agent 循环,在库外,本站已有四本书(pi-agent、langgraph、deepseek-harness、claude-code)拆过各自的实现。

这一章把库内的五个环节连成一条链,标清每一环的文件与函数;然后在最后给一张「分界表」——做 Agent 该从库里拿什么、自己写什么。你读完应该能回答:「transformer 在工具调用这件事里,到底是哪个部件?」

答案地图 四问的答案摆在一起::① 工具说明书 = JSON Schema,随 tools 参数进模板,与普通文本一样被 tokenize——「模型认识工具」只是「模型读过说明书」(9.1);② 决定「调不调、调哪个、参数是什么」的是模型权重,库内管不到;库内能管的是格式正确性与解析可靠性(9.2);③ 从生成到解析的五环链:schema 织入 → 生成 → 停止截取 → 流式解析 → 类型收敛,五环全部在库内(9.3);④ 执行、记忆、重试、多轮决策在库外——第 0 章分界表在工具场景的落地(9.4)。

9.1第一环:schema 织入 prompt

工具说明书走的是 get_json_schema(chat_template_utils.py:256),第 8 章见过它的入口;这一环的完整细节:

chat_template_utils.py:256 — 函数 → JSON Schema(核心流程,注释为译注)
pythondef get_json_schema(func: Callable) -> dict:
    doc = inspect.getdoc(func)
    if not doc:                      # 无 docstring 直接拒绝——没说明书就没法给模型看
        raise DocstringParsingException(...)
    main_doc, param_descriptions, return_doc = parse_google_format_docstring(doc)
    json_schema = _convert_type_hints_to_json_schema(func)   # type hints → 参数类型
    for arg, schema in json_schema["properties"].items():
        if arg not in param_descriptions:    # 每个参数必须有描述,少一个都不行
            raise DocstringParsingException(...)
        enum_choices = re.search(r"\(choices:\s*(.*?)\)\s*$", desc, flags=re.IGNORECASE)
        if enum_choices:                 # docstring 里写 (choices: ["tea","coffee"]) → enum
            schema["enum"] = json.loads(enum_choices.group(1))
    return {"type": "function", "function": {"name": ..., "description": ..., "parameters": ...}}
这个函数的三条纪律值得记住:① 无 docstring 就抛异常——「写不出说明书的函数,不配给模型调用」;② 每个参数都要有描述——模型只能按说明填参,没说明的参数就是猜;③ (choices: [...]) 语法把 docstring 里的一行注释变成 schema 的 enum——参数取值范围在文档里声明,不用写配置文件。模型的「工具理解力」上限由这份 schema 的质量决定:类型、描述、枚举、必填,每项都直接影响调用准确率。库内走到 schema 为止;schema 怎么写得好,是提示工程,也是库外的事。

schema 进模板后长什么样?由各模型的 chat template 决定——通用做法是把工具列表以 JSON 形式织进 system 消息或专用区段,并把「调用格式」的示例写进指令(第 8 章 8.1 节)。从此工具说明书就是普通 token,走第 2-4 章的全部路径:编码、进缓存、算注意力。

9.2第二环:决定权在权重

「模型怎么知道该调工具了?」——这个问题没有代码答案。决定「读到这里该调 search_weather 还是直接回答」的,是模型在训练时见过的海量「工具调用对话」(第 11 章训练侧)。库内能做的只有两件事:

第一,保证格式选择面:chat template 把「怎么调」的格式规范写进 prompt,模型照葫芦画瓢;若模型训练时见过这种格式,产出就格式正确。第二,保证硬约束可表达:6.2 节的处理器族里有 PrefixConstrainedLogitsProcessor(logits_process.py:1502)——按前缀限制可选 token;配合第 5 章的 StopStringCriteria(stop_strings),可以强行约束输出以指定格式开头、到指定字符串为止。这两样是「结构化输出」的库内地基:不靠模型自觉,靠 logit 面上做手脚。

「会不会调」与「让不让调」是两件事:前者在权重(训练产物),后者在推理栈(可编程)。工程上常说的「引导性生成/guided decoding」都活在后者:约束解码器,让模型只能在合法 token 里选——模型还是那个模型,但行为被架构框住了。这也是第 0 章说的「表达机制」的准确含义:库不能给模型能力,但能把能力约束成可靠的行为。

9.3第三到五环:生成、截取、解析

模型开始产出。以下三环全部在库内,拼起来是「从 token 到可执行参数」的路:

流式解析的价值在并发与前端:ResponseParser 的 region 事件(8.4 节)让前端在模型还在生成时就知道「现在写的是思考区/参数区/正文区」,工具参数在 region_close 时收敛——不用等全文。配合第 7 章的连续批处理,「同时给 100 个对话做工具调用解析」是事件流驱动的,不是轮询。这三层(批处理执行、停止截取、流式解析)是 v5 把「工具调用」从「应用层拼装」变成「库内一等公民」的工程证据。

还有一处值得点名:第 2 章 2.4 节的 sanitize_control_tokens 与第 8 章的 mark_control_tokens,在工具场景有了双重身份——模型产出的文本里若混入控制符,解析层必须能区分「格式标记」与「内容里恰好长像控制符的字符」。分界仍是那个原则:结构权在模板与解析器,内容权在用户与模型。

9.4分界表:Agent 循环在库外

五环之外的一切,属于 Agent 运行时。下表是第 0 章问题二分界的完整落地——左边库内(本章各节),右边库外(去哪里学):

环节库内(transformers)库外(参考本站书籍)
工具说明书get_json_schema + 模板渲染(9.1)工具注册表、权限模型 → claude-code 书第 9 章
决定调用—(权重里,训练侧第 11 章)决策循环、重试策略 → pi-agent 书第 3 章
生成调用generate + 停止条件(9.3)流式协议、中断处理 → deepseek-harness 书协议章
解析回参ResponseParser + schema 收敛(9.3)执行沙箱、结果校验 → pi-agent 书第 9 章
多轮循环—(需要外部状态)会话状态、上下文管理 → langgraph 书第 4-5 章
服务化generate_batch(第 7 章,单节点)多机调度、KV 复用 → sglang/vLLM 相关书
读表的方式:「transformer 是工具调用里的什么?」——它是把「工具说明书 + 对话」变成「工具调用文本」、再把文本变回「结构化调用」的那个函数。它是链条上最贵的一环(一次前向),也是唯一「有智能」的一环;但链条的长度、韧性、可运维性,全在库外。这个认知分界决定了:调优模型行为看训练与 prompt(库内能改的部分),调优系统行为看 harness 设计(库外)。本站四本 agent 书覆盖右列,合起来才是完整的「AI 解决问题」图景——这也是第 0 章问题三要接着讲的:解决问题的能力从哪来。

本章小结

工具调用的模型侧五环全部在库内:get_json_schema 从函数签名 + docstring 生成 schema(无文档拒绝转换,choices 语法生成 enum),随 tools 参数进模板织入 prompt;「会不会调」在权重,「让不让调」在推理栈(PrefixConstrained 截断可选 token,stop_strings 截取调用);ResponseParser/parse_response 按与模板同源的 response_template 把输出解析回结构化消息,工具参数按 schema 类型收敛。执行、多轮循环、权限、服务化在库外——本站四本 agent-runtime 书覆盖。transformer 在链条中的角色:把「说明书 + 对话」变「调用文本」再变回「结构化调用」的那个最贵且唯一有智能的环节。
