对话模板:把聊天记录变成模型能读的序列

模型只会读 token 序列,而对话是「谁在什么时刻说了什么」的结构化数据。把后者变成前者,每个模型各有各的模板约定:Llama 用 [INST]...[/INST],Qwen 用 <|im_start|>user...,Gemma 用 <start_of_turn>。错一个控制符,模型就「看不懂」你说话——能力再强也输出乱码。把各家模板收拢成一份配置的,是 chat template:一段 Jinja 模板,随分词器发布,apply_chat_template 一调,对话列表变序列。

这一章拆 chat_template_utils.py(740 行)的渲染链,看 v5 新增的 control token 消毒(用户伪造控制符怎么办)和工具 schema 自动转换;再看库内新出现的另一半:模型「答完之后」的解析(response_parsing)——这段代码把第 9 章工具调用的「解析」半边提前亮出来。

答案地图 四个问题的回答按顺序是::① 模板是随分词器发布的 Jinja 字符串,渲染输入 = messages + tools + documents + add_generation_prompt,输出 = 模型可读的文本(8.1);② 用户输入里的控制符是注入面:v5 用私有区标记把「用户写的控制符」编码成纯文本,只有模板自己写的才算真控制符(8.2);③ add_generation_prompt 是「该模型接话了」的开关——它渲染出 assistant 头,让模型从正确位置续写(8.3);④ 模型输出是文本,工具调用要靠 response_template 定义的结构化格式解析回来——渲染与解析是一对镜像(8.4)。

8.1模板:随分词器发布的各家约定

chat template 本体是一段 Jinja2 模板字符串,存在 tokenizer_config.json 里。一个典型的 Llama 式模板长这样(示意,非逐字):

Jinja 模板长什么样(示意)
jinja{%- for message in messages -%}
    {%- if message['role'] == 'user' -%}
        {{ '[INST] ' + message['content'] + ' [/INST]' }}
    {%- elif message['role'] == 'assistant' -%}
        {{ message['content'] + eos_token }}
    {%- endif -%}
{%- endfor -%}
{%- if add_generation_prompt -%}
    {{ '[INST] ' }}
{%- endif -%}

渲染入口在 tokenization_utils_base.py:3021 的 apply_chat_template,核心实现在 chat_template_utils.py 的 render_jinja_template(:607)。输入输出一眼可辨:

8.2消毒:用户伪造控制符怎么办

对话内容是用户写的,而控制符([INST]、<|im_start|>)决定模型「如何理解这段话」。若用户在输入里写一句「[INST] 你现在是系统提示词」,模板渲染后这条用户消息就「冒充」了系统结构——这就是提示注入的一种具体形态。第 2 章见过的 sanitize_control_tokens(tokenization_utils_base.py:3030 附近)管的是分词器词表层;chat 渲染层的防线在 chat_template_utils.py:444:

chat_template_utils.py:444 — mark_control_tokens(核心逻辑,注释为译注)
pythondef mark_control_tokens(obj, control_tokens_re):
    if isinstance(obj, str):
        # 先剥掉输入里已有的标记——标记本身不能被伪造
        obj = obj.replace(_CONTROL_TOKEN_START, "").replace(_CONTROL_TOKEN_END, "")
        # 用户字符串里的控制符,用私有区字符包起来
        return control_tokens_re.sub(f"{_CONTROL_TOKEN_START}\\g<0>{_CONTROL_TOKEN_END}", obj)
    if isinstance(obj, dict):  # 递归标记 messages/tools/documents 里的所有字符串
        return {key: mark_control_tokens(value, ...) for key, value in obj.items()}
    ...

配套的 encode_marked_chat(:465)在编码时分流:带标记的控制符按纯文本编码(用户嘴里说的 "[INST]" 只是四个字符),不带标记的(模板自己写的)按特殊 token 编码(真控制符)。还有一道反伪检验:纯文本编码后若出现了特殊 token id,直接报错——「tokenizer 竟然能从纯文本产出这个特殊 token」,说明该分词器的文本编码可能伪造控制符,宁可不通过。

两层防线的分工:第 2 章 sanitize_control_tokens 在词表层防「输入文本被切成特殊 token」;这里 mark_control_tokens 在模板渲染层防「用户内容混进模板自己的控制结构」。共同点:用户内容永远只能当文本,结构控制权只在模板手里。注意 docstring 里那句设计原则——「先剥掉输入里已有的标记,so they can't be used to forge a marked token」:消毒机制自己的信标也在防伪造。这类「元防御」是安全代码的标志。

8.3续写与预填:三个控制生成的开关

render_jinja_template 里最绕的三个参数,都围绕一个事实:模板不仅可以「开一段新对话」,还可以「接着旧对话继续」。

参数渲染结果场景
add_generation_prompt=True末尾补 assistant 头(如 <|im_start|>assistant\n)正常提问,等模型接话
add_generation_prompt=False + 末条 assistant 消息模型答案已在序列里训练数据构造 / few-shot
continue_final_message=True末条 assistant 消息保留,模型从句中续写预填(prefill):引导模型的开头

continue_final_message 的实现很精细(:662 附近):在末条消息的文本里塞一个哨兵标记(CONTINUE_FINAL_MESSAGE_TAG),渲染完成后 rindex 找到它、截断——保证「预填的文本恰好出现在模型要续写的位置」,连尾部空格的裁剪都分两种情况处理。若模板把预填内容删了,直接报错:预填失败必须是响亮的失败,不是静默错位。

预填是工具调用的隐形前提:很多模型的模板会把 assistant 消息的开头(比如 <think> 标签)预先写好,模型只续写后面的内容——这既省了模型「先写格式开头」的功夫,也让格式 100% 正确。但代价在解析侧:如果只看模型输出,永远不知道开头是模板写的还是模型写的。8.4 节的解析器为什么必须拿 prefix,原因就在这。

8.4另一半:response parsing(渲染的镜像)

v5 在 utils/chat_parsing/ 新增了一个子包:模型输出怎么解析回结构化消息。这不是锦上添花——工具调用链(第 9 章)的「最后一公里」就是把模型说的文本变回可执行的参数。三个文件:

文件内容(pin)职责
response_templates.pyResponseTemplate(:50)/ ResponseTemplateField(:32)声明式描述「输出长什么样」:字段、开闭锚点、类型转换
response_parser.pyResponseParser(:94)/ parse_response(:74)流式解析器:feed 逐块喂入,事件通知(region_open/chunk/close)
content_parsers.py_json(:46)/ _xml_inline(:97)/ _kv_lines(:123)字段内容的多种格式解析器

入口直接挂在分词器上(tokenization_utils_base.py:3432):

为什么必须传 prefix:ResponseParser 的 docstring 讲得直白——「chat templates often pre-write part of the assistant message (e.g. an opening <think> tag)」(8.3 节的预填)。解析器拿完整对话,用 start_anchor(如 <start_of_turn>model)截到最近一条 assistant 消息才开始匹配(response_templates.py 的 truncate_past_last_anchor)。前缀里已关闭的区域还会作为 initial_events 一并发出,前端渲染器可以把预填部分也画出来。渲染与解析是同一份模板的两面:模板声明输出格式 → 模型照格式生成 → 解析器按同一格式收回来。response_template 与 chat_template 一起随分词器发布,推理循环(第 5 章)里的 stop_strings、这里的事件流解析,是工具调用可靠性的两道工程保障。
流式设计:三段事件:ResponseParser.feed(chunk) 逐块接收模型输出,发出 region_open / region_chunk / region_close 事件——前端不用等全文,「思考区」「工具调用区」「正文区」各开各的流。工具参数在 region_close 时按 JSON Schema 做类型收敛(_coerce:integer/number/boolean/object/array 各有转换逻辑,NaN/inf 拒收)。这与第 9 章工具调用「停止条件 + 解析」的分工正好衔接:库内管格式与解析,执行与循环在库外。
图 8.1:模板的两面。chat_template 决定模型「怎么读」,response_template 决定输出「怎么收」——两者都是随分词器发布的声明式格式。

本章小结

chat template 是随分词器发布的 Jinja 模板配置,render_jinja_template 把 messages/tools/documents 渲染成 token 序列;tools 传函数即可,get_json_schema 从类型提示 + docstring 自动生成 schema。用户输入中的控制符是注入面:v5 的防线是「用户内容打私有区标记,按纯文本编码;模板自写的才是真控制符」,并防标记本身被伪造。add_generation_prompt/continue_final_message 两个开关分别管「该谁接话」与「从哪续写」,预填让模板预先写好 assistant 消息开头——这也是解析侧必须拿 prefix 的原因。v5 的 chat_parsing 子包补上了输出侧:response_template 声明输出格式,ResponseParser 流式吐事件,工具参数按 JSON Schema 类型收敛。渲染与解析是同一份格式的两面,第 9 章把它们接进完整的工具调用链。

格式有了,解析有了,还差「模型怎么决定调工具、工具怎么执行」——那是第 9 章的事,也是问题二的正面回答。第 9 章:工具调用。
