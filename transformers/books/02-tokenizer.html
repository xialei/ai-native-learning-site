分词:互联网的文字,先变成一串整数

模型的世界里没有字,只有整数。你输入的一句话在进入第一层网络之前,要被切成 token、查表变成 ID 序列;模型输出的一串 ID,也要查表拼回文字。这一步看着像字符串处理,实际上决定了三件大事:一段话花多少算力(中文和英文的 token 效率差几倍)、模型「没见过」的东西怎么处理(字节回退)、以及第八、九章要讲的——工具调用和控制符,全靠 token 表里的特殊符号撑起来。

这一章讲三件事:token 从哪来(词表和算法)、v5 把分词器动成什么样(双后端重构)、一条文本编码成张量的完整路径。锚定 tokenization_utils_base.py(3764 行)和 tokenizers 库的接缝层。

答案地图 四问的答案依次是:① token 的边界由词表 + 合并规则决定,不是空格——BPE 把高频字节对合并成单元,词表是训练语料的统计产物(2.2);② 中文慢在 UTF-8 一字三字节,常见汉字在词表里是单 token,生僻字要退回字节(2.3);③ v5 删掉慢分词器,只留 tokenizers 库后端 + 一层 Python 纯实现(2.4);④ token 不是模型「理解」的最小单位,是工程折中——词表大小、分词质量、解码效率在互相拉扯(2.6)。

2.1一分钟版本

分词器在回答一个问题:「文本的哪一段,应该被当作一个不可分的单位?」 切法不是语言学,是统计学:训练语料里高频出现的字节序列,合并成一个单元。由此得到一张词表(vocab)+ 一套切分规则,编码是「文本 → token 串 → ID 序列」的两步查表,解码反过来,还有一步查不到时的回退。

库里的层次结构在 v5 之后变得非常干净,总共三层:

  • PreTrainedTokenizerBase(tokenization_utils_base.py:968) — 抽象基类:编码/解码/截断/填充/特殊 token 的统一接口,加上了 v5 里从 SpecialTokensMixin 合并进来的特殊 token 管理;
  • TokenizersBackend(tokenization_utils_tokenizers.py:86) — 唯一的重量级后端,把 HuggingFace tokenizers 库(Rust 实现)包进来;
  • 各模型目录的 tokenization_*.py — 只有几十到一百多行,声明这个模型用哪种算法(BPE/Unigram)、哪些特殊 token、什么前后处理。

2.2token 边界从哪来:BPE 的一条合并链

以 byte-level BPE(GPT-2、Llama 系列、Qwen 系列都用它)为例,词表的构建过程是:

  1. 把训练语料全部按 UTF-8 展开成字节序列——256 种字节,保证任何文本都能表示;
  2. 统计相邻字节对的共现频率,把最高频的一对合并成一个新单元,记进 merges 表;
  3. 重复第 2 步,直到词表达到目标大小(Llama 2 是 32000,Llama 3 扩到 128256,Qwen3 也到 15 万级)。

所以词表不是「词的列表」,而是训练语料的压缩摘要:英文里 "the" 会被早早合并成单 token,因为出现太频繁;一个冷门化学名则要拆七八块。推理时用词表 + merges 表执行同样的合并,token 边界由此确定。

这带来一个容易被误读的后果:token 数量 ≈ 算力与显存的计价单位。注意力计算量随序列长度平方涨,KV Cache 随长度线性涨(第 4 章的账)。同一段内容,英文一个 token 约 4 字符,中文常见字一个 token 一字,生僻中文字一个 token 一个字节还要乘三。所谓「模型的长上下文是多少 token」,换算到中文文本,实际能装的字数要打 6 到 7 折,再打折——这不是 bug,是词表构建语料的偏置:英文语料占大头,合并规则自然偏向英文。

常见的误读 「模型按词理解文本」不成立——"unbelievable" 可能是一个 token,"un" + "believ" + "able" 也可能是三个,取决于训练语料里的频率,和语义无关。反过来说,「模型理解不了 token 边界内外的字符」也不成立——字节回退保证了任何字节序列都可表示,只是代价是多个 token、更多算力。token 化是统计压缩,不是语义单位。

2.3特殊 token:控制符的物理载体

词表的前几个位置不装文字,装控制符。看 LlamaConfig 里的默认值:

src/transformers/models/llama/configuration_llama.py:76 — 控制 ID(摘录)
python    bos_token_id: int | None = 1      # <s>  序列开始
    eos_token_id: int | list[int] | None = 2   # </s> 序列结束(可以是多个,见 05 章)

这两个 ID 之外的「特殊 token」家族,在 v5 里被分成两组,基类里能直接看到这个划分:

src/transformers/tokenization_utils_base.py:968 — 特殊 token 的 v5 分组(摘录,注释为译注)

        "bos_token", "eos_token", "unk_token",
        "sep_token", "pad_token", "cls_token", "mask_token",
    ]

    def __init__(self, **kwargs):
        ...
        # v5:命名特殊 token 与模型专属 token 分开存

为什么要分两组:命名槽位是协议级的(所有模型共用这几个名字);extra 是模型自留地——视觉模型要 <image> 占位符,工具调用模型要有包住函数调用的标记。第 8、9 章会看到,chat template 的本质就是「把对话渲染成控制符序列」,而这些控制符必须是词表里的真 token,模型才能在训练时学会「看到它意味着什么」。这正是问题二(工具调用)在模型侧的第一块基石:工具调用的语法,是靠特殊 token 和普通文本一起拼出来的。

还有一个安全细节值得提前知道:v5 新增了 sanitize_control_tokens 参数(apply_chat_template 的签名里,tokenization_utils_base.py:3012)。用户输入里如果混着 </s> 这样的字面量,默认会被编码成普通文本而不是控制 token——防止用户伪造「对话结束」或「工具调用」标记。提示注入的一个攻击面,就是从分词这一层堵的。

2.4v5 的断代:慢分词器退场

v4 时代的分词器是双轨的:每个模型一份 tokenization_<model>.py(纯 Python,慢)和一份 tokenization_<model>_fast.py(Rust 的 tokenizers 库,快)。两份代码实现同样的行为,但总会有行为不一致的角落——这是长期积累的技术债。

v5 的迁移指南(MIGRATION_GUIDE_V5.md)写得很直白:慢分词器文件整体移除,原 _fast 后缀的文件改名顶替;sentencepiece 等其他后端以「轻量适配层」的方式保留在加载失败时的回退路径里。配套的 API 精简:encode_plus → __call__、batch_decode → decode、prepare_seq2seq_batch → __call__(text_target=...)。

纯 Python 侧没有全删——tokenization_python.py 里的 PythonBackend(400 行)保留,但定位变了:它是「没有 Rust 环境时的兜底」,以及在 doctest 和单元测试里跑得起来的一份参考实现。那份文件里的 Trie(45 行起)值得一看:最长匹配优先的 special token 扫描器,是「文本里混进控制符怎么办」这个问题的原始答案。

为什么值得记住这次删减:分词器是全库「双轨并存」时间最长的组件,双轨的动机(渐进迁移)和代价(行为漂移)都写在了 git 历史里。v5 用「一个 Rust 后端 + 一层声明」收敛它,和第 1 章的 modular 机制是同一个思路——把「每模型一份重复实现」换成「一份机制 + 每模型一份声明」。这也是全书反复出现的模式。

2.5从字符串到张量:一次编码的完整路径

日常用的入口是 tokenizer(text, return_tensors="pt")。它背后的调用链:

图 2.1:编码路径。BatchEncoding(tokenization_utils_base.py:201)是字典的子类,既当 dict 用,又携带字符↔token 的映射信息——下游的对齐、抽取、训练标签错位检查全靠它。

三个工程细节值得记:

  • padding_side 不是装饰参数。LlamaTokenizer 声明 left(第 88 行)——生成场景下模型从右边续写,左边补 pad 才能让所有序列的最后一个真实 token 对齐;BERT 这类理解模型用 right。填错边,生成模型的输出会整体错位;
  • truncation 默认关。超长输入不会自动截断而是报错——刻意为之,静默截断对训练数据是灾难;
  • tokenizer 和模型的词表尺寸要一致。LLM 加载时校验 embedding 行数与 vocab_size;换分词器(比如给 Llama 换 Qwen 的词表)意味着 embedding 矩阵尺寸对不上——装载器不会静默重塑,LOAD REPORT 会列出 mismatch 并抛错;真要换词表,走显式的 resize_token_embeddings(第 12 章)。

2.6为什么不用字、不用词:一个三方权衡

把 BPE 放回设计空间里,能看清它为什么成了默认选择:

切法词表大小序列长度问题
按字/字节切极小(256 起)极长序列平方增长的注意力算不动态;每个字都要「拼」出语义
按词切巨大(百万级)短词表本身就是知识瓶颈:新词、拼写变体、任何语言外文本全成 OOV;embedding 矩阵大到离谱
BPE/子词(业界选择)3 万 ~ 25 万适中边界是统计产物,与语义无关;跨语言效率不均

这张表也解释了词表扩容的动机:Llama 2 的 32000 词表在多语言和代码场景下明显吃亏,Llama 3 直接翻四倍到 128256——词表越大,同样文本切的 token 越少,同样的上下文窗口装的内容越多。代价是 embedding 矩阵和输出投影(lm_head)的参数量线性涨:128256×4096 ≈ 5.25 亿参数,这是 2.1 节提过的权重绑定(tie_word_embeddings)存在的理由——输入 embedding 和输出投影共享一份矩阵,直接省下这 5 亿参数。

要点 分词器是「互联网 → 模型」的关税关卡:所有内容在这里被计价(token 数)、被整形(控制符)、被卡住或放行(特殊 token、字节回退)。第 3 章开始,模型拿到这些 ID 之后发生的事——权重怎么「记住」互联网——才正式开场。

本章小结

token 边界由词表和合并规则决定,是训练语料的统计产物,不是语义单位;字节级 BPE 用 256 字节打底加字节回退,保证任何文本可表示,代价是序列长度(中文尤其明显);特殊 token 是控制符的物理载体,v5 把命名槽位与模型专属 token 分开管理,sanitize_control_tokens 从分词层堵提示注入;v5 删掉双轨分词器,收敛成「一个 Rust 后端 + 每模型一层声明」,与 modular 机制同一个思路。

文本已变成 ID 序列。下一章看它流进的第一个部件:注意力层,以及权重为什么能「记住」互联网。第 3 章:记忆。
