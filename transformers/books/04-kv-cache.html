KV Cache:当前对话的记忆,为什么关掉就忘

第 3 章说权重是「长期记忆」——训练一次,所有对话共享。但一次对话内部还需要另一种记忆:这轮说过的话,下一轮还要记得。这就是 KV Cache 的职责。它也是全书从「模型内部」走向「工程实践」的第一站:第 3 章的注意力只讲了数学,生产环境里真正决定成本的是这份缓存的显存账——为什么 7B 模型对话一小时能吃掉几十 GB 显存、为什么 GQA 和滑动窗口是标配、为什么 vLLM/SGLang 要做分页。

这一章拆 cache_utils.py(2166 行)的双层结构:每层一张表(CacheLayer 家族),整个模型一个账本(Cache)。锚定生成入口处 cache 的选择逻辑(generation/utils.py:2222)。

答案地图 把四问的答案先放在这里::① 不缓存则每生成一个 token 都要重算全部历史的 K/V——缓存把「每步 O(N) 次前向」变成「每步一次前向增量」(4.1);② 显存公式 = 2(K/V) × 层数 × 头数 × 头维 × 上下文长 × batch × 字节数,7B 模型 8k 上下文单请求 GQA 下约 1 GB、无 GQA 4 GB(4.2);③ 同一个注意力接口下有动态/静态/滑窗/量化/线性五族缓存层,按模型 config 自动配(4.3);④ 长窗口不是把缓存撑大,而是换记忆结构——滑窗丢远处、线性注意力压成固定状态、RoPE 缩放撑长检索距离(4.5)。

4.1为什么非缓存不可:一次前向的代价账

先算不用缓存的账。生成第 N 个 token 时,注意力需要全部 N 个位置的 K/V。如果每步都重新前向整个序列,生成 1000 个 token 的总计算量是 O(N²) 次前向——而其中每次都把前 N-1 个 token 的 K/V 原样重算一遍。K/V 只由「它自己之前的 token」决定,因果模型里历史 token 的 K/V 永远不变——重复计算纯属浪费。

于是有了这条 3.3 节出现过的关键一行:

modeling_llama.py:251 — 缓存注入点(摘录)
pythonif past_key_values is not None:
    key_states, value_states = past_key_values.update(key_states, value_states, self.layer_idx)
    # 新 token 的 K/V 追加进缓存;返回「缓存里的全部 K/V」给注意力用

每步只算新 token 的 K/V,追加进缓存,注意力读「缓存 + 新 K/V」——这就是生成式模型的增量解码。position_ids 的接续逻辑(3.1 节骨架 ③)也在这里:past_seen_tokens 从缓存账本上查,而不是数 input 长度。

「关掉就忘」的准确含义:KV Cache 是推理进程里的 GPU 张量,不在 checkpoint 里。对话结束、进程重启,这份记忆就没了——想「接着上次聊」,要么重发全部历史重新 prefill(按 token 计费的产品都是这么干的),要么用KV 缓存持久化(第 7 章服务端场景会回到这点)。它和权重的分工:权重记「世界」,缓存记「本次对话」;权重的读取靠缓存里那行新 token 的 Q。

4.2显存账:一个公式和一笔 2 GB 的账

KV Cache 的显存占用可以一行公式写死:

项含义典型值(7B,GQA 8 KV 头,Llama 3 式)
2K 和 V 各一份—
num_layers每层独立一份缓存32
num_kv_heads × head_dim每层每 token 的 K/V 尺寸(GQA 压过)8 × 128 = 1024
seq_len上下文长度8192
batch并发对话数1
bytes每参数字节数2(fp16)

2 × 32 × 1024 × 8192 × 1 × 2 bytes ≈ 1 GB;如果不用 GQA(32 头 KV)则是 4 GB。再乘上并发数,这笔账就是第 7 章调度器的起点:vLLM/SGLang 整套分页系统,本质都是把「缓存显存」从整块预分配变成按需分页,让显存装下更多并发。

常被忽略的一项 这笔账按「模型自己认定的 KV 头数」算。缓存张量的 dtype 跟着模型走(bf16/fp16),但量化缓存(QuantizedCache)能把它压到 4 bit——精度换容量,极端场景下同显存并发数翻数倍。4.3 节看它的实现位置。

4.3双层结构:五族缓存层,一个账本

cache_utils.py 的组织是两层:外层 Cache 是账本(layers 列表 + update 分发),内层每层一个 CacheLayerMixin 子类,真正的存储和更新逻辑在内层。五族内层类:

层类(cache_utils.py pin)增长方式适用场景
DynamicLayer(:103)torch.cat 追加,想要多长长多长默认生成路径
DynamicSlidingWindowLayer(:195)追加但只保留最近 W 个滑动窗口模型
StaticLayer(:389)预分配满长度,原地写入torch.compile / CUDA Graph
QuantizedLayer(:692)动态追加,K/V 存成 4/8 bit显存紧张的长上下文
LinearAttentionLayer(:1046)不存历史,存固定大小的递归状态线性注意力/Mamba 类模型

最简单的 DynamicLayer 一眼可见:

cache_utils.py:118 — DynamicLayer.update(核心三行)
pythondef update(self, key_states, value_states, *args, **kwargs):
    if not self.is_initialized:
        self.lazy_initialization(key_states, value_states)   # 首次:按 K/V 的 dtype/device 建空张量
    self.keys = torch.cat([self.keys, key_states], dim=-2)   # 追加,每次都产生新张量
    self.values = torch.cat([self.values, value_states], dim=-2)
    return self.keys, self.values
简单直观,但每个解码步都整块复制一遍:cat 是分配新内存 + 拷贝,序列越长拷贝越多。这正是 vLLM 用「分页块表」重写这套逻辑的动机——Transformers 的 DynamicCache 是正确性优先的单机实现,服务引擎要的是吞吐优先的显存管理。两条路线在第 7 章合流对比。另一个细节:懒初始化(lazy_initialization)——建缓存时不假定 dtype/设备/头数,第一次 update 时照着真实张量抄。这是为了分布式/量化场景少写一摞特判。

StaticLayer:为编译而生

DynamicCache 的「每步变长」对 torch.compile 是灾难——形状一变就触发重编译。StaticLayer 的解法是预分配满长度、原地写入、用一个 cumulative_length 记账:

cache_utils.py:389 — StaticLayer 的两处关键(摘录,注释为译注)
pythonclass StaticLayer(CacheLayerMixin):
    is_compileable = True

    def lazy_initialization(self, key_states, value_states):
        ...
        self.keys = torch.zeros((self.batch_size, self.num_heads, self.max_cache_len, self.k_head_dim), ...)
        self.values = torch.zeros(...)                       # 一次性分配满
        # 把张量标成固定地址——否则每次原地写都会让 CUDA Graph 跳过捕获
        if not is_torchdynamo_compiling():
            torch._dynamo.mark_static_address(self.keys)
            torch._dynamo.mark_static_address(self.values)
mark_static_address 那行注释值得读原文:「Without this, we cannot use cudagraphs!」——固定数据指针是 CUDA Graph 捕获的前提,图捕获要求地址不变。一层缓存实现的取舍(动态灵活 vs 静态可编译)直接决定上层能不能用编译加速,这层耦合在选 cache_implementation 时要一起考虑。

外层账本:一个 update,按层分发

cache_utils.py:1393 — Cache.update(摘录,注释为译注)
pythondef update(self, key_states, value_states, layer_idx, *args, **kwargs):
    if self.layer_class_to_replicate is not None:
        while len(self.layers) <= layer_idx:            # 惰性补层
            self.layers.append(self.layer_class_to_replicate())
    if self.offloading:                                  # 层级 offload 模式
        torch.cuda.default_stream(key_states.device).wait_stream(self.prefetch_stream)
        self.prefetch(layer_idx + 1, self.only_non_sliding)  # 提前搬运下一层到 GPU
    keys, values = self.layers[layer_idx].update(key_states, value_states, *args, **kwargs)
    if self.offloading:
        self.offload(layer_idx, self.only_non_sliding)   # 本层用完搬回 CPU
    return keys, values
账本只做三件事:补层、分发、(可选)卸载调度。offloading 模式用独立 CUDA stream 做异步搬运——算第 N 层时,第 N+1 层的缓存在后台从 CPU 预取上来,第 N 层用完搬回去。GPU 显存里始终只有一两层的缓存,长上下文的显存墙就被「时间换空间」绕过(offload_only_non_sliding 默认 True:滑窗层本来就小,不值得搬)。注意这是 Transformers 自己的 offload;第 7 章服务引擎的「KV offload」是另一套按请求的冷热分层,名字像,机制不同。

4.4缓存怎么被选中:生成入口的协商

调用 model.generate() 时缓存从哪来?v5 的规则在 generation/utils.py:2222 的 _prepare_cache_for_generation,逻辑是三条「快速通道」加一条兜底:

generation/utils.py:2222 — 缓存选择逻辑(骨架,注释为译注)
pythondef _prepare_cache_for_generation(self, generation_config, model_kwargs, generation_mode,
                                   batch_size, max_cache_length):
    user_defined_cache = model_kwargs.get(cache_name)
    if user_defined_cache is not None: return     # ① 用户自带缓存:只查冲突,直接用
    if generation_config.use_cache is False: return  # ② 明确不用缓存
    if not self._supports_default_dynamic_cache(): return  # ③ 特殊架构(mamba 等)自理
    # ④ 否则按 cache_implementation 建:静态族 / quantized / 默认 DynamicCache
    ...
v5 的一个重要变化藏在这里:迁移指南写明,generate 不传缓存时,默认缓存类由模型自己决定(PR #41505),不再一律 DynamicCache。模型的 config.layer_types 逐层声明注意力类型,cache_utils.py:1726 的 get_layer_types_and_kwargs 把它翻译成每层的缓存类——「混合注意力」模型(qwen3_next:线性注意力层 + 少量全注意力层)会得到 LinearAttentionAndFullAttentionLayer 这类混合缓存:线性层只存固定递归状态,全注意力层才存 KV。缓存结构 = 注意力结构的镜像,这张对应关系在 4.3 的表里已经列了一半。

对 beam search 的支持也落在缓存上:CacheLayerMixin.reorder_cache(cache_utils.py:96)按 beam 重排 batch 维度(index_select 挑出留下来的 beam)——beam 展开时缓存跟着复制,beam 收缩时缓存跟着重排。缓存是「对话状态」的物理载体,所以任何改变「有几条对话、各是什么前缀」的解码策略,最后都要在缓存上动刀(第 6 章展开)。

4.5长窗口:不是把缓存撑大,是换记忆结构

「上下文 100 万 token」的宣传读法要过三道账。第一道是 RoPE:外推能力。默认 RoPE 在训练长度外打分崩坏,扩长靠缩放频率——modeling_rope_utils.py 里一字排开的几个函数:

方案(rope_type)思路代码位置
linear位置 ID 除以 factor:100k 位置当 10k 用(有损插值)rope_utils
dynamic超过训练长度才切插值,以内保持原样dynamic_rope_update 装饰器
yarn(:345)低频维插值、高频维外推,双 ramp 混合_compute_yarn_parameters
longrope(:486)逐维度搜索缩放系数_compute_longrope_parameters
llama3(:580)分段:低频不动、中频渐变、高频缩放_compute_llama3_parameters

这五个函数共享同一个签名(config → inv_freq + attention_scaling),3.3 节的 ROPE_INIT_FUNCTIONS 查表把选择权交给 config.rope_parameters——「换长窗口方案」在源码里就是换一行配置。DeepSeek 的 yarn 变体还有个细节:_compute_yarn_parameters 里处理了「original_max_position_embeddings 与 max_position_embeddings 的比值」作为默认缩放因子——同一机制,不同厂商配置习惯不同,代码里留了兼容分支。

第二道账是滑窗:不外推,认怂。滑动窗口注意力只让每个 token 看最近 W 个,缓存只要存 W 个 token 的 K/V——DynamicSlidingWindowLayer.update 里那句 self.keys = full_key_states[:, :, -self.sliding_window + 1:, :] 就是「滚出窗口即遗忘」。远处信息理论上可被多层滑窗「接力」传递(每层看 W 个,N 层传导 N×W),这就是 Gemma/Qwen3 把滑窗层与全注意力层交替混排的设计动机:大部分层滑窗省显存,少数全注意力层保住全局。

第三道账是线性注意力家族:干脆不存 KV。递归状态固定大小,新 token 来了用状态更新公式消化——缓存显存 O(1),代价是「检索精度」换成了「状态压缩」,细节丢失。qwen3_next 就是 3:1 的线性/全注意力混合(4.4 节的 layer_types),全库的 LinearAttentionAndFullAttentionLayer 等混合缓存类就是为这类模型准备的。

图 4.1:三种缓存形态。「百万上下文」各有各的代价:全注意力贵在缓存,滑窗贵在远处遗忘,线性注意力贵在检索精度。
要点 KV Cache 是「当前对话的记忆」的物理形态:每层一张表,五族层类覆盖从「全记」到「全压」的光谱。权重记忆 + KV 记忆合起来,才是第 0 章问题一的完整答案。而「对话怎么被组织成缓存里的序列」——对话格式与角色控制符,下一章先讲生成循环,第 8 章讲格式。

本章小结

KV Cache 存在的理由是因果注意力的「历史 K/V 不变」性质,它把生成从 O(N²) 次前向压成 N 次增量前向;显存账的公式(2 × 层数 × KV 维 × 长度 × batch × 字节)决定了 7B 模型 8k 上下文单请求 1 GB(GQA)/ 4 GB(无 GQA),GQA 是第一道减法;cache_utils 的双层结构里,五族层类对应五种注意力结构,缓存由 config.layer_types 自动配置——v5 起默认缓存类由模型决定;长上下文有三条路:RoPE 缩放(五种方案)、滑窗(显存有顶、远处遗忘)、线性注意力(固定状态、检索换压缩)。缓存还是解码策略的操作对象:beam search 的重排、淘汰都落在 reorder_cache 上。
