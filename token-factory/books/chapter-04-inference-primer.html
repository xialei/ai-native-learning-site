推理原理速览：从 Prefill/Decode 到 KV Cache

【压缩章】原理不展开，只立三样后面反复要用的东西：两种阶段的不同瓶颈、一张显存预算表、PagedAttention 与 Prefix Cache 两项机制。要看逐行源码，vLLM/SGLang 的源码精读系列更合适；这一章只保证你读完能自己算"这个模型在我这张卡上能服务多少并发"。

两个阶段，两种瓶颈

一次自回归生成请求，在 GPU 上走两种完全不同的阶段。Prefill处理输入的全部 token：它们一次进模型，相互之间可以并行算，一个 2k token 的输入就是一次 2k 长度的前向。计算量大，但每个 token 的算术强度高，是算力受限（compute-bound）的阶段。Decode逐个生成输出 token：每生成一个，都要把当前序列的注意力算一遍。矩阵-向量运算为主，算术强度低，瓶颈在显存带宽——每一步都要把权重和 KV Cache 从显存搬一遍，是带宽受限（memory-bound）的阶段。

两种瓶颈混在一起，就是调度困难的根源：批处理能救 Decode（多个请求共享一次权重搬运，带宽利用率上去），但会把 Prefill 的延迟拖坏（ Decode 步骤被长 prefill 阻塞）；反过来照顾 Prefill，Decode 的批就凑不满。第 5 章的 chunked prefill 和第 8 章的 PD 分离，都是对这对矛盾的不同解法。

KV Cache：第二座显存大山

Decode 为什么每步都要"重算"注意力？因为自回归生成的每一步都要用到之前所有 token 的 Key/Value 向量。缓存它们，就是 KV Cache。它是继模型权重之后第二座占显存的大山，而且这座山随并发增长、随上下文增长。

一笔算清（公式，量级示意）：

KV Cache 显存 ≈ 2 (K与V) × 层数 × KV头数 × 头维度 × 精度字节数
                × 上下文 token 数 × 并发请求数

例（示意）：7B 模型（32 层、8 个 KV 头、head_dim 128、FP16 = 2 字节）
  每 token KV = 2 × 32 × 8 × 128 × 2 B = 128 KB
  4k 上下文单请求 ≈ 0.5 MB … 听起来很小
  但 256 并发 × 4k 上下文 ≈ 128 GB —— 超过一张 H100 的全部显存

几个工程推论，后面章节会直接引用：长上下文场景里 KV Cache 比权重更吃显存（权重 16GB 的模型，256 并发 × 32k 上下文的 KV 要几十上百 GB）；GQA/MQA 架构（KV 头数远小于注意力头数）之所以成为标配，省钱是首要原因；量化 KV Cache（FP8）能直接砍一半，是长上下文场景的常见开关。

显存预算表

把一张卡上的显存账全部列出来。这张表是本书的"地基表"——容量规划（第 14 章）、调度决策（第 10 章）、分离比例（第 8 章）都从它出发：

项目大小（示意，以 7B 模型 / H100-80G 为例）随什么增长
模型权重FP16 约 15 GB；INT4 约 4–5 GB模型参数量与精度
KV Cache0（空载）→ 数十 GB（满载）并发数 × 上下文长度
激活值 / 中间张量1–3 GB（与批大小、chunk 长度相关）批大小、序列长度
CUDA Graph / 框架开销1–5 GB图数量与 batch 档位
框架保留（权重副本、工作区）2–6 GB引擎实现

预算表的用法：引擎启动时会"预分配"一个 KV 池——用 gpu_memory_utilization（vLLM，默认 0.92，见 vLLM cache 配置）之类的参数告诉引擎"你最多用到显存的多少比例"，引擎在装完权重和运行时开销后，把剩下的显存几乎全给 KV 池。KV 池大小 = 并发能力 × 单请求上下文上限，所以这张表直接决定"这台机器能扛多少并发、扛多长上下文"——第 14 章的容量公式从这里出发。

PagedAttention：把虚拟内存搬进 KV Cache

早期推理框架给每个请求预分配一整块连续显存放 KV Cache（按最大上下文长度算），浪费惊人：请求实际用到 300 token，却按 4k 预留，碎片率常常超过一半。vLLM 的 PagedAttention（OSDI 2024 之前的 SOSP 2023 论文）把操作系统虚拟内存的思路搬过来：显存切成固定大小的 page（典型 16 token 一个），请求的 KV 按需映射到不连续的 page，用一张页表维护逻辑-物理映射。碎片率从"按最大预留"降到接近零，同样的显存能扛的并发直接翻倍以上。

对工厂视角的读者，PagedAttention 只需要记住一件事：它把"显存能装多少请求"从静态预留问题变成了动态分配问题，推理集群的并发容量从此是可调度的资源，而不是被预留锁死的资产。这也是后面"抢占、换出、分级缓存"这些调度手段（第 10、11 章）能成立的前提。SGLang 的页式分配与 RadixCache 在其源码精读系列有逐行分析，此处不重复。

Prefix Cache：工厂的免费产能

真实流量有一个对工厂极其友好的性质：大量请求共享相同前缀。同一个 Agent 的系统提示每轮都一样；多轮对话的历史本身就是自己前几轮的输出；同一客户的多名员工提问时共用同一条 6k 级的机构知识前缀。对这些请求，prefill 的绝大部分计算是重复的——算过的 KV 直接复用，TTFT 从"秒级"降到"毫秒级"。RAG 是这条规则的例外：检索回来的文档每次排序和组合都可能不同，简单的前缀匹配接不住，复用要靠更靠后的缓存层或专门的融合方案。

这就是 Prefix Cache（vLLM 的 automatic prefix caching、SGLang 的 RadixCache）：把请求的前缀 KV 按树/页结构存下来，新请求来了先匹配前缀，命中的部分跳过计算。两个要点：其一，命中率是负载形态的函数——Agent 流量命中率高（系统提示固定），随机问答流量低；其二，缓存占用的显存和"给新请求用"存在竞争，缓存策略（保留多久、多少显存给缓存）是调度器要做的决定之一。

工厂语言的翻译：Prefix Cache 是一座"记忆工厂"——用显存换计算，把重复劳动变成库存复用。它的产能贡献（省下的 prefill 时间）可以折成 token 计入有效产能，是少数"不花硬件钱就能提升产能"的手段。第 9 章的路由策略会专门利用它。

▶ 实验：不同模型 / 上下文长度下的 KV Cache 占用实测

验证上面那张预算表（至少验证 KV 行），并拿到你自己环境的系数：

  1. 启动引擎，记录空载已用显存（这一项包含权重 + 运行时开销）。
  2. 发送单条长输入请求（比如 32k），记录增量——这就是"单请求满上下文"的 KV 占用 + 激活。
  3. 逐档提升并发（1、2、4、8…），记录每档显存，验证"KV 占用随并发线性增长"是否成立、斜率是多少。
  4. 换输入长度重复（8k / 16k / 32k），拿到"每 GB 显存能换多少 token-上下文"的系数。
  5. 打开 FP8 KV Cache 重复一遍，记录斜率变化。

交付物是一张填了你自己的数字的预算表。有了它，"这批卡能不能扛住下个季度的流量"从玄学变成乘法。

本章小结

Prefill 吃算力、Decode 吃带宽，这对物理矛盾是全书调度讨论的根。KV Cache 是随并发与上下文增长的第二座显存大山，显存预算表把它与权重、激活、框架开销一起算清，直接决定并发容量。PagedAttention 把 KV 显存变成可分页的动态资源；Prefix Cache 把重复前缀变成免费产能。原理至此够用，细节归引擎文档与源码精读。
