Token 工厂的经济学与指标体系

这一章定义全书唯一的指标体系。之后每一章谈性能、谈优化、谈容量，用的都是这里的词。核心只有一个定义：有效产能。它把吞吐量、延迟 SLA 和合格产出缝在同一个数里——看懂它，你就看懂了为什么"GPU 利用率 90%"可能是个坏消息。

基础计量单位

工厂的账本从三个单位开始：GPU 小时、token 吞吐、单位成本。三者的关系是一台"换算机"——花掉 GPU 小时，产出 token 吞吐，两者相除得到单位成本。

GPU 小时（GPU-hour）。一座工厂的全部投入最终都能折成 GPU 小时：8 卡机跑一小时是 8 GPU 小时，运维人力按分摊折进去。它是成本侧的总纲——第 15 章的成本核算就是把一张账单摊到 GPU 小时上。

token 吞吐（throughput）。产出侧的总数，但要立刻拆成两个轴：输入 token 和输出 token。两者在成本上完全不同——输入 token 在 prefill 阶段批量算（一次前向处理一整段），输出 token 在 decode 阶段逐个算（每生成一个都要跑一次前向，且每步都受显存带宽约束）。同一个模型的每百万输入 token 成本可以做到每百万输出 token 的几分之一，这不是厂商定价策略，是计算结构决定的。所以任何吞吐数字都要问一句：输入输出比例是多少？没有这个比例的吞吐数字没有可比性。

单位成本（unit cost）。每百万 token 的完全成本，即"当月全部投入 ÷ 当月合格 token 产出"。注意分母——是合格产出，不是 raw 吞吐；分子——是完全成本，不只是 GPU 折旧。这两个"注意"正是下一节的主角。

延迟指标：TTFT、ITL 与 SLA

有效产能的定义里写着"SLA 约束"，所以先把 SLA 的三个组成部分说清楚。

TTFT（Time To First Token），从请求发出到第一个 token 返回。它由排队时间加 prefill 时间构成，决定用户"系统有没有反应"的体验。流式界面上，TTFT 之外的时间用户都在等待，这个指标一般按 P50/P95/P99 分档承诺，比如 P95 ≤ 2s。

ITL（Inter-Token Latency），流式输出中相邻两个 token 的时间间隔，工程上也叫 TPOT（Time Per Output Token）。它决定"字蹦得快不快"的体验。ITL 有个隐蔽的坑：平均 ITL 很好看，但被批调度打断时会出现周期性长尾——某个 decode 步恰好和一条大 prefill 拼在一起，那一步的 ITL 可能是平均值的五倍。所以 ITL 的 SLA 通常对 P99 或"最大值"做约束，这也是 chunked prefill（第 5 章）要解决的问题。

E2E（端到端时延）≈ TTFT + 输出 token 数 × ITL。它是前两者的派生指标，SLA 里经常用它兜底（"P95 请求 30s 内完成"）。

指标含义体验对应受什么主导
TTFT首 token 时延反应快不快排队 + prefill
ITL/TPOT逐 token 间隔输出顺不顺decode 步时延（受批影响）
E2E完整响应时长等多久出全结果两者之和 + 输出长度

这三个指标构成 SLA 的技术部分。完整的 SLA 还要加上可用性和质量（输出合格率），后两者在第 11 章和第 13 章分别展开。SLA 在本书里不只是运维承诺，它是有效产能定义里的约束条件——没有 SLA，"产能"这个词就退回了吞吐量。

有效产能：全书的核心定义

现在可以完整给出定义了。

有效产能 = 在 TTFT / ITL 等 SLA 约束下，单位 GPU（或单位集群）在单位时间内承载的合格请求所产出的 token 数。

拆开看三个限定词，每个都对应一种"白干的 token"：

  • "SLA 约束下"——超时被客户端放弃的请求、重试浪费的算力、违背延迟承诺的输出，都不计。这是被排队和过载吃掉的产能。
  • "合格请求"——4xx/5xx、被截断、内容不合格的产出不计。这是被错误和质量吃掉的产能。
  • "单位 GPU"——按投入的 GPU 小时归一，扩容不等于增产能，效率掉了扩容也可能是负收益。这是被浪费配置吃掉的产能。

这套定义和学术界 goodput 的思想一致：DistServe 论文把"在各自延迟约束下完成"的请求产出定义为 goodput，并指出预填充与解码共享资源时，goodput 优化目标会导出与吞吐优化完全不同的系统设计。来源：DistServe, OSDI 2024它的实战量级有现成的参照：AMD 在单机 8 卡 MI300X 上跑 Qwen3-235B（TTFT 1s + ITL 50ms 的双门槛），同样 8 张卡，单实例混部达标 26/100、拆成两个混部实例 30/100，拆成 prefill/decode 两池后 73/100——有效产能 2.5 倍，卡一张没加；差距不来自"卡多了"，来自违约形态从"输出抖动"换成了"首 token 稍慢"。来源：vLLM Blog《Next-Level Inference: Why Your Single-Node vLLM Setup Needs Prefill-Decode Disaggregation》（AMD / Embedded LLM，MoRI-IO）, 2026-04-07本书的贡献是把它工程化：给出一个运维每天能算、每周能复盘的口径。

计算方法。对一个观测周期（比如一天）：

有效产能 = Σ(合格请求的产出 token)
           ÷ 投入的 GPU 小时数
           ÷ SLA 达标窗口占比修正

工程实现上更常用的形式是先算达标率：把请求按是否满足各自 SLA 分档，有效产能 = raw 吞吐 × 达标请求占比 × 合格产出占比。分母里的两个占比从网关日志和模型日志聚合，第 13 章的监控面板会专门给这两个数留位置。

三个限定词各自的量级感（示意）：管理不善的集群，排队超时能吃掉两三成产能；重试风暴叠加时更多；质量不合格在 Agent 场景（一个失败请求意味着整条链路重来）造成的浪费最重。三项相乘，"有效产能是吞吐量的六成"在真实集群里不是极端值。

为什么 GPU 利用率高不等于经济效益好

现在回答概述里埋的问题。GPU 利用率（SM 利用率或"有任务在跑"的时间占比）衡量的是资源忙不忙，不衡量忙得值不值。三种典型的高利用率低效益：

拿离线任务填坑。在线低峰时跑离线批处理把卡填满，利用率上去了，但如果这些离线 token 本来可以等到更闲的窗口、或者本来可以跑在更便宜的卡上，那这是用最贵的产能干了最便宜的活。混部本身是对的（第 10 章整章讲），但账要分开算：在线 SLA 达标率和离线任务完成量是两个指标，合并成"利用率"会掩盖两边。

无效重试填满机器。过载导致超时，客户端重试，重试进一步加剧过载——重试流量是吞吐量表上的"产出"，账本上的废品。监控上要单独分列"重试消耗的 GPU 小时"。

在错误的配置上满负荷。TP=8 跑一个本可以 TP=2 的模型，四倍的卡跑出了 1.3 倍的吞吐，每张卡都很忙，单位成本是别人的三倍。利用率考核不出这种问题，只有单位成本能。

一条管理原则：利用率用于发现浪费，单位成本用于评估经营。拿利用率考核团队，团队会学会把卡"看起来很忙"；拿单位成本和有效产能考核，团队才会去优化真正重要的东西。

读这张图的要点：有效产能的最大值不在吞吐最大处。并发 256 时吞吐比并发 64 高两成，但 P99 ITL 涨了五倍以上，若 SLA 是"P99 ITL ≤ 50ms"，并发 256 的产出几乎全部不合格。有效产能在拐点附近达到峰值，然后掉头向下——并发更高、吞吐更高，产出却更不值钱，这就是第 1 章那座"利用率三成可能比 API 还贵"的工厂在指标层面的形态。拐点在哪里，取决于负载分布和调度策略，这正是后续章节反复出现的权衡。

▶ 实验：吞吐与有效产能随并发的变化曲线

把上一节示意图变成你自己的数据，方法固定如下：

  1. 固化负载：一组真实流量分布（输入/输出长度分布、请求间隔分布），第 14 章讲怎么采；此处用录制的 trace 回放，保证可重复。
  2. 并发爬坡：并发数从 1 起按 1-2-5 序列（1、2、5、10、20、50、100、200）逐步上调，每档稳定运行 10 分钟。
  3. 记录四列：吞吐（token/s，分输入输出）、TTFT P50/P95/P99、ITL P50/P95/P99、完成率与重试率。
  4. 代入你的 SLA：设 TTFT ≤ 2s（P95）、ITL ≤ 50ms（P99），把每档标注"达标/不达标"。

本章小结

指标体系五个词：GPU 小时（投入）、吞吐（产出，必须按输入输出拆开）、TTFT 与 ITL（两个独立的延迟轴）、有效产能（SLA 约束下的合格产出）、单位成本（完全投入除以合格产出）。有效产能的定义拆出三种白干：排队超时、质量不合格、配置浪费。利用率是发现浪费的仪表，单位成本才是经营的标尺。

下一章把视角从数字拉回结构：一座工厂从下到上分五层，控制面和数据面怎么分，单机长成集群时架构怎么演进。
