GPU 资源调度器与混合任务

全书的贯穿案例在本章展开。场景：同一批 GPU 上，既要接在线对话与 Agent 请求（SLA 敏感），又要跑每 15 分钟一次的定时预测（气象/电力类），还要消化随时到达的离线批处理。本章给出这套调度的完整设计——以及一个贯穿全书的架构立场：调度器做薄，推理内核不自己写。章末把任务模型延伸到后训练负载：RL 相位循环的结构性空转怎么靠时间切片回收。

场景：三类任务抢一批卡

先把问题具体化。一家做行业预测的公司，GPU 池同时承载三类负载：

负载类型特征SLA 形态失败代价
在线请求（对话/Agent）随机到达、输入输出长度方差大TTFT/ITL 硬 SLA用户直接感知
定时推理（预测任务）每 15 分钟批量到达、有 deadline必须在窗口内完成错过窗口，业务下游空转
离线批处理量大、无 deadline、可中断只求吞吐无（重跑即可）

三类负载的资源画像互补又冲突：在线负载有明显的潮汐（白天高夜间低），定时任务有固定的资源脉冲（每 15 分钟一波），离线任务永远能吃掉所有空闲。混部得当，整体利用率从三成提到七八成（示意），等于用同样硬件多出一倍产能；混部失当，定时任务错过窗口、在线请求 ITL 崩掉、离线任务两头抢——一次事故就能让所有业务方要求"独占资源"。调度的全部艺术，就是在共享与隔离之间找到那条能让业务方信任的线。

调度器的对象模型

动手设计前，把调度器要管的四个概念钉死。这是本章最重要的一节——概念混了，后面全乱：

GPU 池是物理事实的登记簿：哪些卡、什么型号、NVLink 拓扑、RDMA 网络、健康状态。调度器做的所有分配都要过这张表——它也是第 7 章"硬件 × 引擎对照表"的落库形态。

模型实例是占卡的生产单元，有自己的资源画像（几张卡、什么精度、就绪状态）。注意实例与模型是两个概念：一个模型可以有多个实例（副本），一个实例只属于一个模型。调度器的原子操作单位是实例，不是模型。

配额与服务等级是租户视角的契约：谁能用多少并发、多少 token、什么优先级。配额是资源侧的硬约束（防抢跑），服务等级是延迟侧的承诺（决定谁先被满足）。第 11 章的租户体系是它的展开。

任务与请求是被调度的对象。在线请求、定时任务的一次运行、离线批的每一个分片，在调度器眼里都是"带优先级、带资源需求、带生命周期的工作项"。统一的任务模型是混部的地基——三套各自为政的任务系统不可能公平抢一批卡。

设计原则：调度器做薄

先立架构立场，这一段是本章的中心思想。调度器做薄——token 怎么生成、batch 怎么凑、KV 怎么管，全部交给引擎；自研部分只做四件事：资源编排、任务生命周期、路由与计量。

这条立场的论证分两半。第一半：不要自研推理内核。vLLM/SGLang 的调度器（continuous batching、chunked prefill、缓存管理）是数百人年级别的工程迭代，自研任何一部分都要面对"引擎三个月后追上了你自研的功能"的处境。你的调度器对引擎的接口应当只有一个动作——"这个实例，接这条请求"，加上"这个实例，给我让路"（见下文抢占）。引擎的实例内部调度策略用配置调（第 5、6 章），不要代码接管。

第二半：引擎不管的、又必须有人管的，才是自研要写的部分。引擎看见的世界是一个实例内的队列；看不见跨实例的流量分配、跨任务的资源腾挪、跨租户的配额执行。这些"实例之上"的编排职责在主流引擎里是缺位的（vLLM/SGLang 的文档自己都说明这不是它们的职责），开源的编排查（llm-d、Dynamo、K8s 生态）可以作为参照与组件，但"我们工厂的负载画像、配额规则、优先级语义"永远要自己写——因为它们本来就是业务定义。

一句话的边界测试：这段代码需要理解"token"吗？需要——放引擎侧（或复用引擎能力）；不需要——才允许放进自研调度器。按这个标准，负载均衡、生命周期、计量都在自研侧，批调度与 KV 管理都在引擎侧。

三个核心机制：预留、抢占、恢复

混合任务调度的难点集中在三个机制上。每个机制给"做什么、怎么做、错在哪"：

资源预留

定时任务有 deadline，必须在窗口开始时拿到资源。做法是提前量预留：调度器维护"未来 N 个窗口的资源视图"，定时任务的资源需求提前登记，与在线负载的容量上限做对冲（在线可用容量 = 总量 − 已预留）。预留的粒度是"实例级"：与其动态腾挪单卡，不如给定时任务维护一组专用实例（平时也接在线流量，窗口前开始清退）——这样预留就变成"控制在线流量导入的速率"，比硬抢卡温和得多。

抢占

在线流量突增、定时窗口将到，而 GPU 被离线任务占着——需要把低优先级任务"请下去"。抢占的分层动作（从轻到重）：限流新请求 → 拒绝新请求 → 对可中断任务发暂停（保存进度）→ 杀进程释放。推理负载的特殊性在于抢占成本：一个跑了两小时的离线任务被杀掉，损失以 GPU 小时计。所以离线任务的调度协议必须从一开始就支持定期 checkpoint（把中间状态和产出落盘），被抢占后从最近的 checkpoint 续跑。把"可抢占 + 可恢复"写进离线任务框架的接口约定，是混部能成立的前提——第 16 章 Lab V2 的验收标准就是"离线任务被抢占三次，最终结果仍正确"。

故障恢复

实例崩溃时，调度器要做三步：摘流量（网关把该实例从路由摘除）、重启或迁移（按失败等级，第 7 章）、回填（把积压请求分给其他实例，注意限速防止二次过载）。在线请求的损失面控制在重试层；定时任务要重排窗口（错过 deadline 的运行要么顺延要么跳过并告警，策略要预定义）；离线任务从 checkpoint 续跑。三类任务的恢复动作不同，调度器的事件处理要按任务类型分派，不要写成一个通用的"重启一切"。

贯穿案例：15 分钟预测任务的混部方案

把三个机制串成完整的时间线（示意配置）：总量 64 卡，其中 8 卡承担"预测任务实例池"。

这个设计的每个数字都可调、也要复盘：提前量 2 分钟来自实测的"实例内请求自然清空时间"（输入输出分布决定，几秒到几分钟）；8 卡的规模来自预测任务的 SLA（3 分钟内完成）除以单卡吞吐。混部的完整验收（▶ 实验）看四个数：在线 SLA 达标率（不能降）、定时任务准时率（100%）、离线吞吐（能吃到的余量）、以及一个常被漏掉的——让位动作的发生率（多少窗口靠自然清空、多少靠抢占，抢占率应当是个位数百分比，高抢占率说明预留提前量不够）。

▶ 实验：混部前后的利用率与在线 SLA

  1. 基线：只跑在线负载一周，记录利用率曲线与 SLA 达标率。
  2. 加入定时任务（不混部，独立小池），记录定时任务的资源消耗与总利用率。
  3. 开启混部（本章的预留 + 导流机制），同样跑一周。
  4. 对比四组数：总利用率、在线 SLA 达标率、定时任务准时率、离线任务完成量。
  5. 复盘让位事件：抢占率、被抢占任务的 checkpoint 恢复耗时。

延伸：第四类负载——后训练与时间切片

统一任务模型再往前走一步，会接到后训练（RL / SFT 微调）这类负载。它的形状与前三类都不同：一个 RL 作业内部是"采样生成 → 训练 → 权重更新"的相位循环，生成相占推理资源，训练相占整卡做反向传播，两相严格交替——同步 RL 的依赖结构决定了专用卡上有 30–74% 的时间在空转，而且这份空转是负载内部结构性的，作业自己填不上，只能靠别的作业来填。于是问题回到调度器：多个训练作业怎么共享同一批卡？

本章抢占机制的默认代价是"杀进程 + checkpoint 续跑"——对推理负载这是对的（KV 重算便宜），对训练负载太重：训练进度、优化器状态、累计梯度都要重建，恢复以分钟计。llm-d 的时间切片（time-slicing）给了一个更轻的原语：快照代理把 worker 的显存状态整体搬到主机内存，编排器轮转授予独占访问权，客户端库用 acquire() / yield() 两个调用包住每个工作单元——上下文切换 0.5–1.6 秒（中位），比重新拉起进程低两个数量级。注意这套机制与"调度器做薄"自洽：快照与轮转完全不需要理解 token，纯资源编排。它成立的前提则是一条接口纪律——任务接口要暴露相位边界。微调框架天然满足：generate_samples、forward_backward、optim_step 这些原语就是现成的可调度单元，服务层在每单元外包一层 acquire/yield，用户写的仍是普通训练循环。不需要 GPU 的工作（如 checkpoint 落盘）从主机侧副本跑，不占锁。

一组小规模实测（三个异构作业——两个 RL 一个 SFT、三种底模——挤在同一对 H100 上，一卡训练一卡采样）：

形态（真实基准）GPU 数总时长GPU 小时
专用，全并发621 min2.10
共享，作业串行排队254 min1.80

同硬件比串行快约 28%（省下的正是相位空转），比六卡专用少配三分之二的卡、省约 38% 的 GPU 小时，训练卡利用率从 15.6% 提到 34.2%；三个作业的收敛曲线与专用基线逐点一致——时间切片改变作业跑在哪，不改变学到什么。代价照实记：单个实验比六卡专用慢 1.9–2.5 倍；但六卡不存在的现实里，真实的替代项不是"专用"而是"排队"——排队时实验不是慢，是根本没在跑。同 2 卡串行 54 分钟对切片 39 分钟，同一时间窗里能多排约四成实验，这正是"研究者迭代速度"的账。来源：llm-d Blog《Run 40% more post-training experiments on the same GPUs with llm-d time-slicing》, 2026-09-14（Google 工程师，OpenRL 案例）另一个读表前提：3 作业 2 卡是时间切片的最难案例——相位以秒计、切换成本占比最大；生产规模下相位以分钟计，切换开销摊薄，可回收的空转只多不少。落到你的工厂，这类负载带出一个新指标：相位边界的暴露程度——训练框架把相位拆得越干净，切片调度能填的空转越多；第 16 章 Lab 的任务模型要为它预留接口位。

本章小结

四个对象（GPU、实例、配额、任务）一个立场（调度器做薄，编排归自研、生成归引擎）三个机制（预留靠导流、抢占靠 checkpoint、恢复分三级）。混合调度的成功标准不是利用率最高，是在线 SLA、定时准时、离线吞吐三个数字同时可签字。一切抢占策略的前提是任务框架支持可恢复——把这条写进离线任务的接口约定。训练型负载是统一任务模型的延伸：RL 相位循环的结构性空转靠时间切片（显存快照 + 轮转独占）回收，前提是任务接口暴露相位边界。
