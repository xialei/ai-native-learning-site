分布式 Checkpoint：存的是分片，读回来还能变拓扑

并行度改了之后旧 checkpoint 还能读吗——「存的是分片」和「读回来变拓扑」之间的矛盾怎么解？保存的复杂度其实是几个独立问题？ShardedTensor 的坐标系怎么让任意 rank 找回自己要的那部分？异步保存期间训练崩溃，checkpoint 会坏吗？

12.1分片存下的，怎么变拓扑读回来

千亿模型的 checkpoint 是分片散落在几百张卡上的。麻烦在恢复：续训时并行度改了怎么办？微调时 DP 数量不同怎么办？朴素做法（每卡存自己的分片 + 全局 metadata）在拓扑变化时对不上号——要么报错，要么静默错。拆开看，checkpoint 的复杂性常被低估成一个问题，实际是三个：存什么（模型/优化器/RNG/dataloader 状态）、怎么存（分片布局 + metadata，保存速度）、怎么读（变拓扑 reshard + 部分加载如仅权重供推理），两库的工程量大头都在后两个。而读这一问的答案先给一句：把「物理布局」与「逻辑布局」分开存，加载时按新拓扑重分片——保存慢一点没关系，永远能读才是底线。

一分钟版本

  • 朴素做法的坑：每卡存自己的分片 + 全局 metadata。加载时若并行度变了，各卡的「自己那份」对不上号——要么报错，要么静默错。
  • 解决思路：存「每个张量的完整形状 + 分片位置描述」，加载时按新拓扑重新切。代价是加载时要跨卡读（reshard 本质是重新 all-gather/scatter）。
  • DeepSpeed：universal checkpoint——把 ZeRO 分片布局转成「每参数完整 + 优化器状态分片」的规范形式，任意 ZeRO stage/DP 数恢复。

12.2Megatron 的 reshardable 格式

变拓扑读回的关键，是让每个分片带「全局坐标」。ShardedTensor 定义在 dist_checkpointing/mapping.py，读写策略放在 strategies/ 下；优化器状态再按 sharding type 分层：

megatron/core/dist_checkpointing/ — 结构盘点（译注）
textmegatron/core/dist_checkpointing/
├── mapping.py                 # ShardedTensor 抽象：每个分片带全局坐标
├── serialization.py           # save/load 入口，默认 backend=torch_dist
└── strategies/
    ├── torch.py               # torch_dist 主路径：基于 torch.distributed.checkpoint 读写
    ├── fully_parallel.py      # --ckpt-fully-parallel-save/load：多 rank 并行 IO 包装
    └── checkpointable.py      # 兼容 PyTorch DCP 库的 ShardedTensor 扩展
ShardedTensor 的语义：每个分片不只是裸 tensor，而是「tensor 的哪个部分」的描述（global_offset + local_shape + global_shape）。保存时把各卡的分片都写盘、metadata 记录完整坐标系；加载时给定新拓扑，每个新 rank 按 ShardedTensor 描述反查「我要的张量部分散落在哪些旧分片里」，读盘后拼装。优化器状态在这套坐标之上还分 sharding type（metadata 里的 distrib_optim_sharding_type）：默认 dp_reshardable 只沿 DP 维重分片；fully_reshardable（即 checkpoint_fully_reshardable_formats 开关，第 7 章 DistributedOptimizer）保存时把缓冲汇到 DP rank 0 重排成规范表示，加载时任意拓扑可读；fsdp_dtensor 服务 Megatron FSDP——不开的格式只能按原 DP 数恢复。

异步保存的语义：千卡集群一次全量保存要数十秒到分钟级，训练停下来等 IO 是巨大浪费。Megatron 的 async save 把「整理分片」与「写盘」分开：整理（需要 GPU 参与的部分）同步做，纯 IO 扔后台。加载的对称功能是 --ckpt-fully-parallel-load（多 rank 并行读盘再互发）。实战纪律：async save 期间若训练崩溃，最后一次 checkpoint 可能不完整——所以保存目录用「写入完成后原子改名」或双目录轮换。

12.4存的不只是参数

参数和优化器状态之外，还有几类「不存最难察觉」的 metadata：

内容MegatronDeepSpeed
模型参数ShardedTensor 分片 + metadatafp16 全量/分片 + ZeRO 布局
优化器状态DistributedOptimizer 的窗口分片master/m/v 分片（32bit 逐组）
lr scheduler / RNGcheckpoint 里带（RNG 决定 dropout 续训一致）engine 内部状态
dataloader 位置consumed_samples（第 5 章采样器靠它续位）micro_steps + dataloader state
变拓扑加载原生（reshardable formats）universal checkpoint 转换
RNG 与 consumed_samples 续训要做到「跟没停过一样」，有两个隐形条件：RNG 状态（不存则续训后 dropout 序列变了，loss 曲线在恢复点出现小跳变）与 consumed_samples（不存则数据从重头开始，重复样本扰动分布）。两者都是 metadata 级的小数据，漏了却最难察觉。

还有一类「当时不知道、半年后想要」的 metadata：训练本身的配置。2026-09 之前，Megatron 的 checkpoint 目录里只有权重和训练状态，当时的并行布局、超参、模型结构都要靠翻保存作业的日志才能拼出来；#7344 把完整的配置容器（run_config.yaml）直接落进每个 checkpoint 目录——训练、模型、优化器、scheduler、checkpoint、tokenizer 各节齐全，dataclass 的完整结构配合每项的 docstring，checkpoint 从此自带说明书。两个工程细节值得留意：写入时机在 tracker 文件（latest_checkpointed_iteration.txt）更新之前，也就是「配置永远先于『可发现的 checkpoint』出现」，不会出现 tracker 指着一个没有配置的目录；读取走 rank 0 读盘 + broadcast，运行期对象（Timers 这类无法离线重建的）在反序列化时置为 None。DeepSpeed 侧对应的字段早已有之——engine 的 checkpoint state 里存 ds_config 和 ds_version，但那是存在 checkpoint 文件内部；Megatron 这次补齐的是「目录级、人可直接打开」的形态。自研时这两层都值得做：机器读的配置进 state（保 round-trip），人读的配置落一个 yaml/json（保排查）。

这套「args 随 checkpoint 走」的机制在 2026-09 末又经受了第一次实战扩展：#6716/#7599 给 Megatron 加了 streamwise wide-residual 连接（每条残差流有独立保留门），五个新架构超参跟着进了 checkpoint 流程——check_checkpoint_args 里按「使能参数为 None 默认、具体默认值跟随 checkpoint」的规则逐一比对（checkpointing.py 的 _WIDE_RESIDUAL_ARG_DEFAULTS），load_args_from_checkpoint 里成对恢复。看它的形状而不是内容：每加一类模型结构，checkpoint 校验表就要长一列——「旧 checkpoint 加载时逐项断言架构一致」这个机制的生命力，恰恰靠这种持续的小扩展维持。

图 12.1：4 卡存、2 卡读的 reshard 坐标反查。每个分片的 (global_offset, local_shape, global_shape) 三元组是变拓扑的关键——新 rank 用它算出「我的窗口覆盖哪些旧分片」。

12.5小结 + 自研启示

本章的三个问题到这里都有了答案：存什么/怎么存/怎么读确实是三个独立问题，工程量大头在后两个；ShardedTensor 用 (global_offset, local_shape, global_shape) 描述每个分片，任意新 rank 靠 metadata 就能反查自己要读哪些旧分片（图 12.1）；DS 的 universal checkpoint 是事后转换、Megatron 是原生保存，功能等价、工作流不同；至于 RNG 和 consumed_samples 这两个隐形条件，它们都是 metadata 级的小数据，漏了却最难察觉——而 run_config.yaml（12.4）补的是另一层：不只机器能读，人也打开得开。落到自研路径：

自研启示 自研 checkpoint 的最小正确路径：第一版就按「每参数完整张量 + 保存时 DP 无关」存（torch 的 state_dict 天然如此）——大不了保存慢，但永远能读；分片布局优化等真的遇到 IO 瓶颈再做；metadata 单独一个小 json（版本号、并行布局、参数形状表）——半年后你一定会感谢它。最容易错的三点：只存了模型没存 optimizer（续训 loss 跳变）、RNG 没存（续训曲线微抖）、保存目录名带 step 但进程崩溃留下半截文件（用原子改名）。
