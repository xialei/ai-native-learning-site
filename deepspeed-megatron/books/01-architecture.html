总架构：两库如何拼成一台训练机

两个库的入口长什么样，为什么形状完全不同？一次 train step 里，两库的代码各在哪些环节被调用？哪些活归谁干、靠什么组合——这三件事看清了，这台训练机的图纸就有了。

1.1从三个问题开始

训练一个 LLM，这两个库各答一半。但「各答一半」只是个印象，真要理解它们怎么拼成一台训练机，得回答三件事。第一，两个库的入口长什么样——同样一个训练任务，Megatron 和 DeepSpeed 给用户的代码形状完全不同。这个差异不是随意的，入口怎么设计，暴露的是每个系统认为自己该管什么。第二，一次 train step 里，两库的代码分别在哪些环节被调用——从数据进来到参数更新，谁在前向、谁在反向、谁在优化器 step。第三，哪些活归谁干——模型怎么切开、副本冗余怎么砍、谁把这一切串起来。

答案先给一句：模型怎么切开是 Megatron 的事，副本里的冗余怎么砍是 DeepSpeed 的事，两者接口正交，所以能自由组合。这句话现在读起来可能有点空——接下来几节把它拆开验证。

1.2两条入口：从各自的主脚本看系统形状

先看 Megatron。仓库根目录的 pretrain_gpt.py 是参考实现。用户不写训练循环，而是提供三个回调函数，塞给 megatron/training/training.py 的 pretrain()：

pretrain_gpt.py — pretrain 主程序组装（摘录）
pythonfrom megatron.training import pretrain, get_args
from megatron.core.models.gpt import GPTModel

if __name__ == "__main__":
    pretrain(
        train_valid_test_dataset_provider=provider,   # 数据管线回调
        model_provider=model_provider,                # 返回一个「裸模型」的回调
        forward_step_func=forward_step,               # 一个 micro-batch 怎么算 loss
        model_type=ModelType.encoder_or_decoder,
    )
pretrain() 的注释把流程写得很直白：初始化 Megatron（进程组）→ 用 model_provider 造模型、包 DDP、配优化器 → 调 dataset provider 拿数据 → 用 forward_step_func 驱动 train() 循环。所有并行决策（TP/PP/DP/CP 多大）来自命令行参数，在 initialize_model_parallel() 一处定型。

DeepSpeed：initialize() 包裹任意模型

DeepSpeed 走了另一条路：不要求用户换主循环，而是把你的 nn.Module 包进 DeepSpeedEngine：

deepspeed/__init__.py — initialize() 签名（摘录，注释为译注）
pythondef initialize(
    args=None,
    model: torch.nn.Module = None,                # 你的模型原样传入
    optimizer=None,                               # 也可只在 json 配置里给
    model_parameters=None,
    training_data=None,
    lr_scheduler=None,
    config=None,                                 # json 配置：ZeRO stage、offload、累积步数…
) -> Tuple[DeepSpeedEngine, Optimizer, DataLoader, Any]:
    """Initialize the DeepSpeed Engine."""
注意返回值：engine 顶替了原模型——之后的 engine.forward/backward/step 全部走 DeepSpeed 的编排。并行切分本身 DeepSpeed 基本不管（除非用它的 pipe 引擎或 AutoTP）：模型得先被 Megatron 或其它工具切好，再交给 DeepSpeed 管「副本内显存」。这就是两个库能长期协作的结构原因——接口彼此正交。

1.3一次 train step 里两库各自的调用链

入口看完，往下钻一层：从数据进来到参数更新，两库的代码各在哪些环节被调用。Megatron 的单步训练在 megatron/training/training.py 的 train_step()（training.py:3243）里，主干只有几行（源文件 6000+ 行，但除去日志、容错、RL 分支后核心就是下面这些）：

megatron/training/training.py — train_step 主干（摘录+删减，注释为译注）
pythondef train_step(forward_step_func, data_iterator, model, optimizer,
                 opt_param_scheduler, config, forward_backward_func, ...):
    for model_chunk in model:
        model_chunk.zero_grad_buffer()          # 清零 DDP 梯度桶
    optimizer.zero_grad()

    # 核心：一次调度完所有 micro-batch 的前向+反向
    forward_backward_func(
        forward_step_func, data_iterator, model,
        num_microbatches=get_num_microbatches(),
        seq_length=args.seq_length, micro_batch_size=args.micro_batch_size,
        forward_only=False, ...)

    # 跨切分收尾：补规约 LN/嵌入梯度等 TP/PP 特有的遗漏项
    for model_chunk in model:
        config.finalize_model_grads_func(model, num_tokens=num_tokens)

    optimizer.step()
    return loss_dict, skipped_iter, ...
这几行里藏着三个角色：forward_backward_func 是流水线调度器（第 4 章），单卡时是普通循环，PP 时是 1F1B；zero_grad_buffer 证明梯度不是散在参数上的，而是住在 DDP 的连续 buffer 里（第 7 章）；finalize_model_grads 处理「梯度不是简单 all-reduce 就完事」的收尾——序列并行的 LN 梯度、TP 首尾阶段的嵌入梯度等（第 3 章）。

DeepSpeed 侧对应的是用户手里的三行：

用户训练循环 vs DeepSpeed 引擎（对比）
python# 普通 PyTorch              →   DeepSpeed
loss = model(batch)          →   loss = engine(batch)          # forward: 顺手挂钩子
loss.backward()              →   engine.backward(loss)         # 缩放 loss、触发 ZeRO 钩子
optimizer.step(); zero_grad()→   engine.step()                 # 只在 GAS 边界真更新
逐行对应得上：engine 的 backward() 里把 loss 除以 gradient_accumulation_steps 再 loss.backward()（deepspeed/runtime/engine.py:3297）；step()（engine.py:3482）先判断 is_gradient_accumulation_boundary()，非边界直接跳过更新。Megatron 的「一个 train_step 吃掉所有 micro-batch」与 DeepSpeed 的「用户自己循环调 backward、攒够 GAS 次」是同一件事的两种调度粒度。

1.5组合方式：谁包谁

分工边界说清了，还有一个现实问题：这两个库实际协作时，长什么样？翻遍各家的生产部署，只有三种合法姿势，各自的代表与代价：

组合结构代表代价 / 局限
Megatron 一体化栈pretrain() + Megatron DDP + DistributedOptimizer + TENVIDIA 内部主推、Llama 系复现主流选择绑定 Megatron 模型写法（必须用它的模块）
Megatron-DeepSpeedpretrain() 循环保留，mpu 传给 DeepSpeed，ZeRO 替换优化器BLOOM-176B（TP+PP+ZeRO-1 的 3D 并行实证）ZeRO stage 与 PP 曾互斥（DeepSpeed pipe 引擎限制 stage<2）；梯度收尾要两库协同
DeepSpeed 任意模型HF Trainer / Lightning + DeepSpeed，模型不改数万 HF 微调任务的事实标准没有 TP/PP，规模上限取决于 ZeRO + offload
注意 「ZeRO 与流水线并行互斥」曾经是硬约束：DeepSpeed 的 PipelineEngine.__init__ 至今保留断言 zero_optimization_stage() < ZeroStageEnum.gradients（即 pipe 引擎内 ZeRO 只能到 stage 1）。绕过方式是把 PP 交给 Megatron、ZeRO 只包 DeepSpeed 侧——这正是 Megatron-DeepSpeed 组合的意义。第 4 章展开。

1.7对「自研训练框架」的第一个启示

现在回头看开头那句话，它应该扎实多了：Megatron 的入口是回调式 pretrain() 主程序——绑定自己的循环；DeepSpeed 的入口是 initialize()——保留你的循环，只接管引擎。一次 train step 里，Megatron 的代码集中在 forward_backward_func（调度）、zero_grad_buffer（梯度 buffer）、finalize_model_grads（跨切分收尾），DeepSpeed 的代码则藏在 engine.backward/step 里（缩放、钩子、GAS 边界）。至于分工：Megatron 管「算不过来」——切分逻辑长在模型与算子里；DeepSpeed 管「存不下」——副本内的显存记账。两者接口正交，所以才有 1.5 那三种组合姿势。

要点 别从并行开始。自研训练框架的 MVP 是单卡混合精度训练循环 + 一份正确的梯度累积（这就是 DeepSpeed engine 在 stage 0 做的事）。然后按痛感逐层加：显存先爆 → 上 ZeRO-1；单卡算力不够 → 上 TP；batch 上不去 → 上 PP。顺序错了，每一步都在给后面埋雷。路线图见第 14 章。
