激活重算：用 33% 的算力换显存

激活显存到底多大，重算换显存的算力代价（33%）怎么算出来的？DS 的 CheckpointFunction 为什么要把三份 RNG 状态存下来，漏一份的后果是什么？Megatron 的 selective 重算保什么、重什么？重算与 PP/ZeRO-3/CP 共存时互相影响吗？

10.1显存不够时先砍哪块

第 6 章的账本只算了参数侧；长序列大 batch 下，激活才是显存大头。重算（activation checkpointing / gradient checkpointing）的策略简单粗暴：前向不存中间激活，反向用到时重算一遍。听上去是免费的显存，但有两个问题必须先答清楚：重算的那一遍怎么保证和第一遍逐位相同——第一遍有 dropout；以及为什么生产默认是 selective 而不是全重算。结论先放在这：重算是「用 33% 算力换显存」的确定交换，正确性的关键只有一条——重算的前向必须逐位复现第一遍，RNG 恢复是共同责任。

一分钟版本

transformer 一层的激活量 ≈ s × b × h × (34 + 5·a·s/h) 字节（fp16，s 序列长、b batch、h hidden、a 头数）。长序列时注意力矩阵那项平方增长。三个档位：

  • 不重算：全存。显存最大，速度最快。
  • 选择性重算：只重算便宜的、保留昂贵的——保存 QKV 线性层的输出（后面要用很多次），重算 LN/dropout/注意力概率（一次 GEMM 就能重得）。
  • 全重算：每层只存输入，反向时整层重算。显存 ≈ √层数 量级（最优分段），代价 ~33%。
33% 从哪来 反向本来就约等于 2 倍前向计算量（dgrad+wgrad 两套 GEMM）。重算给每层加 1 次前向 → 总计算从 3×F 变 4×F，即 +33%。全重算是上界；选择性重算通常 +15% 以内就能省一半以上激活显存，所以是生产默认。

10.2DeepSpeed 的 CheckpointFunction

先追那个正确性问题。重算要求第二遍前向和第一遍逐位相同——DS 的解法是把所有随机性源头全部存下来：

deepspeed/runtime/activation_checkpointing/checkpointing.py — CheckpointFunction.forward（摘录，译注）
pythonclass CheckpointFunction(torch.autograd.Function):
    @staticmethod
    def forward(ctx, run_function, preserve_rng_state, *args):
        ctx.run_function = run_function
        if preserve_rng_state:
            # 关键：保存 CPU/CUDA RNG 状态——dropout 位置必须可复现
            ctx.fwd_cpu_rng_state = torch.get_rng_state()
            ctx.fwd_cuda_rng_state = torch.cuda.get_rng_state()
            # 以及张量并行专用的 RNG tracker（各卡不同的 dropout mask）
            ctx.fwd_cuda_rng_state_tracker = tensor_parallel.get_cuda_rng_tracker().get_state()
        with torch.no_grad():
            outputs = run_function(*args)          # 前向算一遍，不建图、不留中间激活
        # PARTITION_ACTIVATIONS：输入也切分（DP 内多级并行时）
        # CPU_CHECKPOINT：切下的输入再挪 CPU（更省，搬运更贵）
        ctx.save_for_backward(*args_for_backward)

    @staticmethod
    def backward(ctx, *args):
        with torch.random.fork_rng(devices=...):
            # 恢复 RNG → 重算前向（这次建图）→ 正常反传
            with torch.enable_grad():
                outputs = ctx.run_function(*ctx.inputs)
                # 重算时 PARTITION_ACTIVATIONS 需要先 all-gather 输入
        return None, None, *gradients
漏一份 RNG 状态会怎样：重算出来的前向必须和第一遍逐位相同——dropout 的 mask、TP 各卡不同的随机数（RNG tracker 给每张卡派不同 seed）都要原样恢复。漏一个就是「重算的前向 ≠ 原前向」，梯度悄悄错，loss 曲线看着正常但收敛变差——这类 bug 极难排查。PARTITION_ACTIVATIONS 服务于「DP 之内还有数据切分」的场景（如 MoE），CPU_CHECKPOINT 把存的输入也挪 CPU——三级显存/带宽的取舍。DS 用法是模型里显式包 checkpoint(checkpoint, f, args)，属于侵入式 API。

10.3Megatron 的层内重算与选择性重算

全重算存得最少，但每个算子都付一遍算力——能不能只重算「便宜的」、保留「昂贵的」？Megatron 的 selective 档就是这个思路：

10.4与 PP/ZeRO-3 的互动

重算也不是一个孤立开关——它改变显存分布，和 PP、ZeRO-3、CP 都有互动：

  • PP：1F1B 的 in-flight 激活本来就少（第 4 章），但 warmup 阶段的激活仍随阶段位置涨——重算把 in-flight 峰值再压一档，让 PP 能开更多 microbatch。
  • ZeRO-3：fetch 参数本身要占显存，重算省下的激活空间正好给 max_live_parameters 让路——两者是互补而不是竞争。
  • CP：zigzag 切分后每卡的注意力已是 O(s²/CP)，重算在 CP 内部段照常工作，无需特判。
e2e 的排布顺序 显存不够时的调参顺序（经验）：先开 selective 重算（几乎免费）→ 再上 ZeRO-2 → 还不够上 ZeRO-3 + offload_optimizer → 最后 offload_param / NVMe。每一步都比下一步便宜（带宽税更小）。很多训练事故源于直接跳到最重方案。

10.5小结 + 自研启示

回望这一章：激活公式里的 s² 项既是长序列显存爆炸的根源，也是 selective 重算的靶子；DS 把 CPU、CUDA、TP tracker 三份 RNG 状态全存下来，重算时 fork_rng 恢复，漏一份就是静默数值错误；selective 只重算「一次 GEMM 就能重得」的部分，算力代价不到全重算一半；而它和 PP/ZeRO-3/CP 是互补不是竞争——省下的激活显存正好给参数 fetch 让路。三种实现的差别用一张表收拢：

实现侵入性RNG 处理特色
DS CheckpointFunction显式包裹函数保存 CPU+CUDA+tracker 三份PARTITION_ACTIVATIONS / CPU_CHECKPOINT
Megatron checkpointed_forward配置开关，模型无感复用 TP RNG trackerselective 重算 + uniform/block 分段
torch.utils.checkpoint原生 API自动 fork_rnguse_reentrant 区别（新版默认 False）
自研启示 自研重算的最小正确路径：直接用 torch.utils.checkpoint（非 reentrant 版），不要自己写 RNG 保存——TP 场景下 RNG tracker 的坑非常深。真正值得自己写的是分段策略：按「层输入大小 × 层数」做背包问题，均匀分段是基线。最容易错的三点：checkpoint 段内含 TP 通信（重算触发重复归约，结果错）、checkpoint 包住了带 dropout 的层但没恢复 RNG（静默数值错误）、非 reentrant 模式下在 checkpoint 内部修改了全局状态（第一次与重算结果不一致）。
