ZeRO 1/2 与 Megatron 分布式优化器：同一思想的两个实现

优化器状态为什么能安全地按 DP 切、切完之后梯度归约怎么改、step 只更新本卡分区的语义怎么保证一致？Megatron 不叫 ZeRO 却做了等价物——它的「bucket + range map」和 DS 的「IPG bucket」差在哪？换个更新规则的优化器（Muon）怎么进分片框架？fp16 训练的 loss scale 归谁管？

7.1同一份优化器状态，为什么要存 N 份

第 6 章的账本说优化器状态占 12B/参数。ZeRO-1 的主张就从这里来：每个 DP 副本的优化器状态一模一样，那为什么要存 N 份？切成 N 份，各存一份。听上去简单，但马上有一串追问：每个 DP 副本都要更新全部参数，凭什么只存 1/N 的状态，step 之后各副本参数怎么保持一致？梯度 all-reduce 之后每卡都有全量——可 ZeRO-2 说归约完就丢，用什么集合通信替换 all-reduce？Megatron 不用 DS 的 ZeRO，却实现了一个等价物，它的「bucket + range map」和 DS 的「IPG bucket」差在哪？再往后，换个更新规则的优化器（比如要看到完整矩阵的 Muon），分片框架还接得住吗？最后，fp16 需要动态缩放、bf16 不需要，loss scale 归谁管、两库的 scaler 语义一致吗？

一句话结论先放在这：ZeRO-1/2 的全部改动收在 optimizer 侧——模型和梯度代码零改动，这是它性价比最高的原因。下面从 DeepSpeed 侧开始验证。

一分钟版本

  • ZeRO-1：优化器状态（fp32 master + m + v，12B/参数）按 DP 组分片。每卡只更新自己那片参数的 master/m/v，更新完 all-gather 同步新参数。
  • ZeRO-2：再加一条——反向传播时每个参数的梯度最终只需要在负责它的那张卡上存在，其他卡的副本归约完即可丢弃 → 梯度也分片（reduce-scatter 代替 all-reduce）。
  • Megatron DistributedOptimizer：不叫 ZeRO，但等价于 ZeRO-1——fp32 主参数和梯度缓冲按 DP 分片，蓝图是「bucket + range map」。
为什么 ZeRO-2 止步于此 参数不能像梯度那样「归约完就丢」——前向每一步都要用全部参数。参数分片意味着每次前向都要现场拼装（fetch），这就是 ZeRO-3，第 8 章专门讲它的代价与工程。

7.3Megatron DistributedOptimizer

再看 Megatron 侧。它不用 DeepSpeed 的 ZeRO，但实现了一个等价物。核心数据结构是「主缓冲 + range map」：

        "gbuf_world_start" : gbuf_world_start,  # 本卡分片的起点（全局坐标）
        "gbuf_world_end" : ...,                  # 终点

range map 的窗口视角：每个参数在世界缓冲（gbuf world）里有一个位置区间；DP 组把世界缓冲均分成 N 份，每张卡持有其中一份的fp32 拷贝。归约时用 reduce-scatter 直接把每份梯度送进负责卡的窗口，不需要「先 all-reduce 再分片」。优化器只对窗口内的参数做 step。这套映射支撑了另一个重要功能：checkpoint_fully_reshardable_formats——保存的 checkpoint 可以被任意 DP 规模加载（第 12 章）。

7.4两份实现，同一思想：差异清单

两份代码读完了，差异集中在哪？收进一张表——

维度DeepSpeed ZeRO-1/2Megatron DistributedOptimizer
分片对象fp32 master + m/v（按参数分组）fp32 主参数 + 梯度缓冲（按平坦缓冲窗口）
梯度归约IPG bucket 异步 reducereduce-scatter 直达窗口
fp16 梯度ZeRO-2 分片（非本卡释放）始终全量（在 grad_data 缓冲）

场景判断 用 DS 主导的代码库（hf transformers + accelerate），ZeRO-2 是默认起点；用 Megatron 主导的训练栈，DistributedOptimizer 几乎总是开着（use_distributed_optimizer）。两者不要混用——Megatron 的 mpu 插头传给 DS 后，两套优化器状态会重复。

7.5Muon 进 ZeRO：分片框架收编新优化器

ZeRO 的分片语义原本是照着 Adam 写的：状态按参数切、梯度按分区归约、step 只碰本卡那片。Muon 换掉了更新规则（动量 + Newton-Schulz 正交化，要看到完整矩阵才能做），进 ZeRO 框架时撞上的正是这个前提——2026-09 的 #8464 一次修了四个相关问题，把它们摆出来比任何设计文档都清楚地说明了「优化器状态分片」和「优化器算法」是两层事：

  • 几何结构丢失：ZeRO 分片把参数摊平成一维段，Muon 的 Newton-Schulz 需要 2D/3D 矩阵——先按原形状复原、算完再切回去，1D 辅助参数（Adam 侧的）保持原样。
  • offload 下的设备错位：动量在 CPU、梯度在 GPU，反向中直接调更新会跨设备报错还会重复更新——ZeRO-3 的 Muon 更新挪到 step 边界（_apply_muon_to_accumulated_grads，在溢出检查之后，被 loss scale 丢弃的 step 不再污染动量）。
  • gather 缓冲无上限：all-gather 的临时缓冲没做预算管理，显存尖峰和碎片——现在用 LRU 缓存封顶（cache 总量 256MB，单次 gather 的 scratch 预算 64MB），destroy() 时清空。
  • NVMe 换入的子组：动量标记 swappable = False 才能常驻内存；梯度仍从 NVMe 换入再算——「优化器状态常驻」不等于「梯度常驻」。
deepspeed/runtime/zero/stage_1_and_2.py — 有界 gather 缓冲（摘录，注释为译注）
python# 每个子组的 all-gather scratch 缓冲按 cache_key 复用，总量封顶

读法：这不是「新优化器接入」的常规姿势——没有抽象出通用的「分片优化器接口」，而是在 ZeRO 引擎内部逐点适配（stage_1_and_2.py 与 stage3.py 各有一份 Muon 路径，step 里在溢出检查和子组循环之间插一步）。集成成本全部由框架承担、用户配置不变（optimizer 名改成 Muon），代价是每来一个非 Adam 形状的优化器都要再走一遍这个过程。Megatron 侧的回答不同：Muon 走的是独立的 emerging_optimizers 体系（TensorParallelMuon），从设计起就带 TP 语义，不往 DistributedOptimizer 里塞——两条路线的取舍在第 14 章的自研语境里还会回来。另外一条实用性提示：ZeRO-1/2 + CPU offload 时 Muon 只 gather 本卡拥有的梯度/动量切片，按 64MB 预算分批处理，超出预算的矩阵单独算（Newton-Schulz 必须整矩阵），这个限制不含 Newton-Schulz 自己的工作区。

同一周里的 #8633 又补了一刀，暴露的坑更隐蔽——动量的提交时机。ZeRO-1/2 的 Muon 把「梯度折进动量」这一步提前到了分区填充时（get_flat_partition 逐参数做 muon_update），但溢出检查要等 step 才知道本 step 是否作废——作废的 step 不能污染动量，可梯度折进动量已经发生了。#8633 的解法是把动量拆成「暂存/提交」两态：

deepspeed/runtime/zero/stage_1_and_2.py — _muon_staging_momentum / step（摘录，注释为译注）
python# 每个分区只暂存一次：staging 是从已提交动量拷贝出来的，
# 逐参数暂存会把前面参数刚写进去的更新冲掉
staged_momentum = self._muon_staging_momentum(flatten_copy, param_group_idx)
# 填分区时：muon_update 直接写进 staged 副本（不碰 optimizer.state）
buffer = torch.narrow(staged_momentum, 0, buffer_idx, tensor.numel()).view(tensor.size())

# step() 里：溢出检查通过才提交
if not self.overflow:
    self._commit_muon_momentum()      # staged → optimizer.state["momentum_buffer"]
为什么是暂存而不是回滚：溢出后要把「梯度折进动量」撤销，最直觉的方案是保存旧动量、失败时恢复——但那要求每个被更新过的参数都留一份副本。暂存方案反过来：step 前动量照常更新，但写进的是一个副本（staged），optimizer.state 里的已提交动量始终不动；step 活下来才把 staged 整体 copy_ 回去。还有个细节：staged 副本不进 optimizer.state（代码注释明说 Kept off optimizer.state so it does not travel into checkpoints）——否则 checkpoint 里会多出一份无效动量。自研时凡是「计算提前到溢出检查之前」的优化器，都要面对这个「作废 step 的状态回退」问题，暂存/提交是比回滚便宜的答案。

7.6loss scale：fp16 训练的最后一环

分片、归约都解决了，fp16 下还剩最后一环——梯度太小会下溢。bf16 和 fp16 在这里走的是两条路：

megatron/core/optimizer/__init__.py — scaler 选择（摘录，译注）
python# _get_optimizer_config_solver 附近：fp16 → DynamicLossScaler
if config.bf16:
    return None                          # bf16 不需要缩放（指数位足够）
elif config.fp16:
    return DynamicLossScaler(
        initial_scale=...,
        min_scale=...,
        growth_interval=...,             # 连续多少 step 无溢出则 scale 翻倍
        hysteresis=...,                  # 溢出后回退几档，防止反复抖动
    )
bf16 与 fp16 的差别全在指数位：bf16 指数位与 fp32 相同，动态范围够，不需要 loss scale；fp16 尾数位多但指数位窄，小梯度下溢 → 需要动态缩放。DS 与 Megatron 的 scaler 语义一致（growth_interval + 溢出回退 + hysteresis），DS 的配置键是 loss_scale_window/min_loss_scale。自研时如果只支持 bf16，可以直接跳过整个 scaler 模块——这是现代训练栈大幅简化的根源之一。

7.7自研 ZeRO-1 还剩什么

顺带回答一个动手党的问题：bf16 训练跳过整个 scaler 模块后，自研 ZeRO-1 还剩什么？

自研启示 自研 ZeRO-1 的最小正确路径：把 optimizer 状态（master/m/v）按 DP rank 分片——改动只在 optimizer.step 里，模型/梯度代码零改动，这就是为什么 ZeRO-1 是性价比最高的起点；step 后 all-gather 同步参数；溢出检查用 torch.isinf/isnan 的 all-reduce（一票否决）。最容易错的三点：master 权重更新后忘记 all-gather（各副本参数漂移）、all-gather 用了错误的 group（DP group 而不是全局）、初始 lr 预热算在分片 optimizer 的 step 计数上（应算全局 step）。

7.8小结

本章从「为什么要存 N 份」的疑问出发，答案逐层落地：优化器状态能切，是因为 DP 副本间它完全冗余——分片语义收在 optimizer.step 内部，模型和梯度代码零改动；梯度归约跟着改——IPG bucket 满即异步归约与反向计算重叠，ZeRO-2 用 reduce 代替 all-reduce 让梯度只在负责卡存在；Megatron 的等价物是「bucket + range map」——与 DS 的差异是按平坦缓冲窗口而非按参数分组，reduce-scatter 直达窗口；换更新规则的优化器进分片框架，撞上的全是「状态按参数切」这个预设——Muon 的四个坑加动量暂存/提交（7.5）就是预设与新算法的边界清单；loss scale 归 optimizer 管——bf16 指数位够直接跳过，fp16 的 growth_interval + hysteresis 两库语义一致。7.4 末尾那条场景判断是本章最实用的一句：用 DS 主导的代码库就从 ZeRO-2 起步，用 Megatron 栈就常开 DistributedOptimizer，两者不要混用。
