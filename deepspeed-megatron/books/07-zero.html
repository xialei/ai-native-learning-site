ZeRO 1/2 与 Megatron 分布式优化器：同一思想的两个实现

优化器状态为什么能安全地按 DP 切、切完之后梯度归约怎么改、step 只更新本卡分区的语义怎么保证一致？Megatron 不叫 ZeRO 却做了等价物——它的「bucket + range map」和 DS 的「IPG bucket」差在哪？fp16 训练的 loss scale 归谁管？

7.1同一份优化器状态，为什么要存 N 份

第 6 章的账本说优化器状态占 12B/参数。ZeRO-1 的主张就从这里来：每个 DP 副本的优化器状态一模一样，那为什么要存 N 份？切成 N 份，各存一份。听上去简单，但马上有一串追问：每个 DP 副本都要更新全部参数，凭什么只存 1/N 的状态，step 之后各副本参数怎么保持一致？梯度 all-reduce 之后每卡都有全量——可 ZeRO-2 说归约完就丢，用什么集合通信替换 all-reduce？Megatron 不用 DS 的 ZeRO，却实现了一个等价物，它的「bucket + range map」和 DS 的「IPG bucket」差在哪？最后，fp16 需要动态缩放、bf16 不需要，loss scale 归谁管、两库的 scaler 语义一致吗？

一句话结论先放在这：ZeRO-1/2 的全部改动收在 optimizer 侧——模型和梯度代码零改动，这是它性价比最高的原因。下面从 DeepSpeed 侧开始验证。

一分钟版本

  • ZeRO-1：优化器状态（fp32 master + m + v，12B/参数）按 DP 组分片。每卡只更新自己那片参数的 master/m/v，更新完 all-gather 同步新参数。
  • ZeRO-2：再加一条——反向传播时每个参数的梯度最终只需要在负责它的那张卡上存在，其他卡的副本归约完即可丢弃 → 梯度也分片（reduce-scatter 代替 all-reduce）。
  • Megatron DistributedOptimizer：不叫 ZeRO，但等价于 ZeRO-1——fp32 主参数和梯度缓冲按 DP 分片，蓝图是「bucket + range map」。
为什么 ZeRO-2 止步于此 参数不能像梯度那样「归约完就丢」——前向每一步都要用全部参数。参数分片意味着每次前向都要现场拼装（fetch），这就是 ZeRO-3，第 8 章专门讲它的代价与工程。

7.3Megatron DistributedOptimizer

再看 Megatron 侧。它不用 DeepSpeed 的 ZeRO，但实现了一个等价物。核心数据结构是「主缓冲 + range map」：

megatron/core/optimizer/distrib_optimizer.py — _build_model_gbuf_param_range_map（结构摘录，译注）
python# 每 (DP rank, buffer, bucket) 一张 range map：描述「本卡负责哪些参数」

    return {
        "gbuf_world" : gbuf_world,              # 全局缓冲引用
        "gbuf_world_start" : gbuf_world_start,  # 本卡分片的起点（全局坐标）
        "gbuf_world_end" : ...,                  # 终点
        "gbuf_local" : ...,                     # 换算成局部坐标
        "param_range_list" : ...,                # 本卡窗口内的参数列表
    }
range map 的窗口视角：每个参数在世界缓冲（gbuf world）里有一个位置区间；DP 组把世界缓冲均分成 N 份，每张卡持有其中一份的fp32 拷贝。归约时用 reduce-scatter 直接把每份梯度送进负责卡的窗口，不需要「先 all-reduce 再分片」。优化器只对窗口内的参数做 step。这套映射支撑了另一个重要功能：checkpoint_fully_reshardable_formats——保存的 checkpoint 可以被任意 DP 规模加载（第 12 章）。

7.4两份实现，同一思想：差异清单

两份代码读完了，差异集中在哪？收进一张表——

维度DeepSpeed ZeRO-1/2Megatron DistributedOptimizer
分片对象fp32 master + m/v（按参数分组）fp32 主参数 + 梯度缓冲（按平坦缓冲窗口）
梯度归约IPG bucket 异步 reducereduce-scatter 直达窗口
fp16 梯度ZeRO-2 分片（非本卡释放）始终全量（在 grad_data 缓冲）
与 PP/EP 关系DS pipe 不兼容（第 4 章）原生配合（train_step 全链路）
与 ZeRO-2 差异——更接近 ZeRO-1 + fp32 梯度缓冲（省 fp16→fp32 拷贝）
场景判断 用 DS 主导的代码库（hf transformers + accelerate），ZeRO-2 是默认起点；用 Megatron 主导的训练栈，DistributedOptimizer 几乎总是开着（use_distributed_optimizer）。两者不要混用——Megatron 的 mpu 插头传给 DS 后，两套优化器状态会重复。

7.5loss scale：fp16 训练的最后一环

分片、归约都解决了，fp16 下还剩最后一环——梯度太小会下溢。bf16 和 fp16 在这里走的是两条路：

megatron/core/optimizer/__init__.py — scaler 选择（摘录，译注）
python# _get_optimizer_config_solver 附近：fp16 → DynamicLossScaler
if config.bf16:
    return None                          # bf16 不需要缩放（指数位足够）
elif config.fp16:
    return DynamicLossScaler(
        initial_scale=...,
        min_scale=...,
        growth_interval=...,             # 连续多少 step 无溢出则 scale 翻倍
        hysteresis=...,                  # 溢出后回退几档，防止反复抖动
    )
bf16 与 fp16 的差别全在指数位：bf16 指数位与 fp32 相同，动态范围够，不需要 loss scale；fp16 尾数位多但指数位窄，小梯度下溢 → 需要动态缩放。DS 与 Megatron 的 scaler 语义一致（growth_interval + 溢出回退 + hysteresis），DS 的配置键是 loss_scale_window/min_loss_scale。自研时如果只支持 bf16，可以直接跳过整个 scaler 模块——这是现代训练栈大幅简化的根源之一。

7.6自研 ZeRO-1 还剩什么

顺带回答一个动手党的问题：bf16 训练跳过整个 scaler 模块后，自研 ZeRO-1 还剩什么？

自研启示 自研 ZeRO-1 的最小正确路径：把 optimizer 状态（master/m/v）按 DP rank 分片——改动只在 optimizer.step 里，模型/梯度代码零改动，这就是为什么 ZeRO-1 是性价比最高的起点；step 后 all-gather 同步参数；溢出检查用 torch.isinf/isnan 的 all-reduce（一票否决）。最容易错的三点：master 权重更新后忘记 all-gather（各副本参数漂移）、all-gather 用了错误的 group（DP group 而不是全局）、初始 lr 预热算在分片 optimizer 的 step 计数上（应算全局 step）。

7.7小结

本章从「为什么要存 N 份」的疑问出发，答案逐层落地：优化器状态能切，是因为 DP 副本间它完全冗余——分片语义收在 optimizer.step 内部，模型和梯度代码零改动；梯度归约跟着改——IPG bucket 满即异步归约与反向计算重叠，ZeRO-2 用 reduce 代替 all-reduce 让梯度只在负责卡存在；Megatron 的等价物是「bucket + range map」——与 DS 的差异是按平坦缓冲窗口而非按参数分组，reduce-scatter 直达窗口；loss scale 归 optimizer 管——bf16 指数位够直接跳过，fp16 的 growth_interval + hysteresis 两库语义一致。7.4 末尾那条场景判断是本章最实用的一句：用 DS 主导的代码库就从 ZeRO-2 起步，用 Megatron 栈就常开 DistributedOptimizer，两者不要混用。
