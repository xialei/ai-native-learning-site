Offload：GPU 装不下，内存与 NVMe 来凑

ZeRO 分片到极限还不够时，DeepSpeed 的第二张牌是「挪出去」：优化器状态挪 CPU（Offload）、参数也挪 CPU（ZeRO-Infinity）、再往后挪 NVMe（DeepNVMe 异步读写）。挪出是容易的，难的是带宽账：PCIe 与 NVMe 比显存带宽慢两个数量级，所有设计都在回答「怎么让挪动的时间藏进计算」。

9.1一分钟版本

方案挪什么挪到哪带宽假设
ZeRO-Offload优化器状态 + fp32 masterCPU 内存PCIe ~25 GB/s
ZeRO-Offload（梯度也挪）+ fp16 梯度在 CPU 上更新CPU 内存同上，CPU Adam 消耗算力
ZeRO-Infinity+ 参数分片CPU / NVMeNVMe ~6 GB/s/盘
SuperOffload参数/梯度/状态分层放置NVMe 优先多盘并行 + 计算重叠
带宽是第一性约束 每个训练 step，offload 方案至少要挪两次：梯度下行（GPU→CPU）+ 更新后的参数上行（CPU→GPU）。7B 模型 DP=8（ZeRO 切过）：每卡每 step 仍有 ~2 GB 级别的数据要过 PCIe。带宽不够，GPU 就在等——offload 的性能下限由 PCIe 决定，上限由「重叠做得好不好」决定。

9.2用代码看｜CPU Adam：更新的算力从哪来

Offload 后优化器状态在 CPU，那 Adam 的更新公式在哪算？DS 用一个编译好的 CPU kernel：

为什么专门写 CPU kernel：PyTorch 原生 optimizer 在 CPU 上是单标量循环，7B 模型的 12B/参数更新慢到不可用。DS 的 CPU Adam 用 SIMD + 多线程把更新压到「与 PCIe 传输同量级」。这带来一个部署约束：CPU Adam 吃满物理核——offload 训练时 CPU 是第二台「优化器机器」，dataloader 的 worker 要让核，否则两边抢核互相拖慢。机器选型时核数与内存带宽（不止容量）一起看。

9.4DeepNVMe：NVMe 当扩展内存用

deepspeed/runtime/zero/offload_states.py 相关 + csrc/aio — DeepNVMe（结构摘录，译注）
python# offload 配置示例（ds_config.json 片段）
{
  "offload_optimizer": {
    "device": "nvme",
    "nvme_path": "/local_nvme",       # 本地盘，不是网络盘
    "pin_memory": true                 # CPU 侧固定内存，DMA 直传
  },
  "aio": {
    "block_size": 1048576,             # 1MB 块——顺序 IO 的甜点区
    "queue_depth": 8,                  # 异步队列深度
    "single_submit": false,
    "overlap_events": true
  }
}
读懂 aio 配置：DeepNVMe 是 DS 自研的异步 IO 层（csrc/aio，libaio 封装）：请求切成大块（block_size）、排进深队列（queue_depth）、多请求并行在途（overlap_events）——把 NVMe 的随机小 IO 劣势扭成顺序大 IO。实战数字：企业级 NVMe 盘 4–7 GB/s，两盘并行可到 10+ GB/s；训练 step 的参数搬运若能压进计算窗口内，GPU 利用率几乎不掉。盘选本地 NVMe，不要网络盘——网络盘的延迟抖动会直接打穿重叠窗口。
SuperOffload / ZenFlow 一句话 论文级扩展：SuperOffload 用「NVMe 优先 + CPU 副本保留热数据 + 专用算子」进一步压 PCIe 依赖；ZenFlow 研究「把不活跃参数长期留在远端、活跃参数留在 GPU」的放置策略。两者是 Offload 思想的延伸，主线配置里先掌握 offload_optimizer / offload_param 两个开关即可。

9.5选型决策树

情况建议
单卡/小 DP 组，模型放不下ZeRO-3 + offload_optimizer(cpu)——优化器状态 12B/参数最重，先挪它
CPU 内存也紧张offload_param + offload_optimizer 都开，参数按需换入
内存+显存都不够device 改 nvme，确认本地盘 + aio 调优
DP 组很大（≥16）先别 offload——ZeRO-3 纯 GPU 分片往往已经够了，offload 是带宽税
自研启示 自研 offload 的最小正确路径：① 只挪优化器状态（性价比最高的一步）；② CPU 侧用 pinned memory + torch 的 .to('cpu', non_blocking=True)，配 stream 同步；③ 先不做重叠，量出「每 step 搬运总时长」再决定要不要重叠。最容易错的三点：pin_memory 忘了开（搬运走慢速路径）、CPU 侧用了默认 dtype（fp32 搬运量翻倍）、NVMe 用了网络盘（延迟抖动打穿重叠窗口）。bandwidth 账先算再写代码：搬运字节 ÷ PCIe 带宽 = 每 step 的最低时间下限。
