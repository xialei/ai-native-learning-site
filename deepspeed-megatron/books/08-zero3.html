ZeRO-3：参数也切了，前向怎么算

参数也按 DP 切掉之后，前向要用参数时怎么办？借还循环怎么做到不改一行模型代码，prefetch 怎么把 all-gather 的通信藏进计算？step 时「子组逐个更新」的写法在省什么显存？哪些模型写法会让 ZeRO-3 静默出错？

8.1参数不在本地，前向怎么算

ZeRO-1/2 切优化器状态和梯度，参数本身各卡仍有完整副本。ZeRO-3 把参数也按 DP 切——每卡只剩 16/DP 字节。代价立刻出现：前向时参数不在本地，要用之前现场 all-gather、用完立刻释放。整个 ZeRO-3 就建立在这个「借还循环」上。一分钟版本：

  • init 时：模型构造完成后，参数立刻被切走（每卡只留 1/N 的分片，记作 ds_tensor），原 param 换成空壳（metadata）。
  • 前向时：算到哪一层，就把该层参数 all-gather 成完整形状，算完立刻归还（除非在 prefetch 队列里要留着）。
  • 反向时：同样 fetch → 算 → 梯度留在本地分片（梯度归约成 reduce-scatter）。
  • step 时：优化器状态也分片，子组逐个更新、逐个写回。

循环本身不难理解，难的是工程细节：借还的总管是谁、prefetch_bucket_size / max_reuse_distance / max_live_parameters 这几个旋钮各管什么；参数是在哪一刻被切走的、借还动作挂在哪里才能做到用户模型代码一行不改；step 时怎么进一步压显存峰值；以及哪些模型写法会让这一整套静默出错。先把答案放在这：ZeRO-3 是「借还循环」+ hook 自动化——通信量随模型大小线性涨，靠 prefetch 和子组步进把显存峰值和通信代价同时压住。

与 TP 的本质区别 TP 切参数是永久的计算切分（每卡永久持有固定一半，输出也是分片）；ZeRO-3 切参数是临时的存储分片（前向一凑就是完整的，凑是全量 all-gather，通信量 = 参数全量）。DP 内的卡跑的是完整模型——所以 ZeRO-3 后面不能再挂 TP 语义的东西（同一段模型所有 DP 卡一起算）。TP 便宜是因为算子级通信小且固定；ZeRO-3 的通信随模型大小线性涨，靠 prefetch 和重叠把代价藏进计算。

8.2借还的总管：PartitionedParameterCoordinator

借还循环需要一个总管——谁登记借出、谁控制同时借出的上限、谁决定提前多久发通信？答案是 PartitionedParameterCoordinator：

deepspeed/runtime/zero/partitioned_param_coordinator.py — 核心配置（摘录，译注）
pythonclass PartitionedParameterCoordinator:
    """Handles borrowing and returning parameters."""

    def __init__(self,
                 prefetch_bucket_size,      # 预取桶：提前多少参数开始 all-gather
                 max_reuse_distance,        # 距离内会再用的参数用完不还（省重复 fetch）
                 max_live_parameters,       # 同一时刻最多借出的参数量（显存上限）
                 prefetch_nvme, ...):
三个旋钮各管一件事：prefetch_bucket_size：本层还在算，下一层的 all-gather 已经发出去——通信躲在计算后面；max_reuse_distance：参数复用（如 tied embedding 与 output layer 共享权重）时，距离近就先不还，省一次 fetch；max_live_parameters：借出的总量上限，防止「要的太多同时借出」把显存挤爆——这是 ZeRO-3 显存峰值的主要决定项。三者默认值都是「层大小 × 若干倍」量级，通常不用动；改变它们的行为就是改变 ZeRO-3 的性能曲线。
图 8.1：借还流水。prefetch 提前一层、all-gather 异步飞行，等第 i 层算完，第 i+1 层参数刚好完整落位。若 prefetch 桶太小，流水断档，前向变成「算一层等一层」。

fetch 与 prefetch 的区别：fetch（forward/backward hook 触发）是同步的——参数必须到位才能算；prefetch（前一层开始算时提前触发）是异步提交，等计算需要时再等待完成。事件名（FORWARD_FETCH_SUBMIT / FORWARD_FETCH_WAIT 等）是 DS 性能分析时的锚点。独立 allgather_stream 是为了不让通信阻塞计算 stream 的 kernel 排队。
演化痕迹（2026-09 修复） 合批路径 _allgather_params_coalesced（partition_parameters.py:2004）曾有一个隐蔽 bug：逐参数发起异步 all-gather 后只等最后一个 handle 就把 param.data 指向结果缓冲——前面的 all-gather 还在飞行，读到的就是未初始化内存（表现为 denormal 垃圾值、参数莫名 NaN）。修复（#8539）是等完全部 launch_handles 再改指向。教训值得记一辈子：提交了 N 个异步操作、只同步最后一个，其余 N−1 个处于无主状态——「异步提交、同步等待点要数清楚」这句话在 DS 源码里是有尸检报告的。

8.3参数在 __init__ 里就被切走

总管的借还动作最终要挂到模型上——挂在哪里才能做到用户模型代码一行不改？答案是 PyTorch 的模块 hook：

deepspeed/runtime/zero/parameter_offload.py — hook 注册（摘录，译注）
pythondef setup_zero_stage3_hooks(self, module):
    # 对每个叶子 sub_module 挂 pre/post forward/backward 四个 hook
    def _pre_sub_module_forward_function(sub_module):
        param_coordinator.fetch_sub_module(sub_module)   # 借参数
    def _post_sub_module_forward_function(sub_module):
        param_coordinator.release_sub_module(sub_module) # 还参数
    for sub_module in module.modules():
        if has_parameter(sub_module):        # 只挂有参数的叶子
            sub_module.register_forward_pre_hook(...)
            sub_module.register_forward_hook(...)
hook 即借还点：ZeRO-3 不改模型代码——借还挂在 PyTorch 的 forward pre/post hook 上。每个有参数的叶子模块，进之前 fetch、出之后 return。这意味着 ZeRO-3 对模型结构的要求：参数必须挂在「模块的直属 _parameters」上，用户自己把参数藏在 list/dict 里（不在 register_parameter 里）会被漏掉——这是 ZeRO-3 的经典报错来源（persistent/leaf 参数问题，见下）。
deepspeed/runtime/zero/stage3.py — step()（结构摘录，译注）
pythondef step(self, closure=None):
    # ① 梯度归约完成、参数全部归位（partition_all_parameters）
    self._pre_step()
    # ② 溢出检查：fp16 梯度 any NaN/Inf → 全组跳过
    if found_inf: return
    # ③ 子组循环：每组（参数组的一段分片）单独走完全流程
    for sub_group in self.fp16_groups:
        self._prepare_sub_group(sub_group)          # 取回本组分片
        self.unscale_and_clip_grads(...)            # 去 loss scale + GAS 均值
        self._optimizer_step(sub_group)             # 更新 fp32 分片
        self._reassign_or_swap_out_partitioned_parameters(sub_group)  # 写回 fp16
        self._release_sub_group(sub_group)          # 释放，下一组
子组循环的意义：不是「全部参数取回 → 一次 step → 全部还回」，而是每组取回→更新→写回→释放——任一时刻 GPU 上最多只有一组的完整参数。显存峰值进一步压低，代价是更多次小 all-gather（幸好子组间还能与通信重叠）。unscale_and_clip_grads 同时做两件事：去 loss scale、除 GAS（两库在这一步的语义一致——scale 与 GAS 均值都在优化器侧撤销，第 6 章 6.3 的边界在引擎侧）。

8.4哪些模型写法会出事

子组循环的 step 写法见上一节——它把「同时借出的参数量」从全模型压到一组；但 hook 自动化有前提，模型的写法必须让 hook 找得到参数。四个疑难场景：

  • 参数没被切到（显存异常高）：参数没挂进 register_parameter，hook 漏掉 → 检查模型写法。
  • fp32 小参数：极小的参数（如若干 bias）逐个 all-gather 不划算，DS 允许保留不分片（stage3_max_parameters_per_partition 不适用，看 prescale_unscale 相关分支），过小参数留在 fp32。
  • tied weights：两处引用同一 Parameter，切分时只认一个 owner；reuse distance 之内不还，否则两边各自 fetch。
  • 非训练参数（buffers）：不参与切分，各卡全量——模型大 buffer 多时这里反而是浪费。

8.6小结 + 自研启示

到这里，ZeRO-3 的全貌可以串起来了：借还总管是 PartitionedParameterCoordinator，三个旋钮分别控制 prefetch 提前量、复用不还的临界距离、同时借出的显存上限；参数在 __init__ 里就被切走，借还挂在 forward pre/post hook 上，模型代码零改动；step 用子组循环把「同时借出的参数」从全模型压到一组，显存峰值随子组大小下降。而这套自动化有个前提——参数必须挂进 register_parameter，藏在 list/dict 里的参数 hook 找不到，会以 NaN 或显存异常的方式静默出错。生命周期归拢成一张表：

阶段动作代码位置
init遍历叶子模块，参数切分、留 ds_tensor 分片InsertPostInitMethodToModuleSubClasses
forward pre-hookfetch_sub_module（all-gather 完整参数）partitioned_param_coordinator.py
forward post-hookrelease_sub_module（还参数）同上
step子组逐个取回→更新→写回→释放stage3.py step()
自研启示 自研 ZeRO-3 的最小正确路径：不用 hook，先用显式上下文管理器（with gather(params): ...）手写借还——语义清楚、方便调试，跑通后再自动化成 hook；prefetch 做成「提前一层」而非「提前一层+复用分析」，先跑对再跑快；显存峰值盯 max_live_parameters，通信时长盯 all-gather 完成事件。最容易错的三点：借出参数忘记释放（显存线性涨到 OOM）、梯度写到了壳 param 的 .grad 上（应该在分片缓冲）、leaf 参数在 hook 外被直接访问（拿到的是空壳，静默产出 NaN）。
