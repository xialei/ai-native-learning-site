Kernel 层：并行框架底下的算子竞赛

前面章节讲的都是「怎么切」；切完之后每个小 GEMM 的效率由算子决定。两库都在框架底下维护了自己的 kernel 层：Megatron 走「融合算子 + TransformerEngine fp8」，DeepSpeed 走「csrc 自研 kernel（transformer/adam/aio）」。这一章盘点两边的家底，并给出「哪些值得自研抄、哪些直接用现成」的判断。

11.1为什么融合：内存带宽的账

一个 bias+GELU 若分开算，读两遍写两遍中间张量；融合后只读写一遍。激活函数融合省的不是计算，是显存往返：

  • LLM 的 GEMM 是计算密集（tensor core 打满）；其间的 LN/激活/dropout 是带宽密集——kernel 启动 + 显存往返占比高。
  • 融合的甜点区：把「带宽密集的小算子」并进相邻计算或彼此并成一个大 kernel，减少 launch 次数与中间张量。
  • scale 项：s×b×h×层×序列中间张量，每省一次往返就省一次全量读写。
判断标准 看 kernel 是否「拉满 tensor core」：GEMM 类不用管（cuBLAS/cuBLASLt 已极致）；LN+激活+dropout+残差这类元素级算子才值得融合——这也是两库融合清单的共同形态。

11.2Megatron：core/fusions/ 与 TransformerEngine

megatron/core/fusions/ — 融合算子清单（目录盘点）
textmegatron/core/fusions/
├── fused_softmax.py            # 缩放+mask+softmax 一体（scale_mask_softmax）
├── fused_bias_swiglu.py        # bias + swiglu 融合（C++/CUDA，autograd 配对）
├── fused_bias_gelu.py          # bias + gelu 融合（forward/backward 各一 kernel）
├── fused_cross_entropy.py      # 词表投影后的并行 cross-entropy，不落地全量 logits
├── fused_layer_norm.py         # LN 融合（TE 之外的非 TE 路径）
├── fused_bias_dropout_add.py   # 残差段三合一：bias+dropout+residual add
└── __init__.py
清单读法：七个文件全在「带宽密集区」——softmax、激活、LN、残差、cross-entropy，没有一个 GEMM。这就是 11.1 判断标准的落地。每个融合算子都是 forward/backward 两个 kernel + autograd 配对（与第 3 章 f/g 的做法同构：通信/融合进 autograd，用户层无感）。TransformerEngine（TE）是更外的一层：NVIDIA 维护的库，提供 TEColumnParallelLinear 等「并行感知 + fp8 管理」的算子族（第 5 章 5.1 的 TELayerNormColumnParallelLinear 就来自它）。TE 的 fp8 路径做三件事：当前 scale 的动态调整、GEMM 输入输出量化、与延迟缩放的联调（fp8 需要按张量尺度管理，比 fp16 的全局 loss scale 细得多）。

11.3DeepSpeed：csrc/ 的三大家当

deepspeed/csrc/ — 自研 kernel 盘点
textdeepspeed/csrc/
├── transformer/               # 推理/训练 transformer kernel：attn/ln/gelu 融合
│   └── (ds_attention, bias_gelu, ...)   # 与 Megatron fusions 同思路、独立实现
├── adam/                      # GPU fused Adam（第 6 章 _take_model_step 调用）
│   └── (multi-tensor Adam：多参数组一次 kernel，减少 launch)
├── cpu_adam/                  # 第 9 章的 CPU 侧 SIMD Adam
├── aio/                       # 第 9 章的 DeepNVMe 异步 IO
├── quantizer/                 # 量化搬运（低精度 offload 的带宽减半）
└── csrc 通用（cpu_lion, ragged 等）
两库家底的形态对比：Megatron 的 fusions 服务「训练前向/反向的热路径」，DS 的 csrc 服务「训练周边（optimizer、IO、offload）+ 推理 kernel」——各自补自己主打场景的短板。共同点：multi-tensor / multi-param 的 batch 化（一次 kernel 处理多个参数张量，减少 launch 开销）——DS 的 fused Adam 与 Megatron 的分布式 optimizer 步进都受益于此思路。

11.4哪些值得抄，哪些直接用

类别建议理由
GEMM直接用 cuBLAS/cuBLASLt 或 TE自研打不过厂商库
注意力直接用 FlashAttention / TE同样打不过，且变长支持复杂
LN+激活+残差融合值得抄思路（简单、收益明确）元素级 kernel，C++/Triton 一天能写
Fused optimizer值得抄（multi-tensor batch 化）launch 开销是 optimizer 热路径大头
异步 IO / offload直接用 DS 的 DeepNVMe调优过的 libaio 封装，重写不经济
fp8 量化调度直接用 TEscale 管理的状态机深，别自己碰
自研启示 kernel 层的自研纪律：先 profile 再动手——nsight 里看到 launch gap 或带宽打满才值得写融合；GEMM 与注意力的时间占比决定了自研 kernel 的天花板（通常 < 40% 时间在元素级算子上，融合的全部收益在这 40% 里）。最容易错的三点：融合 kernel 的 backward 忘了与 forward 配对（autograd 断链静默错）、用了 fp16 累加（元素级 kernel 应 fp32 累加）、融合边界跨了 TP 通信（第 10 章同款坑）。
