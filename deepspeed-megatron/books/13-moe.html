MoE：专家并行与 token 的往返

MoE 参数量乘 N、计算量不变——代价是什么，token 的往返通信怎么构成？一个 token 的四段旅程（route→dispatch→compute→combine）在代码里各对应什么，router 的四个中间量叫什么名字？负载均衡 aux loss 为什么用「未截断的 scores」算？DS 的 residual MoE 是另一条什么路？

13.1token 怎么找到自己的专家

MoE 把 FFN 换成 N 个专家、每个 token 只走 top-k 个。参数量乘 N、计算量不变——但前提是 token 能被送到专家所在的卡上，而 MoE 的代价也全藏在这个「送」字里。一句话结论先放这：MoE 的代价全在 token 往返——dispatch/combine 两次 all-to-all 是通信大头，EP 与 DP 共卡时带宽预算要一起算。下面顺着 token 的旅程看。

一分钟版本

MoE 层的一个 token 的旅程：

  1. route：router（一个小线性层 + softmax）给每个 token 算出 N 个专家的得分，选 top-k。
  2. dispatch：token 按目的地重排（permute），跨卡发送到专家所在 rank（all-to-all）。
  3. compute：各专家在自己的卡上处理分到的 token（就是普通 MLP，EP 内部还可以再 TP）。
  4. combine：结果按原位重排（unpermute）送回，与 k 个专家的输出加权求和。
EP 与 DP 的纠缠 专家是「参数的另一种切法」：普通 FFN 参数每个 DP 副本都有一份，专家参数被 EP 组瓜分。EP 组通常取自 DP 组（num_experts ≤ DP×EP），所以 MoE 训练里「DP 卡」同时是「EP 卡」——token 的 all-to-all 和数据的 DP 归约共享同一批卡，带宽预算要一起算。

13.2MoELayer 的四段流水

一分钟版本里的四段旅程，在 MoELayer.forward 里依次展开——

megatron/core/transformer/moe/moe_layer.py — MoELayer.forward（结构摘录，译注）
pythondef forward(self, hidden_states):
    # ① route：router 打分 + top-k 选择 → probs + routing_map
    scores, routing_map = self.router(hidden_states)
    # ② dispatch：按专家重排 token，跨卡 all-to-all（dispatcher 多态）
    dispatched, tokens_per_expert = self.token_dispatcher.token_permutation(
        hidden_states, scores, routing_map)
    # ③ compute：各专家自己的 MLP（专家内部可再 TP）
    expert_output, mlp_bias = self.experts(dispatched, tokens_per_expert)
    # ④ combine：unpermute + 加权合并 + all-to-all 回程
    output, mlp_bias = self.token_dispatcher.token_unpermutation(expert_output, mlp_bias)
    return output, mlp_bias
命名约定值得记：router 的输出链是 logits → scores（softmax 后）→ probs（top-k 后归一）→ routing_map（bool：谁去哪）——读 MoE 源码时抓住这四个名字就不迷路。dispatch 与 combine 是一对（permute/unpermute），dispatcher 决定它们的实现。aux loss（负载均衡）在 router 里算、加进总 loss，不在这四段里。
megatron/core/transformer/moe/router.py — TopKRouter（结构摘录，译注）
class TopKRouter(...):
    # 三种 aux loss（可叠加）：负载均衡 / 路由器 z-loss / 专家间方差
    def routing(self, logits):
        scores = softmax(logits)              # 全专家概率
        # top-k 选择（带/不带 renormalize 两种）
        probs, routing_map = topk_softmax_with_capacity(
            logits, topk, ..., capacity_factor, ...)   # 容量限制在此
        # aux loss 用「无 topk 的 scores」算——这是与主梯度不同的信号
        self.apply_load_balancing_loss(scores, ...)   # save_to_aux_losses_tracker
aux loss 的语义：负载均衡 loss 惩罚「专家间分配不均」——没有它，router 会早期锁死少数专家（富者愈富），其他专家永远得不到训练。注意代码细节：aux 用未截断的 scores（即使某 token 因容量限制没被派去那个专家，均衡信号仍然传递）。capacity_factor 是另一个正交机制：给每个专家设 token 容量上限，超出的 token 丢弃（或走 residual）——它是通信量与训练质量之间的旋钮。
图 13.1：token 的四段旅程。dispatch 与 combine 是一对（permute/unpermute），dispatcher 家族（13.3 节）决定它们的实现；aux loss 在 router 内算，不占这四段。

13.3三种 token dispatcher 家族

dispatch/combine 这对操作用哪种集合通信实现？Megatron 提供三族 dispatcher：

Dispatcher机制适用
AllGather先 all-gather 全部 token，本地算完自己的专家再 reduce-scatter 回去EP=1（专家不跨卡）或小规模
AlltoAlltoken 按目的地跨卡精确发送（两跳：进专家、出结果）标准 EP，生产默认
FlexDispatcher融合 permute 与通信的优化实现（按后端选择）大规模 + 特定硬件栈
通信形状 AlltoAll 的通信量 = 每 token 发往 EP 组内其他卡的部分（top-k 决定）。它与 TP 的 all-reduce 不同：没有求和语义，纯路由——所以无法像 RS/AG 那样与 SP 合并。MoE + TP 时 Megatron 强制开 SP（第 3 章图 3.2 的注），就是为了把 token 路由与激活切分解耦。

13.4DeepSpeed 的 MoE 与 Tutel

DS 的 MoE 是可插拔模块，另外还带两条特色路线：

deepspeed/moe/layer.py — MoE 类（docstring 摘录，译注）
pythonclass MoE(torch.nn.Module):
    """    MoE(MLP): capacity_factor=1.0, top_k=1, ...
        hidden_size, expert_repo_size, ...
        noisy_gate_policy: 'Jitter' | 'RSample' | 'None'

    def forward(self, hidden_states):
        # gate 打分 → expert 计算或 residual 分支
        if self.use_residual:
            # residual MoE：输出 = 原始 FFN + 专家修正项（DeepSpeed 特色）
            output_mlp = self.deepspeed_moe(hidden_states)
            ...
两条特色路线：第一条是 residual MoE——不是替换 FFN，而是在普通 FFN 之上并联一个「专家修正」分支，token 用不完的容量走原路径，对「先训 dense 再改 MoE」的迁移场景友好；第二条是 Tutel——微软的 all-to-all 优化库（自适应分块、与计算重叠的调度），use_tutel: true 一键切换。DS 的 noisy_gate_policy（Jitter/RSample）是 router 的噪声注入策略，与 Megatron 的 aux loss 是「鼓励探索」的两种手段。另有 top2_2nd_expert_sampling 之类的实现细节开关，属于复现论文行为用。

13.5两份实现对照 + 自研启示

token 的旅程串完了：route（本卡打分）→ dispatch（permute + all-to-all 去程）→ compute（专家本地 MLP）→ combine（all-to-all 回程 + unpermute + 加权求和），代价全在中间两跳（图 13.1）。router 那边的命名链 logits→scores→probs→routing_map 值得记住，容量因子在 topk_softmax_with_capacity 处截断；AlltoAll 无求和语义、纯路由，不能与 SP 合并，所以 MoE+TP 强制 SP；负载均衡则各有各的手段——Megatron 的 aux loss（用未截断 scores），DS 的 noisy gate。两份实现放到一张表里对照：

维度Megatron MoEDeepSpeed MoE
架构定位专家是模型内的一等公民（experts 层）MoE 是可插拔模块（包一层 MLP）
dispatcherAllGather / AlltoAll / Flex 三族标准 all-to-all + Tutel 加速
特色机制aux loss 家族 + 容量因子 + EP×TP 组合residual MoE + noisy gate + Tutel
与并行栈关系EP 与 3D 并行完整正交（rank 布局见第 2 章）独立于 Megatron 布局（mpu 插头接入）
自研启示 自研 MoE 的最小正确路径：先做 EP=1 的本地 MoE（router + top-k + 按专家分组 GEMM），验证 aux loss 收敛行为；再上 all-to-all dispatch（dispatch 的正确性测试：EP=1 与 EP=2 在相同 seed 下输出应一致）；容量因子最后加——它引入「丢 token」的非确定性，调试期关掉。最容易错的三点：unpermute 时 k 个专家输出的加权顺序错了（静默数值错误）、aux loss 忘了乘 aux_loss_coeff 就加进主损失（量级失衡）、EP 组 rank 计算复用 DP group（token 发错卡）。
