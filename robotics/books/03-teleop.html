遥操作与数据采集：让人类示范，让机器人记录

模仿学习的数据从哪来？答案是「人类上手演一遍」。这一章拆解 LeRobot 的两条采集链路：lerobot-teleoperate（纯遥操作）与 lerobot-record（遥操作 + 数据落盘），重点是一条节拍严苛的循环和一套可插拔的 processor 流水线。

3.1Teleoperator 基类：动作的「输入源」

第 2 章的 Robot 是动作的出口（send_action）；遥操作设备是动作的入口。两者接口刻意长得像：

src/lerobot/teleoperators/teleoperator.py:29 — Teleoperator 抽象基类（摘录）
pythonclass Teleoperator(abc.ABC):
    # 与 Robot 相同的结构描述约定
    config_class: builtins.type[TeleoperatorConfig]
    name: str

    @property
    @abc.abstractmethod
    def action_features(self) -> dict:
        """输出动作的结构：键与 get_action() 返回一致"""

    @property
    @abc.abstractmethod
    def feedback_features(self) -> dict:
        """力反馈的结构（可空）：键与 send_feedback() 入参一致"""

    @abc.abstractmethod
    def connect(self, calibrate: bool = True) -> None: ...
    @abc.abstractmethod
    def get_action(self) -> RobotAction: ...
    @abc.abstractmethod
    def send_feedback(self, feedback: RobotAction) -> None: ...
    @abc.abstractmethod
    def disconnect(self) -> None: ...
关键不对称：遥操作设备的 get_action() 返回的字典键名必须能对上机器人的 action_features——leader 臂的 "shoulder_pan.pos" 直接就是 follower 臂的 "shoulder_pan.pos"。因为第 2 章说过：所有物理差异（方向反转、零位、量程）已在标定时折算成统一归一化坐标，所以 leader 的关节读数可以原样当作 follower 的目标。这个「归一化对齐」是主从臂遥操作成立的全部秘密。

设备家族一览：

类别实现（teleoperators/ 下）原理
主从臂（leader）so_leader、koch_leader、omx_leader、bi_so_leader、rebot_102_leader同构硬件，leader 臂卸掉扭矩只读位置，follower 臂复现
外骨骼homunculus、openarm_leader穿戴式，关节映射到机械臂
通用输入keyboard、gamepad、phone把按键/摇杆/手机姿态映射成关节增量
整机映射unitree_g1、reachy2_teleoperator人形/整机专用遥操协议
为什么主从臂是主流：键盘/手柄是「增量为动作」，操作者要在大脑里做关节坐标变换，效率低；主从臂是「位姿即动作」，人类肌肉记忆直接复用。代价是要多买一只臂。so_leader 与 so_follower 硬件同构（都是 sts3215 舵机），leader 臂的 bus 只调 disable_torque()（在 SOLeader.configure 里，so_leader.py:128）让关节自由活动，读数即示范动作。

3.2teleoperate：一条节拍严苛的闭环

lerobot-teleoperate 的主循环只有一个 while，但它揭示了所有实时机器人程序共同的骨架——固定节拍的三段式：

src/lerobot/scripts/lerobot_teleoperate.py:193 — 主循环（节选）
pythontimer = CycleTimer(fps, records_data=False)
while True:
    timer.tick()
    loop_start = time.perf_counter()

    with timer.section("observe"):
        obs = robot.get_observation()          # 读 follower 全部关节 + 相机
        if robot.name == "unitree_g1":
            teleop.send_feedback(obs)           # 力反馈设备把状态回传给操作者

    with timer.section("teleop"):
        raw_action = teleop.get_action()        # 读 leader 关节
        teleop_action = teleop_action_processor((raw_action, obs))
        robot_action_to_send = robot_action_processor((teleop_action, obs))

    with timer.section("send"):
        _ = robot.send_action(robot_action_to_send)

    timer.wait()                                 # 睡掉剩余时间，保证固定 fps
    if duration is not None and time.perf_counter() - start >= duration:
        return
逐段读：
  • CycleTimer 是整个循环的节拍器：tick() 打点、section() 记录每段耗时、wait() 把「这一拍用剩的时间」睡掉。循环结束时打印 Teleop loop time: 18.2ms (55 Hz) 这样的自检——掉拍立刻可见。写实时控制程序的第一课：先修好节拍器，再谈功能。
  • obs 在遥操作里其实没被用（注释原话：Not really needed for now other than for visualization）——leader 臂的读数本身就是动作，follower 观测只用于可视化和 processor 链。但在第 11 章的 policy 部署里，同一条循环中 obs 是策略的输入，这个骨架是通用的。
  • 两段 processor：teleop_action_processor（处理「人给的原始动作」）与 robot_action_processor（处理「发给机器人的动作」）——见 3.4。

3.3lerobot-record：在循环里落盘

record_loop（scripts/lerobot_record.py:228）与 teleoperate 的循环同构，只多了三件事：帧构造、写盘、多遥操作设备。先看源码里自带的 ASCII 数据流图——它就是本章的地图：

src/lerobot/scripts/lerobot_record.py:204 — 源码注释中的数据流
python""" --------------- record_loop() data flow --------------------------
       [ Robot ]
           V
     [ robot.get_observation() ] ---> raw_obs
           V
     [ robot_observation_processor ] ---> processed_obs
           V
     [ Teleoperator ]
     |
     |  [teleop.get_action] -> raw_action
     |          |
     |          V
     | [teleop_action_processor]
     |          |
     '--> processed_teleop_action
                               V
                  [ robot_action_processor ] --> robot_action_to_send
                               V
                    [ robot.send_action() ] -- (Robot Executes)
                               V
                    ( Save to Dataset )
                               V
                  ( Rerun Log / Loop Wait )
"""

3.4episode 生命周期：录、停、重置、重录

record()（scripts/lerobot_record.py:381）在循环外面包了一层 episode 编排。一次录制会话由多个 episode 组成，每个 episode 之间穿插不录制的重置阶段：

录制阶段（写帧） 重置阶段（不写帧） 收尾动作 重录 / 退出分支
图 3.4：episode 编排。实线是正常流程，虚线是键盘事件触发的提前退出/重录分支。三个事件标志（exit_early / rerecord_episode / stop_recording）由监听线程置位、控制循环轮询。

配置参数（DatasetRecordConfig，configs/dataset.py:25）决定了数据的形态：

src/lerobot/configs/dataset.py:25 — DatasetRecordConfig（节选）
pythonclass DatasetRecordConfig:
    repo_id: str = ""            # {hf用户名}/{数据集名}，如 "you/so101_pick"
    single_task: str = ""        # 任务描述，会写进每帧的 "task" 字段
    fps: int = 30
    episode_time_s: int | float = 60   # 每集时长
    reset_time_s: int | float = 60     # 每集间重置时长
    num_episodes: int = 50
    video: bool = True           # 相机帧编码成 mp4（否则存 png）
    push_to_hub: bool = True     # 结束后上传 HF Hub
    num_image_writer_threads_per_camera: int = 4  # 写图线程数，掉 fps 先调这里
两个容易踩的坑：
  • fps 不稳是写盘阻塞主循环：源码注释说得很直白——Too many threads might cause unstable teleoperation fps due to main thread being blocked / Not enough threads might cause low camera fps。图片写入被放进独立线程/进程池（image_writer_processes/threads），调参口诀：先加线程，仍不稳加进程。
  • 「重置」是模仿学习的隐形成本：每一集结束，场景要回到近似初始状态，否则数据集里「同一任务」的初始条件五花八门，策略学不到一致的映射。reset_time_s 60 秒 + 不落盘，就是在为下一集「对齐初始分布」。录制 50 集，实际有一半时间是重置。

3.5Processor 流水线：动作/观测的「可插拔中间件」

循环里反复出现的 xxx_processor 是 LeRobot 3.x 的关键扩展点。它是对 EnvTransition（观测+动作+奖励+done 的字典）做变换的步骤序列：

src/lerobot/processor/pipeline.py:150 — ProcessorStep 抽象（摘录）
pythonclass ProcessorStep(ABC):
    def __call__(self, transition: EnvTransition) -> EnvTransition:
        """对一条 transition（obs/action/reward/done…字典）做原地变换"""

预置步骤都在 processor/ 下，各自剪裁一件事：

Processor职责在哪一章还会见到
identity_processor（IdentityProcessorStep，pipeline.py:2120）默认空操作（遥操作/录制默认链就是它）—
normalize_processor（NormalizerProcessorStep，normalize_processor.py:426）按数据集 stats 归一化/反归一化动作与观测第 5 章策略输入、第 11 章部署
delta_action_processor绝对位置 ↔ 增量动作互转第 11 章 rollout
device_processor（DeviceProcessorStep，device_processor.py:36）张量搬进/搬出 GPU第 6 章 VLA 推理
tokenizer_processor（TokenizerProcessorStep，tokenizer_processor.py:58）语言指令 → tokenizer 输入第 6-7 章 VLA
相机帧的处理不在 processor 链上：resize / 归一化等图像变换由数据集层的 ImageTransforms（transforms/transforms.py:700）在 __getitem__ 里做（第 4 章），processor 链只管 observation/action 张量的搬运与变换——这条分界在排查「图像没被 resize」时很有用。
为什么这个设计重要：录制时用一条 processor 链（决定数据格式），部署时用反向一条（决定策略输入输出格式）——两边的格式约定不再硬编码在脚本里，而是数据集和 checkpoint 一起保存、一起加载。策略从 A 机器人迁到 B 机器人时，换 processor 而不是改代码。这与第 4 章数据集 features 的设计一脉相承：格式即元数据，元数据随数据走。

3.6小结与自建采集系统的清单

概念lerobot 实现你自己做时
输入源抽象Teleoperator.get_action() → 与机器人 action_features 同键位输入源与执行端用同一套归一化坐标，杜绝单位换算散落各处
节拍控制CycleTimer.tick/section/wait + 掉拍自检打印先建节拍器与耗时统计，实时性问题 90% 是节拍被 IO 阻塞
写盘解耦图像线程池（4 线程/相机）+ 视频批量编码 VideoEncodingManager落盘永远异步；编码放到 episode 结束或后台
episode 编排录/重置交替 + 键盘事件（n/r/q）+ save_episode 落定把「重置」当一等公民设计；数据质量取决于初始条件对齐
可插拔变换RobotProcessorPipeline，录制链与部署链互逆格式变换写成中间件，随数据集/checkpoint 持久化
一句话记住：数据采集不是「录视频」，是以固定节拍把「观测-动作」对齐成帧，并在人手松开的那一刻还知道哪一帧属于哪个任务。节拍（fps）、帧（frame）、任务标签（task）三样齐了，才是一份能训练的数据。
