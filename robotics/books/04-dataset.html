LeRobotDataset：机器人数据的通用容器

NLP 有 Text，CV 有 ImageNet，机器人学一直没有等价物——直到各实验室自创格式互不相通。LeRobotDataset 用「parquet + mp4 + 元数据」把异构机器人数据统一成一种能放 Hub、能流式读、能直接喂策略的格式。这一章从目录结构读到 __getitem__，读完你就知道一份训练数据到底由什么构成。

4.1目录结构：一切按 chunk 分片

先约定全书最重要的数据单位——episode：机器人从头到尾做完一次任务的一段连续记录（比如「抓起方块→放进盒子」的 30 秒），包含这段时间所有的相机帧和关节读数。一个数据集就是许多 episode 的集合——对应视频里的「一集」。v3.0 格式的磁盘布局由一组路径模板决定（src/lerobot/datasets/utils.py:89-149）：

src/lerobot/datasets/utils.py — v3.0 布局常量（节选）

为什么要分片（chunk）：50 集 × 60 秒 × 30fps ≈ 9 万帧，全塞一个 parquet/一个 mp4 既难流式读、又超出上传工具的单文件习惯。v3.0 按「每 1000 个文件或 100/200 MB」滚动开新文件，chunk_index/file_index 两级寻址让数据集可以无限增长而文件数保持可控。Hub 上的下载也按需拉取单个 chunk——这是「数据集即仓库」的工程基础。

命名约定就是接口约定：observation.state / observation.images.* / action / task 这几个键名贯穿数据集 → DataLoader → 策略 forward → 异步部署协议（第 11 章 gRPC 的 Observation 消息同样按此组织）。dtype 还区分 "video" 与 "image"（utils/feature_utils.py:92 的 dtype = "video" if use_video else "image"）：前者按时间戳从 mp4 解码，后者按文件读 png——同一套代码透明处理两种存储。此外每帧自动带五个标准列：index、episode_index、frame_index、timestamp、task_index（dataset_writer.py:223 自动补齐）。

4.3写入路径：add_frame 与 save_episode 的分工

LeRobotDataset 有两种模式：写模式（create/resume）与读模式。第 3 章录制时走的写路径，核心是两个方法：

src/lerobot/datasets/lerobot_dataset.py:475 / dataset_writer.py:213 — add_frame（节选）
pythondef add_frame(self, frame: dict) -> None:
    """加入当前 episode 缓冲区。除图片临时落盘外，什么都不写。"""
    for name in frame:
        if isinstance(frame[name], torch.Tensor):
            frame[name] = frame[name].numpy()

    validate_frame(frame, self._meta.features)   # schema 校验：键齐、形状对
    if self.episode_buffer is None:
        self.episode_buffer = self._create_episode_buffer()

    # frame_index 与 timestamp 自动补齐——调用方不用管节拍
    frame_index = self.episode_buffer["size"]
    timestamp = frame_index / self._meta.fps
    self.episode_buffer["frame_index"].append(frame_index)
    self.episode_buffer["timestamp"].append(timestamp)
    self.episode_buffer["task"].append(frame.pop("task"))
    ...
src/lerobot/datasets/lerobot_dataset.py:491 — save_episode
pythondef save_episode(self, episode_data: dict | None = None, parallel_encoding: bool = True) -> None:
    """把缓冲区落盘：编码视频、写 parquet、更新元数据，然后清空缓冲区。"""
    self._require_writer("save_episode")
    self.writer.save_episode(episode_data, parallel_encoding)
这个分工是「实时性」与「完整性」的折中：add_frame 在 30 Hz 循环里被调用，所以它只做校验 + 追加内存数组（相机帧先以 png 丢进临时目录，由第 3 章的写盘线程池异步处理）；save_episode 在 episode 结束才跑，做所有「贵」的事——视频编码（可并行，parallel_encoding）、parquet 写出、meta 计数器更新。录制循环里的任何一次 add_frame 都不该阻塞超过几毫秒，这是 3.2 节 fps 稳定的前提。若某集录坏了，clear_episode_buffer 直接丢弃缓冲（3.4 的 r 键）。

4.4读取路径：__getitem__ 与 delta_timestamps（重点）

训练时 DataLoader 每次要的不只是「当前帧」——策略要历史观测 + 未来动作块（action chunk）。这是靠 delta_timestamps 实现的：

src/lerobot/datasets/lerobot_dataset.py:53 — 构造时传入 delta_timestamps（摘录 docstring）
pythondelta_timestamps: dict[str, list[float]] | None = None
# 例：观测取过去 2 帧（-0.1s、-0.05s、0s），动作取未来 0.5 秒的动作块
# {
#   "observation.state": [-0.1, -0.05, 0.0],
#   "action": [t / fps for t in range(50)],   # 30fps 下 ≈ 未来 1.67 秒
# }
# 每个 key 是相对当前帧的时间偏移列表；数据集负责把这些偏移换算成
# 绝对索引、越界裁剪、并从视频解码对应帧。

def __getitem__(self, idx: int | slice) -> dict | list[dict]:
    """返回一帧（或切片），所有变换已应用：delta-timestamps 展开、
    视频解码、图像变换。核心逻辑委托给 DatasetReader。"""
    return self._ensure_reader().get_item(idx)
时间轴 / 单帧 当前帧 t 被取进样本的帧
图 4.4：delta_timestamps 把「单帧样本」变成「时间窗样本」。观测往回看，动作往前看——这正是第 5 章 ACT / 第 6 章 flow matching 输出 action chunk 的数据基础。注意两边的 delta 都含 0：观测的 0.0 就是当前帧，动作的 0 则是 chunk 的第一个目标（ACT 的 action_delta_indices 是 range(chunk_size)，不跳过当前帧）。
为什么 action chunk 如此重要：单步动作预测会让误差逐帧累积（分布漂移：模型见过自己的错误状态后不知道怎么办）。输出一整段动作再执行，相当于把「决策频率」降到 chunk 长度的倒数，给模型留了抗漂移的缓冲。数据集用 delta_timestamps 支持它，策略接口（第 5 章 predict_action_chunk）暴露它，部署层（第 11 章 action queue）消费它——三处串成一条线。

4.5stats.json：归一化从这里来

第 2 章标定解决了「跨机器坐标统一」，但不同特征量纲仍差几个数量级（夹爪 0-100，关节 ±100，图像 0-255）。训练前的归一化不能临时算——必须落盘成元数据，让推理时能精确反变换：

pythonclass RunningQuantileStats:
    def __init__(self, quantile_list: list[float] | None = None, num_quantile_bins: int = 5000):
        ...  # 直方图近似分位数：一遍扫完百万帧也算得动

    def update(self, batch: np.ndarray) -> None: ...
    def get_statistics(self) -> dict[str, np.ndarray]:
        ...  # {count, min, max, mean, std, q01, q10, q50, q90, q99} 每个特征一份
读法：save_episode 时先对这一集算一遍（dataset_writer.py:322/324 的 compute_episode_stats），再与已有统计聚合（dataset_metadata.py:677 的 aggregate_stats），最后整体写进 meta/stats.json（:678 write_stats）。所以是增量累积，不是每存一集就把全量数据重扫一遍。min/max 分位数（q01/q99）用来抗离群值——直接用全局 min/max 会被一帧「关节飞了」的坏数据毁掉归一化。训练时 processor 链（3.5 的 normalize_processor）读取 stats 把输入压到 [-1,1]；部署时同一份 stats 从 checkpoint 加载，把策略输出反归一化回真实关节量。数据集的 stats 与模型权重必须配套——它们是同一个「坐标系」的两半。
延伸 Hugging Face 生态里官方数据集（如 lerobot/aloha_sim）都是这个格式，LeRobotDataset("lerobot/aloha_sim") 一行代码即下载即用。push_to_hub（lerobot_dataset.py:619）会上传全部文件、生成数据卡，并打上 codebase_version 标签——加载端据此校验格式兼容性，v2.1 旧数据会提示用 convert_dataset_v21_to_v30 迁移（utils.py 的 V30_MESSAGE）。

4.6LeRobotDataset 对比 Isaac Lab 的「数据从哪来」

真机数据贵（50 集 = 一个人一天），仿真数据便宜（4096 个并行环境同时跑）。两条线的数据格式在 LeRobot 栈里是统一的：

真机（lerobot-record）仿真（Isaac Lab，第 9-10 章）
数据来源遥操作示范（人）RL 探索或运动规划（脚本）
帧率30 fps 固定节拍sim.dt=0.01 × decimation=2 → 50 Hz 控制
每帧内容state + 相机 mp4 + action + task观测张量（joint_pos/object_position…）+ reward
数量级几十~几百集百万步/小时（4096 envs 并行）
用途模仿学习（第 5-7 章）RL 训练、域随机化数据（第 10 章）
汇合点都能转成 LeRobotDataset → 都能喂 SmolVLA/π0 训练（第 6-7 章）
一句话记住：LeRobotDataset 的设计把「机器人数据」变成了「可版本管理、可流式读取、可跨策略复用」的一等公民。理解了它的 schema（4.2）与 delta_timestamps（4.4），后面所有策略章节的输入输出就都有了坐标参照。
