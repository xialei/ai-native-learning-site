Sim2Real：把策略安全地放到真机上

前两章在仿真里练出了策略，本章解决「下真机」的三道坎：一是差距本身（actuator 延迟、传感器噪声——靠第 10 章的域随机化提前覆盖）；二是推理时延（VLA 推理 100ms 起，机器人等不起——靠 action chunk + 异步推理）；三是工程集成（策略跑在工控机、机器人只有 MCU——靠 gRPC 把两边连起来）。lerobot 的 async_inference 栈是第三个问题的完整参考实现，我们逐行走读。

11.1差距清单与缓解手段

差距仿真里真机上缓解
执行器动态ImplicitActuator 指令即达电机延迟、力矩饱和、摩擦DelayedPDActuator（8.5）、DR 随机化刚度/阻尼
感知enable_corruption 高斯噪声相机曝光/色偏、深度空洞随机化光照纹理；真机数据微调（第 4 章数据）
物理保真刚体近似、接触求解误差形变、间隙、绳缆系统辨识 + DR 组合（10.6）
控制频率精确 50Hz 时钟推理抖动、网络抖动本章主角：action chunk + 异步推理
为什么 chunk 是 sim2real 问题：第 5 章说过 ACT 一次输出 100 步动作、SmolVLA 50 步——设计动机正是掩盖推理延迟：推理期间机器人照常执行队列里的旧动作，视觉上无缝。但「旧动作」基于旧观测，执行越久偏差越大——所以实际是「队列消费新观测补块」的循环，时序设计见 11.3。

11.2架构：gRPC 双服务

lerobot 的 transport 层定义了两个 gRPC 服务（transport/services.proto:28-45）——一个是「远程大脑」，一个是「在线学习」：

lerobot/src/lerobot/transport/services.proto — 两个服务的接口
proto// LearnerService：Actor→Learner 推 transition（在线 RL / 从示范学习用）
service LearnerService {
  rpc StreamParameters(Empty) returns (stream Parameters);   // 参数下发
  rpc SendTransitions(stream Transition) returns (Empty);    // 经验回传
  rpc SendInteractions(stream InteractionMessage) returns (Empty);
  rpc Ready(Empty) returns (Empty);                            // 客户端握手
}

// AsyncInference：机器人把观测流给远端 Policy 服务器，换回动作块
service AsyncInference {
  rpc SendObservations(stream Observation) returns (Empty);  // 机器人 → 策略
  rpc GetActions(Empty) returns (Actions);                  // 策略 → 机器人
  rpc SendPolicyInstructions(PolicySetup) returns (Empty);  // 下发任务与策略参数
  rpc Ready(Empty) returns (Empty);                            // 客户端握手（服务器在此重置状态）
}
读法：观测用 stream（图像序列可能超 gRPC 4MB 单消息上限，按 TransferState BEGIN/MIDDLE/END 分块）；动作回传用一元 RPC——一次取回整个 action chunk（pickle 序列化的 TimedAction 列表）。策略支持白名单在 constants.py 的 SUPPORTED_POLICIES：["act", "smolvla", "diffusion", "tdmpc", "vqbet", "pi0", "pi05", "groot"]——正是第 5-7 章讲过的策略家族；机器人侧白名单是 so100/so101 等 follower（不过这条客户端校验目前被注释掉了，实际不强制）。第 10 章的 RL checkpoint 不走这条路——rsl_rl 的 play.py 直接本地加载；要包装成 policy 插件上服务，除了注册配置类，还得把名字加进这个硬编码列表，因为服务器校验的是它（policy_server.py:130），不是 draccus 注册表。锚点：白名单 constants.py:26/:29、客户端校验注释 robot_client.py:501-503。

11.3三个精妙的工程细节

① must-go 观测直通（robot_client.py:440-450）。正常情况下队列还有存货时，新观测发上去也不急着推理（服务器会因「与上次太相似」跳过）。但若队列恰好空了且保险丝处于复位态（must_go.is_set()）——机器人面临「无动作可执行」的停摆风险——这条观测才被标记 must_go=True（robot_client.py:442 是这两个条件的与），服务器无条件处理：

lerobot/src/lerobot/async_inference/robot_client.py:441 — 空队列触发直通
pythonwith self.action_queue_lock:
    observation.must_go = self.must_go.is_set() and self.action_queue.empty()
if observation.must_go:
    self.must_go.clear()      # 收到动作块后 receive_actions 再 set 回来 :350
读法：must_go 是一个「保险丝」——队列空 → 观测必达 → 服务器必须产出动作块 → 队列续上。它防的是异步系统最隐蔽的故障模式：观测和处理互相等待、双双饿死。

② 队列聚合（robot_client.py:237-280）。连续两次推理的动作块在时间轴上重叠（新块的前几步对应旧块还没执行完的步）。客户端按 timestep 对齐合并：

robot_client.py:254 — 重叠 timestep 的聚合（节选）
pythonif new_action.get_timestep() <= latest_action:
    continue                        # 已执行过的动作，直接丢弃
elif new_action.get_timestep() not in current_action_queue:
    future_action_queue.put(new_action)      # 纯新增，直接入队
else:
    # 新旧块在同一 timestep 都有动作 → aggregate_fn 融合
    future_action_queue.put(TimedAction(..., action=aggregate_fn(
        current_action_queue[new_action.get_timestep()], new_action.get_action())))
读法：融合函数从注册表里按名字取（aggregate_fn_name），默认是 weighted_average（0.3·旧 + 0.7·新），可换成 latest_only（直接取新）、average（各半）、conservative（0.7 旧 + 0.3 新）。注意 robot_client.py 里还有一个「未传 aggregate_fn 就取新动作」的兜底分支，但正常路径是 config 构造时把 aggregate_fn_name 解析成函数再传进来，所以走不到那个兜底——别把它当成默认行为。weighted_average 即第 5 章 ACT 时序集成的「网络版」。两条队列融合线路在此汇合：本地策略的队列消费 + 远程策略的队列聚合，本质都是「怎么优雅地用新预测覆盖旧预测」。锚点：注册表 async_inference/configs.py:29-34、兜底分支 robot_client.py:243-246、解析点 configs.py:182。

③ 服务器侧省推理（policy_server.py:268-284）。观测入队前两道体检：timestep 已预测过 → 跳过；与上次预测的观测在关节空间距离 < atol=1（observations_similar，helpers.py:281）→ 跳过。机器人静止或缓慢移动时，服务器不重复推理——这份省下来的算力让单个 GPU 服务一台机器人时余量充足（目前一个 policy_server 同时只服务一个客户端）。

11.4两条部署路径对比

路径 A：本地推理路径 B：异步远程推理
策略在哪与机器人同一台机器（笔记本/工控机）远程 GPU 服务器
适用策略ACT、Diffusion（小，CPU/边缘 GPU 可跑）SmolVLA、π0（大，需要 GPU 服务器）
延迟构成纯推理时间推理 + 网络 RTT + 序列化
队列机制policy.select_action 内部队列（第 5 章）客户端 action_queue + 聚合（本章）
多机器人一机一策略一次服务一个机器人客户端（观测体检去重；新客户端连入会先清空服务器队列，:100-111）
代码入口lerobot-record / python 推理脚本async_inference/{policy_server,robot_client}.py
选型口诀 策略推理时间 < 控制周期 → 本地最简单；推理时间 > 控制周期（VLA 几乎总是如此）→ 要么靠 chunk 掩盖（本地大 chunk），要么上异步栈（远程 GPU）。两条路都靠「队列」把不稳定延迟摊平。

11.5仿真策略与真机栈的汇合

把全书的线收拢：第 10 章 rsl_rl 训出的 RL 策略（MLP，低维观测）可以直接 play.py 回放到真机吗？不行——中间还隔着第 2 章的硬件抽象：仿真里的 JointPositionAction 目标要翻译成 Feetech 电机的 goal_position（02 章 MotorsBus），观测要从相机帧 + 电机读数构造出与仿真一致的向量。工程上常见做法：

①直接移植：把 Isaac Lab 的 obs/action 归一化参数导出成 lerobot processor（第 4 章的 dataset stats、第 5 章的 preprocessor/postprocessor 管道），RL 策略注册为 PreTrainedPolicy 子类——白名单以外的策略通过 @PreTrainedConfig.register_subclass 插件机制接入——注意注册的是策略的配置类（如 ACTConfig，policies/act/configuration_act.py:22），策略本体再按 configuration_* → modeling_* 的命名约定被 factory.py 解析出来。

②蒸馏成 VLA 数据：仿真策略当「老师」在 Isaac Lab 里跑成功 rollout，用 RecorderManager（9.2 节）录成 HDF5 数据集，再用转换脚本（如 scripts/imitation_learning/locomanipulation_sdg/gr00t/convert_dataset.py）转成 LeRobotDataset——再把 VLA（第 6-7 章）当「学生」在这些数据上模仿学习。学生上位后自带视觉泛化，老师负责量产数据。

第 11 章是全书的「汇合点」：仿真线（8-10 章）的产出与真实线（2-7 章）的产出，最终都要通过本章的部署栈变成机器人的动作。12 章的路线图会把两条线串成六个里程碑。
