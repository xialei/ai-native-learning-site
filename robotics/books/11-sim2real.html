Chapter 11 · Sim2Real

Sim2Real：把策略安全地放到真机上

前两章在仿真里练出了策略，本章解决「下真机」的三道坎：仿真和真机差在哪、各靠什么缓解；VLA 推理 100ms 起机器人等不起，时延怎么藏；策略跑在工控机、机器人只有 MCU，两边怎么连。lerobot 的 remote_inference 栈是第三个问题的完整参考实现。

这一章是全书两条线（真机线第 2-7 章、仿真线第 8-10 章）的汇合点——仿真练出的策略和真机采的数据在这里会师。

11.1① 差距清单与缓解手段

差距仿真里真机上缓解
执行器动态ImplicitActuator 指令即达电机延迟、力矩饱和、摩擦DelayedPDActuator（8.5）、DR 随机化刚度/阻尼

控制频率精确 50Hz 时钟推理抖动、网络抖动本章主角：action chunk + 异步推理
为什么 chunk 是 sim2real 问题：第 5 章说过 ACT 一次输出 100 步动作、SmolVLA 50 步——设计动机正是掩盖推理延迟：推理期间机器人照常执行队列里的旧动作，肉眼看不出停顿。但「旧动作」基于旧观测，执行越久偏差越大——所以实际是「队列消费新观测补块」的循环，时序设计见 11.3。

11.2② 架构：Zenoh 远程推理

第二个问题（时延）在 11.1 已经点名 chunk 与异步，第三个问题（集成）则要选通信架构。lerobot 的 remote_inference 栈用 Zenoh（面向机器人的 pub-sub 中间件）替换了旧 gRPC 方案：观测是单向发布（不需要「问」服务器拿动作，动作块由服务器主动推回），每条消息是 MessagePack 编码的定长信封（Envelope，带版本号与请求 ID，protocol.py:23），序列化尺寸有硬上限，超了直接报协议错误而不是截断。机器人侧不加载任何权重——只发观测、执行动作。连接从「发现部署 → 声明能力 → 拿到独占会话」三步开始，每一步都可协商、可失败：

remote_inference/client.py:255 — admit：机器人契约与服务器能力的对照（节选）

11.3②（续）三个精妙的工程细节

① 饿死宽限与位置保持（execution.py:265）。新栈把「队列空了怎么办」从赌运气变成有界等待：30 Hz 的插值循环把队列最后一个端点消费完后，不再有 policy 动作可执行——此刻控制线程调 _wait_for_actions，旧运动被吊销（invalidate），机器人保持在最后目标位置（position hold，so100/so101 等机型在硬件层声明支持），同时开一个 action_starvation_grace_s（默认 1.0 秒）的倒计时：

inference/execution.py:265 — _wait_for_actions：饿死宽限
pythondef _wait_for_actions(self) -> None:
    """Revoke exhausted motion without forgetting an outstanding call's deadline."""
    if not self.starvation_grace:
        self.fault("Active motion buffer exhausted")
        return
    self.invalidate(held=True)                       # 旧运动作废，保持姿态
    self.starvation_deadline = self.clock() + self.starvation_grace
    self.wait_events.append({"event": "waiting", "grace_s": self.starvation_grace})
读法：宽限期内一旦新动作块到账，从新观测重新出发（旧轨迹已吊销，避免「新旧拼接」的不连续）；宽限耗尽还没动作 → 终止性故障（fault），机器人受控停机。它防的是异步系统最隐蔽的故障模式：观测和处理互相等待、双双饿死。配套的还有双重时限——推理请求超时 action_timeout_s（默认 5s）与首块启动超时 startup_timeout_s（默认 10s），任何一个超了都是同样的终止处理（execution.py:348-350 的 check_deadlines）。

② 对齐替换与混合（execution.py:531）。新块到达时，它依据的观测已经有点旧了——机器人在这期间执行了旧块的若干步。新栈的默认合并模式 aligned 不做时间戳数值平均，而是用承诺游标（commitment cursor）对齐：每个观测采样时绑定一个队列游标（anchor），新块到达后先剪掉「机器人已经走过去」的前缀，只替换未来：

inference/execution.py:531 — _accept_aligned：裁剪 + 混合（节选）
pythonanchor = request.observation.action_cursor
trim = snapshot.cursor - anchor            # 已提交的步数 = 要剪掉的前缀
if trim < 0 or trim >= len(actions):
    ...  # 没有可用的对齐后缀 → 拒收
future = actions[trim:].clone()
# 重叠窗口内逐分量混合：旧目标 q_t 与新目标 i_t 各占多少由 blend_weight 决定
future[index, coordinates] = (1 - self.blend_weight) * previous[index, coordinates] \
                           + self.blend_weight * future[index, coordinates]
读法：混合公式 blended = q_t + b_w·(i_t − q_t)（blend_weight 默认 0.5，blend_steps 窗口默认关）只作用于尚未提交的未来端点——正在插值中的目标已承诺给电机，谁也不能改。被混合的分量必须显式指定（blend_components，只选连续量如关节角，夹爪这种离散量别混）。旧 gRPC 栈按 timestep 数值聚合、新旧块都保留的做法换成了「剪旧+换新+可选平滑」三段式：先保证不倒退，再谈平滑。锚点：裁剪 execution.py:539、混合 :562-564、游标语义 policies/rtc/action_queue.py:38。

③ 控制线程的门（execution.py:352）。什么时候发起新一轮推理？should_request 在每次采样前问三个问题：队列剩余播放时间（qsize × interval）是否跌破 effective_refill——一个含实测周转时间的自适应水位（max(refill_seconds, turnaround + interval)，:224）；观测是否新鲜（begin 里 age > max_age=5s 直接不发，:386-387）；同一任务下是否已有更新锚点（aligned 模式用 _last_anchor 去重，旧观测的预测不覆盖新锚——:399-406 的比较与记录）。机器人静止时不会拼命发请求：回放余量充足就一根观测都不推理。请求容量为 1（capacity-one executor）：同一时刻只有一个在途推理， turnaround 窗口（最近 100 次采样）反过来校准下次该什么时候问——「问」的节奏从网络状况里学出来，而不是配置拍脑袋。

11.4③ 两条部署路径对比

路径 A：本地推理路径 B：远程推理（remote）
策略在哪与机器人同一台机器（笔记本/工控机）远程 GPU 服务器（同机亦可）
适用策略ACT、Diffusion（小，CPU/边缘 GPU 可跑）SmolVLA、π0（大，需要 GPU 服务器）
延迟构成纯推理时间编码 + 网络 + 排队 + 推理 + 解码（实测为 turnaround，进 refill 水位）
队列机制policy.select_action 内部队列（第 5 章）ChunkRuntime 队列 + 对齐替换 + 混合（本章）
多机器人一机一策略一个服务器进程一个部署、一次一个会话（顺序客户端可复用；并发共享不在设计内）
代码入口lerobot-record / python 推理脚本lerobot-policy-server --config_path=server.yaml + lerobot-rollout --inference.type=remote
选型口诀 策略推理时间 < 控制周期 → 本地最简单；推理时间 > 控制周期（VLA 几乎总是如此）→ 要么靠 chunk 掩盖（本地大 chunk，或 RTC 后端），要么上远程栈（远程 GPU）。三条路都靠「队列 + 有界等待」把不稳定延迟摊平。

11.5④ 仿真策略与真机栈的汇合

最后把全书的线收拢：第 10 章 rsl_rl 训出的 RL 策略（MLP，低维观测）可以直接 play.py 回放到真机吗？不行——中间还隔着第 2 章的硬件抽象：仿真里的 JointPositionAction 目标要翻译成 Feetech 电机的 goal_position（02 章 MotorsBus），观测要从相机帧 + 电机读数构造出与仿真一致的向量。工程上常见做法：

①直接移植：把 Isaac Lab 的 obs/action 归一化参数导出成 lerobot processor（第 4 章的 dataset stats、第 5 章的 preprocessor/postprocessor 管道），RL 策略注册为 PreTrainedPolicy 子类——白名单以外的策略通过 @PreTrainedConfig.register_subclass 插件机制接入——注意注册的是策略的配置类（如 ACTConfig，policies/act/configuration_act.py:22），策略本体再按 configuration_* → modeling_* 的命名约定被 factory.py 解析出来。

②蒸馏成 VLA 数据：仿真策略当「老师」在 Isaac Lab 里跑成功 rollout，用 RecorderManager（9.2 节）录成 HDF5 数据集，再用转换脚本（如 scripts/imitation_learning/locomanipulation_sdg/gr00t/convert_dataset.py）转成 LeRobotDataset——再把 VLA（第 6-7 章）当「学生」在这些数据上模仿学习。学生上位后自带视觉泛化，老师负责量产数据。

第 11 章是全书的「汇合点」：仿真线（8-10 章）的产出与真实线（2-7 章）的产出，最终都要通过本章的部署栈变成机器人的动作。12 章的路线图会把两条线串成六个里程碑。

11.6收尾：三道坎的一张表

本章小结

三道坎三张方子：物理差距靠 DR + actuator 随机化提前覆盖（第 8.5/10.3 节）；推理延迟靠 action chunk + 队列消费（第 5.2/11.3 节）；工程集成靠 Zenoh remote_inference——观测发布上行、动作信封下行，接入先过契约协商（特征名/形状/单位/频率逐一相等才放行），新旧动作靠承诺游标对齐替换（剪已走、换未来、窗口内混合），饿死宽限 + 位置保持防停摆。全书两条线在这里会师。
