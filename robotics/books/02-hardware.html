硬件抽象层：三个基类把千差万别的机器人拉齐

LeRobot 支持 15 种以上的机械臂、移动底盘与人形机器人，但上层代码只认识三个抽象：Robot（机器人）、MotorsBus（电机总线）、Camera(相机)。这一章把这三个基类逐方法读透——它们是整个真机栈的地基，也决定了「换一台机器人要写多少代码」。

2.1为什么需要硬件抽象：从「换机器人重写一切」到「换一个配置」

机器人领域的现实是：每个硬件厂商都有自己的 SDK、通信协议、标定流程。没有抽象层时，写一个「抓取演示」程序意味着把 SO-101 的 Feetech 协议、Koch 的 Dynamixel 协议、Unitree G1 的整套 SDK 各写一遍。LeRobot 的解法是经典的依赖倒置：定义三个稳定接口，所有硬件各自实现接口，上层（遥操作、录制、策略推理）只依赖接口。

  • Robot：整机抽象。「给我观测 / 接受动作」，是策略和录制脚本唯一看到的对象。
  • MotorsBus：关节驱动抽象。电机挂在哪条总线（Feetech/Dynamixel/Damiao/Robstride）上被它挡住，机器人类通过 sync_read / sync_write 与之交互。
  • Camera：视觉输入抽象。USB 摄像头、RealSense 深度相机、ZMQ 网络相机都长一个样：read() / async_read() 返回一个数组。

与 Isaac Lab 对照：仿真侧的对应物是 isaaclab/assets/ 下的 Articulation / RigidObject（第 8 章）——同样是「给上层一个稳定的读写接口，把物理引擎细节挡住」。真机与仿真在接口层面长得相似（读状态、写目标），这正是第 11 章 sim2real 能「换底座不换逻辑」的原因。

2.2Robot 基类：一台机器人该有的八个接口（重点）

Robot 是抽象基类（ABC）。它没有多少代码，但每个方法都是一份「承诺」——子类必须兑现，上层才能放心依赖。通读一遍：

src/lerobot/robots/robot.py:30 — Robot 抽象基类（摘录核心部分）
pythonclass Robot(abc.ABC):
    # 子类必须设置的类属性
    config_class: builtins.type[RobotConfig]   # 该机型的配置类
    name: str                                  # 机型唯一名，如 "so_follower"

    def __init__(self, config: RobotConfig):
        self.robot_type = self.name
        self.id = config.id
        self.calibration_dir = (
            config.calibration_dir if config.calibration_dir else HF_LEROBOT_CALIBRATION / ROBOTS / self.name
        )
        # 标定文件路径固定为 {calibration_dir}/{id}.json，构造时自动加载
        self.calibration_fpath = self.calibration_dir / f"{self.id}.json"
        self.calibration: dict[str, MotorCalibration] = {}
        if self.calibration_fpath.is_file():
            self._load_calibration()

    @property
    @abc.abstractmethod
    def observation_features(self) -> dict:
        """观测的结构描述：键与 get_observation() 返回一致；
        简单值给类型（float），数组给形状（(h, w, c)）"""

    @property
    @abc.abstractmethod
    def action_features(self) -> dict:
        """动作的结构描述：键与 send_action() 的入参一致"""

    @abc.abstractmethod
    def connect(self, calibrate: bool = True) -> None: ...
    @abc.abstractmethod
    def calibrate(self) -> None: ...
    @abc.abstractmethod
    def configure(self) -> None: ...
    @abc.abstractmethod
    def get_observation(self) -> RobotObservation: ...
    @abc.abstractmethod
    def send_action(self, action: RobotAction) -> RobotAction: ...
    @abc.abstractmethod
    def disconnect(self) -> None: ...
逐个读：
  • observation_features / action_features 是「模式描述」，不是数据本身。它们让不连接硬件也能写上层代码（docstring 特别强调 can be called regardless of whether the robot is connected）——录制脚本靠它预建数据集 schema（第 4 章），策略靠它校验输入维度。
  • connect / disconnect / __enter__ / __exit__：基类实现了上下文管理器（with make_robot(...): 即自动连接断开），这是所有资源型类的标配写法。
  • calibrate 与 calibration_dir：标定数据以 JSON 落盘（_load_calibration / _save_calibration），键是电机名，值是 MotorCalibration。下次连接自动加载——机器人不用每次重新摆位。
  • send_action 的返回值是本章最重要的细节：返回的是实际发送的动作（可能被 max_relative_target 安全限幅修改过），而不是入参。但要注意录制时落盘的还不是这个返回值——lerobot_record.py 里它被赋给 _sent_action 后并没有被使用，真正写进数据集的动作帧仍由限幅前的 action_values 构造（源码 :356 的 TODO 明确承认了这一点）。这条「发送值 ≠ 记录值」的缝在第 3 章 3.3 展开。

2.3一个具体实现：SO-Follower 如何兑现这七个承诺

抽象读起来总有点虚，直接看最流行的机型——SO-100/SO-101（SOFollower）。先看它在 __init__ 里怎么「装配」：

src/lerobot/robots/so_follower/so_follower.py:46 — 六个关节 + 一条 Feetech 总线
pythondef __init__(self, config: SOFollowerRobotConfig):
    super().__init__(config)
    self.config = config
    norm_mode_body = MotorNormMode.DEGREES if config.use_degrees else MotorNormMode.RANGE_M100_100
    self.bus = FeetechMotorsBus(
        port=self.config.port,
        motors={
            "shoulder_pan":  Motor(1, "sts3215", norm_mode_body),
            "shoulder_lift": Motor(2, "sts3215", norm_mode_body),
            "elbow_flex":    Motor(3, "sts3215", norm_mode_body),
            "wrist_flex":    Motor(4, "sts3215", norm_mode_body),
            "wrist_roll":    Motor(5, "sts3215", norm_mode_body),
            "gripper":       Motor(6, "sts3215", MotorNormMode.RANGE_0_100),
        },
        calibration=self.calibration,
    )
    self.cameras = make_cameras_from_configs(config.cameras)
读懂这段：一台 6 自由度机械臂的「全部硬件知识」浓缩在这里：电机 ID → 电机型号 → 归一化方式。MotorNormMode（motors_bus.py:169）决定读数怎么归一：RANGE_M100_100 把关节行程映射到 [-100, 100]，夹爪用 RANGE_0_100（0=张开，100=闭合）。策略看到的动作空间就是这组归一化后的数——换机型时只要归一化方式一致，数据集和策略可以复用。

然后是观测与动作的两个核心实现——注意它们全部经由 bus，没有一行 Feetech 协议细节：

src/lerobot/robots/so_follower/so_follower.py — get_observation / send_action（节选）
pythondef get_observation(self) -> RobotObservation:
    obs_dict = self.bus.sync_read("Present_Position", num_retry=self.config.num_read_retries)
    obs_dict = {f"{motor}.pos": val for motor, val in obs_dict.items()}
    # 相机用 read_latest()：拿最新一帧，不阻塞关节读取节奏
    for cam_key, cam in self.cameras.items():
        obs_dict[cam_key] = cam.read_latest()
    return obs_dict

def send_action(self, action: RobotAction) -> RobotAction:
    goal_pos = {key.removesuffix(".pos"): val for key, val in action.items() if key.endswith(".pos")}
    # 安全限幅：目标离当前位置太远时截断
    if self.config.max_relative_target is not None:
        present_pos = self.bus.sync_read("Present_Position", ...)
        goal_pos = ensure_safe_goal_position(goal_present_pos, self.config.max_relative_target)
    self.bus.sync_write("Goal_Position", goal_pos)
    return {f"{motor}.pos": val for motor, val in goal_pos.items()}  # 实际发送值
三个值得记住的设计：
  • 键名即接口："shoulder_pan.pos"、"laptop"（相机键）这些字符串键贯穿全栈——观测、动作、数据集列名、策略输入全部用它对齐。它取代了任何 IDL/接口定义文件，是 LeRobot 的「通用语言」（lerobot_types.py 中 RobotAction = dict[str, Any]，就是平铺字典）。
  • 相机走 read_latest()：关节同步读必须准点（控制频率），而相机帧偶尔迟到。用「最新可用帧」而不是「阻塞等下一帧」，让视觉延迟不至于拖垮控制回路——这是实时机器人系统的常见权衡。
  • 限幅发生在设备层：max_relative_target（config_so_follower.py:36）在 ensure_safe_goal_position（robots/utils.py:93）里把「单步目标位移」钳在阈值内。这意味着哪怕策略输出一个疯狂数值，物理执行也只是朝目标挪一小步——安全网放在了离电机最近的地方。

2.4MotorsBus：一条串行总线上的「寄存器读写」

舵机机械臂的关节电机不接网卡、不跑 ROS，它们挂在一条串行总线上（Feetech 用 TTL 串口，Dynamixel 同理），每个电机有 ID，协议本质是读写寄存器。LeRobot 把这套「查表寻址」抽象在 MotorsBusBase 里：

src/lerobot/motors/motors_bus.py:58 — MotorsBusBase 最小接口（摘录）
pythonclass MotorsBusBase(abc.ABC):
    def __init__(self, port: str, motors: dict[str, Motor], calibration: ... | None = None):
        self.port = port          # 串口路径，如 "/dev/ttyACM0"
        self.motors = motors      # {电机名: Motor(id, model, norm_mode)}

    @abc.abstractmethod
    def read(self, data_name: str, motor: str) -> Value: ...
    @abc.abstractmethod
    def write(self, data_name: str, motor: str, value: Value) -> None: ...
    @abc.abstractmethod
    def sync_read(self, data_name: str, motors: str | list[str] | None = None) -> dict[str, Value]: ...
    @abc.abstractmethod
    def sync_write(self, data_name: str, values: dict[str, Value]) -> None: ...
    @abc.abstractmethod
    def enable_torque(self, motors=..., num_retry: int = 0) -> None: ...
    @abc.abstractmethod
    def disable_torque(self, motors=..., num_retry: int = 0) -> None: ...
两个读写族的区别是总线效率的核心：
  • read / write：单电机逐个读写。读 6 个关节要发 6 次请求-响应，串行总线上就是 6 倍延迟。
  • sync_read / sync_write：广播一次指令，所有电机同时返回/写入同一个寄存器。FeetechMotorsBus 内部用 scs.GroupSyncRead（feetech.py:123）实现。30 Hz 控制回路里读 6 关节，sync_read 是能不能跑起来的差别。
  • data_name 是寄存器名：如 "Present_Position"、"Goal_Position"、"Torque_Enable"。get_address()（motors_bus.py:140）按电机型号查 tables.py 里的控制表，把名字翻译成 (地址, 长度)——每种电机芯片的寄存器布局不同，这份差异被压在 tables.py 一个文件里。

继承结构是 MotorsBusBase（纯接口）→ SerialMotorsBus（motors_bus.py:303，串口通用逻辑：端口收发、包超时、重试）→ FeetechMotorsBus / DynamixelMotorsBus（各自协议细节）。Damiao、Robstride 是 CAN 总线，另走一条实现线。

延伸 伺服层级之上才是策略层级。低层控制循环（读当前位置 → 写目标位置）跑在 30-100 Hz；策略推理可能只有 5-10 Hz（VLA 模型更慢）。两者的解耦靠「action chunk + 插值」——这是第 5 章（action chunking 与两种消费模式）和第 11 章（远程队列聚合）的主线。硬件抽象层保证的是：控制循环永远能以固定节拍拿到 Present_Position、写下去 Goal_Position。

2.4.1标定：归一化的前提

同一型号的舵机装配角度各不相同，读数 2048 在 A 机器上是「水平」，在 B 机器上可能偏了 30°。所以每个电机需要一份 MotorCalibration：

src/lerobot/motors/motors_bus.py:176 — MotorCalibration 与 Motor
pythonclass MotorNormMode(str, Enum):
    RANGE_0_100 = "range_0_100"        # 行程映射到 [0, 100]（夹爪）
    RANGE_M100_100 = "range_m100_100"  # 行程映射到 [-100, 100]（关节）
    DEGREES = "degrees"                # 直接用角度

@dataclass
class MotorCalibration:
    id: int              # 总线 ID
    drive_mode: int      # 方向反转（装反了读数会反向）
    homing_offset: int   # 零位偏移
    range_min: int       # 行程下限（原始读数）
    range_max: int       # 行程上限
标定流程（lerobot-calibrate CLI 触发）：把关节手动摆到标定姿势（如全部伸直）→ 软件记录各电机当前原始读数作为 homing_offset，再引导你手动把每个关节转到行程两端记录 range_min/range_max。之后 range_0_100 模式下的「50」对任何一台 SO-101 都意味着「行程中点」。这就是为什么数据集能用统计归一化（第 4 章 stats.json）、策略能跨机器迁移——所有物理差异在标定这一步被折算成统一坐标。

2.5Camera 基类：read / async_read / read_latest 三种节拍

相机抽象比电机简单得多——核心是三种取帧方式的取舍：

src/lerobot/cameras/camera.py:26 — Camera 基类（摘录）
pythonclass Camera(abc.ABC):
    def __init__(self, config: CameraConfig): ...

    def read(self) -> NDArray[Any]:
        """阻塞式取一帧（等下一帧到来才返回）"""

    def async_read(self, timeout_ms: float = ...) -> NDArray[Any]:
        """非阻塞式：后台线程持续抓帧，调用立即返回（等不到则超时）"""

    def read_latest(self, max_age_ms: int = 500) -> NDArray[Any]:
        """拿后台线程缓存里的最新一帧，绝不等待（过旧则报错）"""

    @staticmethod
    def find_cameras() -> list[dict[str, Any]]: ...  # 枚举系统上的相机设备
三种取帧各服务一个场景：read() 适合离线脚本（每帧都要新鲜）；async_read() 适合单相机主循环；read_latest()（2.3 里 SOFollower 用的）适合多传感器并发——关节读数是主节奏，相机帧顺手取最新的即可。2.3 的 get_observation() 里那两行 time.perf_counter() 计时日志就是在验证这一点：关节读取和相机读取的耗时都被监控，防止某一环悄悄掉帧。

配置侧，相机是 draccus 注册表（与第 3 章遥操作设备、第 5 章策略同一套机制）：

src/lerobot/cameras/configs.py:60 与 opencv/configuration_opencv.py:25
pythonclass CameraConfig(draccus.ChoiceRegistry, abc.ABC):
    fps: int | None = None
    width: int | None = None
    height: int | None = None

class OpenCVCameraConfig(CameraConfig):
    index_or_path: int | Path      # 设备号或视频文件路径

注册表模式全文只此一处主题：lerobot 里的「可插拔组件」——相机、电机总线、机器人、遥操作设备、策略——全都用 draccus.ChoiceRegistry。CLI 里 --cameras.front.type=opencv 这类参数就是这个注册表在驱动：按 type 字符串反查类并实例化。学会这一个模式，就学会了所有 LeRobot 配置。

2.6小结：接口即架构

概念lerobot 实现你自己做硬件接入时
整机接口Robot ABC：observation_features / connect / get_observation / send_action / disconnect先定接口再写实现；新机型 = 新子类 + 配置类，不动上层
关节读写MotorsBusBase.sync_read / sync_write 广播式总线访问，寄存器名经 tables.py 查表寻址控制回路永远用同步组读/组写；协议差异压进一个查表文件
安全限幅max_relative_target → ensure_safe_goal_position 逐步钳位，返回实际发送值安全网放离电机最近处；数据落盘用「实际执行值」
标定MotorCalibration（drive_mode/homing_offset/range）以 JSON 持久化，连接时自动加载把装配差异折算成统一归一化坐标，是数据可复用的前提
相机Camera ABC 的 read / async_read / read_latest 三种节拍多传感器系统里，主循环取 latest、离线脚本才用阻塞读
可插拔配置draccus.ChoiceRegistry + CLI --type 参数一套注册表机制贯穿所有组件类型，别为每个组件发明新写法
一句话记住：LeRobot 硬件层的设计哲学是「接口窄到不能再窄」——Robot 只承诺「观测进来、动作出去」，把协议、标定、限幅都关进实现里。上层的一切（录制、训练、部署）都建立在这份承诺上。
