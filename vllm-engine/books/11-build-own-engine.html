从「看懂 vLLM」到「写出自己的推理引擎」

这一页把你前面学的所有机制，重组成一条可以落地的开发路线。原则：先把它跑对，再让它快；先单线程，再并发；先单卡，再并行。

11.1总览：六个里程碑

图 11.1：六个里程碑，每步都可独立交付与验证。

11.2M1 · 最小单请求引擎（先跑对）

复刻第 2 章末尾的最小循环，但要点是把它做成「类 vLLM 的分层」，方便之后扩展：

建议的最小模块划分（伪代码，注释为本书说明）
pythonclass Request: ...        # id, prompt_tokens, num_computed_tokens
class Engine:                 # 决策 + 循环
    def step(self): ...          # 选请求→前向→采样
class Worker:                 # 真正跑 GPU
    def forward(self, batch): ...
验收标准：单个 prompt 能正确生成直到 max_tokens 或 stop。用热门小模型（如 Qwen2.5-0.5B 或 Llama-1B）验证。不要用随机权重。

11.3M2 · 分页 KV cache（学第 3 章）

把整条连续 KV 换成固定小块按需分配：

  • 引入 BlockPool（预分配物理块）与每请求 block_table（逻辑→物理）。
  • KV 不足时返回 None 背压，而不是 OOM（学 allocate_slots 的返回语义）。
  • 此刻注意力仍可用 torch 原生 attention，但传入 block table 很麻烦——第一次感受到「分页要和 kernel 配合」。可先用「把该请求的物理块 gather 成连续张量再算」过渡。
提示 前缀缓存（第 3 / 8 章）不必在 M2 就做。它解决的是「重复 prompt」的浪费，属于吞吐优化。先保证正确。

11.4M3 · 连续批处理（学第 4 章，最大的吞吐提升点）

这一步做完，你的引擎开始有真实的吞吐量。核心是第 4 章的心智模型：不再区分 prefill 阶段 / decode 阶段，只有一个统一的「当前 batch」概念：

  • 每个请求持有 num_computed_tokens 与 num_tokens_with_spec。
  • 每步：把能跑的请求拼成 batch → 一次 GPU 前向 → 各自采样 → 更新各自的计数器与 KV。
  • 新请求到位 → 加入；完成的请求 → 移出。batch 每步都变。
连续批处理主循环（伪代码，注释为本书说明）
pythonwhile self.running:
    batch = self.scheduler.schedule()          # 挑一批
    outputs = self.worker.forward(batch)       # 一次前向
    for r, out in zip(batch, outputs):
        r.advance(out.tok)                     # 更新 num_computed_tokens
        if finished(r): self.running.remove(r)
关键难点：不同请求长度不同、prefill 与 decode 混在一个 batch。要么做「定长 padded 张量」，要么做「变长削峰」。vLLM 在 Model Runner 里处理这个——这也是为什么会有 InputBatch（GPU 侧实现，见 vllm/v1/worker/gpu/input_batch.py）那套东西。

11.5M4 · chunked prefill + 调度策略（学第 4 章后半）

  • chunked prefill：把超长 prompt 切成若干 chunk 逐步 prefill，避免一次性算满卡住 decode（学 num_new_tokens 预算）。
  • 优先级：给请求加 priority，不足时抢占最低优先级（学 key=(r.priority, r.arrival_time)）。
  • 此时你的「调度器」从 M3 的简单循环，变成独立的 Scheduler 模块，输出每步的 batch 与 KV 分配指令。

11.6M5 · 采样 + 流式服务（学第 6 / 9 章）

  • 采样：在 top-k / top-p / 温度之上，加 penalty、logprobs、多路输出 n（第 6 章；束搜索可选——注意 V1 已把旧 best_of 拆成 n 与独立的 BeamSearchParams，没有单独的 best_of 参数可实现了）。
  • 服务：把你的 Engine.step 接到 FastAPI，做 /v1/completions 与流式（第 9 章）。把 HTTP 层和引擎解耦——此时它们本就不该耦合。

11.7M6 · 性能与并行（学第 5 / 7 / 10 章，按需）

到这一步你已经「功能完整」。性能优化是基于 profiling 的决定，而不是盲目堆技术：

瓶颈信号对应优化学的章节
kernel launch 开销大 / 小 batch 慢CUDA Graph 捕获（注意固定 shape 限制）05 / 07
decode 访存瓶颈更优 attention kernel（flash-attn/FlashInfer）、批量更大07
单卡放不下权重TP（先）+ PP10
需要更高吞吐前缀缓存、speculative decoding、DP08 / 04
最重要的一条 vLLM 的优秀 ≠ 它的每一项技术你都要在第一天实现。PagedAttention、CUDA Graph、前缀缓存、四路并行都是「在正确性之上叠加的吞吐优化」。 你的路线应当是：M1 跑对 → M3 拿到最大的吞吐收益（连续批处理）→ 之后按 profiling 决定要不要做其余项。这样才能避免在没跑通的情况下先去「造完备架构」。

11.8参考资料怎么用

这 11 页把 vLLM v1 的关键路径过了一遍。当你在自研中卡住时：

  • 回到本代码库逐行读：每个概念页都标了真实文件路径（如 vllm/v1/core/kv_cache_manager.py）。先读懂，再决定是否借鉴。
  • 对照 vLLM 官方文档（docs.vllm.ai）与论文「Efficient Memory Management for Large Language Model Serving with PagedAttention」。
  • 不要照抄内部工程细节：很多是兼容性/可扩展性的产物。只带走「该解决的问题」与「解决思路」，用你自己的、更简单的方式实现。
