采样：logits 如何变成 token

模型前向的终点是一个 vocab 大小的 logits 向量，但它还不是答案。这一章问：客户端要的「温度 0.7、top-p 0.9」怎么作用到这串分数上？50 个请求各要各的采样方式，怎么一次算完？什么时候停？先讲清参数怎么表达、怎么作用到 logits，再看 batch 怎么一次算完、输出怎么停；6.6–6.7 是两个延伸场景，末了拿 SGLang 对照一眼。

6.1分数怎么变成 token

Transformer 输出层（LM Head）对每个位置输出一个形状为 [vocab_size] 的向量，叫 logits。它只是「分数」：分数越高的 token 越像合理的下一个词，但它本身不是 token。要拿到一个可读的 token id，必须经过采样。把「分数 → token」这一步拆开，会撞到四个问题：

  • 请求的口味怎么表达？客户端要「temperature=0.7、top_p=0.9、遇到 stop 就停」——这些要求以什么形式传进引擎、存在哪？
  • 参数怎么作用到 logits 上？温度、top-k、top-p、repetition penalty……这些操作有先后依赖，谁先谁后？顺序错了会怎样？
  • 一个 batch 怎么一次算完？50 个请求各要各的采样方式，是跑 50 次采样还是一次算完？逐请求的参数怎么变成 batch 级的张量运算？
  • 输出怎么停？token id 怎么变回文本、EOS 和 stop 串怎么判、请求什么时候算结束？

最基础的事实先立住：采样的两种根本行为——

  • 贪心（greedy）：直接取 logits 最大的下标，即 argmax。确定性高，但容易重复、呆板。
  • 随机（random）：先把 logits 转成概率分布，再按概率随机抽。温度越高分布越平、越随机。

在 vLLM 里，这两种行为由 temperature 决定：temperature=0（严格来说 < 1e-5）走贪心，否则走随机。这正是下一节看到的字段与采样代码的分界线。

图 6.1：采样即「把 logits 变成 token id」。贪心可跳过 softmax，随机才需要完整概率分布。
本章路线：口味怎么表达（6.2 SamplingParams）→ 参数怎么作用到 logits（6.3 后处理链）→ batch 怎么一次算完（6.4 采样元数据）→ 输出怎么停（6.5 解码与停止）。6.6/6.7 是两个延伸场景（多路采样、投机解码），6.8 拿 SGLang 对照。

6.2请求的口味怎么表达：SamplingParams

每个请求都要带上一组采样参数。vLLM 用 vllm/sampling_params.py 里的 SamplingParams 描述。下面只摘和我们本章相关的字段（原文件字段顺序如此）：

vllm/sampling_params.py — SamplingParams（字段摘录；注释为译注，默认值照抄）
pythontemperature: float = 1.0
# 控制随机性。低值更确定，零值即贪心采样。
top_p: float = 1.0
# 累积概率截断：只考虑累积概率到 top_p 的最优 token。=1 表示考虑全部。
top_k: int = 0
# 只考虑概率最高的 top_k 个 token。0（或 -1）表示全部。
max_tokens: int | None = 16
# 每个输出序列最多生成的 token 数。
stop: str | list[str] | None = None
# 生成到这些字符串时停止。返回内容不含 stop 串。
stop_token_ids: list[int] | None = None
# 生成到这些 token id 时停止。
ignore_eos: bool = False
# 是否忽略 EOS 继续生成。
n: int = 1
# 为同一个 prompt 返回几个输出（即旧版 best_of 的继承者）。
读懂默认值：默认 temperature=1.0、top_p=1.0、top_k=0 表示「全开」——不截断、按原始分布随机。而一旦你设置 temperature=0（贪心），SamplingParams.__post_init__ 会把 top_p、top_k、min_p 一并重置为「禁用」，并校验必须用贪心。

另一个变化：V0 时代的 best_of 在 V1 里被语义拆开了。n 对应「一个 prompt 出几条独立输出」，而真正的束搜索则是一个单独的 BeamSearchParams（见 6.6），字段是 beam_width、max_tokens、length_penalty、temperature=0.0。

6.3参数怎么作用到 logits：后处理链的顺序

vLLM 的 Sampler（vllm/v1/sample/sampler.py）把整条链路写得很直白。类 docstring 列出了严格顺序：先做 allowed-token-ids 白名单、bad-words 排除、可影响贪心的 logits processor，再施加各类 penalty，然后才进 sample() 做温度缩放、top-k/top-p、softmax 与采样。

vllm/v1/sample/sampler.py — Sampler.forward（主干摘录）
pythondef forward(self, logits, sampling_metadata, ...):
    # 1) 用原始 logits（未惩罚、未缩放）算 top-k logprobs
    raw_logprobs = self.compute_logprobs(logits)   # log_softmax
    logits = logits.to(torch.float32)
    # 2) 白名单 / bad words / penalties
    logits = self.apply_logits_processors(logits, sampling_metadata, ...)
    # 3) 温度 / top-k / top-p / softmax / 采样
    sampled, processed_logprobs = self.sample(logits, sampling_metadata)
    ...
    return SamplerOutput(
        sampled_token_ids=sampled.unsqueeze(-1),  # [num_requests, 1]
        logprobs_tensors=logprobs_tensors,
    )

核心的 sample() 方法：先看是否全贪心（all_greedy）——是就直接 greedy_sample（即 logits.argmax(dim=-1)）返回；否则先 apply_temperature 做 logits.div_(temp.unsqueeze(1))，再跑 argmax 不变的 logits processor，最后交给 topk_topp_sampler。而温度内部对贪心请求把分母换成 1（避免除零）。

vllm/v1/sample/sampler.py — sample 中温度与 topk/topp
python# 温度：logits /= temperature（贪心请求分母换 1）
logits = self.apply_temperature(logits, sampling_metadata.temperature,
                                sampling_metadata.all_random)
# 只作用于随机采样的 logits processor（argmax 不变）
for processor in sampling_metadata.logitsprocs.argmax_invariant:
    logits = processor.apply(logits)
# top-k 与 top-p 截断 + softmax + 采样
random_sampled, _ = self.topk_topp_sampler(
    logits, sampling_metadata.generators,
    sampling_metadata.top_k, sampling_metadata.top_p)
注意一个细节：vLLM 的随机采样并没有显式调用 torch.multinomial，而是用「指数噪声技巧」——定义在 vllm/v1/sample/ops/topk_topp_sampler.py，先把 top-k/top-p 之外的 logits 打成 -inf，softmax 后 probs.div_(q).argmax() 得到采样结果。之所以绕开 multinomial，是为了避免它带来的 CPU-GPU 同步开销。

6.4一个 batch 一次算完：Sampler 与采样元数据

采样层的关键设计是把所有请求并成一个 batch 向量化算。为此需要一个描述「这个 batch 各自怎么采样」的结构——SamplingMetadata（vllm/v1/sample/metadata.py）：

vllm/v1/sample/metadata.py — SamplingMetadata（字段摘录）
pythontemperature: torch.Tensor | None   # 每请求一个温度（batch 向量）
all_greedy: bool                       # 整批都是贪心？可跳过整段随机逻辑
all_random: bool
top_p: torch.Tensor | None
top_k: torch.Tensor | None
generators: dict[int, torch.Generator] # 有 seed 的请求的 PRNG
no_penalties: bool                     # 无 penalty → 跳过惩罚分支
frequency_penalties: torch.Tensor
presence_penalties: torch.Tensor
repetition_penalties: torch.Tensor
output_token_ids: list[list[int]]        # 已生成的 token，供 penalty 参考

这些字段几乎全是对齐 batch 的 tensor：temperature、top_k、top_p、各类 penalty 都是每请求一个值。于是 Sampler.forward 一次就能对整个 batch 的 logits 做后处理并采样，返回 SamplerOutput（形状 [num_requests, 1] 的 sampled_token_ids）。性能优化点：no_penalties、all_greedy 这类「整批布尔」让常见简单场景直接走快捷路径，不动 penalty 分支。

读懂采样元数据：它是「逐请求采样参数 → 对齐 batch 的 tensor」这一转换的产物。自研引擎哪怕只做单请求，也从一开始就按 batch 向量的形状组织采样参数，为后续并发铺路。

6.5输出怎么停：解码、EOS 与请求结束

采样给出的是 token id 序列，要让用户看到文本，得解码（detokenize）。vLLM 的 vllm/v1/engine/detokenizer.py 提供 IncrementalDetokenizer —— 增量解码：每来一个新 token 只解这段、拼进已有的文本，而不是每次都重解整条序列。它分两类：快路径 FastIncrementalDetokenizer（走 tokenizers 库的 DecodeStream）和慢路径 SlowIncrementalDetokenizer。

vllm/v1/engine/detokenizer.py — IncrementalDetokenizer.update（摘录）
pythondef update(self, new_token_ids, stop_terminated):
    # 1) 增量解码新 token，拼进 output_text
    for new_token_id in new_token_ids:
        self.token_ids.append(new_token_id)
        self.output_text += self.decode_next(new_token_id)
    # 2) 在此之后还要对 stop 字符串做匹配（见 update 返回的 stop 串）

请求怎么结束？有三个终止条件，任一命中即终止本次生成：

  • EOS / stop_token_ids：采到了 EOS 或 stop_token_ids 里的 id。引擎会把这些 id 合并进 SamplingParams.all_stop_token_ids（见 update_from_generation_config）。
  • stop 字符串：需要先解码才能判断「文本里出现 stop 串」。这也是为什么 stop 只在 detokenize=True 时被允许。__post_init__ 里还专门算了个 output_text_buffer_length，把末尾可能构成 stop 前缀的那几个字符「扣住」不吐给用户。
  • max_tokens：达到上限强制结束（兜底保证不无限生成）。

ignore_eos=True 则忽略 EOS 继续生成（但仍受 max_tokens 约束）。

6.6束搜索与多路采样 | n / best_of

除了单路随机/贪心，还有两类「一次出多条候选」的能力：

  • 多条独立采样（n）：同一个 prompt 独立跑 n 条序列，各自随机，互相不共享信息。用于多次采样取最佳、或做诸如「多次尝试」的对比。
  • 束搜索（beam search）：真正的启发式搜索——每一步保留概率最高的 beam_width 条序列，权衡「长度惩罚」后择优。vLLM 用独立的 BeamSearchParams（vllm/sampling_params.py），字段为 beam_width、max_tokens、length_penalty、temperature=0.0。
vllm/sampling_params.py — BeamSearchParams（字段摘录）
pythonclass BeamSearchParams(msgspec.Struct, ...):
    beam_width: int          # 每步保留几条序列
    max_tokens: int
    ignore_eos: bool = False
    temperature: float = 0.0   # 束搜索通常是贪心的扩展
    length_penalty: float = 1.0
辨析：n 是「独立并行」，beam 是「共享搜索树」——两者要的显存/算力都随路数成倍上涨。绝大多数在线服务用 n=1 单路就够，beam 更适合离线评测。

6.7投机解码与 rejection sampling：一次验证多个猜测

前六节都在回答「怎么从一份 logits 里挑一个 token」——每步一个。投机解码（speculative decoding）的回答是：一步前进多个 token，且不改变输出分布。

为什么这两件事能同时成立。加速来自两半：草稿便宜——用一个便宜的来源（小模型、n-gram 匹配、Medusa 头）先猜出 k 个 token；验证几乎免费——目标模型一次 forward 本来就能对 k 个位置各出一份 logits（第 4、5 章的统一调度），猜对的部分直接保留，猜错的部分按概率规则回退。分布不变则是数学保证：arXiv:2211.17192 证明「接受/回退」规则产出的分布与直接用大模型采样完全一致。

源码锚点。代码分草稿 proposer 和验证 rejection sampler 两块；Model Runner 有两套实现（第 5 章：V2 现在默认，V1 作回退），两套的落点不同：

  • proposer：V1 用 vllm/v1/spec_decode/ 下的各 proposer，统一 propose() 接口，由 gpu_model_runner.py 的 propose_draft_token_ids（:4957）在每步采样之后调用；V2 换成 vllm/v1/worker/gpu/spec_decode/ 下的 BaseSpeculator（speculator.py:59），由 self.speculator.propose(...)（gpu/model_runner.py:886）调用。
  • 验证：V1 是 vllm/v1/sample/rejection_sampler.py 的 RejectionSampler.forward；V2 另有一份 vllm/v1/worker/gpu/spec_decode/rejection_sampler.py（__call__，配 rejection_sampler_utils.py 里的 Triton kernel）。两者语义相同，V2 那份改成了「分块验证」以适配 V2 的 batch 表示。

草稿来源的清单（两套共用）：

先看最便宜的一个：ngram 完全不用第二个模型。NgramProposer（vllm/v1/spec_decode/ngram_proposer.py）在已有序列里找「历史上一模一样的上下文后面跟的是什么」，把那段抄下来当草稿——对翻译、代码补全、agentic 循环里高度重复的输出特别有效。核心是一个 numba 加速的 batch_propose_numba，在 prompt_lookup_min/max 长度范围内找最长匹配 n-gram，把它后面的 k 个 token 抄出来：
vllm/v1/spec_decode/ngram_proposer.py — propose（摘录）
pythondef propose(self, num_speculative_tokens, sampled_token_ids,
             num_tokens_no_spec, token_ids_cpu, ...):
    for i, sampled_ids in enumerate(sampled_token_ids):
        num_tokens = num_tokens_no_spec[i]
        if num_tokens >= self.max_model_len:   # 到顶了，没法再抄

EAGLE / MTP 这类方法则把目标模型最后一层的隐状态喂给一个轻量头（EagleProposer，继承 SpecDecodeBaseProposer，见 llm_base_proposer.py），先跑一次 draft 前向拿第 1 个草稿 token，再循环 num_speculative_tokens - 1 次自回归地补齐 k 个草稿。草稿模型小、每步只算 1 个 token 的 batch，所以比目标模型一次 forward 便宜得多。

图 6.7：投机解码把「k 次 decode forward」变成「1 次便宜草稿 + 1 次多位置验证 forward」。decode 是访存瓶颈、算力闲置，正好用它并行验证。

验证的规则在 RejectionSampler。注意它的位置：不在调度器里，而是嵌在 Model Runner 的采样函数里——投机解码只是「换了一种采样」，第 6.3/6.4 节的整条 logits 后处理链照样要跑。两套 runner 的写法如下，判断条件一样（「本步有没有草稿 token」），差别在传参：

V1：vllm/v1/worker/gpu_model_runner.py — _sample（摘录，:3636）

RejectionSampler 的 docstring 把三个关键词定义得很清楚（vllm/v1/sample/rejection_sampler.py）：accepted（草稿与目标概率关系成立、直接采纳）、recovered（被拒后按「目标分布减去草稿分布的残差」重新采样一个补偿 token）、bonus（k 个草稿全部接受时额外奖励 1 个，只由目标模型采样）。最终 output = accepted + recovered + bonus。贪心请求有专门一条快路径 kernel，逐位「草稿 == 目标 argmax 才接受」（下面这段取自 V1 的那份，V2 把同样的逻辑收进了 _rejection_kernel，读法一样）：

vllm/v1/sample/rejection_sampler.py — rejection_greedy_sample_kernel（摘录，V1）

接受率会周期性打进日志（vllm/v1/spec_decode/metrics.py），格式是一行 SpecDecoding metrics: Mean acceptance length: %.2f, Accepted throughput: %.2f tokens/s, Drafted throughput: %.2f tokens/s, ...——平均接受长度（含 bonus）就是「每个 decode step 实际前进几个 token」的直观度量，也是判断该调大还是调小 k 的依据。注意投机的代价与参数：num_speculative_tokens（每步猜几个）越大，单步验证的 prefill 越长、KV 占用越多，而接受率通常随位置递减（Per-position acceptance rate），所以 k 不是越大越快。

收拢一下：投机解码 = 「草稿便宜地猜 + 验证严格地收」。它能加速的本质是decode 阶段算力闲置（访存瓶颈，见第 3、4 章）：与其一次 forward 只前进 1 个位置，不如让它并行验证 k 个位置。自研启示：先别做模型类 drafter——n-gram/suffix 这类零成本草稿 + 贪心逐位验证，几十行就能实现，对重复性高的负载马上见效。

6.8SGLang 对照与自研启示

回到 6.1 摆出的四个问题，vLLM 的答案是「SamplingParams 带进 Request → 后处理链按固定顺序压 logits → 采样元数据把逐请求参数压成 batch 向量、一次算完 → 输出处理器管解码与停止」。同一串问题，SGLang 的组织方式：

概念vLLM 实现你的引擎可以做
贪心greedy_sample → argmax先做这个，最简单、最好 debug
温度apply_temperature（logits/temp）第二版加温度，复用同一份 logits 路径
top-k / top-papply_top_k_top_p → -inf 掩码top-k 最便宜（一次 topk），top-p 要排序，后加
penalty / bad wordsapply_all_penalties 等明确不需要就先跳过，靠 all_greedy 快路径
多路 / beamn / BeamSearchParams最后再加；fallback 到跑 n 次即可
投机解码SpecDecodeMetadata + RejectionSampler先用 n-gram 草稿 + 贪心逐位验证（几十行）；按平均接受长度调 k
自研启示 最小引擎只需要：argmax + 温度采样 + top_k 三个足矣跑通一条对话链路。penalty、bad-words、beam 全是增量优化——把采样参数、采样元数据从一开始就按「batch 向量」的形状设计，未来加功能才不会返工。
与 SGLang 对照 逐项对照：
对比点vLLMSGLang
逐请求参数 → batch 张量SamplingMetadata（vllm/v1/sample/metadata.py）：temperature/top_p 等压成 batch 向量SamplingBatchInfo.from_schedule_batch（sampling/sampling_batch_info.py），同样压张量 + 归约出布尔标志
贪心快路径一条路径内按 all_greedy 分支Sampler.forward 开头显式分两条路（python/sglang/srt/layers/sampler.py）
grammar 约束落点采样前压 logit一致（apply_logits_bias 一并处理）；function call 解析都在反分词后的 serving 层
投机解码怎么插入长在 runner 内部（vllm/v1/spec_decode/），每步采样后由 runner 调 propose独立 spec worker，与普通 GPU worker 同接口 forward_batch_generation——调度器一行不改
前三行是同一问题的两种写法；最后一行是真正的组织分歧——「改内部」与「换组件」。详见 深入浅出SGLang · 08 采样与结构化输出；EAGLE 草稿-验证结构另见其 第 13 章。
下一步 采样看似只是一次 argmax 或一次随机抽样，为什么值得单独一章讲 kernel？因为 vLLM 把 top-k/top-p、softmax 都下沉成了高度优化的 kernel。采样加速正是第 7 章：Kernel 的内容。而投机解码被调度器怎么排进 batch（草稿 token 占 num_speculative_tokens 个调度位）、KV 怎么预留，见第 4 章：调度器的统一调度。
