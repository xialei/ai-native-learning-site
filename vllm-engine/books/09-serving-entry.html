服务入口：从离线 generate 到在线流式 API

前几章都在讲「引擎内部」。这一章走到能被人调用的外壳：OpenAI 兼容的 HTTP API、异步引擎的 background loop，以及「API server 与引擎核心分离」的部署架构。

9.1从离线到在线：LLM.generate vs 服务端

会话外第一件事：vLLM 有两套完全不同的用法。离线 API vllm/entrypoints/llm.py 里的 LLM.generate() 是阻塞、一次性的——你给它一批 prompt，它算完再一次性把结果全部返回给你：

  • 阻塞：调用期间主线程被占住，算完才返回。
  • 一次性：一批输入进来，整批跑完才交付，没有「边算边给」。
  • 自包含：它内部自己 spawn 一个后台 EngineCore，用完即走。

而在线服务要做的是并发、流式、持续运行：无数客户端同时连上来，每个请求希望「第一个 token 越早越好」，服务进程要一直活着响应。离线 API 完全应付不了这种场景。

关键转折：vLLM 为在线场景抽象出 AsyncLLMEngine（新版其实是指向 vllm.v1.engine.async_llm.AsyncLLM 的别名，见下）。它和同步 LLM 的区别，就在于用 asyncio 事件循环驱动一个常驻的引擎后台循环，请求可以并发地进、逐个地出。下面 vllm/engine/async_llm_engine.py 全文件就三行，直接把别名指了过去：
vllm/engine/async_llm_engine.py（全文）
pythonfrom vllm.v1.engine.async_llm import AsyncLLM

AsyncLLMEngine = AsyncLLM  # type: ignore
"""The `AsyncLLMEngine` class is an alias of [vllm.v1.engine.async_llm.AsyncLLM][]."""

所以「AsyncLLMEngine」这个名字在老版本里是独立类，现在则统一收敛到 AsyncLLM。本章都围绕它展开。

对照 离线 LLM.generate 适合离线评测、脚本处理；线上服务走 AsyncLLM.generate()（注意同名但语义不同，前者阻塞整批返回，后者返回一个可逐个迭代、边生成边吐结果的 AsyncGenerator）。

9.2OpenAI 兼容入口：路由怎么接进来

HTTP 层是用 FastAPI 搭的 build_app()（定义在 vllm/entrypoints/launchers/app.py；旧的 openai/api_server.py 已废弃，只是重新导出它）。注意：实际的 /v1/... 路由并不直接写在 build_app 里——build_app 调 register_api_routers()，后者再调各子模块的 api_router.py，通过 app.include_router(...) 注册。抓主干：

vllm/entrypoints/launchers/app.py + api_server/routers.py — build_app 的路由装配（摘录，注释为译注）

from vllm.entrypoints.generate.api_router import (
    register_generate_api_routers,

register_generate_api_routers(app)
# 其中 register_generate_api_routers 依次挂入 chat / responses / completion 等路由

register_generate_api_routers（vllm/entrypoints/generate/api_router.py）把 /v1/completions 和 /v1/chat/completions 挂到 FastAPI app 上。来看完整函数。

vllm/entrypoints/generate/api_router.py — 注册 completion 与 chat 路由（摘录，注释为译注）

这两个路由端点分别定义在 chat_completion/api_router.py（/v1/chat/completions → create_chat_completion）和 completion/api_router.py（/v1/completions → create_completion）。路由装上之后，FastAPI 收到 HTTP 请求就交给这些 handler，handler 再调用 openai_serving_xxx（如 OpenAIServingCompletion / OpenAIServingChat）把 HTTP 请求翻译成「引擎能力请求」。以 completion 为例：

vllm/entrypoints/openai/completion/api_router.py — /v1/completions 端点（摘录，注释为译注）
python@router.post("/v1/completions", ...)
@with_cancellation
@load_aware_call
async def create_completion(request: CompletionRequest, raw_request: Request):
    handler = completion(raw_request)          # 拿到 OpenAIServingCompletion
    generator = await handler.create_completion(request, raw_request)

    if isinstance(generator, ErrorResponse):
        return JSONResponse(content=generator.model_dump(), ...)
    elif isinstance(generator, CompletionResponse):
        return JSONResponse(content=generator.model_dump(), ...)

    return StreamingResponse(content=generator, media_type="text/event-stream")
看懂这段：三种返回分支很有意思——出错了给 JSONResponse；一次性（非流式）请求给普通 JSONResponse；而流式请求时 handler.create_completion(...) 返回的是一个异步生成器，被包进 StreamingResponse(content=generator, media_type="text/event-stream") 逐段推给客户端。相同的处理流程也出现在 /v1/chat/completions 的 create_chat_completion。

9.3异步引擎与流式：background loop + StreamingResponse

服务端流式的核心在 vllm/v1/engine/async_llm.py 的 AsyncLLM。它的关键设计是：

  • 构造时通过 EngineCoreClient.make_async_mp_client(...) 在后台进程里拉起 EngineCore（见 9.4）。
  • _run_output_handler() 起一个随事件循环跑的 asyncio 后台任务（output_handler），不断 await engine_core.get_output_async() 从引擎拉输出，交给 output_processor 处理后推给每个请求自己的队列。
  • 调用方（这里是 serving handler）迭代 AsyncLLM.generate() 返回的生成器，边产边取边 yield 给客户端。

看 generate() 里等待输出那一段——它从按请求的队列里拿 RequestOutput，不是攒到最后，而是拿到一个吐一个：

vllm/v1/engine/async_llm.py — AsyncLLM.generate 的取流循环（摘录，注释为译注）
pythonasync def generate(self, prompt, sampling_params, request_id, ...)
        -> AsyncGenerator[RequestOutput, None]:
    q = await self.add_request(...)   # 把 EngineCoreRequest 加进后台 EngineCore
    finished = False
    while not finished:
        out = q.get_nowait() or await q.get()   # 没有就先等，不空转
        finished = out.finished
        if out is not STREAM_FINISHED:
            yield out                     # 边生成边吐，绝不攒批
贯通整条链：/v1/completions?stream=true → create_completion → OpenAIServingCompletion 调 engine_client.generate(...)（拿到上面的异步生成器）→ 逐 token 包成 data: {...}\n\n 事件片 → 经 StreamingResponse 立即写回 TCP。于是客户端第一个 token 秒到，这就是「流式」的落地点。

9.4引擎/核心分离部署：无状态 API + 有状态 EngineCore

vLLM 的现代架构把「HTTP 外壳」和「真正干活的引擎」拆成两个进程：

  • API server / AsyncLLM（无状态、可水平扩）：只做 HTTP 解析、请求翻译、流式回包。它不持有模型权重、不占 GPU，可以起很多个副本。
  • EngineCoreProc（有状态、常驻）：持有模型、KV cache、调度器，常驻后台进程，监听 ZMQ 端口。见 vllm/v1/engine/core.py 的 EngineCoreProc——类 docstring 直接写着「ZMQ-wrapper for running EngineCore in background process」。
  • 两端通过 vllm/v1/engine/core_client.py 里的 MPClient 家族通信：input_socket 推请求，output_socket 拉输出，底层是 ZMQ。

看 MPClient 的类注释，它说明了这套传输模型：

vllm/v1/engine/core_client.py — MPClient 类注释（摘录）
pythonclass MPClient(EngineCoreClient):
    """MPClient: base client for multi-proc EngineCore.
    EngineCore runs in a background process busy loop, getting
    new EngineCoreRequests and returning EngineCoreOutputs

    * pushes EngineCoreRequests via input_socket
    * pulls EngineCoreOutputs via output_socket

    * AsyncMPClient subclass for AsyncLLM usage
    * SyncMPClient subclass for LLM usage
    """

因为 API server 无状态，一个请求打在哪个副本上都行，天然适配多副本 + 负载均衡；而引擎核心是有状态、且通常只该有一份（持有全部 KV）的地方。这张图画出整套部署：

图 9.4：无状态 API server 副本 ↔ 有状态 EngineCore ↔ Executor/GPU，全程走 ZMQ。
为什么这么拆：把 HTTP/编排逻辑从昂贵、有状态的推理进程里拿出去，调度器（KV、并发）专心在 EngineCore 里做；API 层随便复制、随便重启而不影响引擎，也方便在 API 前面加 nginx 做负载均衡与限流。

9.5用代码看：输出的最后一公里

承接 9.3，我们把 AsyncLLM 里那个「后台输出循环」看完整。它在一个 asyncio 任务里无限循环，从引擎拉 EngineCoreOutputs，处理成各请求的 RequestOutput 塞进队列：

vllm/v1/engine/async_llm.py — _run_output_handler 里的 output_handler 协程（摘录，注释为译注）
pythonasync def output_handler():
    while True:
        # 1) 从后台 EngineCore 拉一批输出
        outputs = await engine_core.get_output_async()
        num_outputs = len(outputs.outputs)
        # 2) 切成小块处理，避免阻塞事件循环
        for start in range(0, num_outputs, chunk_size):
            outputs_slice = outputs.outputs[start:end]
            output_processor.process_outputs(
                outputs_slice, outputs.timestamp, iteration_stats)
        # 3) 若有 stop string 触发的请求，通知引擎 abort
        if processed_outputs.reqs_to_abort:
            await engine_core.abort_requests_async(
                processed_outputs.reqs_to_abort)

self.output_handler = asyncio.create_task(output_handler())
逐行拆解：(1) get_output_async() 是跨进程（ZMQ）拉取，是真正「读引擎」的地方；(2) 切成小片处理是为了不长期占住事件循环，让其他请求（包括流式连接的 IO）也能跑；(3) 某些终止条件（stop string）由输出处理器判定后，反向通知引擎 abort——注意这是一个回环：请求的结局也可能是引擎外决定的。

再回头把「流式字节流」那段看一遍，它是 9.2 那段路由里 StreamingResponse 实际消费的内容。在 OpenAIServingCompletion.completion_stream_generator 里，每个 RequestOutput 被序列化成 OpenAI 风格的事件片：

vllm/entrypoints/openai/completion/serving.py — 流式生成器（摘录，注释为译注）
pythonasync for i, res in result_generator:   # 迭代引擎输出流
    # ... 包装成 deltas ...
    yield f"data: {response_json}\n\n"   # SSE 事件，一个 token 一片
...
yield f"data: {final_usage_data}\n\n"  # 结束前补 usage
yield "data: [DONE]\n\n"              # SSE 终止标记
看懂：这就是 HTTP 侧的「边想边说」——每个 data: {...} 都是一个新的 SSE 事件，含当前已生成的那一小段 delta。StreamingResponse 一拿到就 flush 给客户端，直到最后发 [DONE] 收尾。

9.6可观测性：TTFT / ITL / 吞吐，vLLM 怎么量自己

前面所有章节讲的优化——分页 KV、连续批处理、chunked prefill、CUDA Graph——最终都要落到数字上才算数：「这个优化把哪个指标改善了、代价是什么」。vLLM 在引擎内部就埋好了一整套统计：每个请求记录一组时间戳（vllm/v1/metrics/stats.py 的 RequestStateStats），汇总成 Prometheus 指标（vllm/v1/metrics/loggers.py），还能进一步算 MFU（vllm/v1/metrics/perf.py）。

vllm/v1/metrics/stats.py — RequestStateStats：每个请求的时间戳（摘录）
python@dataclass
class RequestStateStats:
    """Stats that need to be tracked across delta updates."""
    num_generation_tokens: int = 0
    num_preemptions: int = 0

    # This is an engine frontend timestamp (wall-clock)
    arrival_time: float = 0.0       # 请求到达 API server 的时刻

    # These are engine core timestamps (monotonic)
    queued_ts: float = 0.0          # QUEUED 事件
    scheduled_ts: float = 0.0      # 第一次被调度
    first_token_ts: float = 0.0    # 第一个新 token 产出
    last_token_ts: float = 0.0     # 最后一个新 token 产出

请求结束时，这些时间戳两两相减，就得到完整的延迟分解——排队、prefill、decode 各占多少一目了然：

vllm/v1/metrics/stats.py — update_from_finished_request：延迟分解（摘录）
pythone2e_latency = self._time_since(req_stats.arrival_time)

# Queued interval is from first QUEUED event to first SCHEDULED
queued_time = req_stats.scheduled_ts - req_stats.queued_ts

# Prefill interval is from first SCHEDULED to first NEW_TOKEN
prefill_time = req_stats.first_token_ts - req_stats.scheduled_ts

# Decode interval is from first NEW_TOKEN to last NEW_TOKEN
decode_time = req_stats.last_token_ts - req_stats.first_token_ts

# Inference interval is from first SCHEDULED to last NEW_TOKEN
inference_time = req_stats.last_token_ts - req_stats.scheduled_ts
图 9.6：TTFT 覆盖「排队 + prefill」，ITL 是 decode 段相邻 token 的间隔。前者由排队/prefill 决定，后者由每步 batch 大小与 kernel 速度决定——所以调参时两者往往此消彼长。

这些字段汇总成一组 Prometheus 指标名。挑最常用的记录在案（均出自 vllm/v1/metrics/loggers.py）：

vllm/v1/metrics/loggers.py — 核心指标名（摘录）
python# Gauge：当前瞬时状态
name="vllm:num_requests_running"       # 正在跑的请求数
name="vllm:num_requests_waiting"       # 排队中的请求数
name="vllm:kv_cache_usage_perc"        # KV cache 占用率

# Counter：只增不减的累计量
name="vllm:prefix_cache_queries"       # 累计查询的块数（对应第 8 章）
name="vllm:prefix_cache_hits"          # 累计命中的块数（对应第 8 章）

# Histogram：延迟分布（看 P50/P99，别只看均值）
name="vllm:time_to_first_token_seconds"      # TTFT
name="vllm:inter_token_latency_seconds"      # ITL
name="vllm:e2e_request_latency_seconds"      # 端到端
name="vllm:request_queue_time_seconds"       # 排队时长
name="vllm:request_num_preemptions"          # 被抢占次数（对应第 4 章）
把指标映射回机制：kv_cache_usage_perc 高位 + num_requests_waiting 高位 → 该扩 KV 预算（第 8 章）或上抢占/优先级（第 4 章）；prefix_cache_hits 低 → 前缀缓存没吃上（第 8.5 章，或多副本没做会话亲和）；request_num_preemptions 非零 → KV 频繁不够，系统在反复重算（第 4.5 章）。每个指标都能追溯到某一章的机制——这就是「可观测性」和「读懂引擎」的关系。
延伸：MFU vLLM 还内置了一个更底层的度量：用解析法估算每步的 FLOPs 与读写字节数（vllm/v1/metrics/perf.py 模块，"Analytic flops/memory estimation ... to help derive MFU (Model Flops Utilization) stats"），打开 VLLM_DEBUG_MFU_METRICS=1 后日志会输出「MFU: N TF/s/GPU M GB/s/GPU」。MFU 回答的问题是「这张卡的算力我用满了几成」——它是判断「瓶颈在算力还是在访存」的最终依据，也正是第 7.1 章 arithmetic intensity 概念的实测形态。

9.7小结与自研启示

概念vLLM 实现你的引擎可以做
离线LLM.generate（阻塞、整批）先做同步 CLI + 一个生成接口，最快跑通正确性
在线/并发AsyncLLM（asyncio 常驻循环）自研第二步再加 asyncio + 请求队列
流式AsyncGenerator + StreamingResponse引擎每步产出就 yield，绝不攒批
分层API server ↔ EngineCore（ZMQ）把「HTTP 壳」与「引擎」解耦，才能水平扩
可观测RequestStateStats 时间戳 + Prometheus 直方图（TTFT/ITL/e2e）第一版只记 arrival/first_token/last_token 三个时间戳就够——没有度量的优化是盲目的
自研启示 别一上来就搞 FastAPI + 流式 + 多副本。推荐的成长路径：先做同步 CLI + 一个 generate 接口把模型正确性跑通（第 5-7 章），再考虑并发——届时把「引擎（有状态、唯一）」与「HTTP 层（无状态、可复制）」解耦，自然就拿到水平扩展能力。无状态，是一切可扩展性的前提。
下一步 单机的入口与引擎讲完了。当模型太大、一块 GPU 放不下时，引擎要被拆到多机多卡上跑——这就是第 10 章：分布式。
