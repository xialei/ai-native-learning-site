Model Runner：把「调度器决定跑什么」翻译成「GPU 真正算什么」

调度器交出计划，CPU 侧的决策就结束了。本章站在 GPU 侧回答三个具体问题：几十个请求的 token 怎么拼成一个张量、一次算完；每个 attention 层怎么在显存里找到自己要读写的 KV；一次前向几百次 kernel 启动的固定开销怎么省。

5.1从调度器的计划到 GPU 的执行

上一章结束时，调度器产出了 SchedulerOutput——一张「这个 step 要跑哪些请求、每个请求调度几个新 token」的计划表。这张表是 CPU 上的 Python 对象；GPU 上的 transformer 只认张量。从对象到张量、从计划到执行，中间的转换都在 Model Runner 里完成。本章只讲三件事：token 怎么拼、KV 怎么找、启动开销怎么省。

先看全貌。一次执行的路径是：

  • 拼 token 张量：把 N 个请求这步要算的 token 拼成一个一维的 input_ids，外加每个 token 的位置编号（positions）和每个请求的序列长度（seq_lens）。对应 prepare_inputs。
  • 给 attention 层准备 KV 的地址信息：第 3 章说过，每个请求的 KV 物理块不连续，attention 层手里必须有一张「逻辑块 → 物理块」的对照表（block table）才能读写 KV。这一步把这些表从 CPU 搬到 GPU 并整理成 kernel 要的形状。对应 prepare_attn，细节在 5.3 展开。
  • 跑一次前向：调用 self.model(**model_inputs)。
  • 取出需要算 logits 的位置：前向输出所有位置的 hidden states，但下一步采样只需要其中几个位置。这一步把它们挑出来。对应 sample。

这些步骤都写在 GPUModelRunner.execute_model 里（vllm/v1/worker/gpu/model_runner.py）。下面三节按「拼 token → 找 KV → 省启动开销」的顺序拆开。

图 5.1：Model Runner 把调度批次变成 GPU 张量，跑完整 transformer。输出的 hidden states 交采样层（第 6 章）。

5.2token 怎么拼：整 batch 一个一维张量

第一个问题：这个 step 要给 50 个请求算共 800 个 token，怎么把它们交给 transformer？

vLLM 的答案是把它们拼成一个一维张量——50 个请求的 800 个 token 首尾相连，变成一个 [800] 的 input_ids，而不是 50 个独立张量。请求之间的分界记在另一个张量 query_start_loc 里：它是一个前缀和，形如 [0, 5, 37, …, 800]，第 i 个请求的 token 就占区间 query_start_loc[i] : query_start_loc[i+1]。任何 kernel 想单独处理某个请求，按这个区间取就行。

承载这些数据的数据结构叫 InputBatch，几乎所有字段都是按 token 或按请求排布的连续张量：

vllm/v1/worker/gpu/input_batch.py — class InputBatch（关键字段摘录，注释为译注）
python@dataclass
class InputBatch:
    # 本 batch 里每个槽位对应哪个请求
    req_ids: list[str]
    num_reqs: int
    num_reqs_after_padding: int

    # [num_reqs + 1] 每个请求的 token 区间起点（前缀和）
    query_start_loc: torch.Tensor
    # [num_reqs] 每个请求当前的序列长度
    seq_lens: torch.Tensor

    # [num_tokens_after_padding] 拼 token / 拼位置
    input_ids: torch.Tensor
    positions: torch.Tensor
    is_padding: torch.Tensor

    # 要算 logits 的 token 位置（通常是每请求最后一个）
    logits_indices: torch.Tensor
    ...
为什么这样拼：GPU 每启动一个 kernel 都有固定开销，张量个数越多、次数越多，开销越大。50 个请求一个张量，一轮 kernel 启动就全覆盖；拆成 50 个张量就要启动 50 轮。这是本章的底色，5.4 的 CUDA Graph 会把它推到极致。

input_ids 的长度是 num_tokens_after_padding 而不是真实 token 数——多出来的部分是往尾部补的假 token，用 is_padding=True 标记，kernel 会跳过它们。为什么要补、补到多长，到 5.4 讲 CUDA Graph 时就清楚了。

5.3KV 怎么找：每个请求一张表，每个 token 一个槽位

第二个问题：token 张量拼好了，attention 层去哪读 KV？

每个请求的 KV 散落在物理内存的不同块里。具体到「请求 A 的第 7 个 token，它的 K/V 存在哪个块、块内第几格」，答案是两张表：

  • block table——每个请求一张，把「这个请求的第 0、1、2… 个逻辑块」翻译成「物理块 #7、#13、#2…」。读序列里任何一个 token 的历史 KV，都要先查它。第 3 章讲 PagedAttention 时见过这张表，这里是它在执行侧真正被使用的地方。
  • slot mapping——这个 step 要新写入的每个 token 一个槽位号：物理块号 × 块内偏移。attention 算完这个 token 的 K/V，就按槽位号把结果写进显存的那个格子。读历史 KV 靠 block table，写新 token 靠它。

两者都在 prepare_attn 里生成：

vllm/v1/worker/gpu/model_runner.py — prepare_attn（摘录，注释为译注）
pythondef prepare_attn(self, input_batch: InputBatch):
    # Block tables: num_kv_cache_groups x [num_reqs_padded, max_num_blocks]
    block_tables = self.block_tables.gather_block_tables(
        input_batch.idx_mapping,
        num_reqs_padded=input_batch.num_reqs_after_padding,
    )
    # Slot mappings: [num_kv_cache_groups, num_tokens_padded]
    slot_mappings = self.block_tables.compute_slot_mappings(
        input_batch.idx_mapping,
        input_batch.query_start_loc,
        input_batch.positions,
        num_tokens_padded=input_batch.num_tokens_after_padding,
    )
    return block_tables, slot_mappings

到这里，每个请求的两张表都有了。还剩一步打包：把这些张量连同 seq_lens、区间切分等组装成 attention metadata，交给每个 attention 层。

交给谁？模型里 attention 层有几十个，但它们的 KV 布局规格并不都相同——普通全注意力的层和滑窗层块数不同，MLA 层的缓存形状也不同。vLLM 把「布局规格相同」的层归成一组（kv_cache_group，第 8 章会看到它是怎么分的），同一个组里的层用同一份 metadata、同一批物理块。于是 metadata 不用按层构建几十份，每个组构建一份、组内共享：

vllm/v1/worker/gpu/attn_utils.py — build_attn_metadata（每层绑定同一份 metadata 的部分）
pythonfor attn_group in attn_groups[i]:
    metadata = attn_metadata_builder.build(common_prefix_len=0,
                                           common_attn_metadata=common_attn_metadata)
    for layer_name in attn_group.layer_names:
        attn_metadata[layer_name] = metadata   # 这层就用这份 metadata
读懂这段：metadata 的构建按组进行（外层按 kv_cache_group 分组循环），构建好一份就复制给组内每个 layer（内层按 layer_names 循环）。省内存也省构建时间。至于每个层真正要读写的物理 KV 大张量，则在引擎启动时由 bind_kv_cache_to_layers 按层名绑定到层上——那是一次性的，不在每步的路径里。每步真正随 batch 变化的只有这两张表。

5.4启动开销怎么省：CUDA Graph

第三个问题在 5.2 已经埋下：GPU 每启动一个 kernel 都有固定开销，而一次前向要跑几十上百个 kernel。decode 时每个请求通常只算 1 个 token，计算本身很短，启动开销就占了相当比例。省掉它的手段是 CUDA Graph：把一次前向的全部 kernel 启动录成一张「图」，之后每步只需一次命令就整图回放（replay），几百次启动变成一次。

录制在引擎启动时做。以 5.2 的 50 请求 800 token 为例：vLLM 预先枚举一组 batch 形状（比如 token 数 1、2、4、8、…），对每个形状把整个前向录成一张图：

vllm/v1/worker/gpu/cudagraph_utils.py — CudaGraphManager.capture（摘录，注释为译注）
pythonwith torch.cuda.graph(graph, self.pool):
    forward_fn(CUDAGraphMode.NONE)      # 把整条前向录成一张图
self.graphs[desc] = graph              # {batch形状: 图} 存起来复用

推理时每个 step 查一次表：这个 batch 的形状命中哪张图，就回放哪张。命中不了才走普通路径，逐 kernel 调 model()：

vllm/v1/worker/gpu/model_runner.py — execute_model（FULL 模式回放）
pythonif batch_desc.cg_mode == CUDAGraphMode.FULL:
    # 输入已拷到 CUDA graph 的输入缓冲区，回放即可
    model_output = self.cudagraph_manager.run_fullgraph(batch_desc)
else:
    # Eager / PIECEWISE：直接调 model()
    model_output = self.model(**model_inputs)

限制：图的形状是死的，batch 是活的

CUDA graph 一旦录好，里面每个 kernel 的尺寸就固定了。而第 4 章的连续批处理意味着每个 step 的 batch 大小都在变——请求随时加入、退出。两件事要兼容，只有一个办法：把活 batch 补齐到某张图的尺寸再回放。

具体做法：预先枚举一组「捕获尺寸」（cudagraph_capture_sizes，如 1、2、4、8、…直到最大批），batch 落在哪个区间，就补齐到该区间的上限。比如 50 个请求补到 56，多出来的 6 个槽位填上假 token——正是 5.2 里 is_padding=True 的来源。补的那几个 token 白算一点点计算，换回来的是整次前向只付一次启动开销，划算。

为什么 decode 单独一套尺寸：decode 每步固定每个请求 +1 token，batch 之间只差请求数，形状种类少，枚举尺寸容易命中；prefill 的 token 数每个请求各不相同，命中预录形状的概率低得多。所以 vLLM 对 decode 用「枚举尺寸 + 补齐」，prefill 走别的路径（如 PIECEWISE 编译图），两者分开处理。

5.5用代码看：一次完整前向

把 5.1–5.4 串起来。下面的片段取自 execute_model：组装输入字典，命中 CUDA graph 就回放、否则直接调模型，最后从 hidden states 里挑出要算 logits 的位置。

vllm/v1/worker/gpu/model_runner.py — execute_model（组装输入 + 前向 + 取 logits，语义逐行注释）
python# 1) 组装模型输入：整个 batch 的 input_ids + positions
model_inputs = {
    "input_ids": input_ids,
    "positions": input_batch.positions,
    "inputs_embeds": inputs_embeds,
    "intermediate_tensors": None,
    # model_state.prepare_inputs 可覆盖 positions（如 RoPE 场景）
    **self.model_state.prepare_inputs(input_batch, self.req_states),
}

# 2) 命中 FULL CUDA graph 就直接回放；否则 eager 调 model()
if batch_desc.cg_mode == CUDAGraphMode.FULL:
    model_output = self.cudagraph_manager.run_fullgraph(batch_desc)
else:
    model_output = self.model(**model_inputs)

# 3) 只取每请求最后位置的 hidden state 算 logits
sample_hidden_states = hidden_states[input_batch.logits_indices]
logits = self.model.compute_logits(sample_hidden_states)
逐行读懂：(1) 把输入装进一个字典传给模型，其中的张量就是 5.2 拼好的一维大张量；(2) 是 5.4 说的「命中图就回放，否则 eager」；(3) 里前向输出的是每个 token 位置的 hidden states，logits_indices 从中挑出每个请求真正要出 logits 的位置（decode 是最后一个 token，prefill 挑到需要的位置），只对这些位置算 logits，不白算整条序列。至于 logits 怎么变成 token，是第 6 章的事。

5.6小结与自研启示

阶段vLLM 的做法你的引擎该怎么做
拼 token整 batch 拼成一维张量（InputBatch），query_start_loc 记分界同上，一个前缀和张量切分请求
找 KV每请求一份 block table + 每个 token 一个 slot 槽位同样两张表传给 attention kernel
CUDA Graph按捕获尺寸各录一张，不命中就补齐到更大尺寸先不做；把 eager 前向跑通、正确性稳定后再优化
算 logitslogits_indices 只挑每请求最后位置同思路，别白算整条序列
自研启示 单请求引擎（或 batch 很小的引擎）不需要 CUDA graph——kernel launch 的开销只有在并发很大的时候才值得用「固定 shape + 回放」来省。先把 eager 前向完整跑通、验证正确性，再把 CUDA graph 当第二版优化来做。优先级永远是：先对，再快。
