Model Runner：把「调度器决定跑什么」翻译成「GPU 真正算什么」

调度器只说了「这批请求、每个请求几个 token」。Model Runner 负责把这份「计划」变成 GPU 能吃的张量：token ids、positions、每层的 KV 指针和 block table，然后把整个 batch 喂进 transformer，产出一批 logits 给采样器。它是 CPU 世界与 GPU 世界之间的翻译官。

5.1Model Runner 是做什么的

上一章调度器给出了 SchedulerOutput——一张「这个 step 要跑哪些请求、每个请求调度几个新 token」的计划表。Model Runner 的职责是：把这份计划变成 GPU 上的一堆张量，跑一遍 transformer，再吐回 logits。它站在「EngineCPU 决定跑什么」和「GPU 真正算」中间当翻译官。

  • 翻译批次：把 N 个请求的 token 拼成一个连续的 input_ids 大张量（还有对应的 positions、每个请求的 seq_lens）。
  • 翻译 KV 布局：从 KV 缓存里，按层取出每个请求的物理块指针，组装成 attention metadata（含 block table），让分页注意力 kernel 能按表取 K/V。
  • 跑模型：调用 self.model(**model_inputs) 完成一次前向。
  • 产出 logits：把 hidden states 里真正的「最后一个位置」取出来算 logits，交给采样器。

在真实代码里，这段逻辑分布在 GPUModelRunner.execute_model 这条大流水线里：prepare_inputs（拼 token 张量）→ prepare_attn（取 block tables & slot mappings）→ attention metadata 构建 → 模型前向 → sample（算 logits）。

图 5.1：Model Runner 把调度批次翻译成 GPU 张量，跑完整 transformer，产出 logits。

5.2组装输入：把整 batch 拼成一个大张量

关键数据结构是 InputBatch（v1 里叫 InputBatch，继承自一段 dataclass）。它几乎全是「按 token 或按请求维度排列的连续张量」——整个 batch 拼成一个大张量，而不是每个请求一个张量。这样一次 kernel launch 就能处理所有请求，极大减少 CPU→GPU 的启动开销。

vllm/v1/worker/gpu/input_batch.py — class InputBatch（关键字段摘录，注释为译注）
python@dataclass
class InputBatch:
    # batch_idx -> req_id：本 batch 里每个槽位对应哪个请求
    req_ids: list[str]
    num_reqs: int
    num_reqs_after_padding: int

    # [num_reqs + 1] 每个请求的 token 区间起点（前缀和，方便切分）
    query_start_loc: torch.Tensor
    # [num_reqs] 每个请求当前的序列长度
    seq_lens: torch.Tensor

    # [num_tokens_after_padding] 整个 batch 拼在一起的 token ids / 位置
    input_ids: torch.Tensor
    positions: torch.Tensor
    is_padding: torch.Tensor

    # [total_num_logits] 哪些 token 位置要产出 logits（通常是每请求最后一个）
    logits_indices: torch.Tensor
    cu_num_logits: torch.Tensor
    ...
为什么拼成大张量：GPU kernel 的开销大头是每次 launch 的固定成本（指令下发、上下文切换）。vLLM 把所有请求的所有 token 摊平成 input_ids 一个 [num_tokens] 的张量，一次 kernel launch 就能覆盖整个 batch。分界信息（谁到谁）靠 query_start_loc 前缀和保存，每个 kernel 按需取自己的区间。

填充（padding）也在这里出现：CUDA graph 模式要求固定 shape，所以会往尾部补 is_padding=True 的假 token，kernel 里再跳过它们。

5.3KV cache 怎么进 kernel：按层聚合指针

光有 token ids 还不够——attention 层要知道「这个请求的 KV 缓存在显存哪里」。这块由 prepare_attn 负责：它对每个请求取出 block table（逻辑块→物理块映射）和 slot mapping（每个 token 落在哪个物理槽位），再按 kv_cache_group 聚合。

vllm/v1/worker/gpu/model_runner.py — prepare_attn（摘录，注释为译注）
pythondef prepare_attn(self, input_batch: InputBatch):
    # Block tables: num_kv_cache_groups x [num_reqs_padded, max_num_blocks]
    block_tables = self.block_tables.gather_block_tables(
        input_batch.idx_mapping,
        num_reqs_padded=input_batch.num_reqs_after_padding,
    )
    # Slot mappings: [num_kv_cache_groups, num_tokens_padded]
    slot_mappings = self.block_tables.compute_slot_mappings(
        input_batch.idx_mapping,
        input_batch.query_start_loc,
        input_batch.positions,
        num_tokens_padded=input_batch.num_tokens_after_padding,
    )
    return block_tables, slot_mappings

拿到 block tables / slot mappings 后，model_state.prepare_attn 调 build_attn_metadata：按 kv_cache_group 生成一份 attention metadata，再把同一份 metadata 绑定到该组的所有 layer。物理 KV 张量则通过 bind_kv_cache 按层名绑到每个 attention 层。

vllm/v1/worker/gpu/attn_utils.py — build_attn_metadata（每层绑定同一份 metadata 的部分）
pythonfor attn_group in attn_groups[i]:
    metadata = attn_metadata_builder.build(common_prefix_len=0,
                                           common_attn_metadata=common_attn_metadata)
    for layer_name in attn_group.layer_names:
        attn_metadata[layer_name] = metadata   # 这层就用这份 metadata
读懂这段：「按层」体现在这块——每个 attention 组里的所有 layer 共享同一批 block table 和 slot mapping（因为它们的 KV 布局规格相同），于是 vLLM 只构建一份 metadata 再复制到多处，省内存也省构建时间。而真正的物理 KV 指针，早在 bind_kv_cache 时按 layer_name 绑好了，kernel 里按 block table + slot 索引即可读写对应的物理块。

5.4CUDA Graph：省掉 kernel launch 开销

对 decode 这种「每步只算 1 个新 token、但 batch 里有几十上百个请求」的负载，瓶颈常常不是计算量，而是每个 kernel 的启动开销——一次前向几十上百个 kernel，每个 launch 都有固定成本。CUDA Graph 把整条计算流「录」下来，之后只需一次回放（replay），省掉反复的 kernel 下发。

vllm/v1/worker/gpu/cudagraph_utils.py — CudaGraphManager.capture（摘录，注释为译注）
pythonwith torch.cuda.graph(graph, self.pool):
    forward_fn(CUDAGraphMode.NONE)      # 把整条前向录成一张图
self.graphs[desc] = graph              # {batch描述: 图} 存起来复用

回放侧在 execute_model 里：当 batch 形状命中某张已捕获的图时，self.cudagraph_manager.run_fullgraph(batch_desc) 直接回放，不再逐 kernel 调用。

vllm/v1/worker/gpu/model_runner.py — execute_model（FULL 模式回放）
pythonif batch_desc.cg_mode == CUDAGraphMode.FULL:
    # 输入已拷到 CUDA graph 的输入缓冲区，回放即可
    model_output = self.cudagraph_manager.run_fullgraph(batch_desc)
else:
    # Eager / PIECEWISE：直接调 model()
    model_output = self.model(**model_inputs)

限制：固定 batch shape 才能复用

CUDA graph 一旦捕获，kernel 的 grid 尺寸就固定住了。因此只能按一组「捕获尺寸」（cudagraph_capture_sizes，decode 通常是 1、2、4、8、…、max_batch）各录一张图，实际 batch 命中某个尺寸就用那张，不命中就向上取整到更大的图，多余的槽位填 padding token。这就是 5.2 里 is_padding 的由来。

张力：固定的图尺寸和「按需动态批处理」是天然的矛盾——你越想让每个 step 的 batch 正好填满，越难命中预录的尺寸。vLLM 用「pad 到最近捕获尺寸」来折中：宁可多算几个 padding token，也省下 kernel launch。这也解释了为什么把 decode（每步固定 +1 token、batch 可变）用单独一套捕获尺寸，和 prefill（num_tokens 每步不同）分开。

5.5用代码看：一次完整前向

把 5.1–5.4 串起来。下面的片段取自 execute_model：先组装 model_inputs，再按是否命中 CUDA graph 决定回放还是 eager 调 model()，最后算 logits。

vllm/v1/worker/gpu/model_runner.py — execute_model（组装输入 + 前向 + 采样，语义逐行注释）
python# 1) 拼一个大张量 batch：整个 batch 的 input_ids + positions
model_inputs = {
    "input_ids": input_ids,
    "positions": input_batch.positions,
    "inputs_embeds": inputs_embeds,
    "intermediate_tensors": None,
    # model_state.prepare_inputs 可覆盖 positions（如 RoPE 场景）
    **self.model_state.prepare_inputs(input_batch, self.req_states),
}

# 2) 命中 FULL CUDA graph 就直接回放；否则 eager 调 model()
if batch_desc.cg_mode == CUDAGraphMode.FULL:
    model_output = self.cudagraph_manager.run_fullgraph(batch_desc)
else:
    model_output = self.model(**model_inputs)

# 3) 采样：只取每请求最后位置的 hidden state 算 logits
sample_hidden_states = hidden_states[input_batch.logits_indices]
logits = self.model.compute_logits(sample_hidden_states)
逐行读懂：(1) 里 k/v 都对齐到 [num_tokens] 的一维张量，一次前向覆盖整个 batch；(2) 是 5.4 说的「命中图就回放，否则 eager」；(3) 里 logits_indices 标记了每个请求真正要出 logits 的位置——decode 是最后 1 个，prefill 是最后一个 token——所以模型只在这几个位置算 logits，不白算整条序列。

5.6小结与自研启示

阶段vLLM 的做法你的引擎该怎么做
批次翻译整 batch 拼成一维大张量（InputBatch）同上，query_start_loc 前缀和切分
KV 进 kernel按 kv_cache_group 聚合 block table / slot从每层 KV 取物理指针 + block table 传给 kernel
CUDA Graph按捕获尺寸各录一张，不命中就近 padding先不做；把 eager 前向跑通、正确性稳定后再优化
logitslogits_indices 只算每请求最后位置同思路，别白算整条序列
自研启示 单请求引擎（或 batch 很小的引擎）不需要 CUDA graph——kernel launch 的开销只有在并发很大的时候才值得用「固定 shape + 回放」来省。先把 eager 前向完整跑通、验证正确性，再把 CUDA graph 当第二版优化来做。优先级永远是：先对，再快。
