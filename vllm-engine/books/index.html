为什么需要 vLLM

一个常见的疑问：模型厂商自己就做推理，为什么还需要 vLLM？前提要先拆开——「厂商能做推理」不等于「厂商包办所有人的推理」。

  • 托管 API 之外，开源权重本来就是给你自己部署的。数据不出域、合规审计、按自己的流量特征核算成本，这三件事把大量使用场景推回私有化。但权重公开只是第一步：「在自己的 GPU 上把几百 GB 权重跑起来、跑得便宜」是另一套工程——调度、显存管理、kernel、分布式。这门工程的开源事实标准就是 vLLM（SGLang 是另一个）。
  • 厂商不绕开 vLLM，而是把模型适配进 vLLM。DeepSeek-V4/V4.1 的官方模型卡直接给出 vllm serve 启动命令；GLM-5.2 的官方部署文档标注了对 vLLM 的版本要求（v0.23.0+）。厂商发新模型，出 vLLM/SGLang 适配是发布流程的一部分。vLLM 由 UC Berkeley Sky Lab 起家，如今有 2000+ 贡献者、数十家机构参与（NVIDIA、AMD、Red Hat 都在其中）——引擎是公共基础设施，没有厂商会只为自家模型重写一遍调度和显存管理。
  • 推理服务和训练是两个目标函数。训练是离线批任务，框架优化「算得快」；推理服务是 7×24 在线、多租户并发，对 TTFT（首 token 延迟）和 ITL（token 间延迟）敏感，显存是硬约束。厂商内部服务自家 API 用的同样是这套服务工程，只是不开放。你能学、能改、能自建的那份实现，就是 vLLM。
定位 厂商的交付物是模型和权重；vLLM 的交付物是「任何人在任何 GPU 上把任何模型服务好」。两者是上下游关系，不是竞争关系。

vLLM 怎么把推理变快

先算一笔账（公式推导见第 8 章）：每个 token 的 KV 状态占 2 × num_layers × num_kv_heads × head_dim × dtype 字节。一个 32 层、8 个 KV 头、head_dim=128 的 bf16 模型，每 token 就是 128 KiB——一条 4K 序列约 512 MiB，10 条并发就是 5 GiB，还没算权重。这正是 PagedAttention 论文（SOSP 2023）的根本判断：LLM 推理的瓶颈不在算力，在 KV cache 的显存管理。传统实现按最长序列预留连续显存，官方博客的统计是：碎片与预留浪费掉 KV 显存的 60%–80%；PagedAttention 分页管理后，浪费只发生在序列最后一块，降到 4% 以内——省下的显存换成更大的并发 batch，这是 vLLM 吞吐优势（论文对比同期系统 2–4×）的主要来源。vLLM 的优化几乎都挂在这条主线上：

优化手段解决什么问题章节
PagedAttention 分页 KV显存碎片、按最长序列预留造成的浪费03
Continuous batching整批等待，短请求被长请求拖住04
Chunked prefill / PD 分离prefill 与 decode 相互阻塞04
Prefix caching公共前缀重复计算08
显存预算与 KV 预估权重 / KV cache / activation 怎么分08
CUDA Graph / torch.compilekernel 启动开销05
FlashAttention / FlashInfer / 融合 MoE算子本身的效率07
投机解码decode 一步只出一个 token、算力闲置06
量化加载（FP8/INT4）权重显存与带宽12
TP / PP / DP / EP单卡装不下、单卡不够快10

还有一条容易被忽略的：新模型的跟进速度。厂商一发新权重，vLLM 靠「注册表 → loader → 权重重映射 → 量化调优」这条管线在几天内支持（第 12 章拆解的就是它），官方宣称的 200+ 模型架构覆盖就是这么来的。反过来，模型架构创新如何推动引擎长出新机制，见第 14 章。

全书词表

各章反复出现的术语收拢在这里，按学习路径顺序排列。「详见」指向讲得最透的章节；读正文遇到陌生词，先回来查这一张表。

术语含义详见
token（词元）模型处理文本的最小单位。文本先经 tokenize（分词）变成 token 编号序列，输出时再经 detokenize 变回文字02
embedding（嵌入向量）token 编号对应的一串数字向量，是模型真正「看」到的输入形式02
logits（未归一化得分）前向最后一层输出：给词表里每个 token 打一个分，采样层再从这里挑 token；取 log_softmax 后即 logprobs06
KV cache（键值缓存）注意力「回看历史」的凭据：每个 token 每层存 K、V 两组向量，随对话变长变大，是显存的大头03
prefill / decode一次生成的两段：prefill 一次算入整个 prompt（算力密集）；decode 每次只进 1 个新 token（带宽密集）04
PagedAttention（分页注意力）像操作系统管内存页一样管 KV cache：逻辑上连续、物理上分块，把显存浪费压到序列最后一块03
block table（块表）每请求一张「逻辑块 → 物理块」的对照表；读历史 KV 靠它，写新 token 靠 slot mapping（槽位号 = 物理块号 × 块内偏移）05
continuous batching（连续批处理）每个 step 把还在生成的请求重新组一次批，新请求随时加入、完成的随时退出，不等整批跑完04
chunked prefill（分块预填充）把过长的 prefill 切成小块分多个 step 算，避免一个长 prompt 卡住整批 decode04
PD 分离（disaggregated prefilling）更彻底的做法：prefill 与 decode 跑在两个独立实例/两张卡上，KV 经高速网络传输04
step（引擎步）引擎主循环的一次迭代：调度 → GPU 前向 + 采样 → 记账，整批重新组批后进入下一步02
prefix caching（前缀缓存）多请求的公共前缀（system prompt、few-shot 示例）只算一遍 KV，后续复用08
MLAMulti-head Latent Attention，DeepSeek 的多头潜在注意力：把 KV 压缩进低秩潜在向量，KV cache 比 MHA 小一个量级14
GQAGrouped-Query Attention，分组查询注意力：多个 query 头共享一组 KV 头，num_kv_heads 变小即省显存08
MoE（混合专家）Mixture of Experts，前馈层换成多个「专家」，每个 token 只激活其中少数几个07
RMSNorm（均方根归一化）/ RoPE（旋转位置编码）transformer 标配的小算子：前者稳定每层激活的数值范围，后者把位置信息旋进 Q/K 向量07
kernel（算子/核函数）GPU 上一次具体计算（矩阵乘、注意力……）的实现。注意力后端（backend）指把 FlashAttention / FlashInfer / TRT-LLM 等实现统一在一套接口下的可插拔层07
GEMMGeneral Matrix Multiply，通用矩阵乘；QKV 投影等大块计算的载体，走 CUTLASS / cuBLAS 高度调优实现07
CUDA Graph（计算图捕获）把一串 GPU 操作录制成一张图、一次提交回放，消除每步成千上万次 kernel 启动的 CPU 开销05
投机解码（speculative decoding）用便宜的「草稿」来源（小模型 / n-gram / MTP 头）先猜 k 个 token，大模型一次前向并行验证，猜对就省了重算、猜错回退——输出分布不变06
MTPMulti-Token Prediction，多 token 预测：模型自带的额外输出头，一次给未来多个位置各出一份草稿，是最常用的草稿来源14
量化（FP8 / INT4 / MXFP4）用更低精度的数字格式存权重和 KV cache：显存减半甚至更多，带宽跟着省，精度损失换容量12
TP / PP / DP / EP四种并行：张量并行（一层切开多卡算）/ 流水线并行（按层分段接力）/ 数据并行（多份副本分流量）/ 专家并行（MoE 专家摊到多卡）10
TTFT / ITL / TPOT服务指标三件套：首 token 延迟（排队 + prefill）/ token 间延迟（decode 相邻间隔）/ 每 token 平均耗时，与吞吐往往此消彼长09
MFUModel FLOPs Utilization，模型算力利用率：实际有效计算量 ÷ 硬件理论峰值，衡量「GPU 有多少在干正事」09
EngineCore / Worker / Model Runnerv1 引擎三层执行主体：EngineCore 独立进程跑调度循环（与前端走 ZMQ）；Worker 是持有模型与 KV cache 的 GPU 执行者；Model Runner 把 batch 变成 GPU 张量并跑前向01
KVCacheSpec（KV 缓存规格）声明一层注意力的 KV 形状/布局的抽象。新模型架构催生专用子类（MambaSpec、SlidingWindowMLASpec……），是架构变迁留在引擎上的「化石层」14
DSADeepSeek Sparse Attention，稀疏注意力 + Lightning Indexer：先粗筛相关 token 再精算注意力，把 MLA 的 KV 进一步省成「只算被索引到的块」14
