2.2第 1 步：入口把「文本」变「token」

调用 generate() 后，_run_completion()（定义在 vllm/entrypoints/offline_utils.py）负责把用户给出的 prompt 处理成引擎能用的形式：文本 → prompt_token_ids。

vllm/entrypoints/offline_utils.py — 摘录
pythondef _run_completion(self, prompts, params, output_type, ...):
    # 1) 把每个 prompt 解析、tokenize，生成 Request（含 prompt_token_ids）
    self._add_completion_requests(prompts=prompts, params=params, ...)
    # 2) 跑引擎主循环，返回所有输出
    return self._run_engine(use_tqdm=use_tqdm, output_type=output_type)
读懂这段：两个阶段分工清晰——「准备（_add_*，把外部输入变成内部 Request）」和「执行（_run_engine，阻塞直到所有请求完成）」。做引擎时建议就采用这种「准备/执行」两阶段 API。

2.3第 2 步：Request 是引擎的「工作单元」

v1 取消了旧版的 Sequence，改用统一的 Request（vllm/v1/request.py）。它是贯穿引擎、调度器、KV cache 的身份证。

vllm/v1/request.py — 关键字段（摘录）
pythonclass Request:
    def __init__(self, request_id, prompt_token_ids, ...):
        self.request_id = request_id            # 唯一 id
        self.prompt_token_ids = prompt_token_ids # 已 tokenize 的输入
        self.num_computed_tokens = 0          # 已计算过多少个 token（KV 已存）
        self.sampling_params = sampling_params  # 采样参数（温度、max_tokens…）
        ...
        self.kv_transfer_params = None        # PD 分离时 KV 跨节点传输参数（非 None 才走）
        self.kv_cache_report_mode = "incremental"  # KV 块占用上报模式（块本身由 KVCacheManager 持有）
核心概念 num_computed_tokens：这是连续批处理的关键计数器。它记录「这个请求的 KV cache 已经算到第几个 token」。新到的请求为 0（还没算过，要做 prefill）；已算过的则从这之后继续算（decode）。调度器正是靠它决定 prefill 还是 decode。

2.4第 3 步：引擎主循环 step()

所有请求被 add 进引擎后，进入核心循环。vLLM 的魔法在于：它不是一条一条请求跑，而是每步把一个 batch 的请求合并成一次模型前向。

vllm/v1/engine/llm_engine.py — step（概念化）
pythondef step(self) -> list[RequestOutput]:
    # 1) 把所有待处理的请求交给 EngineCore（内部是 Scheduler + Worker）
    # 2) Core 选出本步 batch → 分配/复用 KV 块 → 交给 Worker
    # 3) Worker 前向 + 采样，返回每个请求的新 token
    # 4) Engine 侧 detokenize、判断是否结束（stop/max_tokens），
    #    生成 RequestOutput 返回给调用者
    outputs = self.engine_core.get_output()   # 见 core.py：取回 EngineCore 的输出
    processed = self.output_processor.process_outputs(outputs.outputs, ...)
    return processed
读懂这段：「有人负责批处理的前端（Engine），有人负责批处理的决策（Core/Scheduler），有人负责批处理的执行（Worker）」。这三段的职责分离，你的引擎也应当照做——即使单进程时也在逻辑上分清楚。

2.5第 4 步：prefill vs decode

一个请求的一生只有两种「模式」：

  • prefill（预填充/首 token）：一次前向算出 整个 prompt 的 KV cache，并产出第一个 token。计算量大但只发生一次。
  • decode（解码）：每步只算「上一个新 token」对 KV cache 的增量，产出下一个 token。计算量小但反复多次。
prefilldecode
输入长度整个 prompt（可能很长）1 个新 token
计算强度计算密集（算力瓶颈）访存密集（受 KV 读取带宽限制）
KV 增长一次写入多块每次写一块
vLLM 处理chunked prefill（可分块）与其它 decode 请求合并成一大 batch
自研启示 两种模式计算特征不同，是后续所有优化的根源：chunked prefill（把长 prompt 切片喂入避免饿死 decode）、连续批处理（动态加入/移除请求）、以及 speculative decoding（用更小的模型猜 token 减少 decode 步数）。先把「prefill 一次 + decode 循环」跑通，你已经有一个可用的单请求引擎。

2.6从生命周期反向看你的引擎

把这条链「减到最小」就是自研引擎的骨架（这会是第 11 章的起点）：

一个最小引擎的主循环（伪代码）
python# 伪代码：单请求、无批处理的最小引擎
def generate(prompt: str, max_tokens=16) -> str:
    tokens = tokenizer.encode(prompt)          # 1. 文本→token
    kv_cache = alloc_kv_cache(len(tokens))     # 2. 给 prompt 预留 KV
    out_ids = []
    while len(out_ids) < max_tokens:
        logits = model_forward(tokens[-1:], kv_cache)  # 3. 前向（首步是整个 prompt）
        tok = sample(logits)                    # 4. 采样
        out_ids.append(tok); tokens.append(tok)
    return tokenizer.decode(out_ids)          # 5. token→文本
下一步：上面的 kv_cache 是「整个序列一次性分配」，浪费且限制了并发。第 3 章的 PagedAttention 教你把它改成分页、按需分配——这正是 vLLM 每秒吞吐量高的关键，也让你理解为什么它能同时服务几千个请求。
