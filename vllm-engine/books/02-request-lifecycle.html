一条请求的完整路径：从 generate() 到输出 token

第 1 章认了部件，这一章把它们「跑起来」。跟着一次调用问下去：文本进引擎前后发生了什么？一个请求在引擎里长什么样？每一步由谁推进、传了什么？先摆出整条路径，再逐站走读，末了用这条路径反推你的引擎主循环。

2.1生命周期总览（泳道图）

先立起这次走读要回答的问题。从你在客户端写下 LLM.generate("你好") 到屏幕上出现第一个字，中间有五个问题：

  • 文本怎么进引擎？GPU 和模型只认 token id，你给的是字符串。谁来做「文本 → token」这道转换、在哪一站做？
  • 请求长什么样？进了引擎，这次调用变成引擎里的一个什么对象？它要带哪些信息才能在后续几十步里一直被正确处理？
  • 每一步谁来跑？引擎「跑」起来指的到底是什么？主循环的每一步做了哪几件事，循环点在哪？
  • CPU 和 GPU 空等怎么办？CPU 做调度时 GPU 闲着，GPU 前向时 CPU 闲着——这个空档 vLLM 怎么填掉？
  • prefill 和 decode 有区别吗？算完整段 prompt 和续写一个 token，在引擎里是两条流程还是一条？

下面这张泳道图先给出整条路径的全貌——分词和入队在最左上，主循环在中部，「空档」是 vLLM 的隐藏浪费点（2.5 展开），prefill/decode 之问在右下。看不懂具体节点没关系，先记住「文本 → add_request → 循环 → GPU 前向 → 回传」这五个节点，后面逐站走读：

2.2文本怎么进引擎：入口把「文本」变「token」

调用 generate() 后，_run_completion()（定义在 vllm/entrypoints/offline_utils.py）先把用户给出的 prompt 处理成引擎能用的形式：文本 → prompt_token_ids。

vllm/entrypoints/offline_utils.py — 摘录，注释为译注
pythondef _run_completion(self, prompts, params, output_type, ...):
    # 1) 把每个 prompt 解析、tokenize，生成 Request（含 prompt_token_ids）
    self._add_completion_requests(prompts=prompts, params=params, ...)
    # 2) 跑引擎主循环，返回所有输出
    return self._run_engine(use_tqdm=use_tqdm, output_type=output_type)
两个阶段分工清晰——「准备（_add_*，把外部输入变成内部 Request）」和「执行（_run_engine，阻塞直到所有请求完成）」。做引擎时建议就采用这种「准备/执行」两阶段 API。

2.3请求长什么样：Request 是引擎的「工作单元」

v1 取消了旧版的 Sequence，改用统一的 Request（vllm/v1/request.py）。引擎、调度器、KV cache 各环节看到的都是同一个 Request 对象。

vllm/v1/request.py — 关键字段（摘录，注释为译注）
pythonclass Request:
    def __init__(self, request_id, prompt_token_ids, ...):
        self.request_id = request_id            # 唯一 id
        self.prompt_token_ids = prompt_token_ids # 已 tokenize 的输入
        self.num_computed_tokens = 0          # 已计算过多少个 token（KV 已存）
        self.sampling_params = sampling_params  # 采样参数（温度、max_tokens…）
        ...
        self.kv_transfer_params = None        # PD 分离时 KV 跨节点传输参数（非 None 才走）
        self.kv_cache_report_mode = "incremental"  # KV 块占用上报模式（块本身由 KVCacheManager 持有）
核心概念 num_computed_tokens：这是每个请求自带的「进度条」——记录「这个请求的 KV cache 已经算到第几个 token」。新到的请求为 0（KV 还没存任何东西）；之后每步由引擎往前推进。调度器的一切决策（包括这步是补 prefill 还是续 decode）都从「拿它跟目标长度作差」开始，差值怎么用是第 4.2 节的主题。

2.4每一步谁来跑：引擎主循环 step()

所有请求被 add 进引擎后，进入核心循环。循环每步「跑谁、各算多少」由 Scheduler 决定（算法见第 4 章）；本节看这条循环在引擎侧的代码长什么样。

vllm/v1/engine/llm_engine.py — step（概念化，注释为译注）
pythondef step(self) -> list[RequestOutput]:
    # 1) 把所有待处理的请求交给 EngineCore（内部是 Scheduler + Worker）
    # 2) Core 选出本步 batch → 分配/复用 KV 块 → 交给 Worker
    # 3) Worker 前向 + 采样，返回每个请求的新 token
    # 4) Engine 侧 detokenize、判断是否结束（stop/max_tokens），
    #    生成 RequestOutput 返回给调用者
    outputs = self.engine_core.get_output()   # 见 core_client.py：取回 EngineCore 的输出
    processed = self.output_processor.process_outputs(outputs.outputs, ...)
    return processed
分工一句话：批处理的前端在 Engine，决策在 Core/Scheduler，执行在 Worker。这三段，你的引擎也应当照做——即使单进程时也在逻辑上分清楚。
一张图别当真：上面的泳道图和本节代码为了易懂，把循环画成了纯串行——调度完、等 GPU 算完、回传、再调度。真实引擎不会傻等，见下一节。

2.5空档怎么填：重叠执行——CPU 调度 step N+1 时，GPU 在算 step N

2.4 的串行图里有个隐藏浪费：CPU 做调度（选 batch、分配 KV 块）时，GPU 闲着；GPU 在前向时，CPU 闲着。而这两件事用的是不同资源——CPU 调度只碰 dict 和 list，GPU 前向才是重计算。vLLM v1 的解法是异步调度（async scheduling）：GPU 算第 N 步时，CPU 已经在为第 N+1 步做调度，两件事重叠进行，GPU 的空档就被填掉了。

图 2.5：async scheduling 把「下一步的 CPU 调度」与「本步的 GPU 前向」重叠，消除 GPU 等待调度的空档。

开关在 vllm/config/scheduler.py:203，官方注释把动机写得很直白；执行它的调度器是 vllm/v1/core/sched/async_scheduler.py 里的 AsyncScheduler（Scheduler 的子类，1.2 架构图里那个「Scheduler(AsyncScheduler)」说的就是它）：

vllm/config/scheduler.py:203 — async_scheduling 配置（摘录）
pythonasync_scheduling: bool | None = None
"""If set to False, disable async scheduling. Async scheduling helps to
avoid gaps in GPU utilization, leading to better latency and throughput.
"""
为什么要「占位符」：重叠的代价是信息滞后——CPU 为第 N+1 步调度时，第 N 步还没算完，它不知道每请求会产出几个 token。v1 的解法是让请求先持有 num_output_placeholders（vllm/v1/request.py:162）这样的「预计产出数」，按占位符预留 KV 与预算，等真实 token 回来再校正（第 4 章调度代码里 num_new_tokens = num_tokens_with_spec + num_output_placeholders - num_computed_tokens 里那一项，正是为重叠模式准备的）。结构化输出（grammar bitmask）在异步模式下也同理用 pending_structured_output_tokens 占位（见 async_scheduler.py）。自研启示：MVP 用串行循环完全够，等 profile 显示 CPU 调度成为 GPU 之间的可见空档时，再上重叠——这与第 11 章「先对再快」的顺序一致。

2.6prefill 和 decode：是两条流程还是一条

一个请求的一生只有两种「模式」：

  • prefill（预填充/首 token）：一次前向算出 整个 prompt 的 KV cache，并产出第一个 token。计算量大但只发生一次。
  • decode（解码）：每步只算「上一个新 token」对 KV cache 的增量，产出下一个 token。计算量小但反复多次。
prefilldecode
输入长度整个 prompt（可能很长）1 个新 token
计算强度计算密集（算力瓶颈）访存密集（受 KV 读取带宽限制）
KV 增长一次写入多块每次写一块
vLLM 处理chunked prefill（可分块）与其它 decode 请求合并成一大 batch
自研启示 两种模式计算特征不同，是后续所有优化的根源：chunked prefill（把长 prompt 切片喂入避免饿死 decode）、连续批处理（动态加入/移除请求）、以及 speculative decoding（用更小的模型猜 token 减少 decode 步数）。先把「prefill 一次 + decode 循环」跑通，你已经有一个可用的单请求引擎。

2.7从生命周期反向看你的引擎

五个问题走完，把答案串起来：分词在入口做完、Request 带着计数器进引擎、step() 是唯一的循环点、空档用重叠执行填掉、prefill 和 decode 是同一循环的两个瞬间。回到自研视角——把这条链减到最小，就是一个能跑的引擎（第 11 章从这个起点开始搭）：

一个最小引擎的主循环（伪代码）
python# 伪代码：单请求、无批处理的最小引擎
def generate(prompt: str, max_tokens=16) -> str:
    tokens = tokenizer.encode(prompt)          # 1. 文本→token
    kv_cache = alloc_kv_cache(len(tokens))     # 2. 给 prompt 预留 KV
    out_ids = []
    while len(out_ids) < max_tokens:
        logits = model_forward(tokens[-1:], kv_cache)  # 3. 前向（首步是整个 prompt）
        tok = sample(logits)                    # 4. 采样
        out_ids.append(tok); tokens.append(tok)
    return tokenizer.decode(out_ids)          # 5. token→文本
下一步：上面的 kv_cache 是「整个序列一次性分配」，浪费且限制了并发。第 3 章的 PagedAttention 教你把它改成分页、按需分配——这正是 vLLM 每秒吞吐量高的关键，也让你理解为什么它在合适的模型、显存与上下文长度配置下能支撑大量并发请求。
