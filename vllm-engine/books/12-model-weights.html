实战：vLLM 是怎么把开源模型权重加载起来、并让它跑得又快又好的

前面 11 章讲的是「模型已经装好之后」怎么推理。这一章回答另一头的问题：当你说 vllm serve deepseek-ai/… --quantization fp8 时，那几 GB～几百 GB 的 safetensors 是怎么从 HF 变成显存里一个能算的模型的？核心是五件事：认出模型（注册表）→ 选加载器（loader）→ 构建模型结构 → 权重参数重映射 → 量化 / KV 缓存调优。我们拿仓库里真实支持的 DeepSeek-V4、GLM-5.2、Kimi-K2 做例子。
先核实模型名（以仓库为准） 你提到的三个名字，对照本仓库最新代码，有两个有小出入：
  • deepseek-v4-flash → 真实即 DeepSeek-V4（DSA 稀疏 MLA 架构）。其中 flash 不是单独的模型，而是FlashMLA 稀疏注意力后端（DeepseekV4FlashMLABackend，位于 vllm/models/deepseek_v4/）。
  • glm-5.2 → 真实即 GLM-5.2，复用 DeepSeek 的 DSA 设计思路服务：架构名 GlmMoeDsaForCausalLM 注册在 deepseek_v2.py（按 config.model_type == "glm_moe_dsa" 触发 DSA 路径）；DeepSeek-V3.2 的 DSA 模型在 vllm/models/deepseek_v32/，其 __init__.py:7 注释写道 "serves any DSA checkpoint, including GLM-5.2"。
  • kimi2.7 → 仓库里没有 2.7。真实支持的是 Kimi K2.5（vllm/model_executor/models/kimi_k25.py，KimiK25ForConditionalGeneration）与 Kimi-K2.6（vllm/env_override.py 提及）。下文以 K2.5 为准，机制完全相同。
关于代码路径（两套并存） 读本章时你会发现模型代码分散在两个目录，这是 vLLM 正在进行的迁移：新模型（DeepSeek-V4、DeepSeek-V3.2、Kimi-K3）已落在 vllm/models/，旧模型（DeepSeek-V2、Kimi-K2.5 等）仍在 vllm/model_executor/models/。两套目录里的模型都正常工作，注册表会统一解析；下文按各模型的真实位置标注路径，遇到 vllm/models/ 与 vllm/model_executor/models/ 混用时不必困惑。

12.1为什么「加载权重」不是一句 from_pretrained 就完事

PyTorch / HF 里加载模型最朴素的一行是 AutoModelForCausalLM.from_pretrained("huggingface/model")。vLLM 不能用它，因为它要解决三件 HF 默认单机代码不解决的问题：

  • 参数名对不上：HF 保存的权重名（如 model.layers.0.self_attn.o_proj.weight）跟 vLLM 融合/改造后的内部参数名（如 fused_qkv_a_proj、gate_up_proj）不一样，必须重映射。
  • 要能分片与精简：权重要按 TP/PP/EP 切到多卡，还要做算子融合、丢掉推理用不到的张量（filter_files_not_needed_for_inference）。
  • 要能量化：FP8、MXFP4、INT4 等都要在加载时做转换，不是先无损加载再转换——否则显存峰值扛不住。

所以 vLLM 把「加载」拆成了一条可插拔的管线，下面逐段拆解。

12.3选加载器：load_format 决定走哪条管线

模型类确定后，还要决定权重从哪来、怎么流进显存。一个 --load-format / --load-format=… 参数决定了 loader 的选择。全在 get_model_loader 这张表里：

vllm/model_executor/model_loader/__init__.py:48 — load_format → 加载器映射（摘录）
python_LOAD_FORMAT_TO_MODEL_LOADER = {
    "auto": DefaultModelLoader,          # 默认：按文件类型自动判断
    "hf": DefaultModelLoader,

def get_model_loader(load_config) -> BaseModelLoader:
    return _LOAD_FORMAT_TO_MODEL_LOADER[load_config.load_format](load_config)

日常跑这三个模型，默认 auto 走 DefaultModelLoader；当 checkpoint 是 tensorizer 等专用格式、或想多机多进程并行加载时，再切换别的 loader。所有 loader 都继承 BaseModelLoader，因此 load_model 的主流程是共同的。

图 12.2：加载器主流程与调用链。Executor→Worker→ModelRunner→loader（gpu_worker.py:436 / gpu_model_runner.py:5413）。
逐层追源码：gpu_runner.load_model 里 model_loader = get_model_loader(self.load_config)，再 model_loader.load_model(vllm_config, model_config)（gpu_model_runner.py:5433-5434）；而 BaseModelLoader.load_model（base_loader.py:43）依次做「构建结构 → load_weights → 量化收尾 → model.eval()」。

12.4DefaultModelLoader：权重从磁盘进显存

默认走 DefaultModelLoader。它的活分两步：找文件（_prepare_weights）和喂给模型（load_weights）。

vllm/model_executor/model_loader/default_loader.py — 核心两段（摘录）
python# 1) 准备权重文件：按 load_format 选 pattern，本地直接列、远端下载，再精简
def _prepare_weights(self, model_name_or_path, subfolder, revision,
                  fall_back_to_pt, allow_patterns_overrides):
    if not is_local:                         # 远端：按 pattern 下载
        hf_folder = download_weights_from_hf(model_name_or_path, ...)
    if use_safetensors:                      # safetensors 走索引去重
        hf_weights_files = filter_duplicate_safetensors_files(...)   # 去重
    else:
        hf_weights_files = filter_files_not_needed_for_inference(hf_weights_files)

# 2) 把惰性权重迭代器交给各模型的 load_weights（在 load_weights 里调 get_all_weights）
def load_weights(self, model, model_config):
    loaded_weights = model.load_weights(self.get_all_weights(model_config, model))
    self.track_weights_loading(model, loaded_weights)   # 严格校验不漏加载

注意这里 get_all_weights 返回的是一个惰性的权重迭代器（(name, tensor) 对），不是一次性全部塞进内存——几百 GB 的 MoE 是一块一块流式处理的。而且加载完会校验 loaded_weights 集合，确保没有参数「漏载」（对非量化模型默认开严格检查，default_loader.py:434-445）。

自研启示：你的引擎第一步不必支持多种格式，先做一个 DefaultModelLoader + safetensors 就够；但「惰性迭代 + 严格校验」这个习惯值得从一开始就养成——它直接决定了你能不能加载几百 GB 的模型而不爆内存。

12.5真正的魔法：load_weights 的参数重映射

模型框架 initialize_model 建好后，HF 权重还散在磁盘里。真正把「HF 参数名 → vLLM 内部参数名」对齐的，是每个模型自己实现的 load_weights。vLLM 为了跑得快，常常把多个 HF 权重融合成一个，例如 q_a_proj + kv_a_proj_with_mqa 合并为 fused_qkv_a_proj。这段映射在 DSA 模型里写得非常直白，以 DeepSeek-V3.2 为例（GLM-5.2 的 GlmMoeDsaForCausalLM 继承自同族基类，思路一致）：

vllm/models/deepseek_v32/nvidia/model.py:314 — DSA 模型的参数重映射（摘录）
pythondef load_weights(self, weights) -> set[str]:
    # 熔断式参数映射： (vLLM 参数名, HF 权重名前半段, 切到哪个 shard)
    stacked_params_mapping = [
        ("gate_up_proj",     "gate_proj", 0),
        ("gate_up_proj",     "up_proj", 1),
        ("fused_qkv_a_proj", "q_a_proj", 0),
        ("fused_qkv_a_proj", "kv_a_proj_with_mqa", 1),
        ("wk_weights_proj",  "wk", 0),
        ("wk_weights_proj",  "weights_proj", 1),
    ]
    for name, loaded_weight in weights:
        if "rotary_emb.inv_freq" in name: continue      # 推理不需要
        # …查 stacked_params_mapping，把 HF 张量塞进融合后的 vLLM 参数…

这一小段就是「让模型跑得快」的结构性前提：把 attention 的 Q/KV 三份投影拼成一个大矩阵，就能一次 GEMM 算完，减少 kernel 启动与显存搬运。再用 default_weight_loader（weight_utils.py）按名把每个张量 copy_ 到位。

图 12.3：stacked_params_mapping 把若干 HF 小投影「拼」成一个 vLLM 大投影，一次 GEMM 处理更多参数。
逐行拆解：(param_name, shard_name, shard_id) 三件套的意思是：vLLM 的 param_name 由 HF 的 shard_name 在 shard_id 这个位置拼接而成。读权重的循环里看到 gate_proj 就写进 gate_up_proj 的 0 号切片，看到 up_proj 写进 1 号切片。这不只是「换个名」，而是真的把两个矩阵贴在一起变成一个更大的算子输入。

12.6让它「跑得好」：量化 + KV cache + 稀疏后端的组合拳

权重加载进来了。但「跑得好」还差最后一层：用什么 dtype 存权重、用什么格式存 KV、用哪个注意力后端。三者必须配合，DeepSeek-V4 / GLM 这类 DSA 稀疏模型尤其如此。

  • 权重量化：FP8 / MXFP4 等。vllm/models/deepseek_v4/quant_config.py 是 DeepSeek-V4 的量化配置；GLM-5.2 也常见 amd/GLM-5.2-MXFP4 这类已量化 checkpoint（见 quark/utils.py 注释）。权重越小，I/O 越省、显存越够。
  • KV cache dtype：稀疏 MLA 用的是 --kv-cache-dtype fp8_ds_mla 的专用分页布局（FlashMLA 稀疏）。见 vllm/v1/attention/backends/mla/sparse_swa.py:90——fp8_ds_mla 还需要 576B 对齐。
  • 注意力后端：DeepseekV4FlashMLABackend（FlashMLA 稀疏）等通过 vllm/v1/attention/backends/registry.py 注册，按平台选 NVIDIA/AMD/XPU 的实现。

12.7开源权重仓库长什么样：三个真实 checkpoint 的目录结构

前面 12.3–12.6 讲的是加载管线怎么「吃」权重。那权重本身，在 HuggingFace / ModelScope 仓库里到底长什么样？这一节拿三个真实 checkpoint 的目录结构做对照——它们恰好覆盖了「标准仓库 / 带 chat_template / 需远程代码」三种典型形态，每一种都会在加载管线上踩到不同的坑。

模型名对齐 这三个 checkpoint 与本章所用模型家族的对应：DeepSeek-V4-Flash-0731 是 DeepSeek-V4（DSA）系列的一个具体版本；GLM-5.2 即 12.6 / 12.8 的 GLM-5.2；Kimi-K3 是比 12.8 表中 K2.5 更新的一代（K2.5 已原生进 vLLM，K3 仓库自带自定义建模代码，集成路径见下）。注意 DeepSeek-V4-Flash 里的「Flash」是 checkpoint 命名（该版本主打 FlashMLA 稀疏后端），与 12.6 的 FlashMLA 后端同名但所指不同——这个 checkpoint 仍由 DeepSeek-V4（DSA）模型代码服务。

自研启示 你的引擎不需要一上来就支持这三家。推荐的落点：先把 safetensors → 注册表/模型类 → load_weights 这条链做通，支持一个标准 Dense 模型（比如 LLaMA），验证正确性；等需要 MoE 或稀疏模型时，再学着加「多权重融合（12.5）」和「量化 + KV dtype + 后端的协同（12.6）」——这两件恰恰是 vLLM「跑得好」、而一般手写代码跑不动的分水岭。它们共通的心法：先保证一个默认路径端到端正确，再做为了性能而做的各种“映射与剪裁”。
延伸阅读 权重加载与「跑得好」还牵扯两个已讲过的主题：第 8 章显存预算（权重吃掉多少显存）和 第 10 章分布式（权重怎么按 TP/EP 分片）。把这三章连起来读，你就完整掌握了「一个大开源模型从盘上到多卡高速服务」的全程。
