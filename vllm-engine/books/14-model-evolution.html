实战：追踪国产开源模型的架构变迁——同一个趋势，四家四种走法，引擎各付了什么代价

第 12 章讲了「权重怎么装进显存」，这一章往前一步讲「模型本身在怎么变」。近一年 DeepSeek、智谱、月之暗面、通义四家的旗舰模型都在改同一件事——注意力和状态的表达方式：稀疏注意力怎么省索引开销、线性注意力怎么替代越写越长的 KV cache、残差流要不要拆成多条。本章以引擎视角追踪这条线：每一家在 vllm/models/ 里落地成了什么，架构上每动一刀，引擎被迫补了哪些机制（KV cache spec、ModelState、CacheDType、注册表）。四家原型：DeepSeek-V4/V4.1、GLM-5.2/5.3-Flash、Kimi-K2.6/K3、Qwen3.8-27B/Flash-Next。
本章材料从哪来 模型侧事实（参数量、训练配方、benchmark）来自各团队的发布材料；引擎侧事实（类名、文件、行号）全部核对自本仓库 vLLM 源码（版本 proto-v0.3.0-307-g94f4170df3，与前 13 章同一锚点）。本章不复述模型发布稿——那不是 vLLM 这本书该干的事——只回答一个问题：这些新架构到达引擎时，长成了什么样的代码？

14.1模型迭代的速度已经快过引擎的「通用层」，引擎怎么跟

这一章要回答的问题是：近一年四家旗舰模型都在改注意力和状态的表达方式，每动一刀，引擎被迫补了哪些机制？答案按家分节：14.2 DeepSeek、14.3 GLM、14.4 Kimi、14.5 Qwen；14.6 横向对照收敛与分化，14.7 汇总「被迫新增」的接入接口。为什么这个问题值得单开一章？vLLM 前几年的模型接入方式很稳定：新模型来了，写一个 nn.Module，注册进 ModelRegistry，注意力后端如果特殊就加一个 AttentionBackend。大部分「模型差异」被压在模型文件内部，引擎通用层（调度器、KV cache 管理器、采样器）感知不到。

这一批国产旗舰把这个边界打破了。同一个 config.json 里会出现线性注意力层和全注意力层混排（Kimi-K3 的 69+24、GLM-5.3-Flash 的 sparse+linear）、残差流从一条变成多条（DeepSeek-V4 的 mHC、Qwen4Exp 的 GatedResidual）、注意力索引器的开销被当成一等公民来优化（GLM 的 IndexShare/IndexPool、Qwen 的 QSA）。本章会反复出现几个缩写，先各用一句话说清它们解决的问题，细节留到对应小节：

  • DSA（DeepSeek Sparse Attention）：注意力只对 indexer 选出的 top-k 块计算，解决「长序列下全注意力 KV 读取太贵」。
  • KDA（Kimi Delta Attention）：线性注意力，解决「KV cache 随序列长度线性增长」——把缓存换成固定形状的循环状态（14.4）。
  • QSA（Queried Sparse Attention）：Qwen 的块级稀疏注意力，解决「稀疏化粒度」问题——按 micro-block 而非逐 token 选块（14.5）。
  • PLE（n-gram 短语级嵌入表）：一张 2000 万行的 n-gram 嵌入表插进第 2 层，解决「小激活模型记不住 few-shot 上下文里的表面模式」——直接查表抄（14.5）。
  • DSpark：DeepSeek/Kimi 配套的轻量草稿模型，用于投机解码（speculative decoding，第 6 章 6.7）。
  • mHC / GatedResidual / AttnRes：残差流的多通道变体，解决「单条残差流不够用」（14.2 / 14.4 / 14.5）。

这些不再是「模型文件内部的事」：

  • KV cache 不再只有一种形状——MambaSpec、KpoolTailSpec、SlidingWindowMLASpec 这些新的 KVCacheSpec 子类都是为了承接某一家的架构而生；
  • 模型开始要求在 runner 层拥有自己的状态管理——get_model_state_cls() 这个钩子就是为 Qwen4Exp 的 n-gram 上下文缓冲加的；
  • 量化 KV 的取值范围一路扩容——CacheDType 里 fp8_ds_mla、turboquant_k8v4、nvfp4_4over6 这些名字每一个都对应一家或几家的具体方案。

所以追踪架构变迁，最可靠的位置不是发布稿，而是引擎里这些「被迫新增的机制」。它们是架构变更留在引擎上的化石层。

图 14.1：本章结构。每个观测点都按同一顺序拆解——模型改了什么、落成什么代码、引擎被迫补了什么机制。

14.2DeepSeek：DSA 定型之后，V4 的变化转向残差流和 MoE

DeepSeek-V3.2 用 DSA（DeepSeek Sparse Attention + Lightning Indexer）确立了「稀疏 MLA」这条线：一个轻量 indexer 先为每个 query 选出 top-k 相关块，注意力只在这些块上算，长序列下省掉大部分 KV 读取；GLM-5.2 直接复用这套设计（GlmMoeDsaForCausalLM 落在哪个模型类，是加载问题，见第 12 章）。到 DeepSeek-V4，注意力侧延续 DSA，变化转移到了两个新位置：残差流的拓扑和 MoE kernel。

图 14.2：DeepSeek-V3.2 → V4 的变迁位置。注意力延续 DSA，变化转移到残差流（mHC）与 MoE（MegaMoE）；下排是每处变化迫使引擎新增的机制。

V4 在 vllm/models/deepseek_v4/ 落地，硬件隔离成 {__init__.py, nvidia/, common/} 三件套。先看注意力后端的选择逻辑：

vllm/models/deepseek_v4/nvidia/model.py — 按平台选稀疏 MLA 后端（摘录，行号 1086–1117）
pythondef _select_dsv4_attn_cls(...):
    # 两套稀疏 MLA 后端并存：FlashMLA 与 FlashInfer
    # SM120/130 等新卡默认走 FlashInfer 变体

DeepseekV4FlashMLAAttention 与 DeepseekV4FlashInferMLAAttention 实现同一个 DeepseekV4Attention 抽象基类。「同一架构、两个 kernel 供应商」是 V4 时代的新常态，第 7 章讲 kernel 分层时提过这个趋势，V4 把它带进了稀疏注意力。锚点：nvidia/flashmla.py:51、nvidia/flashinfer_sparse.py:195、基类 attention.py:173。

残差流是更大的变化。经典 Transformer 只有一条残差流，子层输出逐层相加；层数深了之后，单条流要同时承载注意力、MLP、多种语义信息，成为表达瓶颈。V4 用 mHC（multi-head connection）把它拆成多条并行的通道，层间交互用一个小的路由矩阵混合——每个子层在多条通道上独立计算，跨层时由路由矩阵决定信息怎么在通道间流动。引擎侧对应的实现：

vllm/model_executor/kernels/mhc/tilelang.py — mHC 的 TileLang kernel（摘录，行号 542–550）
pythondef mhc_pre_tilelang(...,
                      hc_sinkhorn_eps: float,
                      sinkhorn_repeat: int, ...):

mHC 的路由矩阵在训练时用 Sinkhorn 迭代约束成近双随机，推理时这个迭代成本还在——hc_sinkhorn_iters 配置项直接暴露给用户，模型的正向传播里（nvidia/model.py:1333–1408）串起 mhc_pre_broadcast_tilelang 和 mhc_fused_post_pre_tilelang 两个 kernel。这是「残差流拓扑」第一次成为引擎要专门写 kernel、专门暴露配置的东西。

图 14.3：两种残差流变体的形态对比。mHC 是「多条通道 + 跨层路由矩阵（Sinkhorn 约束，推理时仍要迭代）」；GatedResidual 是「多条分支 + 逐支路标量门」，没有跨层混合，kernel 成本低一档。

MoE 侧的变化是 MegaMoE——把 MoE 的 expert 计算合并进一个大 GEMM 后端（deep_gemm_mega_moe），在 SM100 上替换通用 grouped GEMM 路线。引擎侧落点：DeepseekV4MegaMoEExperts 走该后端且只在 SM100 上可用；vllm/config/kernel.py 里 MEGA_MOE_BACKENDS 与 FlashInfer 的 moe_ep 后端并列为合法取值。锚点：nvidia/model.py:211（SM100 检查在 :369）、vllm/config/kernel.py:157。

另一个值得注意的点是 KV cache 规格的专用化：SlidingWindowMLASpec 在代码里明确标注 model_version 只接受 "deepseek_v4"——一个 KVCacheSpec 子类只服务一个模型，这在以前的通用缓存设计里不可想象。这类新规格（连同 KpoolTailSpec、MambaSpec）在 14.7 的清单里集中盘点。

V4.1 的增量（视觉多模态、DSML、数值化的 reasoning_effort）在引擎侧体现为 DeepseekV4ForConditionalGeneration（common/vl_model.py:86，nvidia/vl_model.py 只剩转发）——多模态版走 conditional generation 的注册形态，与第 12 章讲过的 Kimi-K2.5 同一模式。

V4.1 的注意力在 2026-09 又落了一刀（d6a1677d55）：FlashMLA 的 mega attention kernel 成了 SM100 上的默认选择，并带来一种新的压缩 KV 记录 nvfp4_ds_mla。先说它是什么：mega 指 kernel 一次吞下四件事——Q 的 RoPE、稀疏注意力、输出的逆 RoPE、输出转 FP8；后端名 FLASHMLA_MEGA_ATTN_DSV41，注册在 registry.py:117。

它为什么改写了接口契约：过去 Q 侧的 norm/RoPE 由注意力层外面的代码做，mega 层声明自己要的是未经 norm、未经 RoPE 的原始 wq_b 输出（基类新增 accepts_unnormed_unroped_query 属性，attention.py:202），Q 侧的活儿它自己干——于是 fused KV insert 那一发对 Q 只剩零填充（TP1 下 shard 已够宽时连填充都免了，attention.py:974-1050 的 apply_q_rope/is_q_interleaved 两个开关就为此加的）。输出也不必再单独量化——kernel 吐出的已是带 per-32-group scale 的 FP8（QuantizedActivation），wo_a 直接吃。权重的对策是在加载后一次性重排 wq_b 行、wo_a 列，让 GEMM 直接吐出 kernel 要的 chunk-interleaved 布局，免去每步搬运（flash_mla_mega_attn.py:232-247 的 finalize_loaded_weights）。

值不值得开，取决于 TP 而非 batch——这句就印在文件头。原因是：kernel 吸收的活随活跃头数缩放，自己的开销却按填充后的头数算（FlashMLA FP8 decode 只认 64/128 头），所以 TP1 赚到最多（GB300 实测至 1.45 倍），TP2 起两者相抵。

NVFP4 记录是另一面。滑动窗口 cache 保持 V4.1 的 528B MXFP8 记录，压缩 cache 换成 288B 的 NVFP4（512 个 e2m1 值两两一字节 + 32 个 e4m3 scale，各 16 维一组；cache_utils.py:38-54）——每 token 288B 对 528B，省的正是长上下文里大头的那份拷贝。这个记录只有 mega kernel 读得动，所以不指定 --kv-cache-dtype 时该层会把它作为默认解析目标（packed_kv_cache_dtype，attention.py:212-219）；对非 SM100 则整个退回普通 FlashMLA 路径。锚点：mega 层 nvidia/flash_mla_mega_attn.py:143（可用性判定 :148-170）、后端 sparse_mla.py:235、布局重排 common/ops/fused_layout.py:18。

DeepSeek 线说到这里可以收一句：变迁重心已经从「注意力怎么稀疏」移到「残差流怎么组织、MoE kernel 谁来供」。对引擎的含义是：模型定义的不再只是前向计算图，还包括残差流的拓扑和 MoE 的执行策略。

14.3GLM：同一个 DSA 索引器，两代模型给出两种省法

DSA 路线有个绕不开的税：Lightning Indexer 每层都要为每个 query token 算一遍与全序列 key 的索引分数，选出 top-k 个块再做稀疏 MLA。注意力本身省了，索引器自己却成了新的开销点。GLM 两代模型给出了两种不同的省法，恰好对应引擎里两个不同的实现。

图 14.4：DSA 的索引税与两种省法。5.2 在「层数」维度省钱（跨层共享同一份 top-k 索引）；5.3-Flash 在「每次算多少」维度省钱（先把索引器的 key 池化压缩）。

GLM-5.2 的省法：跨层共享。相邻几层共用同一份 top-k 索引，算一次用多次。引擎里这个机制其实先在 DeepSeek-V3.2/GLM-5.2 共用的 deepseek_v2.py 里落地：

vllm/model_executor/models/deepseek_v2.py — IndexCache 与跳层算索引（摘录，行号 1141–1146、1645–1663）
python# IndexCache config / Refer: https://arxiv.org/abs/2603.12201
# skip_topk 的层模式：max(layer_id - offset + 1, 0) % index_topk_freq != 0 的层不建索引器

# load_weights 里的一个容易困惑的点：
# checkpoint 给每一层都存了 indexer 权重，但 freq>1 时只有部分层真的建了索引器——
# 加载时要主动丢弃用不上的那份

这套机制后来被 MiniMax（ATOM）独立采用过：vllm/models/minimax_m3/amd/model.py:156 的 _should_skip_index_topk 注释写明「相邻稀疏层选出的块几乎相同」，并报告了 ATOM 用 freq=4 在 GSM8K 上验证过不掉点的实验结果。启用方式是 --hf-overrides '{"use_index_cache": true, "index_topk_freq": 4}'。两家不同团队做了同一个尝试——这是该方向可行的信号，但结论仍应按自己的模型和任务复测。

GLM-5.3-Flash 的省法：压缩索引器自己的 key。它不共享，而是把索引器的 key 先池化——连续 index_kpool 个 token 压成一个 fp8 的 K 再算索引分。模型落在独立目录 vllm/models/glm5next/（架构名 Glm5NextForCausalLM），核心类是 SparseAttnIndexerKpool。配置项 index_kpool: int | None = 4，即默认 4:1 压缩。锚点：注册表 registry.py:122、核心类 vllm/models/glm5next/nvidia/sparse_indexer.py:622、配置 vllm/transformers_utils/configs/glm5_next.py:73。

这个省法在引擎侧的代价明显更大。池化改变了索引器元数据的粒度，KV cache 管理器必须跟着改：

vllm/models/glm5next/common/attention.py — Kpool 索引器缓存对 block_size 的约束（摘录，行号 78 起的 docstring 与 116–120；类本体 :78）
python# tokens_per_state = index_kpool 时，indexer metadata builder 会改发

# 因此 block_size 必须是 index_kpool * 32 的倍数（index_kpool=16 时即 512）

assert block_size % index_kpool == 0

除了 assert，还有一个新的 KVCacheSpec 子类专门接住池化后的尾部：KpoolTailSpec（vllm/v1/kv_cache_interface.py:988），注释称它是「给 kpool 索引器裸尾部用的一块环形草稿缓存」，且 prefix_cacheable=False——这部分缓存不参与前缀复用。GLM-5.3-Flash 同时是 sparse+linear 混合架构，线性层用 Glm5NextLinearAttention（glm5next/common/kda.py:153，继承自 GatedDeltaNet），这部分留到 14.5 一起讲。

图 14.5：KPool 的引擎代价。池化让索引计算量缩为 1/kpool，但序列尾部的「未满池」需要一块独立的环形草稿缓存，且它被排除在前缀复用之外。

同一个索引器开销问题，5.2 选择「少算几层」，5.3-Flash 选择「把被算的东西变小」。引擎为前者付出的代价是权重加载时的丢弃逻辑，为后者付出的是新的缓存规格和 block_size 约束。

14.4Kimi：从纯 MLA 到 KDA 混合，外加注意力残差这个新变量

Kimi-K2.6 还是纯 MLA（1T 参数、32B 激活），到 K3（2.8T/104B）架构动了两处：层布局改成 69 层 KDA（Kimi Delta Attention，线性注意力）+ 24 层 Gated MLA 的 3:1 混排；注意力残差（AttnRes）让每个块能回读上一个块的输出。K3 落在 vllm/models/kimi_k3/，同样按 14.2 那套「硬件隔离三件套」的目录惯例组织，__init__.py 的 docstring 注明布局「镜像 vllm.models.minimax_m3」。

图 14.6：Kimi-K3 的层混排与两种缓存的显存行为。KDA 层把「缓存」从随长度增长的 KV 换成固定形状的循环状态，这就是 MambaSpec 要表达的东西。

层分派按 is_kda_layer() 走（vllm/transformers_utils/configs/kimi_linear.py:157–161，判断式是 (layer_idx + 1) in kda_layers）。模型文件里的分支：

vllm/models/kimi_k3/nvidia/model.py — KDA/MLA 分派与 NoPE 约束（摘录，行号 880–911）

    # use_full_rank_gate 时走私有的 KimiK3DeltaAttention，否则用通用 GDN 实现
    ...
# MLA 一侧有个断言值得记住：
# "Kimi-K3 MLA (MultiHeadLatentAttention) is NoPE-only"
# —— K3 把位置信息全部交给 KDA 层，MLA 层不带 RoPE

KimiK3DeltaAttention（nvidia/kda.py:475）改编自 flash-linear-attention 项目，文件头保留了对方的版权声明；运行时状态由 kimi_gdn_linear_attn.py 管理。对引擎来说，线性注意力层的「缓存」不再是随序列增长的 KV，而是一个固定形状的循环状态：

vllm/model_executor/layers/mamba/mamba_utils.py — KDA 状态形状（摘录，行号 303–326）

这就是 MambaSpec（vllm/v1/kv_cache_interface.py:1014）要表达的东西——KV cache 这个概念在 K3 里被推广成「注意力状态」，长序列下的显存曲线从线性变成常数。代价是调度器和内存管理要为这种固定形状状态单独建池，第 8 章讲过的 KV cache 管理器由此多了一个平行体系。

AttnRes 是另一处引擎可感知的变化：attn_res_block_size（config，kimi_linear.py:51）把层分组，组内每层配一个 self_attention_res_proj / mlp_res_proj（ReplicatedLinear(hidden,1)，nvidia/model.py:974–987），前向时逐标量门控回读上一块输出（调用点 :1016–1026、:1049–1061）。它不动 KV cache，但改写了 DecoderLayer 的前向结构——任何 fork vLLM 自己实现 K3 的人，漏掉这组投影权重就会加载报错。

图 14.7：注意力残差（AttnRes）的数据流。它不改 KV cache，只往 DecoderLayer 里加了一组标量门控回读边。

Kimi 线到这里也收一句：把「KV cache」这个词拆开了——MLA 层的还是 KV，KDA 层的是固定状态，AttnRes 再往层结构里塞了一条回读边。

14.5Qwen：小模型先探路，Flash-Next 把三条新机制凑齐

Qwen3.8-27B 是这一批里最小的模型（dense，27B），架构试探反而最激进：每 4 层配 3 层 GDN（GatedDeltaNet，线性注意力——解决的问题与 14.4 的 KDA 同源，机制见该节）+ 1 层 GQA 的 3:1 混排，外加 YaRN 长文本扩展。到 Flash-Next（125B/6B 激活），Qwen 把散落在各家的新机制一次凑齐：块级 QSA 稀疏注意力（按 micro-block 选块的稀疏化）、GatedResidual 残差变体（多分支 + 逐支路标量门，mHC 的简化版）、n-gram PLE 嵌入（2000 万行的 n-gram 查表，让小激活模型能直接从上下文抄表面模式），外加 51B 的 n-gram 草稿模型和 4B MTP 头。

模型落在 vllm/models/qwen4_exp/，配置类 Qwen4ExpTextConfig 继承自 Qwen3NextConfig（config.py:34）；hc_count、hc_lowrank、ple_layer_ids、ngram_size、ngram_vocab_size_base 这些关键字段的取值，随下文各机制首次用到时给出。

先看残差。同样的「单条残差流不够用」问题（14.2），DeepSeek 和 GLM 用 mHC（Sinkhorn 约束的路由矩阵做跨层混合），Qwen4Exp 用的是更简单的 GatedResidual——4 条并行分支，每条一个 learned gate，没有跨层路由：

再看 QSA（Queried Sparse Attention）。GLM 的两条路线都在 token 粒度上做文章，QSA 把稀疏化的粒度抬到 micro-block：索引器（QSAIndexer）用 MQA 形态算块分数，预算是 token_topk=config.indexer_budget（512 块 / 2048 token）。它对精度形态挑剔——要求 BF16 和 paged KV，注意力后端是专门的 Qwen4ExpQSAFlashAttentionBackend（继承 FlashAttentionBackend）。锚点：索引器 nvidia/indexer_qsa.py:89（预算 :114-117、精度约束 :110-111）、后端 nvidia/qsa.py:64。

挑剔最近松了一半：QSA 路径的主 KV cache 现在可以是 fp8_e4m3（dff1bde84d）。分三段看这件事——先说结论，再说 QSA 为什么能绕开常规 fp8 后端的限制，最后看 kernel 与权重侧的配套改动。

结论：模型 dtype 仍锁 BF16（indexer_qsa.py:110-111 的门没动），变的只是主 KV cache 的存储精度——写入仍是常规 reshape_and_cache，读侧才见反量化。

为什么 QSA 能支持，常规后端不能：flash-attn 对量化 KV 有探测、不支持就整个拒绝；而 QSA 根本不在量化 cache 上跑 flash-attn，反量化在自己的 Triton kernel 里做。所以后端类把 supported_kv_cache_dtypes 扩到 fp8/fp8_e4m3，并重写 supports_combination 全盘放行（nvidia/qsa.py:96-99）；构造函数里有个小迂回：先对父类谎报 auto 绕过它的 fp8 探测，构造完再改回真实 dtype（:153-169）。

kernel 与权重侧的细节（锚点密集，按数据流顺序）：读侧 forward 时把 uint8 cache 按位重解释成 e4m3（同 itemsize，形状步长不变，:217-221），k_scale 预乘进 softmax 缩放、v_scale 当作输出缩放，都是 host 标量，kernel 不需要 device scale 缓冲（ops/qsa.py:608-613）。kernel 内部还有两处精挑：QK 点积前先把 e4m3 升格到 Q 的 dtype（fp8 QK 实测更慢更不准），PV 点积把 V 降格到 fp16 而非 bf16——概率 P ≤ 1 时 fp16 尾数更宽、升格也更快（ops/qsa.py:153-172）。权重侧配了个 checkpoint 兼容层：常规注意力的 cache scale 挂在 attn 子模块下，QSA 层直接持有 cache，_remap_qsa_cache_scale_name 在加载时把这些 scale 名改挂到 owner 的 _k_scale/_v_scale 常驻缓冲（nvidia/model.py:94-127）。

最后是 n-gram PLE 嵌入，这是本章四家里引擎侧牵动最大的一处。它解决的问题是：小激活模型的容量都给了「推理」，在 few-shot 场景记不住上下文里的表面模式——PLE 在第 2 层插一张 2000 万行的 n-gram 嵌入表，让模型能直接从上下文抄 n-gram 级别的表面信息，不用「学会」。结构分三层：真正的嵌入表 Qwen4ExpPLEEmbedding 继承 PLEVocabParallelEmbedding；外层是容器类 Qwen4ExpNGramEmbedding（一个 nn.Module，按 cpu_offload 选 pinned-host 或 device 实现），持有为 self.ngram_embedding；按 head 拆成素数大小的子词表由 _make_vocab_layout 完成。这套结构本身不难，真正的麻烦在下一层——它的查表结果随上下文变化，而 CUDA graph 要求每次重放的输入形状不变。模型层自己管不了这件事，于是 vLLM 开了一个通用扩展点。锚点：容器类 nvidia/ngram_embedding.py:535、PLE 嵌入子类 :52、基类 common/ple.py:80、子词表布局 nvidia/ngram_embedding.py:613、挂载点 ple_layer.py:96。

三件收敛的事：

图 14.9：跨家族收敛（限于本章样本）。索引器省法三条路线（共享 / 压缩 / 换粒度）指向同一结论；四家新模型均带 MTP；残差流在四家全部从单条变多条。
  • 本章选取的四个模型家族，MTP 无一缺席。这四家的新模型全部注册了 MTP 模型（registry.py:674–704 一整段 MTP 注册），且 method="mtp" 已是规范名，家族专名（DeepSeek MTP、Glm5Next MTP…）在 vllm/config/speculative.py:1132–1137 标记为废弃。在这个样本里，推测解码从「可选加速」变成了旗舰模型的标配；是否是行业普遍做法，样本之外未必成立。
  • 索引器开销被当成独立问题。共享（DeepSeek/GLM/MiniMax）、压缩（GLM KPool）、换粒度（Qwen QSA）三种方案并存，指向同一个判断：「稀疏注意力本身不是瓶颈，索引才是」。
  • 残差流成了可调结构。mHC、iHC（Hunyuan-V4，hc_mult 并行通道）、GatedResidual、AttnRes 四种变体出现在四个团队，细节各异，方向一致：单一流不够用了。

分化的一件事是稀疏 vs 线性的路线选择：DeepSeek 坚持全 DSA，Kimi 和 Qwen 大比例押注线性注意力，GLM 两头下注。这不是纯技术分歧——线性注意力牺牲精确检索能力换常数显存，各家按自己的目标场景（长上下文 agent vs 通用对话）取舍。对引擎使用者的含义很直接：选模型前先看它的注意力构成，KDA/GDN 为主力的模型在超长上下文下显存优势巨大，但在需要精确检索的任务上要先做评测。

14.7新一代模型接入接口——从 nn.Module 到完整合约

回到 14.1 的问题：这一批模型每动一刀，引擎被迫补了哪些机制？先把「接入一个模型」在 vLLM 里意味着什么，新旧两版各说一遍——差别比看起来大。

旧式接入（也是绝大多数教程里教的那种）：模型实现一个 nn.Module，提供 forward(input_ids, positions, intermediate_tensors)，在 registry.py 里登记架构名，完事。至于 KV cache 长什么样——默认页 + 默认 dtype；运行时状态怎么管——runner 统一包办；要不要草稿——那是用户开不开的配置项。引擎背后的假设是：模型只是个纯函数，一切运行时资源由引擎单方面推断。Llama 时代这样够用，因为所有模型的注意力都长得一样：一个 head_dim、一种 dtype、一块矩形分页缓存。

本章的四个家族把这套假设逐条打碎。上一节那三条收敛与一条分化，落到引擎侧就是一张「被迫新增」清单——如果你要在自己的推理栈里支持这一代模型，它就是工作量清单：

  • KVCacheSpec 家族扩容：SlidingWindowMLASpec（kv_cache_interface.py:909，绑死 deepseek_v4）、KpoolTailSpec（:988，不可前缀复用的草稿块）、MambaSpec（:1014，含 tp_replicated 标志与 KDA 形状）。缓存规格从「页大小 + dtype」的二维描述，膨胀成按模型家族定制的对象体系。
  • CacheDType 扩容（vllm/config/cache.py:39–58）：fp8_ds_mla、nvfp4_ds_mla（DSA 专用）、turboquant_k8v4 / _4bit_nc / _k3v4_nc / _3bit_nc（Kimi 系）、int4/int8/fp8_per_token_head、nvfp4、nvfp4_4over6。每一项背后是一种 KV 量化的精度/布局折中。
  • ModelState 扩展点（v1/worker/gpu/model_states/__init__.py:28）：模型第一次有了「接管 runner 层状态」的合法通道，Qwen4Exp 是第一个用户，但机制是通用的。
  • 推测解码体系重组：MTP 规范名统一、DSpark 草稿模型入册（DSparkDeepseekV4ForCausalLM、K3DSparkForCausalLM，经 DSparkMarkovHead/DSparkConfidenceHead 复用 qwen3_dspark 的实现）、K3 的 RecoverSSM（vllm/config/vllm.py:3333–3373：KDA 推测解码时自动启用，白名单只放 Kimi 两个架构，mamba_cache_mode 限 none/align）。
  • MTP 与稀疏索引的协同：index_share_for_mtp_iteration（vllm/config/speculative.py:443）——多步草稿时 top-k 只在第 0 步算，后续步复用，glm5next/common/mtp.py:146 的 set_skip_topk 是执行点。推测解码和稀疏注意力不再各自为政。

把「旧式合约」和「新式合约」并排放进一张表，差距就不再是「多了些类」，而是「换了签署方式」：

合约条款旧式：nn.Module 接入新式：完整合约
计算实现 forward()，就这一条同左——这条没变，但它从「全部」降格为「其中之一」
KV 缓存形状引擎默认推断：一种分页布局，页大小、dtype 由配置决定模型申报 get_kv_cache_spec()：逐层返回自己的 spec（MLA+滑窗、KDA 状态块、不可复用的草稿块……）
KV 精度auto/fp16/bf16/fp8，全模型一个值模型家族决定合法 dtype 集（fp8_ds_mla 等只在 DSA 家族合法），并与注意力后端联动校验（7.3 的 validate_configuration）
运行时状态模型不得触碰 runner 状态get_model_state_cls() 申报状态类，PLE 预取这类需求有了合法入口（Qwen4Exp 首用，机制通用）
草稿策略与模型无关的外挂配置（ngram / eagle…）MTP 是模型自带组件（注册进 registry.py），草稿模型复用主干实现（DSpark 家族），KDA 架构自动启用 RecoverSSM——「会不会自己给自己当草稿」写进了架构
接入验收跑通 forward 就算接入完成还要过：KV spec 与后端能力匹配、dtype 在家族白名单、speculative 注册齐备——任何一条缺失都在启动期报错，而不是跑着跑着崩
为什么这个变化值得单独一节：它把「引擎演进」的方向钉死了。前 13 章里引擎是主动方：模型被动接入，引擎替它决定一切运行时细节；本章的新模型，每一个都反过来对引擎提要求——新的缓存规格、新的 dtype、新的状态钩子、新的草稿通道。而引擎的全部回应不是为每家模型写 if，而是开标准的申报通道，让差异表达为数据而不是代码。这就是「合约化」的含义：扩展点接口不变，每次新模型接入都只是往通道里填一份新的声明。
自研启示 如果你在自研引擎里支持多种模型，这张合约表可以直接抄：先把扩展点想清楚（缓存形状、缓存精度、运行时状态、草稿策略），再决定模型要申报什么。反过来做——模型先各自 hack 进来、扩展点事后归纳——结果就是一串散落在 runner 里的 if model_type == "deepseek_v4"。vLLM 的这几个扩展点每一个都由真实模型逼出来，但接口本身不出现任何模型名：这是「具体驱动抽象」与「为未来臆想抽象」的区别。

这张清单有一个共同的形状：引擎不再把模型当成「一个实现了 forward 的 nn.Module」，而是当成一份会声明自己缓存形状、状态管理方式、草稿策略的完整合约——图 14.10 把这四条通道合起来算总账。

图 14.10：引擎为这一代模型付出的总账。四条扩展通道（缓存形状 / 缓存精度 / 运行时状态 / 草稿策略）合起来，把「接入一个模型」从实现 forward 变成了签一份完整合约。
