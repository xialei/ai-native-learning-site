调度器：决定「这一步跑哪些请求」

vLLM v1 的调度器用「连续批处理」把 GPU 算力填满。它没有单独的 prefill 阶段和 decode 阶段——只有一个统一的目标：让每个请求的 num_computed_tokens 追上 num_tokens_with_spec。

4.1为什么要调度器：连续批处理 vs 静态批处理

Transformer 推理是自回归的：一次只生成一个 token，下一步要拿到上一步的输出才能继续。最朴素的做法是「静态批处理」——一批请求同时进去，等整批全部生成完才轮到下一批。问题是：

  • 批内拖尾（tail latency）：只要有一个请求要生成很多 token，整批都得陪它等，GPU 频繁空转。
  • 批间空隙：批与批之间、以及一批内早结束的请求侧，都有计算资源闲置。

连续批处理（continuous batching）的解法是：不再把请求捆成不可拆分的「批」，而是每一步都重新决定「这步让哪些请求、各算多少个 token」。一个请求结束了就立刻从这批里摘掉，让新请求无缝补进来，GPU 始终忙于有效计算。

为什么要「尽量多塞请求」？因为 decode 每一步只是读回 KV cache、算一次 attention，是典型的访存（memory-bandwidth）瓶颈：算力其实富余，但显存带宽被 「把整个序列的 KV 读一遍」 占满。所以同一时刻并行请求越多，访存被摊得越薄，吞吐越高——这就是调度器尽量多塞请求的动机。而 prefill 要同时喂完整段 prompt、算全部注意力，是算力（compute）密集的。两者内存/算力特征不同，调度器要照顾到这种不对称。

4.2核心思想：没有「阶段」，只有两个计数器（重点）

vLLM v1 的调度器最反直觉的一点，是它没有显式的 prefill 阶段 / decode 阶段。作者在 schedule() 里用一大段注释说明了设计意图。整个 v1 调度器的设计都在这段注释里，值得逐句读懂：

vllm/v1/core/sched/scheduler.py:572 — 调度算法设计注释
python# NOTE(woosuk) on the scheduling algorithm:
# There's no "decoding phase" nor "prefill phase" in the scheduler.
# Each request just has the num_computed_tokens and
# num_tokens_with_spec. num_tokens_with_spec =
# len(prompt_token_ids) + len(output_token_ids) + len(spec_token_ids).
# At each step, the scheduler tries to assign tokens to the requests
# so that each request's num_computed_tokens can catch up its
# num_tokens_with_spec. This is general enough to cover
# chunked prefills, prefix caching, speculative decoding,
# and the "jump decoding" optimization in the future.
读懂这段：每步调度不过是：给每个请求定一个 num_new_tokens，然后把 num_computed_tokens 往前推一点，让它朝 num_tokens_with_spec 逼近。当 num_computed_tokens 还没到 num_prompt_tokens 即「还没把 prompt 算完」→ 那就是 prefill（可能是一个 prefill chunk）；一旦追平、开始追加输出 token → 那就是 decode。二者是同一个循环的两个瞬间，而不是两套流程。如果读到这里还是抽象，先往下走——本节末尾的图 4.2 会把五个典型时刻各画成一根进度条，到时回头再看这段注释就具象了。

这两个计数器在 Request 上有真实定义：

为什么「统一模型」是成立的：新请求若前缀缓存命中，num_computed_tokens 一上来就已推进到命中长度，不必从 0 算；被抢占后重算的请求则从「已算 + 输出」的进度继续。num_tokens_with_spec 里的 + len(spec_token_ids) 把投机解码的 draft token 也并进来；max_tokens（来自 sampling_params.max_tokens，见 request.py:113）决定什么时候算「完事」可以收尾。因为一切都被表达成「数字追数字」，所以 chunked prefill（prefill 拆小）、prefix caching（开头直接算好）、speculative decoding（提前多算几个）在调度器眼里都只是同一套机制的不同「追赶距离」——这正是那份注释说的 generality。自研引擎最大的启示也在这里。

抽象说「追赶」容易，落到一个具体请求身上，这两个数字是怎么变的？下面用一个请求走完五种典型时刻——注意 num_computed_tokens 全书只有三个地方会变：入队时直接设、调度成功后按排上的 token 数推进、被抢占时清零（投机解码被拒时还会小幅回退）。示例设定：prompt 100 个 token，max_tokens 足够大，块大小 16，token_budget 充足。

时刻发生了什么num_computed_tokensnum_tokens_with_spec下一步的「追赶距离」
① 首轮入队 请求刚建好，一个 token 都没算过 0 100 整段 prompt 都要算——这就是纯 prefill

③ 命中前缀缓存 该请求被抢占后重新入队，前 64 个 token 的 KV 在前缀缓存里能直接找到 0 → 64 100 前 64 个 token 白捡，只需真算后 36 个
④ 投机 token prompt 算完进入 decode，draft 模型一次塞来 3 个猜测 token 100 → 103 100 → 103 追赶距离 = 3；验证后没被采纳的部分会在出结果时回滚

4.3用代码看 schedule()：每一步怎么填满 GPU

schedule() 每次被调用，都对应模型的一次 forward。它维护一个 token_budget——这步总共最多能算多少个 token（来自 max_num_scheduled_tokens），然后逐请求「分」这个预算。图 4.3 先把一次 schedule() 的全程画出来：开场定三道预算 → 逐个发放给 RUNNING → 用剩余预算过 WAITING 的闸 → 产出 SchedulerOutput。下面三段代码摘录（标了 ①②③）就是图上的三个区域，建议对照着读。

图 4.3：一次 schedule() 的全程，三个虚线区域对应本节三段代码摘录。开场定三道预算；第一段逐个发 RUNNING——算差距、夹预算、要 KV 块，块不够先问 connector、再抢占最低优先级；第二段用剩余预算过 WAITING 的三道闸。两处灰虚线回环正是正文强调的两个细节：num_new_tokens == 0 时 continue 不 break（不严格 FCFS）、抢到受害者就重试。图省略了 encoder 预算等次要分支。
vllm/v1/core/sched/scheduler.py:570 — schedule() 开头（摘录①；对应图 4.3 的开场与第一段上半）
pythondef schedule(self, throttle_prefills: bool = False) -> SchedulerOutput:
    self.current_step += 1
    ...
    scheduled_new_reqs: list[Request] = []
    scheduled_running_reqs: list[Request] = []
    preempted_reqs: list[Request] = []

    token_budget = self.max_num_scheduled_tokens
    ...

    req_index = 0
    while req_index < len(self.running) and token_budget > 0:
        request = self.running[req_index]
        ...
        num_new_tokens = (
            request.num_tokens_with_spec
            + request.num_output_placeholders
            - request.num_computed_tokens
        )
        num_new_tokens = min(
            num_new_tokens, token_budget, input_budget - draft_slots
        )
逐段读：
  • token_budget = self.max_num_scheduled_tokens：这步的「总 token 定额」。每把一个请求纳入，就减掉它的 num_new_tokens；预算耗尽则停止继续塞。
  • 先调度 RUNNING，再调度新请求：注释 # First, schedule the RUNNING requests. 说明优先级——已经在跑的请求（多数是 decode）优先续命，避免它们等太久；等 running 处理完、token_budget 还有富余，才去看 waiting 里的新请求（waiting 怎么进 RUNNING，本节末尾讲）。
  • 待算 token 数的计算：num_new_tokens = num_tokens_with_spec + num_output_placeholders - num_computed_tokens——「还差多少没算」，然后被 min() 约束在预算之内。这就是 4.2 那个「追赶模型」在代码里的直接落地。
  • min() 里另外两个名字先交代清楚：input_budget 是「一次 forward 最多吃多少 token」（即 max_num_batched_tokens，scheduler.py:593；它怎么挤占显存见 8.4）；draft_slots 是投机解码给 draft token 预留的槽位数，不开投机时就是 0（scheduler.py:592）——所以平时这条约束就是 input_budget 本身。它与 token_budget 平时也是同一个数（后者默认取 max_num_batched_tokens，scheduler.py:134-138），分开写是因为调度预算可以被单独调小。下面 waiting 闸门里那句 input_budget <= draft_slots 说的就是「预算全被 draft 槽占走、连一个正经 token 都放不下，别再放人」。

算出 num_new_tokens 之后还有两处补丁值得看一眼。一是它可能被再削几次：超过 long_prefill_token_threshold 的长 prefill 被压到阈值（:670-671），超过 max_model_len 减本步已采样数的部分被砍掉（:678-683），混合模型还要求 prefill chunk 对齐 mamba 块（:686-689）——都是特定场景的护栏，主线逻辑不变。二是如果削完之后 num_new_tokens == 0，这个请求这步会被跳过，但注意跳的方式是 continue 而不是 break（scheduler.py:715-733）：

为什么是 continue 不是 break：注释列了五种可能（PP>1 时 prompt 已全排上但没算完、异步调度到达上限、encoder 预算/缓存耗尽、mamba 块对齐放不下、MTP lookahead 窗口放不下），然后 woosuk 特别标了一句：这里用 continue 而不是 break，刻意不严格遵守 FCFS——队头请求这步塞不下，就跳过它继续试后面的请求，让后面的「小请求」先走。这和 4.5 抢占时「先让低优先级让路」是同一个思想的另一面：FCFS 只是默认策略，预算真紧张时，让资源落到能立刻用起来的人手里。

拿到 num_new_tokens 后，下一步是找 KV cache 要块。如果 KV 不够（比如被别的请求占满），allocate_slots 会返回 None，此时调度器要么抢占一个低优先级请求腾地方，要么放弃调度当前请求：

读懂这段：本节只看调度器收到 None 之后怎么决策——按顺序两步：先抢占一个更低优先级的 RUNNING 请求腾地方；腾不出（没有可抢的，或受害者就是自己）才放弃这个请求，并且 break 直接停止本步对后续 RUNNING 请求的尝试。压力就这样逐层外泄：分配器拒绝 → 调度器抢占 → 抢不动就整个 step 减载，而不是硬塞导致 OOM。分配器为什么用 None 而不是异常表达拒绝，见 3.4 的契约说明。num_lookahead_tokens 又为投机解码预留了 KV 空间，等下 4.5 里再说。
重试循环还有个提前退出的口子：抢占之前，先问一句 connector「有没有还挂着没落账的块释放」（scheduler.py:748-752 的 has_pending_block_frees）。有就 break 直接放弃——因为配了异步 KV connector 时，别的请求的块释放会被推迟，可能马上就轮到它们归还；与其费劲抢人，等一步白捡。这也是 4.5 那道 _request_blocks_can_be_freed 关卡的孪生：一边「现在抢也腾不出块就别抢」，一边「块的归还在路上就别抢」。

上面只讲了 RUNNING 怎么续。waiting 侧的入口是一道独立的门：schedule() 在处理完 RUNNING 后进入 waiting 循环，每次放人前先数一数 RUNNING 里已经有多少请求，超了就停止放行：

vllm/v1/core/sched/scheduler.py:867 — waiting 循环的准入闸（摘录③；对应图 4.3 第二段）
pythonwhile (self.waiting or self.skipped_waiting) and token_budget > 0:

这里有个容易看漏的演化痕迹：闸门上用的 max_num_active_reqs 是个独立字段，不再直接用 max_num_seqs。历史上这两个概念是绑死的——max_num_seqs 既是并发上限，又决定了 model runner 要按多大容量来分配每请求缓冲、录制 CUDA graph（调度器侧 max_num_running_reqs = max_num_seqs，见 scheduler.py:126）。这带来的限制是：想在 decode 高峰把批次压小一点（少放进几个并发请求，让每步算得快些），就得连 runner 容量一起缩，CUDA graph 也要按新容量重录。于是拆出来一个 --max-num-active-seqs（vllm/config/scheduler.py:70，默认 None 表示维持原行为）：只往下调 RUNNING 的准入上限，runner 和 graph 的容量不动。注释把动机写得很直白：max_num_seqs 给 runner 定容量、同时兼任默认准入上限；单独设这个参数「decode batches stay smaller without shrinking runner or graph capacity」，且必须 ≤ max_num_seqs。调度器初始化时二选一（scheduler.py:129-133）：max_num_active_reqs 取显式配置，没配就回落到 max_num_running_reqs。另外注意计数上有个细节：暂停中的流式会话（WAITING_FOR_STREAMING_REQ）不在 running 列表里，但仍占着一个 runner 请求槽，所以闸门数的是 len(self.running) + num_waiting_for_streaming_input。

4.4状态流：一个请求的一生

请求在调度器里按状态流动。核心节点是 Waiting（排队）→ Running（运行）→ Finished（结束），Running 里又内部区分 prefill 与 decode；Running 因资源不足被抢占时，会回退到 Waiting（状态为 PREEMPTED）重算。

注意 decode 那条回退边：decode 并不总是一路走到 Finished——当这步预算或 KV cache 不够、而 running 队列里还有更「重」的请求时，调度器会 preempt 掉最低优先级请求，让它回 waiting 重来（见 4.5）。这也是为什么「统一模型 + 抢占」能保证稀缺资源始终被高优先级工作占用。

4.5优先级与抢占：稀缺资源怎么分

调度策略由 SchedulingPolicy 决定（FCFS 或 PRIORITY）。在 PRIORITY 策略下，抢占发生时，调度器会挑 最低优先级的请求下手。代码里用 key=(r.priority, r.arrival_time) 作为排序依据：

vllm/v1/core/sched/scheduler.py:755 — 抢占最低优先级请求
python# The request cannot be scheduled.
# Preempt the lowest-priority request.
if self.policy == SchedulingPolicy.PRIORITY:
    preempted_req = max(
        self.running,
        key=lambda r: (r.priority, r.arrival_time),
    )
else:
    preempted_req = self.running[-1]

# A deferred free will not help with immediate allocation.
if not self._request_blocks_can_be_freed(preempted_req):
    break

if self.policy == SchedulingPolicy.PRIORITY:
    victim_index = self.running.index(preempted_req)
    del self.running[victim_index]
    if victim_index < req_index:
        req_index -= 1
    ...  # 若受害者本轮已被调度，还要退还 token/encoder 预算
else:
    preempted_req = self.running.pop()

self._preempt_request(
    preempted_req,
    scheduled_timestamp,
    drop_stale_output=self.requires_kv_delivery,
)
preempted_reqs.append(preempted_req)
读懂这段：max(..., key=(r.priority, r.arrival_time))——取 priority 最大者，同优先级再取 arrival_time 最大（即来得最晚）者：也就是「最不重要、最新到」的那个先被牺牲。
选出来之后有一道关卡：_request_blocks_can_be_freed 检查受害者的块现在能不能立刻释放。引擎配了异步 KV connector 时块释放会被推迟（defer_block_free），若受害者还有没落账的异步写入（last_sched_seq > processed_step_seq），现在抢它也腾不出立即可用的块——调度器直接 break 放弃本次调度，而不是白抢一个。
过了关卡才动手：先从 running 里摘人（PRIORITY 按 index del，FCFS 才是 pop），再调用 _preempt_request：释放 KV 块、num_computed_tokens = 0、投回 waiting 队列（见 4.4 的回退边）。num_preemptions 计数会 +1，用于观测与评估。
延伸 「低优先级先让路」这个思想，正是投机解码（speculative decoding）能跑起来的调度的另一半。投机解码用一个小而快的 draft model 先猜接下来的几个 token，再用大模型一次性验证，接受就赚、拒绝就只损失一点点（num_rejected 会回滚 num_computed_tokens，见 scheduler.py:2034）。但要让投机有效，调度器必须给 draft 的 lookahead 预留 KV 空间（num_lookahead_tokens、spec_token_ids 一并算进 num_tokens_with_spec）。调度器越会「夹缝里塞请求」，投机 batch 越满，draft 越可能一次命中多个 token——吞吐增益和调度质量强相关。这也是理解第 4.7 里「先不碰投机」结论的原因。

4.6PD 分离：把 prefill 和 decode 拆到不同的 GPU

前面 4.1–4.5 讲的是一个实例内部如何混排 prefill 与 decode。但还有一种更彻底的做法——PD 分离（disaggregated prefilling）：干脆让 prefill 和 decode 在两个独立的 vLLM 实例 / 两张卡上跑，prefill 节点算出的 KV cache 通过高速网络传给 decode 节点，后者只做「读已有 KV、一步步 decode」。仓库是支持这个的（vllm/distributed/kv_transfer/ + docs/features/disagg_prefill.md，标注为 experimental）。

为什么值得

官方文档点出两个动机（docs/features/disagg_prefill.md）：

  • TTFT 与 ITL 可以分开调：prefill 节点和 decode 节点各自用不同的并行策略（如不同的 TP / PP）——想降 TTFT 就扩 prefill 的算力，想稳 ITL 就调 decode 节点，互不影响。
  • 压住尾部 ITL：非分离时，一个长 prefill 请求会插进 decode 的批次里，抬高某些请求的尾延迟。PD 分离让 decode 节点永远只做 decode，尾部延迟更可控、可预测。
别误会 PD 分离不提升吞吐（文档明确写着 "Disaggregated prefill DOES NOT improve throughput"）。它换的是延迟可预测性与调优自由度——用「多一台机器的网络传输」换「更低的、更稳的延迟」。如果你的目标只是吞吐，单实例连续批处理就够；PD 分离是延迟敏感在线服务的选择。

用代码看：怎么配

关键是一份 --kv-transfer-config（配置类在 vllm/config/kv_transfer.py），里面声明用哪个 kv_connector、本实例当 kv_producer（prefill）还是 kv_consumer（decode）：

两个独立实例启动，各给一个 role——下面这段是 prefill 端（示例，模型路径按你加载的 checkpoint 填）
bashvllm serve <your-model-path> \
  --kv-transfer-config '{"kv_connector":"NixlConnector",
                                    "kv_role":"kv_producer",   # prefill 端
                                    "kv_connector_extra_config":{"backends":["UCX","GDS"]}}'

decode 端则用 "kv_role":"kv_consumer"。NixlConnector 源码里写得很直白：「use kv_role='kv_producer' for prefill instances and kv_role='kv_consumer' for decode instances」（vllm/distributed/kv_transfer/kv_connector/v1/nixl/connector.py:93-98），旧版 kv_both 已被弃用。支持的 connector 有 Nixl、LMCache、Mooncake、Offloading、FlexKV、Multi 等，本质都是「一条 push / pull KV 的通道」。

回到调度视角：PD 分离并没有推翻 4.1–4.5 的调度模型——每个实例内部仍用统一调度器连续批处理。它只是在更外层把「阶段」拆开了：prefill 节点只跑 prefill，decode 节点只跑 decode。也就是说：你先把单实例内的「统一调度」学好（本章前半），PD 分离只是把这类实例按阶段分机部署，外加一层 KV 搬运约定。

4.7小结与自研启示

概念vLLM 实现你的引擎可以做
统一调度无 prefill/decode 阶段，只有 num_computed_tokens 追 num_tokens_with_spec别维护两套状态机，用一个「还差多少没算」覆盖一切
连续批处理每步 schedule() 重排 running + waiting请求结束即腾出、新请求即补位，中间不空转
token 预算token_budget / max_num_scheduled_tokens设一个每步 token 上限，防止一步算太多拖慢延迟
抢占allocate_slots 失败 → preempt 最低优先级 (priority, arrival_time)KV 不够先让低优让位，兼顾「尽量让请求跑得动」的稳健性
投机解码num_lookahead_tokens + spec_token_ids 并入 num_tokens_with_spec先不做；这是吞吐优化，等基础连续批处理跑通再说
PD 分离prefill / decode 拆到两个实例，kv_producer / kv_consumer 靠 --kv-transfer-config 传 KV更晚的部署级优化：为压尾部延迟、分开调 TTFT/ITL；不提升吞吐，起步别碰
本章收束：调度器不是「判断 vanilla 还是 greedy」的分派器，而是一个预算分配器——每步把有限的 token 预算、KV 空间，按请求优先级分摊出去，让每个请求的 num_computed_tokens 都朝目标持续推进。
下一步 调度器想好了「这步跑谁、各算多少 token」，但「怎么真正把这些 token 算出来」是另一回事——输入如何拼成 tensor、KV 如何喂进 kernel、NCCL 如何同步，都由下一层的 Model Runner 完成。这是第 5 章：Model Runner。
