整体架构：vLLM 的「机器」由哪些部件组成

打开 vLLM 源码，第一眼是上百个文件。这一章先回答四个问题：这台机器由哪些部件组成？它们怎么协作？为什么拆成这么多层和进程？每个部件住在哪个目录？先摆问题，再一层层往代码里走，末了拿 SGLang 的组织方式对照一眼。

1.1读懂一台推理引擎，要先回答什么

不管读 vLLM 还是自研引擎，上来都会撞到同一串问题。先把它们摆出来：

  • 部件怎么分？一张 GPU、一堆并发请求，系统里必然有「管事」的和「干活」的。哪些组件管「一批请求现在该跑什么」，哪些管「把请求真正算出来」？这条边界切在哪？
  • 数据怎么流？一个 prompt 进来、一串 token 出去，中间要穿过哪些部件、每站传了什么？整台机器的循环点在哪？
  • 为什么拆这么多？能不能写成一个进程一个循环跑完？vLLM 拆出 Engine / Core / Worker / Executor 这么多层、甚至拆成多个进程，是为了解决什么问题、付出了什么代价？
  • 代码在哪？每个部件对应哪个目录、哪个类？读代码时从哪个文件进？

这四个问题里，前三个的共同背景是一个核心矛盾：「内存有限，但每步都要保留每个请求的 KV 状态」——多个请求要共享一张 GPU、交错推进，系统必须切出「决策」和「执行」两个角色。vLLM 的切法是两个并发跑的大块：

  • 引擎层（Engine / Core，常驻 CPU）：管「一批请求现在该跑什么」—— 调度（Scheduler）、KV cache 分配（KVCacheManager）、输入输出处理（tokenize / detokenize / 结构化输出）。
  • 执行层（Worker / Model Runner / Sampler，跑在 GPU）：管「把这一批请求真正喂给模型算出 token」—— 组装张量、跑 transformer、采样。

两者之间通过一个 「步进（step）」同步点协作：CPU 决定 batch → 发给 GPU → GPU 跑一次模型前向 → 返回新 token → CPU 决定下一步。后续讲的「连续批处理」，全部逻辑就落在这个循环里（动机、预算与调度算法见第 4 章）。

四个问题怎么作答：部件与数据流 → 1.2 的分层图；为什么要拆 → 1.3 用代码看构造、1.4 专讲「引擎和 Core 为什么分开」；目录地图 → 1.5 一张表。1.6 拿 SGLang 的进程组织对照。

1.3拆这么多，代码里怎么长出来的

先答第三个问题的前一半：这些部件在代码里是怎么被装配起来的。从入口 LLM 出发，一步步创建引擎。核心事实：vLLM 现在默认跑 v1 引擎。

vllm/entrypoints/llm.py — LLM.__init__ 里创建引擎（摘录，注释为译注）
pythonfrom vllm.v1.engine.llm_engine import LLMEngine   # 用的是 v1 引擎

class LLM:
    def __init__(self, model: str, ...):   # model 是必填位置参数，无默认值
        self.llm_engine = LLMEngine.from_engine_args(engine_args)  # L2 引擎

    def generate(self, prompts, sampling_params=None, ...):
        return self._run_completion(prompts=prompts, params=sampling_params, ...)
别被名字绕晕： LLMEngine（在 vllm/v1/engine/llm_engine.py）是「同步、阻塞」的简单封装；而在线服务用的是它的异步版本 vllm/engine/async_llm_engine.py 与 v1/engine/async_llm.py。它们背后都通向同一个 EngineCore。

1.4接着问：为什么「引擎」和「Core」要分开

第三个问题的后一半：拆层的代价是复杂度，那分进程买到的是什么？v1 里，真正干活的核心是一个独立进程 EngineCoreProc（可由子进程或 Ray actor 承载），它内部持有 Scheduler 与 KVCacheManager，通过 ZMQ 套接字与调用方通信。

vllm/v1/engine/core.py — EngineCore 的核心结构（简化，注释为译注）
pythonclass EngineCore:
    # 持有 CPU 侧核心状态
    def add_request(self, request: Request, request_wave=0): ...
    def step(self) -> tuple[dict[int, EngineCoreOutputs], bool]:
        # 1) scheduler 决定 batch  2) 交给 worker 前向  3) 采样  4) 回传输出
        ...
为什么这么设计： 把 Core 变成独立可寻址的进程，才能在多卡/多机部署里「一个调度者协调多个执行者」，也为未来分离式 prefill/decode 铺路。做自己的引擎时不需要这么重——单进程足够起步（见第 11 章）。

1.6SGLang 的另一种拆法与自研启示

回到 1.1 摆出的四个问题，vLLM 的答案是「两块分层 → step 同步点 → 引擎/Core 分进程 → 十个部件十行目录」。但「拆成两个角色」是共识，「拆到哪一层」是选择——SGLang 给出了不同的切法：

要点 别急着堆并行和分布式。自研引擎的 MVP 只需两块：一个能跑「单请求 prefill + decode」的循环，外加一个最朴素的连续批处理循环。 分层（Engine / Core / Worker）是 vLLM 为「可扩展性」付出的复杂度，你可以在理解之后再决定要不要这么切。下一步进入 第 2 章：请求全生命周期。
与 SGLang 对照 两边的共识是「调度和执行要分开」，分歧在把什么当成独立进程。
对比点vLLMSGLang
调度进程调度 + KV 管理 + 执行编排在一个 EngineCore 进程（vllm/v1/engine/core.py）调度 + KV 管理 + 发起前向在一个 Scheduler 进程，每个 TP rank 一个（python/sglang/srt/managers/scheduler.py）
谁在 EngineCore/Scheduler 之下Executor（UniProc/Multiproc/Ray）→ Worker 跑模型没有单独执行层——Scheduler 直接调 TpModelWorker
反分词（token id → 文本）留在前端进程（output_processor）独立成第三个进程（DetokenizerManager）

每张卡都当独立引擎、调度简单直接，代价是多个 rank 重复持有调度状态；vLLM 的拆法换来了「一个调度者管多个执行者」。对照着读，更容易分辨「必然」与「取舍」。详见 深入浅出SGLang · 01 整体架构与进程模型。
