整体架构：vLLM 的「机器」由哪些部件组成

理解 vLLM（尤其新版 v1 引擎）如何分层，是读懂后续每一章的前提。这一页我们把整台机器拆开，讲清每个部件各干什么。

1.1一分钟版本

现代 LLM 推理引擎要解决的核心矛盾是：「内存有限，但每步都要保留每个请求的 KV 状态」。为了让多个请求共享一张 GPU、交错推进，vLLM 把系统拆成两个并发跑的大块：

  • 引擎层（Engine / Core，常驻 CPU）：管「一批请求现在该跑什么」—— 调度（Scheduler）、KV cache 分配（KVCacheManager）、输入输出处理（tokenize / detokenize / 结构化输出）。
  • 执行层（Worker / Model Runner / Sampler，跑在 GPU）：管「把这一批请求真正喂给模型算出 token」—— 组装张量、跑 transformer、采样。

两者之间通过一个 「步进（step）」同步点协作：CPU 决定 batch → 发给 GPU → GPU 跑一次模型前向 → 返回新 token → CPU 决定下一步。continuous batching 的全部逻辑就落在这个循环里。

1.3用代码看｜引擎如何被构造

从入口 LLM 出发，一步步创建引擎。核心事实：vLLM 现在默认跑 v1 引擎。

vllm/entrypoints/llm.py — LLM.__init__ 里创建引擎（摘录，注释为译注）
pythonfrom vllm.v1.engine.llm_engine import LLMEngine   # 用的是 v1 引擎

class LLM:
    def __init__(self, model: str, ...):   # model 是必填位置参数，无默认值
        self.llm_engine = LLMEngine.from_engine_args(engine_args)  # L2 引擎

    def generate(self, prompts, sampling_params=None, ...):
        return self._run_completion(prompts=prompts, params=sampling_params, ...)
读懂这段： LLMEngine（在 vllm/v1/engine/llm_engine.py）是「同步、阻塞」的简单封装；而在线服务用的是它的异步版本 vllm/engine/async_llm_engine.py 与 v1/engine/async_llm.py。它们背后都通向同一个 EngineCore。

1.4为什么「引擎」和「Core」要分开

v1 里，真正干活的核心是一个独立进程 EngineCoreProc（可由子进程或 Ray actor 承载），它内部持有 Scheduler 与 KVCacheManager，通过 ZMQ 套接字与调用方通信。

vllm/v1/engine/core.py — EngineCore 的核心结构（简化，注释为译注）
pythonclass EngineCore:
    # 持有 CPU 侧核心状态
    def add_request(self, request: Request, request_wave=0): ...
    def step(self) -> tuple[dict[int, EngineCoreOutputs], bool]:
        # 1) scheduler 决定 batch  2) 交给 worker 前向  3) 采样  4) 回传输出
        ...
为什么这么设计： 把 Core 变成独立可寻址的进程，才能在多卡/多机部署里「一个调度者协调多个执行者」，也为未来分离式 prefill/decode 铺路。做自己的引擎时不需要这么重——单进程足够起步（见第 11 章）。

1.6对「自研引擎」的第一个启示

要点 别急着堆并行和分布式。自研引擎的 MVP 只需两块：① 一个能跑「单请求 prefill + decode」的循环；② 一个最朴素的连续批处理循环。 分层（Engine / Core / Worker）是 vLLM 为「可扩展性」付出的复杂度，你可以在理解之后再决定要不要这么切。下一步进入 第 2 章：请求全生命周期。
