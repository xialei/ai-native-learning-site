PagedAttention & KV cache：vLLM 吞吐量高的根源

这是 vLLM 的灵魂。它借鉴操作系统「分页」思想来管理注意力缓存，解决了「显存浪费 + 内存碎片」两大痛点，是自研引擎最值得抄的一个设计。

3.1问题：KV cache 为什么会“爆炸”

Transformer 自回归每算一个新 token，都要把每个历史 token 的 K（key）和 V（value） 存起来，供后续注意力使用。这个缓存叫 KV cache，它随序列长度线性增长。

对每个请求、每层、每个注意力头，KV cache 都要占一块显存。并发 N 个请求、序列都较长时，KV cache 会吃下大部分显存。旧版 naive 方案给每个请求一次性预留最大长度的连续显存，导致：

  • 预留浪费：多数请求根本不会生成满 max_tokens，预留的尾部一直空着。
  • 碎片化：不同长度的请求占用不同大小的连续块，删掉一个中间的请求就留下无法合并的洞。
浪费 / 碎片（朴素方案） vLLM 分页块 预留未用

3.2核心思想：逻辑块 vs 物理块

关键是把「连续性」和「存储」解耦：

  • 逻辑视图（序列自己看）：一个请求的 KV 是一串连续的 token，逻辑块编号 0,1,2,…。
  • 物理视图（显存实际）：这些逻辑块被映射到物理内存里不连续的固定小块（block）。由 BlockPool 统一分配。
逻辑块 / 物理块 空闲块
图 3.2：逻辑连续、物理离散。映射关系由每请求的 block table 记录（Worker 端持有，调度器分配后下发）。
为什么能省显存：因为块——不管是请求 A 用了 3 块还差半块，还是请求 B 只用了 1 块——都从同一个块的池子里按需拿。满了就再拿一块，而不是一次性预留整条序列。这样内存利用率大幅提升，能同时塞进更多请求，吞吐自然更高。

3.4用代码看｜KVCacheManager 如何分配插槽

调度器决定「这个请求这步要追加多少新 token」后，会调用 KVCacheManager.allocate_slots 给请求腾出 KV 空间。签名很长，因为要兼顾前缀命中、投机采样 lookahead、跨 attention 组等；抓主干：为请求的这批新 token 找出可写的物理块。

读懂这段：返回值 None 是个重要的「背压」信号——KV cache 满了新块拿不到，调度器就把这个请求挪到下一轮，而不是硬塞导致 OOM。这是引擎稳健性的关键设计，自研时务必保留。

3.5Attention 侧：kernel 需要知道 block table

因为 KV 在物理上不连续，标准的 FlashAttention 不能直接用。vLLM 的注意力 kernel 接收 block table，在 kernel 内通过索引拿到每个逻辑块对应的物理偏移。这个「分页的 flash attention」就是 PagedAttention 名字的来源。

3.6小结与自研启示

概念vLLM 实现你的引擎可以做
分页 KVBlockPool + block table先做固定连续 KV，理解了再用分页（第二版）
按需分配allocate_slots 返回 None 即背压KV 不足时不调度，宁可等待不 OOM
前缀缓存块内容哈希 + BlockHashToBlockMap先跳过；这是吞吐优化，不是正确性要求
kernelv1/attention/backends先用 torch 原生 attention 跑通，再换优化 kernel
下一步 KV 只回答「块从哪来」。谁决定「这批 KV 该属于哪些请求、每步跑哪些请求」？这就是第 4 章：调度器。
