PagedAttention & KV cache：vLLM 吞吐量高的根源

vLLM 借鉴操作系统「分页」思想来管理注意力缓存，直接针对原生实现「显存浪费 + 内存碎片」两个问题。要自研引擎，这是最值得先搬过去的一个设计。

3.1问题：KV cache 为什么这么占显存

Transformer 自回归每算一个新 token，都要把每个历史 token 的 K（key）和 V（value） 存起来，供后续注意力使用。这个缓存叫 KV cache，它随序列长度线性增长。

对每个请求、每层、每个注意力头，KV cache 都要占一块显存。并发 N 个请求、序列都较长时，KV cache 会占掉大部分显存。旧版 naive 方案给每个请求一次性预留最大长度的连续显存，导致：

  • 预留浪费：多数请求根本不会生成满 max_tokens，预留的尾部一直空着。
  • 碎片化：不同长度的请求占用不同大小的连续块，删掉一个中间的请求就留下无法合并的洞。

3.2核心思想：逻辑块 vs 物理块

关键是把「连续性」和「存储」解耦：

  • 逻辑视图（序列自己看）：一个请求的 KV 是一串连续的 token，逻辑块编号 0,1,2,…。
  • 物理视图（显存实际）：这些逻辑块被映射到物理内存里不连续的固定小块（block）。由 BlockPool 统一分配。
逻辑块 / 物理块 空闲块
图 3.2：逻辑连续、物理离散。映射关系由每请求的 block table 记录（Worker 端持有，调度器分配后下发）。
为什么能省显存：因为块——不管是请求 A 用了 3 块还差半块，还是请求 B 只用了 1 块——都从同一个块的池子里按需拿。满了就再拿一块，而不是一次性预留整条序列。这样内存利用率大幅提升，能同时塞进更多请求，吞吐自然更高。

3.3块从哪里来：BlockPool

vllm/v1/core/block_pool.py 的 BlockPool 是显存页分配器：预分配一批物理块，谁要就给谁，并对 已缓存（prefix cache）的整块做复用登记。前缀缓存「块内容哈希 → 跨请求复用 → 省掉重复 prefill」的完整机制是吞吐优化的另一条线，这里只立个牌子——见第 8.5 节。

3.4用代码看｜KVCacheManager 如何分配槽位

调度器决定「这个请求这步要追加多少新 token」后，会调用 KVCacheManager.allocate_slots 给请求腾出 KV 空间。签名很长，因为要兼顾前缀命中、投机采样 lookahead、跨 attention 组等；抓主干：为请求的这批新 token 找出可写的物理块。

读懂这段：对分配器来说，None 是它唯一的拒绝表达——不抛异常、不部分分配：要么给出完整的一批可写块引用并把新块登记进前缀缓存，要么什么都不给。至于收到 None 的一方（调度器）怎么决策，是另一个组件的事，见第 4.3 节。

为什么偏偏是「返回 None」这个不起眼的设计值得停下来看一眼？拿几种同样能表达「不够了」的替代方案对比一下，就看出好处了：

  • 分配器一直塞、塞到 OOM：错误发生得太晚——CUDA OOM 是进程级灾难，没有任何降级空间，代价是整条 forward 作废甚至整个引擎重启，而不是「一个请求晚几步被调度」。背压的全部意义就是把「不够」拦在可控的时机。
  • 分配器直接抢别人的块：抢占要动 waiting 队列、退还 token 预算、给受害者记状态——这些全是调度器的私有账本。分配器越权意味着换个调度策略（FCFS ↔ PRIORITY）就得改分配器，两层从此互相咬死。
  • 用异常表达拒绝：调度主循环是每步都在跑的热路径，「KV 暂时不够」不是异常而是日常——让它走异常通道，成本高还容易和真 bug 混在一起；返回 None 就是一次普通的 if 判断。
  • 部分分配（给一半块）：attention 没法只算半步——块要么整批可写，要么一个都不给，请求原样留在原处，状态零污染。
调度器 拒绝信号 分配成功 调度器应对
图 3.4：allocate_slots 返回 None 之后信号怎么走——分配器到「拒绝」为止，抢占还是放弃是调度器的决策；两个出口都不产生半步数据，下一轮重试即可。

3.5Attention 侧：kernel 需要知道 block table

因为 KV 在物理上不连续，标准的 FlashAttention 不能直接用。vLLM 的注意力 kernel 接收 block table，在 kernel 内通过索引拿到每个逻辑块对应的物理偏移。这个「分页的 flash attention」就是 PagedAttention 名字的来源。

概念vLLM 实现你的引擎可以做

kernelv1/attention/backends先用 torch 原生 attention 跑通，再换优化 kernel
下一步 KV 只回答「块从哪来」。谁决定「这批 KV 该属于哪些请求、每步跑哪些请求」？这就是第 4 章：调度器。
