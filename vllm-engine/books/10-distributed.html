分布式推理：一张卡装不下时怎么办

模型太大、一张 GPU 放不下或跑不动时，就要把它「切开」分到多张卡。切法不同，通信量、实现难度、适用场景天差地别。这一章从 vLLM 的 Executor 层看它如何把「一次推理」分发到多个 worker 进程。

10.1为什么需要并行：单卡放不下 / 算不动

放不下：模型权重 + KV cache + 激活，加起来超过单卡显存。比如 671B 参数的 MoE 模型，光权重就几百 GB，任何一张消费级卡都装不下。

算不动：即使塞得进一张卡，单卡算力也有上限。吞吐（每秒处理多少 token）上不去，尤其面对高并发请求时，需要多张卡分摊计算。

于是有了四种「切法」。它们切的对象不同，通信的频率和量也完全不同：

被切分到某张卡的权重 / expert Router（EP） 完整模型副本（DP）
图 10.1：四种并行的直观区分。TP/PP 切模型，DP 复制模型，EP 只切 MoE 的 expert 层。

10.2Executor 层职责：把「意图」分发给 worker

在 vllm/v1/executor/abstract.py 里，Executor 是抽象基类，注释写得很直白：“An executor is responsible for executing the model on one device, or it can be a distributed executor that can execute the model on multiple devices.” 它位于 EngineCore 的调度意图 和 每个 worker 进程 之间：引擎拿到调度输出后，把它交给 Executor，由 Executor 决定如何落到一个个 worker 上。

关键接口是 collective_rpc(method, ...)——「把同一个方法名广播给所有 worker 执行」，以及 execute_model(scheduler_output)。抽象基类还声明了两个类级标志位，用于描述实现的能力：

pythonclass Executor(ABC):
    uses_ray: bool = False   # 是否用 Ray 来编排进程
    supports_pp: bool = False  # 是否支持流水线并行(PP)
    # 下面都是统一入口，交给 subclass 实现：
    ...

get_class(vllm_config) 根据 parallel_config.distributed_executor_backend 选出具体实现。vLLM 提供三种主流后端：

  • uni（UniProcExecutor）：单进程。worker 和一个 driver worker 跑在同一个进程里，没有任何跨进程调度。适用于单卡、不需要分布式的场景，最简单也最快。
  • mp（MultiprocExecutor）：多进程。每个 worker 是 context.Process(target=WorkerProc.worker_main, name=f"VllmWorker-{rank}") 拉起的独立进程，进程间用共享内存消息队列 MessageQueue 通信。vLLM 默认的多卡后端，不依赖 Ray，只需标准库多进程，适合单机多卡。
  • ray（RayDistributedExecutor / RayExecutorV2）：Ray 编排。每个 worker 是一个 Ray actor（ray.remote(RayWorkerProc)，远端对象），能跨节点、跨机调度，支持 PP 的编译 DAG。适合大规模、多机集群。注意 RayExecutorV2 继承自 MultiprocExecutor，复用了后者的基于消息队列（MQ）的控制平面，但 worker 进程由 Ray 管理、是 Ray actor 而非裸多进程。
一句话：Executor = 引擎与 worker 之间的「调度/分发层」。你把蓝图（并行配置）给它，它负责拉起进程、把每步的调度输出广播下去（collective_rpc("execute_model", ...)），再把结果收回来。uni 是「同一个进程直接调」，mp/ray 是「跨进程 RPC」。

10.3用代码看：三种 Executor 的差异 & 并行配置

先看后端是怎么被选出来的。下面这段来自抽象基类的工厂方法，按字符串挂载对应类：

vllm/v1/executor/abstract.py — get_class（摘录）
pythonelif distributed_executor_backend == "ray":
    executor_class = RayDistributedExecutor
elif distributed_executor_backend == "mp":
    executor_class = MultiprocExecutor
elif distributed_executor_backend == "uni":
    executor_class = UniProcExecutor

单进程的 collective_rpc 最朴素——根本没有网络，直接在同进程内调用 worker 方法：

vllm/v1/executor/uniproc_executor.py — UniProcExecutor.collective_rpc（摘录）
python# driver_worker 就在当前进程里，调用等同于直接执行
result = run_method(self.driver_worker, method, args, kwargs)
return result if single_value else [result]

而 Ray 版每个 worker 是一个远端 actor，于是 collective_rpc 变成「把方法序列化后 .remote() 发出去，再 ray.get() 收结果」：

vllm/v1/executor/ray_executor.py — RayDistributedExecutor.collective_rpc（摘录）
pythonray_worker_outputs = [
    worker.execute_method.remote(sent_method, *args, **kwargs)
    for worker in self.workers
]
return ray.get(ray_worker_outputs, timeout=timeout)

并行规模最终由配置决定，而 worker 总数 world_size 是这样来的（vLLM 里它被定义为 TP×PP，CP/DP 再在此基础上扩展）：

vllm/config/parallel.py — world_size（摘录，注释为官方）
pythonworld_size: int = Field(init=False)
"""world_size is TPxPP, it affects the number of workers we create."""

@property
def world_size_across_dp(self) -> int:
    """Process world size across TP, PCP, PP, and DP."""
    return self.world_size * self.data_parallel_size
逐行读：vLLM 里 world_size 的本质是 TP × PP（决定 worker 数量）；world_size_across_dp 在它基础上再乘 data_parallel_size，把 DP 的复制份也算进来。注意官方 docstring 写的是“TPxPP”，但代码里实际计算是 PP × TP × PCP（prefill_context_parallel_size，默认 1，所以多数情况等价于 TP×PP）；DCP（decode context parallel）则复用 TP 的 rank 来切序列。另外 vLLM 没有独立的 expert_parallel_size 字段——MoE 的 expert 切分直接复用 TP/DP 的世界大小（enable_expert_parallel 只是开关）。

多卡之间的「对话」最终落到设备通信。TP 组里每层都要做一次 all-reduce，走在 GroupCoordinator 上：

vllm/distributed/parallel_state.py — GroupCoordinator.all_reduce（摘录）
pythondef all_reduce(self, input_: torch.Tensor) -> torch.Tensor:
    if self.world_size == 1:        # 单卡直接跳过
        return input_
    if self.use_custom_op_call:
        return torch.ops.vllm.all_reduce(input_, group_name=self.unique_name)
    else:
        return self._all_reduce_out_place(input_)  # 最终调 device_communicator

底层设备通信在 vllm/distributed/device_communicators/ 里（如 pynccl.py 的 PyNcclCommunicator、custom_all_reduce.py）。而各个并行组的句柄由 parallel_state 提供，例如 get_tp_group()、get_pp_group()、get_dp_group()、get_ep_group()、get_pcp_group()、get_world_group()。

10.4通信的成本：TP 与 PP 的取舍

分布式的悖论在于：切开的多卡必须互相说话，而跨卡通信（甚至跨机走网卡）比显存内带宽慢得多。两种主要切法通信模式截然不同：

图 10.4：TP 通信频繁但单次小、卡间算力均衡；PP 通信少但引入串行 bubble。
  • TP（张量并行）：通信发生在每一层。同一层切开后，前向和后向都要 all-reduce / all-gather，通信量大致正比于 层数 × 张量大小。带宽要求高（最好在同一节点、走 NVLink），但每张卡算的工作量均衡。适用：单卡放得下、只想更快。
  • PP（流水线并行）：通信只发生在流水线阶段之间——上游把整段激活传给下游。几十上百层只传一两次，通信少、对带宽不敏感（可跨机）。代价是 phase 串行会引入「流水线气泡」（bubble），且不同阶段间显存占用不均衡。
  • 小结取舍：能塞进一张卡 → 优先 TP；模型大到必须分阶段（且带宽紧张/跨机）→ 才上 PP。这也是 vLLM 默认优先用 TP、把 PP 留给超大模型的原因。

10.5小结 + 自研启示

并行切的对象通信什么时候用
TP同一层权重每层 all-reduce（多）单卡放得下、想更快，带宽好
PP不同层分段阶段间传激活（少）模型大到必须分段、可跨机
DP复制完整模型训练时同步梯度推理=人多力量大，扩容负载
EPMoE 的 expert 层token 路由 + all-to-all超大 MoE，最省显存
自研启示 先跑通单卡（等价 vLLM 的 UniProcExecutor），把正确性搞对。等需要更大模型时，再上 TP——它最容易且通信模型清晰，是「单卡放不下」时的第一选择；PP/DP 是更晚的优化，别一开始就为多机并行分心。纪律是：正确性优先，并行度后置。
