分布式推理：一张卡装不下时怎么办

模型太大、一张 GPU 放不下或跑不动时，就得把它切到多张卡上。这一章讲三件事：四种并行切法各切的是什么；vLLM 怎么用 Executor 这一层把多张卡组织起来干活；切开的卡之间要付出多少通信代价。先立概念，再看代码，末了拿 SGLang 对照。

10.1单卡放不下、算不动，怎么办

先说多卡推理为什么存在，原因就两个，都很直接。一是放不下：模型权重、KV cache、中间激活加在一起，超过一张卡的显存。671B 参数的 MoE 模型光权重就有几百 GB，任何一张消费级卡都装不下。二是算不动：模型塞得进一张卡，但高并发下单卡算力见顶，吞吐上不去，需要几张卡分摊计算。

解决办法都绕不开同一个动作——把模型「切开」，或者把请求「摊开」。vLLM 有四种并行的说法：TP、PP、DP、EP。这四个缩写经常一起出现，但它们切的不是同一样东西，卡之间要做的通信也完全不同。一个一个看。

TP（张量并行）是把一层内部的权重切成几份，每张卡拿一份。比如一个 4096×4096 的权重矩阵，TP=2 时每张卡各算一半，算完把两半的结果合起来。因为每一层都被切了，每层算完都得合一次——通信又频繁，又吃带宽。

PP（流水线并行）是按层分段：前 32 层放 A 卡，后 32 层放 B 卡，A 算完把结果交给 B。它切的是「层与层之间」，卡之间只在段与段的边界上传数据，通信少得多；代价是像工厂流水线，各段必须衔接好，否则有的卡在空等。

DP（数据并行）不切模型——每张卡放一份完整的模型副本，各接各的请求，互相不通信（训练时才同步参数）。推理里它就是最朴素的扩容手段：请求多了就加副本。

EP（专家并行）只针对 MoE 模型。MoE 的一层里有很多「专家」，每个专家是一块独立的 FFN 权重，token 按路由结果只走其中少数几个。EP 把不同的专家放到不同的卡上，路由到谁，就把 token 发给谁。它不增加 KV cache 开销，只搬运激活，是大 MoE 模型最省显存的切法。

切法怎么选、通信代价差多少，10.4 再算这笔账。中间两节先解决一个更工程的问题：这些「切法」最终都要落到一个个独立进程上，谁来管这些进程、谁来把「这一步该跑了」通知到每一张卡？vLLM 给出的答案是 Executor。

10.2谁来分发：Executor 把每一步交给所有 worker

第 1 章讲过 vLLM 的进程划分：EngineCore 是一个独立进程，里面跑着调度器，每一步它决定「处理哪些请求、每个请求算几个 token」。单卡时，决定做完，直接在本进程里把模型跑了就行。多卡时，「跑模型」这件事发生在别的进程、甚至别的机器上——EngineCore 自己够不着那些卡，中间必须有一层传话的代码。

这一层就是 Executor。抽象基类的 docstring 把职责说得很直白：一个 executor 负责在单个设备上执行模型，也可以是分布式 executor，在多个设备上执行。类上还挂着两个能力标志：

vllm/v1/executor/abstract.py — class Executor（摘录，注释为译注）
pythonclass Executor(ABC):
    uses_ray: bool = False   # 进程编排是否交给 Ray
    supports_pp: bool = False  # 是否支持流水线并行(PP)

对上，Executor 暴露的方法很少，最核心的是 execute_model(scheduler_output)——把这一步的批次交下去。它内部统一走另一个入口 collective_rpc：把一个方法名连同参数，发给所有 worker 执行，再把结果收回来。基类里的默认实现就是一层薄封装：

vllm/v1/executor/abstract.py — execute_model 默认实现（摘录）
pythonoutput = self.collective_rpc(
    "execute_model", args=(scheduler_output,), non_block=non_block
)
return output[0]

换句话说，EngineCore 不关心有几张卡、卡在哪个进程，它只对 Executor 这一个入口说话；「同一个方法怎么送到每一张卡上」，是 Executor 的事。worker 从哪来、彼此怎么通信，由「后端」决定。vLLM 内置三种后端：

后端worker 进程从哪来怎么通信什么时候用
uni（UniProcExecutor）不起 worker——模型就在 EngineCore 所在的进程里跑普通函数调用单卡；最简单也最快
mp（MultiprocExecutor）每张卡一个 multiprocessing 子进程共享内存上的消息队列（MessageQueue）单机多卡；默认的多卡后端，不依赖 Ray
ray（RayDistributedExecutor / RayExecutorV2）每张卡一个 Ray actor控制面复用 mp 的消息队列实现多机集群；支持 PP 编译 DAG

不指定后端时怎么选，配置里也写了规则：world_size 为 1 就用 uni；单机放得下就用 mp；显式要求 Ray、或者引擎跑在 Ray placement group 里，才用 ray。

分工小结：EngineCore 对 Executor 说话，Executor 按后端拉起 worker（同进程 / 子进程 / Ray actor），每步通过 collective_rpc 广播下去、把结果收上来。uni 和 mp/ray 的区别是「同进程直调」还是「跨进程传消息」；ray 和 mp 的区别只在 worker 进程由谁拉起——RayExecutorV2 直接继承自 MultiprocExecutor，消息队列那套控制面代码是同一份。

10.3落到代码：后端怎么选、worker 怎么跑

三种后端在 get_class 里就是一段字符串分支，没什么玄机——按配置里的 distributed_executor_backend 挂载对应的类：

vllm/v1/executor/abstract.py — get_class（摘录，注释为译注）
pythonelif distributed_executor_backend == "ray":
    executor_class = RayDistributedExecutor
elif distributed_executor_backend == "mp":
    executor_class = MultiprocExecutor
elif distributed_executor_backend == "uni":
    executor_class = UniProcExecutor

uni 版的 collective_rpc 是三种里最短的：所谓「广播给所有 worker」，实际上就是直接调用那唯一的 worker——它就住在当前进程里，连序列化都不需要：

vllm/v1/executor/uniproc_executor.py — UniProcExecutor.collective_rpc（摘录，注释为译注）
python# driver_worker 就在当前进程里，调用等同于直接执行
result = run_method(self.driver_worker, method, args, kwargs)
return result if single_value else [result]

mp 是默认的多卡后端，也最能说明「分布式」在 vLLM 里具体指什么。每个 worker 是一个用 multiprocessing 拉起的独立子进程（进程名 VllmWorker-{rank}），和 EngineCore 之间不共享任何 Python 对象，全靠共享内存上的消息队列传话：Executor 把方法名和参数写进广播队列，每个 worker 取到自己那份，执行完再把结果写回各自的应答队列：

vllm/v1/executor/multiproc_executor.py — MultiprocExecutor.collective_rpc（摘录）
pythonif isinstance(method, str):
    send_method = method
else:
    send_method = cloudpickle.dumps(method, protocol=pickle.HIGHEST_PROTOCOL)
self.rpc_broadcast_mq.enqueue((send_method, args, kwargs, output_rank))

写进队列之后，Executor 逐个从各 worker 的应答队列里收结果，timeout 参数管的就是这一步的等待上限。方法名可以直接传字符串；传整个函数的话，先 cloudpickle 序列化再入队。

ray 版的思路一样，只是 worker 换成了 Ray actor——它们可能住在别的机器上，所以调用方式从「写队列」变成 Ray 的远程调用：把方法通过 .remote() 发给每个 actor，再用 ray.get 把所有结果等齐：

vllm/v1/executor/ray_executor.py — RayDistributedExecutor.collective_rpc（摘录，注释为译注）
pythonray_worker_outputs = [
    worker.execute_method.remote(sent_method, *args, **kwargs)
    for worker in self.workers
]
return ray.get(ray_worker_outputs, timeout=timeout)

worker 一共该有几个？这是并行配置算出来的。TP、PP、DP 各有一个尺寸字段，它们的乘积决定了进程总数，配置里对应的名字就叫 world_size：

vllm/config/parallel.py — world_size（摘录，注释为官方）
pythonworld_size: int = Field(init=False)
"""world_size is TPxPP, it affects the number of workers we create."""

@property
def world_size_across_dp(self) -> int:
    """Process world size across TP, PCP, PP, and DP."""
    return self.world_size * self.data_parallel_size
几处容易认错的细节：docstring 写的是 world_size = TP × PP，但 __post_init__ 里的实际计算还乘了第三个因子 PCP——prefill context parallel，把长 prefill 的序列维再切给几张卡算，默认 1，所以平时把它当 TP × PP 没错。DCP（decode context parallel）是另一个维度：decode 时把 KV cache 切到几张卡上，它不增加进程数，直接复用 TP 的 rank。还有，vLLM 没有 expert_parallel_size 这个字段——EP 不单独占一维，MoE 的专家切分就发生在 TP/DP 的组上，enable_expert_parallel 只是个开关。

worker 之间真正搬数据的地方不在 Executor 层，而在通信库里。TP 切开后，每层末尾要把各卡的「半份结果」合成整体，这个「合」就是集合通信里的 all-reduce：每张卡各持有一部分和，通信做完，每张卡都拿到总和。vLLM 给它留了统一入口，在 GroupCoordinator 上：

vllm/distributed/parallel_state.py — GroupCoordinator.all_reduce（摘录，注释为译注）
pythondef all_reduce(self, input_: torch.Tensor) -> torch.Tensor:
    if self.world_size == 1:        # 单卡直接跳过
        return input_
    if self.use_custom_op_call:
        return torch.ops.vllm.all_reduce(input_, group_name=self.unique_name)
    else:
        return self._all_reduce_out_place(input_)  # 最终调 device_communicator

单卡时原样返回，什么通信都不做；多卡时走 torch 自定义算子，或直接调底层通信器——实现在 vllm/distributed/device_communicators/ 下，如 pynccl.py 的 PyNcclCommunicator、custom_all_reduce.py。各个并行组的句柄则由 parallel_state 提供，例如 get_tp_group()、get_pp_group()、get_dp_group()、get_ep_group()。

10.4切开的代价：TP 与 PP 的通信取舍

分布式不是免费的。切开的卡必须互相说话，而跨卡通信——尤其是跨机走网卡——比卡内显存带宽慢得多。所以选切法，本质是在选「把通信花在哪里」。

TP 把通信花在每一层。同一层切到多张卡，每层前向结束都要 all-reduce 一次，通信量正比于「层数 × 每次合的张量大小」。它对带宽的要求很高，最好几张卡在同一台机器上、走 NVLink 互联。换来的是各卡干一样的活，负载天然均衡。

PP 把通信压到阶段边界。整条流水线几十上百层，只在段与段之间传一两次激活，通信量小，对带宽不敏感，可以跨机。代价有二：一是流水线气泡——下游必须等上游，节奏对不齐就有卡在空转；二是各阶段持有的层数不同，显存占用不均衡。

图 10.2：TP 通信频繁但单次小、卡间算力均衡；PP 通信少但引入串行 bubble。

两种切法不互斥，可以组合着用。选型的出发点是通信路径：卡挨得近、带宽足，TP 通常是第一选择——通信虽频繁，但走的是卡间高速互联，而且负载均衡；模型大到单机放不下，就把跨机的部分交给 PP，让它把「贵」的通信压缩到段边界那几次。vLLM 默认优先 TP、把 PP 留给超大模型，道理就在这笔账上。

PP 在 v1 里怎么跑：整批逐段接力，不是 1F1B

图 10.2 里「阶段间串行」这句话，落到 v1 引擎上有一个明确的实现形态：每个调度步，micro-batch 整批从第一阶段流向最后阶段，各段接力执行。和训练框架里的 1F1B（micro-batch 交错、前后向重叠）不同，v1 的 PP 只做前向、整批传接力棒，流水线气泡大，换来的是实现极简。看非末段的返回值——它把 hidden_states 原样交出去：

vllm/v1/worker/gpu_model_runner.py — execute_model 的 PP 分支（摘录，注释为译注）
pythonif not self.broadcast_pp_output:
    if not get_pp_group().is_last_rank:
        # 非末段：把中间张量原样返回给 Executor，交给下一段
        assert isinstance(hidden_states, IntermediateTensors)
        self.kv_connector_output = kv_connector_output
        return hidden_states
    # 末段才算 logits
    sample_hidden_states = hidden_states[logits_indices]

接力棒从哪接？模型侧自己声明。Llama 的 forward 开头就是这段判位逻辑：

vllm/model_executor/models/llama.py — LlamaModel.forward 的 PP 接棒分支（摘录，注释为译注）

    hidden_states = self.embed_input_ids(input_ids)   # 第一段：查 embedding
    residual = None
else:

两个容易看漏的细节：① 段间传的不是一个张量而是一对——hidden_states 和 residual（RMSNorm 残差流的另一半），所以非首段 runner 在进模型前会先把它们拷进常驻缓冲（sync_and_gather_intermediate_tensors，gpu_model_runner.py:3348），避免每步重新分配显存；② 默认路径下每段执行完直接返回，由 EngineCore 侧串行驱动下一段——只有 external_launcher（torchrun）模式才开 broadcast_pp_output（gpu_model_runner.py:535），改由最后一段算完 logits 后用 broadcast_tensor_dict（src=末段，:4487）把结果反向广播给所有段，保证 torchrun 各 rank 同步。还有一个隐含约定：last rank 才有 lm_head、first rank 才有 embed_tokens（tie_word_embeddings 时两头都有），层权重按 PP 各分各的——这就是 PP 显存不均衡的那个「不均衡」。

EP 的落地：expert_map + all2all，token 跨卡两次

10.3 提到 EP 不单独占一维，现在把这个说法拆开。enable_expert_parallel 打开后，FusedMoE 层内部把「TP 切权重」整个换成「EP 切专家」：每个设备独占若干个专家的完整权重，tp_size 个 rank 变身 ep_size 个 rank（层配置 FusedMoEParallelConfig 里的派生规则：use_ep 时 ep_size = tp_size、tp_size 归 1，fused_moe/config.py:1212——「In EP, each device owns a set of experts fully」）。哪张卡管哪些专家，由 ExpertMapManager 管：determine_expert_map（expert_map_manager.py:22）把 E 个专家尽量均分给 ep_size 个 rank，默认 "linear"（连续段），可选 "round_robin"（隔一个发一个）——这就是 expert_placement_strategy 旋钮；映射表里非本卡的专家记 -1，路由时一眼可判。

token 怎么到拥有它的专家那里？答案是 all2all，分两跳：dispatch 把 hidden_states 连同 topk 权重、专家 id 发出去，各卡收下「路由到我」的 token；本地专家算完，combine 把结果送回去并按位置归约。通信实现由 all2all_backend 旋钮选（config/parallel.py:202，默认 "allgather_reducescatter"）：

后端机制适用
allgather_reducescatter（默认，类 AgRsAll2AllManager）不用专门 all2all kernel：dispatch=全卡 all-gather（token 复制到每张卡，各自挑出自己专家的份），combine=reduce-scatter实现最简单，token 冗余传输，中小规模够用
deepep_high_throughput（DeepEPHTAll2AllManager）DeepEP 高吞吐 kernel，真 all2all，只传「该走的 token」；跨机走 RDMA预填大 batch，吞吐优先
deepep_low_latency（DeepEPLLAll2AllManager）DeepEP 低延迟 kernel，纯 RDMA、低延迟模式，支持容错收缩（enable_shrink）decode 小 batch，延迟优先

选型暗含一条分界线：什么时候才需要专门的 all2all kernel？层配置里的判据（fused_moe/config.py:1025）是 use_all2all_kernels = use_ep and (dp_size > 1 or pcp_size > 1 or 序列并行)——纯 TP 内的 EP（单机、无 DP）各卡 batch 相同，all-gather 就够；一旦上了 DP（各卡 batch 不同）或跨机，token 分布参差，就值得上 DeepEP 这种「精确按需投递」的 kernel。另外还有一层与显存预算的联动：开了 EP 后加载权重时，每个 rank 只读自己那份专家权重（enable_ep_weight_filter，config/parallel.py:181），DeepSeek/Mixtral 这类逐专家存盘的模型能省一大截磁盘 IO。

EPLB 是这套机制上的补丁：均匀切专家的前提是「token 均匀路由」，而真实负载永远偏斜——热门专家所在卡排队，冷门卡闲着。enable_eplb（expert parallelism load balancing）就是为此准备的：runner 每步收尾时调 eplb_step（gpu_model_runner.py:3378），累计各专家的命中率，热度高到阈值就复制出「冗余专家」（num_redundant_experts）挪到冷卡，再重排 expert_map。配合 expert_placement_strategy 的两种初始摆法（连续段 vs 隔行），这是 MoE 大模型上线后真正要调的东西。EPLB 组本身也是一个通信组（get_eplb_group，parallel_state.py:1625），用于重排时的权重同步。
TP 切 KV 有一个特殊档位——只复制、不切分：TP 的本意是均摊显存，但对某些模型，KV cache 的头数太少，硬切到 N 张卡上每张剩不下几个头，通信换来的显存节省不划算。vLLM 给 KV cache 规格加了两个对应字段（kv_cache_interface.py:489 的 max_tp_shards）：这份 cache 在 TP 维度上最多切成几份，超过这个份数的 TP rank 不再拿「四分之一份」，而是整份复制。实际切几份、复制几份在启动时统一算出：kv_cache_groups_tp_replicas（core/kv_cache_utils.py:2408）对每组 KV 规格算 tp_size // max_tp_shards，再对全组取 gcd，得到 kv_tp_replicas（#57652）——「相邻的几个 TP rank 持有完全相同的 KV」。取 gcd 是因为一个 KV 组里有多层、多个 spec 时，复制数必须对所有层都成立。这个数随后写进 KVCacheConfig.kv_tp_replicas（kv_cache_interface.py:1497），供 KV 卸载等下游按「真身 + 副本」理解布局。初读容易误以为这是新加的并行维度——它不增加进程数、不引入新通信组，只是 TP 显存账本上的一个标注：这几张卡的 KV 是彼此的镜像。

all-reduce 的实现栈：从 torch 到 custom kernel

TP 的账算完，还剩一个问题：同样叫 all-reduce，vLLM 内部有几条路？答案在 cuda_communicator.py 的 all_reduce（:335）里，是一条按条件逐级下落的链：

实现条件与特点
NCCL symmetric memory窗口注册的对称显存做 all-reduce，免一次中转拷贝（有输入形状门槛）
QuickAllReduce（ROCm）AMD MI300 专用快速归约，custom allreduce 的补充
Flashinfer allreduce按张量大小与拓扑判断是否启用
CustomAllreduce（ca_comm）vLLM 自写的小消息 all-reduce：抢锁注册对称显存缓冲，跨卡直接读写对方显存，绕开 NCCL 栈；支持 2/4/6/8/16 卡，单条消息上限 8 MiB（custom_all_reduce.py:140）
torch symm-mem / PyNccl / torch.distributed大消息或无 custom 后端时的兜底，pynccl 最常见

这条链解释了一个常见现象：同是 TP=8，矩阵乘之间那种几百 KB 的小 all-reduce 走 custom_allreduce（延迟比 NCCL 低一截），而采样后拼接 logits 的大 all-gather 走 NCCL——不是哪个快用哪个，而是按消息大小各走各的通道。注意 custom allreduce 只在单机内生效，跨机回到 NCCL/RDMA。

还有一半通信在算子内部。TP 对线性层有两种切法，它们的通信方向相反，成对出现：

vllm/model_executor/layers/linear.py — RowParallelLinear.forward（摘录，注释为译注）
pythondef forward(self, input_):
    if self.input_is_parallel:
        input_parallel = input_   # 输入已按特征维切好（前一层是列切）
    ...
    # bias 只加一次：仅在 rank 0 融进 GEMM，其余卡传 None
    bias_ = None if (self.tp_rank > 0 or self.skip_bias_add) else self.bias
    output_parallel = self.quant_method.apply(self, input_parallel, bias_)
    if self.reduce_results and self.tp_size > 1:
        output = tensor_model_parallel_all_reduce(output_parallel)
行切（RowParallelLinear，linear.py:1626）：输入按特征维切、输出要 all-reduce——每张卡算的是部分和，末尾合起来；所以 bias 不能每卡都加（会加 N 次），代码里让它只在 rank 0 融进 GEMM（:1777 的注释原文「bias will not get added more than once in TP>1 case」）。reduce_results 默认 True，但连续两个线性层可由调用方关掉它、把归约推迟到下一层——MLP 的 gate/up 用列切（MergedColumnParallelLinear，linear.py:673）、down_proj 用行切，正是「列切出激活 → 行切接住 → 层尾一次 all-reduce」这套组合。列切（ColumnParallelLinear，linear.py:433）反过来：输入完整、输出按特征维切，gather_output（:609）控制是否 all-gather 回完整输出——vLLM 的层间衔接让它是 False（下一层本来就是行切，要的就是切开的结果）。所以 TP 的一层里，attention 内部投影与 MLP 各发生一次 all-reduce，其余交接零通信——第 7 章讲 kernel 时说的「TP 通信藏在 Linear 层里」，位置就在这。

10.5对照 SGLang：同一个问题的另一种组织

vLLM 的答案到这里齐了：切法按对象分四种；Executor 负责拉起 worker、把每步广播下去；通信代价上，TP 每层都付、PP 只在段边界付。先把四种切法收进一张表：

并行切的对象通信什么时候用
TP同一层权重每层 all-reduce（多）单卡放得下、想更快，带宽好
PP不同层分段阶段间传激活（少）模型大到必须分段、可跨机
DP复制完整模型训练时同步梯度推理=多副本分摊负载，直接扩容
EPMoE 的 expert 层token 路由 + all-to-all超大 MoE，最省显存
自研启示 先跑通单卡（等价 vLLM 的 UniProcExecutor），把正确性搞对。等需要更大模型时，再上 TP——它最容易且通信模型清晰，是「单卡放不下」时的第一选择；PP/DP 是更晚的优化，别一开始就为多机并行分心。原则不变：正确性优先，并行度后置。
与 SGLang 对照 同样是「多卡跑一次推理」，SGLang 的进程组织完全不同。逐项对照：
对比点vLLMSGLang

dp_attention 那行稍微展开一点：大 MoE 模型上，注意力部分每张卡复制一份，MoE 部分切开分片，而每张卡上跑的仍是一个完整的 Scheduler——变的只是并行组的切法。「每卡一个完整调度者」这个组织，换来的正是这种扩展上的自由度。详见 深入浅出SGLang · 10 分布式推理。
