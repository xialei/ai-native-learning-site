实战：给 vLLM 补一层「有状态」的 Agentic 网关

第 9 章的结论是「vLLM 的 API server 是无状态的」——这正是它水平扩展的资本。但真实的 Agent 应用偏偏需要状态：previous_response_id 续聊、服务端工具循环、多轮编排、持久化。这一章拆解 vllm-project/agentic-api（Rust）——一个坐在 vLLM 前面、专门承接这些「状态活」的网关，看它如何把「一次客户端请求」变成「N 轮无状态推理 + 工具执行」，再拼成一条响应流还给你。
代码来源 本章所有 Rust 片段摘自 vllm-project/agentic-api（v0.5.0-24-gc04ac19，Apache-2.0），核心库在 crates/agentic-server-core/（对外叫 agentic_core）。它不是 vLLM 的 fork，而是一个独立进程：vLLM 用 vllm serve 原样启动，网关把请求翻译成 vLLM 自己的 OpenAI 兼容 Responses API 再转发。片段有删节，行内中文注释是本书补写的说明——源码里的注释是英文。

13.1问题：vLLM 是无状态的，Agent 是有状态的

先回到第 9 章的架构：vLLM 的 OpenAI API server（vllm/entrypoints/openai/）被刻意设计成无状态、可水平扩。它其实也实现了一个 Responses API，但状态管理非常有限——看 vllm/entrypoints/openai/responses/serving.py 里存储是怎么做的：

vllm/entrypoints/openai/responses/serving.py — vLLM 自带的「响应存储」（摘录）
python# HACK(woosuk): This is a hack. We should use a better store.
# FIXME: If enable_store=True, this may cause a memory leak since we
# never remove responses from the store.
self.response_store: dict[str, ResponsesResponse] = {}
self.response_store_lock = asyncio.Lock()
看懂这段：三行注释把问题说透了——默认 store=False 直接忽略；即便用 VLLM_ENABLE_RESPONSES_API_STORE=1 打开，也只是一个进程内 dict：重启即失、单机限死、从不清理（官方注释自认 may cause a memory leak）。对「续聊要带着全部历史、跨请求、跨副本」的 Agent 场景，这层是不够的。

更关键的是工具循环。Agent 一句话触发十几次工具调用很常见，而 vLLM 的定位是「一次请求进、一批 token 出」的推理引擎。把循环放在每个客户端里，意味着：每个 SDK、每个脚本都要自己重放历史、自己执行工具、自己处理 SSE 拼接——这就是 agentic-api README 说的「Today, all of that complexity lives in your client code」。

agentic-api 的答案：状态上移到网关，推理留在 vLLM。整体架构是这样：

图 13.1：agentic-api 在 vLLM 前承接「有状态的活」。vLLM 只看到一份份自包含的无状态请求；历史、工具循环、持久化都由网关负责。
对照第 9 章第 9 章讲「API server ↔ EngineCore」是进程内的无状态/有状态分层；本章是它的镜像补充：把「对话级状态」从推理进程里彻底拿出去，放到一个独立的 Rust 网关进程。两层拆分之后，vLLM 侧保持纯粹的「token 工厂」，可以随便重启、扩缩容，而对话状态安稳地躺在网关的数据库里。

13.2一次请求的两条路：executor 还是纯代理

网关并不劫持所有流量。每个 POST /v1/responses 先做一个路由判定：请求里有没有「只有网关才能干」的活？没有就原样透传给 vLLM，一个字节都不改：

crates/agentic-server/src/handler/http/responses.rs — 路由判定（摘录，注释为译注）
rustlet should_execute = routing_payload.store
    || routing_payload.previous_response_id.is_some()
    || routing_payload.in_process_feature().is_some();

if should_execute {
    execute_responses(&state, parts, payload).await
} else {
    proxy_responses(&state, parts, bytes).await   // 原样透传 vLLM
}

其中 in_process_feature()（crates/agentic-server-core/src/types/request_response.rs:182）枚举了「网关专属」的四种特征：conversation_id、任何非 function 的工具声明（网关自有工具与 client 侧 custom 工具都在此列——后者虽由客户端执行，但「注册、改写为 function」这一步必须发生在网关进程里）、compaction 输入、context_management。命中任意一个就走执行器路径。

为什么值得学：这是网关类的「透明降级」设计——用户发一个纯无状态请求时，网关只做转发（agentic_core::proxy，不解析不落库）；只有真的需要状态时才启动编排。代价小、语义清晰：vLLM 自己能干的事绝不代劳。

13.3状态恢复：previous_response_id → 完整历史

执行器路径的第一步是 rehydrate（恢复历史）：客户端只带一个 previous_response_id，网关把这条 ID 背后的全部历史从数据库里捞出来，拼到本轮输入前面。入口在 crates/agentic-server-core/src/executor/rehydrate.rs：

crates/agentic-server-core/src/executor/rehydrate.rs — rehydrate_conversation（摘录，注释为译注）
rustpub async fn rehydrate_conversation(
    request: RequestPayload,
    exec_ctx: &ExecutionContext,
) -> ExecutorResult<RequestContext> {
    let response_id = uuid7_str("resp_");   // 先领好本轮 response id
    ...
    if ctx.original_request.conversation_id.is_some()
        && ctx.original_request.previous_response_id.is_some()
    {
        return Err(ExecutorError::InvalidRequest(
            "provide only one of conversation_id or previous_response_id".into(),
        ));
    }
    if ctx.original_request.conversation_id.is_some() {
        from_conversation(&mut ctx, exec_ctx).await?;   // 会话树
    } else if ctx.original_request.previous_response_id.is_some() {
        from_response(&mut ctx, exec_ctx).await?;      // 响应链
    } else {
        ctx.enriched_request.input = ResponsesInput::Items(ctx.new_input_items.clone());
    }
    Ok(ctx)
}

两种取历史的模式：conversation_id 走会话树（一个 conversation 对应一串 items，天然支持多人/多端共享一个会话），previous_response_id 走响应链（每个 response 记录自己继承的 history_item_ids）。看响应链这边怎么把历史与新输入拼合，并顺手校验「悬空的工具调用」：

crates/agentic-server-core/src/executor/rehydrate.rs — from_response（摘录，注释为译注）
rustasync fn from_response(ctx: &mut RequestContext, exec_ctx: &ExecutionContext) -> ExecutorResult<()> {
    let stored = exec_ctx.resp_handler.get(ctx).await?;      // 上一条 response 的元数据
    let history = exec_ctx.resp_handler.rehydrate(ctx).await?;  // 它的全部 items

    let mut items = InOutItem::into_input_items(history);  // 行 → 领域类型
    items.extend(ctx.new_input_items.iter().cloned());    // 追加本轮新输入
    if let Some(pending) = pending_calls(&items)?.into_iter().next() {
        // 上一轮有个 function_call 还没等到 function_call_output？
        // 拒绝整个请求，而不是带着悬空调用去推理。
        return Err(ExecutorError::Tool(ToolError::MissingOutput {
            call_id: pending.call_id,
        }));
    }

    ctx.enriched_request.previous_response_id = None;   // 对上游：无状态！
    ctx.enriched_request.input = ResponsesInput::Items(items);
    ...
}
三个细节：(1) 拼完历史立刻做 pending calls 校验——每个 call_id 必须唯一、每个 call 必须有且仅有一个 output，有悬空就拒绝请求（4xx），绝不把烂账喂给模型；(2) previous_response_id 被清空——vLLM 收到的永远是自包含全量输入，它不需要知道「续聊」的存在；(3) 工具声明可以从上条 response 的元数据里继承（resolve_tools），续聊不必每次重发 tools。

那数据库里到底存了什么？看建表 SQL，整个存储只有三张表，核心是一张 items 流水表：

crates/agentic-server-core/migrations/0001_initial.sql（摘录）
sqlCREATE TABLE IF NOT EXISTS conversations (
    id          TEXT PRIMARY KEY,
    created_at  INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS items (
    id              TEXT PRIMARY KEY,
    data            TEXT NOT NULL,      -- 一条 message / function_call / reasoning… 的 JSON
    created_at      INTEGER NOT NULL,
    conversation_id TEXT REFERENCES conversations(id) ON DELETE CASCADE,
    seq             INTEGER             -- 会话内序号，重放顺序的依据
);

CREATE TABLE IF NOT EXISTS responses (
    id                   TEXT PRIMARY KEY,
    conversation_id      TEXT REFERENCES conversations(id),
    previous_response_id TEXT REFERENCES responses(id),
    history_item_ids     TEXT,   -- 本 response 继承 + 新增的 item id 列表
    metadata             TEXT,   -- 有效 tools / tool_choice 快照，供续聊继承
    created_at           INTEGER NOT NULL
);
设计取舍：没有「响应表存整段对话」的宽表，而是 append-only 的 item 流水 + 链式索引。每一轮持久化时，把本轮的输出转成 InputItem 追加进 items，再把继承的 id 链写进 responses.history_item_ids。好处：续聊只需按 id 列表捞行、按序号重放；纯 JSON 列让 item 类型天然可扩展（SQLite 默认库，可切 PostgreSQL）。

13.4核心：多轮工具循环 run_gateway_tool_loop

这是整章的核心。客户端发来一句话，模型可能要调 3 次工具才能答——「推理一轮 → 执行工具 → 把结果喂回去 → 再推理」的循环发生在网关里，客户端对此无感。看 crates/agentic-server-core/src/executor/engine.rs（下为摘录拼接，保留了原始顺序）：

crates/agentic-server-core/src/executor/engine.rs — run_gateway_tool_loop（摘录，注释为译注）
rustconst MAX_GATEWAY_TOOL_ROUNDS: usize = 10;

async fn run_gateway_tool_loop(
    mut ctx: RequestContext,
    exec_ctx: &ExecutionContext,
    ...
) -> ExecutorResult<(ResponsePayload, RequestContext)> {
    let mut registry = build_tool_registry(&mut ctx, exec_ctx).await?;

    for round in 0..MAX_GATEWAY_TOOL_ROUNDS {
        // ① 每轮推理前：先看上下文要不要压缩（13.7）
        let compaction_usage = maybe_compact_context(&mut ctx, exec_ctx, auth).await?;

        // ② 一轮无状态推理：把全量历史发给 vLLM
        let (mut payload, deferred_stream_events) = if stream_upstream {
            fetch_stream_payload(&ctx, exec_ctx, auth, &registry, ...).await?
        } else {
            (fetch_blocking_payload(&ctx, exec_ctx, auth).await?, Vec::new())
        };

        // ③ 本轮产出的 function_call，按所有权分派执行
        let has_client_owned = has_client_owned_calls(&current_output, &registry);
        let gateway_results = execute_and_emit_round_output_calls(
            &current_output, &registry, output_offset, ...
        ).await?;

        // ④ 决定：继续循环 / 交还客户端 / 完成 / 轮数耗尽
        match classify_round(has_client_owned, &gateway_results, round, MAX_GATEWAY_TOOL_ROUNDS) {
            LoopDecision::Continue => {
                ctx.enriched_request.tool_choice = Some(ToolChoice::Auto);
                append_output_items_to_input(&mut ctx.enriched_request.input, &current_output);
                append_gateway_calls_to_new_input(&mut ctx, &current_output, &registry);
                append_tool_outputs(&mut ctx, ...);   // 工具结果 → 下一轮输入
            }
            LoopDecision::Done | LoopDecision::RequiresClientAction
            | LoopDecision::Incomplete(_) => { finalize_loop(...); return Ok((payload, ctx)); }
        }
    }
}

而「怎么决定下一步」的函数非常短，值得整段读——它就是循环的状态机：

crates/agentic-server-core/src/executor/engine.rs — classify_round（全文；注释为译注）
rustfn classify_round(
    has_client_owned_calls: bool,
    gateway_results: &[GatewayCallResult],
    round: usize,
    max_rounds: usize,
) -> LoopDecision {
    if has_client_owned_calls {
        LoopDecision::RequiresClientAction   // 客户端工具：交还调用方
    } else if gateway_results.is_empty() {
        LoopDecision::Done                   // 模型不再要工具：收工
    } else if round + 1 >= max_rounds {
        LoopDecision::Incomplete(...)        // 10 轮用完：返回 status=incomplete
    } else {
        LoopDecision::Continue
    }
}
看懂这个状态机：四个出口的优先级就是语义：客户端工具最优先（哪怕本轮同时有网关工具，网关的也先执行、记档，但响应仍交还客户端——这样客户端下一轮带着完整上下文回来）；「模型这轮没要工具」才意味着完成；10 轮上限不报错，而是把已积累的输出以 status: "incomplete" 交还，且最后一轮的调用/结果照常落库，保证续聊时没有悬空的 function_call。把「错误」「部分成功」「预算耗尽」都表达成正常的状态而非异常，长循环服务应当这样设计。
图 13.2：客户端的一次请求 = 网关里的 N 轮「推理→执行→回灌」。vLLM 每轮都是独立的无状态调用。

13.5工具所有权：一个工具，三种命运

循环里「执行工具」这一步有个关键前提：网关必须知道每个工具归谁执行。agentic-api 把它做成了显式类型，而不是靠名字猜：

crates/agentic-server-core/src/tool/ownership.rs — 所有权枚举（摘录，注释为译注）
rustpub enum ToolOwnership {
    Client,
    /// `None` 表示原则上归网关、但还没实现 handler（如 FileSearch/CodeInterpreter）。
    Gateway(Option<GatewayBinding>),
}

三种命运对应三个归属：Client——调用原样交还客户端执行（function、custom、Codex 命名空间）；Gateway(Some)——网关绑定执行器自己跑（web_search、MCP 发现的工具）；Gateway(None)——原则上归网关、但 handler 尚未实现（如 FileSearch / CodeInterpreter），调度器派活时命中 GatewayExecutionPlan::MissingHandler（gateway.rs:242），生成一条「has no registered handler」的错误输出喂回模型，请求照常继续而不是 500。

每个请求开始时，网关把客户端声明的所有工具「过一遍注册流程」，建出一张 模型可见名 → 条目 的请求级注册表：

crates/agentic-server-core/src/tool/registry.rs — build_with_handlers（摘录，注释为译注）
rustpub async fn build_with_handlers(
    tools: &mut [ResponsesTool],
    executors: &mut GatewayExecutors,
) -> Result<Self, ToolError> {
    let mut entries = HashMap::with_capacity(tools.len());
    for (index, tool) in resolved_tools.iter().enumerate() {
        match tool {
            ResponsesTool::Function(p) => { /* 客户端自有：Client */ }
            ResponsesTool::Mcp(p) => {
                // 现场连 MCP server，tools/list 发现该 server 的工具
                let tool_set = executors.mcp_server_tools(p).await?;
                for discovered in handlers {
                    insert_discovered_mcp_entry(...);   // 归网关
                }
            }
            ResponsesTool::WebSearch(p) => {
                insert_web_search_entry(..., executors.web_search_handler());
            }
            ...
        }
    }
}
为什么 vLLM 只见到 function 工具推理前有个「规范化」步骤（RequestPayload::to_upstream_request，types/request_response.rs:258）：所有能执行的声明——web_search、mcp、custom、Codex 命名空间——统统统一成普通的 {"type":"function"} 工具再发给 vLLM。因为 vLLM 只认 function 工具。推理完拿到 function_call 后，网关再用注册表把名字还原成真实的公开形态（web_search_call / mcp_call / custom_tool_call）。概括成一句：wire 层做加法，语义层做还原。

「网关侧执行」由一个两段式 trait 决定，所有工具类型都实现它：

crates/agentic-server-core/src/tool/handler.rs — 两个核心 trait（摘录，注释为译注）
rust/// 所有工具（无论归谁执行）都实现：校验 + 转成 vLLM 的 function 工具
pub trait ToolHandler: Send + Sync {
    type ToolParams: Send + Sync;
    fn tool_type(&self) -> ToolType;
    fn validate(&self, params: &Self::ToolParams) -> Result<(), ToolError>;
    fn normalize(&self, params: &Self::ToolParams) -> Vec<FunctionTool>;
}

/// 只有「网关执行」的工具才实现：真正干活 + 生命周期投影
pub trait GatewayExecutor: ToolHandler + 'static {
    type ExecutionParams: Clone + Send + Sync + 'static;

    fn execute(&self, call_id: &str, tool_name: &str, arguments: &str,
        params: &Self::ExecutionParams)
        -> Pin<Box<dyn Future<Output = Result<ToolOutput, ToolError>> + Send + '_>>;

    /// 同名工具能不能并发跑自己？（默认 false：只串行化同名调用，
    /// 不同工具之间照样并发）
    fn supports_parallel_execution(&self) -> bool { false }
    ...
}
拆开看：ToolHandler 管「声明侧」（校验、转成 function 工具）；GatewayExecutor 额外管「执行侧」（真跑、超时、并发策略、对外事件）。客户端工具（function/custom/Codex namespace）只实现前者——它们的调用永远原样交还客户端。这样新增一种工具 = 实现两个 trait + 注册，循环代码一行不改（设计文档称 additive 原则：「The executor loop doesn't change.」）。

落到具体工具上，比如内置的 web_search（You.com 后端）：一次调用最多带 5 个 query，逐个拿信号量后并发查：

crates/agentic-server-core/src/tool/web_search.rs — execute_search（摘录，注释为译注）
rustconst MAX_WEB_SEARCH_QUERIES: usize = 5;

async fn execute_search(&self, call_id: &str, arguments: &str, params: ...) {
    let queries = WebSearchArguments::from_json(arguments)?.all_queries();

            let _permit = query_permits.acquire_owned().await?;  // 信号量限流

最后，循环里真正「派活」的是 GatewayScheduler——它把每轮产出的 function_call 过一遍注册表，找出网关拥有的那些，绑定执行器并并发执行（注意错误处理：单个工具失败不会炸掉整个响应，而是变成一条错误结果喂回模型）：

crates/agentic-server-core/src/executor/gateway.rs — GatewayScheduler::execute 与 run_one（摘录，注释为译注）
rustpub(super) async fn execute(&mut self) -> ExecutorResult<Vec<GatewayCallResult>> {
    let execution_slots = Semaphore::new(self.policy.max_concurrent_calls.get());  // 默认 5
    let results = join_all(self.calls.iter().cloned()
        .map(|call| self.run_one(call, &execution_slots))).await...;
    ...
}

async fn run_one(&self, plan: GatewayCallPlan, execution_slots: &Semaphore)
    -> ExecutorResult<GatewayCallResult>
{
    let _permit = match &binding.self_exclusion {
        Some(semaphore) => Some(semaphore.acquire().await...),  // 同名互斥
        None => None,
    };
    let _execution_slot = execution_slots.acquire().await...;  // 全局并发上限

    let dispatched = match tokio::time::timeout(self.timeout,
        binding.execute(&call.call_id, &call.name, &call.arguments)).await
    {
        Ok(output) => output,
        Err(_elapsed) => Err(ToolError::Execution(format!(
            "gateway tool '{}' timed out after {:?}", call.name, self.timeout))),
    };
    // 执行失败 → 一条 error 结果回喂模型，而不是 500 掉整个请求
    let (output, status) = match dispatched {
        Ok(output) => (output, GatewayCallStatus::Completed),
        Err(ToolError::Execution(message)) =>
            (execution_error_output(&call, &message)?, GatewayCallStatus::Failed),
        ...
    };
}
三层并发控制叠在一起：(1) 全局滑动窗口 max_concurrent_gateway_calls（默认 5，来自 config.rs:23 的 DEFAULT_MAX_CONCURRENT_GATEWAY_CALLS）；(2) 每个工具自己的 self_exclusion 信号量——supports_parallel_execution() 返回 false 的工具，同名调用自动排队；(3) 单次调用 60s 超时（GATEWAY_TOOL_TIMEOUT，gateway.rs:47）。三层正交：改全局吞吐、改单工具串行策略、改超时互不干扰。

13.6流式重组：N 轮 SSE 拼成一条流

客户端要的是「一次请求、一条平滑的 SSE 流」。但网关内部跑了 N 轮推理，每轮 vLLM 都各自发一套 response.created / sequence_number / output_index。直接转发就会出现「第 3 轮突然又来一个 created、序号倒退」的乱序流。做重组的是 GatewayStreamAccumulator：

crates/agentic-server-core/src/executor/gateway_accumulator.rs（摘录，注释为译注）
rustpub struct GatewayStreamAccumulator {
    next_sequence_number: u64,     // 跨轮单调递增
    emitted_created: bool,          // response.created 只发一次
    emitted_in_progress: bool,
}

pub fn process_event(&mut self, frame: &mut EventFrame, output_offset: usize) -> bool {
    if !self.should_emit_lifecycle(frame.event_type) { return false; }
    self.stamp_event(frame, output_offset);   // 重打 sequence_number / output_index
    true
}
它只做三件事：① 全流 sequence_number 单调递增（跨轮连续）；② 后面轮次的 output_index 整体平移（output_offset），让第 2 轮的输出接在第 1 轮后面而不是顶掉它；③ response.created/in_progress 去重，每个 response 只发一次。其余帧原样透传。名字里虽然有 accumulator，但它不攒数据——攒数据的是另一头的 ResponseAccumulator（把流拼回完整 JSON 用）。

更麻烦的是工具事件：vLLM 不管工具归谁，一律吐 function_call 事件。但公开 API 里 web_search/MCP 调用应该是 web_search_call / mcp_call 形状，而且要等真实执行完才能给结果。翻译器 FunctionSseTranslator 在流上做三方分流（executor/function_sse.rs:15 的 FunctionCallShape）：

crates/agentic-server-core/src/executor/function_sse.rs — 流上的三种形状（摘录）
rustenum FunctionCallShape {
    PublicFunction,   // 客户端 function 工具：原样透传
    GatewayOwned,     // web_search/MCP：先扣下（suppress），执行完再合成公开事件
    Custom(CustomCallState),  // 自由格式工具：把 arguments 流重拼成 input 流
}

const MAX_PENDING_FUNCTION_BYTES: usize = 256 * 1024;  // 未知名调用缓冲上限
难点在时序：模型可能先吐 arguments 后吐名字（甚至不吐），网关收到「没名字的 function_call delta」只能先缓冲——但必须封顶（256 KiB，防恶意流打爆内存）；等名字到了再决定「透传 / 改写 / 抑制」。而网关工具的公开生命周期事件（开始/完成/失败）是执行完事后合成的，并把 defer 边界记住，保证客户端看到的顺序仍然是模型输出的顺序。

整条流的入口在 engine.rs::run_stream——一个 tokio::select! 循环，一边消费后台循环发出的事件，一边保证「持久化先于 response.completed 出门」：

crates/agentic-server-core/src/executor/engine.rs — run_stream（摘录）
rustloop {
    tokio::select! {
        Some(event) = event_rx.recv() => {
            yield consume_stream_event(event, &mut next_sequence_number);
        }
        result = &mut run_handle.handle => {
            match result {
                Ok((Ok((payload, ctx)), mut stream_accumulator)) => {
                    // Codex 收到 completed 就会立刻断开 WebSocket，
                    // 所以必须先落库、再发终态事件，防止续话断档。
                    match persist_if_needed(payload, ctx, ch, rh).await {
                        Ok(()) => { if let Ok(chunk) = terminal_chunk { yield chunk; } }
                        Err(e) => yield stream_accumulator.executor_error_chunk(&e),
                    }
                    yield DONE_MARKER.to_string();   // data: [DONE]
                }
                ...
            }
        }
    }
}
工程细节「持久化先于终态事件」是一个容易踩的坑：如果先把 response.completed 发出去，客户端（尤其 Codex 这种拿到终态就关连接的）会立刻断开，此时持久化若还没完成就被取消，下一轮 previous_response_id 就指向一条没写完的历史。顺序反过来，掉电都不怕。

13.7上下文压缩：compaction，长会话的活命机制

对话越长，每轮「全量重放」就越贵（这正是第 8 章讲过的 KV/显存预算问题的 API 层版本）。agentic-api 提供了 compaction：把旧上下文压成一条「检查点摘要」，之后的轮次只带摘要 + 摘要后的新内容。可以显式调 POST /v1/responses/compact，也可以挂自动阈值，每轮推理前检查：

crates/agentic-server-core/src/executor/compaction.rs — maybe_compact_context（摘录）
rustpub(crate) async fn maybe_compact_context(
    ctx: &mut RequestContext, exec_ctx: &ExecutionContext, auth: Option<&str>,
) -> ExecutorResult<Option<ResponseUsage>> {
    let Some(threshold) = ctx.enriched_request.context_management
        .as_deref().unwrap_or_default()
        .iter().find(|entry| entry.type_ == "compaction")
        .and_then(|entry| entry.compact_threshold)
    else { return Ok(None); };                     // 没配阈值：不压缩

    let estimated_tokens = estimate_input_tokens(&ctx.enriched_request.input);
    if estimated_tokens <= threshold { return Ok(None); }  // 没超阈值：不压缩

    let (compacted, usage) = compact_items(&model, input, ..., exec_ctx, auth).await?;
    ctx.enriched_request.input = ResponsesInput::Items(compacted.clone());
    ctx.new_input_items = compacted;
    Ok(Some(usage))
}

压缩的执行本身也是一次普通的推理调用——用一段固定的 CHECKPOINT 提示词让模型自己总结：

crates/agentic-server-core/src/executor/compaction.rs — 压缩提示词（原文）
rustconst COMPACTION_PROMPT: &str = "You are performing a CONTEXT CHECKPOINT COMPACTION. Create a concise handoff summary that preserves current progress, decisions, constraints, unresolved work, and critical references for the next model. Return only the summary.";

压完之后，「历史可见性」有两条边界，值得分开看（types/io/input.rs:340）：

crates/agentic-server-core/src/types/io/input.rs — model_input：模型可见性边界（摘录）
rustpub fn model_input(&self) -> Cow<'_, Self> {
    // ① 剥掉编排用的内部项（mcp_list_tools / compaction_trigger）——模型永远看不到
    // ② 若有压缩检查点：检查点之前的旧上下文被摘要取代；
    //    检查点本身转成一条 assistant 消息（内容即摘要文本）
    let model_items = window.retained_user_items(items)
        .chain(items[window.latest_index()..].iter())
        .filter(|item| item.is_model_visible())
        .map(|item| match item {
            InputItem::Compaction(compaction) => InputItem::Message(...),  // → assistant 摘要
            other => other.clone(),
        }).collect();
}
两层边界要分清：持久化层（rehydrate 时 InOutItem::into_input_items）保留全量历史（含压缩项、MCP 发现记录），供编排决策用；模型可见层（model_input()）在每次上游请求前现场裁剪。存的是全量，发的是裁剪后的——这样将来改压缩策略不用迁移历史数据。

13.8实战串联：把三层跑起来

把第 9 章（vLLM 服务）和本章（网关）拼成一条完整命令链——注意 vLLM 的启动参数只有解析器类配置（工具解析器 + 自动工具选择 + 推理解析器），状态与循环完全不归它管：

三层启动（终端）
bash# ① vLLM：无状态推理引擎（第 9 章的 AsyncLLM + EngineCore）

  --tool-call-parser qwen3_coder --enable-auto-tool-choice \
  --reasoning-parser qwen3 --port 5050

# ② agentic-api 网关：状态、工具循环、持久化（本章主角）
YOU_API_KEY=<you.com-key> cargo run -p agentic-server -- --llm-api-base http://0.0.0.0:5050

# ③ 客户端：带工具发一次请求，后续用 previous_response_id 续聊
curl http://localhost:9000/v1/responses -H "Content-Type: application/json" -d '{
  "model": "Qwen/Qwen3-30B-A3B-FP8",
  "input": "What is new in vLLM this month?",
  "tools": [{"type": "web_search"}]

层次谁状态这一章的关键词
推理引擎vLLM（第 1-10 章）仅 KV cache 级状态每轮独立、自包含输入
状态/编排agentic-api 网关会话、响应链、工具结果rehydrate → 循环 → persist
存储SQLite / PostgreSQLitems 流水 + responses 链追加式、重放式
工具三方分权—Gateway / Client / Provider 所有权
自研启示 把本章和第 9 章的启示拼起来，得到自研引擎的状态层路线图：① 引擎保持彻底无状态（自包含输入、自包含输出），把「续聊」从引擎里扔出去；② 需要多轮时，先写一个进程内的工具循环（本章 13.4 的 classify_round 十几行就是完整语义）；③ 历史重放先用「每次全量拼接」的笨办法，跑通后再加 compaction；④ 最后才考虑把状态层拆成独立进程 + 数据库——到那一步，你的架构就和 agentic-api + vLLM 同构了。
延伸阅读 网关背后的一切仍是前十章的引擎：第 9 章解释了为什么 vLLM 侧可以无状态；第 4 章的抢占与调度决定了「N 轮循环」里每一轮的时延；第 8 章的显存预算则是 compaction 之所以必要的根本原因。另外 agentic-api 还有一个 agentic-llm-d crate，把同一套存储/工具原语以「后端模式」暴露给 llm-d 编排器——同一份核心库，两种部署形态，这也是「核心与传输分离」的又一例证。
