内存规划与 KV 预算：GPU 显存怎么分、KV 能塞多少

启动一个 vLLM 实例时，它要先回答一个问题：权重占了多少，还剩多少能给 KV cache，够几个请求同时跑？这一章讲清楚显存划分、内存 profile/warm-up、KV 预算公式、batch 上限，以及前缀缓存为什么能白赚很多 prefill。

8.1显存怎么分：权重 + KV cache + activation

一张 GPU 的显存，在 vLLM 看来大致分成三大块。前三块是「常驻」的，最后一块是「每步临时」的：

  • 模型权重：加载进显存的参数（含每层的权重），一进来就占满，不会波动。
  • KV cache：给所有并发请求存 K/V。数量由「剩余显存 ÷ 每块字节」决定，是本章主角。
  • activation / 临时缓冲：一次 forward 里算出来的中间激活、CUDA graph 捕获的输入输出缓冲区等，随 batch 大小波动。

图 8.1：显存三块——权重与 activation 是固定开销，KV 是“吃剩下的”。比例仅为示意。

划总预算的开关是 CacheConfig.gpu_memory_utilization：0~1 之间，表示「这份 GPU 显存的多少比例拿来给本实例」。注意：当前代码里默认值是 0.92，而不是很多人以为的 0.9，它是可配置的（--gpu-memory-utilization）。

vllm/config/cache.py — CacheConfig（摘录）
pythonclass CacheConfig:
    DEFAULT_BLOCK_SIZE: ClassVar[int] = 16          # 每块 16 个 token

    gpu_memory_utilization: float = Field(default=0.92, gt=0, le=1)
    # The fraction of GPU memory to be used for the model executor ...
    # If unspecified, will use the default value of 0.92.
    # 这是 per-instance 限制：只作用于当前实例。
关键理解：0.92 不是「KV 占 92%」，而是「整个实例最多用 92%」。权重先吃一份，activation 再吃一份，剩下的才轮到 KV。所以比例调高 → KV 预算变大；调低 → KV 变小。

8.2内存 profile / warm-up：KV 预算怎么“量出来”

vLLM 不是「猜一个 KV 大小」，而是真在 GPU 上跑一遍。启动时它用 memory_profiling 上下文量好权重+activation 的峰值，然后算「还能腾多少给 KV」。

实测口径在 vllm/v1/worker/gpu_worker.py：先记录初始空闲显存 init_snapshot，把「请求的总预算」记为 requested_memory；profile 过后量出 non_kv_cache_memory（权重 + activation），相减就是可给 KV 的字节数：

vllm/v1/worker/gpu_worker.py — KV 预算计算（摘录）
pythonself.total_consumed = profile_result.total_consumed
# 权重 + activation 峰值（profile 中实测出的占用）
self.peak_activation_memory = (...)
...
self.available_kv_cache_memory_bytes = (
    self.requested_memory                # 0.92 × 初始空闲显存
    - profile_result.non_kv_cache_memory # 减掉权重 + activation
    - cudagraph_memory_estimate_applied  # CUDA graph 缓冲也要留
)
# 之后据这个字节数算 num_blocks，见 8.3

而「怎么把能用的显存试出来」靠两大段 warm-up。其一：GPUModelRunner.profile_run() 在 profile 期间用一个 _dummy_run(max_num_tokens) 的假前向把 weights + activation 的峰值顶出来（第 5 章讲过这个假前向）。其二：vllm/v1/worker/gpu/warmup.py 里跑一批真实的 warmup_kernels，把要用的 kernel 都点亮，并用 run_mixed_prefill_decode_warmup 专门验证「KV 块够不够塞下我准备调的 batch」：

vllm/v1/worker/gpu/warmup.py — 用 KV 块数决定 warmup 批大小（摘录）
pythonnum_reqs = min(
    model_runner.scheduler_config.max_num_seqs,
    model_runner.scheduler_config.max_num_batched_tokens
    // max(prompt_len, decode_query_len),
)
if max_blocks_per_req > 0:
    # 预留 null block(0)，并保证块够用
    num_reqs = min(
        num_reqs,
        max(1, (model_runner.kv_cache_config.num_blocks - 1)
            // max_blocks_per_req),
    )
这段话的份量：warm-up 不是「热身就完事」——它把 num_blocks 和 max_num_seqs / max_num_batched_tokens 绑在了一起：如果 KV 块不够放下我要调的 batch，它不会硬调，而是把批改小。KV 预算直接决定了你能扛多大的并发。对自研引擎而言，这一整套「profile → 算剩余 → 定 KV 预算」就是成熟度分水岭。

8.3KV 预算公式：每 token 多少字节，能分几块

KV cache 的大小可以直接算出来。每个 token 要存 K 和 V 两组向量，层数以外还有「每组 KV 头」这个关键参数（num_kv_heads——GQA/MLA 下它比 query heads 小很多，是省显存的关键）：

每 token 字节 ≈ 2（K 和 V 两份）× num_layers × num_kv_heads × head_dim × dtype 字节

例如一个 32 层、kv_heads=8、head_dim=128、bf16（2 字节）的模型：
2 × 32 × 8 × 128 × 2 = 131,072 字节 ≈ 128 KiB / token。
一条 4K 的序列就要 128 KiB × 4096 ≈ 512 MiB；GPU 里想塞 10 条这样的，KV 就得 5 GiB 起步。

vLLM 按「块」来装这些 token。每块 block_size（默认 16）个 token，那么一块的字节就是「每 token 字节 × 16」。块数和可用显存的关系，在 kv_cache_utils.py 里就是一句除法：

vllm/v1/core/kv_cache_utils.py — 可用显存 ÷ 每块字节（摘录）
pythondef get_kv_cache_config_from_groups(vllm_config, kv_cache_groups,
                                           available_memory):
    # 每个块占多少字节（把该组所有层、所有 KV 头的 K+V 都算进去）
    bytes_per_block = _get_kv_cache_bytes_per_block(kv_cache_groups)
    # 块数 = 可用显存 / 一个块的字节
    num_blocks = available_memory // bytes_per_block
    num_blocks = may_override_num_blocks(vllm_config, num_blocks)
    size = bytes_per_block * num_blocks
    return KVCacheConfig(num_blocks=num_blocks, kv_cache_tensors=[...], ...)
读懂 num_blocks = available_memory // bytes_per_block：这个 num_blocks 就是最终写回 cache_config.num_gpu_blocks 的值，即 8.2 的 available_kv_cache_memory_bytes 换算来的块数。它是 BlockPool 预先分配的总物理块数；may_override_num_blocks 允许你用 num_gpu_blocks_override 手动指定（测试/预取用）。

8.4max_num_seqs / max_num_batched_tokens：每步能跑多少

KV 预算回答了「显存够不够」，但每一步实际跑多少请求、多少个 token，由 SchedulerConfig 的两个上限管着：

vllm/config/scheduler.py — SchedulerConfig（摘录）
pythonDEFAULT_MAX_NUM_BATCHED_TOKENS: ClassVar[int] = 2048
DEFAULT_MAX_NUM_SEQS: ClassVar[int] = 128

max_num_batched_tokens: int = Field(default=DEFAULT_MAX_NUM_BATCHED_TOKENS, ge=1)
# Maximum number of tokens that can be processed in a single iteration.
max_num_seqs: int = Field(default=DEFAULT_MAX_NUM_SEQS, ge=1)
# Maximum number of sequences to be processed in a single iteration.
  • max_num_batched_tokens（默认 2048）：一步 ≤ 多少个 token。它决定单次 forward 的激活峰值——预分配 max_num_tokens = max_num_batched_tokens 的中间缓冲，是 activation 显存的主要来源。
  • max_num_seqs（默认 128）：一步 ≤ 多少个序列（请求）。防止 decode 步里一堆只出 1 个 token 的序列把 batch 撑爆。
注意：默认值随硬件动态变化 上面 ClassVar 里的 2048 / 128 只是最底层的 fallback。真实启动时，EngineArgs（vllm/engine/arg_utils.py 的 _set_default_max_num_seqs_and_batched_tokens_args）会按 GPU 显存档位 + 用途（离线 LLM / 在线 API server）覆盖它们：≥70GB 的非 A100 卡（如 H100/H200）上 max_num_batched_tokens 默认开到 8192～16384、max_num_seqs 开到 1024；TPU/CPU 又是另一套表。所以你在 H100 上跑会看到与 2048 不同的默认值——以实际为准，别死记 2048/128。

这两个值和 KV 预算的关系非常直接：batch 越大 → 同时跑的序列越长/越多 → 需要的 KV 块越多。8.2 里 warmup 那行 min(max_num_seqs, max_num_batched_tokens // ...) 又在 KV 块够的前提下把这些上限封顶。所以：

留白 特意留出 activation 显存：profile 量出来的是 activation 的峰值（按 max_num_batched_tokens 顶满），所以 KV 拿到的永远比「总显存 − 权重」更少——多出来的那一段是留给 activation 的「安全余量」。这也是为什么调大 --max-num-batched-tokens 后 KV 往往会被挤小：激活峰值高了，non_kv_cache_memory 变大，KV 预算变少。

8.5前缀缓存 prefix caching：相同开头 → 复用已算 KV

对话应用里，很多请求有相同的开头（system prompt、历史、few-shot 例子都一模一样）。naive 引擎每个请求都要从头 prefill 一遍，纯属浪费。vLLM 的前缀缓存的关键：块满后，把块的「内容」算一个哈希，同一个哈希的物理块只算一次、让多个请求共用一个物理块。

哈希与查找都落在 vllm/v1/core/block_pool.py 的 BlockHashToBlockMap——一个 {block_hash: KVCacheBlock(s)} 的映射。只有满块才进这个缓存；而每个块用自己的引用计数 ref_cnt 记录「有几个请求在用它」。复用逻辑由 BlockPool.get_cached_block 查询、cache_full_blocks 登记、ref_cnt 归零后再 evict_blocks 回收。

vllm/v1/core/kv_cache_utils.py — KVCacheBlock 字段（摘录）
pythonclass KVCacheBlock:
    block_id: int        # 0 ~ num_gpu_blocks-1

为什么“块哈希”是关键：一样的 token 序列一定算出一样的块哈希，所以 BlockHashToBlockMap 一查即中。默认 enable_prefix_caching = True 且哈希算法为 "sha256"（见 CacheConfig，可用 xxhash 提速）。命中率越高，省下的 prefill 越多——而省下的 prefill 本身就是省显存省时间。

8.6小结与自研启示

概念vLLM 实现你的引擎可以先做
总预算gpu_memory_utilization=0.92先写成「总显存 × 比例 − 权重 − 激活」的公式
KV 预算来源profile 实测 non_kv_cache_memory 后取剩余先用估值算 KV，不用一开始就做 profile 回退
KV 块数available_memory // block_stride固定 block 数 + 简单统计即可起步
每步上限max_num_batched_tokens / max_num_seqs先做“每步最多 N token”这一个上限
前缀缓存BlockHashToBlockMap + ref_cnt先跳过；这是吞吐优化，不是正确性要求
自研启示 别一上来就照抄 vLLM 那套 profile。一个能跑的最小版本就够了：
  • 固定块数：启动时算一次 num_blocks = (总显存×util − 权重 − 激活估算) // 每块字节，之后不再变。
  • 简单统计：维护 num_free_blocks，分配/释放就加减，不够就延迟调度（别 OOM）。
  • 预警信号：当你看到“明明还有空闲显存但吞吐上不去”，或“prefill 占了绝大部分时间”，再回来做 profile 回退与前缀缓存。
最小可用公式：
num_blocks = (total_gpu_mem × util − weights_bytes − activation_est) // (bytes_per_token × block_size)
