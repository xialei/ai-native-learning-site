内存规划与 KV 预算：显存从哪来，到哪去

推理服务占一张卡，权重和激活之外，还剩多少能给 KV cache？这些字节换算成多少个物理块？每一步又能塞进多少请求？重复的前缀能不能共享？先看显存总量怎么圈、KV 分到多少，再一路推进到块换算、每步限额与前缀共享；末了拿 SGLang 的做法逐项对照。

8.1一张 80 GiB 的卡，KV cache 能分到多少

先把场景摆出来：一张 80 GiB 的数据中心卡，加载一个 7B 级 FP16 模型，权重吃掉约 14 GiB。之后每来一个请求、每生成一个 token，都要往 KV cache 里写 K 和 V——这些字节不会凭空出现，必须在启动那一刻就圈定一块专属区域。圈多大，是个两难的判断：

  • 圈大了，挤掉 activation 和 CUDA graph 缓冲的空间，跑到一半 OOM——那一步 forward 直接失败，已经接下的请求进退两难；
  • 圈小了，KV 装不下几条序列，GPU 算力闲着，吞吐上不去。

先把两难里一笔带过的 activation 说清。它指一次 forward 里现算出来的中间激活张量——各层的 hidden states、attention 输出、FFN 的中间向量、最后的 logits（这里「激活」说的是张量，不是激活函数）。它和权重、KV 的差别在寿命：权重和 KV 都要长期占着显存——权重是模型本身，KV 是每个请求的上下文；activation 只在计算过程中被使用——进 forward 才出现，这步算完就不再需要。它占多少显存由单步塞进的 token 数决定，所以要量的是峰值。

顺着这个两难往下想，会撞见一串具体的问题，它们环环相扣：

  • 总量怎么圈？显存不是只给这个进程用的——CUDA context、驱动、同卡其他进程都要占。能不能「用到 OOM 为止」？不能，OOM 来的时候没有任何商量余地。得先划一条明确的线。
  • 线内扣掉权重和 activation，剩多少给 KV？权重加载完可以量出来，activation 峰值呢？拍脑袋估一个数：估小了运行时 OOM，估大了 KV 白白少一块。得在最坏情况下实测。
  • 字节怎么变成调度单位？调度器分配的不是字节，是块。56 GiB 这样的字节数要换算一次才知道能装多少块——每块多大？公式长什么样？
  • 每一步塞多少请求？总量够不等于每步都能塞：单步 token 数决定激活峰值，序列数决定同时持有的 KV。这两个上限跟 KV 预算互相牵制。
  • 重复的前缀怎么办？对话场景里大量请求共享同一段开头，naive 引擎各自 prefill 一遍、各存一份，费算力也费显存。能不能共享？

五个问题的答案这样铺开：8.2 合并回答前两问——划线用配置声明总量上限，实测扣除靠启动时跑一遍假前向量出峰值；8.3 把字节数换算成块，那是一条除法；8.4 定每步上限，落在两个调度参数上；8.5 讲前缀共享，靠块哈希加引用计数。8.6 再看 SGLang 对同一串问题给出的另一套答案。

8.2划线与实测：剩余显存怎么量

vLLM 把前两个问题合成一个流程：边界用配置划，剩余用实测分。边界就是 CacheConfig.gpu_memory_utilization（0~1，当前默认 0.92），声明「这个实例最多占整卡显存的多少比例」。先看配置：

vllm/config/cache.py — CacheConfig（摘录；前半为官方英文注释，后半为译注）
pythonclass CacheConfig:
    DEFAULT_BLOCK_SIZE: ClassVar[int] = 16          # 每块 16 个 token

    gpu_memory_utilization: float = Field(default=0.92, gt=0, le=1)
    # The fraction of GPU memory to be used for the model executor ...
    # If unspecified, will use the default value of 0.92.
    # 这是 per-instance 限制：只作用于当前实例。
关键理解：0.92 不是「KV 占 92%」，而是「整个实例最多用 92%」。它回答的是「总量怎么圈」：权重先吃一份，activation 再吃一份，剩下的才轮到 KV。要算出「剩下」具体是多少字节，就得先量出前两项——这是第二个问题。

「权重 14 GiB、激活大概 2 GiB」这种估算能起步，但离生产差得远：不同 batch 形状下激活峰值差好几倍，CUDA graph 缓冲更是只有捕获时才知道。vLLM 的做法是把「量」做成启动流程的一部分：加载权重后，用一个顶满 batch 的假前向（第 5 章讲过的 _dummy_run）把 activation 的峰值顶出来，前后各拍一次显存快照，差值就是实测占用。

整个过程在 vllm/v1/worker/gpu_worker.py 的 determine_available_memory 里。先在启动时记下初始快照，并按配置算出「本实例申请的总预算」：

vllm/v1/worker/gpu_worker.py — 启动快照与总预算（摘录，注释为译注）
python# take current memory snapshot
self.init_snapshot = init_snapshot = MemorySnapshot(device=self.device)
self.requested_memory = request_memory(init_snapshot, self.cache_config)
request_memory（vllm/v1/worker/utils.py）就干一件事：ceil(总显存 × gpu_memory_utilization)——上面 CacheConfig 里那个 0.92 在这里变成具体字节数。如果当前空闲显存连这个数都不到，直接抛错让你调低比例。

然后是关键的量测段：

vllm/v1/worker/gpu_worker.py — profile 假前向（摘录，注释为译注）
python# Execute a forward pass with dummy inputs to profile the memory usage
# of the model.
with memory_profiling(
    self.init_snapshot,
    weights_memory=int(self.model_runner.model_memory_usage),
) as profile_result:
    self.model_runner.profile_run()
这段的重点在「顶满」二字：profile_run 内部就是 _dummy_run(max_num_tokens)——按 max_num_batched_tokens 顶满的假输入跑一次完整前向（V2 实现在 vllm/v1/worker/gpu/model_runner.py）。顶满而不是随便跑，量出来的才是 activation 的峰值；之后运行时无论 batch 怎么变，都不会超过这个数。memory_profiling 上下文负责前后快照相减，把权重（显式传入）和激活峰值分开记账。
假输入还有个容易踩的坑：全是零会骗过 MoE 的路由。dummy 输入默认全零，而 MoE 的路由器是按 token 内容选 expert 的——全零的 token 长得一模一样，会全部涌进同一个 expert。profile 量出的 MoE 部分（激活、kernel 耗时）随之失真，而且这是启动期的失真，混进 KV 预算里就再也不会被纠正。vLLM 后来加了 VLLM_RANDOMIZE_DP_DUMMY_INPUTS（envs.py:186，默认关）来应对（#58411）：打开后 profile_run 会把假 input_ids 随机撒到词表上，让 token 均匀路由。注释把原因写得很直白：「All-zero input_ids route every token to the same experts.」（model_runner.py:1805）。注意它只在 DP>1 时生效（gpu_worker.py 的 randomize_dummy_inputs 属性，:1369）——单卡没有「多个 DP rank 假输入完全相同、expert 负载全部一致偏斜」的问题，也就没必要随机。自研引擎若用假输入做 profile，MoE 模型记得这一手。

量完之后，KV 预算就是三行减法：

vllm/v1/worker/gpu_worker.py — KV 预算计算（摘录，注释为译注）
pythonself.available_kv_cache_memory_bytes = (
    self.requested_memory                # 0.92 × 总显存
    - profile_result.non_kv_cache_memory # 减掉权重 + activation 峰值
    - cudagraph_memory_estimate_applied  # CUDA graph 缓冲也要留
)
三项都有出处：第一项来自启动时的 request_memory；第二项是 profile 实测（权重显式传入 + 激活峰值快照差）；第三项在启用 CUDA graph 时按捕获计划估算（profile_cudagraph_memory，gpu_worker.py），捕获前就得给它留位。这个减法是 vLLM 显存管理的全部秘密：KV 拿到的不是「总显存减权重」，而是「预算减去所有实测占用」——谁的峰值涨了，KV 就让位。

代进一张具体的卡算一遍就清楚了。设定：单张 80 GiB 数据中心卡，跑一个 7B 级 FP16 模型，gpu_memory_utilization 取默认 0.92，块大小 16，KV 每 token 128 KiB（8.3 推这个数）。一步步扣：

步算什么结果依据
1总预算 = 80 GiB × 0.92≈ 73.6 GiBrequest_memory（留给系统与其他进程约 8%）
2扣权重：7B 参数 × 2 字节−14 GiB → 余 59.6profile 实测的 non_kv_cache_memory 的大头
3扣 activation 峰值（_dummy_run 顶出来的最大 batch 假前向）−2 GiB → 余 57.6同上，profile 的另一部分
4扣 CUDA graph 缓冲估计值−1.6 GiB → 余 56.0cudagraph_memory_estimate_applied
5得到 KV 总字节 56 GiB ≈ 6.0 × 10¹⁰ Bavailable_kv_cache_memory_bytesgpu_worker.py 的减法结果

注意第 4 步和第 8 步是纯预留：CUDA graph 缓冲和水印块平时都闲着，但前者保证回放时不会 OOM，后者让新请求和被抢占的请求恢复时「总有一个块可拿」。反过来读这张表也成立：线上问「为什么并发上不去」，答案就藏在哪一行扣掉了多少——权重超预期？activation 峰值没量准？还是 watermark 留多了。

量出来之后还有最后一道保险。第 5 步的 56 GiB 换成块、num_gpu_blocks 写回配置之后，vLLM 会跑一整段 warm-up（compile_or_warm_up_model，gpu_worker.py）：先把要用的 kernel 都真实执行一遍（warmup_kernels，gpu_worker.py 调入），其中专门有一段拿 KV 块数反推 warmup 批大小——如果块不够塞下我准备调的 batch，就把批改小，而不是硬调到 OOM：

vllm/v1/worker/gpu/warmup.py — 用 KV 块数决定 warmup 批大小（摘录，注释为译注）
pythonnum_reqs = min(
    model_runner.scheduler_config.max_num_seqs,
    model_runner.scheduler_config.max_num_batched_tokens
    // max(prompt_len, decode_query_len),
)
if max_blocks_per_req > 0:
    # 预留 null block(0)，并保证块够用
    num_reqs = min(
        num_reqs,
        max(1, (model_runner.kv_cache_config.num_blocks - 1)
            // max_blocks_per_req),
    )
warm-up 不只是热身：它把 num_blocks 和 max_num_seqs / max_num_batched_tokens 绑在了一起：KV 块不够放要调的 batch，就不硬调。KV 预算直接决定了你能扛多大的并发。对自研引擎而言，「profile → 算剩余 → 定 KV 预算」这一整套流程，是引擎从能跑到可靠的分界线。

7B 的账好算，难的是别被它骗了——7B 模型每 token 才 128 KiB 的 KV，因为 GQA 把 KV 头压到了 8 个。换 70B 级模型，两个数一起变大：

参数7B（GQA-8）70B（GQA-8，80 层）
层数3280
每 token KV 字节（8.3 公式，bf16）2×32×8×128×2 ≈ 128 KiB2×80×8×128×2 ≈ 320 KiB
权重（FP16）≈ 14 GiB≈ 140 GiB——单张 80 GiB 卡根本装不下
一条 4K 序列的 KV≈ 512 MiB≈ 1.25 GiB

70B 把三个事实摆到明面上：其一，权重超过单卡显存，TP/PP 不再是「要不要」而是「不并行没得跑」（第 10 章）；其二，就算 8 卡摊开（每卡 17.5 GiB 权重），KV 也是每 token 320 KiB，一条 4K 序列 1.25 GiB，8 卡合计的块池也就多扛几十条长序列；其三，decode 每步要把整条序列的 KV 读一遍，序列越长、并发越多，显存带宽越是先于算力打满——第 4 章讲的「调度器尽量多塞请求」在 70B 上从优化手段变成了生存条件。同样的 gpu_memory_utilization 公式照用，只是减法里每一项都被放大，容错空间被压得更薄：70B 上把 batch 顶满测出的 activation 峰值差 10%，KV 预算就少出好几个 GiB。

8.3换算：字节数变成多少个块

第三个问题：8.2 算出的 56 GiB 还是一笔「字节账」，调度器没法用——它分配的单位是块。换算要先知道每 token 占多少字节。每个 token 要存 K 和 V 两组向量，层数以外还有「每组 KV 头」这个关键参数（num_kv_heads——GQA/MLA 下它比 query heads 小很多，是省显存的关键）：

每 token 字节 ≈ 2（K 和 V 两份）× num_layers × num_kv_heads × head_dim × dtype 字节

例如一个 32 层、kv_heads=8、head_dim=128、bf16（2 字节）的模型：
2 × 32 × 8 × 128 × 2 = 131,072 字节 ≈ 128 KiB / token。
一条 4K 的序列就要 128 KiB × 4096 ≈ 512 MiB；GPU 里想塞 10 条这样的，KV 就得 5 GiB 起步。

vLLM 按「块」来装这些 token。每块 block_size（默认 16）个 token，那么一块的字节就是「每 token 字节 × 16」。块数和可用显存的关系，在 kv_cache_utils.py 里就是一句除法：

vllm/v1/core/kv_cache_utils.py — 可用显存 ÷ 每块字节（摘录，注释为译注）
pythondef get_kv_cache_config_from_groups(vllm_config, kv_cache_groups,
                                           available_memory):
    # 每个块占多少字节（把该组所有层、所有 KV 头的 K+V 都算进去）
    bytes_per_block = _get_kv_cache_bytes_per_block(kv_cache_groups)
    # 块数 = 可用显存 / 一个块的字节
    num_blocks = available_memory // bytes_per_block
    num_blocks = may_override_num_blocks(vllm_config, num_blocks)
    size = bytes_per_block * num_blocks
    return KVCacheConfig(num_blocks=num_blocks, kv_cache_tensors=[...], ...)
这行除法的去向：这个 num_blocks 就是最终写回 cache_config.num_gpu_blocks 的值（写入点在 vllm/v1/engine/core.py），即 8.2 的 available_kv_cache_memory_bytes 换算来的块数。它是 BlockPool 预先分配的总物理块数；may_override_num_blocks 允许你用 num_gpu_blocks_override 手动指定（测试/预取用）。

回到 8.2 表格第 6 步——「÷ 每 token 128 KiB → 再 ÷ 块 16 token」两次除法，和代码里「只除一次」的 bytes_per_block 是同一件事：源码不做两次除，它先把「每 token 128 KiB × 16 token」合算成「每块 2 MiB」，再拿可用显存一次除到位。两种算法结果相同，图 8.2 把这条对应关系画出来：

8.4限额：每一步塞多少请求

第四个问题：块数管的是「总量」，但每一步 forward 还受两个更细的上限管着——这也是显存问题：SchedulerConfig 的两个字段。

vllm/config/scheduler.py — SchedulerConfig（摘录；前半为官方英文注释，后半为译注）
pythonDEFAULT_MAX_NUM_BATCHED_TOKENS: ClassVar[int] = 2048
DEFAULT_MAX_NUM_SEQS: ClassVar[int] = 128

max_num_batched_tokens: int = Field(default=DEFAULT_MAX_NUM_BATCHED_TOKENS, ge=1)
# Maximum number of tokens that can be processed in a single iteration.
max_num_seqs: int = Field(default=DEFAULT_MAX_NUM_SEQS, ge=1)
# Maximum number of sequences to be processed in a single iteration.
  • max_num_batched_tokens（默认 2048）：一步 ≤ 多少个 token。它决定单次 forward 的激活峰值——预分配 max_num_tokens = max_num_batched_tokens 的中间缓冲，是 activation 显存的主要来源。
  • max_num_seqs（默认 128）：一步 ≤ 多少个序列（请求）。防止 decode 步里一堆只出 1 个 token 的序列把 batch 撑爆。

8.5共享：前缀缓存让同样的块装更多对话

最后一个问题：对话应用里有个现成的优化机会——很多请求共享同一段开头（system prompt、历史、few-shot 例子都一模一样）。naive 引擎每个请求都要从头 prefill 一遍这段重复内容，算一遍、存一份。vLLM 的做法：块满后把块的「内容」算一个哈希，同一个哈希的物理块只算一次、让多个请求共用一个物理块——省一份 prefill 计算，也省一份显存。

哈希与查找都落在 vllm/v1/core/block_pool.py 的 BlockHashToBlockMap——一个 {block_hash: KVCacheBlock(s)} 的映射。只有满块才进这个缓存；而每个块用自己的引用计数 ref_cnt 记录「有几个请求在用它」。复用逻辑由 BlockPool.get_cached_block 查询、cache_full_blocks 登记、ref_cnt 归零后再 evict_blocks 回收。

pythonclass KVCacheBlock:

为什么「块哈希」是关键：一样的 token 序列一定算出一样的块哈希，所以 BlockHashToBlockMap 一查即中。默认 enable_prefix_caching = True 且哈希算法为 "sha256"（见 CacheConfig，可用 xxhash 提速）。命中率越高，省下的 prefill 越多——而省下的 prefill 本身就是省显存省时间。

「一样的 token 序列算出一样的哈希」这句话里藏着一个实现选择。第 1 个块没有前驱，它的哈希从哪来？如果只哈希「本块 token」，那么不同请求的两个开头相同的块倒是能命中，但也仅仅如此——第 2 个块无法确认「我前面那块」是不是同一个。vLLM 的做法是把父块哈希链进去：每块的哈希 = hash(父块哈希, 本块 token_ids, extra_keys)，一环扣一环：

vllm/v1/core/kv_cache_utils.py — hash_block_tokens（摘录，注释为译注）
pythondef hash_block_tokens(hash_function, parent_block_hash,
                      curr_block_token_ids, extra_keys=None):
    # 第一个块没有父哈希，用 NONE_HASH 兜底
    if not parent_block_hash:
        parent_block_hash = NONE_HASH
    curr_block_token_ids_tuple = tuple(curr_block_token_ids)
    return BlockHash(
        hash_function((parent_block_hash, curr_block_token_ids_tuple, extra_keys))
    )
这条链给了三样东西：① 前缀匹配自动逐块成立——第 n 块哈希相同 ⇔ 前n块全部相同，查找时不用回溯验证；② 哈希仍是 O(1) 查表，代价只是链式计算；③ 出现了「种子块」问题——NONE_HASH（kv_cache_utils.py:118）就是链的第一环，它从哪来决定了「独立进程能不能共享同一个前缀缓存」。答案是分情况的（resolve_none_hash_seed，kv_cache_utils.py:131）：SHA-256 这类密码学哈希用固定种子 "vllm-none-hash"（DEFAULT_NONE_HASH_SEED，:122），于是独立启动的两个 vLLM 进程对同一段 prompt 算出完全相同的哈希，跨节点复用 KV 不用额外约定（P2P 缓存层在握手时核对的就是这个种子，get_none_hash_seed）；而 xxhash 不是抗碰撞的，种子可预测会让攻击者离线预造碰撞块（#12621），所以用 os.urandom(32) 每进程随机——代价是两个进程的哈希互不相认。设 PYTHONHASHSEED 则两种算法都听你的。多租户隔离不是靠种子，是靠下一节讲的 cache_salt。

块哈希的输入不止 token 序列。generate_block_hash_extra_keys（kv_cache_utils.py:614）会往哈希里追加一组 extra_keys，四路来源、每路都带着自己的标签：

vllm/v1/core/kv_cache_utils.py — extra_keys 的四路来源（摘录，注释为译注）
pythonextra_keys = (
    lora_extra_keys          # [("lora", lora_name, lora_path)] —— LoRA 名 + 适配器路径
    + mm_extra_keys          # [("mm", mm_id, offset - start_token_idx)] —— 块内偏移
    + cache_salt_keys        # [("cache_salt", salt)] —— 只进第一个块
    + prompt_embeds_keys     # [("prompt_embeds", embeds_hash)] —— 逐块 sha256
)
为什么要打标：这四种内容都会改变「同样 token 算出不同 KV」——挂了不同 LoRA 的同一串 prompt、同一个多模态图在不同位置、不同 cache_salt 隔离的租户，token 序列相同但算出的块不能混用，所以必须进哈希。但它们各自的结构不同：mm 要记「图在块内的偏移」，lora 要「名字和路径都算」——vLLM 曾因为只用名字、没把 lora_path 算进去，导致同名换适配器时复用了旧 KV（#59335 补上 path，docstring 写明「re-pointing a LoRA name at a different adapter does not reuse KV computed with the previous one」，kv_cache_utils.py:570）。早期这些键是裸值混在一起，按位置猜类型；#51899 把每路打上 ("mm",…)/("lora",…) 这样的来源标签，结构一眼可辨。但 KV 事件（external consumer 监听块增删）不能跟着变——下游还在解析旧格式——于是 to_event_extra_keys（:655）在发布前把标签剥掉，块哈希用带标格式、对外事件保持旧格式，两边各取所需。

淘汰：ref_cnt 归零之后，谁先让位

引用计数只回答「这块能不能收」，没回答「收回来之后谁先被复用」。答案在 FreeKVCacheBlockQueue（kv_cache_utils.py:246）——一个手写的双向链表，不用 deque 的理由写在 docstring 里：要从队列中间 O(1) 摘块（命中的块还在队里等着被复用，得随时摘出）。队头是 LRU 端，分配就从头弹：

vllm/v1/core/block_pool.py — get_new_blocks：分配即淘汰（摘录，注释为译注）
pythondef get_new_blocks(self, num_blocks):
    ret = self.free_block_queue.popleft_n(num_blocks)
    if self.enable_caching:
        for block in ret:
            # 弹出的块若还挂着哈希，就地从哈希表里摘除——这就是淘汰
            self._maybe_evict_cached_block(block)
            block.ref_cnt += 1
vllm/v1/core/block_pool.py — free_blocks：两个桶决定再入队的位置（摘录，注释为译注）
pythondef free_blocks(self, ordered_blocks):
    # 无哈希块：插到队头（LIFO，刚释放的块大概率马上被复用，GPU 局部性好）
    # 有哈希块：接到队尾（FIFO，等价于 LRU——最久未命中的先被复用）
    self.free_block_queue.prepend_n(blocks_to_evict_first)
    self.free_block_queue.append_n(blocks_to_evict_last)
一个队列、两种入队姿势，就是全部淘汰策略：分配 get_new_blocks（block_pool.py:669）从队头拿块，如果拿到的块还挂着哈希，_maybe_evict_cached_block（:732）就地把它从 BlockHashToBlockMap 摘掉——分配动作本身就是淘汰动作，没有独立的「清理线程」。释放时按有无哈希分两桶（free_blocks，:777）：无哈希块永远碰不到缓存查找，插队头让它尽快被复用（省 GPU cache miss）；有哈希块接队尾，等它排到队头那天，正好是它「最久没人命中」之时——LRU 就这么免费拿到了。命中时的 touch（:755）把 ref_cnt=0 的命中块从队列里摘出来（调用点在 single_type_kv_cache_manager.py:307，注释原文「make sure they won't be evicted」），重新挂 ref_cnt——命中的块退出淘汰候选。至于显式淘汰，evict_blocks（:810）只摘哈希不腾物理块（ref_cnt>0 的块继续服务当前请求），reset_prefix_cache（:830）整表清空且只在所有块都已归还时成功（docstring 点明两个用途：RLHF 换权重后作废旧缓存、基准测试前清状态；否则记 warning 返回 False，scheduler.py:2811 处拿这个返回值决定是否报错）。

命中率什么时候掉：四个场景

前缀缓存的红利全押在「同一段开头反复出现」上。以下场景会把红利吃掉，运维时要能对着指标认出它们：

场景机制表现与对策
缓存压力过大块池被大量短对话塞满，早期长 system prompt 的块被 LRU 冲走，新请求即使前缀相同也查不到命中率随负载波动、上量就掉。对策：加显存、缩短 system prompt，或用多实例分流量
多租户混跑不设 cache_salt 时所有租户共抢同一个 LRU 池，互相冲刷；设了则物理隔离，各自命中各自的命中率的「量」变了，「配比」也变了。看 per-tenant 指标，别看全局平均
LoRA 轮换哈希链里串着 LoRA 名+路径（extra_keys），换适配器 = 整段前缀换一套哈希，旧 KV 还在池里但永远查不中，白占空间直到被淘汰命中率掉的同时 num_cached_blocks 不降。适配器频繁轮换的场景要预留更多块
显式重置reset_prefix_cache 清空整张哈希表（RLHF 换权重、压测清场）；xxhash 种子每进程随机，多进程间天然不共享命中率瞬间归零再爬坡。压测脚本里留意是否误触了 reset 接口

8.6SGLang 的另一套答案与自研启示

回到 8.1 摆出的五个问题，vLLM 的答案是「配置划线 → profile 实测 → 除法换算 → 双上限 → 块哈希」。回到最初那条减法和那条除法：profile 量出权重与激活的峰值，预算减去实测占用得到 KV 的字节数；字节除以每块字节得到物理块数。批上限决定激活峰值，块数反过来封顶批大小——三个变量互相咬合，牵一发而动全身。前缀缓存则不动这条链路，只是让同一个块服务更多请求。

概念vLLM 实现你的引擎可以先做
总预算gpu_memory_utilization=0.92先写成「总显存 × 比例 − 权重 − 激活」的公式
KV 预算来源profile 实测 non_kv_cache_memory 后取剩余先用估值算 KV，不用一开始就做 profile 回退
KV 块数available_memory // bytes_per_block固定 block 数 + 简单统计即可起步
每步上限max_num_batched_tokens / max_num_seqs先做「每步最多 N token」这一个上限
前缀缓存BlockHashToBlockMap + ref_cnt先跳过；这是吞吐优化，不是正确性要求
自研启示 别一上来就照抄 vLLM 那套 profile。一个能跑的最小版本就够了：
  • 固定块数：启动时算一次 num_blocks = (总显存×util − 权重 − 激活估算) // 每块字节，之后不再变。
  • 简单统计：维护 num_free_blocks，分配/释放就加减，不够就延迟调度（别 OOM）。
  • 预警信号：当你看到「明明还有空闲显存但吞吐上不去」，或「prefill 占了绝大部分时间」，再回来做 profile 回退与前缀缓存。
最小可用公式：
num_blocks = (total_gpu_mem × util − weights_bytes − activation_est) // (bytes_per_token × block_size)
