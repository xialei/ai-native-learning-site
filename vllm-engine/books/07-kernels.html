Kernels：引擎「为什么快」的最后一步

模型跑多快，最终由 kernel 决定。注意力 kernel 有 FlashAttention、FlashInfer、TRT-LLM 等好几家，vLLM 让它们实现同一个接口，模型代码只调接口、不直接碰任何一家的库——这就是「架构无关」。RMSNorm（均方根归一化）、RoPE（旋转位置编码）这类小算子不走这条通道，而是由 _custom_ops.py 把 C++/CUDA 实现包成普通 Python 函数。这一章讲这两条通道怎么分工，以及为什么自研引擎不必从零写 kernel。
图 7.1：全章地图——两条通往 C++/CUDA 的通道。模型代码永远站在最上层，不直接碰 kernel；7.2–7.3 讲通道 A，7.4 讲通道 B，7.5 走读真实 forward 代码。

7.1为什么 kernel 决定性能：HBM、SRAM 与计算强度

先把两块存储分清。GPU 线程想算数，数据得先到它手边，而手边有两级：

  • HBM（High Bandwidth Memory，高带宽显存）：焊在 GPU 旁边的大容量显存，几 GB 到一百多 GB，模型权重和 KV cache 都住这里。带宽高（H100 约 3.35 TB/s），但相对计算单元仍然很慢——一次访存的时间里，计算单元能做几百上千次浮点运算。
  • SRAM（静态随机存取存储器）：直接长在计算单元旁边的片上存储，每个 SM 自带一小块，全 GPU 加起来只有几十 MB（A100 是 108 个 SM × 192 KB，合计约 20 MB）。读写几乎零等待，但容量极小，装不下任何一整个矩阵。

差距可以量化：HBM 的容量是 SRAM 的几千倍，代价是访问延迟高一个数量级以上。所以 kernel 设计要回答的核心问题就是——数据放哪、搬多少次。每次从 HBM 搬数据到 SRAM 都要占用带宽，能少搬一次就少搬一次。

图 7.2：HBM 与 SRAM 的位置关系——计算单元紧挨 SRAM，SRAM 再从 HBM 取数。kernel 优化的核心问题就是减少这两级之间的搬运量。

理解了存储层级，就能看懂「算子类型」怎么决定瓶颈。一个简单判断标准是计算强度（arithmetic intensity） = 每秒浮点运算 / 每秒访存字节。它决定了瓶颈在哪：

  • prefill（算力密集，compute-bound）：序列很长，一次要算整段 K/V 与 Q 的注意力。矩阵乘法充足，把 SM 的 FMA 运算填满就能提升——瓶颈是每个 SM 每秒能做多少次乘加。
  • decode（访存密集，memory-bound）：每个请求一次只为一个 token 算注意力，但要把整条历史 K/V 从 HBM 读一遍。FLOPs 很小、读显存很大——瓶颈是 HBM 带宽（GB/s），而不是算力。

这两类在之前 PagedAttention 一章已经反复出现：prefill 一次算一大段，decode 一个 token 一个 token 挤出来。所以 vLLM 会对同一份注意力逻辑提供不同的 kernel 路径（prefill 用 batch-gemm 类实现、decode 用专为「每行单独小任务」优化的实现）。

具体到 kernel 层，两个关键优化方向：

  • FlashAttention 的 IO 优化：Naive 注意力要把完整的 S×S 分数矩阵 + softmax 中间结果写回 HBM 再读回——SRAM 装不下整个矩阵，中间结果只能先落回显存，下一步再搬回来。FlashAttention 把 Q/K/V 分块（tiling），让每块在 SRAM 里算完分数、做在线 softmax、累加输出，避免把完整的 S×S 分数矩阵和 softmax 中间量物化到 HBM——Q/K/V 本身仍要从 HBM 分块读入，省掉的是中间结果的写回再读回。它把显存往返次数从 O(N) 降到 O(N²/M)，代价是部分分块要在 SRAM 里重算——SRAM 快，多算一点换少搬大量数据是划算的。
  • 矩阵乘（GEMM）直接用现成库：QK^T、PV 这类矩阵乘在注意力 kernel 内部算，不单独走库；模型其余的大头矩阵乘（QKV 投影、输出投影）里，非量化的走 F.linear → cuBLAS，量化（FP8/INT8）的走 CUTLASS 写的 cutlass_scaled_mm（7.4 节）。自己写一个平庸的矩阵乘核没有意义。
收拢成一句：HBM 大而慢、SRAM 小而快，prefill 的瓶颈是算力，decode 的瓶颈是 HBM 带宽。kernel 层做的事，就是安排好数据在这两级之间的搬运，针对这两种瓶颈分别优化。

7.2注意力后端抽象：接口与多实现

先说清问题是什么。注意力 kernel 有好几个来源：FlashAttention、FlashInfer、TRT-LLM、Triton……它们 API 各不相同，擅长的硬件不同（Hopper 上 FlashAttention 快，Blackwell 上 FlashInfer / TRT-LLM 快），支持的特性也不同（MLA、FP8 KV cache、sliding window……）。如果模型代码直接写 flash_attn_varlen_func(...)，那么换一块 GPU、跑一个 MLA 模型（DeepSeek），就得改模型代码。

vLLM 的解法：定义一组架构无关的接口，让所有 kernel 实现都去实现它。「架构无关」指的是模型架构无关——Llama 这类 MHA 模型和 DeepSeek 这类 MLA 模型走同一套调用方式，模型代码里永远不出现某家 kernel 的名字。换硬件、换 kernel 是选择器的事（7.3 节），不是模型代码的事。

核心是两个抽象基类，都在 vllm/v1/attention/backend.py：

vllm/v1/attention/backend.py — AttentionBackend（接口）与 AttentionImpl.forward（契约；注释为译注）
pythonclass AttentionBackend(ABC):
    # 声明这个后端支持哪些 dtype / kv_cache_dtype / block_size
    # 前后端选择器（selector）靠这些 supports_* 判断是否可用
    @staticmethod
    def get_name() -> str: ...

    @staticmethod
    def get_impl_cls() -> type[AttentionImplBase]: ...

    @staticmethod
    def get_builder_cls(): # -> AttentionMetadataBuilder
        ...

class AttentionImpl(AttentionImplBase[T]):
    def forward(self, layer, query, key, value,
        kv_cache, attn_metadata, ...) -> torch.Tensor: ...

每个后端要回答三件事：

  • get_impl_cls() —— 返回真正算注意力的实现类（如 FlashAttentionImpl）；
  • get_name() —— 后端名字，如 "FLASH_ATTN" / "FLASHINFER"；
  • get_builder_cls() —— 返回一个「元数据构建器」，把调度器给出的 block table、seq_lens 等整理成后端 kernel 需要的形式（见下边 metadata）。

forward 的签名非常统一：输入 query/key/value、kv_cache、attn_metadata，输出 attention 结果。模型层每层注意力都按这个签名调用，到底执行哪个实现由上层选择器决定。同一份模型代码因此能跑在 FlashAttention、FlashInfer、TRT-LLM 任何一家上；MLA 模型也一样——接口下有 MLAAttentionImpl 子类，对模型层透明。vLLM 几乎全平台的支持，靠的就是这个结构。

后端的全量清单在 vllm/v1/attention/backends/registry.py 里：一个 AttentionBackendEnum 枚举，每一项的值是类的完整限定名。例如：

vllm/v1/attention/backends/registry.py — 后端枚举（摘录，注释为译注）
pythonclass AttentionBackendEnum(Enum, ...):
    FLASH_ATTN  = "vllm.v1.attention.backends.flash_attn.FlashAttentionBackend"
    FLASHINFER  = "vllm.v1.attention.backends.flashinfer.FlashInferBackend"
    TRITON_ATTN = "vllm.v1.attention.backends.triton_attn.TritonAttentionBackend"
    CUTLASS_MLA = "vllm.v1.attention.backends.mla.cutlass_mla.CutlassMLABackend"
    ...
    def get_class(self) -> type[AttentionBackend]:
        return resolve_obj_by_qualname(self.get_path())
图 7.3：接口在中间，多个实现各连各的 kernel，metadata（block table 等）从侧边流入提供给所有后端。

枚举展开有 40 多项，第一眼容易以为里面藏着 40 种注意力算法。不是。绝大多数条目算的是同一个注意力数学，差别集中在四个维度：

  • kernel 是谁家的：flash-attn、FlashInfer、TRT-LLM、vLLM 自带的 Triton、CUTLASS 各有一份 kernel，性能和特性各有所长；
  • 硬件门槛：每个后端用 supports_compute_capability 声明能跑哪代 GPU——FlashAttention 要求 SM80+，FlashInfer 是 SM80–SM121（SM75 有 bug，临时抬到 SM80），Triton 实现对任何算力都返回 True，兼容面最宽；CUTLASS_MLA 只认 SM100；
  • KV cache 格式：supported_kv_cache_dtypes 清单不同——fp8_e5m2 只有 Triton 系支持，fp8_ds_mla / nvfp4_ds_mla 只有稀疏 MLA 系支持，turboquant_* 是 TurboQuant 专有格式；
  • 服务谁：MLA 家族只接 MLA 模型，稀疏 MLA 只接带 indexer 的模型，DiffKV 只接 QK 与 V 头维度不一致的模型。

这些家族怎么和选择器（7.3 节）接上？标准注意力和 MLA 两个家族进平台优先级列表：SM90 非 MLA 默认 FLASH_ATTN → FLASHINFER → TRITON_ATTN → FLEX_ATTENTION → TURBOQUANT，SM100 因果注意力把 FLASHINFER 提到最前；MLA 在 SM100 上是 FLASHINFER_MLA → TOKENSPEED_MLA → CUTLASS_MLA → …。DiffKV、DSV4/DSV41、MiniMax 这些模型专属后端不进任何平台列表——模型代码直接点名。平台列表的完整顺序在 vllm/platforms/cuda.py 的 _get_backend_priorities。

另外线性注意力（Mamba / GatedDeltaNet / 短卷积）不在这个枚举里——MambaAttentionBackendEnum（MAMBA1 / MAMBA2 / SHORT_CONV）是并列的第二个枚举，注册与覆盖机制和主枚举相同。

7.3后端选择：selector 怎么挑

模型初始化时调 get_attn_backend，它把「模型配置 + 设备信息」打包成一个 AttentionSelectorConfig，再层层下发给平台层去挑后端。关键逻辑在 vllm/v1/attention/selector.py：

vllm/v1/attention/selector.py — 根据配置与平台选择后端类（注释为译注）
pythondef get_attn_backend(...) -> type[AttentionBackend]:
    config = AttentionSelectorConfig(head_size=..., dtype=...,
        kv_cache_dtype=..., block_size=..., use_mla=...,
        has_sliding_window=..., use_non_causal=..., ...)
    backend = attention_config.backend          # 用户可用 --attention-backend 指定
    return _cached_get_attn_backend(backend, config, ...)

def _cached_get_attn_backend(backend, config, num_heads):
    attention_cls = current_platform.get_attn_backend_cls(   # 平台决定
        backend, attn_selector_config=config, num_heads=num_heads)
    backend_cls = resolve_obj_by_qualname(attention_cls)      # 类名字符串 -> 类
    ...

最终决策落在平台的 get_attn_backend_cls（如 vllm/platforms/cuda.py），逻辑是：

  • 如果用户显式指定了 --attention-backend，就校验它是否满足当前配置（validate_configuration 跑一遍所有 supports_* 检查），满足就用，不满足直接报错；
  • 否则按一个优先级列表逐个试：get_valid_backends 返回「可用后端 + 优先级」，取优先级最高的（min(valid_backends_priorities, key=lambda c: c.priority)）。
  • 不同硬件/场景给不同列表，例如 SM100f 的非因果注意力优先 FlashAttention，普通 CUDA 平台一般默认 FLASH_ATTN → FLASHINFER → TRITON_ATTN → FLEX_ATTENTION。

所以「是否 enable_flashinfer」这类开关并不是硬编码一个 if，而是：每个后端声明自己的 supports_* 能力（dtype、head_size、block_size、是否是 MLA、是否支持 sliding window、GPU 算力…），选择器用这些能力把所有候选过滤一遍，再在剩下的里挑优先级最高的。这样新增一个后端只需要注册到枚举并实现能力检查，选择器零改动。

这套过滤最好用一个具体的（也是故意刁难的）请求走一遍。假设模型要求：MLA + FP8 KV cache + sliding window。候选一开始是全家族的 MLA 后端，逐个过 validate_configuration：

候选后端逐项检查结果
FLASH_ATTN_MLAis_mla ✓；算力 SM90 ✓；KV dtype 清单只有 auto/fp16/bf16✗ FP8 KV 不支持
FLASHMLAis_mla ✓；算力 SM90/SM100 ✓；dtype 含 fp8_e4m3 ✓；块 64 ✓——但 supports_sliding_window() 返回 False✗ 滑窗不支持
FLASHINFER_MLA / CUTLASS_MLAis_mla ✓；dtype fp8_e4m3 ✓——但算力只认 SM100，本机是 SM90✗ 算力不符
TRITON_MLAis_mla ✓；算力不限 ✓；dtype 含 fp8_e4m3 ✓；块 16 的倍数 ✓——supports_sliding_window() 同样返回 False✗ 滑窗不支持

四个候选全军覆没——而且这不是巧合：检查完整个 MLA 家族，没有任何一个后端声明支持 sliding window（基础接口的默认实现就是返回 False，MLA 系没有谁去覆盖它）。如果此时用户还显式指定了 --attention-backend FLASHMLA，得到的是一条 ValueError；没指定的话，候选集为空，平台层抛出「No valid attention backend found」。报错信息里能看到每个后端被淘汰的具体原因（invalid_reasons）——这份「体检报告」正是逐项过滤留下的痕迹。

这个例子的普适性：把需求换成「SM90 + fp16 + 无滑窗」，表里 FLASH_ATTN_MLA 一路绿灯直接当选——同一套检查既负责「为什么选了它」也负责「为什么没选它」。能力声明 + 过滤 + 优先级排序三段式，是 vLLM 里所有「多实现挑一个」问题的通用答案（采样器、量化方案同理）。

7.4自定义算子入口：_custom_ops.py

先划清界限：C++/CUDA 性能这条线有两条通道。注意力本身是 hot loop，不走 Python 封装——后端实现里直接调库（如 flash_attn_varlen_func）。走 _custom_ops.py 的是另一批小算子：RMSNorm（均方根归一化）、RoPE（旋转位置编码）、KV cache 写入、量化 GEMM，模型层代码会直接调用它们。本节讲第二条通道。

vllm/_custom_ops.py 是 C++/CUDA 算子的 Python 封装：把 torch.ops._C.* / _vllm 这些算子包成好读、带类型注解的 Python 函数，同时用 @register_fake 给自定义算子在 torch 里登记 shape 规则（供 torch.compile / fake tensor 用）。

vllm/_custom_ops.py — 几个真实自定义算子入口（注释为译注）
pythondef rms_norm(out, input, weight, epsilon) -> None:
    torch.ops._C.rms_norm(out, input, weight, epsilon)

def rotary_embedding(positions, query, key, head_size, cos_sin_cache, ...):
    torch.ops._C.rotary_embedding(...)

def paged_attention_rocm(out, exp_sum, max_logits, tmp_out, query,
    key_cache, value_cache, ..., block_tables, seq_lens, ...) -> None:
    torch.ops._rocm_C.paged_attention(...)

def merge_attn_states(output, prefix_output, prefix_lse,
    suffix_output, suffix_lse, output_lse=None, ...) -> None:
    torch.ops._C.merge_attn_states(...)   # prefill 分块后合并各块状态（前缀/后缀的 output 与 lse）

看 rms_norm 就够了：Python 里唯一干的事就是把四个参数原样传给 torch.ops._C.rms_norm。真正的实现是 C++ 侧编译进 _C 库的 kernel（源在 csrc/），Python 只是入口/适配层。优点：模型代码不用碰 C++，写出来像普通 PyTorch 函数；ops.rms_norm(out, input, weight, 1e-6) 一行就完成一次融合的 RMSNorm。

上一节提的量化 GEMM就是这条通道里的重头。cutlass_scaled_mm（FP8/INT8 量化线性层用的矩阵乘）封装的 torch.ops._C.cutlass_scaled_mm，C++ 实现在 csrc/libtorch_stable/quantization/w8a8/cutlass/，基于 NVIDIA 开源的 CUTLASS 模板库写成。CUTLASS 和 cuBLAS 的分工值得分清：cuBLAS 是闭源成品库，PyTorch 的 F.linear（非量化矩阵乘）在 CUDA 上就是调它；CUTLASS 给的是 C++ 模板积木而不是成品，vLLM 用它写 cuBLAS 没有的变体——带 scale 的 FP8 GEMM、DeepSeek V3 那种 blockwise 量化、以及 SM100 上的 MLA decode kernel（csrc/libtorch_stable/attention/mla/sm100_cutlass_mla_kernel.cu，即 7.2 节后端清单里的 CUTLASS_MLA）。为什么要自己写？因为量化矩阵乘要把「反量化」融合进 GEMM 内部——scale 乘在累加的哪个阶段、按什么粒度（per-tensor / per-token / 128×128 块），cuBLAS 没有现成入口，CUTLASS 模板可以。

除了 C++ 算子，vLLM 还用 Triton 写了一批「Python 写、照样能跑在 GPU」的算子，集中在 vllm/v1/attention/ops/（如 triton_attention_helpers.py、triton_prefill_attention.py、triton_decode_attention.py），配合 vllm/triton_utils/ 做一些缓存与自动调参。Triton 的好处是无需手写 CUDA 也能做 kernel 级优化，常用来实现那些没有现成库覆盖的注意力变体。

7.5用代码看：一个后端到底怎么 forward

以默认的 FlashAttentionImpl.forward 为例（vllm/v1/attention/backends/flash_attn.py）。先看它拿什么、给什么：

vllm/v1/attention/backends/flash_attn.py — FlashAttentionImpl.forward（签名）
pythondef forward(self, layer, query, key, value, kv_cache, attn_metadata,
    output, output_scale=None, output_block_scale=None) -> torch.Tensor:
    # query:  [num_tokens, num_heads,     head_size]        # 本次所有 token 的 Q
    # key:    [num_tokens, num_kv_heads,  head_size]        # 新算的 K
    # value:  [num_tokens, num_kv_heads,  head_size]
    # kv_cache: [num_blocks, num_kv_heads, block_size, 2*head_size]  # 分页缓存
    # attn_metadata: FlashAttentionMetadata —— 装着 block table、seq_lens 等
    # returns: [num_tokens, num_heads * head_size]         # 注意力输出

    if attn_metadata is None:
        return output.fill_(0)          # profiling 时直接填 0 跳过
    ...
    # 内部按 attn_type 分流：decode 走一次一 token 路径，
    # prefill 走 varlen 向量化路径，最终都落到 flash_attn_varlen_func 等
读懂这段：这是「分页」与「后端」接缝处——它拿到的是物理上分页的 kv_cache 和 block table（metadata），而底层 FlashAttention kernel 恰好知道怎么按 block table 去读不连续的 KV。这也正是第 3 章「PagedAttention 就是懂 block table 的 FlashAttention」在代码里的落点。

摘录只展示了骨架，真实的 forward 是一条按顺序检查的决策链。图 7.4 拿两个具体 batch 各走一遍——左边是没有任何共享前缀的常规 batch（绝大多数情况），右边是 8 个请求共用同一个 2048-token system prompt 的 batch（cascade 的用武之地）。图后按「结论 → 为什么 → 锚点」拆三个要点：

两个例子共用的开头 例 A 的落点：一次 launch 例 B 专属：cascade 三步
图 7.4：同一个 forward，两种走法。判断本身只有一处——前缀够不够长、请求够不够多；满足就走「共享前缀算一次 + 各自后缀各算一次 + 合并」，不满足就一次算完。两边的目的地都是同一个 kernel（flash_attn_varlen_func），区别只是调几次、对哪段 KV 算。

图上三个值得停一停的点。每点先给结论，再说为什么，最后标锚点：

  • 结论：KV 写入不归 forward 管——attention 层先写缓存、再算注意力。为什么：写缓存与 forward 是两个自定义 op，中间靠一个空张量 kv_cache_dummy_dep 建立数据依赖，保证 torch.compile 不重排先后。「先写缓存再 forward」不是唯一顺序：接口基类的 forward_includes_kv_cache_update 默认 True（写入归 forward 管），FlashAttention、FlashInfer 等绝大多数后端都覆写成 False，于是走上面这条先写后算的路；真正在 forward 内部写缓存的是少数，如 HPC_ATTN。锚点：vllm/model_executor/layers/attention/attention.py（写缓存即 do_kv_cache_update，内部是 reshape_and_cache_flash 算子）。
  • 结论：cascade 拆成两半算，结果精确等价，不是近似。为什么：softmax 注意力对「先看哪些 KV」可以分块——kernel ① 和 ② 各自除了输出还带出一个 LSE（log-sum-exp，配分函数的对数），merge_attn_states 拿这两组 (输出, LSE) 按 LSE 加权合成，数学上精确等价于对完整 KV 一次算完。收益在带宽：例 B 里 2048-token 前缀的 KV 如果走例 A 的路，8 个请求每人读一遍就是 8 次重复读取；cascade 只读 1 次。门槛也就由此而来——前缀 ≥256 token、请求 ≥8 个、无 sliding window / alibi，三者缺一就不值得拆。锚点：后两者不支持直接 assert 在 flash_attn.py:1996。
  • 结论：CPU 开销被当成一等公民。为什么：源码里 woosuk 的注释专门警告这段代码跑在 eager 模式（分段 CUDA graph 的间隙），view、[:n] 这类操作慢得出人意料，所以整个 forward 的原则是——Python 里只做切片和标量计算，注意力本体一概交给 kernel。

再看看一个 MLA 后端如何把 KV 写进缓存——这里直接调用 _custom_ops 里的算子（vllm/v1/attention/backend.py 的 do_kv_cache_update）：

vllm/v1/attention/backend.py — MLAAttentionImpl.do_kv_cache_update（摘录）
pythondef do_kv_cache_update(self, kv_c_normed, k_pe, kv_cache,
    slot_mapping, kv_cache_dtype, k_scale) -> None:
    if kv_cache.numel() == 0:
        return
    from vllm import _custom_ops as ops
    ops.concat_and_cache_mla(                     # 把 MLA 的 K/V 写进分页缓存
        kv_c_normed, k_pe.squeeze(1), kv_cache,
        slot_mapping.flatten(), kv_cache_dtype=kv_cache_dtype, scale=k_scale)
看懂这条链路：模型层算出的新 K/V → 后端实现（这里是 MLA）把新算的 KV 写进每请求的 slot（slot 是 block table 展开后的一个具体位置）→ 真正干活的是 ops.concat_and_cache_mla 这个自定义算子。于是「内存管理（第 3/8 章）+ 后端抽象（本章）+ 算子入口」三者在这里汇合。

7.6小结与自研启示

环节vLLM 的做法你的引擎可以
注意力 kernelbackend 抽象 + FlashAttention / FlashInfer 等多实现先用 torch.nn.functional.scaled_dot_product_attention 或现成 flash-attn 库，别自己写
后端选择各后端 supports_* + 平台优先级列表第一版直接写死 sdpa，跑通了再加选择
小算子_custom_ops.py 包 torch.ops._C.*RMSNorm 等先用 torch 组合代替，后续再考虑 kernel
GEMMCUTLASS / cuBLAS调 torch 的 matmul 就已走 cuBLAS，够用
Triton 变体vllm/v1/attention/ops/需要特殊注意力时再学 Triton，属于进阶
自研启示 kernel 是「懂了再优化」的事，不是「起步就自己写」。你的第一个版本用 torch.nn.functional.scaled_dot_product_attention（SDPA，内部会自动选 FlashAttention/Memory-Efficient）和 flash-attn 现成库就能获得几乎 SOTA 的注意力性能。vLLM 最值得借鉴的是它的抽象分层——后端接口 + 注册表 + 按能力选择——让你换 kernel 如换插件，而不是跟 kernel 死磕。
