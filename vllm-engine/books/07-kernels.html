Kernels：引擎「为什么快」的最后一公里

模型跑多快，最终由 kernel 决定。vLLM 用「架构无关的注意力后端接口」把 FlashAttention、FlashInfer、TRTLLM 等各家 kernel 统一起来，再用自定义算子把 C++/CUDA 性能调到位。这一章讲清楚它的分层设计，以及你自研时不必从零写 kernel。

7.1为什么 kernel 决定性能：计算强度分类

GPU 上「快不快」取决于算子属于哪种类型。一个简单判断标准是计算强度（arithmetic intensity） = 每秒浮点运算 / 每秒访存字节。它决定了瓶颈在哪：

  • prefill（算力密集，compute-bound）：序列很长，一次要算整段 K/V 与 Q 的注意力。矩阵乘法充足，把 SM 的 FMA 运算喂满就能提升——瓶颈是每个 SM 每秒能做多少次乘加。
  • decode（访存密集，memory-bound）：每个请求一次只为一个 token 算注意力，但要把整条历史 K/V 读一遍。FLOPs 很小、读显存很大——瓶颈是显存带宽（GB/s），而不是算力。

这两类在之前 PagedAttention 一章已经反复出现：prefill 一次算一大段，decode 一个 token 一个 token 挤出来。所以 vLLM 会对同一份注意力逻辑提供不同的 kernel 路径（prefill 用 batch-gemm 类实现、decode 用专为「每行单独小任务」优化的实现）。

具体到 kernel 层，两个关键优化方向：

  • FlashAttention 的 IO 优化：Naive 注意力要把完整的 S×S 分数矩阵 + softmax 中间结果写回显存（HBM）再读回。FlashAttention 把整个 Q/K/V 分块（tiling），把当前分块读进片上 SRAM，在 SRAM 里算分数、做在线 softmax、累加输出，绝不让整个 K/V 或中间分数矩阵落回 HBM。它把显存往返次数从 O(N) 降到 O(N²/M)，本质是「以多算一点为代价，少搬大量数据」。
  • GEMM 用 CUTLASS / cuBLAS：注意力里的矩阵乘（QK^T、PV）本质是 GEMM，直接调 NVIDIA 已有高度调优的库，而不是自己写一个平庸的矩阵乘核。
一句话：prefill 拼算力、decode 拼带宽——kernel 层就是针对这两种瓶颈分别做极致优化的地方。

7.2注意力后端抽象：接口与多实现

vLLM 并不自己闷头写死一套注意力 kernel，而是定义了一组架构无关的接口，然后让 FlashAttention、FlashInfer、TRT-LLM、Triton 等实现都去实现它。模型层代码只依赖接口，不需要知道底层是哪个 kernel。

核心是两个抽象基类，都在 vllm/v1/attention/backend.py：

vllm/v1/attention/backend.py — AttentionBackend（接口）与 AttentionImpl.forward（契约）
pythonclass AttentionBackend(ABC):
    # 声明这个后端支持哪些 dtype / kv_cache_dtype / block_size
    # 前后端选择器（selector）靠这些 supports_* 判断是否可用
    @staticmethod
    def get_name() -> str: ...

    @staticmethod
    def get_impl_cls() -> type[AttentionImplBase]: ...

    @staticmethod
    def get_builder_cls(): # -> AttentionMetadataBuilder
        ...

class AttentionImpl(AttentionImplBase[T]):
    def forward(self, layer, query, key, value,
        kv_cache, attn_metadata, ...) -> torch.Tensor: ...

每个后端要回答三件事：

  • get_impl_cls() —— 返回真正算注意力的实现类（如 FlashAttentionImpl）；
  • get_name() —— 后端名字，如 "FLASH_ATTN" / "FLASHINFER"；
  • get_builder_cls() —— 返回一个「元数据构建器」，负责把调度器给出的 block table、seq_lens 等整理成后端 kernel 需要的形式（见下边 metadata）。

forward 的签名非常统一：输入 query/key/value、kv_cache、attn_metadata，输出 attention 结果。模型层每层注意力都按这个签名调用，到底执行哪个实现由上层选择器决定。这就是「架构无关接口 + 多后端实现」——同一份模型代码能同时跑在 FlashAttention、FlashInfer、TRTLLM 上，而 vLLM 几乎是全平台支持的。

后端的「账单」在 vllm/v1/attention/backends/registry.py 里：一个 AttentionBackendEnum 枚举，每一项的值是类的完整限定名。例如：

vllm/v1/attention/backends/registry.py — 后端枚举（摘录）
pythonclass AttentionBackendEnum(Enum, ...):
    FLASH_ATTN  = "vllm.v1.attention.backends.flash_attn.FlashAttentionBackend"
    FLASHINFER  = "vllm.v1.attention.backends.flashinfer.FlashInferBackend"
    TRITON_ATTN = "vllm.v1.attention.backends.triton_attn.TritonAttentionBackend"
    CUTLASS_MLA = "vllm.v1.attention.backends.mla.cutlass_mla.CutlassMLABackend"
    ...
    def get_class(self) -> type[AttentionBackend]:
        return resolve_obj_by_qualname(self.get_path())
图 7.1：接口在中间，多个实现各连各的 kernel，metadata（block table 等）从侧边流入提供给所有后端。

7.3后端选择：selector 怎么挑

模型初始化时调 get_attn_backend，它把「模型配置 + 设备信息」打包成一个 AttentionSelectorConfig，再层层下发给平台层去挑后端。关键逻辑在 vllm/v1/attention/selector.py：

vllm/v1/attention/selector.py — 根据配置与平台选择后端类
pythondef get_attn_backend(...) -> type[AttentionBackend]:
    config = AttentionSelectorConfig(head_size=..., dtype=...,
        kv_cache_dtype=..., block_size=..., use_mla=...,
        has_sliding_window=..., use_non_causal=..., ...)
    backend = attention_config.backend          # 用户可用 --attention-backend 指定
    return _cached_get_attn_backend(backend, config, ...)

def _cached_get_attn_backend(backend, config, num_heads):
    attention_cls = current_platform.get_attn_backend_cls(   # 平台决定
        backend, attn_selector_config=config, num_heads=num_heads)
    backend_cls = resolve_obj_by_qualname(attention_cls)      # 类名字符串 -> 类
    ...

最终决策落在平台的 get_attn_backend_cls（如 vllm/platforms/cuda.py），逻辑是：

  • 如果用户显式指定了 --attention-backend，就校验它是否满足当前配置（validate_configuration 跑一遍所有 supports_* 检查），满足就用，不满足直接报错；
  • 否则按一个优先级列表逐个试：get_valid_backends 返回「可用后端 + 优先级」，取优先级最高的（min(valid_backends_priorities, key=lambda c: c.priority)）。
  • 不同硬件/场景给不同列表，例如 SM100f 的非因果注意力优先 FlashAttention，普通 CUDA 平台一般默认 FLASH_ATTN → FLASHINFER → TRITON_ATTN → FLEX_ATTENTION。

所以「是否 enable_flashinfer」这类开关并不是硬编码一个 if，而是：每个后端声明自己的 supports_* 能力（dtype、head_size、block_size、是否是 MLA、是否支持 sliding window、GPU 算力…），选择器用这些能力把所有候选过滤一遍，再在剩下的里挑优先级最高的。这样新增一个后端只需要注册到枚举并实现能力检查，选择器零改动。

7.4自定义算子入口：ops 那层皮

模型里大量直接调用的是 vllm/_custom_ops.py。它是「Python 壳」：把 torch.ops._C.* / _vllm 这些 C++/CUDA 算子包成好读、带类型注解的 Python 函数，同时用 @register_fake 给自定义算子在 torch 里登记 shape 规则（供 torch.compile / fake tensor 用）。

vllm/_custom_ops.py — 几个真实自定义算子入口
pythondef rms_norm(out, input, weight, epsilon) -> None:
    torch.ops._C.rms_norm(out, input, weight, epsilon)

def rotary_embedding(positions, query, key, head_size, cos_sin_cache, ...):
    torch.ops._C.rotary_embedding(...)

def paged_attention_rocm(out, exp_sum, max_logits, tmp_out, query,
    key_cache, value_cache, ..., block_tables, seq_lens, ...) -> None:
    torch.ops._rocm_C.paged_attention(...)

def merge_attn_states(output, prefix_output, prefix_lse,
    suffix_output, suffix_lse, output_lse=None, ...) -> None:
    torch.ops._C.merge_attn_states(...)   # prefill 分块后合并各块状态（前缀/后缀的 output 与 lse）

看 rms_norm 就够了：Python 里唯一干的事就是把五个参数原样传给 torch.ops._C.rms_norm。真正的实现是 C++ 侧编译进 _C 库的 kernel（源在 csrc/），Python 只是入口/适配层。优点：模型代码不用碰 C++，写出来像普通 PyTorch 函数；ops.rms_norm(out, input, weight, 1e-6) 一行就完成一次融合的 RMSNorm。

除了 C++ 算子，vLLM 还用 Triton 写了一批「Python 写、照样能跑在 GPU」的算子，集中在 vllm/v1/attention/ops/（如 triton_attention_helpers.py、triton_prefill_attention.py、triton_decode_attention.py），配合 vllm/triton_utils/ 做一些缓存与自动调参。Triton 的好处是无需手写 CUDA 也能做 kernel 级优化，常用来实现那些没有现成库覆盖的注意力变体。

注意：注意力这类 hot loop 并不走 _custom_ops.py 的 Python 壳，而是后端实现里直接调动静库（如 flash_attn_varlen_func）或 torch.ops。Python 壳更多用于 RMSNorm、RoPE、KV cache 写入、量化 GEMM 这类模型层直接用的小算子。

7.5用代码看：一个后端到底怎么 forward

以默认的 FlashAttentionImpl.forward 为例（vllm/v1/attention/backends/flash_attn.py）。签名告诉你它拿什么、给什么：

vllm/v1/attention/backends/flash_attn.py — FlashAttentionImpl.forward（签名）
pythondef forward(self, layer, query, key, value, kv_cache, attn_metadata,
    output, output_scale=None, output_block_scale=None) -> torch.Tensor:
    # query:  [num_tokens, num_heads,     head_size]        # 本次所有 token 的 Q
    # key:    [num_tokens, num_kv_heads,  head_size]        # 新算的 K
    # value:  [num_tokens, num_kv_heads,  head_size]
    # kv_cache: [num_blocks, num_kv_heads, block_size, 2*head_size]  # 分页缓存
    # attn_metadata: FlashAttentionMetadata —— 装着 block table、seq_lens 等
    # returns: [num_tokens, num_heads * head_size]         # 注意力输出

    if attn_metadata is None:
        return output.fill_(0)          # profiling 时直接填 0 跳过
    ...
    # 内部按 attn_type 分流：decode 走一次一 token 路径，
    # prefill 走 varlen 向量化路径，最终都落到 flash_attn_varlen_func 等
读懂这段：这是「分页」与「后端」接缝处——它拿到的是物理上分页的 kv_cache 和 block table（metadata），而底层 FlashAttention kernel 恰好知道怎么按 block table 去读不连续的 KV。这也正是第 3 章「PagedAttention 就是懂 block table 的 FlashAttention」在代码里的落点。

再看看一个 MLA 后端如何把 KV 写进缓存——这里直接调用 _custom_ops 里的算子（vllm/v1/attention/backend.py 的 do_kv_cache_update）：

vllm/v1/attention/backend.py — MLAAttentionImpl.do_kv_cache_update（摘录）
pythondef do_kv_cache_update(self, kv_c_normed, k_pe, kv_cache,
    slot_mapping, kv_cache_dtype, k_scale) -> None:
    if kv_cache.numel() == 0:
        return
    from vllm import _custom_ops as ops
    ops.concat_and_cache_mla(                     # 把 MLA 的 K/V 写进分页缓存
        kv_c_normed, k_pe.squeeze(1), kv_cache,
        slot_mapping.flatten(), kv_cache_dtype=kv_cache_dtype, scale=k_scale)
看懂这条链路：模型层算出的新 K/V → 后端实现（这里是 MLA）把新算的 KV 写进每请求的 slot（slot 是 block table 展开后的一个具体位置）→ 真正干活的是 ops.concat_and_cache_mla 这个自定义算子。于是「内存管理（第 3/8 章）+ 后端抽象（本章）+ 算子入口」三者在这里汇合。

7.6小结与自研启示

环节vLLM 的做法你的引擎可以
注意力 kernelbackend 抽象 + FlashAttention / FlashInfer 等多实现先用 torch.nn.functional.scaled_dot_product_attention 或现成 flash-attn 库，别自己写
后端选择各后端 supports_* + 平台优先级列表第一版直接写死 sdpa，跑通了再加选择
小算子_custom_ops.py 包 torch.ops._C.*RMSNorm 等先用 torch 组合代替，后续再考虑 kernel
GEMMCUTLASS / cuBLAS调 torch 的 matmul 就已走 cuBLAS，够用
Triton 变体vllm/v1/attention/ops/需要特殊注意力时再学 Triton，属于进阶
自研启示 kernel 是「懂了再优化」的事，不是「起步就自己写」。你的第一个版本用 torch.nn.functional.scaled_dot_product_attention（SDPA，内部会自动选 FlashAttention/Memory-Efficient）和 flash-attn 现成库就能获得几乎 SOTA 的注意力性能。vLLM 最值得借鉴的是它的抽象分层——后端接口 + 注册表 + 按能力选择——让你换 kernel 如换插件，而不是跟 kernel 死磕。
