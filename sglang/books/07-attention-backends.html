注意力后端：模型代码不选 kernel，注册表选

同一个 transformer，attention kernel 有二十多种实现可选（flashinfer、fa3、triton、flashmla……）。SGLang 把「模型怎么写」和「attention 怎么算」拆开：模型层只调用一个 RadixAttention 模块，具体 kernel 由注册表按启动参数装配。这一章拆这层接口。

7.1一分钟版本

注意力后端（attention backend）= 分页注意力在某一类硬件/kernel 家族上的具体实现。它要回答的问题都一样：给定 q/k/v、KV 池的槽位索引（req_to_token）、每个请求的序列长度，怎么把这一步的 attention 算出来，并把新的 K/V 写进池子。

SGLang 在 attention_registry.py 里注册了 23 个后端工厂。启动时按 --attention-backend（或不指定，按硬件与模型自动挑）解析出两个名字——prefill 和 decode 各一个——分别实例化，必要时组合成混合后端。之后模型代码的每一层都不再碰 kernel 选择：每层只有一个 RadixAttention 模块，它的 forward 把调用转给当前装配好的后端。

  • MHA 路线（标准多头）：flashinfer、fa3/fa4、triton、trtllm_mha……K/V 是两个独立张量。
  • MLA 路线（DeepSeek 潜空间注意力）：flashmla、trtllm_mla、cutedsl_mla、tokenspeed_mla……KV 压缩成一个 latent 向量加 rope 部分，kernel 形状完全不同。

同一个注册表覆盖两条路线：多数 MLA 后端的工厂函数会先检查 runner.use_mla_backend，不匹配直接报错。

7.3注册表机制：一个 dict + 一个装饰器

注册表本身短得可疑——一个模块级 dict，加一个把工厂函数塞进去的装饰器：

python/sglang/srt/layers/attention/attention_registry.py — 注册表与 flashinfer 工厂（摘录，注释为译注）
pythonATTENTION_BACKENDS = {}

def register_attention_backend(name):
    def decorator(fn):
        ATTENTION_BACKENDS[name] = fn
        return fn
    return decorator

@register_attention_backend("flashinfer")
def create_flashinfer_backend(runner):
    import torch

    if not runner.use_mla_backend:
        from sglang.srt.layers.attention.flashinfer_backend import (
            FlashInferAttnBackend,
        )
        # 投机解码时 plan 要跑在独立 stream 上，避免和主前向串行
        if get_spec().speculative_algorithm == "EAGLE":
            if not hasattr(runner, "plan_stream_for_flashinfer") or \
                    not runner.plan_stream_for_flashinfer:
                runner.plan_stream_for_flashinfer = torch.cuda.Stream()
        return FlashInferAttnBackend(runner, init_new_workspace=runner.init_new_workspace)
    else:
        # 同一个名字，MLA 模型走另一个实现
        from sglang.srt.layers.attention.flashinfer_mla_backend import (
            FlashInferMLAAttnBackend,
        )
        return FlashInferMLAAttnBackend(runner)
读懂这段： 每个工厂都是一个「字符串 → 实例」的函数，imports 写在函数体内（惰性加载），所以没装 flashinfer 的环境只要不选它就不会 import 失败。工厂也是做兼容检查的地方：比如 fa3 断言 SM80/SM90、trtllm_mla 断言 MLA 模型、triton 拒绝 encoder-decoder 模型——把兼容性检查放在工厂里，报错发生在启动时而不是跑了几步之后。

工厂还有第三种职责：建运行时资源。flashinfer 这个工厂里，投机解码启用时会给 runner 挂一个 plan_stream_for_flashinfer（注意它检查 hasattr 再赋值，因为同一 runner 可能被多次创建后端）。这种「副作用写在工厂里」的做法好处是资源跟着后端走、后端不选就不建；代价是工厂不再是纯函数，读代码时别把它当查表。

装配发生在 ModelRunner 初始化时，最后一行就是查表：

python/sglang/srt/model_executor/model_runner_components/attention_backend_setup.py — 解析与实例化（摘录，注释为译注）
pythondef resolve_attention_backend_strs(*, model_runner: ModelRunner) -> ResolvedAttentionBackendStr:
    # draft runner 的后端是它自己的：target 与 draft 同进程共存，
    # 不能取自进程级配置
    is_draft_worker = model_runner.is_draft_worker
    draft_attn_backend = model_runner.draft_attention_backend
    if is_draft_worker and draft_attn_backend:
        logger.warning(f"Overriding draft attention backend to {draft_attn_backend}.")
        # draft 所有模式共用同一个后端，不做 prefill/decode 拆分
        return ResolvedAttentionBackendStr(
            prefill=draft_attn_backend, decode=draft_attn_backend,
            is_draft_override=True)
    prefill, decode = attention_backends()
    return ResolvedAttentionBackendStr(prefill=prefill, decode=decode)


def _build_resolved_backend(*, model_runner, resolved, init_new_workspace):
    if resolved.is_draft_override:
        attn_backend = _build_backend_from_str(model_runner=model_runner,
                                             backend_str=resolved.prefill, ...)
    elif resolved.decode != resolved.prefill:
        # 先把两个 full-attention 后端组合起来，再统一套一次模型级 wrapper。
        # 分别包再组合会让混合架构模型（如 Qwen3.5）的线性/稀疏侧后端被复制两份
        # （两个 GDN dispatcher），初始化与状态都翻倍，而一次前向只有一侧真正生效。
        attn_backend = attn_backend_wrapper(
            model_runner,
            HybridAttnBackend(
                model_runner=model_runner,
                decode_backend=_build_full_attention_backend_from_str(..., backend_str=resolved.decode, ...),
                prefill_backend=_build_full_attention_backend_from_str(..., backend_str=resolved.prefill, ...),
            ),
        )
        # 且会打一条 warning：混用后端是实验特性，可能被默认值覆盖
    else:
        attn_backend = _build_backend_from_str(model_runner=model_runner,
                                             backend_str=resolved.prefill, ...)
    return attn_backend

def _build_full_attention_backend_from_str(*, model_runner, backend_str, init_new_workspace):
    if backend_str not in ATTENTION_BACKENDS:
        raise ValueError(f"Invalid attention backend: {backend_str}")
    model_runner.init_new_workspace = init_new_workspace
    return ATTENTION_BACKENDS[backend_str](model_runner)
读懂这段： 三个分支的优先级要按顺序读：draft 覆盖 > prefill/decode 不同 > 单一后端。解析分成了两个函数，值得留意：resolve_attention_backend_strs 只负责决定用哪些字符串、并置上 is_draft_override 这个标志；_build_resolved_backend 只负责按标志决定怎么装配。draft 覆盖之所以要单独走一条路，是因为 draft worker 和 target 模型共存于同一进程，后端不能取自进程级配置，只能来自 ModelRunner.draft_attention_backend——而且它会先打一条 logger.warning，说明这是「用户配置被静默改写」的场景，出问题时要先看日志。名字不相等时先包一层 HybridAttnBackend（prefill 走一个、decode 走另一个），再套 attn_backend_wrapper 处理混合架构模型（GDN/Mamba 线性注意力层替换部分层）。也就是说「后端」不一定是单个 kernel 实现，可以是一棵组合树。
wrapper 为什么套在外面： 源码这里有一段明确的注释，值得当成演进痕迹读。原来的写法是每个子后端各包一次 wrapper，再组合。问题出在混合架构模型上：wrapper 内部要建线性/稀疏侧的副后端（比如 GDN dispatcher），包两次就建两个——初始化和状态都翻倍，而一次前向里只有一侧真正生效。现在改成先组合、再统一包一次。init_new_workspace 这个参数也是一路透传到 _build_full_attention_backend_from_str 里，赋给 model_runner.init_new_workspace 后才调用工厂——工厂要靠这个标志决定是新建 workspace 还是复用已有的。
演进痕迹 注册表里有现成的弃用样本：nsa 现在只是 dsa（DeepSeek 稀疏注意力）的别名，注册的是一个打 DeprecationWarning 的转发函数。改名而留别名，是为了不打破用户脚本——这类兼容层在演进快的模块里很常见。

7.4RadixAttention 层：名字与职责

困惑点 模型代码里每层 attention 都是 RadixAttention，但这个类和第 3 章的基数树缓存没有关系。它只是 QKV 到后端 kernel 的转发层——「Radix」是项目早期论文里注意力实现与前缀缓存绑定的历史遗留；如今这一层对缓存一无所知，纯粹是把张量交给后端。真正的前缀逻辑在 mem_cache/radix_cache.py。

这个类存的都是 kernel 需要的每层常量，forward 里做三件事：reshape、判断是否走编译路径、转发：

python/sglang/srt/layers/radix_attention.py — 字段与 forward 分派（摘录，注释为译注）
pythonclass RadixAttention(nn.Module):

        self.tp_k_head_num = num_kv_heads
        self.head_dim = head_dim
        self.scaling = scaling              # 1/sqrt(d)，kernel 直接用
        self.layer_id = layer_id            # 用来在 KV 池里找本层的 k_buffer/v_buffer

        self.sliding_window_size = sliding_window_size or -1

                v = v.view(-1, self.tp_v_head_num, self.v_head_dim)

                k = k.view(-1, self.tp_k_head_num, self.v_head_dim)

                and context is not None ...):

            ...
        else:

读懂这段： get_attn_backend() 从 forward context 里取当前实例——ModelRunner 在每次前向外围把后端挂进 context，模型代码因此完全不用持有后端引用。layer_id 是后端与 KV 池对上的关键：后端用它去 k_buffer[layer_id] 读写（第 5 章）。layer.scaling / logit_cap / sliding_window_size 这些常量也经 layer 参数透传给 kernel。

上面那个 k_rope 分支是目前唯一一处「按 kwargs 决定 reshape 形状」的地方：带 k_rope 的模型（部分 MLA/混合结构）会把 rope 部分从 k 里拆出去，此时 k 剩下的宽度是 v_head_dim 而不是 qk_head_dim。这种「靠约定参数名换行为」的写法读起来突然，但它避开了在每层 forward 里传一个显式标志位。key_value_num_tokens 则是新加的可选形参，给需要显式知道 KV token 数的后端（如跨层共享、异构 batch）留的口子。

7.5AttentionBackend 契约：三个初始化钩子 + 两个 forward

每个后端要实现的接口分两组。第一组是每步前向前的元数据准备——paged attention 需要页表（kv_indptr、kv_indices、kv_last_page_len），这些张量每个 batch 都不同，而 CUDA Graph 按地址捕获，所以准备动作被拆成三段：

python/sglang/srt/layers/attention/base_attn_backend.py — 类文档与默认实现（摘录，docstring 译文）
pythonclass AttentionBackend(ABC):
    """
    Forward-data init contract (3 methods):

      - ``init_forward_metadata(fb)`` — eager entry point. Default is a wrapper
        that calls ``_out_graph(fb)`` then ``_in_graph(fb)``.
      - ``init_forward_metadata_out_graph(fb, in_capture=False)`` — per-iter
        metadata prep, runs outside ``with graph.capture():``. Capture
        sites pass ``in_capture=True``; replay/eager use the default False.
      - ``init_forward_metadata_in_graph(fb)`` — graph-recordable static-shape
        GPU op, runs inside ``with graph.capture():`` at capture time and
        is auto-replayed by ``graph.replay()``. Default is no-op.

    The legacy ``init_forward_metadata_capture_cuda_graph`` and
    ``init_forward_metadata_replay_cuda_graph`` overrides are fully
    deprecated and removed from the ABC.
    """

    def init_forward_metadata(self, forward_batch: ForwardBatch):
        # eager = 图外准备 + 图内准备，顺序执行
        self.init_forward_metadata_out_graph(forward_batch)
        self.init_forward_metadata_in_graph(forward_batch)
读懂这段： 为什么要拆成图外/图内两半：.item()、动态 shape 的 torch.empty、CPU 端计算都没法被 CUDA Graph 记录，必须放在 out_graph（每次 capture/replay 前跑，写进固定的静态缓冲区）；in_graph 只放静态 shape 的纯 GPU op，capture 时被记录、replay 时随图自动重放。基类还写了 lint 约束：in_graph 的覆盖实现不许调用 .item()/.cpu()/.tolist()。旧的 init_forward_metadata_capture_cuda_graph / ..._replay_cuda_graph 两个钩子已被删除、统一进 out_graph(fb, in_capture)——这是接口本身的一次收敛。

第二组是真正的前向。基类的 forward 按 forward_mode 分派，idle（DP 空跑填充）直接返回空张量：

python/sglang/srt/layers/attention/base_attn_backend.py — forward 分派（摘录，注释为译注）
pythondef forward(self, q, k, v, layer, forward_batch, save_kv_cache=True, **kwargs):
    if forward_batch.forward_mode.is_idle():
        return q.new_empty(q.shape[0], layer.tp_q_head_num * layer.v_head_dim)
    elif forward_batch.forward_mode.is_decode():
        return self.forward_decode(q, k, v, layer, forward_batch, ...)
    elif forward_batch.forward_mode.is_mixed() and is_npu():
        return self.forward_mixed(q, k, v, layer, forward_batch, ...)
    else:
        return self.forward_extend(q, k, v, layer, forward_batch, ...)
为什么 decode 和 extend 必须分成两个方法： decode 步每个序列只有一个新 query token，用 paged kernel 逐 seq 查 KV 池即可；prefill（EXTEND/TARGET_VERIFY）的新 token 是一段 ragged 序列、还要带因果掩码，kernel 形状和 plan 流程完全不同。
MIXED 的归属变过一次： 上面这个分派里，is_mixed() 现在有一条单列的分支——仅在 NPU 上走 forward_mixed，其余情况落到 forward_extend。所以在非 NPU 平台上，「MIXED 也走 extend」这句话仍然成立，但它已经不再是无条件的班底规则，而是兜底分支的结果。这类「某个平台上多一条专用路径」的分叉在基类里通常意味着该平台的 kernel 对混合批次有特殊处理需求，不适合硬套 extend 的形状。

7.6代表实现：flashinfer 的 decode 与 extend

以 flashinfer 后端为例。decode 路径把新 K/V 写进池子，然后调用本 batch 预先 plan 好的 wrapper：

python/sglang/srt/layers/attention/flashinfer_backend.py — forward_decode（摘录，注释为译注）
pythondef forward_decode(self, q, k, v, layer, forward_batch, save_kv_cache=True):
    # 本层的 wrapper：sliding window / cross-attention 层用不同的实例
    decode_wrapper = self.forward_metadata.decode_wrappers[
        self._get_wrapper_idx(layer)
    ]
    cache_loc = (
        forward_batch.out_cache_loc
        if not layer.is_cross_attention
        else forward_batch.encoder_out_cache_loc
    )

    if k is not None and save_kv_cache:
        # 把本步新 token 的 K/V 写进 KV 池（第 5 章的 set_kv_buffer）
        self.token_to_kv_pool.set_kv_buffer(
            layer, KVWriteLoc(cache_loc, ...), k, v, ...)

    kv_cache = self.token_to_kv_pool.get_kv_buffer(layer.layer_id)

    o = decode_wrapper.forward(
        q.contiguous().view(-1, layer.tp_q_head_num, layer.head_dim),
        kv_cache,
        sm_scale=layer.scaling,
        logits_soft_cap=layer.logit_cap,
        k_scale=layer.k_scale_float,
        v_scale=layer.v_scale_float,
    )
    return o.view(-1, layer.tp_q_head_num * layer.head_dim)
读懂这段： 每步 decode 前的 init_forward_metadata 已经用本 batch 的 seq_lens 更新了页表并重新 plan 出 decode_wrappers；这里只是「写 KV → 取 KV → 调 kernel」。注释里那行 Must use _float to avoid device-to-host copy 值得注意：传量化 scale 的 float 属性而不是 tensor 属性，是为了不触发 D2H 拷贝——那会破坏 CUDA Graph 捕获。这类约束遍布后端代码，是「接口为 CUDA Graph 让路」的具体表现。

prefill（extend）路径多一个分叉：有没有已缓存前缀。无前缀的新 token 用 ragged kernel（直接吃 q/k/v 三个张量），有前缀的用 paged kernel（吃整个 KV 池 + 页表）：

python/sglang/srt/layers/attention/flashinfer_backend.py — forward_extend 的两条路（摘录，注释为译注）
pythondef forward_extend(self, q, k, v, layer, forward_batch, save_kv_cache=True):
    prefill_wrapper_paged = self.forward_metadata.prefill_wrappers[
        self._get_wrapper_idx(layer)
    ]
    # use_ragged：本批没有任何已缓存前缀
    if not self.forward_metadata.use_ragged:
        if k is not None and save_kv_cache:
            self.token_to_kv_pool.set_kv_buffer(layer, ..., k, v, ...)
        o = prefill_wrapper_paged.forward(
            q.view(-1, layer.tp_q_head_num, layer.head_dim),
            kv_cache,
            causal=causal,
            sm_scale=layer.scaling,
            window_left=layer.sliding_window_size,
            logits_soft_cap=layer.logit_cap, ...)
    else:
        # ragged 入参可能干脆不带 k/v，那就从 KV 池里取本层已写入的缓存当 KV 源
        if k is None and v is None:
            k, v = self.token_to_kv_pool.get_kv_buffer(layer.layer_id)
        if self.forward_metadata.extend_no_prefix:
            # 连页表都不用查：全批都无前缀，直接一次 causal attention
            o = self.prefill_wrapper_ragged.forward(
                q.view(...), k.view(...), v.view(...),
                causal=causal, sm_scale=layer.scaling, ...)
        else:
            # 无前缀但有滑动窗口等约束：ragged 段与 paged 段分别出 lse，再合并
            o1, s1 = prefill_wrapper_ragged.forward_return_lse(
                q.view(...), k.view(...), v.view(...), causal=causal, ...)
            o2, s2 = prefill_wrapper_paged.forward_return_lse(
                q.view(...), kv_cache, causal=False, ...)
            o, _ = _safe_merge_state(o1, s1, o2, s2)
读懂这段： ragged 分叉是 prefill 的重要优化：首批请求（无共享前缀）跳过页表间接寻址，直接在连续张量上算，速度更接近普通 attention；一旦命中 RadixCache 前缀（第 3 章），就只能走 paged 路径，因为历史 KV 散布在池里。这也是「前缀缓存省的是算力，但会增加 kernel 访问模式复杂度」的一个具体体现。

三处演进痕迹：① use_ragged 之下现在还有一层 extend_no_prefix——只有当整个批次都没有前缀时才走单次 ragged 调用，否则要用 forward_return_lse 拿回 log-sum-exp 统计量、再和 paged 段的结果合并（softmax 不能简单相加，必须权重化）。② ragged 分支开头多了 k is None and v is None 的兜底：调用方可以不传 KV 张量，此时从 token_to_kv_pool 里取本层已写入的缓存当 KV 源，省掉一次重物化。③ 注意 causal=False 那行——paged 段已经通过位置索引把可见性编码进去了，不能再叠一层 causal 掩码，否则短 query 会看不到自己的历史。

关于 MHA 与 MLA 的分野：MHA 后端操作 k_buffer/v_buffer 两个张量；MLA（DeepSeek 系列）把 KV 压缩成 kv_lora_rank 维的 latent 向量 + 解耦的 rope 部分，decode 时可以「吸收」（absorb）进投影矩阵，用一个大 latent 头的 kernel 代替多头的 K/V。因此 MLA 有自己的一组后端（flashmla、trtllm_mla、cutedsl_mla、tokenspeed_mla），注册表里多数 MLA 工厂以 if not runner.use_mla_backend: raise ValueError(...) 开头。fa3（FlashAttention-3）则是 MHA 路线上 Hopper（SM90）卡的常用选择，工厂里用 get_device_capability() 断言算力等级。
