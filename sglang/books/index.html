深入 SGLang：从源码到自研推理引擎

SGLang 版本 gateway-v0.3.1-9918-g9eda772a21 git describe 标注 · HEAD 9eda772a21 · 2026-09-22

目标读者：想理解 SGLang 内部、并最终写出自己推理引擎的工程师。
浏览方式：双击 sglang/books/index.html，或用浏览器打开；可对照仓库源码逐行阅读。

图 0：SGLang 的高层数据流。HTTP 进程、Scheduler 子进程、Detokenizer 子进程通过 ZMQ 相连；调度与 KV 管理（RadixCache + 分页内存池）都在 Scheduler 里。

学习路径

STEP 1

整体架构与进程模型

SRT 的四个进程：HTTP 服务、TokenizerManager、Scheduler（每 TP rank 一个）、DetokenizerManager，以及连接它们的 ZMQ 通道。
STEP 2

请求全生命周期

从 /generate 到流式输出的完整链路：分词 → 入队 → 调度 → 前向 → 采样 → 反分词；含重叠调度（CPU 调度与 GPU 前向并行）的两套事件循环。
STEP 3

RadixCache 前缀缓存

SGLang 的招牌：用基数树管理 KV 前缀。match_prefix / insert / evict / 锁引用，页对齐与命名空间隔离，多轮对话为什么快。
STEP 4

调度器与调度策略

PrefillAdder 的三本预算账（总 token / chunk / 输入 token）、cache-aware 排序策略、chunked prefill、retract 抢占回收。
STEP 5

内存池与显存预算

ReqToTokenPool、TokenToKVPool（MHA/MLA）、分页分配器；mem_fraction_static 如何通过启动 profiling 定出 KV 池大小，alloc_extend 的向量化三段式。
STEP 6

ModelRunner 与 CUDA Graph

ForwardBatch 如何从 ScheduleBatch 派生；forward 的三级路径：decode graph 回放 → prefill 分段图 → eager 回退；capture 与 replay。
STEP 7

注意力后端

注册表机制、MHA 与 MLA 两条路线、AttentionBackend 的三个初始化钩子契约（eager / out-of-graph / in-graph），flashinfer 与 fa3 例解。
STEP 8

采样与结构化输出

Sampler 的贪心/概率两条路径、top-k / top-p / min-p、logit_bias 与禁止 token；grammar 约束生成（xgrammar 等）与 function call 解析。
STEP 9

服务入口

http_server 的 80 多条路由、/generate 的 SSE 流式协议、OpenAI 兼容层、离线 Engine 的进程编排；ServerArgs 与 runtime_context 配置体系。
STEP 10

分布式推理

TP / PP / DP / EP 四个维度的正交组合；DataParallelController 的四种负载均衡；dp_attention 的 MLP 同步；自定义 allreduce。
STEP 11

HiCache 分层缓存

KV cache 出了 GPU 之后放哪：L1 显存 / L2 主机内存 / L3 存储后端（file、mooncake、hf3fs…），HiRadixTree、预取与回写。
STEP 12

PD 分离部署

Prefill 与 Decode 拆成独立实例：bootstrap 房间握手、KV 传输（Mooncake / NIXL）、两套专用事件循环与三个队列。
STEP 13

投机解码

EAGLE-2/3 的草稿-验证结构、MTP 权重复用、NGRAM 提示内 n-gram 草稿；草稿 worker 如何挂在 overlap 调度上（spec v2）。
说明 本站基于 SGLang 主仓库（sgl-project/sglang）的 SRT（SGLang Runtime）编写，所有代码片段从当前仓库摘录并标注了真实文件路径（python/sglang/srt/...）。 代码对应 gateway-v0.3.1-9918-g9eda772a21（git describe --tags，HEAD 9eda772a21）。 仓库持续演进，若某处路径/函数名对不上，以仓库最新代码为准 —— 那本身就是最好的学习材料。
与 vLLM 对照 如果读过本站《深入浅出vLLM》：两者解决同一问题（连续批处理 + 分页 KV + 前缀缓存），但切法不同。SGLang 的调度与 KV 管理集中在 Scheduler 单进程内（vLLM 是 EngineCore + KVCacheManager），前缀缓存用的是基数树（vLLM 是哈希块表），进程间用 ZMQ ipc 通道（vLLM v1 用 ZMQ tcp）。对照着读能更快看清「哪些设计是本质的、哪些是工程取舍」。

全书词表

各章反复出现的术语收拢在这里，按学习路径顺序排列。「详见」指向讲得最透的章节；读正文遇到陌生词，先回来查这一张表。

术语含义详见
SRT（SGLang Runtime）SGLang 的运行时本体：把分词、调度、反分词拆成四个独立进程，进程间全部走 ZMQ ipc 通道，没有共享内存队列01
Scheduler（调度器）每 TP rank 一个的子进程，整个引擎的大头：请求队列、查前缀缓存、分配 KV 槽位、组装 batch、发起 GPU 前向都集中在这一层01
overlap 调度（重叠调度）默认启用的事件循环：CPU 处理上一批输出与 GPU 跑下一批并行，中间靠 future_map 给还没算完的 token 占位02
RadixCache（前缀缓存）用一棵基数树管住 KV 前缀：树边是页对齐的 token 序列，match_prefix 查复用、insert 存结果、evict 按 LRU 淘汰03
RadixAttention论文标题留下的名字：模型层里「QKV 投影之后、attention kernel 之前」的分发层，只管存 KV、选后端、转发调用，与那棵树没有运行时关系03
prefill / decode一次生成的两段：prefill 一次算入整个 prompt（算力密集）；decode 每步只进一个新 token（带宽密集），瓶颈相反04
PrefillAdder（预算制准入）prefill 批的收编者：三本账（总 token / chunk / 输入 token）决定「能不能收」，cache-aware 排序决定「先收谁」04
chunked prefill（分块预填充）把过长的 prefill 切成小块分多个 step 算完，避免一个长 prompt 卡住整批 decode04
retract（抢占回收）running batch 的 KV 放不下下一步时，把部分请求踢回等待队列、KV 释放重排；只做最后一道防线04
ReqToTokenPool / TokenToKVPoolKV 池的两个核心对象：前者是「请求的第 j 个 token 存在哪个槽位」的目录表，后者是每层 k/v buffer 张量本体，按下标即槽位号存取05
mem_fraction_static显存预算旋钮：权重 + KV 池装进「静态区」，KV 池在启动时按一次 profiling 一次性建好，运行期大小不变05
ForwardBatch调度侧 ScheduleBatch 压平成的一批 GPU 张量，是 ModelRunner.forward 的唯一入口06
CUDA Graph（图捕获回放）把一串 GPU 操作录成图、一次提交回放：decode 走整图回放、prefill 走分段图，都放不下再 eager 回退06
AttentionBackend（注意力后端）可插拔的 attention kernel 层：注册表按启动参数装配（flashinfer、fa3、flashmla……），模型层只调一个 RadixAttention07
MHA / MLAKV 布局的两条路线：MHA（Multi-Head Attention）是标准多头，K/V 是两个独立张量；MLA（Multi-head Latent Attention）是 DeepSeek 的潜空间注意力，KV 压成低秩 latent 向量07
grammar（语法约束）结构化输出的约束生成：采样前把非法 token 的 logits 掩掉，保证输出符合 JSON schema / 正则；内置 outlines、xgrammar、llguidance 三种后端08
OpenAI 兼容层 / 离线 Engine原生 /generate 之外的两扇入口：/v1/* 把 OpenAI 协议翻译成 GenerateReqInput；离线 Engine 绕开 HTTP 直接驱动同一套进程09
TP / PP / DP / EP四个正交的并行维度：张量并行切每层权重、流水线并行按层分段接力、数据并行复制整个模型分流量、专家并行把 MoE 专家摊到多卡10
allreduceTP 组内每层前向做 1~2 次的同步原语；SGLang 的选路有六条，从平台专用通信器一路兜底到 torch 默认，custom allreduce 只在「消息够小 + 链路够好」时才赢10
dp_attentionDeepSeek 类 MLA 模型的省通信玩法：注意力按 DP 复制、MoE 按分片算，进 MoE 前把各 DP rank 的本地 token 拼成全局缓冲区10
HiCache / HiRadixCacheKV 出了 GPU 之后的分层去处：L1 显存、L2 主机内存、L3 存储后端；L1 逐出前先回写备份，未命中时按页哈希预取拉回11
PD 分离（prefill/decode disaggregation）Prefill 与 Decode 拆成两个独立实例池、中间传 KV；实现克制：不是另写一套引擎，而是同一个 Scheduler 里加两条专用事件循环和三个队列12
bootstrap（房间握手）PD 分离的握手步骤：prefill 侧分配 bootstrap_room，decode 侧预注册接收方（host/port/room），握手完成请求才进 waiting 队列12
Mooncake / NIXLKV 传输引擎的两个生产后端：都实现同一套 conn 基类，按启动参数在后端枚举里选，MooncakeKVManager 与 NixlKVManager 各管各的连接12
EAGLE（投机解码）草稿-验证式投机解码：便宜的草稿器一次提出 k 个候选，目标模型一次前向整批验证，输出分布与直接采样完全一致；与 overlap 调度的配合方案叫 spec v213
MTP / NGRAM两个省事的草稿来源：MTP 是模型自带的 multi-token prediction 头（随权重发布、通常无需单独下载）；NGRAM 从提示与已生成内容里查 n-gram 匹配直接抄片段13
