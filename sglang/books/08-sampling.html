采样与结构化输出：logits 之后发生了什么

模型前向算出 logits 只是半成品。这一章讲剩下的三件事：把每个请求各自的采样参数合并成 batch 级张量、Sampler 按「贪心/概率」两条路径选出 token、以及两类输出约束——grammar 逐 token 屏蔽和 function call 文本解析。

8.1一分钟版本

前向结束后，LogitsProcessorOutput.next_token_logits（形状 [batch, vocab_size]）交到采样链路手里。剩下的事分三步：

  • 参数合并：每个请求带着自己的 SamplingParams（temperature、top_k、top_p、min_p、logit_bias、penalties…）。GPU kernel 不喜欢逐请求分支，所以 SamplingBatchInfo.from_schedule_batch 把它们压成 batch 级张量，并顺手算出几个布尔标志（is_all_greedy、need_top_k_sampling…）供代码走快速路径。
  • 选 token：Sampler.forward 先看 is_all_greedy——整个 batch 都是贪心时直接 argmax，一个 kernel 完事；否则按需走 top-k/top-p/min-p 的采样内核。
  • 约束：两类约束作用在两个不同的位置。grammar（JSON schema、正则）在采样之前把非法 token 的 logit 压成 -inf，逐 token 生效；function call 解析在反分词之后对文本做解析，把模型输出的特定标记格式转成结构化的 tool_calls。

8.3Sampler 源码：两条路径

Sampler.forward 的分叉逻辑非常直白：整个 batch 都是贪心就 argmax，否则进概率路径。注意贪心路径连 softmax 都不做：

python/sglang/srt/layers/sampler.py — Sampler.forward（摘录，注释为译注）
pythondef forward(self, logits_output, sampling_info, return_logprob,
            top_logprobs_nums, token_ids_logprobs, positions):
    logits = logits_output.next_token_logits

    # 预处理：自定义 logit processor + NaN 清洗
    logits = self._preprocess_logits(logits, sampling_info)

    if sampling_info.is_all_greedy:
        # 贪心快路径：不需要概率分布，argmax 一步到位
        if _use_aiter and not _disable_aiter_greedy_sample:
            batch_next_token_ids = torch.empty(
                logits.shape[0], device=logits.device, dtype=torch.int32
            )
            _aiter_greedy_sample(batch_next_token_ids, logits)
        else:
            batch_next_token_ids = torch.argmax(logits, -1)
        if return_logprob:
            original_logprobs = logprobs = torch.nn.functional.log_softmax(
                logits, dim=-1
            )
    else:
        simple_sampling_case = (
            not sampling_info.need_top_p_sampling
            and not sampling_info.need_top_k_sampling
            and not sampling_info.need_min_p_sampling
        )
        ...  # 概率路径，见下
读懂这段： 三个布尔标志（is_all_greedy、need_top_*_sampling）把 batch 里所有请求的参数归约成一个分支决策。只要有一个请求不是贪心，整个 batch 就走概率路径——贪心请求在概率路径里靠 top_k=1 的 renorm 得到等价结果。

两个同名函数要分清：Sampler._preprocess_logits（上面这个）只做「自定义 logit processor + NaN 清洗」两件事；真正施加 grammar 掩码的是 ModelRunner._preprocess_logits（model_executor/model_runner.py），它调用 sampling_info.update_regex_vocab_mask() + apply_logits_bias()。调用关系是 ModelRunner 先做、再进 Sampler.forward。两者同名但职责不重叠，读代码时按文件路径区分。positions 是后来加到签名里的：确定性采样要用它给每个位置算唯一 seed。

概率路径先做温度缩放和 softmax，再按需选择内核：simple_sampling_case（top_k/top_p/min_p 全默认）直接多项式采样；否则用 flashinfer 的融合内核：

python/sglang/srt/layers/sampler.py — _sample_from_probs 的 flashinfer 分支（摘录，注释为译注）

    logits[:] = torch.softmax(logits, dim=-1)

读懂这段： 采样后端是可配的（get_exec().kernel.sampling_backend，CUDA 上默认 flashinfer，另有 pytorch/ascend）。min-p 没有融合内核，所以走「两次 renorm + 一次采样」的三步组合；top-k/top-p 用 joint 顺序的融合内核一次完成。这段代码里还留着一条演进痕迹：确定性推理（enable_deterministic）要求 logprob 一律取自 log_softmax 内核而不是 log(softmax(x))——两者在数学上等价，数值上有 ~1e-6 差异，足以破坏 prefill/decode 的逐位对齐，源码注释专门记录了这个坑。

python/sglang/srt/layers/sampler.py — _build_sampling_mask_output（摘录，注释为译注）
python# 状态码：支撑集算不出来 = INVALID，超过容量上限 = OVERFLOW

    torch.where(overflow, SamplingMaskStatus.OVERFLOW, SamplingMaskStatus.OK),

读懂这段： 新契约是一个定长 SamplingMaskOutput：token_ids 形状固定为 [batch, sampling_mask_max_tokens]，真实长度写在 lengths 里；超长就截断并标 OVERFLOW。请求准入也因此收紧——Scheduler.handle_generate_request 现在要求 top_k=1（贪心）或 1 < top_k <= sampling_mask_max_tokens，否则直接以 400 拒绝，不再等到采样时才发现要炸。组内的 all_reduce(MAX) 是让整个 TP/CP 组对状态码取最坏值——只要有 rank 溢出，全组一起 abort，避免各 rank 对请求生死判断不一致而挂死（第 12 章讲过 PD 分离下这个值还要经元数据缓冲传给 decode 侧，且 prefill / decode 两侧都要开 SGLANG_ENABLE_DISAGG_SAMPLING_MASK，默认关闭）。
拒绝路径也重构过： 上面这段准入检查的形状变过一次。原来的写法是四处分散的「设错误 → init_req_max_new_tokens → 塞进队列」，让请求先走一遍正常流程再被 abort；现在统一收进 Scheduler._reject_sampling_mask_request(req, error_msg)，它只做三件事：记日志、prepare_abort（带 HTTPStatus.BAD_REQUEST）、stream_output 把错误送到客户端——模型一步都不跑。同时错误文案本身也细化了：原来只笼统说「需要有限 top_k」，现在明确告诉你期望是 top_k=1（贪心）或 1 < top_k <= sampling_mask_max_tokens，并把实际收到的 top_k 值打进消息，还提示可以调大 --sampling-mask-max-tokens。PD 分离那条也从「要求某个 max_tokens 环境变量大于 0」改成了直接点名要开的开关名。
演进痕迹 这段代码完整保留了一次「Python 对象 → 设备张量」的迁移。留意 SamplingBatchInfo 里新加的 sampling_mask_batch_indices：它把「哪些请求要掩码」这个判断也从逐轮扫描 return_sampling_masks 的布尔列表，变成了一个预先算好的设备索引张量。capture 工作只在 index_select 选出的那几行上做——不设掩码的请求（绝大多数）完全不进这条路径。这类「把控制流从 Python 挪进张量」的重构，在推理引擎里几乎总发生在同一个触发点：某个分支开始出现在 TPOT 的热路径上。

8.4SamplingBatchInfo：逐请求参数怎么变成 batch 张量

采样参数的合并发生在 SamplingBatchInfo.from_schedule_batch。它把每个请求的标量参数收成 GPU 张量，并归约出分支标志：

python/sglang/srt/sampling/sampling_batch_info.py — from_schedule_batch（摘录，注释为译注）

    )
    .to(device, non_blocking=True)
    .view(-1, 1)
)

min_ps = torch.tensor([r.sampling_params.min_p for r in reqs], ...)

    temperatures=temperatures, top_ps=top_ps, top_ks=top_ks, min_ps=min_ps,
    # 分支标志：任一 / 全体的归约
    is_all_greedy=all(r.sampling_params.top_k <= 1 for r in reqs),
    need_top_p_sampling=any(r.sampling_params.top_p != 1.0 for r in reqs),
    need_top_k_sampling=any(r.sampling_params.top_k != TOP_K_ALL for r in reqs),
    need_min_p_sampling=any(r.sampling_params.min_p > 0 for r in reqs),
    ...)
困惑点 is_all_greedy 的判定是 top_k <= 1，不是 temperature == 0。为什么？因为贪心语义在参数归一化阶段就已经折算进去了：temperature=0 的请求会被改写成 top_k=1（见 sampling_params.py 的 normalize 逻辑）。所以 Sampler 只需要看一个条件。logit_bias 则不走这条路——它直接展开成 [batch, vocab_size] 的稠密张量，在前向 bias 阶段逐元素加上去。

惩罚类参数（frequency/presence/repetition/min_new_tokens）由一个可选的编排器统一管理。源码注释解释了为什么做成「总是创建、按需生效」：

python/sglang/srt/sampling/sampling_batch_info.py — penalizer_orchestrator 构造（摘录，注释为译注）

8.5grammar 约束生成：FSM 位掩码

当请求带 json_schema / regex 等 custom_params 时，TokenizerManager 会为它编译一个 grammar 对象。后端可插拔，注册表在 constrained/base_grammar_backend.py：

读懂这段： 三个内置后端对应三种 FSM 实现：xgrammar 是默认（编译快、内核级的 token mask），outlines 最老牌（保留了 jump-forward 优化——FSM 确定走的字符序列直接跳过采样，见 outlines_jump_forward.py 与 BaseGrammarObject.jump_and_retokenize，这是早期「跳过确定性前缀」路线留下的接口），llguidance 支持最复杂的语法。编译是异步的：请求先进 GrammarManager.grammar_queue，FSM 编好之前不进调度。

编译之前还有一道刚加上去的闸：constrained/json_schema_validation.py。有些 JSON Schema 关键字后端并不支持但也不报错——编译照常过，生成时才悄悄失效（比如 xgrammar 会无视 contains/uniqueItems/multipleOf）。这个模块在编译入口先扫一遍 schema（validate_xgrammar_json_schema / validate_outlines_json_schema，xgrammar_backend.py:349 与 outlines_backend.py:171 调用），碰到本后端保不住的关键字直接抛 UnsupportedJSONSchemaFeature，让请求在进入调度前就 400，而不是等用户拿到一份「不合法也没人告诉你」的输出。两个后端各自一张不支持清单，llguidance 没有——它语法覆盖最全，暂时不用这份体检。

编译期间的请求卡在 grammar 队列里，调度器每轮先放行已就绪的——这是 grammar 对调度准入的直接干预点：

真正施加约束的位置不在 Sampler 里，而在 ModelRunner._preprocess_logits——每一步前向之后、采样之前。掩码由 SamplingBatchInfo 生成并就地应用到 logits：

python/sglang/srt/sampling/sampling_batch_info.py — update_regex_vocab_mask / apply_logits_bias（摘录，注释为译注）
pythondef update_regex_vocab_mask(self):
    if not self.grammars:
        self.grammar_mask = None
        return

    # 同一 batch 共享一个掩码缓冲；未列出的行保持「不约束」
    first_grammar = next(grammar for grammar in self.grammars if grammar)
    vocab_mask = first_grammar.allocate_vocab_mask(
        vocab_size=self.vocab_size, batch_size=len(self.temperatures), device=self.device,
    )
    entries = [GrammarRow(row=row, grammar=grammar)
               for row, grammar in enumerate(self.grammars)
               if grammar and not grammar.finished and not grammar.is_terminated()]
    first_grammar.fill_vocab_mask_batched(entries, vocab_mask)
    vocab_mask = first_grammar.move_vocab_mask(vocab_mask, self.device)
    self.grammar_mask = GrammarMask(first_grammar, vocab_mask)

def apply_logits_bias(self, logits):
    self._apply_pre_grammar_logits_transforms(logits)   # logit_bias、自定义 processor
    if self.grammar_mask is not None:
        self.grammar_mask.apply(logits)                # 非法 token → -inf
    self._apply_post_grammar_logits_transforms(logits)
读懂这段： 一个 batch 里可以混装「有 grammar」和「没 grammar」的请求：掩码按行填，没 grammar 的行保持初始的「全放行」。应用之后掩码立即释放——ModelRunner._preprocess_logits 末尾有一行 sampling_info.grammar_mask = None，源码注释写明：overlap 调度下 sampling_info 会被 delay_sample 闭包多持有一步，不释放就是稳定的显存泄漏。这是结构化输出 + 重叠调度交叉处的一个真实事故痕迹。

8.6function call 解析：为什么在 serving 层

grammar 约束「让模型只能生成合法序列」，而 function call 解决另一个问题：各家模型把工具调用编码进普通文本（特殊标记 + JSON），需要把它解析回结构化的 tool_calls。这个解析器按模型分派：

        ...  # 共 39 个模型条目，多个模型共享同一 detector 类
    }
读懂这段： 39 个条目对应 35 个不同的 detector 类——同一家族的模型变体（glm/glm45、qwen/qwen25）共用实现，部分模型直接别名到别人的 detector（step3p5 → Qwen3CoderDetector）。每个 detector 实现两个入口：detect_and_parse（整段解析）和 parse_streaming_increment（流式增量解析——每收到一段新文本就尝试识别「调用开始了没有 / 参数写完了没有」，半截调用要缓冲到 SSE 下一帧）。这份枚举表本身就可以当「各家模型工具调用格式速查表」用。
为什么不在 Sampler 里做 采样器工作在 token id 空间，而工具调用的边界（比如 <tool_call> 标记、JSON 的完整闭合）是文本层的概念，和分词边界不对齐——一个标记可能被切成多个 token，半个 JSON 对象在 token 序列里无法判定合法性。所以解析只能等反分词之后按文本做，位置自然落在 entrypoints/openai/serving_chat.py（FunctionCallParser 在流式与非流式两个分支里分别构造）。代价是约束不「硬」：模型输出格式坏了，解析层只能尽力恢复或报错；要硬约束得靠 8.5 节的 grammar 路线。

8.7对「自研引擎」的启示

要点 三条可落地的结论。① 贪心 argmax 路径从第一天就要有：它是最常用的服务形态，且实现只是一个 kernel，跳过 softmax 和采样内核的开销在大 batch 下很可观。② 逐请求参数先归约再进 kernel：像 is_all_greedy / need_top_k_sampling 这样的 batch 级布尔标志，把「逐请求分支」变成「一次分支决策」，这是保持 GPU 利用率的基本功。③ 约束分两层想清楚：token 级硬约束（grammar 位掩码，逐 token 生效，注意与重叠调度的内存生命周期交互）和文本级软约束（工具调用解析，放在 serving 层）。做 OpenAI 兼容 API 时，前者可以后补，后者迟早要补。下一步进入 第 9 章：服务入口。
