投机解码：一次前向换多个 token

decode 阶段每生成一个 token 都要完整读一遍模型权重，瓶颈在显存带宽而不在算力。投机解码的思路是：用一个便宜的草稿器一次提出 k 个候选，再用目标模型的一次前向整批验证。这一章拆 SGLang 的实现：算法族、EAGLE worker 的结构、以及它怎么挂在第 2 章讲过的 overlap 调度上。

13.1一分钟版本

decode 慢的根源：batch 里每个序列每步只算一个 token，权重却要整份读一遍。算术强度（每次权重读取换来的浮点运算量）很低，GPU 的算力单元大部分在等数据。投机解码把「读一遍权重」的收益放大：

  • 草稿阶段：一个便宜的草稿器（小模型 / MTP 头 / n-gram 表）快速提出若干候选 token，按树或链组织。
  • 验证阶段：目标模型以 ForwardMode.TARGET_VERIFY 跑一次前向，把这 k 个候选当作 k 个输入位置一起算——这些位置共享同一次权重读取。
  • 接受阶段：逐位比较目标分布与草稿分布，做拒绝采样。数学上保证最终输出分布与直接用目标模型采样完全一致；接受多少发多少，从第一个不一致处截断。

收益由接受长度决定：平均每次验证接受 α 个 token，decode 就近似提速 α 倍（草稿开销摊进去之后）。SGLang 内置的算法装在一个枚举里（见 13.3），入口统一是 --speculative-algorithm，值用字符串传入、由 from_string 转成枚举或插件对象。

图 13.2：虚线是「拒绝」路径——验证分布与草稿不一致处之后的所有候选都作废，对应 KV 位置回收。接受是前缀式的：从第一个不匹配处截断，不存在跳过中间接受后面。
为什么分布不变： 拒绝采样按 min(1, p_target(x)/p_draft(x)) 的概率接受每个草稿 token；被拒时从修正后的残差分布里重新采一个。目标模型的 logits 是唯一事实来源，草稿只影响「提议什么」，不影响「输出什么分布」。

13.3算法族一览

所有算法共享同一套调度与验证框架（ForwardMode.TARGET_VERIFY + spec worker），差别只在「草稿从哪来」：

算法草稿从哪来额外权重何时选它
EAGLE-2EAGLE 草稿模型：拿目标模型倒数第二层特征做草稿，树状展开单独草稿权重兼容面最宽的默认选择；调 --speculative-num-steps / -eagle-topk / -num-draft-tokens

13.4EAGLE 在 SGLang 里的结构

调度器不认识 EAGLE。它只看到一个实现了 forward_batch_generation(batch, on_publish) 接口的 worker——普通模式这是 TpModelWorker，开投机后换成 EAGLEWorkerV2，内部包着「目标 worker + 草稿 worker」两个 TpModelWorker：

python/sglang/srt/speculative/eagle_worker_v2.py — EAGLEWorkerV2 构造（摘录，注释为译注）
pythonclass EAGLEWorkerV2(BaseSpecWorker):
    def __init__(self, server_args, gpu_id, ps, nccl_port, target_worker: TpModelWorker):
        ...
        self.topk = get_spec().speculative_eagle_topk
        self.speculative_num_steps = get_spec().speculative_num_steps
        self.speculative_num_draft_tokens = get_spec().speculative_num_draft_tokens
        self._target_worker = target_worker

        # 只有 PP 最后一级真的跑草稿；其余 rank 拿代理，保持各 rank 分发一致
        self._hosts_draft = get_pp_group().is_last_rank
        self._draft_worker = (
            EagleDraftWorker(server_args, gpu_id, ps, nccl_port, target_worker)
            if self._hosts_draft
            else None
        )
读懂这段： EagleDraftWorker（同文件 ~237 行）内部再起一个 TpModelWorker，只是 is_draft_worker=True——草稿模型复用整套 ModelRunner/注意力后端/CUDA Graph 机制，只是权重小、层数少。所以「草稿模型」在 SGLang 里不是一个特殊物种，是同一个执行框架的第二次实例化。

一次 decode 迭代在这个 worker 里的顺序是 draft → verify → draft_extend，publish 卡在 verify 结束的时点：

python/sglang/srt/speculative/eagle_worker_v2.py — forward_batch_generation 的 decode 分支（摘录，注释为译注）
pythondef forward_batch_generation(self, batch, on_publish=None, ...):
    if batch.forward_mode.is_extend() or batch.is_extend_in_batch:
        # prefill：目标模型算完就 publish，再让草稿模型做 draft_extend
        batch_output = self.target_worker.forward_batch_generation(...)
        if on_publish is not None:
            on_publish(batch_output.new_seq_lens)
        batch_output.next_draft_input = self.draft_worker._draft_extend_for_prefill(...)
        return batch_output
    else:
        # decode：先草稿，再验证
        verify_input: EagleVerifyInput = self.draft_worker.draft(batch)
        batch.spec_info = verify_input
        batch_output = self.verify(batch, grammar_barrier=grammar_barrier)
        # Publish before draft_extend so the fence is at verify-end.
        if on_publish is not None:
            on_publish(batch_output.new_seq_lens)
        ...  # draft_extend：草稿模型消化验证结果，为下一轮准备
读懂这段： draft()（~701 行）按 topk 逐层展开草稿树，输出 EagleVerifyInput；verify()（~1836 行）委托给 eagle_worker_common.py 的 run_eagle_verify。注意 publish 的位置——它在 verify 之后、draft_extend 之前，这个时点选择是 13.5 节 overlap 设计的关键。

验证的核心在 run_eagle_verify：准备 TARGET_VERIFY 批 → 目标模型一次前向 → 采样并统计接受长度：

python/sglang/srt/speculative/eagle_worker_common.py — run_eagle_verify（摘录，注释为译注）
pythondef run_eagle_verify(batch, *, target_worker, ...) -> GenerationBatchResult:
    # 验证批的准备放在独立的 plan stream 上，与草稿前沿重叠
    with plan_stream_ctx:
        verify_forward_batch, can_run_cuda_graph = eagle_prepare_for_verify(
            verify_input, req_to_token_pool, batch, target_worker,
        )

    # Run target verify batch in the main compute stream (GPU compute).
    forward_batch_output = target_worker.forward_batch_generation(
        batch=None,
        forward_batch=verify_forward_batch,
        is_verify=True,
    )

    # grammar 约束在树结构上生成词表掩码，再一起采样
    grammar_mask = None
    if batch.has_grammar:
        grammar_mask = build_grammar_vocab_mask(reqs=batch.reqs, tree=grammar_tree, ...)

    (predict, accept_lens, accept_index) = eagle_sample(
        verify_input, batch, logits_output, grammar_mask, ...)
读懂这段： accept_lens 是每个请求实际接受的 token 数，后续 new_seq_lens = batch.seq_lens + accept_lens 直接以它为准；未接受位置的 KV 会被回收（调用 clear_unaccepted_c128_draft_states，定义在 deepseek_v4_memory_pool.py，由 eagle_worker_common.py 用 getattr 探测式调用——所以是 DSV4 专用的一条路径，别的模型不会碰它）。验证批的 ForwardMode 在 eagle_prepare_for_verify 里被置为 ForwardMode.TARGET_VERIFY（eagle_utils.py:592），idle batch 则保持 IDLE。
演进痕迹 run_eagle_verify 的 docstring 写明：单层 EAGLE 的验证体是「事实来源（超集）」，多层 EAGLE 的历史行为差异靠两个开关（metadata_ready_pre_pad / finalize_tree_path）逐字保留。这是典型的收敛过程——先各自实现，后合并函数、用开关保住旧路径的数值行为。读这类代码时，开关本身就是在讲「哪些行为曾被观测到不同」。

13.5与 overlap 调度的配合（spec v2）

第 2 章讲过 overlap 调度：CPU 在 GPU 算上一批时准备下一批，中间靠 future_map 把「尚未算完的 token」占位。投机解码把一步拆成 draft/verify/draft_extend 三段，fence 的位置就得重新设计——这就是 spec v2。调度器把 on_publish 回调交给 worker，由 worker 决定在哪个时点宣布「这批的长度已定」：

python/sglang/srt/managers/scheduler.py — run_batch 的 spec 分支（摘录，注释为译注）
python# Spec_v2 fires on_publish mid-worker (between verify and draft_extend) so
# schedule prep can overlap with draft_extend. Non-spec has no later work.
fwd_kwargs = {}
if not batch.spec_algorithm.is_none():
    fwd_kwargs["on_publish"] = partial(self.future_map.publish, future_indices)
    if batch.spec_algorithm.supports_grammar_overlap():
        fwd_kwargs["grammar_barrier"] = self._advance_pending_grammar

batch_result = self.model_worker.forward_batch_generation(batch, **fwd_kwargs)
if batch.spec_algorithm.is_none():
    # 非投机：worker 返回后再 publish
    self.future_map.publish(future_indices, batch.seq_lens + 1)
读懂这段： 对比两种时序：非投机在 worker 返回后由调度器 publish（此时 GPU 侧已全部结束）；投机则在 verify 与 draft_extend 之间由 worker 主动 publish——schedule stream 上的下一批准备得以与 draft_extend 重叠。grammar_barrier 同理：让 grammar FSM 的推进也塞进这段空隙。

两个专用 ForwardMode 在 forward_batch_info.py 里紧挨着普通模式定义：

python/sglang/srt/model_executor/forward_batch_info.py — ForwardMode 中的投机项（摘录）
pythonclass ForwardMode(IntEnum):
    ...
    # Used in speculative decoding: verify a batch in the target model.
    TARGET_VERIFY = auto()
    # Used in speculative decoding: extend a batch in the draft model.
    DRAFT_EXTEND_V2 = auto()

读懂这段： TARGET_VERIFY 被归入 is_extend()（验证批的注意力形态与 prefill 同类：一次算多个位置），但它不进 prefill 调度，而是由 spec worker 在 decode 迭代内部构造。DRAFT_EXTEND_V2 的注释点出它的存在理由：给 EAGLE v2 worker 一个固定形状的 logits 输出，方便图捕获。

CUDA Graph 的约束也随之而来：草稿侧有自己的图 runner（eagle_draft_cuda_graph_runner.py / eagle_draft_extend_cuda_graph_runner.py），目标侧的验证批要按「bs × num_draft_tokens」的加宽形状捕获——这就是配置项 --speculative-num-draft-tokens 必须在启动时定死的原因之一。验证路径里也能看到对图边界的处理：update_verify_buffers_to_fill_after_draft 在草稿结束后回填 custom_mask/position 这类依赖草稿输出的元数据（eagle_worker_common.py:533）。

困惑点 草稿 KV 存在哪？答案是和目标模型共用同一套 req_to_token_pool 与 token_to_kv_pool_allocator——EagleDraftWorker.alloc_memory_pool（~307 行）接收的就是调度器传进来的同一对池子，只是草稿模型层数少、每层张量小。所以第 4 章讲的 PrefillAdder 预算公式里 max_new + page_size 的预留，在开投机后实际上还要覆盖草稿树的槽位（speculative_num_draft_tokens 是显式参与预算的）。

13.6MTP 与 NGRAM 简述

MTP：模型厂商随权重发布一个额外的预测头（DeepSeek-V3 的 MTP 层、Qwen 的 multi-token head）。它不是独立的第二个模型，而是目标模型的一个附加模块——草稿权重路径直接指向这些头。命令行上 DeepSeek 的惯用写法是 --speculative-algorithm NEXTN（代码里是 EAGLE 的保留别名），新一点的路径是 FROZEN_KV_MTP（验证时冻结目标 KV 的专用 worker，frozen_kv_mtp_worker_v2.py）。MTP 头与目标模型同源训练，接受率通常高于外挂小模型，代价是每层多一次头的前向。

NGRAM：连草稿模型都不要。从当前提示与已生成序列里建 n-gram 索引，decode 时查「上一个 token 之后历史上跟过什么」，把命中的片段展开成草稿树。零额外显存权重、零额外前向，适合输出高度可预期的负载——agentic 场景里反复出现的工具调用格式、代码编辑里的重复结构。代价明显：CUDA-only、不支持 dp-attention、禁 overlap 调度器与 mixed chunked prefill（与 DFLASH 同样的限制，见 13.3 节表格）。

两个极端放在一起看很清楚：草稿器的质量（接受长度）与它的开销（额外前向/显存/实现限制）是同一根轴的两端。EAGLE 系列在这根轴的中间，所以成了默认推荐。

13.7对「自研引擎」的启示

要点 投机解码不是采样器上的补丁，它会穿过你的引擎三层：调度器（验证批要按 num_draft_tokens 预留 KV 与图形状）、ForwardMode（TARGET_VERIFY / DRAFT_EXTEND）、采样（拒绝采样替换普通 argmax 路径）。SGLang 的切入方式值得照抄：① 新增 TARGET_VERIFY 模式，让验证批 ride 在既有 extend 机制上；② spec worker 实现与 TpModelWorker 相同的 forward_batch_generation(batch, on_publish) 接口，调度器零改动；③ 先测接受长度，再谈参数调优——平均接受长度不到 1.5 的负载上，投机解码大概率是负收益。另外留意 zero-step 分支（speculative_num_steps == 0，eagle_worker_v2.py:1461）：高并发时引擎会主动停掉草稿、只做验证，让草稿 KV 保持温热——这是「投机可动态开关」的实现雏形。本系列到这一章就走完了，返回索引可按路径重读。
演进痕迹 PP 与投机解码的组合刚刚打通（SGLANG_ENABLE_PP_SPEC，默认关）。冲突点在草稿模型的归所：lm_head 和末层 hidden states 只在最后一个 PP stage 上，所以草稿只能由最后一段做——非末段进程在 maybe_init_draft_worker 里直接不建 draft worker（scheduler.py:1029 附近），末段草稿完的树要走输出中继往回传。传的载体是 speculative/pp_spec_relay.py 的 PPSpecRelayInput：树按请求逐行挂在 ScheduleBatch.spec_info 上随批走，而不是放在旁路表里——因为 microbatch 会重组（请求完成/被收回/并批），树必须跟着它所属的请求行一起过滤、合并、迁移，各 stage 才能重建出同一份验证输入。验证输入在中间 stage 不重新草拟，直接用上一轮中继来的 batch.spec_info（eagle_worker_v2.py:1456 的注释写得很直白：必须与前面 stage 已跑的一致）。当前约束不少：要求 --disable-overlap-schedule、只支持单层 EAGLE 系草稿、不兼容 PD 分离与 dp-attention——实验开关而非默认路径，但它把「草稿模型住哪」这个 PP×spec 的根本问题给出了可复用的答案。
