HiCache：KV cache 出了 GPU 之后放哪

第 3 章的 RadixCache 只把前缀留在显存里，节点一被逐出，KV 就没了。HiCache 给每个树节点补上两层去处：主机内存（L2）和分布式存储（L3）。这一章看它的树结构怎么改、数据怎么搬、策略怎么配。

11.1一分钟版本

前缀缓存的价值取决于能留住多少前缀。显存就那么大：一个 32K 上下文的请求，一次 prefill 就要吃掉几十 GB 的 KV 池空间；多轮对话、few-shot、共享 system prompt 的负载下，HBM 很快装不下值得复用的前缀，RadixCache 只能不断逐出。

HiCache 的做法是借 CPU 缓存的层级设计，把 KV 数据放到三层（官方设计文档 docs/docs/advanced_features/hicache_design.mdx 的原话：GPU 是 L1、host memory 是 L2、分布式存储是 L3）：

  • L1 · GPU 显存：就是第 3 章的 RadixCache.value，容量最小、读写最快，每实例私有。
  • L2 · 主机内存（DRAM）：每个节点多了 host_value——一段指向 host KV 池的索引。L1 逐出前先备份到这里，容量约是 L1 的 hicache_ratio 倍（默认 2.0），每实例私有。
  • L3 · 存储后端：以页哈希为键写入外部存储（file、mooncake、hf3fs、nixl、aibrix……）。键是内容寻址的，所以集群里多个实例天然共享同一份前缀。

对应到树结构上：L1 命中走老路（value 里的 device 索引直接用）；L1 未命中但 L2 有备份（node.backuped）就先 load back 拉回显存；L2 也没有，就看 L3 是否存过这个前缀的页，命中则 prefetch 到 L2 再 load back。写方向对称：新算出的 KV 先备份到 L2（write-through），再按策略落到 L3。

11.2三层结构与数据流

L1 · GPU（设备池） L2 · 主机（host 池） L3 · 存储后端
图 11.2：三层缓存与传输路径。L1↔L2 是拷贝关系（同一节点在两层各有索引），L2↔L3 以页哈希为键；向下写、向上读，虚线是 prefetch 未命中后的重试。注意 L2 不跨实例共享——同机两个进程的 L2 是各存各的，跨实例复用只能经 L3。

重要前提

HiCache 的树实现只剩一个了。HiRadixCache——那个独立的 2034 行文件 hiradix_cache.py——在 commit 4ce23542bf（#40787，2026-09-24）中被整体删除。自 commit 44806dc507（2026-08-21，"Using unified radix tree by default for all case"）统一树成为默认后，它已经没有任何构造函数调用点，删除是收尾而非重构。本章引用的每一行代码，取的都是实际执行的那条路径：mem_cache/registry.py 的 create_unified_radix_cache() 构造 UnifiedRadixCache(params)（registry.py，签名里留了 cache_class 覆盖口，供 MLX 等 backend 注入自己的组件注册表），并在 enable_hierarchical_cache 或 disaggregation_decode_retraction_backup == "host_pool" 时调用 cache.init_hicache(server_args, params) 把 HiCache 挂上去（registry.py）。

结构上它比被删的前身多一层间接：mem_cache/unified_cache/ 包把「树骨架」和「各组件的数据」拆开——unified_tree_core.py（树核心，节点以整数 NodeId 索引）、components/base.py（组件数据与行为基类）、unified_cache_linker.py（外接缓存链接器，--enable-unified-cache-external-linker，后端可选 mooncake / mori）、storage_attachment.py（L3 存储的运行时挂载）。关键变化在节点结构：分层状态不再是一批散在 TreeNode 上的字段，而是每个组件一份的 ComponentData——这正是 hybrid 模型（全注意力 KV + SWA/Mamba 状态）需要的形状：同一个节点上，FULL 组件在 L1/L2 各有索引，Mamba 状态组件有自己独立的备份生命周期。下一节展开这个结构。

11.3树上的分层状态：UnifiedTreeNode 与 ComponentData

统一树的骨架仍是第 3 章那棵基数树，但「树骨架由谁执行」最近换了一次底座：树核心（TreeCore）本身成了可插拔件，注册表在 tree_core_registry.py，默认后端是 Rust（SGLANG_UNIFIED_RADIX_TREE_CORE_BACKEND，environ.py，EnvStr("rust")）。Rust 实现落在 rust/sglang-radix-tree（独立的 Cargo 工程经 rust_extensions 装载），Python 侧的 unified_tree_core.py 降级为兼容后端。选型是「默认 rust、条件不满足就静默回退」：_rust_fallback_reason（tree_core_registry.py）列出一串硬条件——session-aware 缓存要 Python、组件集超出 FULL/SWA/Mamba 之外的要 Python、自定义组件注册表要 Python、非 Linux 要 Python、PyTorch 版本超出支持区间要 Python、非 cpu/cuda 设备要 Python——命中任何一条就回落 Python 并记一条日志。对本书读者这意味着：树骨架的遍历、匹配、逐出代码有两份实现，本章引用的 unified_tree_core.py 是 Python 兼容路径，但两边遵守同一个接口（UnifiedTreeCoreInterface），上层统一缓存看不出区别。本章其余引用的源码段落仍以 Python 实现为准——它是审读语义时最可读的一份。

骨架的「数据在哪一层」状态换了住处：UnifiedTreeNode（unified_tree_core.py）自己只挂树骨架字段（children/parent/key/hash_value/priority）加上跨组件共享的登记项（write_through_pending_id、load_back_pending_id、rotation_base）；每个节点带一个按组件类型索引的数组 component_data，分层状态全部长在组件数据里：

一个节点，每组件三种状态： 判断走组件的派生属性（UnifiedTreeNode 上，unified_tree_core.py 起）：backuped 看 FULL 组件的 host_value 是否在（「Tree-level: Full KV present on host」），evicted 看 FULL 组件的 value 是否没了。于是每个节点、每个组件都有三种状态组合：value 在（L1 在）、value 没了但 host_value 在（L1 逐出、L2 兜底）、两边都没了（只剩 L3 的页哈希还在）。

两套哈希值：hash_value 是「每一页一个哈希」的列表，是 L3 存储的主键；event_hash_value 是另一套按事件算的哈希，给外接缓存链接器（--enable-unified-cache-external-linker）用。同一个节点上并存两套，是因为它们服务两种不同的消费者，而不是新旧替换关系。另外注意 priority：树骨架字段，第 3 章的淘汰顺序里就在用；根节点初始化 -sys.maxsize（unified_tree_core.py）——保证根永远排在任何真实节点后面，是「不要先动树根」的一个廉价实现。

SWA/Mamba 混排时这个结构的价值才显出来：FULL 和 SWA 组件各自有 host_value、各自的 host 锁，Mamba 状态甚至有自己的备份节奏——「KV 已备份、状态还没落」可以是合法中间态，而不是一场事故。

前缀匹配的返回值也由组件接力。树的骨架匹配（UnifiedRadixCache.match_prefix，unified_radix_cache.py）只走 tree_core.match_prefix(params)，随后每个组件调 finalize_match_result_in_cache 补自己的部分——FULL 组件在这一步算出 host_hit_length：

python/sglang/srt/mem_cache/unified_cache/components/full.py — FULL 组件的 match 收尾（摘录，注释为译注）
python    def finalize_match_result_in_tree_core(self, result, params,
                                            value_chunks, best_value_len):
        # Compute Full KV host hit length: walk from last_host_node up to
        # last_device_node, summing host_value lengths of evicted nodes.
        ct = self.component_type
        kv_host_hit = 0
        node = result.best_match_node
        root_node = self.tree_core.root_node
        while node is not result.last_device_node and node is not root_node:
            full_host = node.component_data[ct].host_value
            if full_host is not None:
                kv_host_hit += len(full_host)
            node = node.parent
        if kv_host_hit > 0:
            return result._replace(
                host_hit_length=max(result.host_hit_length, kv_host_hit)
            )
        return result
困惑点 host_hit_length 是 HiCache 版 MatchResult 独有的字段，普通 RadixCache 永远返回 0。它表示「匹配到的这段前缀当前不在显存、但在 L2 有备份」的 token 数。调度器拿到它之后，这段前缀按「待拉回」而不是「待重算」计价（init_load_back 的门就是 host_hit_length > 0，unified_radix_cache.py 起）——这就是 HiCache 相比普通前缀缓存省下的那部分 prefill。

host 池（L2 的物理内存）不再是构造函数里 if-elif 四选一，而是装配时选型。统一路径由 hybrid_cache/hybrid_pool_assembler.py 装配 host 池：MLA 走 MLATokenToKVPoolHost，MHA 走 get_mha_host_pool_cls（mha.py）做三选一：设备池是 MXFP8（块缩放量化）→ MHATokenToKVPoolMXFP8Host——host 池必须连每页的 UE8M0 缩放块一起搬，所以单独一个类（pool_host/mha_mxfp8.py）；K/V head_dim 不对称 → AsymmetricMHATokenToKVPoolHost；否则默认 MHATokenToKVPoolHost。全部就位后 init_hicache（unified_radix_cache.py）把 controller 挂上树核心，顺手打开 HiCache 使能标志。树侧的事到此说完了；剩下的传输模型和被删的前身完全一致，下一节直接看 controller。

四本在途账： 实例上挂着四个记录在途操作的字典（构造函数里，unified_radix_cache.py）：ongoing_write_through（D2H 备份中）、ongoing_load_back（H2D 拉回中）、ongoing_prefetch（L3 预取中，按 CacheRequestHandle 键控）、ongoing_backup（L2→L3 落盘中，按 operation_id 键）。HiCache 的树操作大多是「先记账、异步搬运、事后对账」，这四个字典就是对账的账本。

11.4传输路径：HiCacheController

L1 和 L2 之间的搬运由 HiCacheController（注意：在 managers/cache_controller.py，不在 mem_cache/ 下）完成。它的模型很朴素：两个队列 + 两个后台线程。write 先在 host 池里分配槽位再入队，load 反过来先在 device 池分配：

python/sglang/srt/managers/cache_controller.py — HiCacheController.write / load（摘录，合并了两个方法，注释保留原文）
python    def write(self, device_indices, priority=None, node_id=-1, extra_pools=None):
        """
        Back up KV caches from device memory to host memory.
        """
        if extra_pools:
            raise ValueError("Side-pool transfers require HybridCacheController.")
        host_indices = self.mem_pool_host.alloc(len(device_indices))
        if host_indices is None:
            return None
        self.write_queue.append(
            CacheOperation(host_indices, device_indices, node_id, priority)
        )
        self.start_writing()
        return host_indices

    def load(self, host_indices, priority=None, node_id=-1):
        """
        Load KV caches from host memory to device memory.
        """
        device_indices = self.mem_pool_device_allocator.alloc(len(host_indices))
        if device_indices is None:
            return None
        self.load_queue.append(
            CacheOperation(host_indices, device_indices, node_id, priority)
        )
        return device_indices
三个要点： 先说先分配后搬运：host/device 两边的槽位都在入队前就占好，传输失败不会留下半截状态。再说页对齐：所有索引按 page_size 对齐，传输以页为单位（host 池的 page_num 就是按页算的）。最后是分层计数器：构造函数里 LayerDoneCounter(self.transfer_layer_id_max) 注册到 device 池（这个字段以前叫 layer_num，commit 9f3d275940 改名——见本节末尾的演进痕迹）——KV 池是逐层布局的，D2H 拷贝按层推进，每层完成都计数，TP 组内各 rank 再对齐进度，保证多卡间备份进度一致。extra_pools 参数是新签名里唯一的新面孔：主 KV 之外还有 side pool（辅助池）要一起搬时，调用方会把 PoolTransfer 列表传进来；基类不认它，直接 raise 指路 HybridCacheController——「主池 + 辅助池」的传输只有混合控制器会做，接口按能力显式分家。
IO 后端有三种：kernel（默认；把索引搬到 GPU，用 CUDA kernel 逐层拷贝）、direct（CPU 直接按索引读写 pinned 内存），以及 kernel_ascend（华为 NPU 路径）。arg_groups/hicache_hook.py 的 resolve_layout_io_compatibility 里能看到组合约束：page_first 布局配 direct 后端时会被自动切换布局——这两个开关是联动的，不是独立的。
NPU 路径上的一处分叉： kernel_ascend 里还套着一层判断。融合的 acc_offload 换入换出 kernel 直接在设备上读 token 索引，索引就保持在设备上；而遗留的 memcpy2d 换入换出算子需要 CPU 索引，由它自己转换。前者额外走一步 pinned memory 上传——源码注释解释了原因：host_indices 来自基数树匹配，是一个可分页的 CPU 张量，而可分页张量的 .to(device) 会带一次 stream synchronize，把当前（默认）stream 上排队的全部计算都排干。一次多余的同步就足以让整个按层分组的流水线退化成串行，所以要显式绕开。
困惑点 write 的返回值是 host 索引，load 的返回值是 device 索引，但两者都不代表「数据已经搬完」——入队只代表搬运已受理。真正的完成事件由后台线程写入完成队列，再由 check_hicache_events（11.5 节）在调度循环里收割。树上节点状态（backuped 等）只在收割之后才更新，这也是为什么调度器必须每轮显式调用一次对账。

11.5预取与回写策略

这里有一处容易看漏的次序：预取阶段不分配 host 槽位。prefetch_from_storage 只登记「要取哪些 token」（PoolTransfer(host_indices=None)），KV staging 的 alloc 延后到命中时才做——源码注释 "Size the component's staging now; it is allocated at hit time, next to the KV staging, so the query holds no host memory"（unified_radix_cache.py 附近）。原因是预取是乐观的：三级存储里可能只有一部分真的存在，提前按 prefetch_length 全额占位会浪费 host 池；等 L3 命中数确定后，_drain_and_alloc_storage_hit()（unified_radix_cache.py）按实际命中长度分配，只付真正拿到的那部分。等不了那么久也有退出机制：hicache_storage_prefetch_policy 支持 best_effort（随时可放弃）、wait_complete（死等）、timeout（按传输量线性放宽的超时）：

            time.monotonic() - operation.start_time
            > self.prefetch_timeout_base
            + len(operation.hash_value) * self.prefetch_timeout_per_page
        )

回写（L1→L2→L3）由 --hicache-write-policy 控制，三种策略：

策略行为适用
write_through（默认）每个新 KV 一算完就备份到 L2（阈值 write_through_threshold = 1）带宽充裕，追求最大缓存收益
write_through_selective访问次数超过阈值（2）才备份，只留热数据降低 I/O，牺牲部分命中率
write_back平时不写，L1 逐出时才落 L2存储带宽紧张、要榨干内存利用率

write-through 路径有一个必须满足的不变量。统一树把它从「父没备份就跳过」改成了更主动的形状：备份一个节点时，把从它向上到第一个已备份祖先之间的整条链一起备份：

python/sglang/srt/mem_cache/unified_cache/unified_tree_core.py — _build_backup_kv_action（摘录，注释保留原文）
python    def _build_backup_kv_action(
        self, node: UnifiedTreeNode, write_back: bool = False
    ) -> BackupKV:
        """Build the backup action for a node; write-through also chains its
        unbacked ancestors."""
        chain = [node]
        if not write_back:
            ancestor = node.parent
            while (
                ancestor is not None
                and ancestor is not self.root_node
                and not ancestor.backuped
                and not ancestor.external_cache_stored
                and (
                    not self.enable_external_cache_linker
                    or ancestor.write_through_pending_id is None
                )
            ):
                chain.append(ancestor)
                ancestor = ancestor.parent
            # write_through: Ancestors first to preserve backup invariant
            chain.reverse()
        return BackupKV([target.id for target in chain])
备份不变量： L2 上的备份必须从根开始连续。旧实现遇父未备份就放弃子节点的备份；统一实现改成补齐整条链再从根往下执行（chain.reverse() 的注释原话 "Ancestors first to preserve backup invariant"），cache 侧 _execute_and_commit_kv_backup 按 "top-down, stopping at the first failed backup" 逐个执行（unified_radix_cache.py）——链上有空洞时，空洞自己被补上，而不是让子节点一直等。原因没变：预取锚点从匹配终点向上走的是「找第一个已备份节点」这条链，中间有洞，L3 的页哈希链就对不上。为什么统一树有底气补链？因为备份动作不再内联在热路径里，而是作为 BackupKV 动作排队执行——in-flight 的搬运与节点分裂的对账由 _replace_pending_write_through_node 单独处理。

调度侧与 HiCache 的交接点收敛在 _process_hicache_events（scheduler.py）：每轮调度先调 self.tree_cache.check_hicache_events()（scheduler.py）收割写备份/加载/预取的完成事件，再调 _process_storage_prefetch_retries() 对上一轮未命中的预取按轮次间隔重发，重试次数由 hicache_storage_prefetch_retry_max_attempts 封顶。收割入口有个 TP 共识的讲究，注释写在函数开头：「The HiCache drain is TP-wide consensus; run it before rank-local decisions」——必须赶在 rank 各自做本地决策（比如 _should_defer_prefill）之前，否则各 rank 进入不同的集合通信，直接挂死。

演进痕迹 两个正在被替换的旧设计值得留意。其一，write_back 模式要求逐出时同步搬运，把 I/O 塞进了调度关键路径，是三层模型里最别扭的一条路——统一树把它改写成「延迟降级」（deferred demote）：逐出时只产出 BackupKV 动作，cache 侧执行完备份再 demote 掉设备副本（backup_node_for_write_back 的 docstring，unified_radix_cache.py）。其二，存储接口正从 v1（_generic_page_get，标着「todo: deprecate」，用 dummy page 中转）迁往 v2 的零拷贝字节接口（batch_exists_v2 / batch_get_v2 / batch_set_v2）——L3 后端越来越多，接口必须收敛到「不关心页对象、只搬字节」。
演进痕迹 两处针对存储 I/O 的修补也在这条交接线上。其一，调度器空闲分支（没有可跑的 GPU batch 时）会检查 enable_hicache_storage，是就 time.sleep(0) 让出一次 GIL（scheduler.py 附近）——存储 worker 的 I/O 调用之间需要 GIL，死循环轮询会饿死它们的 ack 回传，一次显式让步换来事件及时收割。其二，mooncake 后端的 SSD 卸载目录改为按 rank 分子目录（ssd_offload_path/rank_{dp}_{tp}_{pp}_{attn_cp}）：bucket id 是每进程独立生成、重启后从同一起点续扫的，bucket 文件又以 O_CREAT|O_TRUNC 打开——多个 rank 共享一个卸载目录时，文件名撞上就会截断别的 rank 正在写的 bucket，静默产坏页。每个 rank 一个私有子目录后，路径不再交叉。
演进痕迹 MHA host 池的容量语义最近修正过一次（commit 5d703de9e4，#40304）：池子按「token 槽位」建，但一个 token 槽位在 host 侧要装的可能是多行注意力数据——池宽 head_num = device_pool.row_dim // device_pool.head_dim（mha.py 起的两行注释与赋值）。此前 host 池只按设备池的 K/V head_dim 定宽，遇到设备池一行里并排多个注意力行（row_dim > head_dim）的布局，host 镜像就装不下完整的一行。顺带同一次改动里，get_hybrid_pool_buffer() 开始把 K/V 的 host 张量直接暴露出来，供零拷贝 I/O 注册。另外上一段的空闲让步条件本身也拓宽了：enable_hicache_storage or disaggregation_mode != NULL 才 time.sleep(0)——PD 模式的传输 worker 同样需要 GIL 让步，源码注释写明 "Storage and transfer workers need the GIL between I/O calls"。只看 HiCache 的读者可以忽略这半句，但它解释了为什么这个条件长在通用调度循环上。
演进痕迹 host 池的大小最近从「拍脑袋比例」走向「按机器实测定容」（commit 7a6c652c77，#40135）。以前的规则是固定比例：--hicache-ratio 默认 2.0（cache 模式）/ 1.2（buffer_only 模式），host 池 = 设备池 × 比例——设备池大一点 host 内存就可能被打爆。现在多了一个 --hicache-host-memory-fraction（默认 0.8）：只在用户没有显式给 ratio 或 --hicache-size 时生效，启动时按「本机可用内存（以 cgroup 的 memory.max/memory.high 为上界，扣掉 10 GiB 预留）× fraction」算预算，把默认比例往下压到刚好放得下（hicache_auto_size.py 的 auto_size_hicache：预算 ÷ 设备侧字节数，再扣 5% 给页对齐和分配器元数据的 slack），并在 TP/PP 组内做一次 all-reduce 取最小——各 rank 的池子结构不同（PP 各 stage 池数不一样），必须全体取最小才能都放得下，注释还特意说明这一锤子买卖要在任何池子构建之前做，不然按池逐次集合通信会死锁。多个引擎共居一个 cgroup 时把 fraction 调小即可。显式给了 ratio/size 则自动定容直接关闭，行为回到从前。
演进痕迹 hybrid 模型的传输层编号也修正过一次语义（commit 9f3d275940，#37870）。cache_controller.py 里计数器的构造参数从 layer_num 改名 transfer_layer_id_max——名字变了的背后是语义收紧：对 hybrid 模型（KV 层 + Mamba 层混排），传输层 ID 要覆盖所有组件池的编号空间，包括「不吃缓存、在传输布局里挖了洞」的层；锚点池自己报的层数描述不了这些洞。旧名 layer_num 让人以为它等于模型层数，sparse 布局下两层 ID 之间可以跳号，hybrid_cache_controller.py 的注释原话："Hybrid transfer IDs span every component pool, including holes for uncached layers"。分层计数器本身没变，变的只是「数到几」。
演进痕迹 延迟降级最近补了一个它当初没覆盖的角落：内部节点的 Mamba 状态（commit 6f4c2b9b91，#40680）。背景在 11.3 节讲过——匹配验证器只放行「某层上还持有状态」的节点；对叶子，统一树的逐出走延迟降级（先产出 BackupKV、备份完再 demote），设备上的状态不会凭空消失。但 Mamba 组件的设备逐出遇到内部节点时会做「状态墓碑」（tombstone）：把该节点的状态从组件层抹掉、树继续向下逐出。修复前的墓碑是凭空的——设备上的状态直接消失，L2 上没有对应物。后果在 docstring 里讲得很直白："a dropped internal state caps the match frontier at this node forever, leaving the subtree's still-resident KV unservable"：下一个请求匹配到这里，发现「状态没了」，匹配终点被永久卡在这个节点，而它子树里明明还留着的 KV 全都服务不了——一个组件的墓碑，报废了整棵子树的缓存。修法后来被一个更一般的协议收编（commit 77091cea68，#39627）：组件逐出内部节点不再自带备份动作，而是返回一个暂停请求 InternalStateBackup（base.py，就两个字段：node_id 加 host 容量需求 num_tokens）——Mamba 组件的逐出在需要备份时 return InternalStateBackup(node_id=x.id, num_tokens=1)（mamba.py），SWA 组件同款。树核心收到后把这颗节点记进 _pending_internal_evictions 暂停逐出（unified_tree_core.py），由统一缓存来兑现：_evict_device_next_node（unified_radix_cache.py 起）看到 mamba_backup_node_id 就先给 host 池腾位（available_size() < 1 时 evict_host(1, MAMBA)）、调 backup_node_for_write_back 把状态真正搬下去，再调 finish_mamba_state_eviction 让树核心恢复逐出（SWA 走 finish_swa_state_eviction，且要为整个未备份窗口 swa_backup_num_tokens 一次腾够）。这是一个 best-effort 兜底——host 分配失败逐出照样推进（注释原话 "eviction still proceeds to make room on the device"），保住进度优先于保住缓存。又是那个熟悉的形状：三类组件各自有备份生命周期（11.3 节的「四本在途账」），墓碑这种「树骨架记了、组件数据没了」的裂缝，最初只有组件自己的逐出器知道怎么补，#39627 把它升格成树核心与组件之间的正式契约——组件声明「这里要暂停」，暂停后怎么继续（finish_*）由树核心统一管。

共享语义是这一节最需要记住的事实（设计文档原文要点）：L1、L2 都是实例私有——同一台机器上跑两个 SGLang 进程，它们的 L2 各是各的，互不共享；只有 L3 按后端配置决定共享范围。所以「同机多实例去重」必须走 L3，L2 再大也只帮本实例。

多 rank 一致性由两件事保证。其一，L3 的键是逐页哈希（内容寻址），两棵树算出同样的页序列就指向同样的键，天然去重；其二，TP 组内预取前要先对存储命中页数做一次 all-reduce 取最小值（prefetch_thread_func 里的 ReduceOp.MIN）——各 rank 命中数不一致时按最少者对齐，保证所有 rank 拉回同一长度。文件后端还按 rank 拆键，避免多 rank 写同一个文件：

11.7对「自研引擎」的启示

要点 三层缓存的复杂度主要不在「多存两份数据」，而在每层索引的对账：一个前缀段在 L1/L2/L3 各有一份索引（device 索引、host 索引、页哈希），树上任何一个节点拆分、合并、逐出，三份索引都得跟着对——ongoing_write_through 的 replace 逻辑（_replace_pending_write_through_node）就是为「搬运在途时节点被拆了」存在的。如果你只想低成本拿到八成收益：先做 L2 备份，它给 decode 抢占（retraction）提供了现成的落点，被逐出的请求可以直接从 L2 拉回而不是重新 prefill；L3 只在多个实例共享存储、且前缀重复率高时才划算。下一步进入 第 12 章：PD 分离部署。
