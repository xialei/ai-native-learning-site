HiCache：KV cache 出了 GPU 之后放哪

第 3 章的 RadixCache 只把前缀留在显存里，节点一被逐出，KV 就没了。HiCache 给每个树节点补上两层去处：主机内存（L2）和分布式存储（L3）。这一章看它的树结构怎么改、数据怎么搬、策略怎么配。

11.1一分钟版本

前缀缓存的价值取决于能留住多少前缀。显存就那么大：一个 32K 上下文的请求，一次 prefill 就要吃掉几十 GB 的 KV 池空间；多轮对话、few-shot、共享 system prompt 的负载下，HBM 很快装不下值得复用的前缀，RadixCache 只能不断逐出。

HiCache 的做法是借 CPU 缓存的层级设计，把 KV 数据放到三层（官方设计文档 docs/docs/advanced_features/hicache_design.mdx 的原话：GPU 是 L1、host memory 是 L2、分布式存储是 L3）：

  • L1 · GPU 显存：就是第 3 章的 RadixCache.value，容量最小、读写最快，每实例私有。
  • L2 · 主机内存（DRAM）：每个节点多了 host_value——一段指向 host KV 池的索引。L1 逐出前先备份到这里，容量约是 L1 的 hicache_ratio 倍（默认 2.0），每实例私有。
  • L3 · 存储后端：以页哈希为键写入外部存储（file、mooncake、hf3fs、nixl、aibrix……）。键是内容寻址的，所以集群里多个实例天然共享同一份前缀。

对应到树结构上：L1 命中走老路（value 里的 device 索引直接用）；L1 未命中但 L2 有备份（node.backuped）就先 load back 拉回显存；L2 也没有，就看 L3 是否存过这个前缀的页，命中则 prefetch 到 L2 再 load back。写方向对称：新算出的 KV 先备份到 L2（write-through），再按策略落到 L3。

11.2三层结构与数据流

L1 · GPU（设备池） L2 · 主机（host 池） L3 · 存储后端
图 11.2：三层缓存与传输路径。L1↔L2 是拷贝关系（同一节点在两层各有索引），L2↔L3 以页哈希为键；向下写、向上读，虚线是 prefetch 未命中后的重试。注意 L2 不跨实例共享——同机两个进程的 L2 是各存各的，跨实例复用只能经 L3。
关键映射（按目录）： python/sglang/srt/mem_cache/hiradix_cache.py → HiRadixCache（树 + 各层状态机）； python/sglang/srt/managers/cache_controller.py → HiCacheController（L1↔L2/L3 传输）； python/sglang/srt/mem_cache/pool_host/ → host KV 池（L2 的物理内存）； python/sglang/srt/mem_cache/storage/ → L3 后端实现与工厂。
重要前提

本章的代码摘录取自 hiradix_cache.py——但今天默认跑的已经不是它了。自 commit 44806dc507（2026-08-21，"Using unified radix tree by default for all case"）起，mem_cache/registry.py 的选择链末路改为 _create_unified_radix_cache()：它构造 UnifiedRadixCache(params)，随后在 enable_hierarchical_cache 或 disaggregation_decode_retraction_backup == "host_pool" 时调用 cache.init_hicache(server_args, params) 把 HiCache 挂上去（registry.py:146, 192-195）。在 python/sglang/ 下，HiRadixCache 已经没有任何构造函数调用点（只剩测试与混合池装配处的类型标注）。

两者概念同源、命名不同：write_through_threshold、match_prefix、prefetch_from_storage、_prefetch_timeout_check_linear_func、write_backup_storage 在 unified_radix_cache.py（3610 行）里各有一份对应实现，而 hiradix_cache.py 是 2034 行。统一路径多出来的东西集中在 mem_cache/unified_cache/ 这个包：unified_tree_core.py（树核心抽象）、unified_cache_linker.py、tree_core_registry.py、storage_attachment.py、component_type.py——一套「树核心 + 多种组件（FULL / SWA / MAMBA / C128）」的插拔结构，外加 --enable-unified-cache-external-linker 这条外接缓存链接器入口（后端可选 mooncake / mori）。

为什么这一章仍按 HiRadixCache 讲：它是这个概念最小、最完整的形态——三层状态机、锁引用、预取/回写策略在 2034 行里能一次读完，而统一树的对应部分散在多个文件、还叠着组件注册与链接器两层间接。先读懂这里，再去读 unified_radix_cache.py 就是找对应关系，而不是重新理解一遍。代价是：本章代码里出现的行号与调用点，在默认配置下未必是实际执行的那条路径。

11.3树上的分层状态：HiRadixCache 与 TreeNode

HiRadixCache 直接继承第 3 章的 RadixCache，树形、锁引用、淘汰顺序全部沿用；它新增的是每个节点的「数据在哪一层」状态。先看 TreeNode 补的字段：

一个节点，三种状态： 一个节点现在有三种状态组合：value 有值（L1 在）、value 没了但 host_value 在（L1 逐出、L2 兜底）、host_value 也没了但页哈希还在（只剩 L3 的可能）。

两套哈希值：hash_value 是「每一页一个哈希」的列表，是 L3 存储的主键；event_hash_value 是另一套按事件算的哈希，给外接缓存链接器（--enable-unified-cache-external-linker）用。同一个节点上并存两套，是因为它们服务两种不同的消费者，而不是新旧替换关系。另外注意 priority：它不是 HiCache 独有的字段，第 3 章的淘汰顺序里就在用（eviction_strategy.get_priority），只是在这里一并列出来；根节点那个 -sys.maxsize 的初始化值得记一下——保证根永远排在任何真实节点后面，是「不要先动树根」的一个廉价实现。

困惑点 host_hit_length 是 HiCache 版 MatchResult 独有的字段，普通 RadixCache 永远返回 0。它表示「匹配到的这段前缀当前不在显存、但在 L2 有备份」的 token 数。调度器拿到它之后，这段前缀按「待拉回」而不是「待重算」计价（见 11.5 节调度侧的接线）——这就是 HiCache 相比普通前缀缓存省下的那部分 prefill。

11.4传输路径：HiCacheController

L1 和 L2 之间的搬运由 HiCacheController（注意：在 managers/cache_controller.py，不在 mem_cache/ 下）完成。它的模型很朴素：两个队列 + 两个后台线程。write 先在 host 池里分配槽位再入队，load 反过来先在 device 池分配：

python/sglang/srt/managers/cache_controller.py — HiCacheController.write / load（摘录，合并了两个方法，注释保留原文）
python    def write(self, device_indices, priority=None, node_id=-1):
        """
        Back up KV caches from device memory to host memory.
        """
        host_indices = self.mem_pool_host.alloc(len(device_indices))
        if host_indices is None:
            return None
        self.write_queue.append(
            CacheOperation(host_indices, device_indices, node_id, priority)
        )
        self.start_writing()
        return host_indices

    def load(self, host_indices, priority=None, node_id=-1):
        """
        Load KV caches from host memory to device memory.
        """
        device_indices = self.mem_pool_device_allocator.alloc(len(host_indices))
        if device_indices is None:
            return None
        self.load_queue.append(
            CacheOperation(host_indices, device_indices, node_id, priority)
        )
        return device_indices
三个要点： 先说先分配后搬运：host/device 两边的槽位都在入队前就占好，传输失败不会留下半截状态。再说页对齐：所有索引按 page_size 对齐，传输以页为单位（host 池的 page_num 就是按页算的）。最后是分层计数器：构造函数里 LayerDoneCounter(self.transfer_layer_id_max) 注册到 device 池（这个字段以前叫 layer_num，commit 9f3d275940 改名——见本节末尾的演进痕迹）——KV 池是逐层布局的，D2H 拷贝按层推进，每层完成都计数，TP 组内各 rank 再对齐进度，保证多卡间备份进度一致。
IO 后端有三种：kernel（默认；把索引搬到 GPU，用 CUDA kernel 逐层拷贝）、direct（CPU 直接按索引读写 pinned 内存），以及 kernel_ascend（华为 NPU 路径）。arg_groups/hicache_hook.py 的 resolve_layout_io_compatibility 里能看到组合约束：page_first 布局配 direct 后端时会被自动切换布局——这两个开关是联动的，不是独立的。
NPU 路径上的一处分叉： kernel_ascend 里还套着一层判断。融合的 acc_offload 换入换出 kernel 直接在设备上读 token 索引，索引就保持在设备上；而遗留的 memcpy2d 换入换出算子需要 CPU 索引，由它自己转换。前者额外走一步 pinned memory 上传——源码注释解释了原因：host_indices 来自基数树匹配，是一个可分页的 CPU 张量，而可分页张量的 .to(device) 会带一次 stream synchronize，把当前（默认）stream 上排队的全部计算都排干。一次多余的同步就足以让整个按层分组的流水线退化成串行，所以要显式绕开。
困惑点 write 的返回值是 host 索引，load 的返回值是 device 索引，但两者都不代表「数据已经搬完」——入队只代表搬运已受理。真正的完成事件由后台线程写入完成队列，再由 check_hicache_events（11.5 节）在调度循环里收割。树上节点状态（backuped 等）只在收割之后才更新，这也是为什么调度器必须每轮显式调用一次对账。

11.5预取与回写策略

预取（L3→L2）发生在调度阶段。每次给 waiting 队列里的请求做前缀匹配时，若存储后端启用，Scheduler 会顺手发起一次预取——把「当前匹配不到、但 L3 可能有」的那段 token 提前拉到 L2：

这里有一处容易看漏的次序：预取阶段不分配 host 槽位。prefetch_from_storage 只登记「要取哪些 token」，真正的 mem_pool_host.alloc 延后到 _drain_and_alloc_storage_hit() 里做——也就是等 L3 命中数确定了再按需分配（源码在 hiradix_cache.py:1807-1809 附近留了注释说明这个懒分配）。原因是预取是乐观的：三级存储里可能只有一部分真的存在，提前按 prefetch_length 全额占位会浪费 host 池；等结果回来按实际命中长度分配，只付真正拿到的那部分。等不了那么久也有退出机制：hicache_storage_prefetch_policy 支持 best_effort（随时可放弃）、wait_complete（死等）、timeout（按传输量线性放宽的超时）：
python/sglang/srt/mem_cache/hiradix_cache.py — 线性超时函数（摘录，注释为译注）
python    def _prefetch_timeout_check_linear_func(self, operation):
        cfg = self.prefetch_timeout_config
        num_tokens = len(operation.hash_value) * self.page_size
        # 传输量越大，允许等得越久，但封顶 cfg.max
        timeout = min(cfg.max, cfg.base + cfg.per_ki_token * num_tokens / 1024)
        return time.monotonic() - operation.start_time > timeout

回写（L1→L2→L3）由 --hicache-write-policy 控制，三种策略：

策略行为适用
write_through（默认）每个新 KV 一算完就备份到 L2（阈值 write_through_threshold = 1）带宽充裕，追求最大缓存收益
write_through_selective访问次数超过阈值（2）才备份，只留热数据降低 I/O，牺牲部分命中率
write_back平时不写，L1 逐出时才落 L2存储带宽紧张、要榨干内存利用率

write-through 路径有一个必须满足的不变量，写在 write_backup 的注释里：

python/sglang/srt/mem_cache/hiradix_cache.py — write_backup 的备份不变量（摘录，注释保留原文）
python    def write_backup(self, node: TreeNode, write_back=False) -> int:
        # Backup invariant (for write-through mode): backed-up nodes must form a
        # contiguous prefix from root — no gaps.  Skip if parent isn't backed
        # up yet;
        if not write_back and (
            node.parent != self.root_node and not node.parent.backuped
        ):
            return 0

        host_indices = self.cache_controller.write(
            device_indices=node.value, node_id=node.id, ...)
备份不变量： L2 上的备份必须从根开始连续。原因在 11.3 节的 match_prefix 里：预取锚点向上走的是 while not last_host_node.backuped: 取 parent 这条链——如果中间有空洞，锚点会跳过未备份的节点，L3 的页哈希链就对不上了。这也解释了为什么父节点没备份时子节点直接跳过备份，而不是补齐父节点（那样会在热路径上引入连锁搬运）。

调度侧与 HiCache 的交接点在 _get_new_batch_prefill_raw：每轮调度先调 self.tree_cache.check_hicache_events()（scheduler.py:3617）收割写备份/加载/预取的完成事件，再调 _process_storage_prefetch_retries() 对上一轮未命中的预取按轮次间隔重发，重试次数由 hicache_storage_prefetch_retry_max_attempts 封顶。

演进痕迹 两个正在被替换的旧设计值得留意。其一，_evict_write_back 的 docstring 自述「note this path will be deprecated in the future」——write_back 模式要求逐出时同步搬运，把 I/O 塞进了调度关键路径，是三层模型里最别扭的一条路。其二，存储接口正从 v1（_generic_page_get，标着「todo: deprecate」，用 dummy page 中转）迁往 v2 的零拷贝字节接口（batch_exists_v2 / batch_get_v2 / batch_set_v2）——L3 后端越来越多，接口必须收敛到「不关心页对象、只搬字节」。
演进痕迹 两处针对存储 I/O 的修补也在这条交接线上。其一，调度器空闲分支（没有可跑的 GPU batch 时）会检查 enable_hicache_storage，是就 time.sleep(0) 让出一次 GIL（scheduler.py:4917 附近）——存储 worker 的 I/O 调用之间需要 GIL，死循环轮询会饿死它们的 ack 回传，一次显式让步换来事件及时收割。其二，mooncake 后端的 SSD 卸载目录改为按 rank 分子目录（ssd_offload_path/rank_{dp}_{tp}_{pp}_{attn_cp}）：bucket id 是每进程独立生成、重启后从同一起点续扫的，bucket 文件又以 O_CREAT|O_TRUNC 打开——多个 rank 共享一个卸载目录时，文件名撞上就会截断别的 rank 正在写的 bucket，静默产坏页。每个 rank 一个私有子目录后，路径不再交叉。
演进痕迹 MHA host 池的容量语义最近修正过一次（commit 5d703de9e4，#40304）：池子按「token 槽位」建，但一个 token 槽位在 host 侧要装的可能是多行注意力数据——池宽 head_num = device_pool.row_dim // device_pool.head_dim（pool_host/mha.py:209 起的两行注释与赋值）。此前 host 池只按设备池的 K/V head_dim 定宽，遇到设备池一行里并排多个注意力行（row_dim > head_dim）的布局，host 镜像就装不下完整的一行。顺带同一次改动里，get_hybrid_pool_buffer() 开始把 K/V 的 host 张量直接暴露出来，供零拷贝 I/O 注册。另外上一段的空闲让步条件本身也拓宽了：enable_hicache_storage or disaggregation_mode != NULL 才 time.sleep(0)——PD 模式的传输 worker 同样需要 GIL 让步，源码注释写明 "Storage and transfer workers need the GIL between I/O calls"。只看 HiCache 的读者可以忽略这半句，但它解释了为什么这个条件长在通用调度循环上。
演进痕迹 host 池的大小最近从「拍脑袋比例」走向「按机器实测定容」（commit 7a6c652c77，#40135）。以前的规则是固定比例：--hicache-ratio 默认 2.0（cache 模式）/ 1.2（buffer_only 模式），host 池 = 设备池 × 比例——设备池大一点 host 内存就可能被打爆。现在多了一个 --hicache-host-memory-fraction（默认 0.8）：只在用户没有显式给 ratio 或 --hicache-size 时生效，启动时按「本机可用内存（以 cgroup 的 memory.max/memory.high 为上界，扣掉 10 GiB 预留）× fraction」算预算，把默认比例往下压到刚好放得下（hicache_auto_size.py 的 auto_size_hicache：预算 ÷ 设备侧字节数，再扣 5% 给页对齐和分配器元数据的 slack），并在 TP/PP 组内做一次 all-reduce 取最小——各 rank 的池子结构不同（PP 各 stage 池数不一样），必须全体取最小才能都放得下，注释还特意说明这一锤子买卖要在任何池子构建之前做，不然按池逐次集合通信会死锁。多个引擎共居一个 cgroup 时把 fraction 调小即可。显式给了 ratio/size 则自动定容直接关闭，行为回到从前。
演进痕迹 hybrid 模型的传输层编号也修正过一次语义（commit 9f3d275940，#37870）。cache_controller.py 里计数器的构造参数从 layer_num 改名 transfer_layer_id_max——名字变了的背后是语义收紧：对 hybrid 模型（KV 层 + Mamba 层混排），传输层 ID 要覆盖所有组件池的编号空间，包括「不吃缓存、在传输布局里挖了洞」的层；锚点池自己报的层数描述不了这些洞。旧名 layer_num 让人以为它等于模型层数，sparse 布局下两层 ID 之间可以跳号，hybrid_cache_controller.py 的注释原话："Hybrid transfer IDs span every component pool, including holes for uncached layers"。分层计数器本身没变，变的只是「数到几」。

共享语义是这一节最需要记住的事实（设计文档原文要点）：L1、L2 都是实例私有——同一台机器上跑两个 SGLang 进程，它们的 L2 各是各的，互不共享；只有 L3 按后端配置决定共享范围。所以「同机多实例去重」必须走 L3，L2 再大也只帮本实例。

多 rank 一致性由两件事保证。其一，L3 的键是逐页哈希（内容寻址），两棵树算出同样的页序列就指向同样的键，天然去重；其二，TP 组内预取前要先对存储命中页数做一次 all-reduce 取最小值（prefetch_thread_func 里的 ReduceOp.MIN）——各 rank 命中数不一致时按最少者对齐，保证所有 rank 拉回同一长度。文件后端还按 rank 拆键，避免多 rank 写同一个文件：

python/sglang/srt/mem_cache/hicache_storage.py — HiCacheFile 的按 rank 分键（摘录，注释保留原文）

11.7对「自研引擎」的启示

要点 三层缓存的复杂度主要不在「多存两份数据」，而在每层索引的对账：一个前缀段在 L1/L2/L3 各有一份索引（device 索引、host 索引、页哈希），树上任何一个节点拆分、合并、逐出，三份索引都得跟着对——HiRadixCache 里大量代码是在处理「搬运在途时节点被拆了」的对账（ongoing_write_through 的 replace 逻辑就是为此存在）。如果你只想低成本拿到八成收益：先做 L2 备份，它给 decode 抢占（retraction）提供了现成的落点，被逐出的请求可以直接从 L2 拉回而不是重新 prefill；L3 只在多个实例共享存储、且前缀重复率高时才划算。下一步进入 第 12 章：PD 分离部署。
