整体架构：SRT 由哪几个进程组成

SGLang 的运行时叫 SRT（SGLang Runtime）。它最鲜明的选择是把「分词、调度、反分词」拆成独立进程，用 ZMQ 连起来。这一章先看清整台机器：谁在哪个进程、消息怎么走、为什么这么拆。

1.1一分钟版本

SGLang 要解决的核心问题和其他推理引擎一样：一张 GPU 上并发跑很多请求，每个请求都要保有自己的 KV 状态。SRT 的做法是把系统拆成四个部分，分布在 2~N 个进程里：

  • HTTP 服务 + TokenizerManager（主进程）：收请求、分词、把 token id 发给调度器；输出回来时负责流式整理。
  • Scheduler（子进程，每个 TP rank 一个）：整个引擎的「大头」——请求队列、RadixCache、KV 内存池分配、组装 batch、发起 GPU 前向，全在这一层。
  • DetokenizerManager（子进程）：把 Scheduler 吐出的 token id 反分词成文本，统一发给 TokenizerManager。
  • TpModelWorker / ModelRunner（在 Scheduler 进程内）：真正持有模型和 GPU 的执行者。

进程之间全部走 ZMQ ipc socket，没有共享内存队列。这个设计直接写在 launch_server 的文档字符串里，是理解 SGLang 的起点。

1.3进程是怎么被拉起来的

launch_server 的 docstring 就是官方架构图。它明确写出三个组件和通信方式：

python/sglang/srt/entrypoints/http_server.py — launch_server（摘录，docstring 译文）
pythondef launch_server(server_args, ...):
    """
    Launch SRT (SGLang Runtime) Server.

    The SRT server consists of an HTTP server and an SRT engine.

    - HTTP server: A FastAPI server that routes requests to the engine.
    - The engine consists of three components:
        1. TokenizerManager: Tokenizes the requests and sends them to the scheduler.
        2. Scheduler (subprocess): Receives requests from the Tokenizer Manager,
           schedules batches, forwards them, and sends the output tokens to the
           Detokenizer Manager.
        3. DetokenizerManager (subprocess): Detokenizes the output tokens and
           sends the result back to the Tokenizer Manager.

    Note:
    1. The HTTP server, Engine, and TokenizerManager all run in the main process.
    2. Inter-process communication is done through IPC (each process uses a different port) via the ZMQ library.
    """
看布局： 主进程持有 HTTP server 和 TokenizerManager；Scheduler 和 Detokenizer 都是子进程。进程个数不是写死的：tp_size=8 就是 8 个 Scheduler 子进程（每 rank 一张卡）。

子进程在 Engine._launch_scheduler_processes 里创建，注意循环的嵌套顺序——外层 PP rank、内层 TP rank，每个组合一个 mp.Process：

python/sglang/srt/entrypoints/engine.py — _launch_scheduler_processes（摘录，注释为译注）
pythonuse_dp_controller = (
    get_parallel().dp_size > 1 or get_exec().moe.ep_join_mode == "scale"
)

if not use_dp_controller:
    # 直接按 (pp_rank, tp_rank) 起子进程
    for pp_rank in pp_rank_range:
        for tp_rank in tp_rank_range:
            reader, writer = mp.Pipe(duplex=False)
            gpu_id = (
                get_device().base_gpu_id
                + ((pp_rank % pp_size_per_node) * tp_size_per_node)
                + (tp_rank % tp_size_per_node) * get_device().gpu_id_step
            )

                target=run_scheduler_process_func,
                args=(server_args, port_args, gpu_id, tp_rank, ...), ...)
两条分支： dp_size == 1 时直接为每个 TP/PP rank 起 Scheduler 进程；dp_size > 1 时改由 DataParallelController 统一拉起并做请求分发（第 10 章）。mp.Pipe(duplex=False) 的 reader 用来等子进程初始化完成，真正的请求/响应流量走 ZMQ。

1.3Scheduler 里持有哪些状态

Scheduler 的构造函数把所有引擎状态聚到一处。内存池和缓存不是 Scheduler 私有的，而是从 TpModelWorker 初始化结果里拿来的引用——也就是说，KV 池的 GPU 内存在 worker 里分配，但分配决策由 Scheduler 做：

python/sglang/srt/managers/scheduler.py — Scheduler.__init__ 的组件接线（摘录，注释为译注）
pythonclass Scheduler:
    def __init__(self, ...):
        # TP worker：持有模型 + GPU 内存池
        self.init_model_worker()

        # 内存池与前缀缓存：从 kv_cache_builder 的结果里取引用
        result = kv_cache_builder.build_kv_cache(..., tp_worker=self.tp_worker, ...)
        self.req_to_token_pool = result.req_to_token_pool
        self.token_to_kv_pool_allocator = result.token_to_kv_pool_allocator
        self.tree_cache = result.tree_cache

# init_model_worker 内部（同名文件）：
def init_tp_model_worker(self):
    worker_kwargs = dict(server_args=..., gpu_id=get_device().gpu_id, nccl_port=...)
    if use_mlx():
        self.tp_worker = MlxTpModelWorker(**worker_kwargs)
    else:
        self.tp_worker = TpModelWorker(**worker_kwargs)
三个核心状态的分工： req_to_token_pool 是「请求 → 它的 token 都在哪些槽位」的目录；token_to_kv_pool_allocator 管 KV 物理槽位；tree_cache（RadixCache）管哪些前缀可以复用。第 3、5 章会分别展开。注意这中间的两跳：worker 的构造被收进了 init_tp_model_worker()（多一个 MLX 分支），而内存池结果来自 kv_cache_builder.build_kv_cache() 而非 worker 本身——KV 池的 GPU 内存在 worker 里分配，但分配决策由 Scheduler 通过 builder 做出。这是「Scheduler 拿引用、不持有实现」的具体形态。

1.4为什么拆进程：演进与代价

一个自然的问题是：为什么不像 vLLM 那样把调度器放进引擎主进程，而要单独开进程？从代码里能找到答案的一半——Scheduler 持有 GPU 上下文并做 Python 层的调度计算（排序、预算扣减、树操作），这些工作和 HTTP/分词的 asyncio 事件循环互相拖累。拆开后：

  • GIL 隔离：Scheduler 的事件循环是纯 while True（见 1.5 节），RadixCache 的树操作和 PrefillAdder 的预算计算是 CPU 密集的 Python 代码，与 uvloop 的网络 IO 各跑各的。
  • 每 TP rank 一个进程：模型权重按 TP 分片到多卡，每张卡要独立做内存 profiling 和 CUDA Graph 捕获，天然是一个进程一张卡的边界。
  • 崩溃隔离：一个 rank 的 CUDA OOM 不会带走 HTTP 服务；主进程有 watchdog 监控子进程存活。

代价也很直接：每个 token 的输出都要多走一跳 ZMQ（Scheduler → Detokenizer → TokenizerManager → HTTP），延迟链变长。SGLang 用 batch 化的消息结构（BatchTokenIDOutput，一次携带整个 batch 的 token）摊薄这个成本。

困惑点 为什么 DetokenizerManager 单独一个进程，而不是放回 TokenizerManager？历史原因是把反分词的 CPU 开销也挪出主进程（流式请求每个输出步都要做一次 bytes→str 解码）；如今这个进程很轻，但通道结构没再合并——先有隔离、后有重叠调度器依赖这条稳定通道，是代码里能看到的演进痕迹。

1.5事件循环在哪：dispatch_event_loop

Scheduler 的事件循环不止一种。启动时按配置分发到不同实现——普通/重叠（overlap）、流水线（PP）、prefill-decode 复用（pdmux）、PD 分离各自的前后端循环：

python/sglang/srt/managers/scheduler.py — dispatch_event_loop（摘录，注释为译注）
pythondef dispatch_event_loop(scheduler: Scheduler):
    disaggregation_mode = scheduler.disaggregation_mode
    if disaggregation_mode == DisaggregationMode.NULL:
        if scheduler.enable_pdmux:
            scheduler.event_loop_pdmux()
        elif get_parallel().pp_size > 1:
            scheduler.event_loop_pp()
        elif scheduler.enable_overlap_mlx:
            scheduler.event_loop_overlap_mlx()
        elif scheduler.enable_overlap:
            scheduler.event_loop_overlap()
        else:
            scheduler.event_loop_normal()
    elif disaggregation_mode == DisaggregationMode.PREFILL:
        ...  # event_loop_*_disagg_prefill（定义在 disaggregation/prefill.py 的 mixin 里）
    elif disaggregation_mode == DisaggregationMode.DECODE:
        ...  # event_loop_*_disagg_decode（定义在 disaggregation/decode.py 的 mixin 里）
模式矩阵： PD 分离 × PP × overlap 各选一个入口。注意 PD 分离的循环根本不定义在 scheduler.py 里，而是 mixin（disaggregation/prefill.py:632 起）注入——后面第 12 章会看到这些循环长什么样。默认走 event_loop_overlap，第 2 章会专门拆它。

1.7对「自研引擎」的第一个启示

要点 多进程不是必需品。自研引擎的 MVP 用一个进程、一个 asyncio 事件循环 + 一个 GPU 前向线程就够。SGLang 拆进程换来的收益（GIL 隔离、rank 独立、崩溃隔离）只有在并发上去之后才值得。但有一个设计从第一天就该学：token id 通道和文本通道分开——调度层只传 id，反分词独立成段，这决定了你的流式协议好不好做。下一步进入 第 2 章：请求全生命周期。
