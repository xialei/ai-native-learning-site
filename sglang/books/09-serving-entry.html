服务入口：HTTP、OpenAI 兼容层与离线 Engine

第 2 章已经跟过一条请求从进入引擎到流式输出的完整路径。这一章看入口本身：http_server.py 里 80 多条路由怎么组织、/v1/* 兼容层做了什么、离线 Engine 如何绕开 HTTP 直接驱动同一套进程、论文里的前端语言（gen/fork/select）如何编译成对运行时的请求，以及 ServerArgs → runtime_context 的配置体系。

9.1一分钟版本

进入 SGLang 引擎有三扇门，门后是同一个 TokenizerManager：

  • HTTP server（launch_server）：FastAPI 应用，注册 80 多条路由，覆盖生成、OpenAI 协议、运维和权重管理。
  • OpenAI 兼容层（/v1/chat/completions 等）：不是独立服务，而是 HTTP 路由后挂的一组 OpenAIServing* 适配器，把 OpenAI 请求翻译成 GenerateReqInput。
  • 离线 Engine（sgl.Engine）：拉起完全相同的进程结构，但不启动 HTTP——Python 代码直接调用 tokenizer_manager.generate_request()。

在这三扇门之外还有一个客户端侧的老入口：论文里的前端语言（sgl.gen / s.fork / sgl.select，§9.6）。它不发新协议，就是把多段生成程序组织成一连串对 /generate 的调用，靠 radix tree 吃掉公共前缀——所以放在这一章末尾讲：它只是第一扇门上多挂的一种用法。

所有入口最终都汇到同一个调用：tokenizer_manager.generate_request(obj)。这意味着协议层的差异（SSE 帧、chat 模板、tool call 解析）全部被挡在 TokenizerManager 之外——调度器和 GPU 不关心请求来自 curl 还是 OpenAI SDK。

路由的共同写法很薄——解析参数、调 TokenizerManager、包错误。以 /flush_cache 为例：

python/sglang/srt/entrypoints/http_server.py — 运维路由示例（摘录）
python@app.api_route("/flush_cache", methods=["GET", "POST"])
@auth_level(AuthLevel.ADMIN_OPTIONAL)
async def flush_cache(timeout: float = Query(0.0, ge=0.0)):
    """Flush the radix cache."""
    ret = await _global_state.tokenizer_manager.flush_cache(timeout_s=timeout)
    if ret.success:
        content = (
            "Cache flushed.\nPlease check backend logs for more details. "
            "(When there are running or waiting requests, the operation will not be performed.)\n"
        )
    else:
        content = ret.message or "Flush cache failed.\n"
薄路由： 路由层不做业务，只做三件事：鉴权（@auth_level）、调用、包装响应。注意 flush 在有 running/waiting 请求时会拒绝执行——缓存清空请求和正在跑的请求之间存在一致性问题，调度器侧（第 4 章）会检查队列再动手。

python/sglang/srt/utils/watchdog.py — SubprocessWatchdog（摘录）

    When a subprocess crashes (e.g., NCCL timeout causing C++ std::terminate()),
    Python exception handlers never run, leaving the main process as a zombie
    service. This watchdog polls subprocess liveness in a daemon thread and
    sends SIGQUIT to trigger proper cleanup.
    """
困惑点 为什么有 /health 和 /health_generate 两条？代码给出了答案：/health 默认只查进程状态，直接 200，负载均衡器高频轮询时零开销；/health_generate 会真的发一条 input_ids=[0]、max_new_tokens=1 的生成请求，验证「前向通路是好的」而不仅是「进程活着」。另外 /health 支持 SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION 开关把它也升级成真生成——是运维口径分裂后的收敛痕迹。
演进痕迹 新近多出的第三条：/ready（http_server.py）。它与 /health 的分野在语义：/health 回答「进程活着」，/ready 回答「这个实例现在该不该接新请求」——实现读 TokenizerManager.is_ready()（tokenizer_manager.py）：未暂停、未在优雅排空、ServerStatus.Up 三个条件同时成立才 200，否则 503。滚动发布时先把实例置为排空、等它退出负载均衡、再停进程，探针就得盯 /ready 而不是 /health——活着但不想接活的实例，用 /health 看不出来。
演进痕迹 权重更新这条路最近长出了「会话」语义（commit f4d9d2e670，#40777）。此前的三条 /update_weights_* 是一次性 RPC，发一条做一件事；#40777 加了 /begin_weight_update 和 /end_weight_update（http_server.py、:1415，都是 ADMIN_OPTIONAL）把更新包进一个开关区间，动机是 RL 训练循环里反复推权重——而这些服务里大量模型做了原地量化打包（weight pack）：参数在显存里已经不是加载时的形状，新权重根本塞不进去。所以 begin 干的事是「恢复出厂形状」：调 DefaultModelLoader.restore_weights_before_loading，docstring 一句话讲清目的——"Undo in-place quant packing so fresh weights can be loaded"（loader.py）。

会话有三条规矩。其一，update_weights_from_tensor / from_distributed 在会话外直接拒绝——scheduler 侧 .py、:219.py 的错误信息就是字面意思："must run between begin_weight_update() and end_weight_update()"；from_disk 不受此限，它本来就按「完整加载」的流程走。其二，end 时只在整个会话期间没跑过任何加载才补 post_load_weights（run_post_load = not session.loaded_weights，weight_updater.py）——P2P/RDMA 走自组网直拷，加载路径自己收尾；跑过 tensor/distributed 加载的会话，加载器已经做过后处理，再跑一次会把打包做两遍。其三，end 收尾的 runner 集合取自 begin 时记下的 selector，而不是 end 请求里重新给的那份——_WeightUpdateSession 就两个字段（weight_updater.py，注释原话 "recorded at begin so end finalizes the same runners"）。

selector 是这次改动引入的新旋钮：Literal["target","draft","all"]（io_struct.py），默认 all。实现不是 if-else，而是每个 worker 暴露 weight_update_runners() 返回 (role, runner) 列表：目标侧 tp_worker 返回 [("target", …)]（tp_worker.py），投机侧 BaseSpecWorker 返回 [("draft", r) for r in draft_runners]——NGRAM / UNO 这类无草稿模型的返回空表；多层 EAGLE 则按层给 ("draft_step_0", …), ("draft_step_1", …)。_select_runners 把两边的表拼接起来，权重更新第一次能精确落到草稿模型上——RL 训 EAGLE 草稿头时不用再重启引擎。begin/end 各自以 torch.distributed.barrier(group=self.tp_cpu_group) 收尾，保证 TP 组对「会话开着/关着」的判断同步。
演进痕迹 路由表里评分类那一行最近热闹了两轮。其一，新增 /v1/systemone（http_server.py，commit 16d1c93b3d #41208）——System One 兼容的决策 API，与 /v1/decisions 共用 OpenAIServingDecisions 的渲染、标签校验与打分（serving.py 的子类说明写得很直白："Answers System One questions with the rendering, label checks, and scoring of /v1/decisions"）；唯一特化在错误格式：全局 422→400 的改写器单独给它留了口子，保留 System One API 文档规定的 422 detail list（http_server.py 的注释）。兼容层的「兼容」二字再次显形——不只兼容请求格式，连错误码语义都要兼容。其二，打分本身多了一种 setwise 读出（#38965/#41188）：请求带 score_extraction_token（protocol.py）后，读出点从「序列最后一个 token」变成「query+item 拼接里每次出现该 token 的位置」，返回嵌套形状 [num_items][Nᵢ × num_labels]——一次前向给一组候选各自打分（SeqCls 在该 token 处池化，CausalLM 读标签 logprob），嵌套深度本身用来区分 pointwise/setwise 两种返回形状（protocol.py 的 ScoringResponse 注释）。用途是 rerank/评审类负载：逐 item 独立打分对「候选项互相关」是盲的，setwise 让同批候选在同一个上下文里被比出来。

还有一个值得注意的演进：HTTP 层本身正在被 Rust 重写。SGLANG_RUST_SERVER=1 时，Python 主进程不再跑 FastAPI 和 TokenizerManager——api-server、tokenizer、detokenizer 全部由 sgl-model-gateway 的 Rust 侧承担，Python 这边只等 Scheduler 退出：

python/sglang/srt/entrypoints/http_server.py — launch_server 的双分支（摘录，注释为译注）

9.4OpenAI 兼容层：不止是格式转换

/v1/chat/completions 的 handler 本身只有一行转发，真正的工作在 OpenAIServingChat：

python/sglang/srt/entrypoints/http_server.py — /v1 路由的薄转发（摘录）
python@app.post("/v1/chat/completions", dependencies=[Depends(validate_json_request)])
async def openai_v1_chat_completions(
    request: ChatCompletionRequest, raw_request: Request
):
    """OpenAI-compatible chat completion endpoint."""
    return await raw_request.app.state.openai_serving_chat.handle_request(
        request, raw_request
    )
不止转格式： 每个 /v1 端点对应一个 OpenAIServing* 对象，启动时统一挂到 fast_api_app.state 上，构造参数都是同一个 TokenizerManager 加 TemplateManager。适配层要干的活比「转格式」多得多。

第一件重活是 chat 模板。messages 数组要按模型自带的 Jinja 模板渲染成 prompt token 序列，tools 定义也要拼进模板。通用路径在 _render_and_encode_chat_template：

python/sglang/srt/entrypoints/openai/serving_chat.py — chat 模板渲染（摘录，节选自 _render_and_encode_chat_template）
pythonrendered_prompt = self.tokenizer_manager.tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
    tools=tools,
    return_dict=False,
    **template_kwargs,
)
prompt_ids = self.tokenizer_manager.tokenizer.encode(rendered_prompt, **encode_kwargs)
两步渲染，整体缓存： 通用路径是「先渲染成文本、再 encode」两步，中间结果（rendered_prompt / prompt_ids / 反解码的 decoded_prompt）按 (chat_template, messages, tools, kwargs) 整体做 LRU 缓存（上限 128，仅多模态请求启用）——同一批图片重复请求时渲染和编码都省掉。template_manager 负责处理「模型没带模板」「用户传了 chat_template_kwargs」这类边界。
演进痕迹 这条路径上有过两次收敛。其一，渲染结果怎么交给引擎：可能是文本（普通 VLM：带占位符字符串的 prompt，交给多模态处理器去 tokenize），也可能是预渲染好的 input_ids（token-first 编码器：单个占位符 id，文本部分是空的——这时必须原样透传，否则会去 tokenize 一个空串）。这个「文本还是 id」的分叉原来长在 _convert_to_internal_request 里，是逐模型 elif 链（先 kimi_k3 再 inkling），后来抽成 _engine_prompt()，判断依据从模型名字符串换成能力查询 chat_encoding.spec_renders_prompt_ids(self.chat_encoding_spec)——每接一个特殊编码器就加一个 elif 是这类地方的典型退化路径，换成能力位之后新模型声明行为即可，这里不用动。其二，tokenize 本身：kimi_k3 一族仍走「apply_chat_template(tokenize=True) 一步出 id」的快路径（_encode_messages 内），通用模型走上面渲染+编码两步——一步出 id 少一次 tokenize 往返，但两步版能拿到中间文本做多模态缓存键，各取所需。如今两条路之间还插了一个自动仲裁：构造时跑一次 _probe_prompt_text_round_trip（serving_chat.py）——拿一条 [{"role": "user", "content": "x"}] 分别走「渲染成文本再 encode」和「直接 tokenize=True」，结果不同就标记 lossy，此后该 tokenizer 的请求直接走一步出 id。这是被 mistral_common 类 tokenizer 逼出来的：它们的控制 token（[INST]、[AVAILABLE_TOOLS]）没有文本形式，渲染成字符串会变成字面字母、再 encode 还会多出一个 BOS——模型看到的不再是框住工具块的控制 token，而是字面字符。探测失败（比如模板需要探测没给的 kwargs）时保守回到老的文本路径。
演进痕迹 logprobs 的 bytes 字段最近也修了一处静默损坏：_build_token_logprobs_from_raw（serving_chat.py）的 docstring 讲得很清楚——引擎返回的三元组里 token id 永远是真的，但 token text 是展示用的反解码字符串，会丢碎片字节 token：比如 U+20BB7 的四个单字节 BPE 片段各自 decode 都是坏字节，拼出来是 U+FFFD。此前 OpenAI 响应里的 bytes 字段从展示文本反推，多字节字符就被这几个 U+FFFD 毁掉；现在改成从 token_id 走 GPT-2 字节解码器恢复真实字节。SentencePiece 系 tokenizer 没有这种字节回退表，仍退回展示文本。凡是做「把内部 (logprob, token_id, text) 三元组映射成 OpenAI 格式」的适配层，这条「id 才是真身、text 是投影」的教训都直接适用。
演进痕迹 input-logprob 的临时显存最近开始「借」CUDA Graph 池的空地（commit 9e5a62a767，#40038）。问题背景：chunked prefill 开 input-logprob 时，LM-head 的 logits 矩阵（行数 × 词表 × 4 字节）是整段临时分配的大块显存，prefill batch 一大就直接顶到 OOM；而 CUDA Graph 捕获用的内存池里，两次捕获之间天然留着大片空闲（最大连续空闲段，graph_pool_borrow_largest_run()）。现在 logprob_processor.py 的 _can_borrow_logprob_memory 会先算「这块空地按 1~3 个矩阵/行能躺多少行」，不够放整个 chunk 就不借——chunk 边界必须与图池布局无关（借不到就退回常驻 workspace，注释写明：改 chunk 大小会改变 LM-head GEMM 的形状与取整），TP 下还要跨 rank all-reduce 取最小。借来的空间当然随时可能被图重放覆写，所以复制结果时挂一个 input_logprobs_copy_done CUDA event，LogitsProcessorOutput.finalize_input_logprobs() 在消费侧同步它，再把借址上按 span 排布的片段拉平成列表。这是「图池死空间再利用」的一例——第 6 章讲的 CUDA Graph 捕获策略决定了这块空地有多大。
演进痕迹 模板这一层最近补上了一道安全闸（commit 3e7e652900，#28135）：请求的 chat_template_kwargs 会原样展开进 apply_chat_template（serving_chat.py 的 extra_template_kwargs.update），而这个函数的签名里本来就有 chat_template: str | None 参数——kwargs 里塞进同名键就等于替服务端换掉模板本身，客户端得以重写整套渲染规则。现在 _validate_request（serving_chat.py）直接拒掉这个键，报错指路 --trust-request-chat-template；开关定义在 serving.py，注释写明「Off by default for safety」。值得注意 reasoning_effort 走的也是 chat_template_kwargs 这条路，却不会被误伤——校验只拦名为 chat_template 的键，其余 kwargs 照常透传。这是「请求体字段流入模板引擎前必须过白名单」的一例，自研适配层里凡是 **kwargs 直通 Jinja 的地方都值得对照检查。

第二件重活是 tool call。适配层要把请求里的 tools 翻译成模型能输出的格式约束，并在输出流里把模型吐出的特殊 token 解析回结构化 tool_calls——SGLang 为约 40 种模型的对话格式各写了一个 detector：

glm47 走单独一条路： 入口现在分两路：glm47（且没有 tool 声明 strict）先在前面单独构建一条全助手回复的 EBNF 约束，后面的通用分支用 not glm_constraint 跳过；其余模型仍走通用路径。required_parsed_natively 的初值就是 glm_constraint——glm47 的调用格式必须由模型原生吐出，不能靠采样掩码兜底。tool_call_constraint 会一路传到采样层变成结构化输出约束（第 8 章），让模型在生成时就被限制在合法的调用格式内；流式响应阶段再用 detector 从输出 token 里解析出 function name / arguments 的增量。推理内容（reasoning）的分离也是同样套路，靠 reasoning_parser 的前后缀检测。

9.5离线 Engine：同一套进程，不设 HTTP

sgl.Engine 的 docstring 与 launch_server 几乎逐字相同——同样的三个组件、同样的 ZMQ 通信，区别只在主进程不跑 FastAPI，由 Python 调用方直接持住 TokenizerManager：

python/sglang/srt/entrypoints/engine.py — Engine.generate 的流式包装（摘录，注释为译注）
pythongenerator = self.tokenizer_manager.generate_request(obj, None)

if stream:
    def generator_wrapper():
        while True:
            try:
                chunk = self.loop.run_until_complete(generator.__anext__())
                yield chunk
            except StopAsyncIteration:
                break

    return generator_wrapper()
else:
    ret = self.loop.run_until_complete(generator.__anext__())
    return ret
同步包装，同一协程： 离线 Engine 把 asyncio 生成器包成同步生成器：内部跑自己的事件循环，逐块 run_until_complete。因为底层 API 与 HTTP 路径完全相同（同一个 generate_request 协程），离线压测得到的数据可以代表在线行为——这是「离线引擎优先」设计带来的直接好处。

进程编排入口是 _launch_subprocesses，开头几行值得细读——配置在发布给子进程前有一道「快照-恢复」保护：

python/sglang/srt/entrypoints/engine.py — _launch_subprocesses 开头（摘录，注释为译注）
pythonconfigure_logger(server_args)
server_args.resolve_once()

# publish 把 server_args 安装为本进程的全局配置，role 记录进程角色；
# snapshot/restore 保证启动失败时上下文回到发布前

publish(server_args, role="tokenizer")
role 不只是元数据： publish(role="tokenizer") 之后，主进程内所有 get_schedule() 式的读取都有了着落。每个角色有一张「允许读取哪些配置命名空间」的表（ROLE_NAMESPACE_SETS），SGLANG_ROLE_NAMESPACES=enforce 时表外的读取直接报错——这是把「哪类进程依赖哪些配置」显式写进了代码。
这张表目前还很宽松，原因写在注释里： 查表会发现，scheduler、tokenizer、detokenizer、encoder 等角色的值都是 None——None 的语义是整棵树都可以读，不是「什么都不能读」。真正被收窄的只有一个：dp_controller，限定在 {"exec", "parallel", "device", "disagg", "observability", "serving"} 六个命名空间。tokenizer 那一项旁边留了一段注释解释为什么不收窄：做记录模式审计时只跑通了文本模型的几个端点，多模态处理器、LoRA / score 端点、disagg 角色、gRPC 桥都没覆盖到，「收窄需要把这些形态也审计完；写错的集合会让请求失败，而不是让测试失败」。所以这张表现在的实际作用是：框架就位、失败关闭（fail-closed）已经生效，但生产角色还没有一个真正被限制住。

离线 Engine 还补齐了一块与 sglang serve 的能力差：多 tokenizer 进程。此前 --tokenizer-worker-num > 1 只在 HTTP 服务路径生效（uvicorn worker 各挂一个 TokenizerWorker），Engine 构造时拿到 MultiTokenizerRouter 就没辙了——它只负责把多个 worker 桥到 scheduler，自己没有 generate_request，调用方拿到的是个空壳。#40260 后 Engine 检测到这个形态会自己补齐（commit 66454d704b）：

python/sglang/srt/entrypoints/engine.py — Engine 检测 MultiTokenizerRouter（摘录，注释为译注）
pythonif isinstance(tokenizer_manager, MultiTokenizerRouter):
    # --tokenizer-worker-num > 1：router 只桥接，没有 generate_request；
    # 发布共享内存里的启动数据（与 sglang serve 同一契约），
    # 本进程自己挂一个 worker，其余进程用 attach_tokenizer_worker 加入

发布-加入的两段式： 主 Engine 进程把 port_args、server_args、scheduler 信息写进共享内存（write_data_for_multi_tokenizer，与 sglang serve 同一套契约），自己持一个 worker 保证 Engine.generate() 在本进程可用；其他进程调 Engine.attach_tokenizer_worker(parent_pid) 加入——attach 返回的 Engine 没有自己的子进程，只持一个注册到父进程 MultiTokenizerRouter 的 TokenizerWorker，generate 在本进程跑、prefill/decode 还在父进程的 scheduler 上。docstring 顺带划了一条界线："Weight updates and other RPCs must go through the parent Engine"——分出去的只是每请求的 Python 开销（分词、模板渲染），控制面 RPC 仍归父进程。读代码时留意区分两套机制：detokenizer_worker_num 的多 worker 是引擎自带的进程编排（engine.py 起，worker 各持私有 IPC socket、由 MultiDetokenizerRouter 持原名扇出），而 tokenizer 的多 worker 复用了 sglang serve 的共享内存 + attach 机制，两条路径的落点不同。

9.6前端语言：gen / fork / select 怎么落到 /generate

上面四节讲的都是「一次请求一个响应」的形态。SGLang 还有一套更老的前端——论文里那门「结构化生成语言」：sgl.gen、s.fork、sgl.select，让多轮生成、分支探索、多项选择写成一段普通 Python。它不在 srt/ 目录下，而在 python/sglang/lang/（642 行的 ir.py 定义表达式，interpreter.py 负责解释执行）。注意它至今仍是发布的一部分——只是如今绝大多数用户走 OpenAI 兼容层，这条线被冷落了；要理解「一个推理引擎的 API 能长成什么样」，它比 /v1/* 更有启发性：

python/sglang/lang/api.py — 一段多分支程序（示意，run 于任意 backend 之上）
python@sgl.function
def multi_choice(s, question, choices):
    s += system("请仔细回答。") + user(question)
    with s.fork(len(choices)) as exes:
        for i, choice in enumerate(choices):
            exes[i] += assistant() + sgl.gen("answer", max_tokens=64, stop=["\n"])
    for i, choice in enumerate(choices):
        exes[i] += sgl.gen("score", choices=["A", "B"])
    branches = exes.join("gather_variable")   # 收回分支里的变量

把它编译到运行时的，是三层各司其职的组件。用户函数先被 @sgl.function 包成 SglFunction（lang/ir.py，构造时用 inspect.getfullargspec 校验第一个参数必须叫 s）；调用 run() 时 run_program（lang/interpreter.py）为它开一个 StreamExecutor——每条执行流一个，内部一根工作线程从队列里逐个取表达式执行：

python/sglang/lang/interpreter.py — StreamExecutor 的分发核心（摘录，注释为译注）
pythondef _execute(self, other):
    if isinstance(other, str):
        other = SglConstantText(other)

    if isinstance(other, SglConstantText):
        self._execute_fill(other.value)          # 拼进 text_，不发请求
    elif isinstance(other, SglGen):
        self._execute_gen(other)                 # → backend.generate → POST /generate
    elif isinstance(other, SglSelect):
        self._execute_select(other)              # → backend.select → 多路 logprob
    elif isinstance(other, SglConcateAndAppend):
        ...                                      # fork 分支的 KV 拼接（见下）
    elif isinstance(other, SglRoleBegin):
        self._execute_role_begin(other)          # chat 模板的角色包裹
    ...
不是先编译成 AST 再执行，是边解释边发请求： s += sgl.gen(...) 这一句，语义就是「把当前累计文本发给 /generate，生成结果存进变量」。两个执行时的支撑结构值得记：variables 字典保存每个 gen(name=...) 的产物，variable_event 让跨分支读取变量时能等待生成完成（fork 出的分支读一个还没算完的变量，会先阻塞在 event 上）；工作线程 + 队列让流式场景下主线程拿 token 的同时生成还在继续。

fork 的实现直白得令人愉快——深拷贝执行器状态，各分支从分叉点各自生长：

python/sglang/lang/interpreter.py — StreamExecutor.fork（摘录，注释为译注）
pythondef fork(self, size=1, position_ids_offset=None):
    if size > 1 and str(self.text_):
        self.submit(SglCommitLazy())    # 先把公共前缀算进 KV（commit_lazy_operations）
    self.sync()

    exes = [StreamExecutor(self.backend, self.arguments, ...) for _ in range(size)]
    for i in range(size):
        exes[i].variables = dict(self.variables)
        exes[i].text_ = str(self.text_)            # 分支继承全部已生成文本
        exes[i].fork_start_text_pos = len(self.text_)  # 记下分叉点，join 时用
        ...
    return exes
fork 的第一件事是 commit： 分支各自向前生成后，共享前缀只有一份 KV——前缀复用不靠前端做什么特殊事，靠的正是第 3 章那棵树：每个分支的 generate 都把「整段 text_」发给 /generate，公共前缀在 radix tree 上命中，后端只对增量做 prefill。这就是「前端语言如何复用前缀」的答案：前缀复用不是前端的能力，是它敢于「每次都发全文」的底气。 fork 时 SglCommitLazy 先把没提交的文本推成一次真实请求（max_new_tokens=0 的 /generate，只进树不生成），确保分叉点之前的 KV 已在树上。

join 的两种模式： ProgramStateGroup.join("gather_variable") 是默认——把各分支新产生的变量收回主分支；join("concate_and_append") 则调 /concate_and_append_request，让引擎在 KV 层把各分支的 token 直接拼回主分支（_execute_concatenate_and_append_kv_cache，runtime 后端才支持）——分支重汇合时免去重算拼接段，这是只有自控引擎的前端才做得出的操作。

select 最能看出「前端语言」和「裸 API」的差距。它要在多个候选里挑一个概率最高的，却不做任何新内核，只是把请求组织得聪明：

python/sglang/lang/backend/runtime_endpoint.py — RuntimeEndpoint.select（摘录，注释为译注）
pythondef select(self, s, choices, temperature, choices_method):
    # ① 先把公共前缀算进缓存：max_new_tokens=0 的 /generate
    data = {"text": s.text_, "sampling_params": {"max_new_tokens": 0}}
    obj = self._generate_http_request(s, data)
    prompt_len = obj["meta_info"]["prompt_tokens"]

    # ② 一次请求批量给「前缀+候选 c」逐个打分（list 批量形式）
    data = {
        "text": [s.text_ + c for c in choices],
        "sampling_params": {"max_new_tokens": 0, "temperature": 0},
        "return_logprob": True,
        "return_text_in_logprobs": True,
        # logprob_start_len 收在 prompt 末尾附近——token healing 的回退空间
        "logprob_start_len": logprob_start_len,
    }
    obj = self._generate_http_request(s, data)
    ...
    return choices_method(choices=choices, normalized_prompt_logprobs=..., ...)
select 是三个动作的组合： 缓存公共前缀（①）→ 批量打分（②，一次 /generate 发 N 条变体，依赖引擎对批量 text 的支持）→ 归一化比较（choices_method 决定按 token 长度归一还是直接加和）。另有一处容易被略过的细节：候选的第一个 token 可能和前文「黏」成一个不同分词的 token（token healing），所以 logprob_start_len = max(prompt_len - 2, 0) 多退两步，把「被切分方式改变的那个 token」也纳入比较窗口，失配时把它的 logprob 从归一化里剔掉。全部逻辑在客户端——引擎只要会返回 logprob，select 就成立了。这一节的模板价值不在功能，在思路：高级原语可以用「聪明地组织朴素请求」来实现，前提是引擎把 match_prefix + 批量 + logprob 三件事做扎实。
困惑点 这套语言和 vLLM 的「前端」是什么关系？vLLM 没有对应物——它的可编程面就是 OpenAI 协议 + 离线 LLM 类；把「多步生成程序」作为一等公民、在客户端库层做编排，是 SGLang 论文（2023）的原始出发点，也是项目名字的来源。后来工程重心移到 SRT 运行时（本书主体），这套语言退守为 sgl.RuntimeEndpoint 上的可选客户端：同样的原语也可以对着 openai/litellm/anthropic 等 API 后端跑（lang/backend/ 下六七个实现），只是 fork/join 的 KV 级拼接只有在自家 runtime 上才成立。读 SRT 源码时不必找它对调度的影响——没有；它是纯粹的客户端构造层。

9.7配置体系：ServerArgs 与 runtime_context

SGLang 的启动参数有 200 多个，全部收在 ServerArgs 一个 msgspec Struct 里。它的字段声明方式有个特点：CLI flag 直接从字段名推导，帮助文本写在类型注解里：

python/sglang/srt/server_args.py — ServerArgs 的字段注解约定（摘录，docstring 译文）
pythonclass ServerArgs:
    """
    1. **Use the ``A[T, ...]`` annotation.** ``A`` is an alias for
       ``typing.Annotated``. The primary CLI flag is auto-derived from the
       field name (``tp_size`` → ``--tp-size``):

           # Bare string — simplest form (just help text):
           host: A[str, "The host of the HTTP server."] = "127.0.0.1"
           trust_remote_code: A[bool, "Whether to allow custom models."] = False

一处声明，三份产出： 字段定义、CLI 注册、帮助文档三份信息合并成一处声明，加参数只改一个文件。这个文件本身也是配置演进的记录：代码里专门列出了哪些参数「必须手动注册」（废弃 flag 重定向、动态 choices），并按注释块分区（# Model and tokenizer、# LoRA……），新参数必须归入对应分区。

配置的读取端不在 ServerArgs 上，而是发布到一组进程级全局对象。Scheduler、ModelRunner、Sampler 里的代码到处在调 get_schedule().page_size、get_memory().disable_radix_cache 这类语句：

演进 从代码注释能还原这次重构的动机：ServerArgs 的 docstring 写着「Construction leaves the record at what the caller asked for. 9.8对「自研引擎」的启示

要点 最值得迁移的是三个决定。首先是离线 Engine 先行——先把 generate() 做对，HTTP 层只是它的一层皮，两边共用同一协程入口，压测和服务行为才不会分叉。其次是路由薄、适配层厚——路由只做参数解析和转发，chat 模板、tool call、reasoning 分离这类协议工作收敛到独立的 serving 对象；SGLang 的路由清单已经长到 80 多条，靠的就是每条路由都足够薄。最后是配置可以全局读，但要把「谁读什么」写成表——全局包省掉了参数传递的机械劳动，角色-命名空间表让这种妥协保持可审计。下一步进入 第 10 章：分布式推理。
