PD 分离：prefill 和 decode 拆成两套实例

prefill 吃算力、decode 吃显存带宽，两者的资源画像相反。PD 分离把两个阶段部署在独立实例池上，中间传 KV。SGLang 的实现方式很克制：不是另写一套引擎，而是在同一个 Scheduler 里加了两条事件循环和三个队列。

12.1一分钟版本

混合部署（一套实例同时跑 prefill 和 decode）有两个已知的调度问题，官方文档 docs/docs/advanced_features/pd_disaggregation.mdx 一开始就点名：

  • prefill 打断 decode：一条长 prompt 进来，占用一整个前向步（几百毫秒），这期间所有 decode 请求的 token 间隔（ITL）集体被拉长。
  • DP attention 不均衡：开 dp_attention 时，一个 DP rank 在跑 prefill、另一个在跑 decode，做 MLP 同步时快的要等慢的，decode 延迟跟着 prefill 走。

PD 分离的解法：--disaggregation-mode prefill 和 --disaggregation-mode decode 启动两套实例。prefill 实例算完输入的 KV 后，通过 RDMA 把 KV 传给 decode 实例，decode 实例接着自回归生成。请求级别的粘合点是 DisaggregationMode 枚举 + 两条专用事件循环 + 三个队列（bootstrap / prealloc / transfer），全部内联在现有 Scheduler 里，而不是一套新进程模型。

12.3模式与循环：同一个 Scheduler，两套事件循环

第 1 章已经看到 dispatch_event_loop 的分发矩阵，PD 分离占了其中六格（PREFILL/DECODE × PP/overlap/normal）。两条 event_loop_*_disagg_* 循环不在 scheduler.py 里，而是以 mixin 形式定义——这是 SGLang 控制代码规模的做法：不改 Scheduler 主体，把 PD 逻辑全部外挂：

python/sglang/srt/disaggregation/prefill.py — event_loop_normal_disagg_prefill（摘录，注释为译注）
pythondef event_loop_normal_disagg_prefill(self: Scheduler) -> None:
    """A normal scheduler loop for prefill worker in disaggregation mode."""
    while True:
        self.ingest_requests()
        if self._engine_paused:
            ...
            continue
        # 与普通循环的关键差异 ①：只把「握手完成」的请求放进 waiting_queue
        self.waiting_queue.extend(
            self.disagg_prefill_bootstrap_queue.pop_bootstrapped()
        )

        # 调度入口换成了 disagg 版本（内部仍走 get_new_batch_prefill）
        plan = self.get_next_disagg_prefill_batch_to_run(...)
        batch = plan.batch_to_run
        batch = self.ngram_embedding_manager.prepare_for_forward(batch)

        if batch:
            if self.enable_staging:
                self.maybe_prefetch_staging_for_batch(batch)
            result = self.run_batch(batch)
            self.process_batch_result(batch, result)
        else:
            self.on_idle()

        # 关键差异 ②：每轮驱动「传输中」队列（KV 写出、轮询完成态）
        self.process_disagg_prefill_inflight_queue()

        self.last_batch = batch
读懂这段： 和 event_loop_normal（第 2 章）逐行对照，只有两处新增：入口处从 bootstrap 队列取「握手完成」的请求；尾部驱动 KV 传输队列。decode 侧的 event_loop_normal_disagg_decode（disaggregation/decode.py:2500）结构相同，差异是把 process_decode_queue() 插在调度之前。这就是「复用引擎主体」的含义：调度、内存、前向代码一行没动，动的只有请求进出的边界。

DisaggregationMode 本身是三值枚举（NULL / PREFILL / DECODE），挂在 Scheduler 上，所有 if 分支都围绕它展开。

prefill 完成后，KV 的写出有两种时机。一是 process_batch_result_disagg_prefill（prefill 前向结束后整体发送）；二是可选的提前发送——radix cache 命中的前缀 KV 不用等本轮前向，先发出去，让传输和计算重叠。这个开关带一整套防竞态处理，值得看一眼：

python/sglang/srt/disaggregation/prefill.py — maybe_send_cached_prefix_chunk（摘录，注释为译注）
pythondef maybe_send_cached_prefix_chunk(self: Scheduler, req: Req) -> None:
    if not envs.SGLANG_DISAGG_PREFILL_EARLY_SEND_CACHED_PREFIX.get():
        return

    # staging 按位置网格发送，提前发送的边界必须在请求的各个 batch 之间保持稳定：
    # 所以在第一个 batch 上把驻留前缀快照下来。非 staging 则读实时前缀。
    if self.enable_staging and req.early_send_prefix_end is None:
        req.early_send_prefix_end = max(
            0, len(req.prefix_indices) - req.host_hit_length
        )

    if req.pending_bootstrap:
        return

    # 只发设备驻留的前缀；页对齐以保证 start_send_idx 精确
    cached_end = (
        req.early_send_prefix_end
        if self.enable_staging
        else len(req.prefix_indices) - req.host_hit_length
    )
    if cached_end <= req.start_send_idx:
        return
    if cached_end % self.token_to_kv_pool_allocator.page_size != 0:
        # DCP radix 命中可能落在不完整的物理页上；常规最终发送会覆盖全量，
        # 这里只跳过这个可选的提前发送优化
        return
    # 提前发送在本步前向入队之前发出 KV 读请求，但 overlap 调度下上一步的
    # prefill 前向可能还在 forward_stream 上写这些前缀页。记录完成事件，
    # 让传输线程先等写入完成再发起 RDMA 读，避免与写竞争。
    if self.enable_overlap:
        ev = torch.cuda.Event()
        ev.record(self.forward_stream)
        req.disagg_kv_sender._early_send_wait_event = ev
    self.send_kv_chunk(req, last_chunk=False, end_idx=cached_end)
读懂这段： 三个细节都有生产含义：① 只发页对齐的边界（传输协议按页为单位）；② overlap 调度下「读 KV」和「写 KV」在不同 CUDA stream 上，必须用 event 先后排序；③ 这段优化由 SGLANG_DISAGG_PREFILL_EARLY_SEND_CACHED_PREFIX 控制，默认开着（EnvBool(True)）——它是快路径而非实验开关，所以上面那两个 return 的保守语义很重要：宁可少发这一次，也不留半页歧义，因为常规的最终发送会兜住全量。
staging 带来的额外一层： 开头那段快照逻辑是后加的。非 staging 时 cached_end 直接读 len(req.prefix_indices) 的实时值；staging 路径不行，因为它的暂存缓冲是按位置切格的：一个网格槽的宽度是 staging_grid_tokens(chunked_prefill_size, page_size)（即 chunked prefill 大小按页对齐，默认 8192 对齐到页），compute_grid_segments 在 base + k * grid_tokens 这些网格边界上切段，「每段恰好落进一个暂存槽」。而一个请求要占几个网格槽（num_chunks）是在预取时按传输总页数一次算定的——所以此前发送的边界必须在请求的各 batch 之间保持稳定，否则前后两次发送对不上同一套槽位。源码那两行注释写的就是这个约束。于是改成在第一个 batch 上把 early_send_prefix_end 快照一次，后续 batch 都读这个定值。req.pending_bootstrap 的提前返回也是同一类考虑：握手还没完成，decode 侧根本没有可以接收的槽位。同一个函数里，「实时值」和「快照值」两种取法并存——这是加 staging 时留下的形状，不是冗余。

12.5decode 侧：先占坑，再收货

decode 实例的顺序是反的：收到握手就先在 KV 池里把槽位占住（prealloc），等 KV 真正到达再合并进请求。两条队列的分工写在类 docstring 里：

读懂这段： 「prealloc」解决的是资源确定性——如果等 KV 到了再分配，decode 池可能已经没有空间，一条传了一半的 KV 只能扔掉。先占坑意味着传输失败的代价只是释放预留，而不是浪费已传输的数据。retracted_queue 和 resume_retracted_reqs 则把第 4 章的 retraction 机制接了进来：内存不足时 decode 请求也能被收回重排。

队列由 process_decode_queue（每轮循环驱动）串联，注意轮询频率是可配置的节流：

python/sglang/srt/disaggregation/decode.py — process_decode_queue（摘录，注释为译注）
pythondef process_decode_queue(self: Scheduler):
    ...
    # 有被收回的请求在等空间时，不再预分配新请求
    if len(self.disagg_decode_prealloc_queue.retracted_queue) > 0:
        return

    self.polling_count = (self.polling_count + 1) % self.polling_interval
    if self.polling_count % self.polling_interval == 0:
        req_conns, _ = self.disagg_decode_prealloc_queue.pop_preallocated()
        self.disagg_decode_transfer_queue.extend(req_conns)
        transferred_reqs = (
            self.disagg_decode_transfer_queue.pop_transferred()
        )  # KV 已到达的请求
        self.waiting_queue.extend(transferred_reqs)

KV 到达后请求进入 waiting_queue，由 get_new_prebuilt_batch 打包成 ForwardMode.PREBUILT 的 ScheduleBatch——名字里的「fake completed prefill」说明它的前向被跳过，直接以 decode 身份并入 running_batch。从这里开始，这条请求走的完全是第 2~4 章讲过的普通路径。

困惑点 为什么 prefill 的最后一步计算在 prefill 实例上做，而不是把输入 ids 传过去让 decode 实例 prefill？因为 KV 是「算一遍就要占一遍显存」的资产：在 prefill 侧算完再传，decode 侧只需要等一块连续缓冲；反过来传 ids 则要求 decode 侧同时具备 prefill 的峰值算力配置，混合负载下又回到老问题。分离的意义就是把峰值算力和峰值带宽拆到不同的机器上。

  • 缓冲区注册：启动时把 KV 池的显存段注册给传输引擎（GPU 直接 RDMA 读写，不经过 CPU 拷贝）。
  • KVArgs / TransferInfo：描述「哪些层、哪些槽位、什么形状」的传输清单，经 ZMQ 在两实例间交换。
  • KVPoll 状态机：Failed → Bootstrapping → WaitingForInput → Transferring → Success（base/conn.py:100），两侧队列都靠轮询它推进。

分层传输是让传输「不成气泡」的关键：每算完一层就能传一层，传输时间藏进后续层的计算时间里。对 hybrid 模型（如带 SWA/Mamba 层）还有一处细节——full-attention 层与总层数的序号换算（_transfer_start_layer），因为对端池里只有 full-attention 层的缓冲。

路由侧由 sgl-model-gateway（Rust）承担：以 --pd-disaggregation 启动时，router 把请求路由到 prefill 实例，并维护 prefill/decode 实例的负载与存活；decode 实例的挑选依据 bootstrap 信息回传。也就是说 请求级路由在 Rust router，KV 级路由在 bootstrap 房间握手，两层各管各的。

12.7对「自研引擎」的启示

要点 PD 分离是运维面翻倍的架构决策：两套实例、一套传输引擎、router 配置、RDMA 组网，都是新增故障点。自研引擎在单实例的混合调度调优（chunked prefill 配比、priority scheduling）走到头之前，不值得上。但有两个设计现在就能记下：① bootstrap 房间握手——用唯一 id（room）让两侧队列在无共享状态下对齐，这个模式适用于任何「生产者算完再交给消费者」的跨进程交接；② 先占坑再收货——接收侧先预留资源再收数据，失败时退资源而不是扔数据。传输部分（逐层 RDMA 写、预注册缓冲）本质是把第 11 章 HiCache 的「显存↔外部」搬运换成了「显存↔显存」，两者共用同一套 KVArgs 描述语言。下一步进入 第 13 章：投机解码。
