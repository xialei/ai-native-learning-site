RadixCache：用一棵基数树管住所有可复用的 KV

多轮对话、few-shot、共享 system prompt——这些请求的 token 序列开头一模一样，KV 却被反复重算。RadixCache 用一棵以 token id 为键的基数树记住「哪段前缀的 KV 还在池里」，这一章拆它的三个核心操作和淘汰/锁机制。

3.1一分钟版本

把一个 1000 token 的多轮对话请求拆开看：第 2 轮的输入 = 第 1 轮的全部输入输出 + 新增的一句话。前 1000 个 token 的 KV 已经算过，而且大概率还躺在显存里——上一轮请求结束后，它的 KV 槽位没有立刻被覆盖。问题是：引擎怎么知道「哪些槽位还留着这段前缀的 KV」？

SGLang 的答案是 RadixCache（python/sglang/srt/mem_cache/radix_cache.py）：

  • 树的内容：基数树的每条边是一段 token id 序列（页对齐），每个节点存 key（token id 段）和 value（这段 token 的 KV 在内存池里的槽位下标 tensor）。
  • 请求进来时：match_prefix 沿树往下走，找到最长的已缓存前缀，返回它的 KV 槽位下标——调度器直接把这些下标当作该请求的「已就绪部分」，只对剩余后缀做 prefill。
  • 请求算完后：insert 把它用过的 KV 槽位登记回树上，等下一个共享前缀的请求来认领。

注意一件容易忽略的事：树里存的是槽位下标，不是 KV 数据本身。数据始终留在 KV 池里；树只是「下标 → 内容」的记账本。所以淘汰一个节点 = 把下标还给分配器（数据随即被下一个分配覆盖），不需要搬移任何 KV。

3.3核心操作：match_prefix 与 insert

match_prefix 的公开入口很短，真正的语义藏在三行预处理里：

python/sglang/srt/mem_cache/radix_cache.py — match_prefix（摘录，注释为译注）
pythondef match_prefix(self, params: MatchPrefixParams) -> MatchResult:
    key = params.key
    # EAGLE 投机解码时改用 bigram 视图（见第 13 章）
    key, _ = key.maybe_to_bigram_view(self.is_eagle)

    if self.disable or len(key) == 0:
        return self._empty_match_result

    # 页对齐截断：page_size=16 时只匹配 16 的倍数长度
    key = key.page_aligned(self.page_size)

    if len(key) == 0:
        return self._empty_match_result

    value, last_node = self._match_prefix_helper(self.root_node, key)
    if value:
        value = torch.cat(value)
    else:
        value = self._empty_match_result.device_indices
    return MatchResult(device_indices=value, last_device_node=last_node, ...)
读懂这段： 两个决定复用粒度的细节。① page_aligned：开启分页（page_size>1）后，匹配长度向下取整到整页——因为 KV 池按页分配，半页的复用会让后缀 prefill 的页对齐变复杂，宁可少复用几个 token。② 命中结果 device_indices 是把沿途每个节点的 value 段 torch.cat 成的一个一维下标 tensor，调度器拿去直接当 prefix_indices 用。

逐层下行的辅助函数里能看到「劈节点」的时机：

python/sglang/srt/mem_cache/radix_cache.py — _match_prefix_helper（摘录，注释为译注）
pythondef _match_prefix_helper(self, node: TreeNode, key: RadixKey):
    access_time = time.monotonic()
    node.last_access_time = access_time

    child_key = key.child_key(self.page_size)
    value = []
    while len(key) > 0 and child_key in node.children.keys():
        child = node.children[child_key]
        child.last_access_time = access_time
        prefix_len = child.key.match(key, page_size=self.page_size)
        if prefix_len < len(child.key):
            # 请求的前缀在节点中间结束：把节点劈成两半，
            # 上半段成为新的终止节点（不复制 KV，只切下标）
            new_node = self._split_node(child.key, child, prefix_len)
            value.append(new_node.value)
            node = new_node
            break
        else:
            value.append(child.value)
            node = child
            key = key[prefix_len:]
            if len(key):
                child_key = key.child_key(self.page_size)
    return value, node
读懂这段： 匹配中止在节点内部时（prefix_len < len(child.key)），调用 _split_node 把该节点拆成父（共享前缀）+ 子（剩余段）。劈开不是复制的代价问题——value 只是被切片——而是为了让 inc_lock_ref/evict 能以节点为粒度工作：锁只加到匹配终点，终点半页以后的 KV 不该被顺手锁住。

insert 是镜像操作：沿树下行、复用已有段、在分叉处劈节点、把新段挂上。调用方不是调度主循环，而是请求收尾的两个钩子：

python/sglang/srt/mem_cache/radix_cache.py — insert（摘录，注释为译注）
pythondef insert(self, params: InsertParams) -> InsertResult:
    if self.disable:
        return InsertResult(prefix_len=0)

    key = params.key
    value = params.value
    priority = params.priority
    chunked = params.chunked

    key, value = key.maybe_to_bigram_view(self.is_eagle, value)
    key = key.page_aligned(self.page_size)
    if value is not None:
        value = value[: len(key)]
    else:
        # 调试/测试路径：直接拿 token id 当值
        value = torch.tensor(key.token_ids[: len(key)], dtype=torch.int64)

    prefix_len, last_node = self._insert_helper(
        self.root_node, key, value, priority, chunked
    )
读懂这段： insert 的两个入口在同一个文件里：cache_finished_req（请求完整结束，token 序列 = 输入+输出）和 cache_unfinished_req（chunked prefill 的中间块）。也就是说，树上登记的都是已经算完的 KV 段；正在算的请求靠锁保护自己的前缀，而不是靠树节点。
演进痕迹 命名空间隔离经历了从无到有的过程。最早的树只按 token id 分叉，所有请求共享一棵树；后来 RadixKey 增加了 extra_key（LoRA 适配器、采样盐等调用方自定义隔离），最近又把 cache_salt 从 extra_key 里独立出来——代码注释明确写着「kept distinct so it cannot collide with extra_key」，因为 L3/远端存储的键仍然只用 token，进程内外的命名空间契约必须分开表述。

3.4淘汰与锁：谁动得了这棵树

KV 池满了怎么办？答案是先从树上「借」：把最久没人用的叶子槽位收回来。淘汰的候选集是 evictable_leaves，用优先级堆组织：

python/sglang/srt/mem_cache/radix_cache.py — evict（摘录，注释为译注）
pythondef evict(self, params: EvictParams) -> EvictResult:
    if self.disable:
        return EvictResult()

    start_time = time.perf_counter()
    num_tokens = params.num_tokens
    leaves = list(self.evictable_leaves)
    eviction_heap = [
        (self.eviction_strategy.get_priority(node), node) for node in leaves
    ]
    heapq.heapify(eviction_heap)

    num_evicted = 0
    while num_evicted < num_tokens and len(eviction_heap):
        _priority, x = heapq.heappop(eviction_heap)

        # 把该节点的 KV 槽位还给分配器
        self.token_to_kv_pool_allocator.free_segment(x.value, start_pos=0)
        num_evicted += len(x.value)
        self._delete_leaf(x)

        # 父节点若变成无子的可淘汰节点，压入堆中
        if len(x.parent.children) == 0 and x.parent.lock_ref == 0:
            new_priority = self.eviction_strategy.get_priority(x.parent)
            heapq.heappush(eviction_heap, (new_priority, x.parent))

        self.kv_events.record_remove(x)
读懂这段： 三个要点。① 优先级由 eviction_strategy.get_priority 决定，默认 LRU（last_access_time）。② free_segment 归还的是物理槽位；树节点被删，数据等下次分配被覆盖。③ 淘汰只从叶子开始，父节点要等所有孩子都没了才暴露为叶子——这保证被淘汰的永远是一段完整后缀，不会在中间挖洞。
容易搞混的一对 TreeNode.__lt__ 比的是 last_access_time，而堆里排序用的 不是 __lt__，是 eviction_strategy.get_priority(node)。两者在默认 LRU 下刚好一致（LRUStrategy.get_priority 就 return node.last_access_time），所以读代码时容易以为是同一个东西。实际有七种策略可选（lru / lfu / fifo / mru / filo / priority / slru，--radix-eviction-policy，默认 lru），它们的返回值形态不同：LFUStrategy 返回 (hit_count, last_access_time)、SLRUStrategy 返回 (分段号, last_access_time)——都是元组，靠 Python 的元组比较做「先按主键、再按 LRU 打破平局」。PriorityStrategy 的元组是 (priority, last_access_time)，值小的先被淘汰；而 priority 字段本身在 insert 时沿途取 max 向上传播（node.priority = max(node.priority, priority)），根节点则初始化为 -sys.maxsize，保证它永远排在最后。

锁是树的第二个保护层。一个正在运行的请求会把从匹配终点到根的整条路径锁住：

python/sglang/srt/mem_cache/radix_cache.py — inc_lock_ref / dec_lock_ref（摘录，注释为译注）
pythondef inc_lock_ref(self, node: TreeNode) -> IncLockRefResult:
    if self.disable:
        return IncLockRefResult(delta=0)

    delta = 0
    while node != self.root_node:
        if node.lock_ref == 0:
            # 从可淘汰账本挪进受保护账本
            self.evictable_size_ -= len(node.key)
            self.protected_size_ += len(node.key)
            delta -= len(node.key)
        node.lock_ref += 1
        self._update_leaf_status(node)
        node = node.parent
    return IncLockRefResult(delta=delta)

def dec_lock_ref(self, node: TreeNode, ...) -> DecLockRefResult:
    ...
    while node != self.root_node:
        if node.lock_ref == 1:
            self.evictable_size_ += len(node.key)
            self.protected_size_ -= len(node.key)
            delta += len(node.key)
        node.lock_ref -= 1
        ...
读懂这段： 两个账本随锁移动：evictable_size_ 是「可以腾出来的 token 数」，protected_size_ 是「被运行中请求或显式引用锁住的 token 数」。调度器做内存预算时读这两个数（第 4 章的 PrefillAdder 预算、第 5 章的显存水位都依赖它们）。注意锁是沿路径向上累加到根的——因为淘汰是从叶子往根的方向，中间任何一层锁住都足以保护整条前缀。

这个元组为什么这么长：它已经从一个「匹配结果」长成了一个「按层类型分类的匹配结果」。最初只有前两项（槽位 + 终点节点），后来 HiCache 加进来长了 host_hit_length，再后来滑动窗口层（swa_*）和 Mamba/线性注意力层（mamba_*）各自有了独立的命中长度——因为这三类层能复用的历史长度不一样：全注意力层能复用整段前缀，滑动窗口层只能复用最后 window_size 个 token，Mamba 类层的状态则有个「分支点」概念（branching_seqlen，超过它状态就不能直接续用，必须重算）。如果你在别的分支上看到过只有 5 项的版本，那是这个元组扩张过程中的中间形态。

第三个交互在 chunked prefill。长输入被切成多个块，每算完一块就登记一次树：

python/sglang/srt/managers/scheduler.py — stash_chunked_request（摘录，注释为译注）
pythondef stash_chunked_request(self, req: Req):
    maybe_cache_unfinished_req(req, self.tree_cache, chunked=True)

对应到树这边的 cache_unfinished_req（radix_cache.py:539）：把已算好的段 insert 进树、立刻重新 match 一次、用新 prefix_indices 覆盖请求的旧值，然后换锁（dec_lock_ref(req.last_node) → inc_lock_ref(new_last_node)）。这么做的好处是：如果同一前缀的另一个请求此刻到达，它能命中已完成的那几块，而不是等整个 prefill 结束。

困惑点 cache_unfinished_req 里有个专门的 cache_protected_len 字段，注释解释了为什么需要它：page_size>1 时，insert 只把整页部分放进树，末尾的半页留在 prefix_indices 里但不在树上；这半页的槽位不能在中间块结束时归还（下一个块还要接着用），也不能永远占着——所以单独记一个「受保护长度」，推迟到下一个块或最终收尾时统一释放。这是页对齐与树记账之间的一次典型补丁：先有按 token 的树，后有按页的池，接缝处需要这个字段对齐两套粒度。

3.6RadixAttention 名字辨析

困惑点 模型层里那个 RadixAttention 类和这棵树是什么关系？——没有运行时关系。打开 layers/radix_attention.py 会发现它只是「QKV 投影之后、注意力 kernel 之前」的分发层：保存 KV、选后端、转发调用。基数树在 mem_cache/radix_cache.py，两者互相不 import。名字是历史的留存：SGLang 论文（RadixAttention, 2023）发表时，前缀复用和注意力层是论文里的一套系统，类名沿用了论文标题；今天的实现里，注意力层对「KV 存在哪、谁复用它」完全不感知——它只管把 q/k/v 和 forward_batch 交给后端。读代码时不要被名字带偏，找「radix」的实现要去 mem_cache/ 目录。

3.7对自研引擎的启示

要点 这套机制的 v1 版本比看起来小得多：一棵精确匹配的 token id 基数树 + evictable/protected 两个计数器，两三百行 Python 就够，多轮对话能直接砍掉大半 prefill。真正踩过坑之后才需要补的是两件事：① 页对齐——池一旦按页分配，树的匹配、锁、淘汰全都要跟着取整，cache_protected_len 这类补丁字段就是为对齐两套粒度而生；② 命名空间——LoRA、cache_salt、多租户隔离，靠在 RadixKey 里加一个 extra_key 字段解决，别等到缓存串味了再补。反而「近似匹配」「语义缓存」这类花活，生产里几乎用不上。下一步进入 第 4 章：调度器与调度策略。

想继续追「KV 出了 GPU 之后怎么复用」，直接跳到 第 11 章 HiCache；想看树怎么被投机解码改写成 bigram 视图，见 第 13 章。
