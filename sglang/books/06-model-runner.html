ModelRunner：从 ScheduleBatch 到 GPU 前向

调度器决定「这一步跑哪些请求」之后，谁来把这些 Python 对象变成 GPU 张量、喂进模型、采样出 token？这一章拆 TpModelWorker 与 ModelRunner 的分工，以及 forward 的三级路径：decode 图回放、prefill 分段图、eager 回退。

6.1一分钟版本

Scheduler 调 run_batch 后，实际前向在 TpModelWorker.forward_batch_generation 里完成，链条是：

  • ScheduleBatch → ForwardBatch：ForwardBatch.init_new(batch, model_runner) 把调度侧的请求列表压平成一批 GPU 张量；
  • forward：model_runner.forward(forward_batch) 走三级路径（图回放 / 分段图 / eager），输出 logits；
  • sample：model_runner.sample(logits_output, forward_batch) 把 logits 变成 next_token_ids（第 8 章展开）。

三级路径指：decode CUDA Graph 整图回放 → prefill 分段 CUDA Graph（tc_piecewise）→ eager 逐算子执行。能否走图由 batch 形状决定，判断代码集中在 _forward_raw。

6.3ForwardBatch 与 ScheduleBatch：为什么是两个类

初读最容易困惑的地方：调度器里明明有 ScheduleBatch，为什么还要再造一个 ForwardBatch？分工是——ScheduleBatch 面向调度（持有 reqs: List[Req]，每个 Req 是有状态的 Python 对象，含输出列表、采样参数、grammar 状态）；ForwardBatch 面向一次前向（全部压成 GPU 张量，无 Python 对象）。前向要的每个字段都来自压平操作，模型代码只认 ForwardBatch。

python/sglang/srt/model_executor/forward_batch_info.py — ForwardBatch 核心字段（摘录，注释为译注）
pythonclass ForwardBatch(ForwardBatchDeepSeekMHAMixin):
    """Store all inputs of a forward pass."""

    # === 必需核心输入（input_ids / req_pool_indices / seq_lens /
    #     out_cache_loc 从 ScheduleBatch 按引用借用）===
    forward_mode: ForwardMode          # EXTEND / DECODE / MIXED / ...
    batch_size: int
    input_ids: torch.Tensor            # 本步喂给模型的 token
    req_pool_indices: torch.Tensor    # 每个请求在 ReqToTokenPool 的行号
    seq_lens: torch.Tensor             # 每个请求当前序列长度
    out_cache_loc: torch.Tensor       # 新 token 的 KV 写入槽位
    seq_lens_sum: int

    # === 从 ScheduleBatch 借用：GPU 张量（跨流；流隔离时的克隆目标）===
    # FIXME(lsyin): 这些字段目前仍以引用方式与 ScheduleBatch 共享……
读懂这段： 注释里的 FIXME 是真实演进痕迹：核心四字段目前还与 ScheduleBatch 按引用共享（overlap 模式下两条 CUDA stream 同时读写），计划未来在边界处克隆成 ForwardBatch 私有副本。这解释了为什么 overlap 模式需要 resolve_forward_inputs 这一层（第 2 章）。

模式枚举也集中在这里。值得注意 is_extend() 的范围比名字大——投机验证、split prefill 都算 extend 家族：

python/sglang/srt/model_executor/forward_batch_info.py — ForwardMode（摘录，注释为原文+译注）
pythonclass ForwardMode(IntEnum):
    # Extend a sequence. The KV cache of the beginning part of the sequence
    # is already computed (e.g., system prompt).
    EXTEND = auto()
    # Decode one token.
    DECODE = auto()
    # Contains both EXTEND and DECODE when doing chunked prefill.
    MIXED = auto()
    # No sequence to forward. For data parallel attention, some workers
    # will be IDLE if no sequence are allocated.
    IDLE = auto()
    # Used in speculative decoding: verify a batch in the target model.
    TARGET_VERIFY = auto()
    # Used in speculative decoding: extend a batch in the draft model.
    DRAFT_EXTEND_V2 = auto()
    # Used in disaggregated decode worker …
    PREBUILT = auto()
    # Split Prefill for PD multiplexing
    SPLIT_PREFILL = auto()
    # Used in dLLM
    DLLM_EXTEND = auto()
读懂这段： 一个 batch 只有一个 ForwardMode——MIXED（chunked prefill 场景 prefill 与 decode 混跑）是唯一例外。IDLE 存在的理由在注释里：DP attention 下分不到请求的 worker 也要参与集合通信，得有「空跑」模式。
两个容易看漏的成员： DRAFT_EXTEND_V2 在 is_extend() 里被单独用参数 include_draft_extend_v2 控制，默认不算 extend——它是草稿模型侧的扩展，不是目标模型的 prefill，这个默认值一直是个易错点。DLLM_EXTEND 则被无条件算作 extend，因为 dLLM（扩散语言模型）的整块去噪在调度语义上就是一次 prefill。同一个谓词里两个成员两种待遇，读的时候值得对着 forward_batch_info.py:205-213 看一眼。

6.4转换发生在哪：prepare_for_extend 与 init_new

压平工作分两段。Scheduler 侧的 prepare_for_extend 负责 prefill 的输入组装与 KV 分配：

python/sglang/srt/managers/schedule_batch.py — ScheduleBatch.prepare_for_extend（摘录，注释为译注）
pythondef prepare_for_extend(self):
    self.forward_mode = ForwardMode.EXTEND

    if self.is_dllm():
        # dLLM 走单独的 forward mode，虽然在调度语义上仍是 prefill
        self.forward_mode = ForwardMode.DLLM_EXTEND

    reqs = self.reqs
    # 填充 id 序列去掉已命中前缀，只算增量
    input_ids = [r.get_fill_ids()[len(r.prefix_indices) :] for r in reqs]
    extend_num_tokens = sum(len(ids) for ids in input_ids)
    seq_lens = [r.extend_range.end for r in reqs]
    # orig_seq_lens 取「填充区间终点」与「原始输入长度」的较大者
    orig_seq_lens = [max(r.extend_range.end, len(r.origin_input_ids)) for r in reqs]
    prefix_lens = [len(r.prefix_indices) for r in reqs]
    extend_lens = [r.extend_range.length for r in reqs]
    ...
    # 分配 KV 槽位 + req 池行号（调 mem_cache/allocation.alloc_for_extend）
    out_cache_loc, req_pool_indices_tensor, req_pool_indices_cpu = alloc_for_extend(self)
读懂这段： prefix_indices 是 RadixCache 命中的前缀槽位（第 3 章），prefill 只需对增量部分做前向。alloc_for_extend（mem_cache/allocation.py:344）返回三元组：新 token 的 KV 槽位、每请求在 req 池中的行号（设备与 CPU 两份）。decode 步骤的对应操作是 prepare_for_decode，结构类似。

worker 侧的 init_new 只做字段搬运，不做计算。注意 init_new must not mutate the input ScheduleBatch 这条契约：

python/sglang/srt/model_executor/forward_batch_info.py — ForwardBatch.init_new（摘录，注释为译注）
python@classmethod
def init_new(cls, batch: ScheduleBatch, model_runner: ModelRunner, ...):
    # init_new 不得修改输入的 ScheduleBatch；per-forward 覆盖走显式关键字参数。
    ...
    ret = cls(
        # 必需核心输入
        forward_mode=batch.forward_mode,
        batch_size=len(batch.seq_lens),
        input_ids=batch.input_ids,
        req_pool_indices=batch.req_pool_indices,
        seq_lens=batch.seq_lens,
        out_cache_loc=batch.out_cache_loc,
        seq_lens_sum=batch.seq_lens_sum,
        ...)
读懂这段： 这份「不修改输入」的约束是为 overlap 调度服务的：ScheduleBatch 在调度 stream 上继续被改写（比如 prep 下一个 batch），ForwardBatch 在 forward stream 上消费，共享字段必须只在调度侧写入。违例会造成极难复现的数据竞争。

最后串起前向与采样的是 TpModelWorker.forward_batch_generation：

python/sglang/srt/managers/tp_worker.py — forward_batch_generation（摘录，注释为译注）
pythondef forward_batch_generation(self, batch, forward_batch=None, ...):
    if batch is not None:
        forward_batch = ForwardBatch.init_new(
            batch, self.model_runner, capture_hidden_mode=capture_hidden_mode, ...
        )
    ...
    out = self.model_runner.forward(forward_batch, ...)
    logits_output, can_run_cuda_graph = out.logits_output, out.can_run_graph
    ...

读懂这段： 中间省略的分支有两个值得记住：spec 验证步（is_verify）跳过采样，验证逻辑由投机 worker 接管（第 13 章）；overlap 模式下采样可能被包进 delay_sample_func 延迟执行，让 GPU 先跑下一批的前向。

6.5forward 的三级路径

_forward_raw 是路径分发的唯一入口。第一级判断：模式是否可跑图 + runner 是否认可这个 batch：

python/sglang/srt/model_executor/model_runner.py — _forward_raw（摘录，注释为译注）
pythonmode_check = (
    forward_batch.forward_mode.is_cpu_graph
    if self.device == "cpu" else forward_batch.forward_mode.is_cuda_graph
)
can_run_graph = bool(
    mode_check()
    and self.decode_cuda_graph_runner
    and self.decode_cuda_graph_runner.can_run_graph(forward_batch)
)
...
# 能跑图：整图回放，直接返回
if can_run_graph:
    ret = self.decode_cuda_graph_runner.execute(forward_batch, ...)
    return ModelRunnerOutput(logits_output=ret, can_run_graph=can_run_graph)

# 走不到图：先做 DP padding 等准备工作，再分派
self._prepare_eager_forward_batch(forward_batch)
...
elif (
    forward_batch.forward_mode.is_extend(include_draft_extend_v2=True)
    and not isinstance(self.prefill_cuda_graph_runner, EagerRunner)
    and self.prefill_cuda_graph_runner is not None
    and self.prefill_cuda_graph_runner.can_run_graph(forward_batch)
    and _prefill_cuda_graph_allows_context_parallel(
        self.prefill_cuda_graph_runner, forward_batch
    )
):
    # prefill 分段图（piecewise）
    ret = self.prefill_cuda_graph_runner.execute(forward_batch, **kwargs)
else:
    # eager：decode / extend / idle 都在这个 runner 内分派
    ret = self.eager_runner.execute(forward_batch, ...)
读懂这段： 注意注释里的细节：只有 decode 图路径会预先填充静态缓冲并提前返回；split prefill、prefill 图、eager 都要先过 _prepare_eager_forward_batch 做 DP padding——因为那些路径跑的是真实 batch 形状。

decode 图 runner 支持三种后端配置，文件头的 docstring 写得很直白：

python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py — 后端选择（摘录，docstring 译文）
textDecodeCudaGraphRunner — runs DECODE / TARGET_VERIFY / DLLM_EXTEND under

Backend selection comes from cuda_graph_config.decode:

  - "breakable" — experimental, BreakableCudaGraphBackend:
                      segmented capture (no torch.compile).
  - "tc_piecewise"     — not implemented for decode; logs a one-shot warning

读懂这段： 默认 full：每个捕获形状一张完整 torch.cuda.CUDAGraph。breakable 是实验性的分段捕获（图内允许断点、不依赖 torch.compile）。tc_piecewise 只用于 prefill，decode 请求它会警告并退回 full。这是「同一个语义、三种捕获策略」的演进现场：full 最快但形状最死，breakable 换灵活性，仍在验证中。

回放前必须把真实数据拷进捕获时定下的静态 buffer——这就是 padding 的物理实现：

python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py — execute 与 load_batch（摘录，注释为译注）
pythondef execute(self, forward_batch, pp_proxy_tensors=None):
    ...
    with timer_ctx, self.backend.replay_session():
        self.load_batch(forward_batch, pp_proxy_tensors)   # 真实数据 → 静态 buffer
        ...
        output = self.backend.replay(self._replay_graph_key, forward_batch)
    ...
    # 回放按捕获形状算，输出多出来的 padding 行要切掉
    next_token_logits = (
        output.next_token_logits[: self.raw_num_token] # raw_num_token = 真实 token 数
        if output.next_token_logits is not None
        else None
    )

def load_batch(self, forward_batch, ...):
    ...
    self.buffers.input_ids[: self.raw_num_token].copy_(forward_batch.input_ids)
    self.buffers.positions[: self.raw_num_token].copy_(forward_batch.positions)
读懂这段： 捕获时 batch 大小被 pad 到 capture_bs 列表里的固定值（如 1, 2, 4, 8 …），每档一张图；回放时选不小于真实 bs 的最小档，load_batch 把真实数据拷进前 raw_num_token 行，跑完再把输出切片回去。padding 行指向 ReqToTokenPool 的第 0 行（第 5 章讲过的保护行），读写都无害。

什么样的 batch 会被拒之图外？can_run_graph 列了一串条件：

python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py — can_run_graph（摘录，注释为原文+译注）
pythondef can_run_graph(self, forward_batch: ForwardBatch):
    # Disable for token embedding overrides (dynamic per-request)
    if forward_batch.replace_embeds is not None:
        return False
    ...
    if self.require_mlp_tp_gather:
        cuda_graph_bs = self._max_dp_batch_size(forward_batch)
    else:
        cuda_graph_bs = forward_batch.batch_size
    ...
    is_bs_supported = (
        self.backend.can_run(forward_batch, graph_key)
        if self.disable_padding
        else cuda_graph_bs <= self.max_bs
    )
    ...
    # NOTE: cuda graph cannot handle mixed batch (encoder_len = 0)
    is_encoder_lens_supported = (
        torch.all(forward_batch.encoder_lens > 0)
        if self.is_encoder_decoder
        else True
    )
读懂这段： 拒绝图的条件都是「形状动态」类的：embedding 覆写（每请求不同）、投机宽度与捕获宽度不一致、多模态 encoder 长度为 0、bs 超过最大捕获档。默认 disable_padding=False 时 bs 档位不齐也能 pad 进图；关掉 padding 后就必须精确匹配。

6.6CUDA Graph 为什么对 decode 关键

decode 一次前向只有 batch_size 个 token，算子都很小，GPU 大部分时间在等 kernel 启动，而不是计算。CUDA Graph 把几百个 kernel 启动压成一次回放调用，省掉的就是这些 CPU 端的启动开销。prefill 一次几千个 token，单算子够大，启动开销占比低，所以 prefill 走图是可选优化（分段图），decode 走图几乎是标配。

代价也很明确：

  • 形状固定：每档 bs 一张图，显存占用随档位数与模型宽度增长；
  • 捕获耗时：启动时逐档捕获，模型越大越久（SGLang 按倒序捕获，大档先跑，失败尽早暴露）；
  • 动态形状被迫回 eager：bs 超档、投机宽度不匹配、多模态 encoder、embedding 覆写，全都回到逐算子路径。
困惑点 回放时 batch 大小明明在变，图里的张量形状却是固定的，数据从哪来？答案是回放不走 ForwardBatch 的原张量，而是 load_batch 把真实数据 copy_ 进捕获时预留的静态 buffer；attention 需要的变长信息（seq_lens、页表）单独走 init_forward_metadata_out_graph / init_forward_metadata_in_graph 两个钩子在图外/图内刷新——这正是第 7 章注意力后端三钩子契约的由来。

6.8对「自研引擎」的启示

要点 自研引擎 v1 不需要 CUDA Graph。先把 eager 路径做对：ScheduleBatch → 张量 batch 的压平、KV 写入槽位、采样，这三件事的正确性比吞吐重要。图捕获本质是一个「pad 到固定形状、回放时切片」的练习——理解了 load_batch 的 copy + raw_num_token 切片就掌握了八成。真正难的不是 torch.cuda.CUDAGraph API，而是让注意力后端在「图内静态形状」与「真实变长 batch」之间保持一致（第 7 章的三钩子契约）。下一步进入 第 7 章：注意力后端。
