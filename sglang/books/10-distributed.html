分布式推理：TP / PP / DP / EP 各管什么

SGLang 的分布式不是一个东西，而是四个正交的维度：TP 切权重、PP 切层、DP 复制整个模型、EP 切专家。这一章讲清每个维度切的是什么、通信发生在哪，以及 dp_size>1 时那个专门的分发进程在做什么。

10.1一分钟版本

四个维度切的对象不同，通信模式也不同：

  • TP（张量并行）：把每一层的权重矩阵切开，每卡持有一份分片，一次前向每层做 1~2 次 allreduce。解决「单卡装不下 / 算不快一个大模型」。
  • PP（流水线并行）：按层分段，各 stage 之间只传激活张量。解决「跨机带宽跑不动 TP」。
  • DP（数据并行）：整个模型复制多份，每个 DP 组服务不同的请求。解决吞吐，不解决模型大小。
  • EP（专家并行）：MoE 模型把专家分到不同卡，token 按路由结果跨卡传输。解决专家参数总量放不下单卡。

对应到 SGLang 的进程模型（第 1 章）：每个 TP rank 一个 Scheduler 子进程，TP 组内各 rank 通过 NCCL/自定义 allreduce 同步；dp_size > 1 时多了一个 DataParallelController，按负载均衡策略把请求路由到某个 DP 组；PP 有自己独立的事件循环；EP 则藏在 MoE 层内部，不改变进程结构。

维度切什么通信发生在哪什么时候用
TP每层权重矩阵（列/行并行）每层前向 1~2 次 allreduce（NCCL 或 custom allreduce）单卡放不下权重或想降延迟
PP层序列分段stage 边界点对点传激活（pp_proxy_tensors）跨机、机间带宽有限
DP不切模型，切请求请求级路由（ZMQ），组间无集合通信吞吐不够、模型已能放进一组卡
EPMoE 的专家列表token 按专家路由分发（all-to-all 类通信）MoE 模型专家总数过大

10.3DataParallelController：dp_size>1 时的邮差

回顾第 1 章的 _launch_scheduler_processes：只要 dp_size > 1（或弹性 EP 的 ep_join_mode == "scale"），进程编排就走 DataParallelController 分支。它做的事很集中——把 TokenizerManager 发来的请求按策略转发给某个 DP 组：

python/sglang/srt/managers/data_parallel_controller.py — 负载均衡方法与分发表（摘录，注释为译注）
pythonclass LoadBalanceMethod(Enum):
    """Load balance method."""

    ROUND_ROBIN = auto()
    FOLLOW_BOOTSTRAP_ROOM = auto()
    TOTAL_REQUESTS = auto()
    TOTAL_TOKENS = auto()

# __init__ 里注册四个分发函数
self.round_robin_counter = 0
dispatch_lookup = {
    LoadBalanceMethod.ROUND_ROBIN: self.round_robin_scheduler,
    LoadBalanceMethod.FOLLOW_BOOTSTRAP_ROOM: self.follow_bootstrap_room_scheduler,
    LoadBalanceMethod.TOTAL_REQUESTS: self.total_requests_scheduler,
    LoadBalanceMethod.TOTAL_TOKENS: self.total_tokens_scheduler,
}
self.dispatching = dispatch_lookup[self.load_balance_method]

后两种方法基于一份负载快照选目标。快照不是 controller 自己猜的，而是各 Scheduler 定期发布、经共享内存回流（图 10.2 的虚线），DPBudget.dispatch 拿它做选择：

python/sglang/srt/managers/data_parallel_controller.py — DPBudget.dispatch（摘录，注释为译注）
pythondef dispatch(self, method: LoadBalanceMethod, estimated_tokens: int = 0):
    if method == LoadBalanceMethod.TOTAL_REQUESTS:
        target_rank = self.total_requests.index(min(self.total_requests))
    elif method == LoadBalanceMethod.TOTAL_TOKENS:
        # token 数相同时用请求数决出先后
        target_rank = min(
            range(self.dp_size),
            key=lambda i: (self.total_tokens[i], self.total_requests[i]),
        )
    else:
        return None

    # 先记账再发送：刚选中的 rank 立刻加一，避免连发打到同一组
    self.total_requests[target_rank] += 1
    self.total_tokens[target_rank] += estimated_tokens
    return target_rank

四种方法的适用场景。注意 --load-balance-method 的字段默认值是 "auto"，在 handle_load_balance_method 里才解析成上表的具体方法：非 PD 与 PD decode 落到 round_robin，PD prefill 落到 follow_bootstrap_room（prefill 侧必须把请求送到 decode 侧等着的那一组，不能自己均衡）：

方法选择依据适用场景
round_robin轮询计数器请求长短均匀；auto 在非 PD 与 PD decode 下的落点
total_requests各组的运行+排队请求数取最少请求负载以条数计
total_tokens各组总 token 数（按输入长度预估）取最少长 prompt 混短 prompt，条数均衡会失真
follow_bootstrap_roomreq.bootstrap_room % 组数，不做均衡PD 分离：prefill 与 decode 实例必须命中同一个请求

最后一种最特殊。它不看负载，只看请求自带的路由号：

python/sglang/srt/managers/data_parallel_controller.py — follow_bootstrap_room_scheduler（摘录，注释为译注）
pythondef follow_bootstrap_room_scheduler(self, req: Req):
    if self.maybe_external_dp_rank_routing(req):
        return

    assert req.bootstrap_room is not None, (
        "req.bootstrap_room should not be None. Do not send requests directly to "
        "prefill or decode instances; send to the router instead."
    )
    target_rank = req.bootstrap_room % len(self.workers)
    sock_send(self.workers[target_rank], req)
读懂这段： bootstrap room 是 PD 分离部署里 prefill 实例与 decode 实例约定的「会面房间号」（第 12 章展开）。断言文案本身说明了约束：不要绕过 router 直接给 prefill/decode 实例发请求——房间号是 router 分配的，绕过它房间号对不上。
困惑点 为什么 TP 不需要一个 controller，DP 需要？因为两者是不同层面的问题。TP 组内所有 rank 必须逐层执行同一个 batch，靠集合通信（allreduce）在数据面强制同步；DP 组之间彼此独立，各跑各的 batch，唯一要做的只是决定「这条请求发给谁」——一个控制面的路由问题。所以 TP 的正确性由 NCCL 保证，DP 的正确性只由这个 ZMQ 邮差保证。

10.4TP 通信：GroupCoordinator 与 allreduce 选路

TP 组内的同步集中在 GroupCoordinator——它包着 PyTorch 的 ProcessGroup，但所有集合操作先经过它路由。all_reduce 是最热的一条路（每层前向 1~2 次），选路逻辑按平台和消息大小分流：

python/sglang/srt/distributed/parallel_state.py — GroupCoordinator.all_reduce 的选路（摘录，注释为译注）
pythondef all_reduce(self, input_: torch.Tensor) -> torch.Tensor:
    # 单卡直接返回
    if self.world_size == 1:
        return input_

    if input_.is_cpu:
        if is_shm_available(input_.dtype, self.world_size, self.local_size):
            torch.ops.sgl_kernel.shm_allreduce(input_, REDUCE_OP_SUM)
        else:
            torch.distributed.all_reduce(input_, group=self.device_group)
        return input_

    # 各平台专用通信器（hpu / xpu / npu）逐一尝试，命中即返回
    if self.hpu_communicator is not None and not self.hpu_communicator.disabled:
        return self.hpu_communicator.all_reduce(input_)
    if self.xpu_communicator is not None and not self.xpu_communicator.disabled:
        inplace_all_reduce(input_, group_name=self.unique_name)
        return input_
    if self.npu_communicator is not None and not self.npu_communicator.disabled:
        return self.npu_communicator.all_reduce(input_)

    # 编译态（CUDA Graph / torch.compile）下不能按张量形状分支，
    # 否则每个 shape 都要重新编译——统一交给运行时的 opaque 自定义算子
    if torch.compiler.is_compiling():
        if self._can_use_flashinfer_allreduce(input_):
            return flashinfer_allreduce(input_, group_name=self.unique_name)
        if (self.ca_comm is None and self.qr_comm is None
                and self.pymscclpp_comm is None
                and self.torch_symm_mem_comm is None
                and self.pynccl_comm is None):
            inplace_all_reduce(input_, group_name=self.unique_name)
            return input_
        return outplace_all_reduce(input_, ..., method="auto")

    should_use_custom_allreduce = (
        self.ca_comm is not None
        and not self.ca_comm.disabled
        and self.ca_comm.should_custom_ar(input_)
    )
    ...  # 非编译态：pymscclpp → symmetric memory pynccl → flashinfer →
    # _resolve_outplace_all_reduce_method，逐个排除后落到 torch 默认
读懂这段： 单卡短路和 CPU 短路写在最前面，都是为了让常见情形不付检查成本。custom allreduce 只在「消息够小 + 链路够好」时才赢，所以判定函数被压成一个布尔量提前算出来。
这不是二选一，是六路选择： 早先读这段容易得到「custom allreduce 还是 NCCL」的二元印象，现在的实际路径是：平台专用通信器（hpu / xpu / npu）→ 编译态分支 → pymscclpp → symmetric-memory 的 pynccl → flashinfer allreduce → _resolve_outplace_all_reduce_method → torch 默认。其中编译态那一段最值得注意：源码注释写得很清楚，按字节大小和链路选路的逻辑（_pick_algo / should_mscclpp_allreduce）在编译态下会 guard 到符号化的 token 维度上，每换一个 shape 就要重新编译一次，所以整段判断被推迟到运行时——统一发一个 method="auto" 的 opaque 自定义算子，由算子内部再决定。另外 symmetric-memory 的原地路径在编译态下被刻意绕开：它的裸 pynccl 调用不可追踪（fullgraph 下直接报错），而且原地语义塞不进 outplace 自定义算子的契约。

custom allreduce 的适用条件写在 should_custom_ar 里，是个纯字节级的判断：

python/sglang/srt/distributed/device_communicators/custom_all_reduce.py — should_custom_ar（摘录）
pythondef should_custom_ar(self, inp: torch.Tensor):
    if self.disabled:
        return False
    inp_size = inp.numel() * inp.element_size()
    # custom allreduce requires input byte size to be multiples of 16
    if inp_size % 16 != 0:
        return False
    if not is_weak_contiguous(inp):
        return False
    # for 4 or more non NVLink-capable GPUs, custom allreduce provides
    # little performance improvement over NCCL.
    if not _is_hip:
        if self.world_size == 2 or self.full_nvlink:
            return inp_size <= self.max_size
        return False

    # AMD 侧（HIP）：确定性实现无条件放行；否则同样要求全互联 + 消息够小
    if _is_hip:
        if self.use_amd_deterministic_impl:
            return True
        if self.full_nvlink:
            return inp_size <= self.max_size
        return False

    return False
读懂这段： 决策三要素：消息字节大小（小消息走 custom allreduce，直接读对端注册的 IPC 缓冲区，一次往返完成；超过 max_size 落回 NCCL）、链路（要 NVLink 全互联或仅 2 卡，PCIe 上收益趋零）、对齐（16 字节倍数）。decode 阶段 batch 小、激活小，几乎每层都命中 custom allreduce——这是小 batch 延迟的重要来源之一。TP 的另一处集合通信在词表并行：lm_head 按列切分后各 rank 只有一段词表的 logits，需要 all_gather 拼回完整分布。
HIP 分支是后加的： 注意 _is_hip 出现了两次——一次是 NVIDIA 侧提前返回，一次是 AMD 侧单独判断。AMD 路径多出一个短路条件 use_amd_deterministic_impl：开了确定性实现就无条件放行，不再看链路和消息大小。这是个值得留意的形状——「确定性」在这里不是靠牺牲正确性换的，而是换了一条实现路径，代价（性能）由用户自己权衡，所以判断条件从「能不能快」变成了「用户要不要这个保证」。

10.5dp_attention：注意力复制、MoE 分片

DeepSeek 这类 MLA 模型有个不对称性：注意力的 KV 很小（每 token 只存一个 latent 向量加 rope），而 MoE 层的参数和计算占大头。把注意力也切成 TP 会引入频繁的 allreduce，收益却小。--enable-dp-attention 的思路是反着来：注意力侧按 DP 复制（每个 rank 持有自己的请求和 KV），MoE 侧仍按 TP/EP 分片。

token 在两种并行模式之间的搬运靠一对 gather/scatter：进入 MoE 前，把各 DP rank 的本地 token 拼成一个全局缓冲区；MoE 算完后再切回各自的本地段：

python/sglang/srt/layers/dp_attention.py — dp_gather_partial 与 dp_scatter（摘录，注释为译注）
pythondef dp_gather_partial(

    # 本地 token → 全局缓冲区（all_gatherv 类操作）
    _dp_gather(global_tokens, local_tokens, forward_batch, is_partial=True)

def dp_scatter(
    local_tokens: torch.Tensor,  # 输出：本 rank 的那一段
    global_tokens: torch.Tensor,  # 输入：拼好的全局 token
    forward_batch: ForwardBatch,
):
    local_start_pos, local_num_tokens = get_dp_local_info(forward_batch)
    local_tokens.fill_(0)
    ...
    if local_tokens.shape[0] > 0:
        memcpy(local_tokens, global_tokens,
               0, local_start_pos, local_num_tokens, True)
读懂这段： 每层前向的模式就固定成三步：注意力各 rank 算各自的（无通信）→ dp_gather 汇总 → MoE 在全局 token 上计算 → dp_scatter 切回。CUDA Graph 要求形状固定，所以全局/本地缓冲区长度有 max/sum 两种填充模式（get_dp_padding_mode）。这套机制下每张卡仍然是一个完整的 Scheduler 进程，只是并行组划分变了：attn_tp_size = tp_size // attn_dp_size // attn_cp_size，注意力组与 MoE 组是同一批卡的不同切法。
布局约束常被误传： 流传较广的说法是「只支持 attn_tp_size == 1、tp_size == dp_size」，但这只对了一部分。源码只断言 tp_size % dp_size == 0，此外 tp_size % (dp_size * attn_cp_size) == 0——并不要求两者相等。attn_tp_size > 1 是一条活跃支持的路径：layers/communicator.py 与 layers/logits_processor.py 都有 attn_tp_size > 1 的分支，还会为这种形状专门打一条提示日志（"DSA with TP mode is active… attention weights will be sharded across N ranks"）。tp_size == dp_size 这个约束只对 flashinfer MegaMoE 成立。「注意力 TP 与 DP 正交」才是这套设计的一般形态，tp8dp8 只是 attn_tp_size=1 的那个特例。锚点：断言 parallel_hook.py:186（第二条在 :76）、分支 layers/logits_processor.py:422、提示日志 arg_groups/model_hook.py:234。

10.6PP 与 EP：层间流水线与专家分片

PP：一个循环跑多个 microbatch

PP 不改 Scheduler 的职责，只换事件循环：event_loop_pp 维护 pp_loop_size 个 microbatch 槽位轮转，stage 之间用点对点通信传请求和激活（pp_proxy_tensors），发送是异步的、接收是同步的，避免 stage 间失步：

python/sglang/srt/managers/scheduler_pp_mixin.py — event_loop_pp（摘录，注释为译注）
pythondef event_loop_pp(self: Scheduler):
    self.init_pp_loop_state()
    while True:
        for mb_id in range(self.pp_loop_size):
            self.running_batch = self.running_mbs[mb_id]
            self.last_batch = self.last_mbs[mb_id]
            ...
            recv_reqs = self.ingest_requests()
            if not self.pp_group.is_last_rank:
                self._pp_commit_comm_work(self.send_req_work)
                # 异步把请求发往下一 stage
                self.send_req_work = self._pp_send_pyobj_to_next_stage(
                    recv_reqs, async_send=True,
                )
            plan = self.get_next_batch_to_run(...)
            self.mbs[mb_id] = plan.batch_to_run
            ...
            if cur_batch:
                pp_proxy_tensors = self._pp_recv_proxy_tensors()
            ...
            result, self.launch_event = self._pp_launch_batch(
                mb_id, cur_batch, pp_proxy_tensors, ...)
读懂这段： 每个 microbatch 槽位独立维护自己的 running_batch / last_batch，相当于把第 2 章的事件循环复制了 N 份交错执行——stage 0 在算 mb_2 时，stage 1 在算 mb_1，流水线才能填满。pp_async_batch_depth 让最后一 stage 在 GPU 计算期间先处理上一个 microbatch 的结果，削掉尾部的 rank 空转。

EP：专家怎么分、弹性扩缩怎么算

EP 把 MoE 的专家列表按 moe_ep_size 均分，每个 rank 持有一段专家；token 按路由结果发到持有目标专家的 rank。常规情况下「存储分片」和「运行时分片」是一回事，但弹性 EP（ep_join_mode == "scale"）把两者拆开——专家按初始规模落盘，运行时按当前规模计算归属，这样 EP 组扩容/缩容时不用重新分片权重：

python/sglang/srt/layers/moe/fused_moe_triton/layer.py — 专家的存储分片与运行时分片（摘录，注释为译注）
pythonif get_exec().moe.ep_join_mode == "scale":
    storage_ep_size = get_parallel().elastic_ep_initial_size
    assert storage_ep_size is not None
    self._expert_storage_rank = (
        get_parallel().ep_join_rank_offset + self.moe_ep_rank
    )
else:
    storage_ep_size = self.moe_ep_size
    self._expert_storage_rank = self.moe_ep_rank
assert self._num_global_routed % storage_ep_size == 0

读懂这段： 弹性模式下，本 rank 的专家按「初始规模 + rank 偏移」从存储定位，而路由按当前运行规模算——两套编号并存，是支撑在线扩缩的代价。这也解释了 _launch_scheduler_processes 里那个条件：use_dp_controller = dp_size > 1 or ep_join_mode == "scale"——弹性 EP 扩缩需要 controller 参与进程编排，不只是路由请求。

10.7对「自研引擎」的启示

要点 并行顺序别排错：单卡跑到瓶颈，先上 TP——它只需要列/行并行切权重加每层 1~2 次 allreduce，改动集中在 Linear 层；吞吐还不够再上 DP——SGLang 证明了 DP 路由层可以薄到几百行：一个 ZMQ 分发器加一份共享内存负载快照；一个独立部署的 router 进程（如 sgl-model-gateway）能替代它，还免去进程内耦合。EP 只在 MoE 模型上考虑；PP 仅当跨机带宽撑不起 TP 时——它的 microbatch 轮转和 stage 间握手引入的复杂度，是四个维度里最高的。下一步进入 第 11 章：HiCache 分层缓存。
