调度器：每一步该跑谁，内存不够先踢谁

第 2 章看了事件循环的主干，这一章拆其中最重的两步：get_next_batch_to_run 怎么从等待队列里挑请求组成 prefill 批（PrefillAdder 的预算制准入），以及 running batch 内存不够时怎么收缩（retract_decode 抢占）。

4.1一分钟版本

事件循环每转一圈，调度器要回答两个问题：

  • 问题一（admission）：waiting_queue 里哪些请求现在能进 prefill 批？答它的是 get_new_batch_prefill：先由 SchedulePolicy.calc_priority 给队列排序，再由 PrefillAdder 按预算逐个「收编」。
  • 问题二（survival）：running batch 里的 decode 请求下一步的 KV 还放得下吗？放不下就得 retract_decode——把部分请求的 KV 释放掉、扔回等待队列重排。

PrefillAdder 的答案形式是三本账：rem_total_tokens（整个生命周期的 KV 预算）、rem_chunk_tokens（这一步 prefill 能算多少 token）、rem_input_tokens（一轮 prefill 的总量上限）。每个候选请求先估「输入 + 预留输出 + 页对齐开销」，三本账任一超了就停。

4.3PrefillAdder 的三本账

PrefillAdder 接收的三个预算参数，来自 Scheduler 侧的不同配置：

账本来源含义
rem_total_tokensKV 池剩余 + 可淘汰缓存「收下这个请求直到它跑完」的全周期预算：输入 + 预估输出 + 页开销都要扣
rem_chunk_tokens--chunked-prefill-size这一轮 prefill 最多算多少 token；长请求被切成多轮
rem_input_tokens--max-prefill-tokens一轮 prefill 的 token 总量上限（不切分时的约束）

rem_total_tokens 不是构造时定死的数，而是每读一次都现算的属性——预算 = 物理空槽 + 前缀缓存里可淘汰的 token 减去已承诺的部分：

python/sglang/srt/managers/schedule_policy.py — PrefillAdder 构造与 rem_total_tokens（摘录，注释为译注）
pythonclass PrefillAdder:
    def __init__(self, page_size, tree_cache, token_to_kv_pool_allocator,
                 running_batch, new_token_ratio, rem_input_tokens,
                 rem_chunk_tokens, num_mixed_decode_tokens=0, ...):
        self.new_token_ratio = new_token_ratio
        self.rem_input_tokens = rem_input_tokens - num_mixed_decode_tokens
        self.rem_chunk_tokens = rem_chunk_tokens
        if self.rem_chunk_tokens is not None:
            self.rem_chunk_tokens -= num_mixed_decode_tokens
        self.rem_total_token_offset = num_mixed_decode_tokens
        ...
        # running batch 里的每个请求还欠多少 KV，先记成预算偏移
        if running_batch is not None:
            self.rem_total_token_offset += sum(
                self._get_running_request_total_token_offset(r)
                for r in running_batch.reqs
            )

    @property
    def rem_total_tokens(self):
        ...
        available_and_evictable = (
            self.token_to_kv_pool_allocator.available_size()
            + self.tree_cache.evictable_size()   # 前缀缓存可随时淘汰的部分
        )
        return available_and_evictable - self.rem_total_token_offset
树就这样接进了调度： evictable_size() 把第 3 章的基数树接进了调度：树里没被锁住的前缀 KV 平时占着显存，但在预算眼里它们是「随时可腾」的。所以一个请求可以放心地被收进来——真到不够用时先淘汰别人的缓存前缀。这是 RadixCache 和调度器真正的耦合点，比「复用」本身更深。混合 SWA/Mamba 模型各有变体分支（is_hybrid_swa、rem_mamba_slots），机制相同、账本分开。

收请求时的预算计算只有几行，但每行都是生产事故换来的：

python/sglang/srt/managers/schedule_policy.py — add_one_req 的预算判断（摘录，注释为译注）
python# 为页对齐开销预留 page_size：分页分配器可能每请求多消费一页

三个数字各管一件事： cand_extend_input_len 是「扣掉缓存命中后真正要算的输入」；max_new 是输出预算，注意有 CLIP_MAX_NEW_TOKENS（默认 4096）封顶——用户报 max_new_tokens=100000 时只按 4096 估，否则调度器保守到拒绝一切；+ self.page_size 是给分页分配器的余量，alloc_extend 对每个请求可能多花一页，不预留就会在分配那一步才 OOM。收下请求后，_update_prefill_budget 把这三笔从账上扣掉。
演进痕迹 _update_prefill_budget 的调用点里，记入输入的不是上面这个 cand_extend_input_len。普通请求传的是 req.extend_range.length，chunked 请求传的是本次切段的长度——都是「输入 token 数」的未对齐原值。_update_prefill_budget 内部对预算做页对齐（ceil_paged_tokens），但往指标账 log_input_tokens 上写的，是页对齐之前的那个数。源码在这里留了一句 TODO 和一个中间变量 raw_extend_input_len，把「按页预留」和「按真实 token 计数」两件事显式拆开：前者是内存安全需要，后者是给 metrics_reporter 算前缀缓存命中率用的——用对齐后的数字算命中率会被页对齐系统性地拉偏。一个函数里两种口径，读的时候别混。

预算扣账本身最近也动了：KV 预算从 PrefillAdder 内嵌的四个属性抽成了独立的 mem_cache/prefill_budget.py（PrefillBudget 基类 + SWA 变体子类），由分配器的 create_prefill_budget() 工厂创建，rem_total_tokens 等属性现在只是转发。另外新增了一条 compute_charge 口径——gfx95（SGLANG_EXACT_CHUNK_FILL）上 compute 预算（rem_chunk_tokens/rem_input_tokens）按未对齐 token 扣、KV 预算仍按页对齐扣，因为那块硬件的 kernel 按 BLOCK_SIZE_M 取整，短批代价翻倍，把取整的零头花满才划算。默认路径（非 gfx95）两者仍同一口径。

所有停止条件收敛在一个方法里，NO_TOKEN 和 OTHER 的分界也在这里：

python/sglang/srt/managers/schedule_policy.py — budget_state（摘录，注释为译注）
pythondef budget_state(self):
    no_token = not self.memory_budget.has_capacity()
    # mamba 槽位要单独判：rem_total_tokens 里可全量驱逐的部分
    # 盖不住一个 mamba 槽位，得看 mamba 可恢复的字节数
    if not no_token and self.rem_mamba_slots is not None:
        no_token = self.rem_mamba_slots <= 0
    if no_token:
        return AddReqResult.NO_TOKEN

    if self.rem_input_tokens <= 0:
        return AddReqResult.OTHER

    if self.dllm_config is not None:
        # DLLM（扩散语言模型）：按 dllm 专用配额判
        if self.rem_dllm_tokens <= 0:
            return AddReqResult.OTHER
    else:
        if self.rem_chunk_tokens is not None and self.rem_chunk_tokens <= 0:
            return AddReqResult.OTHER
    return AddReqResult.CONTINUE
KV 池真不够 → NO_TOKEN： KV 池真不够 → NO_TOKEN（外层置 batch_is_full，并且这一批收了几个就能跑几个）；只是本轮配额用完 → OTHER（本批照常发，下轮再收）。两种「停」后果不同，所以分成两个枚举值——AddReqResult.CONTINUE / NO_TOKEN / OTHER 就这三个。

「够不够」不是一把尺子：这个函数现在要依次过四道闸，每道闸量的是不同的东西。第一道是通用 KV：memory_budget.has_capacity()——KV 预算抽到 mem_cache/prefill_budget.py 后（PrefillBudget 基类 + SWA 变体），这里只剩一个委托调用；混合 SWA 的第三块配额（remaining_swa，滑动窗口层自己的余量）收在 SWAPrefillBudget.has_capacity() 的重写里，全注意力层剩余再多也补不上。第二道是 Mamba 槽位单独判——源码注释写得很清楚：rem_total_tokens 里「可全量驱逐」的那部分盖不住一个 mamba 槽位，因为槽位要的是 mamba 可恢复的字节数，两者是不同的池子。这是这套预算系统里最容易误读的一处：看到「总剩余 token 还很多」不等于「还能收请求」。最后一道按模型类型分岔：DLLM 用 rem_dllm_tokens，普通模型用 rem_chunk_tokens（chunked prefill 的配额）。

返回值只有三个是刻意的：调用方只需要区分「继续收」「空间没了」「本轮配额没了」，再多枚举值就要在每个 add_one_req 的调用点重复一遍分支。

4.4调度策略：cache-aware 排序

预算决定「能不能收」，策略决定「先收谁」。两族枚举写在文件头部：

python/sglang/srt/managers/schedule_policy.py — 策略枚举（摘录，注释为译注）
pythonclass CacheAwarePolicy(Enum):
    """Scheduling policies that are aware of the tree cache."""
    LPM = "lpm"                # 最长前缀匹配优先
    DFS_WEIGHT = "dfs-weight"  # 按基数树子树权重深度优先
    HRRN = "hrrn"              # 最高响应比优先，token 计龄
    SHORTEST_PREFILL_FIRST = "shortest-prefill-first"  # 最短待算 prefill 优先（实验）

class CacheAgnosticPolicy(Enum):
    """Scheduling policies that are not aware of the tree cache."""
    FCFS = "fcfs"    # 先来先服务（默认）
    LOF = "lof"      # 最长输出优先
    RANDOM = "random"
    ROUTING_KEY = "routing-key"  # 按 running batch 里 routing key 频次

默认策略其实是 FCFS（先来先服务，上面枚举里的注释也这么标）；--schedule-policy lpm 是要显式开的。开了 LPM 之后，命中前缀最长的请求排最前——命中的 KV 直接复用，prefill 便宜，先跑它总吞吐最高。为什么默认不开？LPM 的排序本身有开销（每次准入前重排队列 + 前缀匹配计算），而 prefix 命中率高度依赖负载形态：多轮对话、共享 system prompt 的服务受益明显，随机无关请求的流量排了也白排。这属于「按负载形态选型」的配置，不是无脑默认：

python/sglang/srt/managers/schedule_policy.py — LPM 排序与队长大时的降级（摘录，注释为译注）
python@staticmethod
def _sort_by_longest_prefix(waiting_queue, temporary_deprioritized):
    """Sorts the waiting queue based on the longest prefix match."""
    waiting_queue.sort(
        key=lambda r: (
            -r.num_matched_prefix_tokens
            if r.rid not in temporary_deprioritized
            else float("inf")
        )
    )

def _determine_active_policy(self, waiting_queue: List[Req]) -> Policy:
    if (
        self.policy
        in (
            CacheAwarePolicy.LPM,
            CacheAwarePolicy.HRRN,
        )
        and len(waiting_queue) > 128
    ):
        # 队列太长时关掉昂贵的前缀匹配和排序
        return CacheAgnosticPolicy.FCFS
    return self.policy
两处都值得停一下： 一是 temporary_deprioritized 服务「批内前缀缓存」：几个请求彼此共享一个前缀、但当前缓存里都没有时，只放行一个进 prefill，其余暂时降级排在队尾——等第一个算完，后面的人就能坐享它的 KV。二是队列超过 128 时 LPM 直接退化成 FCFS：LPM 要对每个等待请求做一次 match_prefix，树操作是 Python 代码，排队太长时排序本身就成了瓶颈。这是个能直接抄走的取舍：优化策略自己也要有预算。

注意这个函数的名字和位置：它不叫「选策略」，叫 _determine_active_policy——active 是关键词。用户配的 self.policy 不动，返回的只是「这一轮实际生效的策略」。waiting_queue_prefix_matched 也走这个函数来判断「要不要先做前缀匹配」——所以 128 这个阈值不只影响排序，还决定要不要付匹配的代价。这里只挑 LPM 和 HRRN 两个降级，不含 DFS_WEIGHT，所以它是唯一在长队列下仍做完整树排序的策略。

HRRN 是对 LPM 饥饿问题的修补——响应比 = 1 + 等待量 / 待算量，等得越久越容易出头：

python/sglang/srt/managers/schedule_policy.py — _sort_by_hrrn（摘录，注释为译注）
pythondef _key(r: Req):
    rid = r.rid
    if rid in temporary_deprioritized:
        return (float("inf"), rid)
    uncached = SchedulePolicy._uncached_len(r)   # 真正要 prefill 的 token 数
    if uncached <= 0:
        return (-float("inf"), rid)   # 无需 prefill，直接放行
    waited_tokens = max(0, processed_tokens - r.arrival_processed_tokens)
    ratio_delta = waited_tokens / uncached
    return (-ratio_delta, rid)

waiting_queue.sort(key=_key)
为什么用 token 计数不用秒表： 经典 HRRN 用秒表计时，这里用 token 计数——processed_tokens 是 Scheduler 累计的 prefill token 数，请求入队时打一个 arrival_processed_tokens 戳，两者相减就是「等价等待时间」。用 token 不用时钟，是为了多轮计量与确定性。分母是 uncached 长度而不是总输入长度：缓存命中多的请求理应便宜，不该因为 prompt 长就一直排后面。
困惑点 LPM 排序只动 waiting_queue 的顺序，那 prefix 匹配是在哪做的？在 calc_priority 里，排序前先跑 _compute_prefix_matches：对每个等待请求调用 match_prefix 并把命中长度写进 req.num_matched_prefix_tokens。也就是说排序的代价不只是 sort 本身，还有一遍树查询——这正是队列 128 阈值存在的原因。
演进痕迹 新出的 SHORTEST_PREFILL_FIRST（commit 65ef55e2a8，#40024，实验性）和上面几族思路都不同：它不追求「先做最划算的」（LPM），而是直接削减队头单请求的 prefill 块——让最短的请求尽快走完，压的是尾延迟。排序键是「未命中缓存的待算量」：max(1, len(origin_input_ids) + len(output_ids) - num_matched_prefix_tokens)，同样带 temporary_deprioritized 降级、按入队时间打破平局。真正值得看的是它对 chunked prefill 的配合：shortest_prefill_chunk_limit（schedule_policy.py:451）会在收 chunked 请求之前，先把等待队列里更短请求的页对齐开销预留出来（逐个累加，直到剩余预算只够一页），然后把队头这一块的配额压到 (budget - reserved) // page_size * page_size。这块配额经 scheduler.py:3914 写进 adder.chunked_req_limit，最后在 add_chunked_req 里以 _rem_tokens = min(_rem_tokens, self.chunked_req_limit) 生效——长请求的每一块都被压短，短请求插空的间隔就变小了。使用门槛有三条：要求 prefix caching（tree_cache 被禁用时构造直接报错）、当前只在 rem_chunk_tokens 存在且预算 ≥ 2 页时介入、每 128 次排序打一条 info 日志（队列长度 + 队头待算量），方便验证它确实在起作用。

4.5chunked prefill：长请求怎么切

没有 chunked prefill 时，一个 30k token 的 prompt 会独占 GPU 一整轮，同期的所有 decode 请求 ITL 全部爆炸。SGLang 的处理：把长 prefill 按 rem_chunk_tokens 切成若干步，每步只算一段，切点请求记在 chunked_req 字段上。已算完的部分不浪费——每切一段就 stash 进基数树，下一段可以匹配自己前面那部分：

python/sglang/srt/managers/schedule_policy.py — add_chunked_req（摘录，注释为译注）
pythoncand_extend_input_len = len(req.full_untruncated_fill_ids) - len(
    req.prefix_indices
)
truncated = cand_extend_input_len > _rem_tokens
new_len = min(cand_extend_input_len, _rem_tokens)
req.set_extend_range(len(req.prefix_indices), len(req.prefix_indices) + new_len)
self.can_run_list.append(req)
self._update_prefill_budget(
    0,
    req.extend_range.length,
    (
        min(req.sampling_params.max_new_tokens, CLIP_MAX_NEW_TOKENS)
        if not truncated
        else 0
    ),
    req.retracted_stain,
    ...,
)

# Return if chunked prefill not finished
return req if truncated else None
返回值就是续传标记： 还没算完返回 req 本身，Scheduler 把它存进 self.chunked_req；最后一段算完返回 None。注意一个反直觉的细节：中途某段收不了新请求时也必须把 chunked_req 加进 can_run_list——它上一段的 KV 已经占着内存，不继续算就泄漏了（源码里 _rem_tokens <= 0 时硬性换成 rem_chunk_tokens，注释原话是 "otherwise, it will cause a memory leak"）。这是预算逻辑里少见的「宁可超预算也不能漏请求」的位置。

切段的落账在事件循环侧：get_next_batch_to_run 每轮先调用 stash_chunked_request(self.chunked_req)，其实现只有一行——maybe_cache_unfinished_req(req, self.tree_cache, chunked=True)，把已完成段的 KV 插入基数树。所以长请求的第二段开始，prefix_indices 会命中自己（tree_cache.evictable_size 随之变化，三本账自动更新）。

4.6抢占：decode 内存不够时收缩

prefill 收得再准，decode 是长跑：请求越跑 KV 越长，总有可能把池子跑穿。每轮 update_running_batch 先做体检，体检不过就抢占：

python/sglang/srt/managers/scheduler.py — update_running_batch（摘录，注释为译注）

    ...
    for req in retracted_reqs:
        self._add_request_to_queue(req, is_retracted=True)
else:
    self.new_token_ratio_tracker.decay_step()
体检问的是一步之后： check_decode_mem 问的是「所有在跑请求再各解码一步，KV 池放不放得下」，答案由分配器给出（第 5 章）。放不下 → 抢占；放得下 → 新 token 估计比率衰减一档。

retract_decode 的主循环——按「最不值得保留」的顺序一个个踢，直到体检通过：

谁先被踢： 由 _get_decode_retraction_order 决定，默认排序键是 (len(output_ids), -len(origin_input_ids)) 取反序——已生成 token 多的先踢（沉没成本大、留着占的 KV 也多），输入长的次之（踢掉省得多）。被踢的请求做两件事：KV 释放回池（不进基数树，因为要的是立刻可用的空间），并把已生成的 KV 备份到主机内存，重新入队后用备份续跑。主机备份池也满时没有第三层兜底，只能 FINISH_ABORT 返回 500——代码里连注释都写明 "the request cannot resume"。

抢占之后还有一段恢复动力学：new_token_ratio 是 PrefillAdder 估「每个 decode 请求每步要多少 KV」的系数。正常时它从初始值按固定步长衰减到下限，再由每次抢占按剩余请求的实际进度重估并抬高，之后重新衰减。初始值不是拍脑袋的 1.0，而是 SGLANG_INIT_NEW_TOKEN_RATIO（默认 0.7）乘上 schedule_conservativeness 再和 1.0 取 min——也就是说调度器一开始就假设「估不准输出长度」，宁可少估。效果是：刚抢占完的几轮里 prefill 准入变保守，给 decode 让路，然后逐渐放松。

4.7对「自研引擎」的启示

要点 预算制准入优先于 OOM 反应式抢占。SGLang 两套都有，但 prefill 侧的账（输入 + 输出估计 + page_size 余量）让绝大多数情况根本走不到 retraction。自己实现时按这个顺序补齐：先搭三本账的最简版（只算 rem_total），再加 CLIP 上限，防止单个 max_new_tokens 巨大的请求锁死准入，cache-aware 排序可以最后加，加的时候记得给排序本身留预算（128 阈值的做法）。retract_decode 只做最后一道防线，并且要有「至少保留一个请求」的底线——全部踢光的调度器等于把服务变成抽奖。下一步进入 第 5 章：内存池与显存预算。
