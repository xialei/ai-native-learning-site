内存池与显存预算：token 槽位怎么发、KV 池怎么定大小

调度器每一步做的决定，最终都落在「这一批 token 占哪些 KV 槽位」。这一章拆开三个对象：请求目录（ReqToTokenPool）、KV 本体（TokenToKVPool）、发号器（分配器），以及启动时决定 KV 池大小的一次显存 profiling。

5.1一分钟版本

一张推理卡的显存分成三块：模型权重（启动时加载）、KV cache 池（启动时按 profiling 结果一次性建好，运行期大小不变）、激活值余量（每步前向临时用）。SGLang 用 mem_fraction_static 控制前两块的总量，这一参数的语义在 5.6 节展开。

KV 池一侧有三个对象，各管一件事：

  • ReqToTokenPool：一张 (size+1, max_context_len) 的 int32 表。第 r 行第 j 列写的是「第 r 个请求的第 j 个 token 存在 KV 池的哪个槽位」。它是目录，不是数据。
  • TokenToKVPool（MHA 版 / MLA 版）：真正的张量。每层一对 k_buffer / v_buffer，按下标即槽位号存取。
  • 分配器（TokenToKVPoolAllocator）：维护空闲槽位/空闲页，对外发号（out_cache_loc）。分页版以页为单位，token 版以单个 token 为单位。

运行时的数据流：调度阶段算出 out_cache_loc（本批 token 的槽位号）→ 写进 req_to_token 对应行 → 前向时注意力后端按行取出 K/V 参与计算。第 3 章的 RadixCache 存的也是这套槽位号。

5.3ReqToTokenPool：请求到槽位的目录

这张表是一个 (size+1, max_context_len) 的 int32 张量。行数是最大并发请求数（加一行填充），列数是最大上下文长度。注意 int32——槽位号不会超过池容量，用 32 位正好把每步 gather 索引的传输量减半：

python/sglang/srt/mem_cache/memory_pool.py — ReqToTokenPool.__init__（摘录，注释为原文）
pythonself.size = size

    self.req_to_token = torch.zeros(

读懂这段： 两个细节。第一行是填充行：CUDA Graph 回放时，padding 出来的假请求 req_pool_indices 全是 0，让它们的读写都落在第 0 行，避免越界或污染真请求。free_slots 从 1 开始也是同一个原因。

分配行本身是个简化的空闲链表，但有三处细节值得看：

python/sglang/srt/mem_cache/memory_pool.py — alloc_rows（摘录，注释为译注）
pythondef alloc_rows(self, need_size: int) -> Optional[List[int]]:
    if need_size > len(self.free_slots):
        return None
    if need_size == 0:
        # 单独处理：free_slots[-0:] 是整个列表，不是空列表
        return []
    # 从尾部弹出：O(need_size)；从头部 pop 是 O(len(free_slots))
    select_index = self.free_slots[-need_size:]
    del self.free_slots[-need_size:]
    self.req_generation[select_index] += 1
    if self._on_alloc_rows is not None:
        self._on_alloc_rows(select_index)
    return select_index
读懂这段： free_slots[-0:] 这个特判值得停下来看一眼：Python 里 lst[-0:] 等价于 lst[0:]，即整个列表——「分配 0 行」若不走这个分支会把所有空闲行都发出去。另外每次分配都会把该行的 req_generation 加一：行会被反复复用，重叠调度等异步路径里拿旧行号来写的人，可以凭代数判断自己是不是拿着过期引用。

5.4TokenToKVPool：每层一对 k/v 张量

MHA 版池子按层各建一对 buffer。第一维是 槽位号，长度是 size + page_size——多出的一个填充页，接住 CUDA Graph padding token 的哑写入。三种物理布局由环境和后端决定：

困惑点 MLA（DeepSeek 系列）的池子为什么只有一个 kv_buffer？因为 MLA 把 K/V 压进一个隐空间向量：每 token 每层只存 kv_lora_rank + qk_rope_head_dim 维（解耦 RoPE 部分单独保留），attention 内部再做吸收变换。所以 MLATokenToKVPool 的 buffer 形状是 (size + page_size, 1, kv_lora_rank + qk_rope_head_dim)，比 MHA 的两份 per-head 张量省一个数量级的显存。池子和注意力后端是配套设计的（见第 7 章）。
演进痕迹 池子家族里还有一排刚建好、但还没有生产入口的成员：mem_cache/page_interleave_pool.py 与 allocator/page_interleave.py 实现了「KV 按 shard 组分片存储」——把 N 个连续物理页组成一个逻辑页、每组内各 rank 存自己那一份（GQA/MHA 沿注意力 CP 组、MLA 沿注意力 TP 组，因为这两处 KV 本来就是复制的，直接条带化就能省显存）。树、分配器、req_to_token、调度预算全都在逻辑槽位上看世界，只有池子底层做逻辑页→本 rank 物理页的双射换算；attention 侧经 kv_shard_hooks.py 的 get_kv_shard_pool 探测接线（目前只挂了 flashattention 与 trtllm_mla 两个后端）。不过全仓库还没有任何构造调用点——这是条预留的轨道，读代码时知道有这层设计即可，别当成已启用的路径。

5.5分页分配器：以页为单位发号

调度器拿到的不是零散槽位，而是 out_cache_loc 槽位数组；分页版分配器内部只维护一个 free_pages 张量（空闲页号）。alloc_for_extend（mem_cache/allocation.py:344）把两件事接起来：先从 req_to_token_pool 发请求行，再按 page_size 决定走 token 版还是分页版分配。

python/sglang/srt/mem_cache/allocator/paged.py — alloc_extend / alloc_decode（摘录，注释为译注）

    self,
    prefix_lens: torch.Tensor, prefix_lens_cpu: torch.Tensor,
    seq_lens: torch.Tensor, seq_lens_cpu: torch.Tensor,
    last_loc: torch.Tensor,
    extend_num_tokens: int,
    num_new_pages: int = None,
):
    bs = len(prefix_lens)
    if extend_num_tokens // self.page_size + bs + 1 > len(self.free_pages):
        self.merge_and_sort_free()

    out_indices = torch.empty((extend_num_tokens,), dtype=torch.int64, device=...)

    # 一次 Triton 启动算出整批 token 的槽位号
    alloc_extend_kernel[(bs,)](
        prefix_lens, seq_lens, last_loc, self.free_pages,
        out_indices, next_power_of_2(bs), self.page_size,
    )

    # 本批实际消耗的新页数；不够就返回 None（触发上层淘汰或回退）
    if num_new_pages is None:
        num_new_pages = get_num_new_pages(
            seq_lens=seq_lens_cpu, page_size=self.page_size,
            prefix_lens=prefix_lens_cpu,
        )
    if num_new_pages > len(self.free_pages):
        return None
    self.free_pages = self.free_pages[num_new_pages:]
    return out_indices
读懂这段： alloc_extend_kernel（sglang/kernels/ops/memory/allocator.py:116）每个请求一个 program，把槽位计算拆成三段：① 填满上一个未满页（接续 last_loc）；② 申请若干整页（从 free_pages 取页号乘 page_size 加页内偏移）；③ 开新页放尾巴。全部向量化，一个 batch 一次 kernel，不再有 Python 循环。纯 torch 的 alloc_extend_naive 参考实现留在调用方文件里（mem_cache/allocator/paged.py:40），两版并存——加向量化内核时的对照物，读代码时值得互相对一遍。

5.6显存预算：mem_fraction_static 与启动 profiling

mem_fraction_static 的语义：占启动时总显存的比例，划给「静态区」——权重加 KV 池。剩下的 1 - mem_fraction_static 留给运行时的激活、CUDA Graph 缓冲等。KV 池到底能建多大，不是拿一个写死的 GB 数，而是权重加载完之后现场量出来的：

python/sglang/srt/mem_cache/kv_cache_configurator.py — _profile_available_bytes（摘录，注释为译注）
pythondef _profile_available_bytes(self, pre_model_load_memory: int) -> int:
    # 权重加载的临时对象此时可能仍被引用，empty_cache() 收不回来；
    # 不先 gc 的话空闲量被低估，KV 池会明显偏小
    gc.collect()
    available_gpu_memory = get_available_gpu_memory(...)

    # 运行时余量 = 启动总量 × (1 - mem_fraction_static)
    slack_gb = pre_model_load_memory * (1 - get_schedule().mem_fraction_static)
    ...
    mm_reservation_gb = mm_runtime_reservation_gb(...)  # 多模态预留
    rest_memory = available_gpu_memory - slack_gb - mm_reservation_gb

    # 权重（含投机解码的 draft）可能已经超出静态预算
    if rest_memory <= 0:
        minimum_mem_fraction_static = (
            1 - available_gpu_memory / pre_model_load_memory
        )
        suggested_mem_fraction_static = (
            math.ceil(minimum_mem_fraction_static * 1000) / 1000
        )
        raise ValueError(
            f"Loaded weights leave no GPU memory for the KV cache under "
            f"--mem-fraction-static={...}. Raise --mem-fraction-static above "
            f"{suggested_mem_fraction_static:.3f} ..."
        )

    return int(rest_memory * (1 << 30))  # 字节
读懂这段： 三个要点。其一，权重先加载、再量显存，所以权重已经占掉的部分自动被计入——KV 池大小是「总量减去权重再减去余量」的残差。其二，slack_gb 按「启动时总量」的固定比例扣，而不是按当前空闲量扣，保证运行时余量不随权重变大而缩水。其三，配置得太小、权重就把预算吃光时，直接抛 ValueError 并给出可行的最小值，把「调 mem-fraction」这个用户动作变成一条可执行的错误信息。
困惑点 为什么先 gc.collect()？注释里写得很直白：weight loading 的中间张量此时可能还有引用，empty_cache() 对被引用的块无能为力；不先收集，测得的空闲显存偏小，KV 池可能被算小几个数量级，而显存其实闲着。这是启动路径上少见的「先 gc 再测量」写法，属于用 profiling 结果换稳定性的例子。

5.7对自研引擎的启示

要点 自研引擎分三步走：v1 用 token 粒度的空闲链表（一个 int64 张量切首尾就够）+ 每层 k/v 大张量，几十行代码能跑；要上连续批处理的生产负载，再升级成页粒度 + 向量化分配 kernel（避免每步几千次小分配）；KV 池大小任何时候都从启动 profiling 推导，别写死 GB 数——不同卡、不同模型、不同上下文长度下写死的数字都会错。下一步进入 第 6 章：ModelRunner 与 CUDA Graph。
