请求全生命周期：一次 /generate 走到哪几步

这一章跟着一条请求走完全程：HTTP 进程收请求并分词，Scheduler 子进程把它排进 batch，GPU 前向产出 token，Detokenizer 反分词，最后以 SSE 流式帧回到客户端。四个泳道，五次跨进程消息。

2.1一分钟版本

一次 POST /generate 在 SGLang 里经过这些站：

  1. http_server.py 的 generate_request 收到 GenerateReqInput。若是流式请求，立刻挂一个 SSE 的 StreamingResponse，并注册后台 abort 任务。
  2. TokenizerManager 分词，得到 TokenizedGenerateReqInput，经 ZMQ 发给 Scheduler。
  3. Scheduler 的 handle_generate_request 把它包成 Req 放进 waiting_queue，事件循环在下一拍把它（可能与其他请求一起）装进 ScheduleBatch，转成 ForwardBatch 喂给 TpModelWorker。
  4. ModelRunner 执行 GPU 前向与采样，吐出新 token id。
  5. DetokenizerManager 收到 BatchTokenIDOutput，增量反分词成文本，以 BatchStrOutput 发回主进程。
  6. TokenizerManager 的 _handle_batch_output 按 rid 找到 ReqState，把输出塞进 out_list 并 set event；等待中的 _stream_one_response 被唤醒，产出 SSE 帧。

注意一个不对称：去程和回程走的通道不同。去程是 HTTP→Scheduler（token id），回程是 Scheduler→Detokenizer→TokenizerManager→HTTP（token id 先、文本后）。

2.3入口：/generate 的 SSE 包装

路由函数本身不做分词，只做两件事：把 async 生成器包装成 SSE 帧，以及挂一个断连后自动 abort 的后台任务：

python/sglang/srt/entrypoints/http_server.py — generate_request（摘录，注释为译注）
pythonasync def generate_request(obj: GenerateReqInput, request: Request):
    # 可选：用 HTTP header 覆盖请求字段（需 env 开关）
    if envs.SGLANG_ENABLE_REQUEST_HEADER_OVERRIDES.get():
        apply_header_overrides(obj, request.headers)

    if obj.stream:
        async def stream_results() -> AsyncIterator[bytes]:
            try:
                async for out in _global_state.tokenizer_manager.generate_request(
                    obj, request
                ):
                    yield b"data: " + dumps_json(out) + b"\n\n"
            except ValueError as e:
                # 客户端断连也会从这冒出来：这是客户端取消，不是服务端错误
                if request is not None and await request.is_disconnected():
                    logger.info(f"[http_server] Client disconnected: {e}")
                    return  # 请求已在上游 abort，这里静默收尾，不吐 400
                out = {"error": {"message": str(e), "type": "invalid_request_error", ...}}
                logger.error(f"[http_server] Error: {e}")
                yield b"data: " + dumps_json(out) + b"\n\n"
            # [DONE] 挪到 try/except 之外：出错时也要正常收尾
            yield b"data: [DONE]\n\n"

        return StreamingResponse(
            stream_results(),
            media_type="text/event-stream",
            background=_global_state.tokenizer_manager.create_abort_task(obj),
        )
    else:
        try:
            ret = await _global_state.tokenizer_manager.generate_request(
                obj, request
            ).__anext__()
            return orjson_response(ret)
        except ValueError as e:
            logger.error(f"[http_server] Error: {e}")
            return _create_error_response(e)
读懂这段： 流式与否在 HTTP 层就分叉：流式走 StreamingResponse，每个 chunk 是 data: {json}\n\n，结束发 data: [DONE]；非流式只取异步生成器的第一项（也就是最终结果）。create_abort_task 是关键细节：客户端断连时 FastAPI 不会自动通知引擎，SGLang 用后台任务在响应结束后兜底调用 abort_request，把 GPU 上还在跑的请求收掉——断连不是错误，而是正常路径。
断连处理是后加的： 上面流式分支里的 try/except ValueError 值得单独看。在早先的写法里，客户端断连会以 ValueError 的形式从异步生成器里冒出来，被当作普通错误转成一个 SSE 错误帧吐回去——日志里留下一串 Error，看着像服务端出问题，实际只是用户关掉了页面。现在多了一次 request.is_disconnected() 判断把这种情况分流出来：走 logger.info 然后静默 return，请求早已在上游被 abort，这里不需要再做什么。[DONE] 也从 try 块里挪了出来——原来只要中间抛错就永远发不出结束标记，SSE 客户端会一直挂着等。非流式分支同理套了一层 try/except，转成规规矩矩的 HTTP 错误响应而不是 500。这两处的形状都是「异常路径要显式收尾」，不是新增功能。

2.4TokenizerManager：注册状态、分词、发送、等待

generate_request 是一个很长的 async 生成器，主体是四步。先注册一个 ReqState（含 asyncio.Event 和 out_list），再分词：

python/sglang/srt/managers/tokenizer_manager.py — _tokenize_one_request（摘录，注释为译注）
pythonasync def _tokenize_one_request(self, obj):
    """Tokenize one request."""
    input_text = obj.text
    if obj.input_ids is not None:
        input_ids = obj.input_ids          # 调用方已给 token id，跳过分词
    else:
        input_ids, token_type_ids = await self._tokenize_texts(
            input_text, is_cross_encoder_request
        )

分词完成后经 _send_one_request 发给 Scheduler——注意这里对消息做了一系列「出发前的最后加工」（多模态准备、时间戳、pickle 字段打包），然后才 ZMQ 发出：

python/sglang/srt/managers/tokenizer_manager.py — _send_one_request（摘录，注释为译注）
pythonasync def _send_one_request(self, tokenized_obj):
    tokenized_obj.time_stats.set_api_server_dispatch_time()
    tokenized_obj.wrap_pickle_fields()
    self._dispatch_to_scheduler(tokenized_obj)
    self._mark_state_dispatched(tokenized_obj.rid)

之后这个协程就挂在 _stream_one_response 上等事件。ReqState 是整条回程的枢纽：

python/sglang/srt/managers/tokenizer_manager.py — ReqState（摘录，注释为译注）
pythonclass ReqState:
    """Store the state a request."""
    out_list: List[Dict[Any, Any]]   # 收到的每个输出步
    finished: bool
    event: asyncio.Event            # 有新输出时被 set
    obj: Union[GenerateReqInput, EmbeddingReqInput]

    dispatched: bool = False        # 是否已送达 Scheduler
    abort_sent: bool = False        # 防止重复发 abort
    last_output_offset: int = 0    # 流式增量切片用

_stream_one_response 的消费模式是「等 event → 一次性清空 out_list → 唤醒生产者」：

python/sglang/srt/managers/tokenizer_manager.py — _stream_one_response（摘录，注释为译注）
pythonis_stream = getattr(obj, "stream", False)
while True:
    try:
        await asyncio.wait_for(state.event.wait(),
                              timeout=_REQUEST_STATE_WAIT_TIMEOUT)
    except asyncio.TimeoutError:
        # 断连检查放在超时分支里：等不到输出才有必要问一句
        if request is not None and not obj.background \
                and await request.is_disconnected():
            self.abort_request(obj.rid)
            # 用异常拆掉整个调用栈和 asyncio task
            raise ValueError(f"Request is disconnected ... (type 1)")
        continue

    # 原子清空：拿走全部 pending 输出再清 event
    out_list = state.out_list
    state.out_list = []
    finished = state.finished
    state.event.clear()

    # 增量流式：多个 pending chunk 要合并，否则会丢 token id
    if incremental_stream and len(out_list) > 1:
        out = self._coalesce_streaming_chunks(out_list, obj.rid, ...)
    else:
        out = out_list[-1]

    # 中间块的 text 是 None（免得每步重建整串文本变成 O(n²)），
    # 到这里才补上全量文本
    if is_stream and not incremental_stream and out.get("text") is None:
        out["text"] = state.get_text()

    if out.get("beam_results") and not finished:
        continue      # beam 的中间结果先不吐，等收敛

    if is_stream:
        yield out          # 交给 http 层打 SSE 帧
    if finished:
        break
读懂这段： 这是经典的「event + drain」模式：生产者（_handle_batch_output）只往 out_list 追加并 set 事件，不直接 yield；消费者一次性取走全部积压输出。好处是一个 batch 的多个输出步不会丢帧，也避免了每个 token 一次协程切换。

四处后来才长出来的细节，每一处背后都有一个坑：
① 断连检查在 except TimeoutError 里（而不是循环开头）。这个位置很讲究：等到了输出就说明客户端还在收，没必要付一次 is_disconnected() 的代价；wait_for 超时说明一段时间没有任何输出——可能是请求卡在等待队列里，那正是客户端最可能已经关页面的时候。所以只在超时时问一次，问完没断就 continue 接着等。not obj.background 也一并排除了后台请求（没有客户端可断）。
② 抛 ValueError 是当「拆栈工具」用的，不是表达业务错误——源码注释写着 Use exception to kill the whole call stack and asyncio task。断连的请求已经在上游 abort_request 处理完了，这里只需要让这个协程彻底停掉，异常是最省事的做法。所以看到这个 ValueError 不要当成「出错了」，它就是这条路径的正常终止方式。
③ _coalesce_streaming_chunks 是增量流式独有的：增量模式下每个 chunk 是 delta，攒批窗口里积压多个 chunk 时不能只取最后一个（会丢 token），必须合并；非增量模式取 out_list[-1] 就够，因为每块都是全量快照。
④ out["text"] = state.get_text() 是一笔性能债的偿还：_handle_batch_output 给中间块写的是 "text": None，源码注释解释了原因——每步都重建整串文本会让总代价变成 O(n²)。但 HTTP 层需要一个完整的 text 字段，所以在这里（每次 drain 后）只补一次。beam_results 那个 continue 同理：束搜索的中间结果不是可用的最终答案，跳过。

2.5Scheduler 侧：入队与事件循环

消息到达 Scheduler 后，由 TypeBasedDispatcher 路由到 handle_generate_request。它把 TokenizedGenerateReqInput 转成运行时对象 Req 并放进等待队列：

python/sglang/srt/managers/scheduler.py — handle_generate_request（摘录，注释为译注）
pythondef handle_generate_request(self, recv_req: TokenizedGenerateReqInput, ...):
    # 普通请求或 radix-native 会话请求
    req = Req(
        recv_req.rid,
        recv_req.input_text,
        recv_req.input_ids,
        recv_req.sampling_params,
        return_logprob=recv_req.return_logprob,
        stream=recv_req.stream,
        lora_id=recv_req.lora_id,
        ...
    )
    self._add_request_to_queue(req)     # 进 waiting_queue
中间省略的是一道校验关卡： 上面把构造和入队并排摆着，是为了看清「TokenizedGenerateReqInput → Req → 队列」这条主干。实际源码里这两行之间夹着十几处提前返回的错误分支——会话不存在、多模态输入错、投机算法（dflash / uno）的请求校验、return_sampling_mask 的准入检查（第 8 章）等等。这些分支的形状几乎一样：set_finish_with_abort 挂错误 → init_req_max_new_tokens → _add_request_to_queue ——失败的请求照样入队，只是带了一个已完成的 abort 状态，由事件循环在下一拍把它当作已完成请求把错误吐回客户端。所以「入队」不等于「要跑模型」。

之后完全由事件循环接管。event_loop_normal（非 overlap 版本，最容易读）主干是四步一循环——收请求、挑批次、跑前向、收尾，但入口附近的几条守卫让它比「四步」读起来更长：

python/sglang/srt/managers/scheduler.py — event_loop_normal（摘录，注释为译注）
pythondef event_loop_normal(self):
    """A normal scheduler loop."""
    while True:
        if self.gracefully_exit:
            break

        self.ingest_requests()                # 1) 从 ZMQ 收请求入队
        if self._engine_paused:
            self._record_scheduler_state_for_paused_engine()
            continue

        plan = self.get_next_batch_to_run(    # 2) 决定这一步跑什么
            running_batch=self.running_batch, last_batch=self.last_batch
        )
        self.running_batch = plan.running_batch
        batch = plan.batch_to_run
        self.cur_batch_for_debug = batch

        if batch:
            result = self.run_batch(batch)            # 3) GPU 前向
            self.process_batch_result(batch, result)  # 4) 发输出、更新状态
        else:
            # 空闲：做自检并重置部分状态
            self._sched_idled = True
            self.on_idle()

        self.last_batch = batch
        if envs.SGLANG_ENABLE_STRICT_MEM_CHECK_DURING_BUSY.get():
            self.invariant_checker.self_check_during_busy()
读懂这段： 这个循环是整本书的主干，后面每章都挂在它上面：第 3 章（RadixCache）和第 4 章（调度策略）藏在 get_next_batch_to_run 里；第 5 章（内存池）在 prepare_for_extend 里被调用；第 6 章（ModelRunner）就是 run_batch 的下潜；第 8 章（采样）发生在 run_batch 尾部。真正默认启用的是 event_loop_overlap——CPU 处理上一批结果与 GPU 跑下一批并行，第 2.6 节先给出直觉。

三条容易忽略的守卫：① _engine_paused 时不再挑批次，只记录状态然后 continue——引擎被外部（如权重更新、RL 侧同步）暂停时，不能继续消费 KV 池里的空间。② self.cur_batch_for_debug = batch 是给调试接口（/get_scheduler_snapshot 一类）留的引用，注意它持有 batch 对象，这也是排障时能看到「上一批是谁」的原因。③ 循环末尾的 self_check_during_busy 由环境变量控制，默认关闭——它是内存不变量的开发期断言，跑在热路径上，只在怀疑内存泄漏时打开。
困惑点 为什么 get_next_batch_to_run 返回一个 plan（running_batch + batch_to_run），而不是直接一个 batch？因为「挑选」和「执行」共享状态：这次挑选可能把 prefill batch 合并进 running_batch、可能产生 chunked_req。把两个 batch 一起返回，避免函数内部用 self 暗改状态——这是 overlap 化重构留下的接口痕迹，旧签名只返回一个 batch。

2.6输出回流：token id → 文本 → SSE

前向与采样结束后，Scheduler 侧把整个 batch 的输出打包成一条 BatchTokenIDOutput。它按请求携带增量 token、反分词上下文和计量信息（精简后的字段）：

python/sglang/srt/managers/io_struct.py — BatchTokenIDOutput（字段摘录）
pythonclass BatchTokenIDOutput(BaseBatchReq, kw_only=True):
    finished_reasons: List[Optional[FinishReasonDict]]
    decoded_texts: List[str]          # 增量反分词需要的上下文
    decode_ids: List[array]           # 本步新增 token id
    read_offsets: List[int]
    output_ids: Optional[List[array]]  # 仅 --skip-tokenizer-init 时用
    # 反分词配置（原本散在别处，集中成一组）
    skip_special_tokens: List[bool]
    spaces_between_special_tokens: List[bool]
    no_stop_trim: List[bool]

    prompt_tokens: List[int]
    reasoning_tokens: List[int]         # 推理模型单独计数的 thinking token
    completion_tokens: List[int]
    cached_tokens: List[int]          # RadixCache 命中数（第 3 章）

这条消息先到 DetokenizerManager。它维护每个请求的增量解码状态，把 token id 变成文本后打包为 BatchStrOutput（核心字段就是 output_strs），发回主进程。主进程的 handle_loop 收到后按 rid 分发：

python/sglang/srt/managers/tokenizer_manager.py — handle_loop 与 _handle_batch_output（摘录，注释为译注）
pythonasync def handle_loop(self):
    while True:
        recv_obj = await async_sock_recv(self.recv_from_detokenizer)
        if isinstance(recv_obj, (BatchStrOutput, ..., BatchTokenIDOutput)):
            await self._handle_batch_output(recv_obj)
        else:
            self._result_dispatcher(recv_obj)

async def _handle_batch_output(self, recv_obj):
    for i, rid in enumerate(recv_obj.rids):
        state = self.rid_to_state.get(rid, None)
        ...
        state.out_list.append(out)   # 生产者只追加
        pending_notify[rid] = state      # 注意 key 是 rid，不是 state

    # 攒够 batch_notify_size 个再统一 set 事件，唤醒 _stream_one_response
    if len(pending_notify) >= batch_notify_size:
        for s in pending_notify.values():
            s.event.set()
        pending_notify = {}
        await asyncio.sleep(0)    # 让出控制权给等待中的协程
读懂这段： 两种输出结构各走一段通道：BatchTokenIDOutput 是 Scheduler → Detokenizer 的「id 通道」；BatchStrOutput 是 Detokenizer → TokenizerManager 的「文本通道」。--skip-tokenizer-init 模式下 Detokenizer 被跳过，id 直接回主进程由客户端自己解码。abort 也是一条消息：abort_request 构造 AbortReq 经 ZMQ 发给 Scheduler，Scheduler 在收请求阶段处理并释放 KV——客户端断连、超时、显式取消最终都收敛到这一条路径。

为什么是「攒批唤醒」而不是「来一条 set 一条」：每个请求都有一个 asyncio.Event，消费侧 _stream_one_response 在 event 上等待。_handle_batch_output 是生产侧，它把本批要通知的请求放进 pending_notify 字典，攒够 batch_notify_size 个再一次性 set 全部、清空、然后 await asyncio.sleep(0) 让出去。逐条 set 会让事件循环在「唤醒—切换—再切回来」之间反复抖动，攒批把 N 次上下文切换压成一次，代价是最多等 batch_notify_size 个请求——这是吞吐与首 token 延迟之间一个显式的旋钮。

字典的 key 用 rid 而不是 state：同一请求可能在攒批窗口内被追加多条输出，用 state 当 key 也能去重，但那要求 state 可哈希且身份稳定；用 rid 更直白，且万一同一个 state 被两个 rid 引用（不该发生，但排障时需要能看出来），用 rid 不会把它悄悄吃掉。值仍然是 state，因为 set 事件要用它的 event。

2.7对自研引擎的启示

要点 这一章有三个可以照抄的结构。① id 通道与文本通道分离：调度层只传 token id，反分词独立成进程/任务，流式协议因此不受调度影响；② event + drain 的流式缓冲：生产者 append + set event，消费者一次性清空，天然支持 batch 化且不丢帧；③ abort 当成一等消息：客户端断连不是异常路径而是常规消息，注册 rid 状态时就把 abort 发送/去重（abort_sent）设计进去。overlap 事件循环的细节见 第 4 章；下一步先看回程里那个 cached_tokens 从哪来：第 3 章：RadixCache 前缀缓存。
